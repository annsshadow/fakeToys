
## Special Usage Model of the ACPI Control Method Lid Device


:Copyright: |copy| 2016, Intel Corporation

:Author: Lv Zheng <lv.zheng@intel.com>

## Abstract

带有盖子的平台通过控制方法盖设备（control method lid device）向 OSPM 传达盖子状态（开/关）。
为此，AML 表会在盖子状态发生变化时发出 Notify(lid_device, 0x80) 来通知 OSPM。
必须为该盖设备实现 _LID 控制方法，以将盖子的“当前”状态报告为“已打开”或“已关闭”。

对于大多数平台，_LID 方法和盖子通知都是可靠的。但也存在例外。
为了适配这些存在缺陷的异常平台，需要考虑到一些特殊的限制与例外情况。
本文档描述了 Linux ACPI 盖设备驱动的限制与例外。


## Restrictions of the returning value of the _LID control method


_LID 控制方法被描述为返回盖子的“当前”状态。
然而“当前”一词存在歧义，某些有缺陷的 AML 表返回的是上一次盖子通知时的状态，
而非上一次 _LID 求值时的盖子状态。在运行时对 _LID 控制方法求值时不会有区别，
问题在于它的初始返回值。当 AML 表以缓存值实现该控制方法时，初始返回值很可能不可靠。
有些平台总是将初始盖子状态返回为“已关闭”。

## Restrictions of the lid state change notifications


某些有缺陷的 AML 表在盖子设备状态变为“已打开”时从不发出通知。
因此“已打开”通知无法保证。但可以保证 AML 表在盖子状态变为“已关闭”时总会发出“已关闭”通知。
“已关闭”通知通常用于在 Windows 上触发一些系统省电操作。由于其经过充分测试，所有 AML 表均可靠。

## Exceptions for the userspace users of the ACPI lid device driver


ACPI 按钮驱动通过以下文件将盖子状态导出到用户空间：
```

  /proc/acpi/button/lid/LID0/state

```
该文件实际上会调用上述 _LID 控制方法。结合前面的说明，在某些平台上它并不可靠。
因此建议用户空间程序不要单独依赖此文件来判断实际的盖子状态。

ACPI 按钮驱动向用户空间发出以下输入事件：
  - SW_LID

ACPI 盖设备驱动会尽力将平台触发的事件传递给用户空间。
然而，鉴于有缺陷的固件无法保证“已打开”/“已关闭”事件是成对出现的，
ACPI 按钮驱动使用以下 3 种模式以避免引发问题。

如果用户空间尚未准备好忽略不可靠的“已打开”事件以及不可靠的初始状态通知，
Linux 用户可以使用以下内核参数来处理可能出现的问题：

A. button.lid_init_state=method:
   指定此选项时，ACPI 按钮驱动使用 _LID 控制方法的返回值报告初始盖子状态，
   而“已打开”/“已关闭”事件是否成对完全取决于固件实现。

   此选项可用于修复某些平台，其上 _LID 控制方法的返回值可靠，但缺失初始盖子状态通知。

   在用户空间尚未准备好处理有缺陷的 AML 表的时期内，此选项是默认行为。

B. button.lid_init_state=open:
   指定此选项时，ACPI 按钮驱动总是将初始盖子状态报告为“已打开”，
   而“已打开”/“已关闭”事件是否成对完全取决于固件实现。

   这可以修复某些平台，其上 _LID 控制方法的返回值不可靠且缺失初始盖子状态通知。

如果用户空间已准备好忽略不可靠的“已打开”事件以及不可靠的初始状态通知，
Linux 用户应始终使用以下内核参数：

C. button.lid_init_state=ignore:
   指定此选项时，ACPI 按钮驱动从不报告初始盖子状态，并实现了一种补偿机制，
   通过始终将“已关闭”输入事件与补足的“已打开”输入事件配对，确保可靠的“已关闭”通知总能传递给用户空间。
   但仍无法保证在盖子实际打开时“已打开”通知能传递给用户空间，因为某些 AML 表不会可靠地发送“已打开”通知。

   在此模式下，如果平台固件实现正确，旧的用户空间程序应当仍可工作。否则，需要新的用户空间程序
   来配合 ACPI 按钮驱动工作。此选项将在用户空间准备好处理有缺陷的 AML 表之后成为默认行为。
