
## _DSD 设备属性使用规则


## 属性、属性集合与属性子集


_DSD（Device Specific Data，设备特定数据）配置对象在 ACPI 5.1 中引入，允许通过 ACPI 命名空间
提供任意类型的设备配置数据。原则上，数据的格式可以是任意的，但必须由一个 UUID 标识，且该 UUID 必须被
处理 _DSD 输出的驱动所识别。然而，Linux 内核中的 ACPI 子系统定义了用于 _DSD 的通用 UUID，它们会自动处理
与之关联的数据包，并将这些数据作为“设备属性”提供给设备驱动。

设备属性是由一个字符串键和与之关联的值（特定类型）组成的数据项。

在 ACPI _DSD 上下文中，它是 _DSD 返回包中跟随通用设备属性 UUID 的子包的元素，如 _DSD（Device Specific Data）
实现指南文档 [^1^]_ 中标题为“Well-Known _DSD UUIDs and Data Structure Formats”的小节“Device Properties UUID”所规定。

它也可以被视为一个键以及关联数据类型的定义，该类型可以由给定设备的设备属性 UUID 子包通过 _DSD 返回。

属性集合是适用于某个硬件实体（如设备）的一组属性的集合。在 ACPI _DSD 上下文中，它是该设备可以在
设备属性 UUID 子包中返回的所有属性的集合。

属性子集是嵌套的属性集合。每一个都关联一个额外的键（名称），允许将该子集作为一个整体引用（并作为一个
独立的实体对待）。属性子集的规范表示通过 _DSD（Device Specific Data）实现指南文档 [^1^]_ 中标题为
“Well-Known _DSD UUIDs and Data Structure Formats”的小节“Hierarchical Data Extension UUID”所规定的机制。

属性集合可以是分层的。也就是说，一个属性集合可以包含多个属性子集，而每个属性子集又可以包含它自己的属性子集，依此类推。

## 属性集合的一般有效性规则


有效的属性集合必须遵循设备属性 UUID 定义文档 [^1^] 给出的指引。

_DSD 属性旨在作为对 ACPI 规范所定义现有机制的补充，而非替代。因此，作为一项规则，仅当 ACPI 规范未对
底层用例的处理做出直接规定时，才应使用它们。通常，从与设备属性 UUID 关联的数据包中的 _DSD 返回不遵循
该规则的属性集合是无效的。

### 附加考量


有些情况下，即使原则上遵循了上述一般规则，该属性集合仍可能不被视为有效。

例如，这适用于那些可能导致内核代码（无论是设备驱动还是库/子系统）以某种可能与 ACPI 命名空间中的
AML 方法冲突的方式访问硬件的设备属性。特别是，如果内核代码使用设备属性来操控通常由 ACPI 电源管理相关
方法（如用于设备对象的 _PSx 和 _DSW，或用于电源资源对象的 _ON 和 _OFF）控制的硬件，或者由 ACPI 设备
禁用/启用方法（如 _DIS 和 _SRS）控制的硬件，就可能发生这种情况。

在所有内核代码可能因使用设备属性而做出会混淆 AML 的事情的情况下，相关设备属性不适合 ACPI 环境，因此它们
不能属于一个有效的属性集合。

## 属性集合与 Device Tree 绑定


使 _DSD 返回遵循 Device Tree 绑定的属性集合通常很有用。

然而，在这些情况下，首先必须考虑上述有效性问题，并且必须避免从 _DSD 返回无效的属性集合。因此，可能
无法让 _DSD 逐字且完整返回遵循给定 DT 绑定的属性集合。尽管如此，为了代码复用，以设备属性的形式提供尽可能
多的配置数据，并辅以适合当前用例的 ACPI 特定机制，可能很有意义。

无论如何，无论内容如何，都不应期望逐字遵循 DT 绑定的属性集合能在 ACPI 环境中自动工作。
