
## BIOS/EFI 配置

BIOS 和 EFI 在很大程度上负责配置有关设备（或未来可能接入的设备）的静态信息，以便 Linux 能够构建这些设备的适当逻辑表示。

从高层次来看，在此配置阶段会发生以下事情。

- 引导加载程序启动 BIOS/EFI。

- BIOS/EFI 进行早期设备探测，以确定静态配置。

- BIOS/EFI 创建描述操作系统静态配置的 ACPI 表。

- BIOS/EFI 创建系统内存映射（EFI 内存映射、E820 等）。

- BIOS/EFI 调用 `start_kernel`，开始 Linux 早期引导过程。

本节主要关注的内容是 ACPI 表的生成以及静态内存映射的配置。有关这些表的更多细节，可在 [ACPI Tables <acpi>](ACPI Tables <acpi>) 中找到。

   平台供应商应仔细阅读本节，因为其中包含关于物理内存区域大小与对齐、内存空洞、HDM 交错，以及 Linux 期望尝试配合这些特性的 HDM 解码器做些什么的建议。

## Linux 对 BIOS/EFI 软件的期望

Linux 期望 BIOS/EFI 软件构造足够的 ACPI 表（如 CEDT、SRAT、HMAT 等）以及平台特定的配置（如 HPA 空间和主机桥交错配置），以便 Linux 驱动随后能够在运行时配置 CXL 结构（fabric）中的设备。

HDM 解码器和交换端口的编程并非必需，可以根据管理策略（例如 udev 规则）推迟到 CXL 驱动去完成。

某些平台由于怪异之处（参见：Zen5 地址转换）可能需要预先编程 HDM 解码器并将其锁定，但这并非正常的、“预期”的配置路径。如果可能，应当避免这样做。

某些平台可能希望预先配置这些资源，以便在不要求 CXL 驱动支持的情况下让内存上线。这些平台供应商应当使用现有的 CXL 驱动测试其配置，并且如果需要 RAS 等特性，应当为其自动配置提供驱动支持。

需要启动时就对外编程和/或锁定 CXL 结构组件的平台，可能会妨碍设备热插拔等特性的正常工作。

## UEFI 设置

如果您的平台支持，可以使用 `uefisettings` 命令来读写 EFI 设置。更改将在下次重启后生效。Kexec 并不构成一次充分的重启。

这里一个值得注意的配置是 EFI_MEMORY_SP（特定用途，Specific Purpose）位。启用时，该位告诉 Linux 将对某个内存区域的管理推迟交给一个驱动（在本例中即 CXL 驱动）。否则，该内存会被当作“普通内存”，并在 `__init` 期间暴露给页分配器。

### uefisettings 示例

```
        uefisettings identify

        bios_vendor: xxx
        bios_version: xxx
        bios_release: xxx
        bios_date: xxx
        product_name: xxx
        product_family: xxx
        product_version: xxx

```
在某些 AMD 平台上，`EFI_MEMORY_SP` 位是通过 :code:`CXL Memory Attribute` 字段设置的。在您的平台上它可能有别的叫法。

```
        selector: xxx
        ...
        question: Question {
            name: "CXL Memory Attribute",
            answer: "Enabled",
            ...
        }

```
## 物理内存映射

### 物理地址区域对齐

自 Linux v6.14 起，热插拔内存系统要求内存区域在大小和对齐上是均匀的。虽然 CXL 规范允许内存区域小至 256MB，但热插拔内存所支持的内存块大小和对齐是由体系结构定义的。

Linux 的内存块最小可为 128MB，并以 2 的幂递增。

- 在 ARM 上，默认块大小和对齐为 128MB 或 256MB。

- 在 x86 上，默认块大小为 256MB，并随着系统容量增加到 64GB 而增大到 2GB。

为了在各版本间获得最佳支持，平台供应商应将 CXL 内存放在 2GB 对齐的基地址上，并且区域也应 2GB 对齐。这还有助于避免创建成千上万个内存设备（每个块一个）。

### 内存空洞

内存映射中的空洞十分棘手。考虑一个位于基地址 `0x100000000` 的 4GB 设备：

```
  ---------------------
  |    0x100000000    |
  |        CXL        |
  |    0x1BFFFFFFF    |
  ---------------------
  |    0x1C0000000    |
  |    MEMORY HOLE    |
  |    0x1FFFFFFFF    |
  ---------------------
  |    0x200000000    |
  |     CXL CONT.     |
  |    0x23FFFFFFF    |
  ---------------------
```
有两个问题需要考虑：

- 解码器编程，以及
- 内存块对齐。

如果您的体系结构要求 2GB 均匀大小且对齐的内存块，那么（截至 v6.14）Linux 能够映射的容量将只有从 `0x100000000-0x180000000` 的那一段。剩余容量将被搁置，因为它们不是 2GB 对齐的长度。

假设您的体系结构和内存配置允许 1GB 的内存块，则支持该内存映射，并且应当将其表示为 CEDT 中多个分别描述内存空洞每一侧的 CFMWS——同时配合相应的解码器。

可以使用（也应当使用）多个解码器来管理这样的内存空洞（见下文），但内存空洞的每一块都应当对齐到一个合理的块大小（对齐越大越好）。如果您打算在内存映射中留有内存空洞，请预期为每个连续的主机物理内存块使用一个解码器。

自 v6.14 起，Linux 确实支持由单个 HDM 解码器描述、中间被内存空洞分隔的多个物理内存区域的热插拔。

## 解码器编程

如果 BIOS/EFI 打算将解码器编程为静态配置，有几件事需要考虑，以避免导致 Linux 不兼容的重大陷阱。其中某些建议并非“按规范”所要求，但否则 Linux 不保证提供支持。

### 转换点

按照规范，唯一将主机物理地址（HPA）转换（**TRANSLATE**）为设备物理地址（DPA）的解码器是**端点解码器（Endpoint Decoders）**。结构中的所有其他解码器都旨在路由访问而不转换地址。

```
  CXL Specification 3.1
  8.2.4.20: CXL HDM Decoder Capability Structure
  - Implementation Note: CXL Host Bridge and Upstream Switch Port Decoder Flow
  - Implementation Note: Device Decoder Logic
```
有鉴于此，Linux 做出一个很强的假设：在 CPU 与端点之间的所有解码器，其编程的地址范围都将是其父解码器地址范围的子集。

由于体系结构、ACPI、PCI 和 CXL 规范在各领域之间“交接”责任的方式存在一些歧义，一些早期采用的平台试图在源头的的内存控制器或主机桥处进行转换。这种配置需要对驱动进行平台特定的扩展，并且虽然受支持，但并未得到官方认可。

**强烈建议** **不要**这样做；否则，您只能自行实现针对您平台的驱动支持。

### 交错与配置灵活性

如果提供跨主机桥的交错，则 :doc:`CEDT <acpi/cedt>` 中的一个 CFMWS 条目必须以交错设备集的目标主机桥来呈现（每个主机桥后面可能有多个）。

如果提供主机桥内部的交错，则只需为该主机桥提供一个 CEDT 中的 CFMWS 条目——前提是它覆盖了该主机桥后面设备的全部容量。

如果打算赋予用户在根之外编程解码器时的灵活性，您可能希望在 CEDT 中提供面向不同用途的多个 CFMWS 条目。例如，您可能希望考虑添加：

1) 一个覆盖所有可交错主机桥的 CFMWS 条目。
2) 一个覆盖单个主机桥上所有设备的 CFMWS 条目。
3) 一个覆盖每个设备的 CFMWS 条目。

平台可以选择添加所有这些条目，或者根据某个 BIOS 设置来改变模式。对于每个 CFMWS 条目，Linux 期望在 [SRAT <acpi/srat>](SRAT <acpi/srat>) 中描述所描述的内存区域，以确定其在早期引导/init 期间应当保留的 NUMA 节点数量。

自 v6.14 起，Linux 会为每个 CEDT CFMWS 条目创建一个 NUMA 节点，即使不存在匹配的 SRAT 条目；不过这一点在未来不保证成立，应当避免此类配置。

### 内存空洞

如果您的平台在 CXL 内存之间穿插了内存空洞，建议利用多个解码器来覆盖这些内存区域，而不是试图将解码器编程为接受整个范围并期望 Linux 去管理重叠部分。

```
  ---------------------
  |    0x100000000    |
  |        CXL        |
  |    0x1BFFFFFFF    |
  ---------------------
  |    0x1C0000000    |
  |    MEMORY HOLE    |
  |    0x1FFFFFFFF    |
  ---------------------
  |    0x200000000    |
  |     CXL CONT.     |
  |    0x23FFFFFFF    |
  ---------------------
```
假设这由一个直接连接到主机桥的单一设备提供：

```
     -----------------------   -----------------------
     | root-decoder-0      |   | root-decoder-1      |
     |   base: 0x100000000 |   |   base: 0x200000000 |
     |   size:  0xC0000000 |   |   size:  0x40000000 |
     -----------------------   -----------------------
                |                         |
     -----------------------   -----------------------
     | HB-decoder-0        |   | HB-decoder-1        |
     |   base: 0x100000000 |   |   base: 0x200000000 |
     |   size:  0xC0000000 |   |   size:  0x40000000 |
     -----------------------   -----------------------
                |                         |
     -----------------------   -----------------------
     | ep-decoder-0        |   | ep-decoder-1        |
     |   base: 0x100000000 |   |   base: 0x200000000 |
     |   size:  0xC0000000 |   |   size:  0x40000000 |
     -----------------------   -----------------------
```
配合一个由两个 CFMWS 描述上述根解码器的 CEDT 配置。

Linux 不保证对奇怪的内存空洞情形提供支持。

### 多介质设备

CEDT 的 CFMWS 字段带有特殊限制位，用于描述所描述的内存区域允许易失性内存还是持久性内存（或两者皆可）。如果平台打算支持以下任一情况：

1) 具有多种介质的设备，或
2) 将持久性内存设备用作普通内存

平台可能希望创建多个 CEDT CFMWS 条目来描述同一段内存，目的是赋予最终用户配置该内存时的灵活性。Linux 目前在此领域没有很强的要求。
