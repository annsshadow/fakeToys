
## 为何使用 ACPI 驱动不是一个好主意


:Copyright: |copy| 2026, Intel Corporation

:Author: Rafael J. Wysocki <rafael.j.wysocki@intel.com>

尽管将驱动直接绑定到 struct acpi_device 对象（也称为“ACPI 设备节点”）至少在某些情况下可以提供
基本功能，但这样做存在问题，涉及总体一致性、sysfs 布局、电源管理操作顺序以及代码整洁性。

首先，ACPI 设备节点代表的是固件实体而非硬件，并且在许多情况下，它们提供关于被独立枚举的设备（如
PCI 设备或 CPU）的辅助信息。因此，给它们分配资源通常是值得质疑的，因为由它们所代表的实体并不在
内存或 I/O 地址空间中对地址进行译码，也不产生中断或类似的东西（所有这些都由硬件完成）。

其次，作为一般规则，一个 struct acpi_device 只能作为另一个 struct acpi_device 的父节点。如果不是
这样，子设备在设备层级中的位置至少会令人困惑，并且可能无法直接识别出提供其所代表功能的硬件。然而，
例如，如果给定驱动在其下注册输入设备或唤醒源，将驱动直接绑定到 ACPI 设备节点就可能导致这种情况发生。

接下来，直接在 ACPI 设备节点上使用系统挂起与恢复回调同样值得质疑，因为它可能导致出现顺序问题。即，
ACPI 设备节点在枚举对应于它们的硬件之前就被注册，并且它们落在 PM 列表中的大多数其他设备对象之前。
因此，它们的 PM 回调的执行顺序可能与一般预期不同。此外，通常来说，_DEP 对象返回的依赖关系并不影响
ACPI 设备节点自身，而是影响与它们关联的“物理”设备，这潜在地是另一个将 ACPI 设备节点当作“真实”
设备表示来处理所带来的不一致来源。

以上所有意味着，将驱动绑定到 ACPI 设备节点通常应当避免，因此不应使用 struct acpi_driver 对象。

此外，将驱动直接绑定到 ACPI 设备节点需要一个设备 ID，但设备 ID 通常并不与它们全部关联。其中一些包含
允许识别相应硬件的替代信息，例如由 _ADR 对象返回值所代表的信息，而在这些情况下并不使用设备 ID。结果
是，令人困惑的是，将 ACPI 驱动绑定到 ACPI 设备节点甚至可能根本不可能。

当这种情况发生时，对应于给定 ACPI 设备节点的硬件由另一个设备对象表示，例如 struct pci_dev，而 ACPI
设备节点是该设备的“ACPI 伴侣（companion）”，可通过其 fwnode 指针访问，该指针由 ACPI_COMPANION() 宏
使用。ACPI 伴侣保存关于设备配置的附加信息，以及可能的某些以 AML（ACPI Machine Language，ACPI 机器语言）
字节码形式提供的、关于设备操作的“诀窍”，这些由平台固件提供。因此，ACPI 设备节点的作用类似于在使用
Device Tree 进行平台描述的系统上 struct device_node 的作用。

为了一致性，这种方法已被扩展到使用 ACPI 设备 ID 的情况。即，在这些情况下，会创建一个附加的设备对象来
代表对应于给定 ACPI 设备节点的硬件。默认情况下，它是一个平台设备，但它也可能是 PNP 设备、CPU 设备或其他
类型的设备，取决于给定硬件实际是什么。甚至存在多个设备被一个 ACPI 设备节点“支撑”或“伴随”的情况（例如，
对应于 GPU 的 ACPI 设备节点，除了 GPU 配置信息外，还可能提供用于背光亮度控制的固件接口）。

这意味着，将驱动直接绑定到 ACPI 设备节点真的应该永远没有必要，因为存在一个“恰当”的设备对象代表相应的
硬件，一个“恰当”的驱动可以使用给定的 ACPI 设备节点作为该设备的 ACPI 伴侣来绑定到它。因此，原则上，没有
理由使用 ACPI 驱动，如果它们全部被其他类型的驱动（例如平台驱动）所取代，一些代码就可以被移除，一些复杂性
也会消失。
