## Surface Serial Hub（串行中枢）协议


Surface Serial Hub（SSH）是较新一Surface 设备上嵌入式 Surface Aggregator Module 控制器（SAM EC）的中央通信接口。我们将此协议与接口称为 SAM-over-SSH，以区别于老一代的 SAM-over-HID
在支SAM-over-SSH Surface 设备上，SAM 通过 UART 连接到主机，并在 ACPI 中定义为 ID `MSHW0084` 的设备。在这些设备上，大量功能经由 SAM 提供，包括电池与电源信息及事件、温度读数及事件等等。对Surface Laptops，键盘输入经SAM 定向HID 处理，在 Surface Laptop 3 Surface Book 3 上这也包含触摸板输入
请注意，该子系统的标准免责声明同样适用于本文档：所有内容均为逆向工程所得，因此可能存在错误或不完整
下文使用的所CRC 均为双字节的 `crc_itu_t(0xffff, ...)`。所有多字节值均为小端序，取值之间没有隐式填充

## SSH 数据包协议：定义


SSH 协议的基本通信单元是帧（`struct ssh_frame <ssh_frame>`）。一个帧由以下字段按顺序紧凑排列组成
   :widths: 1 1 4
   :header-rows: 1

   - - Field
     - Type
     - Description

   - - |TYPE|
     - |u8|
     - 帧的类型标识符
   - - |LEN|
     - |u16|
     - 与帧关联的有效载荷长度
   - - |SEQ|
     - |u8|
     - 序列 ID（见下文说明）
每个帧结构之后都跟随一个覆盖该结构CRC。帧结构CRC（|TYPE|、|LEN| |SEQ| 字段）紧接在帧结构之后、有效载荷之前。有效载荷之后跟随其自身CRC（覆盖所有有效载荷字节）。如果有效载荷不存在（即帧的 `LEN=0`），有效载荷CRC 仍然存在，其值为 `0xffff`。|LEN| 字段不包含任CRC，它等于CRC 与有效载CRC 之间的字节数
此外，使用以下固定的双字节序列：

   :widths: 1 1 4
   :header-rows: 1

   - - Name
     - Value
     - Description

   - - |SYN|
     - `[0xAA, 0x55]`
     - 同步字节
一条消息由 |SYN| 开始，后跟帧（|TYPE|、|LEN|、|SEQ| CRC），以及（若帧中指定，即 `LEN > 0`）有效载荷字节，最后无论有效载荷是否存在都跟随有效载荷 CRC。一次交换所对应的消息可通过其具有相同的序列 ID（|SEQ|）来部分标识，该 ID 存储在帧内（下一节详述）。序ID 是一个回绕计数器
一个帧可以具有以下类型（`enum ssh_frame_type <ssh_frame_type>`）：

   :widths: 1 1 4
   :header-rows: 1

   - - Name
     - Value
     - Short Description

   - - |NAK|
     - `0x04`
     - 在先前接收的消息出错时发送
   - - |ACK|
     - `0x40`
     - 用于确认收到 |DATA| 帧
   - - |DATA_SEQ|
     - `0x80`
     - 用于传输数据。带序列
   - - |DATA_NSQ|
     - `0x00`
     - |DATA_SEQ| 相同，但无需ACK
|NAK| |ACK| 类型帧都用于控制消息流，因此不携带有效载荷。|DATA_SEQ| |DATA_NSQ| 类型帧必须携带有效载荷。不同帧类型的流转顺序与交互将在下一节更深入描述

## SSH 数据包协议：流转顺序


每次交换|SYN| 开始，后跟 |DATA_SEQ| |DATA_NSQ| 类型帧，以及CRC、有效载荷与有效载荷 CRC。对|DATA_NSQ| 类型帧，交换到此结束。对|DATA_SEQ| 类型帧，接收方必须通过回复一条包|ACK| 类型帧（其序ID |DATA| 帧相同）的消息来确认收到该帧。换言之，|ACK| 帧的序列 ID 指定要被确认|DATA| 帧。若发生错误（例如无效的 CRC），接收方回复一条包|NAK| 类型帧的消息。由于通过 |NAK| 帧指示出错的上一数据帧的序列 ID 不可靠，因此不应使用 |NAK| 帧的序列 ID，它被设为零。收|NAK| 帧后，发送方应重发所有未完成（未ACK）的消息
序列 ID 在双方之间并不同步，即它们由各方独立管理。因此，识别一次交换所对应的消息依赖于序列 ID、消息类型以及上下文。具体而言，序ID 用于`ACK` 与其 `DATA_SEQ` 类型帧关联，但并不用于将 `DATA_SEQ` `DATA_NSQ` 类型帧与其它 `DATA` 类型帧关联
一次示例交换可能如下所示：

```

    tx: -- SYN FRAME(D) CRC(F) PAYLOAD CRC(P) -----------------------------
    rx: ------------------------------------- SYN FRAME(A) CRC(F) CRC(P) --

```
其中两个帧具有相同的序列 ID（`SEQ`）。此处，`FRAME(D)` 表示 |DATA_SEQ| 类型帧，`FRAME(A)` 表示 `ACK` 类型帧，`CRC(F)` 为前一帧的 CRC，`CRC(P)` 为前一有效载荷CRC。若发生错误，交换如下所示：

```

    tx: -- SYN FRAME(D) CRC(F) PAYLOAD CRC(P) -----------------------------
    rx: ------------------------------------- SYN FRAME(N) CRC(F) CRC(P) --

```
发送方应据此重发消息。`FRAME(N)` 表示 |NAK| 类型帧。注|NAK| 类型帧的序列 ID 固定为零。对|DATA_NSQ| 类型帧，两种交换是相同的
```

    tx: -- SYN FRAME(DATA_NSQ) CRC(F) PAYLOAD CRC(P) ----------------------
    rx: -------------------------------------------------------------------

```
此处可以检测到错误，但无法纠正或通知发送方。这些交换是对称的，即交`rx` `tx` 仍为一次有效的交换。目前已知没有更长的交换

## 命令：请求、响应与事件


命令作为有效载荷在数据帧内部发送。目前这|DATA| 帧唯一已知的有效载荷类型，其有效载荷类型值为 `0x80`（`SSH_PLD_TYPE_CMD <ssh_payload_type>`）
命令类型的有效载荷（`struct ssh_command <ssh_command>`）由一个八字节的命令结构开始，后跟可选、可变长度的命令数据。该可选数据的长度由相应帧中给出的帧有效载荷长度推导，`frame.len - sizeof(struct ssh_command)`。命令结构包含以下按顺序紧凑排列的字段：

   :widths: 1 1 4
   :header-rows: 1

   - - Field
     - Type
     - Description

   - - |TYPE|
     - |u8|
     - 有效载荷类型。对于命令始终为 `0x80`
   - - |TC|
     - |u8|
     - 目标类别
   - - |TID|
     - |u8|
     - 命令/消息的目ID
   - - |SID|
     - |u8|
     - 命令/消息的源 ID
   - - |IID|
     - |u8|
     - 实例 ID
   - - |RQID|
     - |u16|
     - 请求 ID
   - - |CID|
     - |u8|
     - 命令 ID
一般而言，命令结构与数据不包含任何故障检测机制（例如 CRC），这仅在帧层面完成
命令类型的有效载荷由主机用于EC 发送命令与请求，也EC 用于将响应与事件发回主机。我们区分请求（由主机发送）、响应（EC 回复请求而发送）与事件（EC 在没有前置请求的情况下发送）
命令与事件由其目标类别（`TC`）与命令 ID（`CID`）唯一标识。目标类别指定命令的通用类别（例如：系统整体、电池与交流电、温度等等），而命ID 指定该类别内的命令。只|TC| + |CID| 的组合才是唯一的。此外，命令具有实例 ID（`IID`），用于区分不同的子设备。例`TC=3` `CID=1` 是获取某个温度传感器温度的请求，其中 |IID| 指定相应传感器。若不使用实ID，应将其设为零。若使用实例 ID，一般从1 开始，而零可用于与实例无关的查询（若适用）。对请求的响应应具有与相应请求相同的目标类别、命ID 与实ID
响应通过其请ID（`RQID`）字段与相应请求匹配。这是一16 位回绕计数器，类似于帧上的序ID。注意请响应对中帧的序列 ID 并不匹配，只有请ID 必须匹配。从帧协议角度看，这是两次独立的交换，甚至可能分离，例如事件在请求之后、响应之前被发送。并非所有命令都会产生响应，且这无法|TC| + |CID| 检测出。等待响应（或将其告知通信框架，如 SAN/ACPI 中通过 `SNC` 标志所做的那样）是发起方的责任
事件由唯一且保留的请求 ID 标识。主机发送新请求时不应使用这ID。它们在主机上用于：第一，检测事件；第二，将事件与已注册的事件处理程序匹配。事件的请求 ID 由主机选择，并在建立并启用事件源（通过 enable-event-source 请求）时告知 EC。随EC 对来自相应源的事件使用指定的请求 ID。注意，事件仍应通过其目标类别、命ID 以及（若适用）实ID 来标识，因为单个事件源可能发送多种不同的事件类型。不过一般而言，单个目标类别应映射到单个保留的事件请求 ID
此外，请求、响应与事件都具有关联的目标 ID（`TID`）与ID（`SID`）。这两个字段指示消息的来源（`SID`）以及消息的预期目标（`TID`）。注意，因此特定请求的响应其ID 与目ID 与原请求相比是互换的（即请求目标是响应源，请求源是响应目标）。两者可能的取值见（`enum ssh_request_id <ssh_request_id>`）
请注意，尽管请求与事件本应仅通过目标类别与命ID 即可唯一标识，但 EC 可能要求特定的目ID 与实ID 取值才会接受命令。例如，`TID=1` 可接受的命令，对 `TID=2` 可能不被接受，反之亦然。虽然现实中这未必总是成立，但你可以将不同的目ID 视为指示具有潜在不同功能集的不同物理 EC

## 限制与观

理论上，该协议可并行处理多达 `U8_MAX` 个帧，以及多`U16_MAX` 个待处理请求（忽略为事件保留的请ID）。但在实践中，限制更多。根据我们的测试（尽管是通过 python 即一个用户空间程序），EC 似乎能在某一时刻可靠地并行处理最多四个请求。当并行五个或更多请求时，观察到命令被持续丢弃（帧被 ACK 但无命令响应）。对于五个同时的命令，这会稳定地导致一个命令被丢弃、四个命令被处理
然而，也注意到即便并行三个请求，偶尔也会发生帧丢失。除此之外，在三个待处理请求的限制下，未观察到命令被丢弃（即命令被丢弃但承载命令的帧ACK）。无论如何，若超过某个超时，帧（以及可能还有命令）应由主机重发。EC 对帧以一秒超时、最多两次重试（即总共三次传输）来执行此操作。重试限制也适用于收到的 NAK，在最坏情况下可能导致整条消息被丢弃
尽管只要不发生传输失败，这对待处理数据帧似乎也工作良好，但其实现与处理似乎依赖于“只有一个未被确认的数据帧”这一假设。特别地，重复帧的检测依赖于最后一个序列号。这意味着，如果一个已EC 成功接收的帧被再次发送（例如由于主机未收|ACK|），EC 仅在其持EC 收到的最后一帧的序列 ID 时才会检测到这一点。例如：先发`SEQ=0` `SEQ=1` 两个帧，随后重复 `SEQ=0`，将不会把第二个 `SEQ=0` 帧识别为重复，从而每次收到时都会执行该帧中的命令，在本例中即执行两次。先发`SEQ=0`、`SEQ=1` 然后重复 `SEQ=1`，会将第二个 `SEQ=1` 识别为第一个的重复并忽略它，从而只执行其中包含的命令一次
总之，这表明最多只能有一个待处理且未ACK 的帧（每方，这有效地导致帧相关的同步通信），以及最多三个待处理命令。同步帧传输的限制似乎与Windows 上观察到的行为一致
