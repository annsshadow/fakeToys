

## 核心驱动内部实现


Surface System Aggregator Module（SSAM）核心与 Surface Serial Hub（SSH）驱动的架构概览。有API 文档，请参阅

- [内部 API](internal-api)

## 概览


SSAM 核心实现采用分层结构，某种程度上遵循 SSH 协议的结构：

底层的包传输包传输层（PTL实现，直接构建在内核的串口设备（serdev）基础设施之上。顾名思义，该层处理包传输逻辑，并负责诸如包校验、包确认（ACKing）、包（重传）超时，以及将包载荷转发到更高层等工作

其上*请求传输层（RTL*。该层围绕命令类型的包载荷展开，即请求（由主机发往 EC）、EC 针对这些请求的响应，以及事件（由 EC 发往主机）。具体而言，它区分事件与请求响应，将响应与其对应的请求进行匹配，并实现请求超时

**控制*层构建于其上，本质上决定了如何处理请求响应，尤其是事件。它提供事件通知器（notifier）系统，处理事件的激停用，为事件和异步请求完成提供工作队列（workqueue），并管理构建命令消息所需的消息计数器（`SEQ`、`RQID`）。该层基本上SAM EC 提供了一个基础接口，供其他内核驱动使用

虽然控制器层已经为其他内核驱动提供了接口，但客户*总线（bus*扩展了这个接口，通过 |ssam_device| |ssam_device_driver| 为原SSAM 设备（即未在 ACPI 中定义、也未作为平台设备实现的设备）提供支持，从而简化客户端设备与客户端驱动的管理

关于客户端设驱动 API 及其接口选项的文档，请参Documentation/driver-api/surface_aggregator/client.rst。建议在继续阅读下面的架构概览之前，先熟悉该章节以及 Documentation/driver-api/surface_aggregator/ssh.rst


## 包传输层


包传输层|ssh_ptl| 表示，其结构围绕以下关键概念展开

### 包（Packets


包是 SSH 协议的基本传输单元。它们由包传输层管理，该层本质上是驱动的最低层，并SSAM 核心的其他组件所构建。待SSAM 核心发送的包通过 |ssh_packet| 表示（相反，核心接收的包没有任何特定结构，完全由原始 |ssh_frame| 管理）

该结构包含了在传输层内部管理包所需的字段，以及对包含待传输数据（即包裹|ssh_frame| 中的消息）的缓冲区的引用。最值得注意的是，它包含一个内部引用计数，用于管理其生命周期（可通过 |ssh_packet_get| |ssh_packet_put| 访问）。当该计数器归零时，包通过|ssh_packet_ops| 引用所提供`release()` 回调会被执行，该回调随后可以释放包或其外层结构（例如 |ssh_request|）

`release` 回调外，|ssh_packet_ops| 引用还提供一`complete()` 回调，该回调在包完成时运行一次，并提供本次完成的状态，即成功时0，出错时为负 errno 值。一旦包被提交到包传输层，`complete()` 回调总是保证`release()` 回调之前执行，也就是说，包总是会先完成（无论成功、出错还是由于取消），然后才会被释放

包的状态通过`state` 标志（|ssh_packet_flags|）管理，其中也包含包类型。具体而言，以下位值得注意

- `SSH_PACKET_SF_LOCKED_BIT`：当完成即将发生（无论由于出错还是成功）时设置此位。它表示不应再获取该包的任何引用，并且应尽快丢弃任何已有的引用。设置此位的进程负责从该包的包队列和挂起集合中移除对其的所有引用

- `SSH_PACKET_SF_COMPLETED_BIT`：此位由运行 `complete()` 回调的进程设置，用于确保该回调只运行一次

- `SSH_PACKET_SF_QUEUED_BIT`：当包入队到包队列时设置此位，出队时清除

- `SSH_PACKET_SF_PENDING_BIT`：当包加入挂起集合时设置此位，从中移除时清除

### 包队列（Packet Queue


包队列是包传输层中两个基本集合中的第一个。它是一个优先级队列，各包的优先级基于包类型（主）和尝试次数（次）。关于优先级值的更多细节，请参阅 |SSH_PACKET_PRIORITY|

传输层要发送的所有包都必须通过 |ssh_ptl_submit| 提交到该队列。注意这包括传输层自身发送的控制包。在内部，数据包可能因超时或 EC 发送的 NAK 包而重新提交到该队列

### 挂起集合（Pending Set


挂起集合是包传输层中两个基本集合中的第二个。它存储对已发送但等待 EC 确认（例如相应的 ACK 包）的包的引用

注意，如果一个包因包确认超时NAK 而被重新提交，它可能同时处于挂起和入队状态。在这种重新提交时，包不会从挂起集合中移除

### 发送线程（Transmitter Thread


发送线程负责包传输方面的大部分实际工作。在每次迭代中，它（等待并）检查队列中的下一个包（如果有）是否可以传输，如果可以，则将其出队并增加其传输尝试次数计数，即 tries。如果包是带序号的（即需EC ACK），则将其加入挂起集合。接着，包的数据被提交serdev 子系统。如果在此提交过程中出错或超时，发送线程会以相应的状态值完成该包。如果包是无序号的（即不需EC ACK），则发送线程以成功完成该包

带序号包的传输受并发挂起包数量的限制，即可以并行等待 EC ACK 的包的数量上限。此限制当前设为 1（原因请参阅 Documentation/driver-api/surface_aggregator/ssh.rst）。控制包（即 ACK NAK）总是可以传输

### 接收线程（Receiver Thread


EC 接收到的任何数据都会被放入一FIFO 缓冲区以便进一步处理。该处理在接收线程上进行。接收线程将接收到的消息解析并校验为 |ssh_frame| 及其对应的载荷。它会为接收到的消息准备并提交必要的 ACK（以及在校验出错或数据无效时NAK）包

该线程还处理进一步的处理，例如通过序列 ID ACK 消息匹配到相应的挂起包并完成它，以及在收NAK 消息时重新提交当前所有挂起的包（NAK 导致的重新提交类似于超时导致的重新提交，详见下文）。注意，带序号包的成功完成总是在接收线程上运行（而任何表示失败的完成将在发生失败的进程上运行）

任何载荷数据都通过回调转发到上一层，即请求传输层

### 超时收割器（Timeout Reaper


包确认超时是针对带序号包的每个包的超时，在相应包开始（重新）传输时启动（即每次在发送线程上尝试传输时都会启动一次该超时）。它用于触发重新提交，或者在尝试次数超出上限时取消相关包

该超时由一个专用的收割（reaper）任务处理，该任务本质上是一个工作项（work item），被（重新）调度为在下一个包即将超时的时刻运行。然后该工作项检查挂起包集合中是否有任何包已超出超时，如果有剩余包，则将自己重新调度到下一个合适的时间点

如果收割器检测到超时，该包要么在还有剩余尝试次数时被重新提交，要么在没有剩余尝试次数时以 `-ETIMEDOUT` 作为状态完成。注意，此处的重新提交（以及由收NAK 触发的重新提交）意味着包被加入队列且尝试次数加一，从而获得更高的优先级。包的超时将被禁用，直到下一次传输尝试，并且包保留在挂起集合中

注意，由于传输和包确认超时，包传输层总是保证能够取得进展，哪怕仅仅是通过让包超时，并且永远不会完全阻塞

### 并发与加锁（Concurrency and Locking


包传输层中有两个主要的锁：一个保护对包队列的访问，另一个保护对挂起集合的访问。这些集合只能在持有相应锁的情况下被访问和修改。如果需要访问两个集合，必须先获取挂起锁再获取队列锁，以避免死锁

除了保护集合外，在初次提交包之后，某些包字段只能在一个锁下访问。具体而言，包优先级只能在持有队列锁时访问，包时间戳只能在持有挂起锁时访问

包传输层的其他部分独立保护。状态标志由原子位操作和（必要时）内存屏障管理。对超时收割器工作项及其过期时间的修改由其自身的锁保护

包对包传输层的引用（`ptl`）有些特殊。它要么在上层请求提交时设置，要么（如果没有上层请求）在包首次提交时设置。设置之后，其值不会再改变。可能与提交并发运行的函数的取消，不能依`ptl` 引用已被设置。这些函数中对它的访问由 `READ_ONCE()` 保护，而设`ptl` 同样`WRITE_ONCE()` 保护以保持对称

某些包字段可以在保护它们的锁之外读取，具体来说是优先级和状态，用于跟踪（tracing）。在这些情况下，通过采用 `WRITE_ONCE()` `READ_ONCE()` 来确保正确访问。这种只读访问仅在不允许陈旧值的情况下才被允许

就上层接口而言，包提交（|ssh_ptl_submit|）、包取消（|ssh_ptl_cancel|）、数据接收（|ssh_ptl_rx_rcvbuf|）以及层关闭（|ssh_ptl_shutdown|）可以相互并发执行。注意，包提交对于同一个包不能与自己并发运行。同样，关闭和数据接收也不能与自己并发运行（但二者可以彼此并发运行）


## 请求传输层（Request Transport Layer


请求传输层由 |ssh_rtl| 表示，构建于包传输层之上。它处理请求，即由主机发送的、以 |ssh_command| 作为帧载荷的 SSH 包。该层将请求的响应与事件（同样由 EC 通过 |ssh_command| 载荷发送）区分开来。响应在该层处理，而事件通过相应的回调转发到上一层，即控制器层。请求传输层围绕以下关键概念组织

### 请求（Request


请求是带有命令类型载荷的包，由主机发往 EC，以查询其数据或触发其上的某个动作（或二者同时进行）。它们由 |ssh_request| 表示，包裹了存储其消息数据（即带有命令载荷的 SSH 帧）的底|ssh_packet|。注意，所有顶层表示，例如 |ssam_request_sync|，都构建于该结构之上

由于 |ssh_request| 继承|ssh_packet|，其生命周期也由包结构内部的引用计数器管理（可通过 |ssh_request_get| |ssh_request_put| 访问）。一旦计数器归零，就会调用该请求|ssh_request_ops| 引用所提供`release()` 回调

请求可以有一个可选的响应，同样通过带有命令类型载荷SSH 消息发送（EC 到主机）。构造请求的一方必须知道是否需要响应，并在提供|ssh_request_init| 的请求标志中标记这一点，以便请求传输层可以等待该响应

|ssh_packet| 类似，|ssh_request| 也有一个通过其请ops 引用提供`complete()` 回调，并且一旦通过 |ssh_rtl_submit| 提交到请求传输层，就保证在释放之前先完成。对于没有响应的请求，成功完成将在底层包被包传输层成功传输后发生（即从包完成回调内部）。对于有响应的请求，成功完成将在响应被接收并通过其请ID 匹配到该请求后发生（这发生在运行于接收线程上的包层数据接收回调中）。如果请求以错误完成，状态值将被设为相应的（负）errno 值

请求的状态同样通过`state` 标志（|ssh_request_flags|）管理，其中也编码了请求类型。具体而言，以下位值得注意

- `SSH_REQUEST_SF_LOCKED_BIT`：当完成即将发生（无论由于出错还是成功）时设置此位。它表示不应再获取该请求的任何引用，并且应尽快丢弃任何已有的引用。设置此位的进程负责从该请求的请求队列和挂起集合中移除对其的所有引用

- `SSH_REQUEST_SF_COMPLETED_BIT`：此位由运行 `complete()` 回调的进程设置，用于确保该回调只运行一次

- `SSH_REQUEST_SF_QUEUED_BIT`：当请求入队到请求队列时设置此位，出队时清除

- `SSH_REQUEST_SF_PENDING_BIT`：当请求加入挂起集合时设置此位，从中移除时清除

### 请求队列（Request Queue


请求队列是请求传输层中两个基本集合中的第一个。与包传输层的包队列不同，它不是优先级队列，而是采用简单的先到先服务原则

请求传输层要发送的所有请求都必须通过 |ssh_rtl_submit| 提交到该队列。一旦提交，请求不能重新提交，也不会在超时时自动重新提交。相反，请求会以超时错误完成。如果需要，调用方可以创建并提交一个新的请求以再次尝试，但不得再次提交同一个请求

### 挂起集合（Pending Set


挂起集合是请求传输层中两个基本集合中的第二个。该集合存储对所有挂起请求的引用，即等待 EC 响应的请求（类似于包传输层的挂起集合对包所做的那样）

### 发送任务（Transmitter Task


当有新请求可供传输时，发送任务被调度。它检查请求队列中的下一个请求是否可以传输，如果可以，则将其底层包提交到包传输层。该检查确保同时只有有限数量的请求可以处于挂起状态（即等待响应）。如果请求需要响应，则在其包被提交之前将其加入挂起集合

### 包完成回调（Packet Completion Callback


包的完成回调在请求的底层的包完成时被调用。在发生错误完成的情况下，相应的请求以该回调中提供的错误值完成

在包成功完成时，进一步的处理取决于请求。如果请求期望响应，则将其标记为已传输并启动请求超时。如果请求不期望响应，则以其成功完成

### 数据接收回调（Data-Received Callback


数据接收回调通过数据类型的帧通知请求传输层底层包传输层已接收到数据。一般来说，这预期是一个命令类型的载荷

如果命令的请ID 是为事件保留的请ID 之一（从 1 `SSH_NUM_EVENTS`，含边界），则它会被转发到请求传输层中注册的事件回调。如果请ID 表示一个对请求的响应，则会在挂起集合中查找相应的请求，如果找到并标记为已传输，则以成功完成

### 超时收割器（Timeout Reaper


请求-响应超时是针对期望响应的请求的每请求超时。它用于确保请求不会无限期地等待 EC 的响应，并在底层包成功完成后启动

与包传输层上的包确认超时类似，该超时由一个专用的收割任务处理。该任务本质上是一个工作项（work item），被（重新）调度为在下一个请求即将超时的时刻运行。然后该工作项扫描挂起请求集合中任何已超时的请求，并`-ETIMEDOUT` 作为状态完成它们。请求不会被自动重新提交。相反，请求的发起方必须构造并提交一个新请求（如果需要的话）

注意，该超时与包的传输和确认超时相结合，保证了请求层总是能够取得进展，哪怕仅仅是通过让包超时，并且永远不会完全阻塞

### 并发与加锁（Concurrency and Locking


与包传输层类似，请求传输层中有两个主要的锁：一个保护对请求队列的访问，另一个保护对挂起集合的访问。这些集合只能在持有相应锁的情况下被访问和修改

请求传输层的其他部分独立保护。状态标志（再次）由原子位操作和（必要时）内存屏障管理。对超时收割器工作项及其过期时间的修改由其自身的锁保护

某些请求字段可以在保护它们的锁之外读取，具体来说是状态，用于跟踪（tracing）。在这些情况下，通过采用 `WRITE_ONCE()` `READ_ONCE()` 来确保正确访问。这种只读访问仅在不允许陈旧值的情况下才被允许

就上层接口而言，请求提交（|ssh_rtl_submit|）、请求取消（|ssh_rtl_cancel|）以及层关闭（|ssh_rtl_shutdown|）可以相互并发执行。注意，请求提交对于同一个请求不能与自己并发运行（并且每个请求也只能被调用一次）。同样，关闭也不能与自己并发运行


## 控制器层（Controller Layer


控制器层在请求传输层之上进行扩展，为客户端驱动提供一个易于使用的接口。它|ssam_controller| SSH 驱动表示。虽然较低层的传输层负责传输和处理包与请求，但控制器层更多地扮演管理角色。具体而言，它处理设备初始化、电源管理以及事件处理，包括通过（事件）完成系统（|ssam_cplt|）进行的事件投递与注册

### 事件注册（Event Registration


一般而言，某个事件（或更确切地说某一类事件）必须先由主机显式请求，EC 才会发送它（HID 输入事件似乎是例外）。这通过一个事件使能请求来完成（类似地，当不再需要时，应通过事件禁用请求来禁用事件）

用于使能（或禁用）事件的特定请求通过一个事件注册表（event registry）给出，即该事件的管辖机构（可以说），由 |ssam_event_registry| 表示。作为该请求的参数，必须提供目标类别（target category），以及（取决于事件注册表的）要启用的事件的实例 ID（instance ID）。此（可选的）实ID 在注册表不使用它时必须为零。目标类别与实例 ID 一起构成事ID，由 |ssam_event_id| 表示。简而言之，事件注册表和事件 ID 二者都是唯一标识某一类事件所必需的

注意，必须为使能事件请求提供进一步的**请求 ID**参数。该参数不影响被使能的事件类别，而是被设置为 EC 发送的该类每个事件上的请求 ID（RQID）。它用于标识事件（因为仅有一小部分请ID 被保留供事件使用，具体为1 `SSH_NUM_EVENTS`，含边界）并将事件映射到其特定类别。当前，控制器总是将该参数设为 |ssam_event_id| 中指定的目标类别

由于多个客户端驱动可能依赖相同（或重叠）的事件类别，且使禁用调用是严格二元的（即开/关），控制器必须管理对这些事件的访问。它通过引用计数来实现，将计数器存储在一个以事件注册表和 ID 为键的、基RB 树的映射中（目前没有已知的有效事件注册表与事ID 组合的列表）。详情请参阅 |ssam_nf|、|ssam_nf_refcount_inc| |ssam_nf_refcount_dec|

该管理连同通知器注册（在下一节描述）一起，通过顶层函数 |ssam_notifier_register| |ssam_notifier_unregister| 完成

### 事件投递（Event Delivery


要接收事件，客户端驱动必须通过 |ssam_notifier_register| 注册一个事件通知器。这会增加该类事件的引用计数（如上一节详述），在 EC 上使能该类（如果尚未使能），并安装所提供的通知器回调

通知器回调存储在列表中，每个目标类别有一个（RCU）列表（通过事件 ID 提供；注意：目标类别的数量是固定的已知值）。除了通过事件 ID 给定的目标类别和实例 ID 之外，目前没有已知的从事件注册表与事ID 的组合到事件类所能提供的命令数据（目ID、目标类别、命ID 和实ID）的关联

注意，由于通知器的存储方式（或者说必须如此存储），客户端驱动可能会收到它们并未请求的事件，需要对此有所准备。具体而言，默认情况下它们会收到来自同一目标类别的所有事件。为简化处理，在注册通知器时可以请求按目ID（通过事件注册表提供）和实ID（通过事件 ID 提供）对事件进行过滤。该过滤在通知器执行时遍历通知器时应用

所有通知器回调都在一个专用的工作队列（即所谓的完成工作队列，completion workqueue）上执行。事件通过安装在请求层（运行在包传输层的接收线程上）的回调接收后，会被放入其相应的事件队列（|ssam_event_queue|）。从该事件队列中，该队列的完成工作项（运行在完成工作队列上）会取出该事件并执行通知器回调。这样做是为了避免在接收线程上阻塞

每个目标 ID 与目标类别的组合对应一个事件队列。这样做是为了确保对同一目标 ID 和目标类别的事件，其通知器回调按顺序执行。对于目ID 和目标类别组合不同的事件，其回调可以并行执行

### 并发与加锁（Concurrency and Locking


控制器的并发安全保证大部分由较低层的请求传输层提供。除此之外，事件（注销）注册由其自身的锁保护

对控制器状态的访问由状态锁保护。该锁是一个读写信号量（read/write semaphore）。读侧可用于确保在依赖状态保持不变的函数（例|ssam_notifier_register|、|ssam_notifier_unregister|、|ssam_request_sync_submit| 及其衍生函数）执行期间状态不会变化，并且这种保证未以其他方式提供（例如通过 |ssam_client_bind| |ssam_client_link|）。写侧保护任何会改变状态的转换，即初始化、销毁、挂起和恢复

控制器状态可以在状态锁之外（只读）访问，用于对无效 API 使用进行冒烟测试（例如在 |ssam_request_sync_submit| 中）。注意，此类检查并非（也不会）旨在防范所有无效使用，而是旨在帮助捕获它们。在这些情况下，通过采用 `WRITE_ONCE()` `READ_ONCE()` 来确保正确的变量访问

假设关于状态不变的任何前置条件都已满足，所有非初始化且非关闭的函数都可以彼此并发运行。这包括 |ssam_notifier_register|、|ssam_notifier_unregister|、|ssam_request_sync_submit|，以及所有构建于其上的函数
