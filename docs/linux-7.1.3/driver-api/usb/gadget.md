
## Linux USB Gadget API


:Author: David Brownell
:Date:   20 August 2004

## 简

本文档介绍了一Linux-USB “Gadget”内核API，用于内Linux 的外设和其他
USB 设备中。它概述API 的结构，并展示了其如何融入一个系统开发项目。这Linux 上发布的第一个用于解决若干重要问题的此类 API，包括：

- 支持 USB 2.0，用于能够以每秒几十兆字节的速度流式传输数据的高速设备
- 既能处理拥有数十个端点的设备，也能处理只有两个固定功能端点的设备。Gadget
  驱动可以被编写得易于移植到新硬件
- 足够灵活，可以暴露更复杂USB 设备能力，例如多配置、多接口、复合设备以  备用接口设置
- USB “On-The-Go”（OTG）支持，配合 Linux-USB 主机侧的更新
- Linux-USB 主机API 共享数据结构API 模型。这有助OTG 支持，并展望  更对称的框架（主机侧和设备侧驱动使用相同I/O 模型）
- 极简主义，因此更容易支持新的设备控制器硬件。I/O 处理不会对内存或 CPU 资源
  提出很高的要求
大多Linux 开发人员将无法使用API，因为他们在 PC、工作站或服务器中拥USB
`host`（主机）硬件。拥有嵌入式系统Linux 用户更可能拥USB 外设硬件。为了将
运行在此类硬件内部的驱动与更常见Linux “USB 设备驱动”（它们是真USB 设备主机侧代理）区分开来，使用了一个不同的术语：内嵌在外设中的驱动称为“USB gadget
驱动”。在 USB 协议交互中，设备驱动是主设备（或“client driver”），gadget 驱动
是从设备（或“function driver”）
gadget API 类似于主机侧 Linux-USB API，两者都使用请求对象队列来打I/O 缓冲区，
并且这些请求可以被提交或取消。它们共享标USB **Chapter 9**（第 9 章）消息、结和常量的通用定义。此外，两个 API 都将驱动绑定到设备以及从设备解绑。这API 细节上有所不同，因为主机侧当前URB 框架暴露了许多不适合 gadget API 的实现细和假设。虽然控制传输和配置管理的模型必然不同（一侧是硬件无关的主设备，另一侧是
硬件感知的从设备），但这里使用的端点 I/O API 也应该可以用于一个开销降低的主机侧
API銆。

核心 API 并没有暴露每一个可能的硬件特性，只暴露了最广泛可用的那些。有一些重要的硬件
特性，例如设备到设备的 DMA（无需在内存缓冲区中临时存储），将使用特定于硬件的 API
添加
API 允许驱动使用条件编译来处理不同硬件的端点能力，但并不要求这样做。硬件往往任意的限制，涉及传输类型、寻址、包大小、缓冲和可用性。通常，这些差异只对处理设配置和管理的“端点零”逻辑有影响。该 API 支持通过端点的命名约定进行有限的能力运行检测。许多驱动至少能够部分地自动配置自身。特别是，驱动初始化部分通常会有端点自动
配置逻辑，扫描硬件的端点列表以找到符合驱动要求的端点（依赖那些约定），以消除一最常见需要进行条件编译的原因
Linux-USB 主机API 类似，此 API 暴露USB 消息的“块状（chunky）”特性：I/O
请求是以一个或多个“包”为单位，并且包的边界对驱动可见。与 RS-232 串行协议相比，USB
更类似于同步协议（如 HDLC：每N 字节、多点寻址、主机为主站而设备为次站），而非
异步协议（tty 风格：每8 个数据位、无奇偶校验 个停止位）。因此，例如控制器驱不会将两个单字节写入缓冲成一个两字节USB IN 包，尽管 gadget 驱动在实现的协议中包
边界（和“短包”）不重要时可以这样做
### 驱动生命周期


Gadget 驱动向硬件发出端I/O 请求时无需了解硬件的许多细节，但驱动的 setup/配置代码
需要处理一些差异。按如下方式使用 API
1. 为特定的设备usb 控制器硬件注册一个驱动，例如 PCI 上的 net2280（USB 2.0）   Linux PDA 中的 sa11x0 pxa25x 等等。此时设备逻辑上处USB ch9 初始状   （`attached`），不消耗电力且不可用（因为它尚不支持枚举）。任何主机都不应看到   设备，因为它尚未激活主机用于检测设备的数据pullup，即VBUS 电源可用
2. 注册一个实现更高层设备功能gadget 驱动。随后它bind() 到一`usb_gadget`   在检测到 VBUS 之后的某个时刻激活数据线 pullup
3. 硬件驱动现在可以开始枚举。它处理的步骤是接受 USB `power` `set_address` 请求   其他步骤gadget 驱动处理。如gadget 驱动模块在主机开始枚举之前被卸载，则步骤
   7 之前的步骤会被跳过
4. gadget 驱动`setup()` 调用返回 usb 描述符，基于总线接口硬件提供的功能以及正   实现的功能。这可能涉及备用设置或配置，除非硬件阻止此类操作。对OTG 设备，每   配置描述符都包含一OTG 描述符
5. gadget 驱动处理枚举的最后一步，USB 主机发出 `set_configuration` 调用时。它启用
   该配置中使用的所有端点，所有接口都处于其默认设置。这涉及使用硬件的端点列表，根据
   其描述符启用每个端点。它可能还涉及使`usb_gadget_vbus_draw` 来允许从 VBUS 抽取
   更多电力，如该配置所允许的。对OTG 设备，设置一个配置还可能涉及通过用户界面报告
   HNP 能力
6. 做真正的工作并执行数据传输，可能涉及接口设置的改变或切换到新配置，直到设备从主机
   disconnect()（断开连接）。向每个端点排队任意数量的传输请求。在被断开连接之前，它
   可能会被挂起和恢复多次。断开连接时，驱动回到步骤 3（上文）
7. gadget 驱动模块被卸载时，会发出驱动unbind() 回调。这使得控制器驱动可以被
   卸载
驱动通常被安排成这样：只要加gadget 驱动模块（或静态链接到 Linux 内核）就允许外设
被枚举，但有些驱动会推迟枚举，直到某个更高层的组件（如用户态守护进程）启用它。注意在
这个最低层，除了应当服USB 规范之外，关于如何实ep0 配置逻辑没有任何策略。此问题属于 gadget 驱动的范畴，包括了解某些 USB 控制器所施加的实现约束，或理解复合设可能是通过集成可复用组件构建的
注意，上述生命周期对OTG 设备可能略有不同。除了在每个配置中提供额外的 OTG 描述之外，只有与 HNP 相关的差异对驱动代码特别可见。它们涉及在 `SET_CONFIGURATION` 请求
期间的报告要求，以及在某个挂起回调中调用 HNP 的选项。此外，SRP 略微改变`usb_gadget_wakeup` 的语义

## Gadget 驱动


除了 **Gadget Zero**（主要用于配usb 控制器硬件驱动进行测试和开发）之外，还存在
其他 gadget 驱动
有一`ethernet` gadget 驱动，它实现了最有用**Communications Device Class**
（CDC，通信设备类）模型之一。电缆调制解调器互操作性标准之一甚至规定使用此以太网模型
作为两个强制选项之一。使用此代码gadget USB 主机看来就像一个以太网适配器。它
提供对网络的访问，其gadget CPU 是一个主机，可以很容易地桥接、路由或防火墙其网络的访问。由于某些硬件无法完全实CDC 以太网要求，此驱动还实现了一个“仅好部分”的
CDC 以太网子集。（该子集不将自己宣传为 CDC 以太网，以避免产生问题。）

Microsoft `RNDIS` 协议的支持由 Pengutronix Auerswald GmbH 贡献。这类似CDC
以太网，但能运行在更多的 USB 硬件上（但少CDC 子集）。然而，它的主要出名之处是能使用 Microsoft 捆绑并支持的驱动直接连接到最近版本的 Windows，从而大大简化了Windows
的网络连接
还有对使`gadgetfs` 的用户gadget 驱动的支持。这提供了一**用户API**，将每个
端点呈现为单个文件描述符。I/O 使用普通的 `read()` `write()` 调用完成。熟悉的工具GDB pthreads 可用于开发和调试用户态驱动，因此一旦有了健壮的控制器驱动，许多针对的应用就不需要新的内核态软件。Linux 2.6 **异步 I/O（AIO* 支持可用，因此用户软件可以仅以比内核驱动略高的开销来流式传输数据
有一USB 大容量存储类驱动，它为与 MS-Windows MacOS 等系统的互操作性提供了不同解决方案。该 **Mass Storage**（大容量存储）驱动使用文件或块设备作为驱动器的后端存储，
就像 `loop` 驱动一样。USB 主机使用大容量存储类规范BBB、CB CBI 版本，使用透明
SCSI 命令从后端存储访问数据
有一个“serial line”（串行线）驱动，对通过 USB 进行 TTY 风格的操作很有用。该驱动的最版本支持 CDC ACM 风格的操作，就像一USB 调制解调器，因此在大多数硬件上它可以轻松MS-Windows 互操作。该驱动的一个有趣用途是在引导固件（BIOS）中，它有时可以在没真正串行线的非常小的系统上使用此模型
随着此驱动框架的演进，预计未来会开发并贡献对其他种gadget 的支持
## USB On-The-Go (OTG)


Linux 2.6 上的 USB OTG 支持最初由 Texas Instruments `OMAP <http://www.omap.com>`__
16xx 17xx 系列处理器开发。其OTG 系统应该以类似的方式工作，但硬件级别的细节可非常不同
系统需要专门的硬件支持来实OTG，特别是包括一个特殊的 **Mini-AB** 插座和相关的收发以支**双角色（Dual-Role* 操作：它们可以充当主机（使用标准Linux-USB 主机驱动栈），也可以充当外设（使用此 `gadget` 框架）。为此，系统软件依赖于对这些编程接口
的小幅添加，以及一个影响哪个驱动栈连接OTG 端口的新内部组件（这里称为“OTG
控制器”）。在每个角色中，系统都可以复用现有的硬件无关驱动池，这些驱动位于控制器驱接口（`usb_bus` `usb_gadget`）之上。此类驱动最多需要微小的更改，并且为支持 OTG 添加的大多数调用也可以使OTG 产品受益
- Gadget 驱动测试 `is_otg` 标志，并使用它来决定是否在其每个配置中包OTG 描述符
- Gadget 驱动可能需要更改以支持两个新的 OTG 协议，这些协议暴露在诸如 `b_hnp_enable`
  标志等新gadget 属性中。HNP 支持应该通过用户界面报告（两LED 可能就足够了），并且
  在某些情况下当主机挂起外设时触发。SRP 支持可以由用户发起，就像远程唤醒一样，可能通过
  按下同一个按钮
- 在主机侧，需要教USB 设备驱动在适当时刻使用 `usb_suspend_device()` 触发 HNP。这  节省电池电量，即使对于非 OTG 配置也很有用
- 同样在主机侧，驱动必须支OTG “Targeted Peripheral List”。那只是一个白名单，用  拒绝给定 Linux OTG 主机不支持的外设此白名单是产品特定的；每个产品必须修
  `otg_whitelist.h` *以匹配其互操作性规范
