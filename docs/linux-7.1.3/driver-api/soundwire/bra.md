## 批量寄存器访问（BRA

### 约定


本文档中使用的大写单词是有意为之，指SoundWire 1.x 规范中的概念
### 简

SoundWire 1.x 规范提供了一种机制，通过回收部分音频带宽来加速命控制传输。批量寄存器访问（BRA）协议是基于批量有效载荷传输（BPT）定义的标准解决方案
常规控制通道使用 Column 0，每帧只能通过读命令发获取一个字节。在典型48kHz 帧率下，只能传输 48kB/s
可选的批量寄存器访问能力最高可传输 12 Mbits/s，并将传输时间缩短几个数量级，但存在多重设计约束
  (1) 每个帧只能支持一次读或一次写传输，每帧有 10 字节的开销（头部与尾部响应）
  (2) 写应当针对同一帧中连续的寄存器地址。碎片化的寄存器空间会因需要在不同帧中调度多次 BRA 传输而降低协议效率
  (3) 目标外设设备应当支持可选的数据端口 0（Data Port 0），同样管理器应当暴露类似音频的端口，以使用采样间隔（Sample Interval）、HSTART、HSTOP 等概念将 BRA 数据包插入音频有效载荷
  (4) BRA 传输效率取决于可用带宽。如果没有正在进行的音频传输，整个帧减去 Column 0 的部分都可被回收用于 BRA。帧形状也会影响效率：由Column 0 不能用于 BTP/BRA，帧应依赖大量的列并尽量减少行数。总线时钟应尽可能高
  (5) 每帧传输的比特数应当8 位的整数倍。如有必要，应在数据末尾插入填充位
  (6) 常规写命令可以与 BRA 传输并行发出。这便于（例如）处理告警、插孔检测或在固件下载期间改变音量，但必须避免用两种独立协议访问同一地址，以免产生未定义行为
  (7) 某些实现可能无法处理 BRA 协议的带宽，例如SoundWire IP 背后是一条慢I2C 总线时。在这种情况下，传输可能需要在时间上间隔开或进行流控
  (8) 每个 BRA 数据包在传输有效数据时应被标记为“Active”。这允许软件分配一BRA 流，但在处理结果或准备下一批数据、或允许外设处理先前的传输时，不传输/丢弃数据。此外，BRA 传输可以在数据尚未就绪时就提前开始
  (9) 每帧最多可传输 470 字节
  (10) 地址32 位表示，不依Column 0 中常规命控制协议所使用的分页寄存器

### 错误检

固件下载是批量寄存器访问协议的关键用途之一。为确保二进制数据的完整性不受传输或编程错误影响，每BRA 数据包提供：

  (1) 7 字节头部CRC。该 CRC 帮助外设设备检查其是否被寻址，并设置起始地址与字节数。外设设备在字节 7 中提供响应
  (2) 对数据块（不含头部）CRC。该 CRC 作为数据包中倒数第二个字节传输，位于尾部响应之前
头部响应可以是以下之一  (a) Ack（确认）
  (b) Nak（否认）
  (c) Not Ready（未就绪
尾部响应可以是以下之一  (1) Ack（确认）
  (2) Nak（CRC 失败  (3) Good（操作完成）
  (4) Bad（操作失败）

### 寻址限制


头部中指定的设备号遵SoundWire 定义，允许广播与组寻址。目Linux 实现只允许一次对单个设备进行单个 BPT 传输。这可能在以后作为一个优化被重新审视，以便将相同固件发送给多个设备，但这仅对单链路方案有益
在多个外设设备连接到不同管理器的情况下，SoundWire 规范不支持广播与组寻址。每个设备必须通过独立BRA 流处理，可能并行进行——这些链路是真正独立的
### 不支持的特

批量寄存器访问规范提供了若干已知实现中不支持的能力，例如
  (1) 由外设设备发起的传输。BRA 发起者始终是管理器设备
  (2) 基于“NotReady”头部响应的流控能力与重传需要在 SoundWire IP 中额外的缓冲，尚未实现
### 双向处理


BRA 协议既能处理写也能处理读，在每个数据包中头部与尾部响应由外设目标设备提供。在外设设备上，BRA 协议由单DP0 数据端口处理，在底层，总线所有权会在头部/尾部响应以及读期间传输的数据上发生改变
在主机侧，大多数实现依赖一种类似端口的概念，使用两FIFO 并行地消产生数据传输（主机→外设 外设→主机）。这FIFO 消费/产生的数据量并不对称，因此硬件通常会插入标记以帮助软件与硬件解释原始数
每个数据包通常具有
  (1) 一个“包起始”（Start of Packet）指示符
  (2) 一个“包结束”（End of Packet）指示符
  (3) 一个包标识符，用于关联请求与传输的数据，以及每帧的错误状
硬件实现可以在帧级别检查错误，并在出错时重试传输。然而，与流控情况一样，这需要在硬件中有额外的缓冲与智能。Linux 的支持假设：如果在某个响应中检测到单个错误，整个传输将被取消
#### 所需的抽

管理器层面没有标准寄存器或强制实现，因此底层BPT/BRA 细节必须隐藏在管理器特定的代码中。例如，编解码器驱动并不知道上面提到Cadence IP 格式
同样，编解码器驱动不必知道帧大小。CRC 的计算与响应的处理由辅助函数和管理器特定的代码处理
主机 BRA 驱动也可能对DMA 分配的页或其他主DSP 通信协议有限制。编解码器驱动不应知晓这些限制中的任何一个，因为它可能会与不同实现的管理IP 结合复用
#### BRA 与常规读/写之间的并发


现有'nread/nwrite' API 已经依赖于起始地址与字节数的概念，因此可以扩展API，增加一个请求使BPT/BRA 的“提示”（hint）
然BRA 传输可能相当长，而常规读/写与 BRA 共用一个互斥锁则是个大问题。控命令BRA 传输的独立运行是一项基本要求，例如要在下载固件的同时用现有regmap 接口改变音量级别。不过，集成必须确保命令/控制协议BRA 协议不会并发访问同一地址
此外sdw_msg' 结构硬编码了16 位地址与分页寄存器的支持，而这基于原生 32 位地址BPT/BRA 支持无关。使用一个独立的、带 'sdw_bpt_msg' API 更有意义
加速所有初始化任务的一种可能策略是：先启动一个用于固件下载的 BRA 传输，然后与命令通道并行处理所有“常规”读/写，最后等BRA 传输完成。这将允许一定程度的重叠，而非纯粹的串行方案。因此，BRA API 必须支持异步传输，并暴露一个独立的等待函数

### 外设/总线接口


BPT/BRA 的总线接口由两个函数组成：

    - sdw_bpt_send_async(bpt_message)

      该函数使用管理器实现定义的能力（通常DMA IPC 协议）发送数据
      目前不支持排队，调用者需要等待所请求传输的完成
   - sdw_bpt_wait()

      该函数等待编解码器驱动在 'send_async' 阶段提供的整个消息。较小分块的中间状态不会返回给编解码器驱动，只会提供一个返回码
#### Regmap 的使

现有的编解码器驱动依regmap 将固件下载到外设。regmap 暴露的异步接口与上述 send/wait API 类似，因此在高层BRA regmap 结合似乎是自然的。regmap 层可以检BRA 是否可用，在不可用的情况下使用常规的写命令通道。regmap 的集成将在第二步处理
### BRA 流模

对于常规音频传输，machine 驱动暴露一个连CPU DAI Codec DAI dailink
该模型对 BRA 支持并非必需
   (1) SoundWire DAI 主要SoundWire 数据端口的封装，其背后可能带有一些模拟或音频转换能力。在 BRA 的语境中，DP0 是目的地。DP0 寄存器是标准的，可以在不知道每个链路连接了什么外设的情况下盲目编程。此外，如果一个链路上有多个外设，其中一些不支持 DP0，那么对 DP0 寄存器编程的写命令将产生无害COMMAND_IGNORED 响应，这些响应会与支DP0 的外设的响应进行线或（wired-OR）。换言之，DP0 编程可以用广播命令完成，而目标设备的信息只需BRA 头部中添加
   (2) CPU 层面，DAI 概念BRA 没有用处；machine 驱动不会创建依赖 DP0 dailink。唯一需要的概念是端口（port）的概念
   (3) 流的概念依赖一master_rt slave_rt 概念。所有这些实体都表示端口而非 DAI
   (4) 假设每个链路使用一BRA 流，那么该流可以连接主端口以及所有外设的 DP0 端口
   (5) BRA 传输只在单个管理链路的语境中有意义，因此 BRA 流处理不依赖常规 DAI 链路所允许多链路聚合的概念
### 音频 DMA 支持


某些 DMA（如 HDaudio）需要设置一个音频格式字段。该格式进而用于定义可接受的突发传输。BPT/BRA 支持与这些定义并非完全兼容，因为格式与带宽在读写命令之间可能变化
此外，在 Intel 平台HDaudio 上，DMA 需要用BPT/BRA 传输带宽匹配PCM 格式来编程。该格式基于 192kHz 32 位采样，通道数随带宽调整而变化。通道的概念完全是名义上的，因为数据并非典型音PCM。对这些通道编程有助于预留足够带宽并调整 FIFO 大小以避免欠载（xruns）
对齐要求目前在核心层面未强制，而在平台层面强制，例如对 Intel 而言数据大小必须等于或大16 字节
