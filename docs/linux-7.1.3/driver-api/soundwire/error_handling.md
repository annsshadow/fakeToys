## SoundWire 错误处理


SoundWire PHY 经过了精心设计，总线上的错误非常罕见，即便发生也应仅限于单比特错误这一设计的例子可见于同步机制（两次错误后同步丢失）以及用于批量寄存器访问的短 CRC
错误可通过多种机制检测：

1. 总线冲突（Bus clash）或奇偶错误：该机制依赖与负载及用途无关的低层检测器，覆   控制数据与音频数据。当前实现仅记录此类错误。改进方向可以是使整个编程序列失效并   已知位置重新开始。如果此类错误发生在控制/命令序列之外，SoundWire 协议没有为音   数据提供隐藏或恢复机制，错误的位置也会影响其可听度（PCM 中最高有效位受影响更大）   且在检测到若干此类错误后总线可能会被重置。注意，由于编程错误（两个数据流使用相同   位时隙）或收发切换期间的电气问题所导致的“总线冲突”无法区分，尽管在音频开启时反复
   出现的总线冲突是总线分配有问题的一个迹象。中断机制也有助于识别检测到总线冲突或奇   错误的从设备，但它们可能并不对错误负责，因此单独重置它们并非可行的恢复策略
2. 命令状态：每个命令都关联一个状态，仅覆盖设备间数据的传输。ACK 状态表示命令已   收到，并将在当前帧结束前执行。NAK 表示命令出错，将不会被执行。在错误编程（向不存在的
   从设备或未实现的寄存器发送命令）或电气问题的情况下，没有响应意味着命令被忽略。某  主设备实现允许命令重传若干次。如果重传失败，回溯并重启整个编程序列可能是一种解决方案  或者，某些实现可能直接发起总线重置并重新枚举所有设备
3. 超时：在许多情况下（ChannelPrepare ClockStopPrepare），总线驱动应轮询某   寄存器字段，直到其转换到 NotFinished 值为零。MIPI SoundWire 规范 1.1 没有定义超时   MIPI SoundWire DisCo 文档增加了关于超时的建议。如果此类配置未能完成，驱动将返   -ETIMEOUT。此类超时是从设备故障的症状，很可能无法恢复
全局重配置序列期间的错误极难处理
1. BankSwitch：在发出 BankSwitch 的最后一条命令期间出现错误很难回溯。在单段（segment   设置中重Bank Switch 命令也许是可能的，但在启用多个总线段时这会导致同步问题（带   副作用的命令，例如帧重配置，会在不同时间被处理）。全局硬重置可能是最佳解决方案
