## DMAengine 控制器文档


## 硬件简介


大多数 Slave DMA 控制器都遵循相同的一般操作原则。

它们拥有一定数量的通道可用于 DMA 传输，以及一定数量的请求线。

请求与通道在很大程度上是正交的。通道可用于服务于任意请求。简而言之，通道是执行复制操作的实体，而请求则涉及相关的端点。

请求线实际上对应于从支持 DMA 的设备连到控制器本身的物理线路。每当设备想要启动一次传输时，它会通过拉高该请求线来发出一个 DMA 请求（DRQ）。

一个非常简单的 DMA 控制器只会考虑单个参数：传输大小。在每个时钟周期，它会将一个字节的数据从一个缓冲区搬到另一个缓冲区，直到达到传输大小为止。

这在现实世界中并不好用，因为从设备可能要求在单个周期内传输特定数量的位。例如，在进行简单的存储器复制操作时，我们可能希望传输物理总线允许的最大数据量以最大化性能，但我们的音频设备可能拥有更窄的 FIFO，要求数据每次恰好按 16 或 24 位写入。这就是为什么几乎所有 DMA 控制器都能通过调整一个称为传输宽度的参数来适应这种情况。

此外，某些 DMA 控制器在把 RAM 用作源或目标时，可以将存储器中的多次读或写操作归组到一个缓冲区中，从而避免大量低效的小块内存访问，转而获得若干更大的传输。这是通过一个称为突发大小（burst size）的参数实现的，它定义了在不将传输拆分为更小子传输的前提下，控制器允许执行的单次读/写次数。

我们的理论 DMA 控制器随后将只能执行涉及单个连续数据块的传输。然而，我们常见的一些传输并非如此，而是希望把数据从非连续缓冲区复制到连续缓冲区，这称为分散-聚集（scatter-gather）。

DMAEngine，至少对于 mem2dev 传输，要求支持分散-聚集。因此我们面临两种情况：要么我们有一个相当简单的、不支持它的 DMA 控制器，必须在软件中实现它；要么我们有一个更先进的、在硬件中实现分散-聚集的 DMA 控制器。

后者通常使用一组待传输的数据块进行编程，每当传输启动后，控制器会遍历该集合，执行我们在其中编程的操作。

该集合通常是一个表或链表。然后你会推送该表的地址及其元素个数，或者把链表的第一个元素推送到 DMA 控制器的某个通道；每当有 DRQ 被拉高时，它就会遍历该集合以得知从哪里获取数据。

无论哪种方式，该集合的格式完全取决于你的硬件。每个 DMA 控制器都需要不同的结构，但它们全部都要求：对于每个数据块，至少需要源地址和目标地址、是否应对这些地址做递增，以及我们之前见过的三个参数：突发大小、传输宽度和传输大小。

最后一点是：通常从设备默认不会发出 DRQ，你必须在从设备驱动中先将其使能，然后才能使用 DMA。

上面讲的只是一般的存储器到存储器（也称 mem2mem）或存储器到设备（mem2dev）类型的传输。大多数设备还支持 dmaengine 所支持的其他类型传输或内存操作，本文档后续会详述。

## Linux 中的 DMA 支持


历史上，DMA 控制器驱动是使用 async TX API 实现的，用于卸载诸如内存复制、XOR、加密等操作——基本上任何内存到内存的操作。

随着时间的推移，出现了对内存到设备传输的需求，dmaengine 也随之扩展。如今，async TX API 被编写为 dmaengine 之上的一层，并充当其客户端。尽管如此，dmaengine 在某些情况下仍兼容该 API，并做出了一些设计选择以确保其保持兼容。

有关 Async TX API 的更多信息，请参阅 Documentation/crypto/async-tx-api.rst 中的相关文档。

## DMAEngine API


### ``struct dma_device`` 初始化


与任何其他内核框架一样，整个 DMAEngine 的注册都依赖于驱动填充一个结构体并向框架注册。在我们的例子中，该结构体是 dma_device。

在你的驱动中，首先需要做的是分配这个结构体。任何常用的内存分配器都可以，但你还需要初始化其中的几个字段：

- `channels`：应使用例如 INIT_LIST_HEAD 宏初始化为一个链表

- `src_addr_widths`：
  应包含一个所支持的源传输宽度的位掩码

- `dst_addr_widths`：
  应包含一个所支持的目标传输宽度的位掩码

- `directions`：
  应包含一个所支持的从设备方向的位掩码
  （即排除 mem2mem 传输）

- `residue_granularity`：
  上报给 dma_set_residue 的传输残差（residue）的粒度。
  可以是以下之一：

  - Descriptor（描述符）：
    你的设备不支持任何形式的残差上报。
    框架只能知道某个特定的事务描述符已完成。

  - Segment（段）：
    你的设备能够上报哪些数据块已被传输

  - Burst（突发）：
    你的设备能够上报哪些突发已被传输

- `dev`：应持有指向与当前驱动实例相关联的 `struct device` 的指针。

### 支持的事务类型


接下来你需要设置你的设备（及驱动）支持哪些事务类型。

我们的 `dma_device structure` 中有一个名为 cap_mask 的字段，用于保存所支持的各种事务类型；你需要使用 dma_cap_set 函数并传入相应的标志来修改这个掩码，具体标志取决于你所支持的事务类型。

所有这些能力都定义在 `dma_transaction_type enum` 中的 `include/linux/dmaengine.h`

目前可用的类型有：

- DMA_MEMCPY

  - 设备能够执行内存到内存的复制

  - 无论源和目标的合并数据块整体大小如何，实际只会传输两者中较小的那个字节数。这意味着两个列表中分散-聚集缓冲区的数量和大小不必相同，并且该操作在功能上等价于 `strncpy`，其中 `count` 参数等于两个分散-聚集列表缓冲区中较小的总大小。

  - 它通常用于在主机内存与内存映射的 GPU 设备内存（例如现代 PCI 视频显卡上的内存）之间复制像素数据。最直接的例子是 OpenGL API 函数 `glReadPixels()`，它可能需要把庞大的帧缓冲从本地设备内存逐字复制到主机内存。

- DMA_XOR

  - 设备能够在内存区域上执行 XOR 运算

  - 用于加速 XOR 密集型任务，例如 RAID5

- DMA_XOR_VAL

  - 设备能够使用 XOR 算法对内存缓冲区执行奇偶校验。

- DMA_PQ

  - 设备能够执行 RAID6 P+Q 计算，其中 P 为简单的 XOR，Q 为 Reed-Solomon 算法。

- DMA_PQ_VAL

  - 设备能够使用 RAID6 P+Q 算法对内存缓冲区执行奇偶校验。

- DMA_MEMSET

  - 设备能够用提供的模式填充内存

  - 该模式被视为单字节有符号值。

- DMA_INTERRUPT

  - 设备能够触发一个空传输，以产生周期性中断

  - 客户端驱动用它来注册一个回调函数，该回调会通过 DMA 控制器中断被定期调用

- DMA_PRIVATE

  - 设备仅支持从设备传输，因此不可用于异步传输。

- DMA_ASYNC_TX

  - 设备支持异步的内存到内存操作，包括 memcpy、memset、xor、pq、xor_val 和 pq_val。

  - 该能力由 DMA 引擎框架自动设置，设备驱动不得手动配置。

- DMA_SLAVE

  - 设备能够处理设备到内存的传输，包括分散-聚集传输。

  - 在 mem2mem 的场景中，我们用两种不同的类型来分别处理单个待复制数据块或一组数据块；而在这里，我们只有一个事务类型，它应当同时处理两种情况。

  - 如果你想传输单个连续内存缓冲区，只需构建一个只含一项的分散列表即可。

- DMA_CYCLIC
  - 设备能够处理循环传输。

  - 循环传输是指数据块集合会循环自身，最后一个元素指向第一个元素。

  - 它通常用于音频传输，在这种场景中你希望对一个填充了音频数据的单一环形缓冲区进行操作。

- DMA_INTERLEAVE

  - 设备支持交错传输。

  - 这类传输可以把数据从非连续缓冲区传输到非连续缓冲区，这与 DMA_SLAVE 不同，后者是把数据从非连续数据集传输到连续的目标缓冲区。

  - 它通常用于 2D 内容传输，此时你希望把一部分未压缩数据直接传输到显示器上以进行显示。

- DMA_COMPLETION_NO_ORDER

  - 设备不支持按序完成。

  - 如果设备设置了该能力，驱动应在 device_tx_status 中返回 DMA_OUT_OF_ORDER。

  - 如果设备导出了该能力，所有 cookie 跟踪与检查的 API 都应视为无效。

  - 目前，这与 dmatest 的轮询选项不兼容。

  - 如果设置了该能力，建议用户为发送给 DMA 设备的每个描述符提供一个唯一标识符，以便正确跟踪完成情况。

- DMA_REPEAT

  - 设备支持重复传输。重复传输由 DMA_PREP_REPEAT 传输标志标识，它与循环传输类似，都会在结束时自动重复，但额外可以由客户端替换。

  - 该特性仅限于交错传输，因此如果未设置 DMA_INTERLEAVE 标志，则不应设置此标志。这一限制基于 DMA 客户端当前的需求；若未来确有需要，应增加对更多传输类型的支持。

- DMA_LOAD_EOT

  - 设备支持在传输结束（EOT）时通过排队一个设置了 DMA_PREP_LOAD_EOT 标志的新传输来替换重复传输。

  - 基于 DMA 客户端的需求，未来将增加对在当前运行中的传输的其他位置（例如突发结束而非传输结束）进行替换的支持，若有需要即会加入。

这些不同的类型也会影响源地址和目标地址随时间的变化方式。

指向 RAM 的地址通常在每次传输后递增（或递减）。在环形缓冲区的情形中，它们可能循环（DMA_CYCLIC）。指向设备寄存器（例如一个 FIFO）的地址通常是固定的。

### 每个描述符的元数据支持


某些数据移动架构（DMA 控制器与外设）会使用与事务相关联的元数据。DMA 控制器的职责是把有效载荷以及元数据一并传输。
元数据本身并不被 DMA 引擎使用，但它包含外设所需或从外设获得的参数、密钥、向量等。

DMAengine 框架提供通用方式来便利描述符的元数据。根据架构不同，DMA 驱动可以实现其中一种或两种方法，并由客户端驱动自行选择使用哪一种。

- DESC_METADATA_CLIENT

  元数据缓冲区由客户端驱动分配/提供，并通过 dmaengine_desc_attach_metadata() 辅助函数附加到描述符上。

  对于这种模式，DMA 驱动应满足以下要求：

  - DMA_MEM_TO_DEV / DEV_MEM_TO_MEM

    应准备好所提供的元数据缓冲区中的数据，以便 DMA 控制器将其与有效载荷数据一并发送。可以通过复制到硬件描述符，或以高度耦合的数据包形式实现。

  - DMA_DEV_TO_MEM

    在传输完成时，DMA 驱动必须在通知客户端完成之前，将元数据复制到客户端提供的元数据缓冲区中。传输完成后，DMA 驱动不得再触碰客户端提供的元数据缓冲区。

- DESC_METADATA_ENGINE

  元数据缓冲区由 DMA 驱动分配/管理。客户端驱动可以查询元数据缓冲区的指针、最大大小以及当前已用大小，并可直接更新或读取它。框架提供了 dmaengine_desc_get_metadata_ptr() 和 dmaengine_desc_set_metadata_len() 作为辅助函数。

  对于这种模式，DMA 驱动应满足以下要求：

  - get_metadata_ptr()

    应返回元数据缓冲区的指针、元数据缓冲区的最大大小，以及缓冲区中当前已用/有效的字节数（若有）。

  - set_metadata_len()

    由客户端在把元数据放入缓冲区后调用，以告知 DMA 驱动所提供的有效字节数。

  注意：由于客户端会在完成回调（DMA_DEV_TO_MEM 情形）中请求元数据指针，DMA 驱动必须确保
描述符在回调被调用之前不会被释放。

### 设备操作


我们的 dma_device 结构体还需要一些函数指针，以实现真正的逻辑——既然我们已经描述了能够执行哪些操作。

我们必须在此填充、因而也必须实现的函数，显然取决于你之前上报所支持的事务类型。

- `device_alloc_chan_resources`

- `device_free_chan_resources`

  - 每当某个驱动第一次对与该驱动相关联的通道调用 `dma_request_channel` 或 `dma_release_channel` 时，就会调用这些函数。

  - 它们负责分配/释放该通道为你的驱动所用所需的全部资源。

  - 这些函数可以睡眠。

- `device_prep_dma_*`

  - 这些函数与你之前注册的能力相对应。

  - 这些函数都接收与正在准备的传输相关的缓冲区或分散列表，并应据此创建一个硬件描述符或一组硬件描述符。

  - 这些函数可以在中断上下文中被调用。

  - 你可能做的任何分配都应使用 GFP_NOWAIT 标志，以避免潜在睡眠，同时也不要耗尽紧急内存池。

  - 驱动应尽量在探测（probe）阶段预分配传输 setup 期间可能需要的任何内存，以免给 nowait 分配器带来过大压力。

  - 它应返回一个唯一的 `dma_async_tx_descriptor structure` 实例，该实例进一步表示这次特定的传输。

  - 这个结构体可以使用 `dma_async_tx_descriptor_init` 函数进行初始化。

  - 你还需要在该结构体中设置以下字段：

    - flags（标志）：
      TODO：它能否被驱动本身修改，还是应当始终使用作为参数传入的 flags？

    - tx_submit：指向一个你需要实现的函数，它应将当前事务描述符推入一个挂起队列，等待 issue_pending 被调用。

    - phys：描述符的物理地址，DMA 引擎稍后会用它来读取描述符并启动传输。

  - 在该结构体中，可以初始化函数指针 callback_result，以便提交者获知某个事务已完成。早期代码中曾使用函数指针 callback，但它不向事务提供任何状态，因此将被废弃。传入 callback_result 的结果结构体定义为 `dmaengine_result`，它包含两个字段：

    - result（结果）：提供由 `dmaengine_tx_result` 定义的传输结果，即成功或某种错误状态。

    - residue（残差）：为那些支持残差的传输提供剩余字节数。

- `device_prep_peripheral_dma_vec`

  - 与 `device_prep_slave_sg` 类似，但它接收一个指向 `dma_vec` 结构体数组的指针，该数组（长远来看）将取代分散列表。

- `device_issue_pending`

  - 取出挂起队列中的第一个事务描述符并启动传输。该传输完成后，应移动到列表中的下一个事务。

  - 此函数可以在中断上下文中被调用。

- `device_tx_status`

  - 应报告给定通道上剩余待处理的字节数。

  - 只应关心作为参数传入的事务描述符，而非给定通道上当前活动的那个。

  - tx_state 参数可能为 NULL。

  - 应使用 dma_set_residue 来上报。

  - 在循环传输的情形中，只应考虑循环缓冲区的总大小。

  - 如果设备不支持按序完成、并且是乱序完成操作，应返回 DMA_OUT_OF_ORDER。

  - 此函数可以在中断上下文中被调用。

- device_config

  - 使用作为参数传入的配置重新配置通道。

  - 该命令不应同步执行，也不应作用于任何当前已排队的传输，而只作用于后续传输。

  - 在这种情况下，函数会接收到一个 `dma_slave_config`
    结构体指针作为参数，该指针会说明要使用哪种配置。

  - 尽管该结构体包含一个 direction 字段，但此字段已被废弃，改用传给 prep_* 函数的 direction 参数。

  - 该调用仅对从设备操作是强制的。对于 memcpy 操作，不应设置也不应期望被设置。如果某个驱动同时支持两者，它应仅将该调用用于从设备操作，而不用于 memcpy 操作。

- device_pause

  - 暂停通道上的传输。

  - 该命令应在通道上同步操作，立即暂停给定通道的工作。

- device_resume

  - 恢复通道上的传输。

  - 该命令应在通道上同步操作，立即恢复给定通道的工作。

- device_terminate_all

  - 中止通道上所有挂起和正在进行的传输。

  - 对于被中止的传输，不应调用 complete 回调。

  - 可以在原子上下文或某个描述符的 complete 回调内部被调用。不得睡眠。驱动必须能够正确处理这种情况。

  - 终止可以是异步的。驱动不必等待当前活动的传输完全停止。参见 device_synchronize。

- device_synchronize

  - 必须将通道的终止与当前上下文同步。

  - 必须确保 DMA 控制器不再访问之前已提交的描述符所用的内存。

  - 必须确保之前已提交描述符的所有 complete 回调都已经运行完毕，且没有仍在排期中。

  - 可以睡眠。


## 杂项说明


（一些应当被记录、但又确实不知道该放在何处的内容）

`dma_run_dependencies`

- 应在一次异步 TX 传输的末尾被调用，在从设备传输的场景中可忽略。

- 确保在将其标记为完成之前，依赖的操作已经先运行。

dma_cookie_t

- 它是一个会随时间递增的 DMA 事务 ID。

- 自引入 `virt-dma` 将其抽象之后，已不太相关。

dma_vec

- 一个包含 DMA 地址和长度的小型结构体。

DMA_CTRL_ACK

- 如果清除，在客户端确认收到之前（即有机会建立任何依赖链之前），提供方不得复用该描述符。

- 可以通过调用 async_tx_ack() 来确认（ack）。

- 如果设置，并不意味着描述符可以被复用。

DMA_CTRL_REUSE

- 如果设置，描述符在完成之后可以被复用。若设置了该标志，提供方不应释放它。

- 应通过调用 `dmaengine_desc_set_reuse()` 来为复用准备描述符，该函数会设置 DMA_CTRL_REUSE。

- `dmaengine_desc_set_reuse()` 只有在通道支持可复用描述符（由能力标志体现）时才会成功。

- 因此，如果某个设备驱动想跳过两次传输之间的 `dma_map_sg()` 和 `dma_unmap_sg()`，因为 DMA 的数据并未被使用，它可以在传输完成后立即重新提交该传输。

- 描述符可以通过几种方式释放

  - 通过调用 `dmaengine_desc_clear_reuse()` 清除 DMA_CTRL_REUSE，并提交最后一次 txn。

  - 显式调用 `dmaengine_desc_free()`，这只有在 DMA_CTRL_REUSE 已设置时才会成功。

  - 终止通道。

- DMA_PREP_CMD

  - 如果设置，客户端驱动告诉 DMA 控制器，通过 DMA API 传入的数据是指令数据。

  - 指令数据的解释取决于具体的 DMA 控制器。它可用于向其他外设发出指令、进行寄存器读/写，此时描述符应采用与正常数据描述符不同的格式。

- DMA_PREP_REPEAT

  - 如果设置，传输在结束时会被自动重复，直到在同一个通道上排队一个带有 DMA_PREP_LOAD_EOT 标志的新传输为止。如果将在该通道上排队的下一个传输没有设置 DMA_PREP_LOAD_EOT 标志，当前传输会一直重复，直到客户端终止所有传输。

  - 仅当通道报告了 DMA_REPEAT 能力时，才支持该标志。

- DMA_PREP_LOAD_EOT

  - 如果设置，传输会在传输结束时替换当前正在执行的传输。

  - 这是非重复传输的默认行为，因此为非重复传输指定 DMA_PREP_LOAD_EOT 不会带来任何差别。

  - 在使用重复传输时，DMA 客户端通常需要为所有传输设置 DMA_PREP_LOAD_EOT 标志，否则通道会一直重复最后一个重复传输，并忽略正在排队的新传输。若未能设置 DMA_PREP_LOAD_EOT，看起来就像通道卡在上一个传输上。

  - 仅当通道报告了 DMA_LOAD_EOT 能力时，才支持该标志。

## 总体设计说明


你看到的大多数 DMAEngine 驱动都基于类似的设计：在中断处理程序中处理传输结束中断，但把大部分工作（包括在上一个传输结束后启动新传输）推迟到一个 tasklet 中。

不过这是一种相当低效的设计，因为传输间的延迟不仅包括中断延迟，还包括 tasklet 的调度延迟，这会使通道在两次传输之间处于空闲，从而降低整体传输速率。

你应当避免这种做法，与其在你的 tasklet 中挑选新传输，不如把那部分移动到中断处理程序中，以获得更短的空闲窗口（反正这个窗口我们也无法真正避免）。

## 术语表


- Burst（突发）：在刷入内存之前，可以排队到缓冲区中的若干连续读或写操作。

- Chunk（数据块）：一组连续的突发。

- Transfer（传输）：一组数据块（无论是否连续）。
