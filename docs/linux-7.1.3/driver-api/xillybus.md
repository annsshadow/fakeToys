## 简介


### 背景


FPGA（现场可编程门阵列）是一种逻辑硬件，可被编程为几乎任何通常以专用芯片组形式存在的部件：例如显示适配器、网络接口卡，甚至是带外设的处理器。FPGA 是硬件界的乐高：基于某些基本构件，你可以按自己喜欢的方式制作自己的玩具。重新实现市场上已有的芯片组通常没有意义，因此 FPGA 大多用于需要某些特殊功能、且产量相对较低（因此不值得开发 ASIC）的场合。

FPGA 的挑战在于一切都实现在非常低的层次，甚至比汇编语言还低。为了让 FPGA 设计者专注于自己的特定项目，而不是一遍遍重复造轮子，通常会使用预先设计的构件——IP 核。它们是 FPGA 版的库函数。IP 核可以实现某些数学函数、一个功能单元（如 USB 接口）、一整个处理器（如 ARM），或任何可能有用的东西。可把它们想象成一个构件，两侧悬着用于连接其他构件的电线。

FPGA 设计中最令人生畏的任务之一是与一个完整的操作系统（实际上是与运行它的处理器）通信：实现底层总线协议以及与主机（寄存器、中断、DMA 等）稍高层的接口本身就是一个项目。当 FPGA 的功能为人熟知（如显示适配卡或 NIC）时，专门为该项目的 FPGA 接口逻辑做设计是有意义的。这时会编写一个专门的驱动，将 FPGA 作为熟知接口呈现给内核和/或用户空间。在这种情况下，没有理由把 FPGA 与总线上的任何其他设备区别对待。

然而，期望的数据通信往往并不契合任何熟知的外设功能。而且，为数据交换设计一个优雅的抽象层通常被认为代价过大。在这些情况下，人们会寻求一种更快、可能不那么优雅的方案：驱动实际上被写成一个用户空间程序，内核空间部分只负责基本的数据传输。这仍然需要为 FPGA 设计一些接口逻辑，并编写一个简单的临时驱动给内核。

### Xillybus 概述


Xillybus 是一个 IP 核加一个 Linux 驱动。二者共同构成一套用于 FPGA 与主机之间基本数据传输的套件，提供具有简洁用户接口的、类似管道的的数据流。它旨在作为 FPGA-主机混合项目的低代价方案，在这种方案下，将驱动中项目特定的部分放在用户空间程序中运行是合理的。

由于不同 FPGA 项目之间的通信需求可能差异很大（每个方向所需的数据管道数量及其属性），并不存在单一的、作为 Xillybus IP 核的逻辑块。相反，IP 核根据最终用户给出的规格进行配置和构建。

Xillybus 呈现独立的数据流，对用户而言类似于管道或 TCP/IP 通信。在主机侧，使用字符设备文件，就像任何管道文件一样。在 FPGA 侧，使用硬件 FIFO 来传输数据。这与通过固定大小缓冲区通信的常用方法相反（尽管 Xillybus 在底层也使用了这类缓冲区）。单个 IP 核上可以有上百个这样的数据流，也可以只有一个，取决于配置。

为了简化 Xillybus IP 核的部署，它包含一个完全定义该核配置的数据结构。Linux 驱动在初始化过程中获取这一数据结构，并据此设置 DMA 缓冲区和字符设备。结果，单个驱动即可开箱即用地适配任何 Xillybus IP 核。

刚才提到的数据结构不应与 PCI 的配置空间或扁平设备树（Flattened Device Tree）混淆。

## 使用


### 用户接口


在主机上，与 Xillybus 的所有接口都通过 /dev/xillybus_* 设备文件完成，这些文件在驱动加载时自动生成。这些文件的名称取决于载入 FPGA 的 IP 核（见下文探测）。要与 FPGA 通信，请打开对应于你想发送或接收数据的硬件 FIFO 的设备文件，并使用普通的 write() 或 read() 调用，就像使用普通管道一样。在
```

	$ cat mydata > /dev/xillybus_thisfifo

	$ cat /dev/xillybus_thatfifo > hisdata

```
某些阶段可能需要按 CTRL-C，尽管 xillybus_* 管道具备发送 EOF 的能力（但可能不使用）。

驱动和硬件被设计为像管道一样合理工作，包括：

- 支持非阻塞 I/O（通过在 open() 时设置 O_NONBLOCK）。

- 支持 poll() 和 select()。

- 在负载下具有带宽效率（使用 DMA），同时通过自动刷新像 TCP/IP 那样处理少量跨传数据。

设备文件可以是只读、只写或双向的。双向设备文件被当作两条独立的管道处理（实现代码中共享一个"channel"结构除外）。

### 同步


Xillybus 管道在 IP 核上被配置为同步或异步。对于同步管道，write() 只有在部分数据已提交并被 FPGA 确认后才成功返回。这会拖慢批量数据传输，且对于需要恒定速率数据的流而言几乎不可用：在 write() 调用之间（尤其是进程失去 CPU 时）没有数据传输到 FPGA。

当管道配置为异步时，只要缓冲区中有足够空间存放数据，write() 即返回。

对于 FPGA 到主机的管道，异步管道在相应设备文件一打开时就允许从 FPGA 传数据，而不管数据是否已被 read() 调用请求。同步管道则只传输 read() 调用所请求的数据量。

总之，对于同步管道，主机与 FPGA 之间的数据仅在为满足驱动当前处理的 read() 或 write() 调用时传输，且这些调用会等待传输完成再返回。

注意，同步属性与 read() 或 write() 完成字节数少于请求数的可能性无关。有一个单独的配置标志（"allowpartial"）决定此类部分完成是否被允许。

### 可定位管道


同步管道可被配置为将流的位置暴露给 FPGA 上的用户逻辑。这样的管道在主机 API 上也是可定位的。借助此特性，可以在 FPGA 侧将内存或寄存器接口挂载到可定位流上。对挂载内存中某个地址的读或写，通过定位（seek）到目标地址，再按需调用 read() 或 write() 完成。


## 内部实现


### 源代码组织


Xillybus 驱动由一个核心模块 xillybus_core.c，以及依赖于特定总线接口的模块（xillybus_of.c 和 xillybus_pcie.c）组成。

特定总线模块是在内核发现合适设备时被探测的。由于核心模块会用到本质上依赖总线的 DMA 映射与同步函数，初始化时会向核心模块传入一个 xilly_endpoint_hardware 结构。该结构填充了用于在总线上执行 DMA 相关操作的包装函数指针。

### 管道属性


每个管道都有若干属性，在构建 FPGA 组件（IP 核）时设定。这些属性由 xillybus_core.c 中的 xilly_setupchannels() 从 IDT（定义核配置的数据结构，见下文探测）获取，如下：

- is_writebuf：管道方向。非零值表示它是 FPGA 到主机的管道（FPGA "写入"）。

- channelnum：主机与 FPGA 通信中管道的标识号。

- format：底层数据宽度。见下文数据粒度。

- allowpartial：非零值表示 read() 或 write()（视适用者而定）可能返回少于请求字节数的结果。通常选择非零值，以匹配标准 UNIX 行为。

- synchronous：非零值表示管道是同步的。见上文同步。

- bufsize：每个 DMA 缓冲区的大小。总是 2 的幂。

- bufnum：为该管道分配的缓冲区数量。总是 2 的幂。

- exclusive_open：非零值强制以独占方式打开关联的设备文件。如果设备文件是双向的，且已仅在一个方向打开，则相反方向可被打开一次。

- seekable：非零值表示该管道是可定位的。见上文可定位管道。

- supports_nonempty：非零值（这也是典型情况）表示该硬件会发送支持此管道 select() 和 poll() 所需的消息。

### 主机从不从 FPGA 读取


尽管 PCI Express 通常支持热插拔，典型主板并不期望某张卡突然消失。但由于 PCIe 卡基于可重编程逻辑，在主机运行期间因意外重编程 FPGA 而导致从总线上突然消失是相当可能的。在实践中，这种情况不会立刻发生任何事。但如果主机试图读取映射到 PCI Express 设备的地址，在某些主板上会导致系统立即冻结，即使 PCIe 标准要求优雅恢复。

为避免这些冻结，Xillybus 驱动完全避免从设备寄存器空间读取。从 FPGA 到主机的所有通信都通过 DMA 完成。特别地，中断服务例程（ISR）不遵循被调用时检查状态寄存器的常见做法，而是由 FPGA 准备一个包含简短消息的小缓冲区，告知主机中断的原因。

出于统一性的考虑，此机制在非 PCIe 总线上也同样使用。


### 通道、管道与消息通道


呈现给用户的每个（可能为双向的）管道，都被分配一个 FPGA 与主机之间的数据通道。区分通道与管道只是因为通道 0，它用于来自 FPGA 的中断相关消息，且没有挂载任何管道。

### 数据流


尽管向用户呈现的是两侧都无分段的连续数据流，实现上依赖于为每个通道分配的一组 DMA 缓冲区。为便于说明，以 FPGA 到主机的方向为例：当数据流入 FPGA 中相应通道的接口时，Xillybus IP 核将其写入某个 DMA 缓冲区。当缓冲区填满后，FPGA 通知主机（必要时在通道 0 上附加一条 XILLYMSG_OPCODE_RELEASEBUF 消息并发送中断）。主机响应，使该数据可通过字符设备读取。当数据全部读完后，主机写入 FPGA 的缓冲区控制寄存器，允许覆盖该缓冲区。两侧都存在流控机制，以防止欠载和溢出。

这还不足以创建类似 TCP/IP 的流：如果在某个 DMA 缓冲区填满之前数据流暂时停止，直观的预期是缓冲区中的部分数据无论如何都会到达，即使缓冲区尚未填满。这是通过向 XILLYMSG_OPCODE_RELEASEBUF 消息增加一个字段实现的，FPGA 借此不仅告知提交了哪个缓冲区，还告知其中包含多少数据。

但 FPGA 只有在主机指示时才会提交部分填充的缓冲区。这种情况发生在 read() 方法已阻塞 XILLY_RX_TIMEOUT 个 jiffies（当前为 10 ms）之后，此后主机命令 FPGA 尽快提交一个 DMA 缓冲区。该超时机制在总线带宽效率（防止发送大量部分填充的缓冲区）与数据尾部的较低延迟之间取得平衡。

主机到 FPGA 方向使用了类似的设置。不过部分 DMA 缓冲区的处理稍有不同。用户可以通过发起一个字节计数为零的 write() 调用，告诉驱动将其缓冲区中所有数据提交给 FPGA。这类似于刷新请求，但不阻塞。还存在一个自动刷新机制，它在最后一次 write() 之后约 XILLY_RX_TIMEOUT 个 jiffies 触发一次等效刷新。这让用户无需关心底层缓冲机制，却能享受类流的接口。

注意，部分缓冲区刷新的问题对于 "synchronous" 属性非零的管道无关紧要，因为同步管道本就不允许数据在 read() 与 write() 之间停留在 DMA 缓冲区中。

### 数据粒度


数据在 FPGA 侧以 8、16 或 32 位宽的字到达或发送，由 "format" 属性配置。只要可能，当管道以与其自然对齐方式不同的方式被访问时，驱动会尝试隐藏这一点。例如，以 32 位粒度从管道读取单字节毫无问题。向 16 或 32 位粒度的管道写入单字节也能工作，但驱动无法将未完成的字发送给 FPGA，因此最多一个字的数据可能要等到被用户数据填满后才传输。

这在一定程度上使主机到 FPGA 流的处理变复杂，因为当缓冲区被刷新时，可能含有最多 3 个字节不构成 FPGA 侧的完整字，因而无法发送。为防止数据丢失，这些剩余字节需要移到下一个缓冲区。xillybus_core.c 中以某种方式提及 "leftovers"（剩余）的部分与此复杂性有关。

### 探测


如前所述，驱动加载时创建的管道数量及其属性取决于 FPGA 中的 Xillybus IP 核。在驱动初始化期间，包含配置信息的一个二进制块——接口描述表（IDT）——从 FPGA 发送到主机。引导过程分三个阶段：

1. 获取 IDT 的长度，以便为其分配缓冲区。这通过向设备发送一条静默（quiesce）命令完成，因为该命令的应答中包含 IDT 的缓冲区长度。

2. 获取 IDT 本身。

3. 根据 IDT 创建接口。

### 缓冲区分配


为了简化防止 PCIe 包非法越界的逻辑，适用以下规则：如果缓冲区小于 4kB，它不得跨越 4kB 边界；否则，它必须 4kB 对齐。xilly_setupchannels() 函数通过向内核请求整页，并按需将它们切分为 DMA 缓冲区来分配这些缓冲区。由于所有缓冲区大小都是 2 的幂，因此可以以最多浪费一页内存为代价打包任意这样一组缓冲区。

所有缓冲区都在驱动加载时分配。这是必要的，因为有时会请求较大的连续物理内存段，而在系统刚启动时它们更可能可用。

缓冲区内存的分配按照它们在 IDT 中出现的顺序进行。驱动依赖一条规则：管道在 IDT 中按缓冲区大小递减排序。如果请求的缓冲区大于等于一页，则向内核请求所需数量的页，并用于该缓冲区。如果请求的缓冲区小于一页，则向内核请求单个页，并部分使用该页。或者，如果手头已有一个部分使用的页，则该缓冲区被打包进该页。可以证明，这样从内核请求的所有页（可能最后一页除外）都被 100% 利用。

### 支持 poll 的 "nonempty" 消息


为了支持 "poll" 方法（因此也支持 select()），在 FPGA 到主机方向有一个小陷阱：FPGA 可能已经用某些数据填满了 DMA 缓冲区，但尚未提交该缓冲区。如果主机等待 FPGA 提交缓冲区，就可能出现 FPGA 侧已发送数据、但 select() 调用仍会阻塞的情况，因为主机尚未收到任何相关通知。这通过 FPGA 在通道从完全空变为含有部分数据时发送的 XILLYMSG_OPCODE_NONEMPTY 消息来解决。

这些消息仅用于支持 poll() 和 select()。可以将 IP 核配置为不发送它们，以略微减少带宽占用。
