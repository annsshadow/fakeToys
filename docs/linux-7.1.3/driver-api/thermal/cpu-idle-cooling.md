
## CPU 空闲冷却


### 情况（Situation）：


在某些情况下，SoC 会达到一个临界温度上限，并且无法将温度稳定在温度控制点附近。当 SoC 必须稳定温度时，内核可以作用于一个冷却设备来降低耗散功率。当达到临界温度时，必须做出降低温度的决定，而这反过来又会影响性能。

另一种情况是，即使在通过时钟门控将组件动态泄漏降到最低之后，硅片温度仍持续上升。这种失控（runaway）现象会由于静态泄漏而持续。唯一的解决办法是给组件断电，从而消除动态和静态泄漏，使组件得以冷却。

最后同样重要的是，系统可以请求一个特定的功率预算，但由于 OPP 密度（OPP density）的原因，我们只能选择一个功率预算低于请求值的 OPP，从而导致 CPU 利用不足，损失性能。换句话说，一个 OPP 以低于请求功率预算的功率使 CPU 利用不足，而下一个 OPP 又超出了功率预算。如果存在一个中间的 OPP，就可以使用它。

### 解决方案（Solutions）：


如果我们能在一个受控的时间段内消除静态和动态泄漏，SoC 温度就会下降。通过对空闲状态持续时间或空闲周期注入周期加以控制，我们可以通过调节功率预算来缓解温度。

工作性能点（OPP）的密度对 cpufreq 的控制精度有很大影响，然而不同厂商的 OPP 密度千差万别，有些在 OPP 之间存在很大的功率差距，这会导致热控制期间性能损失，以及在其他场景下功率损失。

在一个特定的 OPP 上，我们可以假设，对属于同一集群的所有 CPU 注入空闲周期，且持续时间大于该集群空闲状态的目标驻留时间（target residency），就能在这一时间段内消除静态和动态泄漏（减去进入该状态所需的能量）。因此，带空闲周期的可持续功率与 OPP 的可持续功率呈线性关系，可以通过下式计算：
```

	    Power(IdleCycle) = Coef x Power(OPP)

```
### 空闲注入（Idle Injection）：


空闲注入（Idle Injection）的基本理念是，在每个控制周期强制 CPU 进入空闲状态一段指定的时间，它提供了除 cpufreq 之外另一种控制 CPU 功率和热量（heat）的方式。理想情况下，如果属于同一集群的所有 CPU 同步注入其空闲周期，该集群就能达到其断电状态，实现最小功耗，并将静态泄漏降低到几乎为零。然而，这些空闲周期注入会带来额外的延迟，因为 CPU 必须从深度睡眠状态唤醒。

我们使用固定的空闲注入持续时间，从而带来可接受的性能损失和固定的延迟。通过调节空闲注入的占空比（duty cycle），可以增加或减小缓解程度。
```

     ^
     |
     |
     |-------                         -------
     |_______|_______________________|_______|___________

     <------>
       idle  <---------------------->
                    running

      <----------------------------->
              duty cycle 25%


```
该冷却设备的实现将状态数量建立在占空比百分比之上。当没有进行缓解时，冷却设备状态为零，意味着占空比为 0%。

当缓解释放开始时，根据调节器的策略，会选择一个起始状态。在固定的空闲持续时间和占空比（即冷却设备状态）下，可以计算出运行持续时间。

调节器会改变冷却设备的状态，从而改变占空比，这种变化会调节冷却效果。
```

     ^
     |
     |
     |-------                 -------
     |_______|_______________|_______|___________

     <------>
       idle  <-------------->
                running

      <--------------------->
          duty cycle 33%

     ^
     |
     |
     |-------         -------
     |_______|_______|_______|___________

     <------>
       idle  <------>
              running

      <------------->
       duty cycle 50%

```
空闲注入持续时间值必须符合以下约束：

- 它小于或等于缓解开始时可容忍的延迟。它是平台相关的，并取决于我们想要的用户体验、响应性与性能之间的权衡。此值应当被明确指定。

- 它大于我们为热缓解所希望达到的空闲状态目标驻留时间，否则我们最终会消耗更多能量。

### 功率考量（Power considerations）


当我们达到热跳变点（thermal trip point）时，我们必须维持一个指定的
```

 Power = Capacitance x Voltage^2 x Frequency x Utilisation

```
它大于可持续功率（否则系统配置有问题）。'Capacitance'（电容）和 'Utilisation'（利用率）是固定值，'Voltage'（电压）和 'Frequency'（频率）是被人为固定的，因为我们不想改变 OPP。我们可以将 'Capacitance' 和 'Utilisation' 合并为单一术语，即
```

 Pdyn = Cdyn x Voltage^2 x Frequency

```
功率分配器（power allocator）调节器会以某种方式要求我们降低功率，以瞄准设备树中定义的可持续功率。因此，借助空闲注入机制，我们希望获得一个平均功率（Ptarget），即在一个特定 OPP 上以全功率运行一段时间，并在另一段时间内空闲。这可以表达为
```

 P(opp)target = ((Trunning x (P(opp)running) + (Tidle x P(opp)idle)) /
			(Trunning + Tidle)

  ...

 Tidle = Trunning x ((P(opp)running / P(opp)target) - 1)

```
此时，如果我们知道 CPU 的运行周期，就能得到所需的空闲注入。或者，如果我们有空闲
```

 Trunning = Tidle / ((P(opp)running / P(opp)target) - 1)

```
实际上，如果运行功率小于目标功率，我们会得到一个负的时间值，因此显然该公式的使用受限于功率降低的情况，所以需要更高的 OPP 才能使运行功率大于目标功率。

然而，在此演示中我们忽略了三个方面：

 - 静态泄漏在此未定义，我们可以将其引入方程，但假设它在大多数情况下为零，因为很难从 SoC 厂商处获得这些值

 - 空闲状态唤醒延迟（或进入+退出延迟）未被考虑，必须加入方程才能严格计算空闲注入

 - 注入的空闲持续时间必须大于空闲状态的目标驻留时间，否则我们最终会消耗更多能量，并可能反转缓解效果
```

 Trunning = (Tidle - Twakeup ) x
		(((P(opp)dyn + P(opp)static ) - P(opp)target) / P(opp)target )

```
