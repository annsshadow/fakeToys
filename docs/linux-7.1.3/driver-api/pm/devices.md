Linux 中大部分代码都是设备驱动，因此 Linux 的电源管理（PM）代码大部分也是
驱动相关的。大多数驱动做的事情很少；而另一些驱动，尤其是面向电池容量较小的
平台（如手机）的驱动，会做很多事情。

本文概述了驱动如何与系统级的电源管理目标交互，重点介绍那些挂接到驱动模型
核心之上、被所有设备共享的模型与接口。请将它作为背景资料，配合你针对某个
具体驱动所要做的特定领域工作来阅读。


## 设备电源管理的两种模型


驱动会使用下列一种或两种模型，把设备置入低功耗状态：

    System Sleep model（系统睡眠模型）：

	驱动可以作为进入系统级低功耗状态（如"suspend"（也称"suspend-to-RAM"，
	挂起到内存）、或主要针对带磁盘系统的"hibernation"（也称"suspend-to-disk"，
	挂起到磁盘））的一部分，进入低功耗状态。

	为此，设备驱动、总线驱动和类驱动需要相互协作，实现各种角色特定的
	suspend 与 resume 方法，以干净地关闭硬件与软件子系统，然后在数据不丢失
	的情况下重新激活它们。

	某些驱动可以管理硬件唤醒事件，这些事件会使系统离开低功耗状态。该特性
	可以通过相关的 `/sys/devices/.../power/wakeup` 文件来启用或禁用
	（对于以太网驱动，ethtool 使用的 ioctl 接口也可用于此目的）；启用它会
	消耗一定的功耗，但能让整个系统更频繁地进入低功耗状态。

    Runtime Power Management model（运行时电源管理模型）：

	设备也可以在整个系统仍在运行时，原则上独立于其他电源管理活动，被置入
	低功耗状态。不过，设备之间通常并非相互独立（例如，除非某个设备的所有
	子设备都已被挂起，否则其父设备不能被挂起）。此外，根据设备所在总线的
	类型，可能需要对设备执行一些总线特定的操作。在运行时被置入低功耗状态的
	设备，在系统级的电源状态切换（suspend 或 hibernation）期间可能需要特殊
	处理。

	由于这些原因，不仅设备驱动本身，连同相应的子系统（总线类型、设备类型
	或设备类）驱动以及 PM 核心，都会参与到运行时电源管理中。与系统睡眠电源
	管理的情况一样，它们需要通过实现各种角色特定的 suspend 与 resume 方法来
	协作，从而让硬件被干净地关闭并在不丢失数据或服务的情况下重新激活。

关于这些低功耗状态，除了说它们非常依赖于系统、且常常依赖于具体设备之外，
没有太多可说的。另外，如果把足够多的设备（在运行时）置入低功耗状态，其效果
可能非常接近于进入某个系统级的低功耗状态（系统睡眠）……并且存在协同效应：
多个使用运行时 PM 的驱动可能把系统带入一个连更深层的节能选项都可用状态。

大多数被挂起的设备都会让所有 I/O 静止下来：不再有 DMA 或 IRQ（唤醒事件除外），
不再有数据的读写，来自上游驱动的请求也不再被接受。不过，特定的总线或平台
可能有不同的要求。

硬件唤醒事件的例子包括实时时钟发出的警报、网络上的 wake-on-LAN 数据包、
键盘或鼠标活动，以及介质（针对 PCMCIA、MMC/SD、USB 等）的插入或拔出。

## 进入系统睡眠状态的接口


内核为子系统（总线类型、设备类型、设备类）和设备驱动提供了编程接口，使它们
能够参与所关注设备的电源管理。这些接口同时涵盖系统睡眠和运行时电源管理。


### 设备电源管理操作


设备电源管理操作，无论是在子系统层面还是设备驱动层面，都是通过定义并填充
`include/linux/pm.h` 中定义的 `struct dev_pm_ops` 类型对象来实现的。其中包含的
各个方法的角色将在下文中解释。目前，只要记住最后三个方法专用于运行时电源
管理，而其余方法用于系统级的电源状态切换就足够了。

还存在一个已废弃的用于电源管理操作的"旧"或"legacy"接口，至少在某些子系统中
可用。这种方式不使用 `struct dev_pm_ops` 对象，只适合以有限的方式实现系统睡眠
电源管理方法。因此本文档不描述它，如需了解更多信息请直接查阅源代码。


### 子系统级方法


用于挂起和恢复设备的核心方法位于 `struct dev_pm_ops` 中，该结构由
`struct dev_pm_domain` 的 :c`ops` 成员、或 `struct bus_type`、
`struct device_type` 以及 `struct class` 的 :c`pm` 成员所指向。它们主要让
编写平台和总线基础设施（如 PCI 或 USB）代码，或设备类型和设备类驱动的人
感兴趣。对于其子系统（PM 域、设备类型、设备类和总线类型）没有提供全部电源
管理方法的设备驱动的编写者，它们也同样相关。

总线驱动根据硬件与使用它的驱动的情况，适当地实现这些方法；PCI 与 USB 的工作
方式不同，以此类推。编写子系统级驱动的人不多；大多数驱动代码是构建在总线
特定框架代码之上的"设备驱动"。

关于这些驱动调用的更多信息，请参见后文的说明；它们会在每个设备身上分阶段调用，
并遵循驱动模型树中的父子顺序。


### :file:`/sys/devices/.../power/wakeup` 文件


驱动模型中的所有设备对象都包含用于控制系统唤醒事件（能够强制系统退出睡眠状态的
硬件信号）处理方式的字段。这些字段由总线或设备驱动代码使用
`device_set_wakeup_capable()` 和 `device_set_wakeup_enable()`（定义于
`include/linux/pm_wakeup.h`）进行初始化。

:c`power.can_wakeup` 标志只是记录设备（及其驱动）在物理上是否支持唤醒事件。
`device_set_wakeup_capable()` 例程会影响该标志。:c`power.wakeup` 字段是一个
指向 `struct wakeup_source` 类型对象的指针，用于控制设备是否应当使用其系统
唤醒机制，并用于把设备发出的系统唤醒事件通知给 PM 核心。该对象仅对支持唤醒的
设备（即 :c`can_wakeup` 标志被置位的设备）存在，并由 `device_set_wakeup_capable()`
创建（或移除）。

某个设备是否能够发出唤醒事件属于硬件层面的问题，由内核负责记录。相比之下，
一个支持唤醒的设备是否应当发出唤醒事件属于策略决定，由用户空间通过 sysfs 属性
进行管理：即 `power/wakeup` 文件。用户空间可以向它写入字符串 "enabled" 或
"disabled"，分别表示设备是否应当发出系统唤醒信号。该文件仅在对应设备的
:c`power.wakeup` 对象存在时才存在，并随该对象由 `device_set_wakeup_capable()`
一起被创建（或移除）。从该文件的读操作会返回相应的字符串。

大多数设备的 `power/wakeup` 文件初始值为 "disabled"；主要的例外是电源按钮、
键盘，以及已用 ethtool 设置好 WoL（wake-on-LAN）特性的以太网适配器。对于本身
不产生唤醒请求、只是把唤醒请求从一个总线转发到另一个总线的设备（如 PCI Express
端口），它的默认值也应为 "enabled"。

`device_may_wakeup()` 例程仅当 :c`power.wakeup` 对象存在且对应的 `power/wakeup`
文件包含 "enabled" 字符串时才返回真。这类信息被 PCI 总线类型代码等子系统用来
判断是否需要启用设备的唤醒机制。如果设备的唤醒机制由驱动直接启用或禁用，它们
也应当使用 `device_may_wakeup()` 来决定在系统睡眠切换期间该做什么。不过，设备
驱动在任何情况下都不应直接调用 `device_set_wakeup_enable()`。

应当指出，系统唤醒在概念上不同于运行时电源管理使用的"remote wakeup"（远程唤醒），
尽管它可能是由相同的物理机制支持的。远程唤醒是一项允许处于低功耗状态的设备触发
特定中断、以表示应当把它们恢复到全功率状态的功能。这些中断是否用于发出系统唤醒
事件，取决于硬件设计，可能用也可能不用。在某些系统上，从系统睡眠状态是无法触发
它们的。无论如何，对于所有支持它的设备和驱动，运行时电源管理都应始终启用远程唤醒。

### :file:`/sys/devices/.../power/control` 文件


驱动模型中的每个设备都有一个标志，用于控制它是否受运行时电源管理约束。该标志
:c`runtime_auto` 由总线类型（或一般意义上的子系统）代码使用 `pm_runtime_allow()`
或 `pm_runtime_forbid()` 初始化；默认是允许运行时电源管理。

该设置可由用户空间通过向设备的 `power/control` sysfs 文件写入 "on" 或 "auto"
来调整。写入 "auto" 会调用 `pm_runtime_allow()`，置位该标志并允许设备由其驱动
进行运行时电源管理。写入 "on" 会调用 `pm_runtime_forbid()`，清除该标志，把设备
恢复到全功率（如果它处于低功耗状态），并阻止设备被运行时电源管理。用户空间可以
通过读取该文件来检查 :c`runtime_auto` 标志的当前值。

设备的 :c`runtime_auto` 标志对系统级电源切换的处理没有影响。特别是，即使设备的
:c`runtime_auto` 标志被清除，该设备仍可以（且在大多数情况下应当且将会）在系统级
切换到睡眠状态时进入低功耗状态。

关于运行时电源管理框架的更多信息，请参阅 Documentation/power/runtime_pm.rst。


## 调用驱动进入和离开系统睡眠状态


当系统进入睡眠状态时，每个设备的驱动都会被要求挂起该设备，把它置入与目标系统
状态兼容的状态。这通常某个版本的"off"，但具体细节因系统而异。此外，启用了唤醒的
设备通常会保持部分可用，以便唤醒系统。

当系统离开该低功耗状态时，设备的驱动会被要求通过把它恢复到全功率来恢复它。挂起
和恢复操作总是成对出现，而且两者都是多阶段的操作。

对于简单的驱动，挂起可能使用类代码让设备静止下来，然后在 suspend_noirq 期间尽可能
把硬件关闭。对应的恢复调用则会先完全重新初始化硬件，再重新激活其类 I/O 队列。

更注重功耗的驱动可能会准备让设备触发系统唤醒事件。


### 调用顺序保证


为了确保当设备被挂起或恢复时，那些需要与该设备通信的桥接器和类似链路处于可用状态，
设备层级会以自底向上的顺序遍历以挂起设备。而恢复这些设备时使用自顶向下的顺序。

设备层级的顺序由设备注册的顺序定义：子设备绝不可能在其父设备之前被注册、探测或恢复；
也不可能在父设备之后被移除或挂起。

其策略是设备层级应当匹配硬件总线拓扑结构。[或者至少匹配控制总线，对于那些使用多条
总线的设备而言。] 特别地，这意味着如果设备的父设备正在挂起（即已被 PM 核心选为下一个
要挂起的设备）或已经挂起，以及在所有其他设备都已被挂起之后，设备的注册都可能失败。
设备驱动必须准备好应对这种情况。


### 系统电源管理阶段


挂起或恢复系统分若干个阶段进行。不同的阶段用于 suspend-to-idle、浅度（standby）和
深度（"suspend-to-RAM"）睡眠状态以及 hibernation 状态（"suspend-to-disk"）。每个阶段
会在下一个阶段开始之前，对每一个设备执行回调。并非所有的总线或类都支持所有这些回调，
也并非所有驱动都使用全部回调。各个阶段总是在任务被冻结之后、解冻之前运行。此外，
`*_noirq` 阶段运行在 IRQ 处理程序已被禁用的时间点（被标记为 IRQF_NO_SUSPEND 标志的
处理程序除外）。

所有阶段都会使用 PM 域、总线、类型、类或驱动回调（即定义于 `dev->pm_domain->ops`、
`dev->bus->pm`、`dev->type->pm`、`dev->class->pm` 或 `dev->driver->pm` 的方法）。
这些回调被 PM 核心视为互斥的。此外，PM 域回调总是优先于所有其他回调，例如类型回调
优先于总线、类和驱动回调。准确地说，使用下列规则来决定在给定阶段执行哪个回调：

    1. 如果 `dev->pm_domain` 存在，PM 核心会选择由 `dev->pm_domain->ops` 提供的
	回调来执行。

    2. 否则，如果 `dev->type` 和 `dev->type->pm` 都存在，则选择由 `dev->type->pm`
	提供的回调来执行。

    3. 否则，如果 `dev->class` 和 `dev->class->pm` 都存在，则选择由 `dev->class->pm`
	提供的回调来执行。

    4. 否则，如果 `dev->bus` 和 `dev->bus->pm` 都存在，则选择由 `dev->bus->pm`
	提供的回调来执行。

这使得 PM 域和设备类型能够在必要时覆盖由总线类型或设备类提供的回调。

PM 域、类型、类和总线回调反过来可能调用保存在 `dev->driver->pm` 中的设备特定或驱动
特定的方法，但它们不是必须这样做。

如果被选中的子系统回调不存在，PM 核心会转而执行来自 `dev->driver->pm` 集合的相应方法
（如果有的话）。


### 进入系统挂起


当系统进入 freeze、standby 或 memory 睡眠状态时，阶段依次为：`prepare`、`suspend`、
`suspend_late`、`suspend_noirq`。

    1. `prepare` 阶段的目的是通过阻止注册新设备来防止竞态；如果允许随意注册新的
	子设备，PM 核心永远无法知道某个设备的所有子设备都已被挂起。[相比之下，从
	PM 核心的角度看，设备可能在任何时刻被注销。] 与其他挂起相关阶段不同，在
	`prepare` 阶段设备层级是自顶向下遍历的。

	`->prepare` 回调方法返回之后，就不能在该设备之下注册新的子设备。该方法也可以
	以某种方式为即将到来的系统电源切换准备设备或驱动，但不应把设备置入低功耗状态。
	此外，如果设备支持运行时电源管理，`->prepare` 回调方法不得更新其状态，以防
	后续可能需要把它从运行时挂起中恢复。

	对于支持运行时电源管理的设备，`prepare` 回调的返回值可用于向 PM 核心表明：只要
	该设备的所有后代也保持运行时挂起，就可以安全地把它留在运行时挂起状态（如果已经
	是运行时挂起的话）。也就是说，如果 `prepare` 回调返回一个正数，并且该设备的所有
	后代也都如此，且它们（包括设备本身）都处于运行时挂起，PM 核心就会跳过
	`suspend`、`suspend_late` 和 `suspend_noirq` 阶段，以及这些设备后续恢复时
	的相应所有阶段。在这种情况下，在 `->prepare` 回调之后被调用的下一个回调将是
	`->complete` 回调，由它全权负责把设备置入恰当的、一致的状态。

	注意，这种 direct-complete（直接完成）过程即便在设备被禁用运行时 PM 时也适用；
	只有运行时 PM 的状态才有关系。由此可知，如果一个设备有系统睡眠回调但不支持运行时
	PM，那么它的 `prepare` 回调绝不可返回正值。这是因为所有这类设备最初都被设为
	运行时挂起且运行时 PM 被禁用。

	该特性也可由设备驱动通过使用 `DPM_FLAG_NO_DIRECT_COMPLETE` 和
	`DPM_FLAG_SMART_PREPARE` 驱动电源管理标志来控制。[通常，它们是在驱动针对相关设备
	被探测（probe）时，通过把它们传给 `dev_pm_set_driver_flags` 辅助函数来设置的。]
	如果设置了第一个标志，PM 核心将不会对上述给定设备、进而对其任何祖先应用前面描述的
	direct-complete 过程。第二个标志在被设置时，会通知中间层代码（总线类型、设备类型、
	PM 域、类）应当考虑驱动提供的 `->prepare` 回调的返回值，并且只有在其自身的
	`->prepare` 回调的返回值也为正时，它才可以返回正值。

    2. `->suspend` 方法应当让设备静止下来，停止其 I/O 操作。根据设备所在总线类型的
	不同，它们还可以保存设备寄存器并把设备置入合适的低功耗状态，并且可能启用唤醒事件。

	然而，对于支持运行时电源管理的设备，由子系统（尤其是总线类型和 PM 域）提供的
	`->suspend` 方法必须遵守一条附加规则，涉及在调用设备驱动的 `->suspend` 方法之前
	可以对设备做什么。即，如有必要，它们可以通过对设备调用 `pm_runtime_resume` 把
	设备从运行时挂起中恢复，但在此时不得以任何其他方式更新设备的状态（以防驱动需要
	在它们的 `->suspend` 方法中把设备从运行时挂起中恢复）。事实上，PM 核心通过在发出
	`->prepare` 回调之前调用 `pm_runtime_get_noresume`（以及在发出 `->complete` 回调
	之后调用 `pm_runtime_put`），来阻止子系统或驱动在这些时刻把设备置入运行时挂起。

    3. 对许多设备而言，把挂起拆分为"让设备静止"和"保存设备状态"两个阶段较为方便，此时
	`suspend_late` 用于完成后者。它总是在相关设备的运行时电源管理被禁用之后执行。

    4. `suspend_noirq` 阶段发生在 IRQ 处理程序被禁用之后，这意味着回调方法运行期间
	不会调用驱动的 interrupt handler。`->suspend_noirq` 方法应当保存设备寄存器中
	此前未保存的值，并最终把设备置入合适的低功耗状态。

	大多数子系统和设备驱动不需要实现此回调。不过，允许设备共享中断向量的总线类型
	（如 PCI）通常需要它；否则驱动可能会在挂起阶段，由于自己的设备已被设为低功耗之后
	又收到其他设备产生的共享中断而遇到错误。

在这些阶段结束时，驱动应当已经停止所有 I/O 事务（DMA、IRQ），并保存了足够的信息以便
重新初始化或恢复先前的状态（视硬件需要而定），且已将设备置入低功耗状态。在许多平台上，
它们会关闭一个或多个时钟源；有时它们也会切断供电或降低电压。[支持运行时 PM 的驱动
可能已经执行了部分或全部这些步骤。]

如果 `device_may_wakeup()` 返回 `true`，则应当把设备准备好，以便在系统处于睡眠状态时
产生硬件唤醒信号来触发系统唤醒事件。例如，`enable_irq_wake()` 可能识别出接到开关或其
他外部硬件的 GPIO 信号，而 `pci_enable_wake()` 对 PCI PME 信号做类似的事情。

如果这些回调中的任何一个返回错误，系统就不会进入期望的低功耗状态。相反，PM 核心会通过
恢复所有已被挂起的设备来回滚其操作。


### 离开系统挂起


当从 freeze、standby 或 memory 睡眠中恢复时，阶段依次为：`resume_noirq`、
`resume_early`、`resume`、`complete`。

    1. `->resume_noirq` 回调方法应当执行在驱动的 interrupt handler 被调用之前所需的
	任何操作。这通常意味着撤销 `suspend_noirq` 阶段的操作。如果总线类型允许设备共享
	中断向量（如 PCI），该方法应把设备及其驱动带入这样一种状态：驱动能够识别设备是否
	是传入中断的源（如果有的话）并正确处理它们。

	例如，PCI 总线类型的 `->pm.resume_noirq()` 把设备置入全功率状态（在 PCI 术语中为
	D0）并恢复设备的标准配置寄存器。然后它调用设备驱动的 `->pm.resume_noirq()` 方法
	来执行设备特定的操作。

    2. `->resume_early` 方法应当为执行 resume 方法准备设备。这通常涉及撤销前面的
	`suspend_late` 阶段的操作。

    3. `->resume` 方法应当把设备带回其工作状态，使它能够执行正常的 I/O。这通常涉及
	撤销 `suspend` 阶段的操作。

    4. `complete` 阶段应当撤销 `prepare` 阶段的操作。正因如此，与其他恢复相关阶段不同，
	在 `complete` 阶段设备层级是自底向上遍历的。

	不过要注意，一旦 `->resume` 回调发生，就可以在该设备之下注册新的子设备；没有必要
	等到 `complete` 阶段运行。

	此外，如果前面的 `->prepare` 回调返回了一个正数，那么该设备可能在整个系统挂起和恢复
	期间一直保持运行时挂起（它的 `->suspend`、`->suspend_late`、`->suspend_noirq`、
	`->resume_noirq`、`->resume_early` 和 `->resume` 回调可能都被跳过了）。在这种
	情况下，`->complete` 回调全权负责在必要时于系统挂起之后把设备置入一致的状态。[例如，
	它可能需要为此目的为设备排队一个运行时恢复请求。] 要检查是否如此，`->complete` 回调
	可以查看设备的 `power.direct_complete` 标志。如果该标志在 `->complete` 回调运行时
	被置位，那么就使用了 direct-complete 机制，可能需要采取特殊操作以使设备在之后正常
	工作。

在这些阶段结束时，驱动应当恢复到挂起前那样的功能：可以使用 DMA 和 IRQ 执行 I/O，相关的
时钟已被开启。

不过，这里的细节可能再次因平台而异。例如，某些系统支持多个"run"（运行）状态，而恢复
结束时生效的模式可能不是挂起之前的那个。这意味着某些时钟或供电的可用性发生了变化，这
很容易影响驱动的工作方式。

驱动需要能够处理自所有挂起方法被调用以来已被复位的硬件，例如通过完整的重新初始化。这
可能是最难的一部分，也是最受 NDA 文档和芯片勘误表保护的部分。如果硬件状态自挂起执行以来
没有变化，那是最简单的，但这只有在进入的是 suspend-to-idle 时才能得到保证。对于其他系统
睡眠状态，情况可能并非如此（对于 ACPI 定义的系统睡眠状态（如 S3）通常就不是）。

驱动还必须准备好注意到设备在系统断电期间被移除的情况，只要这在物理上是可能的。PCMCIA、
MMC、USB、Firewire、SCSI 甚至 IDE 都是常见 Linux 平台上会看到此类移除的总线示例。驱动
如何注意到并处理此类移除的细节目前是总线特定的，且通常涉及一个独立的线程。

这些回调可能返回错误值，但 PM 核心会忽略此类错误，因为它除了把它们打印到系统日志之外
无能为力。


### 进入休眠（Hibernation）


让系统休眠比把它置入睡眠状态更复杂，因为这涉及创建并保存系统映像。因此休眠有更多的阶段，
并带有一组不同的回调。这些阶段总是在任务被冻结且已释放足够内存之后运行。

休眠的一般流程是：让所有设备静止下来（"freeze"），在一切稳定时创建系统内存的映像，重新激活
所有设备（"thaw"），把映像写入持久化存储，最后关闭系统（"power off"）。用于完成此过程的
阶段为：`prepare`、`freeze`、`freeze_late`、`freeze_noirq`、`thaw_noirq`、`thaw_early`、
`thaw`、`complete`、`prepare`、`poweroff`、`poweroff_late`、`poweroff_noirq`。

    1. `prepare` 阶段已在上面的"进入系统挂起"一节中讨论。

    2. `->freeze` 方法应当让设备静止下来，使其不产生 IRQ 或 DMA，并且它们可能需要保存设备
	寄存器的值。不过设备不必被置入低功耗状态，为了节省时间最好不这样做。同时，设备不应
	被准备去产生唤醒事件。

    3. `freeze_late` 阶段类似于前面描述的 `suspend_late` 阶段，只是设备不应被置入低功耗
	状态，也不应被允许产生唤醒事件。

    4. `freeze_noirq` 阶段类似于前面讨论的 `suspend_noirq` 阶段，再次强调设备不应被置入
	低功耗状态，也不应被允许产生唤醒事件。

此时创建系统映像。所有设备都应处于非活动状态，并且在此期间内存内容应保持不被扰动，使映像
成为系统状态的一个原子快照。

    5. `thaw_noirq` 阶段类似于前面讨论的 `resume_noirq` 阶段。主要区别在于它的方法可以
	假定设备处于与 `freeze_noirq` 阶段结束时相同的状态。

    6. `thaw_early` 阶段类似于上面描述的 `resume_early` 阶段。其方法应在必要时撤销前面的
	`freeze_late` 的操作。

    7. `thaw` 阶段类似于前面讨论的 `resume` 阶段。其方法应把设备带回工作状态，以便在需要
	时可用于保存映像。

    8. `complete` 阶段已在上面的"离开系统挂起"一节中讨论。

此时系统映像已被保存，然后需要为即将到来的系统关闭准备设备。这很像在把系统置入
suspend-to-idle、浅度或深度睡眠状态之前挂起它们，并且阶段是类似的。

    9. `prepare` 阶段已在上面讨论。

    10. `poweroff` 阶段类似于 `suspend` 阶段。

    11. `poweroff_late` 阶段类似于 `suspend_late` 阶段。

    12. `poweroff_noirq` 阶段类似于 `suspend_noirq` 阶段。

`->poweroff`、`->poweroff_late` 和 `->poweroff_noirq` 回调应当分别做与 `->suspend`、
`->suspend_late` 和 `->suspend_noirq` 回调本质上相同的事情。一个值得注意的区别是它们不必
存储设备寄存器的值，因为这些寄存器应该已经在 `freeze`、`freeze_late` 或 `freeze_noirq`
阶段被保存过了。此外，在许多机器上固件会关闭整个系统，因此回调无需把设备置入低功耗状态。


### 离开休眠


从休眠中恢复，再次比从内存内容被保留的睡眠状态中恢复更复杂，因为这需要把系统映像加载到
内存中，并在控制权交回映像内核之前恢复休眠前的内存内容。

尽管原则上映像可能由 boot loader 加载到内存并恢复休眠前的内存内容，但实际上这无法做到，
因为 boot loader 不够智能，也没有既定协议来传递必要的信息。因此，boot loader 改为把内核
的一个新实例（称为"restore kernel"，恢复内核）加载到内存中，并以通常的方式把控制权交给它。
然后恢复内核读取系统映像，恢复休眠前的内存内容，并把控制权交给映像内核。因此，从休眠中
恢复涉及两个不同的内核实例。事实上，恢复内核可能与映像内核完全不同：不同的配置，甚至不同的
版本。这对设备驱动及其子系统有重要的影响。

为了能够把系统映像加载到内存中，恢复内核需要至少包含允许其访问存放映像的存储媒介的一部分
设备驱动，尽管它不需要包含映像内核中存在的所有驱动。在映像被加载之后，由 boot 内核管理的
设备需要被准备以把控制权交回映像内核。这与创建系统映像所涉及的初始步骤非常相似，并且以
相同的方式完成，使用 `prepare`、`freeze` 和 `freeze_noirq` 阶段。不过，受这些阶段影响的
设备只有那些在恢复内核中有驱动的设备；其他设备仍将处于 boot loader 离开它们时的任何状态。

如果休眠前内存内容的恢复失败，恢复内核将走一遍上面描述的"thawing"（解冻）过程，使用
`thaw_noirq`、`thaw_early`、`thaw` 和 `complete` 阶段，然后继续正常运行。这种情况很少发生。
最常见的是休眠前的内存内容被成功恢复，控制权被交给映像内核，然后由它负责把系统带回到工作
状态。

为此，映像内核必须恢复设备的休眠前功能。该操作很像从睡眠状态（内存内容被保留）中唤醒，尽管
它涉及的阶段不同：`restore_noirq`、`restore_early`、`restore`、`complete`。

    1. `restore_noirq` 阶段类似于 `resume_noirq` 阶段。

    2. `restore_early` 阶段类似于 `resume_early` 阶段。

    3. `restore` 阶段类似于 `resume` 阶段。

    4. `complete` 阶段已在上面讨论。

与 `resume[_early|_noirq]` 的主要区别在于，`restore[_early|_noirq]` 必须假定设备已被
boot loader 或恢复内核访问并重新配置过。因此，设备的状态可能与从 `freeze`、`freeze_late`
和 `freeze_noirq` 阶段记住的状态不同。设备甚至可能需要被复位并完全重新初始化。在许多情况下
这种差别无关紧要，因此 `->resume[_early|_noirq]` 和 `->restore[_early|_norq]` 方法指针
可以被设为相同的例程。不过，在确实有关系的情况下，使用了不同的回调指针。


## 电源管理通知器（Notifiers）


有一些操作无法通过上面讨论的电源管理回调来完成，因为这些回调发生得太晚或太早。为了处理这些
情况，子系统和设备驱动可以注册电源管理通知器，它们在任务被冻结之前和任务被解冻之后被调用。
一般来说，PM 通知器适合执行那些需要用户空间可用、或者至少不会干扰用户空间的操作。

详情请参阅 Documentation/driver-api/pm/notifiers.rst。


## 设备低功耗（挂起）状态


设备低功耗状态并不标准化。一个设备可能只处理"on"和"off"，而另一个可能支持十几种不同的
"on"版本（有多少个引擎在活动？），外加一个比完全"off"更快回到"on"的状态。

某些总线定义了关于不同挂起状态含义的规则。PCI 提供了一个例子：在挂起序列完成之后，非 legacy
的 PCI 设备不得执行 DMA 或发出 IRQ，它发出的任何唤醒事件都将通过 PME# 总线信号发出。此外，
还有若干 PCI 标准的设备状态，其中一些是可选的。

相比之下，集成的片上系统（system-on-chip）处理器经常把 IRQ 用作唤醒事件源（因此驱动会调用
`enable_irq_wake`），并且可能能够把 DMA 完成视为唤醒事件（有时 DMA 也可以保持活动，只是 CPU
和某些外设会睡眠）。

这里的一些细节可能因平台而异。系统可能有设备能在某些睡眠状态下完全活动，例如一个 LCD 显示器
在系统大部分轻睡眠期间通过 DMA 刷新……并且它的帧缓冲甚至可以由 DSP 或其他非 Linux 的 CPU 更新，
而 Linux 控制处理器保持空闲。

此外，所采取的具体操作可能取决于目标系统状态。一个目标系统状态可能允许某个设备非常可操作；
另一个可能要求硬关闭并在恢复时重新初始化。两个不同目标系统可能以不同方式使用同一设备；前面
提到的 LCD 可能在某个产品的"standby"中处于活动，但使用相同 SoC 的另一个产品可能工作方式不同。


## 设备电源管理域


有时设备会共享参考时钟或其他电源资源。在这些情况下，通常不可能把设备逐个置入低功耗状态。
相反，一组共享某个电源资源的设备可以通过关闭该共享电源资源而被同时置入低功耗状态。当然，它们
也需要通过打开共享电源资源而一起被置入全功率状态。具有这种属性的一组设备通常被称为一个电源域
（power domain）。一个电源域也可以嵌套在另一个电源域内部。被嵌套的域被称为父域的子域
（sub-domain）。

对电源域的支持是通过 `struct device` 的 :c`pm_domain` 字段提供的。该字段是一个指向
`struct dev_pm_domain` 类型对象的指针，定义于 `include/linux/pm.h`，提供一组电源管理回调，
这些回调类似于子系统级和设备驱动回调，会在给定设备的所有电源切换期间被执行，而不是执行相应的
子系统级回调。具体而言，如果设备的 :c`pm_domain` 指针不为 NULL，那么由它指向的对象提供的
`->suspend()` 回调将被执行，以取代其子系统（例如总线类型）的 `->suspend()` 回调，其余回调
以此类推。换句话说，如果为给定设备定义了电源管理域回调，它们总是优先于设备子系统（例如总线类型）
提供的回调。

对设备电源管理域的支持，只对那些需要在许多不同电源域配置中使用相同的设备驱动电源管理回调，并且
希望避免把对电源域的支持并入子系统级回调（例如通过修改 platform 总线类型）的平台才有意义。其他
平台不需要实现它，也不需要在任何方面考虑它。

设备可以被定义为 IRQ-safe（IRQ 安全），这向 PM 核心表明它们的运行时 PM 回调可以在中断被禁用
的情况下被调用（更多信息请参阅 Documentation/power/runtime_pm.rst）。如果一个 IRQ-safe 设备
属于某个 PM 域，那么除非该域本身被定义为 IRQ-safe，否则该域的运行时 PM 将被禁止。不过，把一个
PM 域定义为 IRQ-safe 只有在域中所有设备都是 IRQ-safe 时才有意义。此外，如果一个 IRQ-safe 域
有父域，则只有当父域本身也是 IRQ-safe 时才允许父域的运行时 PM，并且附加限制：IRQ-safe 父域的
所有子域也必须都是 IRQ-safe。


## 运行时电源管理


许多设备能够在系统仍在运行时动态地关闭电源。这个特性对未被使用的设备很有用，并且能在运行的
系统上带来显著的节能。这些设备通常支持一系列运行时电源状态，可能使用诸如 "off"、"sleep"、
"idle"、"active" 等名称。这些状态在某些情况下（如 PCI）会部分受设备所用总线的约束，并且通常
会包含系统睡眠状态中也使用的硬件状态。

系统级的电源切换可能在一些设备由于运行时电源管理而处于低功耗状态时开始。系统睡眠 PM 回调应当
识别此类情况并恰当地响应，但必要的操作是子系统特定的。

在某些情况下，决定可能在子系统层面做出，而在其他情况下可能留给设备驱动决定。在某些情况下，可能
希望在系统级电源切换期间把已挂起的设备保持在该状态，但在其他情况下设备必须被暂时放回全功率状态，
例如以便禁用它的系统唤醒能力。这全都取决于相关硬件以及子系统和设备驱动的设计。

如果需要在系统级切换到睡眠状态期间把某个设备从运行时挂起中恢复，可以通过在设备驱动或其子系统
（例如某个总线类型或 PM 域）的 `->suspend` 回调（或对于与休眠相关的切换，其 `->freeze` 或
`->poweroff` 回调）中调用 `pm_runtime_resume` 来完成。但是，子系统不得以其
他方式在调用设备驱动的 `->suspend` 回调（或等价回调）**之前**，通过它们的 `->prepare` 和
`->suspend` 回调（或等价回调）改变设备的运行时状态。


### ``DPM_FLAG_SMART_SUSPEND`` 驱动标志


某些总线类型和 PM 域有一项策略：在它们的 `->suspend` 回调中预先把所有设备从运行时挂起中恢复，
但如果设备的驱动能够处理运行时挂起的设备，这未必真的有必要。驱动可以通过在探测（probe）时
借助 `dev_pm_set_driver_flags` 辅助例程在 :c`power.driver_flags` 中设置
`DPM_FLAG_SMART_SUSPEND` 来表明这一点。

设置该标志会使 PM 核心和中间层代码（总线类型、PM 域等）跳过驱动提供的 `->suspend_late` 和
`->suspend_noirq` 回调，条件是设备在这些系统级挂起阶段始终保持在运行时挂起（对于系统休眠的
"freeze" 和 "poweroff" 部分类似）。[否则同一个驱动回调可能会连续为同一设备执行两次，这在一般
情况下是无效的。] 如果设备存在中间层系统级 PM 回调，则它们负责跳过这些驱动回调；否则由 PM 核心
跳过。子系统回调例程可以通过测试 `dev_pm_skip_suspend` 辅助函数的返回值来决定是否需要跳过驱动
回调。

此外，在设置了 `DPM_FLAG_SMART_SUSPEND` 的情况下，如果设备在前面整个 "freeze" 切换期间保持
运行时挂起，那么它在休眠中的 `->thaw_noirq` 和 `->thaw_early` 回调会被跳过。同样，如果设备存在
中间层回调，则由它们负责执行此操作，否则由 PM 核心处理。


### ``DPM_FLAG_MAY_SKIP_RESUME`` 驱动标志


在从睡眠状态进行系统级恢复时，把设备置入全功率状态是最简单的，如
Documentation/power/runtime_pm.rst 中所解释。[有关此特定问题的更多信息，以及关于设备运行时电源
管理框架的总体信息，请参阅该文档。] 然而，通常在系统切换到工作状态之后把设备留在挂起状态是
可取的，特别是在那些设备在前面的系统级挂起（或类似）切换之前一直处于运行时挂起的情况下。

为此，设备驱动可以使用 `DPM_FLAG_MAY_SKIP_RESUME` 标志，向 PM 核心和中间层代码表明：如果设备
可以在系统级 PM 切换到工作状态之后留在挂起状态，它们允许跳过该设备的 "noirq" 和 "early" 恢复
回调。是否如此通常取决于该设备在给定系统挂起-恢复周期之前的状态，以及正在进行的系统切换的类型。
特别地，与休眠相关的 "thaw" 和 "restore" 切换完全不受 `DPM_FLAG_MAY_SKIP_RESUME` 影响。[无论
标志设置如何，在 "restore" 切换期间都会发出所有回调，而在 "thaw" 切换期间是否有任何驱动回调被
跳过取决于 `DPM_FLAG_SMART_SUSPEND` 标志是否被设置（见 `above <smart_suspend_flag_>`_）。此外，
如果设备的任何子设备将被恢复到全功率，则该设备不允许保持运行时挂起。]

`DPM_FLAG_MAY_SKIP_RESUME` 标志会与 PM 核心在 suspend 类型切换的 "suspend" 阶段设置的
:c`power.may_skip_resume` 状态位结合考虑。如果驱动或中间层有理由阻止驱动在随后的系统恢复切换
中跳过其 "noirq" 和 "early" 恢复回调，它应当在自己的 `->suspend`、`->suspend_late` 或
`->suspend_noirq` 回调中清除 :c`power.may_skip_resume`。[注意，设置 `DPM_FLAG_SMART_SUSPEND`
的驱动需要在其 `->suspend` 回调中清除 :c`power.may_skip_resume`（以防另外两个被跳过）。]

设置 :c`power.may_skip_resume` 状态位以及 `DPM_FLAG_MAY_SKIP_RESUME` 标志是必要的，但通常不足
以保证驱动的 "noirq" 和 "early" 恢复回调被跳过。是否应跳过它们可以通过评估 `dev_pm_skip_resume`
辅助函数来确定。

如果该该函数返回 `true`，则应跳过驱动的 "noirq" 和 "early" 恢复回调，并且设备的运行时 PM 状态
将被 PM 核心设为 "suspended"。否则，如果设备在前面的系统级挂起切换期间处于运行时挂起且其
`DPM_FLAG_SMART_SUSPEND` 被设置，则其运行时 PM 状态将被 PM 核心设为 "active"。[因此，未设置
`DPM_FLAG_SMART_SUSPEND` 的驱动不应期望其设备的运行时 PM 状态在系统级恢复类型切换期间被 PM 核心
从 "suspended" 改为 "active"。]

如果某个设备未设置 `DPM_FLAG_MAY_SKIP_RESUME`，但设置了 `DPM_FLAG_SMART_SUSPEND` 且其驱动的
"late" 和 "noirq" 挂起回调被跳过，那么它的系统级 "noirq" 和 "early" 恢复回调（如果存在）会照常
被调用，并且设备的运行时 PM 状态会在为其启用运行时 PM 之前被 PM 核心设为 "active"。在这种情况下，
驱动必须准备好应对其系统级恢复回调紧挨着其 `->runtime_suspend` 回调被调用（中间没有介入的
`->runtime_resume` 和系统级挂起回调），并且设备的最终状态在那种情况下必须反映 "active" 运行时
PM 状态。[注意，如果驱动的 `->suspend_late` 回调指针指向与其 `->runtime_suspend` 相同的函数，
且其 `->resume_early` 回调指针指向与其 `->runtime_resume` 相同的函数，同时驱动没有其他系统级
挂起-恢复回调，那这根本不是问题。]

类似地，如果为某设备设置了 `DPM_FLAG_MAY_SKIP_RESUME`，其驱动的系统级 "noirq" 和 "early" 恢复
回调可能被跳过，而其 "late" 和 "noirq" 挂起回调可能已被执行（原则上，无论 `DPM_FLAG_SMART_SUSPEND`
是否被设置）。在这种情况下，驱动需要能够应对其 `->runtime_resume` 回调紧挨着其 "late" 和 "noirq"
挂起回调被调用。[例如，如果驱动同时设置 `DPM_FLAG_SMART_SUSPEND` 和 `DPM_FLAG_MAY_SKIP_RESUME`，
并对运行时 PM 和系统级挂起/恢复使用同一对挂起/恢复回调函数，那就无需担心。]
