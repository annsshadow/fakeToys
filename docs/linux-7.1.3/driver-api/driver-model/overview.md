## Linux 内核设备模型


Patrick Mochel	<mochel@digitalimplant.org>

Drafted 26 August 2002
Updated 31 January 2006


#### 概述


Linux 内核驱动模型是对内核中先前使用的各种不同驱动模型的统一。它旨在通过将数据与操作集合整合到全局
可访问的数据结构中，来增强用于桥和设备的总线特定驱动
传统的驱动模型为它们所控制的设备实现了某种树状结构（有时仅仅是一个列表）。不同的总线类型之间没有
任何统一性
当前的驱动模型提供了一个通用的、统一的数据模型，用于描述一条总线以及可以出现在该总线下的设备。统一总线模型包含一组所有总线都携带的通用属性，以及一组通用回调，例如总线探测期间的设备发现、总线关机总线电源管理等
通用的设备和桥接口反映了现代计算机的目标：即实现无缝的设备“即插即用”、电源管理以及热插拔。特别是Intel Microsoft（即 ACPI）规定的模型确保了在 x86 兼容系统上，几乎任何总线上的几乎每个设备都能
在此范式下工作。当然，并非每条总线都能支持所有这些操作，尽管大多数总线支持其中大部分操作

#### 下游访问


公共数据字段已从各个总线层移出，进入一个公共数据结构。这些字段仍必须由总线层、有时由设备特定驱动访问
鼓励其他总线层去做已经为 PCI 层所做的事```

  struct pci_dev {
	...

	struct device dev;     /* 通用设备接口 */
	...
  };

```
注意首先，struct pci_dev 中的 struct device dev 是静态分配的。这意味着设备发现时只进行一次分配
还要注意，struct device dev 不一定定义在 pci_dev 结构体的前部。这是为了让人们在总线驱动与全局驱动之间
切换时思考他们在做什么，并打消在两者之间进行无意义且不正确的强制转换
PCI 总线层可以自由访struct device 的字段。它了解 struct pci_dev 的结构，也应该了struct device
的结构。已被转换为当前驱动模型的单PCI 设备驱动通常不应当也不应该触struct device 的字段，除非这样做的充分理由
上述抽象在过渡阶段避免了不必要的麻烦。如果不这样做，那么当一个字段被重命名或移除时，每个下游驱动都会
崩溃。另一方面，如果只有总线层（而非设备层）访问 struct device，那么需要改变的就只有总线层

#### 用户接口


由于拥有系统中所有设备的完整层级视图，向用户空间导出一个完整的层级视图变得相对容易。这通过实现一名为 sysfs 的专用虚拟文件系统来完成
几乎所有主流的 Linux 发行版都会自动挂载此文件系统；你
```

  $ mount
  ...
  none on /sys type sysfs (rw,noexec,nosuid,nodev)
  ...
  $

```
sysfs 的自动挂载通常通过一个类似于以下的条目完```

  none     	/sys	sysfs    defaults	  	0 0

```
```

  none            /sys    sysfs    nodev,noexec,nosuid    0 0

```
```

	# mount -t sysfs sysfs /sys

```
每当一个设备被插入到树中时，就会为它创建一个目录。该目录可以在发现的每一层——全局层、总线层或设备层——被填充
全局层目前创建两个文件—name' 'power'。前者只报告设备的名称。后者报告设备当前的电源状态。它也将用于
设置当前的电源状态
总线层也可能在探测总线时为它发现的设备创建文件。例如，PCI 层目前为每个 PCI 设备创建 'irq' 'resource' 文件
设备特定的驱动也可以在其目录中导出文件，以暴露设备特定的数据或可调节接口
