
### 简介


V4L2 驱动往往非常复杂，原因在于硬件本身的复杂性：大多数设备包含多个 IC，在
/dev 下导出多个设备节点，并且还会创建非 V4L2 的设备，例如 DVB、ALSA、FB、
I2C 以及 input（IR）设备。

尤其是 V4L2 驱动必须配置支持性的 IC 来完成音频/视频的复用/编码/解码，这使它
比大多数驱动都更复杂。通常这些 IC 通过一条或多条 I2C 总线连接到主桥接驱动，
但也可以使用其它总线。这类设备被称为“子设备”（sub-devices）。

长期以来，该框架仅限于用 video_device 结构体来创建 V4L 设备节点，以及用
video_buf 来处理视频缓冲区（注意本文档不会讨论 video_buf 框架）。

这意味着所有驱动都必须自行完成设备实例的初始化以及与子设备的连接。其中部分
工作做对相当复杂，而且很多驱动从未正确实现过。

同时还有大量公共代码由于缺乏框架而一直无法被重构。

因此，本框架建立了所有驱动都所需的基本构建块，并且同一个框架应当能让将公共
代码重构为所有驱动共享的工具函数变得容易得多。

一个值得作为参考示例的是 samples/v4l/ 中提供的 v4l2-pci-skeleton.c 源码。
它是一个针对 PCI 采集卡的骨架驱动，演示了如何使用 V4L2 驱动框架。它可以用作
真实 PCI 视频采集驱动的模板。

### V4L 驱动的结构


所有驱动都具有以下结构：

1) 每个设备实例对应一个包含设备状态的结构体。

2) 一种用于初始化和控制子设备（如果有）的方式。

3) 创建 V4L2 设备节点（/dev/videoX、/dev/vbiX 与 /dev/radioX）并跟踪
   设备节点相关的数据。

4) 包含每个文件句柄（filehandle）数据的、与文件句柄相关的结构体；

5) 视频缓冲区处理。

以下是它们之间关联关系的粗略示意图：

      |
      +-sub-device instances
      |
      \-V4L2 device nodes
	  |
	  \-filehandle instances


### V4L2 框架的结构


框架与驱动结构非常相似：它用一个 v4l2_device 结构体保存设备实例数据，用
v4l2_subdev 结构体指向子设备实例，video_device 结构体保存 V4L2 设备节点数据，
v4l2_fh 结构体则跟踪文件句柄实例。

V4L2 框架还可以选择性地与 media 框架集成。如果驱动设置了 v4l2_device 结构体的
mdev 字段，子设备与视频节点就会作为实体自动出现在 media 框架中。
