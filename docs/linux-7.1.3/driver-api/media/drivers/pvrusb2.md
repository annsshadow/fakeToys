
## pvrusb2 驱动


作者：Mike Isely <isely@pobox.com>

### 背景


该驱动面向 "Hauppauge WinTV PVR USB 2.0"，这是一款基于 USB 2.0 的电视调谐器。
该驱动仍在开发之中。它的历史始于 Björn Danielsson <pvrusb2@dax.nu> 的逆向工程
工作，其网页位于：
http://pvrusb2.dax.nu/

从那里，Aurelien Alleaume <slts@free.fr> 开始尝试创建一个 video4linux 兼容的驱动。
我以 Aurelien 最后一个已知的快照为基础，将驱动演进到了如今的状态。

关于该驱动的更多信息可以在以下位置找到：
https://www.isely.net/pvrusb2.html


该驱动具有强烈的层级分离。大致如下：

1. 与设备的底层线协议（wire-protocol）实现。

2. I2C 适配器实现，以及 V4L 中其他位置实现的相应 I2C 客户端驱动。

3. 高层硬件驱动实现，它协调所有活动以确保设备的正确运行。

4. 一个"上下文（context）"层，它管理驱动的实例化、设置、拆除、仲裁，并在设备于
   系统中热插拔时与高层接口适当地交互。

5. 将驱动粘合到各种已发布 Linux API（V4L、sysfs，将来可能还有 DVB）的高层接口。

最重要的分割层在顶部两层之间。驱动中投入了大量工作，以确保任何可以想到的 API 都能
置于核心驱动之上。（是的，驱动内部利用 V4L 来完成其工作，但这与该驱动对外发布的
API 实际上毫无关系。）该架构允许多个不同的 API 同时访问驱动。我对 API 有很强的
公平感，并且也认为将实现与接口相互隔离是一个良好的设计原则。因此，虽然目前 V4L
高层接口最为完整，sysfs 高层接口对于类似的功能同样可以工作得一样好，而且我现在看
不出有什么理由不能产生一个可以与 V4L 并排存在的 DVB 高层接口。

### 构建


构建这些模块本质上就只是运行 "Make"，但你需要附近有内核源代码树，并且你可能还需要
先设置几个控制性的环境变量，以便将其与那个源代码树链接起来。请参阅此处的 Makefile
中的注释，其中解释了如何做到这一点。

### 源文件列表 / 功能概述


（注意：下面使用的术语"module"通常指 pvrusb2 驱动内松散定义的功能单元，与 Linux
内核中可加载模块的概念无关。）

pvrusb2-audio.[ch] - 这是位于本驱动与 msp3400.ko I2C 客户端驱动（位于 V4L 的
    其他位置）之间的粘合逻辑。

pvrusb2-context.[ch] - 该模块实现了驱动一个实例的上下文。其他一切都最终回溯到或
    以其他方式实例化于这里实现的数据结构中。热插拔最终在此处协调。所有高层接口都
    通过此模块接入驱动。该模块帮助仲裁每个接口对实际驱动核心的访问，并被设计为允许
    通过多个接口的多个实例进行并发访问（因此，例如，你可以一边通过 V4L 向 mplayer
    的实例流式传输视频，一边通过 sysfs 更改调谐器的频率）。

pvrusb2-debug.h - 该头文件定义了一个 printk() 封装，以及一组可在驱动内启用的各类
    调试消息的调试位定义掩码。

pvrusb2-debugifc.[ch] - 该模块实现了一个粗略的、面向命令行的驱动调试接口。除了作为
    实现手动固件提取过程的一部分（见前面提到的 pvrusb2 网站）外，大概只有我用过
    它。它主要是一种调试辅助工具。

pvrusb2-eeprom.[ch] - 这是位于本驱动与 tveeprom.ko 模块之间的粘合逻辑，后者本身
    在 V4L 的其他位置实现。

pvrusb2-encoder.[ch] - 该模块实现了与 pvrusb2 设备内 Conexant mpeg2 编码芯片交互
    所需的全部协议。它是 ivtv 中相应逻辑的粗略翻版，但设计目标（严格隔离）和物理层
    （通过 USB 而非 PCI 做代理）的差异足够大，使得该实现必须完全不同。

pvrusb2-hdw-internal.h - 该头文件定义了驱动中用于跟踪与硬件控制相关的所有内部状态
    的核心数据结构。除了核心硬件处理模块之外，任何人都无权使用该头文件。对驱动的所有
    外部访问都应该通过某个高层接口（例如 V4L、sysfs 等）进行，而且事实上即便是那些
    高层接口也被限制为只能使用 pvrusb2-hdw.h 中定义的 API，而不是本头文件。

pvrusb2-hdw.h - 该头文件定义了用于控制硬件的完整内部 API。高层接口（例如 V4L、
    sysfs）将通过此处工作。

pvrusb2-hdw.c - 该模块实现了处理特定 pvrusb2 设备整体控制的各种逻辑片段。
    （pvrusb2 设备的策略、实例化和仲裁属于 pvrusb-context 的管辖范围，而非此处。）

pvrusb2-i2c-chips-\*.c - 这些模块实现了粘合逻辑，以便在各种 I2C 模块挂接到 I2C
    总线时将它们连接并配置起来。该文件有两个版本。"v4l2"版本旨在与 V4L 一起在树内
    使用，我们只在其中实现对于纯 V4L 环境有意义的逻辑。"all"版本旨在用于 V4L 之外，
    在那里我们可能会遇到来自 ivtv 或较旧内核快照（甚至是独立快照中的支持模块）的其他
    可能"棘手"的模块。

pvrusb2-i2c-cmd-v4l1.[ch] - 该模块实现了向 I2C 模块发送的通用 V4L1 兼容命令。正是在
    这里，pvrusb2 驱动内部的 state 变化被转换为 V4L1 命令，进而发送给各个 I2C 模块。

pvrusb2-i2c-cmd-v4l2.[ch] - 该模块实现了向 I2C 模块发送的通用 V4L2 兼容命令。正是在
    这里，pvrusb2 驱动内部的 state 变化被转换为 V4L2 命令，进而发送给各个 I2C 模块。

pvrusb2-i2c-core.[ch] - 该模块提供了一个对内核友好的 I2C 适配器驱动实现，其他外部
    I2C 客户端驱动（例如 msp3400、tuner、lirc）可以通过它连接并操作 pvrusb2 设备内
    的相应芯片。其他 V4L 模块正是通过这里深入本驱动来操作特定部件（而这些模块又依次
    由 pvrusb2-hdw 协调的粘合逻辑驱动、由 pvrusb2-context 分发，最终通过某个高层接口
    提供给用户）。

pvrusb2-io.[ch] - 该模块实现了一个非常低层的传输缓冲区环，流式传输设备数据需要它。
    该模块**非常**底层。它只操作缓冲区，并不试图定义任何关于这些缓冲区可能被如何使用的
    策略或机制。

pvrusb2-ioread.[ch] - 该模块位于 pvrusb2-io.[ch] 之上，提供可由 read() 系统调用风格
    的 I/O 使用的流式 API。目前这是 pvrusb2-io.[ch] 之上唯一的层，不过这里底层的架构
    本意是允许用额外的模块实现其他风格的 I/O，例如 mmap() 映射的缓冲区或更奇特的
    东西。

pvrusb2-main.c - 这是驱动的最顶层。模块级和 USB 核心的入口点都在这里。这是我们的
    "main"。

pvrusb2-sysfs.[ch] - 这是将 pvrusb2 驱动接入 sysfs 的高层接口。通过该接口，你可以用
    驱动做除了实际流式传输数据之外的所有事情。

pvrusb2-tuner.[ch] - 这是位于本驱动与 tuner.ko I2C 客户端驱动（位于 V4L 的其他位置）
    之间的粘合逻辑。

pvrusb2-util.h - 该头文件定义了驱动中多处使用的一些公共宏。这些宏并非驱动特有，但
    它们总得有个地方放。

pvrusb2-v4l2.[ch] - 这是将 pvrusb2 驱动接入 video4linux 的高层接口。V4L 应用程序正是
    通过这里以通常的 V4L 方式打开并操作驱动。注意，**所有** V4L 功能都只通过这里
    发布，别无其他出处。

pvrusb2-video-\*.[ch] - 这是位于本驱动与 saa711x.ko I2C 客户端驱动（位于 V4L 的
    其他位置）之间的粘合逻辑。注意，saa711x.ko 在 ivtv 中曾被称为 saa7115.ko。这里
    有两个版本，根据找到的具体 saa711[5x].ko 选择其一。

pvrusb2.h - 该头文件包含编译时可调的参数（而且目前驱动几乎没有什么需要调整的）。
