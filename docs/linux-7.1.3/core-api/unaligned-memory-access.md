Linux 运行在大量不同的体系架构上，这些架构在内存访问方面的行为各不相同。
本文档介绍了关于非对齐访问的一些细节，说明为什么你需要编写不会引发此类
访问的代码，以及如何编写这样的代码！


## 非对齐访问的定义


当我们尝试从某个不能被 N 整除的地址（即 addr % N != 0）开始读取 N 字节
数据时，就会发生非对齐内存访问。例如，从地址 0x10004 读取 4 字节数据是
没有问题的，但从地址 0x10005 读取 4 字节数据就会是一次非对齐内存访问。

上面的描述可能显得有些模糊，因为内存访问可以通过不同的方式发生。这里的
语境是在机器码层面：某些指令会从内存读取或向内存写入若干字节（例如 x86
汇编中的 movb、movw、movl）。正如后文将清楚的那样，识别那些会编译为多字节
内存访问指令的 C 语句相对容易，也就是在处理 u16、u32 和 u64 这类类型时。


## 自然对齐


前面提到的规则构成了我们所说的自然对齐：当访问 N 字节内存时，基地址必须
能被 N 整除，即 addr % N == 0。

编写代码时，应假设目标架构具有自然对齐要求。

实际上，只有少数架构在所有内存访问大小上都要求自然对齐。然而，我们必须
考虑所有受支持的架构；编写满足自然对齐要求的代码，是实现完全可移植性
最简便的方式。


## 为什么非对齐访问是有害的


执行非对齐内存访问所产生的后果因架构而异。为这些差异写一整篇文档都很容易；
下面简要总结一下常见的情况：

 - 某些架构能够透明地处理非对齐内存访问，但通常会有明显的性能代价。
 - 某些架构在非对齐访问发生时引发处理器异常。异常处理程序能够修正该
   非对齐访问，但性能代价很大。
 - 某些架构在非对齐访问发生时引发处理器异常，但这些异常中没有包含足够的
   信息来修正该非对齐访问。
 - 某些架构无法进行非对齐内存访问，却会悄悄地去执行一次与所请求不同的
   内存访问，从而导致一个难以察觉、难以发现的隐蔽代码缺陷！

从上面的内容应该可以清楚地看出：如果你的代码导致非对齐内存访问的发生，
那么你的代码在某些平台上将不能正常工作，而在另一些平台上则会造成性能
问题。


## 不会引发非对齐访问的代码


起初，上面的这些概念看起来可能有点难以与实际编码实践相联系。毕竟，你对
某些变量的内存地址并没有很大的控制权。

幸运的是，事情并没有那么复杂，因为在大多数情况下，编译器会替你保证一切
正常工作。例如，请看下面的代码

```

	struct foo {
		u16 field1;
		u32 field2;
		u8 field3;
	};

```
假设上述结构的一个实例驻留在起始地址为 0x10000 的内存中。以基本的理解
来看，认为访问 field2 会导致非对齐访问并不是没有道理。你可能会预期
field2 位于结构中偏移 2 字节处，即地址 0x10002，但该地址并不能被 4 整除
（记住，这里我们读取的是一个 4 字节的值）。

幸运的是，编译器理解对齐约束，因此在上述情况下，它会在 field1 和 field2
之间插入 2 字节的填充。因此，对于标准的结构类型，你始终可以依赖编译器
对结构进行填充，从而让对字段的访问得到恰当的对齐（前提是你没有把字段
强制转换为不同长度的类型）。

类似地，你也可以依赖编译器根据变量类型的大小，将变量和函数参数对齐到
自然对齐方案。

在这一点上，应该已经很清楚：访问单个字节（u8 或 char）永远不会引发非对齐
访问，因为所有内存地址都能被 1 整除。

相关地，考虑到上述因素，你可能会发现可以通过重新排列结构中的字段，把字段
放到原本会被插入填充的位置，从而减少结构实例所占用的整体内存大小。
对于自然对齐方案，下面是最优的字段布局

```

	struct foo {
		u32 field2;
		u16 field1;
		u8 field3;
	};

```
编译器只需要在结构末尾增加 1 字节的填充。添加这 1 字节填充是为了满足
这些结构的数组的对齐约束。

另一点值得提及的是在结构类型上使用 __attribute__((packed))。这个 GCC
特有的属性告诉编译器永远不要在结构内部插入任何填充，当你想用一个 C 结构
来表示以固定排列“从线上”传来的某些数据时很有用。

你可能会倾向于认为，使用该属性后在访问不满足架构对齐要求的字段时，很容易
导致非对齐访问。然而，同样地，编译器知道对齐约束，并会生成额外的指令，以
不会导致非对齐访问的方式执行内存访问。当然，与未使用 packed 的情况相比，
这些额外指令显然会造成性能损失，因此 packed 属性只应在“避免结构填充”很
重要时才使用。


## 会引发非对齐访问的代码


带着上面的认识，我们来看一个真实的函数示例，它可能导致非对齐内存访问。
下面这个函数取自 include/linux/etherdevice.h，是一个用于比较两个数的
优化例程

```

  bool ether_addr_equal(const u8 *addr1, const u8 *addr2)
  {
  #ifdef CONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESS
	u32 fold = ((*(const u32 *)addr1) ^ (*(const u32 *)addr2)) |
		   ((*(const u16 *)(addr1 + 4)) ^ (*(const u16 *)(addr2 + 4)));

	return fold == 0;
  #else
	const u16 *a = (const u16 *)addr1;
	const u16 *b = (const u16 *)addr2;
	return ((a[0] ^ b[0]) | (a[1] ^ b[1]) | (a[2] ^ b[2])) == 0;
  #endif
  }

```
在上述函数中，当硬件具有高效的非对齐访问能力时，这段代码没有问题。但当
硬件无法在任意边界访问内存时，对 a[^0^] 的引用会导致从地址 addr1 开始
从内存读取 2 字节（16 位）。

想想如果 addr1 是一个奇数地址（如 0x10003）时会发生什么。（提示：那会是
一次非对齐访问。）

尽管上面的函数存在潜在的非对齐访问问题，它仍然被包含进内核中，但要知道
它只在 16 字节对齐的地址上才能正常工作。由调用者来保证这种对齐，或者干脆
不使用这个函数。这个对齐不安全函数依然有用，因为在你能保证对齐的情况下
它是一个不错的优化——在以太网网络环境中，这几乎总是成立的。

```

	void myfunc(u8 *data, u32 value)
	{
		[...]
		*((u32 *) data) = cpu_to_le32(value);
		[...]
	}

```
每当 data 参数指向一个不能被 4 整除的地址时，这段代码就会导致非对齐访问。

总结一下，你可能遇到非对齐访问问题的主要场景有两种：

 1. 将变量强制转换为不同长度的类型
 2. 指针运算之后，再访问至少 2 字节的数据


## 避免非对齐访问


避免非对齐访问最简单的方法是使用 <linux/unaligned.h> 头文件提供的
get_unaligned() 和 put_unaligned() 宏。

回到前面那个可能导致非对齐访问的示例

```

	void myfunc(u8 *data, u32 value)
	{
		[...]
		*((u32 *) data) = cpu_to_le32(value);
		[...]
	}

```

```

	void myfunc(u8 *data, u32 value)
	{
		[...]
		value = cpu_to_le32(value);
		put_unaligned(value, (u32 *) data);
		[...]
	}

```

get_unaligned() 宏的工作方式类似。假设 'data' 是一个指向

```

	u32 value = get_unaligned((u32 *) data);

```
这些宏适用于任意长度的内存访问（并不像上面示例那样仅限于 32 位）。请注意，
与对对齐内存的标准访问相比，使用这些宏来访问非对齐内存在性能上代价可能
很高。

如果不方便使用这些宏，另一个选择是使用 memcpy()，其中源或目标（或两者）
的类型为 u8** 或 unsigned char**。由于这种操作是按字节进行的，因此可避免
非对齐访问。


## 对齐与网络


在需要加载对齐的架构上，网络要求 IP 头对齐到四字节边界，以优化 IP 协议栈。
对于常规以太网硬件，使用常量 NET_IP_ALIGN。在大多数架构上这个常量的值为 2，
因为普通的以太网头部为 14 字节长，所以为了获得恰当的对齐，需要将 DMA 到
一个可以表示为 4*n + 2 的地址。一个显著的例外是 powerpc，它将 NET_IP_ALIGN
定义为 0，因为对非对齐地址进行 DMA 的代价可能非常高昂，以至于超过了非对齐
加载的代价。

对于某些无法进行 4*n+2 这类非对齐地址 DMA 的以太网硬件，或非以太网硬件，
这可能会成为问题，此时需要将收到的帧复制到对齐的缓冲区中。由于在能够进行
非对齐访问的架构上这是不必要的，代码可以写成

```

	#ifdef CONFIG_HAVE_EFFICIENT_UNALIGNED_ACCESS
		skb = original skb
	#else
		skb = copy skb
	#endif

```
