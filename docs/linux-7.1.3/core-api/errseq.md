## errseq_t 数据类型


errseq_t 是一种在一处记录错误，并允许任意数量的“订阅者”判断自上次采样以来该值是否发生了变化的方法。

它最初的应用场景是跟踪文件同步系统调用（fsync、fdatasync、msync 和 sync_file_range）的错误，但也可能用于其他情形。

它被实现为一个无符号 32 位值。低位的若干比特用于保存错误码（介于 1 与 MAX_ERRNO 之间）。高位的比特用作计数器。这一切通过原子操作而非加锁来实现，因此这些函数可以在任何上下文中被调用。

注意，如果频繁记录新的错误，由于可用作计数的比特很少，存在发生冲突的风险。

为缓解这一问题，错误值与计数器之间的那个比特被用作一个标志，用来表明自记录新值以来该值是否已经被采样过。这样，如果在上次记录错误之后无人采样，我们就可以避免递增计数器。

因此，我们得到的值大致如下所示：

+--------------------------------------+----+------------------------+
| 31..13                               | 12 | 11..0                  |
+--------------------------------------+----+------------------------+
| counter                              | SF | errno                  |
+--------------------------------------+----+------------------------+

其基本思想是让“观察者（watchers）”对 errseq_t 值进行采样，并将其保存为一个游标。随后该值可用于判断自采样以来是否发生过任何新的错误，并原子地记录下检查时所处的状态。这使得我们可以将错误记录在一处，然后拥有多个“观察者”，它们能够判断自上次检查以来该值是否发生了变化。

一个新的 errseq_t 应当始终被清零。全零的 errseq_t 值是一种特殊（但常见）的情况，表示从未发生过错误。因此，全零值可作为“纪元（epoch）”，用于判断是否自其首次初始化以来曾经设置过错误。

## API 用法


让我来给你讲一个关于一个打工仔的故事。总体而言，他是个不错的员工，但公司的管理层有点……过于臃肿。今天他要向 77 个主管汇报，而明天“大老板”要从外地过来，肯定也要考考这个可怜的家伙。

他们都把活派给他做——多到他记不清谁给了他什么，但这并不是什么大问题。主管们只想知道，到目前为止交给他的活他是不是都干完了，以及自他们上次问过之后他有没有犯过错。

他犯的错可能是在并非他们真正交给他的活上，但他无法追踪到那种细节程度，他所能记住的只是自己最近犯的那个错。

```

        struct worker_drone {
                errseq_t        wd_err; /* for recording errors */
        };

```
```

        struct worker_drone wd;

        wd.wd_err = (errseq_t)0;

```
主管们进来，对当天的情况做了一次初始读取。他们
```

        struct supervisor {
                errseq_t        s_wd_err; /* private "cursor" for wd_err */
                spinlock_t      s_wd_err_lock; /* protects s_wd_err */
        }

        struct supervisor       su;

        su.s_wd_err = errseq_sample(&wd.wd_err);
        spin_lock_init(&su.s_wd_err_lock);

```
现在他们开始交给他任务去做。每隔几分钟，他们就要求他完成到目前为止交给他的所有工作。然后他们问他
```

        spin_lock(&su.su_wd_err_lock);
        err = errseq_check_and_advance(&wd.wd_err, &su.s_wd_err);
        spin_unlock(&su.su_wd_err_lock);

```
到目前为止，这只是一直返回 0。

如今，这家公司的老板相当吝啬，给了他劣质的设备来工作。设备偶尔会出故障，于是他就犯了错。他重重地叹了口气，并把它标记为
```

        errseq_set(&wd.wd_err, -EIO);

```
……然后继续工作。主管们最终再次轮询，每个人在下次检查时都会收到该错误。后续调用将返回 0，直到记录另一个错误为止，此时会向每个人报告一次。

注意，主管们无法得知他犯了几个错误，只能知道自上次检查以来是否犯过错误，以及记录的最新值。

偶尔，大老板会进来做一次抽查，并让工人为他做一个一次性任务。他并不像主管那样全程监视工人，但确实需要知道在处理他的任务时是否发生过错误。

他只需对工人当前的 errseq_t 进行采样，然后使用该
```

        errseq_t since = errseq_sample(&wd.wd_err);
        /* submit some work and wait for it to complete */
        err = errseq_check(&wd.wd_err, since);

```
由于他在那之后就会丢弃“since”，因此无需在此处推进它。他也不需要任何加锁，因为没有其他人会使用它。

## 串行化 errseq_t 游标更新


注意，errseq_t API 在 check_and_advance_operation 期间并不保护 errseq_t 游标。只有规范的错误码是以原子方式处理的。在可能有多个任务同时使用同一个 errseq_t 游标的情况下，串行化对该游标的更新是很重要的。

如果不这样做，游标就有可能向后回退，从而导致同一个错误被报告多次。

因此，通常更好的做法是先执行一次 errseq_check 以查看是否有变化，稍后再执行
```

        if (errseq_check(&wd.wd_err, READ_ONCE(su.s_wd_err)) {
                /* su.s_wd_err is protected by s_wd_err_lock */
                spin_lock(&su.s_wd_err_lock);
                err = errseq_check_and_advance(&wd.wd_err, &su.s_wd_err);
                spin_unlock(&su.s_wd_err_lock);
        }

```
这样可以在自上次检查以来没有任何变化的常见情况下避免自旋锁。
