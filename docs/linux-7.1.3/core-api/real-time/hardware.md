
## 考量硬件


:Author: Sebastian Andrzej Siewior <bigeasy@linutronix.de>

工作负载的处理方式会受到其所运行硬件的影响。关键组件包括 CPU、内存以及连接它们的
总线。这些资源由系统上的所有应用程序共享。因此，单个应用程序对某一资源的重度使用
可能会影响其他应用程序中工作负载的确定性处理。

以下是一个简要概述。

### 系统内存与缓存


主内存及相关的缓存是系统中任务之间最常见的共享资源。一个任务可能独占可用的缓存，
迫使另一个任务等到缓存行写回主内存后才能继续。这种争用的影响因写入模式和可用缓存
大小而异。较大的缓存可以减少停顿，因为在写回之前可以缓冲更多的行。相反，某些写入
模式可能触发缓存控制器一次刷新许多行，导致应用程序停顿直到操作完成。

如果应用程序不共享同一个 CPU 缓存，这个问题可以部分缓解。内核了解缓存拓扑并将其
导出到用户空间。诸如 Portable Hardware Locality (hwloc) 项目（https://www.open-mpi.org/projects/hwloc/）
中的 **lstopo** 等工具可以可视化该层级结构。

避免共享 L2 或 L3 缓存并不总是可能的。即使缓存共享降到最低，访问系统内存时仍可能
出现瓶颈。内存不仅被 CPU 使用，也被外设通过 DMA 使用，例如显卡或网络适配器。

在某些情况下，如果硬件提供必要的支持，缓存和内存瓶颈是可以被控制的。在 x86 系统上，
Intel 提供了缓存分配技术（Cache Allocation Technology, CAT），它能在应用程序之间
实现缓存分区并对互连进行控制。AMD 在平台服务质量（Platform Quality of Service,
PQoS）下提供了类似功能。在 Arm64 上，对应的是内存系统资源分区与监视（Memory System
Resource Partitioning and Monitoring, MPAM）。

这些特性可以通过 Linux 资源控制接口配置。详细信息，请参阅
Documentation/filesystems/resctrl.rst。

perf 工具可用于监视缓存行为。它可以分析应用程序的缓存未命中，并比较它们在相邻 CPU
上不同工作负载下如何变化。更强大的是，perf c2c 工具可以帮助识别缓存到缓存的问题，
即多个 CPU 核心反复访问和修改同一缓存行上的数据。

### 硬件总线


实时系统通常需要直接访问硬件来完成工作。此过程中的任何延迟都是不受欢迎的，因为它
会影响任务的结果。例如，在 I/O 总线上，改变的输出可能不会立即可见，而是根据用于
通信的总线延迟以可变的延迟出现。

像 PCI 这样的总线相对简单，因为寄存器访问被直接路由到所连接的设备。在最坏情况下，
读操作会使 CPU 停顿直到设备响应。

像 USB 这样的总线更为复杂，涉及多个层。寄存器读或写被封装在 USB 请求块（USB
Request Block, URB）中，然后由 USB 主机控制器发送给设备。时序和延迟受底层 USB 总线
影响。请求无法立即发送；它们必须根据端点类型和主机控制器的调度规则，与下一个帧边界
对齐。这会引入延迟和额外的时延。例如，通过 USB 连接的网络设备仍可能提供充足的吞吐
量，但在发送或接收数据包时增加的延迟可能无法满足某些实时用例的要求。

总线延迟的额外限制可能来自电源管理。例如，启用了活动状态电源管理（Active State
Power Management, ASPM）的 PCIe 可以挂起设备与主机之间的链路。虽然这种行为有利于
节能，但它会延迟设备访问并为响应增加延迟。这个问题不仅限于 PCIe；片上系统（System
on-Chip, SoC）内部的总线也可能受到电源管理机制的影响。

### 虚拟化


在 KVM 这样的虚拟化环境中，每个客户机 CPU 都被表示为宿主机上的一个线程。如果这样的
线程以实时优先级运行，则应该对系统进行测试，以确认它能够长时间维持这种行为。由于其
优先级，该线程不会被较低优先级的线程（例如 SCHED_OTHER）抢占，后者可能因此得不到
CPU 时间。如果较低优先级的线程被固定到已被实时任务占用且无法推进的 CPU 上，这会
引发问题。即使某个 CPU 已被隔离，系统仍可能（意外地）在该 CPU 上启动一个每 CPU 线程。
确保客户机 CPU 进入空闲状态很困难，因为这需要避免任务调度和中断处理。此外，如果
客户机 CPU 确实进入空闲状态，但客户机系统以 **idle=poll** 选项启动，则客户机 CPU
永远不会进入空闲状态，而是会自旋直到事件到来。

设备处理带来了额外的考量。模拟的 PCI 设备或 VirtIO 设备需要宿主机的对应部分来完成
请求。这会增加延迟，因为宿主机必须拦截并直接处理请求，或调度一个线程来完成它。如果
所需的 PCI 设备直接直通给客户机，就可以避免这些延迟。某些设备（如网络或存储控制器）
支持 PCIe SR-IOV 特性。SR-IOV 允许将单个 PCIe 设备划分为多个虚拟功能，然后可以将
它们分配给不同的客户机。

### 网络


对于低延迟网络，完整的网络协议栈可能并不理想，因为它会引入额外的延迟来源。在这种
情况下，可以使用 XDP 作为捷径，在仍然依赖内核网络驱动的同时绕过大部分协议栈。

要求是网络驱动必须支持 XDP（最好使用"skb pool"），并且应用程序必须使用 XDP 套接字。
额外的配置可能涉及 BPF 过滤器、调整网络队列，或配置用于基于时间传输的 qdisc。这些
技术通常应用于时间敏感网络（Time-Sensitive Networking, TSN）环境中。

记录所有必需的步骤超出了本文的范围。有关详细指南，请参阅 TSN 文档
https://tsn.readthedocs.io。

另一个有用的资源是 Linux 实时通信测试台（Linux Real-Time Communication Testbench）
https://github.com/Linutronix/RTC-Testbench。
该项目的目标是验证实时网络通信。它可以被视为网络领域的"cyclictest"，同时也作为
应用程序开发的起点。
