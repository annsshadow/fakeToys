
## 实时内核的差

:Author: Sebastian Andrzej Siewior <bigeasy@linutronix.de>

## 前言


借助强制线程化中断和睡眠自旋锁，以前会导致较长调度延迟的代码路径已经变得可抢占，并被移入了进程上下文。这让调度器能够更有效地管理它们，并以更低的延迟响应更高优先级的任务
以下各章概述PREEMPT_RT 内核与标准、非 PREEMPT_RT 内核之间的关键差异
## 加锁


自旋锁（spinlock_t）用于为既从中断上下文又从进程上下文访问的数据结构提供同步。出于这个原因，加锁函数也提供了_irq() _irqsave() 后缀的版本，它们会在获取锁之前禁用中断。这确保了在中断开启的进程上下文中能够安全地获取锁
然而，PREEMPT_RT 系统上，中断被强制线程化，不再运行在IRQ 上下文中。因此，在使spinlock_t 时，作为加锁过程的一部分去禁用中断是没有必要的
对于中断处理、调度器或定时器子系统等底层核心组件，内核使raw_spinlock_t。这种锁类型保留了传统的语义：它禁用抢占，并且当_irq() _irqsave() 一起使用时，也会禁用中断。这确保了在必须保持不可抢占或中断被禁用的临界区中能够进行正确的同步
## 执行上下

PREEMPT_RT 系统中，中断处理是通过线程化中断在进程上下文中调用的。内核的其他部分也通过不同的机制将其执行转移到线程上下文。目标是保持执行路径可抢占，从而让调度器在有更高优先级任务需要运行时能够中断它们
下面概述了参与这一向线程化、可抢占执行转变的内核子系统
### 中断处理


PREEMPT_RT 系统上，所有中断都被强制线程化。例外是使用 IRQF_NO_THREAD、IRQF_PERCPU IRQF_ONESHOT 标志请求的中断
IRQF_ONESHOT 标志与线程化中断一起使用，即那些使request_threaded_irq() 注册并且只提供线程化处理函数的中断。其目的是保持中断线被屏蔽，直到线程处理函数执行完毕
如果在这种情况下还提供了主处理函数，那么该处理函数绝不能获取任何睡眠锁，因为它不会被线程化。处理函数应当尽量精简，并且必须避免引入延迟，例如对硬件寄存器进行忙等待

### 软中断、底半部处理


软中断由中断处理程序触发，并在处理程序返回后执行。由于它们在线程上下文中运行，因此可以被其他线程抢占。不要假定软中断上下文是在禁用抢占的情况下运行的。这意味着你不能依赖像 local_bh_disable() 这样的机制在进程上下文中保护CPU 变量。因为在 PREEMPT_RT 下软中断处理程序是可抢占的，这种方式无法提供可靠的同步
如果出于性能原因需要这类保护，可以考虑使用 local_lock_nested_bh()。在PREEMPT_RT 内核上，它允lockdep 验证底半部已被禁用。在 PREEMPT_RT 系统上，它会添加必要的锁以确保适当的保护
使用 local_lock_nested_bh() 还能让加锁范围变得显式，更易于读者和维护者理解

### 姣?CPU 鍙橀噺


应当避免仅使preempt_disable() 来保护对CPU 变量的访问，尤其是当临界区具有无界运行时间、或者可能调用会睡眠API 时
如果出于性能原因认为使用 spinlock_t 代价过高，可以考虑使用 local_lock_t。在PREEMPT_RT 配置下，lockdep 被禁用时它不会引入运行时开销。启lockdep 时，它会验证该锁只在进程上下文中获取，而绝不会从软中断或硬 IRQ 上下文获取
PREEMPT_RT 内核上，local_lock_t 使用CPU spinlock_t 实现，它在保持系统可抢占的同时，为每 CPU 数据提供安全的本地保护
由于 PREEMPT_RT 上的 spinlock_t 不会禁用抢占，因此不能依靠隐式的抢占禁用来保护每 CPU 数据。如果这种继承而来的抢占禁用是必不可少的，并且由于性能约束、代码简洁性或 API 内的抽象边界而无法使local_lock_t，那preempt_disable_nested() 可能是一个合适的替代方案。在PREEMPT_RT 内核上，它会通过 lockdep 验证抢占已被禁用。在 PREEMPT_RT 上，它会显式禁用抢占
### 瀹氭椂鍣。

默认情况下，hrtimer 在硬中断上下文中执行。例外是使用 HRTIMER_MODE_SOFT 标志初始化的定时器，它们在软中断上下文中执行
PREEMPT_RT 内核上，这一行为被反转：hrtimer 默认在软中断上下文中执行，通常位于 ktimersd 线程内。该线程以最低的实时优先级运行，确保它在任何 SCHED_OTHER 任务之前执行，但不会干扰更高优先级的实时线程。要PREEMPT_RT 上显式请求在硬中断上下文中执行，定时器必须被标记HRTIMER_MODE_HARD 标志
### 内存分配


内存分配 API（如 kmalloc() alloc_pages()）需要一gfp_t 标志来指示分配上下文。在PREEMPT_RT 内核上，从中断上下文或禁用抢占的区段中分配内存时，必须使GFP_ATOMIC。这是因为分配器在这些上下文中绝不能睡眠以等待内存变得可用
然而，这种方式PREEMPT_RT 内核上不起作用。PREEMPT_RT 中的内存分配器在内部使用睡眠锁，而这些锁在抢占被禁用时无法获取。幸运的是，这通常不成问题，因PREEMPT_RT 将大多数传统上在禁用抢占或中断的情况下运行的上下文移到了允许睡眠的线程上下文中
仍然成问题的是显式禁用抢占或中断的代码。在这种情况下，内存分配必须在临界区之外执行
这一限制也适用于内存释放例程，kfree() free_pages()，它们也可能涉及内部加锁，绝不能从不可抢占的上下文中调用
### IRQ work


irq_work API 提供了一种在中断上下文中调度回调的机制。它设计用于传统调度不可能的上下文，例如NMI 处理程序内部或调度器内部，在这些地方使用工作队列是不安全的
在非 PREEMPT_RT 系统上，所irq_work 项都在中断上下文中立即执行。标IRQ_WORK_LAZY 的项会推迟到下一个定时器节拍，但仍然在中断上下文中执行
PREEMPT_RT 系统上，执行模型发生了变化。因irq_work 回调可能会获取睡眠锁，或者具有无界的执行时间，它们由CPU irq_work 内核线程在线程上下文中处理。该线程以最低的实时优先级运行，确保它在任何 SCHED_OTHER 任务之前执行，但不会干扰更高优先级的实时线程
例外是使IRQ_WORK_HARD_IRQ 标记的工作项，它们仍在硬中断上下文中执行。惰性项（IRQ_WORK_LAZY）继续被推迟到下一个定时器节拍，并且也irq_work 线程执行
### RCU 回调


RCU 回调默认在软中断上下文中调用。它们的执行很重要，因为根据用例的不同，它们要么释放内存，要么确保状态转换取得进展。将这些回调作为软中断链的一部分运行，可能导致不理想的情况，例如ksoftirqd 内执行时与其SCHED_OTHER 任务争用 CPU 资源
为了避免在软中断上下文中运行回调，RCU 子系统提供了一种机制，让它们在进程上下文中执行。这种行为可以通过设置引导命令行参rcutree.use_softirq=0 来启用。在使用 PREEMPT_RT 配置的内核中会强制启用该设置
## 自旋直到就绪


“自旋直到就绪”模式涉及重复检查（自旋等待）某个数据结构的状态，直到它变得可用。这种模式假定抢占、软中断或中断已被禁用。如果数据结构被标记为忙，就假定它正被另一CPU 使用，而自旋应当最终成功，因为那个 CPU 在不断取得进展
一些例子是 hrtimer_cancel() timer_delete_sync()。这些函数会取消在禁用中断或软中断情况下执行的定时器。如果一个线程试图取消一个定时器并发现它处于活跃状态，那么在回调完成之前自旋是安全的，因为回调只能在另一CPU 上运行并最终结束
然而，PREEMPT_RT 内核上，定时器回调运行在线程上下文中。这就带来了一个挑战：一个试图取消定时器的高优先级线程可能会抢占定时器回调线程。由于亲和性约束，调度器无法将回调线程迁移到另一CPU，因此即便在多处理器系统上，自旋也可能导致活锁
为了避免这种情况，取消方和回调方都必须使用支持优先级继承的握手机制。这让取消线程可以挂起，直到回调完成，从而确保向前推进而不会冒活锁的风险
为了API 层面解决这个问题，顺序锁被扩展，以允许自旋的读者与可能阻塞的写者之间进行正确的交接
### 椤哄簭閿。

顺序计数器和顺序锁在 Documentation/locking/seqlock.rst 中有文档说明
该接口已被扩展，以确保写者和自旋读者上下文具有正确的抢占状态。这是通过将写者串行化锁直接嵌入到顺序计数器类型中实现的，从而产生了诸如 seqcount_spinlock_t seqcount_mutex_t 这样的复合类型
这些复合类型允许读者检测到正在进行的写操作，并主动提升写者的优先级，以帮助其完成更新，而不是自旋等待其完成
如果使用普通的 seqcount_t，则必须格外小心地在更新期间将读者与写者同步。写者必须确保其更新相对于读者是串行化且不可抢占的。这无法通过普通的 spinlock_t 实现，因PREEMPT_RT 上的 spinlock_t 不会禁用抢占。在这种情况下，使用 seqcount_spinlock_t 是首选方案
然而，如果其中不涉及自旋，即如果读者只需要检测是否有写操作已开始、而无需与之串行化，那么使用 seqcount_t 是合理的
