## CRC 计算简明教程


CRC 是一个长除法（long-division）的余数。你将 CRC 附加到消息上，整个消息（消息+CRC）就是给定 CRC 多项式的倍数。要校验 CRC，你可以检查 CRC 是否与重新计算的值匹配，**或者**你可以检查消息+CRC 上计算出的余数为 0。后一种方法被许多硬件实现所采用，这也是为何那么多协议将帧结束标志放在 CRC 之后。

它实际上与你在学校学到的长除法相同，只是：

- 我们在二进制下工作，因此数字只有 0 和 1，并且
- 当对多项式做除法时，没有进位。我们不是做加法和减法，而是做异或（xor）。因此，我们往往会稍微混淆加法与减法的区别。

与所有除法一样，余数总是小于除数。要生成 32 位的 CRC，除数实际上是一个 33 位的 CRC 多项式。由于它是 33 位长，第 32 位总是被置位，因此通常 CRC 以十六进制书写时会省略最高有效位。（如果你熟悉 IEEE 754 浮点格式，这是同样的思路。）

注意，CRC 是计算得于一个**比特**串之上，因此你必须决定每个字节内比特的端序（endianness）。为了获得最佳的检错特性，这应对应于它们实际被发送的顺序。例如，标准 RS-232 串口是小端的；最高有效位（有时用于奇偶校验）最后发送。在将 CRC 字附加到消息时，你应按正确的顺序进行，以匹配端序。

就像普通除法一样，你一次处理一位（数码）。除法每一步你取被除数的一位（比特）并将其追加到当前余数上。然后你算出除数的适当倍数去减，使余数回到范围内。在二进制下这很简单 —— 它必须是 0 或 1，而为了让异或相互抵消，它只是余数的第 32 位的拷贝。

在计算 CRC 时，我们不关心商，因此我们可以将商位丢弃，但从余数中减去多项式的适当倍数后，我们又回到了起点，准备好处理下一位。

```
	for (i = 0; i < input_bits; i++) {
		multiple = remainder & 0x80000000 ? CRCPOLY : 0;
		remainder = (remainder << 1 | next_input_bit()) ^ multiple;
	}
```
注意，为了获取移位后余数的第 32 位，我们要查看余数移位**之前**的第 31 位。

但也要注意，我们移入余数的 next_input_bit() 比特实际上直到 32 位之后才影响任何决策。因此，前 32 个周期相当无聊。此外，为了在消息末尾为 CRC 腾出 32 位空间，我们必须在每条消息末尾额外添加 32 个移入零的周期。

这些细节引出了一个标准技巧：将合并 next_input_bit() 延迟到它真正被需要的时刻。于是前 32 个周期可以预先计算，而合并最后 32 个零比特以腾出空间：

```
	for (i = 0; i < input_bits; i++) {
		remainder ^= next_input_bit() << 31;
		multiple = (remainder & 0x80000000) ? CRCPOLY : 0;
		remainder = (remainder << 1) ^ multiple;
	}
```
```
	for (i = 0; i < input_bits; i++) {
		remainder ^= next_input_bit();
		multiple = (remainder & 1) ? CRCPOLY : 0;
		remainder = (remainder >> 1) ^ multiple;
	}
```
余数多项式的最高有效系数存储在二进制“remainder”变量的最低有效位中。
端序的其他细节已隐藏在 CRCPOLY（必须按位反转）和 next_input_bit() 中。

只要 next_input_bit 以合理的顺序返回比特，我们就不**必**等到最后一刻才合并额外比特。

```
	for (i = 0; i < input_bytes; i++) {
		remainder ^= next_input_byte() << 24;
		for (j = 0; j < 8; j++) {
			multiple = (remainder & 0x80000000) ? CRCPOLY : 0;
			remainder = (remainder << 1) ^ multiple;
		}
	}
```
```
	for (i = 0; i < input_bytes; i++) {
		remainder ^= next_input_byte();
		for (j = 0; j < 8; j++) {
			multiple = (remainder & 1) ? CRCPOLY : 0;
			remainder = (remainder >> 1) ^ multiple;
		}
	}
```
如果输入是 32 位的倍数，你甚至可以一次异或一个 32 位字，并将内层循环计数增加到 32。

你也可以混合搭配两种循环风格，例如以逐字节方式处理消息主体，并对末尾的零头字节添加逐位处理。

为了减少条件分支的数量，软件通常使用逐字节查表法，由 Dilip V. Sarwate 推广，
“Computation of Cyclic Redundancy Checks via Table Look-Up”（通过查表计算循环冗余校验），Comm. ACM
v.31 no.8（1988 年 8 月）p. 1008-1013。

这里，我们不是只移位余数的一位来决定要减去的正确倍数，而是可以一次移位一个字节。这会产生一个 40 位（而非 33 位）的中间余数，而多项式的正确倍数则使用一个由高 8 位索引的 256 项查找表获得。

（表项就是给定单字节消息的 CRC-32。）

当空间更受限时，可以使用更小的表，例如两次 4 位移位，然后查一个 16 项的表。

使用这种技术一次处理超过 8 位并不实用，因为大于 256 项的表会占用过多内存，而且更重要的是，会占用过多的 L1 缓存。

为了获得更高的软件性能，可以使用“切片（slicing）”技术。
参见 “High Octane CRC Generation with the Intel Slicing-by-8 Algorithm”（使用 Intel Slicing-by-8 算法生成高性能 CRC），
ftp://download.intel.com/technology/comms/perfnet/download/slicing-by-8.pdf

这不会改变查表的数量，但会增加并行度。使用经典的 Sarwate 算法时，每次查表都必须在下一次查表的索引被算出之前完成。

“切片为 2（slicing by 2）”技术会一次移位余数 16 位，产生一个 48 位的中间余数。它不是在 65536 项的表中做单次查找，而是在两个不同的 256 项表中查找两个高位字节。每个表都包含用于抵消相应字节所需的余数。这些表不同，因为要抵消的多项式不同。一个的多项式从 x^32 到 x^39，另一个从 x^40 到 x^47。

由于现代处理器可以处理许多并行内存操作，这花费的时间仅比单次查表略长，因此执行速度几乎是基本 Sarwate 算法的两倍。

这可以扩展到使用 4 个 256 项表的“切片为 4（slicing by 4）”。每一步，取出 32 位数据，与 CRC 异或，然后将结果拆分为字节并在表中查找。由于 32 位移位使中间余数的低位置零，最终 CRC 就是 4 次查表的异或。

但这仍然强制顺序执行：在下一组的 4 次查表全部完成之前，不能开始第二组查表。因此，处理器的加载/存储单元有时会处于空闲状态。

为了最大限度地利用处理器，“切片为 8（slicing by 8）”并行执行 8 次查找。每一步，32 位 CRC 被移位 64 位并与 64 位输入数据异或。需要注意的是，那 8 个字节中有 4 个只是输入数据的拷贝；它们根本不依赖于先前的 CRC。因此，这 4 次查表可以立即开始，无需等待先前的循环迭代。

通过始终保持 4 次加载在途（in flight），现代超标量处理器可以保持繁忙并充分利用其 L1 缓存。

关于真实世界中 CRC 实现的另外两个细节：

通常，向已经是多项式倍数的消息附加零比特，会产生该多项式更大的倍数。因此，基本的 CRC 无法检测附加的零比特（或零字节）。为了使 CRC 能够检测这种情况，通常会在附加 CRC 之前将其取反。这会使消息+crc 的余数不是零，而是某个固定的非零值。（取反模式的 CRC，0xffffffff。）

同样的问题也适用于消息前面附加的零比特，并使用了类似的解决方案。不是以 0 余数开始 CRC 计算，而是使用全 1 的初始余数。只要你以相同的方式开始解码，这就没有区别。
