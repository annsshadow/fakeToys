## 标签匹配逻辑


MPI 标准定义了一组称为标签匹配（tag-matching）的规则，用于将源发送操作与目标接收相匹配。
以下参数必须与以下源和目标参数匹配：

- 通信器（Communicator）
- 用户标签 - 接收方可以指定通配符（wild card）
- 源秩（Source rank）– 接收方可以指定通配符（wild car）
- 目标秩（Destination rank）– 通配符（wild）

排序规则要求：当可能有多对发送和接收消息信封（envelope）相匹配时，必须使用该对中包含最早
投递的发送和最早投递的接收的配对来满足匹配操作。然而，这并不暗示标签按创建顺序被消耗，
例如，如果较早的标签无法用于满足匹配规则，则较晚生成的标签可能会被消耗。

当消息从发送方发送到接收方时，通信库可能会尝试在对应的匹配接收被投递之前或之后处理该操作。
如果相应的匹配接收已被投递，这就是一个预期消息（expected message），否则称为意外消息
（unexpected message）。实现通常对这两种不同的匹配实例使用不同的匹配方案。

为了降低 MPI 库的内存占用，MPI 实现通常为此使用两种不同的协议：

1. Eager 协议 - 当发送被发送方处理时，完整的消息被发送。在 send_cq 中收到一个完成发送，
   通知缓冲区可以重用。

2. Rendezvous 协议 - 发送方发送标签匹配头，并在首次通知接收方时可能发送一部分数据。当对应的
   缓冲区被投递时，响应方将使用头中的信息直接对匹配缓冲区发起一个 RDMA READ 操作。需要收到
   一个 fin 消息，缓冲区才能被重用。

## 标签匹配实现


使用了两类匹配对象：已投递接收列表（posted receive list）和意外消息列表（unexpected message
list）。应用程序通过调用 MPI 接收例程在已投递接收列表中投递接收缓冲区，并使用 MPI 发送例程
投递发送消息。已投递接收列表的头部可能由硬件维护，软件负责对该列表进行影子（shadow）维护。

当发送被发起并到达接收方时，如果没有为此到达的消息预投递的接收，它会被传递给软件并放入意外
消息列表。否则将处理匹配，包括适当的 rendezvous 处理，将数据投递到指定的接收缓冲区。这允许
接收侧的 MPI 标签匹配与计算重叠。

当接收消息被投递时，通信库将首先检查软件的意外消息列表以寻找匹配的接收。如果找到匹配，则使用
软件控制的协议将数据投递到用户缓冲区。UCX 实现根据数据大小使用 eager 或 rendezvous 协议。
如果未找到匹配，且整个预投递接收列表由硬件维护，并且该列表还有空间再添加一个预投递接收，则
该接收被传递给硬件。软件应对该列表进行影子维护，以协助处理 MPI cancel 操作。此外，由于硬件和
软件在标签匹配操作方面不期望紧密同步，此影子列表用于检测这样一种情况：预投递接收被传递给硬件，
而匹配的意外消息正从硬件传递给软件。
