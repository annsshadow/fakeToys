
## 交换像素缓冲

如最初设计的那样，Linux 图形子系统在进程、设备与子系统之间共享像素缓冲区分配方面的支持极为有限。现代系统需要这三类之间的广泛集成；本文档详述了应用程序与内核子系统应如何针对二维图像数据进行这种共享
本文是参考用GPU 与显示设备的 DRM 子系统、用于媒体设备的 V4L2，以及用于用户空间支持的 Vulkan、EGL Wayland 编写的，然而任何其它子系统也应遵循此设计与建议

## 术语

    image（图像）:
      概念上是一个二维像素数组。像素可存储在一个或多个内存缓冲区中。具有以像素为单位的宽度与高度、像素格式和修饰符（隐式或显式）
    row（行
      沿单一 y 轴值的跨度，例如从坐标 (0,100) (200,100)
    scanline（扫描线
      row 的同义词
    column（列
      沿单一 x 轴值的跨度，例如从坐标 (100,0) (100,100)
    memory buffer（内存缓冲区
      用于存储像素数据（的一部分）的一块内存。具有以字节为单位的跨距与大小，并在某些 API 中至少具有一个句柄。可包含一个或多个平面
    plane（平面）:
      图像部分或全部颜色与 alpha 通道值的二维数组
    pixel（像素）:
      一个图像元素。具有由一或多个颜色通道值（例如 R、G、B，或 Y、Cb、Cr）定义的单一颜色值。也可具有一alpha 值作为附加通道
    pixel data（像素数据）:
      表示像素或图像部分或全部颜色/alpha 通道值的字节或位。一个像素的数据可能根据格式与修饰符分散在多个平面或内存缓冲区中
    color value（颜色值）:
      一组表示颜色的数字。元组中的每个元素是一个颜色通道值
    color channel（颜色通道
      颜色模型中的一个维度。例如，RGB 模型具有 R、G、B 通道。Alpha 通道有时也被视为一个颜色通道
    pixel format（像素格式）:
      描述像素数据如何表示像素的颜色与 alpha 值
    modifier（修饰符
      描述像素数据在内存缓冲区中如何布局
    alpha:
      表示像素中颜色覆盖度的值。有时也用于半透明
    stride（跨距）:
      表示像素位置坐标与字节偏移值之间关系的值。通常用作垂直相邻平铺块起始处两个像素之间的字节偏移。对于线性布局，是垂直相邻两个像素之间的字节偏移。对于非线性格式，跨距必须以一致的方式计算，通常按布局为线性来计算
    pitch（步幅）:
      stride 的同义词

## 格式与修饰符

每个缓冲区必须有一个底层格式。该格式描述为每个像素提供的颜色值。尽管每个子系统都有自己的格式描述（例如 V4L2 fbdev），但应尽可能复`DRM_FORMAT_*` 记号，因为它们是用于交换的标准描述。这些记号在 `drm_fourcc.h` 文件中描述，该文件是 DRM uAPI 的一部分
每个 `DRM_FORMAT_*` 记号描述图像中像素坐标与该像素颜色值（包含在其内存缓冲区中）之间的转换。它描述了颜色通道的数量与类型：是 RGB 还是 YUV、整数还是浮点、每个通道的大小及其在像素内存中的位置，以及颜色平面之间的关系
例如，`DRM_FORMAT_ARGB8888` 描述一种格式，其中每个像素在内存中有一个单一32 位值。Alpha、红、绿、蓝颜色通道均以每通道 8 位精度提供，按从最高有效位到最低有效位的顺序在小端存储中排列。`DRM_FORMAT_*` 不受 CPU 或设备字节序影响；内存中的字节模式始终如格式定义所述，通常为小端
作为更复杂的例子，`DRM_FORMAT_NV12` 描述一种格式，其中亮度与色YUV 样本存储在独立的平面中，色度平面在两个维度上均以一半分辨率存储（即每个 2x2 像素分组存储一U/V 色度样本）
格式修饰符描述这些逐像素内存样本与实际缓冲区内存存储之间的转换机制。最直接的修饰符`DRM_FORMAT_MOD_LINEAR`，描述一种方案：每个平面按行顺序从左上角到右下角布局。这被视为基线交换格式，也最便于 CPU 访问
现代硬件采用复杂得多的访问机制，通常利用平铺访问，可能还利用压缩。例如，`DRM_FORMAT_MOD_VIVANTE_TILED` 修饰符描述一种内存存储：像素以行主序排列4x4 块中，即一个平面中的第一块存储像(0,0) (3,3)（含），第二块存储像(4,0) (7,3)（含）
某些修饰符可能修改图像所需的平面数量；例如，`I915_FORMAT_MOD_Y_TILED_CCS` 修饰符向 RGB 格式添加第二个平面，用于存储每个平铺块的状态数据，尤其是包括该平铺块是完全填充了像素数据，还是可以从单一纯色展开
这些扩展布局高度依赖于厂商，甚至具体到每个厂商设备的特定代次或配置。因此，如后文所述，所有用户必须显式枚举并协商对修饰符的支持，以确保兼容且最优的流水线

## 尺寸与大
每个像素缓冲区必须附带逻辑像素尺寸。这指的是可从底层内存存储中提取、或存储到其中的唯一样本数量。例如，即使一1920x1080 `DRM_FORMAT_NV12` 缓冲区具有一个包Y 分量 1920x1080 样本的亮度平面，以及 960x540 U V 分量样本，整个缓冲区仍被描述为具1920x1080 的尺寸
缓冲区的内存存储并不保证立即从底层内存的基地址开始，也不保证内存存储被紧密裁剪到任一维度
因此，每个平面必须以字节为单位的 `offset`（偏移量）来描述，在对任何逐像素计算之前将其加到内存存储的基地址上。这可用于将多个平面合并到单个内存缓冲区中；例如，`DRM_FORMAT_NV12` 可存储在单个内存缓冲区中，其中亮度平面的存储从缓冲区起始处开始、偏移量0，而色度平面的存储在同一个缓冲区中从该平面的字节偏移处开始
每个平面还必须具有以字节为单位的 `stride`（跨距），表示两个连续行之间的内存偏移。例如，一个尺寸为 1000x1000 `DRM_FORMAT_MOD_LINEAR` 缓冲区可能被分配得如同它1024x1000，以便允许对齐的访问模式。在这种情况下，缓冲区仍被描述为宽度 1000，但跨距将为 `1024 * bpp`，表明在 x 轴正极端24 个像素其值是不重要的
缓冲区也可能y 维度上进一步填充，只需分配比通常所需更大的区域。例如，许多媒体解码器无法原生输出高度为 1080 的缓冲区，而是需1088 像素的有效高度。在这种情况下，缓冲区继续被描述为高1080，而每个缓冲区的内存分配被增加以计入额外的填充

## 枚举

每个像素缓冲区的使用者都必须能够枚举一组一起描述的受支持格式与修饰符。在 KMS 中，这通过每个 DRM 平面上的 `IN_FORMATS` 属性实现，列出受支持的 DRM 格式，以及每种格式受支持的修饰符。在用户空间中，这通过 EGL `EGL_EXT_image_dma_buf_import_modifiers`_ 扩展入口点、Vulkan `VK_EXT_image_drm_format_modifier`_ 扩展，以Wayland `zwp_linux_dmabuf_v1`_ 扩展来支持
这些接口每一个都允许用户查询一组受支持的格修饰符组合

## 协商

由用户空间负责为其用途协商一个可接受的格修饰符组合。这通过对列表的简单求交集来完成。例如，如果用户想使Vulkan 渲染一幅图像以显示KMS 平面上，它必须：

 - 查询给定平面KMS `IN_FORMATS` 属 - 查询 Vulkan 对其物理设备支持的格式，确保
   传入与预期渲染用途相对应`VkImageUsageFlagBits` `VkImageCreateFlagBits`
 - 对这些格式求交集以确定最合适的一 - 对于该格式，KMS Vulkan 各自支持的修饰符列表求交集，以获得该格式一组最终可接受的修饰符

必须对所有用途执行此求交集。例如，如果用户还希望将该图像编码为视频流，它必须查询其打算用于编码的媒API 所支持的修饰符集合，并额外针对该列表求交集
如果所有列表的交集为空列表，则无法以这种方式共享缓冲区，必须考虑替代策略（例如使CPU 访问例程在不同用途之间复制数据，并承担相应的性能代价）
得到的修饰符列表是无序的；顺序无关紧要

## 分配

一旦用户空间确定了合适的格式以及相应的可接受修饰符列表，它就必须分配缓冲区。由于在用户空间层面或内核层面都没有通用的缓冲区分配接口，客户端任意选择一种分配接口，例如 Vulkan、GBM，或一个媒API
每个分配请求必须至少包含：像素格式、一组可接受修饰符，以及缓冲区的宽度与高度。每API 可能以不同方式扩展这组属性，例如允许在两个以上维度分配、预期的用途模式等
分配缓冲区的组件将在可接受列表中任意选择它认为“最佳”的修饰符、所需的任何填充，以及底层内存缓冲区的进一步属性，例如它们存储在系统内存还是设备专用内存中、是否物理连续、以及它们的缓存模式。这些内存缓冲区的属性对用户空间不可见，不过 `dma-heaps` API 正在努力解决这一点
分配之后，客户端必须查询分配器以确定为缓冲区选择的实际修饰符，以及逐平面的偏移量与跨距。分配器不允许更改所用格式、不允许选择可接受列表之外提供的修饰符，也不允许更改除通过偏移量、跨距和大小表达的填充之外的像素尺寸
传达额外的约束，例如跨距或偏移量的对齐、在特定内存区域中的放置等，超出dma-buf 的范围，也不是格式与修饰符记号所能解决的

## 导入

要在不同的上下文、设备或子系统中使用缓冲区，用户将这些参数（格式、修饰符、宽度、高度，以及逐平面的偏移量与跨距）传递给一个导API
每个内存缓冲区由一个缓冲区句柄引用，该句柄在图像内可能唯一也可能重复。例如，一`DRM_FORMAT_NV12` 缓冲区可通过使用逐平面偏移量参数将亮度与色度缓冲区合并到单个内存缓冲区中，或者它们在内存中可能是完全独立的分配。为此，每个导入与分API 必须为每个平面提供独立的句柄
每个内核子系统都有其自己的缓冲区管理类型与接口。DRM 使用 GEM 缓冲区对象（BO），V4L2 有其自己的引用，等等。这些类型在上下文、进程、设备或子系统之间不可移植
为了解决这个问题，使`dma-buf` 句柄作为缓冲区的通用交换。特定于子系统的操作用于将原生缓冲区句柄导出`dma-buf` 文件描述符，以及将这些文件描述符导入为原生缓冲区句柄。dma-buf 文件描述符可以在上下文、进程、设备与子系统之间传输
例如，一Wayland 媒体播放器可能使V4L2 将视频帧解码到一`DRM_FORMAT_NV12` 缓冲区。这将导致两个内存平面（亮度与色度）被用户从 V4L2 出队。这些平面随后每平面被导出到一dma-buf 文件描述符，这些描述符连同元数据（格式、修饰符、宽度、高度、逐平面偏移量与跨距）一起被发送给 Wayland 服务器。Wayland 服务器随后会将这些文件描述符导入为一EGLImage 以通过 EGL/OpenGL (ES) 使用、一VkImage 以通过 Vulkan 使用，或一KMS 帧缓冲对象；这些导入操作每一个都会采用相同的元数据，并将 dma-buf 文件描述符转换为它们的原生缓冲区句柄
拥有一组非空的可接受修饰符交集，并不保证导入会成功进入所有消费者；它们可能有超出修饰符所隐含的、必须满足的约束

## 隐式修饰
修饰符的概念晚于上述所有子系统出现。因此，它被 retrofit（回溯加入）到所有这API 中，并且为了确保向后兼容，需要支持尚不支持修饰符的驱动与用户空间
例如，GBM 用于分配EGL（用于渲染）KMS（用于显示）之间共享的缓冲区。它有两个用于分配缓冲区的入口点：`gbm_bo_create` 只接受格式、宽度、高度与一个用途记号，`gbm_bo_create_with_modifiers` 用一组修饰符扩展了它
在后一种情况下，分配如上所述，被提供一组实现可从中选择的（若无法在这些约束内分配则失败）可接受修饰符。在前一种不提供修饰符的情况下，GBM 实现必须自行选择它认为可能的“最佳”布局。这种选择完全是实现特定的：某些实现会在其内部使用 CPU 不可访问的平铺布局，如果实现通过某种启发式认为这是个好主意的话。确保这种选择恰当是实现的职责
为了支持这种由于不知晓修饰符而不知布局的情况，定义了一个特殊的 `DRM_FORMAT_MOD_INVALID` 记号。该伪修饰符声明布局未知，驱动应使用其自身的逻辑来确定底层布局可能是什么

  `DRM_FORMAT_MOD_INVALID` 是一个非零值。修饰符值零  `DRM_FORMAT_MOD_LINEAR`，它是对图像具有线性布局的显式保证。应小心注意  确保零作为默认值不与“无修饰符”或线性修饰符混淆。还需注意，在某些 API 中，
  无效修饰符值通过带外标志指定，例`DRM_IOCTL_MODE_ADDFB2`
此记号可能在四种情况下使用：
  - 在枚举期间，一个接口可能返`DRM_FORMAT_MOD_INVALID`，既可作为修饰符列表的唯一成员以声明不支持显式修饰符，也可作为更大列表的一部分以声明可使用隐式修饰  - 在分配期间，用户可能提供 `DRM_FORMAT_MOD_INVALID`，既可作为修饰符列表的唯一成员（等同于完全不提供修饰符列表）以声明不支持显式修饰符且不得使用，也可作为更大列表的一部分以声明使用隐式修饰符的分配是可接受的
  - 在分配后查询中，一个实现可能返    `DRM_FORMAT_MOD_INVALID` 作为所分配缓冲区的修饰符，以声明底层布局是实现定义的且显式修饰符描述不可用；按上述规则，这只有当用户已将 `DRM_FORMAT_MOD_INVALID` 作为可接受修饰符列表的一部分包含、或未提供列表时才可返回
  - 在导入缓冲区时，用户可能提供 `DRM_FORMAT_MOD_INVALID` 作为缓冲区修饰符（或不提供修饰符），以表明修饰符因某种原因未知；这只在该缓冲区并非用显式修饰符分配时才可接受

由此得出，对于任何单一缓冲区，由生产者与所有消费者构成的完整操作链必须要么完全隐式、要么完全显式。例如，如果用户希望分配一个在 GPU、显示与媒体之间使用的缓冲区，但媒体 API 不支持修饰符，那么用*绝不可以**用显式修饰符分配该缓冲区并尝试不带修饰符将其导入媒体 API，而要么使用隐式修饰符进行分配，要么为媒体使用单独分配缓冲区并在两个缓冲区之间复制
作为上述规则的一个例外，分配可以从隐式“升级”到显式修饰符。例如，如果缓冲区用
`gbm_bo_create`（不接受修饰符）分配，用户随后可以用
`gbm_bo_get_modifier` 查询修饰符，然后在返回有效修饰符时将其用作显式修饰符记号
当为不同用户之间的交换分配缓冲区且修饰符不可用时，强烈建议实现使`DRM_FORMAT_MOD_LINEAR` 进行分配，因为这是交换的通用基线。然而，这并不能保证对缓冲区内容的正确解释，因为隐式修饰符操作仍可能受驱动特定的启发式影响
任何新的用户——用户空间程序与协议、内核子系统等——若希望交换缓冲区，必须通过 dma-buf 文件描述符提供内存平面的互操作性、用 DRM 格式记号描述格式、用 DRM 格式修饰符描述内存中的布局、至少用宽度与高度描述尺寸，以及至少用每个内存平面的偏移量与跨距描述
