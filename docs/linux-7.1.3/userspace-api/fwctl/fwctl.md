
## fwctl 瀛愮郴缁。
:Author: Jason Gunthorpe

## 概述

现代设备包含大量的固件（FW），并且在许多情况下，本质上是软件定义的硬件。这种方法的演进在很大程度上是对摩尔定律的反应——如今流片（tape out）的成本极高，且芯片设计极其庞大。用灵活且紧密耦合FW/HW 组合来取代固定的硬件逻辑，是针对芯片重新流片风险的有效缓解手段。硬件设计中的问题可以在设备固件中得到弥补。对于那些向操作系统驱动（例NVMe）提供稳定且向后兼容接口的设备而言，这一点尤其明显
设备中的固件层已经增长到惊人的规模，设备经常集成处理器集群来运行它。例如，mlx5 设备拥有超过 30MB 的固件代码，大型配置下运行时由固件管理的状态超1GB
如此灵活的一层可用性的出现，在行业中创造了相当大的多样性：单块硅片现在是可配置的软件定义设备，并且可以根据需求以显著不同的方式运行。此外，我们经常看到特定站点希望以高度专门化的方式操作设备，并需要为它们独特的配置量身定制应用程序
此外，设备已经变得多功能并集成到不再适合内核子系统划分的程度。现代多功能设备具有诸如 bnxt/ice/mlx5/pds 之类的驱动，它们跨越许多子系统，同时使用辅助设备（auxiliary device）系统共享底层硬件
这一切共同给操作系统带来了挑战：设备拥有庞大的固件环境，需要强健的设备专属调试支持，以及不太适合“通用”接口的固件驱动功能。fwctl 旨在从用户空间在调试能力、管理以及首次启N 次启动的配置供给（provisioning）方面，提供对完整设备功能的访问
fwctl 面向一种常见的设备设计模式，即操作系统与固件通过以队列或邮箱（mailbox）方案构建的 RPC 消息层进行通信。在这种情况下，驱动通常会有一层来投RPC 消息并从设备固件收集 RPC 响应。为设备主要用途而运行的、内核内部的子系统驱动会使用这些 RPC 来构建它们的驱动，但设备通常还有一组并不真正适合任何特定子系统的辅助 RPC。例如，一个硬RAID 控制器主要由块层操作，但同时也附带一组用于管理硬RAID 内驱动器构建RPC
过去，当设备更加单一功能时，各个子系统会发展出不同的方法来解决其中一些共性问题。例如，监控设备健康、操作其 FLASH、调试固件、配置供给，在整个内核中都有着各种各样的独特接口
fwctl 的目的是定义一套下面描述的、有限的通用规则，允许用户在设备固件内安全地构造并执行 RPC。这些规则作为操作系统与固件之间关于如何正确设计 RPC 接口的约定。作为一uAPI，该子系统提供了一层精简的发现机制以及一个通用uAPI 来投RPC 并收集响应。它支持一套用户空间库和工具，这些库和工具将使用该接口通过设备原生协议来控制设备
### 作用范围（Scope of Action
fwctl 驱动被严格限制为操作设备固件的方式。它不是访问随机内核内部或其他操作系统软件状态的途径
fwctl 实例必须操作一个定义良好的设备功能（function），并且该设备应当对其功能被允许访问的物理设备内部范围有一个定义明确的安全模型。例如，当今最复杂PCIe 设备可能大致具有以下若干功能级范围：

 1. 一个拥有对设备上全局状态和配置完全访问权限的特权功
 2. 多个对自身及用于虚拟机的子功能进行控制的 hypervisor 功能

 3. 多个严格限定在虚拟机内部的虚拟机功能

设备可以在这些范围之间创建逻辑上的子关系。例如，子虚拟机的固件可能位hypervisor 固件的范围之内。在 VFIO 领域中，hypervisor 环境VFIO 分配给虚拟机的那个功能负有复杂的供给/画像/配置责任，这是相当常见的
此外，在功能内部，设备经常有属于某些通用作用范围RPC 命令（参`enum fwctl_rpc_scope`）：

 1. 对功能及子功能配置、FLASH 等的访问，这些配置在功能复位时生效。对功能及子功能运行时配置的访问，对任一驱动或虚拟机透明或无干扰
 2. 对功能及子功能调试信息的只读访问，这些信息可能报告功能及子功能中的固件对象，包括由其他内核子系统拥有的固件对象
 3. 对功能及子功能调试信息的写入访问，需严格兼容内核锁定（lockdown）和内核完整性保护原则。会触发内核污染（taint）
 4. 完整的调试设备访问。会触发内核污染，需CAP_SYS_RAWIO
用户空间将在每个 RPC 上提供一个作用范围标签，内核必须根据该范围强制实施上CAP 和污染。内核与固件的组合可以强制让 RPC 被用户空间放入正确的范围
### 禁止的行
该接口绝不允许用户空间做许多事情（在没有污染CAP 的情况下），这些事项广泛来源于内核锁定的原则。一些例子：

 1. 对任意内存进DMA、挂起系统、用不受信任的代码破坏固件完整性，或以其他方式危害设备或系统的安全与完整性
 2. 向内核驱动提供一个异常的“后门”。不得操纵由内核驱动拥有的内核对象
 3. 直接配置或以其他方式控制内核驱动。子系统内核驱动可以在功能复驱动加载时对设备配置作出反应，但除此之外不得fwctl 耦合
 4. 以与另一主要内核子系统的核心目的相重叠的方式操作硬件，例如对 LBA 的读/写、网络数据包的发接收，或操作加速器的数据平面
fwctl 不是 uacce VFIO 等设备直接访问子系统的替代品
通过 fwctl 非污染接口暴露的操作应当与设备的其他使用者完全可共享。例如，通过 fwctl 暴露一RPC 绝不应阻止某个内核子系统日后同时使用该相同的 RPC 或硬件单元。在这种情况下，fwctl 的重要性将低于最终出现的合适的内核子系统。该领域中导致冲突的错误将以有利于内核实现的方式解决
## fwctl 用户 API

### sysfs 绫。
fwctl 有一sysfs 类（/sys/class/fwctl/fwctlNN/）和字符设备dev/fwctl/fwctlNN），采用简单的编号方案。该字符设备操作上文描述ioctl uAPI
fwctl 设备可以通过

```
    $ ls /sys/class/fwctl/fwctl0/device/infiniband/
    ibp0s10f0

    $ ls /sys/class/infiniband/ibp0s10f0/device/fwctl/
    fwctl0/

    $ ls /sys/devices/pci0000:00/0000:00:0a.0/fwctl/fwctl0
    dev  device  power  subsystem  uevent

```
与其他子系统中的驱动组件相关联
### 用户空间社区

借鉴 nvme-cli 的经验，参与内核一侧必须同时带有一个位于公TBD git 树中的用户空间，至少要有用地操作内核驱动。提供这样的实现是合并一个内核驱动的前提条件
目标是在我们共同面临的一些共享问题上围绕用户空间建立社区，并理想地开发一些共同的用户空间程序，起始主题包括：

 - 设备现场调试

 - 硬件配置供给

 - 虚拟机启动前VFIO 子设备画
 - 机密计算主题（证明、安全配置供给）

这些主题贯穿内核的所有子系统。fwupd 就是一个很好的例子，展示了优秀的用户空间体验如何从内核侧的多样性中诞生

### fwctl 驱动设计

在许多情况下，fwctl 驱动将成为某个更大的跨子系统设备的一部分，可能使`auxiliary_device` 机制。在这种情况下，若干子系统将共享相同的设备和固件接口层，因此设备设计本身必须已经为内核子系统之间的隔离与合作提供支持。fwctl 应当契合相同的模型
驱动的一部分应当包括对其作用范围限制和安全模型如何运作的描述。驱动和固件必须共同确保用户空间提供RPC 被映射到适当的作用范围。如果验证在驱动中完成，那么验证可以读取设备提供的“命令效果（command effects）”报告，或者硬编码强制实施。如果验证在固件中完成，那么驱动应将 `fwctl_rpc_scope` 连同命令一起传递给固件
驱动和固件必须配合，以确fwctl 要么无法分配任何固件资源，要么其分配的任何资源在文件描述符关闭时被释放。一个主要围绕固RPC 构建的驱动可能会发现其核PCI 功能RPC 层属fwctl，而辅助设备则连接到其他子系统
每种设备类型都必须留Linux 对稳ABI 的理念。固RPC 接口不必满足严格稳定ABI，但它需要满足这样的期望：已部署且被广泛使用的用户空间工具不会被无谓地破坏。固件升级和内核升级应当让被广泛部署的工具继续工作
面向开发和调试、处于更宽松作用范围RPC，如果仅在这些例外情况下运行而非设备日常使用时，可以具有较低的稳定性。调试工具甚至可能要求精确的版本匹配，因为它们可能需要类似来自固件二进制DWARF 调试信息
## 安全响应

内核仍然是该接口的守门人。如果发现违反作用范围、安全或隔离原则的情况，我们有若干选择：让设备通过固件更新来修复它们、推送内核补丁以解析并阻RPC 命令，或推送内核补丁以阻止整个固件版本/设备
虽然内核始终可以直接解析并限RPC，但期望现有的、允许驱动将验证委托给固件的内核模式成为一种有用的设计
## 已有的类似示
本文档中描述的方法并非新想法。几十年来，内核在不同领域都提供过直接或近乎直接的设备访问。随着更多设备希望遵循这种设计模式，越来越清楚的是它并未被完全理解，更重要的是，其安全考量尚未被很好地定义或达成一致
一些例子：

 - 硬件 RAID 控制器。这包括用于诸如将驱动器组合RAID 卷、配RAID 参数、监控硬件等操作RPC
 - 基板管理控制器（Baseboard manager）。用于配置设备内设置等操作的 RPC
 - NVMe 厂商命令封装（vendor command capsule）。nvme-cli 提供了对某些不同产品已定义的监控功能的访问，但还有更多
 - CXL 也有一个类NVMe 的厂商命令系统
 - DRM 允许用户空间驱动通过内核中介向设备发送命令
 - RDMA 允许用户空间驱动不经由内核、直接将命令推送到设备
 - 各种“原始（raw）API，如 raw HID（SDL2）、raw USB、NVMe Generic Interface 等
4 个是 fwctl 旨在覆盖的领域示例。后 3 个是不被允许的行为的示例，因为它们与某个内核子系统的主要目的完全重叠
从过去这些努力中学到的一些关键经验是：拥有一个共同的用户空间项目作为获取内核驱动的前提条件的重要性。在用户空间围绕有用的软件建立良好的社区，是让公司资助参与以使其产品可用化的关键
