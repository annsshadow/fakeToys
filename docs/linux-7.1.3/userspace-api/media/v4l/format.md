


######## 数据格式


## 数据格式协商


不同的设备与应用程序交换不同种类的数据，例如视频图像、原始或切片 VBI 数据、RDS 数据报。即便在同一类数据中也可能存在多种不同格式，尤其是图像格式种类繁多。尽管驱动必须提供默认值，且该选择在关闭并重新打开设备后仍然保持，但应用程序在参与数据交换之前应始终协商一个数据格式。协商意味着应用程序请求某个特定格式，驱动选择并报告硬件为满足该请求所能做到的最佳结果。当然，应用程序也可以仅仅查询当前的选择。

存在一种统一的机制，使用聚合 struct `v4l2_format` 和 VIDIOC_G_FMT <VIDIOC_G_FMT> 与 VIDIOC_S_FMT <VIDIOC_G_FMT> ioctl 来协商所有数据格式。此外，VIDIOC_TRY_FMT <VIDIOC_G_FMT> ioctl 可用于在不实际选择新数据格式的情况下，查看硬件**能够**做什么。V4L2 API 支持的数据格式在 devices 中相应设备章节介绍。关于图像格式的更深入了解，请参见 pixfmt。

VIDIOC_S_FMT <VIDIOC_G_FMT> ioctl 是初始化序列中的一个主要转折点。在此之前的多个面板（panel）应用程序可以并发访问同一设备，以选择当前输入、更改控制或修改其他属性。第一次 VIDIOC_S_FMT <VIDIOC_G_FMT> 将一个逻辑流（视频数据、VBI 数据等）专门分配给一个文件描述符。

“独占”意味着没有其他应用程序，更准确地说没有其他文件描述符，可以抓取该流或更改与协商参数不一致的设备属性。例如，当新的视频标准使用不同数量的扫描行时，可能会使所选图像格式失效。因此，只有拥有该流的文件描述符才能进行使其失效的更改。相应地，抓取了不同逻辑流的多个文件描述符彼此阻止干扰对方的设置。例如，当视频叠加（overlay）即将开始或已在进行时，同时进行的视频捕获可能被限制为相同的裁剪和图像尺寸。

当应用程序省略 VIDIOC_S_FMT <VIDIOC_G_FMT> ioctl 时，其锁定副作用由下一步隐含——通过 VIDIOC_REQBUFS ioctl 选择 I/O 方法，或在第一次 `read()` 或 `write()` 调用时隐式产生。

通常一个文件描述符只能分配一个逻辑流，例外情况是驱动为兼容 V4L 及更早版本 V4L2 而允许使用同一文件描述符同时捕获和叠加视频。通过关闭并重新打开设备可以切换逻辑流或返回“面板模式”。驱动**可能**支持使用 VIDIOC_S_FMT <VIDIOC_G_FMT> 切换。

所有与应用程序交换数据的驱动都必须支持 VIDIOC_G_FMT <VIDIOC_G_FMT> 和 VIDIOC_S_FMT <VIDIOC_G_FMT> ioctl。强烈建议但可选地实现 VIDIOC_TRY_FMT <VIDIOC_G_FMT>。

## 图像格式枚举


除了通用的格式协商函数外，还提供了一个特殊的 ioctl，用于枚举视频捕获、叠加或输出设备支持的所有图像格式。[#f1]_

VIDIOC_ENUM_FMT ioctl 必须由所有与应用程序交换图像数据的驱动支持。


    驱动不应在内核空间转换图像格式。
    它们只能枚举硬件直接支持的格式。
    如有必要，驱动作者应发布一个示例转换例程或库，以便集成到应用程序中。

   枚举应用程序事先并不知晓的格式（否则它本可显式请求而无需枚举）似乎无用，但有些充当驱动与实际视频应用之间代理的程序会发现这很有用。
