
######## 内存到内存无状态（stateless）视频解码器接口

无状态解码器是一种在处理过的帧之间不保留任何状态的解码器。这意味着每一帧都
独立于任何之前和之后的帧进行解码，并且客户端（client）负责维护解码状态，并
在每次解码请求时把它提供给解码器。这与有状态（stateful）视频解码器接口形成
对比，在有状态接口中，硬件和驱动维护解码状态，客户端所要做的只是提供原始的
编码流、并以显示顺序把解码后的帧出队。

本节描述用户空间（"客户端"）应当如何与无状态解码器通信，以成功地解码一个
编码流。与有状态编解码器相比，解码器/客户端的交互序列更简单，但这种简单性的
代价是客户端要承担额外的复杂性——它负责维护一致的解码状态。

无状态解码器使用了 media-request-api。当一个无状态解码器被调用
`VIDIOC_REQBUFS` 或 `VIDIOC_CREATE_BUFS` 时，它必须在其 `OUTPUT` 队列上
暴露 `V4L2_BUF_CAP_SUPPORTS_REQUESTS` 能力。

根据解码器所支持的编码格式，单个解码帧可能是多个解码请求的结果（例如，每帧
有多个 slice 的 H.264 流）。支持这类格式的解码器还必须在它们的 `OUTPUT` 队列
上暴露 `V4L2_BUF_CAP_SUPPORTS_M2M_HOLD_CAPTURE_BUF` 能力。

## 查询能力

1. 为了枚举解码器所支持的编码格式集合，客户端在 `OUTPUT` 队列上调用
   `VIDIOC_ENUM_FMT`。

   - 驱动必须始终返回完整的受支持 `OUTPUT` 格式集合，而不管当前在 `CAPTURE`
     队列上设置的格式是什么。

   - 同时，驱动必须把由编解码器特有的能力控制（例如 H.264 profile）所返回的
     值集合，限制为硬件实际支持的范围。

2. 为了枚举受支持的原始（raw）格式集合，客户端在 `CAPTURE` 队列上调用
   `VIDIOC_ENUM_FMT`。

   - 驱动必须只返回当前在 `OUTPUT` 队列上处于活动状态的格式所支持的格式。

   - 根据当前设置的 `OUTPUT` 格式，受支持的原始格式集合可能取决于某些
     与编解码器相关的控制的值。客户端负责确保在查询 `CAPTURE` 队列之前这些
     控制已被设置。如果未能这样做，将导致使用这些控制的默认值，并返回一组
     可能对客户端试图解码的媒体不可用的格式。

3. 客户端可以使用 `VIDIOC_ENUM_FRAMESIZES` 来检测给定格式所支持的分辨率，
   把期望的像素格式传入 `v4l2_frmsizeenum` 的 `pixel_format` 字段。

4. 当前 `OUTPUT` 格式所支持的 profile 和 level（如果适用），可以通过它们各自的
   控制使用 `VIDIOC_QUERYCTRL` 来查询。

## 初始化

1. 通过 `VIDIOC_S_FMT` 在 `OUTPUT` 队列上设置编码格式。

   - **必填字段：**

     `type`
         一个适用于 `OUTPUT` 的 `V4L2_BUF_TYPE_*` 枚举。

     `pixelformat`
         一个编码的像素格式。

     `width`, `height`
         从流中解析出来的编码宽度和高度。

     other fields
         遵循标准语义。

```
     更改 ``OUTPUT`` 格式可能会改变当前设置的 ``CAPTURE`` 格式。驱动将根据
     正在设置的 ``OUTPUT`` 格式推导出一个新的 ``CAPTURE`` 格式，包括分辨率、
     色度参数等。如果客户端需要特定的 ``CAPTURE`` 格式，它必须在这之后进行
     调整。

```
2. 调用 `VIDIOC_S_EXT_CTRLS` 来设置 `OUTPUT` 格式为了枚举 `CAPTURE` 格式
   所需的所有控制（解析出的头部等）。

3. 对 `CAPTURE` 队列调用 `VIDIOC_G_FMT`，以获取从字节流中解析/解码出来的
   目标缓冲区的格式。

   - **必填字段：**

     `type`
         一个适用于 `CAPTURE` 的 `V4L2_BUF_TYPE_*` 枚举。

   - **返回字段：**

     `width`, `height`
         解码帧的帧缓冲区分辨率。

     `pixelformat`
         解码帧的像素格式。

     `num_planes`（仅适用于 _MPLANE `type`）
         像素格式的平面数。

     `sizeimage`, `bytesperline`
         遵循标准语义；与帧缓冲区格式匹配。

```
     ``pixelformat`` 的值可以是基于硬件能力、为该 ``OUTPUT`` 格式所支持的任意
     像素格式。建议驱动为当前配置选择偏好/最优的格式。例如，如果 RGB 需要额外
     的转换步骤，则 YUV 格式可能比 RGB 格式更受偏好。

```
4. **[可选]** 通过 `VIDIOC_ENUM_FMT` 在 `CAPTURE` 队列上枚举 `CAPTURE` 格式。
   客户端可以使用这个 ioctl 来发现当前 `OUTPUT` 格式支持哪些替代的原始格式，
   并通过 `VIDIOC_S_FMT` 选择其中之一。

```
     驱动将只返回当前所选 ``OUTPUT`` 格式和当前所设置的控制所支持的格式，即使
     解码器总体上可能支持更多格式。

     例如，一个解码器可能在 1920x1088 及更低分辨率下支持 YUV 和 RGB 格式，
     但在更高分辨率下只支持 YUV（由于硬件限制）。在把 1920x1088 或更低的分辨率
     设置为 ``OUTPUT`` 格式之后，:c:func:`VIDIOC_ENUM_FMT` 可能返回一组 YUV 和
     RGB 像素格式；但在设置了高于 1920x1088 的分辨率之后，驱动将不再返回 RGB
     像素格式，因为它们在该分辨率下不受支持。

```
5. **[可选]** 通过 `VIDIOC_S_FMT` 在 `CAPTURE` 队列上选择不同于建议的
   `CAPTURE` 格式。客户端可以选择一个不同于驱动在 `VIDIOC_G_FMT` 中所选择/
   建议的格式。

    - **必填字段：**

      `type`
          一个适用于 `CAPTURE` 的 `V4L2_BUF_TYPE_*` 枚举。

      `pixelformat`
          一个原始像素格式。

      `width`, `height`
         解码流的帧缓冲区分辨率；通常与 `VIDIOC_G_FMT` 返回的值相同，但如果
         硬件支持合成（composition）和/或缩放（scaling），则可能会不同。

   在执行这一步之后，客户端必须再次执行第 3 步，以获得关于缓冲区大小和布局的
   最新信息。

6. 通过 `VIDIOC_REQBUFS` 在 `OUTPUT` 队列上分配源（字节流）缓冲区。

    - **必填字段：**

      `count`
          请求分配的缓冲区数量；大于零。

      `type`
          一个适用于 `OUTPUT` 的 `V4L2_BUF_TYPE_*` 枚举。

      `memory`
          遵循标准语义。

    - **返回字段：**

      `count`
          实际分配的缓冲区数量。

    - 如果需要，驱动会调整 `count`，使其等于或大于给定格式所需 `OUTPUT` 缓冲区
      数量的最小值与请求数量。客户端必须在 ioctl 返回后检查这个值，以获得实际
      分配的缓冲区数量。

7. 通过 `VIDIOC_REQBUFS` 在 `CAPTURE` 队列上分配目标（原始格式）缓冲区。

    - **必填字段：**

      `count`
          请求分配的缓冲区数量；大于零。客户端负责推算出为了正确解码流所需的
          最小缓冲区数量（例如考虑参考帧），并传入一个相等或更大的数字。

      `type`
          一个适用于 `CAPTURE` 的 `V4L2_BUF_TYPE_*` 枚举。

      `memory`
          遵循标准语义。`CAPTURE` 缓冲区不支持 `V4L2_MEMORY_USERPTR`。

    - **返回字段：**

      `count`
          调整为已分配的缓冲区数量，以防编解码器需要比请求更多的缓冲区。

    - 驱动必须把 count 调整为当前格式、流配置和请求数量所需的 `CAPTURE` 缓冲区
      最小数量。客户端必须在 ioctl 返回后检查这个值，以获得分配的缓冲区数量。

8. 通过 `MEDIA_IOC_REQUEST_ALLOC` 在媒体设备上分配请求（很可能每个 `OUTPUT`
   缓冲区一个）。

9. 通过 `VIDIOC_STREAMON` 在 `OUTPUT` 和 `CAPTURE` 两个队列上启动流。

## 解码

对于每一帧，客户端负责提交至少一个请求，并向其附加以下内容：

- 编解码器以其当前配置所期望的编码数据量，作为一个提交到 `OUTPUT` 队列的
  缓冲区。通常，这对应于一帧的编码数据量，但某些格式可能允许（或要求）每单位
  不同的数据量。
- 解码所提交的编码数据所需的全部元数据，形式为与被解码格式相关的控制。

源 `OUTPUT` 缓冲区的数据量和内容，以及必须在请求上设置的控制，取决于当前活动
的编码像素格式，并可能受到编解码器特有的扩展控制的影响，如各格式的文档所述。

如果解码帧有可能需要在当前请求之后再有一个或多个解码请求才能产生，那么客户端
必须在 `OUTPUT` 缓冲区上设置 `V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF` 标志。这将
导致（可能部分解码的）`CAPTURE` 缓冲区不被提供出队，并在下一个 `OUTPUT` 缓冲区
的时间戳没有改变时被重用于下一个解码请求。

因此，一个典型的帧将使用以下序列来解码：

1. 使用 `VIDIOC_QBUF` 把一个 `OUTPUT` 缓冲区入队，该缓冲区包含用于解码请求的
   一个单位的编码字节流数据。

    - **必填字段：**

      `index`
          被入队的缓冲区的索引。

      `type`
          缓冲区的类型。

      `bytesused`
          缓冲区中编码数据帧所占用的字节数。

      `flags`
          必须设置 `V4L2_BUF_FLAG_REQUEST_FD` 标志。此外，如果我们不确定当前
          解码请求是否是产生一个完全解码帧所需的最后一个请求，那么还必须
          设置 `V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF`。

      `request_fd`
          必须设置为解码请求的文件描述符。

      `timestamp`
          必须设置为每帧唯一的值。这个值将被传播到解码帧的缓冲区中，也可以
          用来让这一帧作为另一帧的参考帧。如果一帧使用多个解码请求，那么给定
          帧的所有 `OUTPUT` 缓冲区的时间戳必须相同。如果时间戳改变，那么当前
          持有的 `CAPTURE` 缓冲区将被提供出队，而当前请求将作用于一个新的
          `CAPTURE` 缓冲区。

2. 使用 `VIDIOC_S_EXT_CTRLS` 为解码请求设置编解码器特有的控制。

    - **必填字段：**

      `which`
          必须为 `V4L2_CTRL_WHICH_REQUEST_VAL`。

      `request_fd`
          必须设置为解码请求的文件描述符。

      other fields
          其它字段的设置与设置控制时通常的做法一样。`controls` 数组必须包含
          解码一帧所需的所有编解码器特有控制。

```
     可以在 :c:func:`VIDIOC_S_EXT_CTRLS` 的不同调用中指定控制，或者覆盖之前
     设置的控制，只要 ``request_fd`` 和 ``which`` 被正确地设置。在请求提交
     那一刻的控制状态，将是被采纳的状态。

   .. note::

      第 1 步和第 2 步发生的顺序是可互换的。

```
3. 通过在请求 FD 上调用 `MEDIA_REQUEST_IOC_QUEUE` 来提交请求。

   如果请求在没有 `OUTPUT` 缓冲区的情况下被提交，或者如果请求中缺少某些所需的
   控制，那么 `MEDIA_REQUEST_IOC_QUEUE` 将返回 `-ENOENT`。如果入队了多于一个
   的 `OUTPUT` 缓冲区，那么它将返回 `-EINVAL`。`MEDIA_REQUEST_IOC_QUEUE` 返回
   非零意味着这个请求不会产生任何 `CAPTURE` 缓冲区。

`CAPTURE` 缓冲区不能是请求的一部分，而是被独立地入队。它们以解码顺序返回
（即与提交到 `OUTPUT` 队列的编码帧相同的顺序）。

运行时的解码错误由出队的、携带 `V4L2_BUF_FLAG_ERROR` 标志的 `CAPTURE` 缓冲区
来发出信号。如果一个已解码的参考帧有错误，那么所有引用它的后续已解码帧也会
设置 `V4L2_BUF_FLAG_ERROR` 标志，尽管解码器仍会尝试产生（很可能是损坏的）帧。

## 解码期间的缓冲区管理

与有状态解码器相反，无状态解码器不执行任何类型的缓冲区管理：它只保证出队的
`CAPTURE` 缓冲区在它们被再次入队之前都可以被客户端使用。"使用"在这里涵盖把
缓冲区用于合成或显示。

一个出队的捕获缓冲区也可以用作另一个缓冲区的参考帧。

一个帧通过把它的时间戳转换为纳秒，并存储到与编解码器相关的控制结构的相应成员
中，来被指定为参考帧。必须使用 `v4l2_timeval_to_ns` 函数来执行该转换。只要一帧
的所有编码数据单位都已被成功提交到 `OUTPUT` 队列，该帧的时间戳就可以被用来
引用它。

包含参考帧的已解码缓冲区，在所有引用它的帧都被解码之前，不能被重用作解码目标。
实现这一点最安全的方法是：在所有引用它的已解码帧都被出队之前，避免把参考缓冲
区入队。然而，如果驱动能保证入队到 `CAPTURE` 队列的缓冲区是按入队顺序处理的，
那么用户空间就可以利用这一保证，并在满足以下条件时把一个参考缓冲区入队：

1. 受该参考帧影响的所有帧的请求都已被入队，并且

2. 足以覆盖所有已解码引用帧的 `CAPTURE` 缓冲区数量已被入队。

当入队一个解码请求时，驱动会增加与参考帧相关的所有资源的引用计数。这意味着
客户端可以例如：如果之后不再需要它们，就关闭参考帧缓冲区的 DMABUF 文件描述符。

## 跳转（Seeking）

为了跳转，客户端只需要使用对应于新流位置的输入缓冲区来提交请求。但它必须注意
分辨率可能已经改变，并在这种情况下遵循动态分辨率变更序列。此外，取决于所使用的
编解码器，图像参数（例如 H.264 的 SPS/PPS）可能已改变，客户端有责任确保向
解码器发送一个有效的状态。

然后客户端可以自由地忽略任何来自跳转前位置的、返回的 `CAPTURE` 缓冲区。

## 暂停（Pausing）

为了暂停，客户端可以简单地停止把缓冲区入队到 `OUTPUT` 队列。没有源字节流
数据，就没有数据要处理，编解码器将保持空闲。

## 动态分辨率变更

如果客户端检测到流中的分辨率变更，它将需要使用新的分辨率再次执行初始化序列：

1. 如果最后一个提交的请求由于使用了 `V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF`
   标志而导致一个 `CAPTURE` 缓冲区被持有，那么最后一帧在 `CAPTURE` 队列上
   不可用。在这种情况下，应当发送一个 `V4L2_DEC_CMD_FLUSH` 命令。这将使驱动
   把持有的 `CAPTURE` 缓冲区出队。

2. 等待所有已提交的请求完成，并把相应的输出缓冲区出队。

3. 在 `OUTPUT` 和 `CAPTURE` 两个队列上调用 `VIDIOC_STREAMOFF`。

4. 通过在 `CAPTURE` 队列上以缓冲区计数为零调用 `VIDIOC_REQBUFS` 来释放所有
   `CAPTURE` 缓冲区。

5. 再次执行初始化序列（减去 `OUTPUT` 缓冲区的分配），在新的分辨率被设置到
   `OUTPUT` 队列上。注意，由于分辨率限制，`CAPTURE` 队列上可能需要选择不同的
   格式。

## 排空（Drain）

如果最后一个提交的请求由于使用了 `V4L2_BUF_FLAG_M2M_HOLD_CAPTURE_BUF` 标志
而导致一个 `CAPTURE` 缓冲区被持有，那么最后一帧在 `CAPTURE` 队列上不可用。在
这种情况下，应当发送一个 `V4L2_DEC_CMD_FLUSH` 命令。这将使驱动把持有的
`CAPTURE` 缓冲区出队。

在此之后，为了在无状态解码器上排空流，客户端只需要等待所有已提交的请求完成。
