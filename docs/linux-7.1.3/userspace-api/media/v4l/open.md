######## 设备的打开与关闭


## 通过 V4L2 控制硬件外设


使用 V4L2 uAPI 支持的硬件通常由多个设备或外设组成，每个都有各自的驱动。

桥接驱动（bridge driver）会暴露一个或多个 V4L2 设备节点（参见 v4l2_device_naming）。

还有其他驱动为硬件的其他组成部分提供支持，这些驱动也可能暴露名为 V4L2 子设备（V4L2 sub-devices）的设备节点。

当暴露这类 V4L2 子设备时，它们允许控制那些其他硬件组成部分 —— 通常是通过串行总线（如 I²C、SMBus 或 SPI）连接的。根据桥接驱动的不同，那些子设备可以经由桥接驱动间接控制，也可以通过媒体控制器 <media_controller> 和 V4L2 子设备 <subdev> 显式控制。

需要使用媒体控制器 <media_controller> 的设备称为 **MC-centric**（以媒体控制器为中心）设备。完全通过 V4L2 设备节点控制的设备称为 **video-node-centric**（以视频节点为中心）设备。

用户态可以通过调用 VIDIOC_QUERYCAP 并检查 device_caps 字段 <device-capabilities> 来判断一个 V4L2 硬件外设是否为 MC-centric。

如果设备在 `device_caps` 中返回 `V4L2_CAP_IO_MC` 标志，则它是 MC-centric 的，否则就是 video-node-centric 的。

MC-centric 驱动在使用外设之前，必须通过媒体控制器 API <media_controller> 识别 V4L2 子设备并配置流水线。此外，子设备的配置应通过子设备 API <subdev> 来控制。


   video-node-centric 设备也可能同时提供媒体控制器和子设备接口。

  不过，在这种情况下，媒体控制器和子设备接口是只读的，只是提供有关设备的信息。实际的配置是通过视频节点完成的。


## V4L2 设备节点命名


V4L2 驱动以内核模块的形式实现，由系统管理员手动加载，或在设备首次被发现时自动加载。驱动模块会插入到 `videodev` 内核模块中。它提供本文档中规定的辅助函数以及通用的应用程序接口。

每个如此加载的驱动都会注册一个或多个主设备号为 81 的设备节点。次设备号是动态分配的，除非内核编译时启用了内核选项 CONFIG_VIDEO_FIXED_MINOR_RANGES。在那种情况下，次设备号会根据设备节点类型在各自范围内分配。

Video4Linux 子系统支持的设备节点如下：

======================== ====================================================
默认设备节点名称        用途
======================== ====================================================
`/dev/videoX`		 捕获/输出设备的视频与元数据
`/dev/vbiX`		 垂直消隐数据（如字幕、图文电视）
`/dev/radioX`		 无线电调谐器与调制器
`/dev/swradioX`		 软件定义无线电调谐器与调制器
`/dev/v4l-touchX`	 触摸传感器
`/dev/v4l-subdevX`	 视频子设备（由传感器及硬件外设的
			 其他组成部分使用）\ [#]_
======================== ====================================================

其中 `X` 是一个非负整数。


   1. 实际的设备节点名称取决于系统，因为 udev 规则可能会生效。
   2. 不能保证同一个设备的 `X` 会保持不变，因为该数字取决于设备驱动的探测顺序。
      如果你需要一个唯一的名称，udev 默认规则会生成 `/dev/v4l/by-id/` 和
      `/dev/v4l/by-path/` 目录，其中包含


```
	$ tree /dev/v4l
	/dev/v4l
	├── by-id
	│   └── usb-OmniVision._USB_Camera-B4.04.27.1-video-index0 -> ../../video0
	└── by-path
	    └── pci-0000:00:14.0-usb-0:2:1.0-video-index0 -> ../../video0
```

       一组系统调用，详见 subdev。

许多驱动支持 "video_nr"、"radio_nr" 或 "vbi_nr" 模块选项，用于选择特定的 video/radio/vbi 节点编号。这允许用户请求将设备节点命名为例如 /dev/video5，而不是听天由命。当驱动支持同类型的多个设备时，可以分配多个设备节点编号，以逗号分隔：


   # modprobe mydriver video_nr=0,1 radio_nr=0,1

在 `/etc/modules.conf` 中可写为：


```
    options mydriver video_nr=0,1 radio_nr=0,1
```

当没有作为模块选项给出设备节点编号时，驱动会提供一个默认值。

通常 udev 会为你自动在 /dev 中创建设备节点。如果未安装 udev，那么你需要启用 CONFIG_VIDEO_FIXED_MINOR_RANGES 内核选项，以便能够正确地将次设备号与设备节点编号对应起来。也就是说，你需要确信次设备号 5 映射到设备节点名称 video5。启用该内核选项后，不同的设备类型具有不同的次设备号范围。这些范围列于 devices。

创建字符特殊文件（使用 mknod）是一项特权操作，并且设备不能通过主、次设备号来打开。这意味着应用程序不能 **可靠地** 扫描已加载或已安装的驱动。用户必须输入一个设备名称，或者应用程序可以尝试使用常规的设备名称。


## 相关设备


设备可以支持多种功能。例如视频捕获、VBI 捕获和无线电支持。

V4L2 API 为这些功能中的每一个创建不同的 V4L2 设备节点。

V4L2 API 的设计理念是一个设备节点可以支持所有功能。然而在实践中这从未奏效：这个“特性”从未被应用程序使用过，许多驱动也不支持它，即便支持也肯定从未被测试过。此外，在不同功能之间切换设备节点仅在使用了流式 I/O API 时有效，而不能与 `read()`/\ `write()` API 一起使用。

如今每个 V4L2 设备节点只支持一种功能。

除了视频输入或输出，硬件也可能支持音频采样或播放。如果是这样，这些功能以 ALSA PCM 设备的形式实现，并带有可选的 ALSA 音频混音器设备。

所有这些设备存在一个问题：V4L2 API 没有提供查找这些相关 V4L2 设备节点的方法。一些真正复杂的硬件使用媒体控制器（参见 media_controller）来实现此目的。但有几个驱动没有使用它，而且虽然存在一些使用 sysfs 来发现相关 V4L2 设备节点的代码（参见 `v4l-utils <http://git.linuxtv.org/cgit.cgi/v4l-utils.git/>`__ git 仓库中的 libmedia_dev），但目前还没有一个库能够提供统一的 API 来同时涵盖基于媒体控制器的设备和不使用媒体控制器的设备。如果你愿意为此出力，请写信到 linux-media 邮件列表：`https://linuxtv.org/lists.php <https://linuxtv.org/lists.php>`__。

## 多次打开


V4L2 设备可以被打开多次。[#f1]_ 当驱动支持此特性时，用户可以例如启动一个“面板”应用程序来更改亮度或音量等控制项，而另一个应用程序同时捕获视频和音频。换句话说，面板应用程序类似于一个 ALSA 音频混音器应用程序。仅仅打开一个 V4L2 设备不应改变设备的状态。[#f2]_

一旦某个应用程序分配了流式传输数据所需的内存缓冲区（通过调用 VIDIOC_REQBUFS 或 VIDIOC_CREATE_BUFS ioctl，或者隐式地通过调用 `read()` 或 `write()` 函数），该应用程序（文件句柄）就成为设备的所有者。不再允许做出会影响缓冲区大小的改变（例如通过调用 VIDIOC_S_FMT <VIDIOC_G_FMT> ioctl），其他应用程序也不再被允许分配缓冲区或启动、停止流传输。相反会返回 EBUSY 错误码。

仅仅打开一个 V4L2 设备并不授予独占访问权。[#f3]_ 然而，发起数据交换会将读取或写入所请求类型数据以及更改相关属性的权利分配给该文件描述符。应用程序可以使用 app-pri 中描述的优先级机制来请求额外的访问权限。

## 共享数据流


V4L2 驱动不应通过复制缓冲区、时分复用或类似手段来支持多个应用程序读取或写入同一设备上的同一数据流。这最好由用户态的代理应用程序来处理。

## 函数


要打开和关闭 V4L2 设备，应用程序分别使用 `open()` 和 `close()` 函数。设备则使用 ioctl() <func-ioctl> 函数进行编程，如后续各节所述。

   仍有一些老旧且小众的驱动尚未更新以允许多次打开。这意味着对于这类驱动，`open()` 在设备已被使用时可能返回 `EBUSY` 错误码。

   遗憾的是，在许多驱动中，打开一个无线电设备往往会将设备的状态切换到无线电模式。这种行为最终应当被修正，因为它违反了 V4L2 规范。

   驱动可以识别 `O_EXCL` 打开标志。目前这并非必需，因此应用程序无法知道它是否真的生效。
