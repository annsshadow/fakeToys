


######## 视频叠加接口


**亦称帧缓冲叠加（Framebuffer Overlay）或预览（Previewing）*

视频叠加设备能够将（TV-）视频与显卡的（VGA-）视频信号进行同步锁相（genlock），或者将捕获的图像直接存入显卡的视频内存中（通常带裁剪）。这比捕获图像再用其他方式显示要高效得多。在过去只有核电站才需要冷却塔的年代，这是把实时视频放入窗口的唯一方式
视频叠加设备通过和视频捕<capture> 设备相同的字符特殊文件来访问

   `/dev/video` 设备的默认功能是视频捕获。叠加功能只有在调用
   VIDIOC_S_FMT <VIDIOC_G_FMT> ioctl 之后才可用
驱动可能支持使用 read/write 与流 I/O 方法同时进行叠加和捕获。如果支持，则视频标准标称帧率下的运行无法保证。帧可能被从叠加转向捕获，或者在捕获参数允许的情况下，一个场用于叠加而另一个场用于捕获
应用程序应当为捕获和叠加使用不同的文件描述符。所有支持同时捕获和叠加的驱动都必须支持这一点。这些驱动也可以选择允许使用单个文件描述符进行捕获和叠加，以兼容 V4L 以及更早版本V4L2。[#f1]_

两个文件描述符的一个常见应用是 X11 Xv/V4L <xvideo> 接口驱动与一V4L2 应用程序。当 X 服务器控制视频叠加时，应用程序可以利用内存映射和 DMA
## 查询能力


支持视频叠加接口的设备会VIDIOC_QUERYCAP ioctl 返回`v4l2_capability` 结构体的 `capabilities` 字段中设`V4L2_CAP_VIDEO_OVERLAY` 标志。下面指定的叠加 I/O 方法必须被支持。调谐器和音频输入是可选的

## 辅助功能


视频叠加设备应当按需支持音频输入 <audio>、调谐器、控<control>、裁剪与缩放 <crop> 以及流参<streaming-par> ioctl。所有视频叠加设备都必须支持视频输入 <video> 与视频标<standard> ioctl

## 设置


**注意：对此的支持已被移除* 在开始叠加之前，应用程序必须用帧缓冲参数对驱动进行编程，即帧缓冲的地址和大小，以及图像格式（例RGB 5:6:5）。VIDIOC_G_FBUF <VIDIOC_G_FBUF> VIDIOC_S_FBUF <VIDIOC_G_FBUF> ioctl 分别用于获取和设置这些参数。VIDIOC_S_FBUF <VIDIOC_G_FBUF> ioctl 是特权操作，因为它允许将 DMA 设置到物理内存，从而绕过内核的内存保护机制。只有超级用户才能更改帧缓冲地址和大小。用户不应以 root 身份或设SUID 位来运行电视应用程序。一个具有合适权限的小型辅助程序应当在适当的时候查询图形系统并V4L2 驱动进行编程
某些设备将视频叠加添加到显卡的输出信号上。这种情况下，帧缓冲不会被视频设备修改，驱动也不需要帧缓冲地址和像素格式。VIDIOC_S_FBUF <VIDIOC_G_FBUF> ioctl 不是特权操作。应用程序可以通过调用 VIDIOC_G_FBUF <VIDIOC_G_FBUF> ioctl 来检查是否为这类设备
驱动可以支持以下五种裁剪/混合方法中的任意几种（或全部不支持）
1. 色度键（Chroma-keying）仅在主图形表面的像素取某种特定颜色时才显示叠加图像
2. **注意：对此的支持已被移除* 可以指定一个位图，其中每一位对应叠加图像中的一个像素。当该位被置位时，显示对应的视频像素，否则显示图形表面的一个像素
3. **注意：对此的支持已被移除* 可以指定一个裁剪矩形列表。在这些区域**显示视频，因此可以在此处看到图形表面
4. 帧缓冲带有一alpha 通道，可用于将帧缓冲与视频进行裁剪或混合
5. 可以指定一个全局 alpha 值，用于将帧缓冲内容与视频图像混合
当支持同时捕获和叠加，且硬件禁止不同的图像与帧缓冲格式时，先请求的格式优先。捕获（VIDIOC_S_FMT <VIDIOC_G_FMT>）或叠加（VIDIOC_S_FBUF <VIDIOC_G_FBUF>）的尝试可能`EBUSY` 错误码失败，或者返回相应修改后的参数。

## 叠加窗口


叠加图像由裁剪和叠加窗口参数决定。前者选择要捕获的视频画面区域，后者决定图像如何叠加和裁剪。裁剪初始化至少需要将参数重置为默认值。crop 中给出了一个示例
叠加窗口由结构体 `v4l2_window` 描述。它定义图像的大小、其在图形表面上的位置，以及要应用的裁剪。要获取当前参数，应用程序将结构`v4l2_format` `type` 字段设为 `V4L2_BUF_TYPE_VIDEO_OVERLAY`，并调用 VIDIOC_G_FMT <VIDIOC_G_FMT> ioctl。驱动会填充名为 `win` `v4l2_window` 子结构体。无法取回先前编程的裁剪列表或位图
要对叠加窗口进行编程，应用程序将结构`v4l2_format` `type` 字段设为 `V4L2_BUF_TYPE_VIDEO_OVERLAY`，初始化 `win` 子结构体，并调用 VIDIOC_S_FMT <VIDIOC_G_FMT> ioctl。驱动会根据硬件限制调整参数，并VIDIOC_G_FMT <VIDIOC_G_FMT> 那样返回实际参数。与 VIDIOC_S_FMT <VIDIOC_G_FMT> 类似，VIDIOC_TRY_FMT <VIDIOC_G_FMT> ioctl 可用于在不实际改变驱动状态的情况下了解驱动能力。与 VIDIOC_S_FMT <VIDIOC_G_FMT> 不同，它在叠加启用后也能工作
叠加图像的缩放因子由结构`v4l2_window` 中给出的宽度和高度，以及裁剪矩形的大小隐含决定。更多信息见 crop
当支持同时捕获和叠加，且硬件禁止不同的图像与窗口大小时，先请求的大小优先。捕获或叠加的尝试（VIDIOC_S_FMT <VIDIOC_G_FMT>）可能以 `EBUSY` 错误码失败，或者返回相应修改后的参数


### struct v4l2_window


`struct v4l2_rect w`
    窗口相对于通过 VIDIOC_S_FBUF <VIDIOC_G_FBUF> 定义的帧缓冲左上角的大小和位置。窗口可以超出帧缓冲的宽度和高度，`x` `y` 坐标可以为负，并且窗口可以完全位于帧缓冲之外。驱动会相应裁剪窗口，若无法裁剪则修改其大小或位置
`enum v4l2_field field`
    应用程序设置此字段以决定叠加哪个视频场，通常`V4L2_FIELD_ANY` (0)、`V4L2_FIELD_TOP`、`V4L2_FIELD_BOTTOM` `V4L2_FIELD_INTERLACED` 之一。驱动可能必须选择不同的场顺序并在此返回实际设置
`__u32 chromakey`
    当已通过 VIDIOC_S_FBUF <VIDIOC_G_FBUF> 协商了色度键时，应用程序将此字段设为色度键所需的像素值。其格式与帧缓冲的像素格式（结构`v4l2_framebuffer` `fmt.pixelformat` 字段）相同，字节按主机字节序排列。例如，对于 V4L2_PIX_FMT_BGR24 <V4L2-PIX-FMT-BGR32>，在小端主机上该值应0xRRGGBB，在大端主机上应0xBBGGRR
`struct v4l2_clip * clips`
    **注意：对此的支持已被移除* **协商色度键，VIDIOC_G_FBUF <VIDIOC_G_FBUF> 指示了此能力时，应用程序可将此字段指向一个裁剪矩形数组
    与窗口坐w 类似，裁剪矩形是相对于帧缓冲的左上角定义的。不过裁剪矩形不得超出帧缓冲的宽度和高度，且不得相互重叠。若可能，应用程序应当合并相邻的矩形。究竟必须生x-y 还是 y-x 条带，或者矩形的顺序，均未定义。当不支持裁剪列表时，驱动忽略此字段。调VIDIOC_S_FMT <VIDIOC_G_FMT> 后其内容未定义
`__u32 clipcount`
    **注意：对此的支持已被移除* 当应用程序设置了 `clips` 字段时，此字段必须包含列表中裁剪矩形的数量。当不支持裁剪列表时，驱动忽略此字段，调VIDIOC_S_FMT <VIDIOC_G_FMT> 后其内容未定义。当支持裁剪列表但不希望裁剪时，此字段必须设为零
`void * bitmap`
    **注意：对此的支持已被移除* **协商色度键，VIDIOC_G_FBUF <VIDIOC_G_FBUF> 指示了此能力时，应用程序可将此字段指向一个裁剪位掩码
它必须与窗口 `w.width` `w.height` 大小相同。每一位对应叠加图像中的一个像素，仅当该位*置位**时才显示。像素坐标到位的转换如下


    ((__u8 **) bitmap)[w.width ** y + x / 8] & (1 << (x & 7))

其中 `0` x < `w.width` `0` y < `w.height`。[#f2]_

当不支持裁剪位掩码时，驱动忽略此字段，调VIDIOC_S_FMT <VIDIOC_G_FMT> 后其内容未定义。当支持位掩码但不希望裁剪时，此字段必须设为 `NULL`
应用程序无需创建裁剪列表或位掩码。当两者都传入，或者在已协商色度键的情况下仍传入，结果是未定义的。无论选择何种方法，硬件的裁剪能力在数量或质量上都可能受限。超出这些限制时的结果是未定义的。[#f3]_

`__u8 global_alpha`
    用于把帧缓冲与视频图像混合的全局 alpha 值（前提是已协商全局 alpha 混合，`V4L2_FBUF_FLAG_GLOBAL_ALPHA`，见 VIDIOC_S_FBUF <VIDIOC_G_FBUF>，framebuffer-flags）

   此字段是Linux 2.6.23 中加入的，扩展了该结构体。不VIDIOC_[G|S|TRY]_FMT <VIDIOC_G_FMT> ioctl 接受一个指向末尾带有填充字节的 `v4l2_format` 父结构体的指针，不受影响


### struct v4l2_clip [#f4]_


`struct v4l2_rect c`
    裁剪矩形的坐标，相对于帧缓冲的左上角。只*位于所*裁剪矩形**之外**的窗口像素才会被显示
`struct v4l2_clip * next`
    指向下一个裁剪矩形的指针，当这是最后一个矩形时`NULL`。驱动忽略此字段，它不能用于传递裁剪矩形的链表


### struct v4l2_rect


`__s32 left`
    矩形左上角的水平偏移，以像素为单位
`__s32 top`
    矩形左上角的垂直偏移，以像素为单位。偏移向右和向下递增
`__u32 width`
    矩形的宽度，以像素为单位
`__u32 height`
    矩形的高度，以像素为单位

## 启用叠加


要启动或停止帧缓冲叠加，应用程序调用 VIDIOC_OVERLAY ioctl
   在本 API 设计者看来，任何费心支持同时捕获和叠加的驱动作者，都不会像 V4L 及更早版V4L2 那样，通过要求单个文件描述符来限制这一能力。将其设为可选意味着依赖两个文件描述符的应用程序需要后备例程来兼容所有驱动，这比在不需要的应用程序中直接使用两fd 要费力得多。而且两个 fd 也契合“每个逻辑流一个文件描述符”的总体理念。因此，作为一项复杂性权衡，驱动**必须**支持两个文件描述符，*可以**支持fd 操作
   是否应当要求 `w.width` 8 的倍数
   当图像被写入帧缓冲内存时，如果驱动裁剪掉的像素少于预期，将是不利的，因为应用程序和图形系统并不知道这些区域需要刷新。驱动应当裁剪掉更多像素，或者干脆不写入图像
   X Window 系统定义的“region（区域）”是 ``struct BoxRec { short x1, y1, x2, y2; }`` 的向量，其中 `width = x2 - x1`、`height = y2 - y1`，因此无法直接传X11 的裁剪列表
