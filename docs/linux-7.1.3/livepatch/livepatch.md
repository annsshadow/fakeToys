## 实时补丁（Livepatch

本文概述了关于内核实时补丁（livepatching）的基本信息

## 1. 动机


在许多情况下，用户不愿意重启系统。这可能是因为他们的系统正在执行复杂的科学计算，或者在高峰使用期间处于高负载状态。除了保持系统持续运行之外，用户还希望拥有一个稳定且安全的系统。实时补丁通过允许重定向函数调用，在不重启系统的情况下修复关键函数，从而同时满足这两点

## 2. Kprobes、Ftrace、Livepatching


Linux 内核中有多种机制与代码执行的重定向直接相关；即：内核探针（kernel probes）、函数跟踪（function tracing）和实时补丁（livepatching）：

  - 内核探针是最通用的。可以通过用断点指令替换任何指令来重定向代码
  - 函数跟踪器从函数入口点附近、由编译器使'-pg' gcc 选项生成的预定义位置调用代码
  - 实时补丁通常需要在函数参数或栈以任何方式被修改之前，在函数入口的最开始重定向代码
这三种方法都需要在运行时修改现有代码。因此它们需要彼此感知，而不能互相踩踏。其中大部分问题通过使用动ftrace 框架作为基础来解决。当探测函数入口时，Kprobe 被注册为 ftrace 处理程序，参CONFIG_KPROBES_ON_FTRACE。此外，实时补丁中的替代函数也借助自定义的 ftrace 处理程序来调用。但存在一些限制，见下文

## 3. 一致性模

函数之所以存在是有原因的。它们接受一些输入参数，获取或释放锁，读取、处理甚至以定义的方式写入一些数据，并返回值。换句话说，每个函数都有一个定义的语义
许多修复不会改变被修改函数的语义。例如，它们添加 NULL 指针或边界检查，通过添加缺失的内存屏障来修复竞态，或在临界区周围添加一些锁。这些更改大多是自包含的，函数对系统其余部分呈现的方式相同。在这种情况下，函数可以逐个独立更新
但还有更复杂的修复。例如，一个补丁可能同时更改多个函数中的加锁顺序。或者一个补丁可能交换某些临时结构的含义并更新所有相关函数。在这种情况下，受影响单元（线程、整个内核）需要同时开始使用所有新版本的函数。而且切换必须只在安全时才发生，例如当受影响的锁被释放时，或此刻没有数据存储在被修改的结构中时
关于如何以安全方式应用函数的理论相当复杂。目的是定义一个所谓的一致性模型（consistency model）。它试图定义新实现可以使用、从而系统保持一致的条件
Livepatch 的一致性模型是 kGraft kpatch 的混合体：它使用 kGraft 的每任务（per-task）一致性和系统调用屏障切换，结kpatch 的栈跟踪切换。还有若干回退选项，使其相当灵活
补丁按每任务（per-task）为基础应用，当任务被视为可以安全切换时。当启用一个补丁时，livepatch 进入一个过渡状态，任务正在向已打补丁状态收敛。通常这个过渡状态可以在几秒内完成。当禁用一个补丁时会发生相同的序列，只是任务从已打补丁状态收敛到未打补丁状态
中断处理程序继承它所中断任务的已打补丁状态。对fork 出的任务也是如此：子进程继承父进程的已打补丁状态
Livepatch 使用几种互补的方法来确定何时可以安全地为任务打补丁：

1. 第一个也是最有效的方法是睡眠任务的栈检查。如果给定任务的栈上没有受影响的函数，该任务就被打补丁。在大多数情况下，这会在第一次尝试时就为大部分或所有任务打上补丁。否则它会周期性地继续尝试。此选项仅在体系结构具有可靠栈（HAVE_RELIABLE_STACKTRACE）时可用
2. 第二种方法（如果需要）是内核退出切换。当任务从系统调用、用户空IRQ 或信号返回到用户空间时，它会被切换。它在以下情况下有用
   a) 为正在受影响函数上睡眠的 I/O 密集型用户任务打补丁。这种情况下你必须发SIGSTOP SIGCONT 强制它退出内核并被打补丁   b) CPU 密集型用户任务打补丁。如果任务高度受 CPU 限制，那么它会在下一次被 IRQ 中断时得到打补丁
3. 对于空闲swapper"任务，由于它们从不退出内核，它们反而在空闲循环中有一klp_update_patch_state() 调用，允许它们在 CPU 进入空闲状态之前被打补丁
   （注意，对于 kthread 还没有这样的办法。）

没有 HAVE_RELIABLE_STACKTRACE 的体系结构完全依赖第二种方法。很可能某些任务仍在以旧版本的函数运行，直到该函数返回。在这种情况下你将不得不向任务发送信号。这尤其适用kthread。它们可能不会被唤醒，需要被强制。更多信息见下文
除非我们能想出另一种为 kthread 打补丁的方法，否则没HAVE_RELIABLE_STACKTRACE 的体系结构不被认为得到了内核实时补丁的完全支持
/sys/kernel/livepatch/<patch>/transition 文件显示某个补丁是否处于过渡中。任意时刻只能有一个补丁处于过渡中。如果任何任务卡在初始补丁状态，一个补丁可以无限期地停留在过渡中
在过渡进行期间，通过/sys/kernel/livepatch/<patch>/enabled 写入相反的值，可以反转并有效取消一个过渡。然后所有任务将尝试收敛回原始的补丁状态
还有一/proc/<pid>/patch_state 文件，可用于确定哪些任务正在阻塞打补丁操作的完成。如果某个补丁处于过渡中，此文件显示 0 表示任务未打补丁 表示已打补丁。否则，如果没有补丁处于过渡中，它显-1。任何阻塞过渡的任务都可以用 SIGSTOP SIGCONT 发送信号来强制它们改变已打补丁状态。但这可能对系统有害。向所有剩余阻塞任务发送一个伪信号是更好的替代方案。实际上不会投递任何真正的信号（signal pending 结构中没有数据）。任务被中断或被唤醒，并被迫改变其已打补丁状态。该伪信号每 15 秒自动发送一次
管理员也可以通过 /sys/kernel/livepatch/<patch>/force 属性来影响过渡。在那里写入 1 会清除所有任务的 TIF_PATCH_PENDING 标志，从而强制任务进入已打补丁状态。重要提示！force 属性用于过渡因阻塞任务而长时间卡住的情况。管理员应收集所有必要的数据（即此类阻塞任务的栈跟踪），并从补丁分发方获得强制过渡的许可。未经授权使用可能会对系统造成危害。它取决于补丁的性质、哪些函数被（取消）打补丁，以及阻塞任务正睡眠在哪些函数里（/proc/<pid>/stack 可能在这里有帮助）。使force 功能时会永久禁用补丁模块（rmmod）的移除。无法保证没有任务正睡眠在此类模块中。这意味着如果一个补丁模块被循环禁用和启用，引用计数将不受限制地增长
此外，force 的使用还可能影响实时补丁的未来应用，并对系统造成更大的危害。管理员应首先考虑简单地取消一个过渡（见上文）。如果使用了 force，则应当计划重启，并且不再应用更多实时补丁
### 3.1 为新的体系结构添加一致性模型支

要为新的体系结构添加一致性模型支持，有几个选项
1) 添加 CONFIG_HAVE_RELIABLE_STACKTRACE。这意味着移植 objtool，并且对于非 DWARF 的栈展开器，还要确保栈跟踪代码有一种方法检测栈上的中断
2) 或者，确保每个 kthread 在安全位置都有对 klp_update_patch_state() 的调用。Kthread 通常处于一个无限循环中，重复执行某些动作。切kthread 补丁状态的安全位置应位于循环中一个没有获取锁、且所有数据结构都处于明确定义状态的点
   在使用工作队列或 kthread worker API 时，该位置是清晰的。这kthread 在一个通用循环中处理独立的动作
   对于具有自定义循环的 kthread 则要复杂得多。那里的安全位置必须根据具体情况仔细选择
   在这种情况下，没HAVE_RELIABLE_STACKTRACE 的体系结构仍然能够使用一致性模型的非栈检查部分：

   a) 当用户任务跨越内用户空间边界时为它们打补丁；以及

   b) 在指定的补丁点为 kthread 和空闲任务打补丁
   这个选项不如选项 1 好，因为它需要向用户任务发送信号并唤醒 kthread 来为它们打补丁。但对于那些还没有可靠栈跟踪的体系结构，它仍然可以是一个很好的备份选项

## 4. 实时补丁模块


实时补丁使用内核模块分发，参samples/livepatch/livepatch-sample.c
该模块包含我们想要替换的函数的新实现。此外，它定义了一些描述原始实现与新实现之间关系的结构。然后有一些代码使内核在实时补丁模块加载时开始使用新代码。还有在实时补丁模块移除之前进行清理的代码。所有这些在后续章节中有更详细的解释

### 4.1. 新函

新版本的函数通常只是从原始源代码复制而来。一个好的做法是在名称前加一个前缀，以便与原始函数区分开来，例如在回溯中。此外，它们可以声明static，因为它们不会被直接调用，也不需要全局可见性
补丁只包含真正被修改的函数。但它们可能想要访问原始源文件中可能仅本地可访问的函数或数据。这可以通过生成的实时补丁模块中的一个特殊重定位节来解决，更多细节参Documentation/livepatch/module-elf-format.rst

### 4.2. 元数

补丁由几个结构描述，这些结构将信息分为三个层次：

  - struct klp_func 为每个被打补丁的函数定义。它描述了特定函数的原始实现与新实现之间的关系
    该结构包含原始函数的名称（字符串形式）。函数地址在运行时通过 kallsyms 找到
    然后它包含新函数的地址。通过直接赋值函数指针来定义。注意新函数通常定义在同一源文件中
    作为一个可选参数，kallsyms 数据库中的符号位置可用于消除同名函数的歧义。这不是在数据库中的绝对位置，而是它仅针对特定对象（vmlinux 或某个内核模块）被找到的顺序。注kallsyms 允许根据对象名搜索符号
  - struct klp_object 定义同一对象中被打补丁的函数（struct klp_func）的数组。其中对象要么是 vmlinux（NULL），要么是一个模块名
    该结构有助于将每个对象的函数分组并一起处理。注意被打补丁的模块可能比补丁本身加载得更晚，相关函数可能只在它们可用时才被打补丁

  - struct klp_patch 定义被打补丁的对象（struct klp_object）的数组
    此结构一致且最终同步地处理所有被打补丁的函数。只有当所有被打补丁的符号都被找到时，整个补丁才会被应用。唯一的例外是来自尚未加载的对象（内核模块）的符号
    关于补丁如何按每任务为基础应用的更多细节，请参一致性模章节

## 5. 实时补丁生命周期


实时补丁可以用五个基本操作来描述：加载（loading）、启用（enabling）、替换（replacing）、禁用（disabling）、移除（removing）
其中替换和禁用操作是互斥的。对于给定的补丁它们有相同的结果，但对系统则不然

### 5.1. 加载


唯一合理的方式是在实时补丁内核模块加载时启用补丁。为此，必须module_init() 回调中调klp_enable_patch()。有两个主要原因
第一，只有模块能方便地访问相关的 struct klp_patch
第二，错误码可用于在补丁无法启用时拒绝加载模块

### 5.2. 启用


实时补丁通过module_init() 回调调用 klp_enable_patch() 来启用。系统在此阶段将开始使用被打补丁函数的新实现
首先，根据被打补丁函数的名称找到它们的地址。在"新函一节中提到的特殊重定位被应用。相关条目在 /sys/kernel/livepatch/<name> 下创建。当上述任何操作失败时，补丁被拒绝
其次，livepatch 进入一个过渡状态，任务正在向已打补丁状态收敛。如果某个原始函数第一次被打补丁，则会创建一个函数特定的 struct klp_ops，并注册一个通用ftrace 处理程序\ [#]_。此阶段/sys/kernel/livepatch/<name>/transition 中的'1' 指示。关于此过程的更多信息，请参一致性模章节
最后，一旦所有任务都被打上补丁，'transition' 值变'0'

    注意函数可能被打补丁多次。对于给定的函数，ftrace 处理程序只注册一次。后续的补丁只是struct klp_ops 的列表（参见字段 `func_stack`）添加一个条目。正确的实现ftrace 处理程序选择，请参见"一致性模章节
    也就是说，强烈建议使用累积式实时补丁（cumulative livepatches），因为它们有助于保持所有更改的一致性。在这种情况下，函数可能仅在过渡期间被打补丁两次

### 5.3. 替换


所有已启用的补丁都可能被设置了 .replace 标志的累积式补丁替换
一旦新补丁被启用且 'transition' 完成，与被替换补丁关联的所有函数（struct klp_func）都会从相应struct klp_ops 中移除。此外，当相关函数未被新补丁修改func_stack 列表变为空时，ftrace 处理程序被注销，struct klp_ops 被释放
更多细节参见 Documentation/livepatch/cumulative-patches.rst

### 5.4. 禁用


已启用的补丁可以通过'0' 写入 /sys/kernel/livepatch/<name>/enabled 来禁用
首先，livepatch 进入一个过渡状态，任务正在向未打补丁状态收敛。系统开始使用先前启用的补丁甚至原始补丁的代码。此阶段/sys/kernel/livepatch/<name>/transition 中的'1' 指示。关于此过程的更多信息，请参一致性模章节
其次，一旦所有任务都未被打补丁，'transition' 值变'0'。与被禁用补丁关联的所有函数（struct klp_func）都会从相应struct klp_ops 中移除。当 func_stack 列表变为空时，ftrace 处理程序被注销，struct klp_ops 被释放
第三，sysfs 接口被销毁

### 5.5. 移除


只有当模块提供的函数没有使用者时，模块移除才是安全的。这正是 force 功能永久禁用移除的原因。只有当系统在没有被强制的情况下成功过渡到新的补丁状态（已打补丁/未打补丁）时，才能保证没有任务在旧代码中睡眠或运行

## 6. Sysfs


关于已注册补丁的信息可以/sys/kernel/livepatch 下找到。补丁可以通过写入那里来启用和禁用
/sys/kernel/livepatch/<patch>/force 属性允许管理员影响打补丁操作
更多细节参见 Documentation/ABI/testing/sysfs-kernel-livepatch

## 7. 限制


当前Livepatch 实现有几个限制：

  - 只有可以被跟踪的函数才能被打补丁
    Livepatch 基于动ftrace。特别地，实ftrace livepatch ftrace 处理函数的函数不能被打补丁。否则代码会陷入无限循环。通过"notrace" 标记有问题的函数来防止潜在的错误

  - Livepatch 只有在动ftrace 位于函数最开始时才能可靠工作
    函数需要在栈或函数参数以任何方式被修改之前被重定向。例如，livepatch x86_64 上需要使-fentry gcc 编译器选项
    一个例外是 PPC 移植。它使用相对寻址TOC。每个函数必须先处理 TOC 并保LR，然后才能调ftrace 处理程序。此操作在返回时必须被还原。幸运的是，通用ftrace 代码有相同的问题，所有这些都ftrace 层处理

  - 使用 ftrace 框架Kretprobe 与被打补丁的函数冲突
     kretprobe livepatch 都使用修改返回地址ftrace 处理程序。先到者胜。当处理程序已被另一方使用时，探针或补丁之一会被拒绝

  - 当代码被重定向到新实现时，原始函数中Kprobes 会被忽略
    目前正在进行相关工作，以对此情况添加警告
