## 原子替换与累积补

livepatch（热补丁）之间可能存在依赖关系。如果多个补丁需要对同一函数做不同的
修改，就需要定义一个补丁安装的先后顺序，且任何更新补丁中的函数实现都必建立在旧补丁之上
这可能会成为维护的噩梦，尤其在多个补丁以不同方式修改同一函数时
一个名为“原子替换（Atomic Replace）”的特性提供了一种优雅的解决方案。它允许
创建所谓的“累积补丁（Cumulative Patches）”。累积补丁包含了所有旧 livepatch
中所需的修改，并在一次切换（transition）中完全替换它们
### 用法


可以通过struct klp_patch 中的 "replace" 标志置位来启用原子替换：
```
	static struct klp_patch patch = {
		.mod = THIS_MODULE,
		.objs = objs,
		.replace = true,
	};

```
随后所有进程都会被迁移为只使用新补丁中的代码。一旦切换完成，所有旧补丁都会
被自动禁用
对于不再被新累积补丁修改的函数，Ftrace 处理函数会被透明地移除
因此，livepatch 作者只需维护一个累积补丁的源码即可。这有助于在添加或移各种修复与特性时保持补丁的一致性
在切换完成后，用户只需在系统中保留最后安装的补丁。这样能清晰地看到实正在使用的代码。此外，livepatch 此时可被视为一个修改内核行为的“普通”模块，
唯一的区别在于它可以在运行时更新而不破坏自身功能
### 特

原子替换允许
  - 在升级其他函数的同时，原子地回退某个先前补丁中的函数
  - 移除因核心重定向（core redirection）而对不再被补丁的函数造成    潜在性能影响
  - 减少用户livepatch 之间依赖关系的困惑
### 限制

  - 操作一旦完成，没有直接的办法将其反转并原子地恢复被替换的补丁
    一个良好的实践是：在任何已发布livepatch 中都设置 .replace 标志。这    重新添加旧的 livepatch 就等同于降级到该补丁。只livepatch 没有    （取消）打补丁回调或 module_init()/module_exit() 函数中做额外修改，就
    是安全的（见下文）
    还需注意，被替换的补丁只有在切换未被强制（forced）时才可能被移除并再次加载
  - 只有来自_新_累积 livepatch 的（取消）打补丁回调会被执行。被替换补丁    任何回调都将被忽略
    换句话说，累积补丁有责任执行任何为正确替换旧补丁所必需的行动
    因此，用较旧的累积补丁去替换较新的累积补丁可能是危险的。旧livepatch
    可能无法提供必要的回调
    在某些场景下这可被视为一种限制，但在许多其他场景下它让事情更简单。只    新的累积 livepatch 知道添加移除了哪些修复或特性，以及为平滑切换需    哪些特殊操作
    无论如何，如果要调用所有已启用补丁的各类回调并考虑它们的交互顺序，那将
    是一场噩梦
  - 对影子变量（shadow variables）没有特殊处理。livepatch 作者必须自行制    规则，将它们从一个累积补丁传递到另一个。尤其不应在 module_exit() 函数    盲目地移除它们
    一个良好的做法是在 post-unpatch 回调中移除影子变量。该回调只在 livepatch
    被正确禁用时才会被调用
