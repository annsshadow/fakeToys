## AArch64 Linux 中的活动监视器单元（AMU）扩展


作者：Ionela Voinescu <ionela.voinescu@arm.com>

日期：2019-09-10

本文档简要介绍 AArch64 Linux 中对活动监视器单元（AMU）的支持。


### 架构概述


活动监视器扩展是由 ARMv8.4 CPU 架构引入的一个可选扩展。

每个 CPU 中实现的活动监视器单元（AMU）提供用于系统管理的性能计数器。AMU 扩展为计数器寄存器提供了系统寄存器接口，并支持一个可选的外部内存映射接口。

活动监视器架构的第 1 版实现了一组由四个固定且按架构定义的 64 位事件计数器组成的计数器组。

  - CPU 周期计数器：以 CPU 的频率递增。
  - 常量计数器：以系统时钟的固定频率递增。
  - 已退休指令数：随每条按架构执行的指令递增。
  - 访存停顿周期：统计由时钟域内末级缓存未命中导致的指令分发停顿周期。

处于 WFI 或 WFE 状态时，这些计数器不递增。

活动监视器架构为最多 16 个按架构定义的事件计数器预留了空间。该架构的未来版本可能会利用这一空间来实现额外的按架构定义的事件计数器。

此外，第 1 版还实现了一组最多 16 个辅助的 64 位事件计数器。

冷复位时，所有计数器复位为 0。


### 基本支持


内核可以安全地运行在混用支持与不支持活动监视器扩展的 CPU 的环境上。因此，当选择了 CONFIG_ARM64_AMU_EXTN 时，我们会无条件地启用该能力，以允许任何后续 CPU（次级 CPU 或热插拔 CPU）检测并使用该特性。

当在某个 CPU 上检测到该特性时，我们会标记该特性的可用性，但这并不保证计数器的功能正确，而仅表示扩展存在。

需要固件（运行在更高异常级别的代码，例如 arm-tf）提供支持，以：

 - 为较低异常级别（EL2 和 EL1）启用对 AMU 寄存器的访问。
 - 启用计数器。若未启用，这些计数器将读为 0。
 - 在 CPU 被置于/脱离“off”电源态前后保存/恢复计数器。

当使用启用了该特性但固件存在缺陷的内核启动时，用户在访问计数器寄存器时可能会遇到死机或挂起。即使没有观察到这些症状，寄存器读取返回的值也可能无法正确反映实际情况。最常见的情况是，计数器读为 0，表明它们未被启用。

如果固件未提供适当的支持，最好禁用 CONFIG_ARM64_AMU_EXTN。需要注意的是，出于安全原因，这不会绕过对 AMUSERENR_EL0 的设置，该设置用于将来自 EL0（用户空间）的访问陷阱到 EL1（内核）。因此，固件仍应确保对 AMU 寄存器的访问不会被陷阱到 EL2/EL3。

AMUv1 的固定计数器可通过以下系统寄存器定义访问：

 - SYS_AMEVCNTR0_CORE_EL0
 - SYS_AMEVCNTR0_CONST_EL0
 - SYS_AMEVCNTR0_INST_RET_EL0
 - SYS_AMEVCNTR0_MEM_STALL_EL0

辅助的、平台相关的计数器可使用 SYS_AMEVCNTR1_EL0(n) 访问，其中 n 是 0 到 15 之间的值。

更多细节可在 arch/arm64/include/asm/sysreg.h 中找到。


### 用户空间访问


目前，出于以下原因，禁用了从用户空间对 AMU 寄存器的访问：

 - 安全原因：它们可能暴露有关在安全模式下执行的代码的信息。
 - 用途：AMU 计数器用于系统管理。

此外，该特性的存在对用户空间不可见。


### 虚拟化


目前，由于以下原因，禁用了 KVM 客户机侧从用户空间（EL0）和内核空间（EL1）的访问：

 - 安全原因：它们可能暴露有关其他客户机或宿主执行的代码的信息。

任何访问 AMU 寄存器的尝试都将导致向客户机注入一个 UNDEFINED 异常。
