

## 非对32 SoC


Author: Will Deacon <will@kernel.org>

本文档描述了非对32 SoC 32 位（`AArch32`）应用程序执行所产生的影响

Date: 2021-05-17

## 简


一Armv9 SoC 存在一big.LITTLE 的缺陷特性，即只有一部分 CPU 能够执行 32 位用户应用程序。在这样的系统上，Linux 默认将这种不对称视为一种“不匹配（mismatch）”，并禁用对 `PER_LINUX32` personality 的支持以及对 32 ELF 二进制文件执`execve(2)`，后者会返回 `-ENOEXEC`。如果在仅支64 位的 CPU 晚期上线（late onlining）期间检测到这种不匹配，则上线操作会失败，该CPU 将不可用于调度

令人意外的是，这SoC 正是为了运行遗留32 位二进制文件而生产的。同样不出所料，这与 Linux 的默认行为配合得并不好

未来SoC 似乎不可避免地会彻底放弃 32 位支持，因此如果你不幸处于需要在这些过渡性平台之一上运32 位代码的境地，那么明智的做法是考虑重新编译、模拟或淘汰等替代方案。如果这些选项都不切实际，请继续阅读

## 启用内核支持


由于内核支持对用户空间并非完全透明，要在非对称 32 位系统上允许运行 32 位任务，需要显式的“opt-in”（选择加入），可通过在内核命令行上传`allow_mismatched_32bit_el0` 参数来启用

在本文档的其余部分，我们将用*非对称系来指代运行启用了该内核命令行选项Linux 的非对称 32 SoC

## 对用户空间的影响


在非对称系统上运行的 32 位任务的行为与在同构系统上大体相同，只是CPU 亲和性方面存在几个关键差异

### sysfs


能够运行 32 位任务的 CPU 子集`/sys/devices/system/cpu/aarch32_el0` 中有描述，并Documentation/ABI/testing/sysfs-devices-system-cpu 中有进一步说明

**注意* 该文件在检测到 CPU 时即对其进行通告，因32 位可执行CPU 的晚期上线可能导致内核在运行时修改该文件的内容。一旦通告，CPU 永远不会从该文件中移除

### ``execve(2)``


在同构系统上，任务的 CPU 亲和性在 `execve(2)` 之间是保留的。在非对称系统上这并非总是可行，特别是当所执行的新程序32 位，而亲和性掩码中包含了仅支持 64 位的 CPU 时。在这种情况下，内核按下述方式确定新的亲和性掩码：

  1. 如果亲和性掩码的 32 位可执行子集不为空，则将亲和性限制为该子集，并保存旧的亲和性掩码。该保存的掩码会通过 `fork(2)` 继承，并32 位程序的 `execve(2)` 之间保留

     **注意* 此步骤不适用`SCHED_DEADLINE` 任务。参`SCHED_DEADLINE`_

  2. 否则，会遍历任务cpuset 层级，直到找到一个包含至少一32 位可执行 CPU 的祖先。随后将任务的亲和性修改为与该遍历所确定cpuset 32 位可执行子集相匹配

  3. 如果失败（即内存不足），则将亲和性修改为内核所知晓的所32 位可执行 CPU 的集合

32 位任务随后对 64 位程序执`execve(2)` 会使 (1) 中保存的亲和性掩码失效，并尝试使用该保存的掩码恢复任务的 CPU 亲和性（如果它之前是有效的）。这种恢复可能因截止时间策略cpuset 层级的中间变更而失败，此时 `execve(2)` 会继续执行且亲和性保持不变

32 位任务调`sched_setaffinity(2)` 只会考虑所请求亲和性掩码中32 位可执行 CPU。成功时，任务的亲和性会被更新，并且来自先前 `execve(2)` 的任何已保存掩码会失效

### ``SCHED_DEADLINE``


在非对称 32 位系统上，将 32 位截止时间任务显式接纳到默认根域（例如通过调用 `sched_setattr(2)`）会被拒绝，除非通过`/proc/sys/kernel/sched_rt_runtime_us` 写入 -1 来禁用接纳控制

如果任务的根域包含任何仅支持 64 位的 CPU，且启用了接纳控制，那么64 位截止时间任务对 32 位程序执`execve(2)` 将返`-ENOEXEC`2 位可执行 CPU 的并发下线可能仍然需要执`execve(2)`_ 中描述的过程，此时会跳过步骤 (1) 并在控制台上发出警告

**注意* 如果要在非对称系统上`SCHED_DEADLINE` 用于 32 位任务，建议将一32 位可执行 CPU 放入一个单独的根域。否则很可能导致错过截止时间

### Cpusets


在非对称系统上，32 位任务的亲和性可能包含其所cpuset 未显式允许的 CPU。这可能由以下两种情况导致：

  - 一个附加到仅允64 CPU cpuset 64 位任务，执行了一32 位程序

  - 包含 32 位任务的 cpuset 所允许的所32 位可执行 CPU 都被下线了

在这两种情况下，新的亲和性都会按`execve(2)`_ 中描述过程的步骤 (2) 计算，并且无cgroup 版本如何，cpuset 层级都保持不变

### CPU 热插


在非对称系统上，第一个被检测到32 位可执行 CPU 会被阻止由用户空间下线，任何此类尝试都会返回 `-EPERM`。注意，即使CPU（即 CPU 0）仅支持 64 位，仍然允许挂起

### KVM


尽管 KVM 不会向非对称系统上的任何 vCPU 通告 32 EL0 支持，但处于 EL1 的有缺陷的客户机仍可能尝试在 EL0 执行 32 位代码。在这种情况下，处于 32 位模式的 vCPU 线程退出时，会`exit_reason` `KVM_EXIT_FAIL_ENTRY` 返回到宿主机用户空间，并且在随后成功通过 `KVM_ARM_VCPU_INIT` 操作重新初始化之前将保持不可运行状态

### 调度域隔离（SCHEDULER DOMAIN ISOLATION


32 位任务被强制迁移时，为了避免干扰启动期定义的域隔CPU（使`isolcpus=[domain]` 指定），在启用对非对32 位系统的支持时，这些 CPU 被视为仅支持 64 位

然而，与启动期定义的域隔离不同，使cpuset 隔离分区的运行时定义的域隔离在非对称 32 位系统上不被建议，并会导致未定义行为
