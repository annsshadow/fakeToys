
## 面向开发者的 arch/riscv 维护指南


### 概述


RISC-V 指令集架构是公开开发的：所有人都可以审阅进度中的草案，并试验其实现新的模块或扩展草案在开发过程中可能会发生变化——有时会与之前的草案不兼容这种灵活性给 RISC-V Linux 的维护带来了挑战。Linux 的维护者不赞成无谓的改动，
并且 Linux 的开发流程更偏好经过充分审阅与测试的代科，而不是实验性代码。我希望将同样的原则延伸到将被内核接受纳入的 RISC-V 相关代码上
### Patchwork


RISC-V 有一patchwork 实例，可以在其中查看补丁的状态：

  https://patchwork.kernel.org/project/linux-riscv/list/

如果你的补丁没有出现在默认视图中，RISC-V 维护者很可能已经要求你做出修改，或期望它由另一棵树来应用
针对patchwork 实例运行了自动化任务，会在补丁到达时构建/测试它们。该自动会根据补丁是否被识别为修复（fix），将补丁应用到当前 HEAD RISC-V `for-next`
`fixes` 分支上；若两者都不满足，则使RISC-V `master` 分支。补丁被应用到的
确切提交会在 patchwork 上注明。任何检查未通过而被标记失败的补丁都不太可能被应用，
在大多数情况下需要重新提交
### 提交清单补充

只有当这些模块或扩展的规范被列为在未来不太可能发生不兼容变更时，我们才会接受
针对新模块或扩展的补丁。对于来RISC-V 基金会的规范，这意味着“Frozen”或
“Ratified”；对于 UEFI 论坛的规范，这意味着已发布的 ECR。（当然，开发者可以维他们自己Linux 内核树，其中包含他们想要的任意草案扩展的代码。）

此外，RISC-V 规范允许实现者创建自己的自定义扩展。这些自定义扩展不需要经RISC-V 基金会的任何审阅或批准流程。为了避免为特定实现者的 RISC-V 扩展添加内核
代码所带来的维护复杂性以及潜在性能影响，我们只会考虑符合以下条件的扩展补丁：

- 已被 RISC-V 基金会正式冻结（frozen）或批准（ratified），- 已按照标Linux 实践，在广泛可用的硬件上实现
（当然，实现者可以维护他们自己的 Linux 内核树，其中包含他们想要的任意自定义
扩展的代码。）
