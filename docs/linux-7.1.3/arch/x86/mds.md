## 微体系结构数据采样（MDS）缓解方案


### 概述

微体系结构数据采样（Microarchitectural Data Sampling，MDS）是针对 Intel CPU 内部
缓冲区的一类侧信道攻击。其变种包括：

 - Microarchitectural Store Buffer Data Sampling (MSBDS) (CVE-2018-12126)
 - Microarchitectural Fill Buffer Data Sampling (MFBDS) (CVE-2018-12130)
 - Microarchitectural Load Port Data Sampling (MLPDS) (CVE-2018-12127)
 - Microarchitectural Data Sampling Uncacheable Memory (MDSUM) (CVE-2019-11091)

MSBDS 会泄露 Store Buffer 条目，这些条目作为一种优化可以被推测性地转发给一个
依赖的加载（store-to-load forwarding）。该转发也可能发生到一个针对不同内存地址
的、会产生错误或辅助的加载操作上，在某些条件下可被利用。Store Buffer 在
超线程之间进行了分区，因此无法跨线程转发。但是，如果一个线程进入或退出休眠
状态，Store Buffer 会被重新分区，从而可能将一个线程的数据暴露给另一个线程。

MFBDS 会泄露 Fill Buffer 条目。Fill Buffer 在内部用于管理 L1 未命中（miss）的
情况，并保存因内存或 I/O 操作而返回或发送的数据。Fill Buffer 可以将数据转发给
加载操作，也可以将数据写入缓存。当 Fill Buffer 被释放时，它可能会保留之前操作的
陈旧数据，这些数据随后可以被转发到一个会产生错误或辅助的加载操作，在某些条件下
可被利用。Fill Buffer 在超线程之间共享，因此有可能发生跨线程泄露。

MLPDS 会泄露 Load Port 数据。Load Port 用于从内存或 I/O 执行加载操作。接收到的
数据随后被转发到寄存器文件或后续操作。在某些实现中，Load Port 可能包含来自上一次
操作的陈旧数据，这些数据在某些条件下可以被转发到会产生错误或辅助的加载，最终同样
可被利用。Load Port 在超线程之间共享，因此有可能发生跨线程泄露。

MDSUM 是 MSBDS、MFBDS 和 MLPDS 的一个特例。一次来自内存的、产生错误或辅助的不可
缓存加载，可能会在微体系结构结构中留下数据，稍后可以使用 MSBDS、MFBDS 或 MLPDS
所使用的相同方法之一进行观察。

### 暴露假设

假设攻击代码驻留在用户空间或客户机中，但有一个例外。这一假设背后的理由是，利用
MDS 所需的代码构造需要：

 - 控制加载以触发错误或辅助

 - 具备一个泄露装置（disclosure gadget），它通过侧信道暴露被推测性访问的数据
   以供消费

 - 控制泄露装置用于暴露数据的指针

内核中存在此类构造的可能性无法以 100% 的确定性排除，但其中涉及的复杂性使其极
不可能发生。

有一个例外，即不可信 BPF。不可信 BPF 的功能有限，但仍需彻底研究它是否可用于创建
此类构造。

### 缓解策略

所有变种至少对单 CPU 线程情况（SMT off）具有相同的缓解策略：强制 CPU 清空受影响的
缓冲区。

这是通过结合微码更新，使用原本未使用且已废弃的 VERW 指令来实现的。当执行 VERW
指令时，微码会清空受影响的 CPU 缓冲区。

对于虚拟化，有两种实现 CPU 缓冲区清空的方法。既可以使用修改后的 VERW 指令，也
可以通过 L1D Flush 命令。后者在启用 L1TF 缓解时会发出，因此可以避免额外的 VERW。
如果 CPU 不受 L1TF 影响，则需要发出 VERW。

如果在没有微码更新的 CPU 上执行带有所提供的段选择器参数的 VERW 指令，除了白白
浪费少量 CPU 周期外，没有其他副作用。

这不能防御跨超线程攻击，MSBDS 除外——MSBDS 仅当其中一个超线程进入 C-state 时才
可跨超线程被利用。

内核提供了一个用于调用缓冲区清空的函数：

    x86_clear_cpu_buffers()

此外，宏 CLEAR_CPU_BUFFERS 也可用在退出到用户路径（exit-to-user）后期的汇编中。
与 CFLAGS.ZF 不同，该宏不会破坏任何寄存器。

该缓解措施在内核/用户空间、虚拟机监控器/客户机以及 C-state（空闲）转换时被调用。

作为一个特殊特性，为了应对这样一种虚拟化场景——宿主机已更新微码，但虚拟机监控器
（尚未）向客户机暴露 MD_CLEAR CPUID 位——内核会发出 VERW 指令，希望它确实能够
清空缓冲区。相应的状态会据此反映出来。

根据目前的认识，内核本身内部的额外缓解措施并非必需，因为暴露泄露数据所需的装置
无法被以允许来自恶意用户空间或 VM 客户机的利用方式进行控制。

### 内核内部缓解模式


 ======= ============================================================
 off      缓解措施被禁用。要么 CPU 不受影响，要么内核命令行中提供了
          mds=off

 full     缓解措施已启用。CPU 受影响，且 CPUID 中通告了 MD_CLEAR。

 vmwerv	  缓解措施已启用。CPU 受影响，但 CPUID 中未通告 MD_CLEAR。这主要用于
	  虚拟化场景，其中宿主机拥有更新后的微码，但虚拟机监控器未在 CPUID 中
	  暴露 MD_CLEAR。这是一种尽力而为的方法，不提供保证。
 ======= ============================================================

如果 CPU 受影响且内核命令行中未提供 mds=off，则内核会根据 MD_CLEAR CPUID 位的
可用性选择合适的缓解模式。

### 缓解点


##### 1. 返回用户空间

   当从内核切换到用户空间时，如果在内核命令行上未禁用缓解措施，受影响的 CPU 会
   清空 CPU 缓冲区。该缓解措施通过特性标志 X86_FEATURE_CLEAR_CPU_BUF 启用。

   缓解措施在恢复用户寄存器之后、即将切换到用户空间之前被调用。这样做是为了尽量
   缩小在 VERW 之后（例如通过 VERW 之后的 NMI）可以访问内核数据的窗口。

   **未处理的边界情况**
   返回内核的中断不会清空 CPU 缓冲区，因为退出到用户空间的路径本来就会这样做。
   但是，可能存在这样一种情况：在退出到用户空间的路径已经清空缓冲区之后，在内核中
   产生了一个 NMI。这种情况未被处理，返回内核的 NMI 不会清空 CPU 缓冲区，因为：

   1. 在 VERW 之后、返回用户空间之前得到 NMI 是罕见的。
   2. 对于非特权用户来说，没有已知的方法能让该 NMI 变得不那么罕见或对其定向。
   3. 发动一次实际攻击需要大量这些精确计时的 NMI。想必带宽不足。
   4. 所讨论的 NMI 发生在 VERW 之后，也就是用户状态已恢复、大多数有趣的数据已被
      擦除之时。剩下的只是 NMI 触及的数据，而这些数据可能有也可能没有价值。


##### 2. C-State 转换

   当一个 CPU 进入空闲并进入 C-State 时，如果 SMT 处于活动状态，受影响的 CPU 需要
   清空 CPU 缓冲区。这解决了当一个超线程进入 C-State 时 Store Buffer 被重新分区
   的问题。

   当 SMT 不活动时，即 CPU 不支持 SMT 或所有兄弟线程离线，则不需要清空 CPU 缓冲区。

   空闲清空功能在仅受 MSBDS 影响而不受任何其他 MDS 变种影响的 CPU 上启用。其他 MDS
   变种无法防御跨超线程攻击，因为 Fill Buffer 和 Load Port 是共享的。因此，在受
   其他变种影响的 CPU 上，空闲清空只是装点门面，因此不会被激活。

   该调用由静态键 cpu_buf_idle_clear 控制，它会根据所选的缓解模式和系统的 SMT 状态
   进行切换。

   缓冲区清空仅在进入 C-State 之前被调用，以防止空闲 CPU 的陈旧数据在 Store Buffer
   被重新分区、所有条目都可供非空闲兄弟线程使用之后，泄漏到超线程兄弟线程。

   当从空闲状态恢复时，Store Buffer 会再次被分区，因此每个兄弟线程拥有其中一半的
   可用空间。从空闲恢复的 CPU 随后可能在推测上被暴露给兄弟线程的内容。缓冲区会在
   退出到用户空间或 VMENTER 时被清空，从而使恶意代码无法在推测上访问它们。

   该缓解措施挂接到所有变体的 halt()/mwait()，但不覆盖传统的 ACPI IO-Port 机制，
   因为 ACPI 空闲驱动在 2010 年前后已被 intel_idle 驱动取代，并且在所有预期会在
   微码中获得 MD_CLEAR 功能的受影响 CPU 上都是首选。除此之外，IO-Port 机制是一个
   传统接口，仅用于较旧的系统，这些系统要么不受影响，要么不再接收微码更新。
