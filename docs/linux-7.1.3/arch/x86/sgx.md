
## 软件防护扩展（SGX

## 概述


软件防护扩展（SGX）硬件使用户空间应用程序能够预留出私有的代码和数据内存区域：

- 特权（ring-0）的 ENCLS 函数负责编排这些区域的构建- 非特权（ring-3）的 ENCLU 函数允许应用程序进入并在这些区域内执行
这些内存区域称为飞地（enclave）。只能在固定的入口点集合处进入飞地。每个入口点一次只能容纳一个硬线程。虽然飞地是使用 ENCLS 函数从常规二进制文件加载的，但只有飞地内部的线程可以访问其内存。该区域
CPU 拒绝来自外部的访问，并在离开 LLC 之前被加密
可以通过如下方式确定是否支持
	`grep sgx /proc/cpuinfo`

SGX 必须既在处理器中受支持，又要BIOS 启用。如果在一台具有硬件支持的系统SGX 似乎不受支持请确保在 BIOS 中启用了支持。如BIOS SGX 提供“Enabled”和“Software Enabled”模式的选择，请选择

## 椋炲湴椤电紦瀛。

SGX 利用一*飞地页缓存（EPC*来存储与飞地关联的页面。它包含在一段由 BIOS 保留的物理内存区域中与用于常规内存的页面不同，页面只能在飞地构建期间通过特殊、受限的 SGX 指令从飞地外部访问
只有执行在飞地内部的 CPU 才能直接访问飞地内存。但是，执行在飞地内部的 CPU 可以访问飞地外部的正内存
内核管理飞地内存的方式类似于它对待设备内存
### 椋炲湴椤电被鍨。

**SGX 飞地控制结构（SECS*
   飞地的地址范围、属性以及其他全局数据由此结构定义
**常规（REG*
   常规 EPC 页面包含飞地的代码和数据
**线程控制结构（TCS*
   线程控制结构页面定义飞地的入口点，并跟踪飞地线程的执行状态
**版本数组（VA*
   版本数组页面包含 512 个槽，每个槽可包含一个从 EPC 换出的页面的版本号
### 椋炲湴椤电紦瀛樻槧灏。

处理器在一个称*飞地页缓存映射（EPCM*的硬件元数据中跟EPC 页面。EPCM 为每EPC 页面包含一条目，描述所属飞地、访问权限和页面类型等内容
EPCM 权限独立于常规页表。这防止了内核（例如）允许写入飞地希望保持只读的数据。EPCM 权限只能在常x86
页权限之上施加额外限制
出于所有意图和目的，SGX 架构允许处理器随时使所EPCM 条目失效。这要求软件准备好随时处EPCM 缺页在实践中，这可能发生在诸如加密飞地内存的临时密钥丢失时的电源切换等事件上
## 应用程序接口


### 飞地构建函数


除了传统的编译器和链接器构建过程外，SGX 还有一个单独的飞地“构建”过程。飞地必须先构建，然后才执行（进入）。构建飞地的第一步是打开 **/dev/sgx_enclave** 设备。由于飞地内存受保护而无法被直接访问随后使用特殊的特权指令将数据复制到飞地页面并建立飞地页面权限
   :functions: sgx_ioc_enclave_create
               sgx_ioc_enclave_add_pages
               sgx_ioc_enclave_init
               sgx_ioc_enclave_provision

### 飞地运行时管

支持 SGX2 的系统还支持对初始化后的飞地进行更改：修改飞地页面权限和类型，以及动态添加和移除飞地页面当飞地访问其地址范围内没有后备页面的地址时，一个新的常规页面将被动态添加到飞地。飞地仍需要在使用
新页面之前对其运EACCEPT
   :functions: sgx_ioc_enclave_restrict_permissions
               sgx_ioc_enclave_modify_types
               sgx_ioc_enclave_remove_pages

### 飞地 vDSO


进入飞地只能通过 SGX 特定EENTER ERESUME 函数完成，这是一个不平凡的过程。由于进出飞地转换的
复杂性，飞地通常利用一个库来处理实际的转换。这大致类似于大多数应用程序使用 glibc 实现来包装系统调的方式
飞地的另一个关键特性是，它们可以在正常操作中生成异常，这些异常需要在飞地内部处理，或者是 SGX 特有的
SGX 可以利用 vDSO 提供的特殊异常修复（fixup）来代替传统的信号处理机制来处理这些异常。内核提供的
vDSO 函数包装了进出飞地的底层转换（如 EENTER ERESUME）。vDSO 函数拦截那些本来会生成信号的异常并直接将缺页信息返回给其调用者。这避免了需要摆弄信号处理程序
   :functions: vdso_sgx_enter_enclave_t

## ksgxd


SGX 支持包含一个称**ksgxd** 的内核线程
### EPC 清理


ksgxd SGX 初始化时启动。飞地内存通常在处理器上电或复位时即可使用。但是，如果自复位以来一直在使用
SGX，飞地页面可能处于不一致状态。例如，这可能在崩溃kexec() 周期之后发生。在启动时，ksgxd 重新
初始化所有飞地页面，以便它们可以被分配和重用
清理是通过遍历 EPC 地址空间并对每个物理页面应用 EREMOVE 函数来完成的。某些飞地页面（SECS 页面）对
其他页面有硬件依赖，这会阻止 EREMOVE 起作用。执行两EREMOVE 可以消除这些依赖
### 椤甸潰鍥炴敹鍣。

与核kswapd 类似，ksgxd 负责管理飞地内存的过量提交（overcommitment）。如果系统用完了飞地内存**ksgxd** 将飞地内存“换出”到正常内存
## 启动控制


SGX 提供一个启动控制机制。在复制完所有飞地页面后，内核执EINIT 函数来初始化飞地。只有在此之CPU
才能在飞地内部执行
EINIT 函数接受飞地度量RSA-3072 签名。该函数检查度量是否正确，并且签名是由哈希到四**IA32_SGXLEPUBKEYHASH{0, 1, 2, 3}** MSR（代表公钥的 SHA256）的密钥签名的
这些 MSR 可由 BIOS 配置为可读或可写。Linux 只支持可写配置，以便内核完全控制启动控制策略。在调用 EINIT
函数之前，驱动将 MSR 设置为与飞地的签名密钥匹配
## 加密引擎


为了隐藏飞地数据在离开 CPU 封装时的情况，内存控制器具有一个加密引擎，以透明方式加密和解密飞地内存
Ice Lake 之前CPU 上，使用内存加密引擎（MEE）来加密离开 CPU 缓存的页面。MEE 使用一个以 SRAM 根的 n Merkle 树来维护加密数据的完整性。这提供了完整性和抗重放保护，但不能扩展到大型内存，因更新 Merkle 树所需的时间随内存大小呈对数增长
Icelake 开始的 CPU 使用全内存加密（TME）替MEE。基TME SGX 实现没有完整Merkle 树，这意味着
未缓解完整性和重放攻击。不过，它包含额外的更改以防止密文被返回以及创建 SW 内存别名
MEE TME 系统上，对飞地内存的 DMA 都被范围寄存器阻止（SDM 41.10 节）
## 使用模式


### 鍏变韩搴。

敏感数据以及作用于它的代码被从应用程序中划分到一个单独的库中。该库随后作DSO 链接，可以被加载飞地中。应用程序随后可以通过特殊SGX 指令对飞地进行单独的函数调用。飞地内的运行时被配置为将函参数封送进和封送出飞地，并调用正确的库函数
### 应用容器


应用程序可以被加载到一个容器飞地中，该飞地专门配置了一个库 OS 和运行时以允许应用程序运行。当线程进入
飞地时，飞地运行时和OS 协同工作以执行应用程序
## 潜在内核 SGX 缺陷的影

### EPC 泄漏


当发EPC 页面泄漏时，dmesg 中会显示如下 WARNING
"EREMOVE returned ... and an EPC page was leaked.  SGX may become unusable..."

这实际上是内核对已释EPC 页面use-after-free，并且由SGX 的工作方式，该缺陷在释放时被检测到内核有意泄漏该页面，而不是将其加回可EPC 页面的池中，以避免将来出现额外错误
发生这种情况时，内核可能很快会泄漏更EPC 页面，并且由于可SGX 使用的内存有限，SGX 很可能变得不可用但是，虽然这可能SGX 是致命的，内核的其余部分不太可能受到影响，应当继续工作
因此，发生这种情况时，用户应停止运行任何新的 SGX 工作负载（或任何新工作负载），并迁移所有有价值的工作
负载。尽管机器重启可以恢复所EPC 内存，但该缺陷应报告Linux 开发者

## 虚拟 EPC


该实现还有一个虚EPC 驱动来支持客户机中的 SGX 飞地。与 SGX 驱动不同，由虚拟 EPC 驱动分配EPC 页面
没有与之关联的具体飞地。这是因KVM 不跟踪客户机如何使用 EPC 页面
因此，SGX 核心页面回收器不支持回收通过虚拟 EPC 驱动分配KVM 客户机的 EPC 页面。如果用户希望在同一
台机器上的主机和客户机中都部SGX 应用程序，用户应为主SGX 应用程序保留足够EPC（从物理 EPC 大小
中扣除所SGX VM 的总虚EPC 大小），以便它们能够以可接受的性能运行
架构行为是，在客户机重启后也将所EPC 页面恢复到未初始化状态。由于此状态只能通过对特`ENCLS[EREMOVE]` 指令达到，`/dev/sgx_vepc` 提供 `SGX_IOC_VEPC_REMOVE_ALL` ioctl 以对该虚EPC 中的
所有页面执行该指令
`EREMOVE` 可能因三个原因失败。用户空间必须注意预期的失败并如下处理：

1. 当任何线程正在其所属页面所在的飞地中运行时，页面移除将总是失败。在这种情况下，无论是否已成功移   某些页面，ioctl 都将返回 `EBUSY`；用户空间可以通过阻止执行任何映射了虚EPC vcpu 来避免这些失败
2. 如果对引用同一“SECS”元数据页面的页面并发进行两`EREMOVE` 调用，页面移除将导致一般保护故障。如   存在`SGX_IOC_VEPC_REMOVE_ALL` 的并发调用，或者客户机中的 `/dev/sgx_vepc` 文件描述符与
   `SGX_IOC_VEPC_REMOVE_ALL` 同时关闭，就可能发生这种情况；它也将被报告为 `EBUSY`。这可以在用户空间通过
   串行化对 ioctl() close() 的调用来避免，但一般来说不应成为问题
3. 最后，对于仍具有子页面SECS 元数据页面，页面移除将失败。子页面可以通过对所有映射到客户机中   `/dev/sgx_vepc` 文件描述符执`SGX_IOC_VEPC_REMOVE_ALL` 来移除。这意味着必须调用 ioctl() 两次：一   初始调用用于移除子页面，随后一组调用用于移SECS 页面。第二组调用仅对那些从第一次调用返回非零值的
   映射是必需的。如果任何第二轮 `SGX_IOC_VEPC_REMOVE_ALL` 调用的返回码不是 0，则表明内核或用户空间客户端
   中存在缺陷
