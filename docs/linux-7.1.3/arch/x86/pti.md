
## 页表隔离（PTI

## 概述


页表隔离（pti，之前称KAISER [^1^]_）是针对共享的用内核地址空间攻击（如 “Meltdown方法 [^2^]_）的一种对策
为了缓解这类攻击，我们创建一组独立的页表，仅在运行用户空间应用程序时使用。当通过系统调用、中断或异常进入内核时，页表切换到完整的“内核”副本。当系统切回用户模式时，重新使用用户副本
用户空间页表只包含极少的内核数据：仅包含进入/退出内核所需的内容，例如 entry/exit 函数本身和中断描述符表（IDT）。有一些严格来说不必要的东西也被映射了，例如进入中断时的第一C 函数（见 pti.c 中的注释）
这种方法有助于确保当 PTI 启用时，利用分页结构进行的侧信道攻击无法生效。它可以通过在编译时设置 CONFIG_MITIGATION_PAGE_TABLE_ISOLATION=y 来启用。一旦在编译时启用，可以在引导时通过 “nopti“pti=内核参数禁用（见 kernel-parameters.txt）
## 页表管理


PTI 启用时，内核管理两套页表。第一套与没有 PTI 的内核中存在的单一页表非常相似。这包括内核可用copy_to_user() 等操作的完整用户空间映射
尽管是“完整”的，内核页表的用户部分通过设置顶层NX 位而被削弱。这确保任何错过kernel->user CR3 切换会在用户空间执行其第一条指令时立即崩溃
用户空间页表只映射进入和退出内核所需的内核数据。这些数据完全包含在 “struct cpu_entry_area结构体中，该结构体被放在固定映射（fixmap）区，为每个 CPU 的该区域副本提供一个编译时固定的虚拟地址
对于新的用户空间映射，内核像平常一样在其页表中建立条目。唯一的区别在于内核在顶层（PGD）建立条目时。除了在主内PGD 中设置该条目外，还会在用户空间页表的 PGD 中制作一份该条目的副本
这种PGD 层的共享也天然地共享了页表的所有更低层。这就留下了一组单一的、共享的用户空间页表需要管理。一个需要锁定的 PTE、一组访问位、脏位等…
## 开销


防范侧信道攻击很重要。但是，这种保护是有代价的：

1. 增加的内存使
  a. 现在每个进程需要一order-1 PGD，而不order-0（每个进程多消4k）  b. “cpu_entry_area结构体必须为 2MB 大小2MB 对齐，以便通过设置一PMD 条目来映射它。这在内核解压后会消耗近 2MB RAM，但在内核镜像本身中并不占用空间
2. 运行时开销

  a. 在中断、系统调用和异常的进入与退出时必须进行 CR3 操作以在页表副本之间切换（不过内核被中断时可以跳过）。对 CR3 的写入在约一百个周期的量级，并且在每次进入和退出时都需要  b. Percpu TSS 被映射到用户页表中，以允SYSCALL64 路径PTI 下工作。这没有直接运行时开销，但可以说它开启了某些定时攻击场景  c. 对于所有未同时映射到内核和用户页表的内核结构体，全局页被禁用。MMU 的这一特性允许不同进程共享映射内核的 TLB 条目。失去该特性意味着上下文切换后会有更多 TLB 未命中。实际性能损失非常小，但从未超1%  d. 进程上下文标识符（PCID）是一CPU 特性，允许我们在更改页表时（通过在更改页表时CR3 中设置特殊位）跳过刷新整TLB。这使得切换页表（在上下文切换，或内核进退出时）更便宜。但是，在支PCID 的系统上，上下文切换代码必须将两个用户和内核条目都从 TLB 中刷新。用PCID TLB 刷新被推迟到退出到用户空间时进行，以最小化开销。PCID/INVPCID 的详细内容见 intel.com/sdm  e. 必须为每个新进程填充用户空间页表。即使没PTI，共享的内核映射也是通过把顶层（PGD）条目复制到每个新进程来创建的。但是，有了 PTI，现在有*两个**内核映射：一个映射一切的内核页表中的映射，以及一个用entry/exit 结构体的映射。在 fork() 时，我们需要复制两者  f. 除了 fork() 时的复制外，每当对用于映射用户空间的 PGD 执行 set_pgd() 时，也必须更新用户空PGD。这确保内核和用户副本始终映射相同的用户空间内存  g. 在不支持 PCID 的系统上，每CR3 写入都会刷新整个 TLB。这意味着每次系统调用、中断或异常都会刷新 TLB  h. INVPCID 是一TLB 刷新指令，允许刷新非当前 PCID TLB 条目。某些系统支PCID，但不支INVPCID。在这些系统上，地址只能从当PCID TLB 中刷新。当刷新一个内核地址时，我们需要刷新所PCID，因此单次内核地址刷新将需要在下次使用每个 PCID 时进TLB 刷新CR3 写入

## 测试


为了测试 PTI 的稳定性，推荐以下测试流程，理想情况下并行执行所有这些：

1. 设置 CONFIG_DEBUG_ENTRY=y
2. 在多CPU 上循环运tools/testing/selftests/x86/ 的多个测试副本（不包MPX protection_keys）数分钟。这些测试经常暴露内核入口代码中的边界情况。一般来说，旧内核可能使这些测试本身崩溃，但它们绝不应使内核崩溃3. 以某种模式（top record）运“perf工具，生成许多频繁的、性能监控的非屏蔽中断（见 /proc/interrupts 中的 “NMI”）。这会执NMI 进入/退出代码，已知它会触发那些未预期被中断的代码路径中的缺陷，包括嵌套 NMI。使c会提NMI 速率，使用两-c 配合独立计数器会促使出现嵌套 NMI 以及更少确定性的行为```
	while true; do perf record -c 10000 -e instructions,cycles -a sleep 10; done
```
4. 启动一KVM 虚拟机5. 在支SYSCALL 指令的系统上运行 32 位二进制文件。这是一条测试较少的代码路径，需要额外审查
## 调试


PTI 中的缺陷会导致几种值得在此注意的崩溃特征
 - selftests/x86 代码失败。通常entry_64.S 中某个更冷僻角落的缺 - 早期启动时的崩溃，尤其是围绕 CPU 启动（bringup）时。这些由映射中的缺陷引起 - 第一次中断时的崩溃。由 entry_64.S 中的缺陷引起，例如搞错了页表切换。也由错误地映射 IRQ 处理程序入口代码引起 - 第一NMI 时的崩溃。NMI 代码独立于主中断处理程序，可能有不影响正常中断的缺陷。也由错误地映射 NMI 代码引起。中断入口代码的 NMI 必须非常小心，可能是运行 perf 时出现的崩溃的原因 - 第一次退出到用户空间时的内核崩溃。entry_64.S 的缺陷，或未能映射部分退出代码 - 第一次中断用户空间的中断时的崩溃。entry_64.S 中返回用户空间的路径有时与返回内核的路径分开 - 双重错误（double fault）：由于页错误之上又发生页错误而溢出内核栈。由在入口代码中触碰pti 映射的数据，或在调用pti 映射C 函数之前忘记切换到内CR3 引起 - 启动早期的用户空间段错误，有时表现为 mount(8) 无法挂载 rootfs。这些往往TLB 失效问题有关。通常失效了错误的 PCID，或以其他方式遗漏了一次失效
