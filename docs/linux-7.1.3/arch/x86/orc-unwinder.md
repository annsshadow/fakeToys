## ORC unwinder


## 概述


内核的 `CONFIG_UNWINDER_ORC` 选项启用了 ORC unwinder（栈回溯器），其概念与 DWARF unwinder 类似。不同之处在于 ORC 数据的格式比 DWARF 简单得多，这也使得 ORC unwinder 可以更简单、更快速。

ORC 数据由 objtool 生成的 unwind 表组成。其中包含由内核内 ORC unwinder 使用的带外（out-of-band）数据。objtool 通过先进行编译期栈元数据校验（`CONFIG_STACK_VALIDATION`）来生成 ORC 数据。在分析了某个 `.o` 文件的所有代码路径之后，它确定文件中每条指令地址处的栈状态信息，并将这些信息输出到 `.orc_unwind` 和 `.orc_unwind_ip` 段。

各个目标文件的 ORC 段在链接时合并，并在启动时进行排序和后处理。unwinder 利用生成的数据在运行时将指令地址与其栈状态关联起来。


## ORC 与帧指针


启用帧指针后，GCC 会向内核中的每个函数插入检测代码。内核的 `.text` 体积会增加约 3.2%，导致整体出现明显的内核范围性能下降。Mel Gorman [^1^]_ 的测量显示，某些工作负载下会出现 5-10% 的下降。

相比之下，ORC unwinder 对代码体积或运行时性能没有影响，因为其调试信息位于带外。因此，如果你禁用帧指针并启用 ORC unwinder，可以在全局范围内获得不错的性能提升，同时仍然拥有可靠的栈回溯。

Ingo Molnar 说：

  "注意，这不仅是性能上的提升，也是指令缓存局部性的提升：3.2% 的 `.text` 节省几乎直接转化为缓存占用相近规模的减少。对于缓存局部性处于临界状态的工作负载，这可以转化为更高的加速比。"

ORC 相比帧指针的另一个好处是，它可以可靠地跨越中断和异常进行栈回溯。基于帧指针的栈回溯有时会跳过被中断函数的调用者，如果被中断的是一个叶子函数，或者中断发生在帧指针被保存之前。

ORC unwinder 相比帧指针的主要缺点在于，它需要更多内存来存储 ORC unwind 表：根据内核配置不同，大约需要 2-4MB。


## ORC 与 DWARF


ORC 调试信息相对于 DWARF 本身的优势在于它更简单。它去掉了复杂的 DWARF CFI 状态机，也去掉了对不必要寄存器的跟踪。这使得 unwinder 可以简单得多，意味着更少的 bug，这对于关键任务的 oops 代码尤其重要。

更简单的调试信息格式还让 unwinder 比 DWARF 快得多，这对 perf 和 lockdep 很重要。在 Jiri Slaby [^2^]_ 的一项基础性能测试中，ORC unwinder 比树外的 DWARF unwinder 快约 20 倍。（注意：该测量是在加入一些性能优化之前进行的，那些优化使性能翻倍，因此相对 DWARF 的加速比可能接近 40 倍。）

ORC 数据格式与 DWARF 相比确实有一些缺点。ORC unwind 表占用的 RAM 比基于 DWARF 的 eh_frame 表多约 50%（在 x86 defconfig 内核上多 1.3MB）。

另一个潜在的缺点是，随着 GCC 的演进，可以想见 ORC 数据最终可能过于简单，以至于无法描述某些优化下的栈状态。但在我看来这不太可能，因为 GCC 会为它所做的任何异常栈调整保存帧指针，所以我认为我们真正只需要跟踪调用帧之间的栈指针和帧指针。但即便我们最终不得不跟踪 DWARF 所跟踪的所有寄存器，至少我们仍能控制格式，例如不需要复杂的状态机。


## ORC unwind 表的生成


ORC 数据由 objtool 生成。借助已有的编译期栈元数据校验功能，objtool 已经跟踪了所有代码路径，因此它已经拥有从头生成 ORC 数据所需的全部信息。所以从栈校验到 ORC 数据生成是一个简单的步骤。

也可以用一个简单的工具把 DWARF 转换为 ORC 数据来生成 ORC 数据。然而，由于内核大量使用 asm、内联 asm 以及诸如异常表之类的特殊段，这样的方案会是不完整的。

这可以通过在 `.S` 文件中使用 GNU 汇编器的 `.cfi` 注解、在 `.c` 文件中对内联 asm 使用自制的注解来为这些特殊代码路径手动添加注解来弥补。但在过去曾尝试过 asm 注解，结果发现难以维护。它们经常不正确/不完整，并且使代码更难阅读和更新。而从查看 glibc 代码来看，在 `.c` 文件中为内联 asm 添加注解可能更糟。

Objtool 仍然需要少量注解，但仅用于那些对栈做了异常操作（如入口代码）的代码。即便如此，所需的注解也远少于 DWARF 所需，因此它们比 DWARF CFI 注解更易维护。

因此，使用 objtool 生成 ORC 数据的优点在于，它能以极少的注解给出更准确的调试信息。它还能让内核免受工具链 bug 的影响——这些 bug 在内核中处理起来可能非常痛苦，因为我们常常不得不对旧版本工具链的问题进行多年的规避。

缺点在于，unwinder 现在依赖于 objtool 逆向 GCC 代码流的能力。如果 GCC 的优化变得过于复杂，objtool 无法跟踪，ORC 数据生成可能会停止工作或变得不完整。（值得注意的是，livepatch 已经存在对 objtool 跟踪 GCC 代码流能力的这种依赖。）

如果新版本的 GCC 推出了某些会破坏 objtool 的优化，我们可能需要重新审视当前的实现。一些可能的解决方案包括：请求 GCC 使这些优化更易处理、让 objtool 将 DWARF 作为额外输入、或者创建一个 GCC 插件来辅助 objtool 的分析。但目前，objtool 对 GCC 代码的跟踪相当好。


## Unwinder 实现细节


Objtool 通过集成编译期栈元数据校验功能来生成 ORC 数据，该功能在 `tools/objtool/Documentation/objtool.txt` 中有详细描述。在分析完某个 `.o` 文件的所有代码路径后，它创建一个 `orc_entry` 结构体数组，以及一个与该结构体数组并行的、与这些结构体相关联的指令地址数组，并分别将它们写入 `.orc_unwind` 和 `.orc_unwind_ip` 段。

出于性能原因，ORC 数据被拆分为两个数组，以使数据中可搜索的部分（`.orc_unwind_ip`）更紧凑。这两个数组在启动时并行排序。

通过使用运行时创建的快速查找表，性能得到进一步提升。该快速查找表将给定的地址与 `.orc_unwind` 表的一组索引范围关联起来，这样只需搜索表中很小的一个子集。


## 词源


Orc（兽人）是中世纪民间传说中可怕的造物，是矮人天然的敌人。类似地，ORC unwinder 是为对抗 DWARF 的复杂与缓慢而创建的。

"尽管兽人很少考虑一个问题的多种解法，但他们确实擅长把事情做成，因为他们是行动的生物，而非思考的生物。" [^3^]_ 类似地，与深奥的 DWARF unwinder 不同，真实的 ORC unwinder 不会把时间或 siloconic 精力浪费在解码变长、零扩展、无符号整数、字节编码、基于状态机的调试信息条目上。

类似于兽人经常挫败对手善意的计划，ORC unwinder 经常以粗暴、毫不留情的效率来解开（unravel）栈。

ORC 代表 Oops Rewind Capability（Oops 回退能力）。
