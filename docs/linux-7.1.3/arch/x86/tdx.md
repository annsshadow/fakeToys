
## Intel 信任域扩展（TDX

Intel 的信任域扩展（TDX）通过隔离客户机的寄存器状态并加密客户机内存，保护机密
客户VM 免受主机和物理攻击。在 TDX 中，一个运行于特殊模式下的专用模块位于主机
与客户机之间，管理客户机/主机的隔离
## TDX 主机内核支持


TDX 引入了一种称为安全仲裁模式（SEAM）的CPU 模式，以及一个由 SEAM 范围寄存（SEAMRR）指向的新的隔离区间。一个名为“TDX 模块”的、经CPU 证明的软件模块运于该新的隔离区间内，提供管理与运行受保护 VM 的功能
TDX 还利Intel 多密钥全内存加密（MKTME）为 VM 提供加密保护。TDX 保留部分 MKTME
KeyID 作为 TDX 私有 KeyID，这KeyID 只能SEAM 模式下访问。BIOS 负责划分传统
MKTME KeyID 涓?TDX KeyID銆。
TDX 模块能够被用来创建并运行受保VM 之前，它必须被加载到该隔离区间并正确
初始化。TDX 架构并不要求 BIOS 加载 TDX 模块，但内核假定它由 BIOS 加载
### TDX 启动期检

内核通过在启动期间检TDX 私有 KeyID 来检TDX
```

  [..] virt/tdx: BIOS enabled: private KeyID range: [16, 64)

```
### TDX 模块初始

内核通过新的 SEAMCALL 指令TDX 模块通信。TDX 模块实现SEAMCALL 叶子函数来允内核初始化它
如果 TDX 模块未被加载，SEAMCALL 指令会以一种特殊错误失败。在这种情况下，内核使模块初始化失败
```

  [..] virt/tdx: module not loaded

```
初始TDX 模块大约消1/256 的系RAM 大小，用TDX 内存的“元数据”。初始化这些
元数据以TDX 模块本身还需要额外的 CPU 时间。两者都不容小觑。内核在运行时按需
初始TDX 模块
除了初始TDX 模块外，在该 CPU 上发出任何其SEAMCALL 之前，必须在CPU 上完成一CPU 的初始化 SEAMCALL
用户可以查看 dmesg 来了TDX 模块是否已经初始化
如果 TDX 模块初始化成功，dmesg 会显示类似如下内```

  [..] virt/tdx: 262668 KBs allocated for PAMT
  [..] virt/tdx: TDX-Module initialized

```
如果 TDX 模块初始化失败，dmesg 也会显示其初始化失败
```

  [..] virt/tdx: TDX-Module initialization failed ...

```
### TDX 与其他内核组件的交互


#### TDX 内存策略


TDX 报告一份“可转换内存区域”（CMR）列表，告诉内核哪些内存TDX 兼容的。内核需（基CMR）构建一份作为“TDX 可用”内存的内存区域列表，并将这些区域传递给 TDX
模块。一旦完成，这些“TDX 可用”内存区域在模块的整个生命周期内即被固定
为简单起见，当前内核只是简单地保证页分配器中的所有页都是 TDX 内存。具体而言，内将核心内存管理（core-mm）中“在 TDX 模块初始化时刻”的所有系统内存用TDX 内存同时拒绝在内存热插拔中上线任何非 TDX 内存
#### 物理内存热插

注意，TDX 假定可转换内存在机器的运行期间始终物理存在。一个没bug BIOS 绝不
应当支持热移除任何可转换内存。此实现不处ACPI 内存移除，而是依赖 BIOS 正确行为
#### CPU 热插

TDX 模块要求在某CPU 上发出任何其SEAMCALL 之前，必须在CPU 上完成每 CPU 初始SEAMCALL。内核通过 CPU 热插拔框架，CPU 首次上线时执行必要的初始化
TDX 不支持物理（ACPI）CPU 热插拔。在机器启动期间，TDX 会在启用 TDX 之前验证所启动时就存在的逻辑 CPU 都是 TDX 兼容的。一个没bug BIOS 绝不应当支持物理 CPU 热添移除。当前内核不处理物理 CPU 热插拔，而是依赖 BIOS 正确行为
注意，TDX 可与 CPU 逻辑在线/离线配合工作，因此内核仍然允许逻辑 CPU 下线并再次上线
#### Erratum（勘误）


前几TDX 硬件存在一个勘误。对 TDX 私有内存缓存行的部分写入会静默地“毒化”该行随后的读取会消耗该毒化数据并产生机器检查（machine check）
部分写入是指一次小于缓存行的写事务落在内存控制器上。CPU 通过非临时写指令（如
MOVNTI）或经由 UC/WC 内存映射来完成这些写入。设备也可以通过 DMA 进行部分写入
理论上，一个内bug 可能TDX 私有内存进行部分写入并触发意外的机器检查。更有甚者，
机器检查代码会将这些呈现为“硬件错误”，而事实上它们是由软件触发的问题。但归根结底此问题很难被触发
如果平台存在此类勘误，内核会在机器检查处理程序中打印额外消息，告知用户该机器检可能是由 TDX 私有内存上的内核 bug 引起的
#### Kexec


当前，在上述勘误存在的情况下，kexec TDX 平台上无法工作。它在加kexec 内核映像
时失败。除此之外则正常工作
#### S3 及更深状态的交互


TDX 无法S3 及更深的状态中存活。当平台进入 S3 及更深状态时，硬件会复位并彻禁用 TDX。TDX 客户机与 TDX 模块都会被永久销毁
内核使用 S3 进行挂起到内存（suspend-to-ram），并使S4 及更深的状态进行休（hibernation）。当前，为简单起见，内核选择TDX S3 及休眠互斥
当启用了休眠支持时，内核会在早期启动期间禁用 TDX
```

  [..] virt/tdx: initialization failed: Hibernation support is enabled

```
添加 'nohibernate' 内核命令行参数以禁用休眠，从而能够使TDX
如果启用TDX，ACPI S3 会在内核早期启动期间被禁用。用户需要在 BIOS 中关TDX 才能
使用 S3
## TDX 瀹㈡埛鏈烘敮鎸?

由于主机无法直接访问客户机寄存器或内存，超级虚拟化管理程序（hypervisor）的许多
常规功能必须移入客户机。这是通过由客户机内核处理的虚拟化异常VE）来实现的VE
完全在客户机内核内部处理，但有些情况需要咨询超级虚拟化管理程序
TDX 包含新的、类似超级调用的机制，用于从客户机向超级虚拟化管理程序或 TDX 模块
通信
### 新的 TDX 异常


TDX 客户机的行为不同于裸机与传统 VMX 客户机。在 TDX 客户机中，本来正常的指令内存访问可能引发 #VE #GP 异常
标有 '*' 的指令会按条件引发异常。这些指令的细节将在下文中讨论
#### 基于指令#VE


- Port I/O (INS, OUTS, IN, OUT)
- HLT
- MONITOR, MWAIT
- WBINVD, INVD
- VMCALL
- RDMSR**,WRMSR**
- CPUID*

#### 基于指令#GP


- 所VMX 指令：INVEPT, INVVPID, VMCLEAR, VMFUNC, VMLAUNCH,
  VMPTRLD, VMPTRST, VMREAD, VMRESUME, VMWRITE, VMXOFF, VMXON
- ENCLS, ENCLU
- GETSEC
- RSM
- ENQCMD
- RDMSR**,WRMSR**

#### RDMSR/WRMSR 行为


MSR 访问行为分为三类
- 产生 #GP
- 产生 #VE
- “直接可用
一般而言GP MSR 不应在客户机中使用。使用它们很可能表明客户机中存在 bug。客户机
可能尝试用超级调用处#GP，但成功的可能性不大
#VE MSR 通常能够由超级虚拟化管理程序处理。客户机可以进行一次超级调用，超级虚拟化管理程序处#VE
“直接可用”类 MSR 不需要任何特殊的客户机处理。它们可能是通过MSR 直接透传到硬件，
或在 TDX 模块中陷入并处理来实现的。除了可能较慢之外，这些 MSR 看起来与在裸机上一工作
#### CPUID 行为


对于某些 CPUID 叶与子叶，CPUID 返回值（客户EAX/EBX/ECX/EDX 中）的虚拟化位域可由
超级虚拟化管理程序配置。对于此类情况，Intel TDX 模块架构定义了两种虚拟化类型
- 超级虚拟化管理程序控制客户机 TD 所见的值的位域
- 超级虚拟化管理程序将值配置为使得客户TD 要么看到其原生值，要么看到 0 值的
  位域。对于这些位域，超级虚拟化管理程序可以屏蔽掉原生值，但不*开*值
对于 TDX 模块不知道如何处理的 CPUID 叶与子叶，会产生一#VE。客户机内核可以通过
超级调用向超级虚拟化管理程序索取该值
### 内存访问上的 #VE


本质TDX 内存有两类：私有与共享。私有内存获得完整的 TDX 保护。其内容受保护，
防止来自超级虚拟化管理程序的访问。共享内存预期在客户机与超级虚拟化管理程序之共享，不获得完整TDX 保护
TD 客户机控制其内存访问被视为私有还是共享。它通过页表项中的一个位来选择行为。这
有助于确保客户机不会把敏感信息放入共享内存，从而暴露给不可信的超级虚拟化管理程序
#### 共享内存上的 #VE


对共享映射的访问可能引发 #VE。最终由超级虚拟化管理程序控制一次共享内存访问是引发 #VE，因此客户机必须小心，只引用那些它能够安全处#VE 的共享页。例如，客户应注意不要在读取 #VE 信息结构（TDG.VP.VEINFO.GET）之前，#VE 处理程序中访问共内存
共享映射的内容完全由超级虚拟化管理程序控制。客户机应仅将共享映射用于与
超级虚拟化管理程序的通信。共享映射绝不可用于像内核栈这样的敏感内存内容。一个很的经验法则是，应将超级虚拟化管理程序共享内存视为与映射到用户空间的内存同样对待超级虚拟化管理程序与用户空间都是完全不可信的
虚拟设备MMIO 被实现为共享内存。客户机必须小心，不要访问设MMIO 区域，除非它
同时准备好处#VE
#### 私有页上#VE


对私有映射的访问也可能引#VE。由于所有内核内存也都是私有内存，理论上内核可能
需要在任意内核内存访问上处#VE。这不可行，因此 TDX 客户机确保所有的客户机内在内核使用之前都已被“接受”（accepted）
固件在内核运行前预先接受（pre-accept）了适量内存（通常512M），以确保内核能在不遭遇 #VE 的情况下启动
超级虚拟化管理程序被允许单方面将已接受的页移动到“blocked”（已阻止）状态。然而，
如果它这样做，页访问不会产生 #VE，而是会引发一个“TD Exit”，需要超级虚拟化管理程序
处理该异常
### Linux #VE 处理程序


与页错误或缺页异常（#GP）一样，#VE 异常既可以被处理，也可以是致命的。通常，一未处理的用户空间 #VE 会导SIGSEGV。一个未处理的内#VE 会导致一oops
x86 上处理嵌套异常通常是一件棘手的事。一#VE 可能被一NMI 打断，而该 NMI 触发另一#VE，从而引发混乱。TDX #VE 架构预见了这种场景，并包含一个使其略不那么棘手的特性
#VE 处理期间，TDX 模块确保所有中断（包括 NMI）都被阻塞。该阻塞会一直保持，直到
客户机发起一TDG.VP.VEINFO.GET TDCALL。这使客户机能够控制何时可以递送中断或新的
#VE銆?
然而，客户机内核仍须小心，在阻塞生效期间避免可能引#VE 的动作（上文讨论过）。在
阻塞生效期间，任#VE 都会被提升为双重错误DF），这是不可恢复的
### MMIO 处理


在非 TDX VM 中，MMIO 通常通过给客户机一个在访问时会引发 VMEXIT 的映射来实现，然后由
超级虚拟化管理程序模拟该访问。这TDX 客户机中是不可能的，因为 VMEXIT 会把寄存状态暴露给主机。TDX 客户机不信任主机，也不能让其状态暴露给主机
TDX 中，MMIO 区域通常会在客户机中引发 #VE 异常。随后客户机 #VE 处理程序在客户机
内部模拟MMIO 指令，并将其转换为一次受控的、发往主机TDCALL，而不是将客户机状暴露给主机
x86 上的 MMIO 地址只是特殊的物理地址。理论上它们可以用任何访问内存的指令来访问然而，内核的指令解码方法有限。它只被设计用于解码类似 io.h 宏所生成的那些指令
通过其他手段（如结构体覆盖）进行MMIO 访问可能导致 oops
### 共享内存转换


所TDX 客户机内存在启动之初都是私有的。该内存不能被超级虚拟化管理程序访问。然而，
某些内核用户（如设备驱动）可能需要与超级虚拟化管理程序共享数据。为此，内存必须共享与私有之间转换。这可以使用一些现有的内存加密辅助函数来完成：

 - set_memory_decrypted() 将一段页范围转换为共享 - set_memory_encrypted() 将内存转换回私有
设备驱动是共享内存的主要使用者，但无需改动每一个驱动。DMA 缓冲区与 ioremap() 自动进行转换
TDX 对大多数 DMA 分配使用 SWIOTLB。SWIOTLB 缓冲区在启动时被转换为共享
对于一致DMA 分配，DMA 缓冲区在分配时即被转换。详情请查看 force_dma_unencrypted()
## 证明（Attestation

证明用于在向客户机提供密钥之前，向其他实体验TDX 客户机的可信度。例如，密钥服务可能希望使用证明来确认该客户机就是所需的那个，然后再释放加密密钥以挂载加密的根文件
系统或辅助驱动器
TDX 模块在客户机启动过程的不同阶段，使用构建期度量寄存器（MRTD）与运行时度量寄存器
（RTMR）记TDX 客户机的状态。与客户机初始配置和固件映像相关的度量记录在 MRTD
寄存器中。与初始状态、内核映像、固件映像、命令行选项、initrd、ACPI 表等相关的度记录RTMR 寄存器中。更多细节，例如，请参阅 TDX 虚拟固件设计规范的“TD Measurement一节。在 TDX 客户机运行时，证明过程用于对这些度量进行证明
证明过程包含两个步骤：TDREPORT 生成Quote 生成
TDX 客户机使TDCALL[TDG.MR.REPORT] TDX 模块获取 TDREPORT（TDREPORT_STRUCT）TDREPORT 是由 TDX 模块生成的定长数据结构，包含客户机特定的信息（如构建与启动度量）平台安全版本，以及用于保TDREPORT 完整性的 MAC。一个用户提供的 64 字节 REPORTDATA
作为输入被包含进 TDREPORT。通常它可以是证明服务提供的某nonce，从而使 TDREPORT 能够
被唯一验证。关TDREPORT 的更多细节可Intel TDX 模块规范的“TDG.MR.REPORT Leaf”一中找到
在获TDREPORT 之后，证明过程的第二步是将其发送给引用飞地（Quoting Enclave, QE）以
生成 Quote。TDREPORT 按设计只能在本地的平台上验证，因MAC 密钥绑定到该平台。为支持
TDREPORT 的远程验证，TDX 利用 Intel SGX Quoting Enclave 在本地验TDREPORT 并将转换为可远程验证Quote。将 TDREPORT 发送给 QE 的方法是实现相关的。证明软件可以选择
任何可用的通信通道（如 vsock TCP/IP）将 TDREPORT 发送给 QE 并接Quote
