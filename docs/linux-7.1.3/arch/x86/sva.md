
## 使用 ENQCMD 的共享虚拟寻址（SVA）


## 背景


共享虚拟寻址（SVA）允许处理器和设备使用相同的虚拟地址，从而避免软件将虚拟地址转换为物理
地址的需要。SVA 就是 PCIe 所称的共享虚拟内存（SVM）。

除了方便设备使用应用程序虚拟地址外，它还不需要为 DMA 固定（pin）页。PCIe 地址转换服务
（ATS）与页请求接口（PRI）一起，允许设备以与 CPU 处理应用程序缺页几乎相同的方式工作。更多
信息请参阅 PCIe 规范第 10 章：ATS 规范。

使用 SVA 需要平台支持 IOMMU。IOMMU 还需要支持 PCIe 特性 ATS 和 PRI。ATS 允许设备缓存虚拟地址
的转换结果。IOMMU 驱动使用 mmu_notifier() 支持来保持设备 TLB 缓存与 CPU 缓存的同步。当某个
虚拟地址的 ATS 查找失败时，设备应当使用 PRI 来请求将该虚拟地址分页装入 CPU 页表。设备必须
再次使用 ATS 以在使用前获取转换结果。

## 共享硬件工作队列


与单根 I/O 虚拟化（SR-IOV）不同，可扩展 I/O 虚拟化（SIOV）允许应用程序和虚拟机（VM）都使用
共享工作队列（SWQ）。这比可能导致利用率不足的硬分区资源具有更好的硬件利用率。为了允许硬件
区分由 SWQ 接口在硬件中执行的上下文，SIOV 使用进程地址空间 ID（PASID），这是由 PCIe SIG
定义的 20 位数。

PASID 值编码在来自设备的所有事务中。除了使用 PCIe 资源标识符（RID，即总线/设备/功能）之外，
这还允许 IOMMU 以每个 PASID 的粒度跟踪 I/O。


## ENQCMD


ENQCMD 是 Intel 平台上的一个新指令，它以原子方式向设备提交一个工作描述符。该描述符包含要执行
的操作、所有参数的虚拟地址、完成记录的虚拟地址，以及当前进程的 PASID（进程地址空间 ID）。

ENQCMD 以非发布（non-posted）语义工作，并在命令被硬件接受时带回状态。这使得提交者能够知道提交
是否需要重试，或者是否应提供其他设备特定的机制来实现公平性并确保向前推进。

ENQCMD 是确保应用程序可以直接向硬件提交命令、并允许硬件通过 PASID 的使用感知应用程序上下文
以执行 I/O 操作的粘合剂。

## 进程地址空间标记


一个新的线程作用域 MSR（IA32_PASID）提供了用户进程与硬件其余部分之间的连接。当应用程序首次
访问支持 SVA 的设备时，此 MSR 会被初始化为一个新分配的 PASID。该设备的驱动调用一个 IOMMU
特定的 API 来建立 DMA 和页请求的路由。

例如，Intel 数据流加速器（DSA）使用 iommu_sva_bind_device()，它将执行以下操作：

- 分配 PASID，并在 PASID 上下文项中编程进程页表（%cr3 寄存器）。
- 注册 mmu_notifier() 以跟踪任何页表失效，从而保持设备 TLB 的同步。例如，当某个页表项失效时，
  IOMMU 会将失效传播到设备 TLB。这将强制设备对该虚拟地址的任何未来访问都参与 ATS。如果 IOMMU
  以适当的响应表明某个页不存在，设备将在执行 I/O 之前通过 PCIe PRI 协议请求将该页分页装入。

此 MSR 作为“管理态（supervisor state）”由 XSAVE 特性集管理，以确保在上下文切换期间更新该 MSR。

## PASID 管理


内核必须代表每个将使用 ENQCMD 的进程分配一个 PASID，并将其编程到新的 MSR 中，以将进程标识传达
给平台硬件。ENQCMD 使用存储在此 MSR 中的 PASID 来标记来自该进程的请求。当用户使用 ENQCMD 指令
向设备提交工作描述符时，描述符中的 PASID 字段会自动填入来自 MSR_IA32_PASID 的值。来自设备的
DMA 请求也使用相同的 PASID 标记。平台 IOMMU 使用事务中的 PASID 来执行地址转换。IOMMU API 在
IOMMU 中建立相应的 PASID 项，使用的是 CPU 所使用的进程地址（例如 x86 中的 %cr3 寄存器）。

在任何应用程序线程可以与设备交互之前，必须在每个逻辑 CPU 上配置该 MSR。属于同一进程的线程共享
相同的页表，因此也共享相同的 MSR 值。

## PASID 生命周期管理


进程创建时，PASID 被初始化为 IOMMU_PASID_INVALID（-1）。

只有访问支持 SVA 的设备的进程才需要分配一个 PASID。此分配发生在进程打开/绑定一个支持 SVA 的
设备、但发现该进程没有 PASID 时。随后对同一设备或其他设备的绑定将共享同一个 PASID。

尽管 PASID 是通过打开设备分配给进程的，但它在进程的任何线程中都尚未处于活动状态。当某个线程
尝试使用 ENQCMD 向设备提交工作描述符时，它会惰性（lazy）地加载到 IA32_PASID MSR 中。

由于打开设备时分配给进程的 PASID 尚未被编程到 IA32_PASID MSR 中，首次访问将触发 #GP 故障。
Linux 的 #GP 处理程序注意到已经为该进程分配了 PASID，于是初始化 IA32_PASID MSR 并返回，以便
重新执行 ENQCMD 指令。

在 fork(2) 或 exec(2) 时，PASID 会从进程中移除，因为它不再拥有打开设备时所在的相同地址空间。

在 clone(2) 时，新任务共享相同的地址空间，因此将能够使用分配给该进程的 PASID。IA32_PASID 不会
被预先初始化，因为 PASID 值可能尚未分配，或者内核不知道此线程是否会访问设备，且清除的 IA32_PASID
MSR 通过 xstate 初始化优化减少了上下文切换开销。由于在 PASID 被分配给进程的 mm 之前创建的任何
线程上都必须要处理 #GP 故障，新创建的线程最好也以一致的方式对待。

由于在解绑时释放 PASID 并清除所有线程中的 IA32_PASID MSR 十分复杂，因此只在 mm 退出时惰性释放
PASID。

如果进程执行了设备文件描述符的 close(2) 以及设备 MMIO 门户（portal）的 munmap(2)，那么驱动将
解绑设备。对于任何访问过该设备的进程中的线程，PASID 在 PASID_MSR 中仍被标记为 VALID。但这
无害，因为没有 MMIO 门户它们就无法向设备提交新工作。

## 关系


 - 每个进程有多个线程，但只有一个 PASID。
 - 设备的硬件工作队列数量有限（约几十到几千个）。设备驱动负责管理分配硬件工作队列。
 - 单个 mmap() 将单个硬件工作队列映射为一个“门户”，每个门户映射到一个工作队列。
 - 对于一个进程所交互的每个设备，必须有一个或多个 mmap() 的门户。
 - 进程内的许多线程可以共享单个门户来访问单个设备。
 - 多个进程可以分别 mmap() 同一个门户，这种情况下它们仍然共享一个设备硬件工作队列。
 - 进程范围唯一的 PASID 被所有线程用来与所有设备交互。例如，不存在每个线程或每个线程<->设备
   对的 PASID。

## 常见问题


- 什么是 SVA/SVM？

共享虚拟寻址（SVA）允许 I/O 硬件和处理器在同一个地址空间中工作，即共享它。有些人称之为共享虚拟
内存（SVM），但 Linux 社区希望避免将其与已经在流通中的 POSIX 共享内存和 Secure Virtual Machines
（安全虚拟机）混淆。

- 什么是 PASID？

进程地址空间 ID（PASID）是一个 PCIe 定义的传输层数据包（TLP）前缀。PASID 是一个由 OS 分配和
管理的 20 位数。PASID 包含在平台和设备之间的所有事务中。

- 共享工作队列有何不同？

传统上，为了让用户空间应用程序与硬件交互，每个进程都需要一个独立的硬件实例。例如，考虑将 doorbell
作为向硬件通知待处理工作的机制。每个 doorbell 必须相隔 4k（或页大小）以实现进程隔离。这要求硬件
预留该空间并在 MMIO 中保留它。当线程数量变得相当大时，这无法扩展。硬件还管理共享工作队列（SWQ）
的队列深度，使用者无需跟踪队列深度。如果没有空间接受命令，设备将返回一个指示重试的错误。

用户应检查设备上的可延迟内存写（DMWr）能力，并仅在设备支持时才提交 ENQCMD。在新的 DMWr PCIe
术语中，设备需要支持 DMWr completer 能力。此外，它要求所有交换机端口支持 DMWr 路由，并且必须由
PCIe 子系统启用，很像 PCIe 原子操作的管理方式。

SWQ 允许硬件只在一个地址上分配。当与 ENQCMD 一起用于提交工作时，设备可以区分提交工作的进程，因为
它将包含分配给该进程的 PASID。这有助于设备扩展到大量进程。

- 这与用户空间设备驱动相同吗？

通过共享工作队列与设备通信比一个完整的用户空间驱动要简单得多。内核驱动完成硬件的所有初始化。用户
空间只需要关心提交工作和处理完成。

- 这与 SR-IOV 相同吗？

单根 I/O 虚拟化（SR-IOV）侧重于为虚拟化硬件提供独立的硬件接口。因此，它需要是一个几乎全功能的
接口，以支持传统的 BAR、通过 MSI-X 的中断空间及其自身的寄存器布局。虚拟功能（VF）由物理功能（PF）
驱动辅助。

可扩展 I/O 虚拟化基于 PASID 概念来创建用于虚拟化的设备实例。SIOV 需要主机软件辅助创建虚拟设备；
每个虚拟设备由一个 PASID 以及设备的总线/设备/功能表示。这允许设备硬件优化设备资源的创建，并可以
按需动态增长。SR-IOV 的创建和管理本质上非常静态。更多细节请参阅下面的参考。

- 为何不为每个应用创建一个虚拟功能？

创建 PCIe SR-IOV 类型的虚拟功能（VF）代价高昂。VF 需要为 PCI 配置空间和 MSI-X 等中断复制硬件。
诸如中断之类的资源必须在创建时静态划分给 VF，并且无法按需动态扩展。VF 并非完全独立于物理功能（PF）。
大多数 VF 需要来自 PF 驱动的某些通信和辅助。相反，SIOV 创建一个软件定义的设备，其中所有配置和控制
方面都通过慢速路径中介。工作的提交和完成则不发生任何中介。

- 这支持虚拟化吗？

ENQCMD 可以在客户机 VM 内部使用。在这些情况下，VMM 帮助建立转换表，以从客户机 PASID 转换到主机
PASID。更多细节请参阅 ENQCMD 指令集参考。

- 内存需要被固定吗？

当设备支持 SVA 以及支持此类设备的平台硬件（如 IOMMU）时，无需为 DMA 目的固定内存。支持 SVA 的设备
还支持其他可以消除内存固定需求的 PCIe 特性。

设备 TLB 支持 - 设备在使用前通过地址转换服务（ATS）请求向 IOMMU 查找地址。如果映射存在但 OS 尚未
分配页，IOMMU 硬件返回不存在映射。

设备通过页请求接口（PRI）请求映射虚拟地址。一旦 OS 成功完成映射，它将响应返回给设备。设备再次请求
转换并继续。

IOMMU 与 OS 协作管理页表与设备的一致性。在移除页时，它与设备交互以移除任何可能已在 OS 移除映射之前
被缓存的设备 TLB 项。
