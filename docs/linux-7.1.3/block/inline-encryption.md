

## 内联加密


## 背景


内联加密硬件在逻辑上位于内存与磁盘之间，能够在数据进出磁盘时对其加/解密。对于每个 I/O 请求，软件可以精确控制内联加密硬件将如何对数据进行加/解密，包括密钥、算法、数据单元大小（加/解密的粒度）以及数据单元编号（一个决定初始化向量的值）。

某些内联加密硬件直接接受所有加密参数（包括原始密钥）于底层 I/O 请求中。然而，大多数内联加密硬件则具有固定数量的“密钥槽（keyslot）”，并要求先把密钥、算法与数据单元大小编程进一个密钥槽。然后每个底层 I/O 请求只包含密钥槽索引与数据单元编号。

注意，内联加密硬件与传统加密加速器（通过内核 crypto API 支持）非常不同。传统加密加速器操作于内存区域，而内联加密硬件操作于 I/O 请求。因此，内联加密硬件需要由块层（block layer）管理，而非内核 crypto API。

内联加密硬件也与“自加密驱动器（self-encrypting drives）”（如基于 TCG Opal 或 ATA Security 标准的驱动器）非常不同。自加密驱动器不提供对加密的细粒度控制，也不提供验证所得密文正确性的方法。内联加密硬件提供对加密的细粒度控制，包括为每个扇区选择密钥与初始化向量，并且可以被测试以验证正确性。

## 目标


我们希望在内核中支持内联加密。为了让测试更容易，我们还希望在实际内联加密硬件缺失时能回退到内核 crypto API。我们还希望内联加密能用于 device-mapper 与 loopback 这类层叠设备（即我们希望能够使用底层设备的内联加密硬件（若存在），否则回退到 crypto API 的加/解密）。

## 约束与注意事项


- 我们需要一种方式，让上层（例如文件系统）为 bio 指定一个用于加/解密该 bio 的加密上下文（encryption context），并且设备驱动（例如 UFSHCD）在处理请求时需要能够使用那个加密上下文。加密上下文也会给 bio 合并引入约束；块层需要知晓这些约束。

- 不同的内联加密硬件支持不同的算法、支持的数据单元大小、最大数据单元编号等。我们称这些属性为“加密能力（crypto capabilities）”。我们需要一种方式，让设备驱动以通用的方法把加密能力告知上层。

- 内联加密硬件通常（但不总是）要求在使用前先把密钥编程进密钥槽。由于编程密钥槽可能较慢，且密钥槽数量可能不多，我们不应为每个 I/O 请求都编程密钥，而应追踪哪些密钥在密钥槽中，并尽可能复用已编程的密钥槽。

- 上层通常为加密密钥定义一个特定的生命周期终点，例如当某个加密目录被锁定时，或当某个加密映射被拆除时。在这些时刻，密钥会从内存中被清除。我们必须提供一种方式，让上层也能把密钥从它们所在的任何密钥槽中逐出（evict）。

- 在可能的情况下，device-mapper 设备必须能够直通其底层设备的内联加密支持。然而，device-mapper 设备自身拥有密钥槽是没有意义的。

## 基本设计


我们引入 `struct blk_crypto_key` 来表示一个内联加密密钥以及它将如何被使用。这包括密钥的类型（raw 或 hardware-wrapped）；密钥的实际字节；密钥的大小；该密钥将与之配合使用的算法与数据单元大小；以及表示该密钥将配合使用的最大数据单元编号所需的字节数。

我们引入 `struct bio_crypt_ctx` 来表示一个加密上下文。它包含一个数据单元编号与一个指向 blk_crypto_key 的指针。我们向 `struct bio` 与 `struct request` 添加指向 bio_crypt_ctx 的指针；这允许块层的使用者（例如文件系统）在创建 bio 时提供一个加密上下文，并让它沿着栈向下传递，供块层与设备驱动处理。注意，加密上下文并不显式说明要加密还是解密，因为这由 bio 的方向隐式决定：WRITE 表示加密，READ 表示解密。

我们还引入 `struct blk_crypto_profile` 来包含某个特定内联加密设备的所有通用内联加密相关状态。blk_crypto_profile 是内联加密硬件的驱动向高层通告其加密能力、并向高层提供某些函数（例如编程与逐出密钥的函数）的途径。每个想要支持内联加密的设备驱动都将构造一个 blk_crypto_profile，然后把它关联到磁盘的 request_queue。

blk_crypto_profile 还管理硬件的密钥槽（在适用时）。这发生在块层中，这样块层的使用者只需指定加密上下文，而完全不需要了解密钥槽，设备驱动也无需关心密钥槽管理的大部分细节。

具体来说，对于每个密钥槽，块层（通过 blk_crypto_profile）追踪该密钥槽包含哪个 blk_crypto_key（若有），以及有多少在途的 I/O 请求正在使用它。当块层为一个带有加密上下文的 bio 创建 `struct request` 时，它会尽可能抓取一个已经包含该密钥的密钥槽。否则它会等待一个空闲密钥槽（未被任何 I/O 使用的密钥槽），然后用设备驱动提供的函数把密钥编程进最近最少使用的空闲密钥槽。在这两种情况下，所得的密钥槽都被存入请求的 `crypt_keyslot` 字段，设备驱动可以在此访问它，并在请求完成后释放。

`struct request` 还包含一个指向原始 bio_crypt_ctx 的指针。请求可以由多个 bio 构建，而块层在尝试合并 bio 与请求时必须把加密上下文考虑在内。要让两个 bio/请求被合并，它们必须具有兼容的加密上下文：要么都未加密，要么都用相同的密钥与连续的数据单元编号加密。只保留请求中第一个 bio 的加密上下文，因为其余 bio 已被验证与第一个 bio 合并兼容。

为了让内联加密能用于基于 request_queue 的层叠设备，当一个请求被克隆时，它的加密上下文也被一并克隆。当克隆的请求被提交时，它会像往常一样被处理；这包括在需要时从克隆的目标设备获取一个密钥槽。

## blk-crypto-fallback


希望上层（例如文件系统）的内联加密支持能够在没有真实内联加密硬件的情况下被测试，块层的密钥槽管理逻辑也同样如此。同时也希望上层只是始终使用内联加密，而不必以多种方式实现加密。

因此，我们还引入了 **blk-crypto-fallback**，它是使用内核 crypto API 实现的内联加密。blk-crypto-fallback 内建在块层中，因此无需任何特殊设置即可在任何块设备上工作。本质上，当一个带有加密上下文的 bio 被提交到一个不支持该加密上下文的 block_device 时，块层将使用 blk-crypto-fallback 来处理该 bio 的加/解密。

对于加密，数据不能就地加密，因为调用方通常依赖它保持未被修改。取而代之，blk-crypto-fallback 分配弹跳页（bounce pages），用这些弹跳页填充一个新的 bio，把数据加密进这些弹跳页，然后提交那个“弹跳” bio。当弹跳 bio 完成时，blk-crypto-fallback 完成原始的 bio。如果原始 bio 过大，可能需要多个弹跳 bio；详情请参见代码。

对于解密，blk-crypto-fallback 用自身的完成回调（`bi_end_io`）与私有数据（`bi_private`）“包装”bio 的完成回调与私有数据，取消 bio 的加密上下文，然后提交该 bio。如果读操作成功完成，blk-crypto-fallback 恢复 bio 原始的完成回调与私有数据，然后使用内核 crypto API 就地解密 bio 的数据。解密发生在一个工作队列（workqueue）中，因为它可能会睡眠。之后，blk-crypto-fallback 完成该 bio。

在这两种情况下，blk-crypto-fallback 提交的 bio 都不再带有加密上下文。因此，下层只能看到标准的未加密 I/O。

blk-crypto-fallback 也定义了自己的 blk_crypto_profile，并拥有自己的“密钥槽”；它的密钥槽包含 `struct crypto_skcipher` 对象。这样做的原因有二。首先，它允许在没有真实内联加密硬件的情况下测试密钥槽管理逻辑。其次，与实际内联加密硬件类似，crypto API 也不在请求中直接接受密钥，而是要求提前设置密钥，且设置密钥的代价可能很高；此外，由于 crypto_skcipher 获取锁，分配 crypto_skcipher 根本不可能发生在 I/O 路径上。因此，密钥槽的概念对 blk-crypto-fallback 仍然有意义。

注意，无论使用真实内联加密硬件还是 blk-crypto-fallback，写入磁盘的密文（因而数据的磁盘格式）都将是相同的（假设被使用算法的内联加密硬件实现与内核 crypto API 实现都符合规范并正确工作）。

blk-crypto-fallback 是可选的，由 `CONFIG_BLK_INLINE_ENCRYPTION_FALLBACK` 内核配置选项控制。

## 提供给块层使用者的 API


`blk_crypto_config_supported()` 允许用户提前检查在某个特定 block_device 上使用特定加密设置的内联加密是否会工作——无论是通过硬件还是通过 blk-crypto-fallback。该函数接受一个 `struct blk_crypto_config`，它类似于 blk_crypto_key，但省去了密钥的实际字节，而只包含了算法、数据单元大小等。在 blk-crypto-fallback 被禁用时，此函数可能很有用。

`blk_crypto_init_key()` 允许用户初始化一个 blk_crypto_key。

用户必须在某个 block_device 上真正开始使用一个 blk_crypto_key 之前调用 `blk_crypto_start_using_key()`（即使之前调用过 `blk_crypto_config_supported()`）。这是用来在需要时对 blk-crypto-fallback 进行初始化的。它不可从数据路径调用，因为这可能需要分配资源，而那样的情况下可能发生死锁。

接下来，要把一个加密上下文附加到 bio 上，用户应当调用 `bio_crypt_set_ctx()`。该函数在给定 blk_crypto_key 与将用于加/解密的数据单元编号的情况下，分配一个 bio_crypt_ctx 并将其附加到 bio 上。用户无需担心之后释放 bio_crypt_ctx，因为那会在 bio 被释放或重置时自动发生。

要提交一个使用内联加密的 bio，用户必须调用 `blk_crypto_submit_bio()` 而不是通常的 `submit_bio()`。如果底层驱动支持内联加密，这将把 bio 提交给底层驱动；否则会在把普通 bio 提交给底层驱动之前调用 blk-crypto 的回退例程。

最后，当在某个 block_device 上用完一个 blk_crypto_key 的内联加密后，用户必须调用 `blk_crypto_evict_key()`。这确保该密钥被从其可能被编程进去的所有密钥槽中逐出，并从它可能链接进去的任何内核数据结构中解除链接。

总之，对于块层的使用者而言，blk_crypto_key 的生命周期如下：

1. `blk_crypto_config_supported()`（可选）
2. `blk_crypto_init_key()`
3. `blk_crypto_start_using_key()`
4. `bio_crypt_set_ctx()`（可能多次）
5. `blk_crypto_evict_key()`（在所有 I/O 完成后）
6. 将 blk_crypto_key 清零（这没有专门的函数）

如果一个 blk_crypto_key 被用在多个 block_device 上，那么 `blk_crypto_config_supported()`（若使用）、`blk_crypto_start_using_key()` 与 `blk_crypto_evict_key()` 必须在每个 block_device 上调用。

## 提供给设备驱动的 API


想要支持内联加密的设备驱动必须在其设备的 request_queue 中建立好一个 blk_crypto_profile。为此，它首先必须调用 `blk_crypto_profile_init()`（或其资源管理变体 `devm_blk_crypto_profile_init()`），并提供密钥槽的数量。

接下来，它必须通过设置 blk_crypto_profile 中的字段来通告其加密能力，例如 `modes_supported` 与 `max_dun_bytes_supported`。

然后它必须设置 blk_crypto_profile 的 `ll_ops` 字段中的函数指针，以告诉上层如何控制内联加密硬件，例如如何编程与逐出密钥槽。大多数驱动都需要实现 `keyslot_program` 与 `keyslot_evict`。详情请参见 `struct blk_crypto_ll_ops` 的注释。

一旦驱动向某个 request_queue 注册了一个 blk_crypto_profile，该驱动通过这个队列收到的 I/O 请求就可能带有加密上下文。所有加密上下文都将与 blk_crypto_profile 中声明的加密能力兼容，因此驱动无需担心处理不支持的请求。此外，如果在 blk_crypto_profile 中声明了非零数量的密钥槽，那么所有带有加密上下文的 I/O 请求也都会有一个已经用相应密钥编程好的密钥槽。

如果驱动实现了运行时挂起（runtime suspend），并且其 blk_crypto_ll_ops 在设备运行时挂起时无法工作，那么驱动还必须设置 blk_crypto_profile 的 `dev` 字段，使其指向将在任何底层操作被调用之前被恢复的 `struct device`。

如果存在内联加密硬件丢失其密钥槽内容的情况（例如设备重置），驱动必须处理密钥槽的重新编程。为此，驱动可以调用 `blk_crypto_reprogram_all_keys()`。

最后，如果驱动使用的是 `blk_crypto_profile_init()` 而非 `devm_blk_crypto_profile_init()`，那么它负责在不再需要该 crypto profile 时调用 `blk_crypto_profile_destroy()`。

## 层叠设备


像 dm-rq 这样基于请求队列、希望支持内联加密的层叠设备，需要为它们的 request_queue 创建自己的 blk_crypto_profile，并暴露它们所选择的任何功能。当一个层叠设备想要把该请求的一个克隆传递给另一个 request_queue 时，blk-crypto 会视情况初始化并准备该克隆。

## 内联加密与 blk 完整性之间的交互


在本补丁撰写之时，还没有真正同时支持这两个特性的硬件。然而，这些特性确实会相互影响，而且让它们同时正确工作并非完全平凡。具体而言，当一个 WRITE bio 想要在一个同时支持这两个特性的设备上使用内联加密时，该 bio 将指定一个加密上下文，之后计算其完整性信息（使用明文数据，因为加密将在数据写入时发生），然后把数据与完整性信息发送给设备。显然，完整性信息必须在数据被加密之前被验证。数据被加密之后，设备绝不能存储它与明文数据一起收到的完整性信息，因为那可能泄露有关明文数据的信息。因此，它必须根据密文数据重新生成完整性信息，并改而将其存储到磁盘上。存储明文数据的完整性信息的另一个问题是，它会根据是存在硬件内联加密支持还是使用了内核 crypto API 回退，来改变磁盘格式（因为如果使用了回退，设备将收到密文的完整性信息，而非明文的）。

因为还没有真正的相关硬件，谨慎起见可以假设硬件实现可能无法一起正确实现这两个特性，并暂时禁止这种组合。每当一个设备支持完整性时，内核将假装该设备不支持硬件内联加密（通过把该设备 request_queue 中的 blk_crypto_profile 设为 NULL）。当 crypto API 回退被启用时，这意味着所有带有加密上下文的 bio 都将使用回退，I/O 将如常完成。当回退被禁用时，带有加密上下文的 bio 将以失败告终。


## 硬件包装密钥


### 动机与威胁模型


Linux 存储加密（dm-crypt、fscrypt、eCryptfs 等）传统上依赖原始加密密钥存在于内核内存中，以便能够执行加密。这传统上不被视为问题，因为在进行离线攻击时密钥不会存在——而离线攻击正是存储加密旨在防护的主要攻击类型。

然而，人们越来越希望也能保护用户数据免受其它类型的攻击（在可能的范围内），包括：

- 冷启动攻击（cold boot attacks），攻击者物理接触系统后突然断电，然后立即转储系统内存以提取最近在用的加密密钥，再用这些密钥解密磁盘上的用户数据。

- 在线攻击，攻击者能够读取内核内存而未完全攻陷系统，随后进行离线攻击，任何被提取的密钥都可用于解密磁盘上的用户数据。此类在线攻击的一个例子是：攻击者能够在系统上运行一些代码，利用类似 Meltdown 的漏洞，但无法提升权限。

- 在线攻击，攻击者完全攻陷系统，但其数据外泄在时间上和/或带宽上受到显著限制，因此为了完整外泄数据，他们需要提取加密密钥用于后续的离线攻击。

硬件包装密钥（hardware-wrapped keys）是内联加密硬件的一项特性，旨在（在可能的范围内）保护用户数据免受上述攻击，同时不引入诸如最大密钥数量之类的限制。

注意，要**完全**保护用户数据免受这些攻击是不可能的。即使在攻击者“只是”获得了对内核内存的读访问的攻击中，他们仍能提取内存中存在的任何用户数据，包括加密文件的明文页缓存页。这里的重点只是保护加密密钥，因为它们会立即让任何后续离线攻击获得**所有**用户数据的访问权，而不仅仅是其中一部分（而那“一部分”中具体包含哪些数据可能不受攻击者控制）。

### 方案概览


内联加密硬件通常有“密钥槽”，软件可以把供硬件使用的密钥编程进去；密钥槽的内容通常无法被软件读回。因此，如果内核在把密钥编程进密钥槽后简单地抹除它自己持有的密钥副本，此后仅通过密钥槽编号来引用它们，上述安全目标就可以实现。

然而，那种朴素的做法会遇到几个问题：

- 它把已解锁密钥的数量限制为密钥槽的数量，而这通常是一个较小的数字。在全系统只有一个加密密钥（例如全盘加密密钥）的情况下，这还可以容忍。然而，一般而言可能存在许多已登录用户拥有许多不同的密钥，和/或许多运行中的应用拥有应用特定的加密存储区。如果使用了基于文件的加密（例如 fscrypt），这一点尤其明显。

- 内联加密引擎通常在存储控制器（通常是 UFS 或 eMMC）被重置时会丢失其密钥槽的内容。重置存储控制器是一种标准的错误恢复流程，会在某些类型的存储错误发生时执行，而这类错误可能随时发生。因此，当使用内联加密时，操作系统必须始终准备好在无需用户干预的情况下重新编程密钥槽。

因此，对内核而言，仍然需要一种在不实际持有原始密钥本身的情况下“提醒”硬件某个密钥的方法。

次要一些的是，也希望原始密钥根本不对软件可见，即使在最初解锁时也是如此。这将确保系统内存的只读式攻陷永远不会允许把某个密钥提取出去在系统之外使用，即使它发生在某个密钥正被解锁时。

为了解决所有这些问题，一些内联加密硬件的厂商让他们的硬件支持**硬件包装密钥（hardware-wrapped keys）**。硬件包装密钥是只能由硬件（要么由内联加密硬件自身，要么由一个能够直接向内联加密硬件供给密钥的专用硬件模块）解包（解密）并使用的加密密钥。

（我们称其为“硬件包装密钥”而非简单的“包装密钥”，是为了在可能存在其它类型包装密钥（例如基于文件的加密中）的情况下增加一些清晰度。密钥包装是一种常用的技术。）

包装（加密）硬件包装密钥的密钥是一个硬件内部的密钥，从不暴露给软件；它要么是一个持久密钥（“长期包装密钥”），要么是一个每次启动的密钥（“临时包装密钥”）。密钥的长期包装形式是最初被解锁的形式，但一旦它被转换为临时包装密钥，就会从内存中抹除。正在使用的硬件包装密钥总是临时包装的，而非长期包装的。

由于内联加密硬件只能用于加密/解密磁盘上的数据，硬件还包含了一层间接：它不直接使用解包后的密钥进行内联加密，而是从中派生出一个内联加密密钥和一个“软件密钥（software secret）”。软件可以使用“软件密钥”来完成无法使用内联加密硬件的任务，例如文件名加密。软件密钥不受内存攻陷保护。

### 密钥层级


```

                       Hardware-wrapped key
                                |
                                |
                          <Hardware KDF>
                                |
                  -----------------------------
                  |                           |
        Inline encryption key           Software secret

```
其组成部分为：

- **Hardware-wrapped key（硬件包装密钥）**：硬件 KDF（密钥派生函数）的密钥，以临时包装形式存在。密钥包装算法是硬件实现细节，不影响内核操作，但推荐使用像 AES-256-GCM 这样强认证加密算法。

- **Hardware KDF（硬件 KDF）**：硬件在解包包装密钥后用来派生子密钥的 KDF（密钥派生函数）。硬件对 KDF 的选择不影响内核操作，但出于测试目的需要被知晓，并且假设其至少具有 256 位的安全强度。所有已知的硬件都使用带 AES-256-CMAC 的 SP800-108 KDF 计数器模式，并选用特定的 label 与 context；新硬件应当使用这个已经过审查的 KDF。

- **Inline encryption key（内联加密密钥）**：一个派生的密钥，硬件直接供给内联加密硬件的某个密钥槽，而不暴露给软件。在所有已知硬件中，这始终是一个 AES-256-XTS 密钥。不过，原则上也可以支持其它加密算法。硬件必须为每个受支持的加密算法派生不同的子密钥。

- **Software secret（软件密钥）**：一个派生的密钥，硬件将其返回给软件，以便软件能把它用于无法使用内联加密的加密任务。这个值在密码学上与内联加密密钥相隔离，即知道其一不会泄露另一个（KDF 保证了这一点）。目前软件密钥总是 32 字节，因此适用于需要最高 256 位安全强度的加密应用。某些用例（例如全盘加密）不会需要软件密钥。

示例：在 fscrypt 的情况下，fscrypt 主密钥（保护某组特定加密目录的密钥）被做成硬件包装的。内联加密密钥被用作文件内容加密密钥，而软件密钥（而非主密钥本身）被用于为 fscrypt 的 KDF（HKDF-SHA512）提供密钥，以派生其它子密钥，例如文件名加密密钥。

注意，目前该设计假设每个硬件包装密钥对应单一的内联加密密钥，不再做进一步的密钥派生。因此，在 fscrypt 的情况下，目前硬件包装密钥只与“内联加密优化”设置兼容，后者对每个加密策略使用一个文件内容加密密钥，而非每个文件一个。该设计可以扩展为让硬件使用沿存储栈下传的每文件 nonce 派生每文件密钥，事实上某些硬件已经支持这一点；未来计划通过添加相应的内核支持来消除这一限制。

### 内核支持


内核块层的内联加密支持（“blk-crypto”）已经扩展为在硬件可用时，支持以硬件包装密钥作为原始密钥的替代。其工作方式如下：

- 在 `struct blk_crypto_profile` 的加密能力中添加了一个 `key_types_supported` 字段。这让设备驱动可以声明它们支持原始密钥、硬件包装密钥，或两者都支持。

- `struct blk_crypto_key` 现在可以包含一个硬件包装密钥作为原始密钥的替代；向 `struct blk_crypto_config` 添加了一个 `key_type` 字段，以区分不同的密钥类型。这让 blk-crypto 的使用者能以与使用原始密钥非常相似的方式，使用硬件包装密钥对数据进行加/解密。

- 添加了一个新的方法 `blk_crypto_ll_ops::derive_sw_secret`。支持硬件包装密钥的设备驱动必须实现此方法。blk-crypto 的使用者可以调用 `blk_crypto_derive_sw_secret()` 来访问此方法。

- 硬件包装密钥的编程与逐出通过 `blk_crypto_ll_ops::keyslot_program` 与 `blk_crypto_ll_ops::keyslot_evict` 进行，就像对原始密钥一样。如果一个驱动支持硬件包装密钥，那么它必须处理传给这些方法的硬件包装密钥。

blk-crypto-fallback 不支持硬件包装密钥。因此，硬件包装密钥只能与真实的内联加密硬件一起使用。

以上所有内容只涉及临时包装形式的硬件包装密钥。为了一开始就获得这样的密钥，已经添加了新的块设备 ioctl，提供了一个用于创建与准备此类密钥的通用接口：

- `BLKCRYPTOIMPORTKEY` 把一个原始密钥转换为长期包装形式。它接受一个指向 `struct blk_crypto_import_key_arg` 的指针。调用方必须把 `raw_key_ptr` 与 `raw_key_size` 设为要导入的原始密钥的指针与大小（字节数）。成功时，`BLKCRYPTOIMPORTKEY` 返回 0，并把所得的长期包装密钥 blob 写入由 `lt_key_ptr`（最大大小为 `lt_key_size`）指向的缓冲区。它还会把 `lt_key_size` 更新为该密钥的实际大小。失败时，它返回 -1 并设置 errno。errno 为 `EOPNOTSUPP` 表示该块设备不支持硬件包装密钥。errno 为 `EOVERFLOW` 表示输出缓冲区没有足够空间容纳该密钥 blob。

- `BLKCRYPTOGENERATEKEY` 类似于 `BLKCRYPTOIMPORTKEY`，但它让硬件生成密钥，而非导入一个。它接受一个指向 `struct blk_crypto_generate_key_arg` 的指针。

- `BLKCRYPTOPREPAREKEY` 把一个密钥从长期包装形式转换为临时包装形式。它接受一个指向 ``struct blk_crypto_prepare_key_arg` 的指针。调用方必须把 `lt_key_ptr`` 与 `lt_key_size` 设为要转换的长期包装密钥 blob 的指针与大小（字节数）。成功时，`BLKCRYPTOPREPAREKEY` 返回 0，并把所得的临时包装密钥 blob 写入由 `eph_key_ptr`（最大大小为 `eph_key_size`）指向的缓冲区。它还会把 `eph_key_size` 更新为该密钥的实际大小。失败时，它返回 -1 并设置 errno。errno 值 `EOPNOTSUPP` 与 `EOVERFLOW` 的含义与 `BLKCRYPTOIMPORTKEY` 中相同。errno 为 `EBADMSG` 表示该长期包装密钥无效。

用户空间需要一次性使用 `BLKCRYPTOIMPORTKEY` 或 `BLKCRYPTOGENERATEKEY` 创建一个密钥，然后在每次该密钥被解锁并加入内核时都使用 `BLKCRYPTOPREPAREKEY`。注意这些 ioctl 与原始密钥无关；它们只用于硬件包装密钥。

### 可测试性


硬件 KDF 与内联加密本身都是定义良好的算法，除了解包后的密钥以外不依赖任何秘密。因此，如果解包后的密钥为软件所知，这些算法就可以在软件中复现，以验证内联加密硬件写入磁盘的密文。

然而，解包后的密钥只有在使用了“import”功能时才会为软件所知。“generate”情况下（由硬件自行生成密钥）无法 proper 测试。因此“generate”模式的正确运行依赖于硬件 RNG 及其用于生成密钥的使用的安全性与正确性，以及“import”模式的测试，因为后者应当覆盖除密钥生成外的所有部分。

关于在“import”模式下验证写入磁盘密文的测试示例，请参见 xfstests 中的 fscrypt 硬件包装密钥测试，或 `Android's vts_kernel_encryption_test <https://android.googlesource.com/platform/test/vts-testcase/kernel/+/refs/heads/main/encryption/>`_。
