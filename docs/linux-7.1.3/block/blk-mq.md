
## 多队列块 IO 排队机制（blk-mq）


多队列块 IO 排队机制是一个 API，用于使快速存储设备通过排队并同时向块设备提交
IO 请求来实现海量每秒输入/输出操作数（IOPS），从而受益于现代存储设备提供的
并行性。

## 简介


### 背景


从内核开发之初，机械硬盘就是事实上的标准。块 IO 子系统旨在为这些具有较高
随机访问代价的设备取得尽可能好的性能，瓶颈在于机械运动部件，比存储栈上的
任何一层都慢得多。这类优化技术的一个例子是根据硬盘磁头的当前位置对读/写
请求进行排序。

然而，随着没有机械部件、没有随机访问代价且能够进行高并行访问的固态硬盘和
非易失性存储器的发展，栈的瓶颈已经从存储设备转移到操作系统。为了利用这些
设备设计中的并行性，引入了多队列机制。

先前的设计使用单个队列存储块 IO 请求，并配一把单一锁。在 SMP 系统中它扩展性
不好，因为存在缓存中的脏数据，以及多个处理器共用一把锁的瓶颈。当不同进程
（或同一进程迁移到不同 CPU）想要执行块 IO 时，这种设置还会遭遇拥塞。blk-mq
API 取而代之，生成多个队列，每个队列具有 CPU 本地的独立入口点，从而不再需要
锁。下一节（`Operation`_）将更深入地解释其工作原理。

### 操作


当用户空间对块设备执行 IO（例如读取或写入文件）时，blk-mq 会采取行动：它将
存储并管理对块设备的 IO 请求，充当于用户空间（以及文件系统，如果存在）和
块设备驱动程序之间的中间件。

blk-mq 有两组队列：软件暂存队列和硬件派发队列。当请求到达块层时，它会尝试
尽可能短的路径：将其直接发送到硬件队列。但是，有两种情况它可能不会这样做：
如果该层挂载了 IO 调度器，或者我们想尝试合并请求。在这两种情况下，请求都会被
发送到软件队列。

然后，在请求被软件队列处理后，它们会被放到硬件队列中，这是硬件可以直接访问
以处理这些请求的第二阶段队列。但是，如果硬件没有足够资源接受更多请求，blk-mq
会将这些请求放在一个临时队列中，待硬件具备能力时再发送。

#### 软件暂存队列


块 IO 子系统在软件暂存队列（由 struct blk_mq_ctx 表示）中添加请求，以防它们
没有被直接发送到驱动程序。一个请求是一个或多个 BIO。它们通过数据结构
struct bio 到达块层。块层随后会从中构建一个新的结构，即用于与设备驱动程序
通信的 struct request。每个队列都有自己的锁，队列数量按每 CPU 或每节点
的基准定义。

暂存队列可用于合并相邻扇区的请求。例如，对扇区 3-6、6-7、7-9 的请求可以合并为
对 3-9 的一个请求。即便对 SSD 和 NVM 的随机访问与顺序访问响应时间相同，对顺序
访问的分组请求也减少了单个请求的数量。这种合并请求的技术称为 plugging（塞入）。

除此之外，请求可以被重排序，以确保系统资源的公平性（例如，确保没有应用程序
遭受饥饿）和/或改善 IO 性能，这由 IO 调度器完成。

##### IO 调度器


块层实现了多个调度器，每个都遵循一种启发式方法以改善 IO 性能。它们是"可插拔"
的（如同即插即用），也就是说可以在运行时使用 sysfs 选择。你可以在 `这里
<https://www.kernel.org/doc/html/latest/block/index.html>`_ 阅读更多关于 Linux
IO 调度器的内容。调度只发生在同一队列内的请求之间，因此不可能合并来自不同
队列的请求，否则会出现缓存颠簸，并且每个队列都需要一把锁。调度之后，请求才有
资格被发送到硬件。可以选择的调度器之一是 NONE 调度器，最直接的那种。它只会将
请求放在进程所运行的任何软件队列上，不做任何重排序。当设备开始在硬件队列中
处理请求（即运行硬件队列）时，映射到该硬件队列的软件队列会按其映射顺序被抽空。

#### 硬件派发队列


硬件队列（由 struct blk_mq_hw_ctx 表示）是设备驱动程序用来映射设备提交队列
（或设备 DMA 环形缓冲区）的结构，并且是块层提交代码在底层设备驱动程序取得
请求所有权之前的最后一步。为了运行此队列，块层从关联的软件队列中移除请求，并
尝试派发到硬件。

如果无法将请求直接发送到硬件，它们会被添加到一个请求链表
（`hctx->dispatch`）中。然后，下次块层运行队列时，它会先发送位于 `dispatch`
链表中的请求，以确保与那些已准备好首先发送的请求的公平派发。硬件队列的数量
取决于硬件及其设备驱动程序支持的硬件上下文数量，但不会超过系统的核心数。
在这个阶段没有重排序，每个软件队列都有一组用于发送请求的硬件队列。

        来处理。

#### 基于标签的完成


为了指示哪个请求已完成，每个请求由一个从 0 到派发队列大小的整数标识。此标签
由块层生成，随后被设备驱动程序复用，从而免去了创建冗余标识符的需要。当驱动程序
中一个请求完成时，该标签被发送回块层以通知其完成。这免去了进行线性搜索以找出
哪个 IO 已完成的必要。
