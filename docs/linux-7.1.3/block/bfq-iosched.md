## BFQ（预算公平排队，Budget Fair Queueing）


BFQ 是一个按比例分配的 I/O 调度器，带有一些额外的低延迟能力。除了 cgroups 支持（blkio 或 io 控制器）之外，BFQ 的主要特性有：

- BFQ 保证较高的系统和应用响应性，以及为时间敏感型应用（如音频或视频播放器）提供低延迟；
- BFQ 在进程或组之间分配的是带宽，而不仅仅是时间（在需要保持高吞吐量时切换回时间分配）。

在默认配置下，BFQ 优先保证延迟而非吞吐量。因此，当为了实现更低延迟而有需要时，BFQ 会构建可能导致吞吐量下降的调度方案。如果你对某个设备的主要或唯一目标是在任何时候都达到尽可能高的吞吐量，那么就为该设备关闭所有低延迟启发式，将 low_latency 设为 0。关于如何为延迟与吞吐量之间的期望权衡配置 BFQ，或者如何最大化吞吐量的细节，请参阅第 3 节。

与每个 I/O 调度器一样，BFQ 为每个 I/O 请求的处理增加了一些开销。为了让大家对此开销有个概念，BFQ 受单个锁保护的、每个请求的（端到端）处理时间——即请求插入、分发和完成这三个钩子执行时间的总和——在 Intel Core i7-2760QM@2.40GHz 上为 1.9 微秒（这是一款用于笔记本的旧款 CPU；时间通过简单的代码插桩测量，并使用 S 测试套件 [^1^] 的 throughput-sync.sh 脚本，在性能剖析模式下测得）。作为参照，blk-mq 中最轻量的 I/O 调度器 mq-deadline 的、受单个锁保护的每请求执行时间为 0.7 微秒（mq-deadline 约 800 行代码，而 BFQ 约 10500 行代码）。

调度开销进一步限制了 CPU 能够处理的最大 IOPS（本来就已经受 I/O 栈其余部分执行所限）。为了让大家了解 BFQ 下的限制，在较慢或中等的 CPU 上，以下是三种不同 CPU 在完整层级支持开启（即设置了 CONFIG_BFQ_GROUP_IOSCHED，但未设置 CONFIG_BFQ_CGROUP_DEBUG）情况下，分别在一台普通笔记本、一台老旧台式机和一台廉价嵌入式系统上的 BFQ 限制（第 4-2 节）：

- Intel i7-4850HQ：400 KIOPS
- AMD A8-3850：250 KIOPS
- ARM CortexTM-A53 八核：80 KIOPS

如果设置了 CONFIG_BFQ_CGROUP_DEBUG（当然，完整层级支持也已开启），那么 BFQ 的可持续吞吐量会下降，因为所有 blkio.bfq* 统计信息都会被创建和更新（第 4-2 节）。对 BFQ 而言，在上述相同系统上，这导致以下最大可持续吞吐量：

- Intel i7-4850HQ：310 KIOPS
- AMD A8-3850：200 KIOPS
- ARM CortexTM-A53 八核：56 KIOPS

BFQ 同样适用于多队列设备。

## 1. BFQ 何时会有用？


BFQ 在个人和服务器系统上提供以下好处。

### 1-1 个人系统


##### 交互式应用的低延迟


无论实际的后台工作负载如何，BFQ 都保证对于交互式任务，存储设备的响应性几乎就像它空闲时一样。例如，即使正在执行以下一个或多个后台工作负载：

- 正在读取、写入或复制一个或多个大文件，
- 正在编译一棵树状的源文件，
- 一个或多个虚拟机正在进行 I/O，
- 正在进行软件更新，
- 索引守护进程正在扫描文件系统并更新其数据库，

启动一个应用或从应用中加载一个文件所花的时间，与存储设备空闲时几乎相同。作为对比，在同样条件下使用 CFQ、NOOP 或 DEADLINE，应用会经历高延迟，甚至变得无响应，直到后台工作负载结束（在 SSD 上也是如此）。

##### 软实时应用的低延迟


像音频和视频播放器/流媒体这样的软实时应用，无论后台 I/O 工作负载如何，也都享有低延迟和低丢包率。因此，这些应用几乎不会因后台工作负载而出现任何卡顿。

##### 代码开发任务更高的速度


如果碰巧有额外的负载在并行执行，那么 BFQ 执行典型代码开发任务（编译、检出、合并等）中 I/O 相关的部分，比 CFQ、NOOP 或 DEADLINE 快得多。

##### 高吞吐量


在机械硬盘上，在我们测试考虑的所有顺序工作负载下，BFQ 实现的吞吐量比 CFQ 高至多 30%，比 DEADLINE 和 NOOP 高至多 150%。而对于随机工作负载，以及在基于闪存的设备上的所有工作负载，BFQ 实现的吞吐量与其它调度器大致相同。

##### 强公平性、带宽和延迟保证


BFQ 在任何工作负载下、且无论设备参数如何，都按照 I/O 密集型应用的权重比例，在它们之间分配设备的吞吐量，而不仅仅是设备时间。从这些带宽保证出发，可以通过一个简单的公式计算出严格的逐 I/O 请求延迟保证。如果没有配置为严格的服务保证，BFQ 会（仅）为那些否则会导致吞吐量损失的应用切换回基于时间的资源共享。

### 1-2 服务器系统


服务器系统的大部分好处源自与上述相同的服务特性。特别地，无论是否正在服务额外的、可能很重的工作负载，BFQ 都保证：

- 音频和视频流具有零或极低的抖动和丢包率；

- Web 页面和嵌入式对象的快速检索；

- 在实时转储应用（例如包日志）中的实时数据记录；

- 对服务器的本地和远程访问的响应性。


## 2. BFQ 是如何工作的？


BFQ 是一个按比例分配的 I/O 调度器，其总体结构以及大量代码借自 CFQ。

- 在设备上进行 I/O 的每个进程，都与一个权重和一个 `(bfq_)queue` 相关联。

- BFQ 在一段时间内，一次将一个设备排他地访问权授予一个队列（进程），并通过为每个队列关联一个以扇区数度量的预算来实现这种服务模型。

  - 在队列被授予设备访问权后，每次分发请求时，该队列的预算会按请求的大小递减。

  - 只有在发生以下事件之一时，在役队列才会到期（即其服务被挂起）：1) 队列用完了其预算，2) 队列变空，3) 触发了“预算超时”。

    - 预算超时防止进行随机 I/O 的进程长时间占用设备，从而大幅降低吞吐量。

    - 实际上，与 CFQ 中一样，与一个发出同步请求的进程关联的队列，在变空时可能不会立即到期。相反，BFQ 可能会让设备空闲一小段时间，给该进程一个机会，如果它及时发出新请求，就继续为其服务。如果进程进行同步且顺序的 I/O，设备空闲通常能在旋转设备和非排队式基于闪存的设备上提升吞吐量。此外，在 BFQ 下，设备空闲对于向发出同步请求的进程保证期望的吞吐量占比也是有帮助的（详见本文档中对 slice_idle 可调参数的描述，或 [1, 2]）。

      - 关于为保证服务而进行的空闲：如果多个进程同时竞争设备，但所有进程和组具有相同的权重，那么 BFQ 保证期望的吞吐量分布，而从不让设备空闲。因此在这种常见场景下，吞吐量尽可能高。

     - 在具有内部命令排队（通常是 NCQ）的基于闪存的存储上，设备空闲碰巧总是对吞吐量有害。因此，对于这些设备，BFQ 仅在为保证服务严格需要时才进行空闲，即为了保证低延迟或公平性。在这些情况下，整体吞吐量可能并非最优。目前尚无同时在这类具有内部排队的设备上提供强服务保证和最优吞吐量的解决方案。

  - 如果启用了低延迟模式（默认配置），BFQ 会执行一些特殊启发式来检测交互式和软实时应用（例如视频或音频播放器/流媒体），并降低它们的延迟。为实现这一目标而采取的最重要的动作，是给与这些应用关联的队列比其公平份额更多的设备吞吐量。为简洁起见，我们把 BFQ 为优待这些队列而采取的一整套动作统称为“权重提升（weight-raising）”。特别地，BFQ 为交互式应用提供一种较温和的权重提升，为软实时应用提供一种较强的权重提升。

  - BFQ 会自动为在队列创建突发中诞生的队列停用空闲。事实上，这些队列通常与最能从高吞吐量中获益的应用和服务的进程相关联。例子有启动过程中的 systemd，或 git grep。

  - 与 CFQ 一样，BFQ 合并进行交错 I/O 的队列，即进行随机 I/O、一旦合并就主要变为顺序 I/O 的队列。与 CFQ 不同的是，BFQ 通过一个更具响应性的机制来实现这一目标，称为早期队列合并（Early Queue Merge，EQM）。EQM 在检测交错 I/O（协作进程）时非常灵敏，以至于它使 BFQ 能够通过队列合并实现高吞吐量，即使是对于那些 CFQ 需要另一种机制——抢占——才能获得高吞吐量的队列。因此，EQM 是一个用于通过交错 I/O 实现高吞吐量的统一机制。

  - 队列按照 WF2Q+ 的一个变体调度，称为 B-WF2Q+，并使用一棵增强的 rb 树来实现，以保持 O(log N) 的整体复杂度。更多细节请参阅 [^2^]。B-WF2Q+ 也已为层级调度做好准备，细节见第 4 节。

  - B-WF2Q+ 保证相对于理想的、完美公平且平滑的服务的微小偏差。特别地，B-WF2Q+ 保证每个队列收到的设备吞吐量占比与其权重成正比，即使吞吐量发生波动，并且无论：设备参数、当前工作负载以及分配给队列的预算如何。

  - 最后，预算无关性这一特性（尽管初看起来可能反直觉）无疑是 beneficial 的，原因如下：

    - 首先，对于任何按比例分配的调度器，相对于理想服务的偏差上限与分配给队列的最大预算（时间片）成正比。因此，BFQ 能够将这个偏差保持得很小，不仅因为 B-WF2Q+ 的精确服务，也因为 BFQ **不**需要为某个队列分配更大的预算来让该队列收到更高比例的设备吞吐量。

    - 其次，BFQ 可以自由地为每个进程（队列）选择最适合该进程需求、或最能利用该进程 I/O 模式的预算。特别地，BFQ 用一个简单的反馈环算法更新队列预算，从而能够在仍然为时间敏感型应用提供严格延迟保证的同时，实现高吞吐量。当在役队列到期时，该算法计算队列的下一个预算，以便：

      - 让较大的预算最终被分配给与进行顺序 I/O 的 I/O 密集型应用关联的队列：事实上，这类应用在获得设备访问权后被服务得越久，吞吐量就越高。

      - 让较小的预算最终被分配给与时间敏感型应用（通常进行偶发且短暂的 I/O）关联的队列，因为等待服务的队列被分配的预算越小，B-WF2Q+ 就会越早服务该队列（见 [^2^] 的 Subsec 3.3）。

- 如果多个进程同时竞争设备，但所有进程和组具有相同的权重，那么 BFQ 保证期望的吞吐量分布，而从不让设备空闲。它改用抢占。因此在这种常见场景下吞吐量要高得多。

- ioprio 类别按严格优先级顺序被服务，即只要有更高优先级的队列存在，就不会服务较低优先级的队列。在同一类别的队列中，带宽按每个队列的权重比例分配。然而，Idle 类别会得到极少量额外的带宽保证，以防止它被饿死。


## 3. BFQ 有哪些可调参数，以及如何正确配置 BFQ？


大多数 BFQ 可调参数影响服务保证（基本上是延迟和公平性）和吞吐量。关于如何在服务保证和吞吐量之间选择期望的权衡，请参阅参数 slice_idle、strict_guarantees 和 low_latency。关于如何最大化吞吐量，请参阅 slice_idle、timeout_sync 和 max_budget。其它与性能相关的参数继承自 CFQ，并且主要是为了与 CFQ 兼容而保留的。到目前为止，还没有报告称在 BFQ 中更改后几个参数能带来性能提升。

特别地，下面的 back_seek_max、back_seek_penalty、fifo_expire_async 和 fifo_expire_sync 与 CFQ 中的相同。它们的描述只是从 CFQ 的对应描述复制而来。slice_idle 描述中的一些考量也复制自 CFQ。

### 逐进程的 ioprio 和权重


除非使用 cgroups 接口（见“4. BFQ 组调度”），否则权重只能间接地、通过 I/O 优先级并根据如下关系分配给进程：
weight = (IOPRIO_BE_NR - ioprio) * 10。

注意，如果设置了低延迟，那么 BFQ 会自动提升与交互式和软实时应用关联的队列的权重。如果你需要/想要控制权重，请取消设置此可调参数。

### slice_idle


此参数指定当某些同步 BFQ 队列变空时，BFQ 应为下一个 I/O 请求空闲多长时间。默认情况下 slice_idle 是一个非零值。空闲有双重目的：提升吞吐量，以及确保期望的吞吐量分布得到遵守（请参阅 BFQ 工作原理的描述，以及必要时其中引用的论文）。

至于吞吐量，在像单主轴 SATA/SAS 磁盘这样高度寻道（seeky）的介质上，空闲会很有帮助，因为我们可以减少整体的寻道次数并看到吞吐量的提升。

将 slice_idle 设为 0 会移除队列上的所有空闲，并且应当能在更快的存储设备（如硬件 RAID 配置中的多块 SATA/SAS 磁盘，以及具有内部命令排队（和并行性）的基于闪存的存储）上看到整体吞吐量的提升。

因此，取决于存储和工作负载，设置 slice_idle=0 可能有用。一般来说，对于 SATA/SAS 磁盘和 SATA/SAS 磁盘的软件 RAID，保持 slice_idle 开启应当是有用的。对于任何在单个 LUN 后面有多个主轴的配置（基于主机的硬件 RAID 控制器或存储阵列），或者对于基于闪存的快速存储，设置 slice_idle=0 可能带来更好的吞吐量和可接受的延迟。

然而，在存在差异化权重或差异化 I/O 请求长度的情况下，空闲对于强制实施服务保证是必要的。要理解原因，假设某个给定的 BFQ 队列 A 必须为另一个队列 B 每服务一个请求就服务若干个 I/O 请求。空闲确保，如果 A 在变空后稍晚发出一个新 I/O 请求，那么中间不会分发 B 的任何请求，因此 A 不会失去在 B 的下一个请求被分发之前获得多于一个请求被分发的机会。注意，空闲只在 I/O 请求分发方面保证对队列的差异化处理。为了保证实际的服务顺序随后对应于分发顺序，还必须设置 strict_guarantees 可调参数。

空闲有一个重要的另一面：除了上述那种对吞吐量也有益的情况外，空闲会严重影响吞吐量。一个重要的案例是随机工作负载。由于这个问题，BFQ 倾向于尽可能避免空闲，当它对吞吐量也无益时（详见第 2 节）。这种行为的结果，加上 strict_guarantees 可调参数所描述的进一步问题，短期的服务保证可能会偶尔被违反。而且，在某些情况下，这些保证可能比保证最大吞吐量更重要。例如，在视频播放/流媒体中，极低的丢包率可能比最大吞吐量更重要。在这些情况下，考虑设置 strict_guarantees 参数。

### slice_idle_us


控制与 slice_idle 相同的调优参数，但以微秒为单位。任一可调参数都可用于设置空闲行为。之后，另一个可调参数会在 sysfs 中反映新设置的值。

### strict_guarantees


如果设置了此参数（默认：未设置），那么 BFQ

- 总是在在役队列变空时执行空闲；

- 强制设备一次只服务一个 I/O 请求，即仅当没有未完成的请求时才分发一个新请求。

在存在差异化权重或 I/O 请求大小的情况下，上述两个条件都是保证每个 BFQ 队列收到其应得带宽份额所必需的。第一个条件是因为 slice_idle 可调参数描述中所解释的原因。第二个条件是因为所有现代存储设备都会在内部对排队的请求重排序，这可能轻易破坏 I/O 调度器强制实施的服务保证。

设置 strict_guarantees 显然可能会影响吞吐量。

### back_seek_max


此参数以 Kbytes 给出，指定向后寻道（backward seeking）的最大“距离”。距离是指从当前磁头位置到在距离上位于其“后方”的扇区之间的空间量。

此参数允许调度器预期“向后”方向的请求，并将它们视为“下一个”请求，只要它们在此距离之内、离当前磁头位置足够近。

### back_seek_penalty


此参数用于计算向后寻道的代价。如果请求的向后距离仅为从一个“前向”请求的 1/back_seek_penalty，那么这两个请求的寻道代价被视为等价。

因此调度器不会偏向其中一个或另一个请求（否则调度器会偏向前向请求）。back_seek_penalty 的默认值是 2。

### fifo_expire_async


此参数用于设置异步请求的超时。其默认值是 250ms。

### fifo_expire_sync


此参数用于设置同步请求的超时。其默认值是 125ms。为了让同步请求优先于异步请求，此值应当相对于 fifo_expire_async 减小。

### low_latency


此参数用于启用/禁用 BFQ 的低延迟模式。默认情况下，低延迟模式是启用的。如果启用，交互式和软实时应用会被优待并经历更低的延迟，如 BFQ 工作原理的描述中更详细地解释的那样。

如果你需要对带宽分配有完全控制，请禁用此模式。事实上，如果它启用，那么 BFQ 会自动增加被优待应用的带宽份额，作为向它们保证更低延迟的主要手段。

此外，正如本文档开头已经强调的，如果你的唯一目标是实现高吞吐量，请禁用此模式。事实上，将某些应用的 I/O 置于其余应用之上可能会带来更低的吞吐量。要在非旋转设备上实现尽可能高的吞吐量，可能还需要将 slice_idle 设为 0（代价是放弃任何关于公平性和低延迟的强保证）。

### timeout_sync


一旦某个任务（队列）被选中服务，能够给予它的设备时间的最大量。在寻道代价高昂的设备上，增加此时间通常会增加最大吞吐量。在另一端，增加此时间会粗化短期带宽和延迟保证的粒度，特别是在以下参数被设为 0 时。

### max_budget


一旦某个 BFQ 队列被置为服务（当然在上述超时限制之内），能够提供给它的、以扇区数度量的最大服务量。根据算法描述中所说，较大的值在比例上随顺序 I/O 请求所占百分比的增加而提高吞吐量。较大值的代价是它们粗化了短期带宽和延迟保证的粒度。

默认值是 0，这会启用自动调优：BFQ 根据估计的峰值速率，将 max_budget 设为在 timeout_sync 期间能够服务的最大扇区数。

对于特定设备，一些用户偶尔报告说通过显式设置 max_budget（即把 max_budget 设为高于 0 的值）达到了更高的吞吐量。特别地，他们把 max_budget 设为了比 BFQ 在自动调优下会设置的值更高的值。实现这一目标的另一种方式是直接增加 timeout_sync 的值，同时让 max_budget 保持为 0。

## 4. 使用 BFQ 进行组调度


BFQ 同时支持 cgroups-v1 和 cgroups-v2 的 io 控制器，即 blkio 和 io。特别地，BFQ 支持基于权重的按比例分配。要激活 cgroups 支持，请设置 BFQ_GROUP_IOSCHED。

### 4-1 提供的服务保证


在 BFQ 中，按比例分配意味着根据组权重对设备带宽的真正按比例分配。例如，权重为 200 的组获得的是权重为 100 的组的带宽的两倍，而不仅仅是一倍的时间。

BFQ 支持任意深度的层级（组树）。带宽按预期的方式在组和进程之间分配：对于每个组，该组的子节点按各自权重的比例分享该组的整个带宽。特别地，这意味着，对于每个叶组，除非修改了进程的 ioprio，该组的每个进程都收到整个组带宽的相同份额。

如果向某个组提供带宽保证会使吞吐量下降太多，那么该组的资源共享保证可能会部分或完全从带宽切换到时间。这种切换是按进程进行的：如果一个叶组的某个进程在被服务以获得其带宽份额时会导致吞吐量损失，那么 BFQ 会为该进程切换回仅基于时间的按比例分配。

### 4-2 接口


要使用 BFQ 获得给定设备的带宽按比例分配，BFQ 当然必须作为该设备的活动调度器。

在每个组目录中，与 BFQ 特定的 cgroup 参数和统计信息关联的文件名以 "bfq." 前缀开头。因此，无论是 cgroups-v1 还是 cgroups-v2，BFQ 特定文件的完整前缀是 "blkio.bfq." 或 "io.bfq."。例如，用 BFQ 设置组权重的组参数是 blkio.bfq.weight 或 io.bfq.weight。

至于 cgroups-v1（blkio 控制器），由 bfq 创建并保持最新的确切统计文件集合，取决于是否设置了 CONFIG_BFQ_CGROUP_DEBUG。如果设置了，那么 bfq 会创建 Documentation/admin-guide/cgroup-v1/blkio-controller.rst 中记录的所有统计文件。如果未设置，那么 bfq 只创建以下统计文件：

```

  blkio.bfq.io_service_bytes
  blkio.bfq.io_service_bytes_recursive
  blkio.bfq.io_serviced
  blkio.bfq.io_serviced_recursive

```
CONFIG_BFQ_CGROUP_DEBUG 的值极大地影响了用 bfq 可持续的的最大吞吐量，因为更新 blkio.bfq.* 统计信息相当昂贵，尤其是对某些由 CONFIG_BFQ_CGROUP_DEBUG 启用的统计信息。

### 参数


对于每个组，可以设置以下参数：

  weight
        这指定了 cgroup 在其父节点内的默认权重。
        可用值：1..1000（默认：100）。

        对于 cgroup v1，通过将该值写入 `blkio.bfq.weight` 来设置。

        对于 cgroup v2，通过将该值写入 `io.bfq.weight` 来设置。
        （可带一个可选的 `default` 前缀和一个空格）。

        在可调参数一节开头描述的 ioprio 与权重之间的线性映射仍然有效，但所有高于
        IOPRIO_BE_NR*10 的权重都被映射到 ioprio 0。

        回想一下，如果设置了低延迟，那么 BFQ 会自动提升与交互式和软实时
        应用关联的队列的权重。如果你需要/想要控制权重，请取消设置此可调参数。

  weight_device
        这指定了 cgroup 的逐设备权重。语法为
        `minor:major weight`。权重 `0` 可用于重置为默认
        权重。

        对于 cgroup v1，通过将该值写入 `blkio.bfq.weight_device` 来设置。

        对于 cgroup v2，文件名为 `io.bfq.weight`。
