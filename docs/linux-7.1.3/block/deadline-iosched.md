## Deadline IO 调度器可调参数


本小文件试图说明 deadline IO 调度器的工作原理。特别是，它将阐明那些可能引起高级用户兴趣的、所暴露的可调参数的含义。

### 选择 IO 调度器

有关按设备选择 IO 调度器的信息，请参阅 Documentation/block/switching-sched.rst。

------------------------------------------------------------------------------

### read_expire	（单位 ms）


deadline IO 调度器的目标是尝试保证请求的起始服务时间。由于我们主要关注读延迟，因此这是可调的。当一个读请求首次进入 IO 调度器时，会被分配一个截止时间，即当前时间加上以毫秒为单位的 read_expire 值。


### write_expire	（单位 ms）


与上述 read_expire 类似，但针对写操作。


### fifo_batch	（请求数量）


请求被分组成特定数据方向（读或写）的 `batches`（批次），并按扇区递增顺序被服务。为了限制额外的寻道，deadline 的到期检查仅在批次之间进行。fifo_batch 控制每个批次的最大请求数。

该参数调节单个请求延迟与总体吞吐量之间的平衡。当低延迟是主要关注点时，较小的值更好（值为 1 时产生先来先服务的行为）。增大 fifo_batch 通常能提高吞吐量，代价是延迟的变化。


### writes_starved	（调度次数）


当我们需要将请求从 IO 调度器队列移动到块设备调度队列时，我们总是优先处理读。然而，我们也不希望无限期地饿死写。因此 writes_starved 控制我们优先读而非写的次数。当已经优先了 writes_starved 次之后，我们会根据与读相同的标准调度一些写。


### front_merges	（布尔值）


有时会发生这样的情况：一个进入 IO 调度器的请求与队列中已有的某个请求是连续的。它要么适合在该请求的尾部，要么适合在头部。这分别称为后向合并候选或前向合并候选。由于文件通常的布局方式，后向合并比前向合并常见得多。对于某些工作负载，你甚至可能知道尝试前向合并请求是在浪费时间。将 front_merges 设为 0 会禁用该功能。由于缓存的 last_merge 提示，前向合并仍可能发生，但由于其代价基本为 0，我们保留它。我们只是在调用 IO 调度器合并函数时禁用了 rbtree 前向扇区查找。
