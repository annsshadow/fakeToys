
## 处理混乱的拉取请求 diffstat

子系统维护者经常使用 `git request-pull` 作为将工作发送到上游流程的一部分。
通常，结果会包含一个漂亮的 diffstat，显示哪些文件会被改动，以及每个文件改动
多少。不过，偶尔会有一个开发历史相对复杂的仓库，产生一个包含大量无关工作的
巨大 diffstat。结果看起来很乱，并且掩盖了拉取请求实际在做什么。本文档说明了
发生了什么以及如何修复；它源自 Linus Torvalds 的智慧，可见于 Linus1_ 和 Linus2_。


Git 的开发历史是一系列提交推进的。在一个简化的
```

  ... vM --- vN-rc1 --- vN-rc2 --- vN-rc3 --- ... --- vN-rc7 --- vN

```
如果想查看两个时间点之间发生了什么变化，可以使用类似下面这样的命令
```

  $ git diff --stat --summary vN-rc2..vN-rc3

```
这里，历史中有两个清晰的点；Git 本质上是将起始点从结束点“减去”，并显示得到的
差异。所请求的操作是明确的，也很容易理解。

当子系统维护者创建一个分支并向其中提交改动时，
```

  ... vM --- vN-rc1 --- vN-rc2 --- vN-rc3 --- ... --- vN-rc7 --- vN
                          |
                          +-- c1 --- c2 --- ... --- cN

```
如果该维护者现在使用 `git diff` 来查看主分支（我们称之为“linus”）和 cN 之间的
变化，仍然有两个清晰的端点，结果也符合预期。因此用 `git request-pull` 生成的拉取
请求也会符合预期。但现在
```

  ... vM --- vN-rc1 --- vN-rc2 --- vN-rc3 --- ... --- vN-rc7 --- vN
                |         |
                |         +-- c1 --- c2 --- ... --- cN
                |                   /
                +-- x1 --- x2 --- x3

```
我们的维护者在 vN-rc1 处创建了一个分支，在 vN-rc2 处创建了另一个分支；随后两者
在 c2 处合并。现在为 cN 生成的拉取请求可能确实会变得混乱，开发者们常常搞不明白
为什么。

这里发生的事情是，`git diff` 操作不再有两个清晰的端点可用。以 cN 为终点的开发
始于两个不同的地方；为了生成 diffstat，`git diff` 最终不得不从中选一个，并寄希望
于最好的结果。如果 diffstat 从 vN-rc1 开始，它可能最终会包含从该处到第二个起点
（vN-rc2）之间的所有改动，而这肯定不是我们的维护者所期望的。diffstat 中多了这些
额外的垃圾内容，可能就无法分辨出导致 cN 的改动实际发生了什么。

维护者常常试图通过例如对分支做 rebase，或与 linus 分支再做一次合并，然后重新
创建拉取请求来解决这个问题。这种做法在拉取请求的接收端往往不会带来好结果；在上游
推送之前进行 rebase 和/或合并，是招致不悦回应众所周知的方式。

那么应该怎么做呢？面对这种情况时，最佳应对确实是做一次与你希望工作被拉入的分支
的合并，但要私下做，就好像它是来源的
```

  ... vM --- vN-rc1 --- vN-rc2 --- vN-rc3 --- ... --- vN-rc7 --- vN
                |         |                                      |
                |         +-- c1 --- c2 --- ... --- cN           |
                |                   /               |            |
                +-- x1 --- x2 --- x3                +------------+-- TEMP

```
合并操作解决了由多个起点导致的所有复杂性，产生一个只包含与主分支差异的连贯结果。
现在就可以
```

  $ git diff -C --stat --summary linus..TEMP

```
保存该命令的输出，然后直接删除 TEMP 分支；绝对不要把它暴露给外界。把保存下来的
diffstat 输出编辑进那个混乱的拉取请求，从而得到能显示真实情况的结果。然后就可以
将该请求发送到上游了。
