
## 变基与合
维护一个子系统，一般来说，需要熟Git 源代码管理系统。Git 是一个强大的工具，拥有大量特性；与这类工具常见的情况一样，使用这些特性有正确和错误之分。本文档特别着眼于变基（rebase）和合并（merge）的使用。维护者常常因为在错误地使用这些工具时陷入麻烦，但避免问题其实并不那么难
需要普遍注意的一点是，与许多其他项目不同，内核社区并不害怕在其开发历史中看到合并提交。事实上，考虑到项目的规模，避免合并几乎是不可能的。维护者遇到的一些问题源于想要避免合并，而另一些则来自合并得过于频繁
## 变基

“变基（Rebasing）”是在仓库内改变一系列提交历史的过程。有两种不同类型的操作都被称为变基，因为它们都用 `git rebase` 命令完成，但它们之间有显著差异：

 - 改变一系列补丁所基于的父（起始）提交。例如，一次变基操作可以获取一个基于上一个内核版本的补丁集，转而将其基于当前版本。在下文的讨论中，我们称此操作为“重设父提交（reparenting）”
 - 通过修复（或删除）损坏的提交、添加补丁、向提交变更日志添加标签、或改变提交应用的顺序，来改变一组补丁的历史。在下面的文字中，这类操作将被称为“历史修改（history modification）
“变基”一词将用于指代上述两种操作。使用得当，变基可以产生更干净、更清晰的发展历史；使用不当，则会掩盖那段历史并引入 bug
有一些经验法则可以帮助开发者避免变基最糟糕的危险：

 - 已经暴露到你私有系统之外的世界的历史，通常不应被改变。其他人可能已经拉取了你的树的一个副本并基于它构建；修改你的树会给他们带来痛苦。如果某项工作需要变基，那通常表明它还没有准备好提交到公共仓库
   话虽如此，总有例外。有些树（linux-next 是一个重要的例子）按其本性经常被变基，开发者们知道不要基于它们构建工作。开发者有时会暴露一个不稳定的分支供他人测试或用于自动化测试服务。如果你以这种方式暴露了一个可能不稳定的分支，务必让可能的用户知道不要基于它构建工作
 - 不要变基一个包含由他人创建的历史的分支。如果你从另一个开发者的仓库拉取了变更，你现在是他们历史的管理者。你不应改变它。除了少数例外，例如，这样一棵树中的一个损坏的提交应当被显式地 revert，而不是通过历史修改消失
 - 没有充分的理由不要重设一棵树的父提交。仅仅为了基于一个较新的基线，或避免与上游仓库合并，通常不是一个好理由
 - 如果你必须重设一个仓库的父提交，不要挑选某个随机的内核提交作为新基线。在内核发布点之间，内核经常处于相对不稳定的状态；基于这些点之一进行开发会增加遇到意外 bug 的机会。当一个补丁系列必须移动到新的基线时，挑选一个稳定的点（例如某个 -rc 版本）作为目标
 - 要认识到，重设一个补丁系列的父提交（或进行重大的历史修改）改变了它开发所处的环境，并且很可能使已经完成的许多测试失效。作为一般规则，一个被重设父提交的补丁系列应当被当作新代码对待，并从头重新测试
合并窗口麻烦的一个常见原因是，当 Linus 收到一个明显被重设了父提交（通常是重设到某个随机提交）的补丁系列，而且往往是在拉取请求发出前不久才这样做。这样的系列经过充分测试的可能性相对较低——拉取请求被接受的可能性也同样低
相反，如果变基仅限于私有树，提交基于一个众所周知的起点，并且经过了充分测试，那么出麻烦的可能性就很低
## 合并

合并是内核开发过程中一种常见的操作.1 开发周期包含了 1,126 个合并提交——接近总数9%。内核工作累积在超过 100 个不同的子系统树中，每个树可能包含多个主题分支；每个分支通常独立于其他分支开发。因此，在任何给定分支进入上游仓库之前，自然至少需要一次合并
许多项目要求拉取请求中的分支基于当前trunk，以便历史中不出现合并提交。内核不是这样的项目；任何为了避免合并而对分支进行变基，很可能都会导致麻烦
子系统维护者发现他们不得不做两类合并：来自较低层级子系统树的合并，以及来自其他树（兄弟树或主线）的合并。在这两种情况下要遵循的最佳实践有所不同
### 来自较低层级树的合并

较大的子系统往往有多个层级的维护者，较低层级的维护者向较高层级发送拉取请求。处理这样的拉取请求几乎肯定会生成一个合并提交；理应如此。事实上，子系统维护者可能想要使--no-ff 标志来强制添加一个合并提交，以便在不通常会创建合并提交的罕见情况下记录合并的原因。对于任何种类的合并，合并的变更日志都应当说*为什*要进行合并。对于较低层级的树，“为什么”通常是随该拉取而来变更的摘要
所有层级的维护者都应当在他们的拉取请求上使用签名标签（signed tags），而上游维护者在拉取分支时应当验证这些标签。不这样做会威胁整个开发过程的安全性
按照上面列出的规则，一旦你将别人的历史合并进你的树，你就不能变基那个分支，即使你本来能够这样做
### 来自兄弟或上游树的合
虽然来自下游的合并很常见且不值一提，但当要把一个分支推向上游时，来自其他树的合并往往会成为一个危险信号。这类合并需要仔细考虑并有充分的理由，否则随后的拉取请求很有可能会被拒绝
想要master 分支合并进一个仓库是很自然的；这类合并通常被称为“反向合并（back merge）”。反向合并有助于确保与并行开发没有冲突，并通常会带来一种与时俱进的温暖、模糊的感觉。但这种诱惑几乎在所有时候都应避免
为什么会这样？反向合并会搅浑你自己分支的开发历史。它们会显著增加你遇到来自社区其他地bug 的机会，并使你难以确保你所管理的工作是稳定的、已准备好进入上游的。频繁的合并也会掩盖你树中开发过程的问题；它们会隐藏本不该（经常）发生在管理良好的分支中的与其他树的交互
话虽如此，反向合并偶尔是必需的；当这种情况发生时，务必在提交消息中记*为什*需要它。一如既往，合并到一个众所周知的稳定点，而不是某个随机提交。即便如此，你也不应反向合并高于你直接上游树的树；如果真的需要更高层级的反向合并，应当由上游树先做
与上游合并相关麻烦最常见的原因之一，是维护者在发送拉取请求之前为了解析合并冲突而与上游合并。同样，这种诱惑很容易理解，但绝对应当避免。对于最终的拉取请求尤其如此：Linus 坚持认为，他宁愿看到合并冲突，也不愿看到不必要的反向合并。看到冲突让他知道潜在的麻烦区域在哪里。他做了大量的合并（5.1 开发周期中382 次），并且已经相当擅长解决冲突——往往比涉及的开发者还要好
那么，当子系统分支与主线之间存在冲突时，维护者应该怎么做？最重要的一步是在拉取请求中警告 Linus 冲突将会发生；即便没有其他，这也表明你意识到你的分支如何融入整体。对于特别困难的冲突，创建并推送一*独立**的分支来展示你将如何解决问题。在你的拉取请求中提及该分支，但拉取请求本身应当是针对未合并的分支
即使在没有已知冲突的情况下，在发送拉取请求之前做一次测试合并也是个好主意。它可能会提醒你一些你以某种方式从 linux-next 中没有看到的问题，并有助于准确理解你要求上游去做什么
与上游或另一个子系统树进行合并的另一个原因是为了解决依赖关系。这些依赖问题有时确实会发生，有时与另一个树的交叉合并是解决它们的最佳方式；一如既往，在这种情况下，合并提交应当解释为什么进行了合并。花点时间把它做对；人们会读那些变更日志
不过，依赖问题通常表明需要改变方法。合并另一个子系统树来解决依赖关系，有可能会引入其bug，几乎永远不应这样做。如果那个子系统树未能被上游拉取，它所拥有的任何问题都会阻塞你的树的合并。更好的替代方案包括与维护者达成一致，将两组变更都放在其中一个树中，或者创建一个专门面向前提提交的主题分支，可以合并进两个树。如果依赖关系与重大的基础设施变更有关，正确的解决方案可能是将依赖的提交保留一个开发周期，以便这些变更有时间在主线上稳定下来
## 最
在开发周期开始时与主线合并以拾取树中其他地方完成的变更和修复，是相对常见的。一如既往，这样的合并应当挑选一个众所周知的发布点，而不是某个随机位置。如果你的面向上游的分支在合并窗口期间已经完全清空进入主线，你可以用

```
  git merge --ff-only v5.2-rc1

```
上面列出的准则仅仅是准则。总会有需要不同解决方案的情况，这些准则不应阻止开发者在需要时出现时做正确的事。但应当始终思考这种需要是否真的出现了，并准备好解释为什么需要做一些不正常的事情
