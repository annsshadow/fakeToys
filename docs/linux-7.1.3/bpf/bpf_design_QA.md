## BPF 设计问答


BPF 的可扩展性及其在网络、追踪、安全方面的适用性，加上 Linux 内核中以及若干 BPF 虚拟机用户空间实现，导致了对 BPF 到底是什么的诸多误解。这篇简短的问答试图解决这个问题，并勾勒出 BPF 长期发展的方向。

    :depth: 3

## 问题与回答


### 问：BPF 是类似于 x64 和 arm64 的通用指令集吗？

答：不是。

### 问：BPF 是一个通用的虚拟机吗？

答：不是。

### BPF 是 *带有* C 调用约定的通用指令集。


#### 问：为什么选择 C 调用约定？


答：因为 BPF 程序被设计为运行在以 C 编写的内核中，因此 BPF 定义了与两个最常用架构 x64 和 arm64 兼容的指令集（并考虑到了其他架构的重要怪癖），并且定义了与这些架构上 Linux 内核的 C 调用约定兼容的调用约定。

#### 问：未来是否可能支持多个返回值？

答：不能。BPF 只允许使用寄存器 R0 作为返回值。

#### 问：未来是否可能支持超过 5 个函数参数？

答：不能。BPF 调用约定只允许使用寄存器 R1-R5 作为参数。BPF 不是独立的指令集。（不像 x64 ISA 允许 msft、cdecl 和其他约定）

### 问：BPF 程序能否访问指令指针或返回地址？

答：不能。

### 问：BPF 程序能否访问栈指针？

答：不能。

只有帧指针（寄存器 R10）是可访问的。从编译器的角度看，有必要拥有栈指针。例如，LLVM 在其 BPF 后端中将寄存器 R11 定义为栈指针，但它确保生成的代码从不使用它。

### 问：C 调用约定是否削弱了可能的用例？

答：是的。

BPF 设计强制以内核辅助函数（helper function）和内核对象（如 BPF map）的形式添加主要功能，并在它们之间实现无缝互操作。它让内核可以调用 BPF 程序，程序也可以以零开销调用内核辅助函数，就好像它们都是原生的 C 代码。对于 JIT 编译的 BPF 程序尤其如此，它们与原生内核 C 代码没有区别。

### 问：这是否意味着对 BPF 代码的“创新”扩展被禁止了？

答：基本上是的。

至少目前如此，直到 BPF 核心支持 bpf-to-bpf 调用、间接调用、循环、全局变量、跳转表、只读段，以及 C 代码能够产生的所有其他常规构造。

### 问：能否以安全的方式支持循环？

答：目前尚不清楚。

BPF 开发者正试图找到一种支持有界循环的方式。

### 问：验证器（verifier）有哪些限制？

答：用户空间唯一已知的限制是 BPF_MAXINSNS（4096）。它是非特权 bpf 程序所能拥有的最大指令数。验证器有各种内部限制。例如程序分析期间可探索的最大指令数。目前，该限制被设为 100 万。这本质上意味着最大的程序可以由 100 万条 NOP 指令组成。对后续分支的最大数量有限制，对嵌套 bpf-to-bpf 调用的数量有限制，对每条指令验证器状态的数量有限制，对程序使用的 map 数量也有限制。所有这些限制都可能被足够复杂的程序触达。还有可能导致程序被拒绝的非数值限制。验证器过去只识别指针 + 常量表达式。现在它能识别指针 + 有界寄存器（bounded_register）。bpf_lookup_map_elem(key) 曾要求 'key' 必须是指向栈的指针。现在，'key' 可以是指向 map 值的指针。验证器正在稳步变得“更聪明”。限制正在被移除。知道程序是否会被验证器接受的唯一方法是尝试加载它。bpf 开发过程保证未来的内核版本会接受所有被早期版本接受的 bpf 程序。


### 指令级问题


#### 问：LD_ABS 与 LD_IND 指令 vs C 代码


问：既然 C 代码无法表达 LD_ABS 与 LD_IND 指令、而必须使用内建（builtin） intrinsic，为什么它们还会出现在 BPF 中？

答：这是与经典 BPF（classic BPF）兼容的遗留产物。现代 BPF 网络代码在没有它们的情况下性能更好。参见 “direct packet access”（直接包访问）。

#### 问：BPF 指令与本地 CPU 并非一一对应

问：似乎并非所有 BPF 指令都与本地 CPU 一一对应。例如，为什么 BPF_JNE 以及其他比较和跳转不像 CPU 那样？

答：这是为了避免在 ISA 中引入那些跨 CPU 架构无法做到通用且高效的标志位。

#### 问：为什么 BPF_DIV 指令不映射到 x64 的 div？

答：因为如果我们选取到 x64 的一一对应关系，会使得在 arm64 和其他架构上支持变得更复杂。此外它还需要除零的运行时检查。

#### 问：为什么 BPF 有隐式的 prologue 和 epilogue？

答：因为像 sparc 这样的架构有寄存器窗口，而且一般而言架构之间存在足够多的细微差异，所以将返回地址存入栈这种朴素做法无法工作。另一个原因是 BPF 必须安全地处理除零（以及 LD_ABS 指令的遗留异常路径）。这些指令需要隐式调用 epilogue 并返回。

#### 问：为什么 BPF_JLT 和 BPF_JLE 指令一开始没有被引入？

答：因为经典 BPF 没有它们，而 BPF 作者认为编译器的变通方案是可接受的。结果证明，由于缺乏这些比较指令，程序会损失性能，因此它们被添加了进来。这两条指令是未来可接受并能够添加的新型 BPF 指令的完美范例。这两条指令已经在原生 CPU 中有等价指令。没有到硬件指令一一映射的新指令将不会被接受。

#### 问：BPF 32 位子寄存器要求

问：BPF 32 位子寄存器有一个将 BPF 寄存器高 32 位清零的要求，这使得 BPF 对于 32 位 CPU 架构和 32 位硬件加速器而言是一个低效的虚拟机。未来是否可以向 BPF 添加真正的 32 位寄存器？

答：不能。

但是有一些用于清零 BPF 寄存器高 32 位的优化可用，并且可以被利用来改善 32 位架构上 JIT 编译的 BPF 程序的性能。

从版本 7 开始，LLVM 能够生成操作于 32 位子寄存器的指令，前提是在编译程序时传入选项 -mattr=+alu32。此外，验证器现在可以标记那些需要清零目标寄存器高位的指令，并插入一条显式的零扩展（zext）指令（一个 mov32 变体）。这意味着对于没有 zext 硬件支持的架构，JIT 后端不需要为 alu32 指令或窄加载（narrow load）写入的子寄存器清除高位。相反，后端只需要支持为该 mov32 变体生成代码，并将 bpf_jit_needs_zext() 重写为返回 “true”（以便启用验证器中的 zext 插入）。

注意，JIT 后端有可能拥有对 zext 的部分硬件支持。在这种情况下，如果启用了验证器的 zext 插入，可能会导致插入不必要的 zext 指令。此类指令可以通过在 JIT 后端内创建一个简单的窥孔（peephole）优化来移除：如果一条指令有 zext 的硬件支持，且下一条指令是一条显式的 zext，那么在生成代码时可以跳过后者。

### 问：BPF 有稳定的 ABI 吗？

答：有。BPF 指令、BPF 程序的参数、辅助函数集合及其参数、被识别的返回码，都是 ABI 的一部分。但有一个针对追踪程序的特定例外：它们使用 bpf_probe_read() 之类的辅助函数来遍历内核内部数据结构，并用内核内部头文件编译。这两者都是内核内部实现，可能随更新的内核而改变，从而需要相应地调整程序。

新的 BPF 功能通常通过 kfunc 而非新的辅助函数来添加。Kfunc 不被视为稳定 API 的一部分，它们有自己的生命周期预期，如 BPF_kfunc_lifecycle_expectations 所述。

### 问：tracepoint 是稳定 ABI 的一部分吗？

答：不是。Tracepoint 与内部实现细节绑定，因此会随更新而改变，并可能随更新的内核而失效。BPF 程序需要在这种情况发生时相应地改变。

### 问：kprobe 可以附加的位置是稳定 ABI 的一部分吗？

答：不是。kprobe 可以附加的位置是内部实现细节，这意味着它们会随更新而改变，并可能随更新的内核而失效。BPF 程序需要在这种情况发生时相应地改变。

### 问：一个 BPF 程序使用多少栈空间？

答：目前所有程序类型都被限制为 512 字节的栈空间，但验证器会计算实际使用的栈数量，并且解释器与大多数 JIT 代码都只消耗必要的数量。

### 问：BPF 可以卸载到硬件吗？

答：可以。BPF 硬件卸载由 NFP 驱动支持。

### 问：经典 BPF 解释器还存在吗？

答：不存在。经典 BPF 程序被转换为扩展 BPF（extended BPF）指令。

### 问：BPF 可以调用任意内核函数吗？

答：不能。BPF 程序只能调用以 BPF 辅助函数或 kfunc 形式暴露的特定函数。可用函数的集合针对每种程序类型定义。

### 问：BPF 可以覆写任意内核内存吗？

答：不能。

追踪类 BPF 程序可以通过 bpf_probe_read() 与 bpf_probe_read_str() 辅助函数**读取**任意内存。网络程序不能读取任意内存，因为它们无法访问这些辅助函数。程序永远不能直接读取或写入任意内存。

### 问：BPF 可以覆写任意用户内存吗？

答：某种程度上可以。

追踪类 BPF 程序可以通过 bpf_probe_write_user() 覆写当前任务的用户内存。每次加载这样的程序时，内核都会打印警告消息，因此该辅助函数仅对实验与原型有用。追踪类 BPF 程序仅限 root。

### 问：通过内核模块添加新功能？

问：BPF 功能，例如新的程序或 map 类型、新的辅助函数等，能否在树外内核模块代码中添加？

答：可以，通过 kfunc 和 kptr。

核心 BPF 功能，如程序类型、map 和辅助函数，不能由模块添加。但是，模块可以通过导出 kfunc（它可能返回指向模块内部数据结构的指针作为 kptr）来向 BPF 程序暴露功能。

### 问：直接调用内核函数是一种 ABI 吗？

问：某些内核函数（例如 tcp_slow_start）可以被 BPF 程序调用。这些内核函数会成为 ABI 吗？

答：不会。

内核函数原型会改变，而 BPF 程序会被验证器拒绝。此外，例如，一些可被 BPF 调用的内核函数已经被其他内核 TCP 拥塞控制（cc）实现使用。如果这些内核函数中的任何一个发生了改变，树内和树外的内核 TCP cc 实现都必须被改变。BPF 程序也一样，必须相应地调整。详见 BPF_kfunc_lifecycle_expectations。

### 问：附加到任意内核函数是一种 ABI 吗？

问：BPF 程序可以附加到许多内核函数。这些内核函数会成为 ABI 的一部分吗？

答：不会。

内核函数原型会改变，附加到它们的 BPF 程序也需要改变。应当使用 BPF 的 compile-once-run-everywhere（CO-RE，一次编译到处运行）来让你的 BPF 程序更容易适配不同版本的内核。

### 问：用 BTF_ID 标记一个函数会使该函数成为 ABI 吗？

答：不会。

BTF_ID 宏并不会使一个函数成为 ABI 的一部分，就像 EXPORT_SYMBOL_GPL 宏那样。

### 问：map 值中特殊 BPF 类型的兼容性如何？

问：允许用户在其 BPF map 值中嵌入 bpf_spin_lock、bpf_timer 字段（当使用 BPF map 的 BTF 支持时）。这允许在这些 map 值中的字段上使用针对此类对象的辅助函数。用户还被允许嵌入指向某些内核类型的指针（使用 __kptr_untrusted 与 __kptr BTF 标签）。内核会为这些特性保留向后兼容性吗？

答：视情况而定。对于 bpf_spin_lock、bpf_timer：会；对于 kptr 以及其他一切：不会，但见下文。

对于已经添加的结构体类型，如 bpf_spin_lock 和 bpf_timer，内核会保留向后兼容性，因为它们是 UAPI 的一部分。

对于 kptr，它们也是 UAPI 的一部分，但仅就 kptr 机制而言。在你的结构体中可以用 __kptr_untrusted 和 __kptr 标记的指针使用的类型，不属于 UAPI 契约。受支持的类型会并且将随内核发布而改变。但是，访问 kptr 字段与 bpf_kptr_xchg() 辅助函数等操作，将在内核发布间为受支持的类型继续得到支持。

对于任何其他受支持的结构体类型，除非本文档中明确说明并加入 bpf.h UAPI 头文件，否则此类类型可以并且将随内核发布任意改变其大小、类型与对齐，或任何其他用户可见的 API 或 ABI 细节。用户必须使他们的 BPF 程序适配新的改变，并更新它们以确保程序继续正确工作。

注意：BPF 子系统特别为类型名保留 'bpf\_' 前缀，以便未来引入更多特殊字段。因此，用户程序必须避免使用带有 'bpf\_' 前缀的类型，以免在未来的发布中被破坏。换句话说，如果在 BTF 中使用带有 'bpf\_' 前缀的类型，不保证向后兼容性。

### 问：分配对象中特殊 BPF 类型的兼容性如何？

问：同上，但针对分配对象（即使用 bpf_obj_new 为用户定义类型分配的对象）。内核会为这些特性保留向后兼容性吗？

答：不会。

与 map 值类型不同，处理分配对象的 API 以及其中对任何特殊字段的支持是通过 kfunc 暴露的，因此具有与 kfunc 本身相同的生命周期预期。详见 BPF_kfunc_lifecycle_expectations。
