## BPF 环形缓冲

本文档描述了 BPF 环形缓冲区的设计、API 与实现细节
    :local:
    :depth: 2

### 背景与动

此项工作有两个截然不同的推动因素，现perf 缓冲区无法满足，这促使我们创建了一种新的环形缓冲区实现
- 通过在各 CPU 之间共享环形缓冲区来实现更高效的内存利用- 保留按时间顺序依次发生的事件的顺序，即便跨越多个 CPU 也不例外（例如一个任务的 fork/exec/exit 事件）
这两个问题相互独立，perf 缓冲区无法同时满足二者。二者均源于为每CPU 单独设置 perf 环形缓冲区的选择。二者也都可以通过采用 MPSC（多生产者单消费者）环形缓冲区实现来解决。排序问题在技术上可以通过 perf 缓冲区内的一些内核计数来解决，但由于第一个问题需MPSC 缓冲区，同样的方案也会自动解决第二个问题
### 语义API


单个环形缓冲区在 BPF 程序中表现为类型`BPF_MAP_TYPE_RINGBUF` 的一BPF map 实例。曾考虑过另外两种方案，但最终都被否决
一种方式是，类似于 `BPF_MAP_TYPE_PERF_EVENT_ARRAY`，使 `BPF_MAP_TYPE_RINGBUF` 能够表示一个环形缓冲区数组，但不强制“仅限同一 CPU”的规则。这将是一个与现有 perf 缓冲区在 BPF 中的用法更兼容、更熟悉的接口，但如果应用程序需要更高级的逻辑来按任意键查找环形缓冲区，它就会失效。`BPF_MAP_TYPE_HASH_OF_MAPS` 用当前的方法解决了这个问题。此外，鉴于 BPF ringbuf 的性能，许多用例会直接选用在所CPU 间共享的单一环形缓冲区，而对这种情况当前的方法未免小题大做
另一种方案会引入一个新概念，与 BPF map 并列，用来表示通用的“容器”对象，它不一定具备带 lookup/update/delete 操作的键/值接口。这种方案会增加大量必须为基础可观测性和验证器支持而构建的基础设施。它还会增加 BPF 开发者需要熟悉的另一个概念，以及 libbpf 中的新语法等。但相比使用 map 的方案，它实际上并没有提供额外的好处。`BPF_MAP_TYPE_RINGBUF` 不支lookup/update/delete 操作，但少数其他 map 类型也不支持（例如队列和栈；数组不支delete 等）
所选方案的优势在于：重用现有的 BPF map 基础设施（内核中的自API、libbpf 支持等），是一个熟悉的概念（无需向用户讲BPF 程序中的新型对象），并且可以利用现有工具（bpftool）。对于在所CPU 上使用单一环形缓冲区的常见场景，它和使用专用的“容器”对象一样简单直接。另一方面，由于它是一map，它可以`ARRAY_OF_MAPS` `HASH_OF_MAPS` map-in-maps 结合使用，以实现各种各样的拓扑结构，从每CPU 一个环形缓冲区（例如，作为 perf 缓冲区用例的替代），到复杂的环形缓冲区哈分片应用（例如，拥有一小池环形缓冲区，以哈希后的任tgid 作为查找键来保持顺序，同时减少争用）
键和值的大小被强制为零。`max_entries` 用于指定环形缓冲区的大小，且必须2 的幂
新的 BPF 环形缓冲区语义与 perf 缓冲区（`BPF_MAP_TYPE_PERF_EVENT_ARRAY`）之间有许多相似之处
- 变长记录- 如果环形缓冲区中没有剩余空间，预留失败，不会阻塞- 供用户空间应用程序进行内存映射的数据区，以便轻松消费并获得高性能- 针对新到达数据的 epoll 通知- 但在必要时，仍具备对数据进行忙轮询以实现最低延迟的能力
BPF ringbuf BPF 程序提供两组 API
- `bpf_ringbuf_output()` 允许将数据从一*复制**到环形缓冲区，类似于 `bpf_perf_event_output()`- `bpf_ringbuf_reserve()` / `bpf_ringbuf_commit()` / `bpf_ringbuf_discard()` 这组 API 将整个过程拆分为两步。首先，预留固定大小的空间。若成功，会返回指向环形缓冲区数据区内一段数据的指针，BPF 程序可以像使用数哈希 map 中的数据一样使用它。准备就绪后，这段内存要么被提交，要么被丢弃。丢弃类似于提交，但会让消费者忽略该记录
`bpf_ringbuf_output()` 的缺点是会产生额外的内存复制，因为记录必须先在别处准备好。但它允许提交长度事先不为验证器所知的记录。它也非常接`bpf_perf_event_output()`，因此会显著简化迁移工作
`bpf_ringbuf_reserve()` 通过直接向环形缓冲区内存提供内存指针，避免了额外的内存复制。在很多情况下，记录大于 BPF 栈空间所允许的大小，因此许多程序需要额外使用每 CPU 数组作为临时堆来准备样本。bpf_ringbuf_reserve() 完全避免了这种需要。但作为交换，它只允许预留已知的常量大小的内存，这样验证器才能验BPF 程序不会访问其预留记录空间之外的内存。bpf_ringbuf_output() 虽然因额外的内存复制而稍慢，却覆盖了一些不适合 `bpf_ringbuf_reserve()` 的用例
提交与丢弃之间的差异非常小。丢弃只是将一条记录标记为已丢弃，这类记录应由消费者代码忽略。丢弃在一些高级用例中很有用，例如确保多记录提交的“全有或全无”，或在单次 BPF 程序调用中模拟临`malloc()` / `free()`
每条被预留的记录都通过现有的引用跟踪逻辑由验证器跟踪，类似于 socket 引用跟踪。因此，不可能预留一条记录却忘记提交（或丢弃）它
`bpf_ringbuf_query()` 辅助函数允许查询环形缓冲区的各种属性。目前支4 个：

- `BPF_RB_AVAIL_DATA` 返回环形缓冲区中未消费数据的数量- `BPF_RB_RING_SIZE` 返回环形缓冲区的大小- `BPF_RB_CONS_POS` / `BPF_RB_PROD_POS` 分别返回消费生产者的当前逻辑位置
返回值是环形缓冲区状态的瞬时快照，在辅助函数返回时可能已过时，因此只应将其用于调报告目的，或用于实现各种启发式方法，这些方法需考虑到这些特征中某些高度可变的性质
其中一种启发式方法可能涉及对关于环形缓冲区中新数据可用性的 poll/epoll 通知进行更细粒度的控制。结合用output/commit/discard 辅助函数`BPF_RB_NO_WAKEUP` / `BPF_RB_FORCE_WAKEUP` 标志，它BPF 程序能够高度控制，例如实现更高效的批量通知。不过，默认的自平衡策略对大多数应用来说应该已经足够，并且能可靠、高效地工作
### 设计与实

这种预留/提交模式为多个生产者（无论是在不同 CPU 上，还是甚至在同一 CPU 同一 BPF 程序中）提供了一种自然的方式，可以预留独立的记录并与之协作，而无需阻塞其他生产者。这意味着，如果某BPF 程序被另一个共享同一环形缓冲区的 BPF 程序中断，它们都将获得一条已预留的记录（只要有足够剩余空间），可以与之协作并独立提交。这也适用NMI 上下文，只是在预留期间使用了自旋锁，NMI 上下文中 `bpf_ringbuf_reserve()` 可能获取不到锁，这种情况下即便环形缓冲区未满，预留也会失败
环形缓冲区本身在内部实现为一个大小为 2 的幂的循环缓冲区，带有两个逻辑上不断递增的计数器（在 32 位架构上可能会回绕，但这不成问题）：

- 消费者计数器显示消费者已消费到哪个逻辑位置- 生产者计数器表示所有生产者已预留的数据量
每次预留记录时，“拥有”该记录的生产者将成功地推进生产者计数器。但此时数据还未准备好被消费。每条记录都8 字节的头部，其中包含预留记录的长度，以及两个额外位：busy 位（表示该记录仍在处理中）和 discard 位（在提交时若记录被丢弃则可能被设置）。在后一种情况下，消费者应当跳过该记录并移动到下一条。记录头部还对记录相对于环形缓冲区数据区起始位置（以页为单位）的偏移量进行了编码。这`bpf_ringbuf_commit()` / `bpf_ringbuf_discard()` 只需接受指向记录本身的指针，而不需要同时传入指向环形缓冲区本身的指针。环形缓冲区的内存位置将从记录元数据头部恢复。这显著简化了验证器，同时也改善了 API 的易用性
生产者计数器的递增在自旋锁下被串行化，因此预留之间有严格的顺序。另一方面，提交则是完全无锁且独立的。所有记录都按预留顺序对消费者可用，但前提是之前的所有记录都已被提交。因此，慢速生产者有可能临时扣留稍晚预留、但已提交的记录
一个有趣的实现细节显著简化了（并因此加速了）生产者和消费者的实现，那就是数据区如何在虚拟内存中连续地背靠背映射两次。这让那些需要在循环缓冲区数据区末尾回绕的样本无需采取任何特殊措施，因为在最后一页数据页之后的下一页会再次是第一页数据页，因此样本在虚拟内存中仍会显得完全连续。参`bpf_ringbuf_area_alloc()` 中的注释以及一个直观展示这一点的简ASCII 示意图
BPF ringbuf 区别perf 环形缓冲区的另一个特性，是对新数据可用性的自定步调通知。`bpf_ringbuf_commit()` 的实现只会在消费者已经追平到正被提交的记录时才会在提交后发送新记录可用的通知。如果没有，消费者仍需追平，因此无论如何都会看到新数据，而无需额外poll 通知。基准测试（tools/testing/selftests/bpf/benchs/bench_ringbufs.c）表明，这可以在不必借助 perf 缓冲区所必需的“每 N 个样本才通知一次”之类的技巧的情况下，实现非常高的吞吐量。在极端情况下，BPF 程序希望对通知进行更手动的控制时，commit/discard/output 辅助函数接受 `BPF_RB_NO_WAKEUP` `BPF_RB_FORCE_WAKEUP` 标志，它们赋予了对数据可用性通知的完全控制能力，但使用该 API 时需要格外小心和谨慎
