## 1. 概述


X86 平台最复杂的部分之一，具体而言，是该平台的虚拟化——即大量可用计时设备的多样性以及模拟这些设备的复杂性。此外，时间的虚拟化引入了一系列新的挑战，因为它引入了超出客户机 CPU 控制范围的、多路复用的时间划分。

首先，我们将介绍各种可用的计时硬件，然后提出其中出现的一些问题以及可用的解决方案，并针对某些类别的 KVM 客户机给出具体建议。

本文档的目的是收集与时间记录相关、且在别处可能难以找到的数据和信息，具体而言，是与 KVM 以及基于硬件的虚拟化相关的信息。

## 2. 计时设备


首先我们讨论可用的基本硬件设备。TSC 以及相关的 KVM clock 足够特殊，值得完整阐述，将在下一节中介绍。

### 2.1. i8254 - PIT


最早可用的计时设备之一是可编程中断定时器，即 PIT。PIT 具有固定的 1.193182 MHz 基准时钟频率，以及三个可配置为产生周期性或单次中断的通道。这三个通道可以以不同模式配置，并拥有各自的计数器。在最初的 IBM PC 中，通道 1 和 2 不对通用用途开放，历史上它们被连接到 RAM 刷新控制和 PC 扬声器。如今 PIT 通常作为模拟芯片组的一部分集成，不再使用独立的物理 PIT。

PIT 使用 I/O 端口 0x40 - 0x43。对 16 位计数器的访问通过对 I/O 端口的单字节或多字节访问完成。共有 6 种模式可用，但并非所有模式对所有定时器都可用，因为只有定时器 2 具有连接好的门控输入，这是模式 1 和 5 所必需的。门控信号线为

```

  --------------             ----------------
  |            |           |                |
  |  1.1932 MHz|---------->| CLOCK      OUT | ---------> IRQ 0
  |    Clock   |   |       |                |
  --------------   |    +->| GATE  TIMER 0  |
                   |        ----------------
                   |
                   |        ----------------
                   |       |                |
                   |------>| CLOCK      OUT | ---------> 66.3 KHZ DRAM
                   |       |                |            (aka /dev/null)
                   |    +->| GATE  TIMER 1  |
                   |        ----------------
                   |
                   |        ----------------
                   |       |                |
                   |------>| CLOCK      OUT | ---------> Port 61h, bit 5
                           |                |      |
  Port 61h, bit 0 -------->| GATE  TIMER 2  |       \_.----   ____
                            ----------------         _|    )--|LPF|---Speaker
                                                    / *----   \___/
  Port 61h, bit 1 ---------------------------------/

```
下面介绍各定时器模式。

模式 0：单次超时。
 这是一种单次软件超时，当门控为高电平时开始倒数（对定时器 0 和 1 始终为真）。当计数到达零时，输出变为高电平。

模式 1：触发式单次。
 输出初始设为高电平。当门控线被置为高电平时，开始倒数（即使门控被拉低也不会停止），期间输出为低电平。当计数到达零时，输出变为高电平。

模式 2：速率发生器。
 输出初始设为高电平。当倒数到 1 时，输出变低一个计数周期，然后回到高电平。数值被重新加载，倒数自动继续。如果门控线变低，计数停止。如果在门控被拉低时输出为低，输出自动变为高电平（这仅影响定时器 2）。

模式 3：方波。
 这产生高/低方波。计数决定脉冲长度，到达零时在高低之间交替。计数仅在门控为高时进行，并在到达零时自动重载。每个时钟计数递减两次，以完整周期速率产生完整的高/低周期。如果计数为偶数，时钟保持高电平 N/2 个计数、低电平 N/2 个计数；如果计数为奇数，时钟高电平 (N+1)/2 个计数、低电平 (N-1)/2 个计数。计数器仅锁存偶数值，因此读取时观察不到奇数值。这是定时器 2 的预期模式，它通过对方波输出进行低通滤波来产生类正弦音调。

模式 4：软件触发。
 在编程此模式并加载计数器后，输出保持高电平直到计数器到达零。然后输出变低一个时钟周期并回到高电平。计数器不会重载。计数仅在门控为高时发生。

模式 5：硬件触发。
 在编程并加载计数器后，输出保持高电平。当门控被拉高时，开始倒数（即使门控被拉低也不会停止）。当计数器到达零时，输出变低一个时钟周期，然后回到高电平。计数器不会重载。

除了正常的二进制计数外，PIT 还支持 BCD 计数。命令端口 0x43 用于设置三个定时器中每一个的计数器和模式。

```

  Bit 7-4: Command (See table below)
  Bit 3-1: Mode (000 = Mode 0, 101 = Mode 5, 11X = undefined)
  Bit 0  : Binary (0) / BCD (1)

```

### 2.2. RTC


最初 PC 中可用的第二个设备是 MC146818 实时时钟。原始器件现已过时，通常由系统芯片组模拟，有时由 HPET 以及一些拼凑的 IRQ 路由来模拟。

RTC 通过 CMOS 变量访问，CMOS 使用一个索引寄存器来控制读取哪些字节。由于只有一个索引寄存器，读取 CMOS 和读取 RTC 都需要锁保护（此外，允许用户空间工具如 hwclock 直接访问 RTC 是危险的，因为它们可能破坏内核对 CMOS 内存的读写）。

RTC 产生一个通常路由到 IRQ 8 的中断。该中断可用作周期性定时器、一个额外的每日一次闹钟，并可在 MC146818 完成 CMOS 寄存器更新后发出中断。中断类型在 RTC 状态寄存器中指示。

即使系统关闭，RTC 也会通过电池供电更新当前时间字段。在进行更新时不应读取当前时间字段，如状态寄存器所示。

时钟使用 32.768kHz 晶振，因此若要让 RTC 按秒计数，应将寄存器 A 的位 6-4 编程为 32kHz 分频器。

### 2.3. APIC


在 Pentium 及之后的处理器上，作为高级可编程中断控制器的一部分，每个 CPU 都有一个板载定时器可用。APIC 通过内存映射寄存器访问，并向每个 CPU 提供中断服务，用于 IPI 和本地定时器中断。

尽管在理论上 APIC 是本地中断安全稳定的来源，但在实践中，由于 APIC CPU 本地内存映射硬件的特殊性，已经出现了许多错误和故障。要注意 CPU 勘误表可能会影响 APIC 的使用，并且可能需要变通方法。此外，其中一些变通方法对虚拟化施加了独特的约束——要么需要因额外的内存映射 I/O 读取而产生额外开销，要么需要可能计算开销更大的额外功能。

由于 APIC 在 Intel 和 AMD 手册中有相当完善的文档，我们在此避免重复细节。需要指出的是，APIC 定时器通过 LVT（本地向量定时器）寄存器编程，能够进行单次或周期性操作，并基于由可编程分频寄存器分频后的总线时钟。

### 2.4. HPET


HPET 相当复杂，最初旨在取代 X86 PC 的 PIT / RTC 支持。这是否会成为现实还有待观察，因为 PC 硬件的事实标准是模拟这些较旧的设备。一些被指定为无遗留设备的系统可能仅支持 HPET 作为硬件定时器设备。

HPET 规范相当松散含糊，要求至少 3 个硬件定时器，但允许实现的自由度以支持更多。它对定时器频率也没有施加固定速率，但确实对频率、误差和斜率施加了一些极值限制。

一般来说，HPET 被推荐作为高精度（相比 PIT / RTC）时间源，它独立于本地变化（因为在任何给定系统中只有一个 HPET）。HPET 也是内存映射的，其存在由 BIOS 通过 ACPI 表指示。

HPET 的详细规范超出了本文档当前的范围，因为它在别处有非常完善的文档。

### 2.5. 片外定时器


若干板卡，包括专有的（看门狗板）和常见的（e1000），在卡上内置有时序芯片，其寄存器可能可供内核或用户态驱动访问。据作者所知，使用这些来为 Linux 或其他内核生成时钟源尚未被尝试，并且通常不被认可，因为这没有遵守约定俗成的规则。这样的定时器设备需要额外的支持才能正确虚拟化，目前不认为重要，因为没有已知的操作系统这样做。

## 3. TSC 硬件


TSC（时间戳计数器）在理论上相对简单；它统计处理器发出的指令周期数，可用作时间的度量。在实践中，由于一系列问题，它其实是使用起来最复杂的时间记录设备。

TSC 在内部表示为一个 64 位 MSR，可用 RDMSR、RDTSC 或 RDTSCP（可用时）指令读取。过去，硬件限制使得可以写入 TSC，但在旧硬件上通常只能写入 64 位计数器的低 32 位，而计数器的高 32 位被清零。然而现在，在 Intel 处理器家族 0Fh 的型号 3、4 和 6，以及家族 06h 的型号 e 和 f 上，这一限制已被解除，所有 64 位都可写。在 AMD 系统上，写入 TSC MSR 的能力并不是架构层面的保证。

TSC 可从 CPL-0 访问；对于 CPL > 0 的软件，则通过 CR4.TSD 位有条件地访问，该位启用时会禁用 CPL > 0 的 TSC 访问。

一些厂商实现了额外的指令 RDTSCP，它不仅能原子地返回 TSC，还返回与处理器编号对应的指示值。这可用于索引到一组 TSC 变量数组，以确定在 TSCs 未同步的 SMP 系统中的偏移信息。该指令的存在必须通过查询 CPUID 特性位来确定。

VMX 和 SVM 都在虚拟化硬件中提供扩展字段，允许客户机可见的 TSC 偏移一个常量。较新的实现承诺允许 TSC 额外进行缩放，但这类硬件尚未广泛可用。

### 3.1. TSC 同步


在大多数实现中，TSC 是 CPU 本地的时钟。这意味着在 SMP 平台上，不同 CPU 的 TSC 可能根据 CPU 上电时间的不同而起始时间不同。一般来说，同一晶片上的 CPU 会共享相同时钟，然而并非总是如此。

BIOS 可能尝试在上电过程中重新同步 TSCs，操作系统或其他系统软件也可能尝试这样做。若干硬件限制使问题更加严重——如果无法写入 TSC 的全部 64 位，就可能无法使新到达的 CPU 的 TSC 与系统其余部分匹配，从而导致 TSC 不同步。这可能由 BIOS 或系统软件完成，但在实践中，除非所有值都从同一时钟读取（这通常只有在单插槽系统或具有特殊硬件支持的系统中才可能），否则不可能获得完美同步的 TSC。

### 3.2. TSC 与 CPU 热插拔


如前所述，晚于系统启动时间到达的 CPU 可能没有一个与系统其余部分同步的 TSC 值。系统软件、BIOS 或 SMM 代码实际上可能尝试将 TSC 建立为与系统其余部分匹配的值，但通常不能保证完美匹配。这可能产生这样的效果：使系统从 TSC 已同步的状态退回到可能向操作系统和任何虚拟化环境暴露 TSC 同步缺陷（无论多小）的状态。

### 3.3. TSC 与多插槽 / NUMA


多插槽系统，特别是大型多插槽系统，很可能具有各自的时钟源，而不是单一的、普遍分布的时钟。由于这些时钟由不同的晶振驱动，它们不会具有完全匹配的频率，并且温度和电气变化将导致 CPU 时钟以及随之的 TSC 随时间漂移。根据具体的时钟和总线设计，漂移在绝对误差上可能是固定的，也可能不是，并且可能随时间累积。

此外，非常大的系统可能有意对已斜率调整（slew）各个核心的时钟。这种称为扩频时钟（spread-spectrum clocking）的技术可降低时钟频率及其谐波处的 EMI，这可能是通过电信和计算机设备的 FCC 标准所必需的。

出于这些原因，建议不要信赖 TSC 在 NUMA 或多插槽系统上保持同步。

### 3.4. TSC 与 C-states


C-states，即处理器的空闲状态，特别是 C1E 及更深的睡眠状态，对 TSC 也可能存在问题。TSC 可能在此类状态下停止前进，导致恢复执行时 TSC 落后于其他 CPU。此类 CPU 必须由操作系统基于 CPU 和芯片组标识进行检测并标记。

在这种情况下，TSC 可以通过赶上已知的外部时钟源来进行校正。

### 3.5. TSC 频率变化 / P-states


为了让事情更有趣一点，一些 CPU 可能会改变频率。它们可能以相同速率运行 TSC，也可能不；并且由于频率变化可能是错开或斜率调整（slewed）的，在某些时刻，TSC 速率可能只知道落在一个数值范围内。在这种情况下，TSC 不会是稳定的时间源，必须根据已知的、稳定的外部时钟进行校准才能成为可用的时间源。

TSC 是以恒定速率运行还是随 P-state 缩放，取决于型号，必须通过检查 CPUID、芯片组或厂商特定的 MSR 字段来确定。

此外，一些厂商存在已知缺陷：在正常操作中 P-state 实际上得到了正确补偿，但当处理器空闲时，P-state 可能被临时提高以服务于来自其他处理器的缓存未命中。在这种情况下，处于停机状态的 CPU 上的 TSC 可能比非停机处理器上的 TSC 前进得更快。已知 AMD Turion 处理器存在此问题。

### 3.6. TSC 与 STPCLK / T-states


给处理器的外部信号也可能产生停止 TSC 的效果。这通常用于热紧急功率控制以防止过热情况，并且通常无法检测到这种情况的发生。

### 3.7. TSC 虚拟化 - VMX


VMX 提供对 RDTSC、RDMSR、WRMSR 和 RDTSCP 指令的有条件捕获，这足以以任何方式完全虚拟化 TSC。此外，VMX 允许透传主机 TSC 加上 VMCS 中指定的额外 TSC_OFFSET 字段。必须使用特殊指令来读写 VMCS 字段。

### 3.8. TSC 虚拟化 - SVM


SVM 提供对 RDTSC、RDMSR、WRMSR 和 RDTSCP 指令的有条件捕获，这足以以任何方式完全虚拟化 TSC。此外，SVM 允许透传主机 TSC 加上 SVM 控制块中指定的额外偏移字段。

### 3.9. Linux 中的 TSC 特性位


总之，除非由架构明确保证，否则无法保证 TSC 保持完美同步。即使如此，多插槽或 NUMA 系统中的 TSC 尽管在本地一致，仍可能独立运行。

Linux 使用以下特性位来指示各种 TSC 属性，但它们只能被认为对 UP 或单节点系统有意义。

=========================	=======================================
X86_FEATURE_TSC			TSC 在硬件上可用
X86_FEATURE_RDTSCP		RDTSCP 指令可用
X86_FEATURE_CONSTANT_TSC	TSC 速率不随 P-states 改变
X86_FEATURE_NONSTOP_TSC		TSC 在 C-states 中不停止
X86_FEATURE_TSC_RELIABLE	跳过 TSC 同步检查 (VMware)
=========================	=======================================

## 4. 虚拟化问题


时间记录对虚拟化来说尤其成问题，因为出现了许多挑战。最明显的问题是，时间现在在宿主机以及可能的大量虚拟机之间共享。因此虚拟操作系统并非以 100% 的 CPU 占用率运行，尽管它很可能做出这样的假设。它可能期望在中断源被禁用时保持在非常严格的界限内为真，但实际上只有它的虚拟中断源被禁用，机器仍可能在任何时候被抢占。这会导致问题，因为真实时间的流逝、机器中断的注入以及相关的时钟源不再与真实时间完全同步。

同样的问题在原生硬件上也可能在一定程度上发生，因为当 BIOS 使用 SMM 模式时，SMM 模式可能从 X86 系统上窃取周期，但程度没有这么极端。然而，SMM 模式可能引起与虚拟化类似的问题这一事实，成为在裸机上解决其中许多问题的良好理由。

### 4.1. 中断计时


遗留操作系统出现的最直接的问题之一是，系统时间记录例程通常设计为通过统计周期性中断来跟踪时间。这些中断可能来自 PIT 或 RTC，但问题是相同的：宿主机虚拟化引擎可能无法每秒交付正确数量的中断，因此客户机时间可能落后。如果选择了高中断速率（例如 1000 HZ，不幸的是这是许多 Linux 客户机的默认值），这个问题尤其严重。

解决这个问题有三种方法；首先，可能只需简单地忽略它。拥有用于跟踪“墙上时钟”或“真实时间”的单独时间源的客户机可能不需要对其中断进行任何调整来维持正确时间。如果这还不够，可能有必要向客户机注入额外的中断以提高有效中断速率。这种方法在极端条件下会导致复杂情况，即宿主机负载或客户机滞后过大而无法补偿，因此出现了另一种解决方案：客户机可能需要意识到丢失的时钟节拍（tick）并在内部进行补偿。尽管在理论上很有前景，但这种策略在 Linux 中的实现极其容易出错，许多有缺陷的丢失 tick 补偿变体分布在常用的 Linux 系统中。

Windows 使用周期性 RTC 计时作为内部保持时间的手段，因此需要中断斜率调整（slewing）来保持正确时间。不过它使用的速率足够低（编者注：是 18.2 Hz 吗？），因此在实践中尚未成为问题。

### 4.2. TSC 采样与串行化


作为可用的最高精度时间源，CPU 的周期计数器引起了开发者的浓厚兴趣。如上所述，这个定时器有许多因其作为本地、潜在不稳定且潜在未同步源的本质而产生的独特问题。有一个问题并非 TSC 独有，但因其极高的精度特性而被凸显出来，即采样延迟。根据定义，计数器一旦被读取就已经是旧的了。然而，也可能在实际使用结果之前就读取了计数器。这是指令流超标量执行的结果，它可能乱序执行指令。这种执行称为非串行化。为了使用 TSC 进行精确测量，强制串行化执行是必要的，并且需要串行化指令，例如 CPUID 或 MSR 读取。

由于 CPUID 实际上可能通过捕获与模拟机制进行虚拟化，这种串行化可能对硬件虚拟化造成性能问题。因此，准确的 TSC 读取可能并不总是可用，并且实现可能需要防止从其他 CPU 视角看到的 TSC“倒退”读取，即使在其他方面完美同步的系统中也是如此。

### 4.3. Timespec 别名


此外，当将 TSC 的结果与另一个时间源对照使用时，TSC 缺乏串行化带来了另一个挑战。由于 TSC 精度高得多，在另一个时钟仍表达相同值时，可能读取到许多可能的 TSC 值。

也就是说，当外部时钟 C 保持相同值时，你可能读取到 (T,T+10)。由于非串行化读取，你实际上可能得到波动的范围——从 (T-1.. T+10)。因此，任何从 TSC 计算得到、但基于外部值校准的时间都可能有一系列有效值。重新校准该计算实际上可能导致校准后计算出的时间，相对于校准前计算出的时间，发生倒退。

这个问题在 Linux 的内部时间源——内核时间——上尤为明显，它以理论上高分辨率的 timespec 表示，但以大得多的粒度间隔前进，有时以 jiffies 的速率，并可能在追赶模式下以大得多的步长前进。

这种别名效应要求在对 kvmclock 以及任何源自 TSC 计算的其他值（例如 TSC 虚拟化本身）进行计算和重新校准时小心处理。

### 4.4. 迁移


虚拟机的迁移在两个方面给时间记录带来问题。首先，迁移本身可能耗时，在此期间无法交付中断，之后客户机时间可能需要追赶。NTP 可能在某种程度上有所帮助，因为所需的时钟校正通常足够小，落在 NTP 可校正窗口内。

另一个担忧是，基于 TSC（或 HPET，如果暴露了原始总线时钟）的定时器现在可能以不同的速率运行，需要在管理程序中以某种方式通过虚拟化这些定时器来进行补偿。此外，迁移到更快的机器可能排除使用透传 TSC，因为更快的时钟如果不潜在地让时间比平时前进得更快，就无法对客户机可见。较慢的时钟问题较小，因为它总是可以追赶回原始速率。KVM clock 通过简单地针对 TSC 存储乘数和偏移，供客户机转换回纳秒分辨率的值，从而避免这些问题。

### 4.5. 调度


由于调度可能基于精确计时和中断触发，操作系统的调度算法可能受到虚拟化的不利影响。在理论上，这种影响是随机的，应当普遍分布，但在人为构造以及真实场景中（客户机设备访问、虚拟化退出的原因、可能的上下文切换），情况可能并非总是如此。这种影响尚未被充分研究。

为了规避这一点，若干实现提供了半虚拟化的调度器时钟，它揭示虚拟机已经运行的真实 CPU 时间量。

### 4.6. 看门狗


看门狗定时器，例如 Linux 中的锁检测器，在硬件虚拟化下运行时，可能由于定时器中断被延迟或对真实时间流逝的误解而意外触发。通常这些警告是虚假的，可以忽略，但在某些情况下可能有必要禁用此类检测。

### 4.7. 延迟与精确计时


在虚拟化系统中，可能无法实现精确计时和延迟。如果系统正在控制物理硬件，或者发出延迟以补偿与设备之间较慢的 I/O，就会发生这种情况。第一个问题一般来说在虚拟化系统中无法解决；如果没有完整的实时操作系统，硬件控制软件无法被充分虚拟化，而这将需要一个感知 RT 的虚拟化平台。

第二个问题可能导致性能问题，但不太可能成为重大问题。在许多情况下，这些延迟可以通过配置或半虚拟化消除。

### 4.8. 隐蔽通道与信息泄漏


除了上述问题之外，在除完美虚拟化时间实现之外的任何情况下，时间信息都不可避免地会泄漏给客户机关于宿主机的信息。这可能允许客户机推断管理程序的存在（如 red-pill 类型的检测），并且它可能允许通过使用 CPU 利用率本身作为信号通道在客户机之间泄漏信息。防止此类问题将需要完全隔离的虚拟时间，这可能不再跟踪真实时间。这在某些安全或 QA 场景中可能有用，但通常不推荐用于实际部署场景。
