## 什么是 NUMA？

这个问题可以从几个不同的角度来回答：硬件视角与 Linux 软件视角。

从硬件角度看，NUMA 系统是一种计算机平台，它由多个组件或部件组成，其中每一个都可能包含 0 个或多个 CPU、本地内存和/或 IO 总线。为了简洁，也为了把对这些物理组件/部件的硬件视角与其软件抽象区分开来，本文档中我们将这些组件/部件称为“单元”（cell）。

每个“单元”都可视为该系统的一个 SMP（对称多处理器）子集——尽管构成一个独立 SMP 系统所必需的某些组件未必会在某个给定单元上配备齐全。NUMA 系统的各个单元通过某种系统互连连接在一起——例如，交叉开关（crossbar）或点对点链路是常见的 NUMA 系统互连类型。这两种互连类型都可以聚合起来，构建出其中单元与其他单元相距多种距离的 NUMA 平台。

对 Linux 而言，我们所关注的 NUMA 平台主要是所谓的缓存一致性 NUMA（Cache Coherent NUMA，即 ccNUMA）系统。在 ccNUMA 系统中，所有内存对任何连接到任一单元的 CPU 都是可见且可访问的，缓存一致性由处理器缓存和/或系统互连在硬件层面处理。

内存访问时间和有效内存带宽，取决于发起内存访问的 CPU 或 IO 总线所在单元，与目标内存所在单元之间的距离远近。例如，连接到同一单元的 CPU 访问内存，比访问其他远程单元上的内存具有更快的访问时间与更高的带宽。NUMA 平台中，任一给定单元都可以与处于多种远程距离的单元相连。

平台厂商构建 NUMA 系统并非为了让软件开发者日子“有趣”。相反，这种架构是一种提供可扩展内存带宽的手段。然而，要获得可扩展的内存带宽，系统和应用软件必须让绝大多数内存引用（缓存缺失）都指向“本地”内存——即同一单元上的内存（如果有的话）——或者指向拥有内存的最近单元。

这就引出了 Linux 对 NUMA 系统的软件视角：

Linux 将系统的硬件资源划分为多个称为“节点”（node）的软件抽象。Linux 把这些节点映射到硬件平台的物理单元上，对某些架构则抽象掉部分细节。与物理单元一样，软件节点可以包含 0 个或多个 CPU、内存和/或 IO 总线。同样，对映射到更近单元的“更近”节点进行内存访问，通常比访问更远的单元具有更快的访问时间与更高的有效带宽。

对某些架构（例如 x86），Linux 会“隐藏”任何没有挂载内存的物理单元所对应的节点，并把连接到该单元的 CPU 重新分配给代表有内存单元的节点。因此，在这些架构上，不能假定 Linux 关联到某个给定节点的所有 CPU 都会看到相同的本地内存访问时间与带宽。

此外，对某些架构（同样以 x86 为例），Linux 支持仿真出额外的节点。对于 NUMA 仿真，Linux 会把现有节点——或者非 NUMA 平台的系统内存——切分为多个节点。每个被仿真的节点将管理底层单元物理内存的一部分。NUMA 仿真在非 NUMA 平台上测试 NUMA 内核与应用特性时很有用，并且与 cpusets 配合使用时，还可作为一种内存资源管理机制。
[see Documentation/admin-guide/cgroup-v1/cpusets.rst]

对于每个拥有内存的节点，Linux 构建了一个独立的内存管理子系统，配有自身的空闲页链表、在用页链表、使用统计以及用于协调访问的锁。此外，Linux 为每个内存域（zone，即 DMA、DMA32、NORMAL、HIGH_MEMORY、MOVABLE 中的一个或多个）构建一个有序的“zonelist”。zonelist 指定了当所选 zone/node 无法满足分配请求时要访问的 zone/node。当某个 zone 没有可用内存来满足请求时，这种情况被称为“溢出”（overflow）或“回退”（fallback）。

由于某些节点包含多个持有不同类型内存的 zone，Linux 必须决定 zonelist 的排序方式：是回退到另一节点上同类型的 zone，还是回退到同一节点上不同类型的 zone。这是一个重要的考量点，因为某些 zone（如 DMA 或 DMA32）代表的是相对稀缺的资源。Linux 默认选择按节点（Node）排序的 zonelist，这意味着它会先尝试回退到同一节点的其他 zone，然后才使用按 NUMA 距离排序的远程节点。

默认情况下，Linux 会尝试从执行分配请求的 CPU 所隶属的节点来满足内存分配请求。具体而言，Linux 会尝试从请求发起节点对应 zonelist 中的第一个节点分配。这称为“本地分配”（local allocation）。如果“本地”节点无法满足请求，内核会检查所选 zonelist 中其他节点的 zone，寻找列表中第一个能够满足请求的 zone。

只要内核为之分配内存的那个任务后来不迁离该内存，本地分配就会使后续对已分配内存的访问保持在底层物理资源的“本地”，而不经过系统互连。Linux 调度器知晓平台的 NUMA 拓扑——体现在“调度域”（scheduling domains）数据结构中 [see Documentation/scheduler/sched-domains.rst]——并会尽量减少任务向远程调度域的迁移。不过，调度器并不会直接考虑任务的 NUMA 占用（NUMA footprint）。因此，在出现足够不均衡时，任务可能在节点之间、以及远离其初始节点和内核数据结构的地方迁移。

系统管理员和应用设计者可以利用各种 CPU 亲和性命令行接口（如 taskset(1) 和 numactl(1)）以及编程接口（如 sched_setaffinity(2)）来限制任务迁移，从而改善 NUMA 局部性。此外，还可以借助 Linux NUMA 内存策略来修改内核默认的本地分配行为。[see Documentation/admin-guide/mm/numa_memory_policy.rst]。

系统管理员可以通过控制组和 CPUsets，限制非特权用户在调度或 NUMA 命令与函数中可指定的 CPU 和节点内存。[see Documentation/admin-guide/cgroup-v1/cpusets.rst]

在不隐藏无内存节点的架构上，Linux 只会把拥有内存的 zone（节点）纳入 zonelist。这意味着，对于一个无内存节点，“本地内存节点”——即 CPU 所在节点 zonelist 中第一个 zone 所属的节点——将不会是该节点自身，而是内核在构建 zonelist 时选为最近的有内存节点。因此，默认的本地分配会成功，由内核提供最近可用内存。这是同一机制的结果，正是该机制使得当某个确实含内存的节点溢出时，分配可以回退到附近的其他节点。

某些内核分配并不希望、也无法容忍这种分配回退行为。它们更希望确保从指定节点获得内存，或者获知该节点没有空闲内存。子系统分配每 CPU 内存资源时通常就属于这种情况。

进行此类分配的典型模型是：先用内核的 numa_node_id() 或 CPU_to_node() 函数之一获取“当前 CPU”所隶属节点的节点 id，然后只从该返回的节点 id 请求内存。当这类分配失败时，发起请求的子系统可能回退到它自己的回退路径——slab 内核内存分配器就是一例。或者，该子系统也可能选择在被分配失败时不启用或禁用自身——内核性能分析（profiling）子系统就是一例。

如果架构支持（即不隐藏）无内存节点，那么连接到无内存节点的 CPU 将始终承担回退路径开销，或者某些子系统若试图仅从无内存的节点分配内存则会初始化失败。为了透明地支持这类架构，内核子系统可以使用 numa_mem_id() 或 cpu_to_mem() 函数来定位调用 CPU 或指定 CPU 的“本地内存节点”。同样，这正是默认本地页分配所会尝试的节点。
