
## 页表


分页虚拟内存是在 1962 年随着虚拟内存这一概念的提出、在 Ferranti Atlas 计算机上被发明的，那也是第一台具有分页虚拟内存的计算机。该特性随后迁移到更新的计算机上，并随着时间推移成为所有类 Unix 系统事实上的标准特性985 年，该特性被纳入 Intel 80386，Linux 1.0 正是基于CPU 开发的
页表CPU 所看到的虚拟地址映射为外部内存总线上所看到的物理地址
Linux 将页表定义为一个层级结构，目前高度为五级。每种受支持架构的架构代码随后会将这一层级结构映射到硬件的限制上
与虚拟地址相对应的物理地址通常由底层的物理页框引用*页框**page frame number**，简**pfn**）是页（如外部内存总线上所见）的物理地址除以 `PAGE_SIZE` 所得的结果
物理内存地址 0 即为 **pfn 0**，而最高的 pfn 则是 CPU 外部地址总线所能寻址的物理内存的最后一页
4KB 页粒度与 32 位地址范围下，pfn 0 位于地址 0x00000000，pfn 1 位于地址 0x00001000，pfn 2 位于 0x00002000，依此类推，直到 pfn 0xfffff 位于 0xfffff000。在 16KB 页的情况下，pfn 位于 0x00004000x00008000 0xffffc000，pfn 取值从 0 0x3ffff
如你所见，4KB 页的情况下，页基地址使用地址bit 12-31，这就是 `PAGE_SHIFT` 在此情况下被定义12，`PAGE_SIZE` 通常按页移位定义`(1 << PAGE_SHIFT)` 的原因
随着内存容量的不断增长，人们逐步发展出更深的层级结构。在 Linux 创建之初，使用的4KB 页以及一个拥1024 个条目的称为 `swapper_pg_dir` 的单级页表，覆盖 4MB，这恰好Torvalds 的第一台计算机拥有 4MB 物理内存的事实相符。该单级表中的条目被称为 **PTE**——页表项
软件层面的页表层级反映了这样一个事实：页表硬件本身已变得层级化，而这反过来又是为了节省页表内存并加快映射速度
当然，人们可以设想一种单一、线性的页表，拥有数量极大的条目，将整个内存拆分成单个页。但这种页表会非常稀疏，因为虚拟内存的很大一部分通常处于未使用状态。通过使用层级化的页表，虚拟地址空间中的大段空洞不会浪费宝贵的页表内存，因为在页表层级中只需在更高层级将大片区域标记为未映射即可
此外，在现代 CPU 上，高层级的页表项可以直接指向一段物理内存范围，从而允许在单个高层级页表项中映射连续的若干兆字节甚至若干吉字节的范围，在将虚拟内存映射到物理内存时走捷径：当你找到这样一个被映射的大范围时，无需继续向更深层遍历
```

  +-----+
  | PGD |
  +-----+
     |
     |   +-----+
     +-->| P4D |
         +-----+
            |
            |   +-----+
            +-->| PUD |
                +-----+
                   |
                   |   +-----+
                   +-->| PMD |
                       +-----+
                          |
                          |   +-----+
                          +-->| PTE |
                              +-----+



```
页表层级不同层级上的符号，从底层往上，具有如下含义
- **pte**, `pte_t`, `pteval_t` = **页表项（Page Table Entry* - 前面已提及  **pte** 是一个由 `PTRS_PER_PTE` `pteval_t` 类型元素组成的数组，每个元素将单页虚拟内存映射到单页物理内存。架构定义了 `pteval_t` 的大小和内容
  一个典型的例子是，`pteval_t` 是一32 位或 64 位的值，其高位是 **pfn**（页框号），低位则是一些架构特定的位，例如内存保护位
  名称中的 **entry** 部分有些容易令人困惑：在 Linux 1.0 中，它确实指代单级顶层页表中的单个页表项；但在首次引入两级页表时，它被改造成一组映射元素的数组，因**pte** 是最底层的页***，而非页表***
- **pmd**, `pmd_t`, `pmdval_t` = **页中间目录（Page Middle Directory*，即紧邻 **pte** 上方的层级，包含 `PTRS_PER_PMD` 个指**pte** 的引用
- **pud**, `pud_t`, `pudval_t` = **页上层目录（Page Upper Directory*，是在其他层级之后引入以处理四级页表的。它可能被闲置未用，或被**折叠**，稍后将对此进行讨论
- **p4d**, `p4d_t`, `p4dval_t` = **4 级页目录（Page Level 4 Directory*，是**pud** 引入之后为处理五级页表而引入的。此时已经很清楚，我们需要用表示目录层级的数字来替换 **pgd***pmd***pud** 等名称，不能再继续沿用临时的命名了。该层级仅在实际拥有五级页表的系统上使用，否则会被折叠
- **pgd**, `pgd_t`, `pgdval_t` = **页全局目录（Page Global Directory* - Linux 内核处理内核内存 PGD 的主页表仍位`swapper_pg_dir` 中，但系统中的每个用户空间进程也都拥有自己的内存上下文，因而也有自己的 **pgd**，它位于 `struct mm_struct` 中，而后者又被每`struct task_struct` 所引用。因此，任务`struct mm_struct` 的形式拥有内存上下文，而该结构体又含有一个指向相应页全局目录`struct pgt_t *pgd` 指针
重申一下：页表层级中的每个层级都是一*指针数组**，因**pgd** 包含 `PTRS_PER_PGD` 个指向下一层的指针*p4d** 包含 `PTRS_PER_P4D` 个指**pud** 项的指针，依此类推。层级的个数
```

        PMD
  --> +-----+           PTE
      | ptr |-------> +-----+
      | ptr |-        | ptr |-------> PAGE
      | ptr | \       | ptr |
      | ptr |  \        ...
      | ... |   \
      | ptr |    \         PTE
      +-----+     +----> +-----+
                         | ptr |-------> PAGE
                         | ptr |
                           ...



```
## 页表折叠


如果某个架构不使用全部的页表层级，它们可以被**折叠**，即被跳过，所有针对页表的操作都会在编译期被增强，以便在访问下一更低层级时直接跳过该层级
希望做到架构中立的页表处理代码（例如虚拟内存管理器）需要以遍历当前全部五个层级的方式来编写。架构相关代码也应优先采用这种风格，以便对未来的变更具有鲁棒性

## MMU、TLB 与页错误


`Memory Management Unit (MMU)`（内存管理单元）是一个负责处理虚拟地址到物理地址转换的硬件组件。它可能会使用硬件中相对较小的缓存，称为 `Translation Lookaside Buffers (TLBs)`（转译旁路缓冲）`Page Walk Caches`（页遍历缓存），来加速这些转换
CPU 访问某个内存位置时，它向 MMU 提供一个虚拟地址，MMU 随后检TLB 或页遍历缓存（在支持它们的架构上）中是否已存在相应的转换。如果找不到转换，MMU 就使用页遍历来确定物理地址并建立映射
当页被写入时，该页的脏位被置位（即开启）。每个内存页都关联有权限位和脏位。后者表示该页自被载入内存以来已被修改
若没有任何因素阻止，物理内存最终可以被访问，对所请求的物理页框的操作也会被执行
MMU 找不到某些转换的原因有多种。可能是因为 CPU 正试图访问当前任务无权访问的内存，或者是因为数据并不存在于物理内存中
当这些条件发生时，MMU 会触发页错误，这是一种异常类型，它向 CPU 发出信号，使其暂停当前执行并运行一个专门的函数来处理上述异常
页错误有一些常见且可预期的原因。它们由称为 “Lazy Allocation”（惰性分配）“Copy-on-Write”（写时复制）的进程管理优化技术触发。当页框已被换出到持久化存储（交换分区或交换文件）并从物理位置上被驱逐时，也可能发生页错误
这些技术提升了内存效率、降低了延迟并最小化了空间占用。本文档不会深入 “Lazy Allocation“Copy-on-Write的细节，因为它们属于进程地址管理的范畴，不在本文讨论范围之内
交换（Swapping）与上述其他技术的不同之处在于，它是不被期望发生的，因为它是在内存承受巨大压力时作为缓解手段而执行的
交换无法作用于由内核逻辑地址映射的内存。这些是内核虚拟空间的一个子集，直接映射了一段连续的物理内存。给定任意逻辑地址，其物理地址只需对一个偏移量做简单算术即可确定。访问逻辑地址速度很快，因为它们避免了复杂的页表查找，代价是这些页框不可被驱逐、也不可被换出
如果内核未能为必须存在于物理页框中的数据腾出空间，内核就会调用内存耗尽（OOM）杀手，通过终止低优先级进程来腾出空间，直到压力降到安全的阈值以下
此外，页错误也可能由代码缺陷或蓄意构造的、指CPU 访问的地址所引发。进程的一个线程可能使用指令去寻址不属于其自身地址空间的内存（非共享内存），或者可能试图执行一条想要写入只读位置的指令
如果上述情况发生在用户空间，内核会向当前线程发`Segmentation Fault`（段错误，SIGSEGV）信号。该信号通常会导致该线程及其所属进程的终止
本文档将Linux 内核如何处理这些页错误、如何创建页表及其表项、如何检查内存是否存在，如果不存在则请求从持久化存储或其他设备载入数据，并更MMU 及其缓存，进行简化并给出一个高层次的概览
最初的若干步骤是架构相关的。大多数架构跳转`do_page_fault()`，x86 的中断处理程序由 `DEFINE_IDTENTRY_RAW_ERRORCODE()` 宏定义，该宏调用 `handle_page_fault()`
无论走哪条路径，所有架构最终都会调用到 `handle_mm_fault()`，而后者（通常）最终会调用 `__handle_mm_fault()` 来实际完成分配页表的工作
若不幸无法调`__handle_mm_fault()`，则意味着该虚拟地址指向的是当前上下文（至少）无权访问的物理内存区域。这一情况会导致内核向进程发送上述的 SIGSEGV 信号，并产生前面已说明的后果
`__handle_mm_fault()` 通过调用若干函数来完成其工作，以查找页表上层各层的表项偏移，并分配它所需的表
用于查找偏移的函数名称形`*_offset()`，其对应 pgd、p4d、pud、pmd、pte；而用于逐层分配相应表的函数则称`*_alloc`，沿用上述约定，以层级中对应表的类型来命名
页表遍历可能在某个中间或上层（PMD、PUD）处结束
Linux 支持比通常4KB 更大的页尺寸（即所`huge pages`，大页）。在使用这类更大的页时，更高层的页可以直接映射它们，无需使用更低层的页表项（PTE）。大页包含通常2MB 1GB 不等的大段连续物理区域，分别PMD PUD 页表项所映射
大页带来了若干好处，例如降低 TLB 压力、减少页表开销、提高内存分配效率，以及为某些工作负载带来性能提升。然而，这些好处也伴随着权衡，例如内存浪费和分配困难
在遍历与分配的最末端，如果没有返回错误，`__handle_mm_fault()` 最终会调用 `handle_pte_fault()`，后者经`do_fault()` 执行 `do_read_fault()`、`do_cow_fault()`、`do_shared_fault()` 之一。“read”（读）、“cow”（写时复制）、“shared”（共享）给出了它正在处理的错误的成因与类型提示
该工作流的实际实现非常复杂。其设计允许 Linux 以针对每种架构具体特性量身定制的方式来处理页错误，同时仍共享一个共同的整体结构
作为 Linux 如何处理页错误这一高层次概览的总结，补充一点：页错误处理程序可以分别通过 `pagefault_disable()` `pagefault_enable()` 来禁用和启用
若干代码路径会用到上述两个函数，因为它们需要禁用陷入页错误处理程序，主要是为了防止死锁
