## 高端内存处理


作者：Peter Zijlstra <a.p.zijlstra@chello.nl>


## 什么是高端内存

当物理内存的大小接近或超过虚拟内存的最大大小时，就会使用高端内存（highmem）。在那种
情况下，内核无法始终将所有可用的物理内存都映射起来。这意味着内核需要开始使用临时映来访问它想要访问的那些物理内存片段
没有被永久映射所覆盖的那部分（物理）内存，就是我们所说的"高端内存"。关于那条边究竟在哪里，有各种与体系结构相关的约束
例如i386 架构上，我们选择将内核映射到每个进程VM 空间中，这样我们就不必为内核
的进退出付出完整的 TLB 失效代价。这意味着可用的虚拟内存空间（i386 上为 4GiB必须在用户空间和内核空间之间划分
使用这种方法的架构传统的分割比例3:1，用户空3GiB，内核空```

		+--------+ 0xffffffff
		| Kernel |
		+--------+ 0xc0000000
		|        |
		| User   |
		|        |
		+--------+ 0x00000000

```
这意味着内核在任何时刻最多只能映1GiB 的物理内存，但由于我们还需要虚拟地址空间用于
其他事情——包括用于访问其余物理内存的临时映射——实际的直接映射通常会更小（通常~896MiB）
其他具有mm 上下文标记的 TLB 的架构可以拥有独立的内核和用户映射。不过，某些硬件
（如某些 ARM）在使用 mm 上下文标记时虚拟空间有限

## 临时虚拟映射


内核包含多种创建临时映射的方式。以下列表按使用优先级顺序列出它们
- kmap_local_page()、kmap_local_folio() - 这些函数用于创建短期映射。它们可以从任何
  上下文（包括中断）调用，但这些映射只能在获取它们的上下文中使用。它们之间唯一的区  在于：第一个函数接受指struct page 的指针，第二个函数接受指struct folio 的指  以及用于标识该页folio 内字节偏移
  应当始终使用这些函数，kmap_atomic() kmap() 已被废弃
  这些映射是线程局部和 CPU 局部的，意味着映射只能从该线程内部访问，并且在映射处于活动
  状态时该线程被绑定到该 CPU。虽然此函数从不禁用抢占（preemption），但在映射被释放之前，
  CPU 无法通过 CPU 热插拔（CPU-hotplug）从系统中拔出
  在本kmap 区域中发生缺页（pagefault）是合法的，除非获取本地映射的上下文由于其他原因
  不允许这样做
  如前所述，缺页和抢占永远不会被禁用。没有必要禁用抢占，因为当上下文切换到不同的任务时，
  离开任务的映射会被保存，而进入任务的映射会被恢复
  kmap_local_page() 以及 kmap_local_folio() 总是返回有效的虚拟内核地址，并且假  kunmap_local() 永远不会失败
  CONFIG_HIGHMEM=n 的内核上，对于低端内存页，它们返回直接映射的虚拟地址。只有真正的
  高端内存页才会被临时映射。因此，对于已知不是来自 ZONE_HIGHMEM 的页，用户可以调用普通的
  page_address()。不过，使用 kmap_local_{page,folio}() / kunmap_local() 始终安全
  虽然它们kmap() 快得多，但对于高端内存的情况，它们对指针的有效性有一些限制。与
  kmap() 映射不同，本地映射仅在调用者的上下文中有效，不能传递给其他上下文。这意味着用户
  必须绝对确保返回地址的使用仅限于映射它的那个线程
  大多数代码可以设计为使用线程局部映射。因此，用户应尝试设计自己的代码，通过在与使用
  地址相同的线程中映射页来避免使用 kmap()，并优先使用 kmap_local_page()   kmap_local_folio()
  嵌套 kmap_local_page() kmap_atomic() 映射在某种程度上是允许的（最多到 KMAP_TYPE_NR），
  但它们的调用必须严格有序，因为映射实现是基于栈的。关于如何管理嵌套映射的细节，请参阅
  kmap_local_page() 的内核文档（包含函数"一节中）
- kmap_atomic()。此函数已被废弃；请使用 kmap_local_page()
  注意：转换为 kmap_local_page() 时必须注意遵循施加在 kmap_local_page() 上的映射限制  此外，在调用 kmap_atomic() kunmap_atomic() 之间的代码可能隐式依赖于原子映射  副作用，即禁用缺页或抢占，或两者皆禁用。在这种情况下，必须配合 kmap_local_page() 的使  显式调用 pagefault_disable() preempt_disable()，或两者皆调用
  [遗留文档]

  这允许对单个页进行非常短时间的映射。由于映射仅限于发出它的 CPU，它表现良好，但因此
  发出任务必须留在CPU 上直到它完成，以免其他任务替换掉它的映射
  kmap_atomic() 也可以用于中断上下文，因为它不会睡眠，并且调用者在 kunmap_atomic()   调用之前也不能睡眠
  内核中每kmap_atomic() 的调用都会创建一个不可抢占的区段并禁用缺页。这可能成为不期  延迟的来源。因此用户应优先使用 kmap_local_page() 而非 kmap_atomic()
  假定 k[un]map_atomic() 不会失败
- kmap()。此函数已被废弃；请使用 kmap_local_page()
  注意：转换为 kmap_local_page() 时必须注意遵循施加在 kmap_local_page() 上的映射限制  特别是，有必要确保内核虚拟内存指针仅在获取它的线程中有效
  [遗留文档]

  这应该用于对单个页进行无抢占或迁移限制的短时间映射。它带有开销，因为映射空间受限，  由一把全局锁保护以进行同步。当不再需要映射时，页被映射到的那个地址必须kunmap() 释放
  映射的更改必须传播到所CPU。当 kmap 的池回绕时，kmap() 还需要全局 TLB 失效，并且当
  映射空间被完全占满时，它可能会阻塞直到有槽位可用。因此，kmap() 只能从可抢占上下文中
  调用
  如果映射必须持续相对较长的时间，上述所有工作都是必要的，但内核中绝大多数高端内存映  都是短命的，并且只在一个地方使用。这意味着在这种情况下 kmap() 的开销大多被浪费了  kmap() 本不打算用于长期映射，但它已朝着那个方向演变，在新代码中强烈不建议使用它，而应
  优先使用前面那组函数
  64 位系统上，对 kmap_local_page()、kmap_atomic() kmap() 的调用没有真正的工作  做，因为 64 位地址空间足以寻址所有页被永久映射的物理内存
- vmap()。这可用于将多个物理页做成长时间的映射，映射到一个连续的虚拟空间中。它需要在
  取消映射时进行全局同步

## 临时映射的开销


创建临时映射的开销可能相当高。体系结构必须操纵内核的页表、数TLB MMU 的寄存器
如果未设CONFIG_HIGHMEM，那么内核将尝试仅用一点算术来创建映射，把页结构地址转换指向页内容的指针，而不是折腾各种映射。在这种情况下，取消映射操作可能是个空操作
如果未设CONFIG_MMU，那么就不会有临时映射，也没有高端内存。在这种情况下，也将使用
算术方法

## i386 PAE


在某些情形下，i386 架构允许你在 32 位机器中插入多达 64GiB RAM。这有一系列后果
- Linux 需要为系统中的每个页准备一个页帧（page-frame）结构，而页帧需要驻留在永久映射中，
  这意味着
- 你最多可以有 896M/sizeof(struct page) 个页帧；如果 struct page 32 字节，那最  大约相当112G 的页；然而，内核还需要在该内存中存储不止页帧…
- PAE 会使你的页表变大——这会拖慢系统，因为TLB 填充等过程中需要访问更多数据。一  优点PAE 有更多的 PTE 位，可以提供 NX PAT 等高级特性
一般的建议是，32 位机器上不要使用超过 8GiB——尽管更多对你和你的工作负载可能也行，但
你基本上只能靠自己——如果出乱子了，别指望内核开发者真的很在意
