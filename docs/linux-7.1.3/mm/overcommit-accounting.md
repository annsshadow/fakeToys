## 过量提交（Overcommit）记账


Linux 内核支持以下过量提交处理模式：

0
	启发式过量提交处理。明显的地址空间过量提交会被拒绝。用于典型系统。它确保
	严重离谱的分配失败，同时允许过量提交以减少 swap 使用。这是默认模式。

1
	总是过量提交。适用于某些科学应用程序。典型的例子是使用稀疏数组的代码，
	仅仅依赖几乎完全由零页组成的虚拟内存。

2
	不要过量提交。系统的地址空间总提交不允许超过 swap 加上可配置数量的物理
	RAM（默认为 50%）。根据你使用的数量，在大多数情况下这意味着进程在访问
	页面时不会被杀死，但会在内存分配时收到相应的错误。

	适用于想要保证其内存分配在未来可用、而不必初始化每一页的应用程序。

过量提交策略通过 sysctl `vm.overcommit_memory` 设置。

过量提交的数量可以通过 `vm.overcommit_ratio`（百分比）或 `vm.overcommit_kbytes`
（绝对值）设置。这些仅在 `vm.overcommit_memory` 设置为 2 时生效。

当前的过量提交限制与已提交数量可以在 `/proc/meminfo` 中分别作为 CommitLimit 与
Committed_AS 查看。

## 陷阱（Gotchas）


C 语言的栈增长会执行一次隐式的 mremap。如果你想要绝对的保证并且运行在极限边缘，
你必须为你认为需要的最大大小用 mmap 映射你的栈。对于典型的栈使用这关系不大，但
如果你真的非常在意，这是一个边界情况。

在模式 2 下，MAP_NORESERVE 标志会被忽略。

## 工作原理


过量提交基于以下规则：

对于文件支持的映射
	| SHARED 或只读	-	0 成本（文件即映射，而非 swap）
	| 私有可写	-	每个实例的映射大小

对于匿名或 `/dev/zero` 映射
	| SHARED		-	映射大小
	| 私有只读	-	0 成本（但用处不大）
	| 私有可写	-	每个实例的映射大小

额外记账
	| 由 mmap 制作为可写副本的页面
	| 从同一池中提取的 shmfs 内存
