## 0. 警告


 摆弄这些设置可能导致系统不稳定，这些旋钮仅限 root 操作，并假定 root 知道
 自己在做什么。

最值得注意的是：

 - sched_rt_period_us 的值非常小，当周期小于可用的 hrtimer 分辨率，或小于
   处理预算刷新本身所花费的时间时，可能导致系统不稳定。

 - sched_rt_runtime_us 的值非常小，当运行时间小到系统难以向前推进时
   （注意：迁移线程和 kstopmachine 都是实时进程），可能导致系统不稳定。

## 1. 概述


### 1.1 问题


实时调度的核心在于确定性，一个组必须能够依赖所分配带宽（例如 CPU 时间）的
恒定。为了调度多个实时任务组，每个组必须被分配固定的一部分可用 CPU 时间。
没有最小保证，实时组显然会资源不足。模糊的上限毫无用处，因为无法依赖它。
这就只剩下单一固定份额这一种方式。

### 1.2 解决方案


CPU 时间通过指定在给定周期内可以花费多少运行时间来进行划分。我们为每个
实时组分配这段“运行时间”，其他实时组将不被允许使用它。

任何未分配给实时组的时间都将用于运行普通优先级任务（SCHED_OTHER）。任何
已分配但未使用的运行时间也会被 SCHED_OTHER 取走。

考虑一个例子：一个固定帧率的实时渲染器必须每秒交付 25 帧，即每帧周期 0.04s。
现在假设它还要播放音乐并响应输入，留给图形的 CPU 时间约为 80%。那么我们可以
给这个组 0.8 - 0.04s = 0.032s 的运行时间。

这样，图形组将拥有 0.04s 的周期和 0.032s 的运行时间上限。现在如果音频线程
需要每 0.005s  refill 一次 DMA 缓冲，但只需要约 3% 的 CPU 时间，那么它使用
0.03 * 0.005s = 0.00015s 即可。因此这个组可以用 0.005s 的周期和 0.00015s 的
运行时间来调度。

剩余的 CPU 时间将用于用户输入和其他任务。由于实时任务已显式分配了执行其
任务所需的 CPU 时间，图形或音频中的缓冲欠载（underrun）可以被消除。

注意：上述示例尚未完全实现。我们仍然缺少一个 EDF 调度器，才能使非均匀周期
可用。


## 2. 接口


### 2.1 系统级设置


系统级设置在 /proc 虚拟文件系统下进行配置：

/proc/sys/kernel/sched_rt_period_us:
  等同于 100% CPU 带宽的调度周期。

/proc/sys/kernel/sched_rt_runtime_us:
  对实时调度可使用时间的全局限制。它总是小于或等于 period_us，因为它表示从
  period_us 中分配给实时任务的时间。在未启用 CONFIG_RT_GROUP_SCHED 时，它
  仅用于截止时间任务的准入控制。在 CONFIG_RT_GROUP_SCHED=y 时，它也代表
  所有实时组可用的总带宽。

  - 时间以 us 为单位指定，因为该接口是 s32 类型。这给出了从 1us 到约 35
    分钟的可操作范围。
  - sched_rt_period_us 取值从 1 到 INT_MAX。
  - sched_rt_runtime_us 取值从 -1 到 sched_rt_period_us。
  - 运行时间 -1 表示 runtime == period，即无限制。
  - 为给公平的 dl_server 保留带宽，需满足
    sched_rt_runtime_us/sched_rt_period_us > 0.05。确切值请查看
    /sys/kernel/debug/sched/fair_server/cpuX/ 中 runtime/period 的平均值。


### 2.2 默认行为


sched_rt_period_us（1000000 即 1s）和 sched_rt_runtime_us（950000 即 0.95s）
的默认值。这给出 0.05s 供 SCHED_OTHER（非实时任务）使用。选择这些默认值是为了
让失控的实时任务不会锁死机器，而是留下一点时间用于恢复。将 runtime 设为 -1
即可恢复旧行为。

默认情况下所有带宽都分配给根组，新组从 /proc/sys/kernel/sched_rt_period_us
获取周期，运行时间为 0。如果你想将带宽分配给另一个组，请减少根组的带宽，并将
差额的一部分或全部分配给另一个组。

实时组调度意味着你必须先将一部分总 CPU 带宽分配给该组，它才会接受实时任务。
因此，在你这样做之前，除了 root 之外的任何用户都将无法运行实时任务，即使用户
拥有以实时优先级运行进程的权限！


### 2.3 任务分组依据


启用 CONFIG_RT_GROUP_SCHED 可让你显式地将真实 CPU 带宽分配给任务组。

这使用 cgroup 虚拟文件系统以及 "<cgroup>/cpu.rt_runtime_us" 来控制为每个
控制组保留的 CPU 时间。

关于使用控制组的更多信息，你还应阅读
Documentation/admin-guide/cgroup-v1/cgroups.rst。

为了使配置可调度，组设置会被对照以下限制进行检查：

   \Sum_{i} runtime_{i} / global_period <= global_runtime / global_period

目前，这可以简化如下（但请参见“未来计划”）：

   \Sum_{i} runtime_{i} <= global_runtime


## 3. 未来计划


正在开展工作，以使每个组的调度周期（"<cgroup>/cpu.rt_period_us"）也可配置。

对周期的限制是，子组的周期必须小于或等于其父组的周期。但在现实中没有截止时间
调度时，它还不是很有用，因为它容易导致饥饿（starvation）。

考虑两个兄弟组 A 和 B；两者都有 50% 带宽，但 A 的周期是 B 的两倍长。

- 组 A：period=100000us，runtime=50000us

 - 每 0.1s 运行一次，每次 0.05s

- 组 B：period=50000us，runtime=25000us

 - 每 0.1s 运行两次，每次 0.025s（即每 0.05s 一次）。

这意味着当前 A 中的一个 while (1) 循环会运行整个 B 的周期，并可能让 B 的任务
（假设它们优先级较低）在整个周期内被饿死。

下一个项目将是 SCHED_EDF（最早截止时间优先调度），为 Linux 内核带来完整的截止
时间调度。对上述组进行截止时间调度，并将周期结束视为截止时间，将确保两者都获得
其分配的時間。

实现 SCHED_EDF 可能需要一段时间才能完成。优先级继承（Priority Inheritance）是
最大的挑战，因为当前的 Linux PI 基础设施面向有限的静态优先级级别 0-99。在截止
时间调度中，你需要进行截止时间继承（因为优先级与截止时间增量（deadline - now）
成反比）。

这意味着整个 PI 机制都必须重新设计——而这是我们最复杂的代码之一。
