## Scheduler Nice Design


本文档解释了关于Linux 调度器中重构并精简后的 nice 级别实现的思考
Linux 下，nice 级别一直相当弱，人们不断纠缠我们要nice +19 的任务占用少得多CPU 时间
不幸的是，在旧调度器下这并不那么容易实现（否则我们早就做了），因nice 级别支持在历史上timeslice（时间片）长度耦合，timeslice 单位HZ tick 驱动，因此最timeslice 1/HZ
O(1) 调度器（2003 年）中，我们将负nice 级别改得2.4 中以前强得多（人们对这一改动感到满意），并且我们有意校准了线timeslice 规则，使 nice +19 级别恰好1 jiffy。为了更好地理解，timeslice 图如下（粗糙ASCII 图）
```

                   A
             \     | [timeslice length]
              \    |
               \   |
                \  |
                 \ |
                  \|___100msecs
                   |^ . _
                   |      ^ . _
                   |            ^ . _
 -*----------------------------------*-----> [nice level]
 -20               |                +19
                   |
                   |

```
因此，如果有人真的想 reniced 任务19 会比正常的线性规则造成更大的影响。（改变 ABI 以扩展优先级的方案很早就被放弃了。）

这种方法在一段时间内在一定程度上有效，但后来HZ=1000 时，1 jiffy 变成1 毫秒，这意味着 0.1% CPU 使用率，我们认为这有点过头了。过头_并非_因为它占用的 CPU 太少，而是因为它导致过于频繁的（每毫秒一次）重新调度。（并且会因此扰乱缓存等。请记住，那是很久以前，当时硬件更弱、缓存更小，人们还在nice +19 运行数值计算应用。）

因此对于 HZ=1000，我们将 nice +19 改为 5 毫秒，因为感觉这是正确的粒度下限——这相当5% CPU 使用率。但 nice+19 根本上对 HZ 敏感的属性仍然存在，而且我们从未收到过关nice +19 CPU 使用率方面太_弱_的抱怨，只收到过它（仍然）太_强_的抱:-)

总而言之：我们一直想nice 级别更加一致，但在 HZ jiffies 以及timeslice 和粒度的糟糕设计级别耦合的约束下，这并不可行
关于 Linux nice 级别支持的第二个（不那么频繁但仍周期性出现）抱怨是它围绕原点不对称（你可以在上图中看到演示），或者更准确地说：nice 级别行为也依赖于_绝对_ nice 级别这一事实，nice API 本身从根本上来说相对
   int nice(int inc);

   asmlinkage long sys_nice(int increment)

（第一个是 glibc API，第二个是系统调API。）请注意，'inc' 是相对于当前 nice 级别的。像 bash "nice" 命令这样的工具反映了这个相对 API
在旧调度器下，例如如果你启动了一nice +1 的任务和另一nice +2 的任务，两个任务之间CPU 分配将取决于shell nice 级别——如果它nice -10，CPU 分配就与+5 +10 时不同
针对 Linux nice 级别支持的第三个抱怨是，负nice 级别不够"有力（punchy，所以很多人不得不求助于RT 优先级（SCHED_FIFO）下运行音频（和其他多媒体）应用。但这引发了其他问题：SCHED_FIFO 并不能防止饥饿，一个有 bug SCHED_FIFO 应用也可能永久锁死系统
v2.6.23 中的新调度器解决了所有这三类抱怨：

为了解决第一个抱怨（nice 级别不够"有力"），调度器与"时间HZ 概念解耦（并且将粒度作为一个独立于 nice 级别的概念），因此有可能实现更好、更一致的 nice +19 支持：在新调度器下，nice +19 任务获得HZ 无关1.5%，而不是旧调度器下它们得到的变动的 3%-5%-9% 范围
为了解决第二个抱怨（nice 级别不一致），新调度器使 nice(1) 对任务具有相同的 CPU 使用率效果，无论它们的绝nice 级别如何。因此在新调度器上，运行一nice +10 和一nice +11 的任务，它们之间 CPU 使用率的"分配"与运行一nice -5 和一nice -4 的任务相同。（一个得55% CPU，另一45%。）这就是为什nice 级别被改乘法"（或指数）式的——这样无论你从哪nice 级别开始，'相对结果'总是相同的
第三个抱怨（负的 nice 级别不够"有力"，迫使音频应用运行在更危险的 SCHED_FIFO 调度策略下）几乎是由新调度器自动解决的：更强的负 nice 级别是重新校准后nice 级别动态范围的自动副作用
