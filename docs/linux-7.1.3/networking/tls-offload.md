
## 内核 TLS 卸载


## 内核 TLS 操作


Linux 内核提供 TLS 连接卸载基础设施。一TCP 连接进入 `ESTABLISHED` 状态，用户空间就可以启TLS 上层协议（ULP）并安装加密连接状态。有关面向用户接口的详细信息，请参阅 Documentation/networking/tls.rst 中的 TLS 文档 <kernel_tls>

`ktls` 可以在三种模式下运行

 - 软件加密模式（`TLS_SW`）——由 CPU 处理加密
   在最基础的情况下，只能使用与 CPU 同步的加密操作，但根据调用上下文，CPU 也可能使用异步加密加速器。使用加速器会在套接字读取时引入额外延迟（只有发起读系统调用后才开始解密），并给系统带来额外的 I/O 负载
 - 基于数据包的 NIC 卸载模式（`TLS_HW`）——NIC 在逐个数据包的基础上处理加密，前提数据包按序到达
   这种模式与内核协议栈集成得最好，本文档余下部分会详细说明
   （`ethtool` 标志 `tls-hw-tx-offload` `tls-hw-rx-offload`）
 - 完整 TCP NIC 卸载模式（`TLS_HW_RECORD`）——一种由 NIC 驱动和固件用自身 TCP 处理取代内核网络协议栈的运行模式，它不能用于生产环境，例如任何依Linux 网络协议栈的防火墙能力或 QoS 与数据包调度（`ethtool` 标志 `tls-hw-record`）

运行模式根据设备配置自动选择，目前不支持基于每个连接选择是否启用卸载

### TX（发送）


在较高层面上，用户的写请求会被转换为一个分散列表，TLS ULP 拦截它们，插入记录帧，执行加密（`TLS_SW` 模式下），然后将修改后的分散列表交给 TCP 层。此TCP 协议栈照常继续处理

`TLS_HW` 模式下，加密并不TLS ULP 中执行。相反，数据包会到达设备驱动，驱动根据数据包所附着的套接字将其标记为待加密卸载，并发送给设备进行加密和传输

### RX（接收）


在接收侧，如果设备成功完成了解密和认证，驱动会在相关联的 `struct sk_buff <sk_buff>` 中设置已解密位。数据包到达 TCP 协议栈并被正常处理。当有数据排队到套接字时会通知 `ktls`，并使用 `strparser` 机制来划分记录边界。收到读请求时，记录会从套接字取出并传给解密例程。如果设备已解密该记录的所有分段，则跳过解密，否则由软件路径处理解密

## 设备配置


在驱动初始化期间，设备设`NETIF_F_HW_TLS_RX` 
`NETIF_F_HW_TLS_TX` 特性，并在
`struct net_device <net_device>` :c`tlsdev_ops` 成员中安装其
`struct tlsdev_ops <tlsdev_ops>` 指针

TLS 加密连接状态被安装到一`ktls` 套接字上时（注意这一步会执行两次，一次对RX 方向，一次对TX 方向，两者完全独立），内核会检查底层网络设备是否支持卸载，并尝试进行卸载。如果卸载失败，连接将完全由软件处理，使用的机制与从未尝试卸载时相同

卸载请求通过 `struct tlsdev_ops <tlsdev_ops>` :c`tls_dev_add` 回调执行


	int (**tls_dev_add)(struct net_device **netdev, struct sock *sk,
			   enum tls_offload_ctx_dir direction,
			   struct tls_crypto_info *crypto_info,
			   u32 start_offload_tcp_sn);

`direction` 指示加密信息是用于接收的数据包还是发送的数据包。驱动使`sk` 参数来获取连接的 5 元组以及套接字族（IPv4 还是 IPv6）。`crypto_info` 中的加密信息包括密钥、iv、salt 以及 TLS 记录序列号。`start_offload_tcp_sn` 指示哪个 TCP 序列号对应于`crypto_info` 中序列号开头的记录。驱动可以在内核结构体末尾附加自身状态（参见 `include/net/tls.h` 中的 :c`driver_state` 成员），以避免额外的分配与指针解引用

### TX（发送）


TX 状态安装之后，协议栈保证流的第一段恰好从 `start_offload_tcp_sn` 序列号开始，从而简TCP 序列号匹配

TX 卸载被完全初始化，并不意味着经过驱动且属于被卸载套接字的所有分段都会位于期望的序列号之后，并带有内核记录信息。特别是，在安装连接状态到内核之前，可能已经有加密好的数据被排队到套接字

### RX（接收）


RX 方向上，本地网络协议栈对分段的掌控很小，因此初始记录TCP 序列号可能出现在任意位置
位于该分段内部

## 正常运行


至少，设备会在每个连接、每个方向上维护以下状态：

 - 加密密钥（key、iv、salt
 - 加密处理状态（部分数据块、部分认证标签等
 - 记录元数据（序列号、处理偏移和长度
 - 期望TCP 序列

对于记录长度或记录分段没有任何保证。分段尤其可能从记录的任意一点开始，并包含任意数量的记录。假设分段按序到达，设备应当能够无视分段方式执行加密操作和认证。要做到这一点，设备必须在分段之间保留少量状态。这至少包括

 - 不完整的头部（如果一个分段只携带TLS 头部的一部分
 - 不完整的数据
 - 不完整的认证标签（所有数据都已看到，但部分认证标签必须写入或从后续分段读出）

TLS 卸载不需要重组记录。如果数据包按序到达，设备应当能够分别处理它们并向前推进

### TX（发送）


内核协议栈执行记录成帧，为认证标签保留空间，并填充所有其TLS 头部和尾部字段

由于可能存在重传，且一旦数据包到达设备便没有软件回退路径，设备和驱动都会维护期望TCP 序列号。对于按序传递的分段，驱动会用连接标识符标记数据包（注意：仅5 元组查找不足以识别需要硬件卸载的数据包，参见 5tuple_problems 一节），并将其交给设备。设备识别出该数据包需TLS 处理，并确认序列号与其期望相符。设备对记录数据执行加密和认证，并用正确的值替换认证标签和 TCP 校验和

### RX（接收）


在数据包DMA 到主机之前（但在 NIC 的嵌入式交换和数据包转换功能之后），设备会校验第 4 层校验和，并执行 5 元组查找以找出该数据包可能属于的任何 TLS 连接（严格来4 元组查找就足够——IP 地址TCP 端口号，因为协议始终TCP）。如果数据包匹配到某个连接，设备会确TCP 序列号是否为期望的那个，然后继续进行 TLS 处理（对该数据包中的每个记录做记录划分、解密、认证）。设备保持记录成帧不变，由协议栈负责记录解封装。设备会在传给主机的每包上下文（描述符）中指TLS 卸载处理成功

收到一TLS 卸载数据包后，驱动会在与分段相对应的 `struct sk_buff <sk_buff>` 中设:c`decrypted` 标记。网络协议栈确保已解密和未解密的分段不会被合并（例如GRO 或套接字层），并负责部分解密

## 重新同步处理


在出现丢包或网络数据包乱序时，设备可能会TLS 流失去同步，需要与内核TCP 协议栈重新同步

注意，重新同步只会针对那些已成功加入设备表、且处于 TLS_HW 模式的连接尝试。例如，如果在内核中安装加密状态时设备表已满，这样的连接将永远不会被卸载。因此重新同步请求不携带任何加密连接状态

### TX（发送）


从被卸载套接字发出的分段可能以类似于接收侧的方式失去同步——重传：本地丢包是可能的，但网络乱序则不会。目前有两种机制来处理乱序分段

#### 加密状态重


每当发送一个乱序分段时，驱动会向设备提供足够的加密操作信息。这很可能意味着当前分段之前的记录部分必须作为数据包上下文的一部分传给设备，同时附带其 TCP 序列号和 TLS 记录号。设备随后可以初始化其加密状态，处理并丢弃前面的数据（以便能够插入认证标签），然后转而处理实际的数据包

在这种模式下，根据实现不同，驱动既可以请求带着加密状态和新的序列号继续（下一个期望的分段是乱序分段之后的那个），也可以带着之前的流状态继续——假设该乱序分段只是一次重传。前者更简单，且不需要重传检测，因此在被证明低效之前，它是推荐的方法

#### 下一记录同步


每当检测到乱序分段时，驱动会请求由 `ktls` 软件回退代码对其进行加密。如果该分段的序列号低于期望值，驱动假设是重传，不改变设备状态。如果该分段属于未来，则可能意味着本地丢包，驱动会请求协议栈将设备同步到下一个记录状态，并回退到软件

重新同步请求通过以下方式指示

  void tls_offload_tx_resync_request(struct sock *sk, u32 got_seq, u32 exp_seq)

在重新同步完成之前，驱动不应访问其期望的 TCP 序列号（因为它会从不同的上下文被更新）。应使用以下辅助函数来测试重新同步是否完成：

  bool tls_offload_tx_resync_pending(struct sock *sk)

下一`ktls` 推送记录时，会先将TCP 序列号和 TLS 记录号发送给驱动。协议栈还会确保新记录从分段边界开始（就像连接初次加入时那样）

### RX（接收）


少量RX 乱序事件可能不需要完全重新同步。特别是，在能够恢复记录边界时，设备不应失去同步

在上例中，分1 被接收并成功解密。分2 被丢弃，因此 3 乱序到达。设备根据分1 中的记录长度知道下一个记录在 3 内部开始。分3 原样传递，因为缺少分段 2 的数据，分段 3 内上一个记录的剩余部分无法处理。然而，设备可以收集新记录（在分3 中）的认证算法状态与部分数据块，并在 4 5 到达时继续解密。最后当 2 到达时，它完全落在设备的期望窗口之外，因此原样传递，不做特殊处理。`ktls` 软件回退负责处理横跨分段 1 的记录的解密。即使有两个分段未被解密，设备也没有失去同步

在此例中，分2 被丢弃，且它包含一个记录头。设备只有从分段 2 知道上一个记录的长度时，才能检测到分段 4 也包含一TLS 头部。在这种情况下，设备将与流失去同步

#### 流扫描重新同


当设备失去同步，且流到达TCP 序列号比期望TCP 序列号多出超过一个最大尺寸的记录时，设备开始扫描已知的头部模式。例如，对于 TLS 1.2 TLS 1.3，值为 `0x03 0x03` 的连续字节会出现在头部的 SSL/TLS 版本字段中。一旦模式匹配，设备会继续尝试在期望的位置解析头部（基于猜测位置的头部长度字段）。只要期望位置不包含有效头部，扫描就会重启

当头部匹配时，设备向内核发送一个确认请求，询问所猜测的位置是否正确（是否真的有一TLS 记录从那里开始），以及该头部具有哪个记录序列号

异步重新同步过程在内核侧通过 struct tls_offload_resync_async, which tracks and manages the resync request. 进行协调

管理 struct tls_offload_resync_async 的辅助函数：

`tls_offload_rx_resync_async_request_start()`
通过指定要监控的序列范围并重置结构体内部状态，初始化一次异步重新同步尝试

`tls_offload_rx_resync_async_request_end()`
保留设备猜测TCP 序列号，以便与当前或将来记录的序列号进行比较。它还会清除重新同步请求中的 RESYNC_REQ_ASYNC 标志，表示设备已提交其猜测的序列号

`tls_offload_rx_resync_async_request_cancel()`
取消任何正在进行的重新同步尝试，清除请求状态

当内核处理一个开始新 TLS 记录RX 分段时，它会检查异步重新同步请求的当前状态

如果设备仍在等待提供其猜测的 TCP 序列号（异步状态），内核会记录该分段的序列号，以便日后在设备的猜测可用时进行比较

如果设备已经提交了猜测的序列号（非异步状态），内核现在会尝试将该猜测与重新同步请求启动以来已记录的所TLS 记录头的序列号进行匹配

内核确认所猜测的位置正确，并告诉设备该记录的序列号。与此同时，设备自刚刚确认的那个记录起一直在解析并计数所有记录，它会把自己看到的记录数量加到内核提供的记录号上。此时设备已同步，可以在下一个分段边界恢复解密

在极端情况下，设备可能会锁定在一连串匹配的头部上，而永远收不到内核的回复（内核没有否定确认）。实现可以选择周期性重启扫描。不过鉴于流被错误匹配的可能性极低，周期性重启被认为并无必要

如果要异步地将确认请求传送到数据包流，且记录可能在确认请求之前就被内核处理，则需要特别小心

#### 栈驱动的重新同步


驱动也可以在发现记录不再被解密时，请求协议栈执行重新同步。如果连接配置为这种模式，协议栈在收到两条完全加密的记录后会自动安排重新同步

协议栈等待套接字排空，并把下一个期望的记录号及TCP 序列号告知设备。如果记录持续以完全加密的形式到达，协议栈会以指数退避重试同步（先在2 条加密记录后，然后第 4 条、第 8 条、第 16 条……直到每 128 条记录）

## 错误处理


### TX（发送）


数据包可能被协议栈重定向或重新路由到与所TLS 卸载设备不同的设备。协议栈会使`sk_validate_xmit_skb` 辅助函数处理这种情况（TLS 卸载代码在该钩子点安`tls_validate_xmit_skb`）。卸载会维护所有记录的信息，直到数据被完全确认，因此如skbs 到达了错误的设备，可以由软件回退处理

发送侧任何设备 TLS 卸载处理错误都必须导致该数据包被丢弃。例如，如果某个数据包由于协议栈或设备的缺陷而乱序，到达设备后无法被加密，则必须丢弃该数据包

### RX（接收）


如果设备在接收侧遇到任何 TLS 卸载问题，它应当把数据包按线上收到的样子传递给主机网络协议栈

例如，分段中任何记录的认证失败，都应将未修改的数据包传递给软件回退。这意味着不应“就地”修改数据包。不建议拆分分段来处理部分解密。换句话说，要么数据包中的所有记录都已成功处理并完成认证，要么数据包必须按线上原样传递给主机协议栈（如果设备提供了精确的错误信息，在驱动中恢复原始数据包即可）

Linux 网络协议栈不提供上报每包解密与认证错误的机制，有错误的数据包绝不能设:c`decrypted` 标记

如果数据包包含不正确的校验和，也不应TLS 卸载处理

## 性能指标


TLS 卸载可以由以下基本指标来刻画

 - 最大连接数
 - 连接安装速率
 - 连接安装延迟
 - 总加密性能

注意每个 TCP 连接在双向都需要一TLS 会话，性能可以按每个方向分别上报

### 最大连接数


设备能够支持的连接数可以通过 `devlink resource` API 暴露

### 总加密性能


卸载性能可能取决于分段和记录的大小

设备加密子系统的过载不应对非卸载流产生显著的性能影响

## 统计


驱动应报告以下最小的 TLS 相关统计集合

 - `rx_tls_decrypted_packets`——属TLS 流、且被成功解密的 RX 数据包数量
 - `rx_tls_decrypted_bytes`——RX 数据包中被成功解密的 TLS 有效载荷字节数
 - `rx_tls_ctx`——为解密而添加到设备TLS RX HW 卸载上下文数量
 - `rx_tls_del`——从设备删除TLS RX HW 卸载上下文数量（连接已结束）
 - `rx_tls_resync_req_pkt`——带有重新同步请求的已接TLS 数据包数量
 - `rx_tls_resync_req_start`——TLS 异步重新同步请求启动的次数
 - `rx_tls_resync_req_end`——TLS 异步重新同步请求在提HW 跟踪tcp-seq 后正常结束的次数
 - `rx_tls_resync_req_skip`——TLS 异步重新同步请求已启动但未正常结束的次数
 - `rx_tls_resync_res_ok`——对驱动TLS 重新同步响应调用被成功处理的次数
 - `rx_tls_resync_res_skip`——对驱动TLS 重新同步响应调用未成功终止的次数
 - `rx_tls_err`——属TLS 流、但因状态机中出现意外错误而未被解密的 RX 数据包数量
 - `tx_tls_encrypted_packets`——传递给设备以加密其 TLS 有效载荷TX 数据包数量
 - `tx_tls_encrypted_bytes`——传递给设备加密TX 数据包中TLS 有效载荷字节数
 - `tx_tls_ctx`——为加密而添加到设备TLS TX HW 卸载上下文数量
 - `tx_tls_ooo`——属TLS 流、但未按期望顺序到达TX 数据包数量
 - `tx_tls_skip_no_sync_data`——属TLS 流、且
   属于 TLS 流、且乱序到达，但跳过HW 卸载例程，作为连接握手的重传进入了常规发送流程的 TX 数据包数量
 - `tx_tls_drop_no_sync_data`——属TLS 流、因乱序到达且找不到关联记录而被丢弃TX 数据包数量
 - `tx_tls_drop_bypass_req`——属TLS 流、因同时包含已由软件加密的数据和期望硬件加密卸载的数据而被丢弃TX 数据包数量

## 值得注意的边界情形、例外与附加要求


### 5 元组匹配的局限


设备只能基于套接字的 5 元组来识别收到的数据包。当前的 `ktls` 实现不会卸载经过软件接口（例如用于隧道或虚拟网络的接口）路由的套接字。不过，网络协议栈执行的许多数据包转换（最明显的是任意 BPF 逻辑）并不要求任何中间软件设备，因此 5 元组匹配在设备层面可能会持续失配。在这种情况下，设备仍应能够执行 TX 卸载（加密），并干净地回退到软件解密（RX）

### 乱序


NIC 中引入额外处理不应导致数据包乱序发送或接收，例如纯 ACK 数据包不应相对数据分段被重新排序

### 入口乱序


设备可以对连续的 TCP 分段执行数据包重排序（即把数据包排成正确的顺序），但任何额外缓冲形式都是禁止的

### 与标准网络卸载特性的共存


被卸载的 `ktls` 套接字应当透明地支持标TCP 协议栈特性。启用设TLS 卸载不应导致线上看到的数据包有任何差异

### 传输层透明


为了简TLS 卸载，设备不应修改任何数据包头部

设备不应依赖任何超出 TLS 卸载严格所需范围的数据包头部

### 分段丢弃


只有在发生灾难性系统错误时才允许丢弃数据包，绝不应将其用作正常操作中出现问题的错误处理机制。换句话说，依赖 TCP 重传来应对边界情形是不可接受的

### TLS 设备特


驱动应忽略对 TLS 设备特性标志的更改。这些标志会由核`ktls` 代码相应地处理。TLS 设备特性标志只控制新增 TLS 连接卸载，在标志被清除后，旧连接仍将保持活动

TLS 加密无法卸载到不支持校验和计算卸载的设备上。因此，TLS TX 设备特性标志要求设TX csum 卸载。禁用后者意味着清除前者。禁TX 校验和卸载不应影响旧连接，驱动应确保对它们的校验和计算不被破坏。类似地，设备卸载的 TLS 解密意味着要执RXCSUM。如果用户不想启RX csum 卸载，TLS RX 设备特性也会被禁用
