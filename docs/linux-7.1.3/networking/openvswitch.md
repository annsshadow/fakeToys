
## Open vSwitch datapath 开发者文
Open vSwitch 内核模块允许在选定的网络设备上对数据面（flow-level）包处理进行灵活的用户空控制。它可以用于实现简单的以太网交换机、网络设备绑定（bonding）、VLAN 处理、网络访问控制基于流的网控，等等
该内核模块实现多个“datapath”（类似于桥），每个 datapath 可以有多个“vport”（类似于桥内的
端口）。每datapath 还关联一个“流表”（flow table），用户空间在其中填充“流”（flow），
这些流将基于包头部和元数据的键映射到一组动作。最常见的动作是将包转发到另一vport；其动作也有实现
当包到达某个 vport 时，内核模块通过提取其流键并在流表中查找来处理它。如果存在匹配的流，执行关联的动作。如果没有匹配，它将包排队到用户空间进行处理（作为其处理的一部分，用户空间很
可能会建立一条流，以便在内核中完全处理同类型的后续包）
### 流键兼容
网络协议会随着时间演进。新协议变得重要，而现有协议失去其地位。为了让 Open vSwitch 内核模块
保持相关性，必须允许较新版本将额外协议解析为流键的一部分。也许有一天，甚至可能希望放弃对解已过时协议的支持。因此，Open vSwitch Netlink 接口被设计为允许编写严谨的用户空间应用与
任何版本的流键（过去或未来）配合工作
为了支持这种前向和后向兼容性，每当内核模块将一个包传递给用户空间时，它还会一并传递从包中
解析出的流键。然后用户空间从包中提取自己理解的流键，并将其与内核提供的版本进行比较：

    - 如果用户空间对该包的流键的理解与内核的一致，则不需要任何特殊处理
    - 如果内核的流键包含的字段多于用户空间版本的流键，例如内核解码IPv6 头部但用户空      止步于以太网类型（因为它不理IPv6），那么同样不需要特殊处理。只要用户空间使用内      提供的流键，它仍然可以以通常的方式建立流
    - 如果用户空间流键包含的字段多于内核的，例如用户空间解码了 IPv6 头部但内核止步于以太      类型，那么用户空间可以手动转发该包，而不在内核中建立流。这种情况对性能不利，因为内      视为该流一部分的每个包都必须送往用户空间，但转发行为是正确的。（如果用户空间能够确定
      额外字段的值不会影响转发行为，那么它仍然可以建立一条流。）

流键如何随时间演进对于实现这一点很重要，因此以下各节详述
### 流键格式

流键作为一系列 Netlink 属性通过 Netlink 套接字传递。一些属性表示包元数据，定义为任何无从包本身提取的关于包的信息，例如接收到该包的 vport。然而，大多数属性是从包内的头部提取的，
例如来自以太网、IP TCP 头部的源地址和目的地址
<linux/openvswitch.h> 头文件定义了流键属性的确切格式。这里为了非正式的说明目的，我们将它写成逗号分隔的字符串，括号表示参数和嵌套。例如，以下内容可以表示一个流键：

```
    in_port(1), eth(src=e0:91:f5:21:d0:b2, dst=00:02:e3:0f:80:a4),
    eth_type(0x0800), ipv4(src=172.16.0.20, dst=172.18.0.52, proto=17, tos=0,
    frag=no), tcp(src=49163, dst=80)

```
```
    in_port(1), eth(...), eth_type(0x0800), ipv4(...), tcp(...)

```
### 通配（wildcarded）流键格
通配流由通过 Netlink 套接字传递的两个 Netlink 属性序列描述：一个如上面所述的流键，以及一可选的对应流掩码
通配流可以表示一组精确匹配流。掩码中的每'1' 位指定与流键中对应位的精确匹配0' 位指一个“不关心”位，它将匹配入站包'1' '0' 位。使用通配流可以通过减少需要由用户空间程序处理
的新流数量来提高流建立速率
掩码 Netlink 属性对内核和用户空间程序都是可选的。内核可以忽略掩码属性，安装一条精确匹配流或者将内核中“不关心”位的数量减少到少于用户空间程序指定的数量。在这种情况下，内核未实现的上的变化只会导致额外的流建立。内核模块也能与使用既不支持也不提供流掩码属性的用户空间程序
配合工作
由于内核可能忽略或修改通配位，用户空间程序很难确切知道安装了哪些匹配。有两种可能的方法：
在它们未命中内核流表时被动地安装流（因此根本不尝试确定通配变化），或者使用内核的响应消息确定已安装的通配
在与用户空间交互时，内核应保持键的匹配部分与最初安装时完全一致。这将为所有未来的操作提供
一个句柄来标识该流。然而，在报告已安装流的掩码时，掩码应包含内核施加的任何限制
使用重叠通配流时的行为是未定义的。确保任何入站包最多只能匹配一条流（无论是否通配）是用户空间
程序的责任。当前的实现尽力检测重叠通配流，并可能拒绝其中的一部分而非全部。但是，这种行为未来版本中可能会改变
### 唯一流标识符

使用键的原始匹配部分作为流标识的句柄的一种替代方案是唯一流标识符，即“UFID”。UFID 对内核和
用户空间程序都是可选的
支持 UFID 的用户空间程序应在流建立期间除流之外还提UFID，然后在所有未来的操作中使UFID
来引用该流。如果指定了 UFID，内核不需要按原始流键为流建立索引
### 演进流键的基本规
要真正为遵循上文“流键兼容性”中所列规则的应用维护前向和后向兼容性，需要一些留意
```
    ==================================================================
    新的网络协议支持只能补充现有的流键属性。它不得改变已定义流键属    的含义    ==================================================================

```
这条规则确实有一些不太明显的后果，因此值得通过几个例子来推导。例如，假设内核模块尚未实现
VLAN 解析。相反，它只是将 802.1Q TPIDx8100）解释为 Ethertype，然后停止解析包。任何带802.1Q 头部的包的流键将是：

```
    eth(...), eth_type(0x8100)

```
直观地看，要添加 VLAN 支持，添加一个新的“vlan”流键属性来包含 VLAN 标签，然后继续使用现有字定义解码 VLAN 标签之外的封装头部，是有道理的。有了这个改动，VLAN 10 中的一TCP 包将会有
```
    eth(...), vlan(vid=10, pcp=0), eth_type(0x0800), ip(proto=6, ...), tcp(...)

```
但这个改动会对尚未更新以理解新“vlan”流键属性的用户空间应用产生负面影响。遵循上述流兼容规则，该应用可以忽略它不理解的“vlan”属性，从而假设该流包IP 包。这是一个糟糕的假设（只在解析并跳过 802.1Q 头部时，该流才包IP 包），并且即使它遵循兼容性规则，也可能导致应用的
行为跨内核版本发生变化
解决方案是使用一组嵌套属性。例如，这就是为什802.1Q 支持使用嵌套属性。VLAN 10 中的一TCP 包将是：

```
    eth(...), eth_type(0x8100), vlan(vid=10, pcp=0), encap(eth_type(0x0800),
    ip(proto=6, ...), tcp(...)))

```
注意“eth_type”、“ip”和“tcp”流键属性是如何嵌套在“encap”属性内部的。因此，不理解“vlan”键应用将不会看到这些属性中的任何一个，因而不会误解它们。（此外，外eth_type 仍然0x8100而不是改0x0800。）

### 处理畸形
不要因为畸形的协议头部、错误的校验和等而在内核中丢弃包。这会阻止用户空间实现转发每个包简单以太网交换机
相反，在这种情况下，包含一个带有“空”内容的属性。只要这些空内容在实践中很少见到，即使它可能是有效的协议值也没关系，因为用户空间总是可以将具有这些值的所有包转发到用户空间并逐个
处理
例如，考虑一个包含指示协6（TCP）的 IP 头部、但IP 头部之后就被截断、因而缺TCP 头部包。该包的流键将包含一src dst 全为零的 tcp 属性，例如
```
    eth(...), eth_type(0x0800), ip(proto=6, ...), tcp(src=0, dst=0)

```
再举个例子，考虑一个以太网类型0x8100（表示后面应跟随 VLAN TCI）但在以太网类型之后被截断的
包。该包的流键将包含：

```
    eth(...), eth_type(0x8100), vlan(0), encap()

```
与源端口和目的端口为 0 TCP 包不同，全零位的 VLAN TCI 并不那么罕见，因CFI 位（在内核中
VLAN_TAG_PRESENT）通常被显式地设置vlan 属性中，以便能够区分这种情况。因此，第二个例子中
的流键明确地指示了缺失或畸形VLAN TCI
### 其他规则

流键的其他规则就不那么微妙了
    - 在给定的嵌套层级上不允许出现重复属性
    - 属性的顺序无关紧要
    - 当内核向用户空间发送给定的流键时，它总是以相同的方式组合它。这允许用户空间对它可能无法
      完全解释的整个流键进行哈希和比较
