
## J1939 文档


## 概述 / J1939 是什


SAE J1939 CAN 之上定义了一个高层协议。它实现了一种更复杂的寻址方案
并将最大包大小扩展到了 8 字节以上。存在若干个派生规范，它们在应用层与
原始 J1939 有所不同，如 MilCAN A、NMEA2000，尤其是 ISO-11783（ISOBUS）
最后这一个规定了所谓的 ETP（Extended Transport Protocol，扩展传输协议）
它已被包含在本实现中。这使得最大包大小达到
((2 ^ 24) - 1) * 7 字节 == 111 MiB

### 所用规


- SAE J1939-21：数据链路层
- SAE J1939-81：网络管
- ISO 11783-6：虚拟终端（扩展传输协议


## 动机


鉴于存在SocketCAN 这样 API 类似BSD 套接字的机制，我们找到了一些理
来证明，J1939 所使用的寻址和传输方法提供一个内核实现是合理的

- **寻址* 当一ECU 上的进程通过 J1939 通信时，它不一定要知道自己的源
  地址。不过，每个 ECU 至少有一个进程应当知道源地址。其他进程应当能够复
  该地址。这样，为同一ECU 协作的不同进程的地址参数就不会重复。这种工
  方式UNIX 的理念密切相关，即程序只做一件事并把它做好

- **动态寻址* J1939 中的地址申领（Address Claiming）对时间敏感。此外，
  在地址协商期间应当正确地处理数据传输。将此功能放在内核中，就消除了它作为
  _每个_ 通过 J1939 通信的用户空间进程的要求。这带来了一个具有正确寻址的
  一致的 J1939 总线

- **传输* TP ETP 都复用一PGN 来在其上中继大包。因此，不同进程可能
  在不知情的情况下使用相同TP ETP PGN。各TP ETP 会话 _必须_ 在不
  进程之间被串行化（同步）。内核妥善地解决了这个问题，消除了串行化（同步）
  作为 _每个_ 通过 J1939 通信的用户空间进程的要求

J1939 定义了一些其他特性（中继、网关、快速包传输……）。这些特性的内核代码
无助于协议稳定性。因此，这些部分留给用户空间

J1939 套接字运行在 CAN 网络设备之上（参SocketCAN）。任何运行在 CAN 原始
套接字上J1939 用户空间库仍将正常工作。由于这样的库不与内核实现通信，必
注意二者不要相互干扰。在实践中，这意味着它们不能共享 ECU 地址。一ECU（或
虚拟 ECU）地址要么被该库独占使用，要么被内核系统独占使用


## J1939 概念


### 发往 J1939 栈的数据


从用户空间发往 J1939 栈的数据缓冲区本身并不是 CAN 帧。相反，它们是负载，
J1939 栈会根据缓冲区的大小和传输的类型将其转换为适当CAN 帧。缓冲区的大
影响栈处理数据的方式，并决定用于该传输的内部代码路径

**不同缓冲区大小的处理*

- **大小8 字节或更小的缓冲区：**

  - 它们在栈内部被作为简单会话处理

  - 栈直接将缓冲区转换为单个 CAN 帧，无需分片

  - 这种类型的传输不需要接收侧有实际的客户端（接收者）

- **最1785 字节的缓冲区*

  - 它们被自动作J1939 传输协议（TP）传输处理

  - 在内部，栈将缓冲区拆分为多个 8 字节CAN 帧

  - TP 传输可以是单播或广播

  - **广播 TP* 不需要对端有接收者，可用于广播场景

  - **单播 TP* 需要对端有活跃的接收者（客户端）来确认该传输

- **1786 字节111 MiB 的缓冲区*

  - 它们被作ISO 11783 扩展传输协议（ETP）传输处理

  - ETP 传输用于更大的负载，并在内部被拆分为多个 CAN 帧

  - **ETP 传输（单播）* 需要对端有接收者来处理传入数据并确认传输的每一
    步

  - ETP 传输不能TP 传输那样被广播，并且始终需要接收者才能运作

**使用 `MSG_DONTWAIT` 的非阻塞操作*

J1939 栈在`MSG_DONTWAIT` 标志结合使用时支持非阻塞操作。在此模式下，栈
会尽可能多地取走套接字可用内存所允许的数据。它返回成功取走的字节数，由用户
空间负责监视此值并处理部分传输

- 如果栈无法取走整个缓冲区，它会返回成功取走的字节数，用户空间应当处理剩余
  部分

- **错误处理* 使用 `MSG_DONTWAIT` 时，用户必须依赖错误队列来检测传输错误
  有关如何订阅错误通知的详情，请参**SO_J1939_ERRQUEUE** 一节。没有错
  队列，用户空间就没有其他方式在非阻塞操作期间被告知传输错误

**行为和要求：**

- **简单传输（<= 8 字节）：** 不需要对端有接收者，使得它们易于发送，无需
  地址申领或与目标方协调

- **单播 TP/ETP* 需要对端有接收者来完成传输。接收者必须确认该传输，会
  才能成功进行

- **广播 TP* 允许在没有接收者的情况下发送数据，但仅适用TP 传输。ETP
  不能被广播，并且始终需要一个接收客户端

这些不同的行为严重依赖于提供给栈的缓冲区大小，并且根据负载大小选择适当
传输机制（TP ETP）。栈自动管理大负载的分片和重组，并确保为每个会话生成
并发送正确的 CAN 帧

### PGN


J1939 协议使用具有以下结构29 CAN 标识符：

  ============  ==============  ====================
#   29 bit CAN-ID

#   Bit positions within the CAN-ID

  28 ... 26     25 ... 8        7 ... 0
  ============  ==============  ====================
  Priority      PGN             SA (Source Address)
  ============  ==============  ====================

PGN（Parameter Group Number，参数组编号）是用于标识一个包的数字。PGN 
组成如下

  ============  ==============  =================  =================
#   PGN

#   Bit positions within the CAN-ID

  25            24              23 ... 16          15 ... 8
  ============  ==============  =================  =================
  R (Reserved)  DP (Data Page)  PF (PDU Format)    PS (PDU Specific)
  ============  ==============  =================  =================

J1939-21 中区分了 PDU1 格式（PF < 240）和 PDU2 格式（PF >= 240）。此外，
使用 PDU2 格式时，PS 字段包含一个所谓的组扩展（Group Extension），它是 PGN
的一部分。使PDU2 格式时，组扩展设置在 PS 字段中

  ==============  ========================
#   PDU1 Format (specific) (peer to peer)

#   Bit positions within the CAN-ID

  23 ... 16       15 ... 8
  ==============  ========================
  00h ... EFh     DA (Destination address)
  ==============  ========================

  ==============  ========================
#   PDU2 Format (global) (broadcast)

#   Bit positions within the CAN-ID

  23 ... 16       15 ... 8
  ==============  ========================
  F0h ... FFh     GE (Group Extension)
  ==============  ========================

另一方面，使PDU1 格式时，PS 字段包含一个所谓的 Destination Address（目
地址），_不是_ PGN 的一部分。当从用户空间向内核（或反之）传PGN 并使
PDU1 格式时，PGN PS 字段应设为零。目的地址应在别处设置

关于 PGN 29 CAN 标识符的映射，目的地址应由内核从标识符的适当位中
获取/设置


### 寻址


可以使用静态和动态两种寻址方法

对于静态地址，内核不做额外的检查，所提供的地址被认为是正确无误的。这一责任
在于 OEM 或系统集成商

对于动态寻址，即所谓的地址申领（Address Claiming），内核中提供了额外支持
J1939 中，任何 ECU 都通过64 NAME 来识别。在地址申领成功之时，内
会跟踪被申领NAME 和源地址。这作为过滤方案的基础。默认情况下，目的地不是
本地（local）的包将被拒绝

混合模式包（从静态地址到动态地址，或反之）是允许的。BSD 套接字为获取/设置
本地和远程地址定义了单独的 API 调用，它们适用J1939 套接字

### 过滤


J1939 定义了每个套接字的白名单过滤器，用户可以设置它来接收 J1939 流量的一
子集。过滤可以基于：

- SA
- SOURCE_NAME
- PGN

当为单个套接字设置了多个过滤器，并且一个到来的包匹配其中多个过滤器时，该包
对于这个套接字只被接收一次


## 如何使用 J1939


### API 调用


CAN 上，你首先需要打开一个套接字以通过 CAN 网络通信。要使用 J1939，请
`#include <linux/can/j1939.h>`。由此，`<linux/can.h>` 也会被包含。要打开
一个套接字，使用：


    s = socket(PF_CAN, SOCK_DGRAM, CAN_J1939);

J1939 确实使用 `SOCK_DGRAM` 套接字。在 J1939 规范中，连接是在传输协议会话
上下文中提到的。这些仍然将包交付到对端（使用若CAN 包）。`SOCK_STREAM`
不被支持

成功创建套接字后，你通常会使`bind(2)` `connect(2)` 系统调用来将
套接字绑定到一CAN 接口。在绑定或连接套接字之后，你可以像往常一样从/
该套接字 `read(2)` `write(2)`，或使用 `send(2)`、`sendto(2)`、`sendmsg(2)`
及其 `recv*()` 对应操作。下面还描述J1939 特定的套接字选项

为了发送数据，必须已经成功执行 `bind(2)`。`bind(2)` 为套接字分配一个本
地址

CAN 不同的是，负载数据只是被发送的数据本身，不含其头部信息。头部信息派
自提供给 `bind(2)`、`connect(2)`、`sendto(2)` `recvfrom(2)` sockaddr
一个大小为 4 `write(2)` 将产生一4 字节的包

sockaddr 结构有用J1939 的扩展，如下所述：


      struct sockaddr_can {
         sa_family_t can_family;
         int         can_ifindex;
         union {
            struct {
               __u64 name;
                        /* pgn:
                         - 8 bit: PS in PDU2 case, else 0
                         - 8 bit: PF
                         - 1 bit: DP
                         - 1 bit: reserved
                         */
               __u32 pgn;
               __u8  addr;
            } j1939;
         } can_addr;
      }

`can_family` `can_ifindex` 的作用与其他 SocketCAN 套接字相同

`can_addr.j1939.pgn` 指定 PGN（最0x3ffff）。各个位的说明如上

`can_addr.j1939.name` 包含 64 J1939 NAME

`can_addr.j1939.addr` 包含地址

`bind(2)` 系统调用分配本地地址，即发送包时的源地址。如果在 `bind(2)` 期间
设置PGN，它就被用作 RX 过滤器。即只接收具有匹PGN 的包。如果设置了 ADDR
NAME，它也被用作接收过滤器。它将匹配到来包的目NAME ADDR。NAME 过滤
只有在为name CAN 总线上完成了适当的地址申领并由内核注册/缓存时才起作用

另一方面，`connect(2)` 分配远程地址，即目的地址。`connect(2)` 中的 PGN 
用作发送包时的默认 PGN。如果设置了 ADDR NAME，它将被用作默认的目ADDR
NAME。此外，`connect(2)` 期间设置ADDR NAME 被用作接收过滤器。它
匹配到来包的NAME ADDR

`write(2)` `send(2)` 都会发送一个带有来`bind(2)` 的本地地址和来
`connect(2)` 的远程地址的包。使`sendto(2)` 来覆盖目的地址

如果 `can_addr.j1939.name` 被设置（!= 0），内核会查找该 NAME 并使用相应的
ADDR。如`can_addr.j1939.name` 未被设置= 0），则使
`can_addr.j1939.addr`銆。

创建套接字时，会设置合理的默认值。一些选项可以`setsockopt(2)` 
`getsockopt(2)` 修改

RX 路径相关的选项

- `SO_J1939_FILTER` - 配置过滤器数
- `SO_J1939_PROMISC` - 禁用`bind(2)` `connect(2)` 设置的过滤器

默认情况下，不能发送或接收广播包。要启用发送或接收广播包，请使用套接字选项
`SO_BROADCAST`锛。

##### recvmsg(2)


在大多数情况下，如果你想要提取比 `recvfrom(2)` 能提供的更多信息，就需
`recvmsg(2)`。例如包的优先级和时间戳。目的地址、name 和包优先级（如适用

其中 `cmsg_level == SOL_J1939 && cmsg_type == SCM_J1939_DEST_ADDR`
`SCM_J1939_DEST_NAME` `SCM_J1939_PRIO`。返回的数据中，`priority` 
`dst_addr` `uint8_t`，`dst_name` `uint64_t`


	uint8_t priority, dst_addr;
	uint64_t dst_name;

	for (cmsg = CMSG_FIRSTHDR(&msg); cmsg; cmsg = CMSG_NXTHDR(&msg, cmsg)) {
		switch (cmsg->cmsg_level) {
		case SOL_CAN_J1939:
			if (cmsg->cmsg_type == SCM_J1939_DEST_ADDR)
				dst_addr = *CMSG_DATA(cmsg);
			else if (cmsg->cmsg_type == SCM_J1939_DEST_NAME)
				memcpy(&dst_name, CMSG_DATA(cmsg), cmsg->cmsg_len - CMSG_LEN(0));
			else if (cmsg->cmsg_type == SCM_J1939_PRIO)
				priority = *CMSG_DATA(cmsg);
			break;
		}
	}

##### setsockopt(2)


`setsockopt(2)` 函数用于配置 J1939 通信的各种套接字级选项。支持以下选项

#### ``SO_J1939_FILTER``


`bind(2)` `connect(2)` 的默认行为对于特定用例不够用时，`SO_J1939_FILTER`
选项是必不可少的。默认情况下，`bind(2)` `connect(2)` 允许一个套接字关联
单个单播或广播地址。然而，存在需要对传入消息进行更精细控制的场景，例如按
参数组编号（PGN）而非按地址进行过滤

例如，在一个传输多种类J1939 消息的系统中，一个进程可能只对其中一部分消息
感兴趣，例如特定PGN，而不想接收发往其地址或广播到总线的所有消息

通过应用 `SO_J1939_FILTER` 选项，你可以基于以下内容过滤消息

- **源地址（SA）：** 过滤来自特定源地址的消息

- **源名称（Source Name）：** 过滤来自具有特定 NAME 标识符的 ECU 的消息

- **参数组编号（PGN）：** 专注于接收具有特PGN 的消息，过滤掉无关的消息

这种过滤机制在以下情况下特别有用

- 你想根据消息PGN 接收消息子集，即使地址相同

- 你需要处理广播和单播消息，但只关心某些消息类型或参数

- `bind(2)` `connect(2)` 函数只允许绑定到单个地址，如果进程需要处理多
  PGN 但不想打开多个套接字，这可能不够

要移除现有过滤器，你可以`setsockopt(2)` 传`optval == NULL` 
`optlen == 0`。这将清除当前设置的所有过滤器。如果你*更新**过滤器集合，
你必须将更新后的过滤器集合传递给 `setsockopt(2)`，因为新的过滤器集合
**完全替换**旧的集合。此行为确保任何先前的过滤器配置都被丢弃，只应用新的
集合

移除所有过滤器的示例：


    setsockopt(sock, SOL_CAN_J1939, SO_J1939_FILTER, NULL, 0);

**最大过滤器数量* 使用 `SO_J1939_FILTER` 可应用的最大过滤器数量
`J1939_FILTER_MAX` 定义，其值为 512。这意味着你可以配置最512 个独立的
过滤器来满足你特定的过滤需求

实际用例*监控地址申领**

一个实际用例是通过过滤与地址申领相关的特PGN 来监J1939 地址申领过程
这允许一个进程监控和处理地址申领，而不必处理无关的消息

示例


    struct j1939_filter filt[] = {
        {
            .pgn = J1939_PGN_ADDRESS_CLAIMED,
            .pgn_mask = J1939_PGN_PDU1_MAX,
        }, {
            .pgn = J1939_PGN_REQUEST,
            .pgn_mask = J1939_PGN_PDU1_MAX,
        }, {
            .pgn = J1939_PGN_ADDRESS_COMMANDED,
            .pgn_mask = J1939_PGN_MAX,
        },
    };
    setsockopt(sock, SOL_CAN_J1939, SO_J1939_FILTER, &filt, sizeof(filt));

在此示例中，该套接字将只接收与地址申领相关PGN 的消息：
`J1939_PGN_ADDRESS_CLAIMED`、`J1939_PGN_REQUEST` 
`J1939_PGN_ADDRESS_COMMANDED`。这在你想监控和处理地址申领、而不J1939 网络
其他流量淹没的场景中特别有用

#### ``SO_J1939_PROMISC``


`SO_J1939_PROMISC` 选项启用套接字级的混杂模式。启用此选项后，套接字将接收
所J1939 流量，无`bind()` `connect()` 设置了任何过滤器。这类似于为
以太网接口启用混杂模式，此时网络段上的所有流量都被捕获

然而，**`SO_J1939_FILTER` 的优先级高于 `SO_J1939_PROMISC`**。这意味着即使
混杂模式下，你也可以通过应用 `SO_J1939_FILTER` 的特定过滤器来减少接收到的包
数量。过滤器将限制哪些包被传递给套接字，从而在混杂模式处于活动状态时允许
精细的流量选择

此选项可接受的值大小为 `sizeof(int)`，并且值只`0` 和非零之间区分。值为
`0` 时禁用混杂模式，而任何非零值启用它

这种组合在调试或监控特定类型流量同时仍捕获大量消息时很有用

示例


    int value = 1;
    setsockopt(sock, SOL_CAN_J1939, SO_J1939_PROMISC, &value, sizeof(value));

在此示例中，`value` 设置为任何非零值（例如 `1`）会启用混杂模式，允许该
套接字接收网络上所有的 J1939 流量

#### ``SO_BROADCAST``


`SO_BROADCAST` 选项启用广播消息的发送和接收。默认情况下，J1939 套接字的广播
消息是禁用的。启用此选项后，该套接字将被允许J1939 网络上发送和接收广播包

由于 CAN 总线作为共享介质的特性，总线上传输的所有消息对所有参与者都是可见的
J1939 的上下文中，广播指的是使用特定的目的地址字段，其中目的地址被设置为
一个表示该消息面向所有参与者的值（通常是像 0xFF 这样的全局地址）。启用广
选项允许套接字发送和接收此类广播消息

此选项可接受的值大小为 `sizeof(int)`，并且值只`0` 和非零之间区分。值为
`0` 时禁用发送和接收广播消息的能力，而任何非零值启用它

示例


    int value = 1;
    setsockopt(sock, SOL_SOCKET, SO_BROADCAST, &value, sizeof(value));

在此示例中，`value` 设置为任何非零值（例如 `1`）会启用该套接字发送和接收
广播消息

#### ``SO_J1939_SEND_PRIO``


`SO_J1939_SEND_PRIO` 选项设置该套接字发出J1939 消息的优先级。在 J1939 中，
消息可以有不同的优先级，数值越小表示优先级越高。此选项允许用户通过调整 CAN
标识符中的优先级位来控制从该套接字发出的消息的优先级

此选项可接受的*大小**`sizeof(int)`，并且该值预期在 0 7 的范围内
其中 `0` 为最高优先级，`7` 为最低优先级。默认情况下，如果未显式配置此选项
优先级设`6`

注意，优先级`0` `1` 只有在进程具`CAP_NET_ADMIN` 能力时才能设置
它们保留给高优先级流量，需要管理员权限

示例


    int prio = 3;  // Priority value between 0 (highest) and 7 (lowest)
    setsockopt(sock, SOL_CAN_J1939, SO_J1939_SEND_PRIO, &prio, sizeof(prio));

在此示例中，优先级被设为 `3`，意味着发出的消息将以中等优先级发送

#### ``SO_J1939_ERRQUEUE``


`SO_J1939_ERRQUEUE` 选项使套接字能够从错误队列接收错误消息，提供有关传输失败
协议违规J1939 通信期间发生的其他问题的诊断信息。一旦设置了此选项，用户空
就需要处`MSG_ERRQUEUE` 消息

`SO_J1939_ERRQUEUE` 设置`0` 会清除错误队列中当前存在的任何错误消息
启用后，可以使用 `recvmsg(2)` 系统调用检索错误消息

订阅错误队列时，可以访问以下错误事件

- **`J1939_EE_INFO_TX_ABORT`**：传输中止错误
- **`J1939_EE_INFO_RX_RTS`**：接RTS（Request to Send，请求发送）控制帧
- **`J1939_EE_INFO_RX_DPO`**：接收带有数据页偏移（DPO）的数据包
- **`J1939_EE_INFO_RX_ABORT`**：接收中止错误

错误队列可用于使用会ID（`tskey`）将错误与特定的消息传输会话关联起来。会
ID 通过 `SOF_TIMESTAMPING_OPT_ID` 标志分配，该标志通过启用 `SO_TIMESTAMPING`
选项来设置

如果激活了 `SO_J1939_ERRQUEUE`，用户需要主动从错误队列中提取消息，这意味着
使用普通的 `recv(2)` 不再足够。用户必须使用带有适当标志`recvmsg(2)` 
处理错误消息。如果不这样做，可能导致套接字被队列中未处理的错误消息阻塞

**建议**在大多数情况下将 `SO_J1939_ERRQUEUE` `SO_TIMESTAMPING` 结合使用
这能实现适当的错误处理以及会话跟踪和时间戳，提供对消息传输和错误的更详细分析

此选项可接受的*大小**`sizeof(int)`，并且值只`0` 和非零之间区分
值为 `0` 时禁用错误队列接收并清除任何现有错误消息，而任何非零值启用它

示例


    int enable = 1;  // Enable error queue reception
    setsockopt(sock, SOL_CAN_J1939, SO_J1939_ERRQUEUE, &enable, sizeof(enable));

    // Enable timestamping with session tracking via tskey
    int timestamping = SOF_TIMESTAMPING_OPT_ID | SOF_TIMESTAMPING_TX_ACK |
                       SOF_TIMESTAMPING_TX_SCHED |
                       SOF_TIMESTAMPING_RX_SOFTWARE | SOF_TIMESTAMPING_OPT_CMSG;
    setsockopt(sock, SOL_SOCKET, SO_TIMESTAMPING, &timestamping,
               sizeof(timestamping));

启用后，可以使用 `recvmsg(2)` 检索错误消息。通过`SO_J1939_ERRQUEUE` 
`SO_TIMESTAMPING`（启`SOF_TIMESTAMPING_OPT_ID` `SOF_TIMESTAMPING_OPT_CMSG`
结合使用，用户可以跟踪消息传输、检索精确的时间戳，并将错误与特定会话关联起来

有关启用时间戳和会话跟踪的更多信息，请参`SO_TIMESTAMPING` 一节

#### ``SO_TIMESTAMPING``


`SO_TIMESTAMPING` 选项允许套接字接收与 J1939 中消息传输和接收相关的各种事件的
时间戳。此选项常与 `SO_J1939_ERRQUEUE` 结合使用，以提供详细的诊断信息、会
跟踪以及消息传输的精确时序数据

J1939 中，用户空间提供的所有负载，无论大小，都被内核作*会话**处理。这
包括单帧消息（最8 字节）和多帧协议，如传输协议（TP）和扩展传输协议（ETP）
即使是小的单帧消息，内核也会创建一个会话来管理传输和接收。会话的概念允许内核
管理协议的各个方面，例如重组多帧消息和跟踪传输状态

从错误队列接收扩展错误消息时，错误信息通过 `struct sock_extended_err` 传递，
该结构可通过使用 `recvmsg(2)` 系统调用检索的控制消息（`cmsg`）访问

J1939 中扩展错误消息有两个典型来源

1. `serr->ee_origin == SO_EE_ORIGIN_TIMESTAMPING`锛。

   在这种情况下，`serr->ee_info` 字段将包含以下时间戳类型之一

   - `SCM_TSTAMP_SCHED`：此时间戳对扩展传输协议（ETP）传输和简单传输（8 字节
     或更小）有效。它表示消息或一组帧已被调度进行传输的时间点

     - 对于简单传输（8 字节或更小），它标记消息被排队并准备发送到 CAN 总线
       时刻

     - 对于 ETP 传输，它在发送侧收到 CTS（Clear to Send，清除发送）帧后发送，
       表示一组新的帧已被调度进行传输

     - 此时间戳的传输协议（TP）情况目前尚未实现

     - 在接收侧，ETP 与此事件对应的是`J1939_EE_INFO_RX_DPO` 消息表示的事件，
       它指示接收到了数据页偏移（DPO）控制帧

   - `SCM_TSTAMP_ACK`：此时间戳表示消息或会话已被确认

     - 对于简单传输（8 字节或更小），它标记消息已被发送并CAN 控制器收到回
       确认，表示帧已被传输到总线上

     - 对于多帧传输（TP ETP），它表示整个会话已被确认，通常是在收到消息结束
       确认（EOMA）包之后

2. `serr->ee_origin == SO_EE_ORIGIN_LOCAL`锛。

   在这种情况下，`serr->ee_info` 字段将包含以J1939 栈特定的消息类型之一

   - `J1939_EE_INFO_TX_ABORT`：此消息表示消息或会话的传输被中止。中止的原因
     可能来自各种来源

     - **CAN 栈失*：J1939 栈无法将帧传递给 CAN 框架进行传输

     - **回显失败**：J1939 栈未CAN 控制器收到回显确认，意味着帧可能未成功
       传输CAN 总线

     - **协议级问*：对于多帧传输（TP/ETP），这可能包括与协议相关的错误，例如
       由接收者发出的中止信号或协议级超时，这会导致会话提前终止

     - 相应的错误码存储`serr->ee_data`（`session->err` 在内核侧）中，提
       有关中止具体原因的更多细节

   - `J1939_EE_INFO_RX_RTS`：此消息表示 J1939 栈已收到请求发送（RTS）控制帧
     标志着使用传输协议（TP）或扩展传输协议（ETP）的多帧传输的开始

     - 它通知接收者发送者已准备好传输多帧消息，并包含有关总消息大小和要发送的
       帧数的详细信息

     - `J1939_EE_INFO_RX_RTS` 消息一起提供了诸如 `J1939_NLA_TOTAL_SIZE`
       `J1939_NLA_PGN`、`J1939_NLA_SRC_NAME` `J1939_NLA_DEST_NAME` 等统
       信息，给出有关传入传输的详细信息

   - `J1939_EE_INFO_RX_DPO`：此消息表示 J1939 栈已收到数据页偏移（DPO）控制帧
     它是扩展传输协议（ETP）的一部分

     - DPO 帧通过指示所传输数据中的偏移位置，表ETP 多帧消息的继续。它通过
       标识正在接收消息的哪一部分，帮助接收者管理大数据集

     - 它通常与发送侧的相`SCM_TSTAMP_SCHED` 事件配对，该事件指示下一组帧
       被调度进行传输的时间

     - 此事件包含诸`J1939_NLA_BYTES_ACKED` 等统计信息，它跟踪到该会话此
       为止已确认的字节数

   - `J1939_EE_INFO_RX_ABORT`：此消息表示多帧消息（传输协议或扩展传输协议）的
     接收已被中止

     - 中止可能由协议级错误触发，例如超时、意外帧或来自发送者的特定中止请求

     - 此消息表示接收者无法继续处理该传输，会话被终止

     - 相应的错误码存储`serr->ee_data`（`session->err` 在内核侧）中，提
       有关中止原因的更多细节，例如协议违规或超时

     - 收到此消息后，接收者丢弃部分接收到的帧，多帧会话被视为未完成

在这两种情况下，如果启用`SOF_TIMESTAMPING_OPT_ID`，`serr->ee_data` 将被
设置为会话的唯一标识符（`session->tskey`）。这允许用户空间通过会话标识符跨多个
帧或阶段跟踪消息传输

在所有其他情况下，`serr->ee_errno` 将被设置`ENOMSG`，但 `J1939_EE_INFO_TX_ABORT`
`J1939_EE_INFO_RX_ABORT` 的情况除外，其中内核`serr->ee_data` 设置
存储`session->err` 中的错误。所有特定于协议的错误都被转换为标准内核错误
并存储在 `session->err` 中。这些错误值跨系统调用`serr->ee_errno` 是统一的
一些已知的错误值在 `J1939 栈中的错误码` 一节中描述

当提`J1939_EE_INFO_RX_RTS` 消息时，它将包含多帧消息（TP ETP）的以下
统计信息

  - `J1939_NLA_TOTAL_SIZE`：会话中消息的总大小
  - `J1939_NLA_PGN`：标识消息类型的参数组编号（PGN）
  - `J1939_NLA_SRC_NAME`：源 ECU 64 name
  - `J1939_NLA_DEST_NAME`：目ECU 64 name
  - `J1939_NLA_SRC_ADDR`：发ECU 8 位源地址
  - `J1939_NLA_DEST_ADDR`：接ECU 8 位目的地址

- 对于其他消息（包括单帧消息），只包含以下统计信息

  - `J1939_NLA_BYTES_ACKED`：会话中成功确认的字节数

`SO_TIMESTAMPING` 的关键标志包括：

- `SOF_TIMESTAMPING_OPT_ID`：为每个传输启用使用唯一会话标识符（`tskey`）。此
  标识符有助于在用户空间将消息传输和错误作为不同的会话进行跟踪。启用此选项时，
  `serr->ee_data` 将被设置`session->tskey`

- `SOF_TIMESTAMPING_OPT_CMSG`：通过控制消息（`struct scm_timestamping`）发
  时间戳信息，允许应用程序在检索数据时一并获取时间戳

- `SOF_TIMESTAMPING_TX_SCHED`：提供消息被调度进行传输时的时间
  （`SCM_TSTAMP_SCHED`）

- `SOF_TIMESTAMPING_TX_ACK`：提供消息传输被完全确认时的时间
  （`SCM_TSTAMP_ACK`）

- `SOF_TIMESTAMPING_RX_SOFTWARE`：提供与接收相关事件的时间戳（例
  `J1939_EE_INFO_RX_RTS`、`J1939_EE_INFO_RX_DPO`、`J1939_EE_INFO_RX_ABORT`）

这些标志启用对消息生命周期的详细监控，包括传输调度、确认、接收时间戳，以
收集有关通信会话的详细统计信息，特别是对于像 TP ETP 这样的多帧负载

示例


    // Enable timestamping with various options, including session tracking and
    // statistics
    int sock_opt = SOF_TIMESTAMPING_OPT_CMSG |
                   SOF_TIMESTAMPING_TX_ACK |
                   SOF_TIMESTAMPING_TX_SCHED |
                   SOF_TIMESTAMPING_OPT_ID |
                   SOF_TIMESTAMPING_RX_SOFTWARE;

    setsockopt(sock, SOL_SOCKET, SO_TIMESTAMPING, &sock_opt, sizeof(sock_opt));



### 动态寻址


必须区分使用已申领的地址和进行地址申领。要使用已申领的地址，必须填
`j1939.name` 成员并将其提供给 `bind(2)`。如果该 name 之前已申领了地址，则
所有进一步发送的消息都将使用该地址。并`j1939.addr` 成员将被忽略

此规则的一个例外是 PGN 0x0ee00。这地址申领/无法申领地址"消息，内核将
在必要时对该 PGN 使用 `j1939.addr` 成员

要申领地址，可以使用以下代码示例：


	struct sockaddr_can baddr = {
		.can_family = AF_CAN,
		.can_addr.j1939 = {
			.name = name,
			.addr = J1939_IDLE_ADDR,
			.pgn = J1939_NO_PGN,	/** to disable bind() rx filter for PGN **/
		},
		.can_ifindex = if_nametoindex("can0"),
	};

	bind(sock, (struct sockaddr *)&baddr, sizeof(baddr));

	/** for Address Claiming broadcast must be allowed **/
	int value = 1;
	setsockopt(sock, SOL_SOCKET, SO_BROADCAST, &value, sizeof(value));

	/** configured advanced RX filter with PGN needed for Address Claiming **/
	const struct j1939_filter filt[] = {
		{
			.pgn = J1939_PGN_ADDRESS_CLAIMED,
			.pgn_mask = J1939_PGN_PDU1_MAX,
		}, {
			.pgn = J1939_PGN_REQUEST,
			.pgn_mask = J1939_PGN_PDU1_MAX,
		}, {
			.pgn = J1939_PGN_ADDRESS_COMMANDED,
			.pgn_mask = J1939_PGN_MAX,
		},
	};

	setsockopt(sock, SOL_CAN_J1939, SO_J1939_FILTER, &filt, sizeof(filt));

	uint64_t dat = htole64(name);
	const struct sockaddr_can saddr = {
		.can_family = AF_CAN,
		.can_addr.j1939 = {
			.pgn = J1939_PGN_ADDRESS_CLAIMED,
			.addr = J1939_NO_ADDR,
		},
	};

	/* Afterwards do a sendto(2) with data set to the NAME (Little Endian). If the
  - NAME provided, does not match the j1939.name provided to bind(2), EPROTO
  - will be returned.
	 */
	sendto(sock, dat, sizeof(dat), 0, (const struct sockaddr *)&saddr, sizeof(saddr));

如果在传输后 250ms 内没有其他方对地址申领提出异议，内核将NAME-SA 分配标记
为有效。该有效分配将与其他有效 NAME-SA 分配一起保留。从那一刻起，任何绑定到
NAME 的套接字都可以发送包

如果另一ECU 申领了该地址，内核将把该 NAME-SA 标记为过期。没有任何绑定到
NAME 的套接字可以发送包（地址申领除外）。要申领另一个地址，某个绑定到 NAME 
套接字必须再`bind(2)`，但只将 `j1939.addr` 改为新的 SA，然后必须发送一
有效的地址申领包。这会为NAME 重启内核（以及总线上任何其他参与者）中的状态机

`can-utils` 也包`j1939acd` 工具，因此它可以作为代码示例，或作为默认的地址
申领守护进程

### J1939 栈中的错误码


本节列出了在J1939 栈交互时可能暴露给用户空间的所有潜在内核错误码。它既包
标准错误码，也包括那些从协议特定的中止码派生出来的错误码

- `EAGAIN`：操作会阻塞；重试可能成功。一个常见原因是存在一个活跃的 TP ETP
  会话，并且尝试在相同的对端之间发起一个新的重叠的 TP ETP 会话

- `ENETDOWN`：网络已关闭。这发生CAN 接口被切换到 "down" 状态时

- `ENOBUFS`：没有可用的缓冲区空间。当 CAN 接口的发送（TX）队列已满，无法
  排队更多消息时会发生此错误

- `EOVERFLOW`：值对于已定义的数据类型来说过大。在 J1939 中，如果请求的数
  位于已排队缓冲区之外，就可能发生这种情况。例如，如果 CTS（Clear to Send）请
  一个内核缓冲区中不可用的偏移，因为用户空间没有提供足够的数据

- `EBUSY`：设备或资源忙。例如，如果相同的会话已经处于活跃状态，而栈无法
  该状态恢复，就会发生这种情况

- `EACCES`：权限被拒绝。例如，当尝试发送广播消息，但套接字未配`SO_BROADCAST`
  时，可能发生此错误

- `EADDRNOTAVAIL`：地址不可用。此错误在以下情况发生：

  - 尝试使用 `getsockname(2)` 检索对端的地址，但套接字未连接

  - 尝试向某NAME 发送数据或从某NAME 接收数据，但NAME 的地址申领未由
    栈执行或未被检测到

- `EBADFD`：文件描述符处于错误状态。如果以下情况发生，可能出现此错误：

  - 尝试向未绑定的套接字发送数据

  - 套接字已绑定但没有源 name，并且源地址`J1939_NO_ADDR`

  - `can_ifindex` 不正确

- `EFAULT`：错误的地址。主要发生在栈无法从 sockptr 复制或向其中复制时，即用
  空间提供的数据不足，或用户空间提供的缓冲区对于请求的数据来说不够大时

- `EINTR`：在任何数据传输之前发生了信号；参见 `signal(7)`

- `EINVAL`：传入了无效参数。例如：

  - `msg->msg_namelen` 小于 `J1939_MIN_NAMELEN`

  - `addr->can_family` 不等`AF_CAN`

  - 提供了不正确PGN

- `ENODEV`：没有这样的设备。当为所提供`can_ifindex` 找不CAN 网络设备
  或`can_ifindex` 0 时，会发生这种情况

- `ENOMEM`：内存不足。通常与栈中内存分配的问题有关

- `ENOPROTOOPT`：协议不可用。当使用 `getsockopt(2)` `setsockopt(2)` 时，
  如果请求的套接字选项不可用，就可能发生这种情况

- `EDESTADDRREQ`：需要目的地址。此错误在以下情况发生：

  - `connect(2)` 的情况下，如`struct sockaddr *uaddr` `NULL`

  - `send*(2)` 的情况下，如果尝试将 ETP 消息发送到广播地址

- `EDOM`：参数超出域。如果尝试将 TP ETP 消息发送到保留TP ETP 操作
  控制 PGN PGN，就可能发生此错误

- `EIO`：I/O 错误。如果为 TP ETP 会话提供给套接字的数据量与为该会话声明的
  数据量不匹配，就可能发生此错误

- `ENOENT`：没有这样的文件或目录。当栈尝试传CTS EOMA 但再也找不到匹配
  接收套接字时，可能发生这种情况

- `ENOIOCTLCMD`：套接字层没有可用的 ioctl

- `EPERM`：操作不被允许。例如，当请求的操作需`CAP_NET_ADMIN` 权限时，可能
  发生此错误

- `ENETUNREACH`：网络不可达。最可能发生在帧无法传输CAN 总线时

- `ETIME`：定时器过期。如果尝试发送简单消息时发生超时，例如未收到来自控制器的
  回显消息，就可能发生这种情况

- `EPROTO`：协议错误

  - 用于 J1939 中的各种协议级错误，包括

    - 重复的序列号

    - 意外EDPO ECTS 包

    - EDPO/ECTS 中无效的 PGN 或偏移

    - EDPO 包的数量超过CTS 的允许量

    - 任何其他协议级错误

- `EMSGSIZE`：消息过长

- `ENOMSG`：没有可用消息

- `EALREADY`：ECU 已经参与了一个或多个连接管理的会话，无法再支持另一个

- `EHOSTUNREACH`：发生了超时，会话被中止

- `EBADMSG`：在活跃数据传输期间收到CTS（Clear to Send）消息，导致中止

- `ENOTRECOVERABLE`：达到了最大重传请求限制，会话无法恢复

- `ENOTCONN`：收到了意外的数据传输包

- `EILSEQ`：收到了错误的序列号，软件无法恢复
