
## 以太网端

本文档是phy_port 基础设施的基本描述，该基础设施用于描述以太网设的物理接口
在没phy_port 的情况下，我们已经可以通过 `struct ethtool_link_ksettings <ethtool_link_ksettings>`
属性获得大量关NIC 面向介质一侧接口的能力与外观的信息，包括：

 - NIC 的能力，通过 :c`supported` 字段
 - 链路对端（Link Partner）的通告能力，通过 :c`lp_advertising`
 - 我们自身通告的特性，通过 :c`advertising`

我们还拥有关于线对数量与 PORT 类型的信息。这些信息是通过汇总链路上的各设备所上报的信息构建而来
  - NIC 自身，通过 :c`get_link_ksettings` 回调
  - MAC PCS 的精确信息，通过MAC 驱动中使phylink
  - PHY 设备上报的信  - SFP 模块上报的信息（SFP 模块本身也可能包含一PHY
然而，当我们考虑拥有多个介质接口的设备时，该模型开始显现出其局限性在这种情况下，只会报告当前正在使用的接口的信息，而无法得知其他接能做些什么。事实上，我们对于是否存在其他介质接口也知之甚少
phy_port 表示的目的是：无论端口由什么驱动（NIC 通过固件、SFP 模块、以太网 PHY），
都提供一种表NIC 物理接口的方式
## 多端口接口示

目前观察到的多接NIC 有以下几种情况：

```

  +------------------+
  | SoC              |
  |          +-----+ |           +-----+
  | +-----+  |     |-------------| PHY |
  | | MAC |--| Mux | |   +-----+ +-----+
  | +-----+  |     |-----| SFP |
  |          +-----+ |   +-----+
  +------------------+

```
```

  +------------------------+
  | SoC                    |
  |          +-----+ +-----+
  | +-----+  |     |-| PHY |
  | | MAC |--| Mux | +-----+   +-----+
  | +-----+  |     |-----------| SFP |
  |          +-----+       |   +-----+
  +------------------------+

```
```

  +---------+
  | SoC     |  +-----+  +-----+
  |         |  |     |--| PHY |
  | +-----+ |  |     |  +-----+
  | | MAC |----| Mux |  +-----+
  | +-----+ |  |     |--| PHY |
  |         |  +-----+  +-----+
  |         |     |
  |    GPIO-------+
  +---------+

```
```

  +---------+
  | SoC     | +-----+
  |         | |     |--- RJ45
  | +-----+ | |     |
  | | MAC |---| PHY |   +-----+
  | +-----+ | |     |---| SFP |
  +---------+ +-----+   +-----+

```
phy_port 旨在通过以一种与驱动无关的方式表示介质接口，从而为支持上述所有拓扑结构提供途径struct phy_port 对象拥有自己的一组回调操作，并且
```

             _____      +------+
            (     )-----| Port |
 +-----+   (       )    +------+
 | MAC |--(   ???   )
 +-----+   (       )    +------+
            (_____)-----| Port |
                        +------+

```
