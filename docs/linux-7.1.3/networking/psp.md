
## PSP 安全协议


## 协议


PSP 安全协议（PSP）由 Google 定义，并发布于：

https://raw.githubusercontent.com/google/psp/main/doc/PSP_Arch_Spec.pdf

本节简要介绍理解内核 API 所必需的关键协议内容。更多细节请参阅协议规范。

注意，内核实现与文档使用 “device key”（设备密钥）而非 “master key”
（主密钥），这既不易让普通开发者困惑，也不太可能违反任何命名规范。

### 派生的 Rx 密钥


PSP 借鉴了 IPsec 的一些术语和机制。PSP 在设计时考虑了 HW（硬件）卸载。PSP
的关键特性是，每条连接的 Rx 密钥不必由接收方存储，而是可以从设备密钥和数据
包头中的信息派生出来。这使得实现接收方时可以做到不论连接数量多少都只需恒定
大小的内存（`O(1)` 扩展）。

Tx 密钥必须像其他协议一样存储，但 Tx 对延迟的敏感度远低于 Rx，从慢速内存
获取密钥的延迟不太可能导致丢包。最好将 Tx 密钥随数据包一起提供（例如作为
描述符的一部分）。

### 密钥轮换


仅接收方知晓的设备密钥是该设计的基础。按照规范，此状态不能直接访问（必须
无法从接收方 NIC 的硬件中读出）。此外，它必须定期（“轮换”，通常每天）进行
 “rotation”（轮换）。轮换意味着生成新的设备密钥（由设备的随机数生成器生成），
并用于所有新连接。为避免中断旧连接，旧设备密钥保留在 NIC 中。包头中携带的
一个相位位（phase bit）指示该数据包是用哪一代设备密钥加密的。

## 用户态 API


PSP 主要面向硬件卸载而设计。对于没有支持 PSP 的 NIC 的系统，目前没有软件回退
方案。也没有建立 PSP 安全连接或交换对称密钥的标准（或其他已定义）方式。

预期由高层协议负责协议与密钥协商。例如，可以使用 TLS 密钥交换，通告 PSP 能力，
并在两端都支持 PSP 时切换到 PSP。

PSP 的所有配置都通过 PSP netlink 族完成。

### 设备发现


PSP netlink 族定义了用于获取系统上可用 PSP 设备的信息、配置它们以及访问 PSP
相关统计的操作。

### 保护连接


PSP 加密目前仅支持 TCP 连接。Rx 和 Tx 密钥分开分配。首先需要发出 `rx-assoc`
Netlink 命令，指定一个目标 TCP 套接字。内核将从 NIC 分配一个新的 PSP Rx 密钥，
并将其与给定套接字关联。在此阶段，套接字既接受 PSP 保护的 TCP 包，也接受明文
TCP 包。

Tx 密钥通过 `tx-assoc` Netlink 命令安装。一旦安装了 Tx 密钥，从套接字读取的
所有数据都将是 PSP 保护的。换言之，安装 Tx 密钥这一动作会对 Rx 方向产生附带
影响。

在 `tx-assoc` 成功返回之后、TCP 套接字遇到其第一个 PSP 认证数据包之前，存在
一个中间阶段，在此期间即便数据包未经过 PSP 认证，TCP 栈也允许某些非数据报文
（即 ACK、FIN 和 RST）进入 TCP 接收处理。在 `tx-assoc` 调用期间，会记录 TCP
套接字的 `rcv_nxt` 字段。此时，ACK 和 RST 将以任意序列号被接受，而 FIN 仅会
在锁存（latched）的 `rcv_nxt` 值处被接受。一旦 TCP 栈遇到第一个包含 PSP 认证
数据的 TCP 包，连接另一端必然已执行过 `tx-assoc` 命令，因此任何 TCP 包（包括
无数据的包）若未成功认证，都会在接收处理前被丢弃。下表对此作了总结。上述拒绝
所有非 PSP 包的状态被称为 “PSP Full”。

+----------------+------------+------------+-------------+-------------+
| 事件           | 普通 TCP   | Rx PSP     | Tx PSP      | PSP 完整    |
+================+============+============+=============+=============+
| Rx 明文        | 接受       | 接受       | 丢弃        | 丢弃        |
| （数据）       |            |            |             |             |
+----------------+------------+------------+-------------+-------------+
| Rx 明文        | 接受       | 接受       | 接受        | 丢弃        |
| (ACK|FIN|RST)  |            |            |             |             |
+----------------+------------+------------+-------------+-------------+
| Rx PSP (有效)  | 丢弃       | 接受       | 接受        | 接受        |
+----------------+------------+------------+-------------+-------------+
| Rx PSP (无效   | 丢弃       | 丢弃       | 丢弃        | 丢弃        |
| crypt, !=SPI)  |            |            |             |             |
+----------------+------------+------------+-------------+-------------+
| Tx             | 明文       | 明文       | 加密        | 加密        |
|                |            |            | （重传除外）| （重传除外）|
+----------------+------------+------------+-------------+-------------+

为确保 `tx-assoc` 调用成功返回后从套接字读取的任何数据都已被认证，内核会在
`tx-assoc` 时扫描该套接字的接收队列和 ofo（乱序）队列。如果有任何已入队的包
是以明文接收的，Tx 关联将失败，应用程序应在排空套接字后重试安装 Tx 密钥（若
两端都行为良好，则无需如此）。

由于在升级到 PSP 之前 TCP 序列号未受完整性保护，中间人（MITM）有可能偏移序列
号，从而删除 TCP 流中 PSP 保护部分的前缀。如果用户空间希望缓解此类攻击，应在
`tx-assoc` 之后交换一个特殊的 “start of PSP”（PSP 起始）消息。

### 轮换通知


设备密钥的轮换是异步发生的，通常由管理守护进程执行，不受应用程序控制。每当
密钥轮换时，PSP netlink 族都会生成通知。应用程序应在密钥再次轮换之前重新建立
连接。

## 内核实现


### 驱动说明


驱动应尽可能以未启用 PSP 的状态启动（`dev-get` 中的 `psp-versions-ena` 设为
`0`）。用户空间不应依赖此行为，因为未来的扩展可能需要创建已启用 PSP 的设备，
尽管如此，驱动默认不应启用 PSP。启用 PSP 应属于同时负责密钥轮换的系统组件的
职责。

注意，`psp-versions-ena` 预期仅用于启用接收处理。在 `psp-versions-ena` 被
禁用后，设备不应拒绝发送请求。用户也可能在存在活动关联时禁用 `psp-versions-ena`，
这将导致所有 PSP Rx 处理中断。

驱动应确保在初始化时设备密钥即可用且安全，无需用户空间显式轮换密钥。必须能够
分配可用的密钥，且不得生成重复密钥。如果设备允许主机为任意 SPI 请求密钥——驱动
应丢弃两个设备密钥（将设备密钥轮换两次），以避免可能使用先前 OS 实例已经访问
过的 SPI+密钥。

驱动必须使用 `psp_skb_get_assoc_rcu()` 来检查是否为给定 skb 请求了 PSP Tx
卸载。在 Rx 方向，驱动应分配并填充 `SKB_EXT_PSP` skb 扩展，并将 skb->decrypted
位置为 1。

### 内核实现说明


PSP 实现比 IPsec 卸载更接近 TLS 卸载，采用每套接字状态，并使用 skb->decrypted
来防止明文泄漏。

PSP 设备与 netdev 相互独立，以便能将 PSP 卸载能力 “delegate”（委派）给软件
设备（例如 `veth`）。
