## NO_HZ：减少调度时钟节拍


本文档描述了可以减少调度时钟中断数量的 Kconfig 选项和启动参数，从而提升能效并
降低 OS 抖动。降低 OS 抖动对于某些类型的计算密集型高性能计算（HPC）应用以及实时
应用非常重要。

管理调度时钟中断（也称为“调度时钟节拍”或简称“节拍”）主要有三种方式：

1. 从不省略调度时钟节拍（CONFIG_HZ_PERIODIC=y，或在较旧内核中
	CONFIG_NO_HZ=n）。你通常 -不- 会想要选择此选项。

2. 在空闲 CPU 上省略调度时钟节拍（CONFIG_NO_HZ_IDLE=y，或在较旧内核中
	CONFIG_NO_HZ=y）。这是最常见的方法，应作为默认选项。

3. 在空闲或仅有一个可运行任务的 CPU 上省略调度时钟节拍
	（CONFIG_NO_HZ_FULL=y）。除非你在运行实时应用或某些类型的 HPC
	工作负载，否则通常 -不会- 想要此选项。

这三种情况将在接下来的三节中描述，之后有一节专门讨论 RCU 相关的考量，一节讨论
测试，以及最后一节列出已知问题。


## 从不省略调度时钟节拍


1990 年代和 2000 年代初的非常老的 Linux 版本无法省略调度时钟节拍。事实证明，在
某些情况下这种老式方法仍然是正确的做法，例如，在具有大量使用 CPU 短突发任务的
繁重工作负载中，其中存在非常频繁的空闲期，但这些空闲期也相当短（数十或数百微秒）。
对于这类工作负载，调度时钟中断通常无论如何都会送达，因为每个 CPU 上经常会存在多个
可运行任务。在这些情况下，试图关闭调度时钟中断除了增加进出空闲态以及在用户态和
内核态执行之间切换的开销外，不会有其他效果。

可以使用 CONFIG_HZ_PERIODIC=y（或在较旧内核中 CONFIG_NO_HZ=n）选择这种模式。

然而，如果你运行的是具有较长空闲期的轻量级工作负载，未能省略调度时钟中断将导致
过度的功耗。这在电池供电的设备上尤其糟糕，会导致电池续航时间极短。因此，如果你在
运行轻量级工作负载，应该阅读下一节。

此外，如果你运行的是实时工作负载或具有短迭代的 HPC 工作负载，调度时钟中断可能
会降低应用程序的性能。如果你的情况符合这一点，应该阅读接下来的两节。


## 为空闲 CPU 省略调度时钟节拍


如果某个 CPU 处于空闲状态，向它发送调度时钟中断就没有什么意义。毕竟，调度时钟
中断的主要目的是迫使繁忙的 CPU 在多项任务之间切换注意力，而空闲的 CPU 没有需要
切换注意力的任务。

不接收调度时钟中断的空闲 CPU 被称为处于“dyntick-idle”、“dyntick-idle 模式”、
“nohz 模式”或“无节拍运行”。本文档余下部分将使用“dyntick-idle 模式”。

CONFIG_NO_HZ_IDLE=y 这一 Kconfig 选项会让内核避免向空闲 CPU 发送调度时钟中断，这
对电池供电的设备和高度虚拟化的主机都至关重要。运行 CONFIG_HZ_PERIODIC=y 内核的
电池供电设备会很快耗尽电量，速度很容易达到运行 CONFIG_NO_HZ_IDLE=y 内核的同款
设备的 2-3 倍。运行 1,500 个 OS 实例的主机可能会发现其一半的 CPU 时间被不必要的
调度时钟中断消耗。在这些情况下，有很强的动机去避免向空闲 CPU 发送调度时钟中断。
话虽如此，dyntick-idle 模式并非免费：

1. 它增加了进出空闲循环路径上执行的指令数量。

2. 在许多架构上，dyntick-idle 模式还会增加昂贵的时钟重编程操作次数。

因此，具有激进实时响应约束的系统经常运行 CONFIG_HZ_PERIODIC=y 内核（或在较旧内核中
CONFIG_NO_HZ=n），以避免退化空闲转换延迟。

还有一个启动参数 “nohz=”，可以在 CONFIG_NO_HZ_IDLE=y 内核中通过指定 “nohz=off”
来禁用 dyntick-idle 模式。默认情况下，CONFIG_NO_HZ_IDLE=y 内核以 “nohz=on” 启动，
启用 dyntick-idle 模式。


## 为仅有一个可运行任务的 CPU 省略调度时钟节拍


如果某个 CPU 只有一个可运行任务，向它发送调度时钟中断就没有什么意义，因为没有
其他任务可以切换。请注意，为仅有一个可运行任务的 CPU 省略调度时钟节拍，也意味着
为空闲 CPU 省略它们。

CONFIG_NO_HZ_FULL=y 这一 Kconfig 选项会让内核避免向具有单个可运行任务的 CPU 发送
调度时钟中断，此类 CPU 被称为“adaptive-ticks CPU（自适应节拍 CPU）”。这对于具有
激进实时响应约束的应用很重要，因为它允许这些应用把最坏情况响应时间改善一个调度
时钟中断的最大持续时间。它对于计算密集型的短迭代工作负载也很重要：如果任何 CPU
在给定迭代期间被延迟，所有其他 CPU 都将被迫空闲等待，直到被延迟的 CPU 完成。因此，
延迟被乘以 CPU 数量减一。在这些情况下，再次有强烈动机去避免发送调度时钟中断。

默认情况下，没有 CPU 会成为自适应节拍 CPU。“nohz_full=”启动参数指定自适应节拍
CPU。例如，“nohz_full=1,6-8” 表示 CPU 1、6、7、8 为自适应节拍 CPU。请注意，你
被禁止将所有 CPU 都标记为自适应节拍 CPU：必须至少有一个非自适应节拍 CPU 保持在线，
以处理时间保持任务，从而确保像 gettimeofday() 这样的系统调用在自适应节拍 CPU 上
返回准确的值。（这对于 CONFIG_NO_HZ_IDLE=y 不是问题，因为没有运行的用户进程会
观察到时钟速率上的轻微漂移。）请注意，这意味着你的系统必须至少有两个 CPU，
CONFIG_NO_HZ_FULL=y 才能对你产生任何效果。

最后，自适应节拍 CPU 必须将其 RCU 回调卸载。这将在下面的“RCU 影响”一节中介绍。

通常，只要可能，CPU 就会一直保持在自适应节拍模式。特别是，转换到内核态不会自动
改变模式。相反，CPU 只有在需要时才会退出自适应节拍模式，例如，当该 CPU 入队了一个
RCU 回调时。

就像 dyntick-idle 模式一样，自适应节拍模式的好处也不是免费的：

1. CONFIG_NO_HZ_FULL 会选择 CONFIG_NO_HZ_COMMON，因此你无法在运行 dyntick 空闲
	的同时不运行自适应节拍。这种依赖关系一直延伸到实现层面，因此 CONFIG_NO_HZ_IDLE
	的所有代价也由 CONFIG_NO_HZ_FULL 承担。

2. 由于需要通知内核子系统（例如 RCU）模式的改变，用户态/内核态转换会稍微昂贵一些。

3. POSIX CPU 定时器会阻止 CPU 进入自适应节拍模式。需要基于 CPU 时间消耗采取行动的
	实时应用需要使用其他手段来实现。

4. 如果待处理的 perf 事件数量超过硬件所能容纳的数量，它们通常会被轮转调度，以便
	随着时间收集全部事件。自适应节拍模式可能会阻止这种轮转的发生。这可能会通过阻止
	具有大量待处理 perf 事件的 CPU 进入自适应节拍模式来修复。

5. 自适应节拍 CPU 的调度器统计可能会以与非自适应节拍 CPU 略微不同的方式计算。这
	反过来可能扰动实时任务的负载均衡。

尽管预期会随着时间不断改进，自适应节拍对于许多类型的实时和计算密集型应用已经相当
有用。然而，上面列出的缺点意味着自适应节拍（目前）不应默认启用。


## RCU 影响


在某些情况下，空闲 CPU 不能被允许进入 dyntick-idle 模式或自适应节拍模式，最常见
的情况是该 CPU 有待处理的 RCU 回调。

通过使用 CONFIG_RCU_NOCB_CPU=y 这一 Kconfig 选项，将 RCU 回调处理卸载到 “rcuo”
kthread 来避免这种情况。要卸载的具体 CPU 可以使用 “rcu_nocbs=” 内核启动参数选择，
它接受一个逗号分隔的 CPU 和 CPU 范围列表，例如 “1,3-5” 选择 CPU 1、3、4、5。请注意，
由 “nohz_full” 内核启动参数指定的 CPU 也会被卸载。

被卸载的 CPU 永远不会入队 RCU 回调，因此 RCU 永远不会阻止被卸载的 CPU 进入 dyntick-idle
模式或自适应节拍模式。话虽如此，请注意，如果需要，由用户态负责将 “rcuo” kthread
固定到特定的 CPU。否则，调度器将决定在哪里运行它们，这可能符合也可能不符合你的
期望。


## 测试


你启用了本文档描述的所有 OS 抖动特性，却没有看到工作负载行为有任何变化。这是因为
你的工作负载受 OS 抖动影响不大，还是因为有其他东西挡在中间？本节通过提供一个简单
的 OS 抖动测试套件来帮助你回答这个问题，该套件可在以下 git 仓库的 master 分支上获取：

git://git.kernel.org/pub/scm/linux/kernel/git/frederic/dynticks-testing.git

克隆该仓库并遵循 README 文件中的说明。此测试过程将产生一个 trace，让你能够评估是否
成功从系统中消除了 OS 抖动。如果此 trace 显示你已经尽可能地消除了 OS 抖动，那么
你可以得出结论：你的工作负载对 OS 抖动并不那么敏感。

注意：此测试要求你的系统至少有两个 CPU。我们目前还没有好办法从单 CPU 系统中
消除 OS 抖动。


## 已知问题


- Dyntick-idle 会稍微减慢进出空闲态的转换。在实践中，除了最具
	攻击性的实时工作负载外，这从来不是问题，而这些工作负载可以选择禁用
	dyntick-idle 模式，大多数也确实这样做了。然而，一些工作负载无疑会
	想要使用自适应节拍来消除调度时钟中断延迟。以下是为这些工作负载提供的
	一些选项：

	a.	从用户态使用 PMQOS 告知内核你的延迟需求（首选）。

	b.	在 x86 系统上，使用 “idle=mwait” 启动参数。

	c.	在 x86 系统上，使用 “intel_idle.max_cstate=” 来限制
		`	最大 C-state 深度。

	d.	在 x86 系统上，使用 “idle=poll” 启动参数。
		但是，请注意使用此参数可能导致你的 CPU 过热，进而可能引起热节流
		从而降低你的延迟——而且这种退化可能比 dyntick-idle 更严重。此外，
		此参数会在 Intel CPU 上有效地禁用 Turbo Mode，这可能显著降低最大
		性能。

- 自适应节拍会稍微减慢用户态/内核态转换。对于计算密集型
	工作负载来说，预计这不是问题，因为它们很少有此类转换。需要仔细的
	基准测试来确定其他工作负载是否受到此效应的显著影响。

- 除非给定 CPU 只有一个可运行任务，否则自适应节拍什么也不做，即使还存在许多其他
	不需要调度时钟节拍的情况。仅举一例，考虑一个 CPU 拥有一个可运行的高优先级
	SCHED_FIFO 任务和任意数量的低优先级 SCHED_OTHER 任务。在这种情况下，该 CPU
	被要求运行 SCHED_FIFO 任务，直到它阻塞或有其他更高优先级任务在该 CPU 上唤醒
	（或被分配给该 CPU），因此向该 CPU 发送调度时钟中断毫无意义。然而，当前的实现
	仍然会向具有单个可运行 SCHED_FIFO 任务和多个可运行 SCHED_OTHER 任务的 CPU 发送
	调度时钟中断，即使这些中断是不必要的。

	即使给定 CPU 上有多个可运行任务，在该当前运行任务的时间片到期之前中断该 CPU
	也毫无意义，而时间片几乎总是远长于下一次调度时钟中断的时间。

	更好地处理这类情况是将来的工作。

- 重新配置自适应空闲和 RCU 回调卸载都需要重启。如果需要，可以提供运行时
	重新配置，然而，由于运行时重新配置 RCU 的复杂性，需要有极其充分的理由。
	特别是考虑到你有一个直接的选择：简单地从所有 CPU 卸载 RCU 回调，并在你想固定
	它们的任何时候将它们固定到你想要的位置。

- 需要处理其他 OS 抖动来源（包括中断和系统工具任务与进程）需要额外的配置。这种
	配置通常涉及将中断和任务绑定到特定的 CPU。

- 某些 OS 抖动来源目前只能通过约束工作负载来消除。例如，消除由全局 TLB
	shootdown 引起的 OS 抖动的唯一方法是避免导致这些 shootdown 的解映射操作
	（例如内核模块卸载操作）。再举一例，可以通过使用大页并约束应用程序使用的内存量
	来减少（并在某些情况下消除）缺页和 TLB 缺失。预故障化（pre-faulting）工作集
	也很有帮助，尤其是与 mlock() 和 mlockall() 系统调用结合使用时。

- 除非所有 CPU 都空闲，否则至少有一个 CPU 必须保持调度时钟中断运行，以支持准确的
	时间保持。

- 如果可能存在一些自适应节拍 CPU，那么即使所有 CPU 在其他方面都空闲，也至少会
	有一个 CPU 保持调度时钟中断运行。

	更好地处理这种情况是正在进行的工作。

- 一些进程处理操作仍然需要偶尔的调度时钟节拍。这些操作包括计算 CPU 负载、维护
	sched 平均值、计算 CFS 实体 vruntime、计算 avenrun，以及执行负载均衡。它们
	目前由大约每秒一次的调度时钟节拍来满足。正在进行的工作将消除对这些不频繁的
	调度时钟节拍的需求。
