### timeofday 与时钟源管理

John Stultz 的通用时间of day（GTOD）框架将大量代码从架构相关区域移出，纳入一个通用管理框架，如#3（OLS 幻灯片第 18 页）所示。架构相关的部分缩减为时钟源的低级硬件细节，这些时钟源在框架中注册，并基于质量决策被选中。低级代码提供硬件设置和读取例程，并初始化供通用时间保持代码使用的数据结构，以将时钟 tick 转换为基于纳秒的时间值。所有其他与时间保持相关的功能都被移入通用代码。GTOD 基础补丁合入2.6.18 内核

### 时钟事件管理

时钟源提供对单调递增时间值的读取访问，而时钟事件设备（clock event device）用于调度下一个事件中断。当前下一个事件被定义为周期性的，其周期在编译时定义。为各种事件驱动功能而进行的事件设备的设置与选择被硬编码进架构相关的代码中。这导致所有架构上出现重复代码，并且使得更改系统配置以使用除已内建在架构中的事件中断设备之外的其他设备变得极其困难。当前设计的另一个含义是：为了提供像高分辨率定时器或动tick 这样的新功能，必须触及所有架构相关的实现
时钟事件子系统试图通过提供一个通用解决方案来解决此问题，以管理时钟事件设备及其在各种时钟事件驱动的 kernel 功能中的使用。时钟事件子系统的目标是将时钟事件相关的架构相关代码最小化为纯粹的硬件相关处理，并允许轻松添加和利用新的时钟事件设备。它还将跨架构的重复代码最小化，因为通用功能一直下探到几乎天生与硬件相关的中断服务处理程序
时钟事件设备由架构相关的引导代码或在模块插入时注册。每个时钟事件设备用一个包含时钟相关属性参数和回调函数的数据结构填充。时钟事件管理通过使用指定的属性参数，决定一个时钟事件设备将被用于支持的一组系统功能。这包括对每 CPU 和每系统全局事件设备的区分
系统级全局事件设备用于 Linux 周期tick。每 CPU 事件设备用于提供本地 CPU 功能，例如进程记账、剖析（profiling）和高分辨率定时器
管理层将以下一项或多项功能分配给一个时钟事件设备：

      - 系统全局周期tick（jiffies 更新      - cpu 本地 update_process_times
      - cpu 本地剖析（profiling      - cpu 本地下一个事件中断（非周期模式）

时钟事件设备将那些与定时器中断相关功能的完全选择委托给管理层。时钟管理层在设备描述结构中存储一个函数指针，该函数指针必须从硬件级处理程序中调用。这从架构相关的定时器中断处理程序中移除了大量重复代码，并将对时钟事件设备以及定时器中断相关功能分配的控制交给了核心代码
时钟事件API 相当小。除了时钟事件设备注册接口外，它还提供调度下一个事件中断、时钟事件设备通知服务以及挂起（suspend）和恢复（resume）支持的函数
该框架增加了700 行代码，导致内核二进制大小增2KB。i386 的转换移除了100 行代码。二进制大小减少400 字节。我们相信，灵活性的提升以及跨架构重复代码的避免，证明了二进制大小的轻微增加是合理的
架构的转换没有功能性影响，但允许在不对时钟事件设备和定时器中断代码做任何改动的情况下，利用高分辨率和动tick 功能。转换之后，启用高分辨率定时器与动tick 只需kernel/time/Kconfig 文件添加到架构相关的 Kconfig，并向空闲例程添加动tick 特定的调用（向空闲函数和 Kconfig 文件总共添加 3 行）

### 楂樺垎杈ㄧ巼瀹氭椂鍣ㄥ姛鑳。
在系统引导期间无法使用高分辨率定时器功能，而使其可用将很困难且没有任何用处。必须完成时钟事件设备框架、时钟源框架（GTOD）以hrtimer 自身的初始化，并注册合适的时钟源和时钟事件设备，高分辨率功能才能工作。在 hrtimer 初始化之前，系统以通常的低分辨率周期模式工作。时钟源和时钟事件设备层提供通知函数，向 hrtimer 告知新硬件的可用性。hrtimer 在切换到高分辨率模式之前，会验证已注册的时钟源和时钟事件设备的可用性。这也确保了一个为高分辨率定时器配置的内核可以运行在缺乏必要硬件支持的系统上
高分辨率定时器代码不支持只有全局时钟事件设备SMP 机器。支持此类硬件将涉及在中断发生时进行 IPI 调用。其开销将远大于收益。这就是为什么我们目前在 i386 SMP 系统上禁用高分辨率和动tick——这些系统在 C3 电源状态下停止本地 APIC。已有作为构想的变通方案，但问题尚未被着手解决
定时器按时间有序的插入提供了全部所需的基础设施，以决定在添加一个定时器时是否必须重新编程事件设备。该决策按定时器基（timer base）进行，并在一个支持函数中跨每 CPU 定时器基同步。该设计允许系统利用独立的每 CPU 时钟事件设备来服务每 CPU 定时器基，但目前仅利用了CPU 一个可重编程的时钟事件设备
当定时器中断发生时，下一个事件中断处理程序由时钟事件分发代码调用，并将过期的定时器从红黑树移动到单独的双向链表，并调softirq 处理程序。hrtimer 结构中的一个附加模式字段允许系统直接从下一个事件中断处理程序执行回调函数。这仅限于可以安全在硬中断上下文中执行的代码。例如，这适用nanosleep 所使用的常见唤醒函数场景。在中断上下文中执行处理程序的优点是避免了多达两次的上下文切换——从被中断的上下文到 softirq，再到被过期定时器唤醒的任务
一旦系统切换到高分辨率模式，周期tick 就被关闭。这会禁用每系统全局的周期性时钟事件设备——例i386 SMP 系统上的 PIT
周期tick 功能由一个每 CPU hrtimer 提供。回调函数在下一个事件中断上下文中执行，更新 jiffies 并调update_process_times profiling。基hrtimer 的周期tick 的实现被设计为可用动tick 功能扩展。这允许UP 系统上使用单个时钟事件设备来调度高分辨率定时器和周期事件（jiffies tick、profiling、进程记账）。这已被证明i386 PIT PPC Incrementer 上可行
用于运行 hrtimer 队列并执行回调的 softirq 已从绑定tick 的定时器 softirq 中分离出来，以允许准确投递被 itimer POSIX 间隔定时器使用的高分辨率定时器信号。此 softirq 的执行仍可能被其softirq 延迟，但总体上延迟已因这一分离而显著改善

### 动tick

动tick 是基hrtimer 的周期tick 替代（sched_tick）的逻辑结果。sched_tick hrtimer 的功能通过三个函数扩展
- hrtimer_stop_sched_tick
- hrtimer_restart_sched_tick
- hrtimer_update_jiffies

当某CPU 进入空闲状态时调用 `hrtimer_stop_sched_tick()`。该代码评估下一个被调度的定时器事件（来hrtimer timer wheel 两者），如果下一个事件比下一tick 更远，它sched_tick 重新编程到该未来事件，以允许更长的空闲睡眠而不会被周期tick 无谓地打断。当一个在空闲期间发生、且不会导致重新调度（reschedule）的中断发生时，也会调用该函数。这次调用是必要的，因为中断处理程序可能已触发了一个新的定时器，其到期时间早于上一次调`hrtimer_stop_sched_tick()` 时所确定的最近事件时间
CPU 在调schedule() 之前离开空闲状态时调用 `hrtimer_restart_sched_tick()`。`hrtimer_restart_sched_tick()` 恢复周期tick，该 tick 保持活动直到下一次调`hrtimer_stop_sched_tick()`
当空闲期间发生中断时，`hrtimer_update_jiffies()` `irq_enter()` 调用，以确保 jiffies 是最新的，且中断处理程序不必处理可能陈旧jiffy 值
动tick 功能提供统计值，这些值通过 /proc/stat 导出到用户空间，并可用于增强的电源管理控制
该实现为进一步的开发留有余地，例如完全tickless 系统（其中时间片由调度器控制）、可变频率剖析，以及未来完全移除 jiffies
除了当前 i386 支持的初始提交外，该补丁集已扩展x86_64 ARM。对 MIPS PowerPC 的初始（进行中）支持也可用
