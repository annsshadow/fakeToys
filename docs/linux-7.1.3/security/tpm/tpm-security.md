
## TPM 安全


本文档的目的在于描述我们如何让内核使TPM 的方式，在面对外部嗅探与报文篡改
攻击（文献中称为被动与主动中间人（interposer）攻击）时具有合理的健壮性。当的安全文档针对的TPM 2.0
### 简

TPM 通常是一个通过某种低带宽总线连接PC 的独立芯片。也有例外，例如 Intel
PTT，它是一个运行在靠近 CPU 的软件环境中的软TPM，会面临不同的攻击；但就目前
而言，大多数加固的安全环境都要求使用独立硬件 TPM，这也是此处讨论的用例
### 针对总线的嗅探与篡改攻击


当前最先进的嗅探手段是 `TPM Genie`_ 硬件中间人，它是一个简单的外部设备，可以在
几秒钟内安装到任何系统或笔记本上。最近，针对 `Windows Bitlocker TPM`_ 系统的攻被成功演示。最近又有针`基于 TPM Linux 磁盘加密`_ 方案的同种攻击。下一阶段
的研究似乎是入侵总线上的现有设备，使之充当中间人，因此攻击者需要物理接触几秒钟
这一前提条件可能会消失。然而，本文档的目标是在这种环境下尽其所能地保护 TPM 秘密与完整性，并力求保证：如果我们无法阻止攻击，那么至少能够检测到它
遗憾的是，包括硬件复位能力在内的大部TPM 功能，都可以被能够访问总线的攻击控制，因此我们将在下面讨论一些可能的破坏手段
### 度量（PCR）完整

由于攻击者可以向 TPM 发送他们自己的命令，他们可以发送任意的 PCR 扩展，从而破度量系统，这将是一种恼人的拒绝服务攻击。不过，还有两类针对密封到信任度量的实体更严重攻击
1. 攻击者可以拦截来自系统的所PCR 扩展，并完全替换为他们自己的值，从而产生一   未被篡改状态的重放，使 PCR 度量证明系统处于可信状态并释放秘密
2. 在某个时间点，攻击者可以复TPM，清PCR，然后发送他们自己的度量值，这将
   有效地覆盖掉 TPM 已经完成的启动时刻度量
第一种可以由 PCR 扩展和读取命令始终使HMAC 保护来挫败，这意味着度量值无法在导致响应中出现可检测到HMAC 失败的情况下被替换。然而，第二种只能真正依赖于某种
TPM 复位时会变化的保护机制来检测
### 秘密保护


某些进出 TPM 的信息，例如密钥密封、私钥导入和随机数生成，容易被拦截，而仅HMAC
保护无法防范，因此对于这类命令，我们还必须采用请求与响应加密，以防止秘密信息
泄露
### TPM 建立初始信任


为了从一开始就提供安全性，必须建立一个初始的共享或对称秘密，并且它也必须不为
攻击者所知。最明显的途径是背书（endorsement）种子和存储（storage）种子，它们可以
用来派生非对称密钥。然而，使用这些密钥很困难，因为将它们传入内核的唯一方式是在
命令行上，而这需要启动系统提供大量支持，并且无法保证这两个层级中的任何一个不带有某种类型的授权
Linux 内核所选择的机制是，使用标准存储种子参数，null 种子派生出主椭圆曲线密钥null 种子有两个优点：首先，该层级在物理上不可能带有授权，因此我们总能够使用它其次，null 种子TPM 复位时会改变，这意味着如果我们在一开始就基于 null 种子建立
信任，那么所有用派生密钥加盐（salt）的会话，在 TPM 被复位、种子改变后都会失败
显然，在没有任何其他预先共享秘密的情况下使用 null 种子，我们必须创建并读取初始
公钥，而它当然可能被总线中间人拦截和替换。然而，TPM 有一种密钥认证机制（使用 EK
背书证书，创建一个证明身份密钥（AK），并用该密钥认null 种子的主密钥），这过复杂而无法在内核内运行，因此我们sysfs 中导出一null 主密钥名称的副本，以用户空间在启动时运行完整的认证。这里明确的保证是：如果 null 主密钥认证正确，就知道自启动以来你所有的 TPM 事务都是安全的；如果认证不正确，你就知道你的系统存在一个中间人（并且启动期间使用的任何秘密可能都已经泄露）
### 信任的堆

在当前的 null 主密钥场景下，TPM 必须被完全清空后才能交给下一个使用者。然而内会把派生出的 null 种子密钥的名称交给用户空间，随后可以在用户空间通过认证进行校验因此，这种名称交接的链条也可以用于各个启动组件之间（通过某种未指定的机制）。例如，
grub 可以使用 null 种子方案来保证安全，并把名称交给启动区域的內核。内核可以自派生密钥和名称，并且确切地知道：如果它们与交接过来的版本不同，就说明发生了篡改因此，只要每个后续组件都知道如何收集名称并将其与派生的密钥进行校验，就可以通过
名称交棒把任意启动组件串联起来（UEFI grub 到内核）
### 会话属

内核使用的所TPM 命令都允许会话。HMAC 会话可用于校验请求与响应的完整性，解密加密标志可用于保护参数与响应。HMAC 和加密密钥通常由共享的授权秘密派生，但对于许多
内核操作而言，这个秘密是众所周知的（且通常为空）。因此，内核使用的每HMAC 会话
都必须使null 主密钥作为加盐（salt）密钥来创建，从而给会话密钥派生提供一个加输入。因此，内核创建一null 主密钥（作为一个易失的 TPM 句柄），并在 tpm_chip 为每次内核内使用 TPM 而保存的上下文中一直保留它。目前，由于内核内资源管理器缺乏
去间隙（de-gapping）能力，会话必须为每个操作创建和销毁；但在未来，单个会话也可能
被复用于内核内的 HMAC、加密和解密会话
### 保护类型


对于每个内核内操作，我们都使null 主密钥加盐的 HMAC 来保护完整性。此外，我们使用
参数加密来保护密钥密封，使用参数解密来保护密钥解封和随机数生成
## 用户空间中的 Null 主密钥认

每个 TPM 都随附几个用于主背书密钥（EK）的 X.509 证书。本文档假设证书的椭圆曲版本存在01C00002，但它同样适用RSA 证书（位01C00001）
认证的第一步是使用 `TCG EK Credential Profile`_ 中的模板创建主密钥，从而可以将生成主密钥与证书中的那个进行比较（公钥必须匹配）。注意，生成 EK 主密钥需EK 层级
密码，但81010002 处应当已存在一个预生成版本EC 主密钥，并且可以在不需要密授权的情况下对其执行 TPM2_ReadPublic()。接下来，证书本身必须被验证能够回溯到制造商
根证书（应当发布在制造商网站上）。完成这一步后，在 TPM 内生成一个证明密钥（AK），
它的名称EK 公钥可用于通过 TPM2_MakeCredential 加密一个秘密。然TPM 运行
TPM2_ActivateCredential，只有当 TPM、EK AK 之间的绑定为真时，它才会恢复该秘密所生成AK 现在可用于运行对内核已导出的 null 主密钥名称的认证。由TPM2_MakeCredential/ActivateCredential 有些复杂，下面描述了一种涉及外部生成私钥的
更简化流程
此流程是通常基于隐私 CA 的认证流程的简化缩写。这里的假设是，认证TPM 所有者执行，
因此他只能访问所有者层级。所有者创建一个外部的公钥/私钥对（此例中假定为椭圆曲线），
并采用内部包装流程进行包装以便导入，且以 EC 派生的存储主密钥作为父密钥。TPM2_Import()
使用一个以 EK 主密钥加盐的参数解密 HMAC 会话来执行（这同样不需EK 密钥授权），意味着内部包装密钥就是被加密的参数，因此除TPM 拥有经过认证EK，否则它将无法执导入；所以如果命令成功且返回HMAC 校验通过，我们就知道我们拥有了一份仅适用于该认证 TPM 的可加载私钥副本。这个密钥现在被加载TPM，并刷新掉存储主密钥（为生成
null 密钥腾出空间）
现在使用 `TCG TPM v2.0 Provisioning Guidance`_ 中概述的存储（Storage）配置文件生null EC 主密钥；计算该密钥的名称（即公开区域的哈希），并与内核在
/sys/class/tpm/tpm0/null_name 中给出的 null 种子名称进行比较。如果名称不匹配，则
TPM 已被攻陷。如果名称匹配，用户使用 null 主密钥作为对象句柄、加载的私钥作为签名
句柄，并提供随机化的限定数据，执行一TPM2_Certify()。返回的 certifyInfo 的签名会
针对加载私钥的公开部分进行校验，并核对限定数据以防止重放。如果所有这些测试都通过用户现在就可以确信：在整个内核的启动序列中，TPM 的完整性和隐私都得到了保持
