## 内核自防御

内核自防御是在 Linux 内核内部设计和实现系统及结构，以保护内核自身免受安全缺陷的侵害。它涵盖范围广泛的问题，包括消除整类缺陷、阻断安全缺陷的利用方法，以及主动检测攻击企图。本文档并未探讨所有主题，但它应当作为一个合理的起点，并解答一些常见问题。（当然，欢迎提交补丁！）

在最坏的情况下，我们假设一个未授权的本地攻击者拥有对内核内存的任意读写访问能力。在许多情况下，被利用的缺陷并不会提供这种级别的访问能力，但只要部署了能够抵御最坏情况的系统，我们也就能覆盖那些受限的场景。一个更高的、并且仍应牢记的门槛是：保护内核免受_privileged_（特权）本地攻击者的侵害，因为 root 用户能够访问大幅扩张的攻击面。（尤其是当他们有能力加载任意内核模块时。）

成功的自防御系统应当具备以下目标：有效、默认开启、不需要开发者主动选择加入、没有性能影响、不妨碍内核调试，并且拥有测试。同时满足所有这些目标的情况并不常见，但值得明确提及它们，因为这些方面需要被探讨、处理以及/或接受。

## 攻击面缩减

针对安全漏洞最基础的防御，是缩减内核中可用于重定向执行流程的区域。这涵盖了限制暴露给用户空间（userspace）的 API、使内核内 API 难以被误用、最小化可写内核内存的区域，等等。

### 严格的内核内存权限

当所有内核内存都可写时，攻击就很容易重定向执行流程。为了减少这些目标的可利用性，内核需要用一套严格的权限来保护其内存。

#### 可执行代码与只读数据必须不可写

任何包含可执行内存的内核区域都不可写。虽然这显然包括内核代码本身，但我们也必须考虑所有其他位置：内核模块、JIT 内存等。（本规则存在一些临时例外，用以支持指令替身（instruction alternatives）、断点、kprobes 等。如果内核中必须存在这些，它们的实现方式是：在更新期间将内存临时置为可写，然后恢复为原始权限。）

用于支持这一点的是 `CONFIG_STRICT_KERNEL_RWX` 和 `CONFIG_STRICT_MODULE_RWX`，它们力求确保代码不可写、数据不可执行、只读数据既不可写也不可执行。

大多数架构默认开启这些选项且不可由用户选择。对于像 arm 这样希望使其可被选择的架构，架构的 Kconfig 可以选中 ARCH_OPTIONAL_KERNEL_RWX 以启用一个 Kconfig 提示。当 ARCH_OPTIONAL_KERNEL_RWX 被启用时，`CONFIG_ARCH_OPTIONAL_KERNEL_RWX_DEFAULT` 决定了默认设置。

#### 函数指针与敏感变量必须不可写

内核内存中有大量区域包含函数指针，内核会查找这些指针并用于继续执行（例如描述符/向量表、文件/网络等操作的 struct，等等）。这类变量的数量必须削减到绝对最小。

许多这样的变量可以通过设置为 "const" 而变为只读，从而使其位于内核的 .rodata 段而非 .data 段，从而获得上文所述内核严格内存权限的保护。

对于那些在 `__init` 阶段初始化一次的变量，可以用 `__ro_after_init` 属性来标记。

剩下的是那些极少被更新的变量（例如 GDT）。这些将需要另一套基础设施（类似于上文提到的为内核代码所做的临时例外），使其在其余生命周期内保持只读。（例如，在更新时，只有执行更新的那个 CPU 线程才会被授予对内存的不可中断写访问。）

#### 内核内存与用户空间内存的隔离

内核绝不能执行用户空间内存。内核也绝不能在未明确预期的情况下访问用户空间内存。这些规则既可以通过基于硬件的限制（x86 的 SMEP/SMAP、ARM 的 PXN/PAN）来强制实施，也可以通过模拟（ARM 的 Memory Domains）来强制实施。通过以这种方式阻断用户空间内存，执行与数据解析就无法被传递给易于受控的用户空间内存，从而迫使攻击完全在内核内存中进行。

### 减少对系统调用的访问

对于 64 位系统而言，一种消除大量系统调用的简单方法是构建时不包含 `CONFIG_COMPAT`。然而，这很少是一个可行的场景。

"seccomp" 系统向用户空间提供了一个可供选择的功能，它提供了一种方式来减少正在运行的进程所能使用的内核入口点数量。这限制了可触及的内核代码广度，可能降低某个给定缺陷对攻击的可利用性。

一个可改进的方向是：创建可行的方式，使对 compat、用户命名空间（user namespaces）、BPF 创建以及 perf 的访问仅对受信任的进程开放。这将使内核入口点的范围被限制为通常对未授权用户空间可用的那一组常规入口点。

### 限制对内核模块的访问

内核绝不能允许未授权用户加载特定的内核模块，因为那样会提供一种设施来意外地扩展可用的攻击面。（通过预定义子系统按需加载模块，例如 MODULE_ALIAS_*，在此被视为"预期"的，尽管即使是这些也应给予额外的考量。）例如，通过一个未授权的 socket API 加载文件系统模块是荒谬的：只有 root 或物理本地用户才应当触发文件系统模块的加载。（即便如此，在某些情况下这也仍可商榷。）

为了保护免受即使是特权用户的侵害，系统可能需要完全禁用模块加载（例如单体内核构建，或 modules_disabled sysctl），或者提供签名模块（例如 `CONFIG_MODULE_SIG_FORCE`，或配合 LoadPin 的 dm-crypt），以防止 root 通过模块加载器接口加载任意内核代码。

## 内存完整性

内核中有许多内存结构在攻击中被频繁滥用，以获取执行控制权，其中最广为人知的是栈缓冲区溢出——即存储在栈上的返回地址被覆盖。这类攻击还有许多其他例子，并且存在相应的保护措施来防御它们。

### 栈缓冲区溢出

经典的栈缓冲区溢出涉及越过栈上变量的预期末尾进行写入，最终向栈帧所保存的返回地址写入一个受控的值。使用最广泛的防御手段，是在栈变量与返回地址之间放置一个栈金丝雀（stack canary）（`CONFIG_STACKPROTECTOR`），并在函数返回前对它进行校验。其他的防御手段还包括影子栈（shadow stacks）之类。

### 栈深度溢出

一种不太为人所理解的攻击是利用某个缺陷，触发内核通过深层函数调用或大块栈分配来消耗栈内存。借助这种攻击，有可能写到内核预分配栈空间的末尾之外，并进入敏感结构。为了提供更好的保护，需要进行两项重要的改动：将敏感的 thread_info 结构移到别处，以及在栈底添加一个会触发错误的内存空洞（hole）来捕获这些溢出。

### 堆内存完整性

用于跟踪堆空闲链表（free lists）的结构可以在分配与释放时被进行完整性检查，以确保它们没有被用于操纵其他内存区域。

### 计数器完整性

内核中有许多地方使用原子计数器来跟踪对象引用，或执行类似的生存期管理。当这些计数器可以被制造为回绕（上溢或下溢）时，传统上会暴露出一个释放后使用（use-after-free）缺陷。通过捕获原子回绕，这类缺陷便消失了。

### 尺寸计算溢出检测

与计数器溢出类似，整数溢出（通常是尺寸计算）需要在运行时被检测出来，以消灭这类缺陷——它传统上会导致能够写到内核缓冲区的末尾之外。

## 概率性防御

虽然许多保护措施可以被视为确定性的（例如只读内存不可被写入），但有些保护仅提供统计性防御，即攻击必须收集关于一个运行系统的足够信息才能克服该防御。虽然并不完美，但这些措施确实提供了有意义的防御。

### 金丝雀、盲化（blinding）以及其他密钥

应当指出，前面讨论的栈金丝雀之类在技术上是统计性防御，因为它们依赖于一个密钥值，而这种值可能通过信息泄露缺陷而被发现。

对于像 JIT 这类东西的常量值进行盲化（blinding）时，需要类似的密钥值，因为其可执行内容可能部分处于用户空间的控制之下。

关键在于，所使用的密钥值必须是彼此独立的（例如每个栈使用不同的金丝雀）并且具有高熵（例如 RNG 是否真的在工作？），以最大化其成功率。

### 内核地址空间布局随机化（KASLR）

由于内核内存的位置几乎总是成功发起攻击的关键，使位置变得不可预测就提高了漏洞利用的难度。（注意，这反过来也提高了信息泄露的价值，因为它们可能被用于发现所需的内存位置。）

#### 代码与模块基址

通过在启动时重定位内核的物理与虚拟基址（`CONFIG_RANDOMIZE_BASE`），那些需要内核代码的攻击就会受挫。此外，偏移模块加载的基址意味着，即使是那些每次启动都以相同顺序加载相同模块集合的系统，也不会与内核其余代码共享一个共同的基址。

#### 栈基址

如果内核栈的基址在不同进程之间不相同，甚至在不同系统调用之间也不相同，那么位于栈上或栈之外的目标就变得更难定位。

#### 动态内存基址

内核的大量动态内存（例如 kmalloc、vmalloc 等）由于早期启动初始化的顺序，其布局最终相对确定。如果这些区域的基址在不同启动之间不相同，定位它们就会受挫，并且需要针对该区域特定的信息泄露。

#### 结构布局

通过对敏感结构的布局进行每次构建的随机化，攻击要么必须针对已知的内核构建进行调优，要么必须暴露足够的内核内存以确定结构布局，然后才能操纵它们。

## 防止信息泄露

由于敏感结构的位置是攻击的主要目标，防御内核内存地址与内核内存内容（因为它们可能包含内核地址或其他敏感内容，例如金丝雀值）的泄露都很重要。

### 内核地址

向用户空间打印内核地址会泄露关于内核内存布局的敏感信息。在使用任何打印原始地址的 printk 说明符时应当谨慎，目前有 %px、%p[ad]（以及在某些情况下的 %p[sSb] [*]）。使用这些说明符之一写入的任何文件，应当只能由特权进程读取。

4.14 及更老的内核使用 %p 打印原始地址。从 4.15-rc1 起，使用说明符 %p 打印的地址会在打印前被哈希化。

[*] 如果启用了 KALLSYMS 且符号查找失败，则打印原始地址。如果未启用 KALLSYMS，则打印原始地址。

### 唯一标识符

内核内存地址绝不能用作暴露给用户空间的标识符。相反，应使用原子计数器、idr 或类似的唯一标识符。

### 内存初始化

复制到用户空间的内存必须始终被完全初始化。如果没有显式地 memset()，这将需要修改编译器，以确保结构中的空洞（holes）被清零。

### 内存中毒（poisoning）

在释放内存时，最好对其内容进行中毒（poison）处理，以避免依赖内存旧内容的重用攻击。例如，在系统调用返回时清除栈（`CONFIG_KSTACK_ERASE`），在释放时擦除堆内存。这阻碍了许多未初始化变量攻击、栈内容泄露、堆内容泄露以及释放后使用攻击。

### 目标跟踪

为了有助于消灭导致内核地址被写入用户空间的那类缺陷，需要跟踪写入的目标。如果缓冲区是发往用户空间的（例如由 seq_file 支撑的 `/proc` 文件），它应当自动审查（censor）敏感值。
