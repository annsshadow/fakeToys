
## 完整性策略执行（Integrity Policy Enforcement，IPE）— 内核文档



   本文档面向开发者，而非系统管理员。
   如果你在寻找关于 IPE 使用方式的文档，请参阅
   [IPE admin guide </admin-guide/LSM/ipe>](IPE admin guide </admin-guide/LSM/ipe>)。

### 历史动机


IPE 最初实现的起因是要构建一个锁定（locked-down）的系统。该系统应当“天生安全”，并且对系统上可执行代码以及对其功能至关重要的特定**数据文件**都提供强完整性保证。这些特定的数据文件在通过完整性策略校验之前是不可读的。系统中会存在一个强制访问控制（MAC）系统，因此 xattr 也必须得到保护。这就引出了对提供完整性声明的方案的选择。当时考虑了两种能够满足上述要求、可为系统提供完整性保证的主要机制：

  1. IMA + EVM 签名
  2. DM-Verity

两种方案都经过了仔细权衡，但在 IPE 最初的使用场景中，选择 DM-Verity 而非 IMA+EVM 作为**完整性机制**，主要基于三个原因：

  1. 对额外攻击向量的防护：

    - 使用 IMA+EVM 时，若不配合加密方案，系统会面临针对前述特定数据文件的离线攻击风险。

      与可执行文件不同，读操作（例如针对受保护数据文件的读操作）无法被强制进行全局完整性校验。这意味着必须存在某种形式的选择器，来决定某次读操作是否应当强制执行完整性策略。

      当时这是通过强制访问控制标签来实现的。IMA 策略会指明哪些标签需要进行完整性校验，但这带来了一个问题：EVM 会保护该标签，但如果攻击者能够离线修改文件系统，就可以抹掉所有 xattr —— 包括用于判断文件是否应受完整性策略约束的 SELinux 标签。

      而使用 DM-Verity 时，由于 xattr 是作为 Merkle 树的一部分保存的，若对受 dm-verity 保护的文件系统进行离线挂载，校验和将不再匹配，文件也就无法被读取。

    - 由于用户态二进制文件在 Linux 中是按页换入的，dm-verity 还额外提供了针对恶意块设备的防护。在这种攻击中，块设备最初上报与 IMA 哈希相符的内容，从而通过所需的完整性检查；随后在访问真实数据的缺页异常（page fault）中，上报攻击者的载荷。由于 dm-verity 会在缺页异常发生（即磁盘访问）时校验数据，此类攻击得以缓解。

  2. 性能：

    - dm-verity 是在块被读取时按需进行完整性校验，而不需要把整个文件读入内存进行验证。

  3. 签名的简便性：

    - 无需两次签名（先 IMA，再 EVM）：一个签名即可覆盖整个块设备。
    - 签名可以存储在文件系统元数据之外。
    - 该签名支持基于 x.509 的签名基础设施。

下一步是选择用于执行完整性机制的**策略**。该策略的最低要求是：

  1. 策略本身必须经由完整性校验（防止对其发起简单攻击）。
  2. 策略本身必须能抵抗回滚攻击。
  3. 策略执行必须存在一个类似 permissive 的模式。
  4. 策略必须能够整体更新，且无需重启。
  5. 策略更新必须是原子的。
  6. 策略必须支持对先前编写的组件的**撤销（revocation）**。
  7. 策略必须可在任意时间点被审计。

当时作为唯一完整性策略机制的 IMA，被拿来与上述要求逐条比对，但并未满足所有最低要求。也曾考虑扩展 IMA 来覆盖这些要求，但最终出于两个原因被放弃：

  1. 回归风险：这些改动中有许多会对已经存在于内核中的 IMA 造成重大代码变更，从而可能影响用户。

  2. IMA 在该系统中被用于度量和证明（measurement and attestation）；将度量策略与本地完整性策略执行相分离被认为是更优的做法。

基于这些原因，决定创建一个新的 LSM，其职责仅为本地完整性策略执行。

### 角色与范围


顾名思义，IPE 本质上是一个完整性策略执行方案；IPE 并不规定完整性应如何提供，而是把这个决定留给系统管理员，由他们通过选择适合自身需求的机制来设定安全门槛。存在多种不同的完整性方案，提供不同级别的安全保证；IPE 允许系统管理员针对理论上所有这些方案表达策略。

IPE 自身并不具备保证完整性的内在机制。相反，在构建能够保证完整性的系统时，有更有效的层次可供利用。需要重点指出的是，证明完整性的机制与执行该完整性声明的策略是相互独立的。

因此，IPE 围绕以下两点设计：

  1. 与完整性提供者的易集成性。
  2. 平台管理员/系统管理员的易用性。

### 设计理念：


IPE 是在评估了其他操作系统和环境中的现有完整性策略方案之后设计的。在这次对其他实现的调研中，识别出了若干陷阱：

  1. 策略不可被人直接阅读，通常需要一个二进制的间接格式。
  2. 单一、不可定制的动作被隐式作为默认动作。
  3. 调试策略需要手动步骤来确定是哪条规则被违反。
  4. 编写策略需要对更大的系统或操作系统有深入了解。

IPE 试图规避上述所有陷阱。

#### 策略


##### 纯文本


IPE 的策略是纯文本的。这会使策略文件比其它 LSM 略大一些，但解决了其他平台上某些完整性策略方案存在的两大问题。

第一个问题是代码维护与重复。要编写策略，策略必须采用某种形式的字符串表示（无论是结构化的，还是通过 XML、JSON、YAML 等），以便策略编写者理解所写的内容。在假想的二进制策略设计中，需要一个序列化器将策略从人类可读的形式写入二进制形式，还需要一个反序列化器将二进制形式解释为内核中的数据结构。

最终，还需要另一个反序列化器把二进制形式转回人类可读的形式，并尽可能保留信息。这是因为该访问控制系统的使用者必须维护一张“校验和—原始文件”对照表，才能弄清系统上部署了哪些策略、未部署哪些策略。对单个用户而言，这或许没问题，因为旧策略在更新生效后几乎可以立即丢弃。但对于管理成千上万乃至数十万台、运行多种不同操作系统、具有多种不同运维需求的计算机集群的用户来说，这很快就会成为问题：多年前陈旧的策略可能依然存在，迅速导致需要恢复策略或投入大量基础设施来追踪每个策略的内容。

在有了三个相互独立的序列化器/反序列化器之后，维护成本变得高昂。如果策略避免使用二进制格式，就只需要一个序列化器：从人类可读形式到内核中的数据结构，从而节省代码维护成本并保持可操作性。

二进制格式的第二个问题是透明度。由于 IPE 是基于对系统资源的信任来控制访问的，其策略的变更本身也必须被信任。这通过签名来实现，从而需要把签名作为一个流程。签名作为一种流程，通常有着很高的安全门槛，因为凡是被签名的东西都可能被用来攻击完整性执行系统。同样重要的是，签名者在签名时应当清楚自己签的是什么。二进制策略会造成对此事实的混淆；签名者看到的是一个不透明的二进制 blob。而纯文本策略下，签名者看到的是提交签名的实际策略。

#### 启动策略（Boot Policy）


如果配置得当，IPE 能够在内核启动、用户态启动之初就强制执行策略。这意味着需要在用户态启动的那一刻，以某种形式存储待应用的策略。通常，该存储可通过以下三种方式之一实现：

  1. 策略文件存放在磁盘上，内核在会触发执行决策的代码路径之前加载该策略。
  2. 策略文件由引导加载程序传递给内核，由内核解析该策略。
  3. 有一个编译进内核的策略文件，在内核初始化时被解析并执行。

第一种方案存在问题：内核从用户空间读取文件通常是不被鼓励的，在内核中也极为罕见。

第二种方案同样存在问题：Linux 在整个生态系统中支持多种引导加载程序 —— 每个引导加载程序都必须支持这种新方法，否则就必须有一个独立的来源。这很可能导致对内核启动流程做出比必要更剧烈的改动。

第三种方案最佳，但需要注意的是，该策略会占用所编译内核的磁盘空间。重要的是让该策略保持足够通用，以便用户空间能够加载一个更新的、更复杂的策略，同时又足够严格，不至于过度授权而引发安全问题。

initramfs 提供了一种建立该启动路径的方式。内核以一个只信任 initramfs 的最小策略启动。在 initramfs 内部，当真正的 rootfs 被挂载但尚未切换过去时，它会部署并激活一个信任新根文件系统的策略。这防止了任何步骤中的过度授权，并将内核策略保持在最小规模。

##### 启动（Startup）


然而，并非每个系统都从 initramfs 启动，因此编译进内核的启动策略需要一定的灵活性来表达下一阶段启动中信任是如何建立的。为此，如果我们直接让编译进内核的策略成为一份完整的 IPE 策略，就能让系统构建者恰当地表达第一阶段的启动要求。

#### 可更新、免重启策略（Updatable, Rebootless Policy）


随着时间推移，需求会发生变化（在先前受信任的应用中发现漏洞、密钥轮换等），将内核更新以满足这些安全目标并非总是合适的选项，因为更新并非总是零风险，而阻断安全更新又会使系统暴露于风险之中。这意味着 IPE 需要一份能够完全更新（允许撤销既有策略）、且来源处于内核之外的策略（从而允许在不更新内核的情况下更新策略）。

此外，由于内核在多次调用之间是无状态的，而从内核空间读取磁盘上的策略文件是个糟糕的主意(tm)，因此策略更新必须以免重启的方式完成。

为了允许来自外部来源的更新（它可能是恶意的），该策略需要一种被识别为可信的方式。这是通过一条链接到内核中信任源的签名来实现的。具体地，这里使用 `SYSTEM_TRUSTED_KEYRING`，这是一个在内核编译时初始填充的密钥环，因为这符合如下预期：上述编译进内核的策略的作者，与能够部署策略更新的实体是同一方。

#### 防回滚 / 防重放（Anti-Rollback / Anti-Replay）


随着时间的推移，会发现有漏洞，受信任的资源可能不再受信任。IPE 的策略对此也不例外。可能出现这样的情况：某个粗心的策略编写者部署了一份不安全的策略，随后又用一份安全的策略加以纠正。

假设不安全的策略一旦被签名，攻击者便获取了它，IPE 就需要一种方法来阻止从安全策略更新回滚到不安全策略更新。

最初，IPE 的策略可以带有一个 policy_version，声明系统上所有可激活策略所需的最低版本。这能在系统运行期间防止回滚。


  然而，由于内核在多次启动之间是无状态的，该策略版本会在下次启动时重置为 0.0.0。系统构建者需要意识到这一点，并确保在启动后尽快部署新的安全策略，从而使攻击者部署不安全策略的机会窗口最小化。

#### 隐式动作（Implicit Actions）：


隐式动作的问题，只有当你考虑到系统中多个操作具有不同安全门槛的混合级别时才会显现。例如，设想一个对可执行代码以及对其功能至关重要的特定**数据文件**都提供强完整性保证的系统。在该系统中，可能存在三类策略：

  1. 未能匹配策略中任何规则时，动作被拒绝的策略。
  2. 未能匹配策略中任何规则时，动作被允许的策略。
  3. 策略中指定了无规则匹配时所采取动作的策略。

```

  op=EXECUTE integrity_verified=YES action=ALLOW

```
在该示例系统中，这对可执行文件工作良好，因为所有可执行文件都应当毫无例外地具备完整性保证。问题出在关于特定数据文件的第二项要求上。这会生成类似如下的策略（假设每一行都是
```

  op=EXECUTE integrity_verified=YES action=ALLOW

  op=READ integrity_verified=NO label=critical_t action=DENY
  op=READ action=ALLOW

```
如果你阅读文档就会明白，这还算清晰：策略按序执行，且默认是拒绝；然而，最后一行实际上把该默认改成了 ALLOW。这是必需的，因为在真实系统中存在一些未经验证的读操作（想象向日志文件追加内容）。

第二种选项，即不匹配任何规则则允许，更为清晰
```

  op=READ integrity_verified=NO label=critical_t action=DENY

```
并且，与第一种选项一样，在执行场景中有所欠缺，
```

  op=EXECUTE integrity_verified=YES action=ALLOW
  op=EXECUTE action=DENY

  op=READ integrity_verified=NO label=critical_t action=DENY

```
于是剩下第三选项。与其让用户耍小聪明用一条空规则覆盖默认值，不如强制最终用户去思考他们的适当默认动作应当是什么
```

  DEFAULT op=EXECUTE action=DENY
  op=EXECUTE integrity_verified=YES action=ALLOW

  DEFAULT op=READ action=ALLOW
  op=READ integrity_verified=NO label=critical_t action=DENY

```
#### 策略调试（Policy Debugging）：


在开发策略时，知道策略的哪一行被违反是有用的，这能降低调试成本，将排查范围缩小到导致该动作的确切行。某些完整性策略系统不提供此信息，而是提供评估时所使用的信息。这之后还需要与策略相关联，以评估出了什么问题。

相反，IPE 直接输出被匹配到的规则。这将排查范围限定在确切的策略行（针对特定规则时）或节（针对 DEFAULT 时）。这减少了在评估策略时观察到策略失败后的迭代与排查时间。

IPE 的策略引擎在设计上也让人一眼就能看清如何排查策略失败。每一行都按书写的顺序被评估，因此该算法对人类而言非常简单，足以复现那些可能导致失败的步骤。在所调研的其他系统中，加载策略时会发生优化（例如对规则排序）。在那些系统中，调试需要多个步骤，且算法对用户而言未必一目了然，除非先阅读代码。

#### 简化策略（Simplified Policy）：


最后，IPE 的策略是面向系统管理员而非内核开发者设计的。IPE 覆盖的是“操作”而非各个 LSM 钩子（或系统调用）。这意味着系统管理员无需知道 `mmap`、`mprotect`、`execve` 和 `uselib` 这些系统调用必须有规则保护，而只需知道他们想要限制代码执行即可。这减少了因缺乏对底层系统的了解而可能产生的绕过；而作为内核开发者的 IPE 维护者，能够正确判断某事物是否映射到这些操作、以及在何种条件下映射。

### 实现说明


#### 匿名内存（Anonymous Memory）


在 IPE 中，匿名内存的对待方式与任何其它访问并无不同。当匿名内存以 `+X` 映射时，它仍会进入 `file_mmap` 或 `file_mprotect` 钩子，但带有一个 `NULL` 文件对象。它像任何其它文件一样被提交给评估。然而，当前所有的信任属性都会求值为假，因为它们都基于文件，而该操作并不与某个文件相关联。


  在 `kernel_load_data` 钩子处也会发生同样的情况，即当内核从不被文件支撑的用户空间缓冲区加载数据时。在这种场景下，当前所有的信任属性也都会求值为假。

#### Securityfs 接口


每个策略的 securityfs 树有些独特。例如，对于
```

  MyPolicy
    |- active
    |- delete
    |- name
    |- pkcs7
    |- policy
    |- update
    |- version

```
该策略存储在 MyPolicy inode 的 `->i_private` 数据中。
