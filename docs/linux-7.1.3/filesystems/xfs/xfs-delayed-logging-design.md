## 简

XFS 使用预写日志（Write Ahead Logging）来确保对文件系统元数据的修改是
原子且可恢复的。出于空间和时间的效率考虑，日志机制多种多样且复杂，它
结合了意图（intent）、逻辑和物理日志机制，以提供文件系统所需的恢复保证
某些对象，例inode dquot，以逻辑格式记录日志，所记录的内容由内核（in-core）结构的修改构成，而不是磁盘上的结构。其他对象——通常缓冲区——记录的是它们的物理修改。长期运行的原子修改由意图将各个修改
链接在一起，确保日志恢复能够重启并完成在系统停止工作时只做了一半的操作
造成这些差异的原因，是为了使被修改对象进行处理所需的日志空间和 CPU 时间
尽可能小，从而让日志开销尽可能低。某些条目被非常频繁地修改，并且对象某些部分比其他部分更频繁地被修改，因此降低元数据日志的开销至关重要
用于记录某个条目或将修改链接在一起的方法，在本文档范围内并不重要。只需
知道，用于记录特定对象或将修改链接在一起的方法是不同的，并依赖于所执行
的对象和（或）修改。日志子系统只关心是否遵循某些特定规则，以保证向推进并防止死锁

## XFS 中的事务


XFS 有两类高层事务，由它们所取的日志空间预留类型来定义。这些被称为
“一次性（one shot）”和“永久（permanent）”事务。永久事务预留可以取跨越
提交边界的预留，而“一次性”事务用于单次原子修改
预留的类型和大小必须与正在进行的修改相匹配。这意味着永久事务可用于一次修改，但一次性预留不能用于永久事务
```

	tp = xfs_trans_alloc(<reservation>)
	<lock items>
	<join item to transaction>
	<do modification>
	xfs_trans_commit(tp);

```
当条目在事务中被修改时，这些条目中的脏区域通过事务句柄进行跟踪。一旦事被提交，所有加入它的资源连同在事务分配时取走的剩余未用预留空间一起被释放
相比之下，一个永久事务由多个链接的单
```

	tp = xfs_trans_alloc(<reservation>)
	xfs_ilock(ip, XFS_ILOCK_EXCL)

	loop {
		xfs_trans_ijoin(tp, 0);
		<do modification>
		xfs_trans_log_inode(tp, ip);
		xfs_trans_roll(&tp);
	}

	xfs_trans_commit(tp);
	xfs_iunlock(ip, XFS_ILOCK_EXCL);

```
虽然这可能看起来类似于一次性事务，但有一个重要区别：xfs_trans_roll() 执行
一个特定的操作，将两个

```

	ntp = xfs_trans_dup(tp);
	xfs_trans_commit(tp);
	xfs_trans_reserve(ntp);

```
这导致一系列“滚动事务（rolling transactions）”，其中 inode 在整个事务链被锁定。因此，在这一系列滚动事务运行期间，其他任何东西都不能读取或写入该
inode，这为复杂的修改从外部观察者的角度看表现为原子操作提供了一种机制
需要注意的是，永久事务中的一系列滚动事务并不构成日志中的原子修改。虽每个单独的修改是原子的，但该*不是原子**的。如果我们在中途崩溃，那么恢复
将只重放到该循环做出的、已提交到日志的最后一个事务修改
这影响了长期运行的永久事务，因为无法预测长期运行操作实际会有多少被恢复，
因为无法保证该操作有多少已经到达陈旧存储。因此，如果长期运行的操作需多个事务才能完全完成，高层操作必须使用意图和延迟操作，以保证一旦第一事务持久化到磁盘上的日志中，恢复就能完成该操作

## 事务是异步的


XFS 中，默认情况下所有高层事务都是异步的。这意味着 xfs_trans_commit()
并不保证在返回时修改已被提交到稳定存储。因此，当系统崩溃时，并非所有已
完成的事务都会在恢复期间被重放
然而，日志子系统确实提供了全局顺序保证，即如果在恢复后看到某个特定修改那么在该修改之前提交的所有元数据修改也都会被看到
对于需要立即到达稳定存储的单次操作，或确保长期运行的永久事务在完成后被
完全提交，我们可以显式地将一个事务标记为同步。这将触发一次“日志强（log force）”以将已提交的未完成事务刷新到稳定存储中的日志，并等待其完成
同步事务很少使用，因为它们将日志吞吐量限制在了底层存储的 IO 延迟限制上相反，我们倾向于只在用户操作需要同步点发生时（例如 fsync）才使用日志强制
来确保修改位于稳定存储上

## 事务预留


现在已经多次提到，日志子系统需要提供向前推进的保证，以便任何修改都不会
因为日志空间不足而无法写入日志。这是通过在事务首次分配时进行的日志预来实现。对于永久事务，这些预留作为事务滚动机制的一部分被维护
事务预留提供了一个保证，即在开始修改对象和条目之前，日志中有可用的物理
日志空间来写入修改。因此，预留必须足够大，以考虑在最坏情况下修改可能需记录的元数据量。这意味着，如果我们正在事务中修改一btree，我们必须预足够的空间来记录btree 从叶子到根的完整分裂。因此，预留相当复杂，因我们必须考虑所有可能发生的隐藏修改
例如，一个用户数据范围的分配涉及从空闲空间中分配一个范围，这会修改空闲
空间树。那是两btree。将范围插入 inode 的范围映射可能需要分裂范围映btree，这又需要一次可能再次修改空闲空间树的分配。然后我们可能必须更反向映射，这又会修改另一btree，可能需要更多空间。依此类推。因此，一“简单”操作所能修改的元数据量可能相当大
这个“最坏情况”计算为我们提供了在挂载时计算的静态“单元预留（unit
reservation）”。我们必须保证在事务被允许继续之前日志中有这么多可用空间这样当我们开始将脏元数据写入日志时，不会在写入中途耗尽日志空间
对于一次性事务，单个单元空间预留就是事务继续所需的全部。然而，对于永久
事务，我们还有一个“日志计数（log count）”，它影响要进行的预留的大小
虽然永久事务可以通过单个单元空间预留来应付，但这样做有些低效，因为它要求
事务滚动机制在每次事务滚动时重新预留空间。我们从永久事务的实现中知道对于需要进行的常见修改，大概会有多少次事务滚动
例如，inode 分配通常是两次事务——一次用于在磁盘上物理分配一个空inode
块（chunk），另一次用于从一个有空闲 inode inode 块中分配一inode因此，对inode 分配事务，我们可能将预留日志计数设为2，以表明常见/
快速路径事务将在一条链中提交两个链接的事务。每次永久事务滚动时，它消一整个单元预留
因此，当永久事务首次分配时，日志空间预留从单个单元预留增加到多个单元预留该倍数由预留日志计数定义，这意味着我们可以在不得不重新预留日志空间之前
多次滚动事务。这确保我们进行的常见修改只需预留一次日志空间
如果永久事务的日志计数达到零，那么它需要重新预留日志中的物理空间。这有些
复杂，并且需要理解日志是如何对已经预留的空间进行记账的

## 日志空间记账


日志中的位置通常被称为日志序列号（Log Sequence Number，LSN）。日志是环形
的，因此日志中的位置由周期号（日志被覆盖的次数）与日志内偏移量的组合定义。一LSN 在上 32 位携带周期，在下 32 位携带偏移量。偏移量以“基本块
（basic blocks）”（512 字节）为单位。因此我们可以做相对简单的基于 LSN 运算来跟踪日志中的可用空间
日志空间记账是通过一对称为“授权头（grant head）”的结构完成的。授权头的位是一个绝对值，因此日志中的可用空间量由授权头位置与当前日志尾（tail）之的距离来定义。也就是说，在授权头完全环绕日志并超过尾位置之前，可以预
消耗多少空间
第一个授权头是“预留（reserve）”头。它跟踪当前活动事务所持有的预留的字节
计数。它是一种纯内存中的预留记账，因此实际上跟踪的是进入日志的字节偏移量而不是基本块。因此从技术上讲，它并没有使用 LSN 来表示日志位置，但为跟踪预留空间的目的，它仍然被视为一个拆分的 {cycle, offset} 元组
预留授权头用于准确地记账确切的事务预留量，以及修改实际做出并需要写入日的确切字节数。预留头用于防止新的事务在头部到达当前尾部时取用新的预留。它
会在 FIFO 队列中阻塞新的预留，并且随着日志尾向前移动，一旦有足够空间可用就会按顺序唤醒它们。这FIFO 机制确保在发生日志空间短缺时，任何事务都
不会被饿死资源
另一个授权头是“写入（write）”头。与预留头不同，这个授权头包含一LSN，它
跟踪日志中的物理空间使用。虽然这听起来像是在记与预留授权头相同的状态—而且它确实大多跟踪与预留授权头完全相同的位置——但它们之间的行为存在关差异，这些差异提供了滚动永久事务所需的向前推进保证
这些差异出现在永久事务滚动且内部“日志计数”达到零、最初的一组单元预留已
耗尽时。此时，我们仍然需要日志空间预留来继续序列中的下一个事务，但我没有剩余的了。我们不能在事务提交过程中休眠等待新的日志空间变得可用，因为
我们可能会落FIFO 队列的末尾，而我们休眠时锁住的对象最终可能会在日志中
有足够空闲空间来满足所有待处理预留之前就把日志尾锁住，然后才唤醒正在进行的
提交中的事务
要在不休眠的情况下取用新的预留，需要即使当前没有可用的预留空间也能够取预留。也就是说，我们需要能*超额提交（overcommit*日志预留空间。如所述，我们不能超额提交物理日志空间。然而，预留授权头不跟踪物理空间——它对我们当前未完成（outstanding）的预留量进行记账。因此，如果预留头越过了
日志尾，这仅意味着新的预留将立即被节流，并保持节流，直到日志尾向前移动足够远以消除超额提交并开始取用新的预留。换句话说，我们可以超额提交预留而不违反物理日志头和日志尾的规则
因此，永久事务只xfs_trans_commit() 调用期间“重新授权（regrant）”预空间，而由写入头跟踪的物理日志空间预留，则在提交完成后通过调用
xfs_log_reserve() 单独预留。一旦提交完成，我们可以休眠等待从写入授权头
预留物理日志空间，但仅限
```

	Code using permanent reservations must always log the items they hold
	locked across each transaction they roll in the chain.

```
“在每次事务滚动时重新记录（Re-logging）”被锁住的对象，确保附加到正在滚动的
事务链上的对象总是被重定位到日志的物理头部，因此不会锁住日志尾。如果一被锁住的对象在我们休眠等待写入预留时锁住了日志尾，那么我们将使日志死锁，
因为我们无法取用将那个对象写回并向前移动日志尾以释放写入授权空间所需的锁重新记录被锁住的对象避免了这种死锁，并保证我们所做的日志预留不会自死锁
如果所有滚动事务都遵守这条规则，那么它们都可以独立地向前推进，因为没有什会阻塞日志尾向前移动，从而确保写入授权空间总是（最终）提供给永久事务，无论
它们滚动多少次

## 重放日志（Re-logging）详

XFS 允许在任意给定时间，对同一对象的多个独立修改同时存在于日志中。这使得
日志无需在记录对象的新修改之前先将每个修改刷新到磁盘。XFS 通过一种称“重放日志（re-logging）”的方法来实现这一点。从概念上讲，这相当简单——它
只要求对对象的任何新修改，都使用一*新副*记录到写入日志的新事务中该副本包含日志中当前持有的所有已有修改
也就是说，如果我们有一系列A F 的修改，并且对象在修D 之后被写磁盘，我们会在日志中看到以下一系列事务、它们的内容以及它们的日志序列号
（LSN）：

```

	Transaction		Contents	LSN
	   A			   A		   X
	   B			  A+B		  X+n
	   C			 A+B+C		 X+n+m
	   D			A+B+C+D		X+n+m+o
	    <object written to disk>
	   E			   E		   Y (> X+n+m+o)
	   F			  E+F		  Y+p

```
换句话说，每次一个对象被重放日志，新事务都包含当前仅保存在日志中的所先前修改的聚合
这种重放日志技术允许对象在日志中向前移动，使得被重放日志的对象不会阻止
日志尾向前移动。这可以在上面的表中通过每个后续事务变化的（递增的）LSN 看出并且正是这项技术让我们能够实现长期运行的、多次提交的永久事务
滚动事务的一个典型例子是inode 中移除范围（extent），由于预留大小的限制，
每个事务只能以两个范围的速度进行。因此，滚动的范围移除事务在每次移除操作被修改时，不断地重放 inode btree 缓冲区。这随着操作的进行让它们在日志中
向前移动，确保当前操作在日志环绕时永远不会被自己阻塞
因此可以看出，重放日志操作对 XFS 日志子系统的正确运作是基础性的。从上面描述中，大多数人应该能看出为什XFS 元数据操作会向日志写入如此之多—对同一对象的重复操作会一遍又一遍地将相同的修改写入日志。更糟的是，对象重放日志时往往会变得更脏，所以每个后续事务写入日志的元数据都更多
现在也应该清楚重放日志与异步事务是如何相辅相成的。也就是说，事务在以情况之前不会被写入物理日志：要么一个日志缓冲区被填满（一个日志缓冲区可以
容纳多个事务），要么一个同步操作将持有这些事务的日志缓冲区强制刷新到磁盘这意味着 XFS 正在内存中聚合事务——如果你愿意，可以称之为批处理——以最小化
日志 IO 对事务吞吐量的影响
异步事务吞吐量的限制是日志管理器提供的日志缓冲区的数量和大小。默认情况下
8 个日志缓冲区可用，每个大小为 32kB——通过使用挂载选项可以将大小增加到
256kB銆。
实际上，这给了我们任何时候可以对文件系统进行的未完成元数据修改的最大上限—如果所有日志缓冲区都已满且正在进行 IO，那么在当前批次完成之前不能再提更多事务。现在，单个当前 CPU 核心能够发出足够多的事务，使日志缓冲区永保持满且正在进行 IO，这已经很常见。因此，XFS 日志子系统可以被认为IO
限制
## 延迟日志：概

关于 XFS 使用的异步日志与重放日志技术，需要注意的关键是，在被提交到日缓冲区中的磁盘之前，我们可能会多次重放被修改的对象。如果我们回到前面的
重放日志例子，事A D 完全有可能被提交到同一个日志缓冲区中
也就是说，单个日志缓冲区可能包含同一对象的多个副本，但其中只有一份副需要在那里——最后一份“D”，因为它包含了之前所有修改。换句话说，我们在日缓冲区中有一个必要的副本，以及三个只是在浪费空间的陈旧副本。当我们在同一对象上重复操作时，这些“陈旧对象”可能占日志缓冲区所用空间的 90% 以上。显然，
减少写入日志的陈旧对象数量，将大大减少我们写入日志的元数据量，而这正是
延迟日志的根本目标
从概念的角度来看，XFS 已经在内存中做着重放日志（其中内== 日志缓冲区）只是它做得极其低效。它使用逻辑到物理的格式转换来做重放日志，因为没有基础
设施在将修改在事务中物理格式化到日志缓冲区之前，在内存中跟踪逻辑修改。因我们无法避免在日志缓冲区中累积陈旧对象
延迟日志是我们将对象的修改在内存中、在日志缓冲区基础设施之外进行保持跟踪的名称。由于重放日志概念对 XFS 日志子系统是基础性的，这实际上相对容做到——对日志条目的所有修改都已经在当前基础设施中被跟踪。大问题是如累积它们并以一致、可恢复的方式将它们送到日志。描述这些问题以及它们是如何解决的，是本文档的重点
延迟日志对日志子系统运作做出的一个关键改变是，它将未完成元数据修改的数量
与可用的日志缓冲区的大小和数量解耦。换句话说，不再是在任何时候最多只2MB
的事务修改未被写入日志，而是可能在内存中累积大得多的数量。因此，崩溃时元数据
丢失的可能性比现有日志机制要大得多
需要注意的是，这并不改变日志恢复将产生一个一致文件系统的保证。它的真含义是，就恢复后的文件系统而言，可能因为崩溃而根本没有发生的交易可能数以计。这使得关心其数据的应用程序在需要维护应用程序级数据完整性时使用 fsync()
变得更加重要
需要说明的是，延迟日志并不是一个值得严格证明以确定其是否正确的创新新概念在写入日志之前在内存中累积修改一段时间的方法，在许多文件系统中都被有效使用，
包括 ext3 ext4。因此，本文档不花时间试图说服读者这个概念是可靠的。相反，
它只是被视为一个“已解决的问题”，因此XFS 中实现它纯粹是软件工程上的练习
XFS 中延迟日志的基本要求很简单：

 1. 至少将写入日志的元数据量减少一个数量级 2. 提供足够的统计信息以验证要求 #1 3. 提供足够的新的跟踪（tracing）基础设施，以便能够调试新代码的问题 4. 不更改磁盘上的格式（元数据或日志格式） 5. 使用挂载选项启用和禁用 6. 对于同步事务工作负载，不出现性能回退
## 延迟日志：设

### 存储修改


在逻辑层面累积修改（即只使用现有的日志条目脏区域跟踪）的问题在于，当要修改写入日志缓冲区时，我们需要确保正在格式化的对象在这样做时不会被改变这需要锁定对象以防止并发修改。因此，将逻辑修改刷新到日志将要求我们锁定每个
对象、格式化它们，然后再次解锁它们
这引入了与已在运行的事务发生死锁的大量可能。例如，一个事务已经锁定并修改对象 A，但需要在提交事务时获取延迟日志跟踪锁。然而，刷新线程已经持有了延日志跟踪锁，并试图获取对A 上的锁以将其刷新到日志缓冲区。这似乎是一个无解决的死锁条件，而解决这个问题正是如此长时间以来实现延迟日志的障碍
解决方案相对简单——只是花了很长时间才认识到它。简而言之，当前的日志代码将
每个条目的修改格式化到一个指向该条目中被修改区域的向量数组中。日志写入代在事务提交期间、条目在事务中被锁定时，简单地将这些向量所指向的内存复制到日志
缓冲区。我们可以使用一个分配的内存缓冲区（足以容纳格式化后的向量）来替代日缓冲区作为格式化代码的目标
如果我们然后将向量复制到内存缓冲区，并重写向量以指向内存缓冲区而不是对象本身，
我们现在就有了一份修改的副本，其格式与日志缓冲区写入代码兼容，且不需要我锁定条目即可访问。这种格式化和重写都可以在事务提交期间对象被锁定时完成，从产生一个事务上一致的向量，无需锁定所属条目即可访问
因此，我们在需要将未完成的异步事务刷新到日志时，避免了锁定条目的需要。现格式化方法与延迟日志格式化之间的差异可以在下图中看到
```

    Object    +---------------------------------------------+
    Vector 1      +----+
    Vector 2                    +----+
    Vector 3                                   +----------+

```
```

    Log Buffer    +-V1-+-V2-+----V3----+

```
```

    Object    +---------------------------------------------+
    Vector 1      +----+
    Vector 2                    +----+
    Vector 3                                   +----------+

```
```

    Memory Buffer +-V1-+-V2-+----V3----+
    Vector 1      +----+
    Vector 2           +----+
    Vector 3                +----------+

```
内存缓冲区和关联的向量需要作为单个对象传递，但仍需要与父对象关联，以便如果
对象被重放日志，我们可以用包含最新修改的新内存缓冲区替换当前内存缓冲区
在格式化内存缓冲区之后保留向量的原因，是为了支持跨日志缓冲区边界正确拆分
向量。如果我们不保留向量，我们就不知道条目中区域边界在哪里，因此我们需日志缓冲区写入中的一种新封装方法（即双重封装）。这将是一个磁盘上的格式更改，
因此不可取。这也意味着我们必须在格式化阶段写入日志区域头，这有问题，因为在
日志写入期间有每区域状态需要放入头中
因此我们需要保留向量，但通过将内存缓冲区附加到它并重写向量地址以指向内缓冲区，我们得到了一个自描述的对象，可以传递给日志缓冲区写入代码，并以与现日志向量完全相同的方式处理。因此，我们避免了需要新的磁盘上格式来处理已在内存中
被重放日志的条目

### 跟踪修改


既然我们可以在一种允许无限制使用的格式中将事务修改记录到内存中，我们就需能够跟踪并累积它们，以便它们可以在稍后的某个时间点写入日志。日志条目是存储
这个向量和缓冲区的自然位置，并且作为用于跟踪已提交对象的对象也很有意义，因为
一旦对象被包含在一个事务中，它将始终存在
日志条目已经被用于跟踪已写入日志但尚未写入磁盘的日志条目。这样的日志条目
被视为“活动（active）”的，因此被存储在活动条目列表（Active Item List，AIL中，这是一个按 LSN 排序的双链表。条目在日志缓冲IO 完成期间被插入此列表之后它们被解除固定（unpinned）并可以写入磁盘。一个处AIL 中的对象可以重放日志，这会导致该对象再次被固定（pinned），然后在该事务的日志缓冲区 IO
完成时在 AIL 中向前移动
本质上，这表明处AIL 中的条目仍然可以被修改和重放日志，因此任何跟踪都必须
AIL 基础设施分离。因此，我们不能重用 AIL 列表指针来跟踪已提交的条目，不能存储在受 AIL 锁保护的任何字段中。因此，已提交条目跟踪需要在日志条目中有
自己的锁、列表和状态字段
AIL 类似，已提交条目的跟踪是通过一个名为已提交条目列表（Committed Item
List，CIL）的新列表完成的。该列表跟踪已经提交并附加了格式化内存缓冲区的日条目。它按事务提交顺序跟踪对象，因此当一个对象被重放日志时，它会从列表中当前位置移除，并重新插入到尾部。这完全是任意的，是为了方便调试——列表中的最条目是最近被修改的。CIL 的顺序对于事务完整性（如下一节所讨论）不是必需的，
因此排序是为了开发者的方便/理智而做的

### 延迟日志：检查点（Checkpoint

当我们有一次日志同步事件，通常称为“日志强制（log force）”时，CIL 中的所条目都必须通过日志缓冲区写入日志。我们需要按它们CIL 中存在的顺序写入这些
条目，并且它们需要作为一个原子事务写入。要求所有对象作为一个原子事务写入，来自
重放日志和日志重放的需求——给定事务中所有对象的所有修改必须要么在日志恢复期间
被完全重放，要么完全不被重放。如果一个事务因为不完整而未被重放，那么也没有更的事务应该被重放
为了满足这一要求，我们需要将整个 CIL 写入单个日志事务中。幸运的是，XFS 日志
代码对事务的大小没有固定限制，日志重放代码也没有。唯一根本的限制是事务不能
大于略小于日志大小的一半。这个限制的原因是，为了找到日志的头和尾，日志中必须
随时至少有一个完整的事务。如果一个事务大于日志的一半，那么在写入这样一个事期间发生崩溃，就有可能部分覆盖日志中唯一完整的先前事务。这将导致恢复失败和文件
系统不一致，因此我们必须强制执行检查点的最大大小为略小于日志的一半
除了这个大小要求之外，检查点事务看起来与任何其他事务没有区别——它包含一事务头、一系列格式化的日志条目和一个在尾部的提交记录。从恢复的角度来看，检查点
事务也没有区别——只是更大，里面有更多的条目。最坏情况的影响是，我们可能需调整恢复事务对象哈希的大小
因为检查点只是另一个事务，并且对日志条目的所有修改都存储为日志向量，我们可以
使用现有的日志缓冲区写入代码将修改写入日志。为了高效地做到这一点，我们需最小化在写入检查点事务时持CIL 锁的时间。当前的日志写入代码通过它将事务内容
（日志向量）的写入与事务提交记录的写入分离的方式，使我们能够轻松做到这一点，跟踪这需要我们有一个贯穿日志写入过程直到检查点完成的每检查点上下文
因此，一个检查点有一个上下文，它跟踪从启动到检查点完成的当前检查点状态。一个新上下文在检查点事务开始的同时被启动。也就是说，当我们在检查点操作期间CIL 移除所有当前条目时，我们将所有这些修改移入当前检查点上下文。然后我们初始化一新上下文并将其附加到 CIL 以聚合新的事务
这允许我们在转移所有已提交条目后立即解CIL，并有效地允许在我们将检查点格式到日志中时发出新事务。它也允许在日志强制繁重的工作负载情况下，将并发检查点写入
日志缓冲区，就像现有的事务提交代码所做的那样。然而，这需要我们在日志中严格排提交记录，以便在日志重放期间保持检查点序列顺序
为了确保我们可以在将一个条目写入检查点事务的同时，另一个事务修改该条目并将其日条目插入新的 CIL，检查点事务提交代码不能使用日志条目来存储需要写入事务的日志
向量列表。因此，日志向量需要能够被链接在一起，以允许它们从日志条目上分离。也就是
说，CIL 被刷新时，附加到每个日志条目上的内存缓冲区和日志向量需要附加到检查点
上下文，以便日志条目可以被释放。以图示形式
```

	CIL Head
	   |
	   V
	Log Item <-> log vector 1	-> memory buffer
	   |				-> vector array
	   V
	Log Item <-> log vector 2	-> memory buffer
	   |				-> vector array
	   V
	......
	   |
	   V
	Log Item <-> log vector N-1	-> memory buffer
	   |				-> vector array
	   V
	Log Item <-> log vector N	-> memory buffer
					-> vector array

```
刷新之后，CIL 头为空，检查点上下文日
```

	Checkpoint Context
	   |
	   V
	log vector 1	-> memory buffer
	   |		-> vector array
	   |		-> Log Item
	   V
	log vector 2	-> memory buffer
	   |		-> vector array
	   |		-> Log Item
	   V
	......
	   |
	   V
	log vector N-1	-> memory buffer
	   |		-> vector array
	   |		-> Log Item
	   V
	log vector N	-> memory buffer
			-> vector array
			-> Log Item

```
一旦这个转移完成，CIL 就可以被解锁，新事务可以开始，而检查点刷新代码则在日志
向量链上工作以提交检查点
一旦检查点被写入日志缓冲区，检查点上下文就与写入提交记录的日志缓冲区一起附加，
并带有一个完成回调。日IO 完成将调用该回调，然后它可以对日志向量链中的日志
条目运行事务提交处理（即插入 AIL 并解除固定），然后释放日志向量链和检查点上下文
讨论点：我不确定日志条目是否是跟踪向量最有效的方式，尽管它似乎是自然而然的做法事实上，我们遍历日志条目（在 CIL 中）只是为了链接日志向量并断开日志条目与日向量之间的链接，这意味着我们对日志条目列表修改产生一次缓存行命中，然后对日志
向量链接产生另一次。如果我们通过日志向量来跟踪，那么我们只需要断开日志条目与日向量之间的链接，这意味着我们应该只弄脏日志条目的缓存行。通常我不会关心一vs
两次弄脏的缓存行，除了我已经在一个检查点事务中看到超80,000 个日志向量。我这是一个“测量并比较”的情况，可以在开发和审阅的实现进入开发树之后再做…
### 延迟日志：检查点排序


XFS 事务子系统的关键方面之一是，它用事务提交的日志序列号为已提交事务打标签这允许即使在可能有未来的操作在该事务完全提交到日志之前无法完成时，事务也能被
异步发出。在罕见的情况下发生依赖操作时（例如，为一个数据范围重用已释放的元数据
范围），可以发出一个特殊的、优化的日志强制，以立即将该依赖事务强制到磁盘
要做到这一点，事务需要记录该事务提交记录LSN。这LSN 直接来自写入该事务的
日志缓冲区。虽然这对现有事务机制工作得很好，但它对延迟日志不起作用，因为事务不直接写入日志缓冲区的。因此，需要某种其他的事务排序方法
如检查点一节所讨论的，延迟日志使用每检查点上下文，因此为给每个检查点分配一序列号很简单。由于检查点上下文的切换必须是原子地进行的，很容易确保每个新上下被赋予一个单调递增的序列号，而无需外部原子计数器——我们可以只取当前上下文序列并为其加一来作为新上下文
然后，与其在提交期间给事务提LSN 分配一个日志缓冲区 LSN，我们可以分配当前检查点
序列。这允许跟踪尚未完成的事务的操作知道在它们可以继续之前需要提交哪个检查点
序列。因此，现在将日志强制到特定 LSN 的代码需要确保日志强制到特定的检查点
为了确保我们能做到这一点，我们需要跟踪当前正在提交到日志的所有检查点上下文。当
我们刷新一个检查点时，该上下文被添加到一个可以搜索的“正在提交（committing）”列表当一个检查点提交完成时，它会从正在提交列表中移除。因为检查点上下文记录了该检查点
提交记录LSN，我们也可以等待包含提交记录的日志缓冲区，从而使用现有的日志强制
机制来执行同步强制
需要注意的是，同步强制可能需要用类似于当前日志缓冲区代码的缓解算法进行扩展，允许在已经有同步事务正在被刷新时聚合多个同步事务。在做出任何决定之前，需要对当前
设计的性能进行调查
关于日志强制的主要关注点是，确保我们要等待的那个检查点之前的所有先前检查点也被
提交到磁盘。因此，我们需要在我们等待需要完成的那个之前，检查正在提交列表中的所先前上下文也都已完成。我们在日志强制代码中做这个同步，这样我们就不需要在其他任何
地方等待这种序列化——这只在做日志强制时才重要
唯一剩下的复杂性是，日志强制现在还必须处理强制序列号与当前上下文相同的情况。也就是
说，我们需要刷CIL 并可能等待它完成。这是对现有日志强制代码的一个简单补充，用于
检查序列号并在需要时推动。事实上，将当前序列检查点刷新放在日志强制代码中，使得发出
同步事务的当前机制保持不变（即提交一个异步事务，然后在该事务LSN 处强制日志）因此无论是否使用延迟日志，高层代码的行为都相同
### 延迟日志：检查点日志空间记账


检查点事务的大问题是该事务的日志空间预留。我们事先不知道检查点事务会有多大，也
不知道写出它需要占用多少日志缓冲区，也不知道将使用多少个拆分的日志向量区域。我可以在将条目添加到已提交条目列表时跟踪所需的日志空间量，但我们仍然需要在日志中为
该检查点预留空间
一个典型的事务为事务的最坏情况空间使用预留足够的日志空间。该预留考虑了日志记录头事务和区域头、拆分区域的头、缓冲区尾部填充等，以及事务中所有被修改元数据的实际
空间。虽然其中一些是固定开销，但大部分取决于事务的大小以及正在被记录的区域数（事务中的日志向量数量）
差异的一个例子是记录目录修改与记inode 修改。如果你修改了大量的 inode 核心
（例`chmod -R g+w *`），那么就有大量事务只包inode 核心inode 日志格式
结构。也就是说，总共两个向量，约 150 字节。如果我们修10,000 inode，我大约1.5MB 的元数据要写20,000 个向量中。每个向12 字节，因此要记录的总量
约为 1.75MB。相比之下，如果我们记录完整的目录缓冲区，它们通常每个 4KB，因此在
1.5MB 的目录缓冲区中，我们大约400 个缓冲区以及每个缓冲区的缓冲区格式结构—大约 800 个向量或 1.51MB 的总空间。由此可以明显看出，静态日志空间预留不是特灵活，很难为所有工作负载选择“最优值”
此外，如果我们要使用静态预留，它覆盖整个预留的哪一部分？我们通过跟踪对象CIL 当前使用的空间，然后在对象被重放日志时计算使用空间的增加或减少，来计入事务预留所
使用的空间。这使得检查点预留只需要计入日志缓冲区元数据（例如日志头记录）所使用空间
然而，即使只使用静态预留来应对日志元数据也是有问题的。通常日志记录头每消1MB
日志空间至少使用 16KB 的日志空间（32k 512 字节），并且预留需要足够大以处任意大小的检查点事务。这个预留需要在检查点启动之前做出，并且我们需要能够在不休眠的
情况下预留空间。对于一8MB 的检查点，我们需要大150KB 的预留，这是一个不小的
空间量
静态预留需要操纵日志授权计数器——我们可以在该空间上取一个永久预留，但我们仍然需在每次检查点事务完成后刷新写入预留（事务实际可用的空间）。不幸的是，如果所需空间需要时不可用，那么重新授权代码将休眠等待它
这里的问题在于，这可能导致死锁，因为我们可能需要提交检查点才能释放日志空间（回滚动事务的描述以了解此例）。因此，如果我们要使用静态预留，我们**必须**始终在日志中
有可用空间，而这是非常困难且复杂的安排。这是可以做到的，但有更简单的方法
更简单的做法是跟CIL 中条目使用的整个日志空间，并用它来动态计算日志元数据所需日志空间量。如果由于事务提交将新的内存缓冲区插CIL 导致此日志元数据空间发生变化那么所需空间的差值会从导致该变化的事务中扣除。这个级别的事务*始终**在其预留中有
足够的可用空间，因为它们已经预留了所需的最大日志元数据空间，并且这样的增量预留始终小于或等于预留中的最大量
因此，我们可以随着条目被添加到 CIL 而动态增长检查点事务预留，而无需预先预留和重授权日志空间。这避免了死锁，并从检查点刷新代码中移除了一个阻塞点
如前所述，事务不能增长到超过日志大小的一半。因此，作为预留增长的一部分，我们还需将预留的大小与允许的最大事务大小进行检查。如果我们达到最大阈值，就需要将 CIL 推到日志。这实际上是一个“后台刷新”，并且是按需完成的。这与由日志强制触发CIL 推相同，只是不等待检查点提交完成。这个后台推送由事务提交代码检查和执行
如果事务子系统在 CIL 中仍有条目时变为空闲，它们将xfssyncd 发出的周期性日志强刷新。这个日志强制会CIL 推送到磁盘，并且如果事务子系统保持空闲，则允许空闲日志
被覆盖（有效地标记为干净），方式与现有日志方法完全相同。一个讨论点是，这个日志强制
是否需要比当前30 秒一次的频率更频繁地进行

### 延迟日志：日志条目固定（Pinning

当前，日志条目在事务提交期间、条目仍被锁定时被固定。这发生在条目被格式化之后，尽管
它可以在条目解锁之前的任何时间完成。这种机制的结果是，条目每次被提交到日志缓冲区时
就被固定一次。因此，在日志缓冲区中被重放日志的条目，对它们被弄脏的每个未完成事务都会
有一个固定计数。当这些事务中的每一个完成时，它们会将该条目解除固定一次。结果，条目只有在所有事务完成且没有待处理事务时才变为未固定。因此，日志条目的固定和解除
固定是对称的，因为事务提交与日志条目完成之间存在 1:1 的关系
然而，对于延迟日志，我们具有非对称的事务提交到完成关系。每次一个对象在 CIL 中被
重放日志时，它都会经过提交过程，而没有注册相应的完成。也就是说，我们现在有事务提与日志条目完成之间的多对一关系。结果是，如果我们保留“在事务提交时固定，在事务完成时
解除固定”模型，日志条目的固定和解除固定就会变得不平衡
为了保持固定/解除固定对称，算法需要改为“在插入 CIL 时固定，在检查点完成时解除固定”换句话说，固定和解除固定围绕一个检查点上下文变得对称。我们必须在对象第一次被插入 CIL
时固定它——如果它在事务提交期间已经在 CIL 中，那么我们不再固定它。因为可能有多个完成的检查点上下文，我们仍然可能看到升高的固定计数，但随着每个检查点完成，固定计将保留根据其上下文的正确值
只是为了让事情稍微复杂一点，固定计数的这个检查点级上下文意味着条目的固定必须在 CIL
提交/刷新锁下进行。如果我们在该锁之外固定对象，我们就无法保证固定计数与哪个上下文
相关联。这是因为固定条目依赖于条目是否存在于当CIL 中。如果我们在检查和固定对象
之前不先固定 CIL，我们就会与在检查和固定（或不固定，视情况而定）之间刷CIL 存在
竞争。因此，我们必须持有 CIL 刷新/提交锁，以保证我们正确地固定条目

### 延迟日志：并发可扩展

CIL 的一个基本要求是，通过事务提交的访问必须扩展到许多并发提交。当前的事务提交代码
即使在来2048 个处理器的同时事务时也不会崩溃。当前的事务代码不会比只有一CPU
使用它时更快，但它也不会变慢
因此，延迟日志事务提交代码需要从底层设计为并发的。很明显，设计中有些序列化点——三重要的点是：

 1. 在刷CIL 时锁定新的事务提 2. 将条目添加到 CIL 并更新条目空间记 3. 检查点提交排序

观察事务提交CIL 刷新交互，很明显我们这里有一个多对一的交互。也就是说，可以尝试同时
提交的并发事务数量的唯一限制，是它们的预留可用的日志空间量。这里的实际限制对于一128MB 的日志来说大约为数百个并发事务，这意味着通常每台机器每个 CPU 一个
事务提交需要阻止刷新的时间相对较长——日志条目的固定需要在我们阻止 CIL 刷新时进行，所目前这意味着它在将对象格式化为内存缓冲区（即 memcpy() 正在进行时）期间被持有。最终，
可以采用两遍算法，将格式化与对象固定分开进行，以减少事务提交侧的持有时间
由于潜在的事务提交侧持有者的数量，锁确实需要是一个可休眠的锁——如CIL 刷新取了锁，我们
不希望机器中的每个其CPU 都在 CIL 锁上自旋。鉴于刷CIL 可能涉及遍历数以万计的日条目列表，它将被持有相当长的时间，因此自旋争用是一个重大关切。防止大CPU 空转什么都
不做，是选择可休眠锁的主要原因，即使在事务提交侧CIL 刷新侧都没有任何东西持有锁休眠
还应该注意到，对于异步事务工作负载，CIL 刷新与事务提交相比也是一个相对罕见的操作——只时间能告诉我们，使用读写信号量（read-write semaphore）进行互斥是否会由于读取侧锁的缓行跳动而限制事务提交并发
第二个序列化点在事务提交侧，条目被插CIL 的位置。因为事务可以并发进入这段代码，CIL 需被单独保护与上述提交/刷新互斥之外。它也需要是一个独占锁，但它只被持有非常短的时间，因此
这里适合用自旋锁。这个锁有可能成为争用点，但考虑到每个事务只有一次短暂的持有时间，我认为
争用不太可能
最后的序列化点是作为检查点提交和日志强制排序一部分运行的检查点提交记录排序代码。触CIL
刷新的代码路径（即任何触发日志强制的）将在将所有日志向量写入日志缓冲区之后、但在写入提记录之前进入一个排序循环。这个循环遍历正在提交的检查点列表，并需要阻塞等待检查点完成它们提交记录写入。因此，它需要一个锁和一个等待变量。日志强制排序也需要相同的锁、列表遍历和阻塞
机制，以确保检查点的完成
这两个排序操作可以使用该机制，即使它们等待的事件不同。检查点提交记录排序需要等待，直到
检查点上下文包含提LSN（通过提交记录写入完成获得），而日志强制排序需要等待，直到先前检查点上下文从正在提交列表中移除（即它们已完成）。一个简单的等待变量和广播唤醒（惊群thundering herds）已被用于实现这两个序列化队列。它们也使用CIL 相同的锁。如果我们看CIL 锁上争用过多，或者由于这些操作的广播唤醒导致过多的上下文切换，可以将它们放在一个新自旋锁下，并赋予单独的等待列表，以减少锁争用以及被错误事件唤醒的进程数量

### 生命周期变化


```

	1. Transaction allocate
	2. Transaction reserve
	3. Lock item
	4. Join item to transaction
		If not already attached,
			Allocate log item
			Attach log item to owner item
		Attach log item to transaction
	5. Modify item
		Record modifications in log item
	6. Transaction commit
		Pin item in memory
		Format item into log buffer
		Write commit LSN into transaction
		Unlock item
		Attach transaction to log buffer

	<log buffer IO dispatched>
	<log buffer IO completes>

	7. Transaction completion
		Mark log item committed
		Insert log item into AIL
			Write commit LSN into log item
		Unpin log item
	8. AIL traversal
		Lock item
		Mark log item clean
		Flush item to disk

	<item IO completion>

	9. Log item removed from AIL
		Moves log tail
		Item unlocked

```
本质上，步骤 1-6 独立于步7 运行，步7 也独立于步骤 8-9。一个条目可以在步骤 1-6 步骤 8-9 被锁定的同时，步7 正在发生，但只有步骤 1-6 8-9 可以同时进行。如果日志条AIL 中，或在步骤 6 7 之间，并且重新进入步1-6，那么该条目就被重放日志。只有当
步骤 8-9 被进入并完成时，该对象才被视为干净

	2. Transaction reserve

		Record modifications in log item

		Insert log item into CIL

由此可以看出，两种日志方法之间唯一的生命周期差异在生命周期的中间——它们仍然有相同的开和结尾以及执行约束。唯一的差异在于将日志条目提交到日志本身以及完成处理。因此，延迟日志
不应引入任何对日志条目行为、分配或释放的、尚不存在的约束
由于延迟日志基础设施这种零影响的“插入”以及内部结构的设计避免了磁盘上格式的更改，我们
基本上可以通过挂载选项在延迟日志和现有机制之间切换。从根本上说，没有理由表明日志管理器
不能根据负载特性自动且透明地交换方法，但如果延迟日志按设计工作，这就没有必要了
