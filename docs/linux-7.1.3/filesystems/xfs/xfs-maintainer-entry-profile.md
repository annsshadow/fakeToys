## XFS 维护者条目档案


### 概述


XFS 是 Linux 内核中著名的高性能文件系统。本项目的目标是提供并维护一个稳健且
高性能的文件系统。

补丁通常被合并到相应 git 仓库的 for-next 分支。经过一段测试期后，for-next 分支
被合并到 master 分支。

内核代码合并到 xfs-linux 树[^0^]。
用户空间代码合并到 xfsprogs 树[^1^]。
测试用例合并到 xfstests 树[^2^]。
磁盘格式文档合并到 xfs-documentation 树[^3^]。

所有涉及 XFS 的补丁集**必须**完整地抄送（cc）到邮件列表
linux-xfs@vger.kernel.org。

### 角色


XFS 项目中有八个关键角色。一个人可以承担多个角色，一个角色也可以由多人担任。
任何承担角色的人都被建议定期与自己和他人沟通，关注是否出现倦怠。

- **外部贡献者**：任何发送补丁、但不定期参与 XFS 项目的人。这些人通常是在
  其它文件系统或内核社区其它地方工作的人。

- **开发者**：熟悉 XFS 代码库到足以编写新代码、文档和测试的人。

  开发者通常可以在内核 MAINTAINERS 文件中 `C:` 条目提到的 IRC 频道中找到。

- **高级开发者**：非常熟悉 XFS 代码库至少某一部分和/或内核中其它子系统的一位
  开发者。这些人共同决定项目的长期目标，并将社区朝该方向推进。他们应帮助为每个
  发布周期确定开发和审查工作的优先级。

  高级开发者往往是 IRC 频道中更活跃的参与者。

- **审查者**：阅读代码提交以做出判断的人（很可能同时也是开发者）：

  0. 贡献背后的想法是否成立？
  1. 该想法是否符合项目的目标？
  2. 该贡献的设计是否正确？
  3. 该贡献是否完善？
  4. 该贡献能否被有效测试？

  审查者应在内核以及 fstests 的 MAINTAINERS 文件中用 `R:` 条目标识自己。

- **测试负责人**：负责设定项目的测试覆盖目标，与开发者协商为新增特性决定新测试，
  并确保开发者和发布经理执行测试的人。

  测试负责人应在 fstests MAINTAINERS 文件的 XFS 小节中用 `M:` 条目标识自己。

- **缺陷分诊员**：以刚好足够的细节检查 incoming 缺陷报告，以确定应将报告转发给
  谁的人。

  缺陷分诊员应在内核 MAINTAINERS 文件中用 `B:` 条目标识自己。

- **发布经理**：将已审查的补丁集合并到集成分支，在本地测试结果，将分支推送到公开
  的 git 仓库，并向上游发送拉取请求的人。发布经理不被期望从事新特性补丁集的工作。
  如果开发者和审查者未能就某一点达成解决方案，发布经理必须能够介入，试图推动达成
  解决方案。

  发布经理应在内核 MAINTAINERS 文件中用 `M:` 条目标识自己。

- **社区经理**：当邮件列表讨论不足以进行集体决策时，召集并主持尽可能多的 XFS
  参与者会议的人。他们也可以作为赞助 XFS 任何部分工作的各组织管理者之间的联络人。

- **LTS 维护者**：将缺陷修复从上游向后移植并测试到 LTS 内核的人。在任何给定时间，
  通常存在六个独立的 LTS 树。

  某个 LTS 版本的维护者应在该 LTS 树的 MAINTAINERS 文件中用 `M:` 条目标识自己。
  无人维护的 LTS 内核应在同一文件中标记为状态 `S: Orphan`。

### 提交清单补充


向 XFS 提交时请遵循以下附加规则：

- 仅影响文件系统本身的补丁应以最新的 -rc 或 for-next 分支为基础。这些补丁将被
  合并回 for-next 分支。

- 触及其它子系统的补丁作者需要与 XFS 以及相关子系统的维护者协调，以决定如何进行
  合并。

- 任何改动 XFS 的补丁集都应完整地抄送到 linux-xfs。不要发送部分补丁集；那会使对
  更改更宽泛上下文的分析变得不必要的困难。

- 任何做出在内核之外、在用户空间工具中也有对应改动的内核改动的人，应在内核补丁集
  之后立即将用户空间改动作为单独的补丁集发送。

- 缺陷修复补丁的作者应当使用 fstests[^2^] 对该补丁执行 A/B 测试，以确定没有回归。
  在可能的情况下，应为 fstests 编写一个新的回归测试用例。

- 新特性补丁集的作者必须确保 fstests 拥有针对该新特性适当的、功能性以及输入边界
  情况的测试用例。

- 在实现新特性时，强烈建议开发者编写一份设计文档，回答以下问题：

  - 这试图解决**什么**问题？

  - **谁**将从该解决方案中受益，他们将在**哪里**访问它？

  - 这个新特性**如何**工作？这应涉及比代码注释更高层面、支撑该解决方案的主要数据
    结构和算法。

  - 构建于新特性之上需要**哪些**用户空间接口？

  - 这项工作的**测试方式**如何，以确保它解决了设计文档中列出的问题，而不会引起新
    的问题？

  设计文档应提交到内核文档目录中。如果该特性社区已经很熟悉，则可以省略。

- 新测试的補丁集应在内核和用户空间代码补丁集之后立即作为单独的补丁集提交。

- 对 XFS 磁盘格式的更改必须在磁盘格式文档[^3^]中描述，并作为补丁集在 fstests
  补丁集之后提交。

- 实现缺陷修复以及进一步代码清理的补丁集应将缺陷修复放在系列的开头，以便于向后
  移植。

### 关键发布周期日期


缺陷修复可以在任何时间发送，不过当下一个合并窗口临近时，发布经理可能决定推迟某个
补丁。

面向下一个合并窗口的代码提交应在 -rc1 到 -rc6 之间发送。这给社区留出时间审查
更改、建议其它更改，并让作者重新测试这些更改。

还需要更改 fs/iomap 并面向下一个合并窗口的代码提交，应在 -rc1 到 -rc4 之间发送。
这给更广泛的内核社区留出充足的时间测试这些基础设施更改。

### 审查节奏


一般来说，在催促进展反馈前请至少等待一周。要寻找审查者，可以查阅 MAINTAINERS
文件，或请拥有 XFS 更改 Reviewed-by 标签的开发者来看一看并提供意见。
