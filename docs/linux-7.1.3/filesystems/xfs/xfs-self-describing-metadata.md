
## XFS 自描述元数据


## 简介


XFS 面临的最大可扩展性问题并非算法层面的可扩展性，而是文件系统结构的
验证问题。磁盘上结构与索引的可扩展性，以及遍历它们的算法，足以支持 PB 级、
拥有数十亿 inode 的文件系统，然而恰恰是这种可扩展性引发了验证问题。

XFS 上几乎所有这些元数据都是动态分配的。唯一位置固定的元数据是分配组头部
（SB、AGF、AGFL 和 AGI），而所有其他元数据结构都需要通过以不同方式遍历
文件系统结构来发现。虽然用户空间工具已经做了这类事情以验证和修复结构，但
它们能验证的范围是有限的，而这反过来限制了 XFS 文件系统可支持的规模。

例如，在试图确定某个损坏问题的根因时，完全有可能手动使用 xfs_db 加一点脚本
来分析一个 100TB 文件系统的结构，但这在很大程度上仍然是一项手工验证工作，
需要确认单比特错误或被错位写入之类的情况不是损坏事件的最终原因。此类取证
分析可能需要花费几小时到几天，因此在这样的规模下根因分析完全可行。

然而，如果我们将文件系统扩展到 1PB，现在就需要分析 10 倍数量的元数据，于是
分析工作量就会膨胀到数周乃至数月的取证工作。大部分分析工作缓慢而乏味，因此
随着分析量的增加，原因更可能在噪声中丢失。因此，支持 PB 级文件系统的首要
关注点在于最小化对文件系统结构进行基本取证分析所需的时间和精力。


## 自描述元数据


当前元数据格式的问题之一是，除了元数据块中的魔数之外，我们没有任何其他方式来
识别它应当是什么。我们甚至无法判断它是否位于正确的位置。简而言之，你不能
孤立地审视单个元数据块并断定“是的，它本应在此，并且内容是有效的”。

因此，取证分析所花的大部分时间都用于元数据值的基本验证，寻找那些处于合法
范围（因而未被自动化验证检查检出）但并不正确的取值。发现并理解诸如交叉链接
的块列表（例如 btree 中的兄弟指针最终形成环）这类问题，是理解出错原因的关键，
但在事后不可能判断这些块是以何种顺序相互链接或写入磁盘的。

因此，我们需要将更多信息记录到元数据中，以便快速判断元数据是否完好、在分析
时是否可以忽略。我们无法防范每一种可能的错误类型，但可以确保常见类型的错误
易于检测。于是便有了自描述元数据的概念。

自描述元数据首要的基本要求是，元数据对象在其已知位置包含某种形式的唯一
标识符。这使我们能够识别该块的预期内容，进而解析并验证元数据对象。如果我们
不能独立识别对象中的元数据类型，那么该元数据根本就描述得不够好！

幸运的是，几乎所有这些 XFS 元数据都已经内嵌了魔数——只有 AGFL、远程符号链接
和远程属性块不包含标识性魔数。因此，我们可以改变所有这些对象的磁盘格式，
添加更多标识信息，并通过改变元数据对象中的魔数来检测它。也就是说，如果它带有
当前的魔数，说明该元数据不具备自标识能力；如果它带有新的魔数，则具备自标识
能力，我们就能在运行时、取证分析或修复期间对该元数据对象做更广泛的全自动
验证。

作为首要关注点，自描述元数据需要某种形式的整体完整性检查。如果我们无法验证
元数据未因外部影响而改变，就不能信任它。因此我们需要某种形式的完整性检查，
这是通过向元数据块添加 CRC32c 校验来实现的。如果我们能验证该块包含的是它本应
包含的元数据，大量的手工验证工作就可以跳过。

之所以选择 CRC32c，是因为 XFS 中元数据长度不可能超过 64k，因此 32 位 CRC 足以
检测元数据块中的多比特错误。CRC32c 现在在主流 CPU 上也已被硬件加速，因此速度
很快。所以，虽然 CRC32c 并非可使用的完整性检查中最强的一种，但已远超我们的
需要，且开销相对较小。相比 CRC32c，支持更大的完整性字段和/或算法并不能带来
额外的价值，却会增加大量复杂性，因此没有提供改变完整性检查机制的预留。

自描述元数据需要包含足够的信息，使得该元数据块能够在无需查看任何其他元数据的
情况下被验证为位于正确位置。这意味着它需要包含位置信息。仅仅向元数据添加块号
不足以防范写入被错误定向——一次写入可能被错误地定向到错误的 LUN，从而被写入
错误文件系统的“正确块”。因此位置信息必须同时包含文件系统标识符与块号。

取证分析中的另一个关键信息点是知道该元数据块属于谁。我们已经知道其类型、位置、
它是否有效和/或损坏，以及它上一次被修改是多久以前。知道块的所有者很重要，因为
它使我们能够找到其他相关元数据以确定损坏的范围。例如，如果我们有一个 extent
btree 对象，我们不知道它属于哪个 inode，因此必须遍历整个文件系统来找到该块的
所有者。更糟的是，损坏可能意味着找不到所有者（即它是一个孤儿块），因此如果
元数据中没有所有者字段，我们就完全无从得知损坏的范围。如果元数据对象中有
所有者字段，我们就能立即自上而下地进行验证以确定问题的范围。

不同类型的元数据具有不同的所有者标识符。例如，目录、属性和 extent 树块都归
一个 inode 所有，而空闲空间 btree 块归一个分配组所有。因此所有者字段的大小与
内容由我们所审视的元数据对象类型决定。所有者信息也能识别被错位的写入（例如
空闲空间 btree 块被写入了错误的 AG）。

自描述元数据还需要包含某种关于它何时被写入文件系统的指示。取证分析时的一个
关键信息点是该块最近被修改的程度。基于修改时间对一组损坏的元数据块进行关联
非常重要，因为它能指示这些损坏是否相关、是否发生过多次导致最终失败的损坏事件，
甚至是否存在运行时验证未能检测出的损坏。

例如，通过查看包含该块的空闲空间 btree 块的最后写入时间，相对于该元数据对象
本身最后写入的时间，我们可以判断该元数据对象应当处于空闲空间状态还是仍被分配。
如果空闲空间块比该对象及其所有者都更新，那么该块很可能本应从所有者处被移除。

为了提供这个“写入时间戳”，每个元数据块都会写入修改它的最近一次事务的日志
序列号（LSN）。这个数字在文件系统的整个生命周期中总是递增的，唯一会重置它的
事情是对文件系统运行 xfs_repair。进一步，通过 LSN 我们可以判断损坏的元数据是否
都属于同一个日志检查点，从而对磁盘上第一个与最后一个损坏元数据实例之间发生了
多少修改有所了解，并能进一步了解从损坏被写入到它被检测出来之间发生了多少修改。


## 运行时验证


自描述元数据的验证在运行时在两个地方进行：

 - 在成功从磁盘读取之后立即进行
 - 在提交写 IO 之前立即进行

验证是完全无状态的——它独立于修改过程进行，目的仅仅是检查元数据是否如其所述，
以及元数据字段是否处于边界之内且内部一致。因此，我们无法捕获块内可能发生的所有
类型的损坏，因为可能存在由操作状态对元数据施加的某些限制，或者可能存在块间
关系（例如被损坏的兄弟指针列表）的损坏。因此我们在主代码体中仍然需要状态化的
检查，但一般而言，大部分逐字段的验证都由验证器处理。

对于读验证，调用者需要指定它应当看到的预期元数据类型，IO 完成过程则验证该元数据
对象是否与预期相符。如果验证过程失败，它会将正在读取的对象标记为 EFSCORRUPTED。
调用者需要捕获此错误（与 IO 错误相同），如果它需要因验证错误而采取特殊行动，可以
通过捕获 EFSCORRUPTED 错误值来做到。如果我们需要在更高层面对错误类型做更细致的
区分，可以按需为不同的错误定义新的错误号。

读验证的第一步是检查魔数并判断是否需要 CRC 验证。如果需要，则计算 CRC32c 并与
对象自身存储的值进行比较。一旦验证通过，再进一步检查位置信息，随后进行大量的
对象特定元数据验证。如果这些检查有任何一项失败，则该缓冲区被视为已损坏，并
适当地设置 EFSCORRUPTED 错误。

写验证与读验证相反——首先对该对象进行大量验证，如果正常，我们再从上一次对该
对象的修改更新 LSN。此后，我们计算 CRC 并将其插入对象。完成后，写 IO 才被允许
继续。如果在此过程中发生任何错误，该缓冲区会再次被标记上 EFSCORRUPTED 错误供
更高层捕获。


## 结构


```

    struct xfs_ondisk_hdr {
	    __be32  magic;		/* magic number */
	    __be32  crc;		/* CRC, not logged */
	    uuid_t  uuid;		/* filesystem identifier */
	    __be64  owner;		/* parent object */
	    __be64  blkno;		/* location on disk */
	    __be64  lsn;		/* last modification in log, not logged */
    };

```
根据元数据的不同，这些信息可能是独立于元数据内容的头部结构的一部分，也可能
分布到一个已有的结构中。后者发生在已经包含其中部分信息的元数据上，例如
超级块和 AG 头部。

其他元数据可能采用不同的信息格式，但提供的信息级别大体相同。例如：

 - 短 btree 块有一个 32 位的 owner（ag 号）和一个 32 位的块号用于定位。这二者
	  组合起来提供了与上述结构中的 @owner 和 @blkno 相同的信息，但在磁盘上
	  少用了 8 字节空间。

 - 目录/属性节点块有一个 16 位的魔数，而包含该魔数的头部中还包含其他信息。
	  因此额外的元数据头部改变了元数据的整体格式。

```

    #define XFS_FOO_CRC_OFF		offsetof(struct xfs_ondisk_hdr, crc)

    static void
    xfs_foo_read_verify(
	    struct xfs_buf	*bp)
    {
	struct xfs_mount *mp = bp->b_mount;

	    if ((xfs_sb_version_hascrc(&mp->m_sb) &&
		!xfs_verify_cksum(bp->b_addr, BBTOB(bp->b_length),
					    XFS_FOO_CRC_OFF)) ||
		!xfs_foo_verify(bp)) {
		    XFS_CORRUPTION_ERROR(__func__, XFS_ERRLEVEL_LOW, mp, bp->b_addr);
		    xfs_buf_ioerror(bp, EFSCORRUPTED);
	    }
    }

```
该代码通过检查超级块的特性位，确保仅当文件系统启用了 CRC 时才检查 CRC；随后，
如果 CRC 验证通过（或不需要 CRC），它再验证块的实际内容。

验证器函数会有几种不同的形式，取决于魔数是否可用于确定块的格式。在
```

    static bool
    xfs_foo_verify(
	    struct xfs_buf		*bp)
    {
	    struct xfs_mount	*mp = bp->b_mount;
	    struct xfs_ondisk_hdr	*hdr = bp->b_addr;

	    if (hdr->magic != cpu_to_be32(XFS_FOO_MAGIC))
		    return false;

	    if (!xfs_sb_version_hascrc(&mp->m_sb)) {
		    if (!uuid_equal(&hdr->uuid, &mp->m_sb.sb_uuid))
			    return false;
		    if (bp->b_bn != be64_to_cpu(hdr->blkno))
			    return false;
		    if (hdr->owner == 0)
			    return false;
	    }

	    /* object specific verification checks here */

	    return true;
    }

```
如果存在用于不同格式的不同魔数，验证器
```

    static bool
    xfs_foo_verify(
	    struct xfs_buf		*bp)
    {
	    struct xfs_mount	*mp = bp->b_mount;
	    struct xfs_ondisk_hdr	*hdr = bp->b_addr;

	    if (hdr->magic == cpu_to_be32(XFS_FOO_CRC_MAGIC)) {
		    if (!uuid_equal(&hdr->uuid, &mp->m_sb.sb_uuid))
			    return false;
		    if (bp->b_bn != be64_to_cpu(hdr->blkno))
			    return false;
		    if (hdr->owner == 0)
			    return false;
	    } else if (hdr->magic != cpu_to_be32(XFS_FOO_MAGIC))
		    return false;

	    /* object specific verification checks here */

	    return true;
    }

```
写验证器与读验证器非常相似，只是它们以如下方式做事
```

    static void
    xfs_foo_write_verify(
	    struct xfs_buf	*bp)
    {
	    struct xfs_mount	*mp = bp->b_mount;
	    struct xfs_buf_log_item	*bip = bp->b_fspriv;

	    if (!xfs_foo_verify(bp)) {
		    XFS_CORRUPTION_ERROR(__func__, XFS_ERRLEVEL_LOW, mp, bp->b_addr);
		    xfs_buf_ioerror(bp, EFSCORRUPTED);
		    return;
	    }

	    if (!xfs_sb_version_hascrc(&mp->m_sb))
		    return;


	    if (bip) {
		    struct xfs_ondisk_hdr	*hdr = bp->b_addr;
		    hdr->lsn = cpu_to_be64(bip->bli_item.li_lsn);
	    }
	    xfs_update_cksum(bp->b_addr, BBTOB(bp->b_length), XFS_FOO_CRC_OFF);
    }

```
这将在我们继续之前验证元数据的内部结构，检测在内存中被修改时发生的损坏。如果
元数据验证通过，且启用了 CRC，我们随后更新 LSN 字段（它上一次被修改的时间）并
计算元数据上的 CRC。完成后，我们才能发起 IO。


## Inode 与 Dquot


Inode 和 dquot 是特殊的“雪花”。它们具备逐对象的 CRC 与自标识符，但它们被紧凑
打包，使得每个缓冲区中包含多个对象。因此我们不使用每缓冲区的验证器来完成逐对象
验证与 CRC 计算的工作。每缓冲区验证器只执行缓冲区的初步识别——确认其中包含
inode 或 dquot，并且在所有预期的位置都有魔数。所有进一步的 CRC 与验证检查都在
每个 inode 被从缓冲区读出或写回时进行。

验证器与标识符检查的结构与上述缓冲区代码非常相似。唯一的区别在于它们被调用的
位置。例如，inode 读验证在 inode 首次从缓冲区读出、struct xfs_inode 被实例化时，于
xfs_inode_from_disk() 中完成。inode 在回写期间（xfs_iflush_int 中）已经过大量验证，
因此这里唯一的补充是在 inode 被复制回缓冲区时向其中加入 LSN 和 CRC。

XXX：inode 未链接列表的修改不会重新计算 inode 的 CRC！所有未链接列表的修改都不
检查或更新 CRC，无论是在 unlink 期间还是在日志恢复期间。因此直到现在它都未被
注意到。这不会立刻产生问题——修复时大概会对此提出警告——但它需要被修复。
