## NFSD 维护者条目档

维护者条目档案（Maintainer Entry Profile）用特定于某个子系统及其维护者的惯例，对顶层流程文档（位Documentation/process/）进行补充。贡献者可以使用本文档来设定预期并避免常见错误。维护者可以使用这些档案跨子系统寻找趋同于最佳实践的机会
### 概述


网络文件系统（Network File System，NFS）是一族标准化的网络协议，能够跨一组网络连接的对等主机访问文件。NFS 客户端上的应用程序访问由 NFS 服务器共享的文件系统上的文件。单个网络对等节点可以同时充NFS 客户端和 NFS 服务器
NFSD Linux 内核中包含的 NFS 服务器实现。内核内NFS 服务器可以快速访问存储在该服务器本地文件系统上的文件。NFSD 可以共享存储在大多数 Linux 原生文件系统类型上的文件，包xfs、ext4、btrfs tmpfs
### 邮件列表


linux-nfs@vger.kernel.org 邮件列表是一个公开列表。其目的是促进从Linux NFS 协议栈（客户端和服务器）开发的开发者之间的协作。它不是讨论Linux NFS 协议栈无直接关系话题的场所
linux-nfs 邮件列表归档`lore.kernel.org <https://lore.kernel.org/linux-nfs/>`_
Linux NFS 社区没有任何聊天室
### 报告 bug


如果你在发行版构建的内核上遇到与 NFSD 相关bug，请先与你的 Linux 发行商合作
针对上游 Linux 代码库的 bug 报告欢迎发送到 linux-nfs@vger.kernel.org 邮件列表，那里可以进行一些积极的分类（triage）。NFSD bug 也可以在 Linux 内核社区bugzilla 上报告：

  https://bugzilla.kernel.org

请将NFSD 相关bug 归类Filesystems/NFSD"组件下。一般而言，尽可能多地包含详细信息是一个好的开始，包括来自客户端和服务器的相关系统日志消息
NFSD 相关的用户空间软件（例如 mountd exportfs 命令）包含在 nfs-utils 包中。这些问题请报告linux-nfs@vger.kernel.org。你可能会被引导将报告转移到特定bug 跟踪器
### 贡献者指

#### 标准合规

NFSD 的首要任务是Linux NFS 客户端完全互操作。我们也会在 NFS bake-a-thon 活动（也称为 plug-fests）中定期针对其他流行NFS 客户端实现进行测试。非 Linux NFS 客户端不属于上游 NFSD CI/CD
NFSD 社区致力于提供一个能与所有符合标准的 NFS 客户端实现互操作NFS 服务器实现。这是通过尽可能贴IETF 发布NFS、RPC GSS-API 标准中的规范性要求来实现的
在代码注释中引用 RFC 和章节号总是有用的，尤其是当行为与标准偏离时（即使行为合规但实现晦涩时也同样如此）
在罕见需要偏离标准强制行为的情况下，对用例或标准缺陷的简要文档是代码内文档的必要部分
必须始终注意避免将本地错误码（即 errnos）泄漏给 NFSD 的客户端。NFS 协议回复中始终需要正确的 NFS 状态码
#### NFSD 管理接口


NFSD 管理接口包括
- NFSD SUNRPC 模块参数

- /etc/exports 中的导出选项

- /proc/fs/nfsd/ /proc/sys/sunrpc/ 下的文件

- NFSD netlink 协议

经常会有引入或修NFSD 某个传统管理接口的请求。引入一个新的管理设置无疑在技术上很容易。然而，NFSD 维护者倾向于将其作为最后手段，是有充分理由的：

- 与任API 一样，管理接口很难一次做对
- 一旦它们被文档化并被长期使用，管理接口就变得难以修改或移除
- 每一个新的管理设置都会使 NFSD 的测试矩阵成倍增加
- 单个管理接口的成本是递增的，但成本会在所有现有接口上累积
如果能在前期下功夫理解新设置的根本需求，然后设法使其自行调优（或以其他方式变得不再必要），通常对所有人都有利
如果确实需要一个新设置，首先考虑将其添加NFSD netlink 协议。或者，如果它不需要作为一个可靠的长期用户空间特性，则可以将其添加到 NFSD 位于 /sys/kernel/debug/nfsd/ 下的一众实验性设置中
#### 现场可观测

NFSD 采用多种不同的机制来观察运行情况，包括计数器、printks、WARNings 和静态跟踪点。它们各有优缺点。贡献者应为其任务选择最合适的工具
- 必须尽可能避免使BUG，因为它经常会直接导致整个系统崩溃
- WARN 仅适用于完整的栈回溯有用时
- printk 可以显示详细信息。但绝不能在与远程用户可重复触发的代码路径中使用它们
- dprintk 可以显示详细信息，但只能在预设的组中启用。输出产生的开销使得 dprintk 不适合用于 I/O 这类频繁的操作
- 计数器始终开启，但除了发生频率外，对单个事件提供的信息很少
- 静态跟踪点可以单独或分组（通过 glob）启用。它们通常开销较低，因此优先用于热路径
- 动态跟踪（例如 kprobes eBPF）相当灵活，但无法在某些环境中使用（例如完整kernel lock-down）
#### 测试


kdevops 项目

  https://github.com/linux-kdevops/kdevops

包含若干 NFS 特定的工作流，以及社区标准的 fstests 套件。这些工作流基于 ltp fio 等开源测试工具。鼓励贡献者在不借助 kdevops 的情况下使用这些工具，或者贡献者应自行安装并使kdevops，在提交前验证其补丁
#### 编码风格


遵循以下文档中描述的编码风格偏好

  Documentation/process/coding-style.rst

但有如下例外
- 以反向圣诞树（reverse Christmas tree）顺序向函数添加新的局部变
- 对以下内容使kdoc 注释风格
  - 非静态函  - 静inline 函数
  - 作为回调/虚函数的静态函
- 所有新的函数名，对于非特定 NFS 版本的函数，`nfsd_` 开头
- 特定NFSv2 NFSv3，或NFSv4 所有次要版本使用的函数名，使用 `nfsdN_`，其N 为版本号
- 特定于某NFSv4 次要版本的新函数名可`nfsd4M_` 命名，其M 为次要版本号
#### 补丁准备


阅读并遵循以下文档中的所有指
  Documentation/process/submitting-patches.rst

使用标签来标识所有补丁作者。不过，审阅者和测试者应通过回复电子邮件补丁提交来添加。电子邮件被广泛用于公开归档审阅和测试的署名。这些标签在补丁被应用时会自动插入到你的补丁中
diff 正文中的代码已经显示了正在更改的/内容/。因此无需在补丁描述中重复这一点。相反，描述应包含以下一项或多项
- 简要的问题陈述这个补丁试图修复什么？"）以及根因分析
- 最终用户可见的症状，或支持工程师可能用来搜索该补丁的项目，例如栈回溯
- 关于为什么该补丁是解决此问题的最佳方式的简要说明
- 审阅者理解补丁所作更改可能需要的任何上下文
- 任何相关的基准测试结果，或功能测试结果
Documentation/process/submitting-patches.rst 中详述，使用 Fixes: 标签来标识所处理的问题被引入的历史节点
如果在补丁描述中无法确定该历史节点——即无法提供 Fixes: 标签——请提及。在这种情况下，请向维护者明确说明，即使没有 Fixes: 标签，是否仍需LTS 反向移植（backport）
NFSD 维护者倾向于在回应补丁提交的公开讨论之后，自行添stable 标签。贡献者可以建stable 标签，但请注意，许多版本管理工具在你发布补丁时会自动添加此类 stable Cc。除非你绝对确定该补丁在初始提交过程中需要进stable，否则不要添Cc: stable"
#### 补丁提交


针对 NFSD 的补丁通过内核基于电子邮件的审阅流程提交，这与大多数其他内核子系统相同
在每次提交之前，将你的补丁或补丁系列 rebase nfsd-testing 分支上，该分支位
  https://git.kernel.org/pub/scm/linux/kernel/git/cel/linux.git

NFSD 子系统与 Linux 内核内的 NFS 客户端是分开维护的。NFSD 维护者通常不会接受客户端更改的提交，也无法权威地回NFS 客户端代码的 bug 报告或功能请求
这意味着，如果补丁被发送到了错误的维护者和审阅者集合，贡献者可能会被要求重新提交补丁。这不是拒绝，而只是对提交流程的纠正
如有疑问，请查阅 MAINTAINERS 文件中的 NFSD 条目，以了解哪些文件和目录属NFSD 子系统
NFSD 补丁的正确电子邮件地址集合为：

To: MAINTAINERS 中列出的 NFSD 维护者和审阅Cc: linux-nfs@vger.kernel.org，可linux-kernel@

如果补丁涉及其他子系统（例如 MM RDMA），它们的主要邮件列表地址也可以包含在 Cc: 字段中。其他贡献者和相关方也可以包含在内
一般而言，我们更倾向于贡献者使用常见的补丁邮件工具，例git send-email"stg email format/send"，它们往往能不出差错地处理好细节
由单个补丁组成的系列不需要有封面信（cover letter）。但是，如果有不适合包含在补丁描述中的大量上下文，也可以包含封面信
请注意，在基于电子邮件的提交流程中，系列封面信不属于提交到内核源代码库或其提交历史的工作的一部分。因此请始终尽量将与主题相关的信息保留在补丁描述中
欢迎设计文档，但由于封面信不会被保留，或许更好的选择是包含一个在 Documentation/filesystems/nfs/ 下添加此类文档的补丁
审阅者会询问测试覆盖率以及补丁预期要解决的用例。请准备好回答这些问题
维护者的审阅评论可能措辞礼貌，但一般而言，当这些评论可操作时，处理它们并非可选。如有必要，当贡献者拒绝处理合理请求时，维护者保留不应用补丁的权利
将内核源代码和用户空间源代码的更改作为独立的系列发布。你可以用封面信中的评论将这两个系列联系起来
一般而言，即使是简单的修改，NFSD 维护者也会要求重新发布（reposts），以便在被拉入 NFSD 树之前公开归档该请求及由此产生的重新发布。这也使我们能够快速重建补丁系列，而不会遗漏可能通过电子邮件讨论过的更改
避免频繁地仅带着微小更改重新发布大型系列。根据经验，每周发布实质性更改超过一次会导致审阅者负担过重
请记住，子系统维护者和审阅者只有少数几个，但贡献来源可能很多。因此，维护者和审阅者始终是扩展性较差的资源。请善待你友好的邻居维护者
#### 补丁接收


NFSD 没有正式的审阅流程，但我们希望看到至少两Reviewed-by: 确认，针对的不只是简单的清理性补丁。审阅在 linux-nfs@vger.kernel.org 上公开进行，并归档lore.kernel.org
目前 NFSD 补丁队列维护在以下分支中
  https://git.kernel.org/pub/scm/linux/kernel/git/cel/linux.git

NFSD 维护者首先将补丁应用nfsd-testing 分支，该分支始终对新提交开放。在审阅进行期间也可以应用补丁。nfsd-testing 是一个主题分支，因此它会频繁变化、会rebase，并且如果你的补丁有问题，可能会被丢弃
通常，一封脚本生成的"thank you"电子邮件会表明你的补丁何时被添加nfsd-testing 分支。你可以使用 linux-nfs patchworks 实例跟踪补丁的进度：

  https://patchwork.kernel.org/project/linux-nfs/list/

当你的补丁位nfsd-testing 中时，它会暴露于各种测试环境，包括社区零日（zero-day）机器人、静态分析工具和 NFSD 持续集成测试。浸泡（soak）期为三到四周
每个nfsd-testing 中未经更改地存活过浸泡期的补丁会被移动到 nfsd-next 分支
nfsd-next 分支每晚会自动合并到 linux-next fs-next
nfsd-next 中存活下来的补丁会被包含在下一NFSD 合并窗口pull request 中。这些窗口通常63 天（九周）发生一次
当上游合并窗口关闭时，nfsd-next 分支被重命名nfsd-fixes，并基于上游 -rc1 标签创建一个新nfsd-next 分支
面向上游 -rc 版本发布的修复也会经nfsd-testing 的考验，然后被应用nfsd-fixes 分支。该分支在短时间内可Linus 拉取。为了限制引入回归的风险，我们将此类修复限制为紧急情况，或对最近一次上游合并期间发生的损坏的修复
提交紧急补丁时，请明确说明需要立即采取行动（无论是应用到 -rc 还是 LTS 反向移植）
#### 敏感补丁提交bug 报告


CVE Linux 内核社区中的特定成员以及若干外部实体生成。Linux NFS 社区不发布也不分CVE。CVE 是在问题及其修复已知之后才被分配的
然而，NFSD 维护者有时会收到敏感的安全报告，有时这些报告足够重要，需要被 embargo（embargoed）。在这种罕见情况下，修复可以在公众视线之外开发和审阅
请注意，许多版本管理工具在你发布补丁时会添加 stable Cc。这通常是个麻烦，但它可能意外地暴露embargo 的安全问题。除非你绝对确定该补丁在初始提交过程中需要进stable@，否则不要添Cc: stable"
从未出现在任何列表上、但带有 Reported-by: Fixes: 标签而被合并的补丁，会被关注安全的人士视为可疑。我们鼓励，在任何私有审阅之后，安全敏感的补丁都应发布到 linux-nfs@ 进行通常的公开审阅、归档和测试期
#### LLM 生成的提

Linux 内核社区作为一个整体，仍在探索 LLM 生成代码的新世界。NFSD 维护者愿意接受部分或全部由基LLM 的开发工具生成的补丁提交。此类提交须遵循与完全由人类作者创建的提交相同的标准：

- 人类贡献者通过 Signed-off-by: 标签标识自己。该标签可视为一DoC（开发者来源证书）
- 人类贡献者照例全权负责代码的来源，以及因无意中包含具有冲突许可证的代码而造成的任何污染
- 人类贡献者必须能够回答并处理审阅问题。诸这修复了我的问题，但我不知道为什这样的补丁描述是不可接受的
- 该贡献须接受与所有其他提交相同的测试流程
- 不要求指明（通过 Generated-by: 标签或其他方式）该贡献是LLM 生成的
LLM 生成的代码中处理审阅评论和修复请求很容易。事实上容易到让人忍不住立即重新发布更新后的代码。请抵制这种诱惑
一如既往，请避免24 小时内重新发布系列修订超过一次
#### 清理补丁


NFSD 维护者不鼓励进行简单的清理性补丁，尤其是那些不在其他工作上下文中的清理。例如：

- 处理合并后的 `checkpatch.pl` 警告
- 处理 Local variable ordering<rcs> 问题
- 处理长期存在的空白符损坏

这是因为我们认为此类更改所产生的变动（churn）成本高于此类清理带来的价值
相反，拼写和语法修复是受到鼓励的

### 功能请求


没有唯一一种方式来提出官方功能请求，但关于该请求的讨论最终应到达 linux-nfs@vger.kernel.org 邮件列表，以供社区公开审阅
#### 瀛愮郴缁熻竟鐣。

NFSD 本身不过是一个协议引擎。这意味着它的主要职责是将 NFS 协议转换Linux 内核中的 API 调用。例如，NFSD 不负责确切了解字节或文件属性在块设备上是如何管理的。它依赖其他内核子系统来完成这些
如果 NFSD 所依赖的子系统没有实现某个特定功能，即使标NFS 协议支持该功能，通常也意味着 NFSD 无法在没有内核其他领域大量开发工作的情况下提供该功能
#### 明确

功能请求可以来自任何地方，因此常常可能含糊不清。请求者可能不理解什么是"use case"user story"。这些描述性范式经常被开发者和架构师用来理解设计的需求，但它们是软件行业中的行话（terms of art），在日常世界中并不使用
为了防止贡献者和维护者不堪重负，我们不会害怕礼貌地对描述不清的请求
### 社区角色及其权限


Linux 子系统社区的目的是为 Linux 内核中一组狭窄的源文件提供专业知识和积极的治理（stewardship）。这也可以包括管理用户空间工具
为了给负责治NFS 服务器代码库Linux NFS 社区结构提供背景，我们在此定义社区角色
- **Contributor（贡献者）** ：任何提交代码更改、bug 修复、建议、文档修复等的人。贡献者可以定期或不定期提交
- **Outside Contributor（外部贡献者）** ：在 Linux NFS 社区中不是常规参与者的贡献者。这可能意味着为内核其他部分做贡献的人，或者只是注意到注释中的拼写错误并发送了补丁的人
- **Reviewer（审阅者）** ：在 MAINTAINERS 文件中被列为 reviewer 的人是领域专家，可以请求对贡献的代码进行更改，并期望贡献者处理该请求
- **External Reviewer（外部审阅者）** ：未MAINTAINERS 文件中被列为 reviewer，但是领域专家的人。例子包括具有网络、安全或持久存储专业知识Linux 内核贡献者，或主要贡献于其他 NFS 实现的开发者
一个或多个人员将承担以下角色。这些人通常被泛称为"maintainers"，并MAINTAINERS 文件中以 NFSD 子系统下M:"标签标识
- **Upstream Release Manager（上游发布经理）** ：此角色负责将贡献整理到分支中、审阅测试结果，然后在合并窗口期间发pull request。发布经理与 Linus 之间存在信任关系
- **Bug Triager（Bug 分类者）** ：对提交linux-nfs 邮件列表bug 跟踪器的 bug 报告做出第一响应的人，并帮助排查问题并确定后续步骤
- **Security Lead（安全负责人* ：安全负责人处理来自安全社区的联系以解决紧急问题，并处理长期安全问题，例如供应链方面的担忧。对于上游而言，这通常关乎贡献是否违反许可证或其他知识产权协议
- **Testing Lead（测试负责人* ：测试负责人构建并运行该子系统的测试基础设施。测试负责人可能因持续的高缺陷率而要求丢弃某些补丁
- **LTS Maintainer（LTS 维护者）** ：LTS 维护者负责管理补丁上Fixes: Cc: stable 标注，并确保无法自动应用LTS 内核的补丁在必要时得到适当的手动反向移植
- **Community Manager（社区经理）** ：这个裁判（umpire）角色可以在冲突期间被请求判定对错（call balls and strikes），但也负责确保社区内部关系的健康，并促进关于长期主题（如如何管理不断增长的技术债务）的讨论
