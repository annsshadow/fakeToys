## RPC 缓存


本文档简要介绍 sunrpc 层中用于（尤其是）NFS 认证的缓存机制。

## 缓存


该缓存机制取代了旧的 exports 表，并允许缓存各种各样的值。

存在许多结构相似但在内容和用途上可能大不相同的缓存。有一套公共代码用于管理这些缓存。

可能需要用到的缓存示例包括：

  - IP 地址到客户端名称的映射
  - 客户端名称与文件系统到导出选项的映射
  - UID 到 GID 列表的映射，用于规避 NFS 最多 16 个 gid 的限制
  - 本地 UID/GID 与远程 UID/GID 之间的映射，适用于未统一分配 uid 的站点
  - 网络身份到公钥的映射，用于加密认证

公共代码负责处理以下事项：

   - 带正确锁定的通用缓存查找
   - 支持“NEGATIVE”（负）条目以及正条目
   - 允许缓存项设置 EXPIRED 过期时间，并在过期且不再被使用时将其移除
   - 向用户空间发起请求以填充缓存条目
   - 允许用户空间直接设置缓存中的条目
   - 延迟依赖尚未完整缓存项的 RPC 请求，并在缓存项补全后重放这些请求
   - 在条目过期时清理旧条目

### 创建缓存


- 缓存需要存储一个数据（datum）。其形式为结构体定义，其中必须包含一个 struct cache_head 元素，通常作为第一个元素。
   它还会包含一个键以及部分内容。每个缓存元素都带有引用计数，并包含供缓存管理使用的过期时间和更新时间。
- 缓存需要一个“cache_detail”结构体来描述该缓存。它存储哈希表、缓存管理的一些参数，以及一些描述如何操作特定缓存项的操作。

   这些操作如下：

    struct cache_head \*alloc(void)
      简单地分配适当的内存并返回嵌入在该结构体中的 cache_detail 指针。

    void cache_put(struct kref \*)
      当对某个项的最后一个引用被释放时调用。传入的指针指向
      cache_head 中的“ref”字段。cache_put 应释放由“cache_init”创建的引用，
      如果设置了 CACHE_VALID，还应释放由 cache_update 创建的引用。
      然后它应释放由“alloc”分配的内存。

    int match(struct cache_head \**orig, struct cache_head \**new)
      测试两个结构体中的键是否匹配。匹配返回 1，否则返回 0。

    void init(struct cache_head \**orig, struct cache_head \**new)
      从“orig”设置“new”中的“key”字段。这可能包括获取对共享对象的引用。

    void update(struct cache_head \**orig, struct cache_head \**new)
      从“orig”设置“new”中的“content”字段。

    int cache_show(struct seq_file \**m, struct cache_detail \**cd, struct cache_head \*h)
      可选。用于提供一个列出缓存内容的 /proc 文件。应显示一项，通常只占一行。

    int cache_request(struct cache_detail \**cd, struct cache_head \**h, char \**\**bpp, int \*blen)
      格式化一条要发送给用户空间以实例化某项的请求。\**bpp 是大小为 \**blen 的缓冲区。
      bpp 应在编码后的消息之上向前移动，\**blen 应相应减小以表示剩余多少空闲空间。
      成功返回 0，空间不足或其他问题返回 <0。

    int cache_parse(struct cache_detail \**cd, char \**buf, int len)
      一条来自用户空间的消息已到达，用于填充缓存项。消息位于长度为“len”的“buf”中。
      cache_parse 应解析该消息，用 sunrpc_cache_lookup_rcu 在缓存中找到该项，并用 sunrpc_cache_update 更新它。

- 缓存需要使用 cache_register() 注册。这会把它加入一个缓存列表，该列表会被定期清理以丢弃旧数据。

### 使用缓存


要在缓存中查找某个值，调用 sunrpc_cache_lookup_rcu，传入一个示例项中填好“key”字段的 cache_head 指针。
该指针会被传给 ->match 以定位目标条目。如果未找到任何条目，则会创建一个新的条目，加入缓存，并标记为不包含有效数据。

返回的项通常会传给 cache_check，它会检查数据是否有效，并可能发起一次向上调用（up-call）以获取新数据。
如果条目为负或需要向上调用但无法进行，cache_check 返回 -ENOENT；如果向上调用正在等待中，返回 -EAGAIN；数据有效则返回 0。

cache_check 可以传入一个“struct cache_req\*”。该结构体通常内嵌在真正的请求中，可用于创建请求的延迟副本（struct cache_deferred_req）。
当找到的缓存项不是最新的、但有理据认为用户空间可能很快会提供信息时，会进行此操作。当缓存项变为有效时，该请求的延迟副本会被重新访问（->revisit）。
预期该方法会重新调度该请求以便处理。

sunrpc_cache_lookup_rcu 返回的值也可以传给 sunrpc_cache_update 以设置该项的内容。传入的第二个项应持有该内容。
如果 _lookup 找到的项已有有效数据，则丢弃它并创建一个新项。这样可让项的任何使用者不必担心在检视内容时内容发生变化。
如果 _lookup 找到的项不包含有效数据，则内容被复制过去并设置 CACHE_VALID。

### 填充缓存


每个缓存都有一个名称，当缓存注册时，会在 /proc/net/rpc 中创建一个同名的目录。

该目录包含一个名为“channel”的文件，这是内核与用户之间用于填充缓存的通信通道。
该目录之后可能包含其他用于与缓存交互的文件。

“channel”的工作方式有点像数据报套接字。每次“write”都会被整体传给缓存进行解析和解释。
每个缓存可以不同地处理写请求，但期望写入的消息包含：

  - 一个键
  - 一个过期时间
  - 一个内容

目的是使缓存中具有给定键的项被创建或更新为具有给定内容，并在该项上设置过期时间。

从通道读取更有意思一些。当缓存查找失败，或者查找成功但发现某个条目可能即将过期时，
会登记一个请求，要求用户空间更新该缓存项。这些请求会出现在 channel 文件中。

连续读取会返回连续的请求。如果没有更多请求可返回，读操作将返回 EOF，但对读的 select 或 poll 会阻塞，等待有新请求加入。

```
  open the channel.
    select for readable
    read a request
    write a response
  loop.
```
如果它崩溃并需要重启，任何未得到应答的请求仍会出现在文件中，并由助手的新实例读取。

每个缓存应定义一个“cache_parse”方法，该方法接收来自用户空间的写入消息并处理它。
它应返回一个错误（会传播回 write 系统调用）或 0。

每个缓存还应定义一个“cache_request”方法，该方法接收一项缓存项并将其编码为请求放入所提供的缓冲区中。

  如果某个缓存在通道上没有活跃读取者，并且已经超过 60 秒没有活跃读取者，则不会再向通道添加请求，
  而是所有未找到有效条目的查找都会失败。这部分是为了向后兼容：先前的 nfs exports 表被视为权威的，
  一次失败的查找意味着明确的“否”。

### 请求/响应格式


虽然每个缓存可以自行决定通过通道使用的请求和响应格式，但推荐采用以下格式，并提供了相应的支持例程：

每条请求或响应记录应为可打印的 ASCII，恰好包含一个换行符，且该换行符应位于末尾。
记录内的字段用空格分隔，通常为一个空格。如果字段中需要空格、换行符或 nul 字符，则必须进行转义。有两种机制可用：

- 如果字段以“\x”开头，则它必须包含偶数个十六进制数字，这些数字两两一组给出字段中的字节。
- 否则，字段中的 \ 之后必须跟随 3 个八进制数字，给出某个字节的编码。其他字符按原样处理。
   至少，空格、换行符、nul 以及“\”必须以这种方式转义。
