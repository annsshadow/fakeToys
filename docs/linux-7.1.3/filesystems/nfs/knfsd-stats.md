## 内核 NFS 服务器统计


:Authors: Greg Banks <gnb@sgi.com> - 2009 年 3 月 26 日

本文档描述内核 NFS 服务器向用户空间提供的统计信息的格式与语义。这些统计信息在
多个文本形式的伪文件中可用，下面分别描述每个文件。

在大多数情况下你不需要了解这些格式，因为 nfs-utils 发行版中的 nfsstat(8) 程序提供了
一个有用的命令行接口来提取并打印它们。

这里描述的所有文件都格式化为一系列文本行，由换行符 '\n' 分隔。以井号 '#' 字符开头的
行是给人看的注释，解析程序应当忽略。所有其它行都包含一系列由空白分隔的字段。

## /proc/fs/nfsd/pool_stats


该文件在 2.6.30 及以后版本的内核中可用，前提是 /proc/fs/nfsd 文件系统已挂载（几乎
总是应当挂载）。

第一行是一条注释，描述所有其它行中出现的字段。其它行以一系列无符号十进制数值字段
呈现以下数据。每个 NFS 线程池显示一行。

所有计数器都是 64 位宽，并自然回绕。无法将这些计数器清零，应用程序应当自行做速率
换算。

pool
	该行使之适用的 NFS 线程池的 id 编号。该编号不会变化。

	线程池 id 是一组从零开始的小整数连续集合。最大值取决于线程池模式，但目前
	不能大于系统中的 CPU 数量。注意，在默认情况下将只有一个线程池，它包含系统
	中所有的 nfsd 线程和所有的 CPU，因此该文件将只有一行，其 pool id 为 "0"。

packets-arrived
	统计到达的 NFS 数据包数量。更准确地说，这是网络栈通知 sunrpc 服务器层某个
	传输上（例如 NFS 或 UDP 套接字，或 NFS/RDMA 端点）可能有新数据的次数。

	取决于 NFS 工作负载模式以及各种网络栈效应（例如 Large Receive Offload，它
	可以在线路上合并数据包），这可能多于或少于接收到的 NFS 调用数量（该统计信息
	在别处提供）。然而，这是衡量因 NFS 网络流量而施加在 sunrpc 服务器层上的 CPU
	负载的更准确、且更不依赖工作负载的指标。

sockets-enqueued
	统计一个 NFS 传输被排入队列等待 nfsd 线程服务的次数，即当时认为没有可用的
	nfsd 线程。

	该统计所跟踪的情况表明存在需要处理的面向网络的 NFS 工作，但无法立即完成，
	从而在服务 NFS 调用时引入了微小的延迟。该计数器的理想变化率为零；显著非零的
	值可能表示性能瓶颈。

	这可能是因为线程池中的 nfsd 线程对于 NFS 工作负载来说太少了（工作负载受线程
	限制），在这种情况下，配置更多的 nfsd 线程可能会改善 NFS 工作负载的性能。

threads-woken
	统计空闲 nfsd 线程被唤醒以尝试从 NFS 传输接收数据的次数。

	该统计跟踪的是传入的面向网络的 NFS 工作正被快速处理的情况，这是好事。该计数器
	的理想变化率应接近但小于 packets-arrived 计数器的变化率。

threads-timedout
	统计 nfsd 线程触发空闲超时的次数，即一段时间内没有被唤醒去处理任何传入的
	网络数据包。

	该统计统计的是配置了多于 NFS 工作负载所能使用的 nfsd 线程的情况。这是一个
	线索，表明可以在不影响性能的情况下减少 nfsd 线程的数量。遗憾的是，它只是一个
	线索而非强指示，原因有几条：

  - 目前该计数器递增的速率相当慢；空闲超时为 60 分钟。除非 NFS 工作负载连续数小时
	   保持不变，否则该计数器不太可能提供仍然有用的信息。

  - 通常明智的策略是提供一些余量，即配置比当前所需稍多的 nfsd，以应对未来的负载
	   峰值。


注意，NFS 传输上的传入数据包将通过三种方式之一被处理。可以唤醒一个 nfsd 线程
（threads-woken 统计此情况），或者将该传输排入队列稍后处理（sockets-enqueued 统计此
情况），或者因为该传输当前正被某个 nfsd 线程使用而暂时推迟该数据包。最后这种情况
不太重要，因此没有显式
```

	packets-deferred = packets-arrived - ( sockets-enqueued + threads-woken )


```
