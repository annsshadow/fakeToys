## 使文件系统可导出


### 概述


所有文件系统操作都需要一个（或两个）dentry 作为起点。本地应用程序通过打开的文件描述符
或 cwd/root 对合适的 dentry 持有引用计数式的持有。然而，通过 NFS 等远程文件系统协议访问
文件系统的远程应用程序可能无法持有这样的引用，因此需要一种不同的方式来引用特定的 dentry。
由于这种替代形式的引用需要在重命名、截断以及服务器重启（以及其他情况，尽管这些往往是最
成问题的）期间保持稳定，所以没有像“文件名”这样简单的答案。

此处讨论的机制允许每个文件系统实现指定：如何为任意 dentry 生成一个不透明（对文件系统外部
而言）的字节串，以及如何为任意给定的不透明字节串找到合适的 dentry。这个字节串将被称为
“文件句柄片段（filehandle fragment）”，因为它对应于 NFS 文件句柄的一部分。

支持文件句柄片段与 dentry 之间映射的文件系统将被称为“可导出（exportable）”的。


### Dcache 问题


dcache 通常包含任意给定文件系统树的一个恰当前缀。这意味着如果任意文件系统对象在 dcache 中，
那么该文件系统对象的所有祖先也都在 dcache 中。由于常规访问是通过文件名进行的，因此这个前缀
是自然地创建并容易维护的（每个对象都维护对其父对象的引用计数）。

然而，当通过解释文件句柄片段将对象纳入 dcache 时，不会自动为该对象创建路径前缀。这导致 dcache
出现两个相关但不同的特性，这些特性在正常文件系统访问中并不需要。

1. dcache 有时必须包含不属于恰当前缀的对象，即未连接到根的对象。
2. dcache 必须准备好一个新发现的（通过 ->lookup）目录已经具有一个（未连接的）dentry，并且必须
   能够将该 dentry 就位（基于 ->lookup 中的父对象和名称）。目录尤其需要这一点，因为 dcache 的
   一个不变式是目录只有一个 dentry。

为了实现这些特性，dcache 具有：

a. 一个 dentry 标志 DCACHE_DISCONNECTED，它设置在任何可能不属于恰当前缀的 dentry 上。
   这在创建匿名 dentry 时设置，并在注意到某个 dentry 是恰当前缀中某个 dentry 的子对象时清除。
   如果对带有此标志的 dentry 的引用计数变为零，该 dentry 会被立即丢弃，而不是保留在 dcache 中。
   如果一个尚未在 dcache 中的 dentry 被文件句柄反复访问（正如 NFSD 可能做的那样），则每次访问
   都会分配一个新的 dentry，并在访问结束时丢弃。

   注意，这样的 dentry 可以获取子对象、名称、祖先等，而不会丢失 DCACHE_DISCONNECTED——该标志
   只在子树成功重新连接到根时才被清除。在此之前，此类子树中的 dentry 仅在存在引用期间保留；
   引用计数归零意味着立即逐出，这与未散列（unhashed）的 dentry 相同。这保证了我们在 umount 时
   无需去搜寻它们。

b. 用于创建次级根的基元——d_obtain_root(inode)。这些**不**带有 DCACHE_DISCONNECTED。它们被
   放在每超级块列表（->s_roots）上，以便在 umount 时可以被定位以用于逐出。

c. 用于分配匿名 dentry、以及在查找时帮助挂载松散目录 dentry 的辅助例程。它们是：

    d_obtain_alias(inode) 将为给定的 inode 返回一个 dentry。
      如果该 inode 已经有一个 dentry，则返回其中之一。

      如果没有，则分配并挂载一个新的匿名（IS_ROOT 且 DCACHE_DISCONNECTED）dentry。

      对于目录，会注意确保永远只能挂载一个 dentry。

    d_splice_alias(inode, dentry) 将把一个新 dentry 引入树中；
      在适当情况下，使用传入的 dentry，或给定 inode 的既有别名（例如由 d_obtain_alias 创建的
      匿名 dentry）。当使用传入的 dentry 时返回 NULL，遵循 ->lookup 的调用约定。

### 文件系统问题


要使一个文件系统可导出，它必须：

   1. 提供如下所述的文件句柄片段例程。
   2. 确保在 ->lookup 为给定父对象和名称找到一个 inode 时，使用 d_splice_alias 而不是 d_add。

```

		d_add(dentry, inode), NULL

      Similarly, d_splice_alias(ERR_PTR(err), dentry) = ERR_PTR(err)

      Typically the ->lookup routine will simply end with a::

		return d_splice_alias(inode, dentry);
	}

```

文件系统实现通过设置在 struct super_block 中的 s_export_op 字段来声明该文件系统的实例
是可导出的。该字段必须指向一个 struct export_operations，它具有以下成员：

   :identifiers: struct export_operations

一个文件句柄片段由一个或多个 4 字节字组成的数组，加上一个单字节的“类型（type）”。
decode_fh 例程不应依赖传递给它的所述大小。该大小可能大于 encode_fh 生成的原始文件句柄，
这种情况下它会被 nul 填充。相反，encode_fh 例程应当选择一个“类型”，向 decode_fh 指示
文件句柄有多少是有效的，以及应当如何解释它。

### 导出操作标志

除了操作向量指针外，struct export_operations 还包含一个“flags”字段，允许文件系统告知 nfsd
它可能在处理该文件系统时希望以不同方式做事。定义了以下标志：

  EXPORT_OP_NOWCC - 在此文件系统上禁用 NFSv3 WCC 属性
    RFC 1813 建议服务器在每次操作后始终向客户端发送弱缓存一致性（WCC）数据。服务器应当原子地
    收集关于 inode 的属性、对其执行操作、然后再收集之后的属性。这允许客户端在某些情况下跳过
    发出 GETATTR，但意味着服务器几乎所有的 RPC 都在调用 vfs_getattr。在某些文件系统（尤其是
    集群或网络化的文件系统）上，这代价高昂且原子性难以保证。此标志告知 nfsd，在对这个文件系统
    执行操作时，应在 NFSv3 应答中跳过向客户端提供 WCC 属性。请考虑在那些具有代价高昂的
    ->getattr inode 操作，或操作前后属性收集之间的原子性无法保证的文件系统上启用此标志。

  EXPORT_OP_NOSUBTREECHK - 禁止在此文件系统上进行子树检查
    许多 NFS 操作处理文件句柄，服务器随后必须审查它们以确保它们位于导出的树内部。当导出的是
    整个文件系统时，这很简单，nfsd 只需确保文件句柄位于该文件系统上。然而，当只导出了文件系统
    的一部分时，nfsd 必须遍历该 inode 的祖先以确保它在导出的子树内。这是一个代价高昂的操作，
    并非所有文件系统都能正确支持。此标志使该文件系统免于子树检查，并在 exportfs 试图在其上启用
    子树检查时返回一个错误。

  EXPORT_OP_CLOSE_BEFORE_UNLINK - 在 unlink 之前始终关闭缓存的文件
    在某些可导出的文件系统（如 NFS）上，unlink 一个仍然打开的文件会带来相当多额外工作。例如，
    NFS 客户端会执行一个“sillyrename”以确保该文件在其仍打开期间一直存在。在重新导出时，该打开的
    文件由 nfsd 持有，因此我们通常会执行一个 sillyrename，然后在实际链接计数归零时立即删除该
    sillyrenamed 文件。有时此删除可能与其他操作（例如对父目录的 rmdir）发生竞争。此标志使 nfsd
    在调用 vfs 执行 unlink 或会替换现有文件的 rename 之前，先关闭该 inode 的任何打开文件。

  EXPORT_OP_REMOTE_FS - 此文件系统的后备存储是远程的
    PF_LOCAL_THROTTLE 是为回环 NFSD 而存在的，其中一个线程需要写入一个 bdi（最终的 bdi）以释放
    排队写入另一个 bdi（客户端 bdi）的写入。此类线程获得一份私有的脏页平衡，使得客户端 bdi 的脏页
    不会影响写入最终 bdi 的守护进程。对于持久存储不是本地的文件系统（如导出的 NFS 文件系统），此
    约束会产生负面后果。EXPORT_OP_REMOTE_FS 允许一个导出禁用回写节流（writeback throttling）。

  EXPORT_OP_NOATOMIC_ATTR - 文件系统不原子地更新属性
    EXPORT_OP_NOATOMIC_ATTR 指示被导出的文件系统无法提供 NFSv4 的 change_info4 中“atomic”布尔值
    所需的语义。该布尔值向客户端指示返回的操作前后变更属性，相对于所请求的元数据操作（UNLINK、
    OPEN/CREATE、MKDIR 等）是否是原子获取的。

  EXPORT_OP_FLUSH_ON_CLOSE - 文件系统在 close(2) 时刷出文件数据
    在大多数文件系统上，inode 在文件关闭后仍可能处于回写状态。NFSD 依赖客户端活动或本地刷出线程
    来处理回写。某些文件系统（如 NFS）在最后一次关闭时刷出某个 inode 的所有脏数据。以这种方式行为的
    导出应设置 EXPORT_OP_FLUSH_ON_CLOSE，以便 NFSD 知道在关闭此类文件时跳过等待回写。

### 带签名的文件句柄


为了防止文件句柄猜测攻击，Linux NFS 服务器可以被配置为使用消息认证码（MAC）对文件句柄进行签名。

标准的 NFS 文件句柄往往是可预测的。如果攻击者能够猜测出一个他们无权通过目录遍历访问的文件的
有效文件句柄，他们就可能绕过基于路径的权限（尽管他们仍然受 inode 级权限的约束）。

带签名的文件句柄通过在将文件句柄发送到客户端之前附加一个 MAC 来防止这种情况。在从客户端收到
文件句柄后，服务器使用其内部密钥重新计算 MAC，并将其与所提供的 MAC 进行验证。如果签名不匹配，
服务器将该文件句柄视为无效（返回 NFS[^34^]ERR_STALE）。

注意，对文件句柄签名提供完整性和真实性，但不提供机密性。文件句柄的内容对客户端仍然可见；它们
只是无法被伪造或修改。

#### 配置


要启用带签名的文件句柄，管理员必须向内核提供一个签名密钥，并启用“sign_fh”导出选项。

1. 提供密钥
   签名密钥通过 nfsd netlink 接口管理。该密钥按网络命名空间（per-network-namespace）划分，
   且必须在任何使用“sign_fh”的导出生效之前设置。

2. 导出选项
   该特性在 /etc/exports 中按导出进行控制：

   sign_fh
     为此导出下生成的所有文件句柄启用签名。

   no_sign_fh
     （默认）禁用签名。

#### 密钥管理与轮换


此机制的安全性完全依赖于签名密钥的保密性。

初始设置：
  密钥应使用高质量的随机源生成，并在启动过程的早期或 nfs-server 启动序列期间加载。

更改密钥：
  如果在客户端持有活动挂载时更改密钥，这些客户端持有的既有文件句柄将变为无效，导致客户端侧
  出现“Stale file handle（陈旧文件句柄）”错误。

安全轮换：
  目前，没有“优雅”密钥轮换（维护多个有效密钥）的机制。更改密钥是一个原子操作，会立即使所有
  先前的签名失效。

#### 过渡中的导出


在从活动导出中添加或移除“sign_fh”标志时，应预期以下行为：

+-------------------+---------------------------------------------------+
| 变更              | 对既有客户端的结果                                |
+===================+===================================================+
| 添加 sign_fh      | 持有未签名文件句柄的客户端会发现它们被拒绝，因为   |
|                   | 服务器现在期望有一个签名。                        |
+-------------------+---------------------------------------------------+
| 移除 sign_fh      | 持有已签名文件句柄的客户端会发现它们被拒绝，因为   |
|                   | 服务器现在期望文件句柄以其传统边界结束，而不带     |
|                   | MAC。                                             |
+-------------------+---------------------------------------------------+

由于文件句柄经常被客户端持久缓存，添加或移除此选项通常应在涉及 NFS 客户端卸载/重新挂载的
计划维护窗口期间进行。
