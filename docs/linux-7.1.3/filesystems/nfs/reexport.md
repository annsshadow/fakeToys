## 重新导出 NFS 文件系统


### 概述


可以通过 NFS 重新导出一NFS 文件系统。然而，该特性带有若干限制。在尝试
之前，我们建议做一些仔细的研究，以确定它是否能满足你的用途
下面讨论当前已知的种种限制
### 需"fsid="，crossmnt 失效


任何NFS 文件系统的重新导出我们都要求使用 "fsid=" 导出选项。你可以使用
"uuidgen -r" 生成一个唯一的参数
"crossmnt" 导出不会传播 "fsid="，因此它将不允许深入导出更多 nfs 文件系统如果你希望导出挂载在被导出文件系统之下的 nfs 文件系统，你需要显式地导出它们为每个分配其各自唯一"fsid=" 选项
### 重启恢复


NFS 协议正常的重启恢复机制在重新导出服务器重启的情况下并不适用，因为源服务并未重启，因此它并不处于 grace（宽限）状态。由于源服务器不处于 grace 状态，无法提供任何保证，保证在锁丢失到任何尝试恢复它们之间文件没有被更改。这一同样适用于委托（delegation）以及任何相关联的锁。客户端不允许从重新导出服务获取文件锁或委托，任何此类尝试都会以“操作不支持”失败
### 文件句柄限制


如果原始服务器对给定对象使用 X 字节的文件句柄，则重新导出服务器对该重新导出
对象的文件句柄将X+22 字节，并向上取整到最接近4 字节倍数
结果必须能放RFC 规定的文件句柄大小限制中
+-------+-----------+
| NFSv2 |  32 bytes |
+-------+-----------+
| NFSv3 |  64 bytes |
+-------+-----------+
| NFSv4 | 128 bytes |
+-------+-----------+

因此，举例来说，你只有在原始服务器给你的文件句柄能放10 字节以内时，才能
通过 NFSv2 重新导出文件系统——而这不太可能
一般而言，在没有询问服务器厂商的情况下，无法知道 NFS 服务器给出的最大文句柄大小
不过下表给出几个示例。第一列是 Linux 服务器导出给定文件系统时文件句柄典型长度，第二列是该 nfs 导出被另一Linux 主机重新导出后的长度
+--------+-------------------+----------------+
|        | filehandle length | after reexport |
+========+===================+================+
| ext4:  | 28 bytes          | 52 bytes       |
+--------+-------------------+----------------+
| xfs:   | 32 bytes          | 56 bytes       |
+--------+-------------------+----------------+
| btrfs: | 40 bytes          | 64 bytes       |
+--------+-------------------+----------------+

因此在重新导出之后，它们都能放入 NFSv3 NFSv4 的文件句柄，但没有一个可通过 NFSv2 重新导出
不过，Linux 服务器的文件句柄比这要复杂一些；例如
        - （非默认的）"subtreecheck" 导出选项通常会在文件句柄中再需4 8 字节        - 如果你导出文件系统的子目录（而不是导出文件系统根），那通常也会
          增加 4 8 字节        - 如果你通过 NFSv2 导出，knfsd 通常使用一个更短的文件系统标识符，
          从而节8 字节        - 一个导出的根目录使用的文件句柄更短
如你所见，128 字节NFSv4 文件句柄足够大，以至于你不太可能在使NFSv4 重新
导出任何来自 Linux 服务器的文件系统时遇到麻烦。一般而言，如果原始服务器支持 NFSv3，你**可能**没问题。通过 NFSv3 重新导出可能会更棘手，而通过 NFSv2
重新导出恐怕永远无法工作
关于 Linux 文件句柄结构的更多细节，最好的参考资料是源代码及其注释；特别参见
        - include/linux/exportfs.h:enum fid_type
        - include/uapi/linux/nfsd/nfsfh.h:struct nfs_fhbase_new
        - fs/nfsd/nfsfh.c:set_version_and_fsid_type
        - fs/nfs/export.c:nfs_encode_fh

### 忽略 Open DENY 

NFSv4 起，NFS 支持取自 Windows ALLOW DENY 位，例如，它们允许你禁止其它读打开或写打开的模式打开一个文件。Linux 客户端不使用它们，而服务器
的支持也一直以来都不完整：它们仅针对其NFS 用户强制执行，而不针对本地访问
被导出文件系统的进程。重新导出服务器也不会把它们传递给原始服务器，因此它们
不会在不同重新导出服务器的客户端之间被强制执行
