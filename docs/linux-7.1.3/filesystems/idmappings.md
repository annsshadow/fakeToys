
## Idmappings（id 映射

大多数文件系统开发者都接触id 映射（idmapping）。当从磁盘读取或写入属主
信息、向用户空间报告属主，或进行权限检查时都会用到它们。本文档面向想要了解
id 映射如何工作的文件系统开发者
### Formal notes（形式化说明

id 映射本质上就是把一id 范围翻译成另一段（或同一段）id 范围。被广泛采用id 映射记法约定```

 u:k:r

```
`u` 表示上层 id 映射`U` 的第一个元素，`k` 表示下层 id 映射`K` 的第一元素。`r` 参数表示 id 映射的范围，即有多少id 被映射。从今往后，我们会始`u` `k` 作为 id 的前缀，以明确我们说的是上层还是下id 映射集中id
```

 u22:k10000:r3

```
```

 u22 -> k10000
 u23 -> k10001
 u24 -> k10002

```
从数学角度看，`U` `K` 是良序集（well-ordered set），id 映射是从 `U` `K` 的一个保序同构（order isomorphism）。所`U` `K` 是保序同构的。事实上`U` `K` 始终是一个给定系统上所有可id 集合的良序子集
简要地从数学角度审视，有助于我们凸显出一些性质，从而更容易理解如何在不同的
id 映射之间进行转换。对```

 k10000 -> u22
 k10001 -> u23
 k10002 -> u24

```
鉴于我们处理的是保序同构，加上我们处理的是子集，我们可以id 映射互相嵌入即我们可以合理地在不同的 id 映射之间进行转换。例如，假设我们```

 1. u0:k10000:r10000
 2. u0:k20000:r10000
 3. u0:k30000:r10000

```
以及由第一id 映射通过把上id 映射集中`u1000` 向下映射到下id 映射中的 `k11000` 所生成id `k11000`
由于我们处理的是保序同构的子集，`k11000` 对应于第二个或第三个 id 映射中的
什id 是有意义的。直接可用的算法是先应用第一id 映射的逆，`k11000` 向上
映射`u1000`；之后，我们可以用第二个或第三个 id 映射把它向下映射。第二个 id
映射会把 `u1000` 向下映射`k21000`。第三个 id 映射会把 `u1000` 向下映射`k31000`
```

 1. u0:k10000:r10000
 2. u0:k20000:r200
 3. u0:k30000:r300

```
转换就会失败，因为这些集合不再在第一id 映射的完整范围上保序同构（但它们第二id 映射的完整范围上仍是保序同构的）。第二个和第三个 id 映射的上id
映射`U` 中都不包`u1000`。这等价于没有某id 被映射。我们可以直接说
`u1000` 在第二个和第三个 id 映射中是未映射（unmapped）的。内核会向用户空间把
未映射的 id 报告overflowuid `(uid_t)-1` overflowgid `(gid_t)-1`
计算某个给定 id 映射到哪里去的算法相当简单。首先，我们需要验证该范围能够容纳
我们的目id。为简单起见我们跳过这一步。之后，如果我们想知`id` 映射到哪里，
可以做简单的计算
```

   u:k:r
   id - u + k = n

```
```

   u:k:r
   id - k + u = n

```
"从左到右"也可以说向下"（down），从右到左"也可以说向上"（up）。显向下映射和向上映射互为逆操作
为了验证上面的简单公式是否可行，考虑下面两个 id 映射
```

 1. u0:k20000:r10000
 2. u500:k30000:r10000

```
假设我们给定第一id 映射的下id 映射集中`k21000`。我们想知道这个 id 第一id 映射的上id 映射集中是从哪个 id 映射来的
```

 id     - k      + u  = n
 k21000 - k20000 + u0 = u1000

```
现在假设我们给定第二id 映射的上id 映射集中id `u1100`，我们想知道这个
id 向下映射到第二个 id 映射的下id 映射集中的哪id。这意味着我们在第二个 id
映射中进行向下映```

 id    - u    + k      = n
 u1100 - u500 + k30000 = k30600

```
### General notes（一般性说明）


在内核语境中，一id 映射可以被理解为映射一段范```

 userspace-id:kernel-id:range

```
用户空间 id 始终是类型为 `uid_t` `gid_t` id 映射的上id 映射集中的一元素，而内id 始终是类型为 `kuid_t` `kgid_t` id 映射的下id 映射集中一个元素。从今往后，"用户空间 id"将用于指代众所周知`uid_t` `gid_t` 类型内核 id"将用于指`kuid_t` `kgid_t`
内核主要关注内核 id。它们在进行权限检查时使用，并存储inode `i_uid` `i_gid` 字段中。另一方面，用户空id 是内核向用户空间报告id，或由用户空传给内核id，或是从磁盘写入或读取的原始设备 id
注意我们只关心内核所存储id 映射，而不关心用户空间会如何指定它们
本文档剩余部分中，我们会给所有用户空id 加上 `u` 前缀，给所有内id 加上
`k` 前缀。id 映射的范围会加上 `r` 前缀。所以一id 映射会被写成
`u0:k10000:r10000`銆?
例如，在这个 id 映射中，id `u1000` 是一个以 `u0` 开头的、位于上id 映射集或
"用户空间 id 映射中的 id。它被映射到 `k11000`，后者是一个以 `k10000` 开的、位于下id 映射集或"内核 id 映射中的内核 id
内核 id 总是由某id 映射创建。这样的 id 映射与用户命名空间（user namespace相关联。由于我们主要关id 映射如何工作，我们不会去关心 id 映射是如何创建的也不会关心它们在文件系统上下文之外是如何使用的。这部分内容最好留给用户命名空的讲解
初始用户命名空间（initial user namespace）是特殊的。它始终拥有一个如下的 id 映射
```

 u0:k0:r4294967295

```
这是一个覆盖该系统上所有可id 范围的恒等（identity）id 映射
```

 u0:k10000:r10000

```
当某个进程创建或想要更改文件的属主，或者当文件系统从磁盘读取文件的属主时，用户
空间 id 会立即按照与相关用户命名空间相关联的 id 映射被翻译成内核 id
例如，考虑一个由文件系统`u1000` 为属主存储在磁盘上的文件
- 如果一个文件系统被挂载在初始用户命名空间中（大多数文件系统都是如此），那么  使用初始 id 映射。正如我们所见，这只是一个恒id 映射。这意味着从磁盘读出的
  id `u1000` 会被映射id `k1000`。所inode `i_uid` `i_gid` 字段  包含 `k1000`
- 如果一个文件系统被`u0:k10000:r10000` id 映射挂载，那么从磁盘读出  `u1000` 会被映射`k11000`。所inode `i_uid` `i_gid` 会包`k11000`
### Translation algorithms（转换算法）


我们已经简要看到，在不同的 id 映射之间进行转换是可能的。现在我们来更仔细地看看
这是如何工作的
#### Crossmapping（交叉映射）


这个转换算法在内核中很多地方都被用到。例如，在通过 `stat()` 系统调用族向用户空间
报告文件的属主时就会用到它
如果我们从某id 映射得到 `k11000`，我们可以在另一id 映射中把这个 id 向上
映射。为了使其能够工作，两个 id 映射都需要在它们的内id 映射集中包含相同的内id。例如，考虑
```

 1. u0:k10000:r10000
 2. u20000:k10000:r10000

```
并且我们在第一id 映射中把 `u1000` 向下映射`k11000`。然后我们可以用第二id 映射`k11000` 翻译成一个用户空id
```

 /* 在第二个 id 映射中把内核 id 向上映射成用户空id*/
 from_kuid(u20000:k10000:r10000, k11000) = u21000

```
注意，我们可以通过取逆操作回到第一id 映射中的内核 id
```

 /* 在第二个 id 映射中把用户空间 id 向下映射成内id*/
 make_kuid(u20000:k10000:r10000, u21000) = k11000

 /* 在第一id 映射中把内核 id 向上映射成用户空id*/
 from_kuid(u0:k10000:r10000, k11000) = u1000

```
这个算法让我们能够回答这样一个问题：在某个给id 映射中，某个给定内核 id 对应什么用户空id。为了能够回答这个问题，两个 id 映射都需要在各自的内id 映射集中
包含相同的内id
例如，当内核从磁盘读取一个原始的用户空间 id 时，它会按照与文件系统相关联id
映射把它向下映射成内id。假设该文件系统是以 `u0:k20000:r10000` id 映射挂载
的，并且它从磁盘读到一个由 `u1000` 拥有的文件。这意味着 `u1000` 将被映射`k21000`，这就是会被存储inode `i_uid` `i_gid` 字段中的值
当某个处于用户空间的调用者调`stat()` 或相关的函数来获取关于该文件的属主信息时内核不能简单地按照文件系统id 映射把这id 向上映射回去，因为如果在调用者使用了
不同 id 映射的情况下这样做，会得到错误的属主
于是内核会在调用者的 id 映射中把这个 id 向上映射回去。假设调用者拥有一个有点非常规
id 映射 `u3000:k20000:r10000`，那`k21000` 会向上映射回 `u4000`。因此用会看到该文件`u4000` 拥有
#### Remapping（重映射

可以通过两个 id 映射的用户空id 映射集，把一个内id 从一id 映射转换到另一id 映射。这等价于对一个内id 进行重映射
```

 1. u0:k10000:r10000
 2. u0:k20000:r10000

```
并且我们给定了第一id 映射中的 `k11000`。为了把这个第一id 映射中的内核 id
翻译成第二个 id 映射中的内核 id，我们需要执行两步：

```

    /* 在第一id 映射中把内核 id 向上映射成用户空id*/
    from_kuid(u0:k10000:r10000, k11000) = u1000

```
```

    /* 在第二个 id 映射中把用户空间 id 向下映射成内id*/
    make_kuid(u0:k20000:r10000, u1000) = k21000

```
如你所见，我们在两id 映射中都使用了用户空id 映射集，来把一id 映射中的
内核 id 翻译成另一id 映射中的内核 id
这让我们能够回答这样一个问题：为了在另一id 映射中得到相同的用户空间 id，我们需使用什么内id。为了能够回答这个问题，两个 id 映射都需要在各自的用户空id 映射中包含相同的用户空间 id
注意，我们可以通过取逆算法轻松地回到第一id 映射中的内核 id
```

    /* 在第二个 id 映射中把内核 id 向上映射成用户空id*/
    from_kuid(u0:k20000:r10000, k21000) = u1000

```
```

    /* 在第一id 映射中把用户空间 id 向下映射成内id*/
    make_kuid(u0:k10000:r10000, u1000) = k11000

```
看待这种转换的另一种方式，是如果这两个 id 映射都有相关的用户空id 被映射，则把视为对其中一id 映射取逆并对另一id 映射应用。这在处id 映射挂载（idmapped
mount）时会派上用场
#### Invalid translations（无效转换）


永远不能把一id 映射的内id 映射集中的某id，当作另一个或同一id 映射用户空间 id 映射集中id 来使用。虽然内id 映射集始终表示内id 空间中的一id 映射集，但用户空```

 /* 在第一id 映射中把用户空间 id 向下映射成内id*/
 make_kuid(u0:k10000:r10000, u1000) = k11000

 /* 无效：在第二id 映射中把内核 id 向下映射成内id*/
 make_kuid(u10000:k20000:r10000, k110000) = k21000
                                 ~~~~~~~

```
```

 /* 在第一id 映射中把内核 id 向上映射成用户空id*/
 from_kuid(u0:k10000:r10000, k11000) = u1000

 /* 无效：在第二id 映射中把用户空间 id 向上映射成用户空id*/
 from_kuid(u20000:k0:r10000, u1000) = k21000
                             ~~~~~

```
由于用户空间 id 的类型是 `uid_t` `gid_t`，而内id 的类型是 `kuid_t` `kgid_t`，当它们被混用时编译器会报错。所以上述两个例子会导致编译失败
### Idmappings when creating filesystem objects（创建文件系统对象时id 映射

id 向下映射或向上映射这两个概念，体现在文件系统开发者相当熟悉的两个内核函数中，
我们在前```

 /* 把用户空id 向下映射成内id*/
 make_kuid(idmapping, uid)

 /* 把内id 向上映射成用户空id*/
 from_kuid(idmapping, kuid)

```
我们将简要地看一id 映射是如何参与到文件系统对象的创建中的。为简单起见，我们
只看 VFS 已经完成了路径查找、正要调用文件系统自身时的情形。所以我们关心的是当
例如 `vfs_mkdir()` 被调用时发生了什么。我们还会假设我们正在其中创建文件系统对的目录对所有人都是可读写的
当创建一个文件系统对象时，调用者会查看调用者的文件系统 id。它们只是常规的
`uid_t` `gid_t` 用户空间 id，但只在确定文件属主时使用，这正是它们被称为
"文件系统 id"的原因。它们通常与调用者的 uid gid 相同，但也可能不同。我们暂假设它们始终相同，以免陷入过多细节
当调用者进入内核时会发生两件事
1. 在调用者的 id 映射中，把调用者的用户空间 id 向下映射成内id   （准确地说，内核只会直接查看保存在当前任务的凭证（credentials）中的内id，但
   为了便于理解，我们假装这个转换是即时发生的。）
2. 验证调用者的内核 id 能够被向上映射到文件系统 id 映射中的用户空间 id
第二步很重要，因为常规文件系统最终在写入磁盘时需要把内核 id 向上映射回用户空id所以通过第二步，内核保证了一个有效的用户空间 id 可以被写入磁盘。如果不能，内核拒绝这个创建请求，以免哪怕只是几乎不可能导致文件系统损坏
细心的读者会意识到，这其实就是我们在前面小节中提到过的交叉映射算法的一个变体。首先，
内核按照调用者的 id 映射把调用者的用户空间 id 向下映射成内id，然后按照文件系统的
id 映射把这个内id 向上映射
从实现的角度值得提一id 映射是如何表示的。所有的 id 映射都取自对应的用户命名空间
    - 调用者的 id 映射（通常取自 `current_user_ns()`    - 文件系统id 映射（`sb->s_user_ns`    - 挂载id 映射（`mnt_idmap(vfsmnt)`
让我们看一些只有调用文件系统 id 映射、但没有挂载 id 映射的例子。这会暴露出我们
可能遇到的一些问题。之后我们会重新审视/重新考虑这些例子，这次使用挂id 映射，看它们如何解决我们之前观察到的问题
#### Example 1（例 1

```

 caller id:            u1000
 caller idmapping:     u0:k0:r4294967295
 filesystem idmapping: u0:k0:r4294967295

```
调用者和文件系统都使用恒id 映射
```

    make_kuid(u0:k0:r4294967295, u1000) = k1000

```
2. 验证调用者的内核 id 能够被映射到文件系统 id 映射中的用户空间 id
   对于这第二步，内核会调用函数 `fsuidgid_has_mapping()`，它最终归结起来就是调```

    from_kuid(u0:k0:r4294967295, k1000) = u1000

```
在这个例子中两个 id 映射相同，所以没什么值得激动的。最终落到磁盘上的用户空id 会是
`u1000`銆。
#### Example 2（例 2

```

 caller id:            u1000
 caller idmapping:     u0:k10000:r10000
 filesystem idmapping: u0:k20000:r10000

```
1. 在调用者的 id 映射中，把调用者的用户空间 id 向下映射成内id
```

    make_kuid(u0:k10000:r10000, u1000) = k11000

```
2. 验证调用者的内核 id 能够被向上映射到文件系统 id 映射中的用户空间 id
```

    from_kuid(u0:k20000:r10000, k11000) = u-1

```
马上就能看出，虽然调用者的用户空间 id 能够成功地向下映射到调用id 映射中的内核 id但这些内id 却无法按照文件系统的 id 映射向上映射。所以内核会拒绝这个创建请求
注意，虽然这个例子不太常见（因为大多数文件系统不能以非初id 映射挂载），但正如我在接下来的例子中看到的，这是一个普遍存在的问题
#### Example 3（例 3

```

 caller id:            u1000
 caller idmapping:     u0:k10000:r10000
 filesystem idmapping: u0:k0:r4294967295

```
1. 在调用者的 id 映射中，把调用者的用户空间 id 向下映射成内id
```

    make_kuid(u0:k10000:r10000, u1000) = k11000

```
2. 验证调用者的内核 id 是否能够被向上映射到文件系统 id 映射中的用户空间 id
```

    from_kuid(u0:k0:r4294967295, k11000) = u11000

```
我们可以看到转换总是成功的。文件系统最终写入磁盘的用户空间 id，将始终等于在调用id 映射中创建的内核 id 的值。这主要有两方面后果
其一，我们不能允许调用者最终以另一个用户空id 写入磁盘。只有当我们用调用者的另一id 映射来挂载整个文件系统时才能这样做。但那种方案仅限于少数几个文件系统，不够灵活。而这恰恰是容器化工作负载中一个相当重要的使用场景
其二，调用者通常将无法创建任何文件，也无法访问具有更严格权限的目录，因为文件系统内核 id 中没有一个能够向上映射到调用id 映射中的有效用户空间 id
```

    make_kuid(u0:k0:r4294967295, u1000) = k1000

```
```

    from_kuid(u0:k10000:r10000, k1000) = u-1

```
#### Example 4（例 4

```

 file id:              u1000
 caller idmapping:     u0:k10000:r10000
 filesystem idmapping: u0:k0:r4294967295

```
为了向用户空间报告属主，内核使用了前面小节引入的交叉映射算法
1. 在文件系统的 id 映射中，把磁盘上的用户空id 向下映射成内id
```

    make_kuid(u0:k0:r4294967295, u1000) = k1000

```
```

    from_kuid(u0:k10000:r10000, k1000) = u-1

```
在这种情况下交叉映射算法失败，因为文件系id 映射中的内核 id 无法被向上映射到调用id 映射中的用户空间 id。因此，内核会把该文件的属主报告overflowid

目前做不到

恶意的文件系统镜像

#### Filesystem types vs idmapped mount types（文件系统类vs id 映射挂载类型

随着 id 映射挂载的引入，我们需要区分像 inode 这样VFS 对象的文件系统属主和挂载属主从文件系统角度看，一inode 的属主可能不同于id 映射挂载角度看时的属主。这种根本性的
概念区分几乎总应该在代码中清晰地表达出来。所以，为了区分 id 映射挂载属主与文件系统属主，
引入了独立的类型
如果一uid gid 是用文件系统或调用者的 id 映射生成的，那么我们会使`kuid_t` `kgid_t` 类型。然而，如果一uid gid 是用挂载 id 映射生成的，那么我们会使用专门的
`vfsuid_t` `vfsgid_t` 类型
所有生成或uid gid 作为参数VFS 辅助函数都使`vfsuid_t` `vfsgid_t` 类型我们因而能够依赖编译器来捕获那些源于把文件系统VFS uid gid 混用的错误
`vfsuid_t` `vfsgid_t` 类型经常`kuid_t` `kgid_t` 类型互相映射，就如同
`kuid_t` `kgid_t` 类型被映射那```

 uid_t <--> kuid_t <--> vfsuid_t
 gid_t <--> kgid_t <--> vfsgid_t

```
每当我们基于 `vfsuid_t` `vfsgid_t` 类型报告属主（例如在 `stat()` 期间），或基`vfsuid_t` `vfsgid_t` 类型把属主信息存储到一个共享的 VFS 对象中（例如`chown()`
期间），我们可以使用 `vfsuid_into_kuid()` `vfsgid_into_kgid()` 辅助函数
为了说明这个辅助函数目前为何存在，考虑当我们从一id 映射挂载更改一inode 的属主时会发什么。在基于挂载 id 映射生成了一`vfsuid_t` `vfsgid_t` 之后，我们稍后会提交这个
`vfsuid_t` `vfsgid_t` 使之成为新的、文件系统范围内的属主。因此，我们是在把这`vfsuid_t` `vfsgid_t` 变成一个全局`kuid_t` `kgid_t`。而这可以通过使用
`vfsuid_into_kuid()` `vfsgid_into_kgid()` 来完成
注意，每当一个共享的 VFS 对象（例如，一个被缓存`struct inode` 或一个被缓存`struct posix_acl`）存储属主信息时，必须使用文件系统或"全局"`kuid_t` `kgid_t`通过 `vfsuid_t` `vfsgid_t` 表达的属主是特定于某id 映射挂载的
我们已经提到，`vfsuid_t` `vfsgid_t` 类型是基于挂id 映射生成的，`kuid_t` `kgid_t` 类型是基于文件系id 映射生成的。为了防止滥用文件系id 映射去生`vfsuid_t` `vfsgid_t` 类型，或滥用挂载 id 映射去生`kuid_t` `kgid_t` 类型文件系统 id 映射和挂id 映射也是不同的类型
所有在 `vfsuid_t` `vfsgid_t` 类型之间映射的辅助函数，都需要传入一个类型为
`struct mnt_idmap` 的挂id 映射。传入一个文件系统或调用者的 id 映射会导致编译错误
与我们在这篇文档中给所有用户空id `u` 前缀、给所有内id `k` 前缀类似，我们会
给所VFS id `v` 前缀。所以一个挂id 映射会被写成：`u0:v10000:r10000`
#### Remapping helpers（重映射辅助函数

新增了一些在 id 映射之间相互转换id 映射函数。它们用到了我们在前面引入的重映射算法我们要看的是
- `i_uid_into_vfsuid()` 鍜?`i_gid_into_vfsgid()`

   make_kuid(filesystem, uid) = kuid

```
- `vfsuid_into_kuid()` 鍜?`vfsgid_into_kgid()`

   每当

注意这两个函数互为逆操作。考虑下面```

 caller idmapping:     u0:k10000:r10000
 filesystem idmapping: u0:k20000:r10000
 mount idmapping:      u0:v10000:r10000

```
假设从磁盘读到一个由 `u1000` 拥有的文件。文件系统按照它id 映射把这id 映射`k21000`。这就是被存储在 inode `i_uid` `i_gid` 字段中的值
当调用者通过 `stat()` 查询该文件的属主时，内核通常只会简单地使用交叉映射算法，把文件
系统的内id 向上映射到调用id 映射中的用户空间 id
但当调用者是在一id 映射挂载上访问该文件时，内核会先调用 `i_uid_into_vfsuid()`从而把文件系统的内id
```

 i_uid_into_vfsuid(k21000):
   /* 把文件系统的内核 id 向上映射成用户空id*/
   from_kuid(u0:k20000:r10000, k21000) = u1000

   /* 在挂载的 id 映射中把文件系统的用户空id 向下映射VFS id*/
   make_kuid(u0:v10000:r10000, u1000) = v11000

```
最后，当内核向调用者报告属主时，它会把挂载 id 映射中的 VFS id 变成调用id 映射中的
用户空间 id
```

  k11000 = vfsuid_into_kuid(v11000)
  from_kuid(u0:k10000:r10000, k11000) = u1000

```
我们可以通过验证在创建一个新文件时会发生什么来测试这个算法是否真的可行。假设用户正在用
`u1000` 创建一个文件
内核把这id 映射到调用id 映射中的 `k11000`。通常内核现在会应用交叉映射，验证
`k11000` 是否能被映射到文件系id 映射中的用户空间 id。由`k11000` 无法直接文件系统 id 映射中向上映射，这个创建请求失败了
但当调用者是在一id 映射挂载上访问该文件时，内核会先调用 `mapped_fs*id()`，从而把
调用者的内核 id 翻译```

    /* 在挂载的 id 映射中把调用者的内核 id 向上映射成用户空id*/
    from_kuid(u0:k10000:r10000, k11000) = u1000

    /* 在文件系统的 id 映射中把挂载的用户空id 向下映射成内id*/
    make_kuid(u0:v20000:r10000, u1000) = v21000

```
当最终写入磁盘时，内核会`v21000` 向上映射```

   k21000 = vfsuid_into_kuid(v21000)
   from_kuid(u0:k20000:r10000, k21000) = u1000

```
如我们所见，我们得到了一个可逆的、因而能够保留信息的算法。在 id 映射挂载上由 `u1000`
创建的文件，也会被报告为`u1000` 拥有，反之亦然

我们在上面已经看到，当调用者、文件系统或两者使用非初始 id 映射时，id 映射挂载如何被用id 映射之间进行转换。当调用者使用非初始 id 映射时有大量的使用场景。这主要发生在容器化
