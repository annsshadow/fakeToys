
## ROMFS - ROM 文件系统


这是一个相当简单、只读的文件系统，主要用于安装盘的初RAM 磁盘。它因需要在启动时链接模块而产生。使用这个文件系统，你能获得非常相似的特性，甚至可以在不占用办公室地下室路由器功能所用宝贵内存的情况下，拥有一个很小的内核与文件系统
作为对比，较老的 minix xiafs（后者现已废弃）文件系统，编译为模块时需要超20000 字节，romfs 不到一页，4000 字节（假设为 i586 代码）。在相同条件下，msdos 文件系统大约需30K（且不支持设备节点或符号链接），而带nfsroot nfs 模块约为 57K。此外，作为一个略有不公平的对比，一张实际的救援盘使ext2 时占用了 3202 个块，而使romfs 时只需 3079 个块
要创建这样的文件系统，你需要一个名genromfs 的用户程序。它可在 http://romfs.sourceforge.net/ 获取
顾名思义，romfs 也可用于（以节省空间的方式）各种只读介质，例如（E）PROM 磁盘——如果有人有这个动力的话.. :)

不过，romfs 的主要用途是拥有一个非常小的内核，其中只链接进这个文件系统，之后便可以用当前的模块工具随时加载任意模块。它也可用于运行某个程序来决定你是否需SCSI 设备，甚IDE 或软盘驱动器也可以在你使用内核的 “initrd”（初始 RAM 磁盘）特性时稍后加载。这算不上什么新突破，但借助 romfs，你甚至可以推迟加载 ext2、minix，甚至可能还affs 文件系统，直到你确实确认需要它们为止
例如，一个发行版启动盘可以只包含 CD 磁盘驱动程序（以及可能的 SCSI 驱动程序）和 ISO 9660 文件系统模块。内核可以足够小，因为它没有包含其他文件系统——比如相当大ext2fs 模块——该模块可以在安装的后阶段从 CD 加载。另一个用途是救援盘：当你从网络重新安装工作站时，你手边服务器上就有所有工模块可用，因此你不想为此携带两张磁盘，仅仅因ext2 装不下
romfs 像你所预期的那样工作在块设备上，其底层结构非常简单。每个可访问的结构都16 字节边界开始，以便快速访问。一个文件占用的最小空间是 32 字节（这是一个空文件，名称少16 个字符）。任何非空文件的最大开销是头部，加上名称和内容的 16 字节填充，也16+14+15 = 45 字节。不过这种情况相当罕见，因为大多数文件名都长3 字节、短15 字节
```

 offset	    content

	+---+---+---+---+
  0	| - | r | o | m |  \
	+---+---+---+---+	The ASCII representation of those bytes
  4	| 1 | f | s | - |  /	(i.e. "-rom1fs-")
	+---+---+---+---+
  8	|   full size	|	The number of accessible bytes in this fs.
	+---+---+---+---+
 12	|    checksum	|	The checksum of the FIRST 512 BYTES.
	+---+---+---+---+
 16	| volume name	|	The zero terminated name of the volume,
	:               :	padded to 16 byte boundary.
	+---+---+---+---+
 xx	|     file	|
	:    headers	:

```
每个多字节值（32 位字，从现在起我将使longword 这一术语）都必须采用大端（big endian）序
8 个字节标识该文件系统，即便是随意查看的人也能识别。之后，在第 3 longword 中，它包含从该文件系统起始开始可访问的字节数。第 4 longword 是前 512 字节（或可访问字节数，取较小者）的校验和。所采用的算法与 AFFS 文件系统相同，即 longword 的简单求和（同样假设为大端量）。细节请查阅源码。选择该算法是因为尽管它不够可靠，但不需要任何表，而且非常简单
以下字节现在属于文件系统的一部分；每个文件头
```

 offset	    content

     	+---+---+---+---+
  0	| next filehdr|X|	The offset of the next file header
	+---+---+---+---+	  (zero if no more files)
  4	|   spec.info	|	Info for directories/hard links/devices
	+---+---+---+---+
  8	|     size      |	The size of this file in bytes
	+---+---+---+---+
 12	|   checksum	|	Covering the meta data, including the file
	+---+---+---+---+	  name, and padding
 16	| file name     |	The zero terminated name of the file,
	:               :	padded to 16 byte boundary
	+---+---+---+---+
 xx	| file data	|
	:		:

```
由于文件头总是16 字节边界开始，next filehdr 指针的最4 位将始终为零。这四位用于存储模式（mode）信息。位 0..2 指定文件类型；位 4 表示文件是否可执行。如果未设置该位，权限假定为全局可读；如果设置，则为全局可执行；字符设备和块设备除外，它们对非属主之外永远不可访问。每个文件的属主是用户和0，这对预期用途来说不应成为问题 个可能值与文件类型的映射如下：

==	=============== ============================================
	  mapping		spec.info 含义
==	=============== ============================================
 0	hard link	链接目标 [file header]
 1	directory	第一个文件的头部
 2	regular file	未使用，必须为零 [MBZ]
 3	symbolic link	未使用，MBZ（文件数据即链接内容 4	block device	16/16 次设备号
 5	char device		    - " -
 6	socket		未使用，MBZ
 7	fifo		未使用，MBZ
==	=============== ============================================

注意，硬链接在该文件系统中被特别标记，但它们的行为与你所预期的相同（即共inode 号）。还要注意，不创建硬链接环、并为目录创建所. .. 链接是你的责任。这通常genromfs 程序正确完成。请不要socket fifo 特殊文件上将可执行位用于特殊用途，它们在未来可能有其他用途。此外，请记住只有常规文件和符号链接才应当拥有非零的 size 字段；它们包含紧跟在（已填充的）文件名之后的可用字节数
另一点需要注意的是，romfs 工作在按 16 字节边界对齐的文件头和数据上，但大多数硬件设备和块设备驱动程序无法处理小于块大小的数据。为克服这一限制，文件系统的整体大小必须填充1024 字节边界

待解决问题：

- 权限和属主信息是一个类 Unix 系统相当基本的功能，romfs 并未提供全部可能性。我从未觉得这有限制，但其他人可能会
- 该文件系统是只读的，因此可以非常小，但如果有人想向文件系统写入_任何_内容，他仍需要一个可写的文件系统，从而抵消了体积优势。可能的解决方案：将写访问实现为编译期选项，或者为 RAM 磁盘实现一个新的、同样小巧的可写文件系统
- 由于文件只要求按 16 字节边界对齐，目前从文件系统中读取或执行文件可能并非最优。可以通过重新排布文件数据，使其中大部分（即除开头和结尾外）位于“自然”边界上，从而可能直接将文件内容的很大一部分映射mm 子系统来解决
- 压缩可能是一个有用的特性，但在我看来内存是一个相当受限的因素
- 它在哪里使用
- 它能否在 intel motorola 以外的架构上工作
