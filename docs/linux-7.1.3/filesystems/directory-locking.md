## Directory Locking（目录加锁）

目录操作所使用的加锁机制基于两类锁：每 inode 锁（`->i_rwsem`）和每文件系统锁（`->s_vfs_rename_mutex`）。

当需要对多个非目录对象加 `i_rwsem` 时，我们总是按照地址递增的顺序来获取锁。在下面的描述中，我们将其称为 “inode 指针” 顺序。


## Primitives（原语）

就我们的目的而言，所有操作可归为 6 类：

1. 读访问。加锁规则：

 - 锁定我们正在访问的目录（共享）

2. 对象创建。加锁规则：

 - 锁定我们正在访问的目录（独占）

3. 对象删除。加锁规则：

 - 锁定父目录（独占）
 - 找到被删除目标
 - 锁定被删除目标（独占）

4. 创建硬链接。加锁规则：

 - 锁定父目录（独占）
 - 检查源不是目录
 - 锁定源（独占；可能可以弱化为共享）

5. 非跨目录的 rename。加锁规则：

 - 锁定父目录（独占）
 - 找到源和目标
 - 决定源和目标中哪些需要加锁。
	  如果源是非目录则需要加锁；目标如果是非目录或即将被删除，也需要加锁。
 - 按 inode 指针顺序取得所需加的锁（独占），若两者都需要加锁的话
	  （这种情况只会发生在源和目标都是非目录时 —— 源之所以需要加锁，是因为
	  否则它不需要被锁定；目标之所以需要加锁，是因为目录与非目录的混合只有在
	  RENAME_EXCHANGE 时才被允许，而那种情况下不会删除目标）。

6. 跨目录 rename。这是所有情况中最棘手的一种。加锁规则：

 - 锁定文件系统
 - 如果父目录没有共同祖先，操作失败。
 - 按 “祖先优先” 顺序锁定父目录（独占）。如果两者都不是对方的祖先，
	  则先锁定源所在的父目录。
 - 找到源和目标。
 - 验证源不是目标的后代、目标也不是源的后代；否则操作失败。
 - 锁定涉及到的子目录（独占），源先于目标。
 - 锁定涉及到的非目录（独占），按 inode 指针顺序。

上述规则显然保证了：所有将被方法读取、修改或删除的目录，都会由调用者加锁。


## Splicing（拼接）

还有一件事需要考虑 —— 拼接（splicing）。它本身不是一种独立的操作，而是可能作为查找（lookup）的一部分发生。我们谈论的是对目录树的操作，但显然我们并没有这些树的完整图景 —— 尤其是对于网络文件系统。我们所拥有的是 dcache 中可见的一堆子树，加锁发生在这些子树上。树会随着操作的进行而增长，内存压力会将它们裁剪掉。通常这不成问题，但存在一个令人讨厌的转折 —— 当一棵正在生长的树到达另一棵树的根时，我们该怎么办？这种情况可能在多种场景下发生，比如 “有人从同一个 NFS4 服务器挂载了两个嵌套的子树，在对其中一个做查找时到达了另一棵的根”；还有基于文件句柄的打开（open-by-fhandle）之类的事情，并且存在这样一种可能：我们在某处看到的目录被服务器移动到了另一个位置，而我们在做查找时碰到了它。

出于很多原因，我们希望同一个目录在 dcache 中只出现一次。不允许有多个别名。所以当查找碰到一个已经有别名的子目录时，需要对 dcache 树做些处理。查找已经持有对父目录的锁定。如果别名是某棵独立树的根，它会被挂接到我们正在做查找的目录下，使用我们一直在查找的那个名字。如果别名已经是我们正在查找的目录的一个子节点，它就把名字改成我们正在查找的那个名字。这两种情况都不涉及额外的加锁。然而，如果它是某个其他目录的子节点，事情就变得更棘手了。首先，我们验证它 **不是** 我们目录的祖先，如果是则查找失败。然后我们尝试锁定文件系统以及别名的当前父目录。如果任一 trylock 失败，我们使查找失败。如果 trylock 成功，我们将别名从其当前父目录上摘下，挂接到我们的目录下，使用我们正在查找的名字。

注意，拼接 **不** 涉及对文件系统的任何修改；我们所改变的只是 dcache 中的视图。此外，持有一个目录的独占锁可以防止涉及其子节点的此类改变，而持有文件系统锁可以防止树拓扑的任何改变，除了让一棵树的根成为另一棵树中某个目录的子节点这种情况。特别地，如果在该文件系统锁被取走之后，发现两个 dentry 拥有共同祖先，那么它们在锁被释放之前关系将保持不变。因此从目录操作的角度看，拼接几乎无关紧要 —— 唯一相关的地方是跨目录 rename 中的一步；在检查父目录是否有共同祖先时我们需要小心。


## Multiple-filesystem stuff（多文件系统情形）

对于某些文件系统，一个方法可能涉及对另一个文件系统的目录操作；这可能是 ecryptfs 在底层文件系统上做操作、overlayfs 对各个层做某种操作、网络文件系统使用一个本地文件系统作为缓存，等等。在所有这些情况下，对其他文件系统的操作必须遵循相同的加锁规则。此外，“对该文件系统的目录操作可能涉及对那个文件系统的目录操作” 应当是一种非对称关系（或者，换句话说，应当可以对文件系统进行排序，使得对某文件系统的目录操作只能触发对排序更高（rank 更高）的文件系统的目录操作 —— 用这些术语来说，overlayfs 的排序低于它的各层，网络文件系统的排序低于它所缓存于其上的任何东西，等等）。


## Deadlock avoidance（死锁避免）

如果没有目录是它自身的祖先，那么上述机制是无死锁的。

证明：

锁上存在一个排序（ranking），使得所有原语都按照 rank 非递减的顺序来取锁。具体而言，

  - 将给定文件系统上非目录的 `->i_rwsem` 按 inode 指针顺序排列。
  - 将文件系统上所有目录的 `->i_rwsem` 置于同一 rank，且低于同一文件系统上任何非目录的 `->i_rwsem`。
  - 将 `->s_vfs_rename_mutex` 置于低于同一文件系统上任何 `->i_rwsem` 的 rank。
  - 在不同文件系统的锁之间，使用那些文件系统的相对 rank。

例如，如果我们有缓存于本地文件系统之上的 NFS 文件系统，我们有

  1. NFS 文件系统的 `->s_vfs_rename_mutex`
  2. 该 NFS 文件系统上目录的 `->i_rwsem`，所有同 rank
  3. 该文件系统上非目录的 `->i_rwsem`，按 inode 地址递增的顺序
  4. 本地文件系统的 `->s_vfs_rename_mutex`
  5. 本地文件系统上目录的 `->i_rwsem`，所有同 rank
  6. 本地文件系统上非目录的 `->i_rwsem`，按 inode 地址递增的顺序

很容易验证，操作绝不会去取一个 rank 低于已持有锁的锁。

假设可能发生死锁。考虑最小的死锁线程集合。它是一个由若干线程组成的环，每个线程都阻塞在环中下一个线程持有的锁上。

由于加锁顺序与排序一致，最小死锁中所有被争用的锁都会是同一 rank 的，即它们都是同一文件系统上目录的 `->i_rwsem`。此外，不失一般性，我们可以假设所有操作都是直接对该文件系统进行的，并且它们都没有真正到达方法调用那一步。

换句话说，我们有一个线程环 T1,...,Tn，以及同样数量的目录（D1,...,Dn），使得

	T1 阻塞在 D1 上，而 D1 由 T2 持有

	T2 阻塞在 D2 上，而 D2 由 T3 持有

	...

	Tn 阻塞在 Dn 上，而 Dn 由 T1 持有

最小环中的每个操作都必须至少锁定了一个目录，并阻塞在试图锁定另一个目录的尝试上。这只留下 3 种可能的操作：目录删除（锁父目录，然后锁子目录），删除某个子目录的同一目录 rename（同理），以及某种跨目录 rename。

集合中必须存在一个跨目录 rename；确实，如果所有操作都是 “锁父目录，然后锁子目录” 那一类，我们就会有 Dn 是 D1 的父目录，D1 是 D2 的父目录，D2 是 D3 的父目录，……，Dn-1 是 Dn 的父目录。这些关系自目录锁被获取的那一刻起就不可能改变，所以在死锁时刻它们会同时成立，我们就会得到一个环。

由于所有操作都在同一文件系统上，它们之间不可能有多于一个的跨目录 rename。不失一般性，我们可以假设 T1 是执行跨目录 rename 的那个，而其他所有都是 “锁父目录，然后锁子目录” 那一类。

换句话说，我们有一个跨目录 rename，它锁定了 Dn，并阻塞在试图锁定 D1 的尝试上，而 D1 是 D2 的父目录，D2 是 D3 的父目录，……，Dn-1 是 Dn 的父目录。D1,...,Dn 之间的关系在死锁时刻同时成立。此外，跨目录 rename 在锁定任何目录之前，必须先获取文件系统锁并验证所涉及的目录拥有共同祖先，这保证了它们所有之间的祖先关系一直是稳定的。

考虑跨目录 rename 锁定目录的顺序：先父目录，然后可能是它们的子目录。Dn 和 D1 必然都在其中，且 Dn 在 D1 之前被锁定。会是哪一对呢？

不可能是父目录 —— 因为 D1 是 Dn 的祖先，它会是第一个被锁定的父目录。因此至少涉及其中一个子目录，从而它们两者都不可能是另一个的后代 —— 否则操作在锁定父目录之后就无法继续推进了。

不可能是某个父目录及其子目录；否则我们就会得到一个环，因为父目录先于子目录被锁定，所以该父目录必须是其自身的子目录的后代。

也不可能是某个父目录和另一个父目录的子目录。否则该父目录的那个子目录就会是另一个子目录的后代。

这样只剩下一种可能 —— 即 Dn 和 D1 都是子目录，以某种顺序。但这也是不可能的，因为两个子目录中没有一个是另一个的后代。

这就完成了证明，因为具备最小死锁所需性质的那种操作集合不可能存在。

注意，跨目录 rename 中检查共同祖先那一步是关键的 —— 没有它就会发生死锁。确实，假设父目录最初处于不同的树中；我们会锁定源的父目录，然后试图锁定目标的父目录，却让一个不相关的查找把源的某个遥远祖先拼接到了目标父目录的某个遥远后代上。此时我们就有了这样一个跨目录 rename：它持有源父目录的锁，并试图锁定它的遥远祖先。再加上在中间所有目录上的一堆 rmdir() 尝试（如果它们曾经拿到锁，都会以 -ENOTEMPTY 失败），瞧 —— 我们就得到了一个死锁。

## Loop avoidance（环避免）

这些操作保证可以避免环的创建。确实，唯一可能引入环的操作是跨目录 rename。假设操作之后出现了一个环；既然操作之前不存在这样的环，该环中至少有一个节点必定改变了它的父目录。换句话说，该环必定经过源，或者在交换（exchange）的情况下经过目标。

由于操作成功了，源和目标不可能互为祖先。因此从源父目录出发的祖先链不可能经过目标，反之亦然。另一方面，任何节点的祖先链不可能经过该节点自身，否则操作之前我们就已经有一个环了。但除了源和目标之外的所有节点在操作后都保留了父目录，所以操作不会改变源和目标的（前）父目录的祖先链。特别地，这些链必然在有限步之后结束。

现在考虑操作所创建的环。它经过源或目标；环中的下一个节点将分别是目标或源的前父目录。之后该环会沿着该父目录的祖先链前进。但正如我们刚刚所证明的，那条链必然在有限步之后结束，这意味着它不可能是任何环的一部分。证毕（Q.E.D.）。

虽然这套加锁机制对任意 DAG 都有效，但它依赖于判断 “某目录是另一个对象的后代” 的能力。当前的实现假设目录图是一棵树。这个假设也被所有操作所保持（在一棵树上不会引入环的跨目录 rename 会让它仍是一棵树，而 link() 对目录会失败）。

请注意，上面所说的 “目录” == “任何可能拥有子节点的东西”，所以如果我们打算引入混合对象，我们就需要确保 link(2) 对它们不奏效，或者对 is_subdir() 做出改动，使得即便存在这类 “怪兽” 它也能正常工作。
