
## UBIFS 认证支持


## 简介


UBIFS 利用 fscrypt 框架为文件内容和文件名提供机密性保护。这可以防止攻击者在某个时间点上读取文件系统内容的攻击。一个典型的例子是丢失的智能手机：没有文件系统解密密钥，攻击者无法读取存储在设备上的个人数据。

在目前的状态下，UBIFS 加密并不能防止攻击者能够修改文件系统内容、随后用户继续使用设备这类攻击。在这种场景下，攻击者可以在用户毫无察觉的情况下任意修改文件系统内容。一个例子是修改某个二进制文件，使其在被执行时执行恶意操作 [DMC-CBC-ATTACK]。由于 UBIFS 的大部分文件系统元数据都以明文形式存储，这使得交换文件并替换其内容变得相当容易。

其他全盘加密系统，如 dm-crypt，覆盖了所有文件系统元数据，这使得此类攻击更加复杂，但依然并非不可能。特别是，如果攻击者在多个时间点都能访问该设备。对于 dm-crypt 以及构建在 Linux 块 IO 层之上的其他文件系统，可以使用 dm-integrity 或 dm-verity 子系统 [DM-INTEGRITY, DM-VERITY] 在块层获得完整的数据认证。这些也可以与 dm-crypt 结合使用 [CRYPTSETUP2]。

本文档描述了一种为 UBIFS 获取文件内容*以及*完整元数据认证的方法。由于 UBIFS 使用 fscrypt 进行文件内容和文件名加密，认证系统可以挂接到 fscrypt 之上，从而利用密钥派生等现有特性。不过，也应该能够在不使用加密的情况下使用 UBIFS 认证。

### MTD、UBI 与 UBIFS


在 Linux 上，MTD（Memory Technology Devices，存储技术设备）子系统提供了访问原始闪存设备的统一接口。构建在 MTD 之上的较著名子系统之一是 UBI（Unsorted Block Images，无序块映像）。它为闪存设备提供卷管理，因此在某种程度上类似于块设备上的 LVM。此外，它处理闪存特有的磨损均衡和透明的 I/O 错误处理。UBI 向上层提供逻辑擦除块（LEBs），并透明地将它们映射到闪存上的物理擦除块（PEBs）。

UBIFS 是一个运行在 UBI 之上的、面向原始闪存的 fs。因此，磨损均衡和一些闪存特性被留给 UBI 处理，而 UBIFS 专注于可扩展性、性能和可恢复性。

```
	|            | |              UBI            | | MTD-BLOCK | | ... |

```

在内部，UBIFS 维护多种持久化到闪存上的数据结构：

- **Index（索引）**：一个闪存上的 B+ 树，其叶子节点包含文件系统数据。
- **Journal（日志）**：一种附加的数据结构，用于在更新闪存上的索引之前收集文件系统变更，从而减少闪存磨损。
- **Tree Node Cache（TNC，树节点缓存）**：一个反映当前文件系统状态的内存中 B+ 树，用于避免频繁的闪存读取。它基本上是索引的内存中表示，但包含额外的属性。
- **LEB property tree（LPT，LEB 属性树）**：一个闪存上的 B+ 树，用于每个 UBI LEB 的空闲空间记账。

在本节的剩余部分，我们将更详细地介绍闪存上的 UBIFS 数据结构。TNC 在这里不太重要，因为它永远不会直接持久化到闪存上。更多关于 UBIFS 的细节也可以在 [UBIFS-WP] 中找到。

#### UBIFS 索引与树节点缓存


基本的闪存 UBIFS 实体称为**节点（node）**。UBIFS 有多种类型的节点。例如，存储文件内容块的数据节点（`struct ubifs_data_node`），或者表示 VFS inode 的 inode 节点（`struct ubifs_ino_node`）。几乎所有类型的节点都共享一个公共头（`ubifs_ch`），其中包含节点类型、节点长度、序列号等基本信息（参见内核源码中的 `fs/ubifs/ubifs-media.h`）。例外是 LPT 的条目以及一些不太重要的节点类型，例如用于在 LEB 末尾填充不可用内容的填充节点。

为了避免每次单一变更都重写整个 B+ 树，它被实现为**游荡树（wandering tree）**，其中只重写发生变化的节点，并将它们的旧版本标记为废弃而不立即擦除。因此，索引并不存储在闪存上的单一位置，而是**游荡**在四处，并且在包含它们的 LEB 被 UBIFS 重新使用之前，闪存上一直存在废弃的部分。为了找到索引的最新版本，UBIFS 将一个称为**主节点（master node）**的特殊节点存储到 UBI LEB 1 中，该节点始终指向 UBIFS 索引的最新根节点。出于可恢复性考虑，主节点还被复制到 LEB 2。因此，挂载 UBIFS 只需简单地读取 LEB 1 和 2 来获取当前主节点，并由此获得最新闪存索引的位置。

TNC 是闪存索引的内存中表示。它包含每个节点的一些未持久化的额外运行时属性。其中一个是脏标志（dirty-flag），用于标记那些在下一次索引写入闪存时必须被持久化的节点。TNC 充当写回缓存，对闪存索引的所有修改都通过 TNC 完成。与其他缓存一样，TNC 不必将完整索引镜像到内存中，而是在需要时才从闪存读取其中的一部分。**提交（commit）**是 UBIFS 更新闪存文件系统结构（如索引）的操作。每次提交时，被标记为脏的 TNC 节点都会被写入闪存以更新持久化的索引。

#### 日志


为了避免磨损闪存，索引只在满足特定条件（例如 `fsync(2)`）时才被持久化（**提交**）。日志用于记录两次索引提交之间发生的任何变更（以 inode 节点、数据节点等形式）。在挂载时，日志从闪存读取并回放到 TNC 上（TNC 将根据需要从闪存索引按需创建）。

UBIFS 预留了一组专门用于日志的 LEB，称为**日志区（log area）**。日志区 LEB 的数量在文件系统创建时配置（使用 `mkfs.ubifs`），并存储在超级块节点中。日志区只包含两种类型的节点：**引用节点（reference nodes）**和**提交起始节点（commit start nodes）**。每当执行索引提交时，都会写入一个提交起始节点。引用节点在每次日志更新时写入。每个引用节点指向属于该日志条目的、闪存上其他节点（inode 节点、数据节点等）的位置。这些节点称为**芽（buds）**，描述了实际的文件系统变更及其数据。

日志区作为一个环形维护。每当日志即将写满时，就会发起一次提交。这也会写入一个提交起始节点，这样在挂载时，UBIFS 会寻找最新的提交起始节点，并只回放其后的每个引用节点。提交起始节点之前的每个引用节点都将被忽略，因为它们已经是闪存索引的一部分。

写入日志条目时，UBIFS 首先确保有足够的空间来写入该条目的引用节点和芽。然后，写入引用节点，之后写入描述文件变更的芽。在回放时，UBIFS 会记录每个引用节点，并检查被引用 LEB 的位置以发现芽。如果这些芽已损坏或缺失，UBIFS 将尝试通过重新读取 LEB 来恢复它们。不过这仅针对日志最后被引用的 LEB 进行。只有这一个可能因为断电而损坏。如果恢复失败，UBIFS 将无法挂载。任何其他 LEB 上的错误都会直接导致 UBIFS 挂载失败。

```
        \    |      |     |        |   /  /      |     |     |               \

        \    |      |     |        |   /  /      |     |     |               \
```

#### LEB 属性树/表


LEB 属性树用于存储每个 LEB 的信息。这包括 LEB 类型以及该 LEB 上空闲空间和**脏（dirty）**（旧的、废弃的内容）空间 [^1^]_ 的大小。类型很重要，因为 UBIFS 绝不会在单个 LEB 上混合索引节点和数据节点，因此每个 LEB 都有特定的用途。这也对空闲空间计算很有用。更多细节参见 [UBIFS-WP]。

LEB 属性树同样是一个 B+ 树，但它比索引小得多。由于其较小的尺寸，它每次提交时总是作为一个整体块写入。因此，保存 LPT 是一个原子操作。

   空闲空间与脏空间的区别，即 LEB 上在不擦除的情况下剩余可写入的空间，以及先前写入但已废弃、却必须擦除整个 LEB 才能覆盖的内容。


## UBIFS 认证


本章介绍 UBIFS 认证，它使 UBIFS 能够验证存储在闪存上的元数据与文件内容的真实性与完整性。

### 威胁模型


UBIFS 认证能够检测离线数据修改。虽然它不能阻止修改，但它使（受信任的）代码能够检查闪存上的文件内容和文件系统元数据的完整性与真实性。这涵盖了文件内容被交换的攻击。

UBIFS 认证不能防止完整闪存内容的回滚。也就是说，攻击者仍然可以转储闪存并在稍后某个时间恢复它而不被检测。它也不能防止单个索引提交的部分回滚。这意味着攻击者能够部分地撤销变更。这是可能的，因为 UBIFS 不会立即覆盖索引树或日志的旧版本，而是将它们标记为废弃，并由垃圾回收在稍后擦除。攻击者可以利用这一点，擦除当前树的一部分并恢复仍留在闪存上、尚未被擦除的旧版本。这是可能的，因为每次提交总是写入索引根节点和主节点的新版本，而不覆盖先前的版本。UBI 的磨损均衡操作也会把内容从一个物理擦除块复制到另一个，而不会原子地擦除第一个擦除块，这进一步方便了此类攻击。

UBIFS 认证不涵盖攻击者在提供认证密钥后能够在设备上执行代码的攻击。必须采取安全启动（secure boot）和可信启动（trusted boot）等额外措施，以确保只有受信任的代码在设备上执行。

### 认证


为了能够完全信任从闪存读取的数据，存储在闪存上的所有 UBIFS 数据结构都经过了认证。即：

- 索引，包含文件内容、文件元数据（如扩展属性、文件长度等）。
- 日志，它也通过记录对文件系统的变更而包含文件内容和元数据。
- LPT，它存储 UBIFS 用于空闲空间记账的 UBI LEB 元数据。

#### 索引认证


通过 UBIFS 的游荡树概念，它已经负责只从叶子节点向上到完整 B+ 树的根节点更新和持久化变更的部分。这使我们能够用对每个节点子节点的哈希来增强树的索引节点。结果，索引基本上也成了一棵 Merkle 树。由于索引的叶子节点包含实际的文件系统数据，其父索引节点的哈希因此覆盖了所有文件内容和文件元数据。当文件发生变更时，UBIFS 索引会相应地从叶子节点向上更新到根节点，包括主节点。这个过程可以被挂接，以便同时只为每个变更的节点重新计算哈希。每当读取文件时，UBIFS 可以验证从每个叶子节点到根节点的哈希，以确保节点的完整性。

为了确保整个索引的真实性，UBIFS 主节点存储了一个对其自身内容以及索引树根节点哈希的带密钥哈希（HMAC）。如上所述，主节点在索引被持久化时（即在索引提交时）总是写入闪存。

使用这种方法，只有 UBIFS 索引节点和主节点被修改以包含哈希。所有其他类型的节点保持不变。这减少了存储开销，而这对 UBIFS 的用户（即嵌入式设备）来说十分宝贵。

```

                             +---------------+
                             |  Master Node  |
                             |    (hash)     |
                             +---------------+
                                     |
                                     v
                            +-------------------+
                            |  Index Node #1    |
                            |                   |
                            | branch0   branchn |
                            | (hash)    (hash)  |
                            +-------------------+
                               |    ...   |  (fanout: 8)
                               |          |
                       +-------+          +------+
                       |                         |
                       v                         v
            +-------------------+       +-------------------+
            |  Index Node #2    |       |  Index Node #3    |
            |                   |       |                   |
            | branch0   branchn |       | branch0   branchn |
            | (hash)    (hash)  |       | (hash)    (hash)  |
            +-------------------+       +-------------------+
                 |   ...                     |   ...   |
                 v                           v         v
               +-----------+         +----------+  +-----------+
               | Data Node |         | INO Node |  | DENT Node |
               +-----------+         +----------+  +-----------+


           Figure 3: Coverage areas of index node hash and master node HMAC



```

对于健壮性和断电安全性最重要的部分，是原子地持久化哈希和文件内容。在这里，UBIFS 关于如何持久化变更节点的现有逻辑已经为此目的而设计，使得 UBIFS 能够在持久化过程中发生断电时安全恢复。向索引节点添加哈希并不会改变这一点，因为每个哈希都将与其相应节点一起原子地持久化。

#### 日志认证


日志也要认证。由于日志是持续写入的，因此有必要频繁地向日志添加认证信息，以便在发生断电时不会有过量的数据无法被认证。这是通过从提交起始节点开始，对先前的引用节点、当前引用节点以及芽节点创建连续哈希来实现的。不时地在合适的时候，会在芽节点之间添加认证节点。这种新节点类型包含一个对哈希链当前状态的 HMAC。这样日志就可以认证到最后一个认证节点。可能没有认证节点的日志尾部无法被认证，并在日志回放时被跳过。

```

    ,,,,,,,,
    ,......,...........................................
    ,. CS  ,               hash1.----.           hash2.----.
    ,.  |  ,                    .    |hmac            .    |hmac
    ,.  v  ,                    .    v                .    v
    ,.REF#0,-> bud -> bud -> bud.-> auth -> bud -> bud.-> auth ...
    ,..|...,...........................................
    ,  |   ,
    ,  |   ,,,,,,,,,,,,,,,
    .  |            hash3,----.
    ,  |                 ,    |hmac
    ,  v                 ,    v
    , REF#1 -> bud -> bud,-> auth ...
    ,,,|,,,,,,,,,,,,,,,,,,
       v
      REF#2 -> ...
       |
       V
      ...

```

由于哈希也包含了引用节点，攻击者无法重新排序或跳过任何日志头进行回放。攻击者只能从日志末尾移除芽节点或引用节点，最多将文件系统回退到最后一次提交的状态。

日志区的位置存储在主节点中。由于主节点如上所述用 HMAC 进行了认证，因此不可能在不被发现的情况下篡改它。日志区的大小在文件系统创建时使用 `mkfs.ubifs` 指定，并存储在超级块节点中。为了避免篡改此值以及存储在那里的其他值，向超级块结构添加了一个 HMAC。超级块节点存储在 LEB 0 中，并且只在特性标志或类似变更时被修改，而不会在文件变更时被修改。

#### LPT 认证


LPT 根节点在闪存上的位置存储在 UBIFS 主节点中。由于 LPT 在每次提交时都是原子地写入和读取的，因此无需认证树的各个节点。只需通过存储在主节点中的一个简单哈希来保护完整 LPT 的完整性就足够了。由于主节点本身是经过认证的，因此可以通过验证主节点的真实性，并将存储在那里的 LTP 哈希与从读取的闪存 LPT 计算出的哈希进行比较，来验证 LPT 的真实性。

### 密钥管理


为简单起见，UBIFS 认证使用单个密钥来计算超级块、主节点、提交起始节点和引用节点的 HMAC。该密钥必须在文件系统创建时（`mkfs.ubifs`）可用，以便对超级块节点进行认证。此外，它必须在文件系统挂载时可用，以便验证已认证的节点并为变更生成新的 HMAC。

UBIFS 认证旨在与 UBIFS 加密（fscrypt）协同工作，以提供机密性和真实性。由于 UBIFS 加密采用每个目录不同加密策略的方法，因此可能存在多个 fscrypt 主密钥，也可能存在未加密的文件夹。另一方面，UBIFS 认证采用“全有或全无”的方法，即它要么认证文件系统的全部内容，要么什么都不认证。因此，并且由于 UBIFS 认证也应该能够在不使用加密的情况下使用，它不与 fscrypt 共享同一个主密钥，而是管理一个专用的认证密钥。

提供认证密钥的 API 尚未定义，但密钥可以由用户空间通过一个 keyring 提供，类似于目前 fscrypt 中的做法。不过应该注意的是，当前的 fscrypt 方法已显现出其缺陷，用户空间 API 最终将会改变 [FSCRYPT-POLICY2]。

尽管如此，用户仍将能够在用户空间提供覆盖 UBIFS 认证和加密的单个口令或密钥。这可以由相应的用户空间工具解决：除派生的用于加密的 fscrypt 主密钥之外，再派生第二个用于认证的密钥。

为了能够检查挂载时是否有正确的密钥可用，UBIFS 超级块节点还将额外存储一个认证密钥的哈希。这种方法类似于为 fscrypt 加密策略 v2 提议的方法 [FSCRYPT-POLICY2]。

## 未来扩展


在某些场景下，供应商希望向客户提供经过认证的文件系统映像，此时应该能够在不共享机密 UBIFS 认证密钥的情况下做到这一点。相反，除了每个 HMAC 之外，还可以存储一个数字签名，供应商将公钥与文件系统映像一起共享。如果此后必须修改该文件系统，UBIFS 可以在首次挂载时用 HMAC 替换所有数字签名，类似于 IMA/EVM 子系统处理此类情况的方式。届时 HMAC 密钥必须以正常方式事先提供。
