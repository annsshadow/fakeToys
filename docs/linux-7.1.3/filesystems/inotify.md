
## Inotify —— 一个强大而简单的文件变更通知系统



文档始于 2005 年 3 月 15 日，作者 Robert Love <rml@novell.com>

文档更新于 2015 年 1 月 4 日，作者 Zhang Zhen <zhenzhang.zhang@huawei.com>

 - 删除了已过时的接口，用户接口请直接参考 manpage。

(i) 设计理由

问：
   不将监视（watch）绑定到被监视对象的打开 fd 之上，这背后的设计决策是什么？

答：
   监视与打开的 inotify 设备相关联，而非与打开的文件相关联。这解决了 dnotify 的主要问题：保持文件打开会固定该文件，进而——更糟的是——固定挂载点。因此，dnotify 对于使用可移动介质的桌面系统是不可行的，因为介质无法被卸载。监视一个文件不应要求它处于打开状态。

问：
   与每个监视一个 fd 相对，使用每实例一个 fd 的设计决策是什么？

答：
   每个监视一个 fd 会很快消耗掉比允许数量更多的文件描述符，比便于管理的更多的 fd，以及比最优 select() 数量更多的 fd。是的，root 可以提高每进程 fd 限制，是的，用户可以使用 epoll，但要求两者同时满足是一种愚蠢且多余的要求。一个监视消耗的内存少于一个打开的文件，因此将两者编号空间分离是明智的。当前的设计正是用户空间开发者想要的：用户初始化 inotify 一次，然后添加 n 个监视，只需一个 fd，无需摆弄 fd 限制。将 inotify 实例初始化两千次是愚蠢的。如果我们能干净地实现用户空间的偏好——而我们可以，idr 层让这类事情变得轻而易举——那么我们就应该这样做。

   还有其他好的论据。使用单个 fd，就只有一个需要阻塞的对象，它映射到一个单一的事件队列。该单个 fd 返回所有监视事件以及任何潜在的带外数据。如果每个 fd 都是独立的监视，

   - 将无法获取事件顺序。文件 foo 和文件 bar 上的事件会在两个 fd 上 pop poll()，但无法判断哪个先发生。单一队列天然给出顺序。这种顺序对于 Beagle 等现有应用至关重要。试想一下没有顺序的 "mv a b ; mv b a" 事件。

   - 我们必须维护 n 个 fd 和 n 个带状态的内部队列，而非仅仅一个。在内核中要混乱得多。单一、线性的队列才是合理的的数据结构。

   - 用户空间开发者偏好当前的 API。例如 Beagle 的家伙们很喜欢它。相信我，我问过。这并不奇怪：谁愿意通过 select 管理并阻塞在 1000 个 fd 上？

   - 无法获取带外数据。

   - 1024 仍然太低。;-)

   当你谈论设计一个可扩展到数千个目录的文件变更通知系统时，摆弄数千个 fd 似乎并不是正确的接口。它太重了。

   此外，确实可以拥有多个实例并摆弄多个队列，从而拥有多个关联的 fd。不必是一对一进程到 fd 的映射；而是一对一队列到 fd，一个进程很容易需要多个队列。

问：
   为什么采用系统调用的方式？

答：
   糟糕的用户空间接口是 dnotify 的第二大问题。信号对于文件通知来说是一种非常、非常糟糕的接口。或者说，对于任何事情都是。从所有角度看，理想的解决方案是基于文件描述符的方案，允许基本的文件 I/O 和 poll/select。获取 fd 和管理监视既可以通过设备文件，也可以通过一组新的系统调用完成。我们决定实现一组新的系统调用，因为那是新内核接口的首选方式。唯一的真正区别在于我们是想使用 open(2) 和 ioctl(2) 还是几个新的系统调用。系统调用胜过 ioctl。
