
## Glock 内部加锁规则

本文档说明了 glock 状态机内部的基本原理。每个 glock（fs/gfs2/incore.h 中的 struct
gfs2_glock）有两个主要的（内部）锁：

 1. 一个自旋锁（gl_lockref.lock），保护内部状态，如 gl_state、gl_target 和持有者列表
    （gl_holders）
 2. 一个非阻塞位锁 GLF_LOCK，用于防止其他线程同时调用 DLM 等。如果一个线程获取了这个锁，
    它在释放时必须调用 run_queue（通常通过工作队列），以确保任何挂起的任务都已完成。

gl_holders 列表包含与 glock 关联的所有排队锁请求（不仅仅是持有者）。如果有任何被持有的锁，
它们将是列表头部连续的条目。锁严格按照它们排队的顺序被授予。

glock 层的使用者可以请求三种锁状态，即共享（SH）、延迟（DF）和独占（EX）。它们转换为如下的
DLM 锁模式：

==========	====== =====================================================
Glock 模式       DLM    锁模式
==========	====== =====================================================
    UN          IV/NL  未锁定（没有与 glock 关联的 DLM 锁）或 NL
    SH          PR     （受保护读，Protected read）
    DF          CW     （并发写，Concurrent write）
    EX          EX     （独占，Exclusive）
==========	====== =====================================================

因此 DF 基本上是一种与“常规”共享锁模式 SH 不兼容的共享模式。在 GFS2 中，DF 模式专用于直接 I/O
操作。glock 基本上是一个锁加上一些处理缓存管理的例程。缓存适用以下规则：

==========      ==============   ==========   ==========   ==============
Glock 模式      缓存元数据       缓存数据     脏数据       脏元数据
==========      ==============   ==========   ==========   ==============
    UN                否            否           否           否
    DF                是            否           否           否
    SH                是            是           否           否
    EX                是            是           是           是
==========      ==============   ==========   ==========   ==============

这些规则通过使用为每种 glock 类型定义的各种 glock 操作来实现。并非所有类型的 glock 都使用所有
模式。例如，只有 inode glock 使用 DF 模式。

glock 操作及按类型的常量表：

==============     =============================================================
字段              用途
==============     =============================================================
go_sync            在远程状态改变之前调用（例如用于同步脏数据）
go_xmote_bh        在远程状态改变之后调用（例如用于重新填充缓存）
go_inval           如果远程状态改变需要使缓存失效则调用
go_instantiate     在获取到一个 glock 时调用
go_held            每次获取到一个 glock 持有者时调用
go_dump            调用以打印调试文件对象的内容，或在出错时将 glock 转储到日志。
go_callback	   如果 DLM 发送回调以丢弃此锁则调用
go_unlocked        在 glock 被解锁（dlm_unlock()）时调用
go_type            glock 的类型，`LM_TYPE_*`
go_flags	   GLOF_ASPACE 被设置，如果该 glock 有关联的地址空间
==============     =============================================================

每个锁的最小持有时间，是在远程锁授予之后我们忽略远程降级请求的一段时间。这是为了防止锁在集群
中从一个节点弹到另一个节点、而没有任何节点取得任何进展的情况。这在被多个节点写入的共享 mmap
文件上最容易显现。通过延迟响应远程回调的降级，这给了用户空间程序在页面被取消映射之前取得一些
进展的时间。

最终，我们希望使 glock 的“EX”模式在本地共享，这样任何本地加锁都将按需通过 i_mutex 完成，而
不是通过 glock。

glock 操作的加锁规则：

==============   ======================    =============================
操作            GLF_LOCK 位锁持有         gl_lockref.lock 自旋锁持有
==============   ======================    =============================
go_sync              是                       否
go_xmote_bh          是                       否
go_inval             是                       否
go_instantiate       否                       否
go_held              否                       否
go_dump              有时                     是
go_callback          有时（N/A）              是
go_unlocked          是                       否
==============   ======================    =============================

   操作在入口处若持有任一位锁或自旋锁，则不得将其丢弃。go_dump 和 do_demote_ok 绝不能阻塞。
   注意，go_dump 只有在 glock 的状态表明它正在缓存最新数据时才会被调用。

GFS2 内部的 glock 加锁顺序：

 1. i_rwsem（如果需要）
 2. 重命名 glock（仅用于重命名）
 3. inode glock（父节点先于子节点，具有相同父节点的“同级” inode 按锁编号顺序）
 4. Rgrp glock（用于（去）分配操作）
 5. 事务 glock（通过 gfs2_trans_begin）用于非读操作
 6. i_rw_mutex（如果需要）
 7. 页锁（始终最后，非常重要！）

每个 inode 有两个 glock。一个处理对 inode 本身的访问（加锁顺序如上），另一个称为 iopen glock，
与 inode 中的 i_nlink 字段一起用于确定该 inode 的生命周期。inode 的加锁是基于每个 inode 的。
rgrp 的加锁是基于每个 rgrp 的。一般而言，我们倾向于先锁定本地锁，再锁定集群锁。

### Glock 统计

统计分为两组：与超级块相关的和与单个 glock 相关的。超级块统计按每 CPU 进行，以尽量降低收集
它们的开销。它们还进一步按 glock 类型划分。所有时间单位都是纳秒。

对于超级块和 glock 统计，在每种情况下收集的信息是相同的。超级块计时统计用于为 glock 计时
统计提供默认值，以便新创建的 glock 在尽可能大的程度上有一个合理的起点。每 glock 计数器在
glock 创建时初始化为零。每 glock 统计在 glock 被从内存中弹出时丢失。

统计分为三对均值和方差，外加两个计数器。均值/方差对是平滑的指数估计，所使用的算法对于那些
习惯计算网络代码中往返时间的人来说会非常熟悉。参见《TCP/IP Illustrated, Volume 1》，W.
Richard Stevens，第 21.3 节“Round-Trip Time Measurement”，第 299 页及之后。还有第 2 卷第
25.10 节，第 838 页及之后。与 TCP/IP Illustrated 的情况不同，均值和方差没有缩放，而是以整数
纳秒为单位。

三对均值/方差衡量以下事物：

 1. DLM 加锁时间（非阻塞请求）
 2. DLM 加锁时间（阻塞请求）
 3. 请求间时间（同样针对 DLM）

非阻塞请求是指无论相关 DLM 锁处于何种状态都会立即完成的请求。目前这意味着以下任一情况时的
请求：(a) 锁的当前状态为独占，即锁降级（demotion）；(b) 请求的状态为 null 或未锁定（同样是
降级）；或 (c) 设置了“try lock”标志。阻塞请求涵盖所有其他锁请求。

有两个计数器。第一个主要用来显示已经发出了多少锁请求，从而显示有多少数据进入了均值/方差
计算。另一个计数器统计 glock 代码顶层持有者的排队数量。希望该数字会远大于发出的 dlm 锁请求
数量。

那么为什么要收集这些统计？我们有几个理由希望更好地了解这些时间：

1. 能够更好地设置 glock 的“最小持有时间”
2. 更容易发现性能问题
3. 改进用于为分配选择资源组（resource group）的算法（基于锁等待时间，而不是盲目使用“try lock”）

由于更新的平滑作用，被采样输入量的阶跃变化只有在 8 个样本之后（方差则是 4 个）才会被完全考虑，
在解读结果时需要仔细考虑这一点。

知道锁请求完成所需的时间以及 glock 锁请求之间的平均时间，意味着我们可以计算出节点能够使用
glock 的时间占总时间的百分比，与集群其余部分拥有其份额的时间之比。这在设置锁最小持有时间时
将非常有用。

我们已非常小心地确保尽可能准确地测量我们确实想要测量的量。任何测量系统总是存在不准确之处，
但我希望这已经是我们能合理做到的最准确的了。

```
    /sys/kernel/debug/gfs2/<fsname>/sbstats

```
```
    /sys/kernel/debug/gfs2/<fsname>/glstats

```
假设 debugfs 挂载在 /sys/kernel/debug，并且 <fsname> 被替换为相关 gfs2 文件系统的名称。

输出中使用的缩写如下：

=========  ================================================================
srtt       非阻塞 dlm 请求的平滑往返时间
srttvar    srtt 的方差估计
srttb      （可能）阻塞的 dlm 请求的平滑往返时间
srttvarb   srttb 的方差估计
sirt       平滑请求间时间（针对 dlm 请求）
sirtvar    sirt 的方差估计
dlm        dlm 请求的数量（glstats 文件中的 dcnt）
queue     排队的 glock 请求数量（glstats 文件中的 qcnt）
=========  ================================================================

sbstats 文件包含每种 glock 类型（因此每种类型 8 行）和每个 CPU（每 CPU 一列）的一组此类统计。
glstats 文件包含每个 glock 的一组此类统计，格式与 glocks 文件类似，但每个计时统计使用
均值/方差格式。

gfs2_glock_lock_time 跟踪点打印出相关 glock 的当前统计值，以及收到的每个 dlm 回复的一些附加
信息：

======   =======================================
status   dlm 请求的状态
flags    dlm 请求的标志
tdiff    此特定请求所花费的时间
