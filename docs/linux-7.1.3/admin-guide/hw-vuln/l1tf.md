## L1TF — L1 终端错误


L1 Terminal Fault 是一种硬件漏洞，当用于控制访问所用虚拟地址的页表项（PTE）的 Present 位被清除或设置了其他保留位时，该漏洞允许未特权的推测性访问 Level 1 Data Cache（一级数据缓存）中可用的数据。

### 受影响的处理器


该漏洞影响大量 Intel 处理器。以下情况不存在该漏洞：

   - 来自 AMD、Centaur 及其他非 Intel 厂商的处理器

   - CPU 系列号 < 6 的较老处理器型号

   - 一系列 Intel ATOM 处理器（Cedarview、Cloverview、Lincroft、Penwell、Pineview、Silvermont、Airmont、Merrifield）

   - Intel XEON PHI 系列

   - 在 IA32_ARCH_CAPABILITIES MSR 中设置了 ARCH_CAP_RDCL_NO 位的 Intel 处理器。若设置了该位，则 CPU 也不受 Meltdown 漏洞影响。这些 CPU 应在 2018 年底之前上市。

处理器是否受影响可从 sysfs 中的 L1TF 漏洞文件读取。参见 l1tf_sys_info。

### 相关 CVE


以下 CVE 条目与 L1TF 漏洞相关：

   CVE-2018-3620  L1 Terminal Fault  OS、SMM 相关方面
   CVE-2018-3646  L1 Terminal Fault  虚拟化相关方面
   =============  =================  ==============================

### 问题


如果某条指令访问一个虚拟地址，而与之相关的页表项（PTE）的 Present 位被清除或设置了其他保留位，那么推测执行会忽略该无效 PTE，并在所引用的数据存在于 Level 1 Data Cache 中时加载该数据，就好像 PTE 中地址位所引用的页仍然存在且可访问一样。

虽然这是一个纯粹的推测机制，且该指令最终退役时会引发页错误，但加载数据并使其对其他推测指令可用这一行为，为未特权的恶意代码打开了侧信道攻击的机会，类似于 Meltdown 攻击。

Meltdown 破坏了用户空间到内核空间的保护，而 L1TF 允许攻击系统中的任意物理内存地址，且该攻击可跨越所有保护域生效。它允许攻击 SGX，并且由于推测执行绕过了扩展页表（EPT）保护机制，它也可从虚拟机内部发起攻击。


### 攻击场景


##### 1. 恶意用户空间


   操作系统在被标记为不存在（non present）的 PTE 的地址位中存储任意信息。这使得恶意用户空间应用程序能够攻击这些 PTE 所解析到的物理内存。在某些情况下，用户空间可以恶意地影响编码在 PTE 地址位中的信息，从而使攻击更具确定性和可行性。

   Linux 内核包含了针对此攻击向量的缓解措施 PTE inversion（PTE 反转），它永久启用且对性能没有影响。内核保证未被标记为存在的 PTE 的地址位绝不会指向可缓存的物理内存空间。

   运行最新内核的系统可抵御来自恶意用户空间应用程序的攻击。

##### 2. 虚拟机中的恶意客户机


   由于 L1TF 破坏了所有域保护，这使得能够直接控制 PTE 的恶意客户机操作系统，以及运行在缺少 L1TF 的 PTE 反转缓解措施的非保护客户机内核上的恶意客户机用户空间应用程序，能够攻击物理主机内存。

   在虚拟化场景下，L1TF 的一个特殊方面是对称多线程（SMT）。Intel 的 SMT 实现称为 HyperThreading（超线程）。受影响处理器上的超线程共享 L1 Data Cache（L1D）这一事实对此很重要。由于该缺陷只允许攻击存在于 L1D 中的数据，运行在一个超线程上的恶意客户机可以攻击由运行在同一物理核的兄弟超线程上的上下文带入 L1D 的数据。该上下文可以是主机操作系统、主机用户空间或另一个客户机。

   如果处理器不支持扩展页表（Extended Page Tables），则只有当虚拟机监视器（hypervisor）未清理有效（影子）页表的内容时，攻击才可能成功。

   虽然存在可完全缓解这些攻击向量的方案，但这些缓解措施在 Linux 内核中默认未启用，因为它们会显著影响性能。内核提供了若干机制，可根据部署场景用于解决该问题。这些缓解措施及其保护范围与影响将在后续章节中描述。

   默认缓解措施及其选择理由在本文档末尾说明。参见 default_mitigations。


### L1TF 系统信息


Linux 内核提供了一个 sysfs 接口来枚举系统当前的 L1TF 状态：系统是否易受攻击，以及哪些缓解措施处于活动状态。相关的 sysfs 文件是：

/sys/devices/system/cpu/vulnerabilities/l1tf

此文件中的可能取值为：

  ===========================   ===============================
  'Not affected'		处理器不受漏洞影响
  'Mitigation: PTE Inversion'	主机保护已激活
  ===========================   ===============================

如果启用了 KVM/VMX 且处理器易受攻击，则以下信息会附加到 'Mitigation: PTE Inversion' 部分之后：

  - SMT 状态：

    =====================  ================
    'VMX: SMT vulnerable'  SMT 已启用
    'VMX: SMT disabled'    SMT 已禁用
    =====================  ================

  - L1D 刷新模式：

    ================================  ====================================
    'L1D vulnerable'		     L1D 刷新已禁用

    'L1D conditional cache flushes'   L1D 刷新条件性启用

    'L1D cache flushes'		     L1D 刷新无条件启用
    ================================  ====================================

由此产生的保护等级将在后续章节中讨论。


### 主机缓解机制


内核可无条件抵御来自运行在主机上的恶意用户空间的 L1TF 攻击。


### 客户机缓解机制


##### 1. 进入客户机（VMENTER）时刷新 L1D


   为确保客户机无法攻击存在于 L1D 中的数据，虚拟机监视器在进入客户机之前刷新 L1D。

   刷新 L1D 不仅会逐出不应被潜在恶意客户机访问的数据，也会逐出客户机的数据。刷新 L1D 会带来性能影响，因为处理器必须将已刷出的客户机数据重新取回 L1D。根据 VMEXIT/VMENTER 的频率以及客户机中计算的类型，观测到的性能下降范围在 1% 到 50% 之间。对于客户机 VMEXIT/VMENTER 较少的场景，性能影响很小。Virtio 与 posted interrupts（投递中断）等机制旨在将 VMEXIT 降到最低，但特定的配置与应用场景仍可能受到较高 VMEXIT 速率的影响。

   内核提供两种 L1D 刷新模式：
    - conditional（'cond'，条件性）
    - unconditional（'always'，无条件）

   条件模式会避免在仅执行了经审计代码路径后才发生相应 VMENTER 的 VMEXIT 之后刷新 L1D。这些代码路径已经过验证，不会向攻击者暴露机密或其他有价值的数据，但它们可能泄露虚拟机监视器的地址空间布局信息。

   无条件模式在每次 VMENTER 调用时都刷新 L1D，提供最大程度的保护。它的开销高于条件模式。由于开销取决于工作负载场景以及由此产生的 VMEXIT 数量，无法准确量化。

   一般建议启用进入客户机时的 L1D 刷新。在内核受影响的处理器上默认采用条件模式。

   **注意**，L1D 刷新并不能解决 SMT 问题，因为兄弟线程也会将其数据重新带回 L1D，从而使其再次可被攻击。

   L1D 刷新可由管理员通过内核命令行和 sysfs 控制文件进行控制。参见 mitigation_control_command_line 与 mitigation_control_kvm。


##### 2. 将客户机 VCPU 限制到专用物理核


   为解决 SMT 问题，可以将一个客户机或一组客户机亲和到一或多个物理核上。合适的机制是利用独占 cpusets（CPU 集），以确保没有其他客户机或主机任务可在这些核上运行。

   如果只有一个客户机或相关客户机运行在同一物理核的兄弟 SMT 线程上，那么它们只能攻击自身内存以及受限的主机内存部分。

   当兄弟 SMT 线程之一运行在主机操作系统（虚拟机监视器）上下文中，而另一个运行在客户机上下文中时，主机内存可被攻击。来自主机操作系统上下文的有价值信息量取决于主机操作系统所执行的上下文，即中断、软中断与内核线程。若不对代码进行深入审查，无法断言这些上下文中的有价值数据对攻击者毫无价值。

   **注意**，将客户机分配给固定的物理核集合会影响调度器进行负载均衡的能力，并可能根据托管场景对 CPU 利用率产生负面影响。对于特定场景，禁用 SMT 可能是一个可行的替代方案。

   有关将客户机限制到单个或一组核的更多信息，请查阅 cpusets 文档：

   https://www.kernel.org/doc/Documentation/admin-guide/cgroup-v1/cpusets.rst


##### 3. 中断亲和性


   中断可以亲和到逻辑 CPU。但这并非普遍成立，因为有些类型的中断是真正的每 CPU 中断，例如本地定时器中断。此外，多队列设备会将其中断亲和到每个队列的单个 CPU 或一组 CPU，且不允许管理员控制这些亲和性。

   将可由亲和性控制的中断从运行不可信客户机的 CPU 上移开，可以缩小攻击向量空间。

   与运行不可信客户机的 CPU 亲和的中断是否为攻击者提供有价值的数据，取决于系统配置以及系统上运行的场景。虽然可以假设某些中断除了暴露主机操作系统内存布局的线索外不会泄露有价值的信息，但无法做出一般性的假设。

   中断亲和性可由管理员通过 /proc/irq/$NR/smp_affinity[_list] 文件控制。有限的文档可在以下位置获取：

   https://www.kernel.org/doc/Documentation/core-api/irq/irq-affinity.rst


##### 4. SMT 控制


   为防止 L1TF 的 SMT 问题，可能需要完全禁用 SMT。禁用 SMT 可能带来显著的性能影响，但具体影响取决于托管场景与工作负载类型。禁用 SMT 的影响还需与其他缓解方案（如将客户机限制到专用核）的影响进行权衡。

   内核提供了一个 sysfs 接口来获取 SMT 状态并对其进行控制。它还提供了用于控制 SMT 的内核命令行接口。

   内核命令行接口包含以下选项：

     =========== ==========================================================
     nosmt	 影响引导期间次级 CPU 的启动。内核在引导过程中尝试让所有存在的
		 CPU 上线。"nosmt" 确保从每个物理核中只激活一个——即所谓的
		 primary（主，超）线程。由于 Intel 处理器与 Machine Check
		 Exceptions（机器检查异常）相关的设计缺陷，非主兄弟线程至少
		 必须部分启动，随后再次关闭。"nosmt" 可通过 sysfs 接口撤销。

     nosmt=force 与 "nosmt" 效果相同，但不允许通过 sysfs 接口撤销 SMT 禁用。
     =========== ==========================================================

   sysfs 接口提供两个文件：

   - /sys/devices/system/cpu/smt/control
   - /sys/devices/system/cpu/smt/active

   /sys/devices/system/cpu/smt/control:

     该文件允许读取 SMT 控制状态，并提供禁用或（重新）启用 SMT 的能力。可能的状态为：

	==============  ===================================================
	on		CPU 支持并启用了 SMT。所有逻辑 CPU 都可以无限制地上线和
			下线。

	off		CPU 支持 SMT 但已禁用。只有所谓的 primary SMT 线程可以
			无限制地上线和下线。尝试让非主兄弟线程上线的操作会被拒绝。

	forceoff	与 'off' 相同，但状态不可被控制。写入控制文件的尝试会被拒绝。

	notsupported	处理器不支持 SMT。因此它不受 L1TF 的 SMT 相关影响。
			写入控制文件的尝试会被拒绝。
	==============  ===================================================

     可写入此文件以控制 SMT 状态的可能取值为：

     - on
     - off
     - forceoff

   /sys/devices/system/cpu/smt/active:

     此文件报告 SMT 是否已启用且处于活动状态，即在任何物理核上是否有两个或更多兄弟线程处于在线状态。

   在引导时也可通过 l1tf 内核命令行参数结合 L1D 刷新控制来进行 SMT 控制。参见 mitigation_control_command_line。

##### 5. 禁用 EPT


  为虚拟机禁用 EPT 可针对 L1TF 提供完全缓解，即使在启用 SMT 的情况下也是如此，因为客户机的有效页表由虚拟机监视器管理并清理。不过禁用 EPT 会带来显著的性能影响，尤其是在启用 Meltdown 缓解措施 KPTI 时。

  EPT 可在虚拟机监视器中通过 'kvm-intel.ept' 参数禁用。

针对禁用 SMT 或 EPT 所带来的性能影响，新的缓解机制仍在持续研究与开发中。


### 内核命令行上的缓解控制


内核命令行允许在引导时通过 "l1tf=" 选项控制 L1TF 缓解措施。该选项的有效参数为：

  ============  =============================================================
  full		为 L1TF 漏洞提供所有可用的缓解措施。禁用 SMT 并启用虚拟机监视器
		中的所有缓解措施，即无条件刷新 L1D。

		SMT 控制与 L1D 刷新控制仍可在引导后通过 sysfs 接口进行。虚拟机监视器
		会在以潜在不安全配置（即启用 SMT 或禁用 L1D 刷新）启动第一个 VM 时
		发出警告。

  full,force	与 'full' 相同，但禁用 SMT 与 L1D 刷新的运行时控制。隐含
		'nosmt=force' 命令行选项。（即 sysfs 对 SMT 的控制被禁用。）

  flush		保持 SMT 启用并启用默认的虚拟机监视器缓解措施，即条件性刷新 L1D。

		SMT 控制与 L1D 刷新控制仍可在引导后通过 sysfs 接口进行。虚拟机监视器
		会在以潜在不安全配置（即启用 SMT 或禁用 L1D 刷新）启动第一个 VM 时
		发出警告。

  flush,nosmt	禁用 SMT 并启用默认的虚拟机监视器缓解措施，即条件性刷新 L1D。

		SMT 控制与 L1D 刷新控制仍可在引导后通过 sysfs 接口进行。虚拟机监视器
		会在以潜在不安全配置（即启用 SMT 或禁用 L1D 刷新）启动第一个 VM 时
		发出警告。

  flush,nowarn	与 'flush' 相同，但在以潜在不安全配置启动 VM 时虚拟机监视器不会
		发出警告。

  off		禁用虚拟机监视器缓解措施且不发出任何警告。
		它还会同时取消对虚拟机监视器与裸机双方的 swap 大小及可用 RAM 限制。
  ============  =============================================================

默认值为 'flush'。有关 L1D 刷新的详细信息参见 l1d_flush。



### KVM 的缓解控制 - 模块参数


KVM 虚拟机监视器的缓解机制——进入客户机时刷新 L1D 缓存——可以通过模块参数进行控制。

该选项/参数为 "kvm-intel.vmentry_l1d_flush="。它接受以下参数：

  ============  ==============================================================
  always	每次 VMENTER 时刷新 L1D 缓存。

  cond		仅在 VMEXIT 与 VMENTER 之间的代码可能泄露被认为对攻击者有价值的
		主机内存时，才在 VMENTER 时刷新 L1D。这仍可能泄露主机内存，从而
		（例如）可用于确定主机的地址空间布局。

  never	禁用该缓解措施
  ============  ==============================================================

该参数可在内核命令行上提供，作为加载模块时的模块参数，并可在运行时通过以下 sysfs 文件修改：

/sys/module/kvm_intel/parameters/vmentry_l1d_flush

默认值为 'cond'。如果在内核命令行上给定了 'l1tf=full,force'，则强制使用 'always'，并且 kvm-intel.vmentry_l1d_flush 模块参数被忽略，对该 sysfs 文件的写入也会被拒绝。


### 缓解措施选择指南


##### 1. 未使用虚拟化


   系统由内核无条件保护，无需采取进一步措施。

##### 2. 使用可信客户机的虚拟化


   如果客户机来自可信来源，且保证客户机操作系统内核已具备 L1TF 缓解措施，则系统已完全抵御 L1TF，无需采取进一步措施。

   为避免默认 VMENTER 时 L1D 刷新的开销，管理员可通过内核命令行与 sysfs 控制文件禁用刷新。参见 mitigation_control_command_line 与 mitigation_control_kvm。


##### 3. 使用不可信客户机的虚拟化


###### 3.1. 不支持或已禁用 SMT


  如果处理器不支持 SMT，或在 BIOS 或内核中已禁用 SMT，则只需强制在 VMENTER 时刷新 L1D。

  条件性 L1D 刷新是默认行为，且可调整。参见 mitigation_control_command_line 与 mitigation_control_kvm。

###### 3.2. 不支持或已禁用 EPT


  如果处理器不支持 EPT，或在虚拟机监视器中已禁用 EPT，则系统已完全受保护。SMT 可保持启用，且 VMENTER 时的 L1D 刷新并非必需。

  EPT 可在虚拟机监视器中通过 'kvm-intel.ept' 参数禁用。

###### 3.3. SMT 与 EPT 均受支持且处于活动状态


  如果 SMT 与 EPT 均受支持且处于活动状态，则可采取不同程度的缓解措施：

  - VMENTER 时刷新 L1D：

    VMENTER 时刷新 L1D 是最低保护要求，但它只有与其他缓解方法结合时才有效。

    条件性 L1D 刷新是默认行为，且可调整。参见 mitigation_control_command_line 与 mitigation_control_kvm。

  - 客户机限制：

    将客户机限制到未运行任何其他进程的单个或一组物理核上，可以显著减小攻击面，但中断、软中断与内核线程仍可能向潜在攻击者暴露有价值的数据。参见 guest_confinement。

  - 中断隔离：

    将客户机 CPU 与中断隔离可以进一步减小攻击面，但仍允许恶意客户机探查有限数量的主机物理内存。这至少可用于获取主机地址空间布局的信息。与运行不可信客户机的 CPU 固定亲和的中断，可能根据场景仍会触发软中断并调度可能暴露有价值信息的内核线程。参见 interrupt_isolation。

上述三种缓解方法结合可在一定程度上提供保护，但必须对剩余攻击面的风险进行仔细分析。为获得完全保护，可用以下方法：

  - 禁用 SMT：

    禁用 SMT 并强制 L1D 刷新可提供最大程度的保护。该缓解措施不依赖于上述任何缓解方法。

    SMT 控制与 L1D 刷新可通过命令行参数 'nosmt'、'l1tf'、'kvm-intel.vmentry_l1d_flush' 以及在运行时通过相应的 sysfs 控制文件进行调整。参见 smt_control、mitigation_control_command_line 与 mitigation_control_kvm。

  - 禁用 EPT：

    禁用 EPT 同样提供最大程度的保护。它不依赖于上述任何缓解方法。SMT 可保持启用，且无需 L1D 刷新，但性能影响显著。

    EPT 可在虚拟机监视器中通过 'kvm-intel.ept' 参数禁用。

###### 3.4. 嵌套虚拟机


使用嵌套虚拟化时，会涉及三个操作系统：裸机虚拟机监视器、嵌套虚拟机监视器与嵌套虚拟机。从嵌套虚拟机监视器进入嵌套客户机的 VMENTER 操作总是由裸机虚拟机监视器处理。如果 KVM 是裸机虚拟机监视器，它将：

 - 在每次从嵌套虚拟机监视器切换到嵌套虚拟机时刷新 L1D 缓存，以使嵌套虚拟机监视器的机密不被暴露给嵌套虚拟机；

 - 在每次从嵌套虚拟机切换到嵌套虚拟机监视器时刷新 L1D 缓存；这是一个复杂的操作，刷新 L1D 缓存可避免裸机虚拟机监视器的机密被暴露给嵌套虚拟机；

 - 指示嵌套虚拟机监视器不执行任何 L1D 缓存刷新。这是一个避免双重 L1D 刷新的优化。



### 默认缓解措施


  对于易受攻击的处理器，内核的默认缓解措施为：

  - 采用 PTE 反转（inversion）以防御恶意用户空间。此操作无条件执行且不可控制。swap 存储被限制为约 16TB。

  - 当为客户机启用 EPT 时，在 VMENTER 时进行 L1D 条件刷新。

  内核默认不强制禁用 SMT，这使得在启用 EPT 运行不可信客户机时，SMT 系统仍处于易受攻击状态。

  做出此选择的理由如下：

  - 强制禁用 SMT 可能会破坏现有配置，尤其是在无人值守更新的情况下。

  - 如果普通用户在其机器上运行不可信客户机，那么 L1TF 只是嵌入在不可信客户机中其他恶意软件（例如垃圾邮件机器人或对本地网络的攻击）的一个附加项。

    没有技术手段可以盲目地阻止用户在自己的机器上运行不可信代码。

  - 从技术上讲，通过 JavaScript 等最流行的攻击机制利用 L1TF 的可能性极低，且根据目前的认知甚至是不可能的，因为这些机制无法控制 PTE。如果这成为可能且没有可行的其他缓解措施，那么默认值可能会不同。

  - 云与托管环境的管理员必须仔细分析其场景的风险，并做出适当的缓解选择，这些选择甚至可能在其部署的机器之间存在差异，并导致整体配置的其他变更。内核无法为这类场景提供合理的默认值。
