
## 核心调度（Core Scheduling

核心调度支持允许用户空间定义可以共享一个核心的任务组。这些组既可以出于安全用例指定（一组任务不信任另一组），也可以出于性能用例指定（某些工作负载因为不需要共享核心的相同硬件资源，而可能受益于运行在同一核心上；或者如果它们确实需要共享硬件资源，则可能更倾向于不同的核心）。本文档仅描述安全用例

### 安全用例

跨超线程（cross-HT）攻击涉及攻击者和受害者运行在同一核心的不同超线程上。MDS L1TF 就是此类攻击的例子。对跨超线程攻击唯一彻底的缓解措施是禁用超线程（HT）。核心调度是一项调度器特性，可以缓解部分（并非全部）跨超线程攻击。它通过确保只有用户指定的受信任组中的任务才能共享一个核心，从而可以安全地开HT。这种核心共享的增加也能提升性能，但并不能保证性能总是会提升，尽管在许多真实工作负载中确实观察到这种情况。理论上，核心调度旨在至少达到与禁用超线程时一样好的表现。在实践中，多数情况下确实如此，但并非总是如此：因为在核心内的 2 个或更多 CPU 之间同步调度决策会带来额外开销——尤其是在系统负载较轻时。当 `total_threads <= N_CPUS/2` 时，额外的开销可能导致核心调度表现比禁SMT 时更差，其中 N_CPUS CPU 的总数。请务必对您的工作负载进行性能测量

### 用法

核心调度支持通过 `CONFIG_SCHED_CORE` 配置选项启用。使用该特性，用户空间定义可以共同调度到同一核心上的任务组。核心调度器利用这些信息来确保不在同一组中的任务永远不会同时运行在一个核心上，同时尽力满足系统的调度需求

核心调度可以通过 `PR_SCHED_CORE` prctl 接口启用。该接口为创建核心调度组提供支持，用
```

    #include <sys/prctl.h>

    int prctl(int option, unsigned long arg2, unsigned long arg3,
            unsigned long arg4, unsigned long arg5);

```
option:
    `PR_SCHED_CORE`

arg2:
    操作命令，必须是下列之一

    - `PR_SCHED_CORE_GET` —获取 `pid` core_sched cookie
    - `PR_SCHED_CORE_CREATE` —`pid` 创建一个新的唯一 cookie
    - `PR_SCHED_CORE_SHARE_TO` —core_sched cookie 推送给 `pid`
    - `PR_SCHED_CORE_SHARE_FROM` —`pid` 拉取 core_sched cookie

arg3:
    操作所适用的任务的 `pid`

arg4:
    操作所适用`pid_type`。它是以
    `PR_SCHED_CORE_SCOPE_` 为前缀的宏常量之一。例如，如果 arg4
    `PR_SCHED_CORE_SCOPE_THREAD_GROUP`，则该命令的操作将针`pid`
    的任务组中的所有任务执行

arg5:
    用户空间指向一unsigned long long 的指针，用于存储
    `PR_SCHED_CORE_GET` 命令返回cookie。对于所有其他命令应0

为了使一个进程能够向另一个进程推cookie 或从另一个进程拉cookie
需要对该进程具ptrace 访问模式：`PTRACE_MODE_READ_REALCREDS`

#### 构建任务层级结构

构建共享同一cookie 因而也共享一个核心的线程/进程层级结构，最简单的方法
利用核心调度 cookie 会在 fork/clone exec 之间被继承这一事实，因此为
“初始”脚可执行文守护进程设置一cookie，就会将其派生的每个子进
放入同一个核心调度组

#### Cookie 传

可以使用 PR_SCHED_CORE_SHARE_FROM PR_SCHED_CORE_SHARE_TO 在当前任务和其他
任务之间传cookie，从而从指定任务继承 cookie 或与某个任务共享 cookie
结合起来，这就允许一个简单的辅助程序从现有核心调度组中的某个任务拉取 cookie
并与已在运行的任务共享它

### 设计/实现

每个被打标签的任务在内核内部都会被赋予一cookie。如 `Usage`_ 所述，具有相同
cookie 值的任务被视为彼此信任并共享一个核心

基本思路是，每次调度事件都尝试为一个核心的所有兄弟线程选择任务，使得在任何时刻
运行在一个核心上的所有被选任务都是受信任的（相同cookie）。内核线程被视为受信任
空闲任务被视为特殊，因为它信任一切，且一切也都信任它

在核心的任意兄弟线程上发schedule() 事件时，如果该兄弟线程的就绪队列中有该任务，
则选取该兄弟线程核心上优先级最高的任务，并分配给调schedule() 的兄弟线程
对于核心中其余的兄弟线程，如果其各自的运行队列中有可运行的、具有相cookie 
最高优先级任务，则选取该任务。如果没有相cookie 的任务可用，则选取空闲任务
空闲任务全局受信任

一旦为核内所有兄弟线程都选定了任务，就会向那些被选中新任务的兄弟线程发送一IPI
收到 IPI 的兄弟线程会立即切换到新任务。如果为某个兄弟线程选中了空闲任务，则该兄弟线程
被视为处`forced idle`（强制空闲）状态。也就是说，它的运行队列上可能还有待运行的任务，
但它仍然必须运行空闲。下一节将详细介绍这一点

#### 超线程的强制空闲

调度器会尽力寻找彼此信任的任务，使得被选中进行调度的所有任务都是核心中优先级最高的
然而，可能存在某些运行队列中有与核心范围内最高优先级任务不兼容的任务的情况。为
安全优先于公平，如果最高优先级任务相对于核心范围内最高优先级任务不受信任，则一个或
多个兄弟线程可能被强制选择较低优先级的任务。如果一个兄弟线程没有受信任的任务可运行
它将被调度器强制空闲（调度空闲线程运行）

当最高优先级任务被选中运行时，会向兄弟线程发送一个重新调IPI 以强制其进入空闲
这会产生 4 种情况，需要根据运行的是虚拟机还是常规用户态进程来考虑
```

          HT1 (attack)            HT2 (victim)
   A      idle -> user space      user space -> idle
   B      idle -> user space      guest -> idle
   C      idle -> guest           user space -> idle
   D      idle -> guest           guest -> idle

```
请注意，为了更好的性能，我们不会等待目CPU（受害者）进入空闲模式。这是因为发IPI
会立即将目标 CPU 从用户空间带入内核模式，或者在客机的情况下触发 VMEXIT。充其量，这只会
泄漏一些调度器元数据，而这些数据可能不值得保护。在某些架构IPI 也可能接收得过晚
但在 x86 上尚未观察到这种情况

#### 信任模型

核心调度通过为任务组分配相同cookie 值作为标签，来维护任务组之间的信任关系
当启用了核心调度的系统启动时，所有任务都被视为彼此信任。这是因为在用户空间使用上述
接口来传达信任关系之前，核心调度器没有关于信任关系的信息。换句话说，所有任务的默认
cookie 值都0，并被视为系统范围内受信任。运cookie 0 的任务的兄弟线程的强制空
也被避免

一旦用户空间使用上述接口将任务集分组，这类组内的任务就被视为彼此信任，但不信任组外
任务。组外的任务也不信任组内的任务

### 核心调度的局限

核心调度试图保证只有受信任的任务才会同时运行在一个核心上。但可能存在一个很小的时间窗口
在此期间不受信任的任务会并发运行，或者内核可能与一个不受内核信任的任务并发运行

#### IPI 处理延迟

核心调度只选择受信任的任务一起运行。IPI 用于通知兄弟线程切换到新任务。但在某些架构上
接收 IPI 可能存在硬件延迟（在 x86 上尚未观察到）。这可能导致攻击者任务在其兄弟线程收
IPI 之前就开始在某个 CPU 上运行。尽管在进入用户模式时会刷新缓存，但兄弟线程上的受害者任
可能在攻击者开始运行之后向缓存和微体系结构缓冲区中填入数据，这就存在数据泄漏的可能性

### 核心调度未能解决的跨超线程开放问

#### 1. 针对 MDS

核心调度无法防御运行在用户模式的兄弟线程与运行在内核模式的其它兄弟线程之间的 MDS 攻击
尽管所有兄弟线程运行的任务彼此信任，但当内核代表某个任务执行代码时，它无法信任在兄弟线程上
运行的代码。此类攻击对于任何兄CPU 模式组合（宿主机或客机模式）都是可能的

#### 2. 针对 L1TF

核心调度无法防御利用客机或宿主机受害者的 L1TF 客机攻击者。这是因为客机攻击者可以构造无效的
PTE，而由于存在漏洞的客机内核，这PTE 不会被反转。唯一的解决方法是禁用 EPT（扩展页表）

对于 MDS L1TF，如果客vCPU 被配置为彼此不信任（通过分别打标签），那么客机到客机的攻击就
消失。或者，也可以将客机到客机的攻击视为客机自身的问题，作为系统管理员策略

另一种解决这些问题的思路是，让系统上每个不受信任的任务都不信任其他任何不受信任的任务
虽然这会降低不受信任任务的并行度，但它仍然能解决上述问题，同时允许系统进程（受信任任务）
共享一个核心

#### 3. 保护内核（IRQ、系统调用、VMEXIT

遗憾的是，核心调度不能保护运行在兄弟超线程上的内核上下文彼此不受攻击。已有缓解措施的原型
发布LKML 以解决此问题，但这类窗口在实际上是否可被利用、以及原型的性能开销是否值得
（更不用说增加的代码复杂性），都存在争议

### 其他用例

核心调度的主要用例是在启SMT 的情况下缓解跨超线程漏洞。该特性还可用于其他用例：

- 隔离需要整个核心的任务：例如实时任务、使SIMD 指令的任务等
- 群组调度（Gang scheduling）：一组需要一起调度的任务的需求，也可以通过核心调度实现
  一个例子是虚拟机的 vCPU
