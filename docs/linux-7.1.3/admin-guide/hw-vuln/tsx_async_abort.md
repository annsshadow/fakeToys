
## TAA - TSX 异步中止

TAA 是一种硬件漏洞，它允许利用 Intel TSX 事务区域内发生的异步中止，
对各类 CPU 内部缓冲区中可用的数据进行无特权的推测性访问。

### 受影响的处理器


该漏洞仅影响支持 Intel 事务同步扩展（TSX）且在 IA32_ARCH_CAPABILITIES
MSR 中 TAA_NO 位（第 8 位）为 0 的 Intel 处理器。在
IA32_ARCH_CAPABILITIES MSR 中 MDS_NO 位（第 5 位）为 0 的处理器上，
现有的 MDS 缓解措施同样也能缓解 TAA。

处理器是否受影响可从 sysfs 中的 TAA 漏洞文件中读出。参见
tsx_async_abort_sys_info。

### 相关 CVE


以下 CVE 条目与本 TAA 问题相关：

   ==============  =====  ===================================================
   CVE-2019-11135  TAA    在某些利用推测执行的微处理器上，TSX 异步中止（TAA）
                          条件可能允许经身份验证的用户通过具有本地访问权限
                          的旁路信道，潜在地实现信息泄露。
   ==============  =====  ===================================================

### 问题


在执行存储、加载或 L1 填充操作时，处理器会将数据写入临时的微体系结构
结构（缓冲区）中。出于优化目的，这些缓冲区中的数据可以被转发给加载
操作。

Intel TSX 是对 x86 指令集架构的扩展，增加了硬件事务内存支持，以提升
多线程软件的性能。TSX 让处理器能够暴露并利用应用程序中由于动态避免
不必要的同步而隐藏的并发性。

TSX 支持原子内存事务，这些事务要么提交（成功），要么中止。在中止期间，
事务区域内发生的操作会被回滚。除其他情况外，当另一个线程访问了同样
用于事务区域的缓存行、且该访问可能导致数据竞争时，就会发生异步中止。

在一场未完成的异步中止之后，某些被推测执行的加载可能会从那些内部
缓冲区中读取数据，并将其传递给依赖操作。随后就可以利用缓存旁路信道
攻击来推断该值。

由于这些缓冲区可能在超线程之间共享，因此存在跨超线程攻击的可能。

恶意行为者的受害者无需使用 TSX。只有攻击者需要发起一个 TSX 事务并
引发异步中止，而这反过来可能泄露存储在缓冲区中的数据。

更详细的技术信息可在 TAA 专用的 x86 架构章节中找到：
Documentation/arch/x86/tsx_async_abort.rst <tsx_async_abort>。


### 攻击场景


针对 TAA 漏洞的攻击可以从运行在宿主机或客户机上的无特权应用程序发起。

与 MDS 一样，攻击者无法控制可能被泄露的内存地址。只有受害者负责将数据
带入 CPU。因此，恶意行为者必须尽可能多地采样数据，然后进行后处理，试图
从中推断出任何有用信息。

潜在的攻击者只对这些数据拥有读访问权限。此外，使用此技术不会导致直接
的权限提升。


### TAA 系统信息


Linux 内核提供了一个 sysfs 接口，用于枚举已缓解系统的当前 TAA 状态。
相关的 sysfs 文件是：

/sys/devices/system/cpu/vulnerabilities/tsx_async_abort

该文件中可能的值有：


   - - 'Vulnerable'
     - CPU 受此漏洞影响，且未应用微码和内核缓解措施。
   - - 'Vulnerable: Clear CPU buffers attempted, no microcode'
     - 处理器存在漏洞，但微码未更新。缓解措施以尽力而为的方式启用。

       如果处理器存在漏洞，但通过 CPUID 并未通告基于微码的缓解机制
       的可用性，内核会选择尽力而为的缓解模式。该模式调用缓解指令，
       但并不保证它们能清空 CPU 缓冲区。

       这样做是为了应对虚拟化场景：宿主机已应用微码更新，但虚拟机
       监控器尚未更新以向客户机暴露 CPUID。如果宿主机已更新微码，
       保护即生效；否则只会无意义地浪费几个 CPU 周期。
   - - 'Mitigation: Clear CPU buffers'
     - 微码已更新以清空缓冲区。TSX 仍处于启用状态。
   - - 'Mitigation: TSX disabled'
     - TSX 已禁用。
   - - 'Not affected'
     - CPU 不受此问题影响。

### 缓解机制


内核会检测受影响的 CPU 以及所需的微码是否存在。如果 CPU 受影响且微码
可用，内核默认启用缓解措施。


可以通过内核命令行选项在引导时控制缓解措施。参见
taa_mitigation_control_command_line。

##### 虚拟化缓解


受影响的系统，如果宿主机的 TAA 微码已就绪、且 TAA 先前已通过禁用 TSX
得到缓解，则无论 VM 状态如何都不存在漏洞。

在所有其他情况下，如果宿主机要么没有 TAA 微码，要么内核未缓解，则系统
可能仍存在漏洞。


### 内核命令行上的缓解控制


内核命令行允许通过 "tsx_async_abort=" 选项在引导时控制 TAA 缓解措施。
该选项的有效参数为：

  ============  =============================================================
  off		  此选项在受影响的平台上禁用 TAA 缓解。如果系统启用了 TSX
                （见下一个参数）且 CPU 受影响，则系统存在漏洞。

  full	          TAA 缓解已启用。如果启用了 TSX，在受影响的系统上，它会在
                环切换时清空 CPU 缓冲区。在受 MDS 影响并部署了 MDS 缓解的
                系统上，TAA 也得到了缓解。在这些系统上指定此选项不会有
                任何效果。

  full,nosmt    与 tsx_async_abort=full 相同，但在启用了 TSX 的受影响 CPU
                上禁用 SMT。这是完整的缓解措施。当 TSX 被禁用时，不禁用
                SMT，因为 CPU 不易受跨线程 TAA 攻击。
  ============  =============================================================

不指定此选项等同于 "tsx_async_abort=full"。对于同时受 TAA 和 MDS 影响的
处理器，仅仅指定 "tsx_async_abort=off" 而不附带 "mds=off" 不会有任何
效果，因为这两种漏洞使用的是相同的缓解措施。

内核命令行还允许在使用支持 TSX 控制的 "tsx=" 参数来控制 TSX 特性。
MSR_IA32_TSX_CTRL 用于控制 TSX 特性以及 CPUID 中 TSX 特性位（RTM 和 HLE）
的枚举。

有效选项为：

  ============  =============================================================
  off		  禁用系统上的 TSX。

                注意，此选项仅在不受 MDS 影响（即
                MSR_IA32_ARCH_CAPABILITIES.MDS_NO=1）并通过微码更新获得
                新的 IA32_TSX_CTRL MSR 的较新 CPU 上生效。这个新的 MSR
                允许可靠地停用 TSX 功能。

  on		  启用 TSX。

                尽管针对所有已知安全漏洞都有缓解措施，但 TSX 曾被视为
                多个先前与推测相关的 CVE 的加速器，因此保持启用可能
                存在未知的安全风险。

  auto		  如果存在 X86_BUG_TAA，则禁用 TSX，否则在系统上启用 TSX。
  ============  =============================================================

不指定此选项等同于 "tsx=off"。

"tsx_async_abort" 和 "tsx" 的以下组合是可能的。对于受影响的平台，
tsx=auto 等同于 tsx=off，结果将是：

  =========  ==========================   =========================================
  tsx=on     tsx_async_abort=full         系统将使用 VERW 来清空 CPU 缓冲区。
                                          在 SMT 机器上跨线程攻击仍然可能。
  tsx=on     tsx_async_abort=full,nosmt   同上，SMT 上的跨线程攻击得到缓解。
  tsx=on     tsx_async_abort=off          系统存在漏洞。
  tsx=off    tsx_async_abort=full         如果微码提供 TSX 控制 MSR，TSX 可能
                                          被禁用。若如此，系统不存在漏洞。
  tsx=off    tsx_async_abort=full,nosmt   同上
  tsx=off    tsx_async_abort=off          ditto
  =========  ==========================   =========================================


对于不受影响的平台，"tsx=on" 和 "tsx_async_abort=full" 不会清空 CPU
缓冲区。对于没有 TSX 控制（MSR_IA32_ARCH_CAPABILITIES.MDS_NO=0）的平台，
"tsx" 命令行参数没有任何效果。

对于受影响的平台，下表指出了 CPUID 位 MD_CLEAR 与 IA32_ARCH_CAPABILITIES
MSR 位 MDS_NO 和 TSX_CTRL_MSR 各种组合下的缓解状态。

  =======  =========  =============  ========================================
  MDS_NO   MD_CLEAR   TSX_CTRL_MSR   Status
  =======  =========  =============  ========================================
    0          0            0        Vulnerable (needs microcode)
    0          1            0        MDS 和 TAA 通过 VERW 缓解
    1          1            0        MDS 已修复，若 TSX 启用则 TAA 仍存在漏洞
                                     因为 MD_CLEAR 无意义且 VERW 不保证
                                     清空缓冲区
    1          X            1        MDS 已修复，TAA 可通过 VERW 或
                                     TSX_CTRL_MSR 缓解
  =======  =========  =============  ========================================

### 缓解选择指南


##### 1. 可信的用户空间和客户机


如果所有用户空间应用程序都来自可信来源，并且不执行外部提供的不可信
代码，那么可以禁用缓解措施。对于拥有可信客户机的虚拟化环境同样适用。


##### 2. 不可信的用户空间和客户机


如果系统上存在不可信的应用程序或客户机，启用 TSX 可能允许恶意行为者
从宿主机或运行在同一物理核心上的其他进程泄露数据。

如果微码可用且在宿主机上禁用了 TSX，那么在虚拟化环境中也能防止攻击，
即使 VM 没有明确启用缓解措施。


### 默认缓解措施


内核对受影响处理器的默认操作是：

  - 部署 TSX 禁用缓解（tsx_async_abort=full tsx=off）。
