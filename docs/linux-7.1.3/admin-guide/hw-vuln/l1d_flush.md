## L1D 刷新


随着围绕一级数据缓存（L1D）数据泄漏报告的漏洞数量不断增加，内核提供了一种
可选择启用的机制，用于在上下文切换时刷新 L1D 缓存。

该机制可用于应对例如 CVE-2020-0550。对于应用程序，该机制可使其免受与 L1D
缓存泄漏（嗅探）相关的漏洞影响。


### 相关 CVE


以下 CVE 可由该机制应对

    =============       ========================     ==================
    CVE-2020-0550       不当的数据转发             与操作系统相关的方面
    =============       ========================     ==================

### 使用指南


详见文档：:ref:`Documentation/userspace-api/spec_ctrl.rst
<set_spec_ctrl>`。

**注意**：该特性默认关闭，应用程序需要显式选择启用该特性才能开启它。

### 缓解措施


当为某个任务启用了 PR_SPEC_L1D_FLUSH 时，会在该任务被调度出去、且进入的任务
属于另一个进程（因而属于另一个地址空间）时执行 L1D 缓存刷新。

如果底层 CPU 在硬件层面支持 L1D 刷新，则使用硬件机制；该缓解措施的软件回退
不受支持。

### 内核命令行上的缓解控制


内核命令行允许在启动时通过 "l1d_flush=" 选项控制 L1D 刷新缓解。该选项的有效
参数为：

  ============  =============================================================
  on            启用 prctl 接口；若 l1d_flush 未启用，尝试使用 prctl() 的
                应用程序将以错误失败
  ============  =============================================================

默认情况下该机制是关闭的。

### 局限性


当系统启用 SMT 时，该机制不能缓解属于不同进程、但在物理 CPU 核心的兄弟线程上
并发执行的任务之间的 L1D 数据泄漏。

这可通过将进程受控地放置到物理 CPU 核心上，或通过禁用 SMT 来应对。参见 L1TF
缓解文档中的相关章节：Documentation/admin-guide/hw-vuln/l1tf.rst <smt_control>。

**注意**：任务对 L1D 刷新的选择启用仅在任务的亲和性被限制为运行于非 SMT 模式的
核心时有效。如果请求了 L1D 刷新的任务被调度到启用了 SMT 的核心上，内核会向其
发送一个 SIGBUS。
