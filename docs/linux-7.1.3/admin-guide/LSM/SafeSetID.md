## SafeSetID


SafeSetID 是一个 LSM 模块，它对 setid 系列的 syscalls 进行门控，以将给定 UID/GID 的
转换限制为仅允许系统范围允许列表中所批准的目标。这些限制还禁止给定 UIDs/GIDs 获得与
CAP_SET{U/G}ID 相关的辅助特权，例如允许用户建立用户命名空间 UID/GID 映射。

## 背景


在没有文件能力（file capabilities）的情况下，Linux 系统上需要切换到不同用户而派生的
进程必须以 CAP_SETUID 特权派生。CAP_SETUID 被授予以 root 身份运行的程序，或被显式赋予
CAP_SETUID 运行时能力的非 root 用户运行的程序。通常更可取的做法是使用 Linux 运行时能力
而非文件能力，因为使用文件能力以提升的特权运行程序会打开可能的安全漏洞，因为任何能
访问该文件的用户都可以 exec() 该程序来获得提升的特权。

虽然可以通过赋予完整的 CAP_SET{U/G}ID 能力来实现一个进程树，但这往往与最初在非 root
用户下运行进程树的目标相冲突。具体来说，由于 CAP_SETUID 允许切换到系统上的任何用户，
包括 root 用户，对于这个场景来说它是过度强大的能力，特别是因为程序通常只调用 setuid()
来放弃特权到一个特权更低的用户——而不是提升特权。不幸的是，在 Linux 中没有普遍可行的
方法可以限制用户通过 setuid() 能够切换到的潜在 UID，只能允许切换到系统上的任何用户。
这个 SafeSetID LSM 正是试图提供一种限制 setid 能力的方式。

该 LSM 的主要用例是允许一个非 root 程序过渡到其他不受信任的 uid，而无需完整的
CAP_SETUID 能力。该非 root 程序仍然需要 CAP_SETUID 来进行任何过渡，但该 LSM 施加的
额外限制意味着它是 CAP_SETUID 的一个"更安全"版本，因为非 root 程序无法利用 CAP_SETUID
来进行任何未经批准的操作（例如 setuid 到 uid 0 或创建/进入新的用户命名空间）。更高
层次的目标是允许基于 uid 的系统服务沙箱化，而无需到处发放 CAP_SETUID，仅仅是为了让非
root 程序能够下降到特权更低的 uid。当系统上一个非 root 守护进程应该被允许以不同的 uid
派生其他进程，但又不希望赋予该守护进程一个基本等同于 root 的 CAP_SETUID 时，这一点
尤其相关。

## 考虑过的其他方法


### 在用户空间解决此问题


对于希望拥有如本 LSM 所实现的受限 setid 能力的目标应用程序，另一种选择是完全从应用
程序中移除 setid 能力，并重构应用程序中的进程派生语义（例如通过使用特权辅助程序来进行
进程派生和 UID/GID 过渡）。不幸的是，这会影响到许多围绕进程派生的语义，例如程序在
fork() 之后不立即调用 exec() 的调用、父进程为派生的子进程指定自定义环境变量或命令行
参数，或者在 fork()/exec() 之间继承文件句柄。因此，在用户空间使用特权辅助程序的
解决方案对于依赖 Linux 中某些进程派生语义的现有项目来说可能不太有吸引力。

### 使用用户命名空间


另一种可能的方法是在其自己的用户命名空间中运行给定的进程树，并赋予树中的程序 setid
能力。这样，树中的程序可以切换到其自身用户命名空间上下文中任何期望的 UID/GID，并且
只有经过批准的 UIDs/GIDs 可以被映射回初始系统用户命名空间，从而有效防止权限提升。
不幸的是，通常无法孤立地使用用户命名空间而不将其与其他命名空间类型配对，而这并不总是
一个选项。Linux 基于"拥有"某个实体的用户命名空间来检查能力。例如，Linux 有网络命名空间
由创建它们的用户命名空间拥有的概念。这样做的一个后果是，对给定网络命名空间的访问能力
检查是通过检查任务在其所拥有该网络命名空间的用户命名空间上下文中是否拥有给定能力来
完成的——而不一定是给定任务所运行的用户命名空间。因此在新用户命名空间中派生进程会
有效阻止其访问由初始命名空间拥有的网络命名空间。对于任何期望保留 CAP_NET_ADMIN 能力
以调整网络配置的应用程序来说，这都是致命问题。孤立使用用户命名空间会在其他系统交互
方面造成问题，包括 pid 命名空间的使用和设备创建。

### 使用现有 LSM


其他任何树内 LSM 都没有能力门控 setid 过渡，甚至根本没有使用 security_task_fix_setuid
钩子。SELinux 关于该钩子说道："由于 setuid 只影响当前进程，并且由于 SELinux 控制不基于
Linux 身份属性，SELinux 不需要控制此操作。"

## 使用指引


该 LSM 钩住 setid syscalls，以确保在有适用的限制策略到位时，过渡是被允许的。策略通过
securityfs 配置，方法是写入 securityfs 挂载位置处的 safesetid/uid_allowlist_policy 和
safesetid/gid_allowlist_policy 文件。添加策略的格式为 '<UID>:<UID>' 或 '<GID>:<GID>'，
使用字面数字，并以换行符结尾，例如 '123:456\n'。写入空字符串 "" 将刷新策略。再次强调，
为 UID/GID 配置策略将阻止该 UID/GID 获得辅助 setid 特权，例如允许用户建立用户命名空间
UID/GID 映射。

## 关于 GID 策略和 setgroups() 的说明


在 v5.9 中，我们添加了对限制 CAP_SETGID 特权的支持，正如之前对 CAP_SETUID 所做的那样。
然而，为了与用户空间中常见的沙箱相关代码约定兼容，我们目前允许具有 CAP_SETGID 限制的
进程进行任意的 setgroups() 调用。在我们于未来版本中添加对限制 setgroups() 调用的支持
之前，这些 GID 策略不提供有意义的安全性。一旦我们具备了策略检查代码，setgroups() 限制
将被强制执行，这将依赖于 v5.9 中添加的 GID 策略配置代码。
