
报告回归问题
+++++++++++++++++++++

"**我们不会引入回归问题**" 是 Linux 内核开发的第一准则；这一准则由 Linux
创始人兼首席开发者 Linus Torvalds 亲自确立，并确保其得到遵守。

本文档说明了该准则对用户意味着什么，以及 Linux 内核的开发模式如何确保所有
已报告的回归问题都得到处理；与内核开发者相关的方面留给
Documentation/process/handling-regressions.rst。


## 要点（即"太长不看"）


#. 如果某样东西在某个 Linux 内核上运行良好，但在更新的版本上表现变差或
   完全无法运行，那就是回归问题。注意，较新的内核必须使用类似的配置编译；
   下面的详细说明会更详细地解释这一点以及其他细节。

#. 按照 Documentation/admin-guide/reporting-issues.rst 中所述的方式报告你的问题，
   该文档已经涵盖了回归问题相关的所有重要方面，为方便起见下面也会重复。
   其中两点很重要：在报告的主题行以 "[REGRESSION]" 开头，并抄送或转发到
   `回归邮件列表 <https://lore.kernel.org/regressions/>`_
   (regressions@lists.linux.dev)。

#. 可选但推荐：在发送或转发报告时，让 Linux 内核回归跟踪机器人 "regzbot"
   通过指定以下内容来跟踪该问题

```
       #regzbot introduced: v5.13..v5.14-rc1


```
## 与用户相关的 Linux 内核回归问题的全部细节


### 重要的基础知识



#### 什么是"回归问题"，什么是"不引入回归"准则？


如果某个在一款 Linux 内核上运行良好的应用程序或实际用例，在使用相似配置
编译的更新版本上表现变差或完全无法运行，那就是回归问题。"不引入回归"准则
禁止这种情况发生；如果意外发生，引发该问题的开发者应当尽快修复。

因此，当来自 Linux 5.13 的某个 WiFi 驱动工作正常，但在 5.14 上完全无法工作、
速度明显变慢，或以某种方式出现异常行为时，这就是回归问题。如果本来运行完美
的应用程序在新内核版本上突然表现出不稳定行为，这也是回归问题；这类问题可能
由 procfs、sysfs 或 Linux 提供给用户空间软件的许多其他接口中的变更引起。但
请记住，如前所述：本例中的 5.14 需要使用与 5.13 相似的配置构建。这可以通过
`make olddefconfig` 实现，下文会有更详细的解释。

注意本节第一句话中的"实际用例"：尽管有"不引入回归"准则，开发者仍可自由更改
内核的任何一个方面，甚至包括提供给用户空间的 API 或 ABI，只要没有破坏现有的
应用程序或用例即可。

还要意识到，"不引入回归"准则只覆盖内核提供给用户空间的接口。因此它不适用于
内核内部接口，例如某些外部开发的驱动用来挂接到内核的模块 API。

#### 如何报告回归问题？


只需按照 Documentation/admin-guide/reporting-issues.rst 中所述的方式报告问题，
该文档已经描述了要点。其中以下几点与回归问题尤其相关：

 - 在查找可加入的现有报告时，也要搜索 `Linux 回归邮件列表的存档
   <https://lore.kernel.org/regressions/>`_ 以及
   `regzbot 的 Web 界面 <https://linux-regtracking.leemhuis.info/regzbot/>`_。

 - 在报告的主题行以 "[REGRESSION]" 开头。

 - 在报告中，清楚说明最后一个正常工作以及第一个出现问题的内核版本。理想情况
   下，尽量使用二分法找到导致回归的确切变更，下文会有更详细的解释。

 - 记得让 Linux 回归邮件列表 (regressions@lists.linux.dev) 知道你的报告：

   - 如果你通过邮件报告回归问题，请抄送回归邮件列表。

   - 如果你将回归问题报告到某个缺陷跟踪器，请将提交的报告通过邮件转发给回归
     邮件列表，同时抄送相关子系统的维护者和邮件列表。

   如果是某个 stable 或 longterm 系列内部的回归（例如 v5.15.3..v5.15.5），
   记得抄送 `Linux stable 邮件列表 <https://lore.kernel.org/stable/>`_
   (stable@vger.kernel.org)。

   如果你成功进行了二分，请将 culprit 提交信息中以 "Signed-off-by:" 开头的
   行里提到的每个人都加入抄送。

在抄送以将报告转发到邮件列表时，考虑直接告诉上述 Linux 内核回归跟踪机器人你的
报告。为此，请

```
       #regzbot introduced: v5.13..v5.14-rc1

```
regzbot 随后会将你的邮件视为在指定版本范围内引入的回归报告。在上述例子中，
Linux v5.13 仍然工作正常，而 Linux v5.14-rc1 是你遇到该问题的第一个版本。如果
你通过二分法找到了导致回归的提交，请指定

```
       #regzbot introduced: 1f2e3d4c5d

```
放置这样的"regzbot 命令"符合你的利益，因为它能确保报告不会被忽视而石沉大海。
如果你省略它，只要向回归邮件列表发送一份副本，Linux 内核的回归跟踪器就会负责
通知 regzbot 你的回归问题。但回归跟踪器只是一个人，他有时需要休息，偶尔甚至
可能乐于远离电脑一段时间（尽管这听起来有些疯狂）。因此依赖此人会导致不必要的
延迟，在回归问题被提及到 `Linux 内核已跟踪且未解决的回归列表
<https://linux-regtracking.leemhuis.info/regzbot/>`_ 以及 regzbot 发送的每周
回归报告之前。这种延迟可能导致 Linus Torvalds 在决定"继续开发还是宣告完成并
发布最终版本？"时对重要的回归问题一无所知。

#### 真的所有回归问题都会被修复吗？


只要可靠地识别出导致回归的变更（"culprit 提交"），几乎都会被修复。有些回归
问题无需此信息也能修复，但这通常是必需的。

#### 谁来查找回归问题的根本原因？


受影响代码区域的开发者应当尝试自行定位 culprit。但对他们来说，这通常很难以
合理的代价完成，因为相当多的问题只发生在开发者无法触及的特定环境中——例如
特定的硬件平台、固件、Linux 发行版、系统配置或应用程序。这就是为什么最终往往
要由报告者来定位 culprit 提交；有时用户甚至可能需要事后运行额外的测试以精确定位
根本原因。开发者应当在力所能及的范围内提供建议和合理帮助，使这一过程对普通用户
来说相对轻松且可行。

#### 如何找到 culprit？


执行二分，大致如 Documentation/admin-guide/reporting-issues.rst 所述，并在
Documentation/admin-guide/bug-bisect.rst 中有更详细的描述。这听起来工作量很大，
但在许多情况下能相对快速地找到 culprit。如果可靠地复现该问题很困难或耗时，
考虑与其他受影响的用户合作，共同缩小搜索范围。

#### 遇到回归问题时我可以向谁寻求建议？


发送邮件到回归邮件列表 (regressions@lists.linux.dev)，同时抄送 Linux 内核的
回归跟踪器 (regressions@leemhuis.info)；如果问题更适合私下处理，可以省略邮件列表。


### 关于回归问题的额外细节



#### "不引入回归"准则的目标是什么？


用户更新内核版本时应当感到安全，不必担心某些东西可能损坏。这符合内核开发者的
利益，使更新具有吸引力：他们不希望用户停留在已被放弃或超过一年半之久的 stable
或 longterm Linux 系列上。这符合每个人的利益，因为 `那些系列可能存在已知缺陷、
安全问题或已在后续版本中修复的其他问题
<http://www.kroah.com/log/blog/2018/08/24/what-stable-kernel-should-i-use/>`_。
此外，内核开发者希望让用户测试和尝试最新的预发布或正式发布变得简单且有吸引力。
这也符合每个人的利益，因为如果在问题被引入后不久就报告，追踪和修复问题要容易
得多。

#### 实践中真的遵守"不引入回归"准则吗？


这一准则被非常认真地对待，从 Linux 创建者兼首席开发者 Linus Torvalds 的许多
邮件列表帖子中可以看出，其中一些被引用在
Documentation/process/handling-regressions.rst 中。

该准则的例外极其罕见；过去当开发者认为特定情况有理由破例时，几乎总是被证明是
错误的。

#### 谁来确保"不引入回归"准则真正得到遵守？


子系统维护者应当负责此事，他们受到树维护者的关注和支持——例如 Linus Torvalds
负责 mainline，Greg Kroah-Hartman 等人负责各种 stable/longterm 系列。

他们所有人都得到一些人的帮助，这些人努力确保没有任何回归报告被忽视。其中之一
是 Thorsten Leemhuis，他目前担任 Linux 内核的"回归跟踪器"；为便于这项工作，他
依赖 regzbot，即 Linux 内核回归跟踪机器人。这就是为什么你希望通过抄送或转发每份
报告到回归邮件列表，让这些人注意到你的报告，理想情况下在邮件中带上"regzbot 命令"
以便立即被跟踪。

#### 回归问题通常修复得有多快？


开发者应当尽快修复任何已报告的回归问题，以便及时为受影响的用户提供解决方案，
并防止更多用户遇到该问题；尽管如此，开发者需要留出足够的时间和谨慎，以确保回归
修复不会造成额外的损害。

因此答案取决于各种因素，例如回归的影响、其存在时间，或它出现的 Linux 系列。但
归根结底，大多数回归问题应在两周内得到修复。

#### 如果问题可以通过更新某些软件来避免，这算回归吗？


几乎总是：算。如果开发者告诉你并非如此，请按上文所述向回归跟踪器寻求建议。

#### 如果较新的内核运行更慢或消耗更多能源，这算回归吗？


算，但差异必须显著。因此微基准测试中百分之五的减速不太可能算作回归，除非它也
使广泛基准测试的结果变化超过百分之一。如有疑问，请寻求建议。

#### 如果更新 Linux 时某个外部内核模块损坏，这算回归吗？


不算，因为"不引入回归"准则针对的是 Linux 内核提供给用户空间的接口和服务。因此
它不涵盖构建或运行外部开发的内核模块，因为它们运行在内核空间，并使用偶尔会
变更的内部接口挂接到内核。

#### 由安全修复引起的回归如何处理？


在极少数情况下，安全问题无法在不引起回归的情况下修复；这些修复会被放行，因为
归根结底它们是较小的危害。幸运的是，这种情况几乎总是可以避免，因为受影响区域的
关键开发者，通常还有 Linus Torvalds 本人，都会非常努力地在不引起回归的情况下
修复安全问题。

尽管如此，如果你遇到这种情况，请检查邮件列表存档，看人们是否已经尽力避免该回归。
如果没有，请报告；如有疑问，请按上文所述寻求建议。

#### 如果修复一个回归问题不可避免地会引起另一个，会怎样？


遗憾的是这种事情会发生，但幸运的是并不经常；如果发生，受影响代码区域的专家
开发者应当调查该问题，以找到一种避免回归或至少减轻其影响的修复方案。如果你遇到
这种情况，请按照已经为安全修复引起的回归所概述的做法：检查先前的讨论，看人们
是否已经尽力，如有疑问请寻求建议。

顺便一提：如果人们能在每个开发周期中定期测试 mainline 的预发布版本（比如
v5.15-rc1 或 -rc3），这些情况本可以避免。最好的解释是设想一个在 Linux v5.14
和 v5.15-rc1 之间合入的变更引起了回归，但同时又是为了 5.15-rc1 而引入的某项
其他改进所硬性要求的。如果有人在 5.15 发布前发现并报告了它，所有这些变更通常
可以简单地被回退，从而解决回归问题。几天或几周后，这种解决方案可能变得不可能，
因为某些软件可能已经开始依赖后续某次变更引入的方面：回退所有变更随后会导致
该软件用户遇到回归，因此不在考虑之列。

#### 如果我依赖的某个功能在数月前被移除，这算回归吗？


算，但由于上一节所述的方面，这类回归往往难以修复。因此需要根据具体情况具体处理。
这是另一个为什么定期测试 mainline 预发布版本符合每个人利益的理由。

#### 如果我看起来是唯一受影响的人，"不引入回归"准则是否仍然适用？


适用，但仅针对实际用途：Linux 开发者希望可以自由地移除对只存在于阁楼和博物馆中
的硬件的支持。

注意，有时为了取得进展，回归无法避免——而后者是防止 Linux 停滞所必需的。因此，
如果似乎只有极少数用户受某个回归影响，为了更大的利益，放任其通过可能符合他们
和所有人的利益。特别是如果存在某种简单的变通方法，例如更新某些软件或使用专为
此目的而创建的内核参数。

#### 回归准则是否也适用于 staging 树中的代码？


根据 `覆盖所有 staging 代码的配置选项的帮助文本
<https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/drivers/staging/Kconfig>`_，

```
       Please note that these drivers are under heavy development, may or
       may not work, and may contain userspace interfaces that most likely
       will be changed in the near future.

```
尽管如此，staging 开发者通常也遵守"不引入回归"准则，但有时会为了取得进展而
放宽它。例如，当 staging 树中的一个 WiFi 驱动被从头编写的完全不同的驱动替换时，
一些用户不得不处理（通常可忽略的）回归。

#### 为什么较新版本必须"使用相似的配置编译"？


因为 Linux 内核开发者有时会合入已知会引起回归的变更，但将其设为可选，并在内核的
默认配置中禁用它们。这一技巧允许取得进展，否则"不引入回归"准则会导致停滞。

例如考虑一个新的安全特性，它阻止访问常被恶意软件滥用的某些内核接口，而这些接口
同时又是运行少数不常用应用程序所必需的。上述方法让两派都满意：使用这些应用程序
的人可以关闭新安全特性，而其他人可以启用它而不会遇到麻烦。

#### 如何创建与旧内核相似的配置？


用已知良好的内核启动机器，并使用 `make olddefconfig` 配置较新的 Linux 版本。这
会让内核的构建脚本将正在运行的内核的配置文件（".config" 文件）作为你即将编译的
新内核的基础；之后它们将所有新的配置选项设为默认值，这应当会禁用可能引起回归的
新特性。

#### 我可以用预编译的 vanilla 内核报告回归问题吗？


你需要确保较新的内核使用了与较旧内核相似的配置文件编译（见上文），因为构建它们
的人可能为较新的内核启用了某些已知不兼容的特性。如有疑问，请向内核提供者报告
此事并寻求建议。


### 更多关于使用 "regzbot" 进行回归跟踪


#### 什么是回归跟踪，为什么我应该在意它？


像"不引入回归"这样的准则需要有人确保它们被遵守，否则它们会被意外或有意地破坏。
历史表明，这对 Linux 内核开发同样适用。这就是为什么 Linux 内核的回归跟踪器
Thorsten Leemhuis 以及一些人会跟踪所有回归，直到它们被解决。他们都没有因此获得
报酬，所以这项工作是在尽最大努力的基础上完成的。

#### 为什么以及如何使用机器人跟踪 Linux 内核回归问题？


由于 Linux 内核开发过程的分布式和松散结构化特性，完全手动跟踪回归问题被证明相当
困难。这就是为什么 Linux 内核的回归跟踪器开发了 regzbot 以便于这项工作，其长期
目标是尽可能地为所有相关人员自动化回归跟踪。

regzbot 通过观察对被跟踪回归报告的回复来工作。此外，它还会留意引用了此类报告
的 "Link:" 标签的已发布或已提交补丁；对此类补丁发布的回复也会被跟踪。这些数据的
结合提供了对修复过程当前状态的良好洞察。

#### 如何查看 regzbot 当前跟踪哪些回归？


查看 `regzbot 的 Web 界面 <https://linux-regtracking.leemhuis.info/regzbot/>`_。

#### 哪些类型的问题应该由 regzbot 跟踪？


该机器人旨在跟踪回归问题，因此请不要为常规问题引入 regzbot。但 Linux 内核的回归
跟踪器允许你引入 regzbot 来跟踪严重问题，例如关于挂起、数据损坏或内部错误（Panic、
Oops、BUG()、warning 等）的报告。

#### 如何更改被跟踪回归的各个方面？


通过在包含报告的邮件的直接或间接回复中使用 "regzbot 命令"。最简单的方法：在
你的"已发送"文件夹或邮件列表存档中找到该报告，并使用邮件客户端的"回复全部"功能
回复它。在那封邮件中，使用以下命令之一，放在一个独立的段落中（换言之：使用空行将
这些命令中的一个或多个与邮件其余文本分隔开）。

 - 更新回归开始发生的时间，例如在二分之后

```
       #regzbot introduced: 1f2e3d4c5d

 * 设置或更新标题::

       #regzbot title: foo

 * 监视讨论或 bugzilla.kernel.org 工单，其中讨论了该问题的其他方面或修复::

       #regzbot monitor: https://lore.kernel.org/r/30th.anniversary.repost@klaava.Helsinki.FI/
       #regzbot monitor: https://bugzilla.kernel.org/show_bug.cgi?id=123456789

 * 指向包含相关进一步细节的位置，例如略微相关但主题不同的邮件列表帖子或缺陷
   跟踪器中的工单::

       #regzbot link: https://bugzilla.kernel.org/show_bug.cgi?id=123456789

 * 将回归标记为无效::

       #regzbot invalid: wasn't a regression, problem has always existed

```
regzbot 支持一些其他主要由开发者或跟踪回归问题的人使用的命令。它们以及上述
regzbot 命令的更多细节可以在 regzbot 的 `入门指南
<https://gitlab.com/knurd42/regzbot/-/blob/main/docs/getting_started.md>`_ 和
`参考文档 <https://gitlab.com/knurd42/regzbot/-/blob/main/docs/reference.md>`_
中找到。
