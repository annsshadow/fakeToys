## 如何访问 sysfs 中信息的规则


内核导出sysfs 会导出内核内部实现细节，并依赖于内核内部的结构和布局。内核开发者已达成共识：Linux 内核不提供稳定的内部 API。因此，sysfs 接口的某些方面在不同内核版本之间可能并不稳定

为了将破sysfs 用户（在大多数情况下是底层用户空间应用程序）的风险降到最低，在新内核发布时，sysfs 的用户必须遵守一些规则，以尽可能抽象的方式访问此文件系统。当前的 udev HAL 程序已经实现了这一点，鼓励用户在可能的情况下接入这些程序所提供的抽象，而不是直接访sysfs

但是，如果您确实想要或需要直接访sysfs，请遵循以下规则，这样您的程序应当能兼容未来版本sysfs 接口

- 不要使用 libsysfs
    它对 sysfs 做了一些不成立的假设。它API 不提供任何抽象，而是把内driver-core 的所有实现细节都暴露在自己的 API 中。因此它并不比您自己去读取目录、打开文件更好
    此外，从反映当前内核开发的角度来说，它并未被积极维护。提供稳sysfs 接口的目标已经失败；它引发的问题比解决的问题更多，并且违反了本文档中的许多规则

- sysfs 始终位于 `/sys`
    解析 `/proc/mounts` 是浪费时间。其他挂载点是您不应尝试解决的系统中配置错误。对于测试用例，可以支持一`SYSFS_PATH` 环境变量来覆盖应用程序的行为，但永远不要尝试搜索 sysfs。除非您是早期启动脚本，否则永远不要尝试挂载它

- 设备只是“设备
    在用户空间中，不存在您可以依赖的诸如 class、bus、physical 设备、接口之类的东西。一切都只是一个简单的“设备”。class、bus、physical 等类型只是内核实现细节，查找 sysfs 中设备的应用程序不应依赖它们

    设备的属性包括：

    - devpath（`/devices/pci0000:00/0000:00:1d.1/usb2/2-2/2-2:1.0`

      - 与内核在设备创建和移除时发送的事件中的 DEVPATH 值相
      - 该时刻设备的唯一
      - 内核到设备目录的路径，不带前导的 `/sys`，且始终以斜杠开
      - devpath 的所有元素都必须是真实目录。指/sys/devices 的符号链接必须始终被解析为其真实目标，且必须使用目标路径来访问设备。这样，到设备的 devpath 才与事件发生时内核使用的 devpath 相匹配
      - devpath 字符串中使用或暴露符号链接值作为元素，是应用程序中bug

    - 内核名称（`sda`、`tty`、`0000:00:1f.2`..

      - 目录名，devpath 的最后一个元素相
      - 应用程序需要处理名称中的空格以`!` 之类的字

    - subsystem（`block`、`tty`、`pci`..

      - 简单字符串，绝不能是路径或链接
      - 通过读取 “subsystem链接并只使用目标路径的最后一个元素来获取

    - driver（`tg3`、`ata_piix`、`uhci_hcd`

      - 简单字符串，可能包含空格，绝不能是路径或链
      - 通过读取 “driver链接并只使用目标路径的最后一个元素来获取
      - 没有 “driver链接的设备就是没有驱动；在子设备上下文中复制驱动值，是应用程序中bug

    - 属

      - 设备目录中的文件，或同一设备目录的子目录下的文件
      - 通过指向另一设备的符号链接（“device链接）访问属性，是应用程序中bug

    其他一切都只是内核 driver-core 的实现细节，不应假设其在不同内核版本之间保持稳定

- 父设备的属性绝不应属于子设备
    始终直接查看父设备自身以确定设备的上下文属性。如果设`eth0` `sda` 没有 “driver链接，那么该设备就没有驱动，其值为空。永远不要将父设备的任何属性复制到子设备中。父设备属性可能会在任何未通知子设备的情况下动态改变

- 单一设备树中的层级结
    sysfs 中只有一个有效的位置可以查看层级结构，那就是 `/sys/devices.` 之下。计划将所有设备目录都归入该目录之下的树中

- subsystem 分类
    目前有三个用于设备分类的位置：`/sys/block`、`/sys/class` `/sys/bus.` 计划让这些位置本身不包含任何设备目录，而只包含指向统一`/sys/devices` 树的扁平符号链接列表。这三个位置的访问设备信息规则完全不同。计划将所有三个分类目录合并到 `/sys/subsystem` 一处，遵循 bus 目录的布局。所bus class，包括转换后block subsystem，都会在那里出现
    属于某个 subsystem 的设备会`/sys/subsystem/<name>/devices` “devices目录中创建一个符号链接

    如果 `/sys/subsystem` 存在，则可以忽略 `/sys/bus`、`/sys/class` `/sys/block`。如果不存在，则始终必须扫描这三个位置，因为只要设备仍能通过相同subsystem 名称访问，内核就可以自由地将某个 subsystem 从一个位置移动到另一个位置

    假设 `/sys/class/<subsystem>` `/sys/bus/<subsystem>`，或 `/sys/block` `/sys/class/block` 不可互换，是应用程序中的 bug

- Block
    位于 `/sys/class/block` `/sys/subsystem/block` 的已转换 block subsystem 会在同一层级包含磁盘和分区的链接，绝不会形成层级结构。假block subsystem 在同一扁平列表中只包含磁盘而不包含分区设备，是应用程序中的 bug

- “device链接<subsystem>:<内核名称> 链接
    永远不要依赖 “device链接。“device链接是针对旧布局的一种权宜之计，在旧布局class 设备不像 bus 设备那样创建`/sys/devices/` 中。如果某设备目录的链接解析不`/sys/devices/` 结束，您可以使用 “device链接`/sys/devices/` 中查找父设备，这“device链接唯一有效的用途；它绝不能在任何路径中作为元素出现。假`/sys/devices/` 中的某设备存“device链接，是应用程序中的 bug。访`/sys/class/net/eth0/device` 是应用程序中bug

    永远不要依赖指回 `/sys/class` 目录class 特定链接。这些链接同样是针对“class 设备未创建在 `/sys/devices.`”这一设计错误的权宜之计。如果某设备目录不包含子设备的目录，这些链接可用于在 `/sys/class.` 中查找子设备。这是这些链接唯一有效的用途；它们绝不能在任何路径中作为元素出现。假设这些链接存在于 `/sys/devices` 树中真正的子设备目录设备上，是应用程序中bug

    计划在所class 设备目录都归`/sys/devices.` 时移除所有这些链接

- 设备沿设备链的位置可能会改变
    永远不要依赖 devpath 中某个特定父设备的位置，或父设备链的位置。内核可以自由地将设备插入链中。您必须始终按其 subsystem 值来请求您要查找的父设备。您需要沿链向上走，直到找到与期望subsystem 匹配的设备。依赖特定父设备的位置，或使`../` 暴露相对路径来访问父设备链，是应用程序中bug

- 在读sysfs 设备属性文件时，尽可能避免依赖特定的错误码。这样可以最小化与内核内错误处理实现的耦合


    一般而言，读sysfs 设备属性失败时应尽可能传播错误。常见错误包括但不限于：

	`-EIO`：不支持读或 store 操作，通常是当读或 store 指针`NULL` 时由 sysfs 系统本身返回

	`-ENXIO`：读store 操作失败

    错误码不会在没有充分理由的情况下被更改；如果错误码的更改导致用户空间出现问题，该问题会被修复，或者相关的违规更改会被回退

    不过，在给定属性的上下文中没有出现版本属性更改的情况下，用户空间应用程序可以预期属性文件的内容和格式保持一致
