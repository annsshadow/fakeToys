### 内核模块签名功能


..


## 概述


内核模块签名功能会在安装模块时对模块进行加密签名，并在加载模块时校验该签名。
这通过禁止加载未签名模块或使用了无效密钥签名的模块，来提高内核安全性。模块
签名使得向内核加载恶意模块变得更困难，从而增强了安全性。模块签名的校验由内核
完成，因此无需可信的用户空间组件。

该功能使用 X.509 ITU-T 标准证书来编码所涉及的公开密钥。签名本身并未采用任何
工业标准类型编码。内置功能目前仅支持 RSA、NIST P-384 ECDSA 和 NIST FIPS-204
ML-DSA 公开密钥签名标准（尽管它是可插拔的，允许使用其他标准）。对于 RSA 和
ECDSA，可用的哈希算法是大小为 256、384 和 512 的 SHA-2 与 SHA-3（算法由签名
中的数据选定）；ML-DSA 自行进行哈希，但允许配合 SHA512 哈希用于已签名属性。


## 配置模块签名


模块签名功能通过进入 `Enable Loadable Module Support`（启用可加载模块支持）
一节并选择
```
	CONFIG_MODULE_SIG	"Module signature verification"
```
来启用。它提供若干选项：

 (1) `Require modules to be validly signed`（`要求模块被正确签名`）
     (`CONFIG_MODULE_SIG_FORCE`)

     这指定了内核应当如何处理这样一种模块：其签名所用的密钥未知，或者该模块
     根本未签名。

     如果关闭（即“宽松/permissive”），那么密钥不可用的模块以及未签名的模块
     被允许加载，但内核会被标记为被污染（tainted），相关模块也会被标记为污染，
     用字符 'E' 显示。

     如果开启（即“严格/restrictive”），则只有拥有内核所持有的公开密钥能够
     验证的有效签名的模块才会被加载。所有其他模块都会产生错误。

     无论此处如何设置，如果模块的签名块无法被解析，它会被直接拒绝。


 (2) `Automatically sign all modules`（`自动签名所有模块`）
     (`CONFIG_MODULE_SIG_ALL`)

     如果开启，模块会在构建的 modules_install 阶段被自动签名。如果关闭，则
     模块必须由
```
	scripts/sign-file
```
手动签名（详见下文）。


 (3) :menuselection:`Which hash algorithm should modules be signed with?`（`模块应该用哪种哈希算法签名？`）

     这里给出安装阶段对模块签名时使用哪种哈希算法的选择：

        =============================== ==========================================
	``CONFIG_MODULE_SIG_SHA256``	:menuselection:`用 SHA-256 为模块签名`
	``CONFIG_MODULE_SIG_SHA384``	:menuselection:`用 SHA-384 为模块签名`
	``CONFIG_MODULE_SIG_SHA512``	:menuselection:`用 SHA-512 为模块签名`
	``CONFIG_MODULE_SIG_SHA3_256``	:menuselection:`用 SHA3-256 为模块签名`
	``CONFIG_MODULE_SIG_SHA3_384``	:menuselection:`用 SHA3-384 为模块签名`
	``CONFIG_MODULE_SIG_SHA3_512``	:menuselection:`用 SHA3-512 为模块签名`
        =============================== ==========================================

     此处选定的算法也会被编译进内核（而不是作为模块），以便用该算法签名的模块
     能够在不会造成依赖环的情况下校验其签名。


 (4) :menuselection:`File name or PKCS#11 URI of module signing key`（`模块签名密钥的文件名或 PKCS#11 URI`）
     (``CONFIG_MODULE_SIG_KEY``)

     将此选项设置为非默认值 ``certs/signing_key.pem`` 之外的其他值，将禁用签名
     密钥的自动生成，并允许用你自行选择的密钥为内核模块签名。所提供的字符串应当
     标识一个包含 PEM 形式私钥及其对应 X.509 证书的文件，或者——在 OpenSSL
     ENGINE_pkcs11 可用的系统上——一个由 RFC7512 定义的 PKCS#11 URI。在后一种
     情况下，PKCS#11 URI 应当同时引用证书和私钥。

     如果包含私钥的 PEM 文件被加密，或者 PKCS#11 令牌需要 PIN，可以在构建时通过
     ``KBUILD_SIGN_PIN`` 变量提供。


 (5) :menuselection:`Additional X.509 keys for default system keyring`（`默认系统密钥环的额外 X.509 密钥`）
     (``CONFIG_SYSTEM_TRUSTED_KEYS``)

     此选项可以设置为一个 PEM 编码文件的文件名，该文件包含额外的证书，这些
     证书默认会被包含进系统密钥环。

```
注意，启用模块签名会为执行签名的工具所在的构建过程增加对 OpenSSL 开发包的
依赖。


## 生成签名密钥


生成和校验签名都需要加密密钥对。私钥用于生成签名，相应的公开密钥用于校验。
私钥只在构建期间需要，之后可以将其删除或安全保存。公开密钥被编译进内核，以便
在加载模块时用来校验签名。

在正常情况下，当 `CONFIG_MODULE_SIG_KEY` 保持默认未变时，内核构建会在构建
vmlinux 期间使用
```
	certs/signing_key.pem
```
自动生成一个新的密钥对（密钥的公开部分需要被构建进
```
	certs/x509.genkey
```
文件，如果该文件不存在也会被生成）。

可以在 RSA（`MODULE_SIG_KEY_TYPE_RSA`）、ECDSA（`MODULE_SIG_KEY_TYPE_ECDSA`）
和 ML-DSA（`MODULE_SIG_KEY_TYPE_MLDSA_*`）之间选择，以生成一个 RSA 4k、一个
NIST P-384 密钥对，或一个 ML-DSA 44、65 或 87 密钥对。

强烈建议你提供自己的 x509.genkey 文件。

最值得注意的是，在 x509.genkey 文件中，req_distinguished_name 段为
```
	[ req_distinguished_name ]
	#O = Unspecified company
	CN = Build time autogenerated kernel key
	#emailAddress = unspecified.user@unspecified.company
```
```
	[ req ]
	default_bits = 4096
```
也可以使用 Linux 内核源码树根节点下的 x509.genkey 密钥生成配置文件和 openssl
命令手动生成私钥/公钥文件。以下是一个示例
```
	openssl req -new -nodes -utf8 -sha256 -days 36500 -batch -x509 \
	   -config x509.genkey -outform PEM -out kernel_key.pem \
	   -keyout kernel_key.pem
```
由此得到的 kernel_key.pem 文件的完整路径名随后可以在 `CONFIG_MODULE_SIG_KEY`
选项中指定，其中的证书和密钥将被用来代替自动生成的密钥对。


## 内核中的公开密钥


内核包含一个可由 root 查看的公开密钥环。它们是
```
	[root@deneb ~]# cat /proc/keys
	...
	223c7853 I------     1 perm 1f030000     0     0 keyring   .builtin_trusted_keys: 1
	302d2d52 I------     1 perm 1f010000     0     0 asymmetri Fedora kernel signing key: d69a84e6bce3d216b979e9505b3e3ef9a7118079: X509.RSA a7118079 []
	...
```
除了专门为模块签名生成的公开密钥之外，还可以通过 `CONFIG_SYSTEM_TRUSTED_KEYS`
配置选项所引用的 PEM 编码文件中提供额外的可信证书。

此外，架构相关代码可能会从硬件存储中获取公开密钥并一并加入（例如来自 UEFI
密钥数据库）。

```
	keyctl padd asymmetric "" [.builtin_trusted_keys-ID] <[key-file]
```
```
	keyctl padd asymmetric "" 0x223c7853 <my_public_key.x509
```
但请注意，内核**只**允许在以下条件时把密钥加入 `.builtin_trusted_keys`：新密钥的
X.509 封装在加入该密钥时，由已驻留在 `.builtin_trusted_keys` 中的某个密钥有效
签名。


## 手动签名模块


要手动签名模块，请使用 Linux 内核源码树中提供的 scripts/sign-file 工具。该
脚本需要 4 个参数：

 1. 哈希算法（如 sha256）
 2. 私钥文件名或 PKCS#11 URI
 3. 公开密钥文件名
 4. 待签名的模块

```
	scripts/sign-file sha512 kernel-signkey.priv \
		kernel-signkey.x509 module.ko
```
所使用的哈希算法不一定要与配置的一致，但如果不一致，你应当确保该哈希算法要么被
构建进内核，要么可以在不需要自身的情况下被加载。

如果私钥需要口令或 PIN，可以通过 $KBUILD_SIGN_PIN 环境变量提供。


## 已签名模块与剥离（stripping）


已签名的模块只是在末尾简单地附加了数字签名。模块文件末尾的字符串
`~Module signature appended~.` 确认存在签名，但它并不确认签名是有效的！

已签名模块是脆弱的（BRITTLE），因为签名位于已定义的 ELF 容器之外。因此一旦
签名被计算并附加，就**绝不能**再对模块进行 strip。注意整个模块都是被签名的
载荷，包括签名时存在的任何及所有调试信息。


## 加载已签名模块


模块通过 insmod、modprobe、`init_module()` 或 `finit_module()` 加载，与未签名
模块完全一样，因为用户空间不做任何处理。签名的校验全部在内核内部完成。


## 无效签名与未签名模块


如果启用了 `CONFIG_MODULE_SIG_FORCE`，或者在内核命令行提供了
module.sig_enforce=1，内核将只加载它有相应公开密钥、且被正确签名的模块。否则，
它也会加载未签名的模块。对于任何内核持有其密钥、但被证明存在签名不匹配的模块，
将不允许加载。

任何拥有无法解析的签名的模块都会被拒绝。


## 管理/保护私钥


由于私钥用于为模块签名，病毒和恶意软件可能利用私钥为模块签名并危害操作系统。
私钥必须被销毁或移动到安全位置，不要保留在内核源码树的根节点下。

如果你使用同一个私钥为多种内核配置的模块签名，必须确保模块版本信息足以防止把
模块加载进不同的内核。要么设置 `CONFIG_MODVERSIONS=y`，要么通过修改 `EXTRAVERSION`
或 `CONFIG_LOCALVERSION` 确保每个配置有不同的内核发布字符串。
