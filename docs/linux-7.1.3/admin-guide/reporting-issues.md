
Reporting issues
++++++++++++++++


## 简明指南（即 TL;DR）


你正面临来自同一 stable 或 longterm 系列的 vanilla 内核的回归吗？一个
仍受支持的系列？那么在 `LKML <https://lore.kernel.org/lkml/>`_ 和
`Linux stable mailing list <https://lore.kernel.org/stable/>`_ 存档中
搜索匹配的报告以加入。如果找不到，安装 `该系列的最新发布版本
<https://kernel.org/>`_。如果它仍然显示该问题，将其报告给 stable 邮件
列表（stable@vger.kernel.org），并抄送 regressions 列表
（regressions@lists.linux.dev）；理想情况下也抄送相关子系统的维护者及其
邮件列表。

在所有其他情况下，尽力猜测可能是哪个内核部分导致了问题。查看
MAINTAINERS <maintainers> 文件，了解其开发者期望如何被告知问题，大多数
情况下是通过邮件，并抄送一个邮件列表。查看目标存档中是否有匹配的报告；
也要搜索 `LKML <https://lore.kernel.org/lkml/>`_ 和网络。如果找不到可
加入的，安装 `最新的主线内核 <https://kernel.org/>`_。如果问题在那里
存在，发送一份报告。

问题在那里被修复了，但你希望在仍受支持的 stable 或 longterm 系列中也
看到它被解决？那么安装其最新发布版本。如果它显示该问题，搜索在主线中
修复它的改动，并检查回溯是否在进行中或被放弃；如果两者都不是，向处理
该改动的人询问。

**一般性备注**：按照上述说明安装和测试内核时，确保它是 vanilla 的（即：
未打补丁且未使用附加模块）。还要确保它构建并运行在健康的环境中，并且在
问题发生前尚未被污染（tainted）。

如果你同时面临 Linux 内核的多个问题，请分别报告每一个。在撰写报告时，
包含与问题相关的所有信息，例如所使用的内核和发行版。在回归的情况下，
将 regressions 邮件列表（regressions@lists.linux.dev）抄送到你的报告中。
同时尝试通过二分来精确定位罪魁祸首；如果成功，包含其 commit-id 并抄送
sign-off-by 链中的所有人。

报告发出后，回答出现的任何问题，并尽其所能提供帮助。这包括通过偶尔用
更新的发布版本重新测试并随后发送状态更新来保持进展。

..
   注意：如果你看到此注释，你正在阅读文本的源文件。你或许想切换到
   渲染版本：它能让阅读和浏览本文档容易得多——尤其是当你想在参考一节中
   查阅某些内容，然后跳回你离开的地方时。

..
   在此处查找本文档的最新渲染版本：
   https://docs.kernel.org/admin-guide/reporting-issues.html


## 向内核维护者报告问题的分步指南


上面的 TL;DR 大致概述了如何向 Linux 内核开发者报告问题。对于已经熟悉向
自由/开源软件（FLOSS）项目报告问题的人来说，这可能就是所需的全部。对于
其他所有人，则有本节。它更详细并采用分步方法。为了可读性，它仍然力求
简洁，并省略了许多细节；这些细节在分步指南下方的参考一节中有更详细的
描述，该节对每个步骤进行更详细的解释。

注意：本节比 TL;DR 涵盖更多方面，并且顺序略有不同。这是为你好，以确保
你尽早注意到看起来像 Linux 内核问题、实际上却是由其他原因引起的问题。
因此，这些步骤有助于确保你在此过程中投入的时间最终不会感觉被浪费：

 - 你正面临 Linux 内核（由硬件或软件供应商提供）的问题吗？那么在几乎
   所有情况下，你最好停止阅读本文档，转而向你的供应商报告问题，除非你
   愿意自己安装最新的 Linux 版本。请注意，后者通常无论如何都需要，以便
   追踪和修复问题。

 - 用你喜欢的互联网搜索引擎对现有报告进行一次粗略搜索；此外，查看
   `Linux Kernel Mailing List (LKML) <https://lore.kernel.org/lkml/>`_ 的
   存档。如果你找到匹配的报告，加入讨论而不是发送新的报告。

 - 查看你处理的问题是否符合回归、安全问题，或真正严重的问题：那些是
   "高优先级问题"，在接下来的一些步骤中需要特殊处理。

 - 确保不是内核的周边环境导致了你所面临的问题。

 - 创建全新的备份，并将系统修复和恢复工具放在手边。

 - 确保你的系统不会通过在运行时动态构建额外的内核模块来增强其内核，
   像 DKMS 这样的解决方案可能会在你不知情的情况下在本地这样做。

 - 检查你的内核在问题发生时是否被"污染（tainted）"，因为使内核设置此
   标志的事件可能正是导致你所面临问题的原因。

 - 粗略记下如何复现该问题。如果你同时处理多个问题，为每个问题创建单独的
   笔记，并确保它们在新启动的系统上独立工作。这是必要的，因为每个问题
   都需要分别报告给内核开发者，除非它们紧密纠缠在一起。

 - 如果你面临 stable 或 longterm 版本系列中的回归（例如从 5.10.4 更新到
   5.10.5 时某物损坏），向下滚动到"处理 stable 和 longterm 内核系列中的
   回归"。

 - 定位似乎导致该问题的驱动程序或内核子系统。弄清楚其开发者期望如何以及
   在哪里接收报告。注意：大多数情况下这不会是 bugzilla.kernel.org，因为
   问题通常需要通过邮件发送给维护者和公共邮件列表。

 - 彻底搜索相关缺陷跟踪器或邮件列表的存档，查找可能与你的问题匹配的
   报告。如果找到任何内容，加入讨论而不是发送新的报告。

完成这些准备后，你现在将进入主要部分：

 - 除非你已经在运行最新的"主线（mainline）"Linux 内核，否则最好去安装
   它来进行报告过程。在某些情况下，用最新的"stable"Linux 进行测试和报告
   也是可接受的替代方案；在合并窗口（merge window）期间，这实际上可能是
   最好的方法，但在那个开发阶段，暂停你的努力几天甚至可能是更好的主意。
   无论你选择哪个版本，理想情况下使用"vanilla"构建。忽视这些建议将显著
   增加你的报告被拒绝或忽略的风险。

 - 确保你刚安装的内核在运行时不会"污染"自身。

 - 用你刚安装的内核复现该问题。如果它在那里没有出现问题，向下滚动到
   仅发生在 stable 和 longterm 内核上的问题的说明。

 - 优化你的笔记：尝试找到并写下复现问题最直接的方法。确保最终结果包含
   所有重要细节，同时易于首次听说它的人阅读和理解。如果你在此过程中学到
   了什么，考虑再次搜索关于该问题的现有报告。

 - 如果你的故障涉及"panic"、"Oops"、"warning"或"BUG"，考虑解码内核日志
   以找到触发该错误的代码行。

 - 如果你的问题是回归，尽量缩小问题被引入的时间范围。

 - 通过撰写关于该问题的详细描述来开始编写报告。始终提及几点：你为复现
   而安装的最新内核版本、所使用的 Linux 发行版，以及你关于如何复现问题的
   笔记。理想情况下，将内核的构建配置（.config）和 `dmesg` 的输出放在
   网络上的某处并提供链接。包含或上传所有其他可能相关的信息，例如 Oops 的
   输出/截图或 `lspci` 的输出。写完这个主要部分后，在它顶部插入一个正常
   长度的段落，快速概述问题和影响。在此之上添加一句话，简要描述问题并让人
   继续读下去。现在给这个东西一个描述性的标题或主题，但要更短。然后你就
   可以像 MAINTAINERS 文件告诉你的那样发送或提交报告，除非你处理的是那些
   "高优先级问题"之一：它们需要特殊处理，这在下面的"高优先级问题的特殊
   处理"中解释。

 - 等待反应，并保持进展，直到你能以某种方式接受结果。因此要公开并及时地
   回应任何询问。测试建议的修复。进行主动测试：用每个新主线版本的第一个
   候选版本（RC）重新测试并报告你的结果。如果事情停滞，发送友好的提醒。
   如果你得不到任何帮助或帮助不令人满意，尝试自助。

### 在 stable 和 longterm 内核系列中报告回归


如果你遵循了上述过程，并在关于 stable 或 longterm 内核版本系列中回归的
那一点被引导到这里，本节就是为你准备的。当你从 5.10.4 更新到 5.10.5 时
某物损坏（从 5.9.15 切换到 5.10.5 不符合条件），你就面临其中之一。开发者
希望尽快修复此类回归，因此有一个简化的流程来报告它们：

 - 检查内核开发者是否仍在维护你关心的 Linux 内核版本系列：前往
   `kernel.org 首页 <https://kernel.org/>`_，确保它提到特定版本系列的最新
   发布版本且没有"[EOL]"标签。

 - 在 `Linux stable mailing list <https://lore.kernel.org/stable/>`_ 的
   存档中检查现有报告。

 - 安装特定版本系列的最新发布版本作为 vanilla 内核。确保此内核未被污染
   且仍显示该问题，因为该问题可能已经在那里被修复。如果你最初是在供应商
   内核上注意到该问题，请检查已知可正常工作的最后一个版本的 vanilla 构建
   是否也表现良好。

 - 将简短的问题报告发送到 Linux stable 邮件列表（stable@vger.kernel.org），
   并抄送 Linux regressions 邮件列表（regressions@lists.linux.dev）；如果你
   怀疑原因在某个特定子系统，抄送其维护者和其邮件列表。粗略描述问题，并
   理想情况下说明如何复现它。提及首次出现问题的版本以及最后一个正常工作
   的版本。然后等待进一步的指示。

下面的参考一节更详细地解释这些步骤中的每一个。

### 仅在较旧内核版本系列中出现的问题的报告


如果你按照上述说明尝试了最新的主线内核，但未能在那里复现你的问题；同时
你希望在该问题在仍受支持的 stable 或 longterm 系列，或定期基于这些系列
重建的供应商内核中得到修复。如果是这种情况，请遵循以下步骤：

 - 为自己做好心理准备：执行接下来的几个步骤可能仍无法在较旧版本中解决
   问题：该修复可能太大或风险太高，无法回溯到那里。

 - 执行上文"处理 stable 和 longterm 内核系列中的回归"一节中的前三个步骤。

 - 在 Linux 内核版本控制系统中搜索在主线中修复该问题的改动，因为其提交
   信息可能会告诉你该修复是否已被安排回溯。如果以此方式找不到任何内容，
   搜索相应的邮件列表，查找讨论此类问题或同行评审可能的修复的帖子；然后
   检查讨论，确认该修复是否被认为不适合回溯。如果根本就没有考虑过回溯，
   加入最新的讨论，询问是否有这种可能。

 - 上述步骤之一应当能带来解决方案。如果不奏效，向你怀疑导致该问题的
   子系统的维护者请求建议；同时抄送该特定子系统的邮件列表以及 stable
   邮件列表。

下面的参考一节更详细地解释这些步骤中的每一个。

## 参考一节：向内核维护者报告问题


上面的分步指南以简要方式概述了所有主要步骤，通常涵盖所需的一切。但即使
是经验丰富的用户有时也会想知道如何实际实现其中某些步骤，或者为何需要
它们；指南为了可读性也忽略了一些边缘情况。这就是本参考一节中各条目的
用途，它们为指南中的每个步骤提供补充信息。

几点一般性建议：

- Linux 开发者很清楚，向他们报告缺陷比其他 FLOSS 项目更复杂和费力。部分
  原因是内核不同，包括其邮件驱动的开发过程，以及它主要由驱动程序组成。
  部分原因是改进事情需要在几个技术领域和分类缺陷的人员方面开展工作——
  而没有人站出来做或资助这项工作。

- 与某个供应商的保修或支持合同并不赋予你向上游 Linux 开发者请求修复的
  权利：此类合同完全在 upstream Linux 内核、其开发社区和本文档的范围之外——
  即使处理该问题的人为签发合同的供应商工作。如果你想主张你的权利，请使用
  供应商的支持渠道。

- 如果你以前从未向 FLOSS 项目报告过问题，考虑浏览诸如 `How to ask good
  questions <https://jvns.ca/blog/good-questions/>`_、`How To Ask Questions
  The Smart Way <http://www.catb.org/esr/faqs/smart-questions.html>`_，以及
  `How to Report Bugs Effectively
  <https://www.chiark.greenend.org.uk/~sgtatham/bugs.html>`_ 之类的指南。

说完这些，下面是在向 Linux 内核开发者报告问题的详细指南中各个步骤的详情。

### 确保你使用的是上游 Linux 内核


   *你正面临 Linux 内核（由硬件或软件供应商提供）的问题吗？那么在几乎所有
   情况下，你最好停止阅读本文档，转而向你的供应商报告问题，除非你愿意自己
   安装最新的 Linux 版本。请注意，后者通常无论如何都需要，以便追踪和修复
   问题。*

与大多数程序员一样，Linux 内核开发者不喜欢花时间处理甚至不会在其当前代码
中出现的问题的报告。这只是浪费每个人的时间，尤其是你的。不幸的是，当
涉及内核时，这种情况很容易发生，并常常导致双方的挫败感。这是因为几乎
所有预装在设备（计算机、笔记本、智能手机、路由器……）上的基于 Linux 的
内核，以及大多数由 Linux 发行商发布的内核，都与 kernel.org 分发的官方
Linux 内核相去甚远：这些来自这些供应商的内核从 Linux 发展的角度来看往往
很古老，或者被大量修改，通常两者兼具。

这些供应商内核大多非常不适合向 Linux 内核开发者报告问题：你在其中之一
遇到的问题可能早在数月或数年前就已被 Linux 内核开发者修复；此外，供应商的
修改和增强可能正是导致你所面临问题的原因，即使它们看起来很小或完全无关。
这就是为什么你应该向这些内核的供应商报告问题。其开发者应调查该报告，如果
结果是上游问题，则直接在上游修复或将报告转发到上游。在实践中，这常常行不通，
或者可能不是你想要的。因此你可能想通过自己安装最新 Linux 内核核心来绕过
供应商。如果这对你来说是一个选项，请在本流程中继续前进，因为本指南后面的
一个步骤将在排除其他潜在原因后解释如何做到这一点。

注意，上一段以"大多数"一词开头，因为有时开发者实际上愿意处理关于供应商
内核中出现的问题的报告。如果他们最终愿意，高度依赖于开发者和所涉及的问题。
如果你的发行商仅对基于近期 Linux 版本的内核应用了小的修改，你的机会相当
好；例如，Debian GNU/Linux Sid 或 Fedora Rawhide 发布的主线内核通常就是
这种情况。一些开发者也会接受关于发布最新 stable 内核的发行版的内核问题的
报告，只要它只是略有修改；例如 Arch Linux、常规 Fedora 发布版和 openSUSE
Tumbleweed 通常就是这种情况。但请记住，你最好想使用主线 Linux 并避免在此
过程中使用 stable 内核，这在"安装全新内核用于测试"一节中有更详细的说明。

显然，你可以自由忽略所有这些建议，向 upstream Linux 开发者报告关于旧的或
大量修改的供应商内核的问题。但请注意，这些报告常常被拒绝或忽略，所以请
视为警告。但它仍然比根本不报告问题要好：有时此类报告会直接或间接地帮助
随着时间的推移修复问题。

### 搜索现有报告，第一轮


   *用你喜欢的互联网搜索引擎对现有报告进行一次粗略搜索；此外，查看 Linux
   Kernel Mailing List (LKML) 的存档。如果你找到匹配的报告，加入讨论而不是
   发送新的报告。*

报告别人已经提出过的问题，通常对涉及的所有人都是时间的浪费，尤其是作为
报告者的你。因此，彻底检查是否有人已经报告了该问题符合你自己的利益。在
流程的这一步，进行一次粗略搜索即可：稍后的一个步骤会告诉你在你知道你的
问题需要报告到哪里后，执行更详细的搜索。尽管如此，不要急于这一报告步骤，
它可以节省你的时间和麻烦。

首先用你喜欢的搜索引擎简单地搜索互联网。之后，搜索 `Linux Kernel Mailing
List (LKML) 存档 <https://lore.kernel.org/lkml/>`_。

如果你被大量结果淹没，考虑告诉你的搜索引擎将搜索时间范围限制在过去一个月
或一年。无论你在哪里搜索，确保使用良好的搜索词；也多次变换它们。这样做时，
尝试从他人的角度看待问题：这将帮助你想到用作搜索词的其他词。还要确保不要
一次使用太多搜索词。记得带和不带诸如内核驱动程序名称或受影响硬件组件名称
之类的信息进行搜索。但其确切品牌名称（例如"ASUS Red Devil Radeon RX 5700
XT Gaming OC"）通常帮助不大，因为它太具体。相反，尝试搜索诸如型号系列
（Radeon 5700 或 Radeon 5000）和主芯片的代码名称（"Navi"或"Navi10"），
带和不带其制造商（"AMD"）。

如果你找到关于你的问题的现有报告，加入讨论，因为你或许能够提供有价值的
额外信息。即使修复已在准备中或处于最后阶段，这很重要，因为开发者可能
正在寻找能提供额外信息或测试建议修复的人。跳到"报告发出后的职责"一节，
了解如何妥善参与的详情。

注意，搜索 `bugzilla.kernel.org <https://bugzilla.kernel.org/>`_ 也可能是
个好主意，因为它可能提供有价值的见解或找出匹配的报告。如果你找到后者，
只需记住：大多数子系统期望在不同地方报告，如下面"检查你需要将问题报告到
哪里"一节所述。因此，应该处理该问题的开发者甚至可能不知道该 bugzilla
工单。因此，检查该工单，看该问题是否已按本文档所述被报告，如果没有，考虑
这样做。

### 高优先级问题？


   *查看你处理的问题是否符合回归、安全问题，或真正严重的问题：那些是
   "高优先级问题"，在接下来的一些步骤中需要特殊处理。*

Linus Torvalds 和领先的 Linux 内核开发者希望尽快看到某些问题得到修复，因此
有"高优先级问题"在报告过程中处理方式略有不同。有三类情况符合：回归、
安全问题和真正严重的问题。

如果你用一种 Linux 内核运行良好的某个应用程序或实际用例，在使用类似配置
编译的较新版本中表现更差或根本不工作，你就面临回归。文档
Documentation/admin-guide/reporting-regressions.rst 更详细地解释了这一点。
它还提供了大量你可能想知道的关于回归的其他信息；例如，它解释了如何将你的
问题添加到被跟踪的回归列表中，以确保它不会从缝隙中溜走。

什么符合安全问题留给你判断。在继续之前，考虑阅读
Documentation/process/security-bugs.rst，因为它提供了关于如何最好地处理
安全问题的额外细节。

当发生某种完全不可接受的可怕事情时，问题就是"真正严重的问题"。例如，当
Linux 内核损坏其正在处理的数据或损害其运行的硬件时，就是这种情况。当内核
突然停止工作并带有错误消息（"kernel panic"）或没有任何告别说明时，你也
面临严重问题。注意：不要将"panic"（内核自行停止的致命错误）与"Oops"
（可恢复错误）混淆，因为内核在后者之后仍在运行。

### 确保健康的环境


   *确保不是内核的周边环境导致了你所面临的问题。*

看起来很像内核问题的故障，有时是由构建或运行时环境引起的。很难完全排除
该问题，但你应该将其最小化：

 - 构建内核时使用经过验证的工具，因为编译器或 binutils 中的错误可能导致
   生成的内核行为异常。

 - 确保你的计算机组件在其设计规格内运行；这对于主处理器、主内存和
   主板尤其重要。因此，在面临潜在内核问题时，停止欠压（undervolting）或
   超频（overclocking）。

 - 尽量确保不是有故障的硬件导致了你的问题。例如，坏的主内存可能导致
   大量问题，这些问题会表现为看起来像内核问题。

 - 如果你处理的是文件系统问题，你可能想用 `fsck` 检查相关文件系统，因为
   它可能以导致意外内核行为的方式受损。

 - 在处理回归时，确保不是与更新内核同时发生的其他变化。例如，问题可能由
   同时更新的其他软件引起。也可能发生硬件组件恰好在你第一次重启进入新的
   内核时损坏的情况。更新系统 BIOS 或在 BIOS 设置中更改某些内容也可能导致
   看起来非常像内核回归的问题。

### 为紧急情况做准备


   **创建全新的备份，并将系统修复和恢复工具放在手边。**

提醒，你正在与计算机打交道，计算机有时会做意想不到的事情，尤其是当你摆弄
像其操作系统内核这样的关键部分时。这正是你在此过程中要做的事情。因此，
确保创建全新的备份；还要确保你手边有修复或重新安装操作系统以及恢复备份
所需的一切工具。

### 确保你的内核不会被增强


   *确保你的系统不会通过在运行时动态构建额外的内核模块来增强其内核，
   像 DKMS 这样的解决方案可能会在你不知情的情况下在本地这样做。*

如果你的内核以任何方式被增强，你的缺陷报告被忽略或拒绝的风险会急剧增加。
这就是为什么你应该移除或禁用像 akmods 和 DKMS 这样的机制：那些会自动构建
附加内核模块，例如当你安装新的 Linux 内核或首次启动它时。还要移除它们可能
已安装的任何模块。然后在继续之前重启。

注意，你可能没有意识到你的系统正在使用这些解决方案之一：它们通常在你安装
Nvidia 的专有图形驱动程序、VirtualBox，或其他需要来自非 Linux 内核一部分的
模块的一些支持的软件时无声地设置。这就是为什么你可能需要卸载带有此类软件
的包，以摆脱任何第三方内核模块。

### 检查"taint"标志


   *检查你的内核在问题发生时是否被"污染（tainted）"，因为使内核设置此
   标志的事件可能正是导致你所面临问题的原因。*

当发生可能导致看起来完全无关的后继错误的事情时，内核会用"taint"标志
标记自身。如果你内核被污染，你所面临的问题可能就是这样一个错误。这就是为什么
在投入更多时间到该过程之前，尽早排除这一点符合你的利益。这是此步骤在此的
唯一原因，因为此过程稍后会告诉你要安装最新主线内核；那时你将需要再次检查
taint 标志，因为那是它重要的时刻，因为那将是报告关注的内核。

在运行的系统上，检查内核是否污染了自身很容易：如果 ``cat
/proc/sys/kernel/tainted`` 返回"0"，则内核未被污染，一切正常。在某些情况下
无法检查该文件；这就是为什么内核在报告内部问题（"kernel bug"）、可恢复
错误（"kernel Oops"）或操作停止前的不可恢复错误（"kernel panic"）时也会
提及污染状态。在这些情况之一发生时打印的错误消息顶部附近查找，并搜索以
"CPU:"开头的行。如果内核在注意到问题时未被污染，它应以"Not tainted"结尾；
如果你看到"Tainted:"后跟几个空格和一些字母，则它已被污染。

如果你的内核被污染，请研究 Documentation/admin-guide/tainted-kernels.rst
以找出原因。尝试消除原因。通常它由这三件事之一引起：

 1. 发生了一个可恢复错误（"kernel Oops"），内核将自己标记为污染，因为内核知道在那之后它可能会以奇怪的方式表现异常。在这种情况下，检查你的内核或系统日志，查找如下部分：

```
       Oops: 0000 [#1] SMP
```

    这是自启动以来的第一个 Oops，括号中的 "#1" 表明了这一点。在那之后发生的每一个 Oops 以及任何其它问题都可能是第一个 Oops 的后续问题，即使两者看起来完全无关。通过消除第一个 Oops 的原因并在之后复现该问题来排除这一点。有时简单地重启就足够了，有时更改配置然后重启可以消除 Oops。但在流程的这一步不要在此投入太多时间，因为该 Oops 的原因可能已经在你稍后将在本流程中安装的更新 Linux 内核版本中修复了。

 2. 你的系统使用了安装自己内核模块的软件，例如 Nvidia 的专有图形驱动程序或 VirtualBox。内核在加载此类来自外部源的模块时（即使它们是开源的）会将自己标记为污染：它们有时会在不相关的内核区域引起错误，因此可能正是导致你所面临问题的原因。因此，当你想向 Linux 内核开发者报告问题时，必须阻止这些模块加载。大多数时候最简单的方法是：暂时卸载此类软件及其可能安装的任何模块。然后重启。

 3. 当内核加载位于 Linux 内核源码 staging 树中的模块时，也会将自己标记为污染。那是用于尚未达到正常 Linux 内核质量标准的代码（主要是驱动程序）的特殊区域。当你报告关于此类模块的问题时，内核被污染显然是可以接受的；只需确保相关模块是污染的唯一原因。如果问题发生在不相关的区域，重启并通过将 ``foo.blacklist=1`` 指定为内核参数（将 'foo' 替换为相关模块的名称）来临时阻止该模块加载。


### 记录如何复现问题


    *粗略记下如何复现该问题。如果你同时处理多个问题，为每个问题创建单独的
    笔记，并确保它们在新启动的系统上独立工作。这是必要的，因为每个问题
    都需要分别报告给内核开发者，除非它们紧密纠缠在一起。*

如果你同时处理多个问题，你将不得不分别报告每一个，因为它们可能由不同的
开发者处理。在一份报告中描述各种问题也会让其他人很难将其拆分。因此，只有
当问题非常紧密地纠缠在一起时，才将它们合并到一份报告中。

此外，在报告过程中你将不得不测试该问题是否发生在其它内核版本上。因此，
如果你确切知道如何在新启动的系统上快速复现一个问题，你的工作会更轻松。

注意：报告只发生过一次的问题通常是徒劳的，因为它们可能是由宇宙辐射引起的
位翻转造成的。这就是为什么你应该通过在此之前复现该问题来排除这种可能性。
如果你经验足够丰富，能够将一个由于硬件故障导致的一次性错误与一个很少发生
因而难以复现的内核问题区分开来，请随意忽略此建议。


### stable 或 longterm 内核中的回归？


    *如果你面临 stable 或 longterm 版本系列中的回归（例如从 5.10.4 更新到
    5.10.5 时某物损坏），向下滚动到"处理 stable 和 longterm 内核系列中的
    回归"。*

stable 和 longterm 内核版本系列中的回归是 Linux 开发者非常想修复的，因为
此类问题比主线开发分支中的回归更不受欢迎，因为它们会迅速影响大量人群。
因此开发者希望尽快了解此类问题，所以有一个简化的流程来报告它们。注意，
较新内核版本系列（例如从 5.9.15 切换到 5.10.5 时某物损坏）的回归不符合条件。


### 检查你需要将问题报告到哪里


    *定位似乎导致该问题的驱动程序或内核子系统。弄清楚其开发者期望如何以及
    在哪里接收报告。注意：大多数情况下这不会是 bugzilla.kernel.org，因为
    问题通常需要通过邮件发送给维护者和公共邮件列表。*

将你的报告发送给正确的人至关重要，因为 Linux 内核是一个庞大的项目，其
大多数开发者只熟悉其中的一小部分。例如，相当多的程序员只关心一个驱动程序，
例如某个 WiFi 芯片的驱动程序；其开发者可能只对远程或不相关的"子系统"（如
TCP 栈、PCIe/PCI 子系统、内存管理或文件系统）的内部了解甚少或一无所知。

问题在于：Linux 内核缺乏一个集中的缺陷跟踪器，你可以简单地在其中提交你的
问题并让它送达需要了解它的开发者。这就是为什么你必须自己找到报告问题的
正确位置和方式。你可以借助一个脚本（见下文）来做到这一点，但它主要面向
内核开发者和专家。对于其他所有人，MAINTAINERS 文件是更好的去处。

#### 如何阅读 MAINTAINERS 文件


为了说明如何使用 MAINTAINERS <maintainers> 文件，让我们假设你的笔记本
中的 WiFi 在更新内核后突然表现异常。在这种情况下，很可能是 WiFi 驱动程序
中的问题。显然也可能是它所基于的某些代码，但除非你怀疑类似情况，否则坚持
从驱动程序入手。如果确实是别的东西，驱动程序的开发者会让正确的人参与进来。

遗憾的是，没有办法以既通用又简单的方式检查是哪个代码在驱动某个特定的硬件
组件。

以 WiFi 驱动程序的问题为例，你可能想查看 `lspci -k` 的输出，因为它列出了
PCI/PCIe 总线上的设备以及

```
       [user@something ~]$ lspci -k
       [...]
```
       3a:00.0 Network controller: Qualcomm Atheros QCA6174 802.11ac Wireless Network Adapter (rev 32)
         Subsystem: Bigfoot Networks, Inc. Device 1535
         Kernel driver in use: ath10k_pci
         Kernel modules: ath10k_pci
       [...]

但这种方法在你的 WiFi 芯片通过 USB 或某些其它内部总线连接时将不起作用。在
那些情况下，你可能想检查你的 WiFi 管理器或 `ip link` 的输出。查找有问题的
网络接口的名称，它可能类似 'wlp58s0'。这个名称可以像这样使用

```
       [user@something ~]$ realpath --relative-to=/sys/module/ /sys/class/net/wlp58s0/device/driver/module
       ath10k_pci
```

如果像这样的技巧没能帮你更进一步，尝试在互联网上搜索如何缩小相关驱动程序
或子系统的范围。如果你不确定是哪个，就尽力猜测，如果你猜错了，会有人帮助
你的。

一旦你知道了驱动程序或子系统，你想在 MAINTAINERS 文件中搜索它。对于
'ath10k_pci'，你什么也找不到，因为名称太具体。有时你将需要在网络上搜索
帮助；但在这样做之前，搜索时尝试一个略短或修改过的名称，例如当你搜索

```
       QUALCOMM ATHEROS ATH10K WIRELESS DRIVER
       Mail:          A. Some Human <shuman@example.com>
       Mailing list:  ath10k@lists.infradead.org
       Status:        Supported
       Web-page:      https://wireless.wiki.kernel.org/en/users/Drivers/ath10k
       SCM:           git git://git.kernel.org/pub/scm/linux/kernel/git/kvalo/ath.git
       Files:         drivers/net/wireless/ath/ath10k/
```

注意：如果你阅读 Linux 源码树根目录中找到的纯文本 MAINTAINERS 文件，行
描述会是缩写。例如，'Mail:' 会是 'M:'，'Mailing list:' 会是 'L'，'Status:'
会是 'S:'。文件顶部附近的一节解释了这些及其它缩写。

首先查看 'Status' 行。理想情况下它应该是 'Supported' 或 'Maintained'。如果
它说明是 'Obsolete'，那么你正在使用某种已被更新的解决方案取代、你需要切换
过去的过时方法。有时代码只有某个在有动力时才提供 'Odd Fixes' 的人。而
'Orphan' 意味着你完全运气不好，因为再也没有人照料这段代码了。那只留下这些
选项：安排自己忍受该问题、自己修复它，或在某处找愿意修复它的程序员。

检查状态后，查找以 'bugs:' 开头的行：它会告诉你到哪里找到子系统特定的缺陷
跟踪器来提交你的问题。上面的例子没有这样的行。大多数节都是这种情况，因为
Linux 内核开发完全由邮件驱动。极少子系统使用缺陷跟踪器，并且只有其中一些
依赖 bugzilla.kernel.org。

因此，在这种以及许多其他情况下，你必须查找以 'Mail:' 开头的行。那些提到了
特定代码的维护者的姓名和电子邮件地址。还要查找以 'Mailing list:' 开头的行，
它告诉你开发该代码的公共邮件列表。你随后的报告需要通过邮件发送给那些地址。
此外，对于所有通过电子邮件发送的问题报告，务必将 Linux Kernel Mailing List
(LKML) <linux-kernel@vger.kernel.org> 加入抄送（CC）。稍后通过邮件发送问题
报告时，不要省略其中任何一个邮件列表！维护者是很忙的人，可能会把一些工作留给
子系统特定列表上的其他开发者；而 LKML 对于拥有一个可以找到所有问题报告的
地方很重要。


#### 借助脚本查找维护者


对于手头有 Linux 源码的人，还有第二个选项来找到报告的正确位置：脚本
'scripts/get_maintainer.pl' 会尝试找到所有需要联系的人。它查询 MAINTAINERS
文件，需要用相关源代码的路径来调用。对于编译为

```
       $ modinfo ath10k_pci | grep filename | sed 's!/lib/modules/.*/kernel/!!; s!filename:!!; s!\.ko\(\|\.xz\)!!'
       drivers/net/wireless/ath/ath10k/ath10k_pci.ko
```

```
       $ ./scripts/get_maintainer.pl -f drivers/net/wireless/ath/ath10k*
       Some Human <shuman@example.com> (supporter:QUALCOMM ATHEROS ATH10K WIRELESS DRIVER)
       Another S. Human <asomehuman@example.com> (maintainer:NETWORKING DRIVERS)
       ath10k@lists.infradead.org (open list:QUALCOMM ATHEROS ATH10K WIRELESS DRIVER)
       linux-wireless@vger.kernel.org (open list:NETWORKING DRIVERS (WIRELESS))
       netdev@vger.kernel.org (open list:NETWORKING DRIVERS)
       linux-kernel@vger.kernel.org (open list)
```

不要将你的报告发送给所有这些地址。将它发送给维护者，即脚本称为"supporter:"的
那些；此外抄送该代码最具体的邮件列表以及 Linux Kernel Mailing List (LKML)。
在这种情况下，因此你需要将报告发送给 'Some Human <shuman@example.com>'，并
抄送 'ath10k@lists.infradead.org' 和 'linux-kernel@vger.kernel.org'。

注意：如果你用 git 克隆了 Linux 源码，你可能想用 `--git` 再次调用
`get_maintainer.pl`。然后该脚本会查看提交历史，找出最近处理过相关代码的
人，因为他们或许能提供帮助。但要小心使用这些结果，因为它很容易把你引向
错误的方向。例如，这在很少更改的区域（如旧的或无人维护的驱动程序）会很快
发生：有时此类代码在 tree-wide 清理期间被根本不关心特定驱动程序的开发者
修改。
### 搜索现有报告，第二轮


    *彻底搜索相关缺陷跟踪器或邮件列表的存档，查找可能与你的问题匹配的
    报告。如果找到任何内容，加入讨论而不是发送新的报告。*

正如前面已经提到的：报告别人已经提出过的问题，通常对涉及的所有人都是时间的
浪费，尤其是作为报告者的你。这就是为什么你应该再次搜索现有报告，既然你
现在知道它们需要报告到哪里了。如果是邮件列表，你通常会在
`lore.kernel.org <https://lore.kernel.org/>`_ 上找到它的存档。

但有些列表托管在不同的地方。例如，上一步中用作示例的 ath10k WiFi 驱动程序
就是这种情况。但你通常会轻易在网络上找到这些列表的存档。例如，搜索
'archive ath10k@lists.infradead.org' 会把你带到 `ath10k 邮件列表的信息页
<https://lists.infradead.org/mailman/listinfo/ath10k>`_，它在顶部链接到其
`列表存档 <https://lists.infradead.org/pipermail/ath10k/>`_。遗憾的是，这个
以及相当多的其他列表缺少搜索存档的方式。在那些情况下，使用常规的互联网
搜索引擎，并在你的搜索词中添加类似 'site:lists.infradead.org/pipermail/ath10k/'
的内容，这将结果限制在该 URL 的存档中。

此时再次检查互联网、LKML，也许还有 bugzilla.kernel.org 也是明智的。如果你
的报告需要提交到缺陷跟踪器，你可能还想检查该子系统的邮件列表存档，因为
有人可能只在那里报告过。

有关如何搜索以及如果找到匹配报告该怎么做，请参阅上面的"搜索现有报告，
第一轮"。

在报告过程的这一步不要着急：花 30 到 60 分钟甚至更长时间可以节省你和
其他人相当多的时间和麻烦。


### 安装全新内核用于测试


    *除非你已经在运行最新的'主线（mainline）'Linux 内核，否则最好去安装
    它来进行报告过程。在某些情况下，用最新的'stable'Linux 进行测试和报告
    也是可接受的替代方案；在合并窗口（merge window）期间，这实际上可能是
    最好的方法，但在那个开发阶段，暂停你的努力几天甚至可能是更好的主意。
    无论你选择哪个版本，理想情况下使用'vanilla'构建。忽视这些建议将显著
    增加你的报告被拒绝或忽略的风险。*

正如第一步的详细说明中已经提到的：与大多数程序员一样，Linux 内核开发者
不喜欢花时间处理甚至不会在其当前代码中出现的问题的报告。这只是浪费每个人的
时间，尤其是你的。这就是为什么在报告之前，确认该问题在最新的上游代码中
仍然存在符合每个人的利益。你可以自由忽略此建议，但正如前面所述：这样做
会显著增加你的缺陷报告被拒绝或干脆忽略的风险。

在内核的范畴内，"最新的上游"通常意味着：

 - 安装一个主线内核；最新的 stable 内核可以是一个选项，但大多数时候最好
   避免。Longterm 内核（有时称为'LTS 内核'）在此流程阶段不合适。下一小节
   会更详细地解释这一切。

 - 再下一小节描述了获取和安装此类内核的方法。它还指出，使用预编译的内核
   是可以的，但更好的是 vanilla，即：它是使用直接从 `kernel.org
   <https://kernel.org/>`_ 获取的 Linux 源码构建的，且未以任何方式修改或
   增强。

#### 为测试选择合适的版本


前往 `kernel.org <https://kernel.org/>`_ 找出你想用于测试的版本。忽略写着
'Latest release'（最新发布）的大黄色按钮，往下一点的表格看。在表格顶部你会
看到一行以 mainline 开头，大多数时候它指向一个版本号类似 '5.8-rc2' 的预发布
版本。如果是这种情况，你会想用这个主线内核进行测试，因为所有修复都必须
先应用到那里。不要让那个 'rc' 吓到你，这些"开发内核"相当可靠——而且你
按照上面的指示做了备份，不是吗？

在大约每九到十周中有两周，mainline 可能指向一个版本号类似 '5.7' 的正式发布
版本。如果发生这种情况，考虑暂停报告过程，直到下一个版本的第一个预发布
（5.8-rc1）出现在 kernel.org 上。那是因为那时 Linux 开发周期正处于其长达两周的
"合并窗口"中。大部分改动以及所有侵入性的改动都会在此期间被合并以供下一个
版本使用。在此期间使用主线风险稍大。内核开发者那时通常也很忙，可能没有
空闲时间处理问题报告。在合并窗口期间应用的众多改动之一也很可能修复了你
面临的问题；这就是为什么你很快无论如何都得用更新的内核版本重新测试，如下面
"报告发出后的职责"一节所述。

这就是为什么等到合并窗口结束可能是有意义的。但如果你处理的是不该等待的事情，
就不要那样做。在这种情况下，考虑通过 git 获取最新的主线内核（见下文），或者
使用 kernel.org 上提供的最新 stable 版本。如果主线由于某种原因目前对你不起作用，
使用它也是可接受的。而总的来说：用它来复现问题也比根本不报告问题要好。

在合并窗口之外，最好避免使用最新的 stable 内核，因为所有修复都必须先应用到
主线。这就是为什么检查最新的主线内核如此重要：任何你想在较旧版本系列中看到
修复的问题，都需要先在主线中修复，然后才能被回溯，这可能需要几天或几周。
另一个原因：你所期望的修复可能太难或风险太高而无法回溯；因此再次报告该问题
不太可能改变任何事情。

这些方面也是为什么 longterm 内核（有时称为"LTS 内核"）不适合报告过程的这一
部分：它们与当前代码相距太远。因此先去测试主线并继续后续流程：如果问题在
主线上没有出现，它会指导你如何在较旧的版本系列中修复它（如果该问题的修复
可行的话）。

#### 如何获取全新的 Linux 内核


**使用预编译内核**：这通常是测试最快、最简单、最安全的方式——尤其是当你
不熟悉 Linux 内核时。问题是：发行商或附加软件仓库发布的大多数内核是从
修改后的 Linux 源码构建的。因此它们不是 vanilla，因此通常不适合测试和报告
问题：这些改动可能导致你面临的问题或以某种方式影响它。

但如果你使用的是流行的 Linux 发行版，那你很幸运：对于其中相当多的发行版，
你会在网络上找到包含以 vanilla 内核构建的最新主线或 stable Linux 的软件包
的仓库。使用这些完全没问题，只需从仓库的描述中确认它们是 vanilla 或至少
接近 vanilla。此外，确保软件包包含 kernel.org 上提供的最新版本。如果软件包
比一周还旧，它们可能不合适，因为新的主线和 stable 内核通常每周至少发布一次。

请注意，稍后你可能需要手动构建自己的内核：正如本文档后面所描述的，有时
调试或测试修复需要这样做。还要意识到，预编译的内核可能缺少解码内核在发生
panic、Oops、warning 或 BUG 时打印的消息所需的调试符号；如果你打算解码
这些，自己编译内核可能更好（详见本节末尾和标题为"解码失败消息"的一节）。

**使用 git**：熟悉 git 的开发者和有经验的 Linux 用户通常最好直接从
`kernel.org 上的官方开发仓库
<https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/>`_
获取最新的 Linux 内核源码。这些可能比最新的主线预发布略微超前一点。不必担心：
它们和正式的预发布一样可靠，除非内核的开发周期当前正处于合并窗口中期。但
即使那样它们也相当可靠。

**传统方式**：不熟悉 git 的人通常最好从 `kernel.org <https://kernel.org/>`_
以 tarball 形式下载源码。

如何实际构建内核此处没有描述，因为许多网站已经解释了必要的步骤。如果你是
新手，考虑遵循那些建议使用 `make localmodconfig` 的操作指南之一，因为它会
尝试获取你当前内核的配置，然后为你的系统稍微调整它。这不会让生成的内核
变得更好，但编译更快。

注意：如果你处理的是来自内核的 panic、Oops、warning 或 BUG，请在配置内核时
尝试启用 CONFIG_KALLSYMS。此外，也启用 CONFIG_DEBUG_KERNEL 和 CONFIG_DEBUG_INFO；
后两者中相关的是 CONFIG_DEBUG_INFO，但只有启用前者才能到达它。要注意
CONFIG_DEBUG_INFO 会显著增加构建内核所需的存储空间。但这是值得的，因为这些
选项之后将允许你精确定位触发你问题的确切代码行。下面的"解码失败消息"一节
会更详细地解释这一点。

但请记住：始终保留遇到的问题记录，以防它难以复现。发送一份未解码的报告比
根本不报告问题要好。


### 检查"taint"标志


    *确保你刚安装的内核在运行时不会"污染"自身。*

正如上面更详细地概述的那样：当发生可能导致看起来完全无关的后继错误的事情时，
内核会设置一个"taint"标志。这就是为什么你需要检查你刚安装的内核是否没有
设置此标志。如果它设置了，在几乎所有情况下，你都需要在报告与它一起发生的
问题之前消除其原因。有关如何做到这一点的详细信息，请参阅上面的小节。


### 用全新内核复现问题


    *用你刚安装的内核复现该问题。如果它在那里没有出现，向下滚动到仅发生在
    stable 和 longterm 内核上的问题的说明。*

检查该问题是否发生在你刚安装的崭新 Linux 内核版本上。如果它已经在那里被
修复，考虑坚持使用此版本系列并放弃报告该问题的计划。但请记住，只要它在
kernel.org 的 stable 和 longterm 版本（以及由此衍生的供应商内核）中都没有
被修复，其他用户可能仍会受到它的困扰。如果你更喜欢使用其中之一，或者只是
想帮助他们的用户，请转到下面的"关于仅在较旧内核版本系列中出现的问题的报告
详情"一节。


### 优化复现问题的描述


    *优化你的笔记：尝试找到并写下复现问题最直接的方法。确保最终结果包含
    所有重要细节，同时易于首次听说它的人阅读和理解。如果你在此过程中学到
    了什么，考虑再次搜索关于该问题的现有报告。*

不必要的复杂报告会让其他人难以理解你的报告。因此尝试找到一个描述起来直接、
因而易于书面理解的复现方法。包含所有重要细节，但同时尽量保持尽可能简短。

在本流程之前的步骤中，你很可能已经对面临的问题了解了一二。利用这些知识
再次搜索现有报告，看看是否有你可以加入的。


### 解码失败消息


    *如果你的故障涉及'panic'、'Oops'、'warning'或'BUG'，考虑解码内核日志
    以找到触发该错误的代码行。*

当内核检测到内部问题时，它会记录有关所执行代码的一些信息。这使得精确定位
源代码中触发该问题的确切行，并展示它是如何被调用成为可能。但这只有在你
配置内核时启用了 CONFIG_DEBUG_INFO 和 CONFIG_KALLSYMS 时才有效。如果你这样
做了，考虑解码来自内核日志的信息。这将使理解是什么导致了'panic'、'Oops'、
'warning'或'BUG'容易得多，从而增加有人能提供修复的机会。

解码可以使用你在 Linux 源码树中找到的脚本完成。如果你

```
       [user@something ~]$ sudo dmesg | ./linux-5.10.5/scripts/decode_stacktrace.sh ./linux-5.10.5/vmlinux
```

如果你运行的是打包的 vanilla 内核，你很可能需要安装带有调试符号的相应软件包。
然后调用该脚本（如果你的发行版没有打包它，你可能需要从 Linux 源码中获取）

```
       [user@something ~]$ sudo dmesg | ./linux-5.10.5/scripts/decode_stacktrace.sh \
        /usr/lib/debug/lib/modules/5.10.10-4.1.x86_64/vmlinux /usr/src/kernels/5.10.10-4.1.x86_64/
```

该脚本会对如下所示的日志行生效，这些日志行显示了

```
       [   68.387301] RIP: 0010:test_module_init+0x5/0xffa [test_module]
```

```
       [   68.387301] RIP: 0010:test_module_init (/home/username/linux-5.10.5/test-module/test-module.c:16) test_module
```

在这种情况下，被执行的代码是从文件
'~/linux-5.10.5/test-module/test-module.c' 构建的，错误发生在第 '16' 行的
指令处。

该脚本同样会解码以 'Call trace' 开头的节中提到的地址，这些地址显示了问题
发生所在函数的路径。此外，该脚本会显示内核正在执行的代码段的汇编输出。

注意，如果你无法让这个工作起来，只需跳过此步骤，并在报告中提及原因。如果
你幸运的话，它可能并不需要。如果需要，有人或许能帮你让事情运转起来。还要
意识到这只是解码内核栈追踪的几种方式之一。有时需要不同的步骤来检索相关
细节。如果那是为你的情况所需，不必担心，开发者会告诉你该怎么做。


### 针对回归的特殊处理


    *如果你的问题是回归，尽量尽可能缩小问题被引入的时间范围。*

Linux 首席开发者 Linus Torvalds 坚持 Linux 内核绝不能变差，这就是为什么他认为
回归是不可接受的，并希望尽快看到它们被修复。这就是为什么引入回归的改动
通常会被迅速回退，如果它们引起的问题无法以任何其它方式快速解决的话。因此
报告回归有点像打一种王牌，以便让某件事被快速修复。但要做到这一点，需要
知道导致回归的改动。通常追踪罪魁祸首是报告者的责任，因为维护者通常没有
时间或现成环境来自己复现它。

要找到该改动，有一个称为"二分（bisection）"的过程，文档
Documentation/admin-guide/bug-bisect.rst 对此有详细描述。该过程通常要求你
构建大约十到二十个内核映像，在构建下一个之前尝试用每个映像复现该问题。是的，
这需要一些时间，但别担心，它比大多数人假设的要快得多。得益于"二分搜索"，
这会把你引向源码管理系统中导致回归的那一个提交。一旦找到它，在网络上搜索
该改动的标题、它的 commit id 以及缩短的 commit id（commit id 的前 12 个字符）。
如果有任何现有报告，这会把你引向它们。

注意，二分需要一点并非每个人都有的诀窍，以及相当多的、并非每个人都愿意
投入的努力。尽管如此，高度推荐你自己执行二分。如果你真的不能或不愿走这条
路，至少找出是哪个主线内核引入了回归。例如，如果从 5.5.15 切换到 5.8.4 时
某物损坏，那么至少尝试该区域的所有主线发布版本（5.6、5.7 和 5.8）以检查它是
何时首次出现的。除非你试图在 stable 或 longterm 内核中查找回归，否则避免
测试版本号有三个小节（5.6.12、5.7.8）的版本，因为这会让结果难以解释，从而
可能使你的测试变得无用。一旦你找到了引入回归的主版本，就可以自由地继续
报告过程。但请记住：在不知道罪魁祸首的情况下开发者能否提供帮助，取决于
手头的问题。有时他们可能从报告中认出哪里出了问题并能够修复它；其他时候，
除非你执行二分，否则他们将无法提供帮助。

在处理回归时，确保你面临的问题确实是由内核引起的，而不是由其它东西引起的，
正如上面已经概述的那样。

在整个过程中请记住：只有当较旧和较新的内核是用相似配置构建时，该问题才有
资格作为回归。这可以通过使用 `make olddefconfig` 来实现，如
Documentation/admin-guide/reporting-regressions.rst 中更详细地解释的那样；该
文档还提供了大量你可能想知道的关于回归的其它信息。


### 撰写并发送报告


    *通过撰写关于该问题的详细描述来开始编写报告。始终提及几点：你为复现
    而安装的最新内核版本、所使用的 Linux 发行版，以及你关于如何复现问题的
    笔记。理想情况下，将内核的构建配置（.config）和 `dmesg` 的输出放在
    网络上的某处并提供链接。包含或上传所有其他可能相关的信息，例如 Oops 的
    输出/截图或 `lspci` 的输出。写完这个主要部分后，在它顶部插入一个正常
    长度的段落，快速概述问题和影响。在此之上添加一句话，简要描述问题并让人
    继续读下去。现在给这个东西一个描述性的标题或主题，但要更短。然后你就
    可以像 MAINTAINERS 文件告诉你的那样发送或提交报告，除非你处理的是那些
    '高优先级问题'之一：它们需要特殊处理，这在下面的'高优先级问题的特殊
    处理'中解释。*

既然你已经准备好了一切，是时候写你的报告了。如何做到这一点部分由上面前言中
链接的三个文档解释。这就是为什么本文本只会提及一些要点以及 Linux 内核特有
的内容。

有一件事同时符合这两类：你报告中最关键的部分是标题/主题、第一句话和第一段。
开发者通常会收到相当多的邮件。因此他们通常只花几秒钟浏览一封邮件，然后决定
是继续还是仔细查看。因此：你的报告顶部部分写得越好，就越有可能有人查看它
并帮助你。这就是为什么你现在应该忽略它们，先写详细报告。 ;-)

#### 每份报告都应提及的内容


详细描述该问题如何发生在你安装的崭新 vanilla 内核上。尝试包含你之前撰写并
优化的分步说明，概述你和（理想情况下）其他人如何复现该问题；在那些不可能
的罕见情况下，尝试描述你做了什么来触发它。

还要包含其他人可能需要理解该问题及其环境的所有相关信息。实际所需的内容
在很大程度上取决于问题，但有些东西你应该始终包含：

 - `cat /proc/version` 的输出，其中包含 Linux 内核版本号以及构建它所用的
   编译器。

 - 机器运行的 Linux 发行版（``hostnamectl | grep "Operating System"``）

 - CPU 和操作系统（operating system）的架构（`uname -mi`）

 - 如果你处理的是回归并执行了二分，提及导致它的改动的标题和 commit-id。

在很多情况下，让阅读你报告的人也能获取另外两样东西也是明智的：

 - 用于构建你的 Linux 内核的配置（'.config' 文件）

 - 你从 `dmesg` 写入文件的kernel 消息。确保它以类似 'Linux version 5.8-1
   (foobar@example.com) (gcc (GCC) 10.2.1, GNU ld version 2.34) #1 SMP Mon Aug
   3 14:54:37 UTC 2020' 这样的行开头。如果缺少它，那么来自第一个启动阶段的
   重要消息已经被丢弃了。在这种情况下，改为考虑使用 `journalctl -b 0 -k`；
   或者你也可以重启、复现该问题，然后立即调用 `dmesg`。

这两个文件很大，因此直接把它们放进你的报告是个坏主意。如果你在缺陷跟踪器中
提交问题，请将它们附加到工单上。如果你通过邮件报告问题，不要附加它们，因为
那会使邮件过大；而是做以下事情之一：

 - 将文件上传到某个公开的地方（你的网站、公共文件粘贴服务、在
   `bugzilla.kernel.org <https://bugzilla.kernel.org/>`_ 上为此目的创建的
   工单，……）并在你的报告中包含指向它们的链接。理想情况下使用文件能保存
   多年的地方，因为多年后它们可能对某人有用；例如，如果五年或十年后某个
   开发者在处理一些仅仅为了修复你的问题而更改的代码时，就可能发生这种情况。

 - 把文件放在一边，并提及你稍后会在给你自己邮件的单独回复中发送它们。只要
   记得在报告发出后确实这样做。 ;-)

#### 可能明智提供的东西


根据你的问题，你可能需要添加更多背景数据。这里有一些通常值得提供的建议：

 - 如果你处理的是来自内核的 'warning'、'OOPS' 或 'panic'，请包含它。如果你
   无法复制粘贴它，尝试捕获一个 netconsole 追踪，或者至少拍一张屏幕照片。

 - 如果问题可能与你的计算机硬件有关，提及你使用的系统种类。例如，如果你
   的显卡有问题，提及它的制造商、卡的型号，以及它使用的芯片。如果是笔记本，
   提及它的名称，但尽量确保它有意义。例如 'Dell XPS 13' 就不合适，因为它可能
   是 2012 年的那一款；那款与今天出售的那款看起来差别不大，但除此之外两者
   毫无共同之处。因此，在这种情况下添加确切的型号，例如 2019 年推出的 XPS 13
   型号是 '9380' 或 '7390'。像 'Lenovo Thinkpad T590' 这样的名称也有些含糊：
   这台笔记本有带和不带独立显卡芯片的变体，所以尝试找到确切的型号名称或
   指明主要组件。

 - 提及所使用的相关软件。如果你在加载模块时遇到问题，你会想提及所用 kmod、
   systemd 和 udev 的版本。如果某个 DRM 驱动程序行为异常，你会想说明 libdrm
   和 Mesa 的版本；还要指明你的 Wayland 合成器（compositor）或 X-Server 及其
   驱动程序。如果你有文件系统问题，提及相应文件系统工具（e2fsprogs、btrfs-progs、
   xfsprogs，……）的版本。

 - 从内核收集其它可能令人感兴趣的信息。例如，`lspci -nn` 的输出将帮助他人
   识别你使用的硬件。如果你有硬件问题，你甚至可能想提供 `sudo lspci -vvv`
   的输出，因为它提供了组件如何被配置的洞见。对于某些问题，包含像
   `/proc/cpuinfo`、`/proc/ioports`、`/proc/iomem`、`/proc/modules` 或
   `/proc/scsi/scsi` 这样的文件内容可能是好的。一些子系统还提供收集相关
   信息的工具。其中一个这样的工具是 `alsa-info.sh`，`音频/声音子系统开发者
   提供的 <https://www.alsa-project.org/wiki/AlsaInfo>`_。

这些例子应该给你一些关于哪些数据可能明智地附加的想法，但你必须自己思考
什么对别人了解会有帮助。不要太担心遗漏了什么，因为开发者会索要他们需要的
额外细节。但从一开始就提供所有重要的东西会增加有人仔细查看的机会。


#### 重要部分：报告的头部


既然你已经准备好了报告的详细部分，让我们进入最重要的部分：开头几句话。因此
转到顶部，在你刚写的部分之前加上类似"详细描述了："的内容，并在顶部插入两个
换行。现在写一段正常长度的段落，粗略描述该问题。略去所有无聊的细节，专注于
读者需要了解的、以理解这是怎么回事的关键部分；如果你认为这个缺陷影响了
很多用户，提及这一点以引起人们的兴趣。

一旦你这样做完，在顶部再插入两行，写一句话摘要，快速解释报告是关于什么的。
之后你必须更加抽象，为报告写一个更短的主题/标题。

既然你已经写好了这部分，花些时间优化它，因为它是你报告中最重要的部分：很多
人只会在决定阅读其余部分是否值得花时间之前读这部分。

现在像 MAINTAINERS <maintainers> 文件告诉你的那样发送或提交报告，除非它是
前面概述的那些"高优先级问题"之一：在这种情况下，请先阅读下面的小节再发送
报告。

#### 高优先级问题的特殊处理


高优先级问题的报告需要特殊处理。

**严重问题**：确保主题或工单标题以及第一段让严重性显而易见。

**回归**：让报告的标题以 '[REGRESSION]' 开头。

如果你执行了成功的二分，使用引入回归的改动的标题作为你标题的第二部分。让
报告也提及罪魁祸首的 commit id。如果二分不成功，让你的报告提及工作正常的
最新测试版本（例如 5.7）以及问题出现的最旧版本（例如 5.8-rc1）。

通过邮件发送报告时，抄送（CC）Linux regressions 邮件列表
（regressions@lists.linux.dev）。如果报告需要提交到某个 Web 跟踪器，请照做。
一旦提交，通过邮件将报告转发到 regressions 列表；抄送相关子系统的维护者及其
邮件列表。确保内联转发报告，因此不要附加它。还要在顶部添加一条简短说明，
在其中提及该工单的 URL。

通过邮件发送或转发报告时，如果二分成功，将罪魁祸首的作者加入收件人；同时
抄送 sign-off-by 链中的所有人，你可以在其提交信息的末尾找到他们。

**安全问题**：对于这些问题，你将不得不评估如果细节被公开披露，是否会对
其他用户造成短期风险。如果不是这种情况，只需按所述继续报告该问题。对于
带有此类风险的问题，你需要稍微调整报告过程：

 - 如果 MAINTAINERS 文件指示你通过邮件报告问题，不要抄送任何公共邮件列表。

 - 如果你本应将问题提交到缺陷跟踪器，请确保将工单标记为"private"或"security
   issue"。如果缺陷跟踪器不提供将报告保密的方式，那就别管它，改为将你的报告
   作为私人邮件发送给维护者。

在这两种情况下，确保也将你的报告邮寄到 MAINTAINERS 文件在"security contact"
一节中列出的地址。理想情况下在通过邮件发送报告时直接抄送他们。如果你将它
提交到缺陷跟踪器，将报告文本转发到这些地址；但在它上面放一条小说明，在其中
提及你提交了它并附上工单链接。

有关更多信息，请参阅 Documentation/process/security-bugs.rst。


### 报告发出后的职责


    *等待反应，并保持进展，直到你能以某种方式接受结果。因此要公开并及时地
    回应任何询问。测试建议的修复。进行主动测试：用每个新主线版本的第一个
    候选版本（RC）重新测试并报告你的结果。如果事情停滞，发送友好的提醒。
    如果你得不到任何帮助或帮助不令人满意，尝试自助。*

如果你的报告写得很好，而且你真的很幸运，那么某个开发者可能立即发现是什么
导致了问题；然后他们可能写一个补丁来修复它，测试它，并直接将它发送以集成
到主线，同时标记它以便稍后回溯到需要它的 stable 和 longterm 内核。然后你
需要做的就是用一句"非常感谢"回复，并在修复发布后切换到带有修复的版本。

但这种理想的场景很少发生。这就是为什么一旦你把报告发出，工作才刚刚开始。
你需要做什么取决于具体情况，但通常会是下面列出的事情。但在深入细节之前，
这里有几件你需要为过程的这一部分牢记的重要事情。


#### 进一步互动的一般建议


**始终公开回复**：当你在缺陷跟踪器中提交了问题时，始终在那里回复，不要
私下联系任何开发者讨论它。对于邮件报告，回复收到的任何邮件时始终使用
"Reply-all"（全部回复）功能。这包括你可能想添加到报告中的带有任何额外
数据的邮件：转到你邮件应用的"已发送"文件夹，并对你带有报告的邮件使用
"reply-all"。这种方法将确保公共邮件列表以及随着时间推移参与进来的其他所有人
都保持知情；它也保持邮件线索完整，这对于邮件列表将所有相关邮件归类在一起
尤其重要。

只有两种情况不适合在缺陷跟踪器中评论或使用"Reply-all"：

 - 有人告诉你私下发送某些东西。

 - 你被告知要发送某些东西，但注意到它包含需要保密的敏感信息。在这种情况下，
   可以私下将它发送给索要它的开发者。但在工单或邮件中注明你这样做了，以便
   其他所有人都知道你遵从了请求。

**在请求澄清或帮助之前先做研究**：在过程的这一部分，有人可能告诉你做一些
需要你尚未掌握的技能的事情。例如，你可能被要求使用你从未听说过的某些测试
工具；或者你可能被要求将补丁应用到 Linux 内核源码以测试它是否有帮助。在某些
情况下，发送回复询问如何做的说明是可以的。但在走这条路之前，尝试通过搜索
互联网自己找到答案；或者考虑在其他地方寻求建议。例如问问朋友，或者在你
通常出没的聊天室或论坛上发帖。

**要有耐心**：如果你真的很幸运，你可能在几小时内得到对报告的回复。但大多数
时候需要更长时间，因为维护者分散在全球各地，因此可能处于不同的时区——一个
他们已经远离键盘享受夜晚的时区。

一般来说，内核开发者会花一到五个工作日来回应报告。有时会更长，因为他们可能
忙于合并窗口、其它工作、参加开发者会议，或者干脆在享受漫长的暑假。

"高优先级问题"（解释见上文）在这里是个例外：维护者应该尽快处理它们；这
就是为什么你最多应该等待一周（如果是紧急的事则仅两天）再发送友好的提醒。

有时维护者可能没有及时回应；其他时候可能存在分歧，例如某个问题是否符合
回归。在这种情况下，在邮件列表上提出你的担忧，并公开或私下询问他人如何
继续。如果这失败了，让更高级别的权威介入可能是合适的。如果是 WiFi 驱动程序，
那就是无线维护者；如果没有更高级别的维护者，或者一切都失败了，可能就是那些
罕见情况之一，此时让 Linus Torvalds 介入是可以的。

**主动测试**：每当一个新主线内核版本的第一个预发布（'rc1'）发布时，去检查
该问题是否在那里被修复，或者是否有任何重要变化。在工单中或作为对你报告的
回复的邮件中提及结果（确保将所有截至那时参与讨论的人都抄送到 CC）。这将
显示你的投入和愿意提供帮助。它也告诉开发者该问题是否持续存在，并确保他们
不会忘记它。一些其它的偶尔重新测试（例如用 rc3、rc5 和最终版）也是个好主意，
但只有在有相关变化发生或你本来就在写些什么时才报告你的结果。

在把所有一般性事项说完之后，让我们进入一旦问题被报告，如何帮助解决问题的
细节。

#### 询问与测试请求


以下是你在收到对报告的回复时的职责：

**弄清你在和谁打交道**：大多数时候会是特定代码区域的维护者或开发者回应
你的报告。但由于问题通常是在公开场合报告的，回复的可能是任何人——包括
想提供帮助的人，但最终可能会用他们的问题或请求把你完全带偏。这种情况很少
发生，但这就是为什么快速进行互联网搜索以了解你在和谁互动是明智的，这是
众多原因之一。通过这样做，你也能意识到你的报告是否被正确的人听到了，因为
如果讨论在没有导向令人满意的解决方案的情况下逐渐平息，稍后对维护者的提醒
（见下文）可能是合适的。

**询问数据**：通常你会被要求测试某些东西或提供额外细节。尽量尽快提供所
请求的信息，因为你引起了某个可能提供帮助的人的注意，等待越久越有可能失去
它；如果你在几个工作日内没有提供信息，这种结果甚至很可能发生。

**测试请求**：当你被要求测试诊断补丁或可能的修复时，也尽量及时测试它。但
要恰当地做，并确保不要仓促：混淆事情很容易发生，并可能给所有相关人员带来
大量困惑。例如一个常见的错误是以为应用了带有修复的提议补丁，但实际上没有。
这样的事情甚至偶尔发生在有经验的测试者身上，但他们大多数时候会在带有修复的
内核表现得和没有修复的内核一样时注意到。

#### 当事情没有实质性进展时该怎么做


一些报告不会得到负责的 Linux 内核开发者的任何反应；或者围绕问题的讨论
展开了，但逐渐平息，没有产生任何实质性结果。

在这些情况下，在发送友好的提醒之前等待两周（更好：三周）：也许当你的报告
到达时维护者只是暂时离开键盘，或者有更重要的事情要处理。写提醒时，友好地
询问是否还需要你这边的任何其它东西以某种方式让事情运转起来。如果报告是通过
邮件发出的，请在作为对你初始邮件（见上文）的回复的邮件的前几行中这样做，其中
在下面包含原始报告的完整引用：这是少数几种"TOFU"（Text Over, Fullquote
Under，文上全引于下）是正确方法的情况之一，因为那样所有收件人都会立即以正确的
顺序掌握细节。

提醒之后，再等待三周以等待回复。如果你仍然没有得到适当的反应，你首先应该
重新考虑你的方法。你是否可能试图联系了错误的人？报告是否可能带有攻击性，或者
如此令人困惑以至于人们决定完全避开它？排除此类因素的最佳方法：将报告展示给
一两个熟悉 FLOSS 问题报告的人，并征求他们的意见。也向他们询问如何推进的建议。
那可能意味着：准备一份更好的报告，并让那些人在你发出之前审阅它。这种方法
完全没问题；只需提及这是关于该问题的第二份也是改进过的报告，并包含第一份
报告的链接。

如果报告是恰当的，你可以发送第二个提醒；在其中询问为什么报告没有得到任何
回复的建议。第二个提醒邮件的好时机是新 Linux 内核版本的第一个预发布（'rc1'）
发布后不久，因为无论如何你在该时刻都应该重新测试并提供状态更新（见上文）。

如果第二个提醒在一周内再次没有引起任何反应，尝试联系更高级别的维护者寻求
建议：即使是忙碌的维护者到那时也应该至少发送某种确认。

记住为自己可能失望做好准备：维护者理想情况下应该以某种方式对每份问题报告
作出反应，但他们只义务修复前面概述的那些"高优先级问题"。因此，如果你得到
类似"感谢报告，我当前有更重要的问题要处理，在可预见的未来没有时间查看这个"
的回复，不要过于崩溃。

也有可能是在缺陷跟踪器或列表上经过一些讨论后什么都没有再发生，提醒也无助于
激励任何人制定出修复。这种情况可能令人崩溃，但在 Linux 内核开发中是在
意料之中的。这个以及其它几个得不到帮助的原因在本文档末尾附近的"为什么有些
问题在报告后得不到任何反应或仍然未修复"中解释。

如果你找不到任何帮助，或者问题最终没有得到解决，不要崩溃：Linux 内核是
FLOSS，因此你仍然可以自助。例如，你可以尝试找到其他受影响的人，并与他们
组队以解决该问题。这样一个团队可以一起准备一份新鲜报告，提及你们有多少人
以及为什么在你们看来这是应该被修复的东西。也许你们一起还能缩小根本原因或
引入回归的改动，这通常使开发修复更容易。并且运气好的话，团队中可能有
知道一点编程并可能能够编写修复的人。
### 关于"在 stable 和 longterm 内核系列中报告回归"的参考


本节为你如果在 stable 和 longterm 内核系列中面临回归时需要执行的步骤提供
详情。

#### 确保特定版本系列仍受支持


    *检查内核开发者是否仍在维护你关心的 Linux 内核版本系列：前往 kernel.org
    首页，确保它提到特定版本系列的最新发布版本且没有 '[EOL]' 标签。*

大多数内核版本系列只获得大约三个月的支持，因为维护它们更长时间是相当多
的工作。因此，每年只选择一个并获得至少两年（通常六年）的支持。这就是为什么
你需要检查内核开发者是否仍支持你关心的版本系列。

注意，如果 kernel.org 在首页列出了两个 stable 版本系列，你应该考虑切换到
较新的那个并忘掉较旧的那个：对它的支持可能很快就会被放弃。然后它会得到一个
"end-of-life"（EOL，生命周期结束）标记。到达这一点的版本系列仍会在 kernel.org
首页上被提及一两周，但不适合测试和报告。

#### 搜索 stable 邮件列表


    **检查 Linux stable 邮件列表的存档以查找现有报告。**

也许你面临的问题已经为人所知，并且已被修复或即将被修复。因此，`搜索 Linux
stable 邮件列表的存档 <https://lore.kernel.org/stable/>`_，查找关于类似你问题
的报告。如果你找到任何匹配，考虑加入讨论，除非修复已经完成并计划很快被应用。

#### 用最新发布版本复现问题


    *安装特定版本系列的最新发布版本作为 vanilla 内核。确保此内核未被污染且
    仍显示该问题，因为该问题可能已经在那里被修复。如果你最初是在供应商
    内核上注意到该问题，请检查已知可正常工作的最后一个版本的 vanilla 构建
    也表现良好。*

在为此过程投入更多时间之前，你想检查该问题是否已经在你感兴趣的版本系列的
最新发布版本中被修复。这个内核需要是 vanilla，并且在问题发生之前不应被污染，
正如上面"安装全新内核用于测试"一节所详细概述的那样。

你最初是用供应商内核注意到回归的吗？那么供应商应用的改动可能正在造成干扰。
你需要通过重新检查来排除这一点。假设你从 5.10.4-vendor.42 更新到 5.10.5-vendor.43
时某物损坏。那么，在按照上一段所述测试了最新的 5.10 发布版本后，检查 Linux
5.10.4 的 vanilla 构建是否也表现良好。如果那里也损坏了，该问题没有资格作为
上游回归，你需要切换回主要的分步指南来报告问题。

#### 报告回归


    *将简短的问题报告发送到 Linux stable 邮件列表（stable@vger.kernel.org），
    并抄送 Linux regressions 邮件列表（regressions@lists.linux.dev）；如果你
    怀疑原因在某个特定子系统，抄送其维护者和其邮件列表。粗略描述问题，并
    理想情况下说明如何复现它。提及首次出现问题的版本以及最后一个正常工作
    的版本。然后等待进一步的指示。*

在报告 stable 或 longterm 内核系列中发生的回归（例如从 5.10.4 更新到 5.10.5）
时，开始时一份简短的报告就足以快速上报该问题。因此，向 stable 和 regressions
邮件列表做一个粗略描述就足够了；但如果你怀疑问题根源在某个特定子系统，也请
同时抄送其维护者和邮件列表，因为这样会加快处理速度。

请注意，如果你能指明引入该问题的确切版本，对开发者帮助很大。因此，在合理
的时间范围内，尽可能使用 vanilla 内核来查找该版本。假设你所使用的发行版在
从 Linux 内核 5.10.5 更新到 5.10.8 时出现了问题。那么按照上面的指示，去检查
该版本系列的最新内核，例如 5.10.9。如果它仍然有问题，尝试一个 vanilla 5.10.5，
以确保发行商应用的补丁不会造成干扰。如果问题在那里没有出现，尝试 5.10.7，
然后（视结果而定）尝试 5.10.8 或 5.10.6，以找出问题首次出现的版本。在报告中
提及它，并说明 5.10.9 仍然有问题。

上一段概述的实质上是一个粗略的手动"二分（bisection）"。一旦你的报告发出，
你可能会被要求做一次正式的二分，因为它允许精确定位导致问题的确切改动（然后
可以轻松地将其回退以快速修复问题）。因此，如果时间允许，考虑立即进行一次
正式的二分。详见"针对回归的特殊处理"一节以及文档
Documentation/admin-guide/bug-bisect.rst 了解如何执行。如果二分成功，请将
罪魁祸首（culprit）的作者加入收件人；同时抄送 sign-off-by 链中的所有人，你
可以在其提交信息的末尾找到他们。


### 关于"仅在较旧内核版本系列中出现的问题"的参考


本节为你提供细节，说明如果无法用主线（mainline）内核复现你的问题，但希望在
较旧版本系列（即 stable 和 longterm 内核）中修复它时，需要采取的步骤。

#### 有些修复过于复杂


    *为自己做好心理准备：执行接下来的几个步骤可能仍无法在较旧版本中解决
    问题：该修复可能太大或风险太高，无法回溯（backport）到那里。*

即使是微小的、看似显而易见的代码改动，有时也会引入全新且完全出乎意料的问题。
stable 和 longterm 内核的维护者非常清楚这一点，因此只会对这些内核应用符合
Documentation/process/stable-kernel-rules.rst 中所列规则的改动。

例如，复杂或有风险的改动不符合条件，因此只会被应用到主线。其他修复很容易
回溯到最新的 stable 和 longterm 内核，但集成到更旧的版本中风险过高。所以要
意识到，你所期望的修复可能正属于那些不会被回溯到你关心的版本系列之列。在
这种情况下，除了忍受该问题或切换到更新的 Linux 版本之外，你别无选择，除非
你想自己将该修复补丁到你的内核中。

#### 通用准备


    *执行上文"仅在较旧内核版本系列中出现的问题"一节中的前三个步骤。*

你需要执行本指南另一节中已经描述过的几个步骤。这些步骤将让你：

 - 检查内核开发者是否仍在维护你关心的 Linux 内核版本系列。

 - 在 Linux stable 邮件列表中搜索已有的报告。

 - 用最新发布版本进行检查。


#### 检查代码历史并搜索现有讨论


    *在 Linux 内核版本控制系统（version control system）中搜索在主线中修复
    该问题的改动，因为其提交信息可能会告诉你该修复是否已被安排回溯。如果
    以此方式找不到任何内容，搜索相应的邮件列表，查找讨论此类问题或同行评审
    （peer-review）可能的修复的帖子；然后查看讨论，确认该修复是否被认为
    不适合回溯。如果根本就没有考虑过回溯，加入最新的讨论，询问是否有这种
    可能。*

在很多情况下，你处理的问题在主线中也曾出现，但已在那里被修复。修复它的提交
也需要被回溯才能解决问题。这就是为什么你要搜索它或围绕它的任何讨论。

 - 首先尝试在保存 Linux 内核源代码的 Git 仓库中找到该修复。你可以使用 Web
   界面 `on kernel.org
   <https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/>`_
   或其镜像 `on GitHub <https://github.com/torvalds/linux>`_ 来做到这一点；如果
   你有本地克隆，也可以在命令行用 ``git log --grep=<pattern>`` 搜索。

   如果找到了修复，查看提交信息靠近末尾处是否包含一个如下所示的 "stable tag"：

          Cc: <stable@vger.kernel.org> # 5.4+

   如果情况如此，开发者已将该修复标记为可安全回溯到 5.4 及更高版本。大多数
   情况下它会在两周内被应用到那里，但有时需要更长时间。

 - 如果提交没有告诉你任何信息，或者你找不到修复，再次查找关于该问题的讨论。
   用你喜欢的互联网搜索引擎搜索网络，以及 `Linux kernel developers mailing
   list <https://lore.kernel.org/lkml/>`_ 的存档。同时阅读上面的 `Locate kernel
   area that causes the issue`（定位导致问题的内核区域）一节，并按照其中的
   说明找到相关子系统：其缺陷跟踪器或邮件列表存档可能有你要找的答案。

 - 如果你看到一个建议的修复，按照上述方式在版本控制系统中搜索它，因为该提交
   可能会告诉你是否可以预期一次回溯。

   - 检查讨论中是否有任何迹象表明该修复风险过高，无法回溯到你关心的版本系列。
     如果是这种情况，你只能忍受该问题或切换到应用了该修复的内核版本系列。

   - 如果修复不包含 stable tag，且未讨论回溯，加入讨论：提及你遇到问题的版本，
     以及如果合适的话你希望看到它被修复。

#### 请求建议


    *上述步骤之一应当能带来解决方案。如果不奏效，向你怀疑导致该问题的
    子系统的维护者请求建议；同时抄送该特定子系统的邮件列表以及 stable 邮件
    列表。*

如果前三个步骤没能让你更接近解决方案，只剩下一个选择：请求建议。在发送给
问题似乎根源所在子系统的维护者的邮件中这样做；抄送该子系统的邮件列表以及
stable 邮件列表（stable@vger.kernel.org）。


## 附录：为何向内核报告缺陷有些困难


Linux 内核开发者很清楚，向他们报告缺陷比其他自由/开源软件（Free/Libre Open
Source）项目更难。其中的许多原因在于内核的本质、Linux 的开发模型，以及世界
使用内核的方式：

- *大多数 Linux 发行版的内核完全不适合向上游报告缺陷。* 上面的参考一节已经
  详细解释了这一点：过时的代码库以及修改和附加组件会导致内核缺陷，这些缺陷
  要么早已在上游被修复，要么一开始就没有在上游出现过。其他开源软件的开发者
  也面临这些问题，但在内核方面情况要糟糕得多，因为改动及其影响要严重得多——
  这也是为什么许多内核开发者期望报告使用的是由全新且几乎未经修改的源代码
  构建的内核。

- **缺陷通常只出现在特定环境中。** 这是因为 Linux 主要由驱动程序组成，并且
  可以以多种方式有使用。开发者通常手头没有匹配的环境——因此经常必须依赖缺陷
  报告者来隔离问题的原因并测试建议的修复。

- **内核有数百名维护者，但全才（all-rounder）非常稀少。** 这同样是由众多特性
  和驱动造成的后果，由于这个原因，许多内核开发者对自己代码相关的底层或高层
  了解甚少，对其他领域更是所知无几。

- *很难找到向哪里报告问题，原因之一是没有集中的缺陷跟踪器。* 即使是一些内核
  开发者也不喜欢这一点，但这是目前每个人都不得不面对的情况。

- *stable 和 longterm 内核主要由专门的"stable 团队"维护，该团队只处理在
  stable 和 longterm 系列中引入的回归。* 当有人报告缺陷时，比如使用 Linux 6.1.2，
  因此团队总会询问主线是否受影响：如果该缺陷在 6.1 中已经发生，或在最新主线
  （例如 6.2-rc3）中出现，他们会为了所有人的利益将其推给常规开发者，因为他们
  最了解代码。

- **Linux 开发者可以自由专注于最新主线。** 因此，有些人对关于例如 Linux 6.0
  中缺陷（而 6.1 已经发布）的报告反应冷淡；一旦 6.2-rc1 发布，即使后者也可能
  不够。有些人也会不太欢迎关于 6.1.5 或 6.1.6 的报告，因为问题可能是 stable
  团队（见上文）引起的系列特定回归，必须由他们修复。

- **有时无人可求助。** 有时这是因为缺乏硬件文档——例如，当一个驱动程序是通过
  逆向工程构建的，或者在硬件制造商弃之不顾后由业余时间的开发者接管时。其他
  时候甚至无人可向其报告缺陷：当维护者离开而没有接替者时，他们的代码只要有
  用途就常会留在内核中。

其中一些方面可以得到改进以促进缺陷报告——许多 Linux 内核开发者清楚这一点，
并乐于看到少数个人或某个实体将此作为他们的使命。
