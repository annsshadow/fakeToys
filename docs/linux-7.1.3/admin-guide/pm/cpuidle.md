

## CPU 空闲时间管理

:Author: Rafael J. Wysocki <rafael.j.wysocki@intel.com>


## 概念


现代处理器通常能够进入某些状态，在这些状态下程序的执行被挂起，属于该程序的指令不会从内存中取出或执行。这些状态就是处理器的**空闲（idle）**状态。

由于在空闲状态下处理器的部分硬件未被使用，进入空闲状态通常可以降低处理器消耗的功率，从而提供了节省能量的机会。

CPU 空闲时间管理就是这样一种能效特性，其目的是利用处理器的空闲状态来节省能量。

### 逻辑 CPU


CPU 空闲时间管理针对的是**CPU 调度器**（即内核中负责分配系统中计算工作的部分）所看到的 CPU。在它看来，CPU 是**逻辑**单元。也就是说，它们不必是彼此独立的物理实体，而可能只是软件层面上表现为独立单核处理器的接口。换句话说，一个 CPU 是这样一个实体：它看起来从内存中取得属于某一序列（程序）的指令并执行它们，但它实际上未必以这种方式在物理上工作。一般而言，这里可以考虑三种不同的情况。

首先，如果整个处理器同一时刻只能遵循一条指令序列（一个程序），那么它就是一个 CPU。在这种情况下，如果要求硬件进入空闲状态，那么这会作用于整个处理器。

其次，如果处理器是多核的，其中的每个核心同一时刻至少能够遵循一个程序。这些核心彼此之间不必完全独立（例如，它们可能共享缓存），但在大多数时间里它们在物理上彼此并行工作，因此如果每个核心只执行一个程序，这些程序在同时刻基本上彼此独立地运行。在这种情况下整个核心是 CPU，如果要求硬件进入空闲状态，那么这会作用于最初请求空闲状态的核心，但也可能作用于该核心所属的更大单元（比如一个“package”或“cluster”）。事实上，它可能作用于包含该核心的一整层更大的单元。也就是说，如果更大单元中除一个核心之外的所有其他核心都已在“核心级”进入了空闲状态，而剩下的那个核心要求处理器进入空闲状态，这可能会触发处理器把整个更大单元置入空闲状态，而这也会影响该单元中的其他核心。

最后，多核处理器中的每个核心可能能够在同一时间帧内遵循多个程序（也就是说，每个核心可能能够从内存中的多个位置取得指令并在同一时间帧内执行它们，但不一定完全彼此并行）。在这种情况下，核心在软件层面表现为“捆绑体（bundle）”，每个捆绑体由多个独立的单核“处理器”组成，这些单核处理器被称为**硬件线程**（在 Intel 硬件上具体称为超线程），每个硬件线程可以遵循一条指令序列。于是，从 CPU 空闲时间管理的角度看，硬件线程就是 CPU，如果其中一个硬件线程要求处理器进入空闲状态，那么请求该状态的那一硬件线程（或 CPU）会被停止，但不会发生更多的事情，除非同一核心内的所有其他硬件线程也都已要求处理器进入空闲状态。在这种情况下，该核心可能被单独置入空闲状态，或者包含它的更大单元可能被整体置入空闲状态（如果该更大单元内的其他核心已经处于空闲状态）。

### 空闲 CPU


逻辑 CPU（下文简称为“CPU”）在没有待运行任务、只有特殊的“idle”任务时，被 Linux 内核视为**空闲**。

任务是 CPU 调度器对工作量的表示。每个任务由一串待执行的指令（或称代码）、运行该代码时被操作的数据，以及每次 CPU 运行该任务代码时需要加载到处理器中的某些上下文信息组成。CPU 调度器通过将任务分配给系统中存在的 CPU 来分配工作。

任务可以处于各种状态。特别地，当没有任何特定条件阻止其代码被 CPU 运行（只要有可用的 CPU 即可）时，它们是**可运行（runnable）**的（例如，它们不等待任何事件发生或类似情况）。当一个任务变为可运行时，CPU 调度器将其分配给某个可用 CPU 运行；如果分配给它的可运行任务已没有更多，该 CPU 将加载给定任务的上下文并运行其代码（从迄今为止执行的最后一条指令之后的那条指令开始，该指令可能由另一个 CPU 执行过）。[如果一个 CPU 上同时分配了多个可运行任务，它们将受到优先级排序和时间片共享的约束，以便使它们随时间推移都能取得一定进展。]

当没有其它可运行任务分配给给定 CPU 时，特殊的“idle”任务变为可运行，此时该 CPU 被视为空闲。换句话说，在 Linux 中，空闲 CPU 运行称为**空闲循环（idle loop）**的“idle”任务的代码。如果有支持，该代码可能会让处理器进入某个空闲状态以节省能量，但如果处理器不支持任何空闲状态，或者距离下一次唤醒事件没有足够时间停留在空闲状态，又或者存在严格的延迟约束使得任何可用空闲状态都无法使用，那么 CPU 将只是在一个循环中执行或多或少无用的指令，直到被分配一个新的任务来运行。


## 空闲循环


空闲循环代码在每次迭代中采取两个主要步骤。首先，它调用一个名为**governor**（调度器）的代码模块，该模块属于称为 `CPUIdle` 的 CPU 空闲时间管理子系统，用于为 CPU 选择一个要请求硬件进入的空闲状态。其次，它调用 `CPUIdle` 子系统中的另一个代码模块，称为**driver**（驱动），用于实际请求处理器硬件进入 governor 所选的空闲状态。

governor 的作用是找到最适合当前情况的空闲状态。为此，逻辑 CPU 可以请求硬件进入的空闲状态以一种与平台或处理器架构无关的方式进行抽象表示，并组织成一个一维（线性）数组。该数组必须由与内核运行所在平台相匹配的 `CPUIdle` driver 在初始化时准备并提供。这使得 `CPUIdle` governor 能够独立于底层硬件，并与 Linux 内核可运行的任何平台配合工作。

该数组中的每个空闲状态都有两个参数需要 governor 考虑：**目标驻留时间（target residency）**和（最坏情况下的）**退出延迟（exit latency）**。目标驻留时间是硬件在该给定状态中必须花费的最短时间，包括进入该状态所需的时间（这可能相当可观），以便比进入某个较浅的空闲状态节省更多能量。[空闲状态的“深度”大致对应于处理器在该状态下消耗的功率。] 退出延迟则是，请求处理器硬件进入空闲状态的 CPU，从该状态唤醒后开始执行第一条指令所需的最大时间。注意，一般而言，退出延迟还必须涵盖进入该给定状态所需的时间，以防唤醒发生在硬件正在进入该状态时，而它必须被完整进入后才能有序地退出。

有两类信息可以影响 governor 的决策。首先，governor 知道距离最近一次定时器事件的时间。这个时间被精确知晓，因为内核对定时器进行编程并确切知道它们何时触发，它也是给定 CPU 所依赖的硬件能够停留在空闲状态中的最长时间，包括进入和退出该状态所需的时间。然而，CPU 可能在任何时候被非定时器事件唤醒（特别是在最近一次定时器触发之前），而且通常不知道这何时会发生。governor 只能在 CPU 被唤醒后看到它实际空闲了多长时间（此后该时间称为*空闲时长 idle duration*），并可以以某种方式将该信息与距离最近定时器的剩余时间一起使用，以估计未来的空闲时长。governor 如何使用该信息取决于它所实现的算法，这也是 `CPUIdle` 子系统中存在多个 governor 的主要原因。

有四种 `CPUIdle` governor 可用：`menu`、`TEO <teo-gov_>`_、`ladder` 和 `haltpoll`。默认使用哪一个取决于内核的配置，特别是取决于调度器 tick 是否可以被`空闲循环停止 <idle-cpus-and-tick_>`_。可用的 governor 可以从 `available_governors` 读取，并且 governor 可以在运行时更改。内核当前使用的 `CPUIdle` governor 的名称可以从 `sysfs` 中 `/sys/devices/system/cpu/cpuidle/` 下的 `current_governor_ro` 或 `current_governor` 文件中读取。

另一方面，使用哪个 `CPUIdle` driver 通常取决于内核运行所在的平台，但也存在拥有多个匹配 driver 的平台。例如，有两个 driver 可以配合大多数 Intel 平台工作，即 `intel_idle` 和 `acpi_idle`，前者内置了空闲状态信息，后者则能从系统的 ACPI 表读取这些信息。即便如此，在这种情况下，系统初始化时选择的 driver 之后也不能被替换，因此关于使用哪一个的决策必须尽早做出（在 Intel 平台上，如果 `intel_idle` 因某种原因被禁用或无法识别该处理器，则将使用 `acpi_idle` driver）。内核当前使用的 `CPUIdle` driver 的名称可以从 `sysfs` 中 `/sys/devices/system/cpu/cpuidle/` 下的 `current_driver` 文件读取。


## 空闲 CPU 与调度器 Tick


调度器 tick 是一个周期性触发的定时器，用于实现 CPU 调度器的时间片共享策略。当然，如果同一时刻有多个可运行任务分配给一个 CPU，要让它们在给定时间帧内取得合理进展，唯一的办法就是让它们共享可用的 CPU 时间。也就是说，粗略地说，每个任务被分到一个 CPU 时间片来运行其代码，受到调度类、优先级等因素的约束，当该时间片用尽时，CPU 应切换到运行另一个任务的（代码）。然而，当前运行的任务可能并不愿意主动交出 CPU，而调度器 tick 正是为了确保这种切换无论如何都会发生。这不是 tick 的唯一作用，但却是使用它的主要原因。

从 CPU 空闲时间管理的角度看，调度器 tick 是个问题，因为它触发频繁且周期较短（取决于内核配置，tick 周期的长度在 1 ms 到 10 ms 之间）。因此，如果允许 tick 在空闲 CPU 上触发，那么请求硬件进入目标驻留时间超过 tick 周期长度的空闲状态就没有意义。此外，在那种情况下任何 CPU 的空闲时长都不会超过 tick 周期长度，而由于空闲 CPU 上 tick 唤醒导致进入和退出空闲状态的能量将被浪费。

幸运的是，并不真正需要允许 tick 在空闲 CPU 上触发，因为（按定义）它们除了特殊的“idle”任务外没有任务可运行。换句话说，从 CPU 调度器的角度看，它们在 CPU 时间上的唯一使用者就是空闲循环。由于空闲 CPU 的时间不必在多个可运行任务之间共享，如果使用给定 CPU 空闲，则使用 tick 的主要原因就消失了。因此，原则上完全可以在空闲 CPU 上停止调度器 tick，尽管这并不总是值得去做。

是否在空闲循环中停止调度器 tick，取决于 governor 的期望。首先，如果在 tick 范围内还有另一个（非 tick）定时器即将触发，那么停止 tick 显然是浪费时间，即便在这种情况下可能不需要对定时器硬件重新编程。其次，如果 governor 期望在 tick 范围内发生一次非定时器唤醒，那么停止 tick 是不必要的，甚至可能是有害的。也就是说，在这种情况下 governor 会选择一个目标驻留时间在距离期望唤醒剩余时间之内的空闲状态，因此该状态将相对较浅。governor 确实无法在那时选择较深的空闲状态，因为那与它自身对即将很快唤醒的预期相矛盾。现在，如果唤醒确实很快发生，停止 tick 将是浪费时间，而且在这种情况下定时器硬件需要被重新编程，这代价高昂。另一方面，如果 tick 被停止而唤醒在很长时间内都没有发生，硬件可能在 governor 所选的较浅空闲状态中无限期地停留，这将浪费能量。因此，如果 governor 期望在 tick 范围内发生任何类型的唤醒，最好允许 tick 触发。然而，否则 governor 将选择一个相对较深的空闲状态，因此应当停止 tick，以免它过早唤醒 CPU。

无论如何，governor 知道它期望什么，是否停止调度器 tick 的决策属于它。不过，如果 tick 已经被停止（在循环的某次先前迭代中），最好保持现状，governor 需要把这一点考虑在内。

内核可以配置为完全禁止在空闲循环中停止调度器 tick。这可以通过其构建时配置（取消设置 `CONFIG_NO_HZ_IDLE` 配置选项）或通过命令行向其传递 `nohz=off` 来完成。在这两种情况下，由于停止调度器 tick 被禁用，空闲循环代码会直接忽略 governor 关于它的决策，tick 永远不会被停止。

运行那些被配置为允许在空闲 CPU 上停止调度器 tick 的内核的系统被称为**无 tick（tickless）**系统，通常认为它们比那些无法停止 tick 的内核运行的系统更具能效。如果给定系统是无 tick 的，它将默认使用 `menu` governor；如果不是无 tick 的，其默认的 `CPUIdle` governor 将是 `ladder`。


## ``menu`` Governor


`menu` governor 是无 tick 系统默认的 `CPUIdle` governor。它相当复杂，但其设计的基本原理很简单。也就是说，当被调用为 CPU 选择一个空闲状态（即 CPU 将请求处理器硬件进入的空闲状态）时，它尝试预测空闲时长，并使用预测值进行空闲状态选择。

它首先使用一个简单的模式识别算法来获得初步的空闲时长预测。也就是说，它保存最近观察到的 8 个空闲时长值，并在下次预测空闲时长时计算它们的平均值和方差。如果方差很小（小于 400 平方毫秒），或者相对于平均值较小（平均值大于标准偏差的 6 倍），则该平均值被视为“典型间隔（typical interval）”值。否则，丢弃所保存的已观察空闲时长值中最长或最短（取决于哪一个离平均值更远）的那个，并对剩余的值重复计算。

再次，如果它们的方差很小（在上述意义上），则取平均值作为“典型间隔”值，依此类推，直到确定“典型间隔”或者忽略了过多数据点为止。在后一种情况下，如果仍在考虑的数据点集合大小足够大，那么下一次空闲时长不太可能高于该集合中仍保留的最大空闲时长值，因此取该值作为预测的下一次空闲时长。最后，如果仍在考虑的数据点集合太小，则不做预测。

如果以这种方式计算出的下一次空闲时长的初步预测足够长，governor 将在假设调度器 tick 将被停止的前提下，取得距离最近一次定时器事件的时间。这个时间在下文中称为**睡眠长度（sleep length）**，它是下一次 CPU 唤醒之前时间的上界。它用于确定睡眠长度范围，而该范围又是获得睡眠长度修正系数所需要的。

`menu` governor 维护一个数组，其中包含若干修正系数值，这些值对应于不同的睡眠长度范围，数组中的范围组织方式是每个范围大约比前一个范围宽 10 倍。

给定睡眠长度范围的修正系数（在为 CPU 选择空闲状态之前确定）在 CPU 被唤醒后更新，并且睡眠长度越接近观察到的空闲时长，修正系数越接近 1（它必须落在 0 到 1 之间，含端点）。睡眠长度乘以它所属范围的修正系数，得到预测空闲时长的近似值，该值与之前确定的“典型间隔”进行比较，取两者中的较小者作为最终的空闲时长预测。

如果“典型间隔”值很小，意味着 CPU 很可能很快被唤醒，则跳过睡眠长度计算，因为那可能代价高昂，并且空闲时长简单地被预测为等于“典型间隔”值。

现在，governor 准备遍历空闲状态列表并选择其中一个。为此，它将每个状态的目标驻留时间与预测的空闲时长进行比较，并将其退出延迟与来自电源管理服务质量（或 `PM QoS <cpu-pm-qos_>`_）框架的延迟限制进行比较。它选择目标驻留时间最接近但仍在预测空闲时长之下的状态，并且其退出延迟不超过该限制。

在最后一步，如果 governor 尚未决定`停止调度器 tick <idle-cpus-and-tick_>`_，它可能仍需要细化空闲状态的选择。这发生在它预测的空闲时长小于 tick 周期且 tick 尚未被停止（在空闲循环的先前迭代中）时。那么，先前计算中使用的睡眠长度可能无法反映距离最近一次定时器事件的真实时间，如果它确实大于那个时间，governor 可能需要选择一个具有合适目标驻留时间的较浅状态。


## 面向定时器事件（TEO）的 Governor


面向定时器事件（TEO）的 governor 是无 tick 系统的一种替代 `CPUIdle` governor。它遵循与 `menu` `相同的基本策略 <menu-gov_>`_：它总是尝试找到适合给定条件的最深空闲状态。然而，它对这个问题采用了不同的方法。

## 空闲状态的表示


出于 CPU 空闲时间管理的目的，处理器支持的所有物理空闲状态都必须表示为一个一维数组，数组元素为 |struct cpuidle_state| 对象，每个对象允许一个独立的（逻辑）CPU 请求处理器硬件进入具有某些属性的空闲状态。如果处理器中存在单元的层级结构，一个 |struct cpuidle_state| 对象可以覆盖不同层级单元所支持的空闲状态的组合。在这种情况下，`它的目标驻留时间和退出延迟参数 <idle-loop_>`_ 必须反映最深层（即包含其他所有单元的单元的空闲状态）空闲状态的属性。

例如，取一个处理器，它在一个更大的称为“module”的单元中有两个核心，并假设一个核心在“core”层级请求硬件进入某个特定的空闲状态（比如“X”），如果另一个核心已经处于空闲状态“X”，将触发该 module 尝试进入它自身特定的空闲状态（比如“MX”）。换句话说，在“core”层级请求空闲状态“X”给硬件一张许可证，使其最深可到达“module”层级的空闲状态“MX”，但这并不保证一定会发生（请求空闲状态“X”的核心可能只是自己进入该状态）。那么，表示空闲状态“X”的 |struct cpuidle_state| 对象的目标驻留时间必须反映在该 module 的空闲状态“MX”中需要花费的最短时间（包括进入该状态所需的时间），因为那是 CPU 需要保持空闲以在进入该状态的情况下节省任何能量的最短时间。类似地，该对象的退出延迟参数必须涵盖该 module 空闲状态“MX”的退出时间（通常也包括其进入时间），因为那是从唤醒信号到 CPU 开始执行第一条新指令之间的最大延迟（假设该 module 中的两个核心在 module 整体恢复运行后始终准备好执行指令）。

然而，有些处理器在其内部单元层级的不同层级之间没有直接的协调。在这些情况下，例如在“core”层级请求空闲状态并不会以任何方式自动影响“module”层级，整个层级的处理由 `CPUIdle` driver 负责。在这种情况下，空闲状态对象的定义完全由 driver 决定，但处理器硬件最终进入的空闲状态的物理属性必须始终遵循 governor 用于空闲状态选择的参数（例如，该空闲状态的实际退出延迟不得超过 governor 所选空闲状态对象的退出延迟参数）。

除了上述目标驻留时间和退出延迟空闲状态参数外，表示空闲状态的对象各自还包含一些描述该空闲状态的其他参数，以及一个指向用于请求硬件进入该状态的函数的指针。此外，对于每个 |struct cpuidle_state| 对象，都有一个对应的 `struct cpuidle_state_usage <cpuidle_state_usage>` 对象，其中包含给定空闲状态的使用统计信息。该信息由内核通过 `sysfs` 暴露。

对于系统中的每个 CPU，在 `sysfs` 中都有一个 `/sys/devices/system/cpu/cpu<N>/cpuidle/` 目录，其中的数字 `<N>` 在初始化时分配给给定 CPU。该目录包含一组名为 `state0`、`state1` 等的子目录，其数量等于为该给定 CPU 定义的空闲状态对象数减一。这些目录中的每一个对应一个空闲状态对象，名称中的数字越大，它所表示的有效空闲状态越深。它们每个都包含若干表示对应空闲状态对象属性的文件（属性），如下：

`above`
	该空闲状态被请求的总次数，但观察到的空闲时长肯定太短，无法匹配其目标
	驻留时间。

`below`
	该空闲状态被请求的总次数，但肯定有更深的空闲状态会更匹配观察到的空闲
	时长。

`desc`
	该空闲状态的描述。

`disable`
	该空闲状态是否被禁用。

`default_status`
	该状态的默认状态，“enabled”或“disabled”。

`latency`
	空闲状态的退出延迟，单位为微秒。

`name`
	空闲状态的名称。

`power`
	硬件在该空闲状态中消耗的功率，单位为毫瓦（若指定，否则为 0）。

`residency`
	空闲状态的目标驻留时间，单位为微秒。

`time`
	给定 CPU 在该空闲状态中花费的总时间（由内核测量），单位为微秒。

`usage`
	给定 CPU 请求硬件进入该空闲状态的总次数。

`rejected`
	在给定 CPU 上进入该空闲状态的请求被拒绝的总次数。

`desc` 和 `name` 文件都包含字符串。它们之间的区别在于，name 期望更简洁，而 description 可能更长，并且可能包含空白或特殊字符。上面列出的其他文件包含整数。

`disable` 属性是唯一可写的属性。如果它包含 1，则该空闲状态对该特定 CPU 被禁用，这意味着 governor 永远不会为该特定 CPU 选择它，而 `CPUIdle` driver 也将永远不会因此请求硬件为其进入该状态。然而，为一个 CPU 禁用一个空闲状态并不能阻止它被其他 CPU 请求，因此必须对所有 CPU 都禁用它，才能使其永不被任何 CPU 请求。[注意，由于 `ladder` governor 的实现方式，禁用一个空闲状态也会阻止该 governor 选择比被禁用状态更深的任何空闲状态。]

如果 `disable` 属性包含 0，则该空闲状态对该特定 CPU 启用，但它仍可能同时被系统中某些或所有其他 CPU 禁用。向它写入 1 会导致该空闲状态对该特定 CPU 被禁用，而向它写入 0 则允许 governor 考虑该给定 CPU 的它，并让 driver 请求它，除非该状态在 driver 中被全局禁用（在这种情况下它完全无法使用）。

`power` 属性定义得并不好，特别是对于表示处理器单元层级不同层级空闲状态组合的空闲状态对象，而且通常很难获取复杂硬件的空闲状态功率数值，因此 `power` 经常包含 0（不可用），如果它包含非零数值，该数值可能不太准确，不应依赖于它做任何有意义的事情。

`time` 文件中的数值通常可能大于给定 CPU 在给定空闲状态中真正花费的总时间，因为它由内核测量，可能无法覆盖硬件拒绝进入该空闲状态而改为进入较浅状态（甚至根本没有进入任何空闲状态）的情况。内核只能测量从请求硬件进入空闲状态到随后 CPU 唤醒之间的时间跨度，而无法说明在此期间硬件层面实际发生了什么。此外，如果所讨论的空闲状态对象表示处理器单元层级不同层级空闲状态的组合，内核永远无法说明硬件在任何特定情况下在层级中下降到了多深。由于这些原因，要找出硬件在其支持的不同空闲状态中花费了多少时间的唯一可靠方法是使用硬件中的空闲状态驻留计数器（如果可用）。

一般而言，在尝试进入空闲状态时收到的中断会导致空闲状态进入请求被拒绝，在这种情况下 `CPUIdle` driver 可能返回一个错误码来指示发生了这种情况。`usage` 和 `rejected` 文件分别报告给定空闲状态被成功进入或被拒绝的次数。


## 针对 CPU 的电源管理服务质量


Linux 内核中的电源管理服务质量（PM QoS）框架允许内核代码和用户空间进程对各种内核能效特性设置约束，以防止性能下降到低于要求的水平。

CPU 空闲时间管理可以通过两种方式受 PM QoS 影响：通过全局 CPU 延迟限制，以及通过针对单个 CPU 的恢复延迟约束。内核代码（例如设备驱动）可以借助 PM QoS 框架提供的特殊内部接口设置这两者。用户空间可以通过打开 `/dev/` 下的 `cpu_dma_latency` 特殊设备文件并向其写入一个二进制值（解释为有符号 32 位整数）来修改前者。相应地，CPU 的恢复延迟约束可以通过向 `sysfs` 中 `/sys/devices/system/cpu/cpu<N>/` 下的 `power/pm_qos_resume_latency_us` 文件写入一个字符串（表示一个有符号 32 位整数）来从用户空间修改，其中 CPU 编号 `<N>` 在系统初始化时分配。两种情况都会拒绝负值，并且在这两种情况下，写入的整数都将被解释为以微秒为单位的所请求的 PM QoS 约束。

然而，所请求的值不会自动作为新约束应用，因为它可能比之前其他人请求的另一个约束限制更少（在本特定情况下即更大）。因此，PM QoS 框架维护一个迄今为止对全局 CPU 延迟限制以及每个单独的 CPU 所发出请求的列表，将它们聚合，并将有效（本特定情况下为最小值）值作为新约束应用。

事实上，打开 `cpu_dma_latency` 特殊设备文件会导致创建一个新的 PM QoS 请求，并将其添加到 CPU 延迟限制请求的全局优先级列表中，“open”操作得到的文件描述符就代表该请求。如果该文件描述符随后用于写入，写入其中的数字将作为新的请求限制值与它所代表的 PM QoS 请求关联。接下来，将使用优先级列表机制来确定整个请求列表的新有效值，该有效值将被设置为新的 CPU 延迟限制。因此，请求一个新的限制值只有在有效“列表”值受到影响时才会改变真实限制，即它是列表中请求值的最小值时。

持有通过打开 `cpu_dma_latency` 特殊设备文件所获得的文件描述符的进程控制与该文件描述符关联的 PM QoS 请求，但它只控制这个特定的 PM QoS 请求。

关闭 `cpu_dma_latency` 特殊设备文件，或者更确切地说，关闭在打开它时获得的文件描述符，会导致与该文件描述符关联的 PM QoS 请求从 CPU 延迟限制请求的全局优先级列表中移除并被销毁。如果发生这种情况，将再次使用优先级列表机制来确定整个列表的新有效值，该值将成为新的限制。

相应地，对于每个 CPU，在 `sysfs` 中 `/sys/devices/system/cpu/cpu<N>/` 下，有一个与 `power/pm_qos_resume_latency_us` 文件关联的恢复延迟 PM QoS 请求，向它写入会导致这个单一的 PM QoS 请求被更新，而不管是哪个用户空间进程这样做的。换句话说，这个 PM QoS 请求由整个用户空间共享，因此需要对与之关联的文件进行仲裁访问，以避免混乱。[可以说，在实践中该机制唯一合法的用途是把一个进程绑定到相关 CPU，并让它使用 `sysfs` 接口来控制它的恢复延迟约束。] 然而，它仍然只是一个请求。它是用于确定每次以这种或那种方式更新请求列表时（该列表中可能有来自内核代码的其他请求）为相关 CPU 设置的恢复延迟约束有效值的优先级列表中的一个条目。

CPU 空闲时间 governor 应将全局（有效）CPU 延迟限制与给定 CPU 的有效恢复延迟约束两者中的最小值，视为它们被允许为该 CPU 选择的空闲状态的退出延迟的上限。它们绝不应选择退出延迟超出该限制的任何空闲状态。

虽然上述 CPU QoS 约束适用于 CPU 空闲时间管理，用户空间也可以通过 `cpu_wakeup_latency` 文件请求 CPU 系统唤醒延迟 QoS 限制。这个 QoS 约束在为 CPU 选择合适空闲状态时被遵守，既在进入系统级挂起到空闲（suspend-to-idle）睡眠状态时，也适用于常规的 CPU 空闲时间管理。

注意，`cpu_wakeup_latency` 文件的管理从用户空间角度看与 `cpu_dma_latency` 文件工作方式一致。此外，单位也是微秒。

## 通过内核命令行控制空闲状态


除了允许为单个 CPU `禁用单个空闲状态的 sysfs 接口 <idle-states-representation_>`_ 外，还有一些内核命令行参数会影响 CPU 空闲时间管理。

`cpuidle.off=1` 内核命令行选项可用于完全禁用 CPU 空闲时间管理。它不会阻止空闲循环在空闲 CPU 上运行，但会阻止调用 CPU 空闲时间 governor 和 driver。如果将其添加到内核命令行，空闲循环将通过 CPU 架构支持代码请求硬件在空闲 CPU 上进入空闲状态，该代码应为此提供默认机制。然而，该默认机制通常是对实现相关架构（即 CPU 指令集）的所有处理器的最小公分母，因此它相当粗糙且能效不高。因此，不建议在生产环境中使用。

`cpuidle.governor=` 内核命令行开关允许指定要使用的 `CPUIdle` governor。它必须追加一个与可用 governor 名称相匹配的字符串（例如 `cpuidle.governor=menu`），该 governor 将取代默认的那个被使用。例如，通过这种方式可以强制在默认使用 `ladder` governor 的系统上使用 `menu` governor。

下面描述的其它控制 CPU 空闲时间管理的内核命令行参数仅与 **x86** 架构相关，对 `intel_idle` 的引用仅影响 Intel 处理器。

**x86** 架构支持代码识别三个与 CPU 空闲时间管理相关的内核命令行选项：`idle=poll`、`idle=halt` 和 `idle=nomwait`。其中前两个完全禁用 `acpi_idle` 和 `intel_idle` driver，这实际上导致整个 `CPUIdle` 子系统被禁用，并使空闲循环调用架构支持代码来处理空闲 CPU。它如何做到这一点取决于向内核命令行添加了这两个参数中的哪一个。在 `idle=halt` 情况下，架构支持代码将使用 CPU 的 `HLT` 指令（通常它会挂起程序的执行，并导致硬件尝试进入最浅的可用空闲状态）来达到此目的；如果使用 `idle=poll`，空闲 CPU 将在一个紧凑循环中执行或多或少“轻量级”的指令序列。[注意，在许多情况下使用 `idle=poll` 有些极端，因为阻止空闲 CPU 节省几乎任何能量可能并非其唯一影响。例如，在 Intel 硬件上，它会有效地阻止 CPU 使用需要 package 中任意数量 CPU 空闲的 P-state（见 |cpufreq|），因此它很可能既损害单线程计算性能，也损害能效。因此，出于性能原因使用它可能根本不是一个好主意。]

`idle=nomwait` 选项阻止使用 CPU 的 `MWAIT` 指令进入空闲状态。使用此选项时，`acpi_idle` driver 将使用 `HLT` 指令代替 `MWAIT`。在运行 Intel 处理器的系统上，此选项会禁用 `intel_idle` driver 并强制改用 `acpi_idle` driver。注意，无论哪种情况，`acpi_idle` driver 只有在它所需的所有信息都存在于系统的 ACPI 表中时才能正常工作。

除了影响 CPU 空闲时间管理的架构级内核命令行选项外，还有一些参数可以影响单个 `CPUIdle` driver，这些参数可以通过内核命令行传递给它们。具体而言，`intel_idle.max_cstate=<n>` 和 `processor.max_cstate=<n>` 参数，其中 `<n>` 是空闲状态索引，也用于 `sysfs` 中给定状态目录的名称（参见`空闲状态的表示 <idle-states-representation_>`_），会导致 `intel_idle` 和 `acpi_idle` driver 分别丢弃所有比空闲状态 `<n>` 更深的空闲状态。在这种情况下，它们将永远不会请求这些空闲状态中的任何一个，也不会把它们暴露给 governor。[对于 `<n>` 等于 `0` 的情况，两个 driver 的行为不同。向内核命令行添加 `intel_idle.max_cstate=0` 会禁用 `intel_idle` driver 并允许使用 `acpi_idle`，而 `processor.max_cstate=0` 等价于 `processor.max_cstate=1`。此外，`acpi_idle` driver 是 `processor` 内核模块的一部分，可以单独加载，`max_cstate=<n>` 可以在加载时作为模块参数传递给它。]
