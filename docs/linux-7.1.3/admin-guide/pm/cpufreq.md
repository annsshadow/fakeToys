## CPU 性能调节的概

现代大多数处理器都能够在多种不同的时钟频率与电压配置下运行，这些配置通常被称工作性能点（Operating Performance Points）或 P-states（在 ACPI 术语中）。通常而言时钟频率越高、电压越高，CPU 在单位时间内能够退休（retire）的指令就越多；但同时，
时钟频率越高、电压越高，CPU 在给P-state 下单位时间内的能耗（或所汲取的功率）越高。因此，CPU 容量（单位时间内可执行的指令数）CPU 所汲取的功率之间存天然的权衡
在某些情况下，希望甚至必须让程序尽可能快地运行，此时没有理由使用除最P-state
（即可用的最高性能频率/电压配置）以外的任何 P-state。然而在另一些情况下，可能并必要如此快速地执行指令，而长时间维持最高的可用 CPU 容量却不充分利用，可能被视为
一种浪费。此外，出于散热或供电能力等原因（或类似原因），在过长时间内维持最CPU
容量在物理上也可能是不可能的。为了涵盖这些情况，存在允许 CPU 在不同频电压配置
之间切换（或ACPI 术语中，被置于不P-state）的硬件接口
通常，这些接口会与估算所需 CPU 容量的算法配合使用，以决定应CPU 置于哪些 P-state当然，由于系统的利用率通常随时间变化，这必须定期重复进行。发生这一活动的机制被称为
CPU 性能调节CPU 频率调节（因为它涉及调整 CPU 时钟频率）

## Linux 中的 CPU 性能调节


Linux 内核通过 `CPUFreq`（CPU 频率调节）子系统支持 CPU 性能调节，该子系统由三层代码
组成：核心（core）、调governor（scaling governors）与调节驱动（scaling drivers）
`CPUFreq` 核心为所有支CPU 性能调节的平台提供公共代码基础设施与用户空间接口。它
定义了其他组件运行于其中的基本框架
调节 governor 实现用于估算所需 CPU 容量的算法。通常，每governor 实现一种（可能参数的）调节算法
调节驱动与硬件对话。它们向调节 governor 提供关于可用 P-state（某些情况下P-state
范围）的信息，并访问平台特定的硬件接口，以按调节 governor 的请求改CPU P-state
原则上，所有可用的调节 governor 都可以与每一个调节驱动配合使用。该设计基于这样一观察：在多数情况下，性能调节算法用于 P-state 选择的信息可以用与平台无关的形式表示因此应当能够使用以完全相同方式实现的同一性能调节算法，而无需关心使用的是哪个调节
驱动。因此，同一组调governor 应当适用于每一个受支持的平台
然而，对于那些基于硬件自身所提供信息（例如通过反馈寄存器）的性能调节算法，上述观可能不成立，因为该信息通常特定于其来源硬件接口，并且可能难以用抽象的、与平台无关方式表示。出于这一原因，`CPUFreq` 允许调节驱动绕过 governor 层并实现它们自己的性能
调节算法。|intel_pstate| 调节驱动就是这样做的

## ``CPUFreq`` 策略对象


在某些情况下，用P-state 控制的硬件接口由多个 CPU 共享。例如，使用同一个寄存器
（或一组寄存器）同时控制多CPU P-state，对其写入会同时影响所有这CPU
共享硬件 P-state 控制接口CPU 集合`CPUFreq` 表示struct cpufreq_policy 对象为了一致性，即便给定集合中只有一CPU，也会使struct cpufreq_policy
`CPUFreq` 核心为系统中的每一CPU（包括当前离线的 CPU）维护一个指struct
cpufreq_policy 对象的指针。如果多CPU 共享同一个硬P-state 控制接口，则对应它们的所有指针都指向同一struct cpufreq_policy 对象
`CPUFreq` 使用 struct cpufreq_policy 作为其基础数据类型，其用户空间接口的设计也基于
策略（policy）这一概念

## CPU 初始

首先，必须注册一个调节驱动，`CPUFreq` 才能工作。同一时刻只能注册一个调节驱动，因此
调节驱动应当能够处理系统中的所CPU
调节驱动可以CPU 注册之前或之后注册。如CPU 较早注册，那么在调节驱动注册期间驱动核心会调`CPUFreq` 核心来记录所有已注册CPU。反过来，如果在调节驱动注册之后
有任CPU 注册，则会在其注册时调用 `CPUFreq` 核心来记录它们
无论如何，只`CPUFreq` 核心准备好处理某个它尚未见过的逻辑 CPU，就会对其进行记录[请注意，逻辑 CPU 可能是物理单核处理器、多核处理器中的一个核，或是物理处理器或处器核中的一个硬件线程。在下文中，除非明确说明CPU" 始终"逻辑 CPU"，"处理
（processor）一词用于指代可能包含多个逻辑 CPU 的物理部件。]

一旦被调用，`CPUFreq` 核心会检查给CPU 的策略指针是否已设置；若是，则跳过策略对的创建。否则，将创建一个新的策略对象并对其进行初始化，其中包括`sysfs` 中创建新策略目录，并将对应于给定 CPU 的策略指针设置为新策略对象在内存中的地址
接下来，使用传入CPU 策略指针作为参数的方式，调用调节驱动`->init()` 回调。该
回调应当初始化给CPU（更准确地说，是其所属、由策略对象表示的、共享硬件接口的那组
CPU）的性能调节硬件接口；并且，如果被调用的策略对象是新的，则设置策略的参数，例硬件支持的最小与最大频率、可用频率表（若所支持P-state 集合不是连续范围），以及
属于同一策略CPU 掩码（包括在线和离线 CPU）。核心随后使用该掩码来填充其中所CPU
的策略指针
新策略对象的下一个主要初始化步骤是为其附加一个调governor（起初是由内核命令行配置决定的默认调governor，但之后可以通过 `sysfs` 更改）。首先，将指向新策略对象指针传递给 governor `->init()` 回调，该回调应当初始化处理给定策略所需的全部数结构，并可能向其中添governor `sysfs` 接口。接下来，通过调用`->start()`
回调来启governor
该回调应当向 CPU 调度器注册属于给定策略的所有在CPU 的每 CPU 利用率更新回调。这利用率更新回调会CPU 调度器在重要事件（如任务入队和出队）、调度器 tick 的每次迭中，或一般每CPU 利用率可能发生变化时（从调度器的角度来看）被调用。它们应当执确定后续给定策略所P-state 所需的计算，并调用调节驱动以按照 P-state 选择对硬件进更改。根据调节驱动与 governor 的配置及能力，调节驱动可能直接从调度器上下文被调用，
或通过内核线程或工作队列异步调用
对于非新但先"inactive"（即属于它们的所CPU 都处于离线状态）的策略对象，也采类似的步骤。该情况下唯一的实质区别在于，`CPUFreq` 核心会尝试使用先前与该策略配合的
、变"inactive"（现被重新初始化）的同一个调governor，而非默认 governor
反过来，如果先前离线CPU 正在重新上线，但共享该策略对象的其他某些 CPU 已经在线则根本无需重新初始化该策略对象。在这种情况下，只需重启调节 governor，使其将新的在线
CPU 考虑在内即可。这是通过对整个策略依次调governor `->stop` `->start()`
回调来实现的
如前所述，|intel_pstate| 调节驱动绕过`CPUFreq` 的调governor 层，并提供其自身P-state 选择算法。因此，如果使用 |intel_pstate|，则不会向新策略对象附加调节 governor相反，会调用驱动`->setpolicy()` 回调，为每个策略注册CPU 利用率更新回调。这回调以与调节 governor 相同的方式由 CPU 调度器调用，但在 |intel_pstate| 的情况下，它从调度器上下文中一次性地既确定要使用P-state，又相应地更改硬件配置
CPU 初始化期间创建的策略对象以及与之关联的其他数据结构，会在调节驱动被注销（例包含它的内核模块被卸载时）或属于给定策略的最后一CPU 被注销时被拆除

## ``sysfs`` 中的策略接口


在内核初始化期间，`CPUFreq` 核心会在 `/sys/devices/system/cpu/` 下创建一个名`cpufreq` `sysfs` 目录（kobject）
该目录为 `CPUFreq` 核心维护的每个策略对象包含一`policyX` 子目录（其中 `X` 代表
一个整数）。每`policyX` 目录都由 `/sys/devices/system/cpu/cpuY/` 下的 `cpufreq`
符号链接所指向（其`Y` 代表一个可能与 `X` 所代表的整数不同的整数），对应于所关联（或属于）给定策略的 CPU。位`/sys/devices/system/cpu/cpufreq` 中的各个 `policyX`
目录各自包含策略特定的属性（文件），用于控制相应策略对象（即所有与之关联的 CPU）的
`CPUFreq` 行为
其中一些属性是通用的。它们由 `CPUFreq` 核心创建，其行为通常不依赖于所使用的具体调驱动，也不依赖于附加到给定策略的具体调节 governor。一些调节驱动还会向 `sysfs` 中的
策略目录添加驱动特定的属性，以控制驱动行为的策略特定方面
`/sys/devices/system/cpu/cpufreq/policyX/` 下的通用属性如下：

`affected_cpus`
	属于此策略的在线 CPU 列表（即共享`policyX` 策略对象表示的硬	性能调节接口）
`bios_limit`
	如果平台固件（BIOS）告OS 应对 CPU 频率施加上限，则该上限将
	通过此属性报告（若存在）
	该限制的存在可能是某些（常常是无意的）BIOS 设置、来自服务处理器
	的限制或其他 BIOS/硬件机制的结果
	这不包括可通过通用散热驱动发现ACPI 散热限制
	如果所用的调节驱动不支持该属性，则它不存在
`cpuinfo_cur_freq`
	此策略所CPU 的当前频率，从硬件获得（单位 KHz）
	这应当是硬件实际运行的频率。若无法确定该频率，则不应存在此属性
`cpuinfo_avg_freq`
	属于给定策略的所CPU 的平均频率（单位 KHz），源自硬件提供的反馈，
	报告的时间窗口跨度最多几毫秒
	这应当基于硬件实际运行的频率，因此可能需要专门的硬件支持（例ARM
	上的 AMU 扩展）。若无法确定，则不应存在此属性
	请注意，对给CPU 获取当前频率的失败尝试将导致相应的错误，例如：对
	保持空闲CPU（在 ARM 上引发）返回 EAGAIN
`cpuinfo_max_freq`
	此策略所CPU 可运行的最大可能工作频率（单位 kHz）
`cpuinfo_min_freq`
	此策略所CPU 可运行的最小可能工作频率（单位 kHz）
`cpuinfo_transition_latency`
	将此策略所CPU 从一P-state 切换到另一P-state 所需的时间，
	单位纳秒
`related_cpus`
	属于此策略的所有（在线与离线）CPU 列表
`scaling_available_frequencies`
	此策略所CPU 的可用频率列表（单位 kHz）
`scaling_available_governors`
	内核中存在的、可被附加到此策略的 `CPUFreq` 调节 governor 列表	或（若正在使|intel_pstate| 调节驱动）由驱动提供、可应用于此策略	调节算法列表
	[请注意，某些 governor 是模块化的，可能需要加载一个内核模块，由该模块
	持有governor 才能变得可用并被此属性列出。]

`scaling_cur_freq`
	此策略所属所CPU 的当前频率（单位 kHz）
	在大多数情况下，这是调节驱动使用其提供的调节接口向硬件请求的最后一	P-state 的频率，它不一定反CPU 实际运行的频率（由于硬件设计及其	限制）
	某些架构（如 `x86`）可能尝试通过此属性提供更精确反映当前 CPU 频率	信息，但这仍可能不是硬件此刻所见的确切当前 CPU 频率。不过，此行为仅
	通过 `CPUFREQ_ARCH_CUR_FREQ` 选项可用
`scaling_driver`
	当前正在使用的调节驱动
`scaling_governor`
	当前附加到此策略的调governor，或（若正在使用 |intel_pstate| 调节
	驱动）当前应用于此策略的、由驱动提供的调节算法
	此属性可读写，向其写入将导致一个新的调governor 被附加到此策略，	由调节驱动提供的一个新调节算法被应用于它（|intel_pstate| 情况下）	具体由写入此属性的字符串指示（该字符串必须是上`scaling_available_governors`
	属性列出的名称之一）
`scaling_max_freq`
	此策略所CPU 被允许运行的最大频率（单位 kHz）
	此属性可读写，向其写入代表整数的字符串将导致设置一个新的上限（它不	低于 `scaling_min_freq` 属性的值）
`scaling_min_freq`
	此策略所CPU 被允许运行的最小频率（单位 kHz）
	此属性可读写，向其写入代表非负整数的字符串将导致设置一个新的下限（	不得高于 `scaling_max_freq` 属性的值）
`scaling_setspeed`
	此属性仅`userspace`_ 调节 governor 被附加到给定策略时才起作用
	它返governor 请求的最后一个频率（单位 kHz），也可被写入以设置策略
	的新频率

## 通用调节 Governors


`CPUFreq` 提供可与所有调节驱动配合使用的通用调节 governor。如前所述，它们各自实现
一种（可能带参数的）性能调节算法
调节 governor 被附加到策略对象，不同的策略对象可以同时由不同的调节 governor 处理
（尽管在某些情况下这可能导致次优结果）
给定策略对象的调governor 可随时通过 `sysfs` 中的 `scaling_governor` 策略属性进更改
某些 governor 会暴`sysfs` 属性以控制或微调它们实现的调节算法。这些被称为 governor
可调参数（tunables）的属性，根据所用调节驱动的不同，可以是全局（系统范围）或每策略的如果驱动要求 governor 可调参数按每策略划分，则它们位于每个策略目录的子目录中。否则，
它们位于 `/sys/devices/system/cpu/cpufreq/` 下的一个子目录中。无论哪种情况，包含
governor 可调参数的子目录名称就是提供它们governor 的名称
### ``performance``


当附加到策略对象时，governor 会导致为该策略请`scaling_max_freq` 策略限制范围的最高频率
该请求在将策略的 governor 设置`performance` 时发出一次，并在此后每当 `scaling_max_freq`
`scaling_min_freq` 策略限制发生变化时发出
### ``powersave``


当附加到策略对象时，governor 会导致为该策略请`scaling_min_freq` 策略限制范围的最低频率
该请求在将策略的 governor 设置`powersave` 时发出一次，并在此后每当 `scaling_max_freq`
`scaling_min_freq` 策略限制发生变化时发出
### ``userspace``


governor 自身不做任何事情。相反，它允许用户空间通过向该策略`scaling_setspeed`
属性写入来设置其附加到的策略的 CPU 频率。尽管意图可能是为策略设置一个精确频率，实际频率可能因硬件协调、散热与功率限制以及其他因素而变化
### ``schedutil``


governor 使用来自 CPU 调度器的 CPU 利用率数据。它通常被视CPU 调度器的一部分因此可以直接访问调度器的内部数据结构
它完全在调度器上下文中运行，尽管在某些情况下，当它决定应改变给定策略CPU 频率时，
可能需要异步调用调节驱动（这取决于驱动是否能够从调度器上下文改CPU 频率）
governor 针对特定 CPU 的动作取决于调用其利用率更新回调的调度类。如果由 RT deadline 调度类调用，governor 会将频率提升至允许的最大值（`scaling_max_freq`
策略限制）。反过来，如果由 CFS 调度类调用，governor 将使用给CPU 根控制组的每实体
负载跟踪（PELT）度量作CPU 利用率估算（有关 PELT 机制的描述，请参**Per-entity
load tracking** LWN.net 文章 [^1^]_）。然后，按照以下公式计算要应用的CPU 频率

	f = 1.25 ** `f_0` ** `util` / `max`

其中 `util` PELT 数值，`max` `util` 的理论最大值，`f_0` 是给定策略的最大可CPU 频率（若 PELT 数值是与频率无关的），否则为当CPU 频率
governor 还采用一种机制，允许它临时为提高最近一直在等待 I/O 的任务提CPU 频率称为 "IO-wait boosting"（IO 等待提升）。这发生在调度器`SCHED_CPUFREQ_IOWAIT` 标志
传递给 governor 回调时，该标志导致频率立即升至允许的最大值，然后随时间回落到上述公式
返回的值
governor 仅暴露一个可调参数：

`rate_limit_us`
	两次连续governor 计算运行之间必须间隔的最短时间（单位微秒	（默认值：调节驱动转换延迟1.5 倍，若驱动未提供延迟值则1ms）
	此可调参数的目的是减governor 的调度器上下文开销，否则该开销可能过大
governor 通常被视为较旧的 `ondemand`_ `conservative`_ governor（如下所述）替代品，因为它更简单且CPU 调度器集成更紧密，其CPU 上下文切换等方面的开销更小并且它使用调度器自身CPU 利用率度量，因此原则上其决策不应与调度器其他部分做出决策相矛盾
### ``ondemand``


governor 使用 CPU 负载作为 CPU 频率选择度量
为了估算当前 CPU 负载，它测量其工作例程连续两次调用之间经过的时间，并计算该时间段给定 CPU 处于非空闲状态的时间占比。非空闲（活跃）时间与CPU 时间的比值被作为负载
估算
如果governor 被附加到由多CPU 共享的策略，则会对它们全部估算负载，并取最大结作为整个策略的负载估算
governor 的工作例程必须在进程上下文中运行，因此它被异步调用（通过工作队列），如有
必要则从那里更新 CPU P-state。因此，来自governor 的调度器上下文开销最小，但它
会导致额外的 CPU 上下文切换相对频繁地发生，且由它触发CPU P-state 更新可能相对
不规律。此外，它通过运行减少 CPU 空闲时间的代码（尽管 CPU 空闲时间的减少非常轻微）
来影响自身的 CPU 负载度量
它通常选择与估算负载成比例CPU 频率，使`cpuinfo_max_freq` 策略属性的值对应于负载
1（即 100%），`cpuinfo_min_freq` 策略属性的值对应于负载 0，除非负载超过（可配置的加速阈值，此时它将直接选用允许使用的最高频率（`scaling_max_freq` 策略限制）
governor 暴露以下可调参数
`sampling_rate`
	这是 governor 工作例程应运行的频率，单位微秒
	通常，它被设置为 2000 ms）量级的值。其默认值是在此 governor 所	加的每个策略上为 `cpuinfo_transition_latency` 增加 50% 的余量	最小值通常是两个调度器 tick 的长度
	如果此可调参数按每策略划分，则以shell 命令将其代表的时间设置为
	转换延迟1.5 ```
	# echo `$(($(cat cpuinfo_transition_latency) * 3 / 2))` > ondemand/sampling_rate

```
`up_threshold`
	如果估算CPU 负载高于此值（单位百分比），governor 会将频率设置	策略允许的最大值。否则，所选频率将与估算的 CPU 负载成比例
`ignore_nice_load`
	如果设置1（默0），将导CPU 负载估算代码把执"nice" 级别
	大于 0 的任务所花费CPU 时间视为 CPU 空闲时间
	如果系统中有在决定以何种频率运行 CPU 时不应被考虑的任务，这可能很有用	此时，只需将这些任务的 "nice" 级别提升0 以上并将此属性设置为 1 即可
`sampling_down_factor`
	临时乘数，介1（默认）100（含）之间，CPU 负载超过 `up_threshold`
	时应用于 `sampling_rate` 值
	这会governor 工作例程的下一次执行（在将频率设置为允许的最大值之后）
	被延迟，从而使频率在更长时间内保持在最大水平
	某些突发（bursty）工作负载中的频率波动可借此避免，代价是为维持最CPU
	容量而消耗额外的能量

	应用governor 原始频率目标（包括在估算 CPU 负载超过 `up_threshold`
	时使用的最大值）的缩减因子，AMD 频率敏感powersave 偏置驱动	灵敏度阈值（`drivers/cpufreq/amd_freq_sensitivity.c`），介于 0 1000
	（含）之间
	如果未加AMD 频率敏感powersave 偏置驱动，则要应用的有效频率由下	给出

		f * (1 - `powersave_bias` / 1000)

	其中 f governor 的原始频率目标。这种情况下该属性的默认值为 0
	如果加载AMD 频率敏感powersave 偏置驱动，则此属性的默认值为 400	并且以不同方式使用

	的性能将如何随频率变化而改变
	敏感性为 0（受内存约束或受 I/O 约束）的工作负载，预计不会因提高 CPU 频率
	而获得任何性能提升；而敏感性为 100%（受 CPU 约束）的工作负载预计在提	CPU 频率时会表现得更好
	如果工作负载敏感性小于由 `powersave_bias` 值表示的阈值，则敏感powersave
	偏置驱动将导governor 选择低于其原始目标的频率，从而避免为那些不会	更高 CPU 频率中受益的工作负载提供过高配置
### ``conservative``


governor 使用 CPU 负载作为 CPU 频率选择度量
它以与上文所`ondemand`_ governor 相同的方式估CPU 负载，但实现CPU 频率选择
算法不同
即，它避免在可能不适合供电能力有限（例如电池供电）系统的短时间区间内显著改变频率为此，它以相对较小的步长一次一步地向上或向下改变频率——取决于估算CPU 负载是否
超过（可配置的）阈值
governor 暴露以下可调参数
`freq_step`
	频率步长，以 governor 允许设置的最大频率（`scaling_max_freq` 策略限制	的百分比表示，介0 100 之间（默5）
	这是允许一次改变的频率量。将其设置为 0 将导致使用默认频率步长（5%），
	而将其设置为 100 实际上会导致 governor `scaling_min_freq` 	`scaling_max_freq` 策略限制之间周期性地切换频率
`down_threshold`
	用于确定频率改变方向的阈值（单位百分比，默认 20）
	如果估算CPU 负载大于此值，频率将上升（`freq_step`）。如果负载小	此值（`sampling_down_factor` 机制未生效），频率将下降。否则，频率
	不会改变
`sampling_down_factor`
	频率降低延迟因子，介1（默认）10（含）之间
	它实际上使频率下降的速度比上升慢 `sampling_down_factor` 倍

## 频率加速（Boost）支

### 背景


某些处理器支持一种机制，可在特定条件下（例如整个芯片未被充分利用且低于其预期的散或功率预算时）临时将多核封装中某些核的工作频率提升（并超过整个封装的可持续频率阈值）
不同厂商使用不同的名称指代此功能。对Intel 处理器，它被称为 "Turbo Boost"；AMD 其为 "Turbo-Core" 或（在技术文档中Core Performance Boost"，依此类推。通常，不厂商的实现方式也不同。为简洁起见，此处使用 "frequency boost"（频率加速）这一简单术来指代所有这些实现
频率加速机制可以是基于硬件的，也可以是基于软件的。如果它是基于硬件的（例如在 x86 上）触发加速的决定由硬件做出（尽管通常它需要将硬件置于能够在一定限制内控制 CPU 频率特殊状态）。如果它是基于软件的（例如在 ARM 上），则由调节驱动决定是否以及何时触加速
### ``sysfs`` 中的 ``boost`` 文件


此文件位`/sys/devices/system/cpu/cpufreq/` 下，用于控制整个系统"boost" 设置如果底层调节驱动不支持频率加速机制（或支持但提供驱动特定的接口来控制它，|intel_pstate|），则它不存在
如果此文件中的值为 1，则频率加速机制被启用。这意味着要么硬件可以被置于能够触发加的状态（在基于硬件的情况下），要么软件被允许触发加速（在基于软件的情况下）。这并不
意味着此刻系统中任CPU 上实际上正在使用加速。它只意味着使用频率加速机制的许可
（该机制仍可能因其他原因而永远不被使用）
如果此文件中的值为 0，则频率加速机制被禁用，完全无法使用
可以写入此文件的唯一值是 0 1
### 加速控制旋钮的合理

频率加速机制通常旨在帮助在低于软件分辨率的时间尺度上（例如在调度tick 间隔以下实现最CPU 性能，并且已证明适用于许多工作负载，但在某些情况下可能导致问题
出于这一原因，许多系统允许在平台固件（BIOS）设置中禁用频率加速机制，但这需要重启系才能调整到所需设置，这至少在某些情况下可能不切实际。例如：

  1. 加速意味着对处理器超频，尽管是在受控条件下。通常，处理器的能耗会因频率与电压
     的提高而增加，即使是暂时的。在切换到有限容量电源（如电池）的系统上，这可能并不
     可取，因此在系统运行时禁用加速机制的能力可能对此有帮助（但这也取决于工作负载）
  2. 在某些情况下，确定性行为比性能或能耗（或两者）更重要，此时在系统运行时禁用加     的能力可能很有用
  3. 为了检查频率加速机制本身的影响，能够在不重启系统的情况下运行有加速和无加速的
     测试是有用的
  4. 可复现的结果在运行基准测试时很重要。由于加速功能依赖于整个封装的负载，单线     性能可能因此而变化，这有时会导致不可复现的结果。这可以通过在运行对此敏感的基准
     测试之前禁用频率加速机制来避免
### 旧式 AMD ``cpb`` 旋钮


AMD powernow-k8 调节驱动支持一个与全局 `boost` 旋钮非常相似`sysfs` 旋钮。它用于
禁用/启用某些 AMD 处理器的 "Core Performance Boost" 特性
如果存在，该旋钮位于 `sysfs` 中每`CPUFreq` 策略目录（`/sys/devices/system/cpu/cpufreq/policyX/`内，名为 `cpb`，这表示一种更细粒度的控制接口。然而，实际实现是在系统范围基础上工作的为一个策略设置该旋钮会导致同时为所有其他策略设置相同的旋钮值
该旋钮在支持其底层硬件特性的 AMD 处理器上仍受支持，但它可能被配置出内核（通过
`CONFIG_X86_ACPI_CPUFREQ_CPB` 配置选项），而全局 `boost` 旋钮则无论如何都存在。因始终可以使用 `boost` 旋钮代替 `cpb` 旋钮，这是强烈推荐的，因为这与所有其他系统的做法
更加一致（并且 `cpb` 旋钮未来可能不再受支持）
即使设置`CONFIG_X86_ACPI_CPUFREQ_CPB` 配置选项，`cpb` 旋钮也绝不会存在于任没有底层硬件特性的处理器（例如所Intel 处理器）上
