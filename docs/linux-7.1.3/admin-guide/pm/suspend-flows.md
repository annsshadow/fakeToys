
## 系统挂起代码流程

:Copyright: |copy| 2020 Intel Corporation

:Author: Rafael J. Wysocki <rafael.j.wysocki@intel.com>

系统至少需要执行一次全局的、系统范围的状态转换，才能从工作状态进入某个受支持[睡眠状<sleep-states>](sleep states <sleep-states>)。为此，休眠（Hibernation）需要发生不止一次转换，但其他通常被称*系统范围挂起**（或简*系统挂起**）的睡眠状态只需要一次
对于那些睡眠状态，将系统从工作状态转换到目标睡眠状态的过程也被称为**系统挂起**（在大多数情况下，这究竟指转换还是指系统的睡眠状态，从上下文中应当可以清楚），而将系统从睡眠状态转换回工作状态的过程被称*系统恢复（system resume*
与挂起和恢复转换相关的内核代码流程对于系统的不同睡眠状态相当相似，suspend-to-idle <s2idle> 代码流程suspend-to-RAM <s2ram> standby <standby> 睡眠状态的代码流程之间存在一些显著差异
suspend-to-RAM <s2ram> standby <standby> 睡眠状态没有平台支持无法实现，它们之间的区别归结为需要由平台驱动提供的挂起和恢复钩子所执行的平台特定操作。除此之外，这些睡眠状态的挂起和恢复代码流程基本完全相同，因此在下文中它们将一起被称为**平台相关挂起（platform-dependent suspend*状态
## Suspend-to-idle 挂起代码流程

为使系统从工作状态转换到 suspend-to-idle <s2idle> 睡眠状态，将依次采取以下步骤：

 1. 调用系统范围的挂起通知器（notifiers）
    内核子系统可以注册回调，在挂起转换即将发生时以及恢复转换完成时调用
    这使它们能够为系统状态的变化做准备，并在回到工作状态后进行清理
 2. 冻结任务
    冻结任务主要是为了避免来自用户空间通过直接暴露给它MMIO 区域I/O 寄存器进行不受控的硬件访问，并防止用户空间在转换的下一步进行期间进入内核（这可能因各种原因而产生问题）
    所有用户空间任务都被拦截，就好像它们收到了一个信号，并被置于不可中断睡眠，直到随后的系统恢复转换结束
    选择在特定原因下在系统挂起期间被冻结的内核线程随后被冻结，但它们不会被拦截。相反，它们应当周期性地检查自己是否需要被冻结，如果需要则将自己置于不可中断睡眠。[不过注意，内核线程可以使用内核空间可用的锁和其他并发控制来与系统挂起和恢复进行同步，这可能比冻结精确得多，因此后者并非内核线程的推荐选项。]

 3. 挂起设备并重新配IRQ
    设备在四个阶段被挂起，称**prepare***suspend***late suspend** **noirq suspend**（关于每个阶段究竟发生什么，请参driverapi_pm_devices）
    每个设备在每个阶段都会被访问，但通常不会超过其中两个阶段进行物理访问
    runtime PM API **late** 挂起阶段对每个设备被禁用，并且高层（“action”）中断处理程序**noirq** 挂起阶段之前被阻止调用
    之后中断仍被处理，但它们仅被确认给中断控制器，而不执行在系统工作状态下会触发的任何设备特定操作（这些操作被推迟到随后的系统恢复转换，如 `下文 <s2idle_resume_>`_ 所述）
    与系统唤醒设备关联的 IRQ 被“武装（armed）”，以便在其中一个发出事件时启动系统的恢复转换
 4. 冻结调度tick 并挂起时间保持（timekeeping）
    当所有设备都已挂起，CPU 进入空闲循环并被置于最深的可用空闲状态。在此过程中，每CPU“冻结”自己的调度tick，使得与tick 关联的定时器事件CPU 被另一个中断源唤醒之前不会发生
    最后一个进入空闲状态的 CPU 同时停止时间保持（这其中包括阻止高分辨率定时器在第一个被唤醒CPU 重启时间保持之前向前触发）。这使得 CPU 能够相对较长时间地停留在深度空闲状态
    从这一点起，CPU 只能被非定时器硬件中断唤醒。如果发生这种情况，它们会回到空闲状态，除非唤醒其中一CPU 的中断来自一个已为系统唤醒武装的 IRQ，在这种情况下，系统恢复转换开始
## Suspend-to-idle 恢复代码流程

为使系统suspend-to-idle <s2idle> 睡眠状态转换到工作状态，将依次采取以下步骤：

 1. 恢复时间保持并解冻调度器 tick
    当其中一CPU 被唤醒（通过非定时器硬件中断）时，它离开在前一个挂起转换的最后一步进入的空闲状态，重启时间保持（除非它已被较早唤醒的另一CPU 重启），并且CPU 上的调度tick 被解冻
    如果唤醒 CPU 的中断是为系统唤醒而武装的，则系统恢复转换开始
 2. 恢复设备并恢IRQ 的工作状态配置
    设备在四个阶段被恢复，称**noirq resume***early resume***resume** **complete**（关于每个阶段究竟发生什么，请参driverapi_pm_devices）
    每个设备在每个阶段都会被访问，但通常不会超过其中两个阶段进行物理访问
    IRQ 的工作状态配置在 **noirq** 恢复阶段之后恢复，并runtime PM API **early** 恢复阶段为每个支持它的设备的驱动重新启用
 3. 解冻任务
    在前一`挂起 <s2idle_suspend_>`_ 转换的步2 中被冻结的任务被“解冻（thawed）”，这意味着它们从当时进入的不可中断睡眠中被唤醒，并且用户空间任务被允许退出内核
 4. 调用系统范围的恢复通知器
    这类似于 `挂起 <s2idle_suspend_>`_ 转换的步1，并且在此时调用同一组回调，但向它们传递不同的“通知类型（notification type）”参数值
## 平台相关挂起代码流程

为使系统从工作状态转换到平台相关挂起状态，将依次采取以下步骤：

 1. 调用系统范围的挂起通知器
    此步骤与上面 `所<s2idle_suspend_>`_ suspend-to-idle 挂起转换的步1 相同
 2. 冻结任务
    此步骤与上面 `所<s2idle_suspend_>`_ suspend-to-idle 挂起转换的步2 相同
 3. 挂起设备并重新配IRQ
    此步骤类似于上面 `所<s2idle_suspend_>`_ suspend-to-idle 挂起转换的步3，但为系统唤醒武IRQ 通常对平台没有任何影响
    有些平台可以在其内部所CPU 都处于足够深的空闲状态且所I/O 设备都已被置于低功耗状态时，进入非常深的低功耗内部状态。在这些平台上，suspend-to-idle 可以非常有效地降低系统功耗
    然而，在其他平台上，底层组件（如中断控制器）需要以平台特定的方式关闭（实现于平台驱动提供的钩子中），以获得相当的功耗降低
    这通常会阻止带内（in-band）硬件中断唤醒系统，而必须通过特殊的平台相关方式来完成。然后，系统唤醒源的配置通常在系统唤醒设备被挂起时开始，并在稍后由平台挂起钩子最终完成
 4. 禁用非启CPU
    在某些平台上，上述挂起钩子必须在系统的单 CPU 配置下运行（特别是，硬件不能被任何与平台挂起钩子并行运行的代码访问，这些钩子可能且经常陷入平台固件以最终完成挂起转换）
    为此，使CPU 离线/在线（CPU hotplug）框架将系统中除一个（启动 CPU）之外的所CPU 离线（通常，被离线CPU 进入深度空闲状态）
    这意味着所有任务都从这CPU 迁移走，并且所IRQ 都被重新路由到唯一仍在线的 CPU
 5. 挂起核心系统组件
    这为核心系统组件准备好（可能）失去电力的后续状态，并挂起时间保持
 6. 平台特定的断电
    这应当从所有系统组件中移除电力，除了内存控制器RAM（为了保留后者的内容）以及某些被指定用于系统唤醒的设备
    在许多情况下，控制权被传递给平台固件，由其根据需要最终完成挂起转换
## 平台相关恢复代码流程

为使系统从平台相关挂起状态转换到工作状态，将依次采取以下步骤：

 1. 平台特定的系统唤醒
    平台被其中一个指定的系统唤醒设备（不必是带内硬件中断）发出的信号唤醒，控制权被交还给内核（在重新获得控制权之前，平台的配置可能需要由平台固件恢复）
 2. 恢复核心系统组件
    恢复核心系统组件的挂起时配置，并恢复时间保持
 3. 重新启用非启CPU
    在前一个挂起转换的步骤 4 中被禁用CPU 重新上线，并恢复其挂起时配置
 4. 恢复设备并恢IRQ 的工作状态配置
    此步骤与上面 `所<s2idle_resume_>`_ suspend-to-idle 挂起转换的步2 相同
 5. 解冻任务
    此步骤与上面 `所<s2idle_resume_>`_ suspend-to-idle 挂起转换的步3 相同
 6. 调用系统范围的恢复通知器
    此步骤与上面 `所<s2idle_resume_>`_ suspend-to-idle 挂起转换的步4 相同
