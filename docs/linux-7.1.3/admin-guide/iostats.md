## I/O 统计字段


内核通过 `/proc/diskstats` 与 `/sys/block/<device>/stat` 暴露磁盘统计信息。这些统计通常由 `sar` 和 `iostat` 等工具访问。

```
   /proc/diskstats:
     259       0 nvme0n1 255999 814 12369153 47919 996852 81 36123024 425995 0 301795 580470 0 0 0 0 60602 106555
     259       1 nvme0n1p1 492 813 17572 96 848 81 108288 210 0 76 307 0 0 0 0 0 0
     259       2 nvme0n1p2 255401 1 12343477 47799 996004 0 36014736 425784 0 344336 473584 0 0 0 0 0 0

   /sys/block/nvme0n1/stat:
     255999 814 12369153 47919 996858 81 36123056 426009 0 301809 580491 0 0 0 0 60605 106562

   /sys/block/nvme0n1/nvme0n1p1/stat:
     492 813 17572 96 848 81 108288 210 0 76 307 0 0 0 0 0 0
```
两个文件都包含相同的 17 个统计。 `/sys/block/<device>/stat` 包含 `<device>` 的字段。在 `/proc/diskstats` 中，字段前面带有主设备号和次设备号以及设备名。在上面的例子中，`nvme0n1` 的第一个统计值在这两个文件中都是 255999。

sysfs 的 `stat` 文件对于监控一个小的、已知的磁盘集合很高效。如果你在跟踪大量设备，`/proc/diskstats` 通常是更好的选择，因为它避免了为每个快照打开和关闭多个文件的开销。

所有字段都是累积的、单调的计数器，除了字段 9，它在 I/O 完成时重置为零。其余字段在启动、设备重新连接或重新初始化时，或者在底层计数器溢出时重置。读取这些计数器的应用程序应在比较统计快照时检测并处理重置。

每组统计仅适用于所指明的设备；如果你想要系统范围的统计，你必须找到所有设备并将它们全部相加。

字段 1 -- 已完成的读取次数（unsigned long）
    这是成功完成的读取总数。

字段 2 -- 合并的读取次数，字段 6 -- 合并的写入次数（unsigned long）
    彼此相邻的读取和写入可能会被合并以提高效率。因此两个 4K 读取在最终交给磁盘之前可能成为一个 8K 读取，因此它会被计数（并排队）为仅一个 I/O。此字段让你知道这种情况发生的频率。

字段 3 -- 已读取的扇区数（unsigned long）
    这是成功读取的扇区总数。

字段 4 -- 读取所花费的毫秒数（unsigned int）
    这是所有读取所花费的总毫秒数（从 blk_mq_alloc_request() 到 __blk_mq_end_request() 测量）。

字段 5 -- 已完成的写入次数（unsigned long）
    这是成功完成的写入总数。

字段 6 -- 合并的写入次数（unsigned long）
    参见字段 2 的描述。

字段 7 -- 已写入的扇区数（unsigned long）
    这是成功写入的扇区总数。

字段 8 -- 写入所花费的毫秒数（unsigned int）
    这是所有写入所花费的总毫秒数（从 blk_mq_alloc_request() 到 __blk_mq_end_request() 测量）。

字段 9 -- 当前进行中的 I/O 数（unsigned int）
    唯一应归零的字段。当请求被交给相应的 struct request_queue 时递增，完成时递减。

字段 10 -- 进行 I/O 所花费的毫秒数（unsigned int）
    只要字段 9 非零，此字段就增加。

    自 5.0 起，此字段在至少有一个请求被启动或完成时计数 jiffies。如果请求运行超过 2 个 jiffies，那么在并发请求的情况下，某些 I/O 时间可能未被计入。

字段 11 -- 进行 I/O 所花费的加权毫秒数（unsigned int）
    此字段在每个 I/O 启动、I/O 完成、I/O 合并，或读取这些统计时，按进行中的 I/O 数（字段 9）乘以自上次更新此字段以来进行 I/O 所花费的毫秒数递增。这可以方便地衡量 I/O 完成时间以及可能正在累积的积压。

字段 12 -- 已完成的丢弃（discard）次数（unsigned long）
    这是成功完成的丢弃总数。

字段 13 -- 合并的丢弃次数（unsigned long）
    参见字段 2 的描述。

字段 14 -- 已丢弃的扇区数（unsigned long）
    这是成功丢弃的扇区总数。

字段 15 -- 丢弃所花费的毫秒数（unsigned int）
    这是所有丢弃所花费的总毫秒数（从 blk_mq_alloc_request() 到 __blk_mq_end_request() 测量）。

字段 16 -- 已完成的 flush 请求数
    这是成功完成的 flush 请求总数。

    块层会合并 flush 请求，并且一次最多执行一个。这统计由磁盘执行的 flush 请求。分区不跟踪。

字段 17 -- 刷新所花费的毫秒数
    这是所有 flush 请求所花费的总毫秒数。

为了避免引入性能瓶颈，在修改这些计数器时不持有任何锁。这意味着当更改发生冲突时可能会引入微小的误差，因此（例如）将每个分区发出的所有读 I/O 相加应该等于对磁盘发出的那些……但由于缺乏锁，它可能只是非常接近。

在 2.6+ 中，有每个 CPU 的计数器，这使得缺乏锁几乎不成问题。读取统计时，会将每 CPU 计数器求和（可能会溢出它们被求和到的 unsigned long 变量）并将结果给用户。没有方便的用户接口来直接访问每 CPU 计数器本身。

自 4.19 起，请求时间以纳秒精度测量，并在显示在此接口中之前截断为毫秒。

### 磁盘与分区


在 2.4 与 2.6+ 之间的 I/O 子系统有显著变化。结果，一些统计信息消失了。从相对于分区的磁盘地址到相对于主机磁盘的磁盘地址的翻译发生得更早。所有合并和计时现在都发生在磁盘级别，而不是像 2.4 那样同时发生在磁盘和分区级别。因此，在 2.6+ 上，你将看到分区与磁盘不同的统计输出。在 2.6+ 机器上，分区只有**四**个可用字段。这反映在上述例子中。

字段 1 -- 发出的读取次数
    这是发出到此分区的总读取数。

字段 2 -- 读取的扇区数
    这是请求从此分区读取的扇区总数。

字段 3 -- 发出的写入次数
    这是发出到此分区的总写入数。

字段 4 -- 写入的扇区数
    这是请求写入此分区的扇区总数。

注意，由于地址被翻译为相对于磁盘的地址，并且不保留相对于分区的地址记录，因此读取的后续成功或失败不能归因于分区。换句话说，分区的读取次数在排队之前稍微计数，而整个磁盘的读取次数在完成时计数。这是一个微妙的区别，在大多数情况下可能无关紧要。

更重要的是由在合并之前计数分区的读/写次数、而在合并之后计数磁盘的读/写次数所引起的误差。由于典型工作负载通常包含大量连续且相邻的请求，发出的读/写次数可能是完成的读/写次数的数倍。

在 2.6.25 中，完整的统计集再次可用于分区，并且磁盘和分区统计再次一致。由于我们仍然不保留相对于分区的地址记录，操作被归因于在最终合并后包含请求第一个扇区的分区。由于请求可以跨分区合并，这可能导致一些（可能无关紧要的）不准确。

### 附加说明


在 2.6+ 中，sysfs 默认不挂载。如果你的 Linux 发行版尚未添加它，这是你将想添加到

```
	none /sys sysfs defaults 0 0
```
的一行。

在 2.6+ 中，所有磁盘统计都已从 `/proc/stat` 中移除。在 2.4 中，它们同时出现在 `/proc/partitions` 与 `/proc/stat` 中，尽管 `/proc/stat` 中的格式与 `/proc/partitions` 中的格式非常不同（参见 proc(5)，如果你的系统有它）。
