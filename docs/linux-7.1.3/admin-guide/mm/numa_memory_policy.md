## NUMA 内存策略


## 什么是 NUMA 内存策略


Linux 内核中，“内存策略（memory policy）”决定了NUMA 系统或模拟的 NUMA 系统中，内核将从哪个节点分配内存。Linux 2.4. 起就支持具有非一致内存访问（NUMA）架构的平台。当前的内存策略支持是在 2004 5 月左右加Linux 2.6 的。本文档试图描述 2.6 内存策略支持的概念与 API

内存策略不应cpusets（`Documentation/admin-guide/cgroup-v1/cpusets.rst`）混淆，后者是一种管理机制，用于限制一组进程可以从哪些节点分配内存。内存策略是 NUMA 感知应用程序可以利用的编程接口。当 cpuset 和策略同时作用于一个任务时，cpuset 的限制优先。更多细节参见下文“内存策略与 cpusets<mem_pol_and_cpusets>

## 内存策略概念


### 内存策略的作用范


Linux 内核支持多_级作用范围_的内存策略，按从最通用到最具体的顺序描述如下：

System Default Policy（系统默认策略）
	该策略被“硬编码”进内核。它管理所有不被下述更具体策略作用范围所控制的页面分配。当系统“启动并运行”后，系统默认策略将使用下文描述的“本地分配（local allocation）”。但在启动过程中，系统默认策略会被设置为在所有具有“足够”内存的节点间交错分配，以免启动节点被启动期分配压垮

Task/Process Policy（任进程策略
	这是一个可选的、每任务的策略。当为某个特定任务定义后，该策略控制由该任务或代表该任务进行、且不被更具体作用范围控制的所有页面分配。如果一个任务没有定义任务策略，那么本应由任务策略控制的所有页面分配会“回退”到系统默认策略

	任务策略作用于任务的整个地址空间。因此，它是可继承的，并且确实会fork()（不CLONE_VM 标志clone()）和 exec*() 继承。这使得父任务可以为从一个对内存策略毫无感知的可执行映像 exec() 出来的子任务建立任务策略。有关任务可用于设置/更改其任进程策略的系统调用概述，参见下文的“内存策API<memory_policy_apis> 一节

	在多线程任务中，任务策略仅适用于安装该策略的线程（Linux 内核任务）以及该线程随后创建的任何线程。在安装新任务策略时已经存在的任何兄弟线程会保留其当前策略

	任务策略仅适用于策略安装之后分配的页面。任务更改其任务策略时已经缺页调入的任何页面，仍留在它们基于分配时的策略所分配的位置

VMA Policy（VMA 策略
	“VMA”或“虚拟内存区域（Virtual Memory Area）”指的是任务虚拟地址空间的一个范围。任务可以为其虚拟地址空间的某个范围定义特定策略。有关用于设VMA 策略mbind() 系统调用概述，参见下文的“内存策API<memory_policy_apis> 一节

	VMA 策略管理用于支撑该地址空间区域的页面分配。任务地址空间中任何没有显VMA 策略的区域，会回退到任务策略，而任务策略本身可能进一步回退到系统默认策略

	VMA 策略有一些复杂细节：

 - VMA 策略仅适用于匿名页。这些包括为匿名段（如任务栈和堆）分配的页面，以及用 MAP_ANONYMOUS 标志 mmap() 的地址空间任何区域。如VMA 策略应用于文件映射，且映射使用了 MAP_SHARED 标志，则该策略会被忽略。如果文件映射使用了 MAP_PRIVATE 标志，则 VMA 策略只会在尝试写入该映射而分配匿名页时——即在写时复制（Copy-On-Write）时——才会被应用

 - VMA 策略在共享同一虚拟地址空间的所有任务（即线程）之间共享，与策略安装的时间无关；并且它们fork() 继承。然而，由于 VMA 策略引用的是任务地址空间的特定区域，而地址空间exec*() 时会被丢弃并重建，VMA 策略不能exec() 继承。因此，只有 NUMA 感知的应用程序才能使VMA 策略

 - 任务可以在先mmap() 的区域的子范围上安装新的 VMA 策略。发生这种情况时，Linux 会把现有的虚拟内存区域拆分为 2 3 VMA，每个都有自己的策略

 - 默认情况下，VMA 策略仅适用于策略安装之后分配的页面。任何已经缺页调VMA 范围的页面仍留在它们基于分配时的策略所分配的位置。不过，2.6.16 起，Linux 通过 mbind() 系统调用支持页面迁移，从而可以将页面内容移动到与 newly 安装的策略相匹配的位置

Shared Policy（共享策略）
	从概念上讲，共享策略适用于被共享映射到一个或多个任务各自不同地址空间中的“内存对象”。应用程序安装共享策略的方式VMA 策略相同——使mbind() 系统调用，指定映射该共享对象的虚拟地址范围。然而，与可以视为任务地址空间某范围属性的 VMA 策略不同，共享策略直接作用于共享对象。因此，所有连接到该对象的任务共享该策略，并且任何任务为该共享对象分配的所有页面都会遵从共享策略

	截至 2.6.22，只有由 shmget() mmap(MAP_ANONYMOUS|MAP_SHARED) 创建的共享内存段支持共享策略。当 Linux 加入共享策略支持时，相关的数据结构被添加到了 hugetlbfs shmem 段中。当hugetlbfs 不支持缺页时分配（即惰性分配），因hugetlbfs shmem 段从未被“接入”共享策略支持。尽hugetlbfs 段现在支持惰性分配，但其共享策略支持尚未完成

	如上文“VMA 策略<vma_policy> 一节所述，对于MAP_SHARED 映射的普通文件，其页缓存页面的分配会忽略安装在由该共享文件映射支撑的虚拟地址范围上的任何 VMA 策略。相反，共享的页缓存页面（包括尚未被任务写入的私有映射所支撑的页面）遵循任务策略（若有），否则遵循系统默认策略

	共享策略基础设施支持在共享对象的子范围上使用不同策略。不过，Linux 仍会为安装了策略的每个不同策略范围拆分安装策略的任务VMA。因此，连接到同一共享内存段的不同任务可以有不同的 VMA 配置来映射那一个共享对象。当某个任务在该区域的一个或多个范围上安装了共享策略时，通过检查共享该共享内存区域的任务的 /proc/<pid>/numa_maps 就可以看到这一点

### 内存策略的组


一NUMA 内存策略由一个“模式（mode）”、可选的模式标志以及一个可选的节点集合组成。模式决定策略的行为，可选的模式标志决定该模式的行为，可选的节点集合可被视为策略行为的参数

在内部，内存策略由一个引用计数的结构struct mempolicy 实现。该结构体的细节将在下文的相应上下文中，在需要解释行为时加以讨论

NUMA 内存策略支持以下 4 种行为模式：

Default Mode鈥斺€擬POL_DEFAULT
	该模式仅用于内存策略 API。在内部，MPOL_DEFAULT 在所有策略作用范围中都被转换NULL 内存策略。指MPOL_DEFAULT 时，任何现有的非默认策略都会被直接移除。因此，MPOL_DEFAULT 意味着“回退到下一个更具体的策略作用范围”

	例如，NULL 或默认的任务策略会回退到系统默认策略；NULL 或默认的 vma 策略会回退到任务策略

	在内存策API 中指定时，Default 模式不使用可选的节点集合

	为该策略指定的节点集合非空是一个错误

MPOL_BIND
	该模式指定内存必须来自策略指定的节点集合。内存将从集合中具有足够空闲内存、且距离分配发生所在节点最近的那个节点分配

MPOL_PREFERRED
	该模式指定应尝试从策略中指定的单个节点分配。如果该分配失败，内核将按照平台固件提供的信息，以距首选节点距离递增的顺序搜索其他节点

	在内部，Preferred 策略使用一个单节点——struct mempolicy preferred_node 成员。当内部模式标志 MPOL_F_LOCAL 被设置时，preferred_node 被忽略，该策略被解释为本地分配。“本地”分配策略可被视为从发生分配CPU 所在节点开始的 Preferred 策略

	用户可以通过传入一个空nodemask 来指定总是优先本地分配。如果传入空nodemask，则该策略不能使用下文描述的 MPOL_F_STATIC_NODES MPOL_F_RELATIVE_NODES 标志

MPOL_INTERLEAVE
	该模式指定页面分配应以页为粒度，在策略指定的节点间交错进行。根据使用上下文的不同，该模式的行为也略有差异：

	对于匿名页和共享内存页的分配，Interleave 模式使用缺页地址在包含该地址的段 [VMA] 中的页偏移，对策略指定的节点集合取模，来索引该集合。然后它尝试从所选节点开始分配一个页面，就像该节点被 Preferred 策略指定、或被本地分配选中一样。也就是说，分配将遵循每节点zonelist

	对于页缓存页面的分配，Interleave 模式使用每任务维护的一个节点计数器来索引策略指定的节点集合。当该计数器达到指定的最高节点后会回绕到最低的指定节点。这将倾向于依据页面被分配的顺序，而非依据任何页偏移，把页面分散到策略指定的节点上
	地址范围或文件。在系统启动过程中，临时的交错系统默认策略以这种模式工作

MPOL_PREFERRED_MANY
	该模式指定分配应优先由策略中指定nodemask 满足。如nodemask 中的所有节点都出现内存压力，分配可以回退到所有现有的 numa 节点。这实际上是允许使用掩码而非单个节点MPOL_PREFERRED

MPOL_WEIGHTED_INTERLEAVE
	该模式与 MPOL_INTERLEAVE 的运作方式相同，只是交错行为基于
	/sys/kernel/mm/mempolicy/weighted_interleave/ 中设置的权重执行

	加权交错依据权重在各节点上分配页面。例如，如果节点 [0,1] 的权重为 [5,2]，则每在节点 1 上分2 个页面，就会在节0 上分5 个页面

NUMA 内存策略支持以下可选模式标志：

MPOL_F_STATIC_NODES
	该标志指定，如果在内存策略定义之后任务或 VMA 的允许节点集合发生变化，用户传入nodemask 不应被重新映射

	如果没有该标志，每当由于允许节点集合变化而导致某mempolicy 被重新绑定时，preferred nodemask（Preferred Many）、preferred node（Preferred）或 nodemask（Bind、Interleave）都会被重新映射到新的允许节点集合。这可能导致使用到先前不期望的节点

	有了该标志，如果用户指定的节点与任务 cpuset 允许的节点重叠，则内存策略应用于它们的交集。如果两组节点不重叠，则使用 Default 策略

	例如，考虑一个附加到 mems 1-3 cpuset、并在同一集合上设Interleave 策略的任务。如cpuset mems 变为 3-5，Interleave 现在会在节点 3 上进行。但有了该标志，由于用户 nodemask 中只允许节点 3，因此“交错”只在该节点上进行。如果用nodemask 中现已没有任何节点被允许，则使用 Default 行为

	MPOL_F_STATIC_NODES 不能MPOL_F_RELATIVE_NODES 标志组合。它也不能用于通过nodemask（本地分配）创建MPOL_PREFERRED 策略

MPOL_F_RELATIVE_NODES
	该标志指定用户传入的 nodemask 将相对于任务VMA 的允许节点集合进行映射。内核保存用户传入的 nodemask，如果允许节点发生变化，则原nodemask 会相对于新的允许节点集合重新映射

	如果没有该标志（也没MPOL_F_STATIC_NODES），每当由于允许节点集合变化而导致某mempolicy 被重新绑定时，node（Preferred）或 nodemask（Bind、Interleave）会被重新映射到新的允许节点集合。该重新映射在连续重新绑定时，可能无法保持用户传入的 nodemask 相对于其允许节点集合的相对性质：nodemask 1,3,5 可能被重新映射为 7-9，然后在允许节点集合恢复到原始状态时又被重新映射1-3

	有了该标志，重新映射的完成方式是：用户传nodemask 中的节点号相对于允许节点集合。换句话说，如果在用户的 nodemask 中设置了节点 0，则策略将在允许节点集合中的第一个（以及Bind Interleave 情形中的第三和第五个）节点上生效。用户传入的 nodemask 表示相对于任务或 VMA 允许节点集合的节点

	如果用户nodemask 包含了超出新允许节点集合范围的节点（例如，当允许节点集合只有 0-3 时，用户 nodemask 中设置了节点 5），则重新映射会回绕nodemask 的开头，并在尚未设置时，将节点设置到 mempolicy nodemask 中

	例如，考虑一个附加到 mems 2-5 cpuset、并MPOL_F_RELATIVE_NODES 在同一集合上设Interleave 策略的任务。如cpuset mems 变为 3-7，交错现在在节点 3-7 上进行。如cpuset mems 随后变为 0,2-3,5，则交错在节0,2-3,5 上进行

	得益于一致的重新映射，使用此标志来准nodemask 以指定内存策略的应用程序，应当忽略其当前cpuset 实际施加的内存放置，而把 nodemask 准备得就像它们始终位于内存节0 N-1 上一样，其中 N 是该策略打算管理的存储节点数量。然后让内核重新映射到任cpuset 允许的存储节点集合，因为这个集合可能随时间变化

	MPOL_F_RELATIVE_NODES 不能MPOL_F_STATIC_NODES 标志组合。它也不能用于通过nodemask（本地分配）创建MPOL_PREFERRED 策略

## 内存策略引用计数


为了解决使用/释放竞争，struct mempolicy 包含一个原子引用计数字段。内部接mpol_get()/mpol_put() 分别递增和递减该引用计数。mpol_put() 只在引用计数归零时才把该结构体释放回 mempolicy kmem 缓存

当分配一个新的内存策略时，其引用计数被初始化为”，表示安装该新策略的任务所持有的引用。当指向某个内存策略结构体的指针被存入另一个结构体时，会添加另一个引用，因为任务的引用会在策略安装完成时丢弃

在运行期对策略的“使用”过程中，我们尽量最小化引用计数上的原子操作，因为这会导致缓存行cpu NUMA 节点之间来回反弹。“使用”在这里指以下之一
1) 查询策略，既可以由任务自身完[使用下文讨论get_mempolicy() API]，也可以由另一个任务通过 /proc/<pid>/numa_maps 接口完成

2) 检查策略以确定策略模式以及相关的节点或节点列表（若有），用于页面分配。这被视为“热路径”。注意，对于 MPOL_BIND，“使用”会跨越整个分配过程，而该过程可能在页面回收期间睡眠，因为 BIND 策略nodemask 通过引用被用来过滤不合格的节点

我们可以通过以下方式，避免在上述使用场景中额外获取引用：

1) 我们永远不需要对系统默认策略执行 get/free，因为一旦系统启动并运行，它既不会被更改也不会被释放

2) 对于查询策略，我们不需要对目标任务的任务策略或 vma 策略额外获取引用，因为在查询期间我们总是以读模式获取任务mm mmap_lock。set_mempolicy() mbind() API [见下文] 在安装或替换任务vma 策略时，总是以写模式获取 mmap_lock。因此，当一个任务或线程正在查询某个策略时，不可能有另一个任务或线程释放它

3) 任务vma 策略的页面分配使用发生在缺页路径中，在那里我们以读模式持mmap_lock。同样，因为替换任务vma 策略要求以写模式持有 mmap_lock，所以当我们正在把它用于页面分配时，该策略不可能在我们脚下被释放

4) 共享策略需要特别考虑。一个任务可以替换一个共享内存策略，而另一个拥有不mmap_lock 的任务正在基于该策略查询或分配页面。为了解决这个潜在竞争，共享策略基础设施在查找共享策略时会持有一把自旋锁，并为共享策略添加一个额外引用。这要求我们在“使用”完该策略后丢弃这个额外引用。我们必须在与非共享策略相同的查分配路径上丢弃共享策略的额外引用。因此，共享策略被如此标记，而额外引用被“有条件地”丢弃——即只对共享策略

   由于这份额外引用计数，也因为我们必须在自旋锁下于树结构中查找共享策略，共享策略在页面分配路径中使用起来开销更大。对于由运行在不NUMA 节点上的任务共享的共享内存区域的共享策略来说尤其如此。这种额外开销可以通过对共享内存区域总是回退到任务或系统默认策略，或者通过把整个共享内存区域预缺页调入内存并锁定来避免。然而，这对所有应用程序可能都不合适

## 内存策略 API


Linux 支持 4 个用于控制内存策略的系统调用。这API 总是只影响调用任务、调用任务的地址空间，或映射到调用任务地址空间中的某个共享对象

   定义这些 API 以及用户空间应用程序参数数据类型的头文件，位于一个不属于 Linux 内核的软件包中。带有“sys\_”前缀的内核系统调用接口定义在 <linux/syscalls.h> 中；模式和标志的定义定义<linux/mempolicy.h> 中

```

	long set_mempolicy(int mode, const unsigned long *nmask,
					unsigned long maxnode);

```
将调用任务的“任进程内存策略”设置为'mode' 参数指定的模式，以及'nmask' 定义的节点集合nmask' 指向一个节id 的位掩码，其中至少包'maxnode' id。可以通过'mode' 参数与标志组合（例如：MPOL_INTERLEAVE | MPOL_F_STATIC_NODES）来传入可选的模式标志

有关更多细节，请参阅 set_mempolicy(2) 手册页

```

	long get_mempolicy(int *mode,
			   const unsigned long *nmask, unsigned long maxnode,
			   void *addr, int flags);

```
根据 'flags' 参数，查询调用任务的“任进程内存策略”，或某个指定虚拟地址的策略或位置

有关更多细节，请参阅 get_mempolicy(2) 手册页

```

	long mbind(void *start, unsigned long len, int mode,
		   const unsigned long *nmask, unsigned long maxnode,
		   unsigned flags);

```
mbind() (mode, nmask, maxnodes) 指定的策略作VMA 策略，安装到'start' 'len' 参数调用的任务地址空间范围上。可以通过 'flags' 参数请求额外的操作

有关更多细节，请参阅 mbind(2) 手册页

```

	long sys_set_mempolicy_home_node(unsigned long start, unsigned long len,
					 unsigned long home_node,
					 unsigned long flags);

```
sys_set_mempolicy_home_node 为任务地址范围中存在的 VMA 策略设置主节点（home node）。该系统调用只更新现mempolicy 范围的主节点，其他地址范围被忽略。主节点是页面分配来源最接近的那NUMA 节点。指定主节点会覆盖默认分配策略，使内存分配到正在执行 CPU 的本地节点附近

## 内存策略cpusets
内存策略cpusets 内部的工作方式如上所述。对于需要单个节点或一组节点的内存策略，节点被限制cpuset 约束所允许的、拥有内存的那些节点。如果为策略指定nodemask 包含cpuset 不允许的节点，且未使MPOL_F_RELATIVE_NODES，则使用为策略指定的节点集合与拥有内存的节点集合的交集。如果结果为空集，则该策略被视为无效，无法安装。如果使用了 MPOL_F_RELATIVE_NODES，则策略的节点会像前面描述的那样被映射并折叠进任务允许的节点集合

当两cpuset 中的任务共享对某个内存区域的访问（例如通过 shmget() 或带MAP_ANONYMOUS MAP_SHARED 标志mmap() 创建的共享内存段），且其中任何任务在该区域上安装了共享策略时，内存策略与 cpusets 的交互可能会成问题——只有两cpuset 都允许其内存的节点才能用于策略。获取这一信息需要“跳出”内存策API 去使cpuset 信息，并且要求知道其他任务可能会把哪cpuset 连接到该共享区域。此外，如果 cpuset 允许的存储集合互不相交，那么“本地”分配是唯一有效的策略
