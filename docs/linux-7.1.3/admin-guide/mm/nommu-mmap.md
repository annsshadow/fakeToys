## MMU 内存映射支持

内核no-MMU 条件下对内存映射的支持有限，例如用于 uClinux 环境。从用户空间的角度看，内存映射与 mmap() 系统调用、shmat() 调用以及 execve() 系统调用结合使用。从内核的角度看，execve() 映射实际上由 binfmt 驱动执行，这些驱动回调到 mmap() 例程以完成实际工作
内存映射行为还涉fork()、vfork()、clone() ptrace() 的工作方式。在 uClinux 下没fork()，clone() 必须提供 CLONE_VM 标志
MMU no-MMU 情况下的行为相似，但不完全相同；并且在后者情况下受到更多限制
 (#) 匿名映射，MAP_PRIVATE

	MMU 情况下：由任意页支持VM 区域；在 fork 时写时复制（copy-on-write）
	no-MMU 情况下：由任意连续页段支持的 VM 区域
 (#) 匿名映射，MAP_SHARED

	它们的行为非常类似于私有映射，只是在 MMU 情况下它们在 fork() clone()（不CLONE_VM）之间共享。由no-MMU 情况不支持这些，那里的行为与 MAP_PRIVATE 相同
 (#) 文件，MAP_PRIVATE，PROT_READ / PROT_EXECPROT_WRITE

	MMU 情况下：由从文件读取的页支持VM 区域；对底层文件的更改会反映到映射中；在 fork 时复制
	no-MMU 情况下：

         - 如果存在一个，内核将复用对同一个文件同一段已有的映射，前提是具有兼容的权限，即使这是由另一个进程创建的
         - 如果可能，当后备设备具有 NOMMU_MAP_DIRECT 能力以及适当的映射保护能力时，文件映射将直接位于后备设备上。Ramfs、romfs、cramfs mtd 都可能允许这样做
  - 如果后备设备不能或不愿意允许直接共享           但具NOMMU_MAP_COPY 能力，那么文件相应部分的副本将被读入一段连续的内存，并EOF 之外的任何多余空间将被清零
  - 对文件的写入不影响映射；对映射的写入在其他进程中可见（无 MMU 保护），但不应发生
 (#) 文件，MAP_PRIVATE，PROT_READ / PROT_EXEC，PROT_WRITE

	MMU 情况下：类似于非 PROT_WRITE 的情况，不同之处在于在实际写入之前相关页会被复制。从那一刻起，对该页底下文件的写入不再反映到映射的后备页中。该页随后由 swap 支持
	no-MMU 情况下：工作方式与不PROT_WRITE 的情况很相似，不同之处在于总会进行复制且从不共享
 (#) 常规文件 / 块设备，MAP_SHARED，PROT_READ / PROT_EXEC / PROT_WRITE

	MMU 情况下：由从文件读取的页支持VM 区域；对页的更改写回文件；对文件的写入反映到支持映射的页中；fork 间共享
	no-MMU 情况下：不支持
 (#) 内存后备的常规文件，MAP_SHARED，PROT_READ / PROT_EXEC / PROT_WRITE

	MMU 情况下：与普通的常规文件相同
	no-MMU 情况下：提供内存后备文件的文件系统（例如 ramfs tmpfs）可以选择通过提供一段连续的页来映射，从而响应一open、truncate、mmap 序列。在这种情况下，共享可写的内存映射将是可能的。它将像 MMU 情况一样工作。如果文件系统不提供任何此类支持，则映射请求将被拒绝
 (#) 内存后备的块设备，MAP_SHARED，PROT_READ / PROT_EXEC / PROT_WRITE

	MMU 情况下：与普通的常规文件相同
	no-MMU 情况下：与内存后备的常规文件相同，但块设备必须能够在未调truncate 的情况下提供一段连续的页。如ramdisk 驱动预先将所有内存分配为一个连续数组，它可以做到这一点
 (#) 内存后备的字符设备，MAP_SHARED，PROT_READ / PROT_EXEC / PROT_WRITE

	MMU 情况下：与普通的常规文件相同
	no-MMU 情况下：字符设备驱动可以选择通过提供对底层设备的直接访问来响mmap()，如果它提供可被直接访问的内存或准内存。这样的例子有帧缓冲区和闪存设备。如果驱动不提供任何此类支持，则映射请求将被拒绝

## 关于 no-MMU MMAP 的进一步说
 (#) 对文件私有映射的请求可能返回一个未按页对齐的缓冲区。这是因为可能发XIP（Execute-In-Place，就地执行），而数据在后备存储中可能未按页对齐
 (#) 对匿名映射的请求将始终按页对齐。如果可能，请求的大小应2 的幂，否则由于内核必须分2 的幂大小的粒度，部分空间可能会被浪费，但只有在适当配置时才会丢弃多余部分，因为这会影响碎片
 (#) 匿名映射请求所分配的内存通常会在返回前由内核清零，这符合 Linux man 手册页（2.22 版或更新）
     MMU 情况下，这可以合理地高性能地实现，因为区域由虚拟页支持，其内容仅在对该特定页发生写入时才映射到已清零的物理页（在此之前，这些页被有效地映射到全局零页，可从中进行读取）。这分摊了初始化页内容所需的时间——取决于映射的写入使用情况
     然而，no-MMU 情况下，匿名映射由物理页支持，并且整个映射在分配时被清零。这可能在用户空malloc() 期间导致显著延迟，因C 库会进行匿名映射，然后内核对整个映射执行 memset
     然而，对于不需要预清零的内存——例malloc() 返回的内存——mmap() 可以接受 MAP_UNINITIALIZED 标志，以向内核表明它不应在返回前费心清零内存。注意，必须启用 `CONFIG_MMAP_ALLOW_UNINITIALIZED` 才能允许这样做，否则该标志将被忽略
     uClibc 使用这一点来加malloc()，ELF-FDPIC binfmt 使用这一点来分配 brk 和栈区域
 (#) no-MMU 模式下，系统上所有私有副本映射和匿名映射的列表可通过 /proc/maps 查看
 (#) no-MMU 模式下，进程使用的所有映射的列表可通过 /proc/<pid>/maps 查看
 (#) 提供 MAP_FIXED 或请求特定的映射地址将导致错误
 (#) 私有映射的文件通常必须提供由驱动或文件系统提供read 方法，以便在 mmap() 选择不直接映射后备设备时，内容可以被读入所分配的内存。如果没有，将导致错误。这最有可能在字符设备文件、管道、FIFO 和套接字中遇到

## 进程间共享内
NOMMU 模式下，SYSV IPC SHM 共享内存POSIX 共享内存都受支持。前者通过通常的机制，后者通过ramfs tmpfs 挂载点上创建的文件

## Futexes

如果架构支持，NOMMU 模式支持 futexes。如果传递给 futex 系统调用的地址位于进程所做的映射之外，或者该地址所在的映射不支futexes（例I/O 字符设备映射），则会给出错误

## No-MMU mremap

mremap() 函数部分受支持。如果指定了 MREMAP_MAYMOVE，并且映射的新大小超过了映射所引用的内存当前所占用slab 对象的大小，或者可以使用更小的 slab 对象，它可能会改变映射的大小，并可能移动它
MREMAP_FIXED 不受支持，尽管如果没有地址变化且对象不需要移动，它会被忽略
共享映射可能不会被移动。可共享映射也可能不会被移动，即使它们当前并未被共享
mremap() 函数必须精确匹配先前映射对象的基址和大小。它不能用于在现有映射中创建空洞、移动现有映射的部分或调整映射部分的大小。它必须作用于一个完整的映射


## 提供可共享的字符设备支持

为了提供可共享的字符设备支持，驱动必须提file->f_op->get_unmapped_area() 操作。mmap() 例程将调用它来获取建议的映射地址。如果它不希望响应映射（因为太长、偏移奇怪、在某些不受支持的标志组合下等），它可以返回错误
驱动还应提供后备设备信息，并设置能力以指示此类设备上允许的映射类型。默认假定为可读可写、不可执行，并且只能直接共享（不能被复制）
file->f_op->mmap() 操作将被调用以实际建立映射。它可以在此点被拒绝。如果指定了 NOMMU_MAP_COPY，返ENOSYS 错误将导致改为复制映射
当字符设备上的最后一个映射被移除时，将调vm_ops->close() 例程。如果可能，现有的映射将被共享（部分或全部），而不通知驱动
file->f_op->get_unmapped_area() 操作也可以返-ENOSYS。这将被理解为该操作只是不想处理它，尽管它确实有一个操作。例如，它可能尝试将调用导向一个二级驱动，结果发现该驱动并未实现它。帧缓冲驱动就是这样的情况，它尝试将调用导向特定于设备的驱动。在这种情况下，如果未指NOMMU_MAP_COPY，映射请求将被拒绝，否则将映射一个副本

	某些类型的设备在某些模式下可能对观察它们的人呈现不同的外观。闪存芯片可能就是这样；例如，如果它们处于编程或擦除模式，你可能会在映射中看到状态而非数据
	在这种情况下，必须小心，以免用户空间在驱动正忙于控制设备时看到显示出此类信息的共享或私有映射。尤其要记住：在某些情况下的私有可执行映射仍可能直接从设备映射！


## 提供可共享的内存后备文件支持

在内存后备文件上提供共享映射，类似于为共享映射的字符设备提供支持。主要区别在于，提供服务的文件系统可能会分配一组连续的页，并允许在其上创建映射
建议，对上述文件应用一个增大文件大小的 truncate 操作（如果该文件为空），应被视为一个请求，即收集足够的页以满足映射。这是支POSIX 共享内存所必需的
内存后备设备由映射的后备设备信息设置memory_backed 标志来指示

## 提供可共享的块设备支
在块设备文件上提供共享映射与字符设备完全相同。如果底层没有真实设备，那么驱动应该分配足够的连续内存以满足任何受支持的映射

## 调整页裁剪行
NOMMU mmap 在执行分配时会自动向上取整到最近的 2 的幂个页。这可能对内存碎片产生不利影响，因此将其设为可配置。默认行为是激进地裁剪分配，并将任何多余的页丢弃回页分配器。为了对碎片保持更细粒度的控制，这种行为可以被完全禁用，或者提高到更高的页 watermark（裁剪开始的阈值）
页裁剪行为可通过 sysctl `vm.nr_trim_pages` 配置
