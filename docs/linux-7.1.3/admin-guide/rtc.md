## Linux 的实时时钟（RTC）驱动


当 Linux 开发者谈论"实时时钟"时，他们通常指的是跟踪墙钟时间并由电池供电的时钟，这样即使在系统断电时它也能工作。除非与 MS-Windows 双启动，这类时钟通常不会跟踪本地时区或夏令时，而是被设置为协调世界时（UTC，前称"格林尼治标准时间"）。

最新的非 PC 硬件往往只计数秒数，就像 time(2) 系统调用所报告的那样；但 RTC 也非常普遍地用公历和 24 小时制表示时间，正如 gmtime(3) 所报告的那样。

Linux 有两个基本兼容的用户空间 RTC API 系列，你可能需要了解：

    - /dev/rtc ... 是由 PC 兼容系统提供的 RTC，因此对非 x86 系统的可移植性不太好。

    - /dev/rtc0、/dev/rtc1 ... 是一个框架的一部分，该框架被各种系统上的大量 RTC 芯片所支持。

程序员需要理解，PC/AT 的功能并不总是可用，而且某些系统能做更多事情。也就是说，RTC 在两个 RTC 框架中使用相同的 API 来发出请求（文件名当然不同），但硬件可能并不提供相同的功能。例如，并非每个 RTC 都连接了 IRQ，因此它们不能全部发出闹钟；标准 PC RTC 只能发出未来最多 24 小时内的闹钟，而其他硬件也许能在接下来的一个世纪内的任意时刻安排闹钟。


### 旧的 PC/AT 兼容驱动：/dev/rtc


所有 PC（甚至 Alpha 机器）都内置了一个实时时钟。通常它们被集成进计算机的芯片组，但有些主板上可能实际有一颗 Motorola MC146818（或兼容芯片）。这就是在计算机断电时保持日期和时间走时的时钟。

ACPI 已将 MC146818 的功能标准化，并以几种方式对其进行了扩展（支持更长的闹钟周期，以及从休眠唤醒）。该功能在旧驱动中并未暴露。

但它也可以用来产生从缓慢的 2Hz 到相对较快的 8192Hz 的信号，以 2 的幂为步进递增。这些信号由中断号 8 报告。（哦！原来 IRQ 8 是用来做这个的……）它还可以作为 24 小时闹钟工作，在闹钟触发时引发 IRQ 8。闹钟也可以被编程为只检查三个可编程值中的任意子集，这意味着例如可以设置为在每个小时的 30 分 30 秒响铃。该时钟还可以被设置为在每次时钟更新时产生一个中断，从而产生一个 1Hz 的信号。

这些中断通过 /dev/rtc（主设备号 10，次设备号 135，只读字符设备）以 unsigned long 的形式报告。低字节包含所引发中断的类型（更新完成、闹钟响铃或周期性），其余字节包含自上次读取以来的中断次数。如果启用了 /proc 文件系统，状态信息通过伪文件 /proc/driver/rtc 报告。该驱动内置了锁定机制，因此同一时刻只允许一个进程打开 /dev/rtc 接口。

用户进程可以通过对 /dev/rtc 执行 read(2) 或 select(2) 来监视这些中断——两者都会阻塞/停止用户进程，直到接收到下一个中断。这对于需要较高频率数据采集、又不想通过轮询 gettimeofday 等方式耗尽 100% CPU 的场合很有用。

在高频或高负载下，用户进程应检查自上次读取以来接收到的中断次数，以确定是否存在所谓的"积压"。仅作参考，一台典型的 486-33 在 /dev/rtc 上运行紧凑的读取循环时，对于高于 1024Hz 的频率，会开始出现偶然的中断积压（即自上次读取以来有 > 1 个 IRQ 事件）。因此你确实应该检查所读取值的高字节，尤其是在高于常规定时器中断（100Hz）的频率上。

编程和/或启用高于 64Hz 的中断频率仅允许 root 用户进行。这或许有点保守，但我们不希望恶意用户在缓慢的 386sx-16 上产生大量 IRQ，从而可能对性能产生负面影响。这个 64Hz 限制可以通过向 /proc/sys/dev/rtc/max-user-freq 写入不同的值来改变。注意中断处理程序只有几行代码，以尽量降低产生这种影响的可能性。

另外，如果内核时间与外部源同步，内核会每 11 分钟将时间写回 CMOS 时钟。在此过程中，内核会短暂关闭 RTC 周期性中断，因此如果你在做严肃的工作要留意这一点。如果你不与外部源（通过 ntp 或其他方式）同步内核时间，那么内核将不会碰 RTC，从而允许你独占访问该设备供你的应用程序使用。

闹钟和/或中断频率通过 ./include/linux/rtc.h 中列出的各种 ioctl(2) 调用来编程进 RTC。与其写 50 页来描述 ioctl() 等等，不如包含一个演示如何使用它们以及展示驱动特性的小程序，这样或许更有用。对于有意编写将使用该驱动的应用程序的人来说，这可能更有用。参见本文档末尾的代码。

### 新的可移植"RTC Class"驱动：/dev/rtcN


因为 Linux 支持许多非 ACPI、非 PC 的平台，其中一些拥有多于一种 RTC 风格时钟，所以它需要一个比"在每个系统上都有一颗电池备份的 MC146818 兼容芯片"更具可移植性的解决方案。相应地，一个新的"RTC Class"框架已被定义。它提供三种不同的用户空间接口：

    - /dev/rtcN ... 与旧的 /dev/rtc 接口大致相同

    - /sys/class/rtc/rtcN ... sysfs 属性支持对某些 RTC 属性进行只读访问。

    - /proc/driver/rtc ... 系统时钟 RTC 可以通过 procfs 接口暴露自身。如果系统时钟没有 RTC，则默认使用 rtc0。这里显示的信息（目前）比通过 sysfs 显示的更多。

RTC Class 框架支持种类繁多的 RTC，从集成到可嵌入式片上系统（SoC）处理器中的 RTC，到使用 I2C、SPI 或其他总线与主机 CPU 通信的离散芯片。甚至还有对 PC 风格 RTC 的支持……包括较新 PC 通过 ACPI 暴露的特性。

新框架还取消了"每系统一个 RTC"的限制。例如，低功耗电池备份的 RTC 可能是一颗离散的 I2C 芯片，而高功能 RTC 则集成在 SoC 中。该系统可能从离散 RTC 读取系统时钟，但出于其功能更强的原因，将所有其他任务都使用集成的 RTC。

有关 ioctl 接口的使用示例，请查看 tools/testing/selftests/rtc/rtctest.c。
