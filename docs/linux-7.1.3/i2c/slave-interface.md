## Linux I2C 从设备（slave）接口

作者：Wolfram Sang <wsa@sang-engineering.com> 2014-15

Linux I2C 从设备接口允许 I2C 控制器以支持从设备（slave）功能的方式工作。为此，总线（bus）驱动需要提供从设备支持，同时还要有一个与硬件无关的软件后端（backend）来提供实际功能。后者的一个例子是 slave-eeprom 驱动，它作为一个双功能内存驱动：I2C 主设备（master）像访问普通 EEPROM 那样访问它，而 Linux 侧的从设备访问则通过 sysfs 处理所需数据。后端驱动与 I2C 总线驱动之间通过事件（event）进行通信。

下图以数据流的方式直观地展示了数据传输过程，虚线标记了一个示例，后端也可能……

```
              e.g. sysfs        I2C slave events        I/O registers
  +-----------+   v    +---------+     v     +--------+  v  +------------+
  | Userspace +........+ Backend +-----------+ Driver +-----+ Controller |
  +-----------+        +---------+           +--------+     +------------+
                                                                | |
  ----------------------------------------------------------------+--  I2C
  --------------------------------------------------------------+----  Bus
```

说明：从技术上讲，I2C 核心对后端驱动是透明的。不过在撰写本文时，这一层尚未完全透明。

## 用户手册

I2C 从设备后端的行为与普通 I2C 客户端（client）类似。它们的实例化方式与文档 instantiating-设备.rst 中描述的方式相同。不同之处在于，I2C 从设备后端拥有自己的地址空间：即在所请求的地址上加上 0x1000。例如，要在用户空间实例化一个地址为 7 位地址 0x64 的 slave-eeprom 驱动：

```
  # echo slave-24c02 0x1064 > /sys/bus/i2c/devices/i2c-1/new_device
```

后端的具体行为与配置在各自独立的文档中描述。

## 开发者手册

首先介绍总线驱动如何借助事件与后端通信，详见下文。随后给出扩展总线驱动以及编写后端的若干要点。

### I2C 从设备事件

```
	ret = i2c_slave_event(client, event, &val)
```

'client' 描述 I2C 从设备。'event' 是下文描述的一种特殊事件类型。'val' 保存一个 u8 数值，即被读取或写入的数据字节，因此是双向的。即使该事件不使用 'val'，指向 val 的指针也总是会被提供，因此请勿传入 NULL。'ret' 是后端返回的返回值。以下事件由总线驱动触发，并由后端驱动检查。

事件类型：

- I2C_SLAVE_WRITE_REQUESTED（必需）

  'val'：未使用

  'ret'：若后端已就绪则返回 0，否则返回相应 errno

  主设备想要向我们写入数据。一旦检测到写入了自身地址（附带写标志），就会发送该事件。此时数据尚未到达，因此无需处理、直接返回即可。返回后，总线驱动始终会对地址阶段（address phase）进行 ACK。若 'ret' 为 0，后端完成初始化与唤醒，准备接收后续数据；若 'ret' 为 errno，总线驱动会对传入字节进行 NACK，直到下一个停止（stop）条件以强制重试传输。

- I2C_SLAVE_READ_REQUESTED（必需）

  'val'：后端返回将要发送的第一个字节

  'ret'：始终为 0

  主设备想要从我们这里读取数据。一旦检测到写入了自身地址（附带读标志），就会发送该事件。返回后，总线驱动会发送第一个字节。

- I2C_SLAVE_WRITE_RECEIVED（必需）

  'val'：总线驱动交付接收到的字节

  'ret'：0 表示字节被 ACK，errno 表示字节被 NACK

  主设备向我们发送了字节，需要设置 'val'。若 'ret' 为 0，总线驱动对该字节进行 ACK；若 'ret' 为 errno，该字节被 NACK。

- I2C_SLAVE_READ_PROCESSED（必需）

  'val'：后端返回将要发送的下一个字节

  'ret'：始终为 0

  总线驱动请求向主设备发送下一个字节，由 'val' 提供。重要的是：这意味着前一个字节已被 ACK，即前一个字节已经移出总线！为确保传输无缝，大多数硬件会在前一个字节仍在移出时请求下一个字节。若主设备发送 NACK，它会停止读取当前正在移出的字节，所请求的字节将永不会被使用，因此很可能需要（取决于后端）在下一次 I2C_SLAVE_READ_REQUEST 时再次发送。

- I2C_SLAVE_STOP（必需）

  'val'：未使用

  'ret'：始终为 0

  收到停止条件。该事件可能在任何时刻发生，后端应重置其状态机，以便能够接收新的 I2C 传输请求。

### 软件后端

若要编写软件后端：

- 使用标准的 i2c_driver 匹配机制
- 编写 slave_callback 来处理从设备事件（最好使用状态机）
- 用 i2c_slave_register() 注册回调

可参考 i2c-slave-eeprom 驱动作为示例。

### 总线驱动支持

若要为总线驱动添加从设备支持：

- 实现用于注册 / 注销从设备的调用，并将其加入 i2c_algorithm 结构体。注册时，可能还需要设置 I2C 从设备地址并启用从设备专用中断。若使用运行时电源管理（runtime PM），通常需要在设备可能随时需要检测从设备地址时，使用 pm_runtime_get_sync() 保持设备上电。注销时则执行相反操作。
- 捕获从设备中断，并向后端发送相应的 i2c_slave_event。

说明：大多数硬件同时支持主设备和从设备功能。因此，在扩展总线驱动时，请确保其同时支持两者。在几乎所有情况下，从设备支持都需要禁用主设备功能。

可参考 i2c-rcar 驱动作为示例。

### ACK/NACK

良好的行为是始终对地址阶段进行 ACK，这样主设备就知道设备基本存在，而不是神秘地消失。使用 NACK 表示“忙碌”状态会带来麻烦。SMBus 要求始终对地址阶段进行 ACK，而 I2C 规范则较为宽松。大多数 I2C 控制器在检测到从设备地址时会自动进行 ACK，并提供禁用 NACK 的选项。出于这些原因，API 支持在地址阶段进行 NACK。

目前，从设备事件仅报告主设备对向我们读取的字节所做的 ACK/NACK。将来这可能成为可选事件，但仅在确有需要时才会添加。不过，主设备期望发送 STOP 事件的情况极为罕见。请记住，I2C 控制器也有可能报告该事件。

### 缓冲区

在开发该 API 时，曾提出是否使用缓冲区而非仅使用字节的问题。这种扩展或许可行，但其用处目前尚不明确。若使用缓冲区，需注意以下几点：

- 缓冲区是可选的——后端驱动必须始终支持基于字节的事务，因为绝大多数硬件都按字节工作，以此作为最终回退方式。
- 对于模拟硬件寄存器的后端，缓冲区帮助不大，因为写入字节会立即触发动作。对于读取，若数据保存在缓冲区中，可能在后端刚通过内部处理更新了寄存器后就变为陈旧数据。
- 主设备发送 STOP 时，部分传输的缓冲区意味着需要额外的代码来处理这种异常，而这类代码往往容易出错。
