## 关于 Linux 软件挂起的目标与实现的文


作者：Gábor Kuti
最后修订：2003-10-20，由 Pavel Machek

### 理念与要达成的目


如今，在许多笔记本上带一个挂起按钮已是常见之事。它把机器状态保存到文件系统或某个分区，并切换到待机模式。之后唤醒机器时，所保存的状态被加载RAM，机器可以继续工作。这有两个实实在在的好处。首先，我们省下了机器关机与之后启动所花的时间，在靠电池运行时能耗着实很高。另一个好处是我们不必打断我们的程序，所以那些长时间做计算进程的应当无需被写成可中断的

swsusp 把机器状态保存到活动的交换区，然后重启或断电。你必须`resume=` 内核选项显式指定用于唤醒的交换分区。如果找到签名，它就加载并恢复所保存的状态。如果指定了 `noresume` 启动参数，它会跳过恢复。如果指定了 `hibernate=nocompress` 启动参数，它会不压缩地保存休眠镜像

与此同时，在系统挂起期间，你不应添加/移除任何硬件、写入文件系统等

## 睡眠状态概


你可以使用三种不同的接口proc/acpi 应当这样工作

```

  echo 1 > /proc/acpi/sleep       # standby
  echo 2 > /proc/acpi/sleep       # suspend to ram
  echo 3 > /proc/acpi/sleep       # suspend to ram，但更省
  echo 4 > /proc/acpi/sleep       # suspend to disk
  echo 5 > /proc/acpi/sleep       # 对系统不友好的关

```
```

  echo 4b > /proc/acpi/sleep      # 经由 s4bios suspend to disk

```

Q:
  也许我漏掉了什么，但为什么常规的 I/O 路径不工作？

A:
  我们确实使用了常规的 I/O 路径。然而我们在加载数据时无法把它恢复到原来的位置。那会制造一个不一致的内核状态，必然导致 oops。相反，我们把镜像加载到未使用的内存，然后原子地把它复制回原位置。这当然意味着镜像大小上限为内存总量的一半

  对此有两种解决方案：

  - 要求挂起期间有一半内存空闲。那样你可以数据读到空闲位置，然cli 并复

  - 假设我们有一个只使用 0-640KB 之间内存的特轮询"ide 驱动。那样，我得确保在挂起期0-640KB 是空闲的，除此之外它就能工作…

  suspend2 有着这个相同的根本限制，但它不把用户数据和磁盘缓存计已用内存"，而是预先把它们保存起来。这意味着在实践中该限制消失了

Q:
  这个 'Encrypt suspend image'（加密挂起镜像）是做什么用的？

A:
  首先：它不能替代 dm-crypt 加密交换。它无法在你的计算机挂起时保护它。相反，它确实能防止在从挂起唤醒之后敏感数据泄露

  想想下面这个情形：你在一个应用程序运行时挂起，该程序在内存中保存着敏感数据。应用程序本身阻止这些数据被换出。然而挂起必须把这些数据写入交换区才能稍后恢复。如果挂起不做加密，你的敏感数据就以明文形式存在磁盘上。这意味着在唤醒之后，你的敏感数据可被所有能直接访问用于挂起的交换设备的应用程序获取。如果你唤醒后不再需要交换，这些数据实际上可以永远留在磁盘上。因此可能出现这样的情况：几周后你的系统被攻破，而你以为已加密并受保护的敏感数据被从交换设备取走偷走。为防止这种情况，你应使'Encrypt suspend image'

  在挂起期间会创建一个临时密钥，并用它来加密写入磁盘的数据。在唤醒期间，当数据被读回内存后，临时密钥被销毁，这简单地意味着挂起期间写入磁盘的所有数据随之不可访问，因而稍后无法被偷走。之后你唯一要留意的是，在正常启动期间尽早对用于挂起的交换分区调'mkswap'。这确保来自一次出错挂起或一次失中止的唤醒的任何临时密钥都从交换设备被抹除

  作为经验法则，用加密交换来保护系统在关机或挂起时的数据。另外再用加密的挂起镜像来防止敏感数据在唤醒后被偷走

Q:
  我如何让挂起输出更详细？

A:
  如果你想在虚拟终端上看到内核在挂起期间切换到的任何非错误内核消息，你必须把内核控制台日志级别设为至少 4（KERN_WARNING），例如通过
```

	# 保存旧的日志级别
	read LOGLEVEL DUMMY < /proc/sys/kernel/printk
	# 设置日志级别以便我们看到进度条
	# 如果级别高于所需，我们就不去动它
	if [ $LOGLEVEL -lt 5 ]; then
	        echo 5 > /proc/sys/kernel/printk
		fi

        IMG_SZ=0
        read IMG_SZ < /sys/power/image_size
        echo -n disk > /sys/power/state
        RET=$?
        #
        # 这里的逻辑是：
        # 如果 image_size > 0（没有内核支持时 IMG_SZ 为零），
        # 则把 image_size 设为零再试一次
	if [ $RET -ne 0 -a $IMG_SZ -ne 0 ]; then # 用最小镜像大小再试一
                echo 0 > /sys/power/image_size
                echo -n disk > /sys/power/state
                RET=$?
        fi

	# 恢复先前的日志级
	echo $LOGLEVEL > /proc/sys/kernel/printk
	exit $RET

```
Q:
  如果我在一USB 设备上挂载了文件系统，然后挂起到磁盘，除非该文件系统是以 "sync" 挂载，否则我会丢数据，这真是这样吗？

A:
  没错……如果你断开那个设备，就可能丢数据。事实上，即便用 "-o sync"，如果你的程序在缓冲区里有尚未写出的信息，或者你在设备完成保存你所写数据之前就断开，你也会丢数据

  软件挂起通常会关USB 控制器，这等同于断开你系统上所USB 设备

  你的系统很可能支持其 USB 控制器在系统睡眠时使用低功耗模式，保持连接，使用像 "suspend-to-RAM" "standby" 这样的真正睡眠模式。（不要/sys/power/state 文件"disk"；写 "standby" "mem"。）我们还没见过任何能在软件挂起下使用这些模式的硬件，尽管理论上某些系统可能支持不会断开 USB 连接"platform" 模式

  记住，拔掉带有已挂载文件系统的磁盘驱动器永远是个坏主意。即便你的系统处于睡眠中也是如此！最安全的做法是在挂起之前卸载所有可移动介质（如 USB、Firewire、CompactFlash、MMC、外SATA，甚IDE 热插拔托架）上的文件系统；然后在唤醒后再挂载它们

  针对此问题有一个变通办法。更多信息见 Documentation/driver-api/usb/persist.rst
