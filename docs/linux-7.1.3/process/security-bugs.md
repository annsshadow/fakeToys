
## 安全漏洞


Linux 内核开发者非常重视安全性。因此，我们希望在发现安全漏洞时能够得知，以便尽快修复并披露
### 准备你的报告


与任何漏洞报告一样，安全漏洞报告需要开发者做大量分析工作，因此你能就问题分享的信息越多越好。如果你不清楚哪些信息有帮助，请查阅 Documentation/admin-guide/reporting-issues.rst 中概述的流程。以下信息在**任何**安全漏洞报告中都是绝对必要的
  - **受影响的內核版本范围**：如果没有版本说明，你的报告将不会被处理。很大一部分报告所针对的漏洞其实已经修复，因此极其重要的是在较新版本（开发树或最新的稳定版）上验证漏洞，至少应确认自发现该漏洞的版本以来相关代码没有变化
  - **问题描述**：需要对该问题进行详细描述，并附上展示其表现形式的跟踪信息，以及你认为观察到的行为属于内核中问题的原因
  - **复现方法**：开发者需要能够复现该问题，才会认为修复是有效的。这包括触发问题的方式以及确认其发生的方式。需要一个依赖关系简单的复现方法（源代码、shell 脚本、操作序列、文件系统映像等）。不接受仅有二进制文件的可执行程序。可用的漏洞利用程序非常有帮助，在未获得报告者同意前不会被公开，除非它们已经公开。依定义，如果一个问题无法复现，那它就不可被利用，因此也就不是安全漏洞
  - **触发条件**：如果漏洞依赖于某些配置选项、`sysctl`、权限、时序、代码修改等，应予以说明
此外，以下信息非常值得提供
  - **可疑的漏洞位*：疑似存在漏洞的文件名和函数非常重要，至少有助于将报告转给合适的维护者。在无法提供时（例如“每次运行此命令系统都会冻结”），安全团队会帮助定位漏洞来源
  - **建议的修复方*：在源代码中分析过漏洞成因的报告者几乎总能准确知道如何修复，因为他们花了很长时间研究它及其影响。提出一个经过测试的修复方案能为维护者节省大量时间，即便最终修复方案并非正确，因为它有助于理解漏洞。提出经过测试的修复方案时，请始终以可直接合并的方式排版（参Documentation/process/submitting-patches.rst）。如果被接受，这将节省一些来回沟通，并且你将为发现并修复此问题获得署名。请注意，在这种情况下只需一`Signed-off-by:` 标签，当报告者与作者为同一人时无需 `Reported-by:`
  - **缓解措施**：在漏洞分析过程中，往往会出现一些缓解该问题的方法。分享它们很有用，因为它们有助于在用户应用修复方案的这段时间内保护最终用户
### 什么才算安全漏

重要的是，大多数漏洞应公开处理，以便让尽可能广泛的受众参与并找到最佳解决方案。从本质上看，在小范围参与者之间以封闭讨论方式处理的漏洞，不太可能产生尽可能好的修复方案（例如，存在遗漏有效用例、测试能力有限的风险）
事实证明，通过安全团队报告的大多数漏洞其实只是普通漏洞，由于缺乏Linux 内核威胁模型（如 Documentation/process/threat-model.rst 所述）的了解而被不当地归类为安全漏洞，本应通过 Documentation/admin-guide/reporting-issues.rst 中描述的常规渠道提交
安全邮件列表用于那些在正确配置的生产系统上授予攻击者本不应拥有的能力、且容易被利用、对许多用户构成迫在眉睫威胁的紧急漏洞。在报告之前，请考虑该问题是否确实跨越了此类系统上的信任边界
**如果你借助AI 辅助来识别漏洞，你必须将其视为已公开**。尽管你可能有充分的理由相信它并非如此，但安全团队的经验表明，以这种方式发现的漏洞会系统性地同时在多名研究者之间浮现，往往就在同一天。在这种情况下，不要公开分享复现方法，因为这可能造成非预期的损害；只需说明存在复现方法，维护者若需要可能会在私下向你索取
如果你不确定某个问题是否符合条件，倾向于私下报告更为稳妥：安全团队宁愿对一份边缘报告进行分流，也不愿漏掉一个真正的漏洞。然而，将普通漏洞报告给安全列表并不会让它们处理得更快，还会消耗其他报告所需的分流能力
### 确定联系

报告安全漏洞最有效的方式是将其直接发送给受影响的子系统维护者，并抄送（Cc:）Linux 内核安全团队。在此阶段不要将其发送到公共列表，除非你有充分理由认为该问题已经公开或极易被发现（例如，来自任何人都能重复的、广泛可用的自动化漏洞扫描工具的结果，或是使用了基于 AI 的工具）
如果你要报告影响内核多个部分的问题，即便它们相当相似，也请分别发送独立的消息（要知道维护者并不会同时处理所有问题）。唯一的例外是：当某个问题涉及由完全相同的一小群维护者维护的紧密关联的部分，且这些部分预期由同一个提交一次性修复时，才可以一次性报告
对大多数首次报告者而言，一个困难在于确定正确的收件人列表。在 Linux 内核中，所有官方维护者都是可信的，因此不小心加入错误的维护者的后果基本上只是给那个人多一点噪音，即并无大碍。因此，一个合适的确定维护者列表的方法（内核安全官员也使用）是借助 get_maintainer.pl 脚本，并调整为只报告维护者。该脚本在传入文件名时，会在 MAINTAINERS 文件中查找其路径，从而得出一份相关维护者的层级列表。第一次调用时使用最精细的过滤级别，
```
  $ ./scripts/get_maintainer.pl --no-l --no-r --pattern-depth 1 \
    drivers/example.c
  Developer One <dev1@example.com> (maintainer:example driver)
  Developer Two <dev2@example.org> (maintainer:example driver)
```

这两名维护者随后应收到该消息。如果该命令没有返回任何内容，说明受影响的文件属于一个更大的子系统，因此我们

```
  $ ./scripts/get_maintainer.pl --no-l --no-r drivers/example.c
  Developer One <dev1@example.com> (maintainer:example subsystem)
  Developer Two <dev2@example.org> (maintainer:example subsystem)
  Developer Three <dev3@example.com> (maintainer:example subsystem [GENERAL])
  Developer Four <dev4@example.org> (maintainer:example subsystem [GENERAL])
```

这里，选取最前面、最具体的几个维护者就足够了。当列表很长时，可以生成一个以逗号分隔的电子邮件地址列表
```
  $ ./scripts/get_maintainer.pl --no-tree --no-l --no-r --no-n --m \
    --no-git-fallback --no-substatus --no-rolestats --no-multiline \
    --pattern-depth 1 drivers/example.c
  dev1@example.com, dev2@example.org
```

```
  $ ./scripts/get_maintainer.pl --no-tree --no-l --no-r --no-n --m \
    --no-git-fallback --no-substatus --no-rolestats --no-multiline \
    drivers/example.c
  dev1@example.com, dev2@example.org, dev3@example.com, dev4@example.org
```

如果到了这一步你仍然难以找到正确的维护者，**并且仅在这种情况*，可以将报告只发送给 Linux 内核安全团队。你的消息会被分流，并在需要时收到关于联系谁的指示。你的消息同样可能被原样转发给相关维护者
### 负责任地使用 AI 查找漏洞


提交给安全团队的漏洞报告中，有相当大一部分其实是借助 AI 工具进行代码审查的结果。虽然这是发现鲜少被探索区域中漏洞的一种高效手段，但它给维护者带来了过重负担，维护者有时因其质量或准确性较差而被迫忽略这些报告。因此，报告者必须特别留意以下往往会使这些报告变得不必要地难以处理的几点：

  - **篇幅**：AI 生成的报告往往过长，包含多个章节和过多的细节。这使得难以发现受影响文件、版本和影响等重要信息。请务必首先呈现对问题的清晰摘要以及所有关键细节。不要要求分流工程师翻阅多页文本。请将你的工具配置为生成简洁、拟人风格的报告
  - **格式**：大多数 AI 生成的报告充斥着 Markdown 标签。这些装饰会使查找重要信息变得复杂，并且在转发或回复所涉及的引用过程中无法保留。请在发送前**始终将报告转换为纯文*，不带任何格式装饰
  - **影响评估**：许AI 生成的报告缺乏对内核威胁模型（参Documentation/process/threat-model.rst）的理解，并费尽心思地编造理论上的后果。这会增加噪音并让分流变得更复杂。请坚持可验证的事实（例如“此漏洞允许任何用户获得 CAP_NET_ADMIN”），而不要列举推测性的影响。请让你的工具在评估过程中阅读此文档
  - **复现方法**：基AI 的工具往往能够生成复现方法。请始终确保你的工具提供一个，*充分测试*。如果复现方法无效，或者工具无法生成，则应认真质疑该报告的有效性。请注意，由于报告将发布到公共列表，复现方法应仅在维护者要求时才分享
  - **提出修复方案**：许AI 工具实际上更擅长写代码而非评估代码。请让你的工具提出一个修复方案并在报告问题前**进行测试**。如果由于依赖稀有硬件或几乎绝迹的网络协议而无法测试该修复方案，那么该问题很可能不是安全漏洞。无论如何，如果提出了修复方案，它必须遵Documentation/process/submitting-patches.rst，并包含指明引入该漏洞的提交'Fixes:' 标签
未能考虑这些要点会使你的报告面临被忽略的风险
在评估报告时要运用常识。如果受影响的文件已超过一年未被改动，且由个人单独维护，那么其使用量很可能已经下降，受影响的用户几乎不存在（例如非常老旧的硬件驱动、过时的文件系统）。在这种情况下，没必要用一份不重要的报告消耗维护者的时间。如果问题显然微不足道且可公开发现，你应直接报告到公共邮件列表
### 发送报

报告只能通过电子邮件发送。请使用一个可用的电子邮件地址，最好与你想出现`Reported-by` 标签中的地址一致（如果有的话）。如果不确定，先给自己发送一份报告
安全团队和维护者几乎总是需要超出报告最初所提供内容的额外信息，并依赖与报告者积极而高效的协作来进行进一步测试（例如验证版本、配置选项、缓解措施或补丁）。在联系安全团队之前，报告者必须确保自己能够解释其发现、参与讨论并运行额外的测试。如果报告者不能及时回应或无法有效讨论其发现，且沟通未能迅速改善，相关报告可能会被放弃
报告必须发送给维护者。如果你的消息中收件人只有两个或更少，你还必须始终抄送（Cc:）Linux 内核安全团队，他们会确保消息送达合适的人，并能够协助小型维护者团队处理他们可能不熟悉流程。对于较大的团队，在你最初几份报告或寻求特定帮助时（例如在一周内重发未获回复的消息时）抄Linux 内核安全团队。一旦你对几份报告的流程感到熟悉，在发送给大型团队时就不必再抄送安全列表。可以通过电子邮件 <security@kernel.org> 联系 Linux 内核安全团队。这是一个由安全官员组成的私人列表，他们将帮助核实漏洞报告并协助开发修复方案的开发者。安全团队可能会邀请相关领域的维护者提供额外帮助，以理解和修复该安全漏洞
请尽可能发送不带附件的**纯文*电子邮件。如果所有细节都藏在附件中，就很难就复杂问题进行带上下文引用的讨论。把它想象成 [常规补丁提交 <../process/submitting-patches>](常规补丁提交 <../process/submitting-patches>)（即便你还没有补丁）：描述问题和影响，列出复现步骤，并随后给出建议的修复方案，全部用纯文本。Markdown、HTML RST 格式的报告尤其不受欢迎，因为它们对人类来说相当难读，并且会促使使用专用查看器（有时是在线的），而这从定义上讲对机密的安全报告是不可接受的。请注意，某些邮件客户端默认往往会破坏纯文本的格式，详情请参Documentation/process/email-clients.rst
### 披露与处于禁运期的信

安全列表并非披露渠道。关于这一点，请参阅下文的“协调”
一旦开发出稳健的修复方案，发布流程即开始。已知公开漏洞的修复方案会立即发布
尽管我们倾向于在可用时尽快发布未公开漏洞的修复方案，但应报告者或相关方的要求，可以推迟，最长从发布流程开始起 7 个日历日，如果一致认为该漏洞的关键程度需要更多时间，则可特别延长14 个日历日。推迟发布修复方案的唯一正当理由，是为了配合需要发布协调的 QA 与大规模部署工作
虽然处于禁运期的信息可能会与可信的个人共享以开发修复方案，但在未经报告者许可的情况下，此类信息不会随修复方案一起发布，也不会在任何其他披露渠道发布。这包括但不限于原始漏洞报告及后续讨论（如有）、漏洞利用程序、CVE 信息或报告者的身份
换言之，我们唯一关心的是修复漏洞。提交给安全列表的所有其他信息以及报告的后续讨论，即使在禁运解除后也会永久保密
### 与其他团队的协调


虽然内核安全团队只专注于修复漏洞，但其他团队专注于修复各发行版中的问题，并在操作系统供应商之间协调披露。协调通常“linux-distros邮件列表处理，披露由公共“oss-security邮件列表处理，两者密切相关，并在 linux-distros wiki 中有所说明https://oss-security.openwall.org/wiki/mailing-lists/distros>

请注意，由于3 个列表追求的目标不同，它们各自的政策和规则也不同。在内核安全团队与其他团队之间进行协调很困难，因为对内核安全团队而言，偶发的禁运（受最大允许天数限制）从修复方案可用时开始，而对 “linux-distros而言，无论修复方案是否可用，禁运都从首次发布到该列表时开始
因此，内核安全团队强烈建议，作为潜在安全问题的报告者，在以下情况之前你**不要**联系 “linux-distros邮件列表：受影响的代码维护者已接受修复方案，且你已经阅读了上面distros wiki 页面，并完全理解联系 “linux-distros将对你和内核社区施加的要求。这也意味着，一般而言同时抄送两个列表没有意义，除非在已接受的修复方案尚未合并时可能为了协调而这样做。换言之，在修复方案被接受之前不要抄“linux-distros”，在合并之后不要抄送内核安全团队
### CVE 分配


安全团队不分CVE，也不要求报告或修复提供 CVE，因为这会不必要地使流程复杂化，并可能推迟漏洞处理。如果报告者希望为已确认的问题分配一CVE 标识符，他们可以联系 :doc:`内核 CVE 分配团队<../process/cve>` 来获取
### 保密协议


Linux 内核安全团队并非正式机构，因此无法签订任何保密协议
