

为何不应使用 "volatile" 类型限定符



C 程序员常常把 volatile 理解为该变量可能在当前执行线程之外被改变；因此，他们在内核代码中使用共享数据结构时，有时会忍不住使用它。换句话说，他们把 volatile 类型当成了某种简单的原子变量来用，但实际上并非如此。在内核代码中使用 volatile 几乎从来都是不正确的；本文档将解释原因。


理解 volatile 的关键点在于：它的目的是抑制优化，而这几乎从来不是人们真正想要做的事情。在内核中，必须保护共享数据结构免受不期望的并发访问，这是一项非常不同的任务。保护免受不期望并发的过程，也会以更高效的方式避免几乎所有与优化相关的问题。


与 volatile 类似，使数据并发访问安全的那些内核原语（自旋锁、互斥锁、内存屏障等）也是为了防止不期望的优化而设计的。如果它们被正确使用，就不需要再使用 volatile。如果仍然需要 volatile，那几乎可以肯定代码某处存在缺陷。在编写良好的内核代码中，volatile 只会拖慢速度。

```

    spin_lock(&the_lock);
    do_something_on(&shared_data);
    do_something_else_with(&shared_data);
    spin_unlock(&the_lock);

```

如果所有代码都遵循加锁规则，那么在持有 the_lock 期间，shared_data 的值不会意外改变。任何其他可能想要操作该数据的代码都会等待该锁。自旋锁原语充当内存屏障——它们是被显式编写来做到这一点的——这意味着对数据的访问不会被跨屏障优化。所以编译器也许以为它知道 shared_data 中会有什么，但 spin_lock() 调用由于充当内存屏障，会迫使它忘掉自己所知道的一切。对该数据的访问将不会有优化问题。


如果将 shared_data 声明为 volatile，加锁仍然是必要的。但编译器同时也会被阻止在临界区_内部_优化对 shared_data 的访问，而此时我们知道没有其他代码能操作它。在持有锁期间，shared_data 并不是 volatile 的。在处理共享数据时，正确的加锁使 volatile 变得不必要——甚至可能是有害的。


volatile 存储类最初是为内存映射 I/O 寄存器设计的。在内核中，寄存器访问同样应当受锁保护，但同时人们也不希望编译器"优化"临界区内的寄存器访问。不过在内核中，I/O 内存访问总是通过访问器函数完成；直接通过指针访问 I/O 内存是不被提倡的，并且在所有架构上都无法工作。那些访问器函数被编写为防止不期望的优化，因此 volatile 再次变得不必要。


另一种人们可能忍不住使用 volatile 的情形，是当处理器正忙等待某个变量的值时。正确的做法是
```

    while (my_variable != what_i_want)
        cpu_relax();

```

cpu_relax() 调用可以降低 CPU 功耗，或让出给超线程孪生处理器；它恰好也充当编译器屏障，因此 volatile 再次变得不必要。当然，忙等待本身通常就是一种不顾及他人的行为。


在内核中，仍有少数罕见情况下使用 volatile 是合理的：


  - 上述访问器函数可能会在使用直接 I/O 内存访问的架构上对访问使用 volatile。本质上，每次访问器调用自身都成为一个小小的临界区，并确保访问按程序员的预期发生。


  - 修改内存但没有其他可见副作用的内联汇编代码，有被 GCC 删除的风险。在 asm 语句中添加 volatile 关键字可防止这种删除。


  - jiffies 变量很特殊，因为它每次被引用时都可能具有不同的值，但又可以在没有任何特殊加锁的情况下读取。所以 jiffies 可以是 volatile 的，但强烈不提倡再添加此类其他变量。在这方面，jiffies 被视为一个"愚蠢的历史遗留"问题（Linus 的原话）；修复它所带来的麻烦超过了它的价值。


  - 指向可能被 I/O 设备修改的 coherent 内存中数据结构的指针，有时可以合理地声明为 volatile。一个由网络适配器使用的环形缓冲区就是这种情形的例子，其中适配器修改指针以指示哪些描述符已被处理。


对大多数代码而言，上述为 volatile 辩护的理由均不适用。因此，使用 volatile 很可能被视为缺陷，并会带来对代码的额外审查。想要使用 volatile 的开发者应当退一步，思考他们真正想要达成什么。


移除 volatile 变量的补丁通常是受欢迎的——只要它们附带能表明并发问题已被妥善考虑的理由。
