
## 简


### 摘要


本节其余部分涵盖内核开发过程的范围，以及开发者和他们的雇主在那里可能遇到的各类挫折。将内核代码合并进官方（“主线”）内核有非常多的理由，包括自动对用户可用、多种形式的社区支持，以及影响内核开发方向的能力。贡献给 Linux 内核的代码必须以GPL 兼容的许可证发布

development_process 介绍开发过程、内核发布周期，以及合并窗口的机制。涵盖了补丁开发、评审与合并周期的各个阶段。还讨论了工具和邮件列表。希望开始内核开发的开发者被鼓励以追踪并修复 bug 作为初步练习

development_early_stage 涵盖早期项目规划，重点是尽早让开发社区参与进来

development_coding 关于编码过程；讨论了其他开发者遇到过的若干陷阱。涵盖了补丁的一些要求，并介绍了一些有助于确保内核补丁正确的工具

development_posting 讨论发布补丁以供评审的过程。要想被开发社区认真对待，补丁必须被正确地格式化与描述，并且必须发送到正确的地方。遵循本节的建议应有助于确保你工作的成果获得最好的接受度

development_followthrough 涵盖发布补丁之后发生的事情；到那时工作还远未结束。与评审者合作是开发过程的关键部分；本节提供了许多关于如何在这一重要阶段避免问题的技巧。开发者被提醒：不要想当然地认为补丁一旦合并进主线，工作就完成了

development_advancedtopics 介绍几个“高级”主题：git 管理补丁，以及评审他人发布的补丁

development_conclusion 以指向更多内核开发信息的来源作为本文档的结尾

### 本文档是关于什么的


Linux 内核拥有超过 800 万行代码，每次发布都有超1000 名贡献者，是现存最大、最活跃的自由软件项目之一。自 1991 年不起眼beginnings 以来，这个内核已经演变成一个一流的操作系统组件，运行在口袋大小的数字音乐播放器、台PC、现存最大的超级计算机，以及介于其间的各类系统上。对于几乎任何场景，它都是一个健壮、高效且可扩展的解决方案

随着 Linux 的发展，希望参与其开发的开发者（和公司）数量也在增长。硬件厂商希望确Linux 良好地支持他们的产品，使这些产品Linux 用户具有吸引力。将 Linux 用作集成产品中一个组件的嵌入式系统厂商，希望 Linux 尽可能强地胜任并适合手头的任务。以 Linux 为基础构建产品的发行商和其他软件厂商，Linux 内核的能力、性能与可靠性有着明确的兴趣。最终用户也常常会希望改Linux，使其更好地满足自己的需要

Linux 最引人注目的特性之一是它对开发者是可及的；任何具备必要技能的人都可以改进 Linux 并影响它的发展方向。专有产品无法提供这种开放性，而这是自由软件过程的特征。但即便如此，内核比大多数其他自由软件项目甚至更加开放。一个典型的三个月内核开发周期可能涉及超1000 名开发者，他们为超100 家不同的公司工作（或者根本不为任何公司工作）

与内核开发社区合作并非特别困难。尽管如此，许多潜在的贡献者在尝试做内核工作时遇到了困难。内核社区已经演化出自己独特的运作方式，使其能够在每天都有数千行代码被改动的环境中平稳运行（并产出高质量的产品）。因此，Linux 内核开发过程与专有开发方法大不相同也就不足为奇了

内核的开发过程对新开发者来说可能显得陌生且令人生畏，但这背后有良好的理由和扎实的经验。一个不理解内核社区行事方式（或者更糟，试图藐视或规避它们）的开发者，将会有一段令人沮丧的经历在等待着他。开发社区虽然乐于帮助那些正在努力学习的人，但很少有时间留给那些不愿倾听或不关心开发过程的人

希望阅读本文档的人能够避免那种令人沮丧的经历。这里有大量材料，但阅读它们所付出的努力很快就会得到回报。开发社区一直需要能够帮助改进内核的开发者；下文应能帮助您——或为您工作的人——加入我们的社区

### 将代码合入主线的重要


一些公司和个人开发者偶尔会疑惑，为什么他们要费心去学习如何与内核社区合作，并把他们的代码合入主线内核（“主线”是Linus Torvalds 维护、并被各 Linux 发行商用作基础的内核）。在短期内，贡献代码可能看起来像是一笔可以避免的开支；似乎把代码单独保留并直接支持用户更容易。事情的真相是，把代码单独保留（“树外”）是一种虚假的节约

为了说明树外代码的成本，这里列出内核开发过程的几个相关方面；其中大多数将在本文档后面更详细地讨论。考虑以下几点

- 已经合并进主线内核的代码对所Linux 用户都可用。它将自动出现在所有启用它的发行版中。不需要驱动盘、下载，也不需要支持多个发行版的多个版本的麻烦；对开发者和用户来说，一切都能正常工作。并入主线解决了一大堆发行与支持的难题

- 虽然内核开发者努力维持对用户空间的稳定接口，但内核内API 在不断变化。缺乏稳定的内部接口是一个有意为之的设计决定；它允许在任何时候进行根本性的改进，并产生更高质量的代码。但这一策略的一个结果是：任何树外代码要想与新内核一起工作，都需要持续的维护。维护树外代码需要大量的工作，仅仅是为了让那段代码能继续工作

  相反，并入主线的代码不需要这种工作，因为有一条简单的规则：任何做 API 改动的开发者也必须修复因该改动而失效的任何代码。所以，合并进主线的代码维护成本低得多

- 除此之外，内核中的代码常常会被其他开发者改进。赋予你的用户社区和客户改进你产品的能力，会带来令人惊讶的结果

- 内核代码在合并进主线之前和之后都会接受评审。无论原始开发者的技能有多强，这个评审过程总会找到可以改进代码的方法。评审常常能发现严重bug 与安全问题。对于在封闭环境中开发的代码尤其如此；这样的代码从外部开发者的评审中获益极大。树外代码就是较低质量的代码

- 参与开发过程是你影响内核开发方向的方式。在场边抱怨的用户也会被听到，但活跃的开发者有更强的声音——以及实现改进、让内核更好地满足他们需要的能力

- 当代码被单独维护时，第三方贡献类似特性的不同实现的可能性总是存在。如果发生这种情况，让你的代码合并进来会变得更加困难——直至不可能。那时你将面临不愉快的选择1) 无限期地在树外维护一个非标准特性，(2) 放弃你的代码并将你的用户迁移到树内版本

- 贡献代码是使整个过程运转起来的基本动作。通过贡献你的代码，你可以为内核添加新功能，并提供对其他内核开发者有用的能力与示例。如果你已经Linux 开发过代码（或正考虑这么做），你显然对这一个平台持续成功有兴趣；贡献代码是确保该成功的最佳方式之一

上述所有理由适用于任何树外内核代码，包括以专有、仅二进制形式分发的代码。然而，在考虑任何形式的仅二进制内核代码分发之前，还应考虑额外的因素。这些包括：

- 围绕专有内核模块分发的法律问题即便往最好了说也是模糊的；相当多的内核版权持有者相信，大多数仅二进制模块是内核的派生产品，因此它们的分发违反了 GNU 通用公共许可证（下文将有更多说明）。本文作者不是律师，本文档中的任何内容都不可能被视为法律建议。闭源模块真正的法律地位只能由法院决定。但笼罩在这些模块上的不确定性无论怎样都是存在的

- 二进制模块极大地增加了调试内核问题的难度，以至于大多数内核开发者甚至不会去尝试。因此，分发仅二进制模块会让你的用户更难从社区获得支持

- 仅二进制模块的分发商支持起来也更困难，他们必须为他们希望支持的每一个发行版和每一个内核版本提供一个模块版本。要提供相当全面的覆盖可能需要数十个构建版本，而你的用户每次升级内核时都不得不单独升级你的模块

- 上文关于代码评审所说的一切，对闭源代码而言加倍适用。由于这段代码根本不可用，它不可能经过社区评审，并且毫无疑问会存在严重问题

嵌入式系统的制造者尤其可能受到诱惑，忽视本节中大部分论述，认为他们交付的是一个自包含产品，使用冻结的内核版本，并且在发布后不再需要开发。这种说法忽略了广泛代码评审的价值，以及允许你的用户为你的产品添加能力的价值。但这些产品同样有有限的商业寿命，之后必须发布新版本。到那时，代码在主线中且维护良好的厂商，将处于有利得多的位置，能够迅速让新产品为上市做好准备

### 许可


贡献Linux 内核的代码使用多种许可证，但所有代码必须与 GNU 通用公共许可证第 2 版（GPLv2）兼容，GPLv2 是覆盖整个内核分发的许可证。在实践中，这意味着所有代码贡献要么被 GPLv2 覆盖（可选地带有允许在后GPL 版本下分发的语言），要么被三条款 BSD 许可证覆盖。任何不被兼容许可证覆盖的贡献都不会被内核接受

向内核贡献代码不需要（也不要求）版权转让。所有合并进主线内核的代码保留其原始所有权；结果，内核现在有了数千名所有者

这种所有权结构的一个含义是：任何试图改变内核许可证的尝试都注定几乎必然失败。在少数实际场景中，有可能获得所有版权持有者的同意（或将他们的代码从内核中移除）。因此，特别是在可预见的未来，不存在GPL 3 版迁移的前景

至关重要的是，所有贡献给内核的代码必须是合法的自由软件。出于这个原因，来自身份未知的贡献者或匿名贡献者的代码不会被接受。所有贡献者都需要在其代码上“签名（sign off）”，声明该代码可以在 GPL 下与内核一起分发。未被其所有者以自由软件许可证授权的代码，或者可能给内核带来版权相关问题的代码（例如源自缺乏适当保障的反向工程工作的代码），都不可被贡献

关于版权相关问题的疑问在 Linux 开发邮件列表上很常见。这类问题通常不乏回答，但应记住，回答这些问题的人不是律师，也无法提供法律建议。如果你有与 Linux 源代码相关的法律问题，没有任何东西可以替代与一位理解这一领域的律师交谈。依赖从技术邮件列表上获得的答案是一件冒险的事
