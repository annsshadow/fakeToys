
## 跟进


此时，您已经遵循了迄今为止给出的指导方针，并且再加上你自己的工程技能，已经发布了一系列完美的补丁。即使是经验丰富的内核开发人员也会犯的最大错误之一，就是认为自己的工作现在已经大功告成。事实上，发布补丁意味着转入流程的下一阶段，而后面可能还有相当多的工作要做。

首次发布就完美到无可改进的补丁十分罕见。内核开发流程认识到了这一事实，因而高度注重对已发布代码的改进。作为该代码的作者，你需要与内核社区合作，以确保你的代码达到内核的质量标准。不参与这一过程，很可能会导致你的补丁无法被并入主线。


### 与审阅者合作


任何有一定分量的补丁都会引来其他开发人员在审查代码时给出的大量评论。对许多开发人员来说，与审阅者合作可能是内核开发流程中最令人畏惧的部分。不过，只要记住几件事，日子会好过得多：

 - 如果你已经把补丁解释得足够清楚，审阅者会理解它的价值，以及你为何费心去写它。但这个价值并不能阻止他们问一个根本性的问题：五年或十年后，维护一个包含这段代码的内核会是什么样子？你可能被要求做出的许多改动——从编码风格的微调到大幅重写——都源于这样一种认识：十年之后 Linux 仍将存在并处于开发之中。

 - 代码审查是一项艰苦的工作，也是一份相对吃力不讨好的差事；人们会记得谁写了内核代码，但审查它的人却几乎留不下什么长久的声名。所以审阅者可能会变得暴躁，尤其是在他们看到同样的错误被一遍又一遍地犯下时。如果你收到的审查意见看起来愤怒、侮辱，甚至公然冒犯，请克制以同样方式回击的冲动。代码审查针对的是代码，而不是人，代码审阅者并非在针对你个人。

 - 同样，代码审阅者也不是要以牺牲你雇主的利益为代价来推进他们自己雇主的议程。内核开发人员通常期望多年以后仍在从事内核工作，但他们明白自己的雇主可能会变。他们几乎毫无例外地，确实是在致力于打造他们所能做到的最好的内核；他们并非想给雇主的竞争对手制造麻烦。

 - 要为看似愚蠢的编码风格改动请求，以及把你的部分代码抽取到内核共享部分的要求做好准备。维护者的一项工作就是让整体看起来一致。有时这意味着，你在驱动里为解决某个问题而采用的那个巧妙的 hack，其实需要变成一个通用的内核特性，以备下次之需。

所有这些归结起来就是：当审阅者给你发送评论时，你需要留意他们所做的技术性观察，不要让他们表达的方式或你自己的骄傲阻碍了这一点。当你的补丁收到审查意见时，花点时间去理解审阅者想表达什么。如果可能，修复审阅者要求你修复的那些问题。并回复审阅者：感谢他们，并说明你将如何回应他们的问题。

请注意，你不必同意审阅者建议的每一处改动。如果你认为审阅者误解了你的代码，请解释实际情况究竟如何。如果你对某项建议的改动持有技术上的反对意见，请描述它，并为你的解决方案辩护。如果你的解释说得通，审阅者会接受。不过，倘若你的解释证明缺乏说服力，尤其是当其他人也开始认同审阅者时，请花点时间重新思考一下。人很容易对自己的解决方案一叶障目，以至于意识不到某些地方存在根本性的错误，或者，也许你根本就没在解决正确的问题。

Andrew Morton 曾建议，每一条没有促成代码改动的审查意见，都应当转而带来一条额外的代码注释；这能帮助未来的审阅者避免第一次出现过的那些疑问。

一个致命的错误是忽视审查意见，指望它们会自动消失。它们不会消失。如果你在没有回应上次收到的意见的情况下重新发布代码，你很可能会发现你的补丁毫无进展。

说到重新发布代码：请记住，审阅者不会记得你上次发布的代码的所有细节。因此，提醒审阅者先前提出过哪些问题、以及你是如何处理的，永远是个好主意；补丁的变更日志（changelog）是放置这类信息的好地方。审阅者不必去翻列表存档来熟悉上次说了些什么；如果你帮他们快速进入状态，他们重新审视你的代码时心情会好一些。

如果你已经尽力把每件事都做对，事情却仍然毫无进展，该怎么办？大多数技术分歧都可以通过讨论解决，但有时总得有人来做个决定。如果你真诚地认为这个决定错误地站在了你对立面，你总可以尝试向更高的权威申诉。截至本文撰写时，那位更高的权威往往是 Andrew Morton。Andrew 在内核开发社区中备受尊重；他常常能解开看似陷入僵局的局面。不过，向 Andrew 申诉不应轻率行事，也不应在所有其他替代方案都尝试过之前就去找他。当然也要记住，他也可能并不同意你的看法。


### 接下来会发生什么


如果一个补丁被认为适合加入内核，并且大多数审查问题已经解决，下一步通常是进入某个子系统维护者的树。具体如何运作因子系统而异；每位维护者都有自己的行事方式。特别地，可能存在不止一棵树——一棵也许专门面向为下一个合并窗口准备的补丁，另一棵面向更长期的工作。

对于应用到没有明显子系统树覆盖的领域（例如内存管理补丁）的补丁，默认的那棵树往往最终是 -mm。影响多个子系统的补丁也可能最终经由 -mm 树。

进入子系统树能让补丁获得更高的可见性。现在，使用该树的其他开发人员会默认拿到这个补丁。子系统树通常也会汇入 linux-next，使其内容对整个开发社区可见。到这个阶段，你很有可能会从一批新的审阅者那里得到更多评论；这些评论需要像上一轮那样得到回应。

在这个阶段，取决于你补丁的性质，也可能出现与他人正在进行的工作相冲突的情况。最坏的情况下，严重的补丁冲突会导致一些工作被放到一边（back burner），以便剩下的补丁能够成形并被合并。其他时候，解决冲突需要与其他开发人员协作，并可能要在树之间移动一些补丁，以确保一切都能干净地应用。这项工作可能很痛苦，但你要心存感激：在 linux-next 树出现之前，这些冲突往往只在合并窗口期间才暴露，不得不仓促处理。现在它们可以在合并窗口打开之前从容解决。

终有一天，如果一切顺利，你登录后会看到自己的补丁已经被合并进了主线内核。恭喜！不过，在庆祝完毕（并且你已经把自己加进 MAINTAINERS 文件）之后，值得记住一个重要的事实：工作仍未完成。并入主线本身也带来了挑战。

首先，你的补丁的可见性再次提高了。可能会有新一轮来自此前并不知道这个补丁的开发人员的评论。由于你的代码是否会被合并已不再有疑问，忽略它们可能很诱人。但要抵制这种诱惑；你仍然需要对那些有疑问或建议的开发人员保持响应。

不过，更重要的是：进入主线会把你的代码交到一大群测试者手中。即便你贡献的是一个面向尚未上市硬件的驱动，你也会惊讶于有多少人会把你的代码编进他们的内核。当然，哪里有测试者，哪里就会有 bug 报告。

最糟糕的一类 bug 报告是回归。如果你的补丁导致了回归，你会发现自己被数量多得令人不安的目光盯着；回归需要尽快修复。如果你不愿或无法修复该回归（也没人替你修复），你的补丁几乎肯定会在稳定期内被移除。除了抵消你为把补丁送进主线所做的一切努力之外，因为未能修复回归而导致补丁被撤下，很可能会让你日后想合并工作变得更难。

在解决了任何回归之后，可能还有其他普通的 bug 需要处理。稳定期是你修复这些 bug、并确保你的代码在主线内核版本中的首次亮相尽可能扎实的最佳机会。所以，请回应 bug 报告，并尽可能修复问题。这正是稳定期的用途所在；一旦旧补丁的任何问题都处理妥当，你就可以开始创建很酷的新补丁了。

别忘了，还有其他里程碑也可能产生 bug 报告：下一个主线稳定版的发布、当知名发行版选用包含你补丁的某个内核版本时，等等。持续回应这些报告，是你对自己工作基本的荣誉感所在。如果这还不够有动力，那么也值得想一想：开发社区会记住那些在代码合并后就对其失去兴趣的开发人员。下次你贴出补丁时，他们会以“你合并后就不会在身边维护它”这个假设来评估它。


### 其他可能发生的事情


有一天，你可能会打开邮件客户端，看到有人给你发来了针对你代码的补丁。毕竟，这正是把代码公开出来的一大好处。如果你同意这个补丁，既可以把它转发给子系统维护者（务必包含一个正确的 From: 行以保证署名正确，并加上你自己的 Signed-off-by），也可以回复一个 Acked-by: 让原始发布者把它向上发送。

如果你不同意这个补丁，请礼貌地回复解释原因。如果可能，告诉作者需要做哪些改动才能让你接受这个补丁。合并那些被代码作者和维护者都反对的补丁，确实存在一定的阻力，但这种阻力也是有限度的。如果你被视为在无谓地阻挡好的工作，那些补丁最终会绕过你，照样进入主线。在 Linux 内核中，没有人对于任何代码拥有绝对的否决权。也许 Linus 除外。

在极罕见的情况下，你可能会看到完全不同的东西：另一位开发人员发布了针对你那个问题的另一种解决方案。到那时，两个补丁很可能只有一个会被合并，而“我的先到这儿”并不被认为是一个有说服力的技术论据。如果别人的补丁取代了你的并进入了主线，真正能做的回应只有一种：为你的问题得到解决而感到高兴，然后继续干你的活。自己的作品以这种方式被推到一边，可能会让人伤心和气馁，但社区对你反应的记忆，会远超过他们对究竟谁的补丁真正被合并了的记忆。
