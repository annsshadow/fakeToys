
## 提交补丁


迟早会有这么一天，你的工作已经准备好呈现给社区评审，并最终合入主线内核。不出所料，内核开发社区在提交补丁方面形成了一套约定与流程；遵循它们会让所有相关方都轻松得多。本文试图合理地详细阐述这些期望；更多信息还可以在以下文件中找到
Documentation/process/submitting-patches.rst <submittingpatches>
鍜?Documentation/process/submit-checklist.rst <submitchecklist>銆。


### 何时提交


人们总是忍不住想要在补丁完全"就绪"之前不去提交。对于简单的补丁，这不成问题。但如果所做的工作很复杂，在完工之前从社区获得反馈会收益良多。因此你应该考虑提交进行中的工作，甚至提供一git 树，让感兴趣的开发者随时跟上你的进度

当提交的代码尚未被认为可以合入时，最好在提交本身中说明这一点。同时提及仍待完成的主要工作以及任何已知问题。看那些已知半成品补丁的人会少一些，但来看的人会带着"我可以帮你把工作引向正确方向"的想法而来


### 创建补丁之前


在考虑向开发社区发送补丁之前，有若干事项应该先做。包括：

 - 在你能力范围内测试代码。利用内核的调试工具，确保内核能在所有合理的配置选项组合下构建，使用交叉编译器为不同架构构建，等等。添加测试，最好使用像 KUnit 这样的现有测试框架，并将其作为你补丁系列中的一个独立成员（关于补丁系列的更多内容见下一节）。注意，在影响某些子系统时，这可能是强制性的。例如，库函数（位于 lib/ 下）几乎随处可见且被广泛使用，应当经过适当测试

 - 确保你的代码符合内核代码风格指南

 - 你的改动是否有性能方面的影响？如果有，你应该运行基准测试来展示改动的影响（或收益）；结果摘要应随补丁一并附上

 - 确保你有权提交这段代码。如果这项工作是为雇主完成的，雇主持有这项工作的权利，并且必须同意在 GPL 下发布它

一般说来，在提交代码前多花些心思，几乎总能很快得到回报


### 补丁准备


为提交而准备补丁可能是出人意料地大量的工作，但同样，即便从短期看，想在这里节省时间通常也不可取

补丁必须基于特定版本的内核来制作。一般规则是，补丁应当基Linus git 树中的当前主线。基于主线时，应从一个众所周知的发布点开始——一个稳定版-rc 版——而不是从主线任意位置分叉

不过，为了便于更广泛的测试与评审，可能也需要基-mm、linux-next 或某个子系统树制作版本。取决于你的补丁所涉领域以及其他地方的动向，基于这些其他树制作补丁可能需要大量工作来解决冲突和应API 变更

只有最简单的改动才应格式化为单个补丁；其他一切都应做成逻辑上的一系列改动。拆分补丁多少是一门艺术；一些开发者花了很长时间才弄明白社区期望的那种拆法。不过有几条经验法则可以很大程度地帮上忙

 - 你提交的补丁系列几乎肯定不会是你工作版本控制系统中那一系列改动。相反，你需要把你做的改动以最终形态来考虑，然后以合理的边界拆分。开发者感兴趣的是离散、自包含的改动，而不是你走到这些改动所经过的路径

 - 每个逻辑上独立的改动都应格式化为一个独立的补丁。这些改动可以很小（"向这个结构加一个字）也可以很大（例如新增一个重要的驱动），但它们在概念上应当小，并且适合用一句话描述。每个补丁都应做出一个可以单独评审、并能被验证确实如其所说那样的特定改动

 - 重申上面这条准则：不要在同一补丁中混入不同类型的改动。如果一个补丁既修复了一个严重的安全漏洞，又重新排布了几个结构，还重新格式化了代码，那么它很可能被跳过，而那个重要的修复就会丢失

 - 每个补丁都应产生一个能正确构建并运行的内核；如果你的补丁系列在中间被打断，结果仍应是一个能工作的内核。在使用 "git bisect" 工具查找回归时，补丁系列的部分应用是一种常见情形；如果结果是一个坏掉的内核，你会让从事追踪问题这项高尚工作的开发者和用户更难受

 - 但也不要过度。曾有位开发者把对一个文件的改动作为 500 个独立补丁发出——这一举动并未让他成为内核邮件列表上最受欢迎的人。只要仍只包含一*逻辑**改动，单个补丁可以相当大

 - 你可能会受诱惑去用一系列补丁添加一整套新基础设施，却让它一直闲置，直到系列中最后一个补丁才启用整体。如果可能，应当避免这种诱惑；如果该系列引入了回归，二分法会把最后一个补丁指为引发问题的那个，即便真正的缺陷在别处。只要可能，添加新代码的补丁应当让那些代码立即生效

打造完美的补丁系列可能是一个令人沮丧的过程，在"真正的工完成后还需要相当多的时间和思考。但只要做得对，这段时间就花得值得


### 补丁格式与变更日


于是你现在有了一系列完美的待提交补丁，但工作还没完全结束。每个补丁都需要被格式化为一条消息，快速而清楚地向世界传达其目的。为此，每个补丁将由以下内容组成

 - 可选的一"From"，注明补丁作者。这行只有在你通过邮件转交别人的补丁时才必要，但有疑问时加上也无妨

 - 一行对补丁所做事的描述。这条消息应当足以让一个在别无上下文情况下看到它的人弄清楚补丁的范围；它会作为"简变更日志出现。这条消息通常以相关子系统名开头，后接补丁的目的。例如：

```

	gpio: fix build on CONFIG_GPIO_SYSFS=n

 - 一个空行，后接对补丁内容的详细描述。描述可长可短，随需要而定；它应当说明补丁做了什么，以及为何应被应用到内核

 - 一行或多行标签，至少要有来自补丁作者的一Signed-off-by:。标签将在下文更详细地描述

```
上面的各项合在一起构成补丁的变更日志。写出好的变更日志是一门关键却常被忽视的艺术；值得再花点时间讨论这个问题。写变更日志时，你应记住会有许多不同的人读到你的文字。其中包括需要决定补丁是否应被合入的子系统维护者与评审者、试图判断补丁是否应被回移植到其他内核的发行商与其他维护者、想知道补丁是否就是他们在追查的问题根源的缺陷猎人、想知道内核变了什么的用户，等等。一条好的变更日志应以最直接、最简洁的方式把所需信息传达给所有这些读者

为此，在单行限制下，摘要行应尽可能描述改动的效果与动机。详细描述则可以展开这些话题，并提供任何需要的附加信息。如果补丁修复了一个缺陷，请尽可能引用引入该缺陷的提交（引用提交时请给出提ID 和标题）。如果问题与特定的日志或编译器输出相关，请包含那些输出，以帮助其他在搜索同一问题解法的人。如果改动是为了支持后续补丁中的其他改动，请说明。如果内API 有变更，请详述这些变更以及其他开发者应如何应对。一般而言，你越能设身处地站在每个将读你变更日志的人位置上，这条变更日志（乃至整个内核）就会越好

毋庸置疑，变更日志应当是提交改动到版本控制系统时所用的文本。它后面跟着

 - 补丁本身，采用统一-u"）补丁格式。对 diff 使用 "-p" 选项会把函数名与改动关联起来，使生成的补丁更易为他人阅读

上面已简要提及的标签用于说明补丁是如何产生的。它们在
Documentation/process/submitting-patches.rst <submittingpatches>
文档中有详尽描述；此处仅作简要总结

有一个标签用于引用由补丁所修复问题由之引入的更早提
```

	Fixes: 1f2e3d4c5b6a ("The first line of the commit specified by the first 12 characters of its SHA-1 ID")

```
另一个标签用于链接带有额外背景或细节的网页，例如导致该补丁的早先讨论
```

	Link: https://example.com/somewhere.html  optional-other-stuff

```
遵照首席企鹅（Chief Penguin）的指引，只有当 Link: 标签指向在提交本身中找不到的有用信息时，才应加到提交上

如果 URL 指向由补丁修复的公开缺陷报告，请使用
```

	Closes: https://example.com/issues/1234  optional-other-stuff

```
一些缺陷跟踪器在应用带有此类标签的提交时能自动关闭对应问题。一些监控邮件列表的机器人也能追踪此类标签并采取某些动作。私有缺陷跟踪器和无URL 是被禁止的

另一种标签用于记录谁参与了补丁的开
```

	tag: Full Name <email address>  optional-other-stuff

```
常用的标签有

 - Signed-off-by: 这是开发者的一份认证，证明其有权提交该补丁以合入内核。它是对开发者原产地证书（Developer's Certificate of Origin）的同意，其全文可在 Documentation/process/submitting-patches.rst <submittingpatches> 中找到。没有恰当签名的代码无法合入主线

 - Co-developed-by: 声明补丁由多名开发者共同创建；当多人协作于单个补丁时，用于向共同作者（除由 From: 标签归属的作者外）致谢。每Co-developed-by: 之后必须紧接相应共同作者的 Signed-off-by:。细节与示例Documentation/process/submitting-patches.rst <submittingpatches>

 - Acked-by: 表示另一位开发者（通常是相关代码的维护者）同意该补丁适合合入内核

 - Tested-by: 声明具名人员已测试该补丁并发现其可用

 - Reviewed-by: 具名开发者已评审该补丁的正确性；详见 Documentation/process/submitting-patches.rst <submittingpatches> 中的评审者声明

 - Reported-by: 点名一位报告了由本补丁所修复问题的用户；此标签用于向那些（常未被充分认可）测试我们的代码、并在事情出错时告知我们的人致谢。注意，除非报告未在网页上公开，否则此标签后应跟一个指向该报告Closes: 标签。如果补丁修复的是所报告问题的一部分，可Link: 标签代替 Closes:

 - Suggested-by: 标签表示补丁的构思由具名人士提出，并确保对其构思致谢。这有望激励他们在未来再次帮助我们

 - Cc: 具名人士收到了补丁的副本，并有机会对其进行评论

在向你补丁添加上述标签时要小心，因为Cc:、Reported-by: Suggested-by: 外，其余都需要具名人士的明确许可。对于这三者，如果相关人依lore 归档或提交历史使用那个名字和邮箱地址Linux 内核作过贡献，则默示许可即已足够——并且对Reported-by: Suggested-by:，其报告或建议是公开的。注意，在此意义bugzilla.kernel.org 是公开场所，但其中使用的邮箱地址是私有的；因此不要在标签中暴露它们，除非该人曾在更早的贡献中使用过


### 发送补


在你邮寄补丁之前，还有几件事要处理好

 - 你确定你的邮件客户端不会破坏补丁吗？被邮件客户端做了无谓空白改动或自动换行的补丁，在另一端无法应用，而且常常不会被细看。如果还有任何疑虑，把补丁寄给你自己，确认它完整无损地到达

   Documentation/process/email-clients.rst <email_clients> 有一些关于让特定邮件客户端适用于发送补丁的有用提示

 - 你确信你的补丁没有低级错误吗？你应当总是把补丁通过 scripts/checkpatch.pl 运行，并处理它报出的问题。请记住，checkpatch.pl 虽体现了关于内核补丁应是什么样子的相当多的思考，但它并不比你聪明。如果修checkpatch.pl 的告警会让代码变差，那就别改

补丁应始终以纯文本发送。请不要作为附件发送；那会让评审者在回复中很难引用补丁的段落。相反，直接把补丁放进你的消息里

邮寄补丁时，给任何可能感兴趣的人发副本很重要。与其他一些项目不同，内核鼓励人们宁可多发副本也不要漏发；不要假设相关人员会在邮件列表上看到你的提交。具体而言，副本应发给

 - 受影响子系统的维护者。如前所述，MAINTAINERS 文件是查找这些人的第一去处

 - 在同一领域工作过的其他开发者——尤其是那些现在可能正在那里工作的人。用 git 查看还有谁修改过你正在处理的文件会很有帮助

 - 如果你是在回应一个缺陷报告或功能请求，也请抄送原始发帖人

 - 给相关邮件列表发一份副本，如果都不适用，则发给 linux-kernel 列表

 - 如果你在修复一个缺陷，考虑这个修复是否应进入下一个稳定更新。如果是，stable@vger.kernel.org 应收到一份补丁副本。同时在补丁本身的标签中加上 "Cc: stable@vger.kernel.org"；这会让稳定团队在你的修复合入主线时收到通知

在为补丁选择收件人时，最好想清楚你认为最终会接受并合入该补丁的人是谁。虽然可以直接把补丁发给 Linus Torvalds 并让他合入，但通常不这样办。Linus 很忙，而且有子系统维护者照看着内核的特定部分。通常你会希望那位维护者来合入你的补丁。如果没有明显的维护者，Andrew Morton 常常是最后的兜底目标

补丁需要好的主题行。补丁行的规范格式类似这样：

```

	[PATCH nn/mm] subsys: one-line description of the patch

```
其中 "nn" 是补丁的序数mm" 是系列中补丁的总数subsys" 是受影响子系统的名称。显然，对单个独立的补丁可以省略 nn/mm

如果你有一系列重要的补丁，习惯上会作为第零部分发送一份介绍性描述。不过这个约定并非普遍遵循；如果你用了它，请记住介绍中的信息不会进入内核变更日志。所以请确保补丁本身具有完整的变更日志信息

一般而言，多部分补丁的第二及后续部分应当作为第一部分的回复发送，以便在接收端它们全部串在一起。像 git quilt 这样的工具有命令可以带正确的线索（threading）寄出一组补丁。不过，如果你有一长串系列并且使用 git，请避开 --chain-reply-to 选项，以免产生异常深的嵌套
