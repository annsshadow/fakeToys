### 代码
KVM x86 目前正处于从KVM 树的一部分转变为“又一KVM 架构”的过渡期。因此，KVM x86 分散在主 KVM `git.kernel.org/pub/scm/virt/kvm/kvm.git` 和一KVM x86 专用`github.com/kvm-x86/linux.git` 之间
一般来说，针对当前周期的修复会直接应用到主 KVM 树，而面向下一周期的所有开发则通过 KVM x86 树路由。在极少数情况下，如果针对当前周期的修复通过 KVM x86 树路由，它会先被应用`fixes` 分支，再进入KVM 树
注意，预计这段过渡期会持续相当长一段时间，即在可预见的未来将成为常态
#### 分支

KVM x86 树被组织成多个主题分支。使用更细粒度的主题分支的目的是，便于跟踪某个开发领域的进展，并限制人为错误或有缺陷提交的连带损害。例如，丢弃某个主题分支HEAD 提交不会影响其它在途提交的 SHA1 哈希；而因缺陷拒绝某个拉取请求只会使该主题分支延迟
`next` `fixes` 之外的所有主题分支，都会按需（即某个主题分支更新时）通过一Cthulhu 合并汇总进 `next`。因此，`next` 的强制推送很常见
#### 生命周期

针对当前版本（即 mainline）的修复通常直接应用到主 KVM 树，即不通过 KVM x86 树路由
面向下一版本的改动通过 KVM x86 树路由。拉取请求（KVM x86 到主 KVM）针对每KVM x86 主题分支发出，通常Linus 打开合并窗口前一周，例如“正常”发布在 rc7 之后那一周。如果一切顺利，这些主题分支会被汇总进 Linus 合并窗口期间发出的主 KVM 拉取请求中
KVM x86 树没有自己正式的合并窗口，但对于新功能大约在 rc5 有一个软截止，对于修复（针对下一版本；针对当前版本的修复见上文）大约rc6 有一个软截止
#### 时间
提交通常会按 FIFO（先进先出）顺序审阅并应用，对于大型系列、处于“缓存热点”的补丁等会留有一些灵活空间。修复（尤其是针对当前版本和/或稳定树的）可以插队。将通过KVM 树（最常是经过 tip 树）处理的和/或已获得其他 ack/review 的补丁也会在某种程度上插队
注意，绝大多数审阅工作在 rc1 rc6 之间完成，浮动少许。rc6 到下一rc1 之间的时段用于处理其它事务，即在此期间“无线电静默”并不少见
欢迎发ping 来获取状态更新，但要留意当前发布周期的时间点并保持合理预期。如果你是在 ping 询问是否会被接纳（即不只是反馈或更新），请在合理范围内尽一切努力确保你的补丁已准备好合并！对破坏构建或测试失败的补丁系列发ping 会让维护者不快！

### 开

#### 基础分支

针对当前版本（即 mainline）的修复应基`git://git.kernel.org/pub/scm/virt/kvm/kvm.git master`。注意，修复并不自动保证被纳入当前版本。没有单一的规则，但通常只有针对紧迫、关键和/或在当前版本中引入的缺陷的修复才应面向当前版本
其它所有改动都应基`kvm-x86/next`，即无需选择某个特定主题分支作为基础。如果存在跨主题分支的冲突和/或依赖，由维护者负责理清
使用 `kvm-x86/next` 作为基础的唯一例外是：某个补丁/系列是多架构系列，即对通用 KVM 代码有非平凡修改或对其它架构代码有不止表层的改动。多架构补丁/系列应改为基KVM 历史中一个公共的稳定点，例如 `kvm-x86 next` 所基于的发布候选版本。如果你不确定某个补系列是否真的是多架构的，宁可谨慎一些，将其当作多架构处理，即使用公共基础
#### 代码风格

在风格、命名、模式等方面，一致性是 KVM x86 的首要优先级。如果其它都行不通，就与已有代码保持一致
除下面列出的少数注意事项外，请遵tip 树维护者偏好的 maintainer-tip-coding-style，因为补系列常常同时触及 KVM 和非 KVM x86 文件，即会同时引KVM *** tip 树维护者的注意
变量声明使用反向圣诞树（reverse fir tree，又reverse Christmas tree reverse XMAS tree）并非严格要求，不过仍然推荐
除少数特例外，不要为函数使用 kernel-doc 注释。绝大多数“公开”的 KVM 函数并非真正公开，因为它们只KVM 内部使用（有计划KVM 的头文件与导出私有化以强制执行这一点）
#### 注释

使用祈使语气编写注释，避免代词。用注释提供代码的高层概览，或解释代码为何这样做。不要复述代码字面上在做什么；让代码自己说话。如果代码本身难以理解，注释也无济于事
#### SDM APM 引用

KVM 代码库的大部分与 Intel 的软件开发手册（SDM）和 AMD 的架构程序员手册（APM）中定义的架构行为直接相关。不加额外上下文地使用“Intel's SDM”和“AMD's APM”，甚至只写“SDM”或“APM”，都是完全可以的
不要按编号引用具体的节、表、图等，尤其是在注释中。相反，如有必要（见下文），请复制粘贴相关片段，并按名称引用图。SDM APM 的排版不断变化，因此编号/标签并不稳定
一般来说，不要在注释中显式引用或复制粘SDM APM 的内容。除少数例外，KVM **必须**遵守架构行为，因此隐含着 KVM 行为是在模拟 SDM APM 行为。注意，在变更日志中引用 SDM/APM 以证明改动的合理性并提供上下文是完全可以且被鼓励的
#### 简短日志（Shortlog
```
  - x86
  - x86/mmu
  - x86/pmu
  - x86/xen
  - selftests
  - SVM
  - nSVM
  - VMX
  - nVMX
```

**不要使用 x86/kvm* `x86/kvm` 专用于把 Linux 作为 KVM 客户机（guest）的改动，即用于 arch/x86/kernel/kvm.c。不要使用文件名或完整文件路径作为主简短日志前缀
注意，这些与主题分支并不对齐（主题分支更关心代码冲突）
所有名称都区分大小写！`KVM: x86:` 是好的，`kvm: vmx:` 则不是
将精简补丁描述的首词首字母大写，但省略结尾的：

```
    KVM: x86: Fix a null pointer dereference in function_xyz()
```

```
    kvm: x86: fix a null pointer dereference in function_xyz.
```

如果某个补丁触及多个主题，沿概念树向上查找第一个公共父节点（通常就是 `x86`）。拿不准时，`git log path/to/file` 应能提供合理的提示
新主题偶尔会出现，但如果你想提议引入新主题，请先在邮件列表中发起讨论，即不要擅自行动
更多相关信息请参the_canonical_patch_format，有一点修正：不要70-75 字符的限制当作绝对的硬性限制。相反，75 字符作为“坚定但非硬性”的限制，以 80 字符作为硬性限制。即，如果有充分理由，可以让简短日志超出标准限制几个字符
#### 变更日志（Changelog
最重要的是，使用祈使语气编写变更日志，避免代词
更多相关信息请参describe_changes，有一点修正：先以一段简短说明介绍实际改动，再补充上下文与背景。注意！这个顺序tip 树偏好的方式直接冲突！在发送主要面arch/x86 代码（且**不是** KVM 代码）的补丁时，请遵tip 树偏好的风格
KVM x86 偏好先说明“改了什么”，原因有几点。首要一点，究竟改了哪些代码可以说是最重要的信息，因此该信息应易于找到。把“实际改了什么”埋3 段以上的背景介绍之后、只用一句话带过的变更日志，会让这些信息极难找到
从初次审阅的角度看，有人会认为“哪里坏了”更重要，但对于快速浏览日志和 git 考古来说，繁琐的细节越来越不重要。例如在连续做“git blame”时，沿途每个改动的细节都毫无用处，细节只对“罪魁祸首”提交有意义。提供“改了什么”可以让人快速判断某个提交是否可能相关
先说明“改了什么”的另一个好处是，几乎总能用一句话说明“改了什么”。相反，除最简单的缺陷外，都需要多个句子或段落才能完整描述问题。如果“改了什么”和“缺陷是什么”都很短，顺序无关紧要。但如果其中一个更短（几乎总是“改了什么”），那么先覆盖较短的那个更有利，因为对于严格偏好某种顺序的读审阅者来说，不便之处更少。例如，跳过一句话去获取上下文，比跳过三段去找“改了什么”痛苦更小
#### 修复（Fixes
如果某个改动修复KVM/内核缺陷，请添加 Fixes: 标签，即使该改动不需要回移植到稳定内核，即使它修复的是更老版本中的缺陷
反之，如果一个修复确实需要回移植，请显式“Cc: stable@vger.kernel标记该补丁（不过邮件本身无需 Cc: stable）；KVM x86 默认选择不回移植 Fixes: 标记的改动。某些自动选中的补丁确实会被回移植，但需要维护者显式批准（搜索 MANUALSEL）
#### 函数引用

当在函数注释、变更日志、简短日志（或任何地方）提到某个函数时，使用 `function_name()` 格式。括号提供了上下文并消除引用的歧义
### 测试

最低限度，**所*系列中的补丁必须针对 KVM_INTEL=m、KVM_AMD=m KVM_WERROR=y 干净地构建。构建所有可能的 Kconfig 组合并不现实，但越多越好。KVM_SMM、KVM_XEN、PROVE_LOCKING X86_64 是特别值得拨动的旋钮
运行 KVM selftests KVM-unit-tests 也是强制性的（不言而喻，测试需要通过）。唯一的例外是那些 affecting 运行时行为概率可忽略的改动，例如只修改注释的补丁。在可行且相关时，强烈建议同时在 Intel AMD 上测试。鼓励启动一个真VM，但非强制
对于触及 KVM 影子分页代码的改动，必须在禁TDP（EPT/NPT）的情况下运行。对于影响通用 KVM MMU 代码的改动，强烈建议禁用 TDP 运行。对于所有其它改动，如果所修改的代码依赖和/或与某个模块参数交互，则必须使用相关设置进行测试
注意，KVM selftests KVM-unit-tests 确实存在一些已知失败。如果你怀疑某个失败不是由你的改动引起的，请验*完全相同**的失败在有和没有你的改动时都发生
触及 reStructured Text 文档（即 .rst 文件）的改动必须干净地构htmldocs，即不出现新的警告或错误
如果你无法完整测试某个改动（例如缺少硬件），请清楚说明你能够进行的测试程度，例如在封面信中说明
#### 新特
除一个例外，新特*必须**附带测试覆盖。KVM 专用测试并非严格要求，例如如果通过运行一个充分启用的客户VM、或VM 中运行相关的内核 selftest 来提供覆盖，但在所有情况下都优先采用专门的 KVM 测试。特别是，对于启用新硬件特性，负面测试用例是强制性的，因为错误和异常流程很少会仅通过运行一VM 就被触发
该规则唯一的例外是：KVM 只是通过 KVM_GET_SUPPORTED_CPUID 声明支持某个特性，即针KVM 无法阻止客户机使用、且不存在真正“启用”的指令/特性
注意，“新特性”并非仅指“新硬件特性”！无法用现KVM selftests KVM-unit-tests 充分验证的新特性必须附带测试
发布未经测试的新特性开发以尽早获得反馈是受到欢迎的，但此类提交应标记为 RFC，并在封面信中清楚说明请期望何种反馈。不要滥RFC 流程；RFC 通常不会收到深入审阅
#### 缺陷修复

除“显而易见”、通过代码审查发现的缺陷外，修复必须附带被修复缺陷的可复现方法。在很多情况下可复现方法是隐式的，例如构建错误和测试失败，但读者仍应清楚什么是坏的以及如何验证修复。对于通过非公开工作负载/测试发现的缺陷留有一定余地，但强烈建议为这类缺陷提供回归测试
一般来说，对于不易触发（hit）的任何缺陷，都优先提供回归测试。例如，即使缺陷最初由 syzkaller 之类的模糊测试器发现，如果触发该缺陷需要命中百万分之一级别的竞态条件，仍可能有必要提供有针对性的回归测试
注意，KVM 缺陷很少有既紧迫***难以复现的。在发布不带可复现方法的修复前，请先问问自己该缺陷是否真的到了世界末日的程度
### 发布


#### 链接

不要通过 `In-Reply-To:` 头显式引用缺陷报告、补系列的早期版本等。对于大型系列和/或版本号较高时，使用 `In-Reply-To:` 会陷入混乱；而且对于没有原始邮件的任何人，`In-Reply-To:` 毫无用处，例如有人没有被 Cc 到缺陷报告中，或者收件人列表在各版本之间发生了变化
要链接到缺陷报告、早期版本或任何感兴趣的内容，请使用 lore 链接。对于引用早期版本，一般来说不要在变更日志中包Link:，因为没有必要在 git 中记录历史，即把链接放在封面信或 git 忽略的段落中。但对于导致该补丁的缺陷报告或讨论，请务必提供正式的 Link:。为何做此改动对未来的读者极具价值
#### Git 基础

如果你使git 2.9.0 或更高版本（Google 的同事，说的就是你们！），请使用带有 `--base` 标志`git format-patch`，以在生成的补丁中自动包含基础树信息
注意，`--base=auto` 当且仅当某个分支upstream 被设置为基础主题分支时才会按预期工作，例如如果你upstream 是出于备份目的设置为你的个人仓库，它就会做错事。另一种“auto”方案是根据 KVM x86 主题来派生你的开发分支名称，并将其喂`--base`。例`x86/pmu/my_branch_name`，然后写一个小包装脚本从当前分支名中提`pmu`，得`--base=x/pmu`，其`x` 是你的仓库用来跟KVM x86 远程的名称
#### 同时发布测试

KVM 改动相关联的 KVM selftests（例如缺陷修复的回归测试）应作为一个系列与 KVM 改动一同发布。适用于二分（bisection）的标准内核规则同样适用，即导致测试失败KVM 改动应排selftests 更新之后，反之亦然，KVM 缺陷而失败的测试应排KVM 修复之后
KVM-unit-tests **应始*单独发布。诸b4 am 之类的工具并不知KVM-unit-tests 是一个独立的仓库，当系列中的补丁应用到不同树时会感到困惑。要KVM-unit-tests 补丁KVM 补丁关联起来，请先发KVM 改动，然后在 KVM-unit-tests 补丁中提供一个指KVM 补丁/系列lore Link:
### 通知

当某个补系列被正式接受时，会回复原始发布（多补丁系列的封面信）发送一封通知邮件。该通知会包含树与主题分支，以及被应用补丁提交的 SHA1
如果只应用了补丁的一个子集，通知中会明确说明。除非另有说明，未被接受的系列中任何补丁都隐含着需要更多工作，应作为新版本提交
如果某个补丁在正式接受后被丢弃，会向通知邮件回复说明丢弃原因以及后续步骤
#### SHA1 稳定
SHA1 在并Linus 的树之前并不100% 保证稳定！一旦发出通知，SHA1 **通常**是稳定的，但事情总有意外。在大多数情况下，如果被应用补丁SHA1 发生变化，会更新通知邮件。但在某些场景下（例如所KVM x86 分支都需要变基），不会逐一给出通知
### 漏洞

能够被客户机用来攻击宿主机（内核或用户空间）、或能够被嵌VM 用来攻击***宿主（L2 攻击 L1）的缺陷，是 KVM 特别关注的对象。如果你怀疑某个缺陷可能导致逃逸、数据泄露等，请遵循 securitybugs 协议
