## CVE


通用漏洞与暴露（CVE®）编号最初是作为识别、定义和编目公开披露的安全漏洞的一种明确方式来开发的。随着时间的推移，它们对于内核项目的用处已经下降，CVE 编号常常以不恰当的方式和不恰当的原因被分配。正因为如此，内核开发社区往往避免使用它们。然而，持续要求分配 CVE 以及其他形式的安全标识符的压力，加上内核社区之外的个人和公司不断的滥用，清楚地表明内核社区应该控制这些分配
Linux 内核开发团队确实有能力的为潜在Linux 内核安全问题分配 CVE。这种分配独立于 :doc:`正常Linux 内核安全漏洞报告流程<../process/security-bugs>`
所有已分配Linux 内核CVE 列表可以linux-cve 邮件列表的归档中找到，见 https://lore.kernel.org/linux-cve-announce/。要获取已分CVE 的通知，请 `订阅 <https://subspace.kernel.org/subscribing.html>`_ 该邮件列表
## 流程


作为正常稳定版发布流程的一部分，潜在的安问题由负责 CVE 编号分配的开发人员识别，并自动为它们分配 CVE 编号。这些分配会频繁地在 linux-cve-announce 邮件列表上作为公告发布
请注意，由于 Linux 内核在系统中所处的层级，几乎任bug 都可能被利用来危害内核的安全，但利用的可能性在修复 bug 时往往并不明显。因此，CVE 分配团队过于谨慎，对他们识别出的任何 bugfix 都分CVE 编号。这也解释了 Linux 内核团队看似发出了数量庞大的 CVE
如果 CVE 分配团队遗漏了某个任何用户认为应当分CVE 的具体修复，请通过 <cve@kernel.org> 给他们发邮件，那里的团队会与你合作处理。注意，任何潜在的安问题都不应发送到这个别名，它仅用于为已经合入已发布内核树的修复分CVE。如果你认为自己发现了未修复的安问题，请遵循 :doc:`正常Linux 内核安全漏洞报告流程<../process/security-bugs>`
对于 Linux 内核中未修复的安问题，不会自动分CVE；分配只会在修复可用并应用到稳定内核树之后自动发生，并通过原始修复git 提交 id 进行跟踪。如果任何人在问题通过提交解决之前就希望分CVE，请联系内核 CVE 分配团队 <cve@kernel.org>，从他们保留的标识符批次中获取一个标识符
对于 Stable/LTS 内核团队当前未主动支持的某个内核版本中发现的任何问题，都不会分配 CVE。当前受支持的内核分支列表可以在 https://kernel.org/releases.html 找到
## 对已分配 CVE 的争

对某个特定内核改动所分配 CVE 提出异议或修改的权力，完全属于受影响的相应子系统的维护者。这一原则确保了漏洞报告的高度准确性和责任可追溯性。只有那些对子系统有深入专业知识和充分了解的个人，才能有效评估所报告漏洞的有效性和范围，并确定其恰当的 CVE 指定。任何在此指定权限之外修改或争议 CVE 的尝试都可能导致混乱、不准确的报告，并最终导致系统受损
## 无效CVE


如果某个 Linux 内核中的安全问题仅因Linux 发行版所做的更改、或该发行版支持一个不再属kernel.org 受支持发布版本的内核版本而存在，那么CVE 不能Linux 内核 CVE 团队分配，而必须向Linux 发行版本身申请
任何由内核分CVE 团队以外的任何团体，针对一个受支持的内核版本分配给 Linux 内核CVE，都不应被视为有效的 CVE。请通过 <cve@kernel.org> 通知内核 CVE 分配团队，以便他们通过 CNA 补救流程使此类条目失效
## 特定 CVE 的适用

由于 Linux 内核可以以许多不同的方式使用，外部用户访问它的方式也各不相同，或者根本无法访问，因此任何特定 CVE 的适用性由 Linux 用户自行判断，而不CVE 分配团队决定。请不要联系我们来试图判断任何特CVE 的适用性
此外，由于源代码树非常庞大，而任何单一系统只使用源代码树的一小部分，任何 Linux 用户都应当意识到，大量已分配CVE 与他们的系统无关
简而言之，我们不知道你的使用场景，也不知道你使用了内核的哪些部分，因此我们无法判断某个特定 CVE 是否与你的系统相关
一如既往，最好采纳所有已发布的内核改动，因为它们作为一个统一的整体由许多社区成员一起测试，而不是作为单独挑选的改动。还要注意，对于许多 bug，整体问题的解决方案并不在于单一的改动，而在于许多修复的叠加。理想情况下，CVE 会分配给所有问题的所有修复，但有时我们会遗漏某些修复，因此请假设一些未分配 CVE 的改动也可能值得采纳
