
## embargo 的硬件问

### 范围


导致安全问题的硬件问题，与仅影响 Linux 内核的纯软件 bug 不同，属于不同类别的安全漏洞
Meltdown、Spectre、L1TF 等硬件问题必须区别对待，因为它们通常影响所有操作系统（"OS"），
因此需要跨不同的操作系统厂商、发行版、芯片厂商、硬件集成商以及其他各方进行协调。对于其一些问题，软件缓解措施可能依赖于微码或固件更新，而这就需要进一步的协调

### 联系方式


Linux 内核硬件安全团队与常规的 Linux 内核安全团队是分开的
该团队仅负责为受 embargo 的硬件安全问题开发修复方案。针Linux 内核中纯软件安全 bug 报告不由该团队处理，报告者会被引导去联系常规Linux 内核安全团队ref:`Documentation/admin-guide/
<securitybugs>`）代替
可以通过电子邮件 <hardware-security@kernel.org> 联系该团队。这是一个由安全官员组成的私有邮件列表，
他们将根据你文档化的流程帮助你协调修复方案
该列表是加密的，发送给列表的邮件可以使PGP S/MIME 加密，并且必须使用报告者的 PGP 密钥
S/MIME 证书签名。列表的 PGP 密钥S/MIME 证书可从以下 URL 获取
  - PGP: https://www.kernel.org/static/files/hardware-security.asc
  - S/MIME: https://www.kernel.org/static/files/hardware-security.crt

虽然硬件安全问题通常由受影响的芯片厂商处理，我们也欢迎已识别出潜在硬件缺陷的研究人员或个主动联系我们

### 保密协议


Linux 内核硬件安全团队并非正式机构，因此无法签订任何保密协议。内核社区意识到此类问题敏感性，转而提供一份谅解备忘录（Memorandum of Understanding）

### 璋呰В澶囧繕褰。

Linux 内核社区深刻理解在不同操作系统厂商、发行商、芯片厂商及其他各方之间协调时，将硬件安问题置于 embargo 之下的要求
Linux 内核社区过去已成功处理过硬件安全问题，并已具备必要的机制，以embargo 限制下允符合社区规范的开发
Linux 内核社区设有专门的硬件安全团队用于初始联系，该团队在 embargo 规则下监督此类问题的
处理流程
硬件安全团队会确定将组成特定问题初始响应团队的开发者（领域专家）。初始响应团队可以引入更开发者（领域专家），以最佳的技术方式解决问题
所有参与的开发者都承诺遵守 embargo 规则并对所收到的信息保密。违反承诺将导致被立即从该问中排除，并从所有相关邮件列表中移除。此外，硬件安全团队还会将该违规者排除在未来的问题之外这一后果的影响在我们的社区中是一种高度有效的威慑。如果发生违规，硬件安全团队将立即通知相关
各方。如果你或任何人察觉到潜在的违规，请立即报告给硬件安全官员

##### 流程


由于 Linux 内核开发的全球分布式特性，面对面会议几乎不可能用来解决硬件安全问题。电话会议由时区和其他因素难以协调，应仅在绝对必要时使用。加密电子邮件已被证明是处理此类问题最有效最安全的通信方式
###### 披露开

披露通过按照上文“联系方式”一节向 Linux 内核硬件安全团队发送电子邮件开始。此初始联系应包含对
问题的描述以及任何已知受影响的芯片列表。如果你的组织制造或分发受影响的硬件，我们也鼓励考虑还可能有哪些硬件会受影响。披露方负责及时联系受影响的芯片厂商
硬件安全团队将提供一个特定于该事件的加密邮件列表，用于与披露方进行初步讨论、进一步披露以协调修复
硬件安全团队将向披露方提供一份开发者（领域专家）名单，在经开发者确认他们将遵守本谅解备忘录
及文档化流程后，应首先被告知该问题。这些开发者组成初始响应团队，并将在初始联系后负责处理该问题硬件安全团队为响应团队提供支持，但不一定参与缓解措施的开发过程
虽然个别开发者可能通过其雇主受到保密协议约束，但他们不能以 Linux 内核开发者身份签订个保密协议。不过，他们将同意遵守本已文档化的流程与谅解备忘录
披露方应提供一份所有其他已被告知或应被告知该问题的实体的联系人列表。这有几个用途：

 - 已披露实体列表允许全行业通信，例如其他操作系统厂商、硬件厂商等
 - 已披露实体可以被联系以指名应当参与缓解措施开发的专家
 - 如果需要处理某个问题的专家受雇于或隶属于某个已列出的实体，则响应团队可以要求该实体披露该专家   这确保该专家也成为该实体响应团队的一员
###### 披露


披露方通过特定的加密邮件列表向初始响应团队提供详细信息
根据我们的经验，这些问题的技术文档通常已是充分的起点，进一步的技术澄清最好通过电子邮件完成
###### 缓解措施开

初始响应团队建立一个加密邮件列表，或在适当情况下重新利用一个已有的邮件列表
使用邮件列表接近于正常的 Linux 开发流程，并且在过去已成功用于为各种硬件安全问题开发缓解措施
邮件列表的运作方式与正常 Linux 开发相同。补丁被发布、讨论和审查，如果达成一致，则被应用一个非公开git 仓库，该仓库仅参与开发的开发者可通过安全连接访问。该仓库包含面向主线内核主开发分支，以及用于稳定内核版本（如需要）的后向移植分支
初始响应团队将根据需要识别来Linux 内核开发者社区的更多专家。任何参与方都可以建议纳入更专家，每位专家都将受到上述相同要求的约束
引入专家可以发生在开发过程中的任何时刻，并且需要及时处理
如果某位专家受雇于或由披露方提供的披露列表中的某个实体成员担任，则将向相关实体请求其参与
如果不是，则会将专家的参与情况告知披露方。这些专家受谅解备忘录约束，披露方被要求确认其参与如果披露方有令人信服的理由反对，任何反对必须在五个工作日内提出，并立即与事件团队解决。如披露方在五个工作日内未作回应，则视为默示确认
在事件团队确认或解决反对意见后，该专家被披露并纳入开发过程
列表参与者不得在私有邮件列表之外讨论该问题。列表参与者在处理补丁时不得使用任何共享资（例如雇主的构建集群、CI 系统等）
###### 提前访问


在列表上讨论和开发的补丁既不能分发给任何非响应团队成员的个人，也不能分发给任何其他组织
为了让受影响的芯片厂商能够与其内部团队和行业合作伙伴进行关于测试、验证和物流的工作，提供以下
例外
	受影响芯片厂商的指定代表被允许随时将补丁移交给该芯片厂商的响应团队。该代表必须就移	事宜通知内核响应团队。受影响芯片厂商必须拥有并维护其自己关于与响应团队共享的任何补丁	文档化安全流程，且该流程须与本策略一致
	芯片厂商的响应团队可以在其文档化的安全流程下，将这些补丁分发给其行业合作伙伴和内部团队	来自行业合作伙伴的反馈返回给芯片厂商，并由芯片厂商传达给内核响应团队
	将补丁移交给芯片厂商的响应团队，免除了内核响应团队因涉及芯片厂商内部团队或行业合作伙	而导致的提前披露的任何责任。芯片厂商通过同意此流程来保证这一责任豁免
###### 协调发布


相关各方将协embargo 结束的日期和时间。届时，准备好的缓解措施被发布到相关的内核树中。没预先通知流程：缓解措施是公开发布的，并在同一时间对所有人可用
虽然我们理解硬件安全问题需要协调的 embargo 时间，但 embargo 时间应限制在让所有相关方开发测试和准备其缓解措施所需的最短时间内。为了迎合会议演讲日期或其他非技术原因而人为延embargo
时间，会给相关的开发者和响应团队带来更多工作和负担，因为补丁需要保持更新以跟上正在进行的内上游开发，这可能会造成冲突性的变更
###### CVE 分配


硬件安全团队和初始响应团队都不分CVE，开发过程也不需CVE。如CVE 由披露方提供，则用于文档目的

### 加密邮件列表


我们使用加密邮件列表进行通信。这些列表的运作原则是：发送给列表的邮件要么使用该列表PGP 密钥
加密，要么使用该列表S/MIME 证书加密。邮件列表软件对邮件解密，然后使用订阅者的 PGP 密钥S/MIME 证书为每位订阅者单独重新加密。有关为确保列表安全性和数据保护而使用的邮件列表软件设置的详细信息，可在此处找到https://korg.wiki.kernel.org/userdoc/remail
##### 列表密钥


有关初始联系，请参见上文的“联系方式”一节。对于特定于事件的邮件列表，密钥S/MIME 证书由该
特定列表通过电子邮件传达给订阅者
##### 订阅特定于事件的列表


对特定于事件的列表的订阅由响应团队处理。希望参与通信的已披露各方向响应团队发送一份潜在专列表，以便响应团队验证订阅请求
每位订阅者都需要通过电子邮件向响应团队发送订阅请求。该邮件必须使用订阅者的 PGP 密钥S/MIME
证书签名。如果使PGP 密钥，它必须可从公钥服务器获取，并且理想情况下应连接Linux 内核PGP 信任网。另请参阅：https://www.kernel.org/signature.html
响应团队核实订阅请求的有效性，并将订阅者加入列表。订阅后，订阅者将收到来自邮件列表的邮件，邮件使用列表PGP 密钥或列表的 S/MIME 证书签名。订阅者的邮件客户端可以从签名中提PGP 密钥
S/MIME 证书，从而订阅者可以向列表发送加密邮件
