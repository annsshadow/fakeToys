## Linux 内核威胁模型

关于内核保护什么、不保护什么，存在大量假设。这些假设往往会导致错误报告（[安全相关的 <security-bugs>](security-related ones <security-bugs>) 与 :doc:`非安全相关的 <../admin-guide/reporting-issues>`）方面的混淆，并且当某些边界的责任在内核、发行版、管理员和用户之间不明确时，会使安全加固变得复杂。

本文档试图澄清内核在这一领域的责任。

### 内核的责任

内核以一种允许多个本地用户公平分享授予他们的可用资源、并且在底层硬件允许时为其通信以及他们正在处理或存储的数据赋予一定保密级别的方式，抽象了对本地硬件资源和远程系统的访问。

内核假设底层硬件按其规范运行。这包括 CPU 指令集的完整性、分支预测单元和缓存单元的透明性、内存管理单元（MMU）的一致性、DMA 能力外设的隔离（例如通过 IOMMU）、控制器中的状态转换、从寄存器读出的值的范围、对文档化硬件限制的遵守等。

当硬件未能维持其规定的隔离（例如 CPU bug、侧信道、对意外输入的硬件响应）时，内核通常会尝试实施合理的缓解措施。这些是最优努力（best-effort）措施，旨在在硬件设施的限制范围内缩小攻击面或提高攻击成本；它们并不构成内核提供的安全保证。

用户总是在管理员的授权下开展活动，管理员能够授予或拒绝可能影响用户如何从可用资源中受益、或其活动保密级别的各种类型的权限。管理员也可以将其自身权限的全部或部分委派给某些用户，特别是通过 capabilities（能力），但不限于此。所有这一切都是通过配置（sysctl、文件系统权限等）执行的。

Linux 内核应用了一组符合其威胁模型的默认设置。发行版有自己的威胁模型，并带有自己的配置预设，管理员可能需要对其进行调整以更好地符合其期望（放宽或收紧）。

默认情况下，当运行在具备特权级别和内存管理单元的常见处理器上时，Linux 内核保证以下保护：

- **基于用户的隔离**：非特权用户可以从运行在同一系统上的其他非特权用户那里限制对其自身数据的访问。这包括：

  - 存储的数据，通过文件系统权限
  - 内存中的数据（默认情况下其他用户不可访问页）
  - 进程活动（不允许其他用户 ptrace）
  - 进程间通信（其他用户不得观察通过 UNIX domain sockets 或其他 IPC 机制交换的数据）。
  - 与同一系统或其他系统之间的网络通信

- **基于能力的保护**：

  - 不具有提升的能力（包括但不限于 CAP_SYS_ADMIN）的用户不得更改内核的配置、内存或状态，不得更改其他用户对文件系统布局的视图，不得授予任何他们所没有的用户能力，也不得影响系统的可用性（关机、重启、panic、挂起，或通过无界资源耗尽使系统无响应）。
  - 不具有 `CAP_NET_ADMIN` 能力的用户不得更改网络配置，不得拦截或伪造来自其他用户或系统的网络通信。
  - 不具有 `CAP_SYS_PTRACE` 的用户不得观察其他用户的进程活动。

当设置了 `CONFIG_USER_NS` 时，内核还允许非特权用户创建自己的用户命名空间，在其中他们拥有所有能力，但有一些限制（他们不得执行对初始用户命名空间有影响的操作，例如更改时间、加载模块或挂载块设备）。更多细节请参阅 `user_namespaces(7)`，用户命名空间的可能性不在本文档覆盖范围内。

内核还提供大量故障排查和调试设施，在错误的人手中可能构成攻击向量。虽然其中一些设计为由具有低风险（例如通过 `/proc/kmsg` 的内核日志）的普通本地用户访问，但有些会暴露足够的信息，在大多数地方构成风险，而是否暴露它们由管理员负责（perf events、traces），其他一些则并非设计为由非特权用户访问（例如 debugfs）。被管理员显式授予权限的用户访问这些设施不构成安全漏洞。

允许违反上述原则的 bug 构成安全漏洞。然而，只有在另一个漏洞已经被利用后才能实施一次违规的 bug 仅仅是弱点（weaknesses）。内核应用了若干自我保护措施，其目的是在发现某些类别的 bug 时避免跨越安全边界，但这些额外保护的失败本身并不构成漏洞。

### 什么不构成安全 bug

在 Linux 内核的威胁模型中，以下类别的问题**不**被视为 Linux 内核安全 bug。但是，当认为内核可以做得更好时，仍应报告它们，以便在合理可能的情况下对其进行审查和修复，但它们将作为任何常规 bug 来处理：

- **配置**：

  - 过时的内核，特别是已到生命周期终点的分支，不在内核威胁模型的范围内：管理员负责保持其系统为最新。一个 bug 要够格成为安全 bug，必须证明它影响积极维护的版本。

  - 构建级别：对内核配置中显式记录为降低安全级别（例如 `CONFIG_NOMMU`）或仅面向开发者的更改。

  - 操作系统级别：对命令行参数、sysctls、文件系统权限、用户能力、特权接口的暴露的更改，这些更改通过向非特权用户提供非默认访问，或降低内核强制执行某些保护或缓解措施的能力，显式增加了暴露面。例如：对 procfs 或 debugfs 的写访问。

  - 仅在使用面向开发或调试的功能（例如 LOCKDEP、KASAN、FAULT_INJECTION）时触发的问题：已知这些功能会引入开销和潜在的不稳定性，并非用于生产。

  - 影响在 `CONFIG_STAGING` 下暴露的驱动以及配置中标记为 EXPERIMENTAL 的功能的问题。

  - 加载显式不安全/损坏/暂存（staging）的模块，以及通常使用任何标记为实验性或非用于生产的子系统。

  - 运行树外（out-of-tree）模块或非官方内核 fork；这些应报告给相关供应商。

- **初始权限过度**：

  - 已经拥有执行该操作或修改该状态所需权限（例如 `CAP_SYS_ADMIN`、`CAP_NET_ADMIN`、`CAP_SYS_RAWIO`、`CAP_SYS_MODULE`，且不再跨越其他边界）的用户执行的操作。

  - 在用户命名空间中执行、且不绕过对初始用户施加的限制的操作（例如 ptrace 使用、信号投递、资源使用、对 FS/device/sysctl/memory 的访问、网络绑定、系统/网络配置等）。

  - 初始命名空间中 root 用户执行的任何操作（例如写入特权设备时内核 oops）。

- **非生产使用**：

  这涵盖了依赖零系统噪声的实验室条件，或需要不现实尝试次数（例如数十亿次试验）的理论/概率性攻击，这些攻击在标准系统监控发现之前很久就会被检测到，例如：

  - 仅在完全静默环境（例如 IP ID、TCP 端口或只能在实验室中猜出的序列号）中才有效的随机数预测。

  - 基于概率方法的活动观察和信息泄漏，这些方法容易产生测量噪声，并且在生产系统上无法实际复现。

  - 只能被重度攻击（例如暴力破解）触发、且其影响使得在成功之前不太可能或不可能保持未被检测到的问题（例如在成功前耗尽所有内存）。

  - 仅在开发模拟器、仿真器或报告时不真实存在的组合下才出现的问题（涉及数千万线程、数万 CPU、不现实的 CPU 频率、RAM 大小或磁盘容量、网络速度的问题）。

  - 其复现需要硬件修改或仿真的问题，包括伪装成另一种设备的伪造 USB 设备。

  - 以及以远高于预期收益的成本才能触发的问题（例如仅为了取回结构中 7 个未初始化字节的完整功能键盘仿真器，或涉及数百万次连接尝试以猜测端口号的暴力方法）。

- **加固失败**：

  - 能够绕过内核某些加固措施、但没有可证明利用路径的能力（例如 ASLR 绕过、无任何可证明后果的事件计时或探测）。这些都只是弱点，不是漏洞。

  - 缺少参数检查以及未能报告某些错误，且无直接后果。

- **随机信息泄漏**：

  这涉及恰好存在且攻击者无法选择、或面临访问限制的小部分数据的泄漏：

  - 由 syscalls 或其他接口报告的结构体填充（padding）。

  - 在错误消息中报告的标识符、部分数据、未终止的字符串。

  - 内核内存地址/指针的泄漏并不构成可直接利用的向量，也不是安全 bug，尽管它们必须被报告并修复。

- **精心构造的文件系统映像**：

  - 由挂载损坏或恶意构造的文件系统映像触发的 bug 通常不算安全 bug，因为内核假设底层存储介质处于管理员控制之下，除非文件系统驱动被特别记录为针对不受信任的介质进行了加固。

  - 通过在挂载前对映像运行文件系统一致性检查（fsck）来解决、缓解或检测到的问题。

- **物理访问**：

  需要物理访问机器、硬件修改，或使用专门硬件（例如逻辑分析仪、通过 PCI-E/Thunderbolt 的 DMA 攻击工具）的问题不在范围内，除非系统被显式配置了旨在防御此类攻击的技术（例如 IOMMU）。

- **功能与性能回归**：

  任何可以通过设置适当权限和限制来缓解的问题都不够格成为安全 bug。
