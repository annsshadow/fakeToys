
## 早期规划


当考虑一个 Linux 内核开发项目时，很可能会直接跳进去开始编码。然而，与任何重要项目一样，许多成功的根基最好是在写下第一行代码之前就打下。在早期规划和沟通上花一点时间，能在日后省下多得多的工夫。


### 明确问题


与任何工程项目一样，一个成功的内核改进始于对所要解决的问题的清晰描述。在某些情况下，这一步很容易：比如当某个特定硬件需要一个驱动程序时。但在另一些情况下，很容易把真正的问题和所提议的解决方案混为一谈，而这可能导致麻烦。

考虑一个例子：几年前，从事 Linux 音频开发的开发人员在寻找一种方法，让应用程序运行时不出现因系统延迟过大而导致的卡顿或其他 artifacts。他们最终给出的解决方案是一个打算挂入 Linux 安全模块（Linux Security Module，LSM）框架的内核模块；该模块可被配置为让特定的应用程序访问实时调度器。这个模块被实现并发送到了 linux-kernel 邮件列表，在那里立刻遇到了麻烦。

对音频开发人员来说，这个安全模块足以解决他们的燃眉之急。但对更广泛的内核社区而言，这被视为对 LSM 框架的滥用（该框架本意并非向进程授予它们原本不会拥有的特权），并且是对系统稳定性的一种风险。他们偏好的解决方案是：短期通过 rlimit 机制获得实时调度访问权限，长期则持续开展降低延迟的工作。

然而，音频社区无法超越他们所实现的那个特定解决方案去看待问题；他们不愿接受替代方案。由此产生的分歧让那些开发人员对整个内核开发流程感到幻灭；其中一人回到一个音频列表并贴出了下面这段话：

	有许多非常优秀的 Linux 内核开发人员，但他们往往会被一大群傲慢的蠢货用更大的嗓门盖过。试图向这些人传达用户需求是在浪费时间。他们太“聪明”了，根本听不进凡人的意见。

(https://lwn.net/Articles/131776/)。

实际情况却不同；与某个特定模块相比，内核开发人员更关心系统稳定性、长期维护，以及为问题找到正确的解决方案。这个故事的寓意是：把重点放在问题上——而不是某个具体的解决方案上——并在投入编写一大堆代码之前，先与开发社区讨论这个问题。

所以，在考虑一个内核开发项目时，应当先得到一组简短问题的答案：

 - 究竟需要解决的是什么问题？

 - 受此问题影响的用户是谁？解决方案应当覆盖哪些使用场景？

 - 内核现在在解决该问题上还差在哪里？

只有在这之后，才开始考虑可能的解决方案。


### 早期讨论


在规划一个内核开发项目时，在开始实施之前与社区展开讨论是非常明智的。早期沟通可以通过多种方式节省时间和麻烦：

 - 很可能内核已经以你所不了解的方式解决了这个问题。Linux 内核十分庞大，拥有许多并不一目了然的特性和能力。并非所有内核能力都得到了人们所期望的那样完善的文档，因而很容易漏掉一些东西。本文作者就见过有人贴出一个完整的驱动程序，结果重复了原作者并不知道的某个已有驱动。重新发明已有轮子的代码不仅是浪费；它也不会被主线内核接受。

 - 所提议的解决方案中，可能包含一些不适合并入主线的要素。这类问题最好在写代码之前就发现。

 - 完全有可能其他开发人员已经思考过这个问题；他们或许有更好的解决方案的想法，并且可能愿意帮忙创建那个方案。

与内核开发社区打交道的多年经验带来一个明确的教训：闭门设计和开发出来的内核代码总是存在一些问题，这些问题只有在代码发布到社区时才会暴露出来。有时这些问题相当严重，需要数月乃至数年的努力才能让代码达到内核社区的标准。一些例子包括：

 - Devicescape 网络栈是为单处理器系统设计和实现的。在使其适用于多处理器系统之前，它无法被合并进主线。往代码里 retrofit（改造）加锁之类的东西是一项困难的任务；结果，这段代码（现在称为 mac80211）的合并被推迟了一年多。

 - Reiser4 文件系统包含了许多能力，而在核心内核开发人员看来，这些能力本应在虚拟文件系统层实现。它还包含了一些特性，若不把系统暴露在由用户引起的死锁之下便难以实现。这些问题暴露得过迟——且拒绝解决其中一些问题——导致 Reiser4 至今仍被挡在主线内核之外。

 - AppArmor 安全模块以被认为不安全也不可靠的方式使用了内部虚拟文件系统数据结构。这种担忧（以及其他一些）让 AppArmor 多年无法进入主线。

在以上每个案例中，如果能与内核开发人员做些早期讨论，大量的痛苦和额外工作本都可以避免。


### 找谁交流？


当开发人员决定把他们的计划公开时，下一个问题便是：我们从哪里开始？答案是找到正确的邮件列表和正确的维护者。对于邮件列表，最好的办法是在 MAINTAINERS 文件中寻找一个相关的发布位置。如果存在一个合适的子系统列表，那么在那里发帖通常优于发在 linux-kernel 上；你更有可能触达在相关子系统方面具有专长的开发人员，而且环境也可能更友好。

找到维护者可能会更难一些。同样，MAINTAINERS 文件是起点。不过，该文件往往并不总是最新的，也并非所有子系统都在其中有记录。事实上，MAINTAINERS 文件中列出的人，可能并非当前实际担任该角色的人。所以，在对该联系谁有疑问时，一个有用的技巧是使用 git（尤其是 `git log`）来查看谁目前在你感兴趣的子系统中活跃。看看谁在编写补丁，以及谁（如果有的话）在这些补丁上附上了 Signed-off-by 行。这些人就是最有条件帮助一个新开发项目的人。

找到合适维护者的任务有时颇具挑战性，以至于内核开发人员专门加了一个脚本来简化这个过程：

```

	.../scripts/get_maintainer.pl

```
当给定 "-f" 选项时，此脚本会返回指定文件或目录当前的维护者。如果在命令行上传入一个补丁，它会列出那些大概应当收到该补丁副本的维护者。这是获取你的补丁应当抄送（Cc）的人员列表的首选方式（与 "-f" 选项不同）。get_maintainer.pl 有许多调节其搜索维护者积极程度的选项；请小心使用那些更激进的选项，因为你最终可能会把一些对你所修改的代码并无真正兴趣的开发人员也包含进来。

如果一切办法都不奏效，与 Andrew Morton 交流往往是追踪某段特定代码的维护者的有效途径。


### 何时发布？


如果可能，在早起阶段发布你的计划只有好处。描述正在被解决的问题，以及关于实现方式已制定的任何计划。你能提供的任何信息都能帮助开发社区为该项目提供有用的意见。

在这个阶段可能发生的一件令人沮丧的事，不是遭到敌意回应，而是几乎或完全没有回应。令人遗憾的真相是：（1）内核开发人员往往很忙，（2）不乏有宏大计划却鲜有代码（甚至代码的影子）来支撑的人，（3）没有人有义务去审查或评论他人发布的想法。除此之外，高层设计常常隐藏着一些问题，只有在某些人真正尝试实现这些设计时才会暴露；因此，内核开发人员宁可看到代码。

如果一篇征求意见稿（request-for-comments，RFC）的发布没能得到多少评论，不要认为这意味着项目无人感兴趣。不幸的是，你同样不能假设你的想法没有问题。这种情况下最好的做法是继续推进，并随时让社区了解你的进展。


### 获得官方认可


如果你是在企业环境中工作——就像大多数 Linux 内核工作那样——显然，在你能把公司的计划或代码发布到公共邮件列表之前，必须获得拥有相应权限的经理的许可。发布那些尚未被清点为可在与 GPL 兼容的许可证下发布的代码，问题尤其严重；公司的管理层和法律人员越早能就发布一个内核开发项目达成一致，对所有相关方就越好。

一些读者此时或许在想，他们的内核工作是为了支持一个尚未被官方承认存在的产品。在公共邮件列表上透露雇主的计划可能并不是一个可行的选项。在这种情况下，值得考虑保密是否真的必要；往往并没有真正的必要把开发计划藏在紧闭的门后。

话虽如此，也有一些情况是公司确实无法在开发流程早期披露其计划。拥有经验丰富内核开发人员的公司，可能会选择以一种“开环”的方式推进，前提是他们认为日后能够避免严重的集成问题。对于没有这种内部专业知识的公司，最好的选择往往是聘请一位外部开发人员，依据保密协议（non-disclosure agreement）审查这些计划。Linux 基金会运营着一个 NDA（保密协议）计划，旨在帮助应对这类情况；更多信息可在以下位置找到：

    https://www.linuxfoundation.org/nda/

这类审查通常足以避免日后出现严重问题，而无需公开披露项目。
