
## 高级主题


此时，希望您已经对开发流程的运作方式有了把握。不过，还有更多东西要学！本节将介绍若干主题，它们对希望成为 Linux 内核开发流程中常规一员的开发人员会有所帮助。

### 使用 Git 管理补丁


内核对分布式版本控制的使用始于 2002 年初，当时 Linus 首次开始试用专有的 BitKeeper 应用。尽管 BitKeeper 颇有争议，但它所体现的软件版本管理方法却绝非如此。分布式版本控制让内核开发项目立刻提速。如今，已有若干 BitKeeper 的免费替代品。无论好坏，内核项目已经选定 git 作为它的首选工具。

使用 git 管理补丁可以让开发人员的生活轻松得多，尤其是当补丁数量增长时。Git 也有它粗糙的棱角和某些隐患；它是一个年轻而强大的工具，其开发者们仍在使之趋于完善。本文档不会尝试教读者如何使用 git；那本身都够写一篇长篇文档了。相反，这里的重点将特别放在 git 如何融入内核开发流程上。希望熟悉 git 的开发人员可以在以下位置找到更多信息：

	https://git-scm.com/

	https://www.kernel.org/pub/software/scm/git/docs/user-manual.html

以及网络上形形色色的教程。

第一要务，是在尝试用 git 把补丁提供给他人之前，先阅读上述站点，对 git 的工作方式建立扎实的理解。一个使用 git 的开发人员应当能够获取一份主线仓库的副本、浏览修订历史、向树中提交改动、使用分支等。理解 git 用于改写历史（例如 rebase）的工具也很有用。Git 带有自己的术语和概念；git 的新用户应当了解 refs、远程分支、索引（index）、快进合并（fast-forward merge）、推送与拉取、分离头（detached head）等。一开始可能有点吓人，但稍加学习，这些概念并不难掌握。

在熟悉的过程中，用 git 生成通过电子邮件提交的补丁不失为一个好练习。

当你准备好开始建立供他人查看的 git 树时，当然需要一个可以被拉取的服务器。如果你有一台可以访问互联网的系统，用 git-daemon 搭建这样的服务器相对简单。否则，免费的公共托管站点（例如 GitHub）正开始在网络上出现。资深的开发人员可以在 kernel.org 上获得一个账号，但那些账号并不容易拿到；更多信息参见 https://kernel.org/faq/ 。

正常的 git 工作流会用到大量分支。每条开发线都可以分离成一个独立的“主题分支”（topic branch）并独立维护。Git 中的分支很廉价，没有理由不自由地使用它们。而且，无论如何，你都不应该在任何你打算请他人从中拉取的分支里做开发。公开可用的分支应当谨慎创建；只有当开发分支中的补丁已成形、准备就绪时才将其合并进来——而不是在此之前。

Git 提供了一些强大的工具，让你能够改写自己的开发历史。一个不方便的补丁（比如一个破坏了二分（bisection）查找、或带有其他某种明显 bug 的补丁）可以就地修复，或者让它彻底从历史中消失。一个补丁系列可以被改写得好似它是基于今天的主线写就的，哪怕你已经为之工作了数月。改动可以在分支之间透明地转移。诸如此类。审慎地使用 git 改写历史的能力，有助于打造出问题更少的干净补丁集。

不过，过度使用这种能力除了会让人单纯痴迷于打造“完美项目历史”之外，还可能导致其他问题。改写历史就会改写该历史中所包含的改动，把一棵（但愿）经过测试的核树变成未经测试的。此外，如果开发人员没有共享的项目历史视图，他们就很难协作；如果你改写了其他开发人员已经拉入其仓库的历史，就会让那些开发人员的生活困难得多。所以这里适用一条简单的经验法则：被导出给他人的历史，此后通常应被视为不可变的。

因此，一旦你把一组改动推送到公开可用的服务器上，这些改动就不应当再被改写。如果你试图推送那些无法构成快进合并（即不共享同一段历史）的改动，git 会尝试强制执行这条规则。这一检查是可以被覆盖的，有时也确实需要改写一棵已导出的树。在树之间移动变更集以避免 linux-next 中的冲突，就是一个例子。但这类行为应当罕见。这也是为什么开发应当在私有分支中进行（必要时可改写），并且只有在公共分支已达到相当advanced的状态时才移入其中的原因之一。

当主线（或一组改动所基于的其他树）向前推进时，很容易通过与之合并来保持在最前沿。对于私有分支，rebase 可以是一种轻松跟上另一棵树的方法，但一旦一棵树被导出给外界，rebase 就不再是一个选项。一旦发生了这种情况，就必须做一次完整的合并（merge）。偶尔合并颇有意义，但过于频繁的合并会不必要地弄乱历史。这种情况下的建议做法是：不要频繁合并，通常只在特定的发布节点（例如主线 -rc 发布）合并。如果你对某些特定改动感到没把握，随时可以在私有分支里做测试性合并。Git 的 “rerere” 工具在这种情形下会很有用；它能记住合并冲突是如何被解决的，这样你就不必重复同样的工作。

关于 git 这类工具，最大的反复出现的抱怨之一是：补丁从一个仓库到另一个仓库的大规模移动，使得一些欠考虑、并避开了审查雷达进入主线的改动很容易溜进去。当内核开发人员看到这类事情发生时，他们往往会不高兴；挂出一棵包含未经审查或离题补丁的 git 树，会影响你日后让树被拉取的能力。引用 Linus 的话：

```

	You can send me patches, but for me to pull a git patch from you, I need to know that you know what you're doing, and I need to be able to trust things *without* then having to go and check every individual change by hand.

```
(https://lwn.net/Articles/224135/)。

为避免这类情况，请确保给定分支中的所有补丁都紧扣相关主题；“驱动修复”分支不该去改动核心内存管理代码。而且，最重要的是，不要用 git 树来绕过审查流程。不时把该树的摘要发布到相关列表上，并在时机合适时，请求将该树纳入 linux-next。

如果他人开始发送补丁要求并入你的树，别忘了审查它们。同时，确保你维护了正确的作者信息；git 的 “am” 工具在这方面做得最好，但如果补丁是经由第三方转发给你的，你可能需要在补丁中加一个 “From:” 行。

请求拉取时，务必给出所有相关信息：你的树在哪里、要拉取哪个分支、以及这次拉取会带来哪些改动。git 的 request-pull 命令在这方面会很有帮助；它会按其他开发人员所期望的格式格式化请求，并且会检查确认你已经记得把这些改动推送到了公共服务器上。


### 审阅补丁


一些读者无疑会反对把本节和“高级主题”放在一起，理由是即便初学的内核开发人员也应当审阅补丁。当然，没有比查看他人贴出的代码更好的方式来学习如何在内核环境中编程了。此外，审阅者永远供不应求；通过查看代码，你就能对整个流程做出重大贡献。

审查代码可能是一副令人生畏的前景，尤其对一个很可能会对公开质疑那些更有经验的人所贴代码而感到紧张的新内核开发人员来说。不过，即便是最有经验的开发人员写的代码，也仍有改进的余地。也许对所有审阅者（无一例外）最好的建议是：把审阅意见表述成问题，而不是批评。问“在这条路径上锁是如何被释放的？”总是比说“这里的加锁是错的”效果更好。

当出现分歧时，另一个有用的技巧是邀请他人参与讨论。如果几轮交流后讨论陷入僵局，那就去征求其他审阅者或维护者的意见。通常，与某位审阅者意见一致的人会保持沉默，除非被点名。多人意见的分量会成倍地更重。

不同的开发人员会从不同的视角审查代码。有些人主要关注编码风格，以及代码行是否带有尾随空格。另一些人主要关注补丁整体所实现的改动对内核是否是件好事。还有一些人会检查是否存在有问题的加锁、过度的栈使用、可能的安全问题、与别处重复的代码、是否文档充分、对性能的不利影响、用户空间 ABI 变更等。所有类型的审阅，只要能引导更好的代码进入内核，都受到欢迎、都值得。

并没有严格要求必须使用像 `Reviewed-by` 这样的特定标签。事实上，即便提供了标签，也更鼓励用平实的英文撰写评审意见，因为这样的内容信息量更大，例如“我查看了此次提交中 A、B、C 等方面的内容，认为没有问题。”显然，以某种形式提供评审信息或回复是必要的，否则维护者将完全无从知晓评审者是否看过这个补丁！

最后但同样重要的是，补丁评审可能会变成一个聚焦于指出问题的负面过程。请偶尔给予称赞，尤其是对新手贡献者！
