## (濡備綍閬垮厤) 鎶?ioctl 鎼炵牳

From: https://blog.ffwll.ch/2013/11/botching-up-ioctls.html

By: Daniel Vetter, Copyright 漏 2013 Intel Corporation

内核图形黑客在过去几年里获得的一个清晰认识是：试图为在完全不同的 GPU 上管理执行单元和内存提出一个统一的接口，是一项徒劳的努力。所以如今每个驱动都有自己的一ioctl 来分配内存并GPU 提交工作。这挺好，因为不再有那种伪通用、实际上却只用过一次的接口的荒唐做法。但明显的缺点是，搞砸事情的潜在可能大得多了
为了避免重复犯下所有同样的错误，我把在drm/i915 驱动干活时（把事情搞砸的过程中）学到的一些经验教训写了下来。这些教训大多只涉及技术细节，而不涉及大局问题，比如命令提ioctl 究竟应该长什么样。学习这些教训大概每GPU 驱动都得自己来
### 先决条件

首先是先决条件。没有这些，你已经失败了，因为你将需要添加一32 位兼容层
 - 只使用固定大小的整数。为了避免与用户空间typedef 冲突，内核有`__u32`、`__s64` 这样的特殊类型。使用它们
 - 对所有内容按自然大小对齐，并使用显式填充2 位平台不一定要64 位值对齐到 64 位边界，64 位平台会。因此我们总是需要填充到自然大小以做到正确
 - 如果结构包含 64 位类型，则把整个结构填充64 位的倍数——否则结构大小在 32 位与 64 位上会不同。当向内核传递结构数组时，或者内核检查结构大小时（例drm core 就会这样做），结构大小不同会带来麻烦
 - 指针`__u64`，在用户空间侧与 `uintptr_t` 相互转换，在内核中与 `void __user *` 相互转换。真的要努力不要推迟这种转换，更不要将原始的 `__u64` 在你的代码中传来传去，因为那样会减少sparse 这样的检查工具所能提供的帮助。内核中的宏 `u64_to_user_ptr` 可用于避免关于不同大小的整数和指针的警告
### 基础

既然避免了编写兼容层的乐趣，我们就可以看看基本的失误。忽视这些会让向前和向后的兼容性变得非常痛苦。而且由于第一次尝试就做错是必然的，你将对任何给定的接口进行第二次迭代，或至少一次扩展
 - 为用户空间提供一种清晰的方法，来判断你的ioctl ioctl 扩展在给定的内核上是否受支持。如果你不能依赖旧内核拒绝新的标模式ioctl（因为过去就是这么搞砸的），那么你需要在某处有一个驱动特性标志或修订号
 - 为用新标志或结构末尾的新字段来扩ioctl 制定计划。drm core 在每ioctl 调用时检查传入的大小，并对内核与用户空间之间的任何不匹配进行零扩展。这有帮助，但并非完整的解决方案，因为在旧内核上的较新用户空间不会注意到末尾新添加的字段被忽略了。所以这仍然需要新的驱动特性标志
 - 检查所有未使用的字段、标志以及所有填充是否为 0，如果不是则拒绝ioctl。否则你对未来扩展的美好计划就会付诸东流，因为有人会提交一个在尚未使用的部分包含随机栈垃圾ioctl 结构。这就会ABI 固定下来：那些字段除了装垃圾之外永远不能用于任何其他用途。这也是为什么你必须显式填充所有结构，即使你从不在数组中使用它们——编译器可能插入的填充可能包含垃圾
 - 为上述所有内容准备简单的测试用例
### 错误路径的乐
如今我们没有任何借口再让 drm 驱动成为整洁的小 root 提权漏洞了。这意味着我们既需要完整的输入验证，也需要可靠的错误处理路径——无论如何，GPU 最终会在最奇特的边角情况中死掉
 - ioctl 必须检查数组溢出。它还需要检查整数值的溢出/下溢和钳位（clamping）问题。通常的例子是 sprite 定位值被直接喂给硬件，而硬件只有约 12 位。在有些古怪的显示服务器不自己做钳位、光标在屏幕上绕回之前，这都工作得很好
 - ioctl 中每个输入验证失败的情况准备简单的测试用例。检查错误码是否符合你的预期。最后，确保每个子测试只测试单一的错误路径，方法是提交其他方面完全有效的数据。没有这一点，一个更早的检查可能就已经拒绝了该 ioctl，从而遮蔽了你真正想测试的代码路径，隐藏 bug 和回归
 - 让你所有的 ioctl 可重启。首X 真的喜欢信号，其次这将允许你仅仅通过用信号不断中断你的主测试套件，就测试到约 90% 的所有错误处理路径。多X 对信号的热爱，你几乎免费就能为图形驱动获得所有错误路径的优秀基础覆盖。同时，在你处理 ioctl 重启的方式上要保持一致——例drm 在其用户空间库中有一个小小的 drmIoctl 辅助函数。i915 驱动set_tiling ioctl 上搞砸了这一点，现在我们永远被困在内核和用户空间双方一些晦涩的语义中
 - 如果你无法让某个给定的代码路径可重启，至少让卡住的任务可被杀死。GPU 就是会死，而如果你的用户整个机器都挂了（通过一个不可杀死的 X 进程），他们不会更喜欢你。如果状态恢复仍然太棘手，就用一个超时或 hangcheck 安全网作为最后的努力，以防硬件发了疯
 - 为你的错误恢复代码中真正棘手的边角情况准备测试用例——在 hangcheck 代码和等待者之间制造死锁实在太容易了
### 时间、等待与错过
GPU 几乎一切都异步进行，所以我们需要为操作计时并等待未完成的操作。这真的很棘手；目前 drm/i915 支持的所ioctl 没有一个能完全做对，这意味着这里还有大量教训要学
 - 始终使用 `CLOCK_MONOTONIC` 作为你的参考时间。这是如alsa、drm v4l 默认使用的。但要让用户空间知道哪些时间戳派生自不同的时钟域，比如你的主系统时钟（由内核提供）或其他某处的独立硬件计数器。如果看得足够仔细，时钟会不匹配，但如果性能测量工具拥有这些信息，它们至少可以进行补偿。如果你的用户空间能拿到某些时钟的原始值（例如通过命令流中的性能计数器采样指令），也考虑把这些暴露出来
 - 使用 `__s64` 秒加`__u64` 纳秒来指定时间。这不是最方便的时间指定方式，但它基本是标准
 - 检查输入的时间值是否已归一化，如果不是则拒绝它们。注意内核原生的 `struct ktime` 对秒和纳秒都使用有符号整数，所以这里要当心
 - 对于超时，使用绝对时间。如果你是个好同志，并且让你ioctl 可重启，相对超时往往太粗略，并且由于每次重启时的取整可能无限延长你的等待时间。尤其是当你的参考时钟是像显示帧计数器这样真正缓慢的东西时。戴上规范律师的帽子，这不算 bug，因为超时总是可以延长的——但如果你的漂亮动画因此开始卡顿，用户肯定会恨你
 - 考虑放弃任何带超时的同步等待 ioctl，而是在一个可 poll 的文件描述符上交付一个异步事件。它更契合事件驱动应用程序的主循环
 - 为边角情况准备测试用例，特别是已经完成的事件、成功等待和超时等待的返回值是否都合理并符合你的需要
### 资源泄漏，不
一个完整的 drm 驱动本质上实现了一个小OS，但专门面向给定GPU 平台。这意味着一个驱动需要向用户空间暴露大量用于不同对象和其他资源的句柄。正确地做到这一点也有它自己的一小套陷阱
 - 始终把你动态创建的资源的生命周期绑定到一个文件描述符的生命周期上。如果你的资源需要跨进程共享，考虑使用 1:1 映射——通过 unix domain sockets 传fd 也简化了用户空间的生命周期管理
 - 始终支持 `O_CLOEXEC`
 - 确保你在不同的客户端之间有充分的隔离。默认选择一个私有的fd 命名空间，强制任何共享都显式进行。只有当对象真正是设备唯一的时，才使用更全局的每设备命名空间。drm modeset 接口中的一个反例是，像连接器这样的每设modeset 对象与帧缓冲对象共享一个命名空间，而帧缓冲对象大多根本不被共享。一个独立的、默认私有的帧缓冲区命名空间本会更合适
 - 思考用户空间句柄的唯一性要求。例如，对于大多drm 驱动，在同一个命令提ioctl 中两次提交同一个对象是用户空间bug。但如果对象可共享，用户空间就需要知道它是否已经从另一个进程见过一个导入的对象。由于缺少一类新对象，我自己还没试过这个，但考虑使用你共享文件描述符上的 inode 号作为唯一标识符——真正的文件也是这么区分的。不幸的是，这需要在内核中有一个完整的虚拟文件系统
### 最后，但并非最不重
并非每个问题都需要一个新ioctl
 - 认真想想你是否真的想要一个驱动私有接口。当然，推行一个驱动私有接口比就一个更通用的解决方案进行漫长讨论要快得多。偶尔，为了开辟一个新概念而做一个私有接口也是必要的。但到头来，一旦通用接口出现，你将无限期地维护两个接口
 - 考虑 ioctl 之外的其他接口。sysfs 属性对于每设备设置，或生命周期相当静态的子对象（比如 drm 中带有所有检测覆盖属性的输出连接器）要好得多。或者也许只有你的测试套件需要这个接口，那么带有“没有稳ABI”声明的 debugfs 会更好
最后，游戏的名字是在第一次尝试时就做对，因为如果你的驱动证明受欢迎、并且你的硬件平台寿命长，那么你将基本上永远被给定的 ioctl 困住。你可以尝试在硬件的较新迭代上弃用糟糕的 ioctl，但这通常要花数年才能完成。然后再过数年，直到最后一个能够对回归发牢骚的用户也消失
