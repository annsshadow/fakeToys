
## 向后移植与冲突解

    :local:
    :depth: 3

## 简


有些开发者在日常工作中可能从不需要处理向后移植补丁、合并分支或解决冲突，因此当合并冲突真的发生时，可能会令人望而生畏。幸运的是，解决冲突和任何其他技能一样，并且有许多有用的技巧可以让这个过程更顺畅，并增强你对结果的信心

本文档旨在成为一份关于向后移植与冲突解决的全面、逐步指南

## 将补丁应用到代码


有时你要向后移植的补丁已经是一git 提交，这种情况下你只需`git cherry-pick` 直接 cherry-pick 它。但如果补丁来自一封邮件（Linux 内核的补丁通常如此），你就需要用 `git am` 把它应用到代码树

如果你用`git am`，你可能已经知道它对补丁必须完美地应用到源码树上这件事相当挑剔。事实上，你大概做过关于 `.rej` 文件、并试图编辑补丁使其能应用的噩梦

强烈建议改为找一个合适的基版本本，让补丁能够干净地应用，****然后****再把cherry-pick 到你的目标树，因为这git 会输出冲突标记，并让你借助 git 以及你偏好的任何其他冲突解决工具来解决冲突。例如，如果你想把一个刚发到 LKML 的补丁应用到较旧的稳定内核，可以先把它应用到最新的主线内核，再 cherry-pick 到你的旧稳定分支

一般来说，最好使用与生成该补丁时完全相同的基版，但只要它能干净地应用、且与原始基版相差不太远，其实关系也不大。把补丁应用到“错误”基版的唯一问题是：当你把它 cherry-pick 到较旧分支时，可能会diff 的上下文中带入更多不相关的改动

比起 `git am`，更倾向`git cherry-pick` 的一个好理由是：git 知道一个已有提交的精确历史，因此当代码被移动过、行号被改变时它也能知晓；这反过来使得补丁被应用到错误位置的可能性降低（错误位置可能导致静默的错误或混乱的冲突）

如果你使`b4`_，并且是直接从邮件应用补丁，你可以使`b4 am`，配`-g`/`--guess-base` `-3`/`--prep-3way` 选项来自动完成其中一部分（更多信息参`b4 presentation`_）。不过，本文其余部分将假设你在进行一个普通的 `git cherry-pick`

一旦你把补丁纳入了 git，就可以继续把它 cherry-pick 到你的源码树。如果你想要一份关于补丁来源的书面记录，别忘了带上 `-x` 进行 cherry-pick

注意，如果你正在stable 提交补丁，格式会略有不同；主题行之后的第一行需要是

```

    commit <upstream commit> upstream

```
```

    [ Upstream commit <upstream commit> ]

```
## 解决冲突


```

    CONFLICT (content): Merge conflict

```
现在该怎么办？

一般来说，当补丁的上下文（即被修改的行或改动周围的行）与你试图把补丁应******的树中的内容不匹配时，就会出现冲突

对于向后移植，可能发生的情况是：你从中移植的分支包含了目标分支中没有的补丁。但反过来也有可能。无论哪种情况，结果都是一个需要解决的冲突

如果你的 cherry-pick 尝试因冲突而失败，git 会自动编辑文件，加入所谓的冲突标记，向你显示冲突在哪里、两个分支是如何分叉的。解决冲突通常意味着以一种兼顾了这些其他提交的方式来编辑最终结果

解决冲突既可以在普通文本编辑器中手工完成，也可以使用专门的冲突解决工具

许多人更喜欢使用他们常用的文本编辑器直接编辑冲突，因为这可能更容易理解自己在做什么、也更容易控制最终结果。每种方法无疑都有其优缺点，有时两者结合使用也很有价值

我们在这里不介绍专用合并工具的使用，只给出一些你可能会用到的工具的指引：

### 前置补丁


大多数冲突的发生，是因为你要移植*******的分支，相比你从中移植的分支，缺少了某些补丁。在更一般的情况下（例如合并两个独立的分支），开发可能发生在任意一个分支上，或者分支只是简单地分叉了——也许你的旧分支上应用过一些其他的向后移植，而它们本身就需要解决冲突，从而导致了分叉

始终找出导致冲突的那个或那些提交非常重要，否则你无法对解决方案的正确性有信心。作为额外的好处，尤其是当补丁位于你不太熟悉的领域时，这些提交的改变日志往往会给你提供理解代码、以及理解你的冲突解决方案中潜在问题或陷阱所需的上下文

#### git log


好的第一步是查看发生冲突文件`git log`——当该文件的补丁不多时这通常足够，但如果文件很大且频繁被打补丁，就可能会让人困惑。你应当在当前检出的分支（`HEAD`）与
```

    git log HEAD..<commit>^ -- <path>

```
的父提交之间的提交范围上运行 `git log`
更好的是，如果你想把输出限制到单个函数（因为冲突就出现在那里），可以使用下面
```

    git log -L:'\<function\>':<path> HEAD..<commit>^

```
     `\<` `\>` 围绕函数名，确保匹配锚定在单词边界上。这很重要，因为这一部分实际上是一个正则表达式，git 只取第一个匹配；所以如果你使用 `-L:thread_stack:kernel/fork.c`，它可能只给出函`try_release_thread_stack_to_cache` 的结果，即使该文件中还有许多其他函数名里包含字符`thread_stack`

`git log` 另一个有用的选项`-G`，它可以让你筛选那些提diff 中出现某些字符串的提交：
```

    git log -G'regex' HEAD..<commit>^ -- <path>

```
这也是快速找出某事物（例如一次函数调用或一个变量）何时被修改、添加或删除的方便方法。搜索字符串是一个正则表达式，这意味着你可以潜在地搜索
```

    git log -G'\->index\>.*='

```
#### git blame


找到前置提交的另一种方法（尽管对给定冲突只能找到最近的一个）是运`git blame`。在这种情况下，你需要针对你要移植的补丁的父提交运行它：
```

    git blame <commit>^ -- <path>

```
这个命令也接`-L` 参数（用于将输出限制到单个函数），但在这种情况下你要指定文件名：
```

    git blame -L:'\<function\>' <commit>^ -- <path>

```
导航到冲突发生的地方。blame 输出的第一列是添加某一行代码的补丁的提ID

`git show` 这些提交，看看它们是否像是冲突的来源，可能是个好主意。有时会有不止一个这样的提交，原因可能是多个提交修改了同一冲突区域的不同行***或***是因为多个后续补丁多次修改了同一行（或几行）。在后一种情况下，你可能需要再次运`git blame`，并指定文件的较旧版本来查看，以便进一步回溯该文件的历史

#### 前置补丁 vs. 偶发性补


找到导致冲突的补丁后，你需要判断它是你要移植的补丁的前置条件，还是仅仅偶发、可以跳过。偶发性补丁是指接触了与你要移植的补丁相同的代码，但并未以任何实质性方式改变代码语义的补丁。例如，空白清理补丁完全是偶发的——同样，仅仅重命名一个函数或变量的补丁也是偶发的。另一方面，如果要修改的函数在你的当前分支中根本不存在，那这就完全不是偶发的，你需要仔细考虑是否应当cherry-pick 那个添加该函数的补丁

如果你发现存在一个必要的前置补丁，那么你需要停下来，改cherry-pick 那个。如果你已经在另一个文件中解决了一些冲突、又不想再做一遍，可以创建该文件的临时副本

要中止当前的 cherry-pick，直接运`git cherry-pick --abort`，然后用前置补丁的提ID 重新启动 cherry-pick 过程

### 理解冲突标记


#### 组合 diff


假设你已决定不再挑选（或回退）额外的补丁，而只想解决冲突。Git 会把冲突标记插入到你的文件中。默认情况下，它看起来像
```

    <<<<<<< HEAD
    this is what's in your current tree before cherry-picking
    =======
    this is what the patch wants it to be after cherry-picking
    >>>>>>> <commit>... title

```
这就是你在编辑器中打开文件时会看到的内容。然而，如果你不带任何参数地运行 `git diff`，则
```

    $ git diff
    [...]
    ++<<<<<<<< HEAD
     +this is what's in your current tree before cherry-picking
    ++========
    + this is what the patch wants it to be after cherry-picking
    ++>>>>>>>> <commit>... title

```
在你解决冲突时，`git diff` 的行为与其正常行为不同。注意有两列 diff 标记，而不是通常的一列；这就是所谓的“`combined diff`_”，这里显示的是以下三者之间的 3 diff（或 diff-of-diffs）：

#. 当前分支（cherry-pick 之前）与当前工作目录，以
#. 当前分支（cherry-pick 之前）与原始补丁应用后文件的外观

#### 更好diff
3 路组diff 包含了你的当前分支与cherry-pick 来源分支之间，发生在该文件上的所有其他改动。虽然这对于发现你需要考虑的其他改动很有用，但这也`git diff` 的输出显得有些吓人、难以阅读。你可能反而更愿意运行 `git diff HEAD`（或 `git diff --ours`），它只显示 cherry-pick 之前的当前分支与当前工作区之间的 diff
```

    $ git diff HEAD
    [...]
    +<<<<<<<< HEAD
     this is what's in your current tree before cherry-picking
    +========
    +this is what the patch wants it to be after cherry-picking
    +>>>>>>>> <commit>... title

```
如你所见，这读起来就像任何其他 diff，并且清楚地表明哪些行在当前分支中，哪些行是因为合并冲突或正cherry-pick 的补丁而被加入的

#### 合并风格diff3


上面显示的默认冲突标记风格被称为 `merge` 风格。还有另一种可用的风格，称`diff3`
```

    <<<<<<< HEAD
    this is what is in your current tree before cherry-picking
    ||||||| parent of <commit> (title)
    this is what the patch expected to find there
    =======
    this is what the patch wants it to be after being applied
    >>>>>>> <commit> (title)

```
如你所见，它有 3 部分而不2 部分，并且包含了 git 原本期望在那里找到、却没有找到的内容***强烈推荐****使用这种冲突风格，因为它能让补丁实际改动了什么更加清晰；也就是说，它让你可以比较你要 cherry-pick 的提交在文件修改前和修改后的版本。这能让你对如何解决冲突做出更好的决策

```

    git config merge.conflictStyle diff3

```
还有第三个选项 `zdiff3`，在 `Git 2.35`_ 中引入，它与 `diff3` 拥有相同3 个部分，但会裁掉公共行，在某些情况下使冲突区域更小

### 迭代冲突解决


任何冲突解决过程的第一步，都是理解你要移植的补丁。对Linux 内核来说这尤其重要，因为一处不正确的改动可能导致整个系统崩溃——或更糟，导致一个未被发现的安全漏洞

理解补丁可能容易也可能困难，这取决于补丁本身、改变日志，以及你对所改代码的熟悉程度。不过，对每个改动（或补丁的每个 hunk）都可以问一个好问题：“为什么这hunk 会在补丁里？”这些问题的答案将指引你的冲突解决

#### 解决过程


有时最简单的做法，就是只保留冲突的第一部分，去掉其余部分，让文件基本保持不变，然后手工应用改动。也许补丁把一个函数调用参数从 `0` 改成`1`，而一个冲突的改动在参数列表末尾添加了一个全新（且无关紧要）的参数；在这种情况下，手工把参数`0` 改成 `1`、而把其余参数原样保留就足够容易了。这种手工应用改动的技巧，在冲突带入了大量你其实不需要关心的无关上下文时最为有用

对于带有许多冲突标记、特别棘手的冲突，你可以使用 `git add` `git add -i` 有选择地暂存你的解决方案，把它们从眼前挪开；这也让你可以使`git diff HEAD` 随时查看还有哪些待解决，或者使`git diff --cached` 查看你的补丁目前是什么样子

#### 处理文件重命


向后移植补丁时最令人恼火的事情之一，就是发现某个被打补丁的文件已被重命名，因为这通常意味着 git 甚至不会放入冲突标记，而是直接摊手说（ paraphrase）：“未合并路径！你来干活……

一般有几种植来处理这种情况。如果要打补丁的重命名文件改动很小，比如只有一行改动，最简单的做法就是直接手工应用改动，然后了事。另一方面，如果改动很大或很复杂，你肯定不想手工做

作为第一步，你可以尝试类似这样的做法，它会把重命名检测阈值降30%（默认情况下 git 使用 50%，意味着两个文件需要至少有 50% 相同，git 才会认为
```

  git cherry-pick -strategy=recursive -Xrename-threshold=30

```
有时正确的做法是也把执行重命名的补丁向后移植，但这绝对不是最常见的情况。相反，你可以做的是：在你移******的分支中临时重命名该文件（使`git mv` 并提交结果），重新尝cherry-pick 该补丁，再把文件重命名回去（`git mv` 并再次提交），最后用 `git rebase -i` 把结果压缩（参见 `rebase tutorial`_），这样在你完成时它看起来就像单个提交

### 陷阱


#### 函数参数


注意变化的函数参数！很容易忽略细节，以为两行相同，但实际上它们在某个小细节上不同，比如哪个变量被作为参数传入（尤其是当两个变量都是看起来相同的单字符，比i j 时）

#### 错误处理


如果cherry-pick 了一个包`goto` 语句（通常用于错误处理）的补丁，绝对必须仔细检查目标标签在你移植到的分支中是否仍然正确。对于新增的 `return`、`break` `continue` 语句也是如此

错误处理通常位于函数的底部，因此即使它可能被其他补丁改动过，它也可能不是冲突的一部分
确保你审查错误路径的一个好办法，是在检查改动时总是使用 `git diff -W` `git show -W`（又`--function-context`）。对C 代码，这会显示补丁中所改动的整个函数。向后移植时经常出错的一点是：在你要移植自或移植到的任一分支上，函数里的其他内容发生了变化。通过diff 中包含整个函数，你能获得更多上下文，并更容易发现那些否则可能被忽略的问题

#### 重构过的代码


相当常见的情况是，代码通过把一个公共的代码序列或模式“提取”成一个辅助函数而被重构。当向后移植补丁到一个已经发生过这种重构的区域时，你在移植时实际上需要做相反的事：对单个位置的补丁，可能需要应用到向后移植版本中的多个位置。（这种情况的一个征兆是函数被重命名了——但也不总是如此。）

为了避免不完整的向后移植，值得尝试弄清楚该补丁修复bug 是否出现在不止一处。一种做法是使用 `git grep`。（这实际上是个普遍的好主意，不仅限于向后移植。）如果你确实发现同一种修复也适用于其他地方，还值得看看这些地方在上游是否存在——如果不存在，那么该补丁很可能需要被调整。`git log` 是弄清楚这些区域发生了什么的好帮手，因为 `git blame` 不会显示已被删除的代码

如果你确实在上游树中发现了同一模式的其他实例，且不确定它是否也是一bug，那么问问补丁作者是值得的。在向后移植过程中发现新 bug 并不罕见

## 验证结果


### colordiff


提交了一个无冲突的新补丁后，你现在可以把你的补丁与原始补丁进行比较。强烈建议你使用诸如 `colordiff`_ 这样的工具，它可以并排显示两个文件并
```

    colordiff -yw -W 200 <(git diff -W <upstream commit>^-) <(git diff -W HEAD^-) | less -SR

```
进行着色

这里，`-y` 表示做并排比较；`-w` 忽略空白；`-W 200` 设置输出宽度（否则默认使130，这通常有点太小）

`rev^-` 语法`rev^..rev` 的便捷简写，本质上只给你那单个提交的 diff；另见官方的 `git rev-parse documentation`_

同样，注意为 `git diff` 包含 `-W`；这确保你能看到任何已改动函数的完整函数体

colordiff 做的一件极其重要的事，是突出显示不同的行。例如，如果一个错误处理的 `goto` 在原始补丁和向后移植补丁之间更改了标签，colordiff 会把它们并排显示，但用不同的颜色高亮。因此，很容易看出两`goto` 语句跳转到了不同的标签。同样，两个补丁都没有修改、但在上下文中存在差异的行也会被高亮，从而在人工检查时凸显出来

当然，这还只是视觉检查；真正的测试是构建并运行被打补丁的内核（或程序）

### 构建测试


我们在这里不介绍运行时测试，但只构建补丁触及的文件作为快速健全性检查是个好主意。对Linux 内核，你可以像这样构建单个文件，前提是你已经设置
```

    make path/to/file.o

```
注意这不会发现链接错误，因此你仍应在确认单个文件能编译后做一次完整构建。通过先编译单个文件，你可以在****万一****你改动过的任何文件中存在编译错误时，避免等待一次完整构建

### 运行时测


即便是成功的构建或启动测试，也未必足以排除某处缺失依赖的可能。尽管可能性很小，但可能存在这样的代码改动：对同一文件的两个独立改动导致既没有冲突、也没有编译期错误，并且只在例外情况下出现运行时错误

一个具体的例子是一对针对系统调用入口代码的补丁，其中第一个补丁保恢复了某个寄存器，而后一个补丁在这个序列中间的某处使用了同一个寄存器。由于改动之间没有重叠，你可cherry-pick 第二个补丁而没有任何冲突，并相信一切正常，而实际上代码现在正在覆写一个未保存的寄存器

尽管绝大多数错误会在编译期间或被对代码的表层执行所捕获，但****真正****验证一次向后移植的唯一方法，是以你对待（或应当对待）任何其他补丁的同等的审查力度来审查最终的补丁。拥有单元测试、回归测试或其他类型的自动测试，有助于提高对向后移植正确性的信心

## stable 提交向后移植


stable 维护者尝试把主线修复 cherry-pick 到他们的稳定内核时，遇到冲突时他们可能会发出邮件请求向后移植，例如见
<https://lore.kernel.org/stable/2023101528-jawed-shelving-071a@gregkh/>銆。
这些邮件通常包含你需要把补丁 cherry-pick 到正确树并提交该补丁的确切步骤

有一件要确保的事是，你的改变日志符合预期
```

  <original patch title>

  [ Upstream commit <mainline rev> ]

  <rest of the original changelog>
  [ <summary of the conflicts and their resolutions> ]
  Signed-off-by: <your name and email>

```
“Upstream commit”行有时会根
```

  commit <mainline rev> upstream.

```
而略有不
最常见的做法是，在邮件主题行中指明补丁所适用的内核版本（例如使用
`git send-email --subject-prefix='PATCH 6.1.y'`），但你也可以把它放Signed-off-by: 区域，或
`---` 行之下

stable 维护者期望针对每个活跃的稳定版本分别提交，并且每次提交也应当分别测试

## 最后的几点建议


1) 以谦逊的态度对待向后移植过程
2) 理解你要移植的补丁；这意味着既要读改变日志，也要读代码
3) 提交补丁时，诚实地说明你对结果的信心程度
4) 向相关维护者请求明确的 ack
