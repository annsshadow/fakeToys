
## 鎶婁唬鐮佸啓瀵。


虽然对于一个扎实且面向社区的设计流程有太多可说的，但任何内核开发项目的证明都在
于最终产生的代码。正是代码将被其他开发者审查，并（或不会被）合并进主线树。所以，
正是这段代码的质量将决定项目的最终成败

本节将考察编码过程。我们将从内核开发者可能出错的若干方式开始。然后重点将转向
把事情做对，以及在此过程中能提供帮助的工具

### 陷阱


######## 编码风格


内核长期以来有一个标准的编码风格，在 Documentation/process/coding-style.rst <codingstyle>
中有描述。在那段大部分时间里，该文件中描述的策略最多只被视为建议性的。结果，内核
有相当数量的代码不符合编码风格指南。这些代码的存在给内核开发者带来了两个独立的危害

其中第一个是相信内核编码标准无关紧要、也不被强制执行。事实是，如果代码不是按照标
编写的，把新代码加入内核是非常困难的；许多开发者甚至会要求先把代码重新格式化，然后
才愿意审查它。像内核这样庞大的代码库需要某种程度的代码统一性，才能让开发者快速理
它的任何部分。所以，再也没有奇怪格式代码的容身之地了

偶尔，内核的编码风格会与雇主强制规定的风格发生冲突。在这种情况下，在内核能够合
之前，内核的风格必须胜出。把代码放进内核意味着在若干方面放弃一定程度的控制——包
对代码如何格式化的控制

另一个陷阱是假设内核中已有的代码急需编码风格的修复。开发者可能开始生成重新格式化
补丁，作为熟悉流程的一种方式，或者作为让自己的名字进入内核变更日志的方式——或两
兼而有之。但是纯粹的编码风格修复被开发社区视为噪音；它们往往会受到冷淡的对待。所
最好避免这类补丁。在出于其他原因处理一段代码时顺带修复它的风格是很自然的，但风
改动不应为了改动本身而做

编码风格文档也不应被解读为永远不可违背的绝对律法。如果有充分的理由违背风格（例如
一行如果拆开以符80 列限制会变得远不易读），就那样做吧

注意，你也可以使`clang-format` 工具来帮助你遵循这些规则，快速自动重新格式化
代码的各个部分，并审查整个文件以发现编码风格错误、拼写错误和可能的改进。它在排
`#includes`、对齐变宏、重排文本以及其他类似任务方面也很方便。更多细节请参阅文件
Documentation/dev-tools/clang-format.rst <clangformat>銆。

一些基本的编辑器设置，如缩进和行尾，如果你使用的是兼容 EditorConfig 的编辑器，会
自动设置。更多信息请参阅官方 EditorConfig 网站
https://editorconfig.org/

######## 鎶借薄灞。


计算机科学教授教导学生大量使用抽象层，以追求灵活性与信息隐藏。当然，内核大量使用
抽象；任何涉及几百万行代码的项目若不如此就无法生存。但经验表明，过度或过早的抽
可能与过早优化一样有害。抽象应该用到所需的程度，不能再多

在一个简单的层面上，考虑一个函数，它有一个参数，所有调用者都总是传零。有人可能会
保留那个参数，以防将来有人最终需要它所提供的额外灵活性。但到那时，实现这个额外参数
的代码很可能已经以某种从未被注意到的方式微妙地坏掉了——因为它从未被使用过。或者，
当对额外灵活性的需求出现时，它出现的方式并不符合程序员早期的预期。内核开发者会例行
地提交补丁来移除未使用的参数；一般来说，它们一开始就不应被添加

隐藏对硬件访问的抽象层——常常是为了让驱动的大部分能在多个操作系统上使用——尤
不受待见。这样的层使代码模糊，并可能带来性能损失；它们不属于 Linux 内核

另一方面，如果你发现自己从另一个内核子系统复制了大量代码，那么是时候问问，把其
一些代码提取到一个单独的库、或者在更高的层级实现该功能，是否实际上更有意义。在整个
内核中复制相同的代码没有任何价值

######## #ifdef 与前处理器的一般使


C 前处理器似乎对有C 程序员呈现出一种强大的诱惑，他们把它视为一种把大量灵活
高效地编码进源文件的方式。但前处理器不是 C，重度使用它会导致代码对其他读者来说更
阅读，对编译器来说更难检查正确性。重度使用前处理器几乎总是一个需要清理工作的代码
标志

#ifdef 进行条件编译确实是一个强大的特性，并且它在内核中被使用。但人们几乎不想
看到洒满 #ifdef 块的代码。作为一般规则，#ifdef 的使用应该尽可能限制在头文件中
条件编译的代码可以限制在一些函数中，如果代码本不应存在，这些函数就简单地变成空的
编译器随后会悄悄地优化掉对那个空函数的调用。结果是干净得多的代码，也更易于跟踪

C 前处理器宏带来若干危害，包括可能对带有副作用的表达式进行多次求值，以及没有类型
安全。如果你忍不住想定义一个宏，考虑改为创建一个内联函数。产生的代码将是一样的，但
内联函数更易读、不会对参数求值多次，并且允许编译器对参数和返回值进行类型检查

######## 内联函数


不过，内联函数本身也带来一种危害。程序员可能会迷恋于避免一次函数调用所固有的、感
到的效率，从而用一个又一个内联函数填满源文件。然而，那些函数实际上可能降低性能。由
它们的代码在每个调用点被复制，它们最终膨胀了编译后内核的大小。这反过来给处理器的
内存缓存造成压力，可能急剧拖慢执行。作为规则，内联函数应该相当小，并且相对罕见
毕竟，一次函数调用的代价并没有那么高；创建大量内联函数是过早优化的典型例子

一般来说，内核程序员忽视缓存效应是要自担风险的。在初级数据结构课上讲授的经典的时间/
空间权衡，常常不适用于当代硬件。空*就是**时间，因为一个更大的程序会比更紧凑的程序
运行得更慢

较新的编译器在决定一个给定函数是否真的应该被内联方面，扮演着越来越积极的角色。所
随意地放"inline" 关键字可能不仅是过度的；它还可能是无关紧要的

######## 加锁


2006 5 月，"Devicescape" 网络协议栈在巨大的宣传下，以 GPL 发布，并可用于合并进
主线内核。这份捐赠是受欢迎的消息；当Linux 对无线网络的支持充其量被认为是不达标
Devicescape 协议栈承诺修复那种状况。然而，这段代码实际上直2007 6 月（2.6.22
才进入主线。发生了什么？

这段代码显示出许多在公司门内开发的迹象。但一个特别大的问题是，它没有被设计成能在
多处理器系统上工作。在这个网络协议栈（现在mac80211）能被合并之前，需要给它加
一套加锁方案

曾几何时，Linux 内核代码可以在不考虑多处理器系统带来的并发问题的情况下开发。然而现在，
本文档是在一台双核笔记本上写就的。即使在单处理器系统上，为改善响应性而做的工作也
提高内核内的并发水平。可以不考虑加锁就写内核代码的时代早已过去

任何可能被多个线程并发访问的资源（数据结构、硬件寄存器等）都必须由一把锁保护。新代码
应该带着这个要求来编写；事后加装锁是一项相当困难得多的任务。内核开发者应该花时间充分
理解可用的加锁原语，以便为工作挑选正确的工具。显示出对并发缺乏关注代码，要进入主
会举步维艰

######## 回归（Regressions


值得提及的最后一个危害是：做一个会导致已有用户某些东西坏掉的改动（可能带来巨大
改进）是诱人的。这种改动被称为“回归（regression）”，而回归在主线程内核中已变得最不受
欢迎。除了少数例外，如果回归不能及时修复，导致回归的改动将被回退。最好在最初就避免
回归

人们常常争辩说，如果一个回归能让它起作用的人数多于它制造问题的人数，那它就是有道理的
如果它每弄坏一个系统就能为十个系统带来新功能，为什么不做这个改动？对这个问题最好的
回答Linus 2007 7 月表达的

```

	So we don't fix bugs by introducing new problems.  That way lies
	madness, and nobody ever knows if you actually make any real
	progress at all. Is it two steps forwards, one step back, or one
	step forward and two steps back?

```
(https://lwn.net/Articles/243460/)銆。

一种尤其不受欢迎的回归类型，是对用户空ABI 的任何改动。一旦一个接口被导出到用户空间，
它就必须被无限期支持。这个事实使得创建用户空间接口格外具有挑战性：由于它们不能以不兼容
的方式被改变，它们必须一次就做对。出于这个原因，对于用户空间接口，总是需要大量的思考
清晰的文档和广泛的审查

### 代码检查工


至少就现在而言，写出无错代码仍然是我们中很少有人能达到的理想。不过，我们能希望做的是
在我们的代码进入主线内核之前，尽可能多地捕获并修复那些错误。为此，内核开发者组装了一
组令人印象深刻的工具，它们能以自动化的方式捕获各种各样的隐蔽问题。任何被计算机捕获的
问题，都是一个将来不会折磨用户的问题，因此自动化工具理应在可能时总是被使用

第一步仅仅是留意编译器产生的警告。当代版本的 gcc 能检测（并警告）大量潜在的错误
这些警告常常指向真实的问题。提交审查的代码，作为规则，不应产生任何编译器警告。在消除
警告时，要小心理解真正的原因，并尽量避免那种不解决原因就让警告消失的“修复”

注意，并非所有编译器警告默认都是开启的。用 "make KCFLAGS=-W" 构建内核以获得全部警告

内核提供了若干打开调试功能的配置选项；其中大多数位于 "kernel hacking" 子菜单中。其
几个选项应该为任何用于开发或测试目的的内核打开。特别是，你应该打开

 - FRAME_WARN 以获得对大于给定数量的栈帧的警告。产生的输出可能很冗长，但无需担心来自
   内核其他部分的警告

 - DEBUG_OBJECTS 会添加代码来跟踪内核创建的各种对象的生命周期，并在事情乱序进行时
   警。如果你正在添加一个创建（并导出）它自己复杂对象的子系统，考虑添加对对象调
   基础设施的支持

 - DEBUG_SLAB 能发现各种内存分配和使用错误；它应该用于大多数开发内核

 - DEBUG_SPINLOCK、DEBUG_ATOMIC_SLEEP DEBUG_MUTEXES 会发现若干常见的加锁错误

还有相当多的其他调试选项，其中一些将在下面讨论。其中一些有显著的性能影响，不应一
使用。但花些时间学习可用的选项，很可能会在短期内得到许多倍的回报

较重量的调试工具之一是加锁检查器，或"lockdep"。这个工具会跟踪系统中每个锁（自旋锁
或互斥体）的获取和释放、锁相对于彼此被获取的顺序、当前的中断环境等等。然后它能确保锁
总是以相同顺序被获取、相同的中断假设在所有情况下都成立，等等。换句话说，lockdep 能发
若干种系统偶尔可能死锁的情形。这种问题在一个已部署的系统中可能是痛苦的（对开发者和
用户都是），lockdep 允许它们在事前以自动化的方式被发现。任何带有任何非平凡加锁
代码，在提交合并之前，都应该在启lockdep 的情况下运行

作为一个勤勉的内核程序员，你无疑会检查任何可能失败的操作用（例如内存分配）的返回状态
但事实是，产生的失败恢复路径很可能完全未被测试。未测试的代码往往是坏掉代码；如果所
那些错误处理路径都被执行过几次，你会对你的代码更有信心

内核提供了一个故障注入框架，它正好能做这件事，特别是在涉及内存分配的地方。启用故障注
后，一个可配置百分比的内存分配会被强制失败；这些失败可以限制在特定范围的代码中。在启用
故障注入的情况下运行，让程序员看到当情况变糟时代码如何响应。关于如何使用这个设施的
更多信息，请参阅 Documentation/fault-injection/fault-injection.rst

其他种类的错误可以用 "sparse" 静态分析工具发现。有sparse，程序员可以被警告用户空
和内核空间地址之间的混淆、大端和小端量的混合、在期望一组位标志的地方传递整数值，等等
Sparse 必须单独安装（如果你的发行版没有打包它，可以https://sparse.wiki.kernel.org/index.php/Main_Page
找到）；然后可以通过在你make 命令中添"C=1" 来在代码上运行它

"Coccinelle" 工具（http://coccinelle.lip6.fr/）能够发现各种各样的潜在编码问题；它也能
为这些问题提出修复。相当多的内核“语义补丁”已经打包在 scripts/coccinelle 目录下；运行
"make coccicheck" 将遍历那些语义补丁，并报告发现的任何问题。更多信息请参阅
Documentation/dev-tools/coccinelle.rst <devtools_coccinelle>銆。

其他种类的可移植性错误最好通过为其他体系结构编译你的代码来发现。如果你手边碰巧没有
S/390 系统Blackfin 开发板，你仍然可以执行编译步骤。一套给 x86 系统用的大量交叉编译
可以

	https://www.kernel.org/pub/tools/crosstool/

找到。花些时间安装和使用这些编译器，将有助于避免日后的尴尬

### 文档


在内核开发中，文档常常更多的是例外而非规则。即便如此，充分的文档将有助于新代码更顺利地
合并进内核，让其他开发者生活更轻松，并且对你的用户有帮助。在许多情况下，添加文档已经
基本成为强制性的

任何补丁的第一份文档是它关联的变更日志。日志条目应该描述正在被解决的问题、解决方案的
形式、参与补丁的人、对性能的任何相关影响，以及任何其他理解该补丁可能所需的东西。务
让变更日志说*为什*该补丁值得被打上；数量惊人的开发者未能提供那方面的信息

任何添加了新用户空间接口的——包括新sysfs /proc 文件——代码，都应该包含对该接口的
文档，以便用户空间开发者知道他们在处理什么。关于这种文档应该如何格式化以及需要提供什
信息，请参阅 Documentation/ABI/README

文件 :ref:`Documentation/admin-guide/kernel-parameters.rst
<kernelparameters>` 描述了内核所有的引导时参数。任何添加了新参数的补丁都应该把适当
条目加到这个文件中

任何新的配置选项都必须伴有帮助文本，清楚地解释这些选项，以及用户可能何时想要选择它们

许多子系统的内部 API 信息是通过特殊格式的注释记录的；这些注释可以被 "kernel-doc" 脚本
以若干种方式提取和格式化。如果你正在一个拥kerneldoc 注释的子系统内工作，你应该维
它们，并酌情为对外可用的函数添加它们。即使在尚未如此记录的区域，为未来添kerneldoc
注释也没有坏处；事实上，这对初学者内核开发者来说可以是一项有用的活动。这些注释的格式
连同一些关于如何创kerneldoc 模板的信息，可以Documentation/doc-guide/ <doc_guide>
中找到

任何读过大量现有内核代码的人都会注意到，常常，注释最引人注目的是它们的缺失。再一次，
对新代码的期望比过去更高；合并没有注释的代码将更难。话虽如此，人们几乎不想要冗长注
的代码。代码本身应该是可读的，注释解释更微妙的地方

某些东西应该总是被注释。内存屏障的使用应该伴有一行解释为什么需要该屏障。数据结构的加锁
规则通常需要在某处解释。主要的数据结构一般都需要全面的文档。独立的代码片段之间不明显的
依赖关系应该被指出。任何可能引诱代码清洁工做出不正确的“清理”的东西，都需要一条注释说
为什么它是那样做的。等等

### 内部 API 改动


内核提供给用户空间的二进制接口不能被破坏，除非在极其严重的情况下。内核内部的编程接口
则相反，是高度流动的，并且可以在需要时改变。如果你发现自己不得不绕过某个内API，或
仅仅因为它不符合你的需求而不使用某个特定功能，那可能是一API 需要改变的信号。作为内
开发者，你被授权去做这样的改动

当然，有一些注意事项。API 改动可以做，但它们需要有充分的理由。所以任何做内部 API 改动
的补丁都应该伴有一个对改动是什么以及为什么必要的描述。这种改动也应该被拆分成一个单独的
补丁，而不是埋在一个更大的补丁中

另一个注意事项是，改动了一个内API 的开发者通常负有修复内核树内任何被该改动弄坏
代码的任务。对于一个被广泛使用的函数，这个职责可能导致字面意义上数百或数千处改动——其
许多很可能与其他开发者正在进行的工作冲突。不用说，这可能是一项大工程，所以最好确保理
是扎实的。注意，Coccinelle 工具可以帮助进行大范围的 API 改动

当做一个不兼容API 改动时，应该尽可能确保未被更新的代码被编译器捕获。这将帮助你确信
你已经找到了该接口所有树内的使用。它也会提醒树外代码的开发者，有一个他们需要响应的改动
支持树外代码并不是内核开发者需要担心的事情，但我们也不必把树外开发者的生活弄得比必要的
更难
