
## Linux 内核贡献成熟度模

## 背景


作为 2021 Linux 内核维护者峰会（Linux Kernel Maintainers' Summit）的一部分，有一`discussion <https://lwn.net/Articles/870581/>`_ 讨论了在招募内核维护者以及维护者继任方面的
挑战。该讨论的一些结论包括：作为 Linux 内核社区一员的公司需要允许工程师把担任维护者作为他工作的一部分，这样他们才能成长为受人尊重的领导者，并最终成为内核维护者。为了支持强大的人才
管线，应该允许并鼓励开发者承担上游贡献，例如审阅其他人的补丁、重构内核基础设施，以及编写文档
为此，Linux 基金会技术顾问委员会（TAB）提出了这个 Linux 内核贡献成熟度模型。这些关于上社区参与的共同期望旨在增加个体开发者的影响力、增强组织的协作，并改善 Linux 内核生态系统的
整体健康
TAB 敦促各组织持续评估其开源成熟度模型，并承诺改进以与本模型对齐。为了有效，该评估应纳入
来自组织各层面的反馈，包括管理层和各级资深程度的开发者。本着开源的精神，我们鼓励各组织发布
其评估结果以及改进其与上游社区参与度的计划
## 等级 0


- 软件工程师不被允许向 Linux 内核贡献补丁

## 等级 1


- 软件工程师被允许Linux 内核贡献补丁，无论是作为其工作职责的一部分，还是在自己的时间里

## 等级 2


- 期望软件工程师作为其工作职责的一部分Linux 内核做出贡献- 软件工程师将被支持参加与其工作相关的 Linux 会议- 软件工程师的上游代码贡献将在晋升和绩效评估中被考量

## 等级 3


- 期望软件工程师作为其工作职责的一部分审阅补丁（包括由其他公司工程师编写的补丁）- Linux 相关或学术会议（例如Linux 基金会、Usenix、ACM 等组织的会议）提交演讲或论文  被视为工程师工作的一部分- 软件工程师的社区贡献将在晋升和绩效评估中被考量- 组织将定期报告其开源贡献的度量指标，并随时间跟踪这些指标。这些指标可以仅在组织内部发布，
  或者由组织酌情将部分或全部对外发布。强烈建议的指标包括
  - 按团队或组织（例如，所有向某个经理、总监VP 汇报的人）统计的上游内核贡献数量  - 已做出上游贡献的内核开发者相对于组织中内核开发者总数的百分比  - 组织服务器和/或产品中使用的内核与内部内核所基于的上游内核发布日期之间的时间间隔  - 内部内核中存在的树外（out-of-tree）提交数量

## 等级 4


- 鼓励软件工程师把一部分工作时间专注于上游工作（Upstream Work），其定义为审阅补丁、担  程序委员会成员、改进核心项目基础设施（如编写或维护测试）、减少上游技术债务、编写文档等- 软件工程师在协助组织 Linux 相关会议方面得到支持- 组织将在正式绩效评估中考虑社区成员的反馈

## 等级 5


- 上游内核开发被视为一个正式的工作岗位，工程师至少三分之一的时间用于做上游工作- 组织将主动寻求社区成员的反馈，作为正式绩效评估的一个因素- 组织将定期在内部报告上游工作与直接追求业务目标工作之间的比例
