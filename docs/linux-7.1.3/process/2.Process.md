
## 开发流程如何进行


90 年代早期的 Linux 内核开发是一件相当松散的事情，涉及的用户和开发人员相对较少。由于如今拥有数以百万计的用户群，且每年约有 2000 名开发人员参与，内核不得不发展出一系列流程来保证开发顺利进行。要想有效地参与其中，就必须扎实地理解这套流程的运作方式。

### 总览


Linux 内核采用一种松散的、基于时间的滚动发布（rolling release）开发模型。一个新的主内核版本（作为示例，我们称之为 9.x）[^1^]_ 大约每两到三个月发布一次，它带来了新特性、内部 API 变更等诸多内容。一个典型的版本可能包含约 13,000 个变更集（changeset），涉及数十万行代码的改动。近期版本及其发布日期可在 `维基百科 <https://en.wikipedia.org/wiki/Linux_kernel_version_history>`_ 找到。

      这里并非采用主次版本号方案，而是以 9.x 这一对数字作为一个整体来标识主发行版本号。对于每个版本，x 都会递增，但只有当 x 被认为足够大时，9 才会递增（例如：Linux 5.0 是在 Linux 4.20 之后发布的）。

关于每个版本的补丁合并，遵循着相对简单的一套纪律。在每个开发周期开始时，所谓的“合并窗口”会被打开。此时，那些被认为足够稳定（且被开发社区接受）的代码会被合并进主线内核。一个新开发周期的大部分改动（以及所有主要改动）都会在这段时间内以接近每天 1000 次变更（“补丁”或“变更集”）的速度被合并。

（顺便说一句，值得注意的是，合并窗口期间整合进来的改动并非凭空而来；它们是提前被收集、测试并暂存好的。这一过程如何运作，稍后将详细描述。）

合并窗口持续大约两周。在这段时间的末尾，Linus Torvalds 会宣布窗口关闭，并发布第一个“rc”内核。例如，对于目标为 9.x 的内核，合并窗口结束时发布的版本将被称为 9.x-rc1。-rc1 的发布是一个信号，表明合并新特性的时机已过，稳定下一个内核的阶段已经开始。

在接下来的六到十周内，只有修复问题的补丁才应当提交到主线。偶尔也会允许较大的改动，但这种情况很少见；试图在合并窗口之外合并新特性的开发人员往往会遭到不友好的对待。一般规则是：如果您错过了某个特性的合并窗口，最好的做法是等待下一个开发周期。（偶尔会为先前不支持的硬件的驱动程序开个例外；如果它们不触碰树内代码，就不会造成回归，随时加入都应当是安全的。）

随着修复进入主线，补丁的提交速率会随时间放缓。Linus 大约每周发布一个新的 -rc 内核；在一个正常的系列中，在内核被认为足够稳定并发布最终版本之前，通常会达到 -rc6 到 -rc9 之间。到那时，整个过程又会重新开始。

举个例子，下面是 5.4 开发周期的演进过程（所有日期均为 2019 年）：

	==============  ===============================
	September 15	5.3 stable release
	September 30	5.4-rc1, merge window closes
	October 6	5.4-rc2
	October 13	5.4-rc3
	October 20	5.4-rc4
	October 27	5.4-rc5
	November 3	5.4-rc6
	November 10	5.4-rc7
	November 17	5.4-rc8
	November 24	5.4 stable release
	==============  ===============================

开发人员如何决定何时结束开发周期并创建稳定版？所使用的最重要指标是相对于先前版本的回归列表。没有任何 bug 是受欢迎的，但那些破坏了过去能正常工作的系统的 bug 被认为尤其严重。因此，导致回归的补丁会遭到反对，并且很可能在稳定期内被回退。

开发人员的目标是在稳定版发布之前修复所有已知的回归。在现实世界中，这种完美很难达成；在如此规模的项目中，变数实在太多。到了某个节点，拖延最终发布只会让问题更糟；等待下一个合并窗口的改动会越积越多，导致下一次出现更多回归。所以大多数内核发布时都会带着少数已知的回归，不过希望其中没有严重的。

一旦稳定版发布，其后续的维护工作就会被移交给“稳定团队”，目前该团队由 Greg Kroah-Hartman 和 Sasha Levin 组成。稳定团队会使用 9.x.y 的编号方案不定期地发布稳定版的更新。

要想被纳入更新版，一个补丁必须（1）修复一个重要的 bug，并且（2）已经合并进下一个开发内核的主线。内核通常会在初始发布之后的一个多开发周期内收到稳定更新。例如，5.2 内核的历史如下（所有日期均为 2019 年）：

	==============  ===============================
	July 7		5.2 stable release
	July 14		5.2.1
	July 21		5.2.2
	July 26		5.2.3
	July 28		5.2.4
	July 31  	5.2.5
	...		...
	October 11	5.2.21
	==============  ===============================

5.2.21 是 5.2 版本的最终稳定更新。

有些内核被指定为“长期”内核；它们会获得更长时间的支持。有关当前活跃的长期的核版本及其维护者的列表，请参考以下链接：

	https://www.kernel.org/category/releases.html

长期支持内核的选择纯粹是维护者是否有需求、有时间来维护该版本的问题。目前没有任何为即将发布的特定版本提供长期支持的已知计划。

### 补丁的生命周期


补丁并不会直接从开发人员的键盘进入主线内核。相反，存在一套多少有些复杂（即便也有些非正式）的流程，旨在确保每个补丁都经过质量审查，并且每个补丁实现的改动都是主线所期望拥有的。对于小的修复，这套流程可能很快完成；而对于那些庞大且有争议的改动，则可能持续数年。许多开发人员的挫败感来源于对这套流程缺乏理解，或者试图绕过它。

为了减少这种挫败，本文档将描述一个补丁是如何进入内核的。下面是一段介绍，以一种略显理想化的方式描述这套流程。更细致的处理将在后续章节给出。

补丁通常要经历以下阶段：

 - 设计。这是补丁真正的需求——以及满足这些需求的方式——被厘清的地方。设计工作常常是在不牵扯社区的情况下完成的，但如果可能，最好在公开场合做这件事；这能省下日后大量重新设计的时间。

 - 早期审查。补丁被发布到相关的邮件列表上，列表中的开发人员会回复他们可能有的任何评论。如果一切顺利，这个过程应当能暴露出补丁的任何主要问题。

 - 更广泛的审查。当补丁接近准备好并入主线时，它应当被相关的子系统维护者接受——尽管这种接受并不能保证补丁一路走到主线。补丁会出现在维护者的子系统树中，并进入 -next 树（如下文所述）。当流程顺利时，这一步会带来对补丁更广泛的审查，并发现将该补丁与他人正在进行的工作集成所产生的问题。

- 请注意，大多数维护者也有本职工作，因此合并您的补丁未必是他们的最高优先级。如果您的补丁收到了需要修改的反馈，您应当要么做这些修改，要么说明理由解释为何不该改。如果您的补丁没有收到审查方面的抱怨，却没有被相应的子系统或驱动维护者合并，您应当坚持不懈地将补丁更新到当前内核以便能干净地应用，并持续发送它以供审查和合并。

 - 合并进主线。最终，一个成功的补丁会被合并进由 Linus Torvalds 管理的主线仓库。此时可能会有更多评论和/或问题浮现；开发人员对这些保持响应并修复出现的任何问题很重要。

 - 稳定版发布。现在可能受该补丁影响的用户数量很大，因此新的问题可能再次出现。

 - 长期维护。虽然开发人员在合并代码后将其抛诸脑后是完全可能的，但这种行为往往会在开发社区中留下糟糕的印象。合并代码能减轻一部分维护负担，因为其他人会修复由 API 变更引起的问题。但是，如果代码要在长期内保持有用，原始开发人员应当继续为它负责。

内核开发人员（或其雇主）所犯的最大错误之一，就是试图把这套流程缩减成单一的“合并进主线”这一步。这种做法无一例外地会让所有相关人员感到挫败。

### 补丁如何进入内核


只有一个人能够将补丁合并进主线内核仓库：Linus Torvalds。但举例来说，在进入 2.6.38 内核的超过 9500 个补丁中，只有 112 个（约 1.3%）是由 Linus 亲自直接挑选的。内核项目早已发展到单一开发人员无法在无人协助的情况下检查并挑选每一个补丁的规模。内核开发人员应对这种增长的方式，是通过使用一套围绕信任链建立的副手（lieutenant）体系。

内核代码库在逻辑上被分解为一组子系统：网络、特定的体系结构支持、内存管理、视频设备等。大多数子系统都有一位指定的维护者，即对该子系统内代码负有总体责任的开发人员。这些子系统维护者（以一种松散的方式）是他们所管理的内核部分的守门人；他们（通常）会接受一个补丁以将其纳入主线内核。

子系统维护者各自管理着自己版本的内核源码树，通常（但绝非总是）使用 git 源码管理工具。像 git（以及 quilt、mercurial 等相关工具）这样的工具允许维护者跟踪一份补丁列表，包括作者信息和其他元数据。在任何时刻，维护者都能识别出他或她的仓库中哪些补丁在主线里找不到。

当合并窗口打开时，顶级维护者会请求 Linus 从他们的仓库中“拉取”（pull）他们为合并所选定的补丁。如果 Linus 同意，补丁流就会向上流入他的仓库，成为主线内核的一部分。Linus 对一次拉取操作中收到的具体补丁投注的注意力程度不一。显然，有时他会看得相当仔细。但一般规则是，Linus 信任子系统维护者不会把糟糕的补丁发往上游。

子系统维护者反过来也可以从其他维护者那里拉取补丁。例如，网络树是由最初积累在专门面向网络设备驱动、无线网络等的树中的补丁构建而成的。这条仓库链可以任意长，尽管很少超过两到三个环节。由于链中的每个维护者都信任那些管理更底层树的人，这一过程被称为“信任链”。

显然，在这样一个系统中，让补丁进入内核取决于找到正确的维护者。直接向 Linus 发送补丁通常并非正确做法。


### Next 树


子系统树的链条引导着补丁流向内核，但它也引出一个有趣的问题：如果有人想查看所有正为下一个合并窗口做准备的补丁怎么办？开发人员会关心还有哪些其他改动在等待，以判断是否存在需要担心的冲突；比方说，一个修改了核心内核函数原型的补丁，就会与任何使用该旧形式函数的其他补丁冲突。审查者和测试人员希望在所有这些改动落入主线内核之前，就能以集成的形式访问它们。人们可以从所有相关的子系统树中拉取改动，但那将是一项庞大且容易出错的工作。

答案以 -next 树的形式出现，子系统树在其中被收集起来用于测试和审查。这些树中较老的一棵由 Andrew Morton 维护，被称为“-mm”（取内存管理之意，它正是以此起步的）。-mm 树集成了来自一长串子系统树的补丁；它也包含一些旨在帮助调试的补丁。

除此之外，-mm 还包含一大批由 Andrew 直接挑选的补丁。这些补丁可能发布在某个邮件列表上，也可能适用于内核中尚无指定子系统树的部分。因此，-mm 充当了一种“最后的子系统树”的角色；如果一条补丁没有其他明显的路径进入主线，它很可能会最终落到 -mm 中。积累在 -mm 中的杂项补丁最终要么被转发到合适的子系统树，要么被直接发送给 Linus。在一个典型的开发周期中，约有 5-10% 进入主线的补丁是经由 -mm 到达的。

当前的 -mm 补丁可在“mmotm”（-mm of the moment）目录中找到：

	https://www.ozlabs.org/~akpm/mmotm/

不过，使用 MMOTM 树可能会是一次令人受挫的体验；它很有可能会连编译都通不过。

用于下一周期补丁合并的主要树是 linux-next，由 Mark Brown 维护。按设计，linux-next 树是下一个合并窗口关闭后主线所预期呈现样子的一个快照。linux-next 树在组装好后会发布在 linux-kernel 和 linux-next 邮件列表上；可从以下位置下载：

	https://www.kernel.org/pub/linux/kernel/next/

Linux-next 已经成为内核开发流程中不可或缺的一部分；在给定合并窗口中合并的所有补丁，都理应在合并窗口打开之前的某个时刻进入过 linux-next。


### Staging 树


内核源码树包含 drivers/staging/ 目录，许多正处于被加入内核树过程中的驱动或文件系统的子目录就放在那里。在仍需要更多工作的时候，它们留在 drivers/staging 中；一旦完成，就可以移入内核本体。这是一种追踪那些尚不符合 Linux 内核编码或质量标准的驱动的方式，但人们可能想使用它们并跟踪其开发。

Greg Kroah-Hartman 目前维护着 staging 树。仍需要工作的驱动会被发送给他，每个驱动在 drivers/staging/ 下拥有自己的子目录。除了驱动源文件外，目录中还应当有一个 TODO 文件。该 TODO 文件列出了该驱动被内核本体接受所需完成的待办工作，以及任何针对该驱动的补丁都应当抄送（Cc）的人员列表。当前的规则要求，贡献给 staging 的驱动至少必须能够正确编译。

Staging 是一种让新驱动进入主线相对容易的途径，运气好的话，它们会引起其他开发人员的注意并迅速改进。不过，进入 staging 并非故事的终点；staging 中没有看到持续进展的代码最终会被移除。发行版也往往相对不愿意启用 staging 驱动。所以 staging 充其量只是通往成为一个合格主线驱动之路上的一个中转站。


### 工具


从上面的文字可以看出，内核开发流程在很大程度上依赖于将一批批补丁朝不同方向驱策的能力。若没有足够强大的工具，整件事根本无法像现在这样良好运转。关于如何使用这些工具的教程远远超出了本文档的范围，不过还是留一点篇幅给几个指引。

迄今为止，内核社区使用的主要源码管理系统是 git。Git 是自由软件社区中开发的众多分布式版本控制系统之一。它非常适合内核开发，因为在处理大型仓库和大量补丁时表现相当好。它也以难以学习和使用而闻名，尽管随着时间推移已有所改善。对内核开发人员来说，对 git 某种程度的熟悉几乎是一项硬性要求；即便他们不在自己的工作中使用它，也需要 git 来跟上其他开发人员（以及主线）正在做什么。

Git 现在已被几乎所有 Linux 发行版打包。其主页位于：

	https://git-scm.com/

该页面提供了文档和教程的指引。

在不使用 git 的内核开发人员中，最受欢迎的选择几乎肯定是 Mercurial：

	https://www.selenic.com/mercurial/

Mercurial 与 git 共享许多特性，但它提供了一个许多人觉得更易用的界面。

另一个值得了解的工具是 Quilt：

	https://savannah.nongnu.org/projects/quilt/

Quilt 是一个补丁管理系统，而非源码管理系统。它不随时间跟踪历史；相反，它面向的是针对一个不断演进的代码库跟踪一组特定的改动。一些主要的子系统维护者使用 quilt 来管理打算推向上游的补丁。对于某些树（例如 -mm）的管理，quilt 是完成这项工作的最佳工具。


### 邮件列表


大量的 Linux 内核开发工作是通过邮件列表完成的。如果不加入至少一个列表，就很难成为社区中一个功能完备的成员。但 Linux 邮件列表对开发人员来说也是一个潜在的隐患：他们可能被海量电子邮件淹没、触犯 Linux 列表上通行的惯例，或者两者兼而有之。

大多数内核邮件列表托管在 kernel.org；主列表可在以下位置找到：

	https://subspace.kernel.org

也有托管在其他地方的列表；请查阅随内核源码附带的 MAINTAINERS 文件，以找到与任何特定子系统相关的列表。

内核开发的核心邮件列表当然是 linux-kernel。这是一个令人生畏的地方；它的邮件量可达每天 500 封，噪音很高，对话可能极其技术化，而且参与者并不总是讲究礼貌。但没有任何其他地方能让内核开发社区作为一个整体聚在一起；回避这个列表的开发人员会错过重要信息。

以下一些提示有助于在 linux-kernel 中生存下来：

- 将列表投递到一个独立的文件夹，而不是您的主邮箱。必须能够长时间地忽略这股洪流。

- 不要试图跟进每一次对话——没人能做到。重要的是要按感兴趣的主题（不过请注意，长篇对话可能在不改变邮件主题行的情况下偏离原主题）以及参与的人员进行过滤。

- 不要给喷子（troll）喂料。如果有人试图激起愤怒的回应，忽略他们。

- 回复 linux-kernel 邮件（或其他列表上的邮件）时，为所有相关人员保留 Cc: 头。在没有强有力的理由（例如明确的请求）时，永远不应移除收件人。务必确保您所回复的人在 Cc: 列表中。这一惯例也让您不必在别人回复您的帖子时明确要求抄送您。

- 在提问之前，先搜索列表存档（以及整个网络）。有些开发人员会对显然没有做好功课的人失去耐心。

- 使用交错式（“行内”）回复，这会让您的回应更易阅读。（即避免顶回复——把您的回答放在所引用文本之上的做法。）更多细节，请见 Documentation/process/submitting-patches.rst <interleaved_replies>。

- 在正确的邮件列表上提问。linux-kernel 也许是通用的汇集点，但它并非寻找所有子系统开发人员的最佳场所。

最后一点——找到正确的邮件列表——是初级开发人员常犯的错误所在。有人在 linux-kernel 上提出与网络相关的问题，几乎肯定会收到一个礼貌的建议：改到 netdev 列表去问，因为那是大多数网络开发人员常驻的列表。还有其他列表服务于 SCSI、video4linux、IDE、文件系统（filesystem）等子系统。寻找邮件列表的最佳位置，是随内核源码打包的 MAINTAINERS 文件。


### 开始内核开发


关于如何着手内核开发流程的问题很常见——无论个人还是公司皆然。同样常见的，是一些让这段关系的开端比必要的更艰难的失误。

公司往往希望聘请知名开发人员来启动一个开发小组。这事实上可以是一种有效的技术。但它也往往代价高昂，并且对壮大有经验的内核开发人员储备帮助不大。只要投入一点时间，是能够让内部开发人员跟上 Linux 内核开发的节奏的。花上这段时间，可以让雇主拥有一批既懂内核又懂公司的开发人员，还能帮助培训其他人。从中期来看，这常常是更有利可图的做法。

单个开发人员常常（这可以理解）对从何处起步感到茫然。从一个大型项目开始可能令人怯步；人们往往想先用小一点的事情探探水深。正是在这一点上，一些开发人员一头扎进创建修复拼写错误或轻微编码风格问题的补丁中。不幸的是，这类补丁会产生一种让整个开发社区分心的噪音，因此越来越被人看不上。希望向社区介绍自己的新开发人员，靠这些手段是得不到他们所期望的那种回应的。

Andrew Morton 给有志于内核开发的开发人员提出了如下建议

```

	The #1 project for all kernel beginners should surely be "make sure
	that the kernel runs perfectly at all times on all machines which
	you can lay your hands on".  Usually the way to do this is to work
	with others on getting things fixed up (this can require
	persistence!) but that's fine - it's a part of kernel development.

```
(https://lwn.net/Articles/283982/)。

在没有明显问题可修的情况下，建议开发人员去查看当前的回归列表和公开的 bug 列表。需要修复的问题从来都不缺；通过解决这些问题，开发人员将在获得流程经验的同时，与开发社区的其他成员建立起尊重。
