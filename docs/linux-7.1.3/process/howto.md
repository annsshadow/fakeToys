
## 如何参与 Linux 内核开发（HOWTO


这是一篇关于本主题的终极参考文档。它包含了如何成为一Linux 内核开发者，
以及如何学会Linux 内核开发社区协作的指导。它尽量不包含任何与内核编程
技术细节相关的内容，但会为你指明获取这些知识的正确方向

如果本文档中的任何内容变得过时，请向本文档的维护者（列在文档末尾）发送补丁


### 入门


那么，你想学习如何成为一Linux 内核开发者？或者是你的经理告诉你，“去
这个设备写一Linux 驱动程序。本文档的目标是通过描述你需要经历的过程
以及关于如何与社区协作的一些提示，教会你达成这一目标所需的全部知识。它也会
试图解释社区为何会按照它现在的方式运作的某些原因

内核大部分是C 语言写成的，少部分与体系结构相关的代码用汇编语言写成
参与内核开发需要对 C 语言有良好的理解。除非你打算为该体系结构做底层开发，
否则不需要掌握汇编语言（任何体系结构）。尽管下面这些书无法替代扎实C 语言
功底或多年的经验，但作为参考资料来说它们是不错的：

 - "The C Programming Language" by Kernighan and Ritchie [Prentice Hall]
 - "Practical C Programming" by Steve Oualline [O'Reilly]
 - "C:  A Reference Manual" by Harbison and Steele [Prentice Hall]

内核是用 GNU C GNU 工具链编写的。虽然它遵循 ISO C11 标准，但也使用了
标准中没有涵盖的若干扩展。内核是一个独立（freestanding）的 C 环境，不依赖
标准 C 库，因此 C 标准中的部分内容不受支持。任意的 long long 除法和浮点运
都是不允许的。有时很难理解内核对工具链的要求以及它所使用的扩展，遗憾的是
目前还没有关于它们的权威参考资料。请查阅 gcc info 页（`info gcc`）以获取
一些相关信息

请记住，你正在尝试学习如何与已有的开发社区协作。那是一个由形形色色的人组成
的群体，对代码、风格和流程有着很高的标准。这些标准是在长期的实践中，基于他们
发现对这样一个庞大且地理上分散的团队最为有效的方式建立起来的。请尽可能提
了解这些标准，因为它们都有良好的文档记录；不要期望别人来适应你或你公司的
做事方式


### 法律问题


Linux 内核源代码是GPL 下发布的。请参阅源代码树主目录中COPYING 文件
Linux 内核许可规则以及如何在源代码中使`SPDX <https://spdx.org/>`_ 标识
的方法，Documentation/process/license-rules.rst <kernel_licensing> 中有说明
如果你对许可还有进一步的问题，请联系律师，而不要在内核邮件列表上询问。邮
列表上的人不是律师，你不应依赖他们对法律事务的表述

关于 GPL 的常见问题与解答，请参阅

	https://www.gnu.org/licenses/gpl-faq.html


### 文档


Linux 内核源代码树中包含大量文档，对于学习如何与内核社区互动极具价值。当
功能被加入内核时，建议同时新增文档文件来解释如何使用该功能。当内核的改动导
其暴露给用户空间的接口发生变化时，建议将相关信息或手册页补丁发送给手册页的
维护alx@kernel.org，并抄送（CC）列linux-api@vger.kernel.org，以说明
变化

以下是内核源代码树中必须阅读的文档列表：

  Documentation/admin-guide/README.rst <readme>
    该文件简要介绍了 Linux 内核的背景，并描述了配置和构建内核所需的操作
    内核新手应该从这里开始

  Documentation/process/changes.rst <changes>
    该文件给出了成功构建和运行内核所需各种软件包的最低版本列表

  Documentation/process/coding-style.rst <codingstyle>
    该文件描述了 Linux 内核的代码风格，以及其背后的部分理由。所有新代码都应
    遵循本文档中的指南。大多数维护者只有在遵循这些规则时才会接受补丁，许多
    人也只会对符合规范的代码进行审查

  Documentation/process/submitting-patches.rst <submittingpatches>
    该文件详细明确地描述了如何成功地创建并发送一个补丁，包括（但不限于）

       - 邮件内容
       - 邮件格式
       - 发送给

    遵循这些规则并不能保证成功（因为所有补丁都会受到内容和风格上的审查），
    但不遵循它们几乎总是会导致失败

    其他关于如何正确创建补丁的优秀说明有：

	"The Perfect Patch"
		https://www.ozlabs.org/~akpm/stuff/tpp.txt

	"Linux kernel patch submission format"
		https://web.archive.org/web/20180829112450/http://linux.yyz.us/patch-format.html

  Documentation/process/stable-api-nonsense.rst <stable_api_nonsense>
    该文件描述了刻意决定不在内核内部保持稳定 API 背后的理由，包括诸如

      - 子系统中间层（为了兼容性？
      - 驱动程序在各操作系统之间的可移植性
      - 缓解（或阻止）内核源代码树内部的快速变化

    该文档对于理Linux 的开发哲学至关重要，对于从其他操作系统开发转
    Linux 的人来说也非常重要

  Documentation/process/security-bugs.rst <securitybugs>
    如果你认为自己在内核中发现了安全问题，请按照本文档中的步骤帮助通知内核
    开发者，并协助解决问题

  Documentation/process/management-style.rst <managementstyle>
    该文档描述了 Linux 内核维护者如何运作，以及他们方法论背后共同的理念。这
    对于任何内核开发新手（或仅仅对此感到好奇的人）都是重要的阅读内容，因为
    消除了许多关于内核维护者独特行为的常见误解和困惑

  Documentation/process/stable-kernel-rules.rst <stable_kernel_rules>
    该文件描述了稳定版内核发布如何进行的规则，以及如果你希望将某个改动纳
    这些发布版本该怎么做

  Documentation/process/kernel-docs.rst <kernel_docs>
    一份与内核开发相关的外部文档列表。如果你在内核自带的文档中没有找到所需
    内容，请查阅此列表

  Documentation/process/applying-patches.rst <applying_patches>
    一篇很好的介绍，确切地描述了什么是补丁，以及如何将其应用到内核的不
    开发分支上

内核还有大量可以从源代码本身ReStructuredText 标记（ReST，如本文档）自动
生成的文档。这包括对内核内API 的完整描述，以及如何处理加锁的相关规则

```

	make pdfdocs
	make htmldocs

```
分别在主内核源代码目录下执行

使用 ReST 标记的文档会生成Documentation/output 目录下
```

	make latexdocs
	make epubdocs

```
### 如何成为一名内核开发


如果你对 Linux 内核开发一无所知，你应该看Linux KernelNewbies 项目

	https://kernelnewbies.org

它包含一个很有帮助的邮件列表，你几乎可以询问任何类型的基础内核开发问题（
提问之前，请务必先搜索邮件归档，确认不要问出过去已经回答过的问题）。它还有
一IRC 频道，你可以用它实时提问，以及大量对学习 Linux 内核开发很有帮助的
文档

该网站包含关于代码组织、子系统和当前项目（无论是树内还是树外）的基础信息
它还描述了一些基本的后勤信息，例如如何编译内核和打补丁

如果你不知道该从哪里入手，但想找一些任务开始做以加入内核开发社区，请前往
Linux 内核“清洁工”（Kernel Janitor）项目：

	https://kernelnewbies.org/KernelJanitors

这是一个很好的起点。它描述了一份相对简单、需要在 Linux 内核源代码树中清理和
修复的问题列表。与负责该项目的开发者协作，你将学到把补丁纳Linux 内核树的
基础知识，如果你自己还没有想法，还可能会被指引下一步该做什么工作

在对 Linux 内核代码做任何实际修改之前，理解相关代码如何运作是必不可少的。为此，
没有什么比直接通读代码更好的了（大多数棘手之处都有良好的注释），或许还可以
借助专门工具的帮助。一个特别值得推荐的工具是 Linux Cross-Reference 项目，它
能够以自引用、带索引的网页格式呈现源代码。一个优秀的、最新的内核代码仓库可以
在以下地址找到

	https://elixir.bootlin.com/


### 开发流


Linux 内核开发流程目前由几个不同的主内核“分支”以及大量不同的、特定于子系统的
内核分支组成。这些不同的分支是：

  - Linus 的主线树
  - 多个主版本号不同的各种稳定树
  - 特定于子系统的树
  - linux-next 集成测试

#### 主线


主线树由 Linus Torvalds 维护，可以在 https://kernel.org 或代码仓库中找到
它的开发流程如下：

  - 一旦一个新内核发布，就会打开一个为期两周的窗口，在此期间维护者可以向
    Linus 提交大段diff，通常这些补丁已经linux-next 中包含了几个星期
    提交大改动的首选方式是使用 git（内核的源代码管理工具，更多信息可以
    https://git-scm.com/ 找到），但普通的补丁也同样完全可行
  - 两周之后会发布一-rc1 内核，重点放在让新内核尽可能坚如磐石上。此
    大多数补丁应该修复一个回归（regression）。一直存在的缺陷不算回归，因
    只有在这些修复很重要时才推送此类修复。请注意，一个全新的驱动程序（或
    文件系统）可能在 -rc1 之后仍被接受，因为只要该改动是自包含的、不影响所
    添加代码之外的区域，就不会有造成回归的风险。在 -rc1 发布之后可以git
    Linus 发送补丁，但补丁也需要同时发送到公开邮件列表以供审查
  - 每当 Linus 认为当前git 树处于一个用于测试足够合理的健全状态时，就
    发布一个新-rc。目标是每周发布一个新-rc 内核
  - 该过程一直持续到内核被认为“就绪”，整个过程应持续大6 周

值得一提的Andrew Morton linux-kernel 邮件列表上关于内核发布所写的
一段话

	*"没有人知道内核何时发布，因为它是根据感知到的缺陷状态发布的，而不
	根据预先设定好的时间表*

#### 多个主版本号不同的各种稳定树


带有三段式版本号的内核是 -stable 内核。它们包含针对某个给定的主版本主线发
中发现的安全问题或重大回归的相对较小且关键的修复。在一个主版本的稳定系列中
每次发布都会递增版本号的第三部分，前两部分保持不变

对于想要最新的稳定内核、又不想帮助测试开实验性版本的用户，这是推荐的分支

稳定树由“stable”团<stable@vger.kernel.org> 维护，并按需发布。正常的发布
周期约为两周，但如果没有紧迫的问题，也可能更长。而一个与安全相关的问题则可能
导致发布几乎立即发生

内核树中的文Documentation/process/stable-kernel-rules.rst <stable_kernel_rules>
记录了哪些类型的改动可以-stable 树接受，以及发布流程是如何运作的

#### 特定于子系统的树


各种内核子系统的维护者——以及许多内核子系统开发者——会在源代码仓库中公开他们
当前的开发状态。这样，其他人就能看到内核不同区域正在发生的事情。在开发迅速的
领域，开发者可能会被要求将其提交基于这样一个子系统内核树，以避免提交与其他
正在进行的工作之间的冲突

这些仓库大多git 树，但也在使用其SCM，或者以 quilt 系列的形式发布补
队列。这些子系统仓库的地址列在 MAINTAINERS 文件中。其中许多可以在
https://git.kernel.org/ 上浏览

在建议的补丁被提交到这样一个子系统树之前，它要接受审查，这主要发生在邮件列
上（见下面相应的章节）。对于若干内核子系统，这个审查过程由 patchwork 工具
跟踪。Patchwork 提供一Web 界面，显示补丁的发布、对补丁的任何评论或修订
维护者可以将补丁标记为审查中、已接受或已拒绝。大多数这些 patchwork 站点列在
https://patchwork.kernel.org/銆。

#### linux-next 集成测试


在来自子系统树的更新被合并进主线树之前，它们需要进行集成测试。为此，存在一
特殊的测试仓库，几乎每天都会将几乎所有子系统树拉取（pull）进去：

	https://git.kernel.org/pub/scm/linux/kernel/git/next/linux-next.git

这样一来，linux-next 对下一个合并周期预计会进入主线内核的内容给出了一个概
预览。非常欢迎勇于尝试的测试者对 linux-next 进行运行时测试


### 报告缺陷（Bug


主内核源代码目录中的文件 'Documentation/admin-guide/reporting-issues.rst'
描述了如何报告一个可能的内核缺陷（bug），并详细说明了内核开发者追踪问题所需
要的各类信息


### 处理缺陷报告


将你的黑客技能付诸实践的最佳方式之一，就是修复其他人报告的缺陷。你不仅将帮
内核变得更加稳定，还将学会修复现实世界的问题、提升自己的技能，其他开发者也
注意到你的存在。修复缺陷是在其他开发者中赢得声誉的最佳方式之一，因为没多少
喜欢把时间浪费在修复别人的缺陷上

要处理已经报告的缺陷，请找一个你感兴趣的子系统。查MAINTAINERS 文件，了
该子系统的缺陷报告发往何处；通常是一个邮件列表，很少是一个缺陷跟踪系统。搜
该处最近的报告归档，在你认为合适的地方提供帮助。你可能也想查看
https://bugzilla.kernel.org 上的缺陷报告；只有少数内核子系统积极地用它来报告
或跟踪，但整个内核的缺陷都会在那里登记


### 邮件列表


正如上面某些文档所描述的，大多数核心内核开发者都参与 Linux 内核邮件列表。关
如何订阅和退订该列表的详细信息可以在以下地址找到

	https://subspace.kernel.org/subscribing.html

网上很多不同的地方都有该邮件列表的归档。使用搜索引擎来查找这些归档。例如：

	https://lore.kernel.org/linux-kernel/

在你将想要提出的主题发到列表之前，强烈建议你先在归档中搜索该主题。许多已经详
讨论过的事情只记录在邮件列表归档中

大多数独立的内核子系统也有它们自己的独立邮件列表，用于开展各自的开发工作。请
参阅 MAINTAINERS 文件，了解这些列表分别对应哪些不同的组

许多列表托管kernel.org 上。关于它们的信息可以在以下地址找到

	https://subspace.kernel.org

请记住在使用这些列表时遵循良好的行为准则。虽然有点俗套，但下面的 URL 包含了一
与列表（或任何列表）互动的简单指南：

	https://subspace.kernel.org/etiquette.html

如果有多人回复你的邮件，收件人的 CC: 列表可能会变得相当长。在没有充分理由的情
下，不要CC: 列表中删除任何人，也不要只回复到列表地址。要习惯收到邮件两次
一次来自发送者，一次来自列表，不要试图通过添加花哨的邮件头来调优这一点，人们
不会喜欢

记住保留你回复内容的上下文和归属，在你的回复顶部保留“John Kernelhacker 写道……：
这样的行，并把你的陈述加在各个被引用的段落之间，而不是写在邮件顶部

如果你在邮件中附带补丁，请确保它们是Documentation/process/submitting-patches.rst <submittingpatches>
中所说的、可直接阅读的纯文本。内核开发者不想处理附件或被压缩的补丁；他们可
想对你补丁的每一行进行评论，而这只有在这种方式下才可行。请确保你使用的邮件程序
不会弄乱空格和制表符。一个很好的初次测试是把邮件发给你自己，并试着自己把你
补丁打上。如果不行，就去修好你的邮件程序，或者更换它，直到它能正常工作

最重要的是，请记住尊重其他订阅者


### 与社区协


内核社区的目标是提供尽可能好的内核。当你提交一个补丁等待接受时，它只会根据
技术价值被审查。那么，你应该期待什么呢

  - 批评
  - 评论
  - 要求修改
  - 要求说明理由
  - 沉默

请记住，这是让你的补丁进入内核的一部分。你必须能够接受对你补丁的批评和评论
从技术层面评估它们，然后要么重新修改你的补丁，要么对你认为那些改动不应被做的
理由给出清晰而简洁的说明。如果你的发布没有任何回应，等上几天再试一次，有时事情
会在海量的邮件中丢失

你不应该做什么？

  - 指望你的补丁毫无疑问地被接受
  - 变得有防备心
  - 忽视评论
  - 在没有做任何所要求的修改的情况下重新提交补

在一个寻求尽可能最佳技术解决方案的社区中，对于一个补丁有多大益处总会存在不同
意见。你必须乐于合作，并愿意调整你的想法以适应内核。或者至少愿意证明你的想
是值得的。请记住，只要愿意朝着正确的方案努力，犯错是可以接受的

你的第一个补丁的回复可能仅仅是一份你需要改正的十几个问题的清单，这很正常。这
**并不**意味着你的补丁不会被接受，*不是**针对你个人的。只需改正针对你补
提出的所有问题，然后重新发送即可


### 内核社区与公司结构的差异


内核社区的运作方式与大多数传统的公司开发环境不同。以下是一些你可以尝试去做
避免问题的清单：

  关于你提议的改动，好的说法：

    - "这解决了多个问题
    - "这删除了 2000 行代码
    - "这里有一个补丁，解释了我想描述的内容
    - "我在 5 种不同的体系结构上测试过…
    - "这是一系列小补丁，它们…
    - "这提高了典型机器上的性能…

  你应该避免说的坏说法

    - "我们AIX/ptx/Solaris 里就是这么做的，所以肯定好…
    - "我干这行 20 年了，所以…
    - "这对我公司赚钱是必需
    - "这是给我们的企业产品线用的
    - "这里是我 1000 页的设计文档，描述了我的想法"
    - "我已经在这上面干6 个月了…
    - "这是一5000 行的补丁，它…
    - "我重写了当前所有的一团糟，这就是…
    - "我有个截止日期，这个补丁现在就得被打上

内核社区与大多数传统软件工程工作环境不同的另一个方面，是互动的匿名性。使
电子邮件IRC 作为主要沟通形式的一个好处，是基于性别或种族的歧视的缺失。Linux
内核的工作环境对女性和少数群体是包容的，因为你在别人眼里只是一个邮件地址。国
化的方面也有助于拉平竞争环境，因为你无法根据一个人的名字猜测其性别。一个男人可
名叫 Andrea，一个女人可能名Pat。大多数Linux 内核工作过并表达过看法的女
都有积极的体验

语言障碍可能会给一些不习惯英语的人带来问题。为了在邮件列表上恰当地表达想法，可
需要很好地掌握这门语言，因此建议你在发送邮件之前检查你的邮件，确保它们在英语中
是通顺的


### 拆分你的改动


Linux 内核社区不会乐意一次性接收一大块代码。改动需要被恰当地引入、讨论，并拆
成微小、独立的部分。这几乎与公司习惯的做法完全相反。你的提议也应该在开发过程很
早的阶段就引入，这样你才能收到关于你在做什么的反馈。这也让社区觉得你是在和他们
协作，而不仅仅是把他们当作你新功能的倾倒场。不过，不要一次性给邮件列表50 
邮件，你的补丁系列几乎在所有时候都应该比那更小

拆分的原因如下：

1) 小的补丁增加了你的补丁被采用的可能性，因为它们不需要太多时间和精力去验
   正确性。一5 行的补丁维护者几乎看一眼就能打上。然而，一500 行的补丁
   可能需要数小时来审查正确性（所需时间随补丁大小呈指数级增长，或类似的关系）

   当出问题时，小的补丁也让调试变得非常容易。一个一个地回退补丁，比在一个大补丁
   被打上（并弄坏了什么东西）之后再剖析它要容易得多

2) 重要的不仅是发送小补丁，还要在提交之前重写和简化（或者仅仅是重新排序）补丁

下面是内核开发Al Viro 的一个类比：

	*"想象一个老师正在批改一个数学学生的作业。老师不想看到学生在得
	解法之前的试错过程。他们想看到最干净、最优雅的答案。好学生知道
	这一点，绝不会在最终解法之前提交她的中间工作

	*内核开发也是同样的道理。维护者和审查者不想看到解决问题过程中
	思考过程。他们想看到一个简单而优雅的解法*

在呈现一个优雅的解法和与社区协作、讨论你尚未完成的工作之间保持平衡可能很有挑战性
因此，在流程早期就获取反馈以改进你的工作是有好处的，但也要把你的改动保持在小
块中，这样它们可能已经可以被接受，即便你的整个任务还没有准备好被合并

还要意识到，发送那些尚未完成、并将“稍后修补”的补丁用于合并，是不可接受的


### 证明你的改动


除了拆分你的补丁之外，让 Linux 社区知道他们为什么要添加这个改动也非常重要。新
功能必须被证明是必要且有用的


### 记录你的改动


在发送你的补丁时，请特别注意你在邮件正文中写的内容。这些信息将成为补丁ChangeLog
信息，并会被永久保留供所有人查看。它应该完整地描述补丁，包含

  - 为什么这个改动是必要
  - 补丁中的总体设计思路
  - 实现细节
  - 测试结果

关于这些应该是什么样子更详细的信息，请参阅文档的 ChangeLog 章节

  "The Perfect Patch"
      https://www.ozlabs.org/~akpm/stuff/tpp.txt


所有这些事情有时非常难做到。可能需要数年（如果有可能的话）来完善这些实践。这
一个需要大量耐心和决心的持续改进过程。但不要放弃，这是可能的。许多人已经做到了，
而每个人都曾经与你现在所处的起点完全相同
