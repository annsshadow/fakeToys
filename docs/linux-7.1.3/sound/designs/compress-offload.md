## ALSA Compress-Offload API（压缩卸载接口）


Pierre-Louis.Bossart <pierre-louis.bossart@linux.intel.com>

Vinod Koul <vinod.koul@linux.intel.com>


## 概述（Overview）


自早期以来，ALSA API 的设计时就考虑了对 PCM 或恒定码率负载（如 IEC61937）的支持。以帧（frames）为单位的参数和返回值是一种常态，这使得扩展现有 API 以支持压缩数据流成为一项挑战。

近年来，音频数字信号处理器（DSP）被集成到了片上系统（SoC）设计中，DSP 也被集成到音频编解码器中。与基于主机的处理相比，在此类 DSP 上处理压缩数据可以显著降低功耗。Linux 对这种硬件的支持一直不是很好，主要原因是在主线内核中缺少一个通用的 API。

与其要求通过更改 ALSA PCM 接口来造成 API 兼容性的破坏，不如引入一个新的“压缩数据（Compressed Data）”API，为音频 DSP 提供控制和数据流接口。

该 API 的设计受到了 Intel Moorestown SoC 两年经验的启发，并做了许多修正，以便将该 API 合入主线内核而非 staging 树，并使其能为他人所用。


## 需求（Requirements）


主要需求如下：

- 字节计数与时间之间的分离。压缩格式可能在每个文件、每一帧都有头部，或者完全没有头部。负载大小可能逐帧变化。因此，在处理压缩数据时，无法可靠地估计音频缓冲区的持续时间。需要专门的机制来实现可靠的音视频同步，这要求精确报告在任意给定时刻已渲染的样本数量。

- 多种格式的处理。PCM 数据只需要指定采样率、通道数和每样本位数。相比之下，压缩数据有各种各样的格式。音频 DSP 可能还提供固件中嵌入的有限数量的音频编码器和解码器的支持，或者通过动态下载库来支持更多选择。

- 关注主流格式。该 API 提供支持用于音频和视频采集与播放的最流行格式。随着音频压缩技术的进步，可能会添加新的格式。

- 多种配置的处理。即使对于像 AAC 这样的给定格式，某些实现可能支持 AAC 多声道但不支持 HE-AAC 立体声。同样，WMA10 level M3 可能需要过多的内存和 CPU 周期。新的 API 需要提供一种通用方式来列出这些格式。

- 仅渲染/抓取（Rendering/Grabbing）。该 API 不提供任何硬件加速手段，即不将 PCM 样本返回用户空间进行额外处理。该 API 侧重于将压缩数据流式传输到 DSP，并假设解码后的样本被路由到物理输出或逻辑后端。

- 隐藏复杂性。现有的用户空间多媒体框架都对每种压缩格式有现成的枚举/结构。这个新的 API 假定存在一个平台特定的兼容层，以暴露、转换并利用音频 DSP 的能力，例如 Android HAL 或 PulseAudio sinks。从设计上看，普通应用程序不应使用此 API。


## 设计（Design）


新的 API 在流控制方面与 PCM API 共享许多概念。无论内容是什么，start、pause、resume、drain 和 stop 命令的语义都相同。

将内存环形缓冲区划分为一组片段（fragments）的概念借自 ALSA PCM API。但是，只能以字节为单位指定大小。

seek/trick 模式假定由主机处理。

不支持倒带/快进（rewinds/forwards）的概念。提交到环形缓冲区的数据无法作废，除非丢弃所有缓冲区。

压缩数据 API 对数据如何传输到音频 DSP 不做任何假设。从主内存到嵌入式音频簇的 DMA 传输，或到外部 DSP 的 SPI 接口都是可能的。与 ALSA PCM 的情况一样，暴露了一组核心例程；每个驱动实现者都必须编写一组必需例程的支持，并可能使用可选的例程。

主要的补充有：

get_caps
  该例程返回所支持的音频格式列表。在采集流上查询编解码器将返回编码器，而在播放流上则会列出解码器。

get_codec_caps
  对于每个编解码器，该例程返回一组能力。其目的是确保所有能力都对应于有效的设置，并最小化配置失败的风险。例如，对于像 AAC 这样复杂的编解码器，所支持的通道数可能取决于特定的 profile。如果能力是用单一描述符暴露的，可能会出现某些 profile/通道/格式的特定组合不受支持的情况。同样，嵌入式 DSP 的内存和 CPU 周期有限，某些实现可能会让能力列表变为动态的、并依赖于现有的工作负载。除了编解码器设置外，该例程还返回该实现所处理的最小缓冲区大小。此信息可以是 DMA 缓冲区大小、同步所需的字节数等的函数，用户空间可以利用它来确定在播放开始之前需要向环形缓冲区写入多少数据。

set_params
  该例程设置为特定编解码器选择的配置。参数中最重要的字段是编解码器类型；在大多数情况下解码器会忽略其他字段，而编码器会严格遵守这些设置。

get_params
  该例程返回 DSP 实际使用的设置。对设置的更改应当仍然是例外情况。

get_timestamp
  时间戳变成了一个多字段结构。它列出了已传输的字节数、已处理的样本数以及已渲染/抓取的样本数。所有这些值都可用于确定平均码率，判断环形缓冲区是否需要重新填充，或判断由于 DSP 上的解码/编码/IO 造成的延迟。

请注意，编解码器/profile/模式的列表取自 OpenMAX AL 规范，而不是重新发明轮子。
修改包括：
- 增加了 FLAC 和 IEC 格式
- 合并了编码器/解码器能力
- 将 profile/模式列为位掩码，以使描述符更紧凑
- 增加了用于解码器的 set_params（OpenMAX AL 中缺失）
- 增加了 AMR/AMR-WB 编码模式（OpenMAX AL 中缺失）
- 增加了 WMA 的格式信息
- 在需要时增加了编码选项（派生自 OpenMAX IL）
- 增加了 rateControlSupported（OpenMAX AL 中缺失）

## 无缝播放（Gapless Playback）


在播放整张专辑时，解码器有能力跳过编码器延迟和填充（padding），并直接从一个曲目的内容移动到另一个。最终用户可以将此感知为无缝播放，因为在从一个曲目切换到另一个时我们没有静音。

此外，由于编码可能会产生低强度的噪声。完美的无缝播放很难用所有类型的压缩数据达到，但对于大多数音乐内容效果良好。解码器需要知道编码器延迟和编码器填充。因此我们需要将此传递给 DSP。这些元数据是从 ID3/MP4 头部提取的，并不默认存在于比特流中，因此需要一个新的接口来将此信息传递给 DSP。另外，DSP 和用户空间需要从一首曲目切换到另一首，并开始使用第二首曲目的数据。

主要的补充有：

set_metadata
  该例程设置编码器延迟和编码器填充。解码器可用它来去除静音。这需要在曲目中的数据被写入之前设置。

set_next_track
  该例程告诉 DSP，在此之后发送的元数据和写入操作将对应于后续的曲目。

partial drain
  当到达文件末尾时调用。用户空间可以通知 DSP 已到达 EOF，现在 DSP 可以开始跳过填充延迟。另外，下一次写入的数据将属于下一首曲目。

无缝播放的顺序流程为：
- Open
- Get caps / codec caps
- Set params
- 设置第一首曲目的元数据
- 填充第一首曲目的数据
- 触发 start
- 用户空间完成所有发送，
- 通过发送 set_next_track 指示下一首曲目的数据
- 设置下一首曲目的元数据
- 然后调用 partial_drain 以刷新 DSP 中的大部分缓冲区
- 填充下一首曲目的数据
- DSP 切换到第二首曲目

（注意：partial_drain 与下一首曲目写入的顺序也可以颠倒）

## 不支持（Not supported）


- 对 VoIP/电路交换呼叫的支持不是本 API 的目标。对动态码率变化的支持将要求 DSP 与主机协议栈之间的紧密耦合，从而限制功耗节省。

- 不支持丢包隐藏（Packet-loss concealment）。这将需要一个额外的接口，以便解码器在传输过程中帧丢失时合成数据。这可能在未来被添加。

- 音量控制/路由不由本 API 处理。暴露压缩数据接口的设备将被视为常规的 ALSA 设备；音量变化和路由信息将通过常规的 ALSA kcontrols 提供。

- 嵌入式音频效果。无论输入是 PCM 还是压缩数据，都应以相同的方式启用此类效果。

- 多声道 IEC 编码。目前尚不清楚是否需要它。

- 如上所述，不支持编码/解码加速。可以将解码器的输出路由到采集流，甚至实现转码能力。这种路由将通过 ALSA kcontrols 启用。

- 音频策略/资源管理。该 API 不提供任何钩子来查询音频 DSP 的利用率，也不提供任何抢占机制。

- 没有 underrun/overrun 的概念。由于写入的字节本质上是压缩的，且写入/读取的数据并不直接按时间转换为渲染输出，因此这不处理 underrun/overrun，可能由用户库来处理。
