## 运行时锁正确性验证器


由 Ingo Molnar <mingo@redhat.com> 发起

Arjan van de Ven <arjan@linux.intel.com> 补充

### 锁类


验证器操作的基本对象是一"类"（class）锁。

一类锁是指一组在加锁规则上逻辑上相同的锁，即便这些锁可能有多个（甚至可能数以万计）实例。例如，inode 结构体中的某个锁属于一个类，而每个 inode 都有该类锁各自的实例。

验证器跟踪锁类的"使用状态"，并跟踪不同锁类之间的依赖关系。锁的使用情况表明锁在其 IRQ 上下文中的使用方式，而锁依赖可以理解为加锁顺序，其中 L1 -> L2 表示任务在持有 L1 的同时尝试获取 L2。从 lockdep 的角度看，这两个锁（L1 和 L2）未必相关；该依赖仅仅表示这个顺序曾经发生过。验证器持续努力证明锁的使用和依赖是正确的，若存在不正确则会输出 splat 报告。

锁类的行为由其所有实例共同构建：当某个锁类在启动后第一次被使用时，该类被注册，之后所有（后续的）实例都会映射到该类，因此它们的使用情况和依赖关系都会对该类产生贡献。当某个锁实例消失时，锁类并不会随之消失，但如果锁类所占用的内存空间（静态或动态）被回收，它也可能被移除，例如当一个模块被卸载或一个工作队列被销毁时就会发生这种情况。

### 状态


验证器跟踪锁类的使用历史，并将使用情况划分为（4 种使用 * n 个 STATE + 1）类：

其中 4 种使用可以是：

- '曾在 STATE 上下文中被持有'
- '曾在 STATE 上下文中作为读锁被持有'
- '曾在 STATE 启用时被持有'
- '曾在 STATE 启用时作为读锁被持有'

其中 n 个 STATE 定义在 kernel/locking/lockdep_states.h 中，目前包括：

- hardirq
- softirq

最后一个类别是：

- '曾被使用'                                       [ == !unused        ]

当加锁规则被违反时，这些使用位会以大括号括起的形式呈现在加锁错误信息中，总共包含 2 * n 个 STATE 位。

```

   modprobe/2287 is trying to acquire lock:
    (&sio_locks[i].lock){-.-.}, at: [<c02867fd>] mutex_lock+0x21/0x24

   but task is already holding lock:
    (&sio_locks[i].lock){-.-.}, at: [<c02867fd>] mutex_lock+0x21/0x24


```
对于某个给定的锁，位位置从左到右依次表示上述每个 STATE 下该锁及读锁（若存在）的使用情况，每个位位置显示的字符表示：

   ===  ===================================================
   '.'  在 irq 禁用且不在 irq 上下文中获取
   '-'  在 irq 上下文中获取
   '+'  在 irq 启用时获取
   '?'  在 irq 启用时的 irq 上下文中获取。
   ===  ===================================================

```

    (&sio_locks[i].lock){-.-.}, at: [<c02867fd>] mutex_lock+0x21/0x24
                         ||||
                         ||| \-> softirq 禁用且不在 softirq 上下文
                         || \--> 在 softirq 上下文中获取
                         | \---> hardirq 禁用且不在 hardirq 上下文
                          \----> 在 hardirq 上下文中获取


```
对于给定的 STATE，锁是否曾在该 STATE 上下文中被获取、以及该 STATE 是否启用，会产生如下表所示的四种可能情况。位字符能够指示截至报告时刻该锁属于哪一种确切情况。

  +--------------+-------------+--------------+
  |              | irq 启用    | irq 禁用     |
  +--------------+-------------+--------------+
  | 曾在 irq 中  |     '?'     |      '-'     |
  +--------------+-------------+--------------+
  | 从不在 irq 中|     '+'     |      '.'     |
  +--------------+-------------+--------------+

字符 '-' 表示 irq 被禁用，否则应为字符 '?'。类似地，'+' 也可作同样的推断。

未使用的锁（例如 mutex）不会成为导致错误的原因。


### 单锁状态规则：


锁被称为 irq-safe 是指它曾在 irq 上下文中被使用过，而锁被称为 irq-unsafe 是指它曾在 irq 启用时被获取过。

softirq-unsafe 的锁类自动也是 hardirq-unsafe。以下状态必须互斥：只允许设置其中之一

```

 <hardirq-safe> or <hardirq-unsafe>
 <softirq-safe> or <softirq-unsafe>

```
这是因为，如果一个锁可以在 irq 上下文中使用（irq-safe），那么它就不能在 irq 启用时被获取（irq-unsafe）。否则可能发生死锁。例如，在该锁被获取之后、释放之前，如果上下文被中断，这个锁会被尝试获取两次，从而产生死锁，即所谓的锁递归死锁。

验证器会检测并报告违反这些单锁状态规则的锁使用情况。

### 多锁依赖规则：


同一个锁类不能被获取两次，因为这可能导致锁递归死锁。

```

 <L1> -> <L2>
 <L2> -> <L1>

```
因为这可能导致死锁——即所谓的锁反转死锁——因为尝试获取这两个锁形成了一个环，可能导致两个上下文永久互相等待。验证器能够查找任意复杂度的此类依赖环，即获取锁操作之间可以存在任何其他加锁序列；验证器仍能判断这些锁是否可能以循环方式被获取。

此外，以下基于使用情况的锁依赖是不允许的

```

   <hardirq-safe>   ->  <hardirq-unsafe>
   <softirq-safe>   ->  <softirq-unsafe>

```
第一条规则源于这样一个事实：hardirq-safe 锁可能被 hardirq 上下文获取，从而中断一个 hardirq-unsafe 锁——因此可能导致锁反转死锁。类似地，softirq-safe 锁可能被 softirq 上下文获取，从而中断一个 softirq-unsafe 锁。

上述规则对内核中发生的任何加锁序列都强制执行：当获取一把新锁时，验证器会检查新锁与任何已持有锁之间是否存在规则违反。

当某个锁类改变其状态时，上面依赖规则的以下方面会被强制执行：

- 如果发现一个新的 hardirq-safe 锁，我们会检查它过去是否获取过任何 hardirq-unsafe 锁。

- 如果发现一个新的 softirq-safe 锁，我们会检查它过去是否获取过任何 softirq-unsafe 锁。

- 如果发现一个新的 hardirq-unsafe 锁，我们会检查过去是否有任何 hardirq-safe 锁获取过它。

- 如果发现一个新的 softirq-unsafe 锁，我们会检查过去是否有任何 softirq-safe 锁获取过它。

（同样，我们做这些检查的依据是：中断上下文可能中断任何 irq-unsafe 或 hardirq-unsafe 锁，这可能导致锁反转死锁——即使该锁场景在实践中尚未触发。）

### 例外：导致嵌套加锁的嵌套数据依赖


在少数情况下，Linux 内核会获取同一个锁类的多个实例。这类情况通常发生在同类对象之间存在某种层级结构时。在这些情况下，两个对象之间存在着固有的"自然"顺序（由层级结构的属性定义），内核会按这个固定顺序在每个对象上获取锁。

这种会导致"嵌套加锁"的对象层级结构的一个例子是"整盘"块设备对象和"分区"块设备对象；分区是整盘的"一部分"，只要始终以比分区锁更高的层级来获取整盘锁，加锁顺序就是完全正确的。验证器不会自动检测这种自然顺序，因为该顺序背后的加锁规则不是静态的。

为了让验证器了解这种正确的使用模式，新增了各种加锁原语的新版本，允许指定一个"嵌套层级"。下面是一个针对块设备 mutex 的调用示例，

```

  enum bdev_bd_mutex_lock_class
  {
       BD_MUTEX_NORMAL,
       BD_MUTEX_WHOLE,
       BD_MUTEX_PARTITION
  };

  mutex_lock_nested(&bdev->bd_contains->bd_mutex, BD_MUTEX_PARTITION);

```
在这种情况下，加锁是在一个已知为分区的 bdev 对象上进行的。

出于验证目的，验证器将以此类嵌套方式获取的锁视为一个独立的（子）类。

注意：当修改代码以使用 _nested() 原语时，务必小心并彻底检查层级结构映射是否正确；否则可能出现误报或漏报。

### 注解


有两种构造可用于注解并检查某些锁在何处、以及是否必须被持有：lockdep_assert_held**(&lock) 和 lockdep_**pin_lock(&lock)。

顾名思义，lockdep_assert_held* 系列宏断言某个特定的锁在某个时刻被持有（否则会产生 WARN()）。这种注解在内核中广泛使用，例如 kernel/sched/

```

  void update_rq_clock(struct rq *rq)
  {
	s64 delta;

	lockdep_assert_held(&rq->lock);
	[...]
  }

```
其中持有 rq->lock 是安全更新 rq 时钟所必需的。

另一系列宏是 lockdep_*pin_lock()，坦白说目前仅用于 rq->lock。尽管采用范围有限，但如果所关注的锁被"意外"释放，这些注解会产生 WARN()。这在调试带有回调的代码时尤为有用：上层假设某个锁仍然被持有，而下层却认为它或许可以释放并重新获取该锁（"无意中"引入竞态）。lockdep_pin_lock() 返回一个 'struct pin_cookie'，随后由 lockdep_unpin_lock() 用于检查

```

  static inline void rq_pin_lock(struct rq *rq, struct rq_flags *rf)
  {
	rf->cookie = lockdep_pin_lock(&rq->lock);
	[...]
  }

  static inline void rq_unpin_lock(struct rq *rq, struct rq_flags *rf)
  {
	[...]
	lockdep_unpin_lock(&rq->lock, rf->cookie);
  }

```
尽管关于加锁需求的注释可能提供有用信息，但注解所执行的运行时检查在调试加锁问题时是无价的，并且在检查代码时它们携带同样详细的级别。如有疑问，始终优先使用注解！

### 100% 正确性证明：


验证器实现了完美的、数学意义上的"闭包"（加锁正确性证明），其含义是：对于内核生命周期中至少发生过一次的每一个简单的、独立的单任务加锁序列，验证器以 100% 的确定性证明，这些加锁序列的任何组合与时序都不会导致任何一类与锁相关的死锁。[^1^]_

也就是说，复杂的多 CPU 和多任务加锁场景不必在实践中发生才能证明死锁：验证器只需这些简单的"组件"加锁链至少发生过一次（在任何时刻、任何任务/上下文中），就能证明正确性。（例如，通常需要 3 个以上 CPU 以及极不可能出现的任务、irq 上下文和时序组合才会发生的复杂死锁，在一台普通的、负载较轻的单 CPU 系统上同样可被检测到！）

这从根本上降低了内核加锁相关 QA 的复杂度：QA 期间需要做的是在内核中触发尽可能多的"简单"单任务加锁依赖，至少一次，以证明加锁正确性——而不必触发 CPU 之间每一种可能的加锁交互组合，外加每一种可能的 hardirq 和 softirq 嵌套场景（这在实际中是不可能的）。


    前提是验证器本身 100% 正确，且系统其他部分不会以任何方式破坏验证器的状态。
    我们还假设所有 NMI/SMM 路径 [甚至可能中断 hardirq 禁用代码路径] 都是正确的，且不会
    干扰验证器。我们还假设 64 位"链哈希"值对系统中每条锁链都是唯一的。此外，锁递归深度
    不得高于 20。

### 性能：


上述规则需要**海量**的运行时检查。如果对每一次加锁和每一次 irq 启用事件都这样做，系统将慢到几乎无法使用。检查的复杂度是 O(N^2)，因此即使只有几百个锁类，我们每次事件也要做上万次检查。

该问题通过只对任何给定的"加锁场景"（依次获取锁的唯一序列）检查一次来解决。内核维护一个简单的已持有锁栈，并计算一个轻量的 64 位哈希值，该哈希对每条锁链都是唯一的。当该链第一次被验证时，其哈希值被放入一个哈希表，该哈希表可以无锁方式检查。如果这条锁链之后再次出现，哈希表会告诉我们无需再次验证该链。

### 故障排查：


验证器最多跟踪 MAX_LOCKDEP_KEYS 个锁类。

```

	(DEBUG_LOCKS_WARN_ON(id >= MAX_LOCKDEP_KEYS))

```
默认情况下，MAX_LOCKDEP_KEYS 当前被设置为 8191，而典型的桌面系统拥有少于 1,000 个锁类，因此该警告通常源于锁类泄漏或未正确初始化锁。下面说明这两个问题：

1. 在运行验证器时反复加载和卸载模块会导致锁类泄漏。问题在于每次加载模块都会为该模块的锁创建一组新的锁类，但模块卸载并不会移除旧的锁类（关于为何不能重用锁类的讨论见下文）。因此，如果该模块被反复加载和卸载，锁类的数量最终会达到上限。

2. 使用包含大量锁且未显式初始化的数组等结构。例如，一个有 8192 个桶的哈希表，每个桶都有自己的 spinlock_t，将消耗 8192 个锁类——除非——每个 spinlock 在运行时被显式初始化，例如使用运行时 spin_lock_init() 而非 __SPIN_LOCK_UNLOCKED() 之类的编译期初始化器。未能正确初始化每个桶的 spinlock 必将导致锁类溢出。相比之下，一个对每个锁调用 spin_lock_init() 的循环会把所有 8192 个锁放入同一个锁类。

	这个故事的寓意是：你应该始终显式初始化你的锁。

有人可能会争辩说应该修改验证器以允许锁类被重用。然而，如果你想提出这个论点，先审查代码并想清楚所需的改动，记住待移除的锁类很可能已链接进锁依赖图中。事实证明，这做起来比说起来难。

当然，如果你真的耗尽了锁类，接下来要做的是找出有问题的锁类。首先，以下命令给出

```

	grep "lock-classes" /proc/lockdep_stats

```

```

	lock-classes:                          748 [max: 8191]

```
如果分配的数量（上例为 748）随时间持续增长，则可能存在泄漏。可以使用以下命令来

```

	grep "BD" /proc/lockdep

```
运行该命令并保存输出，然后与稍后再次运行该命令的输出进行比较，以找出泄漏者。同样的输出也可以帮助你发现省略了运行时锁初始化的情形。

### 递归读锁：


本文档其余部分试图证明某类环等价于死锁可能性。

有三种类型的加锁者：写者（即独占加锁者，如 spin_lock() 或 write_lock()）、非递归读者（即共享加锁者，如 down_read()）和递归读者（递归共享加锁者，如 rcu_read_lock()）。在文档余下部分我们使用以下符号表示这些加锁者：

	W or E:	表示写者（独占加锁者）。
	r:	表示非递归读者。
	R:	表示递归读者。
	S:	表示所有读者（非递归 + 递归），因为二者都是共享加锁者。
	N:	表示写者与非递归读者，因为二者都不是递归的。

显然，N 即"r 或 W"，S 即"r 或 R"。

正如其名，递归读者是允许在同一锁实例的另一个读者的临界区内部获取的加锁者，换句话说，它允许一个锁实例的嵌套读侧临界区。

而非递归读者如果在同一锁实例的另一个读者的临界区内部尝试获取，则会导致自死锁。

递归读者与非递归读者之间的区别在于：递归读者只会被写锁**持有者**阻塞，而非递归读者可能被写锁**等待者**阻塞。考虑以下情形

```

	TASK A:			TASK B:

	read_lock(X);
				write_lock(X);
	read_lock_2(X);

```
任务 A 首先通过 read_lock() 获取 X 上的读者锁（无论递归与否）。当任务 B 尝试获取 X 上的写者锁时，它会被阻塞并成为 X 上写者锁的等待者。如果 read_lock_2() 是递归读者，任务 A 将继续推进，因为写者等待者不会阻塞递归读者，因此不会发生死锁。然而，如果 read_lock_2() 是非递归读者，它将被写者等待者 B 阻塞，从而导致自死锁。

### 同一锁实例上读者/写者之间的阻塞条件：


简单来说有四种阻塞条件：

1. 写者阻塞其他写者。
2. 读者阻塞写者。
3. 写者阻塞递归读者和非递归读者。
4. 而读者（无论是否递归）不会阻塞其他递归读者，但可能阻塞非递归读者（因为可能存在共存的写者等待者）

阻塞条件矩阵，Y 表示行阻塞列，N 表示相反。

	+---+---+---+---+
	|   | W | r | R |
	+---+---+---+---+
	| W | Y | Y | Y |
	+---+---+---+---+
	| r | Y | Y | N |
	+---+---+---+---+
	| R | Y | Y | N |
	+---+---+---+---+

	(W: 写者, r: 非递归读者, R: 递归读者)


递归地获取。与非递归读锁不同，递归读锁只会受当前写锁**持有者**阻塞，而不会受写锁

```

	TASK A:			TASK B:

	read_lock(X);

				write_lock(X);

	read_lock(X);

```
对于递归读锁来说这不是死锁，因为当任务 B 等待锁 X 时，第二个 read_lock() 无需等待，因为它是递归读锁。然而，如果 read_lock() 是非递归读锁，那么上述情形就是死锁，因为即使任务 B 中的 write_lock() 无法获取该锁，它也可以阻塞任务 A 中的第二个 read_lock()。

注意，一个锁可以是写锁（独占锁）、非递归读锁（非递归共享锁）或递归读锁（递归共享锁），具体取决于用于获取它的加锁操作（更具体地说，lock_acquire() 的 'read' 参数值）。换句话说，单个锁实例根据获取函数有三类获取方式：独占、非递归读和递归读。

为简洁起见，我们将写锁和非递归读锁统称为"非递归"锁，将递归读锁称为"递归"锁。

递归锁之间互不阻塞，而非递归锁之间会互相阻塞（这一点对于两个非递归读锁同样成立）。非递归锁可以阻塞对应的递归锁，反之亦然。

```

	TASK A:			TASK B:

	read_lock(X);
				read_lock(Y);
	write_lock(Y);
				write_lock(X);

```
任务 A 在等待任务 B 执行 read_unlock() Y，而任务 B 在等待任务 A 执行 read_unlock() X。

### 依赖类型与强依赖路径：


锁依赖记录一对锁的获取顺序，由于加锁者有三种类型，理论上存在 9 种锁依赖，但我们可以证明 4 种锁依赖就足以进行死锁检测。

```

	L1 -> L2

```
，这意味着 lockdep 在运行时曾看到在同一上下文中先持有 L1 再持有 L2。在死锁检测中，我们关心的是在持有 L1 时是否会在 L2 上被阻塞，换句话说，是否存在一个加锁者 L3，使得 L1 阻塞 L3 且 L2 被 L3 阻塞。因此我们只关心 1) L1 阻塞什么，以及 2) 什么阻塞 L2。于是我们可以把 L1 上的递归读者和非递归读者合并（因为二者阻塞的类型相同），也可以把 L2 上的写者和非递归读者合并（因为二者被阻塞的类型相同）。

通过以上合并简化，lockdep 图中有 4 种依赖边：

1) -(ER)->：
	    独占写者到递归读者的依赖，"X -(ER)-> Y" 表示
	    X -> Y 且 X 是写者、Y 是递归读者。

2) -(EN)->：
	    独占写者到非递归加锁者的依赖，"X -(EN)-> Y" 表示
	    X -> Y 且 X 是写者、Y 是写者或非递归读者。

3) -(SR)->：
	    共享读者到递归读者的依赖，"X -(SR)-> Y" 表示
	    X -> Y 且 X 是读者（递归与否皆可）、Y 是递归读者。

4) -(SN)->：
	    共享读者到非递归加锁者的依赖，"X -(SN)-> Y" 表示
	    X -> Y 且 X 是读者（递归与否皆可）、Y 是写者或
	    非递归读者。

注意，给定两把锁，它们之间可能存在多种依赖，

```

	TASK A:

	read_lock(X);
	write_lock(Y);
	...

	TASK B:

	write_lock(X);
	write_lock(Y);

```
，在依赖图中我们同时有 X -(SN)-> Y 和 X -(EN)-> Y。

我们用 -(xN)-> 表示 -(EN)-> 或 -(SN)-> 的边，类似地 -(Ex)->、-(xR)-> 和 -(Sx)-> 也如此表示。

"路径"是图中一系列连续的依赖边。我们定义"强"路径，表示路径中每个依赖都是强依赖，即该路径不存在两个连续边（依赖）为 -(xR)-> 和 -(Sx)-> 的情况。换句话说，"强"路径是通过锁依赖从一把锁走到另一把锁的路径，如果 X -> Y -> Z 在路径中（其中 X、Y、Z 为锁），且从 X 到 Y 的走法是经由 -(SR)-> 或 -(ER)-> 依赖，那么从 Y 到 Z 的走法不可经由 -(SN)-> 或 -(SR)-> 依赖。

我们将在下一节看到该路径为何被称为"强"。

### 递归读死锁检测：


我们现在证明两件事：

引理 1：

如果存在一个闭合的强路径（即强环），那么存在一组会导致死锁的加锁序列。也就是说，强环对于死锁检测是充分的。

引理 2：

如果不存在闭合的强路径（即强环），那么不存在会导致死锁的加锁序列组合。也就是说，强环对于死锁检测是必要的。

有了这两个引理，我们可以轻易地说闭合强路径对于死锁既是充分的也是必要的，因此闭合强路径等价于死锁可能性。由于闭合强路径代表可能导致死锁的依赖链，而考虑到存在不会导致死锁的依赖环，我们称之为"强"。

充分性证明（引理 1）：

```

	L1 -> L2 ... -> Ln -> L1

```

```

	L1 -> L2
	L2 -> L3
	...
	Ln-1 -> Ln
	Ln -> L1

```
我们现在可以构造一组会导致死锁的加锁序列：

首先让一个 CPU/任务获取 L1 -> L2 中的 L1，然后让另一个获取 L2 -> L3 中的 L2，依此类推。此后，Lx -> Lx+1 中的所有 Lx 都由不同的 CPU/任务持有。

然后，由于我们有 L1 -> L2，L1 的持有者将尝试获取 L1 -> L2 中的 L2，然而 L2 已被另一个 CPU/任务持有，且 L1 -> L2 与 L2 -> L3 不是 -(xR)-> 和 -(Sx)->（强的定义），这意味着 L1 -> L2 中的 L2 是一个非递归加锁者（被任何人阻塞）或 L2 -> L3 中的 L2 是写者（阻塞任何人），因此 L1 的持有者无法获取 L2，它必须等待 L2 的持有者释放。

此外，对 L2 的持有者可得类似结论：它必须等待 L3 的持有者释放，依此类推。现在我们可以证明 Lx 的持有者必须等待 Lx+1 的持有者释放，注意到 Ln+1 就是 L1，于是我们便有了循环等待的情形，谁也无法推进，因此是死锁。

必要性证明（引理 2）：

引理 2 等价于：如果存在死锁场景，那么在依赖图中必定存在一个强环。

根据 Wikipedia[^1^]，如果存在死锁，那么必定存在循环等待的情形，即存在 N 个 CPU/任务，其中 CPU/任务 P1 在等待 P2 持有的锁，P2 在等待 P3 持有的锁，……Pn 在等待 P1 持有的锁。我们将 Px 正在等待的锁命名为 Lx，由于 P1 在等待 L1 且持有 Ln，因此依赖图中有 Ln -> L1。类似地，依赖图中有 L1 -> L2、L2 -> L3、……、Ln-1 -> Ln，这意味着我们

```

	Ln -> L1 -> L2 -> ... -> Ln

```
，现在我们证明这个环是强的：

对于锁 Lx，Px 贡献了依赖 Lx-1 -> Lx，Px+1 贡献了依赖 Lx -> Lx+1，由于 Px 在等待 Px+1 释放 Lx，因此 Px+1 上的 Lx 是读者且 Px 上的 Lx 是递归读者是不可能的，因为读者（无论是否递归）不会阻塞递归读者，因此 Lx-1 -> Lx 与 Lx -> Lx+1 不可能构成 -(xR)-> -(Sx)-> 对，这对于环中的任何锁都成立，因此该环是强的。
