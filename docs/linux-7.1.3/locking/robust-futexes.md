## robust futexes 是什么

:Started by: Ingo Molnar <mingo@redhat.com>

### 背景

什么是 robust futex？要回答这个问题，我们首先要理解什么是 futex：普通的 futex 是一种特殊的锁，在无竞争的情况下，可以在用户空间直接获取和释放，而无需进入内核。

“健壮性（Robustness）”是指处理在持有锁期间发生崩溃的情况：如果一个进程在持有一个 pthread_mutex_t 锁（同时该锁也与其他进程共享，例如 yum 在持有 pthread_mutex_t 时段错误，或被 kill -9）时过早退出，那么等待该锁的等待者需要被告知：该锁的最后拥有者以一种非正常的方式退出了。

futex 本质上是一个用户空间地址，例如一个 32 位的锁变量字段。如果用户空间检测到竞争（锁已被其他线程持有，且另有线程也想获取它），就会把锁标记为“有等待者挂起”的值，并使用 sys_futex(FUTEX_WAIT) 系统调用等待对方释放该锁。内核会在内部创建一个“futex 队列”，以便稍后将等待者与唤醒者配对——双方无需互相知晓。当持有锁的线程释放 futex 时，它会通过变量值注意到有等待者挂起，于是调用 sys_futex(FUTEX_WAKE) 系统调用来唤醒它们。一旦所有等待者都获取并释放了锁，futex 就重新回到“无竞争”状态，内核中也不再关联任何状态。内核会完全忘记该地址上曾经存在过 futex。这种方式使得 futex 非常轻量且可扩展。

### robust futex 的新方法

为了解决这类问题，人们创建了“健壮互斥锁（robust mutex）”的用户空间 API：如果锁的拥有者过早退出，pthread_mutex_lock() 会返回一个错误值，此时新的拥有者可以自行决定：被该锁保护的数据能否安全恢复。

在常见情况下，do_exit() 时没有注册任何列表，因此 robust futex 的代价只是一个简单的 current->robust_list != NULL 比较。如果线程已经注册了列表，那么通常该列表是空的。如果线程/进程以某种不正确的方式崩溃或终止，那么列表可能非空：在这种情况下，内核会小心地遍历列表（不信任它），并将本线程拥有的所有锁标记为 FUTEX_OWNER_DIED 位，并唤醒一个等待者（如果有的话）。

然而，基于 futex 的互斥锁存在一个重大的概念性问题：销毁拥有者任务的是内核（例如由于段错误），但内核却无法协助清理：如果没有“futex 队列”（而且在大多数情况下确实没有，因为 futex 是快速轻量的锁），那么内核就没有任何信息来清理被持有的锁！用户空间同样没有机会清理该锁——毕竟崩溃的正是用户空间，它根本没有机会去做清理。这便是一个两难困境（Catch-22）。

Ulrich Drepper 已经为这种新机制实现了必要的 glibc 支持，从而完全启用了 robust mutex。

在实践中，例如当 yum 被 kill -9（或发生段错误）时，需要重启系统才能释放那个基于 futex 的锁。这也是针对 yum 的主要 bug 报告之一。

 - 它快得多：在线程退出时，不需要遍历每个 vma（！），而基于 VM 的方法必须这样做。只执行一个非常简单的“列表是否为空”操作。

为了解决 vma 方法的问题，传统的做法是扩展 vma（虚拟内存区域描述符）的概念，使其具有“本区域附带有待处理的 robust futex”的语义。这种方法需要为 sys_futex() 新增 3 个系统调用变体：FUTEX_REGISTER、FUTEX_DEREGISTER 和 FUTEX_RECOVER。在 do_exit() 时，内核会搜索所有 vma，查看它们是否设置了 robust_head。这种方法遗留了两个根本性问题：

 - 不需要资源限制。
 - 它的加锁与竞态场景相当复杂。基于 vma 的方法
 - 不需要内核空间的恢复调用（FUTEX_RECOVER）。

 - 实现和加锁都是“显而易见”的，并且不与 VM 交互。
 - 它必须在每次 sys_exit() 时（按线程）扫描每一个 vma！

### 性能

第二个缺点才是真正致命的：在 Linux 上 pthread_exit() 大约只需 1 微秒，但如果存在成千（甚至上万）个 vma，每次 pthread_exit() 就会耗时一毫秒甚至更多，同时还会彻底破坏 CPU 的 L1 和 L2 缓存！

 - 设置了 FUTEX_WAIT（有竞争的 mutex）：130 毫秒

即使在普通的进程 sys_exit_group() 调用中，这一点也非常明显：内核必须无条件地执行 vma 扫描！（这是因为内核并不知道有多少 robust futex 需要清理，因为某个 robust futex 可能已在另一个任务中注册，而该 futex 变量可能只是被 mmap() 进了本进程的地址空间）

### 实现细节

如此巨大的开销迫使内核引入了 CONFIG_FUTEX_ROBUST 配置项，以便普通内核可以将其关闭；但更糟的是：这种开销使得 robust futex 对于任何通用的 Linux 发行版都不切实际。

所以必须有所行动。

### New approach to robust futexes

 sys_set_robust_list(struct robust_list_head __user *head,
                     size_t len);

这种新方法的核心，是用户空间持有的一份“每线程私有”的 robust 锁列表（由 glibc 维护），该列表通过一个新系统调用注册到内核（此注册在每个线程的生命周期内至多发生一次）。在 do_exit() 时，内核检查这份用户空间列表：是否有需要清理的 robust futex 锁？

列表注册非常快：指针只是被存入 current->robust_list。[注意，将来如果 robust futex 变得普遍，我们可以扩展 sys_clone() 为新线程注册一个 robust-list 头，而不需要另一个系统调用。]

在常见情况下，do_exit() 时没有注册任何列表，因此 robust futex 的代价只是一个简单的 current->robust_list != NULL 比较。如果线程已经注册了列表，那么通常该列表是空的。如果线程/进程以某种不正确的方式崩溃或终止，那么列表可能非空：在这种情况下，内核会小心地遍历列表（不信任它），并将本线程拥有的所有锁标记为 FUTEX_OWNER_DIED 位，并唤醒一个等待者（如果有的话）。

该列表在 do_exit() 时保证是私有的、每线程的，因此内核可以无锁地访问它。

不过仍有可能存在一种竞态：由于向列表的添加和移除是在 glibc 获取 futex 之后进行的，因此线程（或进程）有可能在这几指令的窗口内死亡，从而使 futex 悬空。为防止这种可能，用户空间（glibc）还维护一个简单的每线程“list_op_pending”字段，以便在线程在获取锁之后、却尚未将自己加入列表之前死亡时，内核仍能进行清理。glibc 在尝试获取 futex 之前设置该 list_op_pending 字段，并在列表添加（或移除）完成后清除它。

### 测试、架构支持

这就是所需的全部——robust futex 其余所有的清理工作都在用户空间完成（与之前的补丁一样）。

我已经在 x86 和 x86_64 上测试了新的系统调用，并确保即使用户空间列表被故意破坏，对其的解析也是健壮的（ ;-) ）。

Ulrich Drepper 已经为这种新机制实现了必要的 glibc 支持，从而完全启用了 robust mutexes。

 - 它快得多：在线程退出时，不需要遍历每个 vma（！），而基于 VM 的方法必须这样做。只执行一个非常简单的“列表是否为空”操作。
