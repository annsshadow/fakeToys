## 轻量级 PI-futex


我们称其为轻量级，有 3 个原因：

 - 在用户空间快速路径中，启用 PI 的 futex 根本不涉及任何内核工作（或任何其它
   PI 复杂性）。无需注册，无需额外的内核调用——只是用户空间中的纯快速原子操作。

 - 即使在慢速路径中，系统调用和调度模式也与普通 futex 非常相似。

 - 内核内的 PI 实现围绕互斥锁抽象进行了精简，并带有严格规则以保持实现相对简单：
   只有一个所有者可以拥有一个锁（即不支持读写锁），只有所有者可以解锁一个锁，
   不支持递归加锁等。

### 优先级继承——为什么？


简短的回答：用户空间 PI 有助于实现/改善用户空间应用程序的确定性。在最好情况下，
它可以帮助实现确定性以及良好受限的延迟。即使在最坏情况下，PI 也能改善与加锁相关的
应用延迟的统计分布。

### 更长的回答


首先，在多个任务之间共享锁是一种常见的编程技术，往往无法用无锁算法替代。正如我们
在内核中看到的（它本身就是一个相当复杂的程序），无锁结构更像是例外而非常态——当前
共享数据结构的无锁代码与加锁代码的比例大约在 1:10 到 1:100 之间。无锁很难，而无锁
算法的复杂性常常危及对所述代码进行稳健审阅的能力。也就是说，关键 RT 应用常常选择锁
结构来保护关键数据结构，而不是无锁算法。此外，有些情况（如共享硬件或其它资源限制）
下，无锁访问在数学上是不可能的。

媒体播放器（如 Jack）是一个合理的应用设计示例，它使用多个任务（具有多个优先级级别）
共享短期持有的锁：例如，一个高优先级音频播放线程，配合中优先级的构造音频数据线程和
低优先级的显示颜色处理线程。再加上视频和解码，我们就有更多的优先级级别。

因此，一旦我们接受同步对象（锁）是生活中不可避免的事实，一旦我们接受多任务用户空间
应用有非常合理的使用锁的期望，我们就必须思考如何向用户空间提供确定性加锁实现的选项。

大多数反对做优先级继承的技术论据只适用于内核空间锁。但用户空间锁不同，在那里我们
无法在临界区中禁用中断或使任务不可抢占，因此"使用自旋锁"的论点不适用（用户空间
自旋锁与其它用户空间加锁构造有着相同的优先级反转问题）。事实是，目前能为用户空间锁
（如基于 futex 的 pthread 互斥锁）提供良好确定性的唯一技术就是优先级继承：

当前（没有 PI），如果一个高优先级和一个低优先级任务共享一把锁[这对于大多数非平凡的
RT 应用是一个很常见的场景]，即使所有临界区都被仔细编写为确定性的（即所有临界区持续
时间短且仅执行有限数量的指令），内核也无法保证高优先级任务的任何确定性执行：任何
中优先级的任务都可能在低优先级任务持有共享锁并执行临界区时抢占它，并可能无限期地延迟
它。

### 实现


如前所述，启用 PI 的 pthread 互斥锁的用户空间快速路径根本不涉及内核工作——它们的
行为相当类似于普通的基于 futex 的锁：值为 0 表示未锁，值为 TID 表示已锁。（这与
基于链表的健壮 futex 使用的方法相同。）用户空间使用原子操作来锁定/解锁这些互斥锁，
而不进入内核。

为了处理慢速路径，我们添加了两个新的 futex 操作：

  - FUTEX_LOCK_PI
  - FUTEX_UNLOCK_PI

如果加锁快速路径失败（即，从 0 到 TID 的原子转换失败），则调用 FUTEX_LOCK_PI。内核
完成所有剩余工作：如果 futex 地址上尚未挂载 futex 队列，则代码查找拥有该 futex 的
任务（它已经把自己的 TID 放入了 futex 值中），并将一个"PI 状态"结构挂载到 futex 队列。
pi_state 包含一个 rt-mutex，它是一个可感知 PI 的、基于内核的同步对象。'另一个'任务被
设为 rt-mutex 的所有者，并且 FUTEX_WAITERS 位在 futex 值中被原子地设置。然后该任务
尝试锁定 rt-mutex，并在其上阻塞。一旦它返回，它就获取了互斥锁，并将 futex 值设为
自己的 TID 后返回。用户空间没有其它工作要做——它现在拥有锁，且 futex 值包含
FUTEX_WAITERS|TID。

如果解锁侧快速路径成功（即，用户空间成功地将 futex 值从 TID 原子转换为 0），则不会
触发任何内核工作。

如果解锁快速路径失败（因为 FUTEX_WAITERS 位被设置），则调用 FUTEX_UNLOCK_PI，内核
代表用户空间解锁 futex——并且它还会解锁挂载的 pi_state->rt_mutex，从而唤醒任何潜在的
等待者。

注意，在这种方法下，与之前的 PI-futex 方法相反，没有对 PI-futex 的事先"注册"。（由于
pthread 互斥锁现有的 ABI 属性，这本来也不太可能实现。）

此外，在这种方案下，"健壮性"和"PI"是 futex 的两个正交属性，四种组合都是可能的：
futex、robust-futex、PI-futex、robust+PI-futex。

关于优先级继承的更多细节可以在 Documentation/locking/rt-mutex.rst 中找到。
