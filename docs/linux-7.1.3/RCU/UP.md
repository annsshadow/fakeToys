
## 单处理器（UP）系统上的 RCU

一个常见的误解是：在 UP 系统上，call_rcu() 原语可以立即调用它的函数。这种误解的
依据是，既然只有一个 CPU，就不需要等待其他任何事情完成，因为没有其他 CPU 可供
其他事情发生。尽管这种做法在出乎意料多的情况下**勉强**能工作，但总体上它是一个
非常糟糕的主意。本文档给出三个例子，确切地说明这个主意有多糟糕。

### 例 1：softirq 自杀

假设一个基于 RCU 的算法在进程上下文中扫描一个包含元素 A、B 和 C 的链表，并且
可以在 softirq 上下文中删除这个链表中的元素。假设进程上下文的扫描正在引用元素 B
时，被 softirq 处理打断，该处理删除了元素 B，然后调用 call_rcu() 以在一个宽限期
之后释放元素 B。

那么，如果 call_rcu() 直接调用它的参数，那么在从 softirq 返回时，链表扫描会发现自己
正在引用一个刚被释放的元素 B。这种情况会大大缩短你内核的"预期寿命"。

如果 call_rcu() 是从硬件中断处理程序中调用的，也会发生同样的问题。

### 例 2：函数调用的致命性

当然，可以让 call_rcu() 仅在从进程上下文调用时才直接调用它的参数，从而避免前面
例子描述的"自杀"。然而，这也可能以类似的方式失败。

假设一个基于 RCU 的算法再次在进程上下文中扫描包含元素 A、B 和 C 的链表，但它在
扫描时对每个元素调用一个函数。进一步假设这个函数从链表中删除元素 B，然后将其
传递给 call_rcu() 以延迟释放。这可能有点不太常规，但它是完全合法的 RCU 用法，
因为 call_rcu() 必须等待一个宽限期过去。因此，在这种情况下，允许 call_rcu() 立即
调用它的参数会导致它无法兑现 RCU 的基本保证，即 call_rcu() 会将其参数的调用推迟
到当前正在执行的所有 RCU 读端临界区都完成之后。

### 例 3：死锁致死

假设在持有锁的情况下调用 call_rcu()，并且回调函数必须获取同一把锁。在这种情况下，
如果 call_rcu() 直接调用该回调，其结果将是自死锁，**即使**这次调用发生在一个宽限期
之后、来自后来的 call_rcu() 调用。

在某些情况下，可以重构代码，将 call_rcu() 推迟到锁释放之后。但是，有些情况下这会
相当难看：

1. 如果需要在同一个临界区内将若干条目传递给 call_rcu()，那么代码需要先把它们
	创建成一个列表，然后在锁释放后遍历这个列表。

2. 在某些情况下，锁会跨某个内核 API 持有，因此将 call_rcu() 推迟到锁释放，
	要求数据条目通过一个公共 API 向上传递。保证回调在没有任何锁被持有时
	被调用，远比修改这些 API 以允许任意数据条目向上回传要好得多。

如果 call_rcu() 直接调用回调，就需要痛苦的锁限制或 API 变更。

值得注意的是，用户空间 RCU 实现**确实**允许 call_rcu() 直接调用回调，但前提是
这些回调入队以来已经过了一个完整的宽限期。之所以这样，是因为某些用户空间环境
受到了极度限制。尽管如此，强烈建议编写用户空间 RCU 实现的人避免从 call_rcu() 中
调用回调，从而获得上面提到的避免死锁的好处。

### 总结

允许 call_rcu() 立即调用它的参数会破坏 RCU，即使在 UP 系统上也是如此。所以不要
这样做！即使在 UP 系统上，RCU 基础设施也**必须**尊重宽限期，并且**必须**在一个
不持有任何锁的已知环境中调用回调。

注意，在 UP 系统上（包括在 UP 系统上运行的 PREEMPT SMP 构建），synchronize_rcu()
立即返回是**安全的**。

快速测验 #3：
	为什么在运行可抢占 RCU 的 UP 系统上，synchronize_rcu() 不能立即返回？

Answer to Quick Quiz #1：
	为什么在这种情况下调用 synchronize_rcu() 是**不**合法的？

	因为调用函数正在扫描一个受 RCU 保护的链表，因此处于一个 RCU 读端临界区
	之中。因此，被调用的函数是在一个 RCU 读端临界区内被调用的，不允许阻塞。

Answer to Quick Quiz #2：
	RCU 回调必须遵守什么样的锁限制？

	在 RCU 回调中获取的任何锁，都必须在其他地方使用自旋锁原语的 _bh 变体来
	获取。例如，如果 "mylock" 被一个 RCU 回调获取，那么进程上下文中对该锁的
	获取必须使用类似 spin_lock_bh() 的方式来获取。请注意，使用自旋锁的 _irq
	变体（例如 spin_lock_irqsave()）也是可以的。

	如果进程上下文代码简单地使用 spin_lock()，那么由于 RCU 回调可以从 softirq
	上下文调用，该回调可能会从打断了进程上下文临界区的 softirq 中被调用。这将
	导致自死锁。

	这个限制看起来可能有些无端，因为极少有 RCU 回调直接获取锁。然而，大量
	RCU 回调会**间接**获取锁，例如通过 kfree() 原语。

Answer to Quick Quiz #3：
	为什么在运行可抢占 RCU 的 UP 系统上，synchronize_rcu() 不能立即返回？

	因为其他某个任务可能在一个 RCU 读端临界区的中途被抢占了。如果 synchronize_rcu()
	简单地立即返回，它会过早地发出宽限期结束的信号，当那个其他线程重新开始运行时，
	这会令它大吃一惊。
