## 一次穿越 TREE_RCU 宽限期内存排序的旅程


2017 年 8 月 8 日

本文由 Paul E. McKenney 贡献

## 引言


本文档粗略地以可视化的方式概述了 Tree RCU 的宽限期（grace period）内存
排序保证是如何提供的。

## 什么是 Tree RCU 的宽限期内存排序保证？


RCU 宽限期为非空闲、非离线的代码提供了极强内存排序保证。

给定 RCU 宽限期结束后发生的任何代码，都保证能看到在该宽限期开始之前、
位于 RCU 读端临界区之内的所有访问的效果。

类似地，给定 RCU 宽限期开始之前发生的任何代码，都保证不会看到在该宽限期
结束之后、位于 RCU 读端临界区之内的所有访问的效果。

请注意，RCU-sched 读端临界区包含了任何禁止抢占（preemption）的代码区域。
鉴于每条单独的机器指令都可以被视为一段极小的禁止抢占代码区域，可以将
`synchronize_rcu()` 看作是加了料的 `smp_mb()`。

RCU 更新者利用这一保证，将其更新拆分为两个阶段，其中一个在宽限期之前
执行，另一个在宽限期之后执行。在最常见的用例中，阶段一从一个受 RCU 保护
的链表数据结构中移除一个元素，阶段二则释放该元素。为使此机制工作，任何
已经观察到阶段一更新之前状态（常见情况下即移除）的读者，都不能观察到
阶段二更新之后（常见情况下即释放）的状态。

RCU 实现使用由锁保护的临界区、内存屏障和每 CPU 处理的网络来提供这一保证，
如下面各节所述。

## Tree RCU 宽限期内存排序的构建模块


RCU 宽限期内存排序的主力是 `rcu_node` 结构的 `->lock` 临界区。这些临界区
使用辅助函数来获取锁，包括 `raw_spin_lock_rcu_node()`、
`raw_spin_lock_irq_rcu_node()` 和 `raw_spin_lock_irqsave_rcu_node()`。
它们对应的释放锁函数是 `raw_spin_unlock_rcu_node()`、
`raw_spin_unlock_irq_rcu_node()` 和
`raw_spin_unlock_irqrestore_rcu_node()`。为完整起见，还提供了
`raw_spin_trylock_rcu_node()`。关键点在于，锁获取函数（包括
`raw_spin_trylock_rcu_node()`）在成功获取锁之后都会立即调用
`smp_mb__after_unlock_lock()`。

因此，对于任意给定的 `rcu_node` 结构，发生在上述某个释放锁函数之前的任何
访问，所有 CPU 都会视为发生在上述某个之后的锁获取函数之后的任何访问之前。
此外，在某个给定 CPU 上，发生在上述某个释放锁函数之前的任何访问，所有
CPU 都会视为发生在该 CPU 上执行的、上述某个之后的锁获取函数之后的任何
访问之前，即使该释放锁和锁获取函数操作的是不同的 `rcu_node` 结构。

Tree RCU 利用这两个排序保证，在所有以某种方式参与了该宽限期的 CPU 之间
形成一个排序网络，包括在所讨论的宽限期内上线的或离线的任何 CPU。

以下 litmus 测试展示了这些的排序效果
```

    1 int x, y, z;
    2
    3 void task0(void)
    4 {
    5   raw_spin_lock_rcu_node(rnp);
    6   WRITE_ONCE(x, 1);
    7   r1 = READ_ONCE(y);
    8   raw_spin_unlock_rcu_node(rnp);
    9 }
   10
   11 void task1(void)
   12 {
   13   raw_spin_lock_rcu_node(rnp);
   14   WRITE_ONCE(y, 1);
   15   r2 = READ_ONCE(z);
   16   raw_spin_unlock_rcu_node(rnp);
   17 }
   18
   19 void task2(void)
   20 {
   21   WRITE_ONCE(z, 1);
   22   smp_mb();
   23   r3 = READ_ONCE(x);
   24 }
   25
   26 WARN_ON(r1 == 0 && r2 == 0 && r3 == 0);

```
`WARN_ON()` 是在“时间的终点”求值的，即所有变更都已传播到整个系统之后。
如果没有获取函数所提供的 `smp_mb__after_unlock_lock()`，这个 `WARN_ON()`
就可能被触发，例如在 PowerPC 上。`smp_mb__after_unlock_lock()` 的调用防止了
该 `WARN_ON()` 被触发。

#### Tree RCU 宽限期内存排序组件


Tree RCU 的宽限期内存排序保证由若干 RCU 组件提供：

#. `Callback Registry`_
#. `Grace-Period Initialization`_
#. `Self-Reported Quiescent States`_
#. `Dynamic Tick Interface`_
#. `CPU-Hotplug Interface`_
#. `Forcing Quiescent States`_
#. `Grace-Period Cleanup`_
#. `Callback Invocation`_

下面各节逐一详细考察相应的组件。

##### Callback Registry（回调注册）


如果 RCU 的宽限期保证要有任何意义，那么发生在给定 `call_rcu()` 调用之前的
任何访问，也必须发生在相应的宽限期之前。RCU 宽限期保证这一部分的实现如
下图所示：


因为 `call_rcu()` 通常只作用于 CPU 本地状态，它不提供任何排序保证，无论
是对自身，还是对更新的阶段一（同样通常是：从 RCU 保护的数据结构中移除一个
元素）。它只是将 `rcu_head` 结构入队到一个每 CPU 列表上，在该列表通过后面
对 `rcu_accelerate_cbs()` 的调用与某个宽限期关联之前，它都无法与宽限期
关联，如上图所示。

左侧显示的一组代码路径通过 `note_gp_changes()` 调用 `rcu_accelerate_cbs()`，
要么直接从 `call_rcu()` 调用（如果当前 CPU 被排队的 `rcu_head` 结构淹没），
要么更可能是来自一个 `RCU_SOFTIRQ` 处理程序。中间的另一条代码路径仅在构建
了 `CONFIG_RCU_FAST_NO_HZ=y` 的内核中才会走，它经由 `rcu_prepare_for_idle()`
调用 `rcu_accelerate_cbs()`。右侧的最后一条代码路径仅在构建了
`CONFIG_HOTPLUG_CPU=y` 的内核中才会走，它经由 `rcu_advance_cbs()`、
`rcu_migrate_callbacks`、`rcutree_migrate_callbacks()` 和 `takedown_cpu()`
调用 `rcu_accelerate_cbs()`，而 `takedown_cpu()` 又是在即将离线的 CPU 被
完全下线之后，在一个幸存 CPU 上被调用的。

在宽限期处理中还有其他一些代码路径会顺带调用 `rcu_accelerate_cbs()`。但
无论哪种方式，该 CPU 最近入队的所有 `rcu_head` 结构都在该 CPU 的领头
`rcu_node` 结构的 `->lock` 保护下，与一个未来的宽限期编号关联起来。在所有
情况下，都与该同一 `rcu_node` 结构 `->lock` 的任何一个先前临界区存在完整的
排序，并且与该 `rcu_node` 结构 `->lock` 的当前任务或 CPU 的任何先前临界区
也存在完整的排序。

下一节将展示这一排序如何确保发生在 `call_rcu()` 之前的任何访问（特别包括
更新的阶段一）发生在相应宽限期开始之前。

##### Grace-Period Initialization（宽限期初始化）


宽限期初始化由宽限期内核线程执行，该线程在 `rcu_gp_init()` 函数内对
`rcu_node` 树进行多次遍历。这意味着要展示贯穿宽限期计算的完整排序流，将
需要复制这棵树。如果您觉得这令人困惑，请注意 `rcu_node` 的状态随时间变化，
就像赫拉克利特（Heraclitus）的河流一样。不过，为了让 `rcu_node` 这条河流
易于处理，宽限期内核线程的遍历被分成多个部分呈现，本节从宽限期初始化的
各个阶段开始。

第一个与排序相关的宽限期初始化动作，是推进 `rcu_state` 结构的 `->gp_seq`
宽限期编号计数器，如下所示：


实际的递增是通过 `smp_store_release()` 完成的，这有助于排除虚假的（false
positive）RCU CPU 停滞（stall）检测。注意只有根 `rcu_node` 结构被触及。

对 `rcu_node` 树的第一次遍历根据自上一宽限期开始以来上线的或离线的 CPU
更新位掩码。在常见情况下，若该 `rcu_node` 结构的在线 CPU 数量没有过渡到
或从零过渡，这次遍历将只扫描叶子 `rcu_node` 结构。然而，如果某个给定叶子
`rcu_node` 结构的在线 CPU 数量从零过渡而来，`rcu_init_new_rnp()` 将被
为第一个进来的 CPU 调用。类似地，如果某个给定叶子 `rcu_node` 结构的在线
CPU 数量过渡到零，`rcu_cleanup_dead_rnp()` 将被为最后一个离开的 CPU 调用。
下图展示了排序路径：如果最左侧的 `rcu_node` 结构上线的第一个 CPU，并且如果
下一个 `rcu_node` 结构没有在线 CPU（或者，等价地，如果最左侧的 `rcu_node`

`rcu_gp_init()` 对 `rcu_node` 树的最后一次遍历以广度优先方式进行，将每个
`rcu_node` 结构的 `->gp_seq` 字段设置为来自 `rcu_state` 结构的、被推进的
新值，如下图所示。


这一变更还会导致每个 CPU 下一次对 `__note_gp_changes()` 的调用注意到一个新

##### Self-Reported Quiescent States（自报告的静止状态）


当所有可能阻塞宽限期的实体都报告了静止状态（或者如后面一节所述，有静止状态
为其代为报告）时，宽限期就可以结束。在线的非空闲 CPU 报告它们自己的静止
状态，如下图所示：


这是针对最后一个报告静止状态的 CPU 的，它标志着宽限期的结束。更早的静止
状态只会向上推 `rcu_node` 树，直到遇到一个正在等待更多静止状态的
`rcu_node` 结构。然而，排序仍然被保留，因为某个后来的静止状态会获取该
`rcu_node` 结构的 `->lock`。

任何数量的事件都可能导致一个 CPU 调用 `note_gp_changes`（或者替代地，直接
调用 `__note_gp_changes()`），在此时该 CPU 将注意到一个新宽限期的开始，同时
持有它的叶子 `rcu_node` 锁。因此，本图所示的所有执行都发生在宽限期开始之后。
此外，该 CPU 会将任何在调用 `__note_gp_changes()` 之前开始的 RCU 读端临界区
视为在宽限期之前开始，从而是一个该宽限期必须等待的临界区。

| **快速测验（Quick Quiz）**：                                          |
+-----------------------------------------------------------------------+
| 但是一个 RCU 读端临界区可能在宽限期开始（更早时 `->gp_seq` 的推进）   |
| 之后才开始，那么为什么宽限期要等待这样的临界区？                      |
+-----------------------------------------------------------------------+
| **答案**：                                                            |
+-----------------------------------------------------------------------+
| 宽限期确实没有必要等待这样的临界区。然而，等待它是被允许的。而且，等待  |
| 它很重要，因为这种懒惰的方式远比“大爆炸”式一次性启动宽限期要可扩展得多。|

如果 CPU 进行了上下文切换，静止状态将由左侧的 `rcu_note_context_switch()`
记录。另一方面，如果 CPU 在用户态执行时发生了调度器时钟中断，静止状态将由
右侧的 `rcu_sched_clock_irq()` 记录。无论哪种方式，经过静止状态的 passage
都会被记录到一个每 CPU 变量中。

下一次 `RCU_SOFTIRQ` 处理程序在该 CPU 上执行时（例如，在下一个调度器时钟
中断之后），`rcu_core()` 将调用 `rcu_check_quiescent_state()`，它会注意到
被记录的静止状态，并调用 `rcu_report_qs_rdp()`。如果 `rcu_report_qs_rdp()`
验证该静止状态确实适用于当前宽限期，它就调用 `rcu_report_rnp()`，后者如
图底部所示向上遍历 `rcu_node` 树，从每个 `rcu_node` 结构的 `->qsmask` 字段
清除位，并在结果为零时向上传播。

注意，只有当当前 CPU 正在报告以该 `rcu_node` 结构为根的 subtree 的最后一个
静止状态时，遍历才会向上走出该给定的 `rcu_node` 结构。一个关键点是，如果某
个 CPU 的遍历停在某个给定的 `rcu_node` 结构上，那么将会有另一个 CPU（或者
可能就是同一个）后来的、从那一点向上进行的遍历，而 `rcu_node` 的 `->lock`
保证了第一个 CPU 的静止状态发生在第二个 CPU 遍历剩余部分之前。反复应用这种
思路表明，所有 CPU 的静止状态都发生在最后一个 CPU 遍历过根 `rcu_node` 结构
之前，这个“最后一个 CPU”即清除了根 `rcu_node` 结构 `->qsmask` 字段中最后
一位的那个 CPU。

通知 RCU，它们通过一个每 CPU 变量上的、完全有序的返回值原子操作来做到这一点。

##### Forcing Quiescent States（强制静止状态）


如上所述，空闲和离线的 CPU 无法报告它们自己的静止状态，因此宽限期内核线程
必须代为报告。这一过程称为“强制静止状态（forcing quiescent states）”，它
每隔几个 jiffies 重复一次，其排序效果如下图所示：


强制静止状态的每次遍历都保证会遍历叶子 `rcu_node` 结构，如果没有由于最近
空闲化和/或离线的 CPU 而产生的新静止状态，那么只有叶子被遍历。然而，如果
如左侧所示有一个新离线的 CPU，或如右侧所示有一个新空闲的 CPU，相应的静止
状态将被向上驱动朝向根。正如自报告的静止状态一样，向上驱动在到达一个有待
来自其他 CPU 的静止状态的 `rcu_node` 结构时停止。

##### Callback Invocation（回调调用）


一旦某给定 CPU 的叶子 `rcu_node` 结构的 `->gp_seq` 字段被更新，该 CPU 就可以
开始调用正在等待本宽限期结束的那些 RCU 回调。这些回调由 `rcu_advance_cbs()`
识别，它通常由 `__note_gp_changes()` 调用。如下图所示，这一调用可以由调度器
时钟中断（左侧的 `rcu_sched_clock_irq()`）或空闲进入（右侧的
`rcu_cleanup_after_idle()`，但仅针对构建了 `CONFIG_RCU_FAST_NO_HZ=y` 的内核）
触发。无论哪种方式，`RCU_SOFTIRQ` 都会被引发，从而导致 `rcu_do_batch()` 调用
这些回调，进而使这些回调能够（直接或经由唤醒间接）执行每个更新所需的阶段二
处理。


请注意，回调调用也可能由任意数量的边角情况（corner-case）代码路径触发，例如，
当某个 CPU 注意到其排队的回调数量过多时。在所有情况下，CPU 都会在调用回调
之前获取其叶子 `rcu_node` 结构的 `->lock`，这就保留了针对新完成宽限期所需的
排序。

然而，如果回调函数与其他 CPU 通信，例如进行唤醒，那么维持排序就是该函数的
责任。例如，如果回调函数唤醒了一个将在某个其他 CPU 上运行的任务，那么在
回调函数和被唤醒的任务中都必须存在适当的排序。要理解这一点为何重要，请考虑
`grace-period cleanup`_ 图的上半部分。回调可能正在对应于最左侧叶子
`rcu_node` 结构的 CPU 上运行，并唤醒一个将在对应于最右侧叶子 `rcu_node`
结构的 CPU 上运行的任务，而宽限期内核线程可能尚未到达最右侧叶子。在这种
情况下，宽限期的内存排序可能尚未到达该 CPU，因此同样，回调函数和被唤醒的
任务必须提供适当的排序。
