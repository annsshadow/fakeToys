## 漫游 TREE_RCU 的加速宽限期（Expedited Grace Periods）

## 简介

本文档描述 RCU 的加速宽限期。与 RCU 的正常宽限期不同，正常宽限期接受较长的延迟以换取高效率和最小干扰，而加速宽限期接受较低的效率和显著的干扰，以换取更短的延迟。

RCU 有两种风格（RCU-preempt 和 RCU-sched），早先的第三种 RCU-bh 风格已用另外两种实现。两种实现各自在一节中讲述。

## 加速宽限期设计

加速 RCU 宽限期不能被指责为微妙，鉴于它们在一切意图和目的上都在敲打（hammer）每一个尚未为当前加速宽限期提供静默状态（quiescent state）的 CPU。唯一的亮点是，随着时间推移，这把锤子变小了一点：对 `try_stop_cpus()` 的旧调用已被一组对 `smp_call_function_single()` 的调用所取代，其中每一个都会产生一个发往目标 CPU 的 IPI。相应的处理函数检查 CPU 的状态，在可能时促使更快达到静默状态，并触发对该静默状态的报告。与 RCU 一贯的情况一样，一旦所有 CPU 都在静默状态中待了一段时间，加速宽限期就完成了。

`smp_call_function_single()` 处理函数的操作细节取决于 RCU 风格，如下面各节所述。

## RCU-preempt 加速宽限期

实线箭头表示直接动作，例如函数调用。虚线箭头表示间接动作，例如 IPI，或经过一段时间后达到的某个状态。

如果某个给定 CPU 离线或空闲，则 `synchronize_rcu_expedited()` 会忽略它，因为空闲和离线的 CPU 已经处于静默状态中。否则，加速宽限期将使用 `smp_call_function_single()` 向该 CPU 发送一个 IPI，由 `rcu_exp_handler()` 处理。

然而，因为这是可抢占的 RCU，`rcu_exp_handler()` 可以检查该 CPU 当前是否正在 RCU 读侧临界区中运行。如果不是，处理函数可以立即报告一个静默状态。否则，它设置标志，使得最外层的 `rcu_read_unlock()` 调用将提供所需的静默状态报告。这种设置标志的做法避免了对所有可能拥有 RCU 读侧临界区的 CPU 进行先前的强制抢占。此外，这种设置标志的做法是为了避免增加通过调度器的常见情况快速路径的开销。

同样因为这是一个可抢占的 RCU，RCU 读侧临界区可以被抢占。当这种情况发生时，RCU 会将任务入队，该任务随后会继续阻塞当前加速宽限期，直到它恢复执行并找到其最外层的 `rcu_read_unlock()`。CPU 会在将任务入队之后立即报告一个静默状态，因为此时 CPU 不再阻塞该宽限期。取而代之的是那个被抢占的任务在做阻塞。被阻塞任务的列表由 `rcu_preempt_ctxt_queue()` 管理，它由 `rcu_preempt_note_context_switch()` 调用，后者由 `rcu_note_context_switch()` 调用，而后者又由调度器调用。

与 RCU-preempt 一样，RCU-sched 的 `synchronize_rcu_expedited()` 会忽略离线和空闲的 CPU，同样是因为它们处于可被远程检测的静默状态。然而，由于 `rcu_read_lock_sched()` 和 `rcu_read_unlock_sched()` 不会留下其调用的痕迹，通常不可能判断当前 CPU 是否处于 RCU 读侧临界区中。RCU-sched 的 `rcu_exp_handler()` 能做的最好事情就是检查是否空闲，抱着 CPU 在 IPI 飞行途中进入空闲的一线希望。如果 CPU 空闲，则 `rcu_exp_handler()` 报告该静默状态。

否则，处理函数通过设置当前任务的线程标志和 CPU 抢占计数器的 NEED_RESCHED 标志，来强制一次未来的上下文切换。在上下文切换时，CPU 报告静默状态。如果 CPU 先离线了，则它会在那时报告静默状态。

### 加速宽限期与 CPU 热插拔

加速宽限期的加速特性，要求它与 CPU 热插拔操作之间进行比正常宽限期所需的紧密得多的交互。此外，尝试向离线 CPU 发送 IPI 会产生 splat（警告），但未能向在线 CPU 发送 IPI 又会导致过短的宽限期。在生产内核中，这两种选择都不可接受。

加速宽限期与 CPU 热插拔操作之间的交互在多个层级进行：

#. 曾经在线过的 CPU 数量由 `rcu_state` 结构的 `->ncpus` 字段跟踪。RCU `rcu_state` 结构的 `->ncpus_snap` 字段跟踪在 RCU 加速宽限期开始时曾经在线过的 CPU 数量。注意这个数字从不减少，至少在没有时光机的情况下如此。
#. 曾经在线过的 CPU 的身份由 `rcu_node` 结构的 `->expmaskinitnext` 字段跟踪。`rcu_node` 结构的 `->expmaskinit` 字段跟踪在最近一次 RCU 加速宽限期开始时至少在线过一次的 CPU 的身份。`rcu_state` 结构的 `->ncpus` 和 `->ncpus_snap` 字段用来检测新的 CPU 何时首次上线，即当 `rcu_node` 结构的 `->expmaskinitnext` 字段自上次 RCU 加速宽限期开始以来发生了变化，这会触发将每个 `rcu_node` 结构的 `->expmaskinit` 字段从它的 `->expmaskinitnext` 字段更新。
#. 每个 `rcu_node` 结构的 `->expmaskinit` 字段用于在每个 RCU 加速宽限期的开始初始化该结构的 `->expmask`。这意味着只有那些至少在线过一次的 CPU 才会被考虑用于给定的宽限期。
#. 任何离线的 CPU 都会清除其叶 `rcu_node` 结构的 `->qsmaskinitnext` 字段中的位，因此任何该位被清除的 CPU 都可以被安全地忽略。然而，一个正在上线或下线的 CPU 有可能在该位被清除的情况下还将此位保持一段时间，同时 `cpu_online` 返回 `false`。
#. 对于 RCU 认为当前在线的每个非空闲 CPU，宽限期调用 `smp_call_function_single()`。如果成功，说明该 CPU 完全在线。失败表示该 CPU 正在上线或下线的过程中，这种情况下有必要等待一小段时间并重试。这个等待（或一系列等待，视情况而定）的目的是允许一个并发的 CPU 热插拔操作完成。
#. 对于 RCU-sched，一个即将离去的 CPU 最后的行为之一是调用 `rcutree_report_cpu_dead()`，它为那个 CPU 报告一个静默状态。不过，这很可能是偏执带来的冗余。

### 加速宽限期的细化

#### 空闲 CPU 检查

每个加速宽限期在最初形成要被 IPI 的 CPU 掩码时，以及在 IPI 某个 CPU 之前（两次检查都由 `sync_rcu_exp_select_cpus()` 执行），都会检查空闲 CPU。如果 CPU 在这两次之间任何时刻空闲，该 CPU 就不会被 IPI。取而代之的是，推动宽限期前进的任务会将空闲 CPU 包含进传给 `rcu_report_exp_cpu_mult()` 的掩码中。

对于 RCU-sched，还有一个额外的检查：如果 IPI 打断了空闲循环，那么 `rcu_exp_handler()` 会调用 `rcu_report_exp_rdp()` 来报告相应的静默状态。

对于 RCU-preempt，在 IPI 处理函数中（`rcu_exp_handler()`）没有针对空闲的特定检查，但因为 RCU 读侧临界区在空闲循环内是不允许的，如果 `rcu_exp_handler()` 看到该 CPU 正处于 RCU 读侧临界区中，那么该 CPU 就不可能是空闲的。否则，`rcu_exp_handler()` 会调用 `rcu_report_exp_rdp()` 来报告相应的静默状态，无论该静默状态是否由于 CPU 空闲所致。

总之，RCU 加速宽限期在构建必须被 IPI 的 CPU 位掩码时、在发送每个 IPI 之前，以及（或显式或隐式地）在 IPI 处理函数中，都会检查空闲。

#### 通过序列计数器进行批处理

如果每个宽限期请求都被单独执行，加速宽限期将具有糟糕的可扩展性和有问题的高负载特性。因为每个宽限期操作可以服务无限数量的更新，所以**批处理**请求很重要，这样单个加速宽限期操作将覆盖相应批次中的所有请求。

这种批处理由一个名为 `rcu_state` 结构中 `->expedited_sequence` 的序列计数器控制。当有一个加速宽限期正在进行时，该计数器为奇数值，否则为偶数值，因此将计数器值除以二就得到已完成的宽限期数量。在任何给定的更新请求期间，计数器必须从偶数转换到奇数，再回到偶数，从而指示一个宽限期已经过去。因此，如果计数器的初始值是 `s`，更新者必须等到计数器至少达到值 `(s+3)&~0x1`。该计数器由以下访问函数管理：

#. `rcu_exp_gp_seq_start()`，标记一个加速宽限期的开始。
#. `rcu_exp_gp_seq_end()`，标记一个加速宽限期的结束。
#. `rcu_exp_gp_seq_snap()`，获取该计数器的一个快照。
#. `rcu_exp_gp_seq_done()`，如果自相应调用 `rcu_exp_gp_seq_snap()` 以来已经过去一个完整的加速宽限期，则返回 `true`。

同样，在一个给定批次中只需要一个请求实际执行宽限期操作，这意味着必须有一种高效的方式来识别众多并发请求中哪一个将发起宽限期，并且其余请求必须有一种高效的方式来等待该宽限期完成。不过，那是下一节的主题。

#### 工作队列（Workqueues）的使用

在较早的实现中，请求加速宽限期的任务同时也驱动它完成。这种直接的方法有需要为发送给用户任务的 POSIX 信号做处理的缺点，因此较新的实现使用了 Linux 内核的工作队列（workqueues，见 Documentation/core-api/workqueue.rst）。

请求任务仍然做计数器快照和漏斗锁处理，但到达漏斗锁顶部的任务会做一个 `schedule_work()`（来自 `_synchronize_rcu_expedited()`），以便由一个工作队列 kthread 来做实际的宽限期处理。因为工作队列 kthread 不接受 POSIX 信号，宽限期等待处理就无需考虑 POSIX 信号。此外，这种方法允许上一个加速宽限期的唤醒与下一个加速宽限期的处理重叠。因为只有四组等待队列，有必要确保上一个宽限期的唤醒在下一个宽限期的唤醒开始之前完成。这由让 `->exp_mutex` 守护加速宽限期处理、让 `->exp_wake_mutex` 守护唤醒来处理。关键在于，在第一次唤醒完成之前不释放 `->exp_mutex`，这意味着此时 `->exp_wake_mutex` 已经被获取。这种方法确保上一个宽限期的唤醒可以在当前宽限期进行期间执行，但这些唤醒会在下一个宽限期开始之前完成。这意味着只需要三个等待队列，从而保证所提供的四个是足够的。

#### 停滞警告（Stall Warnings）

当 RCU 读者耗时过长时，加速宽限期在加快速度方面无能为力，因此加速宽限期像正常宽限期一样检查停滞。

#### 启动中期（Mid-boot）操作

使用工作队列的优势在于加速宽限期代码无需担心 POSIX 信号。不幸的是，它也有相应的缺点，即在工作队列初始化之前无法使用，而初始化要等到调度器生成第一个任务之后一段时间才会发生。鉴于内核中有一些部分确实想在这个启动中期的“死区”期间执行宽限期，加速宽限期在这段时间内必须做别的事情。

它们所做的，是回退到要求请求任务驱动加速宽限期的旧做法，就像使用工作队列之前那样。然而，请求任务只需要在启动中期死区期间驱动宽限期。在启动中期之前，同步宽限期是一个空操作（no-op）。启动中期之后某段时间，会开始使用工作队列。

非加速的非 SRCU 同步宽限期也必须在启动中期正常运行。这通过让非加速宽限期在启动中期走加速代码路径来处理。

当前代码假设在启动中期死区期间没有 POSIX 信号。然而，如果出于某种原因产生了对 POSIX 信号的压倒性需求，可以对加速停滞警告代码做出适当的调整。其中一种调整会恢复工作队列之前的停滞警告检查，但仅限于启动中期死区期间。

有了这一细化，同步宽限期现在可以在内核生命周期中几乎任何时候从任务上下文中使用。也就是说，除了 suspend、hibernate 或 shutdown 代码路径中的某些点之外。

#### 总结

加速宽限期使用序列号方法促进批处理，使单个宽限期操作可以服务众多请求。使用一个漏斗锁来高效识别并发组中将请求宽限期的那一个任务。该组的所有成员都会阻塞在 `rcu_node` 结构提供的等待队列上。实际的宽限期处理由一个工作队列执行。

CPU 热插拔操作被惰性记录，以避免加速宽限期与 CPU 热插拔操作之间需要紧密同步。dyntick-idle 计数器用于避免向空闲 CPU 发送 IPI，至少在常见情况下如此。RCU-preempt 和 RCU-sched 使用不同的 IPI 处理程序和不同的代码来响应那些处理程序所做的状态变更，但在其他方面使用公共代码。

静默状态用 `rcu_node` 树跟踪，一旦所有必要的静默状态都被报告，所有等待这个加速宽限期的任务都会被唤醒。一对互斥体被用来允许一个宽限期的唤醒与下一个宽限期的处理并发进行。

这种机制的组合让加速宽限期能够相当高效地运行。然而，对于非时间关键的任务，应该改用正常宽限期，因为它们的更长持续时间允许更高程度的批处理，从而低得多的每请求开销。
