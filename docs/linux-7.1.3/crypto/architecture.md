## 内核加密 API 架构


### 密码算法类型


内核加密 API 为以下密码类型提供了不同API 调用
- 对称密码（Symmetric ciphers
- AEAD 密码

- 消息摘要，包括带密钥的消息摘
- 随机数生
- 用户空间接口

### 密码与模

内核加密 API 提供了单块密码和消息摘要的实现。此外，内核加密 API 还提供了许多“模板（template）”，可与单块密码和消息摘要结合使用。模板包括各种类型的分组链接模式、HMAC 机制等
单块密码和消息摘要既可以被调用者直接使用，也可以与模板一起调用来构成多块密码或带密钥的消息摘要
单个块密码甚至可以与多个模板一起调用。但是，模板不能脱离单块密码而单独使用
参见 /proc/crypto 并搜"name"。例如：

- aes

- ecb(aes)

- cmac(aes)

- ccm(aes)

- rfc4106(gcm(aes))

- sha1

- hmac(sha1)

- authenc(hmac(sha1),cbc(aes))

在这些例子中aes" "sha1" 是密码，其余都是模板
### 同步与异步操

内核加密 API 提供了同步和异步API 操作
使用同步 API 操作时，调用者调用一个由内核加密 API 同步执行的密码操作。也就是说，调用者会等待该密码操作完成。因此，内核加密 API 的调用就像普通的函数调用一样。对于同步操作，API 调用集很小，在概念上类似于任何其他加密库
异步操作由内核加API 提供，这意味着对密码操作的调用将几乎瞬间返回。该调用会触发密码操作，但不会发出完成信号。在调用密码操作之前，调用者必须提供一个回调函数，内核加密 API 可以调用它来发出密码操作完成的信号。此外，调用者必须确保能够通过在其数据周围使用适当的锁来处理此类异步事件。内核加API 不会执行任何特殊的串行化操作来保护调用者数据的完整性
### 加密 API 密码引用与优先级


调用者使用字符串来引用一个密码。该字符串具有以下语义：

```
        template(single block cipher)
```

其中 "template" "single block cipher" 分别是前面提到的模板和单块密码。如果适用，额外的模板可以嵌套其他模板，例
```
        template1(template2(single block cipher)))
```

内核加密 API 可能提供同一个模板或单块密码的多种实现。例如，较新Intel 硬件上的 AES 有以下实现：AES-NI、汇编实现，或纯 C 实现。那么，当使用字符串 "aes" 调用内核加密 API 时，会使用哪个密码实现呢？这个问题的答案是内核加API 分配给每个密码实现的优先级数字。当调用者在初始化密码句柄时使用字符串来引用某个密码时，内核加密 API 会查找所有提供该名称实现的实现，并选择优先级最高的那个
现在，调用者可能有必要引用某个特定的密码实现，从而不想依赖基于优先级的选取。为了满足这种场景，内核加密 API 允许密码实现除通用名称外再注册一个唯一名称。当使用该唯一名称时，调用者就能确保引用到预期的密码实现
可用密码的列表在 /proc/crypto 中给出。但是，该列表并未列出模板和密码的所有可能排列组合proc/crypto 中列出的每个块可能包含以下信息——如果下列某个组件不适用于某个密码，则不会显示：

- name：受基于优先级选取影响的密码的通用名——该名称可由密码分配 API 调用使用（上面列出的所有名称都是此类通用名的例子
- driver：密码的唯一名称——该名称可由密码分配 API 调用使用

- module：提供该密码实现的内核模块（对于静态链接的密码则为 "kernel"
- priority：该密码实现的优先级
- refcnt：相应密码的引用计数（即当前该密码的使用者数量）

- selftest：该密码的自检测试是否通过的说
- type锛。
   - skcipher：对称密钥密
   - cipher：可与额外模板一起使用的单块密码

   - shash：同步消息摘
   - ahash：异步消息摘
   - aead：AEAD 密码类型

   - compression：压缩类型转
   - rng：随机数生成
   - kpp：密钥协商协议原语（KPP）密码，例如 ECDH DH 实现

- blocksize：密码的块大小（以字节为单位
- keysize：密钥大小（以字节为单位
- ivsize：IV 大小（以字节为单位）

- seedsize：随机数生成器所需的种子数据大
- digestsize：消息摘要的输出大小

- geniv：IV 生成器（已过时）

### 密钥长度


分配密码句柄时，调用者只指定密码类型。然而，对称密码通常支持多种密钥长度（例AES-128、AES-192 AES-256）。这些密钥长度由所提供密钥的长度决定。因此，内核加密 API 没有提供单独的方式来选择特定的对称密码密钥长度
### 密码分配类型与掩

不同的密码句柄分配函数允许指定一个类型和掩码标志。这两个参数具有以下含义（因此在后续章节中不再赘述）
类型标志指定密码算法的类型。当调用者希望使用默认处理时，通常提供 0。否则，调用者可以提供以下与前述密码类型相匹配的选择
- CRYPTO_ALG_TYPE_CIPHER 单块密码

- CRYPTO_ALG_TYPE_AEAD 带关联数据的认证加密（AEAD，即 MAC
- CRYPTO_ALG_TYPE_KPP 密钥协商协议原语（KPP），例如 ECDH DH 实现

- CRYPTO_ALG_TYPE_HASH 原始消息摘要

- CRYPTO_ALG_TYPE_SHASH 同步多块哈希

- CRYPTO_ALG_TYPE_AHASH 异步多块哈希

- CRYPTO_ALG_TYPE_RNG 随机数生
- CRYPTO_ALG_TYPE_AKCIPHER 非对称密
- CRYPTO_ALG_TYPE_SIG 非对称签
- CRYPTO_ALG_TYPE_PCOMPRESS 增强版的 CRYPTO_ALG_TYPE_COMPRESS，允许进行分段的压缩/解压缩，而不是仅在一个段上执行操作。CRYPTO_ALG_TYPE_PCOMPRESS 旨在在现有使用者被转换后取CRYPTO_ALG_TYPE_COMPRESS
掩码标志限制密码的类型。唯一允许的标志是 CRYPTO_ALG_ASYNC，用于将密码查找函数限制为异步密码。通常，调用者为掩码标志提供 0
当调用者提供了掩码和类型说明时，调用者限制了内核加密 API 为给定密码名称查找合适密码实现所能进行的搜索范围。这意味着，即使调用者在初始化调用时使用的密码名称存在，内核加密 API 也可能由于所使用的类型和掩码字段而不选择它
### 内核加密 API 的内部结

内核加密 API 有一个内部结构，其中密码实现可能使用许多层和间接引用。本节旨在阐明内核加API 如何使用各种组件来实现完整的密码
下面的小节基于现有的密码实现来解释内部结构。第一节讨论最复杂的情况，所有其他情况都是它的逻辑子集
#### 通用 AEAD 密码结构


下面ASCII 图示在使用带自动 IV 生成AEAD 密码时，拆解了内核加API 的各个层。所示例子由 IPSEC 层使用
对于 AEAD 密码的其他用例，ASCII 图同样适用，但调用者可能不会将 AEAD 密码与独立的 IV 生成器一起使用。在这种情况下，调用者必须自己生IV
所描绘的例子基于通用 C 实现（gcm.c、aes-generic.c、ctr.c、ghash-generic.c、seqiv.c）拆解了 GCM(AES) AEAD 密码。该通用实现作为一个例子，展示了内核加API 的完整逻辑
某些经过优化的密码实现（AES-NI）可能提供将各方面合并的实现，在内核加密 API 看来无法再分解为各个层。以 AES-NI 实现为例，CTR 模式、GHASH 实现AES 密码都被合并为一个向内核加密 API 注册的密码实现。在这种情况下，下面 ASCII 图所描述的概念同样适用。不过，内核加密 API GCM 分解为各个子组件的工作不再进行
下面 ASCII 图中的每个块都是从内核加API 获得的独立密码实例。每个块由调用者或其他块使用内核加API 为相应密码实现类型定义的 API 函数来访问
下面的块标明了密码类型以及该密码中实现的具体逻辑
ASCII 图还标明了调用结构，即谁调用哪个组件。箭头指向被调用的块，其中调用者使用适用于该块所指定密码类型API
```
    kernel crypto API                                |   IPSEC Layer
                                                     |
    +-----------+                                    |
    |           |            (1)
    |   aead    | <-----------------------------------  esp_output
    |  (seqiv)  | ---+
    +-----------+    |
                     | (2)
    +-----------+    |
    |           | <--+                (2)
    |   aead    | <-----------------------------------  esp_input
    |   (gcm)   | ------------+
    +-----------+             |
          | (3)               | (5)
          v                   v
    +-----------+       +-----------+
    |           |       |           |
    |  skcipher |       |   ahash   |
    |   (ctr)   | ---+  |  (ghash)  |
    +-----------+    |  +-----------+
                     |
    +-----------+    | (4)
    |           | <--+
    |   cipher  |
    |   (aes)   |
    +-----------+
```
IPSEC 层使esp_output 函数触发加密操作时，以下调用序列适用。在配置期间，管理员seqiv(rfc4106(gcm(aes))) 设置ESP 的密码。下面的 ASCII 图描绘了该调用序列：

1. esp_output() 调用 crypto_aead_encrypt() 来触发带IV 生成器的 AEAD 密码的加密操作
   SEQIV 生成 IV
2. 接着，SEQIV 使用 AEAD API 函数调用来调用关联的 AEAD 密码。在我们的例子中，在实例SEQIV 时，GCM 的密码句柄被提供SEQIV。这意味着 SEQIV 使用 GCM 密码句柄来调AEAD 密码操作
   在实例化 GCM 句柄时，CTR(AES) GHASH 密码被实例化。CTR(AES) GHASH 的密码句柄被保留供以后使用
   GCM 实现负责以正确的方式调用 CTR 模式AES GHASH 密码，以实现 GCM 规范
3. GCM AEAD 密码类型实现现在使用已实例化CTR(AES) 密码句柄来调SKCIPHER API
   在实例化 CTR(AES) 密码时，AES CIPHER 类型实现被实例化。AES 的密码句柄被保留
   这意味着 CTR(AES) SKCIPHER 实现只实现了 CTR 分组链接模式。在执行完分组链接操作后，会调用 AES CIPHER 实现
4. CTR(AES) SKCIPHER 现在使用 AES 密码句柄调用 CIPHER API 来加密一个块
5. GCM AEAD 实现还通过 AHASH API 调用 GHASH 密码实现
IPSEC 层触esp_input() 函数时，遵循相同的调用序列，唯一的区别是操作从步(2) 开始
#### 通用分组密码结构


通用分组密码遵循与上ASCII 图相同的概念
例如，CBC(AES) cbc.c aes-generic.c 实现。上面的 ASCII 图同样适用，区别在于只使用了步(4)，且 SKCIPHER 的分组链接模式是 CBC
#### 通用带密钥消息摘要结

带密钥的消息摘要实现再次遵循与上ASCII 图相同的概念
例如，HMAC(SHA256) hmac.c sha256_generic.c 实现。下面的 ASCII 图说明了该实现：

```
    kernel crypto API            |       Caller
                                 |
    +-----------+         (1)    |
    |           | <------------------  some_function
    |   ahash   |
    |   (hmac)  | ---+
    +-----------+    |
                     | (2)
    +-----------+    |
    |           | <--+
    |   shash   |
    |  (sha256) |
    +-----------+
```
当调用者触HMAC 操作时，以下调用序列适用
1. AHASH API 函数由调用者调用。HMAC 实现按需执行其操作
   在初始化 HMAC 密码时，SHA256 SHASH 密码类型被实例化。SHA256 实例的密码句柄被保留
   在某个时刻，HMAC 实现需要一SHA256 操作，此时会使用 SHA256 的密码句柄
2. HMAC 实例现在使用 SHA256 密码句柄调用 SHASH API 来计算消息摘要
