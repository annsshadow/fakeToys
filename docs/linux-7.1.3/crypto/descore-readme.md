## 动机与历

前一阵子我想要一des 例程，sun 手册页上记载的例程要么不存在，要么崩溃（dumped core）。我听说kerberos，也知道它用 des，所以我想用它的例程。但一旦拿到并看了代码，它真的触发了我许多忌讳——它太绕了，编写代码时没有利IP、E、FP 等操作的正则结构（即作者在编码前没有坐下来思考），它慢得离谱，作者试图通过增加更多语句来让数据移动一以澄清代码，而不是简化实现、减少所有数据移动（特别是他L1、R1、L2、R2 的使用），而且充斥着针对特定机器的愚tweaks"，这tweak 未能带来显著的加速，却把一切都弄得晦涩难懂。于是我从他的验证程序中取出测试数据，重写了其余的一切
过了一阵子，我偶然发现了上面提到的优秀 crypt(3) 软件包。这家伙每次表查找计2 sbox 而非 1 个（过程中还用了大得多的表），这一事实让我也鼓起勇气照做——这只是个小改动，我之前被更大的表吓退了。在他的情况下，他没有意识到你不需要把工作数据保持成两种形式，一种便于索引时用到一sbox，另一种便于用到另一半；相反，你可以把它保持为前半部分的形式，再用一个简单的旋转得到另一半。这意味着我的数据操作和表大小都（几乎）只有一半。不过公平地说，他可能在表中编码crypt(3) 特有的某些东西——我没检查
我很高兴自己用这种方式实现，因为这个 C 版本是可移植的（ifdef 是性能增强），而且比针sparc 手写的汇编版本还要快

## 移植说明


我绝不想做的事，就是写出一个依赖字节序和其他机器怪癖、因而必然为不同机器生成不同代码与不同查找表的巨大烂摊子。看kerberos 代码，就是我不想做的例子；他们所有依赖字节序优化"都把代码弄得晦涩，最终还比更简单的机器无关方法更慢。不过，总有一些移植方面的考虑，我加入了一些用于不同数量寄存器变量的选项也许有人仍会认为结果是一团乱麻！

1) 我假设一切都是字节可寻址的，尽管我实际上并不依赖字节序，并且字节8 位。我假设字指针可以自由地与字符指针相互转换。注99% C 程序都做这些假设。如果高位可能被置位，我总是使用 unsigned char2) 类型定义 `word` 32 位无符号整型。如`unsigned long` 不是 32 位，请修desCore.h 中的类型定义。我假设 sizeof(word) == 4 处处成立
我在密钥迭代周围的数据加载与存储代码中不做字节序特定优化的最大代价小12%。此外还有一个额外好处：输入和输出工作区不需要字对齐

## 可选的性能优化


1) 你应定义 `i386,`、`vax,`、`mc68000,` `sparc,` 之一，选与你机器能力最接近的。参desCode.h 开头，以确切了解此选择的含义。注意，如果你选错了，des 代码仍能工作；这些只是性能微调2) 对于有可`asm` 关键字的人：如果你有机器旋转指令，应ROR ROL 宏改为使用它们。这样每次使用可节省 2 条指令和一个临时变量，即每次加/解密约节32 40 条指令
   注意，gcc 足够聪明，能ROL/R 宏翻译成机器旋转指令
这些优化都相当挑剔，但有了它们你应该能得到与汇编编码相当的性能，例外在于：

1) 由于 C 中没有位旋转运算符，旋转必须用移位合成。因此，如果你的机器有旋转指令，访问 `asm` 会加快速度，如上文 (3) 所述（使用 gcc 则不需要）2) 如果你的机器少于 12 32 位寄存器，我怀疑你的编译器能否生成好的代码
   `i386` 通过只声3 个寄存器来为 386 配置代码（看起来 gcc 能用 ebx、esi edi 来保存寄存器变量）。不过，如果你喜欢汇编编码，386 确实7 32 位寄存器，如果你全部用上，使用带位移8 缩放"地址模式及其他技巧，就能得到合理DesQuickCore... 例程，每个约 250 条指令。对DesSmall... 重新安排 des_keymap 会有帮助，即现在 sbox 编号是索引的高位部分 位数据是其低位部分；交换它们会有帮助
   由于没有方便的方法测试，我未提供我硬塞进去的 386 版本。注意，desCore 的这个版本中，gcc 能够把一切都放进寄存器（！），并DesQuickCore... 例程各生成约 370 条指令！

## 编码说明


解密例程各自使用 6 个必要的寄存器变量，内层迭代期间同时积极使用 4 个。如果你没有 4 个寄存器变量，换台机器吧。在某些配置中，最多还8 个寄存器来保存常量
我假设使用常量比使用寄存器更昂贵
a) 此外，我尝试把较大的常量放进寄存器。注册优先级如下
 - 任何超过 12 位的值（RISC CISC 都不利）
 - 值大127（在 CISC 上无法使movq 或字节立即数 - 9-127（可能无法使CISC 移位立即数或 add/sub quick - 1-8 从未被注册，因为它们是最廉价的常量
b) 编译器可能太笨，意识不到 table table+256 应分配给不同的常量寄存器，反而重复做算术，因此我在可能且有用时，把它们分配给显式`m` 寄存器变量
我假设在索引7 位无符号或更小时，索引比自动减更廉价或相当。对68k vax，这一假设相反
我假设地址可以廉价地由两个寄存器、或由一个寄存器加一个小常量构成。对68000两个寄存器加小偏的形式被谨慎使用。所有索引缩放都是显式完成的——没log2(sizeof) 的隐藏移位
代码编写得即dumb 编译器也绝不需要超过一个隐藏临时变量，从而增加了所有内容都能放进寄存器的机会。如果你改写任何东西，请牢记这个更微妙的点
（实际上，现在有一些代码片段确实需要两个临时变量，但修复它要么会破坏宏的结构，要么需要再声明一个临时变量。）

	s 处的 8 字节执行 des，结果写d 处的 8 字节。（d,s: char *）
