- 将中断处理程序改为基于每个端点的线程化中断（`per-ep-thread-irq`）

  事实证明，某些 DWC3 命令需要约 1ms 才能完成。目前我们采用自旋等待直到命令完成，这种做法不好。

  实现思路：

  - dwc 核心为每个端点实现了一个用于中断解复用的 irq chip。中断号在探测（probe）期间分配，并属于该设备。如果 MSI 提供每端点的中断，则这个虚拟中断芯片可被“真实”的中断替换。
  - 中断在 usb_ep_enable() 时请求/分配，并在 usb_ep_disable() 时移除。最坏情况下有 32 个中断，下限为两个（对应 ep0/1）。
  - dwc3_send_gadget_ep_cmd() 会在 wait_for_completion_timeout() 中休眠，直到命令完成。
  - 中断处理程序被拆分为以下部分：

    - 设备的主处理程序（primary handler）
      遍历每个事件，并对其调用 generic_handle_irq()。从 generic_handle_irq() 返回时确认事件计数器，从而使中断最终消失。

    - 设备的线程化（threaded）处理程序
      无

    - EP 中断的主处理程序
      读取事件并尝试处理它。所有需要休眠的操作都交给线程（Thread）。事件被保存在每个端点的数据结构中。
      我们可能需要注意，一旦将某个事件交给线程，就不要再处理该事件，以免出现事件 X 优先级 Y 被错误处理的情况（其中 X > Y）。

    - EP 中断的线程化（threaded）处理程序
      处理其余的可能休眠的端点工作，例如等待命令完成。

  延迟（Latency）：

   由于中断线程具有高优先级，并且会在用户态的平均任务之前运行（除非用户改变了优先级），因此延迟不应增加。
