## EHCI 驱动程序


2002-12-27

EHCI 驱动程序用于通过支持 USB 2.0 的主机控制器硬件与高USB 2.0 设备通信USB 2.0 标准USB 1.1 标准兼容。它定义了三种传输速度
    - "高速（High Speed 480 Mbit/sec0 MByte/sec    - "全速（Full Speed 12 Mbit/sec.5 MByte/sec    - "低速（Low Speed 1.5 Mbit/sec

USB 1.1 只涉及全速和低速。高速设备可以用USB 1.1 系统上，但它们会降速到
USB 1.1 的速度
USB 1.1 设备也可以用USB 2.0 系统上。当插入 EHCI 控制器时，它们会被交给一USB 1.1 “伴生（companion）”控制器，即通常用于此类设备OHCI UHCI 控制器USB 1.1 设备插入 USB 2.0 集线器时，它们通过集线器中的“事务转换器（Transaction
Translator，TT）”与 EHCI 控制器交互，事务转换器将低速或全速事务转换为不会浪费
传输带宽的高速“分离事务（split transactions）”
在撰写本文时，此驱动程序已被发现可用于（按字母顺序）Intel、NEC、Philips VIA
EHCI 实现。其他厂商的 EHCI 实现也正在出现；你应该预期此驱动程序也能与它协同工作
虽然 usb-storage 设备2001 年中就已可用（在本驱动的 2.4 版本上速度相当快）但集线器直到 2001 年底才可用，而其他类型的高速设备似乎被搁置，直到更多系统内USB 2.0。这类新系统2002 年初就已可用，并2002 年下半年变得更加普遍
请注意，USB 2.0 支持涉及的不仅仅EHCI。它需要对 Linux-USB 核心 API 进行其他
更改，包括集线器驱动程序，但这些更改实际上并不需要改变暴露给 USB 设备驱动基本“usbcore”API

## 功能


此驱动程序在 x86 硬件上经过定期测试，也曾用于 PPC 硬件，因此大小端（big/little
endian）问题应该已经没有了。相信它完成了所有正确的 PCI 魔法，使得即使在具有
特殊 DMA 映射问题的系统上 I/O 也能工作
### 传输类型


在撰写本文时，驱动程序应当可以轻松处理所有控制、批量（bulk）和中断传输，包通过 USB 2.0 集线器中的事务转换器（TT）对 USB 1.1 设备的请求。但你可能仍会发缺陷
高速同步（ISO）传输支持也是可用的，但在撰写本文时还没有任Linux 驱动程序使用
该支持
通过事务转换器的全速同步传输支持目前尚不可用。请注意，ISO 传输的分离事务支无法与高ISO 传输的代码共享太多代码，因为 EHCI 用不同的数据结构来表示它们因此，目前大多数 USB 音频和视频设备无法连接到高速总线
### 驱动程序行为


所有类型的传输都可以排队。这意味着来自一个接口上某个驱动程序（或通过 usbfs）的
控制传输不会干扰另一个驱动程序的传输，并且中断传输可以使用一帧的周期而不会因
中断处理开销而有数据丢失的风险
EHCI 根集线器代码USB 1.1 设备交给它的伴生控制器。此驱动程序不需要了解那驱动程序的任何信息；一个已经能工作OHCI UHCI 驱动程序不会因为同时存在 EHCI
驱动程序就需要改变
电源管理方面存在一些缺陷；挂起/恢复（suspend/resume）目前行为不太正常
另外，在调度周期性事务（中断和等时传输）方面采取了一些捷径。这些对可调度的
周期性事务数量施加了一些限制，并禁止使用小于一帧的轮询间隔

## 使用

假设你有一EHCI 控制器（PCI 卡或主板上）
```

    # modprobe ehci-hcd

```

```

    # rmmod ehci-hcd

```
你还应有一个“伴生控制器”的驱动程序，例如“ohci-hcd”或“uhci-hcd”。如EHCI
驱动程序遇到任何问题，移除它的模块，然后该伴生控制器的驱动程序将接管（以较低速度）所有以前由 EHCI 驱动程序处理的设备
模块参数（传递给“modprobe”）包括
    log2_irq_thresh（默0）：
	默认中断延迟log2 值，以微帧（microframe）为单位。默认值为 0，表	1 个微帧（125 微秒）。最大值为 6，表2^6 = 64 个微帧。这控制 EHCI
	控制器可以发出中断的频率
如果你在 2.5 内核上使用此驱动程序，并且启用了 USB 调试支持，你会在任何 EHCI
控制器的“sysfs”目录中看到三个文件
	"async"
		转储异步调度，用于控制和批量传输。显示每个活动的 qh 以及
		挂起qtd，通常每个 urb 一qtd。（用进行磁I/O 		usb-storage 来观察它；看看请求队列！	"periodic"
		转储周期性调度，用于中断和等时传输。不显示 qtd	"registers"
		显示控制器寄存器状态，以及

这些文件的内容有助于识别驱动程序问题

设备驱动程序不应该关心它们是否运行在 EHCI 之上，但它们可能想检“usb_device->speed == USB_SPEED_HIGH”。高速设备可以做全速（或低速）设备做不的事情，例如“高带宽”周期性（中断ISO）传输。此外，设备描述符中的某些值（例如
周期性传输的轮询间隔）在高速运行时使用不同的编码
但是，务必记得通过 USB 2.0 集线器测试设备驱动程序。这些集线器在使用事务转换器
时会以不同的方式报告某些故障（例如断开连接）；一些驱动程序在看到OHCI UHCI
报告的不同的故障时，会表现出异常行为

## 性能


USB 2.0 吞吐量受两个主要因素制约：主机控制器处理请求的速度，以及设备响应请的速度。所有设备都遵守 480 Mbit/sec 的“原始传输速率”，但总吞吐量也受到诸单个高速数据包之间的延迟、驱动程序智能程度，当然还有整体系统负载等问题的影响延迟也是一个性能关切点
批量传输最常用于吞吐量是问题的情况。要记住，批量传输总是512 字节的数据包进行，并且其中最多有 13 个可以装入一USB 2.0 微帧。八USB 2.0 微帧装入一USB 1.1 帧；一个微帧是 1 毫秒/8 = 125 微秒
因此，当硬件和设备驱动程序软件都允许时，批量传输有超50 MByte/sec 的带宽可用周期性传输模式（等时和中断）允许使用更大的数据包，让你接近所标称480 MBit/sec
传输速率
### 硬件性能


在撰写本文时，单USB 2.0 设备往往最高达到约 20 MByte/sec 的传输速率。这当然发生变化；有些设备现在更快，而另一些更慢
NEC 的第一EHCI 实现似乎在约 28 MByte/sec 的总传输速率处有一个硬件瓶颈。虽这对于一个以 20 MByte/sec 运行的单个设备显然已经足够，但在一条总线上放置三这样的设备并不能让你得到 60 MByte/sec。问题似乎在于控制器硬件不会进行并发USB
PCI 访问，因此它每个微帧只尝试六次（或者可能是七次）USB 事务，而不是十三次（对于一款比所有其他产品早一年多上市的产品来说，这似乎是一个合理的权衡！）

预计更新的实现会改进这一点，在问题上投入更多的硅片面积，以便新的主板芯片组将
更接60 MByte/sec 的目标。这包括 NEC 的更新实现，以及其他厂商的硅片
主机接收 EHCI 控制器发出的指示请求完成的中断，至少有一个微帧（125 微秒）的最延迟。该延迟是可调的；有一个模块选项。默认情况下 ehci-hcd 驱动程序使用最小延迟，
这意味着如果你发出一个控制或批量请求，你通常可以预期在不250 微秒内（取决传输大小）得知它已完成
### 软件性能


为了即便达到 20 MByte/sec 的传输速率，Linux-USB 设备驱动程序也需要保EHCI 队列
填满。这意味着要发出大请求，或者在需要发出一系列小请求时使用批量排队。当驱动
程序不这样做时，它们的性能结果会体现出来
在典型情况下，一个写4 KB 块的 usb_bulk_msg() 循环将浪费一半以上的 USB 2.0
带宽。I/O 完成与驱动程序发出下一个请求之间的延迟将比 I/O 本身更长。如果同一个循使用 16 KB 的块，情况会好一些；一系列 128 KB 的块浪费的会更少
但是，与其依赖这样的I/O 缓冲区来使同I/O 高效，不如将几个（批量）请求排队
HC，然后等待它们全部完成（或在出错时取消）。这样的 URB 排队也应该适用于所USB 1.1 HC 驱动程序
Linux 2.5 内核中，定义了新usb_sg_*() API 调用；它们将分散列表（scatterlist中的所有缓冲区排队。它们还使用分散列表 DMA 映射（可能会应用 IOMMU）和中断减少所有这些都将有助于让高速传输尽可能快地运行
