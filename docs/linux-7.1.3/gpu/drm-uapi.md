
## 用户空间接口


DRM 核心向应用程序导出多个接口，通常旨在通过与之一一对应的 libdrm 封装函数使用。此外，驱动通过 ioctl 与 sysfs 文件导出设备专用接口，供用户空间驱动与设备感知型应用使用。

外部接口包括：内存映射、上下文管理、DMA 操作、AGP 管理、vblank 控制、fence 管理、内存管理以及输出管理。

此处介绍通用 ioctl 与 sysfs 布局。我们仅需要高层级信息，因为其余部分应由 man 手册页覆盖。

## 开源用户空间需求


DRM 子系统对新 uAPI 在用户空间一侧的形态有着比大多数其他内核子系统更严格的要求。本节解释这些要求究竟是什么，以及它们存在的原因。

简而言之，任何对 DRM uAPI 的添加都需要有对应的开源用户空间补丁，而且这些补丁必须经过评审并准备好合并进一个合适的、权威的上游项目。

GFX 设备（显示与渲染/GPU 两侧皆是）是相当复杂的硬件，用户空间与内核必然需要非常紧密地协同工作。用于渲染与 modesetting 的接口必须非常宽泛且灵活，因此几乎不可能为每一个可能的边角情况精确定义它们。这进而导致在实践中几乎无法区分：哪些行为是用户空间所要求的、且不可更改以避免回归，哪些行为仅仅是当前实现的无意产物。

如果没有所有用户空间使用方的完整源代码，就意味着无法更改实现细节，因为用户空间可能在细微之处依赖于当前实现的无意行为。而在没有源代码的情况下调试这种回归几乎是不可能的。因此其结果是：

- Linux 内核的“不回归（no regression）”策略在实践中只对 DRM 子系统的开源用户空间有效。如果闭源 blob 驱动在用户空间中使用与开源驱动相同的 uAPI，DRM 开发者完全接受，但它们必须以与开源驱动完全相同的方式使用。对接口的创造性（滥用）使用将、并且在过去经常会导致功能损坏。

- 任何新的用户空间接口都必须有一个开源实现作为演示载体。

要求开源用户空间的另一个原因是对 uAPI 的评审。由于 GFX 技术栈的内核部分与用户空间部分必须如此紧密地协作，代码评审只能通过同时审视两侧来评估一个新接口是否达成目标。确保该接口确实完整地覆盖了用例，会带来一些额外的要求：

- 开源用户空间不能是一个玩具/测试应用，而必须是真实可用的东西。具体而言，它需要能够处理所有常见的错误与边角情况。这些往往正是新 uAPI 崩塌的地方，因此对于评估一个提议接口是否合适至关重要。

- 用户空间一侧必须按照该用户空间项目的标准被充分评审与测试。例如对 mesa 而言，这意味着需要 piglit 测试用例与邮件列表上的评审。这同样是为了确保新接口确实能完成工作。用户空间一侧的评审者还应当在内核 uAPI 补丁上提供 Acked-by，表明他们认为所提议的 uAPI 是合理的、有充分文档记录并经用户空间验证的。

- 用户空间补丁必须基于权威的上游，而非某个厂商 fork。这是为了确保没有人通过快速 fork 来在评审与测试要求上作弊。

- 内核补丁只有在满足上述所有要求之后才能被合并，但它**必须**在用户空间补丁落地**之前**被合并到 drm-next 或 drm-misc-next 中。uAPI 始终从内核流出，反过来做会让 uAPI 定义与头文件产生分歧的风险。

这些要求相当严苛，但它们是从多年来匆忙添加 uAPI、并且几乎总是一样快地后悔的痛苦经验中成长出来的。GFX 设备变化极快，至少每隔几年就需要一次范式转变和一整套全新的 uAPI 接口。再结合 Linux 内核保证让现有用户空间运行 10 年以上的承诺，这对 DRM 子系统而言已经相当痛苦，多种针对同一事物的不同 uAPI 共存。如果我们每年再往其中掺入几个彻头彻尾的错误，那将完全不可管理。


## 渲染节点


DRM 核心提供多个字符设备供用户空间使用。取决于打开的是哪个设备，用户空间可以执行不同的操作集合（主要是 ioctl）。主节点始终被创建，并称为 card<num>。此外，一个当前未使用的控制节点（称为 controlD<num>）也会被创建。主节点提供所有遗留操作，并且在历史上曾是用户空间唯一使用的接口。随 KMS 引入了控制节点。然而，计划中的 KMS 控制接口从未被编写，因此控制节点至今保持未使用状态。

随着离屏渲染器与 GPGPU 应用使用的增加，客户端不再需要运行 compositor 或图形服务器来使用 GPU。但 DRM API 要求非特权客户端在获得 GPU 访问权之前，先向某个 DRM-Master 认证。为了避免这一步、并授予客户端不认证即获得 GPU 访问权的能力，渲染节点被引入。渲染节点专门服务于渲染客户端，也就是说，在渲染节点上不能发出任何 modesetting 或特权 ioctl。只允许非全局的渲染命令。如果某个驱动支持渲染节点，它必须通过 DRIVER_RENDER 这个 DRM 驱动能力来声明。若不支持，则与遗留的 drmAuth 认证流程一起，主节点必须被用于渲染客户端。

如果某个驱动声明支持渲染节点，DRM 核心将创建一个独立的渲染节点，称为 renderD<num>。每个设备会有一个渲染节点。除了与 PRIME 相关的 ioctl 外，该节点上不允许任何 ioctl。特别是 GEM_OPEN 将被明确禁止。关于可在渲染节点上使用的、与驱动无关的 ioctl 完整列表，请参见在 drm_ioctl.c 中被标记为 DRM_RENDER_ALLOW 的 ioctl。渲染节点旨在避免缓冲区泄漏——这类泄漏发生在客户端在遗留接口上猜测 flink 名称或 mmap 偏移量时。除此基本接口之外，驱动必须将其依赖于驱动的、仅用于渲染的 ioctl 标记为 DRM_RENDER_ALLOW，以便渲染客户端使用它们。驱动作者必须小心，绝不可在渲染节点上允许任何特权 ioctl。

通过渲染节点，用户空间如今可以通过基本的文件系统访问模式来控制对渲染节点的访问。一个在特权的主节点/遗留节点上认证客户端的、正在运行的图形服务器不再被需要。取而代之，客户端可以打开渲染节点并立即获得 GPU 访问权。客户端之间（或服务器之间）的通信通过 PRIME 完成。从渲染节点到遗留节点的 FLINK 不被支持。新的客户端不得使用不安全的 FLINK 接口。

除了丢弃所有 modeset/全局 ioctl 之外，渲染节点也丢弃了 DRM-Master 概念。没有理由将渲染客户端与某个 DRM-Master 关联，因为它们独立于任何图形服务器。此外，无论如何它们都必须在没有任何正在运行的主设备的情况下工作。如果某驱动支持渲染节点，它必须能够在不带主设备对象的情况下运行。另一方面，如果一个驱动需要客户端之间共享、对用户空间可见且可越出打开文件边界访问的状态，它就不可能支持渲染节点。

## 设备热拔出


   以下为计划。实现尚未到位（2020 年 5 月）。

图形设备（显示和/或渲染）可能通过 USB（例如显示适配器或扩展坞）或 Thunderbolt（例如 eGPU）连接。终端用户能够在这些设备正在使用时将其热拔出，并期望至少机器不会崩溃。热拔出 DRM 设备造成的任何损害都需要尽可能被限制，并且用户空间如果愿意，必须获得处理它的机会。理想情况下，热拔出 DRM 设备仍然能让桌面环境继续运行，但这将需要在整个图形技术栈中得到明确支持：从内核与用户空间驱动，经过显示服务器，经由窗口系统协议，一直到应用与库。

应当导致同样结果的其他场景有：不可恢复的 GPU 崩溃、PCI 设备从总线上消失，或是强制解除驱动与物理设备的绑定。

换言之，从用户空间的角度看，一切都需要或多或少地继续工作，直到用户空间停止使用已消失的 DRM 设备并将其完全关闭。用户空间将通过设备移除的 uevent、返回 ENODEV 的 ioctl（或返回厂商特定结果的厂商特定 ioctl），或返回 ENXIO 的 open() 来知悉设备的消失。

只有在用户空间关闭了所有相关的 DRM 设备与 dmabuf 文件描述符、并移除了所有 mmap 之后，DRM 驱动才能拆除它针对那个不再存在的设备的实例。如果同一个物理设备在此期间以某种方式回来，它应当成为一个新的 DRM 设备。

类似于 PIDs，字符设备次设备号不会被立即回收。一个新的 DRM 设备总是选取相对于之前分配的次设备号的下一个空闲次设备号，并在次设备号耗尽时回绕。

这一目标至少对内核与驱动提出了如下要求。

### 对 KMS UAPI 的要求


- KMS 连接器必须将其状态改为 disconnected（断开连接）。

- 遗留的 modeset 与 pageflip，以及原子提交（包括真实提交与 TEST_ONLY），还有任何其他 ioctl，要么以 ENODEV 失败，要么伪造成功。

- 挂起的非阻塞 KMS 操作交付用户空间所期望的 DRM 事件。这也适用于伪造了成功的 ioctl。

- 对底层设备已消失的设备节点执行 open() 将以 ENXIO 失败。

- 试图在一个已消失的 DRM 设备上创建 DRM 租赁将以 ENODEV 失败。已有的 DRM 租赁保持不变，并如上所列继续工作。

### 对渲染与跨设备 UAPI 的要求


- 所有无法再运行的 GPU 作业必须将其 fence 强制置为已信号，以避免给用户空间造成挂起。相关的错误码为 ENODEV。

- 一些用户空间 API 已经定义了设备消失时应当发生什么（OpenGL、GL ES：`GL_KHR_robustness`_；`Vulkan`_：VK_ERROR_DEVICE_LOST；等等）。DRM 驱动可以自由地以它们认为最佳的方式实现这一行为，例如：在厂商特定 ioctl 中返回失败并在用户空间驱动中处理，或依赖 uevent，等等。

- 指向已消失内存的 dmabuf 要么以 ENODEV 导入失败，要么（若它在消失前本可成功）继续被成功导入。关于已导入 dmabuf 的更多信息，也请参见下文关于内存映射的内容。

- 试图将一个 dmabuf 导入到一个已消失的设备，要么以 ENODEV 失败，要么（若没有消失时本可成功）成功。

- 对底层设备已消失的设备节点执行 open() 将以 ENXIO 失败。


### 对内存映射的要求


内存映射有进一步的要求，同时适用于已有的映射以及设备消失之后创建的映射。如果底层内存消失，该映射被创建或修改成使得读与写仍然能够成功完成，但结果未定义。这适用于用户空间 mmap() 的内存，也适用于被 dmabuf 指向、可能被映射到其它设备（跨设备 dmabuf 导入）的内存。

引发 SIGBUS 不是一个选项，因为用户空间无法现实地处理它。信号处理程序是全局的，这使得它们极难在像 Mesa 产出的那些库中被正确使用。信号处理程序不可组合，你不可能为来自不同厂商的 GPU1 与 GPU2 设置不同的处理程序，再为 mmap 的普通文件设置第三个处理程序。线程也给信号处理带来额外的麻烦。

## 设备重置


GPU 技术栈真的非常复杂，并且容易出错，从硬件缺陷、有问题的应用，到众多层次之间的一切皆然。某些错误需要重置设备，以使设备重新可用。本节描述当设备重置时，DRM 与用户模式驱动各自的预期，以及如何传播重置状态。

设备重置无法在不污染内核的情况下被禁用，这可能通过 shrinkers/mmu_notifiers 让整个内核挂起。用户空间在设备重置中的角色是将消息传播给应用，并在存在时，对任何封锁“有罪”应用的特殊策略加以应用。推论是：调试一个挂起的 GPU 上下文需要硬件支持，以便能在它停止时抢占这样的 GPU 上下文。

### 内核模式驱动


KMD 负责检查设备是否需要重置，并视需要执行它。通常，当一个作业卡在执行中时就会检测到挂起。

向用户空间传播错误已被证明是棘手的，因为它与通常的命令流向相反。正因如此，与厂商无关的错误处理被加入到了 &dma_fence 对象中，这样驱动就能在它们发出 fence 信号之前，给 fence 加上一个错误码。关于如何做以及可用错误码示例，请参见函数 dma_fence_set_error()。

DRM 调度器还允许在硬件提交于重置后重启时，为所有挂起的 fence 设置错误码。错误码也会从硬件 fence 转发到调度器 fence，从而将错误冒泡到技术栈的更高层，并最终到达用户空间。

fence 错误可以由用户空间通过通用的 SYNC_IOC_FILE_INFO IOCTL 以及通过厂商特定接口来查询。

除了设置 fence 错误之外，驱动还应该按上下文跟踪重置次数，DRM 调度器提供了 drm_sched_entity_error() 函数作为这一用例的辅助。重置之后，KMD 应当拒绝受影响上下文的新命令提交。

### 用户模式驱动


命令提交之后，UMD 应当检查提交是被接受还是被拒绝。重置之后，KMD 应当拒绝提交，而 UMD 可以向 KMD 发出一个 ioctl 来检查重置状态，如果 UMD 需要，还可以更频繁地检查。检测到重置之后，UMD 接着将使用合适的 API 错误码把重置报告给应用，如下文关于健壮性一节所述。

### 健壮性


在重置之后试图让一个图形 API 上下文继续工作的唯一办法，是它符合其所使用图形 API 的健壮性方面要求。

图形 API 为应用提供了应对设备重置的手段。然而，无法保证应用会正确使用这类特性，而一个不支持健壮接口的用户空间（如非健壮的 OpenGL 上下文，或像 libva 这样没有任何健壮性支持的 API）把健壮性处理完全留给了用户空间驱动。对于用户空间驱动在这种情况下应当做什么，社区没有强烈的共识，因为所有合理的做法都有一些明显的缺点。

#### OpenGL


使用 OpenGL 的应用应当使用可用的健壮接口，例如扩展 `GL_ARB_robustness`（或用于 OpenGL ES 的 `GL_EXT_robustness`）。该接口会告知是否发生过重置，如果发生过，则所有上下文状态被视为已丢失，应用通过创建新状态来继续。对于未使用健壮性时该怎么做，没有共识。

#### Vulkan


使用 Vulkan 的应用应当为提交检查 `VK_ERROR_DEVICE_LOST`。这个错误码除其他含义外，表示发生了设备重置，并且它需要重建上下文以继续。

### 报告重置原因


除了通过技术栈传播重置以便应用能够恢复之外，了解最初是什么导致了重置，对驱动开发者真的很有用。为此，驱动可以利用 devcoredump 来存储关于重置的相关信息，并用 `none` 恢复方法（如“设备 Wedging”一章所述）发送 device wedged 事件来通知用户空间，从而这些信息可以被收集并加入用户的缺陷报告。

## 设备卡死（Wedging）


驱动可以选择使用 device wedged 事件（在 DRM 子系统中实现为 drm_dev_wedged_event()），它通过一个 uevent 将 DRM 设备“卡死（wedged，挂起/不可用）”状态通知用户空间。这在设备不再按预期运行、且从驱动上下文中已无法恢复的情况下特别有用。此实现的目的是为驱动提供一种通用方式，借助用户空间干预来恢复设备，而无需在驱动中采取任何激烈措施（如重置或重枚举底层物理设备所在的总线）。

一个“卡死”的设备，基本上是指驱动在穷尽所有从驱动上下文恢复它的尝试之后，被宣布为死亡的设备。uevent 是发送给用户空间的通知，同时附带一个提示：从用户空间可以做些什么来尝试恢复设备、并将其带回可用状态。不同的驱动对“卡死”设备可能有不同的定义，取决于底层物理设备的硬件实现，因此该事件具有厂商无关的特性。由驱动决定它们何时看到设备恢复的需要，以及它们想用哪种可用方法恢复。

### 驱动前置条件


驱动在寻求恢复之前，需要通过处理好前置条件，确保“卡死”设备不会通过占用系统整体而损害系统。必要的动作必须包括：禁用到系统内存的 DMA，以及任何与其它设备的通信通道。此外，驱动必须确保所有 dma_fence 被发出信号，并且核心内核可能依赖的任何设备状态被清理。所有已有的 mmap 应当被失效，页错误应当被重定向到一个哑页。一旦事件被发出，设备必须保持在“卡死”状态，直到执行了恢复。对设备的新访问（IOCTL）应当被拒绝，最好使用一个类似于设备所遇故障类型的错误码。这将表明卡死的原因，若需要则可报告给应用。

### 恢复


当前的实现定义了四种恢复方法，驱动可以使用其中任意一种、多种，或一种都不用。所选的方法（或多种）将在 uevent 环境中以 `WEDGED=<method1>[,..,<methodN>]` 的形式发送，按副作用由小到大排序。关于 `WEDGED=vendor-specific`，请参见 `Vendor Specific Recovery`_ 一节。如果驱动对恢复不确定或方法未知，则改为发送 `WEDGED=unknown`。

用户空间消费者可以解析此事件，并按如下预期尝试恢复。

    =============== ========================================
    恢复方法        消费者预期
    =============== ========================================
    none            可选的遥测信息收集
    rebind          unbind + bind driver
    bus-reset       unbind + bus reset/re-enumeration + bind
    vendor-specific 厂商特定恢复方法
    unknown         消费者策略
    =============== ========================================

### 无需恢复


这里 `WEDGED=none` 表示消费者无需进行恢复，但它仍可以尝试收集遥测信息（devcoredump、syslog）用于调试目的，以便定位挂起的根因。这很有用，因为第一次挂起通常是最关键的一次，它可能导致连锁挂起或完全的卡死。

### 厂商特定恢复


当发送 `WEDGED=vendor-specific` 时，它表示设备需要一种特定于硬件厂商的恢复流程，而不是标准化方案之一。

`WEDGED=vendor-specific` 可能用于指示单个厂商驱动内的不同情形，每种情形都需要不同的恢复流程。在此类场景中，厂商驱动必须提供全面的文档，描述每种情形，包含用于识别特定情形的额外提示，并列出相应的恢复流程。该文档包括：

Case - 发送 `WEDGED=vendor-specific` 恢复方法的所有情形的列表。

Hints - 用于协助用户空间消费者识别与区分不同情形的额外信息。这可通过 sysfs、debugfs、traces、dmesg 等暴露。

Recovery Procedure - 用于恢复每种情形的清晰指令与指引。这可能包含用户空间脚本、恢复流程所需的工具。

在尝试恢复流程之前，由管理员/用户空间消费者负责识别该情形，并核实额外的识别提示。

示例：如果设备使用 Xe 驱动，那么用户空间消费者应当参考 Xe Device Wedging <xe-device-wedging> 以获取详细文档。

### 任务信息


关于哪个应用（如果有的话）卷入了设备卡死的信息，对用户空间很有用：如果它们想就发生了什么通知用户（例如，compositor 向用户显示消息“<任务名> 导致了图形错误，系统已恢复”），或想实现策略（例如，某个守护进程可能“封禁”一个不断重置设备的任务）。如果任务信息可用，uevent 将显示为 `PID=<pid>` 与 `TASK=<任务名>`。否则，`PID` 与 `TASK` 不会出现在事件字符串中。

此信息的可靠性是驱动与硬件特定的，对它的精确性应谨慎对待。要大致了解真正发生了什么，devcoredump 文件提供了关于设备状态与事件的详细得多的信息。

### 消费者前置条件


在尝试恢复之前，由消费者负责确保在任何进程中设备或其资源都未被使用。由于 IOCTL 会出错，所有设备内存应当被取消映射，文件描述符应当被关闭，以防止泄漏或未定义行为。这里的设想是事先清除设备上的所有用户上下文，为干净恢复做好准备。

对于 `WEDGED=vendor-specific` 恢复方法，在尝试恢复之前，由消费者负责检查驱动文档与用例。

### 示例 - rebind


```
    SUBSYSTEM=="drm", ENV{WEDGED}=="rebind", DEVPATH=="*/drm/card[0-9]",
    RUN+="/path/to/rebind.sh $env{DEVPATH}"
```
```
    #!/bin/sh

    DEVPATH=$(readlink -f /sys/$1/device)
    DEVICE=$(basename $DEVPATH)
    DRIVER=$(readlink -f $DEVPATH/driver)

    echo -n $DEVICE > $DRIVER/unbind
    echo -n $DEVICE > $DRIVER/bind
```
### 定制


虽然用简单脚本即可完成基本恢复，但消费者可以围绕恢复定义自定义策略。例如，如果驱动支持多种恢复方法，消费者可以根据场景（如重复犯错或厂商特定故障）选择合适的方法。消费者也可以选择让设备可用于调试或遥测信息收集，并基于发现来做恢复决策。这在驱动对恢复不确定或方法未知时尤其有用。

### 推荐的 IOCTL 返回值


理论上，驱动的 IOCTL 回调只允许返回极少的错误码。在实践中滥用更多几个也无妨。本节记录了 DRM 子系统内的常见做法：

ENOENT:
        严格地说，这应当只在文件不存在时使用，例如调用 open() 系统调用时。我们复用它来标识任何类型的对象查找失败，例如未知的 GEM 缓冲区对象句柄、未知的 KMS 对象句柄以及类似情况。

ENOSPC:
        一些驱动用它将“内核内存不足”与“VRAM 不足”区分开。有时也适用于渲染所用的其它有限 GPU 资源（例如当你有一个特殊的有限压缩缓冲区时）。命令提交 IOCTL 中的资源分配/预留问题有时也通过 EDEADLK 来标识。

        单纯地耗尽内核/系统内存通过 ENOMEM 来标识。

EPERM/EACCES:
        当某个操作有效但需要更多特权时返回。例如，仅限 root 的、或更常见的、仅限 DRM 主设备的操作，在被非特权客户端调用时会返回此码。EACCES 与 EPERM 之间没有清晰的区别。

ENODEV:
        设备不再存在，或尚未完全初始化。

EOPNOTSUPP:
        驱动不支持某特性（如 PRIME、modesetting、GEM）。

ENXIO:
        远端失败，既可能是硬件事务（如 i2c），也可能是当某个共享 dma-buf 或 fence 的导出驱动不支持所需特性时使用。

EINTR:
        DRM 驱动假设用户空间会重启所有 IOCTL。任何 DRM IOCTL 都可能返回 EINTR，在此情况下应当用未改变的 IOCTL 参数重新启动。

EIO:
        GPU 已死，且无法通过重置复活。modesetting 硬件故障通过“link status”连接器属性来标识。

EINVAL:
        对所有无法工作的无效参数组合的兜底。

IOCTL 也使用其它错误码，如 ETIME、EFAULT、EBUSY、ENOTTY，但它们的用法符合常见含义。上述清单只是试图记录 DRM 特定的模式。注意 ENOTTY 有略微反直觉的含义“此 IOCTL 不存在”，并且在 DRM 中正是如此使用。

## 测试与验证


### 用户空间 API 的测试要求


新的跨驱动用户空间接口扩展，如新的 IOCTL、新的 KMS 属性、sysfs 中的新文件或任何构成 API 变更的东西，都应当在 IGT 中有与驱动无关的测试用例，只要这样的测试可以用 IGT 针对目标硬件合理地做出。

### 使用 IGT 验证变更


有一组测试旨在覆盖 DRM 驱动的全部功能，可用于检查对 DRM 驱动或核心的改动不会让已有功能回归。这个测试套件称为 IGT，其代码以及构建与运行说明可在 https://gitlab.freedesktop.org/drm/igt-gpu-tools/ 找到。

### 使用 VKMS 测试 DRM API


VKMS 是一个仅软件的 KMS 驱动模型，对测试与运行 compositor 很有用。VKMS 旨在无需硬件显示能力即可启用虚拟显示。这些特性使 VKMS 成为验证 DRM 核心行为并支持 compositor 开发者的完美工具。VKMS 使得可以在没有显示器的虚拟机中测试 DRM 函数，从而简化了对某些核心变更的验证。

要用 VKMS 验证 DRM API 的变更，先准备好内核：确保启用 VKMS 模块；编译启用了 VKMS 的内核并安装到目标机器。VKMS 可以在虚拟机（QEMU、virtme 或类似）中运行。推荐使用 KVM，至少 1GB 内存与四个核心。

可以以两种方式在虚拟机中运行 IGT 测试：

 1. 在虚拟机内使用 IGT
 2. 从宿主机使用 IGT，并将结果写入一个共享目录。

以下是使用带共享目录的虚拟机的示例：
```
	$ virtme-run --rwdir /path/for/shared_dir --kdir=path/for/kernel/directory --mods=auto
```
在客户机中运行 igt 测试。此示例运行 'kms_flip'
```
	$ /path/for/igt-gpu-tools/scripts/run-tests.sh -p -s -t "kms_flip.*" -v
```
在此示例中，并非构建 igt_runner，而是使用了 Piglit（-p 选项）。它创建测试结果的 HTML 摘要并保存到 "igt-gpu-tools/results" 文件夹。它只执行匹配 -t 选项的 igt 测试。

## Vblank 事件处理


DRM 核心导出两个与垂直消隐相关的 ioctl：

`DRM_IOCTL_WAIT_VBLANK`
    它接受一个 struct drm_wait_vblank 结构体作为参数，用于在指定的 vblank 事件发生时阻塞或请求一个信号。

`DRM_IOCTL_MODESET_CTL`
    这仅被用于用户模式设置（user-mode-setting）驱动，围绕 modesetting 变更，以允许内核在模式设置后更新 vblank 中断，因为在许多设备上垂直消隐计数器会在 modeset 期间的某个时刻被重置为 0。现代驱动不应再调用它，因为在内核模式设置下它是不操作（no-op）。

### CRTC 索引


CRTC 既有对象 ID，也有索引，它们不是同一个东西。索引用于需要 CRTC 的紧凑标识符的情形，例如 CRTC 的位掩码。struct drm_mode_get_plane 的成员 possible_crtcs 就是一个例子。

`DRM_IOCTL_MODE_GETRESOURCES` 用一个包含 CRTC ID 数组的结构体填充数据，而 CRTC 索引就是它在这个数组中的位置。
