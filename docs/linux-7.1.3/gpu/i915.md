## 内存管理与命令提
本节涵盖i915 驱动GEM 实现相关的所有内容
### Intel GPU 基础

Intel GPU 拥有多个引擎（engine）。引擎有以下几种类型
- Render Command Streamer（RCS，渲染命令流送器）：用于渲染 3D 与执行计算的引擎- Blitting Command Streamer（BCS，位块传送命令流送器）：用于执行位块传送（blitting）和/或复制操作的引擎- Video Command Streamer（视频命令流送器）：用于视频编码与解码的引擎。在硬件文档中有时也称为 'BSD'- Video Enhancement Command Streamer（VECS，视频增强命令流送器）：用于视频增强的引擎。在硬件文档中有时也称为 'VEBOX'- Compute Command Streamer（CCS，计算命令流送器）：可访问媒体与 GPGPU 流水线，但无法访3D 流水线的引擎- Graphics Security Controller（GSCCS，图形安全控制器）：一个专用引擎，用于GSC 控制器就安全相关任务进行内部通信，例High-bandwidth Digital Content Protection（HDCP，高带宽数字内容保护）、Protected Xe Path（PXP）以HuC 固件认证
Intel GPU 家族是一系列采用统一内存访问（Unified Memory Access）的集成 GPU。为了让 GPU "干活"，用户空间会通过 `DRM_IOCTL_I915_GEM_EXECBUFFER2` `DRM_IOCTL_I915_GEM_EXECBUFFER2_WR` 这两ioctl 之一GPU 喂入批处理缓冲（batch buffer）。大多数这样的批处理缓冲会指GPU 执行工作（例如渲染），而该工作既需要用于读取的内存，也需要用于写入的内存。所有内存都被封装在 GEM 缓冲对象（通常经由 `DRM_IOCTL_I915_GEM_CREATE` ioctl 创建）中。提供一个供 GPU 创建的批处理缓冲ioctl 还会列出该批处理缓冲所读取或写入的所GEM 缓冲对象。关于内存管理的实现细节，请参阅 `GEM BO Management Implementation Details`_
i915 驱动允许用户空间通过 `DRM_IOCTL_I915_GEM_CONTEXT_CREATE` ioctl 创建一个上下文（context），该上下文由一32 位整数标识。用户空间应当（粗略地）将这样的上下文视为类似于操作系统CPU 进程的概念。i915 驱动保证：向一个固定上下文发出的命令会按顺序执行，使得先前命令的写入能被后续命令的读取看到。在不同上下文之间发出的操作（即使来自同一个文件描述符）不享有该保证，而跨上下文（即使来自同一个文件描述符）唯一同步的方式是使用栅栏（fence）。至少自 Gen4 起，上下文还携带一GPU 硬件上下文（HW context）；硬件上下文本质上（至少大部分是）GPU 的状态。除了顺序保证之外，当向一个上下文发出命令时，内核会通过硬件上下文恢GPU 状态，这就省去了用户空间在每个批处理缓冲开始时恢复（至少大部分）GPU 状态的需要。用于提交批处理缓冲、未被弃用的 ioctl 可以将该 ID（放drm_i915_gem_execbuffer2 的低**: rsvd1）中传递，以指明命令要使用哪个上下文
GPU 拥有自己的内存管理与地址空间。内核驱动维GPU 的内存转换表。对于较老的 GPU（即 Gen8 之前的那些），存在一张单一的全局转换表，即全局图形转换表（GTT，Graphics Translation Table）。对于更新一代的 GPU，每个上下文都有自己的转换表，称为每进程图形转换表（PPGTT，Per-Process Graphics Translation Table）。需要特别注意的一点是，虽PPGTT 名为 per-process（每进程），但它实际上是 per-context（每上下文）。当用户空间提交一个批处理缓冲时，内核会遍历该批处理缓冲所使用GEM 缓冲对象列表，并保证其中每个 GEM 缓冲对象的内存不仅常驻，而且存在(PP)GTT 中。如果某GEM 缓冲对象尚未被放(PP)GTT，则会给它分配一个地址。这样做有两个后果：当给一GEM BO 分配 GPU 地址时，内核需要修改提交的批处理缓冲、写入正确的 GPU 地址值；并且内核可能会从 (PP)GTT 中驱逐另一GEM BO，以便为另一GEM BO 腾出地址空间。因此，用于提交批处理缓冲执行的 ioctl 还包含缓冲内所有引用了 GPU 地址的位置列表，以便内核能够正确修改缓冲。这一过程被称为重定位（relocation）
### 加锁准则

   This is a description of how the locking should be after
   refactoring is done. Does not necessarily reflect what the locking
   looks like while WIP.

#. 所有加锁规则以及与跨驱动接口（dma-buf、dma_fence）的接口契约都需要被遵守
#. dma_resv 将是最外层锁（在需要时），ww_acquire_ctx 应提升到最高层级，并在调用链中经由 i915_gem_ctx 向下传递
#. 在持lru/内存管理器（buddy、drm_mm 等）锁时，不允许进行系统内存分配
#. 不要将不同的 lru/内存管理器锁相互嵌套。应依次获取它们来更新内存分配，依靠对象dma_resv ww_mutex 来与其他操作串行化
#. 对于 lru/内存管理器锁的建议是：它们应当足够小，可以用自旋锁（spinlock）实现
#. 所有特性都需要附带详尽的 kernel selftest 或（在适当时）IGT 测试
#. 所LMEM uAPI 路径都需要完全可重启（对所有锁/等待/睡眠使用 _interruptible()）
