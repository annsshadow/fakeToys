
## 用户模式队列


## 简介


与 KFD 类似，GPU 引擎队列被移入用户空间。其思路是让用户进程直接管理向 GPU
引擎的提交，绕过驱动中的 IOCTL 调用来提交任务。这降低了开销，并允许 GPU 向
自身提交任务。应用程序可以在多个 GPU 引擎之间建立作业的工作图，而无需经由 CPU
中转。

UMD 通过每个应用程序的共享内存区域直接与固件交互。其中的主要载体是队列。队列
是一个带有读指针（rptr）和写指针（wptr）的环形缓冲区。UMD 向队列中写入特定于
IP 的数据包，固件处理这些数据包，从而在 GPU 引擎上启动任务。应用程序中的 CPU
（或另一个队列或设备）更新 wptr，以告知固件应当处理环形缓冲区中的多少数据包，
而 rptr 则向 UMD 反馈固件执行这些数据包的进度。当 wptr 与 rptr 相等时，队列
处于空闲状态。

## 工作原理


现代 AMD GPU 上的各种引擎支持每个引擎多个队列，并配有一个调度固件，负责在
可用的硬件队列槽位上动态调度用户队列。当用户队列数量超过可用的硬件队列槽位
时，调度固件会根据优先级和时间片动态映射和取消映射队列。每个用户队列的状态
由内核驱动在一个 MQD（Memory Queue Descriptor，内存队列描述符）中进行管理。
这是一块 GPU 可访问内存中的缓冲区，用于存储某个用户队列的状态。当用户队列被
映射时，调度固件使用 MQD 将队列状态加载到 HQD（Hardware Queue Descriptor，硬件
队列描述符）中。每个用户队列还需要若干额外的缓冲区，用于表示环形缓冲区以及
引擎在运行时所需的任何元数据。在大多数引擎上，这包括环形缓冲区本身、一个
rptr 缓冲区（固件将把 rptr 影子复制到用户空间）、一个 wptr 缓冲区（应用程序
将向内写入 wptr 供固件获取）以及一个 doorbell（门铃）。门铃是设备 MMIO BAR
中的一段，可被映射到特定的用户队列。当应用程序写入门铃时，它会通知固件采取
某些动作。写入门铃会唤醒固件，并使其获取 wptr 并开始处理队列中的数据包。门铃
BAR 的每一 4K 页为特定引擎提供特定的偏移范围。队列的门铃必须映射到与队列所用
IP（例如 GFX、VCN、SDMA 等）对齐的窗口中。这些门铃窗口通过 NBIO 寄存器设置。
门铃是门铃 BAR 中 32 位或 64 位（取决于引擎）的数据块。一个 4K 门铃页提供 512
个 64 位门铃，最多对应 512 个用户队列。每一页的一部分会保留给设备上支持的
每种 IP 类型。用户可以通过 INFO IOCTL 查询每种 IP 的门铃范围。更多信息请参阅
IOCTL 接口一节。

当应用程序想要创建一个用户队列时，它会为队列分配必要的缓冲区（环形缓冲区、
wptr 与 rptr、上下文保存区等）。这些可以是独立的缓冲区，也可以全部属于一个
更大的缓冲区。应用程序会将缓冲区映射到其 GPUVM 中，并使用其所要用于用户队列
的内存区域的 GPU 虚拟地址。它还会为这些用户队列使用的门铃分配一个门铃页。
随后，应用程序会在 USERQ IOCTL 结构的 MQD 中填入它要使用的 GPU 虚拟地址和
门铃索引。用户还可以指定用户队列的属性（优先级、队列是否用于受保护内容的
安全队列等）。然后，应用程序会调用 USERQ CREATE IOCTL，使用 IOCTL 中指定的
MQD 细节来创建队列。内核驱动随后会校验应用程序提供的 MQD，并将其转换为该 IP
特定的 MQD 格式。特定于 IP 的 MQD 会被分配，队列会被加入调度固件维护的运行
列表（run list）。一旦队列创建完成，应用程序就可以直接向队列中写入数据包、
更新 wptr，并写入门铃偏移以在用户队列中启动任务。

当应用程序使用完用户队列后，它会调用 USERQ FREE IOCTL 来销毁它。内核驱动会
抢占该队列并将其从调度固件的运行列表中移除。然后特定于 IP 的 MQD 会被释放，
用户队列状态会被清理。

如果某个引擎不支持从未映射队列发起的门铃，则它可能还需要聚合门铃（aggregated
doorbell）。聚合门铃是一段特殊的门铃空间页，用于唤醒调度器。在引擎可能超额
订阅的情况下，某些队列可能未被映射。如果在队列未映射时敲响门铃，引擎固件
可能会错过该请求。某些调度固件可以通过在硬件超额订阅时轮询 wptr 影子来绕过
此问题，其他引擎则可能支持从未映射队列更新门铃。若这些选项中均不可用，内核
驱动会向每个 GPUVM 空间映射一页聚合门铃空间。UMD 随后照常更新门铃和 wptr，并
同时写入聚合门铃。

### 特殊数据包


为了支持传统的隐式同步，以及混合的用户与内核队列，我们需要一种安全的同步
机制。由于内核队列或内存管理任务依赖于内核 fence，我们需要一种让用户队列
更新内存中可供内核用于 fence 的位置、且不会被恶意行为者破坏的方式。为此，我们
添加了受保护 fence 数据包。该数据包的工作方式是向一个只有特权客户端才有
写权限的内存位置写入一个单调递增的值。用户队列只有读权限。当该数据包被执行
时，该内存位置被更新，其他队列（内核或用户）可以看到结果。用户应用程序会在
其命令流中提交该数据包。实际的数据包格式因 IP 而异（GFX/Compute、SDMA、VCN
等），但行为相同。数据包的提交在用户空间处理。内核驱动在应用程序创建队列时
设置每个用户队列所用的特权内存。

## 内存管理


假定映射到进程 GPUVM 空间中的所有缓冲区在 GPU 上的引擎运行时都是有效的。内核
驱动只允许在全部缓冲区都已映射时才运行用户队列。如果发生需要缓冲区迁移的内存
事件，内核驱动会抢占用户队列、将缓冲区迁移到所需位置、更新 GPUVM 页表并使
TLB 失效，然后恢复用户队列。

## 与内核队列的交互


根据 IP 和调度固件的不同，你可以同时启用内核队列和用户队列，但会受 HQD 槽位
限制。内核队列始终被映射，因此进入内核队列的任何任务都会享有优先级。这限制了
可用于用户队列的 HQD 槽位数量。

并非所有 IP 在所有 GPU 上都支持用户队列。因此，UMD 需要根据 IP 同时支持用户
队列和内核队列。例如，某个 GPU 可能支持 GFX、compute 和 SDMA 的用户队列，但不
支持 VCN、JPEG 和 VPE。UMD 需要对两者都提供支持。内核驱动提供了一种方式来
逐 IP 地判定是否支持用户队列和内核队列。UMD 可以通过 INFO IOCTL 查询此信息，
并决定对每个 IP 使用内核队列还是用户队列。

## 队列重置


对于大多数引擎，队列可以单独重置。GFX、compute 和 SDMA 队列都可以单独重置。
当检测到某个挂起的队列时，可以通过调度固件或 MMIO 将其重置。由于大多数用户
队列没有内核 fence，通常只有在发生其他事件时才会被检测到，例如需要迁移缓冲区
的内存事件。当队列被抢占时，如果队列已挂起，抢占将失败。驱动随后会查找抢占
失败的队列并将其重置，同时记录哪些队列已挂起。

在 UMD 侧，我们将添加一个 USERQ QUERY_STATUS IOCTL 来查询队列状态。UMD 会在
IOCTL 中提供队列 id，内核驱动会检查它是否已经将该队列记录为挂起（例如由于抢占
失败），并报告状态。

## IOCTL 接口


用于队列及相关数据（rptr、wptr、上下文保存区等）的 GPU 虚拟地址应由内核模式
驱动校验，以防止用户指定无效的 GPU 虚拟地址。如果用户提供了无效的 GPU 虚拟
地址或门铃索引，IOCTL 应返回错误消息。这些缓冲区还应被内核驱动跟踪，以便当
用户试图从 GPUVM 中解除映射这些缓冲区时，解除映射调用会返回错误。

### INFO

有几个与用户队列相关的新 INFO 查询，用于查询用户队列所需的用户队列元数据大小
（例如上下文保存区或影子缓冲区）、每个 IP 类型是否支持内核或用户队列或两者，
以及每个 IP 类型在每个门铃页中的偏移。

### USERQ

USERQ IOCTL 用于创建、释放和查询用户队列的状态。它支持 3 个操作码：

1. CREATE - 创建一个用户队列。应用程序提供一个类似 MQD 的结构，定义该队列的
   类型以及与之关联的元数据和标志。返回队列 id。
2. FREE - 释放一个用户队列。
3. QUERY_STATUS - 查询队列的状态。用于检查队列是否健康。例如，队列是否已被
   重置。（WIP）

### USERQ_SIGNAL

USERQ_SIGNAL IOCTL 用于提供一组要被触发的同步对象列表。

### USERQ_WAIT

USERQ_WAIT IOCTL 用于提供一组要被等待的同步对象列表。

## 内核队列与用户队列


为了正确地验证和测试性能，我们提供了一个驱动选项来选择启用哪种类型的队列
（内核队列、用户队列或两者）。`user_queue` 驱动参数允许你仅启用内核队列（0）、
用户队列和内核队列（1），以及仅用户队列（2）。仅启用用户队列会释放出原本被
内核队列占用的静态队列分配，供调度固件使用。某些内核队列是内核驱动运行所必需
的，它们将始终被创建。当未启用内核队列时，它们不会被注册到 drm scheduler，
并且 CS IOCTL 会拒绝任何以这些队列类型为目标的传入命令提交。仅内核队列的方式
与所有现有 GPU 上的行为一致。同时启用两类队列可在支持用户队列的同时向后兼容
旧的用户空间。
