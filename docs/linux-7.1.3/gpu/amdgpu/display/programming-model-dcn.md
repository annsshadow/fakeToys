## DC 编程模型


在 Display Core Next（DCN）<dcn_overview> 与 :ref:`DCN 模块 <dcn_blocks>` 页面中，你已经了解了硬件组件以及它们如何相互交互。本页将重点转移到显示代码架构上。因此，提醒读者：DC 中的代码是与其他操作系统共享的；为此，DC 提供了一组抽象与操作，用于将不同的 API 与硬件配置连接起来。可将 DC 视为由显示管理器（amdgpu_dm）使用的一项服务，用于访问和配置 DCN/DCE 硬件（DCE 也是 DC 的一部分，但为简洁起见，本文档只考察 DCN）。

   在本页中，我们使用术语 GPU 来指代 dGPU 和 APU。

## 概述


从显示硬件的角度看，如果一个问题被很好地定义，那么它很可能是在硬件层面实现的，这是合理的。另一方面，当有多种达成某事的方式而范围又没有被很好地定义时，解决方案通常作为策略在 DC 层面实现。换言之，某些策略定义在 DC 核心中（资源管理、功耗优化、图像质量等），而其他在硬件中实现的部分则通过 DC 配置来启用。

在硬件管理方面，DCN 有多个相同模块的实例（例如 HUBP、DPP、MPC 等），在驱动执行期间，可能需要使用其中某些实例。核心针对处理这些实例制定了策略。关于资源管理，DC 的目标相当简单：在驱动执行某些操作时，尽量减少硬件的重新洗牌。当状态从 A 变为 B 时，如果硬件资源仍服务于同一组驱动对象，则认为这种转换更容易驾驭。通常，向 `pipe_ctx`（详见下文）添加或移除资源不是问题；然而，应尽量避免将一个资源从一个 `pipe_ctx` 移动到另一个。

DC 产生影响的另一个领域是功耗优化，它有无数种可能的安排。在某种程度上，仅仅通过 DCN 显示一幅图像应该相对直接；然而，以最佳的功耗占用显示它更为理想，但这伴随许多相关挑战。遗憾的是，由于与此问题相关的变量极其繁多（例如许多不同的 DCN/DCE 硬件版本、不同的显示配置等），没有直接的解析方法来确定某种配置对当前环境是否最佳；为此，DC 实现了一个专用库来尝试某些配置并验证其是否可能被支持。这类策略的创建和维护极其复杂，amdgpu 驱动依赖显示模式库（DML）来生成最佳决策。

总之，DC 必须应对处理多种场景的复杂性，并确定管理它们的策略。提供上述所有信息是为了让读者对从驱动视角驱动显示器的复杂性有一些概念。本页希望能让读者更好地在 amdgpu 显示代码中导航。

### 基本对象


下图概述了基本的显示对象。尤其要注意框中的名称，因为它们代表驱动中的一个数据结构：


让我们从图中中心的块 `dc` 开始。`dc` 结构体按每个 GPU 初始化；例如，一个 GPU 有一个 `dc` 实例，两个 GPU 有两个 `dc` 实例，依此类推。换言之，每个“amdgpu”实例对应一个“dc”。在某些方面，该对象的行为类似于 `Singleton` 模式。

在图中的 `dc` 块之后，你可以看到 `dc_link` 组件，它是连接器的低层抽象。图中一个有趣的方面是，连接器不是 DCN 块的一部分；它们由平台/板卡定义，而不是由 SoC 定义。`dc_link` 结构体是高层数据容器，包含已连接 sink、连接状态、信号类型等信息。在 `dc_link` 之后是 `dc_sink`，它是表示所连接显示器的对象。

   由于历史原因，我们使用了名称 `dc_link`，这给人一种错误的印象，即此抽象只处理开发者可以轻易操作的物理连接。然而，它也涵盖像 eDP 这样的连接，或者输出连接到其他设备的情况。

有两个结构体没有在图中表示，因为它们已在 DCN 概述页中详述（查看 DCN 模块图 :ref:`Display Core Next (DCN) <dcn_overview>`）；不过，对本次概述而言仍值得重新提及，即 `dc_stream` 和 `dc_state`。`dc_stream` 存储许多与数据传输相关的属性，但最重要的是，它表示从连接器到显示器的数据流。接下来是 `dc_state`，它表示此刻硬件内部的逻辑状态；`dc_state` 由 `dc_stream` 和 `dc_plane` 组成。`dc_stream` 是 `drm_crtc` 的 DC 版本，表示混合后（post-blending）的流水线。

说到 `dc_plane` 数据结构（图的第一部分），你可以将其视为类似于 `drm_plane` 的抽象，表示流水线中混合前（pre-blending）的部分。此图像可能已由 GFX 处理，并已准备好在 `dc_stream` 下合成。通常，驱动可能有一个或多个 `dc_plane` 连接到同一个 `dc_stream`，这定义了 DC 层面的一个合成。

### 基本操作


既然我们已经介绍了基本对象，现在来看看一些基本的硬件/软件操作。让我们从 `dc_create()` 函数开始，它直接操作 `dc` 数据结构；该函数就像一个构造函数，负责基本的软件初始化，并为启用 API 的其他部分做准备。需要强调的是，此操作不接触任何硬件配置；它只是软件初始化。

接下来是 `dc_hardware_init()`，它也依赖于 `dc` 数据结构。它的主要功能是将硬件置于一个有效状态。需要强调的是，硬件可能以未知状态初始化，而将其置于有效状态是一项要求；此函数有多个用于硬件特定初始化的回调，而 `dc_hardware_init` 执行硬件初始化，是我们首次接触硬件的地方。

`dc_get_link_at_index` 是一个依赖于 `dc_link` 数据结构的操作。该函数检索并枚举设备上所有可用的 `dc_link`；这是必需的，因为该信息不属于 SoC 定义，而是取决于板卡配置。一旦 `dc_link` 初始化完成，通过使用 `dc_link_detect()` 函数来判断其中是否有任何已连接到显示器是很有用的。在驱动确定是否有任何显示器连接到设备之后，挑战性的阶段开始了：配置显示器以显示某些内容。尽管如此，处理理想配置并非 DC 的任务，因为这是显示管理器（`amdgpu_dm`）的职责，它负责处理原子提交（atomic commits）。DC 在配置阶段提供的唯一接口是函数 `dc_validate_with_context`，它接收配置信息，并据此验证硬件是否支持它。需要补充的是，即使显示器支持某些特定配置，也不意味着 DCN 硬件能够支持它。

在 DM 和 DC 就配置达成一致后，流配置阶段开始。此任务在该阶段激活一个或多个 `dc_stream`，在最佳情况下，你可能能够点亮显示器但显示黑屏（由于尚未关联任何 plane，因此它还不显示任何内容）。最后一步是调用 `dc_update_planes_and_stream,`，它会添加或移除 plane。
