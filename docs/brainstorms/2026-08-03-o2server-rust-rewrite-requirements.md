# O2OA 后端 Rust 改写

## Summary

将 O2OA 后端（`o2server`）从 Java/Maven 逐步迁移到 Rust，前端保持不变。采用「边运行边替换」策略，以单体服务形态运行 Rust 后端，通过 nginx 或等价反向代理前缀路由接入，数据迁移采用一次性切换窗口。第一步产出模块梳理与落地文档，作为后续逐模块替换的实施依据和跟踪清单。

---

## Problem Frame

`o2server` 是 O2OA 的 Java 后端，包含 57+ Maven 模块，是整套 OA 系统的核心。Java 运行时（Jetty + OpenJPA + H2/MySQL）需要持续维护，长期技术栈锁定在 Java 生态。技术探索的目标是验证 Rust 作为企业后端服务语言的可维护性和工程可行性，以单体服务形态逐步替代各 Java 模块，降低长期运行成本和依赖复杂度。

目前缺乏面向改写的全局模块依赖梳理，没有明确的模块替换优先级和落地跟踪机制，这是启动改写前必须解决的前提。

---

## Terminology

- **Maven 模块**：`o2server/` 下的 Java 技术单元，以 `pom.xml` 为单位，共 57+ 个，是模块梳理和优先级排序的基本单位。
- **业务域**：按功能边界划分的逻辑域（如组织、考勤、流程），用于 Rust 侧 crate 划分的依据。
- **迁移模块**：本需求中「模块替换」的基本粒度，与 Maven 模块的映射关系（1:1 或 N:1）在模块梳理阶段确定。

---

## Actors

- A1. 开发者（单人）：负责模块梳理、Rust 编码、数据迁移和部署切换的全流程。
- A2. 现有 Java 后端：改写过程中持续运行的服务，作为 Rust 模块替换前的稳定依赖源。
- A3. 前端 `o2web`：通过 nginx 或等价反向代理访问后端，对后端实现无感知，只关心 URL 前缀路由规则。

---

## Key Flows

- F1. 模块梳理与优先级排序
  - **Trigger:** 启动改写项目
  - **Actors:** A1
  - **Steps:** 扫描所有 `o2server` Maven 模块的 pom.xml 依赖关系 → 构建模块依赖图谱 → 按「依赖少、业务清晰、替换杠杆高」排序 → 确定模块替换优先级
  - **Outcome:** 产出 `docs/brainstorms/o2server-module-index.md`（模块梳理与落地文档），包含模块列表、依赖关系、替换优先级和每模块迁移策略
  - **Covered by:** R1, R2

- F2. Rust 服务独立开发与测试
  - **Trigger:** 优先级最高的模块确定后
  - **Actors:** A1
  - **Steps:** 搭建 Rust 项目（见 Key Decisions 技术选型）→ 实现目标模块的业务逻辑 → 在独立数据库上编写测试数据验证功能 → 确认模块行为与 Java 侧一致
  - **Outcome:** Rust 侧单个模块通过功能验证，处于可上线状态
  - **Covered by:** R3, R4, R5

- F3. 数据迁移与流量切换
  - **Trigger:** Rust 模块功能验证通过
  - **Actors:** A1, A2
  - **Steps:** 编写旧数据迁移脚本（MySQL/OpenJPA → Rust 侧数据库）→ 在低峰期执行迁移 → 切换 nginx 路由，将对应前缀流量切到 Rust 服务 → 监控运行稳定性 → 确认无误后停止 Java 侧对应模块的写入
  - **Outcome:** 该模块的流量由 Rust 服务承载，Java 侧对应模块下线，两份数据完成对齐
  - **Covered by:** R6, R7

- F4. 持续迭代下一模块
  - **Trigger:** 上一模块成功切换
  - **Actors:** A1
  - **Steps:** 参照落地文档中的优先级列表，选择下一模块 → 重复 F2 → F3
  - **Outcome:** 所有模块逐步迁移完成
  - **Covered by:** R8, R9

## Requirements

**模块梳理与落地文档**
- R1. 扫描 `o2server/` 下全部 Maven 模块的 `pom.xml`，产出完整的模块依赖图谱，覆盖所有 57+ 模块及其依赖方向。
- R2. 基于依赖图谱，按「依赖少、业务清晰、替换杠杆高」三个维度对模块进行优先级排序，形成模块替换路线图，输出到 `docs/brainstorms/o2server-module-index.md`。
- R3. 每个模块在落地文档中包含一张标准化卡片，记录：模块名、职责描述、核心对外接口摘要、依赖的其他模块列表、对应的数据库表（如可识别）、替换优先级、迁移策略备注。模块依赖关系以表格形式呈现（至少包含模块名、依赖列表、被依赖列表三列）；优先级排序需注明「依赖少、业务清晰、替换杠杆高」三个维度的评分规则。

**Rust 项目初始化和架构**
- R4. Rust 后端编译为单一进程单体服务，通过单一二进制部署运行。
- R5. 单体服务内部按模块边界组织代码，具体 crate 划分根据模块依赖分析结果确定，在代码层面保持模块化，但运行时为单一进程。
- R6. Rust 服务需支持 HTTP 框架、类型安全的数据访问、连接池管理和 schema 迁移管理。具体技术选型记录于 Key Decisions，在模块分析后确认。
- R7. Rust 项目采用 Cargo workspace 组织，支持按 crate 独立编译和测试；各 crate 最终链接为单一二进制，运行时共享同一进程。

**集成与部署**
- R8. Rust 服务与 Java 服务独立部署、独立进程，互不依赖。
- R9. 前端通过 nginx 或等价反向代理按 URL 前缀路由请求：原有路径（如 `/jaxrs/*`）继续指向 Java 服务，已迁移模块的路径指向 Rust 服务。前端无需改动代码。
- R10. 两个服务在同一 API 前缀空间内无冲突：迁移前后前端感知到的 URL 路径保持不变。

**数据迁移**
- R11. Rust 侧使用独立数据库实例，与 Java 侧的 MySQL/H2 物理隔离，运行时无数据互通。具体数据库类型记录于 Key Decisions，在模块分析后确认。
- R12. 每个模块切换前，需有可执行的数据迁移方案，将 Java 侧该模块的持久化数据转换导入 Rust 侧数据库。
- R13. 数据迁移脚本需在切换窗口期执行，迁移完成后进行数据一致性校验，校验通过后才允许切换流量。

**运行与切换**
- R14. 每个模块的替换遵循「独立开发验证 → 数据迁移 → 流量切换 → Java 下线」四步流程，四步之间允许回滚。流量切换后如发现问题，可在 nginx 层快速将前缀路由切回 Java 服务；数据迁移脚本需支持幂等重跑，以便回滚后重新迁移。
- R15. 在 Rust 服务运行期间，Java 服务持续正常运行，承担未迁移模块的请求处理。

**可追溯性**
- R16. `docs/brainstorms/o2server-module-index.md` 作为跟踪清单，记录每个模块的替换状态（待迁移 / 迁移中 / 已完成 / 已下线）。

## Acceptance Examples

- AE1. **Covers R1, R2.** 扫描完成所有 `o2server` 模块的 `pom.xml` 后，落地文档中包含 57+ 个模块条目，每个条目标注了直接依赖的模块列表和优先级排序，开发者能通过文档看出替换顺序。
- AE2. **Covers R9, R10.** 将考勤模块迁移到 Rust 后，前端访问考勤相关接口的 URL 路径保持不变（如仍为 `/jaxrs/x_attendance_*`），nginx 内部将请求路由到 Rust 服务，前端页面无需任何代码改动，功能正常。
- AE3. **Covers R12, R14.** 组织管理模块切换时，迁移脚本成功将 Java 侧 MySQL 中组织相关数据导入 Rust 侧数据库，校验通过后切流，Java 侧组织模块停止接收写入请求，整个过程可回滚至切流前状态。

---

## Success Criteria

- 模块梳理文档（R1-R3）产出后，能清晰展示所有模块的依赖关系和替换优先级排序，新加入的开发者阅读文档后能理解替换路线图。
- Rust 单体服务启动后，通过 nginx 前缀路由与 Java 服务共存，前端无感知切换。
- 每个模块的替换遵循四步流程（R14），每一步都有可回滚的降级方案。
- 数据迁移脚本可重复执行，迁移结果通过一致性校验，无数据丢失。
- 模块跟踪清单（R16）持续反映真实状态，是后续迭代的唯一权威来源。

---

## Scope Boundaries

- 不修改前端 `o2web` 的任何代码，仅通过 URL 前缀路由适配后端切换。
- 不在改写期间实现 Java ↔ Rust 的实时数据同步，仅依赖一次性迁移窗口。
- 不拆分为微服务，Rust 侧始终以单一进程单体服务运行。
- 不包含 Rust 性能压测或与 Java 的基准对比，可行性验证通过功能正确性和可维护性来判断。
- 不迁移 `o2web` 前端，该部分保持现状，后续独立评估是否需要现代化。

---

## Key Decisions

- **单体服务而非微服务**：单人项目，微服务的运维复杂度和调试成本对新手不可承受，Rust 单体的性能和处理能力足以覆盖当前规模。
- **nginx 前缀路由**：Java 和 Rust 服务独立进程、独立部署，互不知晓，nginx 前缀路由作为唯一集成点，切换和回滚成本最低。
- **PostgreSQL + 一次性迁移**：选择 PostgreSQL 作为 Rust 侧数据库，与 Java 侧的 MySQL/H2 物理隔离，消除 schema 冲突风险；迁移窗口期由开发者手动控制，不引入消息队列等额外基础设施。
- **Axum 作为 HTTP 框架**：社区活跃、文档丰富、学习曲线平缓，适合 Rust 新手起步。
- **SQLx 直写 SQL 而非 ORM**：编译时 SQL 检查降低新手错误率，手动管理 schema 迁移，与 Java 侧 JPA 的 schema 定义解耦。
- **先出模块梳理文档再动手编码**：57+ 模块规模下，没有优先级排序的改写等同于随机替换，落地文档是后续所有模块替换的权威依据。

---

## Dependencies / Assumptions

- Java 服务在 Rust 改写期间持续稳定运行，是 Rust 模块功能验证前的可用参照物。
- 每个模块的 Java 源码可读，作为 Rust 实现的业务逻辑参照。
- 模块梳理阶段能通过 `pom.xml` 完整识别模块依赖关系，如有动态发现或运行时依赖需在规划阶段补充。
- 迁移窗口期的数据量在可接受范围内，迁移脚本能在合理时间内完成执行和数据校验。
- nginx（或等价反向代理）已存在或可部署，作为前缀路由层。

## Outstanding Questions

### Deferred to Planning

- [Affects R12][Needs research] 第一个模块切换时，具体哪些数据表需要迁移、表间关系如何转换，需在规划阶段结合模块梳理结果确定。
- [Affects R5][Needs research] Crate 划分的具体边界（如 `organization`、`attendance`、`process` 各自包含哪些子域）需在规划阶段根据模块依赖分析结果确定。
- [Affects R13][Needs research] 数据一致性校验的具体方案（行数对比、抽样校验、还是业务逻辑校验）需在规划阶段根据数据特性确定。
- [Affects R1][Needs research] 落地文档中的模块依赖图谱的渲染方式（Mermaid 图、表格、还是工具自动生成）需在规划阶段确定。
- [Affects R6][User decision] 认证/授权模块（`x_organization_*` 中相关部分）是否作为第一个被替换的模块，还是在 Rust 侧先建立独立的认证基础设施再替换业务模块，需在规划阶段决定。
- [Affects R8][Needs research] 过渡期内 Rust 与 Java 模块间的运行时调用如何处理——已迁移模块被 Java 侧调用、或 Rust 侧需要调用未迁移模块的场景，需在规划阶段定义跨服务调用机制。
- [Affects R11][Needs research] 数据迁移策略需评估过渡期双写或共享数据库方案的可行性，作为一次性迁移的回滚备选，需在规划阶段完成方案对比并确定最终策略。
- [Affects R12][Needs research] 定时任务、批处理等非 HTTP 后台作业的迁移策略——需在模块梳理阶段识别各模块的后台作业，制定随模块迁移或保持 Java 侧运行的方案。
- [Affects R12][Needs research] 文件存储（本地文件系统、NAS、对象存储、数据库 BLOB）的迁移方案——需在模块梳理阶段统计各模块的文件存储位置和访问方式，确保数据迁移时文件实体不丢失。
