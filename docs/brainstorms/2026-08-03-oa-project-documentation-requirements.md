# oa 子项目完整项目文档

## Summary

为 `oa` 子项目建立一套完整的项目文档，输出到 `docs/oa/` 目录。文档以架构图 + 模块卡片作为主要载体，对 API、配置项等数据密集型内容辅以代码驱动自动提取，覆盖文档目录与入口、架构概览、模块卡片、开发环境与部署、API 与数据结构、业务功能说明、开发者指南、可维护性八大板块。

---

## Problem Frame

`oa` 子项目包含 `o2server`（60+ Maven 模块）和 `o2web`（组件化前端）两大部分，现有 `oa/README.md` 只提供官方介绍，缺少面向开发者的深度文档。新加入的开发者难以快速建立全局架构认知，也缺乏模块级和接口级的参考手册。完整的项目文档需要同时解决"全局架构认知"和"模块/接口细节查询"两个痛点，且保持长期可维护。

---

## Requirements

**文档目录与入口**
- R1. 在 `docs/oa/` 目录下建立完整的项目文档，不替代现有的 `oa/README.md`。
- R2. `docs/oa/` 下提供统一的文档入口（如 `README.md` 或 `INDEX.md`），列出所有板块和对应文件。

**架构概览**
- R3. 提供系统整体架构图（Mermaid），展示 `o2server`、`o2web` 与外部依赖（数据库、缓存、消息推送等）的关系。
- R4. 提供 `o2server` 模块依赖关系图（Mermaid），展示 60+ Maven 模块的层级和依赖方向。

**模块卡片**
- R5. 为每个 `o2server` Maven 模块创建一张标准化的模块卡片（Markdown），包含模块名、职责描述、核心类/接口摘要、依赖模块列表、对外 REST 端点摘要。按模块职责类型（API 服务 / assemble_control / service_processing / 工具模块）定义模板变体，允许非 API 模块省略 REST 端点字段。
- R6. 为 `o2web` 的主要组件（`x_component_*`）创建组件卡片，描述组件职责和关键 JSON 配置文件。

**开发环境与部署**
- R7. 提供 `o2server` 开发环境搭建指南，包括 JDK 版本、Maven 编译命令、本地启动方式。
- R8. 提供 `o2web` 开发环境搭建指南，包括 Node.js 版本、npm install、gulp 编译命令。
- R9. 提供服务器部署指南，覆盖 Windows 和 Linux 环境，包括端口要求、目录结构、启动脚本位置。
- R10. 提供 `o2server` 配置项说明，基于 `configSample/` 下的 JSON 配置文件，逐项解释关键配置。

**API 与数据结构**
- R11. 提供代码驱动的 API 文档提取能力；实施前先对代码库进行 Swagger 注解覆盖率审计，作为提取策略的选择依据；若 Swagger 覆盖率不足，采用降级方案；输出到 `docs/oa/api/` 或等价位置。
- R12. 提供核心数据模型说明，覆盖组织、流程、文件、考勤、CMS 等主要功能域的 JPA 实体类关系。

**业务功能说明**
- R13. 按功能域（组织管理、流程引擎、表单定制、门户、考勤、CMS、文件、会议、消息、AI 等）组织业务功能说明，描述每个功能域的核心能力和二次开发方式。
- R14. 描述平台的低代码/二次开发能力，包括表单定制、页面定制、流程设计器的使用方式。

**开发者指南**
- R15. 描述 `o2server` 的模块扩展方法，包括如何新增一个 assemble_control 或 service_processing 模块。
- R16. 描述 `o2web` 的组件扩展方法，包括如何新增一个 `x_component_*` 组件。
- R17. 描述平台的核心概念和约定（如实体类命名规范、Express 脚本机制、服务发现机制等）。

**可维护性**
- R18. 模块卡片和组件卡片采用统一模板，便于后续批量更新。
- R19. API 文档部分支持定期自动重新生成，与代码变更保持同步。
- R20. 架构图（R3、R4 的 Mermaid 图）随版本发布同步更新；维护责任归属：o2server 模块依赖图由各模块负责人共同维护，系统架构图由技术负责人维护；触发条件为模块依赖结构或系统边界变更时由对应负责人强制更新。

## Success Criteria

- 新加入的开发者能通过阅读 `docs/oa/` 在 30 分钟内建立对系统整体架构的正确认知，具体可验证标准为：能基于 R3 系统整体架构图和 R4 模块依赖关系图，正确描述系统边界、核心模块依赖方向、外部依赖有哪些。
- 每个 `o2server` Maven 模块和 `o2web` 主要组件都有对应的文档卡片，无遗漏。
- 开发者能通过模块卡片找到模块职责、依赖关系和对外端点摘要，无需直接翻源码。
- API 文档能通过自动提取生成，与代码中 Swagger 注解和 JPA 实体保持同步。
- 文档目录 `docs/oa/` 可独立作为项目文档入口，与 `oa/README.md` 并存不冲突。

---

## Scope Boundaries

- 不指定具体的文档生成工具或脚本实现细节，但允许文档描述生成机制的技术选型约束（如基于 Swagger 注解的提取策略、覆盖率不足时的降级方案等）。
- 不输出 PDF 或静态站点，仅输出 Markdown 文件。
- 不替代官方的平台使用手册（`https://www.o2oa.net/handbook.html`），项目文档聚焦于开发者视角的架构、模块和二次开发。
- 不覆盖前端单元测试、E2E 测试等专项工程实践。

## Key Decisions

- **架构图 + 模块卡片作为主要载体**：同时解决全局架构认知和模块级细节查询，模板标准化后维护成本低。
- **API 文档辅以代码驱动自动提取**：避免手工抄接口，与代码保持同步。
- **Mermaid 作为架构图格式**：Markdown 原生支持，无需额外工具链，便于后续维护。
- **`docs/oa/` 独立目录，不替代 `oa/README.md`**：官方介绍和开发者文档分离，各司其职。
