#1 密钥迁移先于文档

assumption-breaking Confidence High Complexity Medium
Description

在写任何系统文档之前，先将 cool.java:162-166 和 cool.java:197 的硬编码生产密钥提取为环境变量/配置文件，完成 cool2.java 与 cool.java 的合并或废弃。否则系统文档会描述一个"已修复的架构"——但实际源码仍有生产密钥。

Basis

direct: cool.java:162-166 — key = "coolcollege20201211sc" + thirdSecret = "135990bd839c5fe0a1ca9cbee2475431" 硬编码在 oaMd5() 方法中；cool.java:197 — key = "whM1376SiX5=78" 在 decodeTicket() 中；cool2.java 存在但未完成合并（135 行，同密钥在 104-108 行重复）。docs/plans/2026-07-30-001-feat-systems-documentation-plan.md:125 的 R11 只约束"文档中不出现真实密钥"，不约束源码。

Rationale

硬编码密钥进入 git 历史意味着即使后续删除，仍可从历史中恢复。如果文档计划先执行，写出来的文档描述的是"已修复"的加密架构，但实际源码仍有生产密钥——新成员按文档改造时会发现不一致，产生信任危机。先修源码，文档才能反映真实系统。

Downsides

需要 git 历史重写（git filter-repo）来彻底清除已提交的密钥；cool2.java 合并需要测试验证行为一致性；O2OA SSO 依赖方可能需要更新密钥分发方式。

Meeting Test

团队是否会讨论"在写文档之前，是否应该先清理源码中的硬编码密钥？"

#2 秘密扫描工具

leverage/compounding Confidence High Complexity Medium
Description

构建一个扫描代码库中硬编码密钥、已知凭证指纹（如 cool.java 的 key+thirdSecret 对）、以及无环境变量回退的配置值的工具。在 compile_all.bat 末尾或作为 pre-commit hook 运行，拦截包含真实凭证的提交。

Basis

direct: cool.java:162-166 — 硬编码的 O2OA SSO 生产凭证对是仓库中最严重的安全问题。watering/config.yaml.example 和 train/enhanceTXT.py:30-31 均有 env var 回退模式，但无机制阻止开发者提交真实值。compile_all.bat:1-49 是现有编译入口，可在末尾追加扫描步骤。

Rationale

cool.java 的凭证目前已在源码中，而文档计划会将其写入 docs/systems/cool.md。扫描工具的介入改变了计划的输出——发现凭证后必须先走提取/替换流程，才能安全地写文档。扫描规则集本身就是可积累的资产——每次发现新类型的凭证，规则就变强一次。

Downsides

可能产生误报（合法密钥如测试密钥 vs. 生产密钥的区分）；需要维护规则集；pre-commit hook 可能降低提交速度。

Meeting Test

团队是否接受在提交流程中加入凭证检测门禁？误报阈值如何设定？

Combines With

与 #1 密钥迁移形成完整闭环：迁移是修复，扫描是持续保障。

#3 可组合数据增强流水线

cross-domain analogy Confidence High Complexity High
Description

构建 Pipeline 类，让每个增强操作（同义词替换、音似替换、回译、LLM 扩充）成为独立的 Pipeline Stage，通过 YAML 配置声明式组合，替代当前散落在注释中的实验代码。

当前：Similarword + Homophone 硬编码在 main() 中；目标：YAML 声明式 Stage 组合，注释代码变为可激活的 Stage
Basis

direct: train/enhanceTXT.py:102-216 — process_json_data 中注释掉的 WordEmbsAug/ContextualWordEmbsAug/BackTranslationAug/Simbert 初始化代码；train/enhanceTXT.py:314-445 — 注释掉的 40 线程 worker 函数。

Rationale

注释掉的代码是有价值的历史资产——它们记录了探索过的技术路径和失败原因（WordEmbsAug 需要本地模型文件，BackTranslationAug 需要 Helsinki 模型）。声明式流水线框架解决的是组合问题，激活的是整个子项目的真实价值。

Downsides

YAML 配置的学习成本；Stage 间的数据流接口设计需要仔细考虑；BERT/回译等 Stage 需要 GPU 资源，不适合所有运行环境。

Meeting Test

是否值得投入将 Python 实验代码转化为可复用框架，还是直接注释删除这些代码路径？

#4 retry+gap-fill 循环抽象为通用库

leverage/compounding Confidence Medium Complexity Medium
Description

将 watering 的 gap-fill 循环、csv2sql 的单条失败跳过、train 的失败缓存+断点续传、storage 的健康检查+拉起——这四个场景的统一循环模式（执行 → 收集失败 → 条件性重试 → 直到闭环或上限 → 记录结果）——抽象为带策略插件的 Go 库。

4 个子项目各自实现了同一循环模式的不同变体——抽象为共享库后， watering U5 直接复用，其余 3 个获得统一接口
Basis

direct: client.go:126-180（SendResult 含 FailedUserIDs + ErrorMessages）；reasoned: readCSV2SQL.go:130-133（continue 跳过失败是最简形态），enhanceTXT.py:276-284（失败写入 fail_file 是带持久化的形态），check_storage_service.sh:7-35（健康检查→拉起是服务管理形态）。

Rationale

watering U5 的 gap-fill 直接复用；csv2sql 和 train 能用统一接口替换各自的循环代码。新工具从第一天起就有成熟的失败处理骨架。

Downsides

Go 库的接口设计需要覆盖所有 4 种场景的变体，可能引入过度抽象；watering 计划中的 gap-fill 逻辑已有详细设计，抽象可能与计划冲突。

Meeting Test

4 个子项目各自实现了同一循环的变体，抽象成本低且复用面覆盖所有有外部 I/O 的项目——值得讨论吗？

#5 技术债务账本

constraint-flipping Confidence Medium Complexity Low
Description

建立 TECH_DEBT.md，每条记录包含：债务描述、根因、修复成本估算（LOC）、影响范围、是否可逆。将"已知 bug 未修"变为"已知债务已登记"，让任何后续代码审查都基于同一个已知问题清单。

Basis

reasoned: 技术债务的最大危害不是代码本身，而是"它在 Nobody's Land 里"——没有被任何人承认、没有 owner、没有修复计划。CLAUDE.md Rule 12 要求"Failed 必须响亮"，但这些已知问题从未被系统记录过。一个开发者（包括未来的自己）在面对 check_storage_service.sh 的语法 bug 时，无法判断"这是故意写的还是忘了修"——直到读到这个账本。

Rationale

债务登记的行为本身改变了代码的解读方式：注释代码不再是"可能有用的保留"，而是"已评估为废弃的代码"。对于 1 人项目，最大的风险不是多人协作混乱，而是"六个月后的自己不知道当初为什么这么做"。

Downsides

债务账本需要 owner 约定和 review 节奏，否则会沦为又一份无人维护的文档；登记行为可能被误解为"承认了就可以不修"。

Meeting Test

是否需要讨论"登记技术债务是否增加了维护负担"？

#6 活文档引擎

constraint-flipping Confidence Medium Complexity High
Description

构建从源码自动提取系统文档的引擎：解析 Go 结构体定义生成配置文档、解析 import 图生成 Mermaid 架构图。人工只需补充"为什么"而非"是什么"。

当前：7 个手工文档文件，写完即过期。目标：自动生成 WHAT 部分，人工补充 WHY 部分
Basis

reasoned: 当前 plan U1-U6 产出 7 个手工文档文件，没有任何机制保证它们在代码变更后仍然准确。U7b 已经意识到"文档与代码变更脱节"是 Medium 风险，但缓解手段仅为"每月人工巡检"。代码结构信息（包名、接口、依赖）是客观事实，不需要人的解读——人的工作是添加"为什么这样设计"的上下文。

Rationale

将"写完即过期"的静态文档变为"代码变更即同步"的动态资产，直接解决 plan 中 R16（变更后一个 sprint 更新）的执行难题——因为更新变成了自动的。

Downsides

自动生成的文档质量上限可能低于手工编写；需要 CI 集成；团队可能不接受"机器写的文档"。

Meeting Test

是否值得用工具生成的部分替代纯人工文档？这直接挑战了 plan 中"纯人工为主、工具辅助为辅"的核心决策。

#7 实时数据汇流层

constraint-flipping Confidence Medium Complexity High
Description

构建跨子项目复用的 Pipeline 框架——定义 Source → Transform → Sink 三段式接口，内置重试、backoff、断点续传、失败队列，让三个现有子项目和一个未来的"调度器"都能用同一套原语描述 I/O 流程。

Basis

reasoned: readCSV2SQL.go:130-133（单条失败跳过是最简形态），enhanceTXT.py:276-284（失败写入 fail_file 是带持久化的形态），check_storage_service.sh:7-35（健康检查→拉起是服务管理形态）。当前 watering 计划的 U3-U6 完全未实现，原因是"这些都是通用的基础设施，不值得为单个项目单独写"。

Rationale

但如果这些基础设施能被 csv2sql 和 train 也复用，投入产出比立刻翻转——一次编写，三个项目受益。这是用"架构杠杆"替代"功能堆叠"的典型决策。

Downsides

三个项目的需求是否足够相似到值得抽象？Go 库对 Python 子项目的调用需要通过 CLI 或 gRPC，增加了耦合复杂度。

Meeting Test

三个项目的 I/O 模式是否足够相似到值得抽象，还是强行统一反而限制各自演进？

✦ Cross-Cutting Combinations — surprise-me 模式下的跨框架协同

可复用模式框架 = #4 retry+gap-fill 库 + #7 数据汇流层 + #3 数据增强流水线

一次抽象，三个项目受益。retry 库提供基础循环，汇流层提供 I/O 编排，增强流水线提供领域特定的 Stage 组合——三层递进，从通用到专用。

测试基础设施 = #8 测试桩=可执行规格 + #9 shell 脚本工程化

将 watering 的 POC test harness 扩展为正式实现，同时将 storage 的 bash 脚本纳入工程化流程（shellcheck + 基本测试），建立"所有代码都经过测试"的文化基线。
