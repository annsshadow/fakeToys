# Rollback Plan — OA4Rust 部署回滚

> **口径（2026-10-14 定案）**：本项目从未上线、无 Java 存量系统。回滚 = **Rust 新版本 → 上一 Rust 版本**的二进制回退，不存在"切回 Java"的运维动作。早期版本中面向"Rust/Java 双轨切流"的方案已废止。

## 1. 触发回滚的条件

以下任一条件触发回滚：

| 条件 | 阈值 | 检测方式 |
|------|------|----------|
| 数据损坏 | 出现脏数据、丢失更新、违反约束 | 数据校验脚本 / 应用层校验失败 |
| 错误率突增 | 5xx 错误率 > 5% 或 401/403 错误率 > 20% | nginx access_log + Prometheus |
| 响应延迟超标 | P95 延迟 > 2s（对比本服务历史基线 P95 的 150%） | APM / nginx `$request_time` |
| 认证失败率突增 | 登录接口 401 率 > 30% | auth crate 日志统计 |
| 数据库连接异常 | 连接池耗尽、查询超时 > 5s | deadpool 指标 |
| 手动触发 | 开发/运维人员在 5 分钟内无法定位问题 | 运维决策 |

## 2. 回滚流程

```
触发 → 确认 → 回退二进制 → 验证 → 复盘
```

### 步骤 1：触发（< 1 分钟）
- 自动监控告警或人工判断触发回滚
- 记录触发时间、触发条件、影响范围

### 步骤 2：确认（< 2 分钟）
- 确认回滚条件满足
- 通知相关开发人员
- 若为误报，可中止回滚

### 步骤 3：回退（< 5 分钟）
- **回退到上一 Rust 版本二进制**（保留每次发布的 `oa4rust` 可执行文件归档）：
  ```bash
  # 停止当前进程后，换回上一版本产物并重启
  # 数据库结构回退仅在必要时手工执行对应迁移的 rollback 脚本：
  #   oa4rust/backend/migrations/NNN_description_rollback.sql
  ```
- 如需网关侧配合（摘流量、限流），改 `backend/deploy/nginx.conf` 模板并 `nginx -s reload`。
- `deploy/toggle_module.sh`（MODULE_ROUTING 切流）为早期灰度方案遗留归档，**不用于回滚**。

### 步骤 4：验证（< 3 分钟）
- `curl http://localhost:3000/health` 与核心业务流程冒烟
- 监控错误率和延迟是否回落

### 步骤 5：复盘（24 小时内）
- 分析根本原因
- 修复问题后在测试环境验证
- 更新本回滚计划

## 3. 上线判据（无旧系统、改好即上线）

见 `backend/docs/ops/REALIZE_RUNBOOK.md` §4.2：全部静态门禁 + 仓内 live E2E 通过即上线。
`RUST_FEATURE_ROLLBACK` 特性开关与管理端点仍为**设计预案**（截至 2026-10-14 未实现），
当前回滚手段即版本二进制回退，已够用。

## 4. 回滚演练计划

- 每次发布前在测试环境执行一次回退演练
- 演练内容：模拟触发 → 回退二进制 → 验证 → 恢复
- 记录演练时间，目标：5 分钟内完成回退

## 5. 数据一致性保障

- 迁移正向脚本与 `*_rollback.sql` 成对提供；结构回退是显式手工动作
- 版本回退前先确认新旧二进制的迁移版本差，必要时先回滚结构再回退二进制
- 例行备份见 `docs/oa4rust/06-install-and-run.md` 部署形态与数据库迁移约定
