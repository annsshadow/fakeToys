# 来一炮

仿微信小游戏《向僵尸开炮》玩法内核自研的**塔防 + 元素反应**小程序游戏。美术 100% Canvas 程序化绘制，不使用任何原作名称、素材、UI 或文案。

```
laiyipao/
├─ server/     Go Fiber + PostgreSQL 后端
├─ miniapp/    uni-app（微信小程序 / H5 双端）
├─ admin/      Vue 3 运营后台 + 玩家玩法文档站
├─ docs/       设计文档（创新点、公式、双端契约）
└─ scripts/    端到端验收脚本
```

## 核心创新点

完整设计见 [`docs/GAME_DESIGN.md`](docs/GAME_DESIGN.md)。

| 编号 | 创新点 | 一句话 |
|---|---|---|
| **I-1** | 元素反应矩阵 | 5 元素 × 7 反应链。**反应伤害中攻击力权重结构性 ≤30%** —— 堆金币永远无法替代正确搭配 |
| **I-2** | 插槽与热量 | 「三选一」不再是无脑增益。给选择装上代价，弃牌回热量，热量满则 2s 无法释放 |
| **I-3** | 专精树 + 装备契合度 | 每层 4 选 2 且需先点亮前层；装备同系 ×3、异系 ×1 反应加成，逼玩家成套配 |
| **I-4** | 地形机制关 | 5 类可交互地形（油桶/潮汐闸/旋转风障/崩塌掩体/蓄能塔），41% 的关卡使用 |
| **I-5** | 防线值守 | 构筑固化成快照，他人**本地模拟**挑战。服务端不跑战斗引擎 |
| **I-6** | 回放哈希验真 | 战斗完全确定性。任何人可取回种子重放，**证伪**可疑分数 |
| **I-7** | 构筑评分 | 主指标不是「战力 9999」，而是元素覆盖/反应链/专精/契合度五维 + 短板建议 |
| L-1 | 卡关诊断 | 连续失败时给出针对性建议（无元素覆盖 / 抗性不匹配 / 专精未投入…） |
| L-2 | 效率榜 | 按**通关时最低战力**排名，给低养成玩家留位置 |
| L-3 | 阵型预设 | 一键套用他人已验证的构筑 |

## 十四个关键工程约束

这些决定了整个架构，写在这里是因为**改动时必须同时满足**。

> 这 14 条不是一次想出来的，而是每一轮踩坑之后补上的 ——
> 所以**上面那几条都是别人（或我自己）踩出来的**，不是设计时就想到的。
> 新增一条的判据：它是否对应一个**真实发生过、且没被已有约束覆盖**的故障。

### 1. 反通胀是结构性保证，不是数值调优

```
反应伤害 = (元素侧 + 攻击侧) × (1 - 抗性)

攻击侧 = min(D × k × 阶,  w × 元素侧 / ((1 - w) × M)) × M     w ≤ 300‰
                                                    ↑
                                          M = 反应倍率（专精/装备/特斯拉栅格）
```

`攻击侧 / (元素侧 + 攻击侧) ≤ w` 是**恒等式**，任意输入下都成立。因此数值膨胀无法绕过搭配收益 —— 这是设计能被信任的原因。

> ⚠️ **M 必须出现在上限的分母里**，这一点很容易写错。
> 推导：约束的对象是乘完 M 之后的量 `A·M`：

> ```
> A·M/(E + A·M) ≤ w  ⟺  A·M(1-w) ≤ wE  ⟺  A ≤ wE/((1-w)·M)
> ```

> 只把 M 乘进伤害而不收紧上限，等于给"堆一个专精节点"开了一扇**绕过反通胀保证的后门** ——
> 那正是这套设计的根基。`anti_inflation.test.ts` 遍历 7 条反应链 × 3 档层数 × 4 档攻击力 ×
> 9 档倍率（含 0‰ 与 100 万‰）验证不变式；变异测试确认去掉这个除法会让 5 条立刻变红。

**M 的实际语义**（写下来免得日后误判为 bug）：

| 情形 | 攻击侧 | 倍率效果 |
|---|---|---|
| `D·k·阶 < 上限` | `D·k·阶 × M` | **随 M 线性增长** |
| `D·k·阶 ≥ 上限` | `w·元素侧/(1-w)` | 与 M 无关（上限收紧恰好抵消） |

也就是说：**倍率只在攻击侧尚未被 I-1 红线顶满时才生效**。
玩家在数值面板上看到"倍率提升 8 倍但伤害没变"，那是攻击侧已顶到红线，不是缺陷。

`M = 1000‰`（无加成）时 `wE/((1-w)×1000) × 1000 = wE/(1-w)`，与旧式**逐位相同** ——
所以这个乘区的接入是零风险的：既有契约向量、既有平衡数据全部保持有效，
Go 一致性测试全绿即为证明。

### 2. 定点整数 + 确定性 PRNG

- 伤害/速度/坐标/血量一律 **bigint × 1000 定点整数**
- 随机只走 `lcg.ts`（PCG-XSH-RR），**禁用 `Math.random`**
- 定步长 **50ms**（20Hz）推进，渲染层独立插值
- 抗性列是**千分比** -500..500（不是百分比）

浮点会带来跨引擎差异 → 同一场战斗算出不同哈希 → I-6 直接失效。

### 3. 攻方属性必须由服务端下发

回放哈希由 **关卡 + 种子 + 攻方属性 + 技能槽** 四者共同决定。四者缺一，重放方就算不出同一个哈希 —— 验真会把所有正常对局都判成伪造。

因此 `/api/v1/me` 与 `/battle/token` 的 `build` 里带 `attacker` 字段，客户端**只读不推算**；技能槽位存在 `user_skill_slots` 表，通过 `/me/loadout` 读写。

> ⚠️ 这条曾被违反：客户端用 `100 + maxStage*200` 自己猜攻击力，服务端无从知晓，双方哈希必然不同 —— I-6 形同虚设。已改为服务端权威下发（`internal/service/attacker.go`）。

### 4. 跨端字段名必须显式约定 —— 且要双向核对

Go struct **漏写 json tag 会按字段名原文（PascalCase）序列化**。客户端类型用 snake_case 时两边对不上，每个字段都是 `undefined` —— 且**不报任何错**。

**同类的第二个形态是「同一个量在两端各写一份常量」**：
`star_targets` 由 Go 按 `scorePerDamageUnit` / `scoreOnKillNormal` / `scoreOnKillBoss` 算出，
而实际得分由 TS 引擎用自己那份 `/100`、`500/5000` 累加 —— 一度有 **5 处副本**。
漂移之后玩家拿到的星级与实际表现对不上，而**两端各自都自洽，没有任何行为测试会发现**。

所以常量也要**可核对**，不能只靠约定：

| 端 | 来源 |
|---|---|
| Go 定义 | `domain.DefaultScoreRules()`（唯一定义处） |
| Go 下发 | `/config` 的 `score_rules` |
| 契约夹具 | `smoke_levels.json` 的 `score_rules` |
| 客户端 | `game/score.ts` 的 `DEFAULT_SCORE_RULES`，由 `score.test.ts` 断言与服务端逐位一致 |

⚠️ 写这条时还踩了一个更基础的坑：那些断言最初**写在 `score.ts` 里**（与实现同文件），
而 vitest 的 `include` 只收集 `*.test.ts` 后缀 —— **它们从来没被执行过**。
一段不运行的测试比没有测试更危险：它看起来在守着某样东西。
发现方式是单独跑 `vitest run src/game/score.ts` 时报 `No test files found`。

字段名这一条踩过两次，方向相反：

| 位置 | 声明 | 实际下发 | 后果 |
|---|---|---|---|
| `domain.RatingWeights` | 无 tag → `ElementCoverage` | `ElementCoverage` | 两端"一致"所以测试全绿，但与同响应里的 `BuildRating`（snake_case）风格割裂 |
| `miniapp/api/client.ts` 的 `chapters` | `ch.ID` / `ch.Name` | `id` / `name` | **关卡页章节标签全空白、点击无效、永远不高亮** |
| `admin/WikiView.vue` 的 `reactions` | `row.BaseCoef` / `row.AoeRadius` | `base_coef` / `aoe_radius` | 文档站反应表整列为空 |
| `admin/SkillsView.vue` 的配方 | `r.A` / `r.Output` | `a` / `output` | 每条配方渲染成 `#undefined + #undefined → #undefined（Tundefined）` |

同一份 `client.ts` 里 `levels` / `enemies` / `skills` 是对的，只有 `recipes` / `reactions` / `chapters` / `rating_weights` 错 —— 说明这些字段是分批写的，**没人做过整体核对**。

双向核对的两个方向：

1. **Go → 客户端**：所有下发结构体必须带 `json:"snake_case"` tag，**嵌套的也算**（`RatingWeights` 就曾漏掉）。加新 struct 时不要漏。
2. **客户端 → Go**：TS 接口的字段名必须逐字对齐服务端的 tag。注意**同名不同义** —— `build.skill_ids` 装的是元素名（历史误命名，现已同时下发正确名 `elements` 并保留旧名作兼容），而 `/me/loadout` 的 `skill_ids` 是真的技能 id 数组。代码内部自洽，但按名字推断语义的消费者会踩坑。

发现手段：**拿真实 `seed` 数据跑一遍，看渲染出来是不是空**。本轮关卡页章节空白就是这样发现的 —— 目视检查比读类型定义可靠。

### 5. 每一道防作弊校验都要有对应的负向测试

结算校验的价值全在"拒绝"分支上。而拒绝分支的特征是**不报任何错，只是默默不给钱** —— 没有专门的负向测试，下一次重构就会把它删掉，而且看起来一切正常。

本轮修的三处都属于这一类，且其中一处是**上一轮修复自己留下的洞**：

| 漏洞 | 触发 | 后果 |
|---|---|---|
| `duration_ms=0` 让得分裁剪整段被跳过 | 上报 `duration_ms:0` + `result:"lose"` | 分数无上限 → 星级恒 3 → 单局金币触顶 60000（正常约 1650） |
| `reactions` 无上界 | 上报 `reactions:1e9` | 一次顶满全部反应类任务与成就 |
| 兑换码 `used_count` 靠 CHECK 约束兜底 | 并发兑换 | 客户端收到 SQLSTATE 23514 而非业务错误；**约束一旦被迁移就是无限超发** |

第三条尤其值得记：`UPDATE ... SET used_count = used_count + 1 WHERE id = $1` 看着无害，资源上确实没超发（CHECK 挡住了），但那是**"恰好"有约束**，不是并发设计。正确写法是条件 UPDATE + 检查 `RowsAffected`，与 `ClaimTask` 的 `claimed_at IS NULL`、`Buy` 的 `FOR UPDATE` 同一个模式。

还有一个更隐蔽的形态：**约束了被保护量却没约束控制量**。给 `reactions` 加了 `reactions <= shots * 8` 的上界，但 `shots` 当时无上界 —— 于是上报 `shots:1.25e8` 时上界正好变成 1e9，恰好放行它本该挡掉的 1e9。约束链上每一环都必须有界。

**规律**：加任何一条上界校验时，同时问「这个上界自己由什么界定，那个东西有界吗」。

### 6. 双端公式一致性是**可执行检查**

`server/testdata/formula_vectors.json` 是唯一事实源：

| 端 | 测试 |
|---|---|
| Go | `internal/domain/consistency_test.go` |
| TS | `src/game/consistency.test.ts` |

两端读同一个 JSON、断言同样的数字。任一端单方面改公式，另一端立刻红。

> ⚠️ 该文件里的 64 位值用**字符串**承载。JSON number 超过 2^53 后 JS 解析即失精，`6917529027818027904` 会被解析成 `...8032`，断言会**悄悄通过**。同理，`/api/v1/battle/token` 与 `/battle/{id}/replay` 的 `seed` 也是字符串下发。

但**跨端一致 ≠ 两端都对**。本轮就有两处「两端同时漏掉同一个东西」，13 个向量全绿：

- `reactionMultPermille` 在 `resolveHit` 里根本没有乘区（专精树 6 个节点白给）
- `applyArmor` 因为向量里 `armor_permille` 恒为 0，**两端都从未执行过第二行**

所以一致性测试的定位是「防漂移」，不是「防错误」。后者要靠各自的单元测试 + 真实内容表的冒烟测试。

### 7. 动数值之前先建立**可比较的基准**

任何涉及数值的改动（伤害公式、关卡生成、敌人血量、星级门槛）前后都跑一遍
`miniapp/src/game/balance.probe.test.ts`，拿到的是**可比数字**而不是"感觉变强了"。

本轮三次误判全部源于缺这个：

| 我当时的判断 | 实际数据 | 缺的是什么 |
|---|---|---|
| 「热量上限压制了攻击力收益」 | 单位误读，`attack` 是千分比 | 没先确认量纲 |
| 「夹具太弱」 | 夹具温和度掩盖了粗糙缺陷 | 没有真实内容表 |
| 「血量是瓶颈」 | **瓶颈是弹丸速度** —— 18 秒飞行时间，85% 输出浪费 | 没测过命中率 |

第三条尤其值得记：我在探针里把 `hpMul` 从 1 扫到 8，**结论一次比一次反直觉**
（hp×2 时击杀数几乎不变 → 瓶颈不在血量），直到加了 `projMul` 参数才发现真正的浪费点。
**没有参数化探针，这些误判会一直留在"看起来合理"的层面。**

探针的关键设计是**支持倍率缩放**，这样不用改内容表就能做对照实验：

```ts
measure({ projMul: 8, hpMul: 4, atkMul: 2, crit: 500, seed: 12345 })
```

⚠️ 一个真实的坑：探针改了 `cfg.skills`（SkillDef）的 `projectile_speed` 却毫无效果，
而 `fire()` 读的是 `cfg.equipped`（EquippedSkill）里的 `projectileSpeed`。
**倍率施加的对象错了，实验会给出"这个变量无影响"的假结论。**

### 8. 「看起来实现了、实际不工作」需要专门的判据


这类缺陷的特征是：代码存在、类型正确、编译通过、测试全绿，但功能不生效。
共同点不是"写错了"，而是**缺少一条能表达"它必须生效"的断言**。

本轮遇到的三个形态：

| 形态 | 实例 | 能被什么抓到 |
|---|---|---|
| **参数与增量差数量级** | 地形 `param`=100~5000 vs 充能增量 ≈0~2 | 端到端行为断言（"12 个油桶关卡 0 个点燃"） |
| **路径几何互斥** | 掩体的每 tick 充能判定半径 110，弹丸在 100 被销毁 | 删除死代码 + 单元测试锁住唯一来源 |
| **判据落在保护之外** | 技能卡"装入空槽"的 `findIndex` 命中已占用槽 | 「施加后状态确实变了」的用例 |

**注意这类缺陷都不会让任何现有测试变红** —— 所以补测试的判据是
「改坏会不会红」，而不是「覆盖到了吗」。后者只能靠变异测试回答。

### 9. 有两类断言**结构上**测不出来，必须专门去构造

前八条约束针对的是"实现存在但不对"。下面两类更进一步 ——
**实现完全正确、行为完全一致，但违反了某条约定**，
而这一点只能靠**绕开行为、直接断言性质**来抓住。

### 9.1 形态断言：本机永远测不出来的那类

定点整数铁律关心的是**跨实现一致**，不是"本机一致"。
把 `spawnProgress` 从整数千分比改回浮点（`+= 0.08`）之后，
**全部 393 个测试照样绿**（实测）—— 因为浮点版本在同一份 V8 上算出同一个数。

这类缺陷的特征：**只有换机器、换引擎版本才会炸**，而那正是上线后才发现的时候。

所以判据必须是形态而不是结果：

- `spawnProgress` 必须是整数
- 必须是 STEP 的整数倍，**或恰好等于 FULL**
  （`1000 % 80 = 40` —— 钳位值不是 STEP 的倍数是正常的，`FULL/STEP = 12.5` 本就不能整除。
  我最初只写 `p % STEP === 0`，**测试自己先红了**。）
- 13 个 tick 达到满 —— 防止有人把 STEP 调成能整除的数，那会平移"敌人何时可被击中"的时刻
- 同 seed 跑两次产生**完全相同**的状态链（混入 `Math.random` 或 `Date.now()` 就会红）
- `Math.random` 的源码检查：判据必须是「没有**调用**」而不是「没有**出现**」——
  `lcg.ts` 的文件头就写着「本模块禁止使用 `Math.random()`」，
  那条警告本身包含这个词，最早写成 `not.toContain` **被自己的注释判失败**

辅助代码本身也要被守：`stripComments` 配了一条自检用例，
否则它写坏了会让上面两条**假绿**。

### 9.2 分布断言：单点自洽不等于整体正确

关卡生成里这类缺陷最典型。`chapterTerrainFor` 曾让 41% 的关卡带地形（意图约 25%），
而**每一关单独看都是自洽的答案** —— 没有报错、没有断言会红。

挖出来的三层，每层都需要不同级别的断言：

| 层 | 现象 | 需要什么级别的断言 |
|---|---|---|
| 算术右移产生负余数 | 负种子那 50% 关卡的 `offset < 3` 恒真 | **函数级**：偏移必须在 `[0, span)` |
| 「保底 3 关」不是保底 | 保底只在 1/4 的关卡里生效，期望 0.15 关/章 | **章级**：每章至少 3 关 |
| 用到的比特位不随关卡号变化 | `(seed>>8)%4` **整章内是同一个值** | **章内分布级**：单桶偏离上限 |

第三层最隐蔽：全局分布看起来是均匀的（各 24~27/100），
**只有分章看**才发现第 4 章是 0/7/13/0 —— 意味着该章要么全是地形关、要么一个都没有。
所以判据必须是**章内**均匀度，因为地形比例是按章体验的。

**两条统计纪律**（我各犯了一次，测试自己先红）：

1. 区间的端点不能用期望值。100 关里 82 关走概率、期望 10.3、σ≈3.0，
   实测 7 在 1.1σ 内 —— 把下限定成期望值 28% 就是错的。
   下限要用**结构性硬下限**（保底 18%），上限用期望 + 2σ。
2. 均匀度容差是**样本量的函数**。20 个样本分 4 桶时偏差 3~4 属正常波动，
   固定容差 2 会让测试误报。改成 `tol = 2 + span/8`。

### 9.3 同一个字段两端的**空值处理**也要一致

`reactionElement` 两端同名，但曾对同一个空值给出不同抗性：

```
TS:  input.reactionElement ??  def.dominantElement()   // '' 不回退 → 无抗性
Go:  if resElement == "" { resElement = dominant(def) } // '' 回退   → 真实抗性
```

抗性不同 → 反应伤害不同 → **replayHash 不同** → I-6 把正常对局判成伪造。
而 13 个契约向量全绿，因为 `reaction_element` 在向量里**从未出现过** ——
一致性测试只在"两端传了同一个合法值"时比对，分歧恰好在**非法输入路径**上。

"类型上不可能"不等于"不会发生"：契约向量经 JSON 往返、DB 里的关卡行被手改、
灰度中的新客户端下发旧客户端不认识的字段 —— 三条路径都能送来 `''`。

两端各配一条**语义相同**的用例（断言 `''` 与 `undefined` 等价，
且回退到守方主元素而非变成无抗性），变异任一端，那一端立刻红。

### 10. 采样会掩盖分布问题，而分布缺陷**不会让单点自检变红**

本项目被这条坑了三次，每次都是同一个形状。

| 缺陷 | 采样时（6 关） | 全量时（100 关） |
|---|---|---|
| 3 关永久死锁 | 全绿（6 关里没有一关是掩体关） | **3 关永远打不完** |
| 地形关 41% | 全绿（6 关恰好落在正常区间） | **41 关**带地形 |
| 3 星白送 | 全绿（6 关都能拿 3 星） | **99/100 关**拿 3 星 |

共同点：**每一关单独看都是自洽的**。`chapterTerrainFor` 返回一个
自洽的答案、每场战斗都正常结束、每关都能通关 ——
没有任何单点断言会红。而「100 关里有几关带地形」「每章有几关地形」
这类**分布性质**没有任何东西在守。

两条硬规矩：

1. **可完成性是逐关性质，必须全量跑。** `no_deadlock.test.ts` 跑全部 100 关，
   并且带一条「夹具确实覆盖了 100 关」的**前提用例** ——
   没有它，"只跑了几关"会假绿。
2. **配比/分布要用分布级断言。** `terrain_ratio_test.go` 断言的是
   100 关的地形关总数区间、每章的下界与上界、**章内**的 mod 分布 ——
   而不只是"每章至少 3 关"。

### 11. 「观测不到」会被读成「机制没生效」——先怀疑观测本身

测 I-4 地形生效率时，度量口径换了**五次**，前四次都是**观测错了**：

| 版本 | 观测方式 | 得到的错误结论 |
|---|---|---|
| 1 | `t.triggered` 标志 | 油桶/潮汐闸/风障全 0% |
| 2 | 「状态动过就算」 | 潮汐闸/风障 100% |
| 3 | 包 `updateProjectiles` 数被挡弹丸 | 潮汐闸 0% |
| 4 | 包 `updateProjectiles` 比速度变化 | 风障 0% |
| 5 | 战斗**结束后**查敌人是否被拦 | 潮汐闸 0% |
| **最终** | **逐 tick 观测引擎公开状态** | 4/5 类 100% |

三个典型错误：

1. **`triggered` 标的是「一次性事件」**，而潮汐闸与风障是**持续型**机制
   （一直挡 / 一直偏转）。用一次性标志度量持续型机制，必然得到假的 0%。
2. **偏转发生在 `updateTerrain` 里**，而我在 `updateProjectiles` 前后取快照 ——
   取到的**已经是被改过的速度**，差值恒为 0。
3. **赢下战斗时敌人已全部死亡**，所以「结束后查有没有敌人被拦」必然是 0。

还有一个更隐蔽的：包私有方法 `updateProjectiles` 时，
它在内部会 `this.projectiles = this.projectiles.filter(...)` **重建数组** ——
前后都读 `eng.projectiles` 得到的是同一个新数组，条件恒假、计数器恒为 0。

> **一段永不执行的插桩比没有插桩更危险**：它给出「没问题」的假结论，
> 而没有插桩至少会让你知道该去查。

**规矩**：度量「机制是否生效」时，先用**已知会生效**的样本自检这套观测，
再用它去测不确定的那些。最终版本不碰任何私有方法，只逐 tick 读公开状态。

### 变异测试里三次"注入失败 ≠ 守卫有效"

这类误读值得单独记，因为它会让人以为守卫已经够强：

| 变异 | 现象 | 真实原因 |
|---|---|---|
| `Math.cos` 换回查表 | 30 个地形用例**全绿** | 守卫断言的是**表本身**；"表是对的"与"运行时用的是表"是两件事 |
| 去掉雪崩只留 `levelID × 奇数` | 均匀度测试**全绿** | 这个变异确实无害 —— 连续整数乘奇数 mod 8 天然均匀。如实记录，不粉饰 |
| Go 侧 `reactionElement` 变异 | 连续三次**注入失败** | 正则漏了闭合括号 / `if false` 触发变量未使用；改用不可能匹配的字面量才成功 |

补第一条的方式是加一条**行为**断言（把 `Math.cos` 打桩记账，跑 3000 tick 断言一次没调用），
它比任何源码文本扫描都强：不管实现怎么写，只看有没有真的调用。

⚠️ 在项目文件上做变异测试的两条纪律：**先备份到项目外**、**必带 `-timeout`**。
本项目已经栽过一次：把 `go func` 改成同步直调导致 `wg.Wait()` 永久阻塞、
命令超时，文件被留在变异状态，备份缺失时是手工改回去的。

### 测试空洞的四种形态

| 形态 | 实例 | 改坏了能绿吗 |
|---|---|---|
| **恒等式** | `expect(levelSeed(1)).toBe(levelSeed(1))` | 能。名字叫「与 Go 侧一致」，实际自己等于自己 |
| **本地复制** | 测试内抄一份 PHI 常量与公式 | 能。改 Go 侧完全不影响它 |
| **夹具落在保护之外** | 契约向量 `armor_permille` 全为 0，而 `applyArmor` 第一行就 `return` | 能。两端都改成 `return dmg`，140+ 测试全绿 |
| **数据文件当开关** | `if (!vectors.balance_invariants.xxx) return` | 能。把 flag 改 false，断言静默消失 |

共同点：**它们全都待在「看起来测了东西」的位置上**。所以补测试的判据不是
"覆盖到了吗"，而是**"改坏被测代码会不会红"** —— 这只能靠变异测试回答，
读代码回答不了。

### 12. 养成接线必须验证「**改变战斗结果**」，而不只是「改变某个字段」

本项目曾有一整层养成是**纯装饰**：18 件装备、8 种宝石、
专精树的 40/96 个节点，对战斗数值**零影响**。

`computeAttacker` 只装了专精树的 3 种 kind（`element_cap` / `reaction_mult` / `crit`），
其余全部只进 I-7 构筑评分与 `/config`。
第 3 层的 `mechanic`（"机制改造"）**在 `EvaluateMastery` 的 switch 里连 case 都没有**。

**为什么没人发现**：`computeRating` 读了这些数据并展示，看起来「有数值」。

> **展示层读同一份数据，不等于战斗层也读。**

三个已有测试都"覆盖"了这些数据，却没有一个断言「它有效果」：
- 内容表测试只查节点数量、层间约束、ID 规则
- 评分测试只查总分落在区间内（贡献 0 也在区间内）
- 战斗测试用固定攻方，不经过成长链路

**形状**：接线存在，但没有「全覆盖」守卫。
与本项目已修的多个缺陷同形（`reactionMultPermille` 空转、`Math.cos` 参与判定、
`reactionElement` 两端分歧）。

新增守卫（每一类都做过变异验证）：

| 守卫 | 抓什么 | 变异结果 |
|---|---|---|
| `TestEveryMasteryKindIsEvaluated` | 每种专精 kind 选中后效果必须**变化** | 删 `mechanic` case → 红 |
| `TestAttackerViewCoversEveryAttackerField` | 反射比对：给 `Attacker` 加字段而漏下发 | 加字段不补 view → 红 |
| `TestEveryAttackerFieldChangesResolveHit` | 扰动每个字段 → 结算结果必须变 | — |
| `TestEquipmentActuallyRaisesAttacker`（打真实 DB） | 穿上装备攻方变、脱下复原 | 删 `applyLoadout` → 红 |
| `loadout_attacker.test.ts`（TS 14 例） | 客户端三项字段真的改变护甲/热量/卡面 | 客户端不读 → 红 |

### 13. 千分比字段必须确认**加法语义**，不能只看字段名

`HeatMeter.cap` 曾写成 `HEAT_MAX + capBonus`，
把**千分比当成绝对值**相加 —— `heatCapPermille=1000‰` 让上限变成 1100 而不是 200。

而**热量衰减率是固定的**，于是上限涨到 11 倍时玩家长期停在
「热量很高但放不出技能」的死区：

| capBonus | cap | 过热次数 | 漏怪 | 分数 |
|---|---|---|---|---|
| 0‰ | 100 | 9028 | 486 | 基准 |
| 1000‰ | **1100** | 1174 | **1168** | **-13.8%** |
| 2000‰ | **2100** | 638 | **1484** | — |

> **「提高热量上限」是「有利属性」。出现反向曲线只能是单位错了，不是平衡问题。**

修法：`cap = HEAT_MAX × (1000 + capBonus) / 1000`；
专精节点值（10/20/30）在 `EvaluateMastery` 里 ×10 换算成千分比。
修正后单调有益（0‰→1000‰：漏怪 486→465、时长 28076s→21513s）。

**判据**：千分比字段参与加法时，先确认「加完之后数量级对不对」。
`+1000‰` 得到的是 **2 倍**，不是 `+1000`。

### 14. 「升级不该让排行变差」是一条可测的不变式

接线完成后才发现：满配（全部封顶）下**有 2 关分数反而下降、1 关从 3 星掉到 2 星**。
关卡仍然 `won`，所以**没有任何已有测试会红**。

收紧 `MaxLoadoutElementCoefPermille`（1800 → 1200）后消失。

`MaxLoadoutAttackPermille` 从 3000 砍到 1000，依据是扫描：

| attack‰ | 击杀数 | 分数 | 反应次数 |
|---|---|---|---|
| 0 | 5262 | 790188 | 15064 |
| 3000 | 5275 | 807665 (+0.6%) | 11279 (**-25.1%**) |

**堆攻击力买不到分数（+0.6%），却直接压制反应 25%** ——
而反应正是 I-1 的核心创新。击杀数几乎不随攻击力变，
说明战斗瓶颈是热量/冷却周期而非伤害。

**分数容差取 2% 而非严格 `>=`**：分数是整数（伤害分 = totalDamage/100），
过杀时序带来 0.01%~1% 噪声。严格 `>=` 会让守卫**永远红**、被当成 flaky 忽略 ——
比没有守卫更糟。2% 仍能抓住 3.9% 那种真回归。

### 15. 「等级」这类养成输入必须**烘进**战斗数值，而不是作为独立字段往下传

接技能升级时（`user_skills.level` 此前是**永远为 1** 的一列）撞上的选择：

| 方案 | 战斗算得对吗 | 验真能区分等级吗 |
|---|---|---|
| 独立 `level` 字段，在 `fire()` 里乘 | 对 | **不能** —— 等级不在 `replayHash()` 锚点里 |
| 烘进 `baseDamage`（本项目采用） | 对 | 能 |

`replayHash()` 的锚点是 `${slot}:${skillId}:${baseDamage}:${applyStacks}:${heatCost}`。
等级若不落在锚点里，两个不同等级的构筑可能算出**同一份哈希** ——
**验真通过但伤害对不上**，哈希在说谎。

与约束「`activeSlots` 缺省必须是 `ACTIVE_SLOTS = 4`」同一个道理：
凡是能改变战斗结果的输入，都必须落在哈希锚点里。
`skill_level_battle.test.ts` 的「不同等级 → 不同 replayHash」是这条约束的直接守卫。

**等级 1 → 1000‰ 必须是精确恒等，不是近似。** 升级上线前所有 `level` 恒为 1，
所以所有**存量战报的重放哈希必须逐位不变**。基线若取 1050‰ 之类，
每个历史战报都会静默失配 —— 而失配表现为「验真失败」，
看起来像作弊，实际只是上线了一个数学常数。

**顺带根除了一处双份实现**：`pages/battle/battle.vue` 此前持有
`replay.ts:equippedFromSnapshot` 的**逐行复制**版本（实战拼一次、重放拼一次）。
两份都自洽，改一处忘另一处 → 实战伤害与重放伤害不同 → 哈希永远失配，
而排查方向会自然滑向「I-6 坏了」。现在 `battle.vue` 直接调那个函数。

## 已知边界（诚实声明）

以下**没有做**，且不会假装做了：

1. **微信支付内购、流量主广告未真实接入** —— 需要 AppID 与商户号。商城、订单、货币流水的数据结构与后台配置已完整，但**没有支付/广告 SDK 的 mock 层**，客户端也没有调起支付的代码路径。真实接入需拿到凭证后从头补。
2. **微信登录通道预留未启用** —— `jscode2session` 已实现（`service/economy.go`），受 `WECHAT_ENABLED` 开关控制。未配置 AppID/Secret 时返回明确的 501 错误而非静默降级成游客登录。当前默认走游客登录，客户端尚未接 `/auth/wechat`。
3. **防线挑战的胜负由客户端裁决** —— 服务端不跑战斗引擎（省掉两套引擎同步的代价），挑战在挑战者设备上用同一套引擎本地模拟攻方，结果上报后服务端只校验「次数未超限 / 护盾已过期 / 资源守恒」。因此**服务端无法独立验证胜负**，后台「防线值守」页对接近 100% 或 0% 的异常胜率做告警。

13. **默认构筑的元素搭配多样性极低** —— fire/fire/fire/ice 只能触发 steam_burst 一种反应（全 100 关实测 100%）。这解释了为什么「放大反应」类的属性对默认构筑几乎无效：没有第二种反应可放大。玩家想要元素收益必须主动凑出冰/雷/蚀的组合。**未做**：装备的 Element 字段描述写着「与该系相关的反应系数更高」，但实际不按元素区分加成。
14. ~~元素系数的惩罚区间在 200~800‰~~ **假设已被否证，改为「严格单调 + 1000‰ 后是纯浪费」** —— 原先写着「元素 DoT 打在已过防线的敌人身上就浪费掉了」，并据此把「改 DoT 结算时机」列为核心系统待办。**代码里没有这个机制**：`damage.ts:resolveHit` 算出的 `elementDmg` 在**同一次调用内**折进 `critPart` → `total` → 立刻扣 `def.hp`，没有延迟队列、没有「下个 tick 才结算」、没有与漏怪阈值的交互。第二条假设「降系数 → 反应变弱 → 冻结/眩晕变少 → 更多敌人走到防线」同样被否证：`engine.ts:1022` 的时长取自**反应表常量** `spec.statusDurationMs`，与 `elementCoefPermille` 无关。**实测曲线是严格单调的**（前 40 关，默认构筑）：200‰→869 漏、400‰→378、700‰→60、1000‰→19、1500‰→1、1800‰→0。没有凹陷、没有惩罚区间 —— 「惩罚区间」这个说法把「低于基准就是更差」误述成了「存在特殊坏区间」，会误导人去改机制。**真实存在的浪费是另一种形态：过量伤害。** 反推总伤害（`score = totalDamage/100 + kills*500`）在 1000‰→3000‰ 之间涨 39%，而**击杀数饱和在 818→820→820 不动** —— 1000‰ 之后元素系数买到的几乎全是打在已死敌人身上的伤害，而 `score` 照样计分。**这一条已完整实现并回滚。** 理由：收益已被现有机制覆盖 —— 结算时 `scoreCapFor` 把分数裁到 `gl.MaxScore`，而 `MaxScore = Σ(击杀分 + (hp+shield)/100)`，**恰好就是「只算有效伤害」口径的天花板**。实测第 50 关满配 v1 得 25496 而上限是 25348：**v1 本来就打出了超过理论满分的分数，然后被服务端截断**。玩家从「多打一点」那里拿不到额外分数，裁剪器就是那道闸。代价却是实打实的：计分版本号机制 + 战报新列 + 跨端下发 + 重放按记录选口径，以及**平衡回归**（第 50/57 关「满配 3 星 → 2 星」—— 被驱散的护盾在「只算吸收量」的口径下一分不给，而驱散是奖励、让它扣分是反的）。**不做。** 守卫见 `elem_coef_shape.test.ts`（6 用例：单调性、控制效果可达性、过量伤害事实）与 `score_cap_guard_test.go`（把「裁剪已覆盖 v2 的收益」这个前提钉成不变式：若有人放宽 `scoreCapFor`，它会红）。

15. **5 个集合类上报字段此前完全无界** —— `elements_used` / `reactions_used` / `terrain_used` / `card_picks` / `replay_hash` 既无长度/取值上界，也不参与任何奖励计算，却**直接落进 battle_records**，其中 `reactions_used` 还会被运营看板的 `GROUP BY` 读走。一个 4096 键的 map 就能把战报行撑到不可用，而塞进 `"fake_reaction": 999` 会让看板上的「反应分布」变成客户端说了算的东西。**「不参与奖励计算」不等于「不需要校验」** —— 不校验它，它就进了数据库、进了报表、进了别人基于它做的决策。已补：键白名单、负计数拒绝、`elements_used` 合计 ≤ `shots × 该关怪数`、`reactions_used` 合计 ≤ `reactions`、`terrain_used` ⊆ 该关地形种类且不重复、`card_picks` 长度 ≤ 波数且每项 ≥ -1、`replay_hash` ≤ 64 字符。并加**反射式覆盖率守卫**（`settle_coverage_test.go`）：`SettleInput` 新增字段若既无边界又未显式豁免（豁免必须写明理由），测试立刻红 —— 这类缺陷不是被测出来的，是**根本没被想过**。跨端由 `settle_bounds_parity.test.ts` 保证服务端的新边界**接受真实引擎的上报**。**边界不是拍出来的**：`elements_used` 的上界曾是 `hits`，而 parity 实测发现真实引擎的元素合计 / hits 最大 **1.214**（AoE 与链式走 `hitEnemy` 却不计入 `hits`）—— 那个界会**拒绝几乎所有正常对局**。顺带确认：`terrain_used` 合法长度**最多是 1**（`generateTerrain` 产出的地形全是同一个 kind，且 100 关里 75 关没有地形），该字段信息量约等于「这一关有没有触发地形」；`stats.go` 若按它做按关的「地形触发率」，分辨率只有 0/1。**未做**：给关卡配多种地形属内容设计改动。

| 原债务 | 实际根因 | 关键教训 |

| 暴击率 10× 单位错 | `roll` 是万分比、阈值是千分比，标称 5% 实际 90.5% | **端点断言抓不到**。critPermille=0 与 1000 两个端点在 10× 错误下**都成立**，所以要靠**分布**才能测出来 |

### 「只写不读」是一类特定缺陷，值得单独命名

`buffs.<字段> += value` 施加 → 引擎某处读取才生效。如果**没有任何读取点**，
代码照样编译、测试照样全绿，玩家拿到那张卡观察不到任何变化 ——
更糟的是它会通过 `mechanicIndex` 参与 `replayHash`，
于是**哈希记录了一个不产生任何效果的选择**。

本项目实际发生两起（`cards.test.ts` 补上）：

1. `overheat_guard`（隔热护罩）—— 5 张机制卡里唯一只写不读的
2. 技能卡的"装入空槽"—— `findIndex(s => s.slot < ACTIVE_SLOTS && s.slot >= 0)`
   在「每个元素代表一个已占用槽」的数组里，**命中的永远是第一个已占用槽**，
   于是抽到新技能直接顶掉槽 0 的老技能，槽位数永远不增加

**判据**：对每一类卡都要有一条「施加后状态确实变了」的用例，
而不只是「调用不报错」。

### 重放如何还原「玩家点了哪张牌」

选牌会改变后续战斗（技能升格 / 属性加成 / 机制词条），所以它是战斗输入的一部分，必须能被复现：

- 引擎记录 `cardPicks`（每波选中的**手牌下标**，-1 = 整波跳过），settle 时上报
- 服务端存进 `battle_records.card_picks`（逗号分隔紧凑文本，迁移 `00008`）
- 重放时 `engine.setReplayScript(picks)` 注入，引擎在选牌阶段**自动**按脚本决策

实现上有三个必须踩准的点，都是实测踩出来的：

1. **决策不占 tick** —— 原局里玩家操作是离散的。重放若把每次决策摊到不同 tick，后续所有事件的 `tick` 都会偏移，哈希必然不同。因此 `applyReplayDecision` 要在**单个 tick 内做完本波全部决策**。
2. **外部循环不能抢先 `skipCards()`** —— `runToEnd` 必须先问 `engine.hasReplayScript()`，否则会在引擎的脚本决策之前把手牌丢掉，表现为「脚本看起来完全没生效」。
3. **索引语义要对齐** —— 记的是手牌下标（0/1/2），不是 `cardIndex()` 的技能 id 编码。混用会选中完全不同的牌，且**不报任何错**。

### 三条被撤回的误判（留档以免重犯）

#### 1. `gofmt -C` 是无效 flag，而我以为格式化过了

本轮写过十几次：

```bash
gofmt -C "$root/server" -w internal 2>&1 | Out-Null
```

`gofmt` **没有 `-C` 这个 flag**（它只接受路径参数）。每次都因为 `| Out-Null`
而看不到任何报错，于是我以为格式化过了。实际是 7 个文件从未被格式化，
`gofmt -l` 一直有输出 —— 而验证流程里只跑了 `go vet`，**从没跑过 `gofmt -l`**。

收尾核对时顺手跑了一次 `gofmt -l`，它明确报出 `flag provided but not defined: -C`。

**这属于「把『命令没报错』当成『命令生效了』** ——
`| Out-Null` 吞掉的不只是输出，还有 stderr 与 exit code。

本轮同类误判的四例：

| 误判 | 表现 | 差别 |
|---|---|---|
| 探针倍率施加到错误对象 | 实验给出「这个变量无影响」的假结论 | 有输出，但输出本身是错的 |
| `gofmt -C` | 格式化从未发生，`gofmt -l` 一直有差异 | **无输出**（被 `Out-Null` 吞掉） |
| `defaultAttacker` 漏调用括号 | 展开函数得到 `{}`，TypeError | 有报错，但被误读成签名不对 |
| `Math.random` 源码检查 | 被**自己的注释**判失败 | 有报错，指向注释而非代码 |

**教训**：验证流程里每条命令都要有一条**能证明它生效**的判据。
`gofmt -w` 的判据是 `gofmt -l` 无输出 —— 只跑 `-w` 等于没验证。

#### 2. 「热量上限压制了攻击力收益」是错的

我曾在 README 断言「热量上限压制了攻击力收益」，依据是实测 `attack` 从 1‰ 提到 100‰（100 倍）后清场耗时一字不变。**这个结论是错的**，两个原因：

1. **单位误读** —— `attack` 是**千分比**。1‰ → 100‰ 只把单发伤害从 120.1 抬到 132（+8%），不足以跨过「多打一发」的门槛，耗时相同完全正常。
2. **夹具太弱** —— 测试敌人只有 3000 血，0‰ 攻方都能全清，攻方差异被**刷怪节奏**掩盖（8 只怪的 spawn 间隔就占了 21 秒）。

用 30000 血重测后，攻击力收益完全正常：

| atk | 击杀 / 漏怪 | 耗时 |
|---|---|---|
| 0‰ | 5 / **3** | 101 s |
| 1000‰ | 6 / 2 | 98 s |
| 50000‰ | **8 / 0** | 51 s |

**教训**：看到「某个成长维度无效」时，先确认单位与量级，再构造能暴露差异的夹具 —— 否则测出来的是夹具的局限，不是系统的缺陷。`defense.test.ts` 现在同时有「攻击力有实际收益」和「1‰ vs 100‰ 差异本就不显著」两条用例，把这个认知钉死。

#### 3. 同一个教训的第二次发作：夹具的"温和度"

上面那次误判让我以为"夹具太弱"是唯一风险。半年后（同一轮审计）又栽了一次，方向相反 —— **夹具太强/太温和**，同样让缺陷隐形：

引擎的 4 个热量用例全部手工构造关卡与敌人。热量吸收态因此完全测不到，因为：

- 夹具只装 1 个技能（热量 20）→ 5 发正好到 100 触发过热 → 缺陷不可见
- 真实配置装 4 个技能（20/18/22/20，总和 80 < 100）→ **永远到不了 cap**，战斗停摆

也就是说，**夹具的参数温和度本身就是一种掩盖**。当时能测出"1‰ vs 100‰ 差异不显著"的精细用例，面对"4 个技能热量加不到 100"这种粗糙缺陷反而毫无办法 —— 两者不在一个量级的问题域。

真正的解法不是"再写一条更细的用例"，而是**把真实内容表接进测试**（`cmd/vectors` 导出 → `engine.smoke.test.ts`）。粗糙的缺陷只能被粗糙的夹具抓住：精细的数值断言对"整体停摆"是盲的，而真实关卡跑一遍就抓住了。

**教训（补充）**：夹具的"分辨率"要与缺陷的"尺度"匹配。数值问题用数值夹具，状态机问题用真实内容。同一个测试文件里两种尺度的用例不能互相替代。

```
server/internal/
├─ domain/     纯逻辑（伤害、元素、关卡生成、专精、战力）—— 与存储无关，可独立测试

└─ store/      Pinia 全局状态
```

**职责边界**：`game/` 不 import 任何 `uni` API，因此同一份内核能同时跑在微信 canvas、H5 canvas 和 Node 测试里。
