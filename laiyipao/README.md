# 来一炮

仿微信小游戏《向僵尸开炮》玩法内核自研的**塔防 + 元素反应**小程序游戏。美术 100% Canvas 程序化绘制，不使用任何原作名称、素材、UI 或文案。

```
laiyipao/
├─ server/     Go Fiber + PostgreSQL 后端
├─ miniapp/    uni-app（微信小程序 / H5 双端）
├─ admin/      Vue 3 运营后台 + 玩家玩法文档站
├─ docs/       设计文档（创新点、公式、双端契约）
└─ scripts/    端到端验收脚本
```

## 核心创新点

完整设计见 [`docs/GAME_DESIGN.md`](docs/GAME_DESIGN.md)。

| 编号 | 创新点 | 一句话 |
|---|---|---|
| **I-1** | 元素反应矩阵 | 5 元素 × 7 反应链。**反应伤害中攻击力权重结构性 ≤30%** —— 堆金币永远无法替代正确搭配 |
| **I-2** | 插槽与热量 | 「三选一」不再是无脑增益。给选择装上代价，弃牌回热量，热量满则 2s 无法释放 |

| **I-6** | 回放哈希验真 | 战斗完全确定性。任何人可取回种子重放，**证伪**可疑分数 |

| L-1 | 卡关诊断 | 连续失败时给出针对性建议（无元素覆盖 / 抗性不匹配 / 专精未投入…） |
| L-2 | 效率榜 | 按**通关时最低战力**排名，给低养成玩家留位置 |
| L-3 | 阵型预设 | 一键套用他人已验证的构筑 |

## 六个关键工程约束

这六条决定了整个架构，写在这里是因为**改动时必须同时满足**。

### 1. 反通胀是结构性保证，不是数值调优

```
反应伤害 = (元素侧 + 攻击侧) × (1 - 抗性)

攻击侧 = min(D × k × 阶,  w × 元素侧 / (1 - w))     w ≤ 300‰
```

`攻击侧 / (元素侧 + 攻击侧) ≤ w` 是**恒等式**，任意输入下都成立。因此数值膨胀无法绕过搭配收益 —— 这是设计能被信任的原因。

### 2. 定点整数 + 确定性 PRNG

- 伤害/速度/坐标/血量一律 **bigint × 1000 定点整数**
- 随机只走 `lcg.ts`（PCG-XSH-RR），**禁用 `Math.random`**
- 定步长 **50ms**（20Hz）推进，渲染层独立插值
- 抗性列是**千分比** -500..500（不是百分比）

浮点会带来跨引擎差异 → 同一场战斗算出不同哈希 → I-6 直接失效。

### 3. 攻方属性必须由服务端下发

回放哈希由 **关卡 + 种子 + 攻方属性 + 技能槽** 四者共同决定。四者缺一，重放方就算不出同一个哈希 —— 验真会把所有正常对局都判成伪造。

因此 `/api/v1/me` 与 `/battle/token` 的 `build` 里带 `attacker` 字段，客户端**只读不推算**；技能槽位存在 `user_skill_slots` 表，通过 `/me/loadout` 读写。

> ⚠️ 这条曾被违反：客户端用 `100 + maxStage*200` 自己猜攻击力，服务端无从知晓，双方哈希必然不同 —— I-6 形同虚设。已改为服务端权威下发（`internal/service/attacker.go`）。

### 4. 跨端字段名必须显式约定 —— 且要双向核对

Go struct **漏写 json tag 会按字段名原文（PascalCase）序列化**。客户端类型用 snake_case 时两边对不上，每个字段都是 `undefined` —— 且**不报任何错**。

这一条踩过两次，方向相反：

| 位置 | 声明 | 实际下发 | 后果 |
|---|---|---|---|
| `domain.RatingWeights` | 无 tag → `ElementCoverage` | `ElementCoverage` | 两端"一致"所以测试全绿，但与同响应里的 `BuildRating`（snake_case）风格割裂 |
| `miniapp/api/client.ts` 的 `chapters` | `ch.ID` / `ch.Name` | `id` / `name` | **关卡页章节标签全空白、点击无效、永远不高亮** |
| `admin/WikiView.vue` 的 `reactions` | `row.BaseCoef` / `row.AoeRadius` | `base_coef` / `aoe_radius` | 文档站反应表整列为空 |
| `admin/SkillsView.vue` 的配方 | `r.A` / `r.Output` | `a` / `output` | 每条配方渲染成 `#undefined + #undefined → #undefined（Tundefined）` |

同一份 `client.ts` 里 `levels` / `enemies` / `skills` 是对的，只有 `recipes` / `reactions` / `chapters` / `rating_weights` 错 —— 说明这些字段是分批写的，**没人做过整体核对**。

双向核对的两个方向：

1. **Go → 客户端**：所有下发结构体必须带 `json:"snake_case"` tag，**嵌套的也算**（`RatingWeights` 就曾漏掉）。加新 struct 时不要漏。
2. **客户端 → Go**：TS 接口的字段名必须逐字对齐服务端的 tag。注意**同名不同义** —— `build.skill_ids` 装的是元素名（历史误命名，现已同时下发正确名 `elements` 并保留旧名作兼容），而 `/me/loadout` 的 `skill_ids` 是真的技能 id 数组。代码内部自洽，但按名字推断语义的消费者会踩坑。

发现手段：**拿真实 `seed` 数据跑一遍，看渲染出来是不是空**。本轮关卡页章节空白就是这样发现的 —— 目视检查比读类型定义可靠。

### 5. 每一道防作弊校验都要有对应的负向测试

结算校验的价值全在"拒绝"分支上。而拒绝分支的特征是**不报任何错，只是默默不给钱** —— 没有专门的负向测试，下一次重构就会把它删掉，而且看起来一切正常。

本轮修的三处都属于这一类，且其中一处是**上一轮修复自己留下的洞**：

| 漏洞 | 触发 | 后果 |
|---|---|---|
| `duration_ms=0` 让得分裁剪整段被跳过 | 上报 `duration_ms:0` + `result:"lose"` | 分数无上限 → 星级恒 3 → 单局金币触顶 60000（正常约 1650） |
| `reactions` 无上界 | 上报 `reactions:1e9` | 一次顶满全部反应类任务与成就 |
| 兑换码 `used_count` 靠 CHECK 约束兜底 | 并发兑换 | 客户端收到 SQLSTATE 23514 而非业务错误；**约束一旦被迁移就是无限超发** |

第三条尤其值得记：`UPDATE ... SET used_count = used_count + 1 WHERE id = $1` 看着无害，资源上确实没超发（CHECK 挡住了），但那是**"恰好"有约束**，不是并发设计。正确写法是条件 UPDATE + 检查 `RowsAffected`，与 `ClaimTask` 的 `claimed_at IS NULL`、`Buy` 的 `FOR UPDATE` 同一个模式。

还有一个更隐蔽的形态：**约束了被保护量却没约束控制量**。给 `reactions` 加了 `reactions <= shots * 8` 的上界，但 `shots` 当时无上界 —— 于是上报 `shots:1.25e8` 时上界正好变成 1e9，恰好放行它本该挡掉的 1e9。约束链上每一环都必须有界。

**规律**：加任何一条上界校验时，同时问「这个上界自己由什么界定，那个东西有界吗」。

### 6. 双端公式一致性是**可执行检查**

`server/testdata/formula_vectors.json` 是唯一事实源：

| 端 | 测试 |
|---|---|
| Go | `internal/domain/consistency_test.go` |
| TS | `src/game/consistency.test.ts` |

两端读同一个 JSON、断言同样的数字。任一端单方面改公式，另一端立刻红。

> ⚠️ 该文件里的 64 位值用**字符串**承载。JSON number 超过 2^53 后 JS 解析即失精，`6917529027818027904` 会被解析成 `...8032`，断言会**悄悄通过**。同理，`/api/v1/battle/token` 与 `/battle/{id}/replay` 的 `seed` 也是字符串下发。

但**跨端一致 ≠ 两端都对**。本轮就有两处「两端同时漏掉同一个东西」，13 个向量全绿：

- `reactionMultPermille` 在 `resolveHit` 里根本没有乘区（专精树 6 个节点白给）
- `applyArmor` 因为向量里 `armor_permille` 恒为 0，**两端都从未执行过第二行**

所以一致性测试的定位是「防漂移」，不是「防错误」。后者要靠各自的单元测试 + 真实内容表的冒烟测试。

三条规则：

1. **只导数据，不导期望值。** 期望值写在 `formula_vectors.json` 里人工推导 —— 用实现生成期望值就是自证，测试会永远绿。
2. **Go 侧不读回自己的导出做自证。** 跨端锁在客户端：改了 TS 侧副本，客户端测试红；改了 Go 侧，`-check` 红。
3. **不写 UTF-8 BOM。** `encoding/json` 拒绝 BOM 而 Vite 会吃掉它 —— 同一个文件在两端被解析成不同内容，是最难查的一类故障。（真实发生过：所有 Go 一致性测试突然集体失败。）

### 端到端冒烟测试为什么必须用真实内容表

`engine.smoke.test.ts` 跑的是**从 Go 真相源导出的真实第 1 关**。这不是为了"更真实"，是因为历史上所有引擎测试都用手工构造的关卡，结果两个致命缺陷一路活到端到端试玩才暴露：

| 缺陷 | 手工夹具为什么测不到 | 真实数据下的表现 |
|---|---|---|
| 热量吸收态（衰减被整数除法截断为 0 + 死区无兜底） | 夹具只装 1 个技能时 5 发正好到 100 触发过热，缺陷不可见 | 4 技能（20/18/22/20，总和 80 < 100）永远到不了 cap，战斗停摆 |
| 刷怪 `delay`/`interval` 是毫秒却被当 tick | 夹具的 delay 是个位数，差 50 倍也看不出 | 第 1 关第一波 1012ms 变成 50.6 秒，全关 18.7 分钟 |

两者都只在"真实参数 + 长时间运行"下暴露。修复后实测：默认构筑第 1 关 **6806 tick（5.7 分钟）通关，score 16048，拿到 3 星**（3 星门槛 14656）。修复前是 385 秒 0 杀 0 星。

这些断言都经**变异测试**验证过有效性 —— 把缺陷改回去，确认测试真的会红：

| 变异 | 结果 |
|---|---|
| 衰减改回 `(10n*50n)/1000n` | `heatmap.test.ts` 5 条红 |
| 衰减截断 + 移除死区兜底（即修复前状态） | `engine.smoke.test.ts` 2 条红（`3000 tick 只开 3 发`） |
| `atTick` 改回直接加毫秒 | `engine.smoke.test.ts` 3 条红 |
| `star_targets` 还原成 `[78000, 93600, 109200]` | `engine.smoke.test.ts` 3 条红 |
| 护甲加成加回敌人 | `engine.smoke.test.ts` 1 条红 |
| 客户端反应表某项漂移 | `reaction_contract.test.ts` 1 条红 |
| `applyArmor` 完全失效 | `armor_test.go` 11 处红 |
| `MAX_ARMOR` 750 → 100 | `armor.test.ts` 4 条红 |
| Go 侧 PHI 末位 +1 | `-check` 报 2 个文件过期 + 客户端 1 条红 |
| 平衡 flag 改 false | `consistency.test.ts` 1 条红 |
| `Buy` 去掉 `FOR UPDATE` | `concurrency_test.go` 稳定 `成功 5 次 > 限购 3 次` |
| `SignIn` 恒返回错误 | `concurrency_test.go` 夹具自检捕获 |

⚠️ 在项目文件上做变异测试的两条纪律：**先备份到项目外**、**必带 `-timeout`**。
本项目已经栽过一次：把 `go func` 改成同步直调导致 `wg.Wait()` 永久阻塞、
命令超时，文件被留在变异状态，备份缺失时是手工改回去的。

### 测试空洞的四种形态

| 形态 | 实例 | 改坏了能绿吗 |
|---|---|---|
| **恒等式** | `expect(levelSeed(1)).toBe(levelSeed(1))` | 能。名字叫「与 Go 侧一致」，实际自己等于自己 |
| **本地复制** | 测试内抄一份 PHI 常量与公式 | 能。改 Go 侧完全不影响它 |
| **夹具落在保护之外** | 契约向量 `armor_permille` 全为 0，而 `applyArmor` 第一行就 `return` | 能。两端都改成 `return dmg`，140+ 测试全绿 |
| **数据文件当开关** | `if (!vectors.balance_invariants.xxx) return` | 能。把 flag 改 false，断言静默消失 |

共同点：**它们全都待在「看起来测了东西」的位置上**。所以补测试的判据不是
"覆盖到了吗"，而是**"改坏被测代码会不会红"** —— 这只能靠变异测试回答，
读代码回答不了。

## 已知边界（诚实声明）

以下**没有做**，且不会假装做了：

1. **微信支付内购、流量主广告未真实接入** —— 需要 AppID 与商户号。商城、订单、货币流水的数据结构与后台配置已完整，但**没有支付/广告 SDK 的 mock 层**，客户端也没有调起支付的代码路径。真实接入需拿到凭证后从头补。
2. **微信登录通道预留未启用** —— `jscode2session` 已实现（`service/economy.go`），受 `WECHAT_ENABLED` 开关控制。未配置 AppID/Secret 时返回明确的 501 错误而非静默降级成游客登录。当前默认走游客登录，客户端尚未接 `/auth/wechat`。
3. **防线挑战的胜负由客户端裁决** —— 服务端不跑战斗引擎（省掉两套引擎同步的代价），挑战在挑战者设备上用同一套引擎本地模拟攻方，结果上报后服务端只校验「次数未超限 / 护盾已过期 / 资源守恒」。因此**服务端无法独立验证胜负**，后台「防线值守」页对接近 100% 或 0% 的异常胜率做告警。
4. **渲染层像素级视觉未在真机验证** —— 验证在无头浏览器完成（`canvas.test.ts` 用打桩上下文覆盖绘制路径），且浏览器标签页隐藏时 rAF 会被冻结、定时器被节流到 ~1Hz，因此无法在本机观察战斗推进的视觉表现。**需要在真机或可见窗口下补一次人工验收。**
5. **关卡节奏偏长、命中率偏低** —— 第 1 关实测 5 波 39 只怪要打 5.7 分钟，`hits/shots ≈ 14%`。数值本身自洽且能通关，但这是**平衡未调**而不是设计意图。根因是敌人血量（70~260）相对默认攻击力（100，单发直接伤害约 44）太低，二者之间没有中间状态：要么几发打死、要么打不动，因此堆攻击力的边际收益也很低（实测 ×1000 只把分数从 16048 抬到 20137）。**未做平衡调优。**
6. **I-4 地形机制大部分未生效** —— 5 类地形里只有蓄能塔能真实触发。油桶/掩体的充能阈值（`param` = 100~5000）与每次命中的实际增量（`totalDamage/100` ≈ 0~1）差 2~3 个数量级；掩体的每 tick 充能路径与弹丸销毁判定在几何上互斥。**需要重标 `param` 并给 `onHit` 加位置判定。**
7. **`reactionMultPermille` 全链路空转** —— 专精树的 `reaction_mult` 节点、装备契合度、防线工程装置「特斯拉栅格」都只写不读，`resolveHit` 里没有这个乘区。因此构筑评分里那一路对战斗零影响。**两端同时漏掉同一个乘区，所以 13 个公式一致性向量全过。**
8. **平衡未调** —— 见第 5 条。第 1 关 5.7 分钟、命中率 14%、堆攻击力边际收益极低。**I-1 的元素反应矩阵在当前数值下基本感受不到**，这是最需要优先解决的设计债。
9. **`reactionMultPermille` 的修复需要重新推导反通胀不变式** —— 见第 7 条。直接把该乘区接进 `resolveHit` 会**破坏** I-1 的核心保证：反应伤害里攻击力占比原本被 `reactAtk = min(D·k·阶, w·elemSide/(1-w))` 压到 ≤30%，乘上 `M > 1` 后占比会上升。正确的接法必须同时把上限改成 `w·elemSide/((1-w)·M)`。这属于**需要判断的设计决策**，没有擅自改。
10. **暴击率存在 10× 单位错** —— `roll` 的语义是 0..9999，而判定用 `roll >= 1000 - critPermille`，于是 `critPermille=50`（5%）实际产生 **90.5%** 暴击率。两端同时错所以 13 个一致性向量全过。修它要重算全部向量并重做平衡，属于设计决策，**未改**。
11. **客户端与服务端的胜负判定曾长期不一致** —— 已修（见提交 `test(laiyipao)`）。修的方向是"清空即胜"而非"零漏怪才胜"：漏怪已经扣 `base_hp`，那是漏怪容忍度的设计载体，再判负等于同一件事惩罚两次。

### 重放如何还原「玩家点了哪张牌」

选牌会改变后续战斗（技能升格 / 属性加成 / 机制词条），所以它是战斗输入的一部分，必须能被复现：

- 引擎记录 `cardPicks`（每波选中的**手牌下标**，-1 = 整波跳过），settle 时上报
- 服务端存进 `battle_records.card_picks`（逗号分隔紧凑文本，迁移 `00008`）
- 重放时 `engine.setReplayScript(picks)` 注入，引擎在选牌阶段**自动**按脚本决策

实现上有三个必须踩准的点，都是实测踩出来的：

1. **决策不占 tick** —— 原局里玩家操作是离散的。重放若把每次决策摊到不同 tick，后续所有事件的 `tick` 都会偏移，哈希必然不同。因此 `applyReplayDecision` 要在**单个 tick 内做完本波全部决策**。
2. **外部循环不能抢先 `skipCards()`** —— `runToEnd` 必须先问 `engine.hasReplayScript()`，否则会在引擎的脚本决策之前把手牌丢掉，表现为「脚本看起来完全没生效」。
3. **索引语义要对齐** —— 记的是手牌下标（0/1/2），不是 `cardIndex()` 的技能 id 编码。混用会选中完全不同的牌，且**不报任何错**。

### 一条被撤回的误判（留档以免重犯）

我曾在 README 断言「热量上限压制了攻击力收益」，依据是实测 `attack` 从 1‰ 提到 100‰（100 倍）后清场耗时一字不变。**这个结论是错的**，两个原因：

1. **单位误读** —— `attack` 是**千分比**。1‰ → 100‰ 只把单发伤害从 120.1 抬到 132（+8%），不足以跨过「多打一发」的门槛，耗时相同完全正常。
2. **夹具太弱** —— 测试敌人只有 3000 血，0‰ 攻方都能全清，攻方差异被**刷怪节奏**掩盖（8 只怪的 spawn 间隔就占了 21 秒）。

用 30000 血重测后，攻击力收益完全正常：

| atk | 击杀 / 漏怪 | 耗时 |
|---|---|---|
| 0‰ | 5 / **3** | 101 s |
| 1000‰ | 6 / 2 | 98 s |
| 50000‰ | **8 / 0** | 51 s |

**教训**：看到「某个成长维度无效」时，先确认单位与量级，再构造能暴露差异的夹具 —— 否则测出来的是夹具的局限，不是系统的缺陷。`defense.test.ts` 现在同时有「攻击力有实际收益」和「1‰ vs 100‰ 差异本就不显著」两条用例，把这个认知钉死。

### 同一个教训的第二次发作：夹具的"温和度"

上面那次误判让我以为"夹具太弱"是唯一风险。半年后（同一轮审计）又栽了一次，方向相反 —— **夹具太强/太温和**，同样让缺陷隐形：

引擎的 4 个热量用例全部手工构造关卡与敌人。热量吸收态因此完全测不到，因为：

- 夹具只装 1 个技能（热量 20）→ 5 发正好到 100 触发过热 → 缺陷不可见
- 真实配置装 4 个技能（20/18/22/20，总和 80 < 100）→ **永远到不了 cap**，战斗停摆

也就是说，**夹具的参数温和度本身就是一种掩盖**。当时能测出"1‰ vs 100‰ 差异不显著"的精细用例，面对"4 个技能热量加不到 100"这种粗糙缺陷反而毫无办法 —— 两者不在一个量级的问题域。

真正的解法不是"再写一条更细的用例"，而是**把真实内容表接进测试**（`cmd/vectors` 导出 → `engine.smoke.test.ts`）。粗糙的缺陷只能被粗糙的夹具抓住：精细的数值断言对"整体停摆"是盲的，而真实关卡跑一遍就抓住了。

**教训（补充）**：夹具的"分辨率"要与缺陷的"尺度"匹配。数值问题用数值夹具，状态机问题用真实内容。同一个测试文件里两种尺度的用例不能互相替代。

## 目录约定

```
server/internal/
├─ domain/     纯逻辑（伤害、元素、关卡生成、专精、战力）—— 与存储无关，可独立测试
├─ service/    业务编排
├─ httpapi/    路由与鉴权中间件
├─ store/      pgx 数据访问
└─ auth/       令牌签发与校验

miniapp/src/
├─ game/       纯 TS 内核（零绘制、零网络）—— 可在 Node 里无头跑
├─ render/     Canvas 2D 渲染层（只读引擎状态，绝不修改）
├─ api/        请求封装（401 自动刷新一次）
└─ store/      Pinia 全局状态
```

**职责边界**：`game/` 不 import 任何 `uni` API，因此同一份内核能同时跑在微信 canvas、H5 canvas 和 Node 测试里。
