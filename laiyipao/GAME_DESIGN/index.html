    来一炮 · 玩法设计¶

    版本 v1.1 · 2026-09-28

    ⚠️ 本文档的地位：玩法设计意图 + 与实现的差异清单。 它不是实现的单一事实源 —— 实现的单一事实源是代码与 server/testdata/ 里的契约夹具。

    本文档与代码不一致的地方，本文档已经标注（每处注明实测值与核实方式）。 数字改动后请跑 go -C server test ./internal/domain -run "GameDesign|OpsDoc|DesignDoc" -v —— docs_drift_test.go 会把本文档里的关键数字与代码逐项比对，漂了就红。 ⚠️ 跑这条命令时应看到恰好 7 条 --- PASS（GameDesign×2 / OpsDoc×3 / DesignDoc×2）； 一条都没有 = 模式没命中任何测试（本守卫家族 2026-10-14 文档迁移后曾因此静默空转过）。

    定位：玩法机制与《向僵尸开炮》同构（关卡闯关 / 守防线 / 局内选卡 / 场外养成）， 表达与系统全原创，并在其之上做 7 项机制级创新以形成自有辨识度。

    逐关数值平衡与实测数据见 IMPLEMENTATION.md，已知边界见 KNOWN_LIMITS.md。

    0. 设计红线¶

    原作被玩家和媒体反复诟病的 4 个问题，直接决定我们的创新方向：

    原作问题 后果 我们的对策
    后期全靠堆数值（技能等级/宝石词条/装备等级都在加伤害） 挑战性崩塌，"氪佬与平民差距"退化成纯资源量 创新 I-1 元素反应矩阵 + I-3 专精树，反应伤害与攻击力解耦
    局内选完技能就不用操作，关卡退化为波数推进 操作无意义，通关=时间问题 创新 I-2 插槽热量（构筑有代价）+ I-4 地形机制关（关卡是谜题）
    技能"三选一"是无脑增益，配方只是解锁更纯的数值 没有构筑决策 I-2 热量/弃牌 + I-3 专精点有限，必须做取舍
    离线收益是纯挂机产出，社交只有排行榜 挂机无意义，社交浅 创新 I-5 防线值守（异步对抗）+ I-6 回放哈希验真（公开可验证）

    三条不可退让的红线

    1. 不许出现"唯一最优解" —— 每个机制都必须至少留 2 条可行路线。
    2. 养成线之间必须互相咬合，不允许 4 条线各自独立加伤害（金币/钻石也必须各有用处）。
    3. 战斗必须确定性可复现（见 I-6），这是反作弊与公平性的技术地基。

    红线的当前达成度：第 1 条未完全达成（见 §11 边界 3）， 第 2 条部分达成（装备契合度未做，见 §11 边界 1）， 第 3 条已达成（I-6 全链路可复现，见 I-6）。

    1. 核心循环¶

    选关 → 布阵（4 主动槽 + 1 被动槽 + 3 工事）
     → 战斗：自动索敌开火，玩家可拖拽微调弹道与提前量
     → 波次间：抽 3 张手牌（技能/属性/机制）→ 有代价地选
     → 胜利：结算星级 + 资源 + 掉落 → 养成（专精/装备/宝石/皮肤）
     → 循环；或失败 → 诊断提示 → 复盘 → 重试 / 一次复活

    单局目标：在防线血量归零前清完所有波次（含 BOSS）。防线血量不随关卡回复。

    2. 创新点（核心）¶

    I-1 元素反应矩阵 —— 破数值通胀¶

    问题：原作所有养成都加攻击力，于是后期"堆数值"就是唯一解。 做法：把伤害拆成三段，其中反应伤害段与攻击力解耦。

    单次命中伤害 = 直接伤害(吃养成攻击力，受护甲减免)
             + 元素层数伤害(吃元素层数/元素系数，不吃攻击力)
             + 反应伤害(吃搭配与时序)

    反通胀的真正保证不是权重，而是"反应伤害里攻击力的占比"：

    反应伤害内部拆分：
    元素侧 ← 元素层数 × 反应倍率 × 反应等级   （与养成无关，弱玩家可拉满）
    攻击侧 ← 玩家攻击力                       （与养成相关，强玩家更快）

    硬性红线：反应伤害中的攻击力权重 ≤ 30%。

    实现上由反应表的 attack_weight_pct 逐条声明，实测取值 200 / 250 / 300， 即 20% / 25% / 30%，全部 ≤ 30%。核实：server/testdata/reaction_specs.json。

    攻击侧还额外受 reactionAttackCap 约束（wE/((1-w)·M)）， 推导见 miniapp/src/game/damage.ts 的注释。

    5 种元素：焰 Fire / 冰 Ice / 电 Lightning / 毒 Corrosion / 动能 Kinetic （核实：elements.ts 的 AllElements()，恰好 5 种）

    7 条反应链（施加 A 后命中带 B 的目标即触发；核实：reaction_specs.json 恰好 7 条）：

    反应 触发 元素倍率 攻击权重 效果
    蒸汽爆发 焰 + 冰 55 30% 范围伤害，驱散护盾
    过热 焰 + 电 55 30% 爆炸 + 眩晕 1.5s
    燃烧云 焰 + 毒 40 25% 生成火区，元素值可续燃
    超导 冰 + 电 50 25% 目标受击伤害 +60%，持续 4s
    急速冻结 冰 + 毒 45 25% 冻结 2s，受击伤害 +30%
    腐蚀扩散 电 + 毒 35 20% 把目标的元素层数传播给半径内目标
    破甲击退 动能 + 任意 30 30% 削穿护甲（4s 内 −150‰），击退目标，为其他伤害开窗口

    ⚠️ 与设计意图的差异：「燃烧云 6s 火区」「超导持续 4s」里的持续伤害周期 未单独实现 —— 反应表只有 status_duration_ms（控制时长）， 没有 DoT 的 tick 定义。燃烧云的火区是地形机制（见 I-4），不是反应自带的 DoT。 见 §11 边界 4。

    ✅ 范围伤害与破甲击退已实现（区别于下面 2 条未实现项）： steam_burst（2026-10-10，半径 120）与 overheat（第 160 轮，半径 90） 的爆炸/溅射走同一条管线（engine.ts triggerReactionAoe，Go 侧镜像）—— 命中敌人为圆心、半径内邻居受 25% 反应伤害；眩晕 / 驱散护盾等状态 只作用主目标，不随溅射扩散。破甲击退触发后 4000ms 内目标 有效护甲被削 150‰，并一次性击退 4px（定点 4000）。两类数值都落在 反应表的 aoe_radius / armor_shred_permille / knockback / status_duration_ms 字段，跨端由 reaction_specs.json 与 reaction_contract.test.ts 双向锁定，行为由 armor_break.test.ts / overheat_aoe.test.ts（TS）与 Go 侧对应行为测试钉住。 其余 2 条（burn_cloud 火区 / corrosion_spread 层数传播）仍是纯反应伤害，未实现，见 §11 边界 4。

    敌人 5 维抗性：每种敌人有 fire/ice/lightning/corrosion/kinetic 五个抗性值， 范围 −50%（吃双倍）~ +50%（几乎免疫）。BOSS 必有高抗 + 负抗组合 → 强制换搭配。

    平衡红线（写进自动化测试）

    1. ✅ 反通胀：反应攻击力权重 ≤ 30% —— 反应表声明 + damage.test.ts 断言
    2. ✅ 以弱胜强可行：低养成 + 正确搭配能打过高养成 + 无搭配（同关卡）—— 由 tier_impact.test.ts 的 3 档位 × 100 关守住
    3. ⚠️ 无唯一最优解：任一关卡穷举「元素组合 × 专精方向」， 通过率最高与次高差距 ≤ 15% —— 未实现该穷举测试，见 §11 边界 3
    4. ⚠️ BOSS 可解：每个 BOSS 高抗元素的负抗反应链须足以破防 —— 未实现该测试

    I-2 插槽与热量 —— 让三选一变成风险管理¶

    问题：原作局内三选一是纯增益，无脑拿。 做法：给选择装上代价。

    • 玩家有 4 个主动插槽 + 1 个被动槽。主动槽只能放主动技能，被动槽只能放被动。 （核实：heatmap.ts 的 ACTIVE_SLOTS = 4； ⚠️ 该常量是重放哈希的锚点，改了会让所有历史战报失去可重放性）
    • 每个波次间隙抽 3 张手牌：1 张技能 / 1 张属性卡 / 1 张机制卡。 （核实：rollWaveCards 恰好产出 3 张）
    • 弃牌：每波可免费弃 1 张（DISCARD_PER_WAVE = 1）， 弃牌回 +1 热量（DISCARD_HEAT_REFUND = 1n，热量是资源不是惩罚）。
    • 热量：释放技能消耗热量，基础上限 100（HEAT_MAX = 100n）， 超限进入 过热 2000ms（2s）（OVERHEAT_DURATION_MS = 2000）内无法释放。
    • 上限可被专精与宝石提升，且提升量是千分比（cap = HEAT_MAX × (1000+bonus)/1000）
    • 过热期间元素层数不清除 → 高热量爆发流可行，而非纯惩罚
    • 抽到重复技能可就地强化（伤害 +20%、元素层数 +1、穿透 +1）

    ⚠️ 与设计意图的差异：原设计写的是「同一技能 3 选 1 变成 1/2/3 阶， 高阶 = 更高热量但更强反应倍率」。实现里没有「阶」这个概念 —— 抽到重复技能就是固定幅度的强化（波次之间选，不在抽牌瞬间就地升格）， 也没有「高阶提高热量消耗」。见 §11 边界 5。

    设计后果：玩家每波都在回答"我要 build 什么、留多少热量、要不要弃牌保空间"。

    📌 玩家实际看到的引导（miniapp/src/pages/battle/battle.vue 选牌界面）： 标题"这一波给你 3 张卡，点一张就装备上"，提示行把"弃牌返还 1 热量"翻译成 "点卡上的「弃」丢掉，还能回 1 点热量（热量攒满就会过热卡 2 秒）"，跳过按钮写成 "一张都不要了，直接下一波"。改这些文案时，数值（discardsLeft、回 1 热量、 过热 2s）要跟上面的 DISCARD_PER_WAVE/DISCARD_HEAT_REFUND/OVERHEAT_DURATION_MS 对得上， 别让引导文字和引擎行为漂移。

    I-3 专精树 + 装备契合度 —— 让养成线互相咬合¶

    问题：原作技能/装备/宝石/皮肤 4 条线各自加伤害，资源可以随便堆。 做法：

    8 系专精树，每系 12 节点（3 层 × 4 节点），共 96 节点：

    family 中文 family 中文
    flame 焰 light 光
    frost 冰 blight 疫
    volt 电 drone 无人机
    kinetic 动能 engineering 工程
    • 节点类型：元素层数上限 / 反应倍率 / 热量上限 / 额外插槽 / 机制改造 （含 ExtraSlots：8 个节点各 +1 槽，客户端按 active_slots 生效）
    • 专精点有限：初始 3 点；每层只能选 2 个（4 选 2，PerLayerPickLimit = 2）
    • 结果：不可能点满，必须选方向

    ⚠️ 与设计意图的差异 1：原设计写「每 10 级 +1」。 实际公式是 mastery_points = 3 + FLOOR((level_exp + 50 + 本局击杀) / 1000) —— 基于累计经验与击杀，不是关卡等级。见 service/game.go 的 applyProgress。

    ⚠️ 与设计意图的差异 2：装备契合度未实现，且已决定不做。 原设计写「装备标签与已装备技能同系 → 反应伤害 +X%；不同系 → 直伤 +Y%（Y < X/3）」。 实际情况：18 件装备的 element 字段全项目从未被读取， 战斗数值只来自 base_armor（合计 430）与 base_bonus_pct（合计 1875）。 不做的两条理由见 §11 边界 1。

    货币分流（解决"金币钻石都能升一切"）：

    货币 唯一用途
    金币 技能/装备的基础升级（便宜、量大、线性）
    钻石 专精点重置、洗练、皮肤（稀缺、不可逆决策）
    体力 进入关卡（软墙，只卡"刷"不卡"玩"）
    钥匙 资源副本 / 每周 BOSS 门票

    I-4 地形机制关 —— 让关卡是谜题而非波数¶

    5 类可交互地形。实测 25/100 关使用地形，75 关没有地形。

    地形 机制 生效率（实测）
    油桶 受到焰命中即引燃 → 爆炸 + 生成火区 33%（需集火）
    崩塌掩体 受到动能伤害累计到阈值即崩塌 → 弹道永久改变 100%
    潮汐闸 周期升降：改变敌人路径与弹道受阻 100%
    旋转风障 持续改变区域内弹丸飞行方向 100%
    蓄能塔 累积被击杀敌人的元素值，满则给全场敌人上同种元素 100%

    逐章地形关数（实测）： ch1 = 4、ch2 = 5、ch3 = 6、ch4 = 4、ch5 = 3、ch6 = 3，合计 25。 油桶的 33% 是有意的战术意图（"集火才点燃"），不是死代码 —— 探针只拦"零生效"，不设 33% 的硬阈值。

    ⚠️ 与设计意图的差异：原设计称"每章至少 3 关"，实测 ch4 只有 4 关但 没有任何一关同时使用 2 种以上地形（每关的 terrain 全部同 kind）。 这意味着 terrain_used 上报字段的合法长度最多是 1， 按关的「地形触发率」统计分辨率只有 0/1。见 §11 边界 6。

    设计后果：地形既是解法（用火区烧整队、用崩塌打开射界）也是约束（掩体会挡你的弹）。

    I-5 防线值守 —— 让"放置"有社交意义¶

    问题：原作离线收益是纯挂机，社交只有一张排行榜。 做法：把玩家的构筑变成可被挑战的资产。

    • 玩家在自家防线布 3 个防御工事（减速带 / 阻击墙 / 电栅），使用同一套养成数据
    • 生成防线快照（技能槽 + 工事 + 元素覆盖 + 战力 + 种子 + 快照哈希）
    • 其他玩家挑战该快照：客户端下载快照 → 用同款引擎本地模拟 → 回传结果与回放哈希 → 服务端做上限校验
    • ⚠️ 服务端不跑战斗引擎，因此不需要 Go/TS 双引擎同步（这正是 I-6 的价值）
    • 代价：服务端无法独立验证胜负 —— 后台对接近 100% 或 0% 的异常胜率做告警
    • 胜者窃取败者 10% 资源（可被偷上限保护）
    • 每日 3 次挑战机会（DefenseAttemptLimit = 3，核实一致）

    I-6 回放哈希验真 —— 公开可验证的公平¶

    问题：客户端结算的分数天然不可信，只能靠上限校验被动防守。 做法：让分数任何人可复现，作弊即自证。

    1. 战斗完全确定性：seed + 固定 20Hz 步进（TICK_HZ = 20 / TICK_MS = 50）
    2. 定点整数数学
    3. 每局记录关键事件序列（发射/命中/反应/击杀/漏怪/地形/选牌）
    4. replayHash = hex16(FNV1a64(前缀 ‖ 事件序列)) 存入 battle_records
    5. 验真入口：小程序「战绩验真」页 + 后台「验真」按钮 → 输入 battle_id， 用同种子本地重放，比对哈希
    6. 排行榜分数因此公开可复现；被质疑的分数可当场验证

    ⚠️ 与设计意图的差异：原设计写「固定 60Hz 步进」「replayHash = FNV64(事件序列)」。 实际是 20Hz，且哈希不只是事件序列 —— 前面还有一段前缀（关卡 id + 攻方 7 个系数 + 技能槽配置）。

    前缀不是冗余：若只哈希事件流，一局全漏怪（kills=0）时事件里没有任何伤害数值， 此时改攻击力、改元素系数都不改变哈希 —— 作弊者能"换一套属性"而不被验真发现。 前缀把这类改动纳入证伪范围。

    哈希锚点的通用规则（README 工程约束）： 凡是能改变战斗结果的输入，都必须落在哈希锚点里。 已有两个实例：槽位数（activeSlots 缺省必须是 4）与技能等级（烘进 baseDamage）。

    ⚠️ 关键技术约束（影响整个引擎）

    浮点运算在不同 JS 引擎/设备上结果可能不一致 → 哈希必然不稳定。 因此所有伤害、速度、坐标、生命值一律使用定点整数（统一 ×1000 取整， 禁止 Math.random，随机只走 PRNG）。渲染层在绘制前才转回浮点。 这条是硬约束，改动物理/伤害代码时必须遵守。

    防作弊的升级路径

    • 旧做法：上限校验（被动，信任服务端给上限）
    • 新做法：哈希可复现（主动，分数的正确性由任何人可独立证明）
    • 上限校验保留为第一道过滤，防止有人构造极端回放骗哈希

    I-7 构筑评分替代战力评分¶

    问题：原作把所有投入折算成一个"战力 9999"数字，引导玩家堆数值。 做法：主指标改为构筑评分（战力榜仍保留）。

    构筑评分 = 元素覆盖数(5)      × 12
         + 反应链完备度(7)    × 15
         + 专精树完成度(8系)  × 10
         + 装备契合度          × 12
         + 机制解锁深度        × 8

    （核实：domain.DefaultRatingWeights() 逐项一致）

    ⚠️ 公式里的「装备契合度」项目前恒为常量 —— 因为装备 element 字段从未被读取（见 §11 边界 1）。 它仍然占 12 分权重，所以构筑评分里有一项是「不随选择变化」的。 后台「玩家短板」页能看出这一项对所有玩家相同。

    • 首页用雷达图展示，短板高亮："你缺 冰 系 → 无法触发 超导 / 急速冻结"
    • 明确告诉玩家缺什么、为什么缺、怎么补，而不是告诉他"再升 5 级"

    双端一致性契约¶

    以下公式在 Go（服务端校验） 与 TS（客户端战斗） 各实现一次，必须同输入同输出：

    1. 元素反应伤害与抗性结算
    2. 构筑评分与战力计算
    3. 掉落表与掉落上限
    4. 分数规则（star_targets 服务端算、得分客户端算）
    5. 技能等级系数与费用
    6. 专精求值

    实现方式：server/cmd/vectors 从 Go 源码生成契约夹具到 server/testdata/：

    夹具 内容
    smoke_levels.json 全 100 关 + 敌人/技能/装备 + score_rules + skill_rules
    reaction_specs.json 7 条反应的完整规格
    level_seeds.json 100 关种子表
    formula_vectors.json 跨端公式向量

    客户端测试用 @vectors/* 别名直接读这些夹具， 断言 DEFAULT_SCORE_RULES / DEFAULT_SKILL_RULES 与 Go 侧逐字段一致。

    任一公式改动必须同时改两处并重跑 go -C server run ./cmd/vectors —— 改了关卡生成却没重生成夹具，存量战报的哈希会失配， 而行为测试在分布变化后往往仍成立（假绿）。 -check 子命令可在 CI 里验证夹具与源码是否同步。

    11. 已知边界（设计意图 vs 实现现状）¶

    完整的已知边界见 KNOWN_LIMITS.md，实测数据见 IMPLEMENTATION.md。 这里只列与本文档设计意图直接冲突的项。

    # 设计意图 实现现状 原因
    1 装备契合度：同系装备 → 反应伤害 +X%，不同系 → 直伤 +Y% 未做，且已决定不做 ① 元素系数是单一标量，改成每元素一个属核心伤害公式改动，会动重放哈希与反通胀不变式；② 反应表完全连接，凑 2 元素就点满，等于没有奖励。18 条装备描述已全部改成陈述真实数值（原先 10 条在骗玩家）
    2 装备支持升星/等级 level / star 两列无任何效果 补它需要一条实测出来的缩放曲线；凭空造一条比留着它更糟
    3 红线 1「不许有唯一最优解」，穷举验证 无该穷举测试 穷举「元素组合 × 专精方向」的测试成本高；现有的是 3 档位 × 100 关的 tier_impact.test.ts
    4 燃烧云「持续 6s 火区」、超导「持续 4s」 反应表只有 status_duration_ms（控制时长），无 DoT tick 定义 火区是地形机制（I-4），不是反应自带的持续伤害
    5 抽到重复技能「就地升格 1/2/3 阶」，高阶提高热量 无「阶」概念；抽到重复是固定幅度强化（+20% 伤害 / +1 层数 / +1 穿透） 「阶」会引入第二套成长曲线，与专精树 + 技能等级三重叠加，实测难度会失控
    6 「每章至少 3 关地形」 满足，但没有任何一关用 ≥2 种地形 generateTerrain 按章节的单一 terrain_kind 生成 1~3 个同种地形
    7 L-3 阵型预设（多套配置一键切换） 未实现 —
    8 「每 10 级 +1 专精点」 3 + FLOOR((level_exp + 50 + 本局击杀) / 1000) 基于经验与击杀，不是关卡等级
    9 破甲击退「削穿护甲 + 击退」 已实现（2026-10-09）：触发后 4s 内目标有效护甲 −150‰，并一次性击退 4px（定点 4000） 数值落在反应表 armor_shred_permille / knockback / status_duration_ms 三字段，客户端引擎消费；跨端契约 + armor_break.test.ts（9 例，含 2 处变异验证）钉住。注意：仅动能参与的构筑会进入这条新路径，默认构筑（fire/fire/fire/ice）的历史 100 关基线不受影响
