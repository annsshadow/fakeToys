## 1. 已修：严重

### F1 · 道具扣减路径恒 500（两条可达路径）

**探针实测**（修复前）：

```
AdminGrantCurrency(revive_token,-1) -> ERROR: new row for relation "user_tokens"
    violates check constraint "chk_user_tokens_nonneg" (SQLSTATE 23514)
Buy(price={mastery_reset:5})        -> 同上
```

**根因**：`grantToken` 只有一条 UPSERT，对 `delta` 正负不分。扣减时必然撞上
`CHECK (balance >= 0)` —— CHECK 是**语句级**判定，于是整笔事务带 23514 回滚，
而那个可读的「道具不足」分支永远执行不到。23514 不在 `isSettleRejection` 名单里，
`failErr` 兜底成 **500「服务内部错误」**。

**为什么「不可达」那句注释是错的**：`grantToken` 的注释写着「这条分支当前不可达
（pay 侧只接受货币）」。当时确实不可达，但第 148~151 轮接上了道具消费端点**并且**
`AdminUpdateShopItem` 的 `validWalletCurrency` **明确允许**把道具名写进商品 `price`。
于是「运营改个价就能踩到」。

**修法**：扣减改走条件 UPDATE（`balance >= $3 RETURNING`），与货币负数分支、
`spendToken` 完全同构；发放保留 UPSERT（道具稀疏，首次没有行）。

**守卫**：`service/security_audit_test.go` 6 例。其中
`TestGrantTokenPartialDebitWorks` 是**必需的**——我第一版把 `$3` 传成带符号的
delta（`balance + $3` 且条件 `balance >= $3`），数值上等价但**比较的一边符号相反**，
守卫条件直接失效。是这条测试抓到它的，而另外三条全绿。
变异实测（把条件改成 `balance >= $3 - 1`）→ 该条红，其余绿。

### F2 · 运营后台可被点击劫持

**证据**：全服务端 `X-Frame-Options` / `Content-Security-Policy` / `frame-ancestors`
grep **0 命中**；`admin/index.html` 也无（且 XFO 本就不能用 meta 设置）。

**攻击路径**：`evil.com` → `<iframe src="https://后台域名/#/admin/users">` → 盖透明遮罩，
把假按钮对齐到 iframe 内的真按钮。已登录运营点一下，请求就**真的**带上了他自己
localStorage 里的 `Authorization` 头发出去 —— 跨域读不到 token 也不影响，
**因为执行的是他自己页面里的代码**。结果落进审计日志，看起来与亲手操作完全一样。

后台所有写操作都是**单次点击即生效**（发币 / 封号 / 改价 / 再生成 100 关），
无二次确认弹窗。**这是本项目唯一一条「不需要任何服务端漏洞、只要运营点一下
就能在后台执行写操作」的路径。**

**修法**：全局中间件下发 `X-Frame-Options: DENY` + `CSP: default-src 'self'; frame-ancestors 'none'`
+ `X-Content-Type-Options: nosniff` + `Referrer-Policy: no-referrer`。

**守卫**：`httpapi/security_headers_test.go` 4 条，覆盖 200 / 4xx / OPTIONS 三类响应。
变异实测（摘掉 `app.Use(securityHeaders())`）→ 3 条同时红。

### F3 · 全站零速率限制

**证据**：`routes.go` 修前**没有任何** limiter 中间件。探针实测：
同一场战报重复验真 **200 次 → `replay_verifications` 写 200 行**
（该表既无唯一约束也无去重）。

四个放大器，各自独立成立：

| 端点 | 未认证？ | 放大倍数 | 后果 |
|---|---|---|---|
| `POST /admin/login` | 是 | **bcrypt cost 10 ≈ 50~100ms 纯 CPU** | 打满并发 → 正常运营**完全登不进后台**；同时无限次口令喷洒 |
| `POST /auth/guest` | 是 | 每次调用 7 行 INSERT | 批量造号把库撑爆，无任何计数 |
| `POST /battle/verify` | 否 | 每次 1 行，无幂等键 | 存储放大（实测 200 倍） |
| `POST /redeem` | 否 | — | 兑换码在线爆破 |

**修法**：按 IP 限未认证入口（登录 5/min、游客 60/min、刷新 60/min、兑换 5/min），
按登录身份限写放大路径（结算 60/min、验真 20/min、兑换 20/min）。
身份额度挡的是「注册 1000 个号、每个号慢慢打」——那是对付 IP 限流最直接的手段。

**额度为什么给得比「直觉上的严」宽松**：小程序玩家大量走运营商 NAT，
同一出口 IP 后面可能有成百上千真实用户。把每 IP 卡到个位数会**误伤整个运营商网段**，
而那比不限流更糟 —— 变成一个谁都说不清为什么的故障。

**守卫**：4 条，含「额度内首次请求不得被限流」与「公开读端点连打 80 次不得被限流」
两条反向断言（防止一个把限流挂得太宽的实现靠上面那条蒙混过关）。
变异实测（摘掉 `admin/login` 的 limiter）→ 该子用例红并报出「实际拒了 0 次」。

## 2. 已修：高

### F4 · 没有登出端点，refresh token 30 天无法切断

玩家手机丢了 / 令牌被 XSS 读走之后，服务端**没有任何办法**切断会话。
唯一会吊销 refresh token 的既有路径是「封禁玩家」，而那会把正常玩家一起踢下线 ——
用「封号」当「登出」，代价与意图完全不成比例。

**修法**：`POST /api/v1/me/logout` 吊销该用户全部 refresh token（幂等，返回吊销条数）；
客户端「我的」页加二次确认的退出按钮。**不限流** —— 登出的作用恰恰是「出事时立刻切断」。

**守卫**：Go 4 条（判据是「refresh 再也换不出 access token」这个**安全后果**，
不是「表被 UPDATE 了」这个**实现形状**；另有单独一条守住「只吊销自己的」）+ 端到端路由消费守卫。

### F5 · 后台审计日志的 IP 恒为空串

`Audit` 写死 `''`。于是**每一行**后台审计的 IP 列都是空的 —— 它看起来像
「这一列是可选的」，而它其实是「本项目从来没有过来源信息」。
F2 那条攻击路径的事后取证材料就只剩这一列。

**修法**：`Audit` 增加 `ip` 参数，全部 10 个调用点传 `c.IP()`。

**残留（如实标注）**：Fiber 未配置 `ProxyHeader`，所以反代之后 `c.IP()` 拿到的是
**反代**的地址。**生产部署必须配好反代的 `X-Forwarded-For` 透传**，
否则审计里记的是反代 IP。这里**没有**顺手打开 `EnableTrustedProxy` ——
在反代没配好之前打开它等于允许任何人用请求头伪造来源 IP，比记反代地址更糟。

## 3. 已修：中

### F6 · admin 前端的 401 处理是**虚构**的

`api/client.ts` 的 `!resp.ok` 分支无条件抛 `ApiError` 就结束了，**没有任何 401 检测**。
而 `router/index.ts` 的注释写着「令牌失效兜底：api 层抛 401 时把令牌清掉并送回登录页……
真正的 401 检测在 api/client 抛出」——**那条检测从来没有被实现过**。
`tests/router.test.ts` 的注释也建立在同一个虚构前提上。

后果：令牌过期（后台 access token 默认 2h）或管理员被停用时，路由守卫看到
`getToken()` 仍为真而放行 → 每个视图反复吃 401 → 运营被**永久卡在已登录的壳里**，
永远不会被提示重新认证，localStorage 里还长期留着一枚失效凭证。

**修法**：`client.ts` 增加 `handleUnauthorized()`，在**读 body 之前**判定
（一旦被后面的普通错误分支抛出去，就再也不会有代码回到这里）。
登录接口自己的 401 排除在外（「密码打错」不能变成「被踢回登录页」）。

**守卫**：TS 7 条，含四条**反向**断言 —— 500 / 403 / 网络错误 / 已在登录页时
**都不**清令牌。把「401」与「其它错误」混起来的后果是「后端重启一次，后台全体掉线」
与「readonly 被降权」被误报成「你掉线了」。

### F7 · miniapp 接口地址硬编码明文回环，且没有任何东西阻止它上生产

`const BASE_URL = 'http://127.0.0.1:8080/api/v1'`，模块级 `const`，无覆写点。
打出来的包只能连用户自己设备的回环地址（生产不可用），
而「唯一的修法」是回去改这个常量 —— 那条路径上**没有任何东西**阻止人保留 `http://`
只把地址换掉，于是最自然的修补就是「照抄，改域名」，令牌（refresh 30 天）**明文过网**。

**修法**：`VITE_API_BASE` 覆盖（与 admin 同一套机制）+ 启动断言：
非回环主机走明文 HTTP 时**直接抛错阻断**；局域网 IP 只警告（真机调试需要）。

### F8 · CORS 在生产环境仍发 `*`

`cors()` 原先**无条件**发 `Access-Control-Allow-Origin: *`，注释写着「生产应收紧」——
**而那只是一句注释**。

**诚实标注**：本项目**不用 cookie 存凭证**（纯 `Authorization: Bearer`，全仓库零 cookie、
零 `credentials:'include'`），所以 `*` **不构成**「带凭证的跨域读」——
把它报成严重漏洞是错的。真正的风险是「将来有人加了 cookie 登录」，那时 `*`
立刻变成全站沦陷，且没有任何东西会提醒。

**修法**：prod 默认**一条 CORS 头都不发**（等价只允许同源），
`CORS_ALLOW_ORIGINS` 配了白名单才回显具体来源 + `Vary: Origin`。
反向默认值的取舍写在 `config.go` 的字段注释里。

### F9 · 后台发币无金额上界

`amount` 来自 JSON 的 `int64`。`2^62` 本身写得进 BIGINT（实测成功），
但**再叠一次**就溢出 → PG `22003` → 不在 `isSettleRejection` 名单 → 500。
即一次手滑（大数粘贴）把整笔发放打成 500，而运营看到的不是「数额不合理」而是「服务端坏了」。

**修法**：上限 1e12（比任何真实运营发放大 6 个数量级，离 int64 溢出足够远）。

### F10 · miniapp 的类型检查一直是**空操作**，却报告成功 ← **验证过程中发现**

这一条不是读代码读出来的，是**验证时自己撞上并查出来的**。

**症状**：`pnpm type-check` 退出码 0、无任何输出 —— 看着完全正常。
但往 `src/api/client.ts` 里塞一行 `const x: number = 'not a number'` 后，
**它依然退出 0**，只在 stderr 留下一行：

```
Search string not found: "/supportedTSExtensions = .*(?=;)/"
```

**根因**：`vue-tsc` 锁在 `^2.0.22`。它依赖 **patch TypeScript 内部**
（volar 2 的 `proxyCreateProgram`），而 TS 已升到 5.9 ——
patch 目标找不到，volar 抛异常，vue-tsc 的顶层把它吞了并**正常退出**。

**后果**：miniapp 的**全部类型检查从未真正执行过** ——
本地 `pnpm type-check` 是空操作，CI 的同名步骤也是空操作，
README 验证状态表里「`vue-tsc`（admin + miniapp）0 error」那一行是**假绿**。

**为什么没被守卫抓到**：`toolchain_pin.test.ts` 里那条 peer 检查的兜底理由写着
「不满足 peer 时 vue-tsc 会在**运行时炸**，而不是安静地降级。真正的把关靠 CI 的 type-check」。
这条前提**已经不成立** —— 它不炸也不降级，它**安静地什么都不做**；
而 CI 的 type-check 又是同一个空操作，于是两层互相指着对方当证据。

**修法**：`vue-tsc` `^2.0.22` → `^2.2.12`（与 admin 同版本）。
升完立刻验证「注入类型错误 → 退出码 2」。

**守卫**（这是本条最关键的部分，版本本身挡不住 dependabot 第二次）：
CI 新增一步 —— 往 `src/api/` 写一个**故意有类型错误**的探针文件，
断言 `pnpm type-check` **必须失败**，然后删掉探针。
两端（admin + miniapp）都加。

> 判据落在「**注入错误后必须失败**」而不是「版本 >= 2.2」。
> 后者会在下一次 dependabot 升级后继续绿 —— 而版本从来不是这件事的判据。

**这条也是「为什么本轮反复强调变异验证」的一个实例**：
若只按惯例把 `vue-tsc --noEmit` 的退出码当结果，`0` 与「什么都没做」根本无法区分，
而本项目的 README 里恰好列着这个坑（「把『命令没报错』当成『命令生效了』」）。

## 4. 已核查、确认无问题

| 项 | 方法 | 结论 |
|---|---|---|
| SQL 注入 | 3 处 `fmt.Sprintf` 拼 SQL 全部逐行核对 + 全量参数化扫描 | 占位符是 `$N`，拼进去的**列名全部来自硬编码 switch**，值一律参数化 |

| CSRF | 全仓库 cookie / `credentials:` / `withCredentials` 扫描 | **0 命中**，纯 Bearer 头，CSRF 不适用 |
| JWT | `auth.go` 逐行 | HS256 + `subtle.ConstantTimeCompare`，`alg` 从**不**从 token 读取（无 `alg=none` 家族）；`Kind` 校验 + 每请求查 `status`（封禁即时生效） |
| 口令 | bcrypt `DefaultCost`；用户不存在与口令错返回**同一**错误 | 无用户名枚举 |
| 随机数 | 宝石 roll 全走 `crypto/rand`（进 `replay_hash` 前缀） | 无 `math/rand` |
| 路径遍历 / 命令注入 | 全量扫描文件与子进程调用 | 无 |
| 存档数据归属 | `getReplay` 剥掉 `settle_input` | 照抄别人的战报蓝本这条路已堵 |

**依赖审计未能完成**：`pnpm-lock.yaml` 下 `npm audit` 报 `ENOLOCK`，走 registry
漏洞接口时网络被拒。静态版本比对未见明显 EOL 或已知高危包，但**此项结论强度低于其他各条**，
建议在有网环境补跑 `pnpm audit`。

## 5. 未修：需要产品决策（**不是** bug，是架构取舍）

### R1 · 结算上限校验可被「恰好顶满」完全绕过 ← **本次审计最重要的结论**

**探针实测**（第 1 关，全字段顶到该关理论上界）：

```
win=true  stars=3  score=19902（== MaxScore，裁剪器未生效）  loot={coin:3770, keys:1, energy:5}
```

**没有任何服务端手段能区分这一局和一次真实的满分通关。**
防作弊是**上限校验**而不是**重算** —— 服务端刻意不跑战斗引擎，
那是 I-5「防线值守」与 I-6「回放验真」得以成立的前提。
而上限校验的性质是：**它挡住越界，挡不住恰好顶满**。

唯一的防御是 I-6 回放哈希，而它是**自愿**的：攻击者可以给自己报一个相同的 hash
让结果「一致」（`verification.go` 的文件头已诚实标注这一点）。
所以现实是：**一个持有合法 token 的玩家可以无限制造满分通关**。

唯一的节流阀是体力（`EnergyCost` 6 > `EnergyOnWin` 5，100 关里 0 关净回体力）：
新号 120 点体力可顶满约 20 局，之后每 6 分钟回 1 点。外加 `max_stage` 会跟着推进，
所以一次会话可以从第 0 关刷到第 100 关。

**为什么本轮不修**：真正的修法是服务端跑一遍战斗引擎（等于放弃「不跑引擎」的取舍），
或者移植 TS 引擎到 Go（约 2470 行 tick 循环，且会引入双引擎漂移）。
这是**产品决策**，不是工程判断 —— 擅自做会推翻项目最核心的两个创新点。

> **2026-10-14 更新**：产品已拍板「服务端跑引擎」+「不符即拒发奖励并记录」。
> 见 §5.1 的当前进度。下方两条旧理由仅保留作决策留痕。

**为什么本轮仍然要写它**：这一点此前只以散文形式记在 README「已知边界」第 3/11 条里。
散文的问题不是不准确，而是**读不到** —— 而这里的危害恰恰是「有人以为它被覆盖了」。
所以已写成三条可执行测试（`domain/settle_ceiling_characterization_test.go`）：

| 测试 | 钉住的事实 |
|---|---|

**为什么必须先有台账再接引擎**：漂移是发布之后立刻发生的，而它的症状是
结算返回 422 —— 客户端只显示「上报不可信」，玩家以为被作弊，运营看不出是我方算错了。
发现方式是玩家投诉。没有台账，R1 就等于把「可刷分」换成「全体玩家被误杀」。

**为什么 `mismatched_fields` 是数组而不是布尔**：一个「不符」信号无法区分
「玩家作弊」（要封号）与「引擎某段算错」（要回滚）—— 处置完全相反。
区分办法是按关卡/字段聚合：集中在少数关卡几乎必然是后者，均匀散布在单个号上是前者。

**熔断阈值**：10 分钟窗口内样本 ≥200 且不符率 >20‰（2%）。两条都要 ——
只看比率的话，低峰期任意一次误判就是 100% 不符率，每天必然降级一次。
诚实玩家的理论不符率是 0，所以任何非零值都值得看；2% 足以把系统性漂移与零星作弊分开。

**熔断不自动升档**：降级的代价是误判（手动开回来即可），升档的代价是**在故障未修好时恢复伤害**。

#### 这一步自己制造又改掉的两个问题

**① 缺省档位定成 `off` —— 会让新装部署出厂关闭反作弊校验。**

第一版的理由是「引擎会漂移，enforce 会误伤」。但那是**整局引擎**的性质，
而当时闸门实际管着的只有 `replay_skills`（S 段）—— 它**没有歧义**：
服务端从 DB 重算、客户端从 DB 上报，两边读同一份数据，中间没有第二个实现，
所以不符只可能是有人手改了上报值。

现有 `replay_skills_e2e_test.go` 立刻把它打红了（那条校验早就在生产上跑着）。
已改为缺省 `enforce`，并加 `TestRecomputeModeDefaultsToEnforce` 守住。
「先 shadow 观察」是**接引擎时**要主动做的动作，不是缺省状态。

**② 熔断与降级状态做成了闸门级全局 —— 会在攻击峰值时自动解除防护。**

第二版才把 scope 区分开（`ScopeEngine` / `ScopeSkills`）。若熔断对 S 段也生效：

```
作弊脚本开刷 → 不符率冲高 → 熔断触发 → 校验被降级
→ 防护恰好在攻击发生时失效，且诚实玩家的请求也一起被放过
```

降级状态最初存在闸门的单个字段上，于是**引擎侧的熔断会连带把 S 段降级** ——
一个「引擎算错了」的故障顺手关掉了反作弊校验。
这个 bug 是 `TestSkillsScopeNeverGoesThroughShadowEvenAfterEngineDemotion` 抓到的，
它写于实现之前，实现时确实写错了（第一次只跑了变异、没跑还原后的全量）。

现按 scope 分开存降级状态，并由两条守卫钉住
（`TestSkillsScopeIsNeverDemoted` / `TestSkillsScopeNeverGoesThroughShadowEvenAfterEngineDemotion`）。

> **教训**：「先写测试描述正确行为」如果没在实现之后跑一遍全量，等于没写。
> 变异验证证明的是「测试能抓住这个变异」，不证明「测试在当前实现上是绿的」。

### R3 · 游客凭证即永久凭证，且无轮换 —— **已在 2026-10-14 修复**

`guest_token` 是与口令同级的凭证（实测：给出同一 `guest_token` 再次登录即可拿到
该账号的 access + refresh token）。它 24 字节随机，不可猜 —— 但：

- 后台的玩家搜索条件**就包含 `guest_token`**（`AdminListUsers` 的 LIKE），
  所以后台被点（F2）或 DB 泄露 ⇒ 批量导出所有玩家凭证；
- **没有轮换机制**。F4 的登出只吊销 refresh token，`guest_token` 依然能换出新会话。

**修法**（提交 `8a23628d7`）：

1. 登出**轮换** `guest_token`，与吊销 refresh token **同事务** ——
   两者必须同生共死：只吊销前者则旧凭证仍能换出新会话，
   只轮换前者则被盗的 refresh token 还活着。
   `UNIQUE` 撞车概率极低但不是零，撞了重试 5 次而不是当不可能。
2. 后台玩家搜索**不再打 `guest_token`**。凭证可检索意味着
   「后台账号被盗 ⇒ 批量导出玩家凭证」。运营用昵称/user_id 就够了。
   这是**功能删减**，所以配了双向守卫（凭证搜不到 + 昵称仍能搜，防删过头）。
3. 客户端登出时落盘新凭证。

**一个必须写下来的形态**：凭证轮换后，拿旧凭证来的人**不会看到任何异常** ——
`GuestLogin` 对未知凭证的语义是「建一个新号」，所以它安静地返回一个**空账号**。
这正是客户端必须立刻存下新凭证的原因：不存的话受害者自己也走这条路，
进度凭空消失且毫无报错。那比「凭证没轮换」严重得多 ——
凭证问题静默，丢进度会被立刻发现并当成无法解释的 bug。

## 7. 部署前置（本轮引入的义务）

1. **反代必须透传 `X-Forwarded-For`**，否则审计里的 IP 是反代地址（F5 的残留）。
2. **多副本部署必须把限流换成共享计数器**（Redis 等）。当前是**进程内**计数，
   实际额度 = 配置值 × 副本数；单实例部署下是准确的。
3. **跨域部署需显式配 `CORS_ALLOW_ORIGINS`**（后台与 H5 不同域名时）。
   prod 未配置 = 只允许同源，这是刻意的默认。
4. `miniapp` 打包前设 `VITE_API_BASE`，否则真机连不上；公网域名必须 https。

### 8.4 早一轮：共享库污染（2026-10-13）

`TestGrantTokenNegativeDeltaNeverAbortsTransaction`（F1 的守卫之一）把共享库里
