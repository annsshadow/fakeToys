## 4. 覆盖攻坚中发现并修复的真缺陷

1. **兑换码创建必然 500**（server）：`redeem_codes.id` 无默认值，`AdminCreateRedeemCode`
   的 INSERT 不供 id → not-null violation。修复：迁移 `00009_redeem_code_identity.sql`
   改列为 IDENTITY + seeder 对齐序列（`setval`）。特征化断言已翻转为验证成功行为。
2. **`PUT /me/loadout` 必然 500**（server）：审计 `detail` 写非法 JSON + `admin_id=0`
   撞外键。修为合法 JSON + `admin_id=NULL`。
3. **bag 槽位错位**（miniapp）：模板 1 基 v-for 传参、`skillOf` 按 0 基读数组，
   「已装备槽后跟空槽」的存档渲染即崩。修为 `skillOf(i-1)`。
4. **battle 页响应式断裂**（miniapp）：引擎 raw mutation 不触发 ref 响应式，
   HUD 永不更新、选牌界面永不出现（软锁）。修为 `step()` 后 `triggerRef(engine)`。
5. **`reachableReactions` 构筑评分虚高**（miniapp，dead code）：未把 incoming 元素
   限定在构筑内，单元素也被算出反应。修为 `if(!elements.has(incoming)) continue`，
   与文档契约「反应需先后两种元素都能打出」一致。

## 7. ✅ 已解决：`internal/service` 的 `skill_recipes` 23505（第 150 轮引入并修复）

### 症状

```
scratch 库种子失败：insert recipe 32: ERROR: duplicate key value violates
unique constraint "skill_recipes_pkey" (SQLSTATE 23505)
```

23505 = PostgreSQL 唯一约束冲突。一次完整跑测里 **129 次建 scratch 库，
101 次在播种这一步失败**；前 ~28 次正常，之后全部失败 —— 随进度劣化。

### 根因

`internal/service/config_verify_test.go` 的 `TestConfigVersionIsStableAndContentDerived`
用「逐类内容各改一处，哈希必须变」来验证内容哈希覆盖了所有字段：

```go
base := func() GameConfig { return zeroed }          // ← 浅拷贝
...
{"recipes", func(g *GameConfig) { g.Recipes[0].Output += 1 }},
```

`GameConfig` 的切片字段在 `LoadGameConfig` 里是**直接别名包级内容表**的
（`Recipes: domain.SeedRecipes`）。浅拷贝让 `g.Recipes[0]`
与 `domain.SeedRecipes[0]` 指向同一个元素，于是这次「为了验证哈希而做的改动」
**把进程全局内容表改掉了**：`SeedRecipes[0].Output` 从 31 变成 **32**。

此后数组里有两个 `Output=32`。`seeder.seedSkills` 用
`id = r.Output*10` 当主键，于是两条配方都算出 `id=320` → 23505。

同一张表里的 14 条 mutation 全都有这个问题（`Enemies[0].HP`、`Gems[0].Descr`、
`Skins[0].Descr`、`Mastery[0].Family`、`Reactions[0].BaseCoef`、`Chapters[0].Name`
都被原地改写）。只是 recipes 恰好是唯一有主键的，于是只有它炸。

### 为什么排查这么久

症状与病因隔了整整一层抽象，且**看起来不是数据库问题**：

| 假设 | 实测结果 |
|---|---|
| 残留孤儿库压垮 PG | 跑前清空所有 `laiyipao*_test*`，仍复现 |
| 库名碰撞（`UnixNano()%1e9` 每秒重复） | 129 个库名全部唯一 |
| 建出来的库不干净 | 播种前逐个查 `count(*) FROM skill_recipes`，129 个全是 0 |
| 连错库 | `SELECT current_database()` 与请求的 DSN 逐个一致 |
| `t.Parallel()` 并发 | 包内零命中；`-parallel 1` 仍复现 |
| 迁移里塞了种子 | 迁移只往 `user_tasks` 插数据 |
| 内容表被谁改写 | 全仓库无 append/赋值 —— **直到把 `domain.SeedRecipes` 的运行期值也打出来** |

最后那条是关键。源文件里 18 条配方 `Output` 是 31..48、无重复（逐条核过），
但诊断日志打出 `SeedRecipes 条数=18 重复=[Output=32 出现 2 次]`
—— **源文件与运行期值不一致**，说明它被就地改写过。
顺着「谁能写它」查到 `config_verify_test.go:154`。

### 修法

1. **`base()` 改为 JSON round-trip 深拷贝**。`GameConfig` 本来就要被 marshal 下发，
   所以这是最贴合上下文的做法，且新增字段自动覆盖，不用手工维护拷贝列表。
2. **加一条「全局内容表没被动过」的收尾断言**。
   这条是关键：深拷贝失效的症状远在几百行之外（上百个用例红），
   而这里当场红。把「测试污染全局状态」从地雷变成红线。
3. **在 `internal/domain` 加三条配方完整性守卫**（`recipes_integrity_test.go`）：
   `Output` 唯一、按播种公式算出的 `id` 唯一、`(a,b)` 唯一。
   第三条防的是另一种静默故障 —— 重复的 `(a,b)` 会让两条配方互相
   `ON CONFLICT DO UPDATE`，结果配方少一条、产物被悄悄换掉，且**不报任何错**。

### 连带修掉的两个问题

**① `scratchdb` 的 DROP 从来没执行成功。** 新加的失败日志把它喊了出来：
`[scratchdb] 删除 ... 失败：closed pool`。原因是 `DSN()` 里的
`defer p.Close()` 在函数返回时就关了池，而 `t.Cleanup` 是**之后**才跑的。
清理逻辑「看起来写了」、Sweep 也在跑，只是每个库都悄悄留成孤儿 ——
正是这个包要根治的症状。修法：cleanup 里自己开池。
修完残留从 15–278 降到 **0**。

**② `TestLeaderboardKinds` 是条「跑得越多越红」的测试。** 它的断言是
「三个榜的前 50 里必须有我」，而共享测试库里前 50 被历次跑测留下的
几千个用户瓜分 —— 库越脏越容易掉出去（实测 stage 榜已稳定失败）。
该用例自己的注释早就写着「依赖『表还不够脏』的断言不是断言，是运气」，
第 82/83 轮为此改过两次口径，但只要还在共享库里就只是**更难的运气游戏**。
改用一次性库根治。

### 教训

这三条（浅拷贝污染全局、cleanup 用已关闭的池、断言依赖共享库的脏度）
**都是同一类**：症状出现在离病因很远、且看起来毫不相干的地方。
第 ① 条尤其值得记住 —— 它是**这一轮我自己引入**的，
而且症状（孤儿库残留）与它的直接后果（DROP 静默失败）之间隔了
「清理钩子」这一层，不加失败日志就只会看到「残留又回来了」。
## 8. 「服务端有扣减逻辑」不等于「玩家能用」：道具闭环的三段（第 151 轮）

### 8.1 问题

第 148–150 轮先后把三种道具的消费端点接上了：

| 道具 | 消费端点 | 效果 |
|---|---|---|
| `mastery_reset` | `POST /mastery/reset` | 清空 `user_mastery_nodes` |
| `revive_token` | `StartBattle`（开战时） | 扣 1 枚，本关 `base_hp` ×1500‰ |

每一条都有测试、都通过了、三口径守卫里的 `PENDING_TOKENS` 变成空表。
按当时的汇报口径，C 口径 100%。

**那是高估。** 三种道具的**唯一发放途径是商城**（签到、任务、成就、兑换码都不发它们），
而 miniapp **没有商城页** —— `fetchShop` / `buyItem` 两个 API 函数
从写下来那天起就没有任何页面调用方。

于是玩家的实际体验是：首页菜单里点不到商城，服务端扣减逻辑齐全，
道具数量永远是 0。**代码完成度 100%，机制完成度 0。**

### 8.2 为什么三段里最容易漏掉第三段

前两段都有明确的完成信号：端点能通、测试能红绿。
第三段「玩家从哪个界面拿到它」没有守卫 —— 没有任何测试会问这个问题，
因为它跨越了「服务端 OK」这条线，而那条线恰好是此前所有汇报的边界。

补 `gem_wash_token` 时本来还会更严重：它的前置还包括
① `gem_affixes` 灌种子（此前表建好了却是 **0 行**）
② 宝石有获取途径。两件都做完才有洗练可洗。

### 8.4 定价：真机跑出来才发现定错了

`gem_wash_token` 初版定 120,000 金币。真机 E2E 时账号只有 52,000，买不了。

回头算：`domain/battle.go` 的金币产出是 `CoinBase 200 + 每星 150 + 每击杀 20`，
三星十杀约 850/局 —— 120,000 要打 **140 局**，
而同表最便宜的消耗品「续战令」只要 5,000。两个消耗品差 24 倍，
定的人自己都觉得不对劲。

「怕玩家买灰宝石反复洗」那个理由也站不住：宝石 60 钻石 ≈ 一个金币箱的量，
洗一次就要再赚一个金币箱，刷不出金色。

改为 30,000（约 35 局，续战令的 6 倍）。
**教训：平衡数值不该只靠「参照同表」推出来，必须在真机上跑一次购买链路。**
