## 4. 覆盖攻坚中发现并修复的真缺陷

1. **兑换码创建必然 500**（server）：`redeem_codes.id` 无默认值，`AdminCreateRedeemCode`
   的 INSERT 不供 id → not-null violation。修复：迁移 `00009_redeem_code_identity.sql`
   改列为 IDENTITY + seeder 对齐序列（`setval`）。特征化断言已翻转为验证成功行为。
2. **`PUT /me/loadout` 必然 500**（server）：审计 `detail` 写非法 JSON + `admin_id=0`
   撞外键。修为合法 JSON + `admin_id=NULL`。
3. **bag 槽位错位**（miniapp）：模板 1 基 v-for 传参、`skillOf` 按 0 基读数组，
   「已装备槽后跟空槽」的存档渲染即崩。修为 `skillOf(i-1)`。
4. **battle 页响应式断裂**（miniapp）：引擎 raw mutation 不触发 ref 响应式，
   HUD 永不更新、选牌界面永不出现（软锁）。修为 `step()` 后 `triggerRef(engine)`。
5. **`reachableReactions` 构筑评分虚高**（miniapp，dead code）：未把 incoming 元素
   限定在构筑内，单元素也被算出反应。修为 `if(!elements.has(incoming)) continue`，
   与文档契约「反应需先后两种元素都能打出」一致。

> ⚠️ **原记录到此为止的部分，在第 150 轮被证明是「只清不防」。**
> 本轮实测再次累积到 **406 个**残留，随后：

> （确实没权限才 Skip，其余 Fatal）。三条结构性守卫钉住复发：

## 7. ⚠️ 未解决：`internal/service` 大量用例因 `skill_recipes` 23505 失败（第 150 轮发现，根因未定位）

### 症状

```
scratch 库种子失败：insert recipe 32: ERROR: duplicate key value violates
unique constraint "skill_recipes_pkey" (SQLSTATE 23505)
```

23505 = PostgreSQL 唯一约束冲突。字面意思是：往 `skill_recipes` 插入
`id = 32*10 = 320` 那一行时，主键 320 已存在。

一次完整跑测里 **129 次建 scratch 库，其中 101 次在播种这一步失败**；
前 ~28 次正常，之后全部失败 —— 是**随进度劣化**，不是随机。

### 已排除的解释（每条都实测过，不是推测）

| 假设 | 实测结果 |
|---|---|
| 残留孤儿库压垮 PG | 跑前清空所有 `laiyipao*_test*`，仍复现 |
| 库名碰撞（`UnixNano()%1e9` 每秒重复） | 129 个库名**全部唯一**，无一组重复 |
| 建出来的库不干净 | 播种前逐个查 `SELECT count(*) FROM skill_recipes`，**129 个全是 0** |
| 连错库 | `SELECT current_database()` 与请求的 DSN **逐个一致** |
| `t.Parallel()` 并发 | 包内 `grep t.Parallel()` **零命中**；`-parallel 1` 仍复现 |
| 测试改坏了包级内容表 | `SeedRecipes` 全仓库无任何写入/append；`service` 包无 `init()` |
| 迁移里塞了种子 | `migrations/*.sql` 只有 `00013` 往 `user_tasks` 插数据，不碰 `skill_recipes` |
| 本次改动引入 | **把 `laiyipao/server` 全部 `git stash` 后仍然复现** |

### 关键矛盾

`internal/seeder` 做**完全相同**的事（建一次性库 → 迁移到 13 → `seeder.Run`），
**全部通过**（16s）。两个包的 `openScratch` 代码逐行等价。

也就是说：空表 + 一次 `seeder.Run` 必然撞主键，而 seeder 包证明它不会。
「表是空的（刚查过）却插入时主键已存在」在单事务下不可能成立 ——
除非同库上还有**另一个**并发事务在插同一批行，但单事务内的插入对他人不可见。

**结论：机制已排除到「必须是某个尚未识别的并发/外部写入者」，但那个写入者
至今没找到。** 叠加第 6 节说的孤儿库问题，这条线索可能相关，也可能只是
时间上的巧合 —— 没有证据，不下判断。

### 下一步建议（未做，需单开一轮）

1. 在 `seeder.Run` 的 recipe 循环里临时加一句「冲突时把 `SELECT id,
   output_skill_id, a_skill_id, b_skill_id FROM skill_recipes` 全表打出来」。
   表里有 320 就实锤外部写入者；表里没有就说明报错与这张表无关。

   任何一次「同一 (a,b) 对应不同 Output」的变更都会静默改写别人的行。
