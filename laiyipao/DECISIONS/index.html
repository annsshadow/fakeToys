    来一炮 · 待拍板决策单¶

    2026-10-20 起。 背景见 KNOWN_LIMITS.md： 29 条已知边界里，真正“工程上就能做”的只有 5 条（已排进实施）， 11 条卡在产品决策 —— 缺一条必答项就做不成（与第 29 条当初同型）。

    本单把这 5 条集中列出：每条给出必答问题、我的推荐、代价估算、 不做的后果。逐条批注即可，批完按序开工。

    D1 · 关卡表是不是玩家侧的关卡来源（KNOWN_LIMITS 第 23 条）¶

    背景：PUT /admin/levels/:id 落库成功、后台界面显示改后值， 但玩家侧走的是纯函数 domain.GenerateLevel（从不查库）—— 运营的关卡调参对玩家完全不生效，而后台完全看不出来。

    # 必答问题 选项
    1 谁是权威？ (a) levels 表 / (b) 生成器
    2 若 (b)：后台怎么表达？ 改文案「记录在案，不影响线上」/ 加字段 / 不动
    3 若 (a)：缓存与失效怎么做？ 无缓存直查 / 进程内缓存 + 失效 / 版本号协商
    4 存量战报怎么办？ 重放哈希锚点是否受关卡表影响

    我的推荐：(b) + 改文案。理由：(a) 要缓存与失效机制，且与 LoadGameConfig「绝不失败」的签名约定冲突；关卡生成是确定性纯函数， 本就是 I-6 可重放的地基，改成查库会把它变成数据依赖。 (b) 的成本是改一句后台文案，收益是“界面不再说谎”。 第 4 问在 (b) 下自动为「不受影响」。

    代价：改文案 ≈ 半天（含 e2e 断言）；(a) ≈ 2–3 周 + 缓存一致性风险。 不做的后果：运营改关卡看不到任何效果，也不知道没生效 —— 属「静默失效」。

    D2 · 剩下两条反应要不要做特殊机制（KNOWN_LIMITS 第 19 条）¶

    背景：7 条反应里剩 2 条只有反应伤害 —— burn_cloud 的火区、corrosion_spread 的层数传播。 它们的 base_coef 虽有区分度，机制上仍是同一个东西。

    # 必答问题 选项
    1 先做哪条？ corrosion_spread（层数传播） / burn_cloud（火区） / 两条都做 / 都不做
    2 传播要不要再触发反应？ 否（安全） / 是（递归风险）
    3 机制伤害计不计入分数？ 计入 / 不计入
    4 服务端要不要一并重算？ 要（否则 I-6 失配） / 不要（只客户端）
    5 火区若是持续伤害，存在哪？ 地形实体（走 terrainTick 那套） / 敌人身上的 DoT 标记

    我的推荐：先做 corrosion_spread（层数传播），火区留后。理由： 层数传播无新概念（复用 applyElement 的层数语义）， 第 2 问取「否」、第 3 问取「计入」、第 4 问取「要」—— 三问都取保守值时，机制不碰重放锚点之外的东西。 火区涉及新的持续状态实体（第 5 问），成本与风险都高一档。

    代价：corrosion_spread ≈ 3–5 天（引擎 + Go 镜像 + 契约 + 守卫）； 火区 ≈ 1–2 周。不做的后果：7 条反应里 2 条同质， 「放大反应」类属性对玩家价值有限。

    D3 · 通关速度要不要进分数（KNOWN_LIMITS 第 5 条）¶

    背景：速率裁剪锚点 ScoreFullAtSec = 60s，而实际通关 146–594s， 该裁剪从不生效。原文说「总血量 → 通关时长相关性很弱」，于是搁置。

    # 必答问题 选项
    1 速率以什么为基准？ 固定秒数 / 按关卡的理论清关时长 / 按玩家历史
    2 权重多少？ 仅封顶（不加分） / 参与星级门槛 / 参与分数
    3 理论时长由谁算？ 关卡生成器推导 / 离线跑一次模拟 / 人工标定表

    我的推荐：按关卡的理论清关时长（第 1 问选第二个）， 基准由关卡生成器推导（第 3 问选第一个）—— 关卡内容（波次、怪数、血量、移动速度）已知，理论时长可推导； 只参与封顶不加分（第 2 问选第一个），避免动分数公式与重放锚点。 原文否证的是「血量相关」，不是「理论时长」——这是一条原文没提到的路径。

    代价：≈ 1 周（推导 + 标定 + 平衡回归）。不做的后果： 慢速通关与快速通关同分，「打得快」没有意义（现状）。

    D4 · 防线挑战的胜负要不要服务端裁决（KNOWN_LIMITS 第 3 条）¶

    背景：服务端不跑战斗引擎，挑战在挑战者设备本地模拟后上报， 服务端只校验次数/护盾/资源守恒 —— 无法独立验证胜负， 后台只能对接近 100% 或 0% 的胜率告警。

    # 必答问题 选项
    1 裁决到哪一层？ 不做 / 只校验构筑（重放 S 段） / 服务端完整跑引擎
    2 若跑引擎：防作弊的收益？ 胜负不可造假（强） / 仍可改上报数值（弱）
    3 成本与响应时间？ 服务端跑 tick 循环（秒级） / 异步复核

    我的推荐：中间档（第 1 问选第二个）——把防线挑战也纳入 replay_hash 的 S 段校验（与结算同一条校验链）， 抓得住「构筑造假」（最常见的作弊面），仍抓不住「胜负本身」， 但把 D4 的风险从「完全没有校验」降到「校验了一半」。 服务端完整跑引擎代价最大（等于放弃“不跑引擎”的核心取舍），不推荐。

    代价：中间档 ≈ 3–5 天；完整裁决 ≈ 3 周 + 响应时间风险。 不做的后果：胜率 100% 的账号只能靠告警事后发现。

    D5 · 要不要给关卡配多种地形（KNOWN_LIMITS 第 15 条尾）¶

    背景：generateTerrain 产出的地形全是同一个 kind，100 关里 75 关没有地形， terrain_used 的合法长度最多是 1 —— 后台若按它统计「地形触发率」，分辨率只有 0/1。

    # 必答问题 选项
    1 一关最多几种地形？ 1（现状）/ 2 / 3
    2 多地形如何共存？ 同时存在 / 按波次轮换 / 按区域分区
    3 多种地形会不会叠加失控？ 单地形效果仍生效、叠加另算

    我的推荐：先做 2 种、按波次轮换（第 1 问选第二个，第 2 问选第二个）—— 轮换让「同一关内多种地形」变成可能，同时保持「同一时刻只有一种地形在作用」， 不引入叠加语义（第 3 问自动为「不叠加」）。

    代价：≈ 1 周（生成器 + 引擎 + 契约 + 平衡基线重测）。 不做的后果：地形机制在 100 关里只有 25 关用得上，且每关只有一种， 机制深度受限。
