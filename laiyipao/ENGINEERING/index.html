    来一炮 · 关键工程约束¶

    2026-10-20 自 laiyipao/README.md 拆出。 定位：决定了整个架构的 19 条约束 —— 每一条都对应一个真实发生过的故障， 改动时必须同时满足。新增一条的判据：它是否对应一个真实发生过、 且没被已有约束覆盖的故障。

    引用约定：本仓代码注释与测试里的「README 工程约束 N」「README 约束 N」 即本文的第 N 条（编号与原 README 完全一致，未重排）； laiyipao/README.md 的「关键工程约束」小节是本文的转发锚。 相关文档：实现状态与实测数据见 IMPLEMENTATION.md， 未做事项见 KNOWN_LIMITS.md。

    关键工程约束¶

    这些决定了整个架构，写在这里是因为改动时必须同时满足。

    这 14 条不是一次想出来的，而是每一轮踩坑之后补上的 —— 所以上面那几条都是别人（或我自己）踩出来的，不是设计时就想到的。 新增一条的判据：它是否对应一个真实发生过、且没被已有约束覆盖的故障。

    1. 反通胀是结构性保证，不是数值调优¶

    反应伤害 = (元素侧 + 攻击侧) × (1 - 抗性)

攻击侧 = min(D × k × 阶,  w × 元素侧 / ((1 - w) × M)) × M     w ≤ 300‰
                                                    ↑
                                          M = 反应倍率（专精/装备/特斯拉栅格）

    攻击侧 / (元素侧 + 攻击侧) ≤ w 是恒等式，任意输入下都成立。因此数值膨胀无法绕过搭配收益 —— 这是设计能被信任的原因。

    ⚠️ M 必须出现在上限的分母里，这一点很容易写错。 推导：约束的对象是乘完 M 之后的量 A·M：

    A·M/(E + A·M) ≤ w  ⟺  A·M(1-w) ≤ wE  ⟺  A ≤ wE/((1-w)·M)

    只把 M 乘进伤害而不收紧上限，等于给"堆一个专精节点"开了一扇绕过反通胀保证的后门 —— 那正是这套设计的根基。anti_inflation.test.ts 遍历 7 条反应链 × 3 档层数 × 4 档攻击力 × 9 档倍率（含 0‰ 与 100 万‰）验证不变式；变异测试确认去掉这个除法会让 5 条立刻变红。

    M 的实际语义（写下来免得日后误判为 bug）：

    情形 攻击侧 倍率效果
    D·k·阶 < 上限 D·k·阶 × M 随 M 线性增长
    D·k·阶 ≥ 上限 w·元素侧/(1-w) 与 M 无关（上限收紧恰好抵消）

    也就是说：倍率只在攻击侧尚未被 I-1 红线顶满时才生效。 玩家在数值面板上看到"倍率提升 8 倍但伤害没变"，那是攻击侧已顶到红线，不是缺陷。

    M = 1000‰（无加成）时 wE/((1-w)×1000) × 1000 = wE/(1-w)，与旧式逐位相同 —— 所以这个乘区的接入是零风险的：既有契约向量、既有平衡数据全部保持有效， Go 一致性测试全绿即为证明。

    2. 定点整数 + 确定性 PRNG¶

    • 伤害/速度/坐标/血量一律 bigint × 1000 定点整数
    • 随机只走 lcg.ts（PCG-XSH-RR），禁用 Math.random
    • 定步长 50ms（20Hz）推进，渲染层独立插值
    • 抗性列是千分比 -500..500（不是百分比）

    浮点会带来跨引擎差异 → 同一场战斗算出不同哈希 → I-6 直接失效。

    3. 攻方属性必须由服务端下发¶

    回放哈希由 关卡 + 种子 + 攻方属性 + 技能槽 四者共同决定。四者缺一，重放方就算不出同一个哈希 —— 验真会把所有正常对局都判成伪造。

    因此 /api/v1/me 与 /battle/token 的 build 里带 attacker 字段，客户端只读不推算；技能槽位存在 user_skill_slots 表，通过 /me/loadout 读写。

    ⚠️ 这条曾被违反：客户端用 100 + maxStage*200 自己猜攻击力，服务端无从知晓，双方哈希必然不同 —— I-6 形同虚设。已改为服务端权威下发（internal/service/attacker.go）。

    4. 跨端字段名必须显式约定 —— 且要双向核对¶

    Go struct 漏写 json tag 会按字段名原文（PascalCase）序列化。客户端类型用 snake_case 时两边对不上，每个字段都是 undefined —— 且不报任何错。

    同类的第二个形态是「同一个量在两端各写一份常量」： star_targets 由 Go 按 scorePerDamageUnit / scoreOnKillNormal / scoreOnKillBoss 算出， 而实际得分由 TS 引擎用自己那份 /100、500/5000 累加 —— 一度有 5 处副本。 漂移之后玩家拿到的星级与实际表现对不上，而两端各自都自洽，没有任何行为测试会发现。

    所以常量也要可核对，不能只靠约定：

    端 来源
    Go 定义 domain.DefaultScoreRules()（唯一定义处）
    Go 下发 /config 的 score_rules
    契约夹具 smoke_levels.json 的 score_rules
    客户端 game/score.ts 的 DEFAULT_SCORE_RULES，由 score.test.ts 断言与服务端逐位一致

    ⚠️ 写这条时还踩了一个更基础的坑：那些断言最初写在 score.ts 里（与实现同文件）， 而 vitest 的 include 只收集 *.test.ts 后缀 —— 它们从来没被执行过。 一段不运行的测试比没有测试更危险：它看起来在守着某样东西。 发现方式是单独跑 vitest run src/game/score.ts 时报 No test files found。

    字段名这一条踩过两次，方向相反：

    位置 声明 实际下发 后果
    domain.RatingWeights 无 tag → ElementCoverage ElementCoverage 两端"一致"所以测试全绿，但与同响应里的 BuildRating（snake_case）风格割裂
    miniapp/api/client.ts 的 chapters ch.ID / ch.Name id / name 关卡页章节标签全空白、点击无效、永远不高亮
    admin/WikiView.vue 的 reactions row.BaseCoef / row.AoeRadius base_coef / aoe_radius 文档站反应表整列为空
    admin/SkillsView.vue 的配方 r.A / r.Output a / output 每条配方渲染成 #undefined + #undefined → #undefined（Tundefined）

    同一份 client.ts 里 levels / enemies / skills 是对的，只有 recipes / reactions / chapters / rating_weights 错 —— 说明这些字段是分批写的，没人做过整体核对。

    双向核对的两个方向：

    1. Go → 客户端：所有下发结构体必须带 json:"snake_case" tag，嵌套的也算（RatingWeights 就曾漏掉）。加新 struct 时不要漏。
    2. 客户端 → Go：TS 接口的字段名必须逐字对齐服务端的 tag。注意同名不同义 —— build.skill_ids 装的是元素名（历史误命名，现已同时下发正确名 elements 并保留旧名作兼容），而 /me/loadout 的 skill_ids 是真的技能 id 数组。代码内部自洽，但按名字推断语义的消费者会踩坑。

    发现手段：拿真实 seed 数据跑一遍，看渲染出来是不是空。本轮关卡页章节空白就是这样发现的 —— 目视检查比读类型定义可靠。

    5. 每一道防作弊校验都要有对应的负向测试¶

    结算校验的价值全在"拒绝"分支上。而拒绝分支的特征是不报任何错，只是默默不给钱 —— 没有专门的负向测试，下一次重构就会把它删掉，而且看起来一切正常。

    本轮修的三处都属于这一类，且其中一处是上一轮修复自己留下的洞：

    漏洞 触发 后果
    duration_ms=0 让得分裁剪整段被跳过 上报 duration_ms:0 + result:"lose" 分数无上限 → 星级恒 3 → 单局金币触顶 60000（正常约 1650）
    reactions 无上界 上报 reactions:1e9 一次顶满全部反应类任务与成就
    兑换码 used_count 靠 CHECK 约束兜底 并发兑换 客户端收到 SQLSTATE 23514 而非业务错误；约束一旦被迁移就是无限超发

    第三条尤其值得记：UPDATE ... SET used_count = used_count + 1 WHERE id = $1 看着无害，资源上确实没超发（CHECK 挡住了），但那是"恰好"有约束，不是并发设计。正确写法是条件 UPDATE + 检查 RowsAffected，与 ClaimTask 的 claimed_at IS NULL、Buy 的 FOR UPDATE 同一个模式。

    还有一个更隐蔽的形态：约束了被保护量却没约束控制量。给 reactions 加了 reactions <= shots * 8 的上界，但 shots 当时无上界 —— 于是上报 shots:1.25e8 时上界正好变成 1e9，恰好放行它本该挡掉的 1e9。约束链上每一环都必须有界。

    规律：加任何一条上界校验时，同时问「这个上界自己由什么界定，那个东西有界吗」。

    6. 双端公式一致性是可执行检查¶

    server/testdata/formula_vectors.json 是唯一事实源：

    端 测试
    Go internal/domain/consistency_test.go
    TS src/game/consistency.test.ts

    两端读同一个 JSON、断言同样的数字。任一端单方面改公式，另一端立刻红。

    ⚠️ 该文件里的 64 位值用字符串承载。JSON number 超过 2^53 后 JS 解析即失精，6917529027818027904 会被解析成 ...8032，断言会悄悄通过。同理，/api/v1/battle/token 与 /battle/{id}/replay 的 seed 也是字符串下发。

    但跨端一致 ≠ 两端都对。本轮就有两处「两端同时漏掉同一个东西」，13 个向量全绿：

    • reactionMultPermille 在 resolveHit 里根本没有乘区（专精树 6 个节点白给）
    • applyArmor 因为向量里 armor_permille 恒为 0，两端都从未执行过第二行

    所以一致性测试的定位是「防漂移」，不是「防错误」。后者要靠各自的单元测试 + 真实内容表的冒烟测试。

    7. 动数值之前先建立可比较的基准¶

    任何涉及数值的改动（伤害公式、关卡生成、敌人血量、星级门槛）前后都跑一遍 miniapp/src/game/balance.probe.test.ts，拿到的是可比数字而不是"感觉变强了"。

    本轮三次误判全部源于缺这个：

    我当时的判断 实际数据 缺的是什么
    「热量上限压制了攻击力收益」 单位误读，attack 是千分比 没先确认量纲
    「夹具太弱」 夹具温和度掩盖了粗糙缺陷 没有真实内容表
    「血量是瓶颈」 瓶颈是弹丸速度 —— 18 秒飞行时间，85% 输出浪费 没测过命中率

    第三条尤其值得记：我在探针里把 hpMul 从 1 扫到 8，结论一次比一次反直觉 （hp×2 时击杀数几乎不变 → 瓶颈不在血量），直到加了 projMul 参数才发现真正的浪费点。 没有参数化探针，这些误判会一直留在"看起来合理"的层面。

    探针的关键设计是支持倍率缩放，这样不用改内容表就能做对照实验：

    measure({ projMul: 8, hpMul: 4, atkMul: 2, crit: 500, seed: 12345 })

    ⚠️ 一个真实的坑：探针改了 cfg.skills（SkillDef）的 projectile_speed 却毫无效果， 而 fire() 读的是 cfg.equipped（EquippedSkill）里的 projectileSpeed。 倍率施加的对象错了，实验会给出"这个变量无影响"的假结论。

    8. 「看起来实现了、实际不工作」需要专门的判据¶

    这类缺陷的特征是：代码存在、类型正确、编译通过、测试全绿，但功能不生效。 共同点不是"写错了"，而是缺少一条能表达"它必须生效"的断言。

    本轮遇到的三个形态：

    形态 实例 能被什么抓到
    参数与增量差数量级 地形 param=100~5000 vs 充能增量 ≈0~2 端到端行为断言（"12 个油桶关卡 0 个点燃"）
    路径几何互斥 掩体的每 tick 充能判定半径 110，弹丸在 100 被销毁 删除死代码 + 单元测试锁住唯一来源
    判据落在保护之外 技能卡"装入空槽"的 findIndex 命中已占用槽 「施加后状态确实变了」的用例

    注意这类缺陷都不会让任何现有测试变红 —— 所以补测试的判据是 「改坏会不会红」，而不是「覆盖到了吗」。后者只能靠变异测试回答。

    9. 有两类断言结构上测不出来，必须专门去构造¶

    前八条约束针对的是"实现存在但不对"。下面两类更进一步 —— 实现完全正确、行为完全一致，但违反了某条约定， 而这一点只能靠绕开行为、直接断言性质来抓住。

    9.1 形态断言：本机永远测不出来的那类¶

    定点整数铁律关心的是跨实现一致，不是"本机一致"。 把 spawnProgress 从整数千分比改回浮点（+= 0.08）之后， 全部 393 个测试照样绿（实测）—— 因为浮点版本在同一份 V8 上算出同一个数。

    这类缺陷的特征：只有换机器、换引擎版本才会炸，而那正是上线后才发现的时候。

    所以判据必须是形态而不是结果：

    • spawnProgress 必须是整数
    • 必须是 STEP 的整数倍，或恰好等于 FULL （1000 % 80 = 40 —— 钳位值不是 STEP 的倍数是正常的，FULL/STEP = 12.5 本就不能整除。 我最初只写 p % STEP === 0，测试自己先红了。）
    • 13 个 tick 达到满 —— 防止有人把 STEP 调成能整除的数，那会平移"敌人何时可被击中"的时刻
    • 同 seed 跑两次产生完全相同的状态链（混入 Math.random 或 Date.now() 就会红）
    • Math.random 的源码检查：判据必须是「没有调用」而不是「没有出现」—— lcg.ts 的文件头就写着「本模块禁止使用 Math.random()」， 那条警告本身包含这个词，最早写成 not.toContain 被自己的注释判失败

    辅助代码本身也要被守：stripComments 配了一条自检用例， 否则它写坏了会让上面两条假绿。

    9.2 分布断言：单点自洽不等于整体正确¶

    关卡生成里这类缺陷最典型。chapterTerrainFor 曾让 41% 的关卡带地形（意图约 25%）， 而每一关单独看都是自洽的答案 —— 没有报错、没有断言会红。

    挖出来的三层，每层都需要不同级别的断言：

    层 现象 需要什么级别的断言
    算术右移产生负余数 负种子那 50% 关卡的 offset < 3 恒真 函数级：偏移必须在 [0, span)
    「保底 3 关」不是保底 保底只在 1/4 的关卡里生效，期望 0.15 关/章 章级：每章至少 3 关
    用到的比特位不随关卡号变化 (seed>>8)%4 整章内是同一个值 章内分布级：单桶偏离上限

    第三层最隐蔽：全局分布看起来是均匀的（各 24~27/100）， 只有分章看才发现第 4 章是 0/7/13/0 —— 意味着该章要么全是地形关、要么一个都没有。 所以判据必须是章内均匀度，因为地形比例是按章体验的。

    两条统计纪律（我各犯了一次，测试自己先红）：

    1. 区间的端点不能用期望值。100 关里 82 关走概率、期望 10.3、σ≈3.0， 实测 7 在 1.1σ 内 —— 把下限定成期望值 28% 就是错的。 下限要用结构性硬下限（保底 18%），上限用期望 + 2σ。
    2. 均匀度容差是样本量的函数。20 个样本分 4 桶时偏差 3~4 属正常波动， 固定容差 2 会让测试误报。改成 tol = 2 + span/8。

    9.3 同一个字段两端的空值处理也要一致¶

    reactionElement 两端同名，但曾对同一个空值给出不同抗性：

    TS:  input.reactionElement ??  def.dominantElement()   // '' 不回退 → 无抗性
Go:  if resElement == "" { resElement = dominant(def) } // '' 回退   → 真实抗性

    抗性不同 → 反应伤害不同 → replayHash 不同 → I-6 把正常对局判成伪造。 而 13 个契约向量全绿，因为 reaction_element 在向量里从未出现过 —— 一致性测试只在"两端传了同一个合法值"时比对，分歧恰好在非法输入路径上。

    "类型上不可能"不等于"不会发生"：契约向量经 JSON 往返、DB 里的关卡行被手改、 灰度中的新客户端下发旧客户端不认识的字段 —— 三条路径都能送来 ''。

    两端各配一条语义相同的用例（断言 '' 与 undefined 等价， 且回退到守方主元素而非变成无抗性），变异任一端，那一端立刻红。

    10. 采样会掩盖分布问题，而分布缺陷不会让单点自检变红¶

    本项目被这条坑了三次，每次都是同一个形状。

    缺陷 采样时（6 关） 全量时（100 关）
    3 关永久死锁 全绿（6 关里没有一关是掩体关） 3 关永远打不完
    地形关 41% 全绿（6 关恰好落在正常区间） 41 关带地形
    3 星白送 全绿（6 关都能拿 3 星） 99/100 关拿 3 星

    共同点：每一关单独看都是自洽的。chapterTerrainFor 返回一个 自洽的答案、每场战斗都正常结束、每关都能通关 —— 没有任何单点断言会红。而「100 关里有几关带地形」「每章有几关地形」 这类分布性质没有任何东西在守。

    两条硬规矩：

    1. 可完成性是逐关性质，必须全量跑。 no_deadlock.test.ts 跑全部 100 关， 并且带一条「夹具确实覆盖了 100 关」的前提用例 —— 没有它，"只跑了几关"会假绿。
    2. 配比/分布要用分布级断言。 terrain_ratio_test.go 断言的是 100 关的地形关总数区间、每章的下界与上界、章内的 mod 分布 —— 而不只是"每章至少 3 关"。

    11. 「观测不到」会被读成「机制没生效」——先怀疑观测本身¶

    测 I-4 地形生效率时，度量口径换了五次，前四次都是观测错了：

    版本 观测方式 得到的错误结论
    1 t.triggered 标志 油桶/潮汐闸/风障全 0%
    2 「状态动过就算」 潮汐闸/风障 100%
    3 包 updateProjectiles 数被挡弹丸 潮汐闸 0%
    4 包 updateProjectiles 比速度变化 风障 0%
    5 战斗结束后查敌人是否被拦 潮汐闸 0%
    最终 逐 tick 观测引擎公开状态 4/5 类 100%

    三个典型错误：

    1. triggered 标的是「一次性事件」，而潮汐闸与风障是持续型机制 （一直挡 / 一直偏转）。用一次性标志度量持续型机制，必然得到假的 0%。
    2. 偏转发生在 updateTerrain 里，而我在 updateProjectiles 前后取快照 —— 取到的已经是被改过的速度，差值恒为 0。
    3. 赢下战斗时敌人已全部死亡，所以「结束后查有没有敌人被拦」必然是 0。

    还有一个更隐蔽的：包私有方法 updateProjectiles 时， 它在内部会 this.projectiles = this.projectiles.filter(...) 重建数组 —— 前后都读 eng.projectiles 得到的是同一个新数组，条件恒假、计数器恒为 0。

    一段永不执行的插桩比没有插桩更危险：它给出「没问题」的假结论， 而没有插桩至少会让你知道该去查。

    规矩：度量「机制是否生效」时，先用已知会生效的样本自检这套观测， 再用它去测不确定的那些。最终版本不碰任何私有方法，只逐 tick 读公开状态。

    12. 养成接线必须验证「改变战斗结果」，而不只是「改变某个字段」¶

    本项目曾有一整层养成是纯装饰：18 件装备、8 种宝石、 专精树的 40/96 个节点，对战斗数值零影响。

    computeAttacker 只装了专精树的 3 种 kind（element_cap / reaction_mult / crit）， 其余全部只进 I-7 构筑评分与 /config。 第 3 层的 mechanic（"机制改造"）在 EvaluateMastery 的 switch 里连 case 都没有。

    为什么没人发现：computeRating 读了这些数据并展示，看起来「有数值」。

    展示层读同一份数据，不等于战斗层也读。

    三个已有测试都"覆盖"了这些数据，却没有一个断言「它有效果」： - 内容表测试只查节点数量、层间约束、ID 规则 - 评分测试只查总分落在区间内（贡献 0 也在区间内） - 战斗测试用固定攻方，不经过成长链路

    形状：接线存在，但没有「全覆盖」守卫。 与本项目已修的多个缺陷同形（reactionMultPermille 空转、Math.cos 参与判定、 reactionElement 两端分歧）。

    新增守卫（每一类都做过变异验证）：

    守卫 抓什么 变异结果
    TestEveryMasteryKindIsEvaluated 每种专精 kind 选中后效果必须变化 删 mechanic case → 红
    TestAttackerViewCoversEveryAttackerField 反射比对：给 Attacker 加字段而漏下发 加字段不补 view → 红
    TestEveryAttackerFieldChangesResolveHit 扰动每个字段 → 结算结果必须变 —

    loadout_attacker.test.ts（TS 14 例） 客户端三项字段真的改变护甲/热量/卡面 客户端不读 → 红

    13. 千分比字段必须确认加法语义，不能只看字段名¶

    HeatMeter.cap 曾写成 HEAT_MAX + capBonus， 把千分比当成绝对值相加 —— heatCapPermille=1000‰ 让上限变成 1100 而不是 200。

    而热量衰减率是固定的，于是上限涨到 11 倍时玩家长期停在 「热量很高但放不出技能」的死区：

    capBonus cap 过热次数 漏怪 分数
    0‰ 100 9028 486 基准
    1000‰ 1100 1174 1168 -13.8%
    2000‰ 2100 638 1484 —

    「提高热量上限」是「有利属性」。出现反向曲线只能是单位错了，不是平衡问题。

    修法：cap = HEAT_MAX × (1000 + capBonus) / 1000； 专精节点值（10/20/30）在 EvaluateMastery 里 ×10 换算成千分比。 修正后单调有益（0‰→1000‰：漏怪 486→465、时长 28076s→21513s）。

    判据：千分比字段参与加法时，先确认「加完之后数量级对不对」。 +1000‰ 得到的是 2 倍，不是 +1000。

    14. 「升级不该让排行变差」是一条可测的不变式¶

    接线完成后才发现：满配（全部封顶）下有 2 关分数反而下降、1 关从 3 星掉到 2 星。 关卡仍然 won，所以没有任何已有测试会红。

    收紧 MaxLoadoutElementCoefPermille（1800 → 1200）后消失。

    MaxLoadoutAttackPermille 从 3000 砍到 1000，依据是扫描：

    attack‰ 击杀数 分数 反应次数
    0 5262 790188 15064
    3000 5275 807665 (+0.6%) 11279 (-25.1%)

    堆攻击力买不到分数（+0.6%），却直接压制反应 25% —— 而反应正是 I-1 的核心创新。击杀数几乎不随攻击力变， 说明战斗瓶颈是热量/冷却周期而非伤害。

    分数容差取 2% 而非严格 >=：分数是整数（伤害分 = totalDamage/100）， 过杀时序带来 0.01%~1% 噪声。严格 >= 会让守卫永远红、被当成 flaky 忽略 —— 比没有守卫更糟。2% 仍能抓住 3.9% 那种真回归。

    15. 「等级」这类养成输入必须烘进战斗数值，而不是作为独立字段往下传¶

    接技能升级时（user_skills.level 此前是永远为 1 的一列）撞上的选择：

    方案 战斗算得对吗 验真能区分等级吗
    独立 level 字段，在 fire() 里乘 对 不能 —— 等级不在 replayHash() 锚点里
    烘进 baseDamage（本项目采用） 对 能

    replayHash() 的锚点是 ${slot}:${skillId}:${baseDamage}:${applyStacks}:${heatCost}。 等级若不落在锚点里，两个不同等级的构筑可能算出同一份哈希 —— 验真通过但伤害对不上，哈希在说谎。

    与约束「activeSlots 缺省必须是 ACTIVE_SLOTS = 4」同一个道理： 凡是能改变战斗结果的输入，都必须落在哈希锚点里。 skill_level_battle.test.ts 的「不同等级 → 不同 replayHash」是这条约束的直接守卫。

    等级 1 → 1000‰ 必须是精确恒等，不是近似。 升级上线前所有 level 恒为 1， 所以所有存量战报的重放哈希必须逐位不变。基线若取 1050‰ 之类， 每个历史战报都会静默失配 —— 而失配表现为「验真失败」， 看起来像作弊，实际只是上线了一个数学常数。

    顺带根除了一处双份实现：pages/battle/battle.vue 此前持有 replay.ts:equippedFromSnapshot 的逐行复制版本（实战拼一次、重放拼一次）。 两份都自洽，改一处忘另一处 → 实战伤害与重放伤害不同 → 哈希永远失配， 而排查方向会自然滑向「I-6 坏了」。现在 battle.vue 直接调那个函数。

    16. replay_skills：前缀 S 段可服务端校验，但攻方系数仍抓不到（第 56 轮）¶

    replay_hash 整体无法被服务端重算 —— 它是 fnv1a64(前缀;事件1;事件2;…) 的 单向哈希，而前缀里的 A 段取自客户端的 currentAttacker()，那个值含 战斗中选卡产生的 buff，服务端在结算时不知道。

    但前缀里的 S 段（技能槽配置）不含 buff，它完全由构筑决定， 服务端可以独立重算并逐字比对。新增字段 replay_skills：

    能抓住 抓不到
    伪造底伤（等价于假报技能等级 —— 等级必须烘进底伤） replay_hash 本身的任何篡改
    上报一套与 user_skill_slots 不同的技能
    槽位错位

    A 段（攻方系数）为什么不该去校验（第 59 轮实测结论）¶

    这一条之前写成「抓不到，因为需要模拟」—— 那是把一个能力缺口 写成了问题，好像补上 tick 循环移植就能解决。量过之后不是。

    攻方系数不参与任何收益计算：

    scoreCapFor(gl, sec)           只用关卡 MaxScore 与时长
MaxKillsFor(gl)                只用关卡敌人总数
computeLoot(gl, stars, kills…)  只用关卡、星级、击杀
validateHPLeft(gl, hpLeft)     只用关卡初始血量

    攻方一个都没进去。而结算能兑换的只有分数、星级、掉落、进度 —— 全都不看攻方。 所以伪造 A 段换不来任何收益，校验它只能证明「哈希与构筑一致」， 抓不到任何能兑现的作弊。

    顺带量过「能不能算出来」：A 段 7 个字段里 3 个不含 buff， 其中 critMultiplierPermille 是硬编码常量 1500（applyLoadout 不碰它）、 reactionTier 来自关卡生成的 max_reaction_tier —— 这两个零风险可算。 但第三个 reactionMultPermille 取决于专精节点与装备， 而 POST /mastery/allocate 与装备变更独立于战局可达， 玩家可以在买 token 后、结算前改掉它 —— 那正是误封入口。

    结论：算了也抓不到作弊，不做还少一个误封入口。 TestAttackerNeverEntersRewardComputation 把这条不变式立成了守卫： 有人把攻方接进收益路径时它会红，并指出是哪个函数的哪一行。

    留着 KNOWN_LIMITS.md 里的描述而不立守卫，代价是将来有人为了「修」它去移植 2,470 行 tick 循环 —— 而那件事解决不了任何问题。

    格式：slot:skillId:baseDamage:applyStacks:heatCost，按字符串升序，逗号连接。 ⚠️ 排的是格式化后的字符串而不是槽位数值 —— TS 的 Array.sort() 无参时按 UTF-16 码元比较，所以 slot=10 排在 slot=2 前面。Go 侧必须用 sort.Strings 才等价。我第一版写成了按槽位排序，读起来完全合理、单测也全绿（当时用例只有 slot < 10），是集成测试在真实数据上炸出来的。

    重算的数据来源是 skills 表，不是 domain.SeedSkills。 客户端的技能内容是服务端从库里下发的（client.ts 的 skills + composite_skills），而运营后台的 PUT /admin/skills/:id 就会改这张表。 读 Go 常量的话，运营一改技能就全量误封。这不是假想：开发库当前就是漂的 （基础技能 1 的底伤被管理端测试改成 33，Go 常量仍是 100），全量跑测试才暴露。

    跨端契约：formula_vectors.json 的 replay_skills.cases（5 条）， Go replay_skills_contract_test.go 与 TS replay_skills_contract.test.ts 读同一个字面期望值。scripts/e2e.ps1 帮不上忙 —— 它自己构造 payload 且 不带这个字段（发空串，按设计放行），所以「上报了必须对得上」那半边只有这两个测试在守。

    空串放行：老客户端不上报这个字段，直接拒会把它们全部锁死。 「没上报」与「上报了但不对」要分开 —— 后者才是作弊。

    上限是实测出来的，且收进跨端契约（第 57 轮）¶

    上一轮那两个上限（1024 字符 / 20 条）是拍脑袋的。本轮改成实测：

    槽位数 4 5 10 12 20（上限） 21
    长度 51 64 130 160 280 293

    17. 名单型守卫必须结构上完备，不能靠人记得同步（第 58 轮）¶

    第 58 轮的实际教训。isSettleRejection 把已知的结算拒绝映射成 422， 其余落兜底 500。名单是硬编码的，而唯一的守卫 TestSettleRejectionsAllMapTo422 只遍历它自己那份名单 —— 它的注释里自己写着「如果漏了某个 domain 错误，这个测试同样会绿」。

    结果扫出三个实际在返回 500 的拒绝：

    哨兵 触发路径 性质
    domain.ErrHPLeftExceedsBase 结算：上报剩余血量 > 关卡初始血量 先前就存在
    service.ErrSlotBudgetExceeded loadout：装备件数 > 槽位预算 先前就存在
    service.ErrReplaySkillsMismatch 结算：回放 S 段与构筑不符 第 56 轮新加，忘了映射

    500 的代价是具体的：客户端只能显示「服务内部错误」， 排查会自然滑向「服务端坏了」而不是「这个上报被拒了」， 而且它们混进服务故障告警，把真正的故障淹掉。

    这类守卫要成立，需要三件事同时做到：

    1. 用 AST 扫源码，而不是人维护名单 —— TestEverySentinelErrorIsClassified 用 go/parser 扫 domain 与 service 两个包的全部 Err* = errors.New(...) 顶层变量声明（扫到 20 个），要求每个都归入 settle / general / 具名豁免。 正则会分不清声明与使用、也分不清注释里的同名 —— 第一版就是正则， 把注释里的名字也算成了声明。

    2. 「在名单里」不等于「生效」 —— 这是最关键的一条。 对 settle 类必须额外断言 isSettleRejection(err) === true。 只比名单的话，名单写了而实现漏了，守卫会绿而实际仍返回 500 —— 装饰品就是这么伪装成守卫的。 变异验证 B/C/D（分别从实现里删掉两个哨兵、把 isSettleRejection 改成恒返回 false）就是这一类；只比名单的版本这三个变异会全绿。

    3. 双向钉死 —— 登记表与源码声明必须一一对应， 否则「登记表漏了新哨兵」会变成误报，而「改名后分类悄悄失效」没人发现。

    豁免必须具名且写清理由（理由为空也红）：「不是拒绝」这种判断 留给写豁免的人，不留给沉默。

    18. 第 96 关的难度墙：卡在防线护甲，不卡攻击力（第 61 轮实测）¶

    项目里记着「第 96 关是刻意的难度墙，已获产品确认：终盘需要养成才能过」。 这句话的结论是对的，但中间的理由错了两次。两次都是因为探针强度不足。

    第一次的理由：方向是反的¶

    终 boss 在第 96 关首次登场，而它的底血比 97~100 关都低 —— 漏怪代价改成随底血等比缩放后，第 96 关从「尖峰」变成了「墙」。

    底血更低意味着每次漏怪伤害更低（baseHpMax × attack / LeakAttackerDivisor）， 也就是更容易过。它解释不了为什么过不去。

    第二次的理由（第 60 轮）：探针攻击力不足，结论是错的¶

    第 60 轮用 defaultAttacker()（attack=100）与手搓的 100 + stage×20 跑， 母皇终局剩 73%~84%，据此写下「很可能是 levelgen 缺陷」。

    那个判断错了。 攻方不足时怎么测都是过不去 —— 这正是本项目记录在案的「单构筑探针掩盖真相」，只是这次方向相反： 不是探针掩盖了破坏性，而是过弱的探针制造了一个不存在的缺陷。

    同轮还写过「第 96 关是纯 DPS 检验」—— 也不对。

    第 61 轮：真实满配下的真实机制¶

    攻方不再手搓：造一个满养成玩家（stage 99 + 96 专精节点 + 18 件装备）， 直接问服务端 computeAttacker 要答案：

    attack elementCoef armor
    基线（新号） 100 1000 0
    真实满配 3080 1600 430

    逐项消融（7 个 seed）：

    构筑 L96 胜 母皇终局余血中位
    基线（新号） 0/7 83.9%
    + 攻击力 2080（stage 99） 0/7 78.7%
    + 专精（elementCoef 1600） 3/7 38.9%
    + 装备（armor 430） 7/7 0.0%
    满配（全部） 7/7 0.0%

    唯一的开关是防线护甲，不是攻击力。 攻击从 100 提到 2080（20.8 倍） 只把母皇余血从 83.9% 推到 78.7%，7 个 seed 一个都过不去； 而单加装备就直接 7/7。

    机制：护甲走 defenseArmorPermille()，减的是漏怪伤害。 漏怪伤害降下来 → 基地血撑得更久 → 战斗拖得更长 → 母皇被打死。 所以第 96 关不是 DPS 门槛，而是「能不能撑到打死母皇」的时间门槛。

    同门对照：第 99 关基线 1/7，加专精后 7/7，加装备则不然 —— 两面墙卡的是不同的养成项，这更像设计而非缺陷。 全 100 关在满配下没有任何一关失败（7 seed 全胜）。

    结论¶

    例外保留原样，数值不改：第 96 关确实是单点墙 （新号过不去、满配过得去、第 97 关不需要满配也能过）， 守卫意图与内容一致。第 60 轮建议的「boss 血量随关卡缩放」撤回。

    顺带一条对上文「攻方加成对关卡的实际影响」的补充： 那张表里「防线护甲 +750‰ → 分数 0%、元素堆叠 0%」是在装备未满的构筑下测的， 所以看不出护甲的价值。这里证明护甲能单独决定终盘能否通关 —— 护甲买的是生存时间，不是分数。 两者不矛盾，但只看分数会完全错过它。

    19. 不能做的操作，不要渲染成可点的入口（第 161 轮）¶

    技能库把全部 42 个技能一律渲染成可点入口，其中 38 个从未拥有过 —— 服务端唯一的 INSERT INTO user_skills 是新人初始化的技能 1–4（service.go:402）。 （这是 2026-10-19 之前的状态：等级解锁落地后，24 个基础技能已可按等级获得； 但「入口给不给由数据权威侧决定」这条判据不变 —— 新增技能类型时同样适用。） 点「装备」收到服务端 400「技能未解锁」（这是既有预期行为， routes_e2e_test.go 里早有断言），客户端却把它显示成 「保存失败，出战配置未变更」—— 一个本地就该拦下的操作被报成了系统故障。

    判据是数据的权威侧：入口给不给，由服务端下发的 build.skills（已解锁行）决定， 不由客户端「有哪些技能定义」决定。build === null（拉取失败）时按未解锁渲染 —— 宁可少给入口，不给假按钮。

    守卫：miniapp/src/pages/bag/bag.test.ts 2 条 —— 未解锁行没有任何可点入口、 直呼 toggleEquip/doUpgrade 被本地拦下且不发请求。 两个方法内部的守卫不可省：模板不给入口 ≠ 不会被调到。

    「不给假按钮」只修掉了假象，发放侧（技能获取）当时仍是空的 —— 后来补上了（等级解锁，2026-10-19），见 KNOWN_LIMITS.md 第 29 条。 本条真正留下的是判据：入口给不给由数据的权威侧决定， 「模板不给入口 ≠ 不会被调到」——方法内部的守卫不可省。
