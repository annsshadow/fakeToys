    laiyipao 安全审计报告（2026-10-13）¶

    覆盖范围：server/（Go + Fiber + PostgreSQL，14.8k 行非测试代码）、 admin/（Vue 3 运营后台）、miniapp/（uni-app 客户端）。 方法：静态分析（gosec + 人工）+ 可执行探针（把每条怀疑打到真实数据库/引擎上验证）。

    本报告遵守项目自己的纪律：每条发现要么给出「改回去会不会红」的守卫，要么明确标为 未修并写清为什么。没有「看起来可疑但没验证」的条目。

    1. 已修：严重¶

    F1 · 道具扣减路径恒 500（两条可达路径）¶

    探针实测（修复前）：

    AdminGrantCurrency(revive_token,-1) -> ERROR: new row for relation "user_tokens"
    violates check constraint "chk_user_tokens_nonneg" (SQLSTATE 23514)
Buy(price={mastery_reset:5})        -> 同上

    根因：grantToken 只有一条 UPSERT，对 delta 正负不分。扣减时必然撞上 CHECK (balance >= 0) —— CHECK 是语句级判定，于是整笔事务带 23514 回滚， 而那个可读的「道具不足」分支永远执行不到。23514 不在 isSettleRejection 名单里， failErr 兜底成 500「服务内部错误」。

    为什么「不可达」那句注释是错的：grantToken 的注释写着「这条分支当前不可达 （pay 侧只接受货币）」。当时确实不可达，但第 148~151 轮接上了道具消费端点并且 AdminUpdateShopItem 的 validWalletCurrency 明确允许把道具名写进商品 price。 于是「运营改个价就能踩到」。

    修法：扣减改走条件 UPDATE（balance >= $3 RETURNING），与货币负数分支、 spendToken 完全同构；发放保留 UPSERT（道具稀疏，首次没有行）。

    守卫：service/security_audit_test.go 6 例。其中 TestGrantTokenPartialDebitWorks 是必需的——我第一版把 $3 传成带符号的 delta（balance + $3 且条件 balance >= $3），数值上等价但比较的一边符号相反， 守卫条件直接失效。是这条测试抓到它的，而另外三条全绿。 变异实测（把条件改成 balance >= $3 - 1）→ 该条红，其余绿。

    F2 · 运营后台可被点击劫持¶

    证据：全服务端 X-Frame-Options / Content-Security-Policy / frame-ancestors grep 0 命中；admin/index.html 也无（且 XFO 本就不能用 meta 设置）。

    攻击路径：evil.com → <iframe src="https://后台域名/#/admin/users"> → 盖透明遮罩， 把假按钮对齐到 iframe 内的真按钮。已登录运营点一下，请求就真的带上了他自己 localStorage 里的 Authorization 头发出去 —— 跨域读不到 token 也不影响， 因为执行的是他自己页面里的代码。结果落进审计日志，看起来与亲手操作完全一样。

    后台所有写操作都是单次点击即生效（发币 / 封号 / 改价 / 再生成 100 关）， 无二次确认弹窗。这是本项目唯一一条「不需要任何服务端漏洞、只要运营点一下 就能在后台执行写操作」的路径。

    修法：全局中间件下发 X-Frame-Options: DENY + CSP: default-src 'self'; frame-ancestors 'none' + X-Content-Type-Options: nosniff + Referrer-Policy: no-referrer。

    守卫：httpapi/security_headers_test.go 4 条，覆盖 200 / 4xx / OPTIONS 三类响应。 变异实测（摘掉 app.Use(securityHeaders())）→ 3 条同时红。

    F3 · 全站零速率限制¶

    证据：routes.go 修前没有任何 limiter 中间件。探针实测： 同一场战报重复验真 200 次 → replay_verifications 写 200 行 （该表既无唯一约束也无去重）。

    四个放大器，各自独立成立：

    端点 未认证？ 放大倍数 后果
    POST /admin/login 是 bcrypt cost 10 ≈ 50~100ms 纯 CPU 打满并发 → 正常运营完全登不进后台；同时无限次口令喷洒
    POST /auth/guest 是 每次调用 7 行 INSERT 批量造号把库撑爆，无任何计数
    POST /battle/verify 否 每次 1 行，无幂等键 存储放大（实测 200 倍）
    POST /redeem 否 — 兑换码在线爆破

    修法：按 IP 限未认证入口（登录 5/min、游客 60/min、刷新 60/min、兑换 5/min）， 按登录身份限写放大路径（结算 60/min、验真 20/min、兑换 20/min）。 身份额度挡的是「注册 1000 个号、每个号慢慢打」——那是对付 IP 限流最直接的手段。

    额度为什么给得比「直觉上的严」宽松：小程序玩家大量走运营商 NAT， 同一出口 IP 后面可能有成百上千真实用户。把每 IP 卡到个位数会误伤整个运营商网段， 而那比不限流更糟 —— 变成一个谁都说不清为什么的故障。

    守卫：4 条，含「额度内首次请求不得被限流」与「公开读端点连打 80 次不得被限流」 两条反向断言（防止一个把限流挂得太宽的实现靠上面那条蒙混过关）。 变异实测（摘掉 admin/login 的 limiter）→ 该子用例红并报出「实际拒了 0 次」。

    2. 已修：高¶

    F4 · 没有登出端点，refresh token 30 天无法切断¶

    玩家手机丢了 / 令牌被 XSS 读走之后，服务端没有任何办法切断会话。 唯一会吊销 refresh token 的既有路径是「封禁玩家」，而那会把正常玩家一起踢下线 —— 用「封号」当「登出」，代价与意图完全不成比例。

    修法：POST /api/v1/me/logout 吊销该用户全部 refresh token（幂等，返回吊销条数）； 客户端「我的」页加二次确认的退出按钮。不限流 —— 登出的作用恰恰是「出事时立刻切断」。

    守卫：Go 4 条（判据是「refresh 再也换不出 access token」这个安全后果， 不是「表被 UPDATE 了」这个实现形状；另有单独一条守住「只吊销自己的」）+ 端到端路由消费守卫。

    F5 · 后台审计日志的 IP 恒为空串¶

    Audit 写死 ''。于是每一行后台审计的 IP 列都是空的 —— 它看起来像 「这一列是可选的」，而它其实是「本项目从来没有过来源信息」。 F2 那条攻击路径的事后取证材料就只剩这一列。

    修法：Audit 增加 ip 参数，全部 10 个调用点传 c.IP()。

    残留（如实标注）：Fiber 未配置 ProxyHeader，所以反代之后 c.IP() 拿到的是 反代的地址。生产部署必须配好反代的 X-Forwarded-For 透传， 否则审计里记的是反代 IP。这里没有顺手打开 EnableTrustedProxy —— 在反代没配好之前打开它等于允许任何人用请求头伪造来源 IP，比记反代地址更糟。

    F6 · admin 前端的 401 处理是虚构的¶

    api/client.ts 的 !resp.ok 分支无条件抛 ApiError 就结束了，没有任何 401 检测。 而 router/index.ts 的注释写着「令牌失效兜底：api 层抛 401 时把令牌清掉并送回登录页…… 真正的 401 检测在 api/client 抛出」——那条检测从来没有被实现过。 tests/router.test.ts 的注释也建立在同一个虚构前提上。

    后果：令牌过期（后台 access token 默认 2h）或管理员被停用时，路由守卫看到 getToken() 仍为真而放行 → 每个视图反复吃 401 → 运营被永久卡在已登录的壳里， 永远不会被提示重新认证，localStorage 里还长期留着一枚失效凭证。

    修法：client.ts 增加 handleUnauthorized()，在读 body 之前判定 （一旦被后面的普通错误分支抛出去，就再也不会有代码回到这里）。 登录接口自己的 401 排除在外（「密码打错」不能变成「被踢回登录页」）。

    守卫：TS 7 条，含四条反向断言 —— 500 / 403 / 网络错误 / 已在登录页时 都不清令牌。把「401」与「其它错误」混起来的后果是「后端重启一次，后台全体掉线」 与「readonly 被降权」被误报成「你掉线了」。

    F7 · miniapp 接口地址硬编码明文回环，且没有任何东西阻止它上生产¶

    const BASE_URL = 'http://127.0.0.1:8080/api/v1'，模块级 const，无覆写点。 打出来的包只能连用户自己设备的回环地址（生产不可用）， 而「唯一的修法」是回去改这个常量 —— 那条路径上没有任何东西阻止人保留 http:// 只把地址换掉，于是最自然的修补就是「照抄，改域名」，令牌（refresh 30 天）明文过网。

    修法：VITE_API_BASE 覆盖（与 admin 同一套机制）+ 启动断言： 非回环主机走明文 HTTP 时直接抛错阻断；局域网 IP 只警告（真机调试需要）。

    F8 · CORS 在生产环境仍发 *¶

    cors() 原先无条件发 Access-Control-Allow-Origin: *，注释写着「生产应收紧」—— 而那只是一句注释。

    诚实标注：本项目不用 cookie 存凭证（纯 Authorization: Bearer，全仓库零 cookie、 零 credentials:'include'），所以 * 不构成「带凭证的跨域读」—— 把它报成严重漏洞是错的。真正的风险是「将来有人加了 cookie 登录」，那时 * 立刻变成全站沦陷，且没有任何东西会提醒。

    修法：prod 默认一条 CORS 头都不发（等价只允许同源）， CORS_ALLOW_ORIGINS 配了白名单才回显具体来源 + Vary: Origin。 反向默认值的取舍写在 config.go 的字段注释里。

    F9 · 后台发币无金额上界¶

    amount 来自 JSON 的 int64。2^62 本身写得进 BIGINT（实测成功）， 但再叠一次就溢出 → PG 22003 → 不在 isSettleRejection 名单 → 500。 即一次手滑（大数粘贴）把整笔发放打成 500，而运营看到的不是「数额不合理」而是「服务端坏了」。

    修法：上限 1e12（比任何真实运营发放大 6 个数量级，离 int64 溢出足够远）。

    TestToFixedRoundsHalfUp 第一版全用整数输入。而 ToFixed(logical int) 时 logical*1000 恒为整数，Round 与 Trunc 结果相同 —— 变异把取整换成截断后 测试没红。

    ① SkillBaseDamageAtLevel 缺了 TS 的恒等快路径 —— 真实溢出。

    TS 在 coef === 1000n 时直接返回 baseDamage，不做那次乘法； Go 原来直接算 base * coef / 1000。变异实测 2^63-1 那个值：

    SkillBaseDamageAtLevel(lvl=1, base=9223372036854775807) = -1   （溢出）

    这不是「理论问题」：等级 1 是所有存量战报的等级（升级功能上线前 level 恒为 1）， 而 replayHash 把 baseDamage 拼进锚点 —— 一旦这一位变了， 每个历史战报都会失配，而失配表现为「验真失败」，看起来像作弊。

    ② 我在向量里的「整数边界」判断错了，被自己写的守卫抓到。

    我第一版用 2^53-1 当「大值」，注释写「乘上 1.45 后是 1.3e16，远小于 int64 上界」。

    那是错的。 2^53-1 × 1050 = 9.46e18 已经越过 int64 上界 9.22e18。 TestSkillVectorsStayInsideSafeIntRange 直接把它挑了出来。

    错在把最终结果的约束当成了中间乘积的约束 —— Go 是先乘后除（TS 的注释专门解释过为什么不能先除后乘），所以边界由中间乘积决定。 改成 2^52。

    同时把这条边界写进了契约文件的 int_width_note 与守卫的注释： 跳过而不写明 = 藏了一个限制，将来有人把底伤上限调高就会踩上去。

    ③ 我的测试前提落在整分钟之外，红的是前提不是代码。

    TestChallengeSeedIsStableWithinMinuteAndChangesAcross 用 1_700_000_000_000 当基准， 而它除以 60000 是 28333333.33 —— 不在整分上。 于是「+59.999s 仍应同一分钟」跨过了边界。被测代码是对的。 现已把基准对齐到整分，并加了 baseMs%60000 != 0 的前提断言 —— 判据落在错误前提上时，它守的不是代码而是我的想当然。

    R3 · 游客凭证即永久凭证，且无轮换 —— 已在 2026-10-14 修复¶

    guest_token 是与口令同级的凭证（实测：给出同一 guest_token 再次登录即可拿到 该账号的 access + refresh token）。它 24 字节随机，不可猜 —— 但：

    • 后台的玩家搜索条件就包含 guest_token（AdminListUsers 的 LIKE）， 所以后台被点（F2）或 DB 泄露 ⇒ 批量导出所有玩家凭证；
    • 没有轮换机制。F4 的登出只吊销 refresh token，guest_token 依然能换出新会话。

    修法（提交 8a23628d7）：

    1. 登出轮换 guest_token，与吊销 refresh token 同事务 —— 两者必须同生共死：只吊销前者则旧凭证仍能换出新会话， 只轮换前者则被盗的 refresh token 还活着。 UNIQUE 撞车概率极低但不是零，撞了重试 5 次而不是当不可能。
    2. 后台玩家搜索不再打 guest_token。凭证可检索意味着 「后台账号被盗 ⇒ 批量导出玩家凭证」。运营用昵称/user_id 就够了。 这是功能删减，所以配了双向守卫（凭证搜不到 + 昵称仍能搜，防删过头）。
    3. 客户端登出时落盘新凭证。

    一个必须写下来的形态：凭证轮换后，拿旧凭证来的人不会看到任何异常 —— GuestLogin 对未知凭证的语义是「建一个新号」，所以它安静地返回一个空账号。 这正是客户端必须立刻存下新凭证的原因：不存的话受害者自己也走这条路， 进度凭空消失且毫无报错。那比「凭证没轮换」严重得多 —— 凭证问题静默，丢进度会被立刻发现并当成无法解释的 bug。

    9.1 config 漂移风险 —— 先说错了，又错地否定了一次，最后变成事实¶

    接线收尾时我提出过这样一个风险：

    "admin 有 PUT /admin/skills/:id 能改技能数值，客户端从 /api/v1/config 拿数据且有 HTTP 缓存；admin 在一局战斗进行中改技能，客户端可能用旧值、 服务端用新值，重算就会失配 —— 于是误拒诚实玩家。"

    随后我读代码「确认」了这个风险不存在，理由是 "/config 出的是进程内静态表，admin 改的是 DB 副本"。

    • 第二次错：我据此宣布「风险不存在」。重写测试用同一个 token 重算两次， 并覆盖 4 类编辑（base_damage / heat_cost / name / element）之后，它确实绿了 —— 这次是真的绿。
