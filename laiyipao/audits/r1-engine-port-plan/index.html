    R1 tick 循环移植计划¶

    状态：2026-10-14 制定。Block A 已完成（见文末）。

    为什么需要这份计划¶

    engine.ts 的 tick 循环是 1855 行里最危险的一块。它的偏差不会报错， 只会让 replay_hash 失配 —— 而失配的表现是「验真失败」，即 把诚实玩家判成作弊。这是本项目唯一能把「可刷分」漏洞换成 P0 事故的地方。

    所以移植它必须满足两条：

    1. 任何时刻都有「当前实现对不对」的可执行答案。 不是「等全部搬完再跑整局看看」，而是每加一块就多一条独立可验证的增量。
    2. 不接任何拒发路径，直到它被证明对。 SETTLE_RECOMPUTE_MODE 保持 off（现有缺省），引擎落地后先在 shadow 档 观察若干天 —— 台账与熔断在第 2026-10-14 第二步就已经造好了。

    分解判据¶

    按「每块结束时能独立验证」切，不按「代码上看起来是一个函数」切。

    判据具体是：在那一块结束时，存在一个 TS 能跑出、Go 也能跑出、且两者 事件流逐条相同的场景。 达不到这个条件的切法不要采用 —— 那只会得到「大块代码一起对或者一起错」。

    依赖图¶

    A 骨架 + tick 序        ← 无依赖，先做
│
├─ B 波次与刷怪
│    └─ C 敌人移动与元素
│         ├─ D 开火与弹道  ──┐
│         └─ E 地形接线      ├─ F 卡牌（依赖 D）
│                             │
G 结算与哈希（依赖 B~F）  ────┘

    E 同时依赖 C（敌人）与 D（弹丸），因为地形要操作两者。 F 依赖 D：选牌会改攻方系数，而攻方系数进 D 的伤害计算。

    各块的验收场景¶

    ⚠️ Block A 的验收与 B~F 不同：它拿不到 TS 逐事件对齐， 因为 start() 会调 beginWave(0)，而 beginWave 属于 B 块。 所以 A 的验收是直接验证排序不变量（见下），第一次真正的跨端逐事件对齐在 B。

    块 内容 验收 断言
    A 全部实体类型（字段齐）、BattleEngine 全部字段、Start、Step、emit/record/DrainEvents、CheckStalemate、Finish、CalcStars、ReplaySkillsSegment/BuildSnapshotSegment 排序不变量（不依赖 TS 对齐）：停滞恰在 tick 30000 触发、elapsedMs == tick×50、终局后 Step 不再推进 tick、停滞事件在战斗逻辑之前、stalemate 进 replay 直接断言
    B beginWave、spawnEnemy、updateSpawns、checkWaveEnd 波次分支、stepEnemyMotion 第一次 TS 逐事件对齐：第 1 关、空构筑跑到本波清空 刷怪 tick 序列 + 事件流逐条
    C updateEnemies、leakDamage、leakDamageFor、withinEnemy 敌人推进到漏怪线 漏怪事件 + leaked
    D updateAutoFire、fire、updateProjectiles、checkProjectileHit、hitEnemy、currentAttacker、defenseArmorPermille、triggerSteamBurstAoe、applyAoe 完整战斗（无地形无选牌） 整局 replay_hash —— 里程碑
    E updateTerrain、terrainCtx、withinTerrain 含地形关 地形事件 + terrain_used
    F finishCardSelect、skipCards、applyReplayDecision、recordPick、applyCard、applyAttribute、applyMechanic 含选牌脚本的战斗 选牌索引序列 + 哈希
    G replayHash、settleInput 所需字段 replay_vectors.json 那 5 个用例 hash + expected_stats 逐项

    D 就能拿到整局哈希（无地形无选牌时）。这是第一个真正的里程碑： 它证明「服务端重算」在技术上成立。G 只是把哈希与结算字段接上， 其场景是 B~F 的子集。

    关于未移植块的处理¶

    B~F 的方法在 A 阶段是空实现（no-op stub），Step 按最终顺序调用它们。 替换顺序固定：B → C → D → E → F。

    ⚠️ 这意味着 A 阶段 Step 产出的事件流必然与 TS 不同。 这不是缺陷，是「尚未搬完」的如实反映；A 的验收因此不比对事件流内容， 只比对排序不变量。等 B 替换掉 beginWave 之后，第一次逐事件对齐才有意义。

    tick 序的三条硬约束¶

    step() 里有三处「位置错了就静默失配」，源码注释已经点明，移植时必须逐条对齐：

    1. cardSelectDone 收尾必须在 applyReplayDecision 之前。 否则同一 tick 内 applyReplayDecision 被调两次， 把下一波的决策当成本波的第二张牌（实测 picks 记成 [-3,-3,-1,-1]）。
    2. applyReplayDecision 必须在 tick++ 之前。 tick 会写进每条 replay 事件，多一格会让后续所有时间戳整体偏移。
    3. checkStalemate 必须在 tick++ 之后、任何战斗逻辑之前。 这样「到上限」这件事本身是这次 tick 的第一个事实。

    这三条要写成守卫，但不是都在 A 块：

    约束 验证时机 原因
    (1) cardSelectDone 在 applyReplayDecision 之前 F 块 A 阶段 applyReplayDecision 是空实现，两种顺序行为相同，写不出能失败的守卫
    (2) applyReplayDecision 在 tick++ 之前 F 块 同上
    (3) checkStalemate 在 tick++ 之后、战斗逻辑之前 A 块 ✅ 它现在就有行为：差一个 tick 就差 50ms，而停滞事件进哈希

    F 块里 (1)(2) 的可观测症状是选牌索引序列错乱（TS 注释记的实测： picks 记成 [-3,-3,-1,-1]）—— 那是具体、可断言的， 而 A 阶段只能断言「两种顺序一样」，那不是守卫。

    「此刻无法验证」要写下来，不要留到忘了。 否则半年后有人看到 Step 里那几行注释，以为三条都已经有守卫兜着。

    每块必须有的东西¶

    1. 契约向量：TS 侧生成器扩展，场景与 Go 侧一一对应
    2. 逐步比对：不是只比最终哈希 —— 中间错了又绕回来的实现能骗过哈希
    3. 变异验证：每块至少 1 处，证明守卫抓得住
    4. 还原态全量：变异后必须重跑还原态，不能只看变异态

    明确不做的事¶

    • 不在任何一块里接线到 SettleBattle。 接线是独立的一步， 需要「整局重算 == 契约期望值」的全绿断言，而不是「某几块绿了」。
    • 不提前提交必然红的测试。 上一步的规矩：长期红灯的唯一效果是被忽略。
    • 不改 TS。 契约向量的期望值来自 TS，那是玩家设备上真实运行的代码。 改它会让「合法的一局」的定义跟着改。

    这是 R1 第一次拿到「完整一局战斗」的两端逐事件一致。 B/C 只能证明骨架与漏怪；D 证明了开火、命中、伤害结算、反应、 击杀、评分、热量、冷却、元素统计全部一致 —— 即 replay_hash 的输入在服务端已可自行计算。

    ⚠️ 必须剥离 terrain 才敢做这个对齐： TS 的 updateProjectiles 里有一段「弹丸被掩体挡住」的判定， 而那块属于 E 块。Go 侧 D 阶段不做它 —— 半接的后果是「地形记了触发事件却从不结算效果」， 表现为「玩家看到油桶被点燃但没有任何作用」。 实测这个选择是必需的：第 1 关带一个 oil_drum， TS 会真的对它做 withinTerrain(t.x, t.y, 100, ...) 判定。 只摘 terrain；element_cap 与 max_reaction_tier 必须保留 —— 它们是 currentAttacker() 的直接输入，摘掉就等于在验一个假攻方。

    ⚠️ 关卡输入必须显式映射，不能 { ...def }： 夹具是 snake_case + JSON number，引擎要 camelCase + BigInt。 前两个字段错了会当场抛错（好找），第三个（slot）不会 —— 它表现为「所有技能都被当成主动槽」，而对 4 槽构筑来说结果一样， 于是「槽位映射错了」这件事在 4 槽场景里完全观察不到。 另外 slot 必须是列表下标而非技能 id：内容表 id 全局递增（1..42）， 直接拿 id 当 slot 的话全部技能都 >= activeSlots=4，一发都放不出来。

    两个 map 序列化的顺序陷阱： elementsUsed / reactionsUsed 在 TS 侧按首次使用顺序插入 （JSON.stringify 保插入序），Go 侧 map 按升序。 同一份统计在两端会序列化成不同顺序的字符串。 解法是两端都排序 —— 比对只针对「各元素各用了多少次」， 顺序信息不进哈希比对（若将来某个 bug 让顺序影响战果， 它也会体现在 score / hits / replay 上，而那些是逐条比对的）。

    变异实测 11 处，4 处首轮存活：

    首轮存活的 4 处与处理：

    1. MUT-D5（currentAttacker 漏加 attack 加成） —— Buffs 是 F 块写的，F 未移植则恒为 0，于是 + Buffs.AttackPermille 永远等于「加 0」，写成 base.Attack 也全绿。 补 TestCurrentAttackerAddsBuffAttack 等 4 条直接单测后红。
    2. MUT-D6（crit 夹取去掉） —— 五个场景的 critPermille 是 150‰，离 1000 的边界很远，夹取那段 一次都没执行。而越界是可达的：6 张 crit 属性卡 = 550+480 = 1030 > 1000， 后果是「每一发都暴击」而暴击率进 replay_hash → 永久失配 → 全员被误判作弊。 补 TestCurrentAttackerClampsCritPermille + 边界表后红。
    3. MUT-D7（增伤被状态时长把门） —— 这正是 TS 源码注释里预言的洞：「当前 7 条反应里没有任何一条 落在这个组合」。解法不是等数据出现，而是把那段逻辑抽成 applyReactionStatus 独立可测的函数，再用一个测试专用的 反应表替换钩子（reactionSpecLookup 函数变量）喂进 ReactionSpec{AmplifyPct: 300, StatusDurationMs: 0}。 用函数变量而不是改 reactionSpecs：后者会让 /config 下发 一个不存在的反应给所有客户端，也会让 reaction_specs.json 的双向契约失败 —— 那是把「数据表」与「代码」的责任边界糊掉。
    4. MUT-D8（索敌忽略飞行/钻地优先） —— 对齐场景里没有飞行/钻地敌人当目标。补 TestPickTargetPrefersEvASiveForMultiTargetSkills 后红。

    补强后重测：D5/D6/D7/D8 全红。另加 D10（击退改成覆盖而非累加）也红。

    1 处「结构性存活」且不去修：MUT-D11（去掉 applyReactionStatus 的 无反应守卫）在 Go 侧观察不到差别 —— Spec() 对未知 key 返回零值， 所有分支自然不进。那道守卫的价值是语义分隔： 若将来给 Spec() 加副作用（日志、计数），没有它就会把无反应也记进去。 这是诚实的现状，不是遗漏。

    本轮修掉的自身问题：

    • TestFilterAlive* 的断言写错：in[:0] 是原地压缩， backing[0] 压缩后已经是存活那只，查它永远非 nil —— 守卫恒绿。 改为查最后一个槽位（被清零的那个），并补 TestFilterAliveKeepsOrder。
    • 两次 Substring 拼接把同文件的其它测试截掉了（结构体定义之后的 全部内容）。这是本轮反复踩到的工具坑：拼接必须保留尾部， 而「写到文件末尾」只对追加成立。已从 git 恢复并改用带尾部的拼接。
    • heat.cap 是 TS 的 getter 不是方法，生成器里写成 cap() 直接抛 Cannot mix BigInt and other types。

    G 块抓到的 bug：技能卡全都是哑弹¶

    现象：第 25 关 tick 444 那发，TS 直接伤害 754 / Go 698、反应伤害 339 / 325。 中间量探针（两端各落 174/180 条 resolveHit 的完整中间量后逐行 diff） 把范围收到一条：

    hit #13  TS: skillDamage=120  applyStacks=2
        Go: skillDamage=100  applyStacks=1

    根因：rollSkillCards 忘了置 hasSkillID。 applyCard 的技能分支判据是 c.Kind == CardKindSkill && c.hasSkillID （对应 TS 的 card.skillId !== undefined），而 hasSkillID 是非导出字段， 除了 JSON 反序列化只有 rollSkillCards 会置它。 于是每一张技能卡都是哑弹：卡被 Deck.Take 取走、emit(card_taken)、 record(card) 全都照做（所以 replay 事件流看起来完全正常）， 但 applyCard 一个分支都没进，技能一次都没升格。

    它为什么能一路绿灯穿过 B~F 的 25 个跨端场景，靠三个巧合：

    1. card 的 replay 记录正常 → 事件流比对看不出问题
    2. kills / waves / terrain_used 正常 → 只有伤害低一档
    3. B~F 的 6 个卡牌场景用的全是 -3 编码 =「弃一张 + 取一张」， 取到的是弃牌之后的第 0 张（属性卡）—— 没有任何一个场景取过纯技能卡

    第 3 条是关键：-3 不是「取第 0 张」，是「弃一张，然后取第 0 张」。 我写场景时把它当成前者了，于是整整两个块都没碰到这条路径。

    教训（三条，都可复用）：

    • 「动作发生了」不等于「效果发生了」。 TakeCard 无论 applyCard 有没有效果都会 emit + record —— 所以「replay 事件流正常」这个证据完全不能用来推断效果正确。 已写成 TestTakeCardStillRecordsWhenEffectIsSilent（反向守卫，说明为什么查不出）。
    • 非导出字段 + 布尔标记 = 哑弹温床。 hasSkillID 这类「字段是否出现」的标记在 Go 里没有 undefined 语义支撑， 靠人工置位就一定会漏。要么每次构造都置（并有守卫钉住），要么干脆别用。
    • 测试替身绕过被测代码（本项目第五次，MUT-E5 / A 段 elementCap / 本次同族）。 那批 TestApplySkillCard* 全都手工构造了 Card{..., hasSkillID: true}， 于是验的是「applySkillCard 对不对」，而不是「deck 里的卡能不能走到那里」。

    一个我自己写错又改回来的默认值¶

    向量文件大小的教训¶

    replay 是累积数组，逐步全量存 = O(n²)。 第一版让长场景逐步全记，向量直接变成 42 MB —— 没人会 review 42 MB， 没人看的契约等于没有契约。改成「replay 存本步新增」+「按 sampleEvery 抽样并对有事件的步强制采样」后是 1.0 MB。

    抽样判据必须两端各自可算（tick % sampleEvery == 0 || 本步新增重放事件）， 不能照抄 trace 的下标 —— 照抄下标等于「Go 跑到第 k 个采样点就断言第 k 个 期望值」，两端之间没有任何时序约束，退化成逐点查表， 「Go 少跑了两步」这类错误永远抓不到。

    B 块的跨端对齐抓不到的两个 bug（靠构造场景的针对性测试补上）：

    1. updateSpawns 改成正序遍历 —— 五个真实场景全部照样绿。 因为真实关卡把 atTick 拉开了，同 tick 到期的通常只有一只， 而「删元素后跳过紧邻项」只在「一次删多项」时发生。 由 TestUpdateSpawnsHandlesMultipleDueInOneTick 覆盖。
    2. 空关卡判成胜利 —— 五个场景的 waves 都非空，抓不到。 由 TestEmptyLevelIsNotAutoWin 覆盖。

    这两条是本轮最值得记的教训：跨端对齐证明的是「在真实数据上两端一致」， 不覆盖「代码想处理的形状」。后者要靠构造用例。
