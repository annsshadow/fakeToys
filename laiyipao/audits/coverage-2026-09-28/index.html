    口径：可测语句/分支/函数/行一律 100%；无法被任何测试覆盖的代码（进程级 main、Go 1.26 下 crypto/rand 崩进程的错误分支、schema 保证的 rows.Scan、 类型化 json.Marshal、合法内容够不到的哨兵封顶、v8→istanbul 伪分支等）逐处 记档豁免，不用宽 exclude 掩盖。

    4. 覆盖攻坚中发现并修复的真缺陷¶

    1. 兑换码创建必然 500（server）：redeem_codes.id 无默认值，AdminCreateRedeemCode 的 INSERT 不供 id → not-null violation。修复：迁移 00009_redeem_code_identity.sql 改列为 IDENTITY + seeder 对齐序列（setval）。特征化断言已翻转为验证成功行为。
    2. PUT /me/loadout 必然 500（server）：审计 detail 写非法 JSON + admin_id=0 撞外键。修为合法 JSON + admin_id=NULL。
    3. bag 槽位错位（miniapp）：模板 1 基 v-for 传参、skillOf 按 0 基读数组， 「已装备槽后跟空槽」的存档渲染即崩。修为 skillOf(i-1)。
    4. battle 页响应式断裂（miniapp）：引擎 raw mutation 不触发 ref 响应式， HUD 永不更新、选牌界面永不出现（软锁）。修为 step() 后 triggerRef(engine)。
    5. reachableReactions 构筑评分虚高（miniapp，dead code）：未把 incoming 元素 限定在构筑内，单元素也被算出反应。修为 if(!elements.has(incoming)) continue， 与文档契约「反应需先后两种元素都能打出」一致。

    6. 运维隐患（第 150 轮已处理 —— 原记录到此为止）¶

    本机 PostgreSQL 曾残留 1049 个孤儿 scratch 测试库（laiyipao_*_test_*）， 历次测试进程被杀 / t.Cleanup 的 DROP DATABASE 未执行累积而成，数量过大导致 PG 全量跑测时崩溃进入 WAL 恢复。已全部清理。

    ⚠️ 原记录到此为止的部分，在第 150 轮被证明是「只清不防」。 本轮实测再次累积到 406 个残留，随后： CREATE DATABASE 超时 → 种子 INSERT 撞 skill_recipes 主键（SQLSTATE 23505） → internal/service 单包 64 个用例红。跑得越多越红。

    根因不是「清得不够勤」，而是三条代码级缺陷（详见 README 工程约束 19）：

    根因 旧写法 症状
    库名每秒重复 time.Now().UnixNano()%1_000_000_000 取的是最后 9 位（秒以下） 两个用例同名，一个的 Cleanup 删掉另一个正在用的库
    DROP 超时留孤儿 t.Cleanup 10 秒预算，库一多就超时 孤儿累积
    建库失败静默跳过 任何 CREATE 失败都 Skipf("无权创建测试库") 「测试全绿」与「一半用例根本没跑」无法区分

    现已收敛到 internal/testutil/scratchdb（原先 5 个包各抄一份）， 各包 TestMain 在跑测试前按自己的前缀清理，CREATE 失败分类处理 （确实没权限才 Skip，其余 Fatal）。三条结构性守卫钉住复发： TestNoScratchNameUsesTimeModulo / TestEveryScratchPrefixIsRegistered / TestNameIsUniqueWithinProcess。

    7. ✅ 已解决：internal/service 的 skill_recipes 23505（第 150 轮引入并修复）¶

    症状¶

    scratch 库种子失败：insert recipe 32: ERROR: duplicate key value violates
unique constraint "skill_recipes_pkey" (SQLSTATE 23505)

    23505 = PostgreSQL 唯一约束冲突。一次完整跑测里 129 次建 scratch 库， 101 次在播种这一步失败；前 ~28 次正常，之后全部失败 —— 随进度劣化。

    根因¶

    internal/service/config_verify_test.go 的 TestConfigVersionIsStableAndContentDerived 用「逐类内容各改一处，哈希必须变」来验证内容哈希覆盖了所有字段：

    base := func() GameConfig { return zeroed }          // ← 浅拷贝
...
{"recipes", func(g *GameConfig) { g.Recipes[0].Output += 1 }},

    GameConfig 的切片字段在 LoadGameConfig 里是直接别名包级内容表的 （Recipes: domain.SeedRecipes）。浅拷贝让 g.Recipes[0] 与 domain.SeedRecipes[0] 指向同一个元素，于是这次「为了验证哈希而做的改动」 把进程全局内容表改掉了：SeedRecipes[0].Output 从 31 变成 32。

    此后数组里有两个 Output=32。seeder.seedSkills 用 id = r.Output*10 当主键，于是两条配方都算出 id=320 → 23505。

    同一张表里的 14 条 mutation 全都有这个问题（Enemies[0].HP、Gems[0].Descr、 Skins[0].Descr、Mastery[0].Family、Reactions[0].BaseCoef、Chapters[0].Name 都被原地改写）。只是 recipes 恰好是唯一有主键的，于是只有它炸。

    为什么排查这么久¶

    症状与病因隔了整整一层抽象，且看起来不是数据库问题：

    假设 实测结果
    残留孤儿库压垮 PG 跑前清空所有 laiyipao*_test*，仍复现
    库名碰撞（UnixNano()%1e9 每秒重复） 129 个库名全部唯一
    建出来的库不干净 播种前逐个查 count(*) FROM skill_recipes，129 个全是 0
    连错库 SELECT current_database() 与请求的 DSN 逐个一致
    t.Parallel() 并发 包内零命中；-parallel 1 仍复现
    迁移里塞了种子 迁移只往 user_tasks 插数据
    内容表被谁改写 全仓库无 append/赋值 —— 直到把 domain.SeedRecipes 的运行期值也打出来

    最后那条是关键。源文件里 18 条配方 Output 是 31..48、无重复（逐条核过）， 但诊断日志打出 SeedRecipes 条数=18 重复=[Output=32 出现 2 次] —— 源文件与运行期值不一致，说明它被就地改写过。 顺着「谁能写它」查到 config_verify_test.go:154。

    修法¶

    1. base() 改为 JSON round-trip 深拷贝。GameConfig 本来就要被 marshal 下发， 所以这是最贴合上下文的做法，且新增字段自动覆盖，不用手工维护拷贝列表。
    2. 加一条「全局内容表没被动过」的收尾断言。 这条是关键：深拷贝失效的症状远在几百行之外（上百个用例红）， 而这里当场红。把「测试污染全局状态」从地雷变成红线。
    3. 在 internal/domain 加三条配方完整性守卫（recipes_integrity_test.go）： Output 唯一、按播种公式算出的 id 唯一、(a,b) 唯一。 第三条防的是另一种静默故障 —— 重复的 (a,b) 会让两条配方互相 ON CONFLICT DO UPDATE，结果配方少一条、产物被悄悄换掉，且不报任何错。

    连带修掉的两个问题¶

    ① scratchdb 的 DROP 从来没执行成功。 新加的失败日志把它喊了出来： [scratchdb] 删除 ... 失败：closed pool。原因是 DSN() 里的 defer p.Close() 在函数返回时就关了池，而 t.Cleanup 是之后才跑的。 清理逻辑「看起来写了」、Sweep 也在跑，只是每个库都悄悄留成孤儿 —— 正是这个包要根治的症状。修法：cleanup 里自己开池。 修完残留从 15–278 降到 0。

    ② TestLeaderboardKinds 是条「跑得越多越红」的测试。 它的断言是 「三个榜的前 50 里必须有我」，而共享测试库里前 50 被历次跑测留下的 几千个用户瓜分 —— 库越脏越容易掉出去（实测 stage 榜已稳定失败）。 该用例自己的注释早就写着「依赖『表还不够脏』的断言不是断言，是运气」， 第 82/83 轮为此改过两次口径，但只要还在共享库里就只是更难的运气游戏。 改用一次性库根治。

    教训¶

    这三条（浅拷贝污染全局、cleanup 用已关闭的池、断言依赖共享库的脏度） 都是同一类：症状出现在离病因很远、且看起来毫不相干的地方。 第 ① 条尤其值得记住 —— 它是这一轮我自己引入的， 而且症状（孤儿库残留）与它的直接后果（DROP 静默失败）之间隔了 「清理钩子」这一层，不加失败日志就只会看到「残留又回来了」。

    8. 「服务端有扣减逻辑」不等于「玩家能用」：道具闭环的三段（第 151 轮）¶

    8.1 问题¶

    第 148–150 轮先后把三种道具的消费端点接上了：

    道具 消费端点 效果
    mastery_reset POST /mastery/reset 清空 user_mastery_nodes
    revive_token StartBattle（开战时） 扣 1 枚，本关 base_hp ×1500‰
    gem_wash_token POST /me/gems/:id/wash 重 roll 词条，品质不变

    每一条都有测试、都通过了、三口径守卫里的 PENDING_TOKENS 变成空表。 按当时的汇报口径，C 口径 100%。

    那是高估。 三种道具的唯一发放途径是商城（签到、任务、成就、兑换码都不发它们）， 而 miniapp 没有商城页 —— fetchShop / buyItem 两个 API 函数 从写下来那天起就没有任何页面调用方。

    于是玩家的实际体验是：首页菜单里点不到商城，服务端扣减逻辑齐全， 道具数量永远是 0。代码完成度 100%，机制完成度 0。

    8.2 为什么三段里最容易漏掉第三段¶

    前两段都有明确的完成信号：端点能通、测试能红绿。 第三段「玩家从哪个界面拿到它」没有守卫 —— 没有任何测试会问这个问题， 因为它跨越了「服务端 OK」这条线，而那条线恰好是此前所有汇报的边界。

    补 gem_wash_token 时本来还会更严重：它的前置还包括 ① gem_affixes 灌种子（此前表建好了却是 0 行） ② 宝石有获取途径。两件都做完才有洗练可洗。

    8.4 定价：真机跑出来才发现定错了¶

    gem_wash_token 初版定 120,000 金币。真机 E2E 时账号只有 52,000，买不了。

    回头算：domain/battle.go 的金币产出是 CoinBase 200 + 每星 150 + 每击杀 20， 三星十杀约 850/局 —— 120,000 要打 140 局， 而同表最便宜的消耗品「续战令」只要 5,000。两个消耗品差 24 倍， 定的人自己都觉得不对劲。

    「怕玩家买灰宝石反复洗」那个理由也站不住：宝石 60 钻石 ≈ 一个金币箱的量， 洗一次就要再赚一个金币箱，刷不出金色。

    改为 30,000（约 35 局，续战令的 6 倍）。 教训：平衡数值不该只靠「参照同表」推出来，必须在真机上跑一次购买链路。

    9. 第 152 轮：把两个「待标定」占位值真正量出来，其中一个是无效的¶

    9.1 起因¶

    上一轮收口时留了两个占位值：

    • domain.SeedGemAffixes 的词条区间 —— 注释写「参照 defaultAttacker 反推」
    • domain.ReviveBaseHPMultPermille = 1500 —— 注释写「需按真实关卡分布标定」

    这一轮的任务就是给出数字。做法一致：先量可测的量，再定值。

    9.2 宝石：量出来的结论改写了内容表¶

    量了三件事，全部来自生产代码与实测：

    属性 硬上限 装备+专精已占 结论
    attack 1000 1080（TestAttackBudgetIsAlreadyExhausted 实测） 满配后攻击宝石价值恒为 0
    armor 750 455（TestArmorBudgetHasRoomForScaling 实测） 余 295，宝石能填
    crit 500 0 宝石唯一来源
    element_coef 1000 0 宝石唯一来源
    reaction_mult 800 0 宝石唯一来源
    heat_cap 600 0 宝石唯一来源
    element_cap base 3 / Max 8 0 唯一来源，且是天花板不是倍率

    三条设计决定：

    1. 攻击宝石的区间压到 5–20（原 20–60）。满配玩家身上它被 clampPermille 整个吃掉 —— 玩家花钱看到词条却毫无变化，比数值小更糟。 留一点是因为 user_equipment 初期为空。
    2. 装备不给的那四条给足，三颗金宝石满配占各自上限 20%–48%。
    3. element_cap 不随品质放大（新增 domain.UnscaledGemAffixes）。 它是「堆叠到顶就停止累积」的天花板，×2 只会把总值推过 MaxElementCap=8 然后被下游 clamp 静默吃掉。

    全部结论写成 service/gem_balance_pins_test.go 的断言 （沿用 internal/domain/balance_scale_pins_test.go 的既有做法）。

    9.3 复活币：任何数值都无效，已重新下架¶

    引擎实跑 100 关（miniapp/src/game/revive_bonus_is_inert.test.ts）：

    普通怪漏怪伤害 = baseHpMax / LeakDamageDivisor   // 与血量同步缩放
可承受漏怪数   = baseHpMax / (baseHpMax/10) = 10 // 与倍率无关
    结果
    漏怪数不同的关卡 1 / 100（L96：100 → 99，两局都是 lost）
    结局从 lost 翻成 won 的关卡 0
    击杀数 / 通关时间不同的关卡 0

    那 1 关的差值来自 baseHpMax*attack/3600 的整数截断（attack=5 时 10000/3600→13 而 15000/3600→20，比值 0.65 而非 0.667），属噪声。

    结论：把 base_hp 抬到任何倍率，可承受的漏怪数恒为 LeakDamageDivisor。 applyArmor 是乘法，也不改变这个比值。

    所以它重新下架了。让玩家花 5,000 金币买一个没有效果的东西，比不卖更糟。

    9.4 这修正了上一轮的一处错误汇报¶

    第 150 轮汇报「复活币接通消费端点，C 口径 100%」。端点确实接通了， 但效果层面是错的 —— 玩家花了 5,000 金币什么也没换到。

    这暴露了 C 口径（道具/机制有消费闭环）只覆盖了扣减端点， 管不了「扣减之后有没有效果」。因此把守卫分成三档：

    档 含义 补法
    无登记 有端点且效果成立 —
    PENDING_TOKENS 还没写端点 写一个扣减端点
    INEFFECTIVE_TOKENS（新增） 有端点、效果不成立 改效果本身，往往要动引擎

    两者必须分开记，否则「待接通」与「效果无效」再也分不清。 TestIneffectiveTokensReallyHaveSpendCall 守住这个边界。

    9.5 守卫自身的两个洞（都是变异测试发现的）¶

    1. worst = ... 写成了赋值而不是取最大值。同一条词条被 5 种宝石提供时， 它量到的是「词条表里最后一条」的区间而不是最坏的一条 —— 看起来在管预算，实际只管了顺序。把 gem_atk 的 attack 调大一倍 （它恰好是第一条），守卫完全无反应。
    2. 「至少有一条值得的词条」原本把 attack 算作有效， 而满配玩家身上 attack 完全无效 —— 等于给一件只有新玩家用得上的东西 发合格证。改成跳过装备已吃满的属性。

    另外一处不是守卫的洞：第一版「漏怪数一个都不变」的断言被 L96 反驳了。 已改成不夸大的判据：「0 关翻盘」+「变好的关卡数 ≤ 5%」。

    10. 第 153 轮：复活币真正修好，并把「加成被自己的分母抵掉」写成通用判据¶

    10.1 起点¶

    第 152 轮量出 ReviveBaseHPMultPermille 任何倍率都无效，把它重新下架了。 这一轮做真正的修复。

    10.2 护甲这条备选：量过，放弃¶

    直觉上「+250‰ 护甲」最省事（applyArmor 是乘法、不需要改引擎）。但量了一下：

    值
    MAX_ARMOR 750
    装备贡献 215（实测）
    专精满配 240
    宝石（标定后满配 3 颗金） 144
    合计 599 + 关卡自带 50–200

    applyLoadout 把装备+专精+宝石那一坨 clamp 到 MaxArmorPermille = 750， applyArmor 又把总值 clamp 到 MAX_ARMOR = 750。 满配玩家的护甲已经贴着天花板，+250 会被整个吃掉 —— 和倍率型一个命运。

    量完就放弃了，没写代码。

    10.3 做法：加在当前血量上，baseHpMax 不动¶

    引擎里 baseHp（当前）与 baseHpMax（上限）本来就是两个字段， 而漏怪伤害只看后者：

    初始血量 = baseHpMax + extra_base_hp
每次漏怪 = baseHpMax / 10          ← 分母没变
→ 多扛 extra_base_hp / (baseHpMax/10) 次

    语义定为「多扛 N 次漏怪」而不是「血量 +X%」：前者是玩家能理解的单位， 且与关卡血量缩放无关 —— 跨 100 关都是同一个「次数」。

    ReviveExtraLeakCount = 3 的依据：

    战斗金币产出 CoinBase 200 + 每星 150 + 每击杀 20 → 三星十杀约 850/局
续战令 5,000 金币 ≈ 6 局
多扛 3 次漏怪 ≈ 一关里 30% 的漏怪额度

    即：花 6 局的钱换「本来会漏死的那一波再多挨三次」。

    10.4 anti-cheat：extra_base_hp 必须进 replay hash¶

    prefix 原本是 L${level.id}|A${attacker}|S${skills}，不含 base_hp —— 因为 base_hp 由 level.id 唯一确定。

    extra_base_hp 不同：它不在关卡里、也不由 level.id 决定， 而服务端不重算 hash（battle_records.replay_hash 只是存）。 所以客户端改本地这一行就能白扛无数次漏怪。 它必须进 prefix 的 |X 段。未复活时写 |X0 而不是省略整段， 避免「有前缀 / 无前缀」两种长度将来混淆。

    10.5 跨端常量一致性¶

    Go 新增 domain.LeakDamageDivisor。它必须与 miniapp/src/game/engine.ts 的 LeakDamageDivisor 完全一致 —— 服务端按它算「多扛 3 次」，引擎按自己的值扣血， 偏差不报错、不 panic，只让道具效果偏掉。

    守卫 revive_contract_test.go 读 engine.ts 源码文本核对 （本包是纯 Go，import TS 不可能；而两边各写各的正是要防的事）。

    10.6 守卫：断言必须拆开，否则无效实现照样能过¶

    TestReviveTokenGrantsExtraBaseHPAndIsSpent 拆成三半：

    断言 挡住什么
    ExtraBaseHP > 0 「扣了币什么都没给」
    Level.BaseHP == 原值 回到那个无效实现（抬高它会同步抬高漏怪伤害）
    ExtraBaseHP == N 次漏怪的伤害 语义漂移（「多扛 3 次」不再是 3 次）

    只断言第一条的话，第 148–152 轮那个无效实现照样能通过 —— 而它当时就是 这么绿的。

    另有 TestReviveDoesNotTouchGeneratedLevel 断言 「revive.go 里不得再出现 ReviveBaseHPMultPermille」。

    客户端 revive_extra_hp.test.ts 三条： 上限不变 / 多扛次数 = 漏怪额度 / |X 进 hash（改本地会被 hash 看出来）。
