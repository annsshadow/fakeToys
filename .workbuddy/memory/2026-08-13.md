## 后续会话：SeaORM 实体↔表 对账闭环（已校验事实优先）

### 结论
消除全部 `*_core_entity` 类 SeaORM 实体的 list 端点运行时 500。最终 `bash scripts/parity_sweep.sh`：**0 failure(s) / 41 endpoint(s) — PARITY OK**（41 = 9 基线 + 32 核心实体模块 list 端点）。当前运行服务（PID 23596，`target/debug/oa4rust.exe`）已含全部改动，重跑仍 41/41。

### 根因分类与修复
1. **缺失表**：`x_ai_app/x_ai_conversation`（026）、`x_ai_model`（027）、CMS `x_cms_category/x_cms_article`（028）、33 个 `*_core_entity` 表（029）。
2. **缺失列**：`x_script.creator_person/deleted_at`、`x_org_group.parent_id/level`、`x_org_identity.person_id`（030）、`x_org_identity.type_`（031）。
3. **SeaORM `type_`→`type` 归一化陷阱**：`cal_calendar`/`org_definition`/`org_identity` 实体字段 `type_` 被映射为保留字 `type`，PG 报 `42703 column X.type does not exist`。修复：实体加 `#[sea_orm(column_name = "type_")]`（保留 `type_` 列名规避保留字）。
4. **种子凭据漂移**：`testuser` bcrypt 哈希会话间失效 → 重新生成标准 bcrypt 写入 `auth_person.password_hash`。

### 关键诊断手段
SeaORM handler 一律吞底层错误返回 `AppError::Internal`；定位时临时在 `.map_err` 注入 `tracing::error!` + `RUST_LOG=debug` 抓真实 PG 错误码，确认后回退注入保持代码干净。

### 产出物
- 迁移 026–031（+ 各自 rollback）。
- 实体改动：`calendar_core_entity/entities/cal_calendar.rs`、`organization_core_entity/entities/org_definition.rs`、`org_identity.rs`（加 `column_name="type_"`）。
- `scripts/parity_sweep.sh`：可复用回归闸门（登录 + 41 个 list 端点断言 `type=="success"`，支持 `TOKEN=` 复用缓存令牌规避登录限流）。
