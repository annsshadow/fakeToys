    06 · 规模化训练：从单卡到集群¶

    一句话定位：模型一旦大到单张卡装不下、单张卡算不快，训练的核心难题就从"怎么学"变成"怎么把参数、梯度、优化器状态、激活塞进有限显存，再把算力铺到成百上千张卡上"——这一篇讲的全是省显存和分摊算力的工程手段。

    本篇先把 torchgpt/train.py 已经实现的三件事（AMP 混合精度、梯度累积、梯度裁剪）讲透，再把本项目未实现但工业必备的手段（梯度检查点、DDP、张量/流水线并行、ZeRO/FSDP）讲清原理与适用场景，并给出 torchrun 启动示意。

    1. 直觉：显存是第一瓶颈，先算一笔账¶

    训练一个模型，显存被四样东西吃掉：

    1. 参数（weights）：模型本身。
    2. 梯度（gradients）：和参数一样多，backward 后每个参数配一份梯度。
    3. 优化器状态（optimizer states）：AdamW 要为每个参数存一阶动量 m 和二阶动量 v（见上一篇 optim.py），两份，又和参数一样多。
    4. 激活（activations）：前向过程中每一层的中间输出，反向时要用它们算梯度，所以得缓存着。激活量随 batch × 序列长度 × 层数 增长，常是显存最大的变量。

    一个粗略但好用的估算：用 FP32（4 字节） 训练，光参数 + 梯度 + Adam 的 m/v 就是 每参数 16 字节（4+4+4+4）。所以 1B（十亿）参数的模型，还没算激活，就要 16 GB——这还是最省的估计。这就是为什么"规模化训练"几乎等同于"想方设法省显存 + 把这些份额拆到多卡上"。

    记住这个 16 bytes/param（FP32 下参数+梯度+Adam 两态）的数字，下面所有技术都是在和它作斗争。

    2. 混合精度 AMP：用 FP16/BF16 省显存提速¶

    torchgpt/train.py 的训练循环已经实现了 AMP（来源：torchgpt/train.py）：

    use_amp = tc.amp and device.startswith("cuda")
# torch 2.4+ 统一 AMP API；enabled=False 时是完全直通（no-op）
scaler = torch.amp.GradScaler("cuda" if use_amp else "cpu", enabled=use_amp)
...
with torch.autocast(device_type="cuda" if use_amp else "cpu", enabled=use_amp):
    _, loss = model(x, y)
    loss = loss / tc.grad_accum_steps
scaler.scale(loss).backward()

    旧代码常见 torch.cuda.amp.GradScaler(...)，自 torch 2.4 起弃用（2.14 会发 FutureWarning），统一换成 torch.amp.GradScaler(device, ...) 即可。

    原理：默认 FP32（32 位浮点）精度高但又占显存又慢。AMP（Automatic Mixed Precision，自动混合精度）让大部分运算（矩阵乘、卷积）用 FP16 或 BF16（16 位）跑——显存减半、现代 GPU 的 Tensor Core 对 16 位有数倍吞吐——而把对精度敏感的部分（如 LayerNorm、softmax、loss 累加）留在 FP32。torch.autocast 这个上下文管理器自动决定每个算子用哪种精度，这就是"混合"。

    FP16 vs BF16：两者都是 16 位。FP16 尾数多、精度高但动态范围窄，很小的梯度会下溢成 0；BF16 用更多位表示指数，动态范围和 FP32 一样宽、几乎不用额外处理，但尾数少、精度略低。A100/H100 等新卡上 BF16 是首选，老卡（如 V100）常用 FP16。

    loss scaling（损失缩放）与 GradScaler：FP16 的致命问题是小梯度下溢为 0。对策是前向算完 loss 后乘一个大系数（比如 1024）再 backward，让梯度整体放大、落回 FP16 能表示的范围；更新前再把梯度除回去。这正是 GradScaler 干的事：scaler.scale(loss).backward() 放大，更新时 scaler.unscale_ 还原、scaler.step/update 自动调整系数（遇到 inf/nan 就跳过这步并调小系数）。BF16 范围够宽，通常不需要 loss scaling——这也是它更省心的原因。注意 torchgpt 里 use_amp 要求 device 是 cuda，CPU 上这套不启用。

    3. 梯度累积：用小 batch 等效大 batch¶

    显存装不下大 batch 怎么办？torchgpt/train.py 用梯度累积（来源：torchgpt/train.py）：

    opt.zero_grad(set_to_none=True)
for _ in range(tc.grad_accum_steps):          # 梯度累积
    x, y = get_batch(train_data, tc.batch_size, cfg.block_size, device)
    with torch.autocast(...):
        _, loss = model(x, y)
        loss = loss / tc.grad_accum_steps      # 关键：除以累积步数
    scaler.scale(loss).backward()
scaler.unscale_(opt)
torch.nn.utils.clip_grad_norm_(model.parameters(), tc.grad_clip)
scaler.step(opt); scaler.update()

    原理：不是一次喂一个大 batch，而是连续跑 grad_accum_steps 个小 batch，每个都 backward()。因为梯度是累加的（上一篇讲过 autograd 用 +=），grad_accum_steps 个小 batch 的梯度自然叠加在一起，等价于一个 grad_accum_steps × batch_size 的大 batch——但峰值显存只需装得下一个小 batch 的激活。累积完才 step() 更新一次。

    那行 loss = loss / tc.grad_accum_steps 不能漏：大 batch 的 loss 是所有样本的平均，而累加梯度得到的是求和。先把每个小 batch 的 loss 除以步数，累加起来才等于平均梯度，否则有效学习率会被放大 grad_accum_steps 倍。

    代价：时间换显存——跑 N 个小 batch 比跑 1 个大 batch 慢（但激活峰值不变）。TrainConfig.grad_accum_steps 默认 1（不累积），注释写得明白："显存不够时放大它，等效于更大 batch"。

    4. 梯度裁剪：防梯度爆炸¶

    scaler.unscale_(opt)
torch.nn.utils.clip_grad_norm_(model.parameters(), tc.grad_clip)   # 梯度裁剪

    原理：训练偶尔会遇到异常大的梯度（坏样本、数值问题），一步就能把参数更新到崩坏，loss 变 nan。梯度裁剪给所有参数梯度拼成的总范数设一个上限 grad_clip（本项目默认 1.0）：若 $|g| > \text{clip}$，就把整个梯度向量按比例缩小到范数正好等于 clip，方向不变、只缩长度。

    $$g \leftarrow g \cdot \frac{\text{clip}}{\max(|g|,\ \text{clip})}$$

    顺序很重要：必须先 scaler.unscale_(opt) 把梯度从"被 loss scaling 放大过"的状态还原回真实尺度，再裁剪——否则裁的是放大后的假梯度，阈值就没意义了。torchgpt 的顺序 unscale_ → clip_grad_norm_ → step 是标准写法。

    至此，torchgpt/train.py 里"真·工业训练循环"的三板斧——AMP、梯度累积、梯度裁剪——就齐了。它还做了周期性 torch.save checkpoint（estimate_loss 后 torch.save({"model": ..., "cfg": ..., "step": ...})），保证中断能续、崩了能恢复。下面是本项目没有实现、但真正上规模必备的内容。

    5. 梯度检查点：用算力换显存¶

    本项目未实现，概念 + 适用场景。

    第 1 节说过，激活常是显存最大的吃货——为了反向传播，前向时每一层的中间输出都得缓存着。梯度检查点（gradient checkpointing，又叫 activation checkpointing）的思路是：前向时只保存少数几个"检查点"层的激活，中间的全部丢掉；反向需要用到某段激活时，再从最近的检查点重新前向算一遍。

    这是一笔时间换空间的交易：激活显存从 $O(L)$ 降到约 $O(\sqrt{L})$（L 为层数），代价是多做一次前向（训练慢约 20~30%）。当"显存不够导致根本训不了"时，慢 30% 远胜于跑不起来。

    PyTorch 用 torch.utils.checkpoint.checkpoint(block, x) 包住某个 Block 即可启用。它和梯度累积（第 3 节）常常一起用：一个砍激活峰值、一个砍 batch 峰值。何时用：单层/单卡激活就爆显存、或想在同样显存下跑更长序列、更大 batch 时。

    6. 数据并行 DDP：最常用的多卡起点¶

    本项目未实现，概念 + 启动示意。

    原理：数据并行（Distributed Data Parallel）是最简单、最常用的多卡方案。每张卡上放一份完整的模型副本，各自吃不同的数据分片跑前向和反向；反向后，所有卡通过 all-reduce 通信把各自的梯度求平均，于是每张卡拿到的是全局平均梯度、各自用它更新——所有副本始终保持一致。N 张卡约等于把有效 batch 扩大 N 倍、吞吐提升近 N 倍。

    torchgpt/train.py 的文件头注释已经点了方向："单机多卡请用 torchrun --nproc_per_node=N 启动并包一层 DDP"。改造示意（概念代码，非本项目实现）：

    # torchrun --standalone --nproc_per_node=8 train.py
import torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group(backend="nccl")        # GPU 间用 NCCL 通信
local_rank = int(os.environ["LOCAL_RANK"])     # torchrun 注入的环境变量
torch.cuda.set_device(local_rank)

model = GPT(cfg).to(local_rank)
model = DDP(model, device_ids=[local_rank])    # 包一层，梯度 all-reduce 自动发生
# 之后训练循环几乎不变；每个进程喂不同数据分片，checkpoint 只在 rank 0 保存

    DDP 和梯度累积天生互补：累积的中间步可以用 model.no_sync() 跳过通信，只在最后一步 all-reduce，省带宽。局限：DDP 要求每张卡放得下整个模型（含梯度和优化器状态）。模型大到单卡装不下，DDP 就无能为力了——这时需要下面的"切模型"方案。

    7. 模型并行与流水线并行：把模型本身切开¶

    本项目未实现，概念。

    当模型单卡都装不下，就得把模型本身拆到多张卡：

    • 张量并行（Tensor Parallelism）：把单层内部的大矩阵乘沿行或列切到多张卡，每张卡算一部分，再通过通信拼起来。比如一个 Linear 的权重按列切成 N 份，N 张卡各算一段输出。它在层内并行，通信频繁（每层都要同步），所以通常只在单机内部（NVLink 高带宽）用。Megatron-LM 是代表。

    • 流水线并行（Pipeline Parallelism）：把模型按层切成若干段，不同段放不同卡——第 1~8 层在卡 A，9~16 层在卡 B……数据像流水线一样逐段流过。朴素做法下，卡 B 等卡 A 算完才能开工，产生"气泡"（空等）。对策是把一个 batch 切成多个 micro-batch 流水起来填满气泡（GPipe、PipeDream）。它在层间并行，通信量小，适合跨机。

    实践中大模型往往把这几种组合使用：机器内张量并行 + 机器间流水线并行 + 外层数据并行，即所谓 3D 并行。

    8. ZeRO / FSDP：把"参数+梯度+优化器状态"也分片¶

    本项目未实现，概念。

    回到第 1 节的账：DDP 虽然分摊了算力，但每张卡都存了一整份参数、梯度、优化器状态（那 16 bytes/param），纯属冗余。ZeRO（Zero Redundancy Optimizer，DeepSpeed 提出）和 PyTorch 原生的 FSDP（Fully Sharded Data Parallel）就是来消灭这个冗余的：把这三样沿卡切片，每张卡只存 1/N。

    ZeRO 分三级，省得越来越狠：

    • Stage 1：只分片优化器状态（Adam 的 m/v，占比最大）。
    • Stage 2：再分片梯度。
    • Stage 3（≈ FSDP）：连参数也分片。某层要用到完整参数时，临时 all-gather 拼齐，用完即丢。

    效果是单卡显存占用近似降到 1/N，让超大模型得以训练，代价是更多通信。选型直觉：模型能塞进单卡 → DDP 最省事；塞不进 → 上 FSDP/ZeRO-3；再不够 → 叠加张量/流水线并行。FSDP 用法上类似 DDP 包一层 FullyShardedDataParallel(model)，但要配 auto_wrap_policy 指定按什么粒度分片。

    9. 显存占用估算：把账算到底¶

    把第 1 节的账正式写成公式，设参数量为 $N$：

    组成 FP32 占用 混合精度（AMP）典型占用
    参数 $4N$ $2N$（FP16 副本）$+ 4N$（FP32 主副本）
    梯度 $4N$ $2N$
    优化器状态（Adam m+v） $8N$ $8N$（FP32）
    小计（不含激活） $16N$ 约 $18N$
    激活 随 batch×序列×层数变化 同左（可被梯度检查点压到 $O(\sqrt L)$）

    两个反直觉的点：

    1. 混合精度不一定省"模型态"显存。为保持数值稳定，AMP 常额外保留一份 FP32 主参数（master weights），所以参数+梯度+优化器状态加起来不比 FP32 少多少（上表 ~18N vs 16N）。AMP 真正省的是激活（FP16 激活减半）和算得更快，而不是优化器状态。要砍优化器状态，得靠 ZeRO/FSDP 分片（第 8 节）。
    2. 优化器状态是大头。Adam 的 m+v 占 $8N$，是参数本身的两倍。这就是为什么 ZeRO Stage 1 先拿它开刀——分片收益最大。

    一道速算：7B 参数、FP32、单卡训练，模型态就要 $16 \times 7\text{B} = 112$ GB，远超单张 80 GB 卡——所以 7B 全参训练必须多卡分片。反过来，推理只需参数本身（$2N$ FP16 ≈ 14 GB），单卡绰绰有余。这解释了"训练比推理吃显存得多"的根本原因：梯度和优化器状态只在训练时存在。

    可以拿上一篇第 8 节的参数量公式 $N \approx 12\,n_embd^2 \cdot n_layer$ 先估 $N$，再套这张表估训练显存——这是开训前该做的第一个心算。

    10. 常见坑¶

    1. CPU 上开 AMP。GradScaler/FP16 Tensor Core 是 GPU 的事；torchgpt 用 device.startswith("cuda") 把 use_amp 关掉就是防这个。CPU 上强开 FP16 往往更慢甚至报错。
    2. 梯度累积忘了除。漏掉 loss = loss / grad_accum_steps，有效学习率被放大 grad_accum_steps 倍，训练发散。
    3. 裁剪在 unscale 之前。loss scaling 放大过的梯度直接裁，阈值失真。顺序必须 unscale_ → clip_grad_norm_ → step。
    4. FP16 不配 loss scaling。小梯度下溢成 0，模型"看着在跑其实没学"。要么上 loss scaling，要么换 BF16。
    5. 以为 DDP 能解决"装不下"。DDP 只分摊数据和算力，每卡仍存整个模型。装不下要用 FSDP/ZeRO 或模型并行。
    6. 多卡 checkpoint 重复/损坏。DDP 下每个进程都存一份会冲突，应只在 rank == 0 保存（torchgpt 单卡版本直接 torch.save，上多卡时要加 rank 判断）。
    7. 只算参数忘了优化器状态。按 $4N$ 估显存会严重低估，真实是 $16N$ 起步。优化器状态 $8N$ 才是训练显存的大头。

    11. 练习（基于本项目代码）¶

    1. 把累积改成等效大 batch 并验证。在 torchgpt 里用 TrainConfig(batch_size=8, grad_accum_steps=4) 和 TrainConfig(batch_size=32, grad_accum_steps=1) 各训几十步，比较 loss 曲线是否接近（有效 batch 都是 32）。再故意删掉 train.py 里 loss = loss / tc.grad_accum_steps 那行，观察 loss 怎么变化，解释为什么。

    2. 估一遍显存。用上一篇的 $N \approx 12\,n_embd^2 \cdot n_layer$ 估算 torchgpt 默认 GPTConfig(n_layer=4, n_embd=128) 的参数量，再套第 9 节的 $16N$ 公式算 FP32 训练的模型态显存。然后把 n_embd 换成 4096、n_layer 换成 32（接近 7B 级），重算，看看为什么这种规模必须多卡分片。

    3. 给训练加梯度检查点（概念实现）。阅读 torchgpt/model.py 的 GPT.forward 里 for block in self.transformer.h: x = block(x) 这段，写出用 torch.utils.checkpoint.checkpoint(block, x) 替换的改法，并说明：它省的是四类显存里的哪一类、代价是什么、在本项目这种小模型上值不值得（提示：小模型激活本就不大，检查点收益有限）。

    • Goyal et al., Accurate, Large Minibatch SGD (2017) —— 大 batch 数据并行与学习率缩放。
