    10 推理优化：KV cache、量化、投机解码与批处理¶

    一句话定位：训练只跑一次，推理要跑无数次——这一讲讲清自回归生成为什么慢，以及工业界用 KV cache、量化、投机解码、连续批处理把它榨快十倍百倍的那些招。

    直觉¶

    自回归生成是"一个字一个字往外蹦"：生成第 t 个 token，要把前面 t-1 个 token 全喂进模型跑一次完整前向。看本项目 torchgpt/model.py 的 generate：

    # torchgpt/model.py  GPT.generate
for _ in range(max_new_tokens):
    idx_cond = idx[:, -self.cfg.block_size :]
    logits, _ = self(idx_cond)          # ← 每一步都把整段上文重新前向一遍
    logits = logits[:, -1, :] / temperature
    ...
    idx = torch.cat((idx, idx_next), dim=1)

    注意那行 self(idx_cond)：每生成一个新 token，都把整段上文 idx_cond 从头跑一遍完整前向，但最后只用了 logits[:, -1, :]（最后一个位置的输出），前面所有位置的计算结果全扔了。下一步序列长了一位，又从头再算一遍——其中绝大部分是和上一步一模一样的重复计算。

    生成 T 个 token，总计算量大致是 1+2+…+T ≈ O(T²)。序列越长，浪费越离谱。这就是推理慢的根源，也是所有优化的靶子。

    原理¶

    自回归为什么是 O(T²)¶

    注意力里，位置 t 的输出需要它的 query 和前面所有位置的 key/value 做运算。关键观察：位置 1…t-1 的 key 和 value，在生成第 t 步时和第 t-1 步时是完全一样的——它们只依赖那些已经确定的 token，不会因为后面新增 token 而改变。

    但 generate 每步重新前向，等于把这些不变的 K、V 一遍遍重算。重复计算量随步数线性增长，累计就是平方级。

    KV cache：把算过的 K、V 存下来¶

    核心思想：缓存每一层、每个历史位置的 key 和 value。生成新 token 时：

    1. 只对那一个新 token计算它的 Q、K、V（而不是整段）。
    2. 把新的 K、V 追加进缓存。
    3. 新 token 的 Q 和缓存里全部 K、V 做注意力。

    这样每步只前向一个 token，总计算量从 O(T²) 降到 O(T)。生成速度质变。

    代价是显存。KV cache 的大小是：

    $$ 2 \times n_{\text{layer}} \times n_{\text{head}} \times d_{\text{head}} \times T \times \text{batch} \times \text{dtype_bytes} $$

    （因子 2 是 K 和 V 各一份）。它随序列长度 T 线性增长，长上下文下能轻松吃掉比模型权重还多的显存。这块显存怎么高效管理，正是后面 PagedAttention 要解决的问题。

    量化：用更少的比特存权重（本项目未实现，仅讲原理）¶

    把权重从 fp16/bf16（16bit）压到 int8（8bit）甚至 int4（4bit），显存和内存带宽直接减半、减四分之三。推理往往是内存带宽受限的——权重从显存搬到计算单元的速度是瓶颈，比特越少搬得越快，所以量化既省显存又提速。

    • int8：每个权重 8bit，常用线性量化 w_q = round(w / scale)，推理时反量化回去算。精度损失通常很小。
    • int4 / NF4：4bit，省得更多，但要更精细的分组量化和校准来保精度。NF4 见第 07 讲 QLoRA。
    • GPTQ：训练后量化（PTQ），逐层用少量校准数据，基于二阶信息（Hessian）贪心地量化权重并补偿误差，能在 4bit 下保持不错精度。
    • AWQ（Activation-aware Weight Quantization）：观察到少数"重要通道"对精度影响大，量化时保护这些通道（按激活幅度缩放），4bit 精度优于朴素方法。

    权重量化（weight-only）主要省显存带宽、提速；若连激活也量化（W8A8）还能用整数计算单元进一步提速，但更难保精度。

    投机解码 speculative decoding（本项目未实现，仅讲原理）¶

    让一个小而快的草稿模型一口气猜 k 个 token，再让大模型一次前向并行验证这 k 个。因为大模型验证 k 个 token 是一次前向（并行），比它自己一个一个生成 k 次快得多。被接受的保留，第一个被拒绝处起用大模型的采样纠正。

    关键：通过精心设计的接受/拒绝规则，最终输出分布和大模型单独生成完全一致——是无损加速，不牺牲质量。草稿命中率高时，能有 2~3 倍加速。伪代码：

    # 伪代码，本项目未实现
draft = small_model.generate(prefix, k)          # 小模型猜 k 个
logits = big_model(prefix + draft)               # 大模型一次并行验证
accepted = verify_and_sample(draft, logits)      # 按接受规则保留/纠正
prefix += accepted

    连续批处理与 PagedAttention / vLLM（本项目未实现，仅讲原理）¶

    服务端要同时处理很多请求：

    • 静态批处理的问题：一批请求里有的生成 10 个 token、有的生成 500 个，先结束的要干等整批结束，GPU 大量空转。
    • 连续批处理（continuous batching）：以 token 为粒度调度，谁结束就把它踢出、立刻放新请求进来，GPU 利用率大幅提升。
    • PagedAttention（vLLM 的核心）：传统 KV cache 要为每个序列预留一整块连续显存，按最大长度分配，浪费严重（内部碎片）。PagedAttention 借鉴操作系统的虚拟内存分页，把 KV cache 切成固定大小的"页"，按需分配、非连续存储，显存浪费从百分之几十降到个位数，于是能塞下更大的 batch、吞吐暴涨。相同前缀的请求还能共享物理页（prefix sharing）。

    工程上直接用 vLLM、TGI、TensorRT-LLM 这类推理引擎，而不是自己写 generate 循环。

    吞吐 vs 延迟的权衡¶

    • 延迟（latency）：单个请求多快出结果，尤其首 token 延迟（TTFT）和每 token 延迟（TPOT）。交互式聊天在意它。
    • 吞吐（throughput）：单位时间处理的总 token 数。批量离线任务在意它。
    • 两者常冲突：增大 batch 提高吞吐（GPU 算得更满），但单个请求要等凑批、也和更多请求抢资源，延迟变差。连续批处理 + PagedAttention 的意义就是把这条权衡曲线整体往外推——在可接受延迟下榨出更高吞吐。

    结合本项目代码¶

    本项目的 generate（torchgpt/model.py 和纯 NumPy 的 minigrad/sample.py）都是没有 KV cache 的朴素版，正好用来看清"不优化长什么样"；而 minigrad/sample.py 里还给出了带 KV cache 的对照实现 generate_cached（见下文），两版放在一起读，优化前后的差别一目了然。

    重看关键两行（torchgpt/model.py）：

    idx_cond = idx[:, -self.cfg.block_size :]   # 取最近 block_size 个 token 作为上文
logits, _ = self(idx_cond)                  # 对整段上文做完整前向，但只用最后一位

    教学点：self(idx_cond) 内部会跑完所有 self.transformer.h 里的 Block，每个 Block 的 CausalSelfAttention.forward 都会对整段 idx_cond 重新算 Q、K、V 和注意力（见 model.py 第 43~59 行）。可下一步循环时，除了末尾多一个 token，前面这些 K、V 和刚才算的一模一样，却被原封不动地重算了一遍。这就是 O(T²) 浪费的现场。

    纯 NumPy 版 minigrad/sample.py 的 generate 同理：

    # minigrad/sample.py
for _ in range(max_new_tokens):
    context = ids[-block_size:]
    logits = model.forward(np.array([context]))  # 整段重算
    last = logits.data[0, -1] / max(temperature, 1e-6)
    ...

    每步 model.forward(context) 都把整个 context 重新前向，和 PyTorch 版是同一种浪费，只是没有框架帮忙，更能看清每一步在算什么。

    本项目的 KV cache 实现（minigrad 轨）¶

    minigrad/nn.py 与 minigrad/sample.py 已把上面五步真实实现（这是本仓库少数"从概念变成代码"的推理优化，配了正确性测试）：

    1. 缓存挂在注意力层：CausalSelfAttention.forward(x, cache=None) 接受一个 {"k": ..., "v": ...} 字典，把新算出的 K/V np.concatenate 追加进缓存（形状 (B, n_head, T_past+T, d_head)）。
    2. 前向只喂新 token：GPT.forward(idx, caches=...) 里各 Block 把缓存传给注意力层；sample.generate_cached 先用完整 prompt 做 prefill，之后每步只喂 1 个 token。
    3. 统一 mask 公式对齐因果性：查询 i（绝对位置 T_past+i）允许看到键 j <= T_past+i，统一写成 np.triu(ones((T, T_total)), k=T_total - T + 1) * -1e9——无缓存时 T_total == T，恰好退化为普通因果 mask，一份公式覆盖两种情形。
    4. 位置编码接续：GPT.forward 用 wpe(np.arange(T_past, T_past + T)) 让新 token 拿到绝对位置，而不是又从 0 开始。
    5. block_size 上限：generate_cached 直接断言 prompt + 生成长度 <= block_size（可学习绝对位置编码的总席位上限）；超长文本仍走会滑窗的朴素 generate。

    正确性验证在 tests/test_kvcache.py，核心不变量正是上一节说的那条——KV cache 是纯粹的计算复用，不改变数学结果：

    # tests/test_kvcache.py：增量前向必须与整段前向逐 logit 一致
caches = [{} for _ in model.blocks]
out1 = model.forward(tokens[:, :5], caches=caches).data
out2 = model.forward(tokens[:, 5:], caches=caches).data   # 一次喂 7 个新 token
assert np.allclose(model.forward(tokens).data, np.concatenate([out1, out2], axis=1))

    而 torchgpt/model.py 的 GPT.generate 刻意保持朴素版——把它改造成带 KV cache（缓存挂在 CausalSelfAttention 上、pos 从缓存长度起算）是本篇练习 3 的动手题。

    常见坑¶

    1. 以为 KV cache 免费。 它拿显存换时间，显存占用随序列长度线性涨，长上下文/大 batch 下可能比权重还占显存，这正是要 PagedAttention 的原因。
    2. 加 cache 后位置编码没对齐。 只喂新 token 时若还用 pos = arange(T=1)，位置永远是 0，输出全乱。必须按缓存已有长度递增位置索引。
    3. 以为量化总是无损加速。 量化有精度损失，int4 尤其需要校准（GPTQ/AWQ）；且 weight-only 量化主要省带宽，激活量化才动整数算力但更易掉点。
    4. 投机解码草稿模型选太大或太不像。 草稿模型太大则本身就慢，和主模型分布差太远则接受率低，加速反而变负。
    5. 一味追求大 batch。 吞吐上去了，单请求延迟会变差；交互场景要盯首 token 延迟，别只看吞吐。
    6. 自己手写推理循环上生产。 教学版 generate 没有 KV cache、没有批调度，别拿它扛线上流量；生产用 vLLM/TGI/TensorRT-LLM。

    练习¶

    1. 量出 O(T²)。 用 GPT(GPTConfig())，对 max_new_tokens 取 50、100、200、400 分别计时调 GPT.generate，画出耗时随生成长度的曲线。确认它比线性增长更快（接近平方），并解释为什么——哪一行代码是罪魁。
    2. 估算 KV cache 显存。 按本项目默认 GPTConfig（n_layer=4、n_head=4、n_embd=128、block_size=128）和公式 2·n_layer·n_head·d_head·T·batch·dtype_bytes，手算在 T=128、batch=1、fp16 下 KV cache 要多少字节。再把模型换算成 n_embd=4096、n_layer=32（接近 7B 量级）、T=4096，看它涨到多大，体会"长上下文时 cache 比权重还大"。
    3. 把 KV cache 移植到 torchgpt。 minigrad 轨已有完整参照（nn.py 的 cache 参数 + sample.generate_cached + tests/test_kvcache.py）。给 torchgpt/model.py 做同样的改造：CausalSelfAttention 挂 KV 缓存、pos 从缓存长度起算、GPT.generate 加 use_cache 开关，并用"同种子下与朴素版输出完全一致"验收。
