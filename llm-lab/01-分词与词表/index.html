    01 · 分词与词表¶

    一句话定位：分词（tokenization）决定了模型"看见"的最小文字单位，是文本进入神经网络之前的第一道、也是最容易被忽视的工程关口。

    直觉：模型并不认识"字"，只认识"编号"¶

    神经网络只会做矩阵运算，它读不懂字符串 "hello"。所以在任何训练开始之前，我们必须把文本切成一个个片段（token），再给每个片段分配一个整数编号。模型真正吃进去的是这串整数，输出的也是"下一个编号最可能是谁"的概率分布。

    把分词想象成"给语言做一本字典"：

    • 字符级：字典里每个条目是一个字符。"猫" 是一条，"a" 是一条。字典小，但一句话会被切得很碎。
    • 词级：字典里每个条目是一个完整单词。"cat" 是一条，"running" 是一条。字典巨大，而且遇到没收录的词就抓瞎。
    • 子词级（BPE）：介于两者之间。常见词保留成整块（"the"），罕见词拆成碎片（"tokeni" + "zation"）。既不会词表爆炸，又不会把句子切得太碎。

    现代大模型（GPT 系列、LLaMA 等）几乎都用子词级方案，本项目的 minigrad/tokenizer.py 同时实现了字符级和一个教学版 BPE，正好对照着学。

    数学原理：词表大小的权衡¶

    设词表大小为 $V$，一段文本被切成的 token 数为 $N$。两者此消彼长：

    $$ V \uparrow \;\Rightarrow\; N \downarrow \qquad V \downarrow \;\Rightarrow\; N \uparrow $$

    • 词表越大，单个 token 承载的信息越多，序列越短，但嵌入矩阵 $(V \times d)$ 和输出投影 $(d \times V)$ 的参数量线性增长，softmax 也更慢。
    • 词表越小，参数省了，但同一句话要用更多 token 表示，而 Transformer 的注意力开销是 $O(N^2)$，序列一长就吃不消。

    BPE 的核心是一个贪心压缩过程。给定初始符号序列，反复做：

    $$ (a^*, b^*) = \arg\max_{(a,b)} \text{count}(a, b) $$

    即找出当前出现频次最高的相邻符号对 $(a, b)$，把它合并成一个新符号，然后重复，直到词表达到目标大小。这本质上是数据压缩里 1994 年提出的 Byte-Pair Encoding 算法被搬到了 NLP 上。

    结合本项目代码：字符级分词器¶

    先看最简单的 CharTokenizer（来自 minigrad/tokenizer.py）：

    class CharTokenizer:
    def __init__(self, text):
        chars = sorted(set(text))
        self.stoi = {c: i for i, c in enumerate(chars)}
        self.itos = {i: c for i, c in enumerate(chars)}

    @property
    def vocab_size(self):
        return len(self.stoi)

    def encode(self, text):
        return [self.stoi[c] for c in text]

    def decode(self, ids):
        return "".join(self.itos[i] for i in ids)

    它做的事情非常直白：

    1. sorted(set(text)) 收集语料里出现过的所有不同字符，排序后固定顺序。
    2. stoi（string-to-int）和 itos（int-to-string）是两张互逆的查找表。
    3. vocab_size 就是不同字符的个数。

    注意一个关键局限：CharTokenizer 的词表完全由构造时传入的 text 决定。如果 encode 时碰到训练语料里没出现过的字符，self.stoi[c] 会直接抛 KeyError——这就是最朴素的 OOV（out-of-vocabulary，未登录词） 问题。

    结合本项目代码：字节级 BPE 的训练¶

    BPETokenizer 的构造函数先铺好 256 个"字节 token"作为基石（来自 minigrad/tokenizer.py）：

    def __init__(self):
    self.merges = {}        # (a, b) -> 新 id
    self.vocab = {i: bytes([i]) for i in range(256)}

    这里有个重要设计选择：在 UTF-8 字节上做 BPE，而不是在字符上。任何文本 encode("utf-8") 后都是 0~255 的字节，因此初始的 256 个 token 能表示世界上任何字符串——这从根本上消除了 OOV：最坏情况也能退化成逐字节表示。

    统计相邻对：_pair_counts¶

    @staticmethod
def _pair_counts(ids):
    counts = Counter()
    for a, b in zip(ids, ids[1:]):
        counts[(a, b)] += 1
    return counts

    zip(ids, ids[1:]) 是一个经典技巧：把序列和"错开一位的自己"配对，就得到了所有相邻对 $(a, b)$。Counter 累加每个对出现的次数。

    执行一次合并：_merge¶

    @staticmethod
def _merge(ids, pair, new_id):
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            out.append(new_id)
            i += 2
        else:
            out.append(ids[i])
            i += 1
    return out

    扫描一遍序列：一旦连续两个 token 正好等于要合并的 pair，就用 new_id 替换这两个并跳过（i += 2）；否则原样抄下来（i += 1）。

    训练主循环：train¶

    def train(self, text, vocab_size=512):
    assert vocab_size >= 256
    ids = list(text.encode("utf-8"))
    for new_id in range(256, vocab_size):
        counts = self._pair_counts(ids)
        if not counts:
            break
        pair = max(counts, key=counts.get)
        ids = self._merge(ids, pair, new_id)
        self.merges[pair] = new_id
        self.vocab[new_id] = self.vocab[pair[0]] + self.vocab[pair[1]]
    return self

    逐行看这个贪心过程：

    • ids = list(text.encode("utf-8"))：文本先变成字节序列。
    • for new_id in range(256, vocab_size)：新 token 的编号从 256 开始递增，每一轮产生一个新 token。
    • pair = max(counts, key=counts.get)：这正是上面公式里的 $\arg\max$——挑出当前最高频的相邻对。
    • self.merges[pair] = new_id：记下"规则"，即 $(a, b) \to$ 新 id。merges 是一个 dict，插入顺序就是合并的先后顺序，这一点在编码时至关重要。
    • self.vocab[new_id] = self.vocab[pair[0]] + self.vocab[pair[1]]：新 token 对应的字节串，就是两个子 token 字节串的拼接。
    • if not counts: break：序列已无相邻对（长度 ≤ 1）时提前停止。

    结合本项目代码：编码与解码¶

    def encode(self, text):
    ids = list(text.encode("utf-8"))
    # 按合并先后顺序反复应用规则
    for pair, new_id in self.merges.items():
        ids = self._merge(ids, pair, new_id)
    return ids

def decode(self, ids):
    data = b"".join(self.vocab[i] for i in ids)
    return data.decode("utf-8", errors="replace")

    encode 把新文本转成字节后，按训练时学到的顺序依次套用每条合并规则。顺序不能乱：早学到的规则（更高频）必须先应用，否则压缩结果会不一致。

    decode 则把每个 id 还原成字节串拼起来，再 decode("utf-8")。注意 errors="replace"：BPE 合并可能切断一个多字节 UTF-8 字符的中间，单独解码会失败，用 replace 兜底成 � 而不崩溃。本项目测试 tests/test_tokenizer.py::test_bpe_roundtrip_ascii_and_unicode 验证了只要是完整文本的往返，中英文都能无损还原。

    中文分词的特殊性¶

    • 英文有空格天然分词，中文没有。传统中文 NLP 要先用分词工具（jieba 等）切词，再建词表。
    • 字节级 BPE 优雅地绕开了这个问题：它根本不关心"词"的边界，直接在 UTF-8 字节上统计高频对。一个常用汉字是 3 个 UTF-8 字节，高频汉字/词组会被 BPE 自动合并成单个 token。这就是 GPT 系列不需要专门中文分词器也能处理中文的原因。
    • 代价是：中文 token 的"字节效率"低于英文。同样信息量，中文往往消耗更多 token，这也是很多 API 对中文计费显得"更贵"的根源之一。

    常见坑 / 误区¶

    1. 以为 BPE 在"字符"上合并——本项目明确在字节上合并（text.encode("utf-8")）。字符级会遇到 OOV，字节级永不 OOV。
    2. 忽视 merges 的顺序——它是 dict 且依赖插入顺序。encode 必须按训练顺序套用规则，打乱会得到错误（且不可逆）的编码。
    3. 期待任意 id 片段都能 decode 成合法中文——因为合并可能切断多字节字符，单独取几个 id 解码可能出现 �。只有完整往返才保证无损。
    4. 词表越大越好——忘了嵌入/输出层参数随 $V$ 线性增长、softmax 变慢。词表大小是要调的超参，不是越大越香。
    5. 字符级分词器跨语料复用——CharTokenizer 的词表绑死在构造语料上，换一段含新字符的文本就 KeyError。

    动手练习¶

    1. 观察合并规则：用 data/tiny_corpus.txt 的内容训练一个 BPE，打印前 10 条 merges 及其对应的 vocab 字节串，看看哪些高频片段最先被合并。
    from minigrad.tokenizer import BPETokenizer
text = open("data/tiny_corpus.txt", encoding="utf-8").read()
tok = BPETokenizer().train(text, vocab_size=300)
for i, (pair, nid) in enumerate(list(tok.merges.items())[:10]):
    print(nid, tok.vocab[nid])

    1. 压缩率曲线：固定一段文本，让 vocab_size 取 260、300、400、512，分别记录 len(tok.encode(text))。画出"词表大小 vs 编码长度"的关系，直观感受 $V \uparrow \Rightarrow N \downarrow$ 的权衡（可参考 tests/test_tokenizer.py::test_bpe_merges_shrink_sequence 的思路）。

    2. 对比两种分词器：对同一段中英混合文本，分别用 CharTokenizer 和训练好的 BPETokenizer 编码，比较 token 数量，并故意给 CharTokenizer.encode 喂一个训练语料里没有的字符，复现 KeyError，再解释为什么 BPETokenizer 不会出现这个错误。
