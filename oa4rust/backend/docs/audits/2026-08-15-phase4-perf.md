# OA4RUST Phase 4 — Performance Baseline

**Date:** 2026-08-15
**Scope:** Add a compile-checked, `#[ignore]`d performance baseline integration test.
No production code, `integration_runner.rs`, or `integration_tests/scenarios/mod.rs` modified.
**CI impact:** None — the new test is `#[ignore]`d and a separate `[[test]]` target, so the existing green gate is untouched.

---

## 1. Methodology

A new standalone integration test lives at `tests/perf_baseline.rs`. It mirrors the
existing runner harness (`tests/integration_runner.rs`) but is a **separate test target**
(`perf_baseline`), so it does not alter the existing `integration_runner` or scenario flow.

Per run it:

1. Calls `integration_tests::db::init_test_database()` to spin up the disposable
   `oa4rust_test_<pid>` Postgres database, run all migrations, and inject the seeded
   admin (`it-admin` / `password123`) plus an active session/token.
2. Boots the full app via `integration_tests::helpers::setup_test_server(pool)`, returning
   `(SocketAddr, JoinHandle, token)`.
3. Warms up the connection pool with `WARMUP = 5` request pairs that are **not** timed.
4. Runs `ITERATIONS = 50` measured iterations, timing each request with
   `std::time::Instant` (wall-clock, end-to-end from `reqwest` send to body read).
5. Computes **avg / p50 / p99** (milliseconds) per endpoint and prints via `println!`
   (also `tracing::info!` for structured logs).

The whole async section runs inside a `tokio` multi-thread runtime built inside the
synchronous `#[test]` fn, exactly as the helpers expect.

### 1.1 Endpoints measured

| # | Method | Path | Path under test | Why |
|---|--------|------|-----------------|-----|
| (a) | `POST` | `/api/authentication` | auth DB-password verify | Exercises bcrypt password verify + session create against the seeded admin. Body: `{"credential":"it-admin","password":"password123"}`. No auth header required. |
| (b) | `GET`  | `/api/cms_assemble_control/data/document` | list read | Exercises the CMS assemble-control list handler + DB read behind the auth middleware. Requires `Authorization: Bearer <token>`. |

Both are timed end-to-end (HTTP request → full response body consumed) so the numbers
reflect real client-visible latency, including connection reuse, middleware, and DB round-trips.

## 2. Baseline numbers

Measured **2026-10-28** on a quiet machine, only the `perf_baseline` test running
(the other `#[ignore]`d scenario tests were filtered out).

| Endpoint | avg (ms) | p50 (ms) | p99 (ms) | max (ms) | samples |
|----------|---------:|---------:|---------:|---------:|--------:|
| `POST /api/authentication` | 1.70 | 1.69 | 2.73 | 2.73 | 50 |
| `GET  /api/cms_assemble_control/data/document` | 1.07 | 1.03 | 1.58 | 1.58 | 50 |

**Run conditions**

- Host: AMD Ryzen 9 7945HX, 32 vCPU visible to the container, 31 GiB RAM,
  Docker Desktop on WSL2 (`6.18.33.1-microsoft-standard-WSL2`).
- Backend: container `oa4rust-cov`, `cargo +1.98.1 test` **debug** build
  (unoptimized; release numbers will be lower).
- PostgreSQL: container `lyp-pg`, PostgreSQL **17.11**, `shared_buffers=128MB`,
  reached over the Docker network (not co-located in the backend process).
- Iterations: 5 warm-up + 50 measured request pairs; no other workload active.
- Rate limiting: the test raises `OA4RUST_AUTH_RATE_LIMIT` /
  `OA4RUST_GENERAL_RATE_LIMIT` to 100000 for its own process. This is required:
  50 logins exceed the production default of 30/minute.

> ⚠️ **Caveat — login is not production bcrypt cost.** The integration fixture
> seeds `it-admin` with a **bcrypt cost 4** hash (`$2b$04$...`), while production
> hashes use a higher cost (typically 12). The 1.70 ms number therefore covers
> HTTP + middleware + DB round-trip + a cheap hash verify; it is a **lower bound**,
> not a production login latency. A production-representative login baseline
> needs a cost-12 fixture or a separate password-verify microbenchmark.

> 🐞 **Defect found by this run (fixed).** The first attempt aborted with
> `429 Too Many Requests` at iteration 10. Root cause: `rate_limit_middleware`
> used the same `ip` key for both the auth bucket and the general bucket, so
> 15 auth + 15 general requests exhausted the 30/minute auth budget. Fixed by
> namespacing the keys (`auth:<ip>` / `general:<ip>`) in
> `crates/shared/src/middleware/rbac.rs`; regression test
> `test_general_traffic_does_not_consume_auth_rate_limit` covers it.

## 3. How to run

```bash
# Compile-check only (safe, does not run anything):
cargo check --test perf_baseline

# Run the baseline on a quiet machine, showing printed output.
# The second `perf_baseline` is a test-name filter: `--ignored` alone also runs
# the 4 ignored scenario tests, which compete for CPU and contaminate p99.
cargo test --test perf_baseline perf_baseline -- --ignored --nocapture
```

Requirements (same as the rest of the integration suite):

- A reachable PostgreSQL server (default `postgres://o2server:password@localhost:5432/postgres`,
  override via `DATABASE_URL`).
- The test creates and drops a temporary database `oa4rust_test_<pid>`; admin connect rights
  are needed for `CREATE/DROP DATABASE`.

### 3.1 Notes / caveats

- The test is `#[ignore]`d, so a plain `cargo test` (the CI gate) will **not** execute it and
  will not require a live database. This keeps Phase 2's green status intact.
- `POST /api/authentication` writes a new session each iteration, so its latency includes a
  DB insert — that is intentional and representative of the real login path.
- `GET /api/cms_assemble_control/data/document` authenticates with the seeded admin token;
  the list may be empty, which is fine for a latency baseline.
- On `WARN` lines, a non-2xx status is printed but does not abort the run, so a single bad
  iteration still contributes a (possibly large) latency sample rather than panicking.
