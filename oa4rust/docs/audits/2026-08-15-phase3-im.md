# OA4RUST Phase 3 — Instant Messaging / Real-Time Feasibility Audit

**Date:** 2026-08-15
**Scope:** READ-ONLY feasibility assessment. No `.rs` or `Cargo.toml` modified; no `cargo build`/`cargo test` run.
**Subject:** Whether the workspace can deliver o2server-equivalent real-time IM (live push, presence, multi-replica fan-out), and what is missing.

---

## 1. Executive summary

The REST/HTTP surface for IM is **already substantial and DB-backed**, but the entire **real-time transport layer is absent**. There is no WebSocket, no SSE, no in-process broadcast/mpsc fan-out, and no connection registry anywhere in the workspace. The o2server IM data model (conversations → single/group, members, messages, per-recipient read status, revoke, favorites, mass) is faithfully modelled in DB tables and served via polling endpoints. To reach o2server parity you must *add* a WS/SSE gateway, a cross-replica connection registry, presence/typing, and wire the existing message-send path into a fan-out + JPush pipeline. None of these exist today.

---

## 2. Current state (evidence-based)

### 2.1 Real-time transport: NOT PRESENT
A precise grep across `crates/*/src` for `WebSocket | axum::extract::ws | ws:: | Sse:: | sse:: | broadcast:: | mpsc:: | BroadcastStream | websocket upgrade` returned **zero matches**. A broad grep that also hit `Event`/`upgrade` was inspected and every hit was a false positive (`assemble` contains "sse"; `upgrade_2021*` are migration endpoints; `Event` is an unrelated entity). The top-level gateway (`src/lib.rs`) is a flat `.merge(...)` of per-crate REST routers — `src/lib.rs:38,59,60,68,91` mount `jpush`, `meeting_assemble_control`, `message_assemble_communicate`, `jpush_assemble_control`, `jpush_core_entity` — with no `ws`/`sse`/`upgrade` handler.

**Conclusion:** there is no live-delivery mechanism of any kind.

### 2.2 IM REST API surface: PRESENT and rich
`crates/message_assemble_communicate/src/routes.rs:44-101` registers the full o2server-style IM API:
- Conversations: `im/conversation` (create), `im/conversation/list/my`, `im/conversation/list/with/person`, `im/conversation/{id}` (single/group), `im/conversation/{id}/group` + `group/quit/self`, `im/conversation/{id}/icon`, `im/conversation/{id}/top/set|cancel` (`routes.rs:53-70`).
- Messages: `im/msg` (send), `im/msg/clear`, `im/msg/revoke/{id}`, `im/msg/list/...`, `im/msg/collection*` (`routes.rs:72-81`).
- Instant / notifications: `instant/currentperson/consumed*`, `instant/list/currentperson/*` (`routes.rs:83-94`) — these are **client-poll** endpoints.
- Mass/broadcast: `mass/*` (`routes.rs:95-99`).
- Legacy send/receive: `send`, `receive/{consume}`, `mark_read`, `consume/list/...`, `unread/count` (`routes.rs:44-47`).

These are all request/response; the client must poll `receive_list` / `instant/list/...` to learn about new messages. This matches o2server's older REST mode but **not** its live WebSocket mode.

### 2.3 IM data model (message-store primitives): PRESENT in DB
The IM tables are accessed via **raw SQL** (not sea_orm entities) inside `crates/message_assemble_communicate/src/lib.rs`:
- `x_message` — message body: `INSERT INTO x_message (id, conversation_id, content, sender, type, create_time)` (`lib.rs:26, 661-674`).
- `x_message_consume` — per-recipient delivery + read state: columns include `consume` (recipient), `read_status`, and `consumed` (boolean). Queried as `WHERE consume = $1 AND consumed = false` (`lib.rs:54`), and `read_status` is returned per consume (`lib.rs:142`). → **read receipts exist at the DB level** (per-recipient), even though there is no live push.
- `x_message_conversation` — conversation: `id, name, type ('single'|'group'), business_id, last_message, create_time, update_time` (`lib.rs:273, 294, 319, 395`). → **single & group conversations exist**.
- `x_message_conversation_member` — group membership: `conversation_id, person_id, role, join_time`, with `DELETE ... WHERE conversation_id = $1 AND person_id = $2` for quit (`lib.rs:421, 450, 466`). → **group membership / roles exist**.
- `x_message_conversation_icon`, `x_message_config` (`lib.rs:482, 643`).

Schema is migrated: `migrations/032_create_assemble_control_tables.sql:1942` (`read_status`), `:1967` (`x_message_conversation_member`); `migrations/038` adds `consumed`, `migrations/039_add_columns_and_fix_boolean.sql:38-42` converts `consumed` TEXT→BOOLEAN.

The legacy `message_core_entity` only models `x_msg_message` (`crates/message_core_entity/src/entities/message.rs:5-14`) with a single `is_read: bool` — this is the older instant-message table, distinct from the new conversation model.

**What already exists (DB-backed):** send/receive, per-recipient read receipts, single + group conversations, group membership/roles/quit, conversation pin/top, message revoke, favorites/collection, mass broadcast, unread counts.

### 2.4 Presence / typing / online-state: NOT PRESENT
Grep for `presence | typing | online | read_receipt | heartbeat | last_active | lastOnline | onlinestate` across `crates` returned **no IM-presence matches** (only unrelated `fallback`/`callback` text). The `meeting` crate (`crates/meeting/src/routes.rs`, `crates/meeting_assemble_control/src/routes.rs`) has `meeting/{id}/checkin` (attendance), not chat presence. **There is no online/offline state, no typing indicator, no heartbeat, anywhere.**

### 2.5 Push notifications (JPush): SCAFFOLDED, NOT WIRED
- Device registry exists: `x_jpush_device (id, user_id, platform, token, create_time)` — `crates/jpush_core_entity/src/entities/jpush_device.rs:4-12`; template table `x_jpush_template`.
- JPush routes expose **device + template CRUD only**: `device/list`, `device/{id}`, `device/create`, `template/list`, `template/{id}` — `crates/jpush/src/routes.rs:13-22`. `jpush_assemble_control` exposes `list_jpushs/get_jpush/create_jpush/save_jpush/delete_jpush` plus `device_check_*`/`device_config_push_type` (`crates/jpush_assemble_control/src/lib.rs:115-352`) — i.e. record management, **no outbound send-to-provider handler**.
- **The message-send path does not call push.** Grep for `jpush | push | notify | broadcast | emit` inside `crates/message_assemble_communicate/src/lib.rs` returned **zero matches** — sending a message merely `INSERT`s into `x_message`/`x_message_consume`; no fan-out to connected clients and no JPush invocation.

### 2.6 Connection / session registry: SINGLE-NODE IN-MEMORY
`crates/shared/src/session.rs:30` holds `sessions: Arc<RwLock<HashMap<String, Session>>>` inside `SessionManager` (auth sessions, `lib.rs:10-33`). This is the only in-process connection-like state and it is **process-local, not shared across replicas, and not for WS connections**. (The only other `tokio::sync` usage is a rate-limiter at `crates/shared/src/rate_limit.rs:20`.) See the parallel distributed-feasibility assessment for cross-replica requirements.

## 3. Gaps vs o2server expectations

| Capability | o2server | oa4rust today | Gap |
|---|---|---|---|
| Live message delivery | WebSocket push | REST polling only (`instant/list/*`, `receive_list`) | **Missing** transport |
| WS connection registry across replicas | Distributed (cluster) | `Arc<RwLock<HashMap>>` single-node (`shared/src/session.rs:30`) | **Missing** cross-replica |
| Presence / online state | Yes | None | **Missing** |
| Typing indicator | Yes | None | **Missing** |
| Per-recipient read receipts | Yes | `x_message_consume.read_status` (DB only) | Present (no live echo) |
| Group chat | Yes | `x_message_conversation` + `_member` | Present (REST) |
| Message revoke / favorites | Yes | `im/msg/revoke`, `im/msg/collection` | Present (REST) |
| Offline message store | Yes (server-held) | `x_message` + `x_message_consume (consumed=false)` persisted | **Present as poll store**; not proactively pushed |
| Mobile push (JPush/Huawei…) | Yes | Device/template registry only; no send path | **Missing** wiring |
| Cross-replica fan-out | Yes (cluster bus) | None | **Missing** (depends on distributed layer) |

## 4. What is needed for full IM

1. **WS/SSE gateway crate** (new, e.g. `im_gateway`): add `axum::extract::ws` (or SSE) route, authenticate via existing `SessionManager`, and on connect register the socket in a connection registry keyed by `person_unique`.
2. **Cross-replica connection registry**: the in-memory map at `shared/src/session.rs:30` must be replaced/augmented by a shared backing store (Redis pub/sub or a consistent-hash shard map — see distributed assessment). Without it, a message sent on replica A cannot reach a client connected to replica B.
3. **Fan-out on send**: modify `im_msg` / `send_message` (`message_assemble_communicate/src/lib.rs:661, 26`) to, after `INSERT`, publish to the registry: deliver to local WS clients for the conversation's members, publish cross-replica via Redis, and trigger JPush for members with no live socket.
4. **Presence & typing**: add `x_im_presence (person, status, last_seen)` + typing events; broadcast via the same registry. No schema or transport exists today.
5. **Push wiring**: implement an outbound JPush send (HTTP to JPush API) invoked from the fan-out step; reuse `x_jpush_device`/`x_jpush_template`. Currently no send handler exists.
6. **Heartbeat / reconnect / ack**: WS ping/pong, client ack → flip `x_message_consume.consumed`/`read_status` to mirror o2server delivery guarantees.

---

## 5. Recommended approach

- **Phase 3a — transport + registry (highest leverage, highest risk):** introduce one `im_gateway` crate with axum WS, backed by a `ConnectionRegistry` trait. Ship a single-node `InMemoryRegistry` first (reusing the `Arc<RwLock<HashMap>>` pattern from `shared/src/session.rs`) to validate end-to-end, then a `RedisRegistry` behind the same trait (depends on the distributed assessment's Redis decision). This decouples IM work from the distributed layer while keeping the integration point explicit.
- **Phase 3b — fan-out + read receipt echo:** extend `im_msg` to publish after insert; echo read-status changes back over WS so sender sees receipts live (DB column already exists).
- **Phase 3c — presence/typing:** add schema + broadcast; low complexity once registry exists.
- **Phase 3d — push:** wire JPush send into fan-out for offline members; device/template tables already exist.
- Reuse existing raw-SQL IM tables; do **not** re-model them as sea_orm entities unless unifying the `message_core_entity` layer.

## 6. Risk register

| # | Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|---|
| R1 | Cross-replica fan-out blocked by missing distributed layer (Redis/pub-sub) | High | High | Define `ConnectionRegistry` trait now; ship in-memory impl, defer Redis to distributed phase (see distributed assessment). |
| R2 | Re-architecting `im_msg` send path regresses existing REST/poll clients | Medium | Medium | Keep REST endpoints; add fan-out as a side-effect after insert; gate behind flag. |
| R3 | No presence/typing schema or transport → must be built from zero | High | Medium | Add `x_im_presence` + typing events in Phase 3c; independent of fan-out. |
| R4 | JPush send unimplemented; offline mobile users get nothing | Medium | Medium | Implement outbound JPush send in Phase 3d reusing `x_jpush_device`. |
| R5 | WS auth/session reuse: current `SessionManager` is single-node in-memory (`shared/src/session.rs:30`) | High | Medium | Share the same distributed backing as the registry; do not multiply session stores. |
| R6 | Backpressure / memory growth with many sockets + broadcast | Medium | High | Bound per-connection buffers; use `tokio::sync::broadcast` per conversation rather than 1:1 mpsc. |
| R7 | o2server client protocol mismatch (binary WS frame format) | Medium | High | Confirm o2server IM wire format before gateway design; may need protocol adapter. |

---

## 7. Conclusion

oa4rust already implements the **IM data model and REST/polling API** needed for o2server-style messaging (conversations, groups, read receipts, revoke, mass — all DB-backed), but it has **zero real-time transport**: no WebSocket/SSE, no broadcast/mpsc fan-out, no connection registry, no presence/typing, and JPush is scaffolded but never invoked from the send path. Full IM therefore requires a new gateway crate with a cross-replica connection registry (dependent on the distributed assessment), a fan-out step on message send, presence/typing schema, and JPush push wiring — all net-new work layered on top of the existing faithful DB schema.
