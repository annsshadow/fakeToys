## BUG-001 — validate_length 按字节计数，误拒合法中文名（已修复）

- **文件**：`oa4rust/backend/crates/shared/src/input_validation.rs:67`（`validate_length`）
- **复现步骤**：
  1. 构造一个 100 个中文字符的文件名字符串（`"中".repeat(100)`，字符数 100，UTF-8 字节数 300）。
  2. 调用 `validate_length("name", &name, 1, 255)`。
  3. 期望：合法（100 字符 ≤ 255）；实际：返回 `TooLong { max: 255, actual: 300 }`（按字节判定）。
  4. 用户可见影响：`POST /api/file/folder/create` 与 `/api/file/folder/update` 对 86–255 字符的中文文件夹名返回 400；数据库列 `file_folder.name VARCHAR(255)` 按字符计数本可容纳。
- **根因**：`validate_length` 用 `value.len()`（UTF-8 字节数），与错误文案 `"must be at most {max} characters"` 及 PostgreSQL `VARCHAR(n)` 的字符计数口径不一致。CJK 字符占 3 字节，导致合法值被误判超长。
- **RED**：新增单测 `validate_length_counts_unicode_characters_not_bytes`；失败信息 `100 个字符应通过 1..=255 校验（按字符而非字节）`，因 `validate_length` 返回 Err(TooLong)——正确原因。
- **修复**：`let len = value.chars().count();`，并补充说明文档注释。
- **验证命令**：
  - `cd oa4rust/backend && cargo test -p shared validate_length_counts_unicode`（RED：FAILED，因 TooLong）
  - 修复后 `cargo test -p shared input_validation::tests`（GREEN：10 passed）
  - 门禁：`cargo check --workspace`、`cargo test --workspace`、`pnpm test -- --run`、`pnpm typecheck`、`pnpm lint`（见任务回执）
- **状态**：已修复、已 GREEN。

## BUG-B — 登录失败错误语义误导为「Session expired」（已修复，RED→GREEN）

来源：t6 真机 E2E（错误凭据探测复现）。

- **现象**：提交错误凭据时前端提示 "Session expired, please login again"，用户仍在 /login 页、并无会话过期发生，语义误导。
- **根因**：前端 SDK 错误映射，非后端状态码。
  - `oa4rust/frontend/packages/sdk/src/api.ts:201-204` 的 `authenticationFailed()` 把所有 401 无条件映射为 `AuthenticationError('Session expired, please login again')`。
  - `request()` 中 401 走 `throw this.authenticationFailed()`；登录 `POST /api/authentication/login` 用 `requireAuth:false`（`session.ts` login()），从不触发 refresh，因此登录失败不可能是会话过期。
  - 后端 `auth/src/lib.rs:238` 对「用户不存在」返回 `AppError::Unauthorized`（401 ExceptionUnauthorized）以防凭据枚举，属合理设计，未改后端。
- **RED**：新增 `oa4rust/frontend/packages/sdk/src/api.login-auth-failure.test.ts`（2 it）：
  - it1：登录端点返回 401 时，断言错误文案含「用户名或密码错误」且不含 "Session expired"、fetch 仅 1 次。
  - it2：受保护资源两次 401（业务+refresh）时，断言仍为 "Session expired"、fetch 2 次且第二次命中 refresh。
  - 命令：`cd oa4rust && pnpm exec vitest run packages/sdk/src/api.login-auth-failure.test.ts` → it1 FAILED：`expected 'Session expired, please login again' not to contain 'Session expired'`（正确原因，非编译错误）；it2 passed。
- **修复（GREEN）**：`api.ts` 新增 `LOGIN_FAILED_MESSAGE='用户名或密码错误，请重新输入'` 与 `SESSION_EXPIRED_MESSAGE`；`authenticationFailed(cause?, path?)` 依据 `isLoginRequest(path)`（/api/authentication/login、/api/authentication、captcha、two-factor 等）选择文案；`request()` 传入 path。upload/uploadBytes/stream/XHR 通道保持会话过期语义不变。
- **验证命令**：
  - RED：`pnpm exec vitest run packages/sdk/src/api.login-auth-failure.test.ts`（修复前 it1 FAILED）
  - GREEN：同上命令 2 passed；`pnpm exec vitest run packages/sdk/src` → 28 files/181 tests 全绿
  - 门禁：`pnpm test -- --run`（181 files/1721 tests）、`pnpm typecheck`（6 项目）、`cargo test -p auth`（103 passed/3 ignored + 集成 1 passed）、`pnpm exec biome check <改动两文件>`（Checked 2 files, No fixes applied）
- **状态**：已修复、已 GREEN。

### BUG-B 关联调查：E2E「HTTP 200 + type:error，无 Set-Cookie，种子/admin 账号都登不进」

按 captain 三类判定要求查证，结论：**①环境/配置 + ②凭证问题，非③产品代码 bug**，故无 RED→GREEN。

- **现象**：直接 `POST /oa4rust-api/api/authentication` 返回 HTTP 200 + `{"type":"error","message":"unauthorized"/"invalid credentials"}`，无 Set-Cookie；种子/admin/DB 账号均如此，locked=f、failed_attempts=0。
- **代码查证**：
  - `auth/src/lib.rs` login handler：用户不存在 → `AppError::Unauthorized`（401）；locked=true 或 `verify_password_async` 返回 false → `Json(ActionResult::error("invalid credentials"))`（HTTP 200 + type:error，无 Set-Cookie）；仅成功路径才 `create_session` + `with_session_cookie`。E2E 所见正是失败分支，非中间件 401。
  - **change_password_time 线索排除（死路）**：`let password_expired = change_password_time.is_none()` 只写入 `LoginResponse.password_expired` 响应字段，位于口令校验**之后**，不影响会话签发/Set-Cookie；前端全仓无 `password_expired` 消费。不是登录失败根因。
  - **种子账号 hash 是占位值**：`backend/migrations/002_seed_auth_data.sql:4` 的 admin 密码 hash 为 `$2b$12$dummy.hash.for.testing`（占位、非真实 bcrypt 摘要，且无 `{bcrypt}` 前缀，即使开启 legacy 兼容也无法验证通过）；`098_seed_org_auth_route_test_data.sql:24` 亦为假 hash。此类种子账号设计上不可登录。
  - **遗留 hash 兼容默认关闭**：`auth/src/password.rs` `legacy_compat_from_env()` 仅在 `AUTH_LEGACY_COMPAT=true` 时开启 MD5/DES 兼容；`verify_password` 对非 `{bcrypt}` 前缀且未开兼容的 hash 直接 `return false`（2026-10 安全审计有意 fail-closed）。若测试库存量账号是旧格式 hash 而未设该环境变量，正确口令也会校验失败。
- **判定**：①环境/配置 + ②凭证问题。建议 E2E runner 用**真实 bcrypt hash 的账号**登录，或按其部署实际设置确认 `AUTH_LEGACY_COMPAT` 与账号密码一致；真值自读自验、不入库不回显。产品代码无对应 bug，未改动后端。
- **E2E 复验建议**：BUG-B 修复后，e2e-runner 应把登录失败断言从脆弱的文本/位置选择器改回**语义选择器**——断言错误提示含「用户名或密码错误」且不含 "Session expired"；会话过期语义另用受保护接口 401 场景验证。
## BUG-D — 组织通讯录 collect 参数提前 await 导致 Promise.catch 崩溃（已修复，RED→GREEN）

来源：t6 真机 E2E 用例 #10/#11（两 project 共 4 条失败）。

- **文件**：`oa4rust/frontend/apps/desktop/src/views/OrgDirectoryApp.vue`
- **现象**：点击「一键查询」后，各分类接口调用抛 `TypeError: e.catch is not a function`，失败接口无「查询失败」提示，出现未处理 Promise rejected。
- **根因**：line 122 的 `const s = <T>(p: Promise<T>): Promise<T | null> => p.catch(() => null)` 期望收到 Promise；但 `collect(label, p)` 内部用 `s(p)` 兜底，而全文件 40+ 处调用写成 `collect('label', await api.get/post(...))`——`await` 在传参时已把 Promise 解析成普通值，`s` 对其调用 `.catch` 即崩溃；若接口 reject，异常在进入 `collect` 前抛出，同样拿不到兜底文案。
- **RED**：新增 `oa4rust/frontend/apps/desktop/src/views/OrgDirectoryApp.awaitPosition.contract.test.ts`（4 例，源码级文本契约 + new Function 提取 `s` 执行）：断言 collect 参数内无 `await api.get/post`、第二参数直接为 `api.get/post(...)`、普通值经 `s` 不抛 TypeError、reject→null。修复前 3 failed/1 passed，失败均为正确业务原因（非编译错）。
- **修复（GREEN）**：批量移除 collect 参数里 `api.get/post` 前的 `await`（共 53 处，含 `/api/unitduty/` 前缀），保留 `loadPersonFilter`、`manage()`、`orgAuth()` 等非 collect 上下文的 `await`；`s` 放宽为 `const s = <T>(p: Promise<T> | T): Promise<T | null> => Promise.resolve(p).catch(() => null)` 作防御。契约 4/4 passed。
- **验证**：`pnpm --filter @oa4rust/desktop exec vitest run src/views/OrgDirectoryApp.awaitPosition.contract.test.ts`（4 passed）；门禁 desktop typecheck / build / biome / git diff --check 见任务回执。
- **状态**：已修复、已 GREEN。
