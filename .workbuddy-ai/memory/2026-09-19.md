### 2. 修 `CI / unit-tests`（提交 `aadddf5c`）——本日最大发现

**先说结论性事实**：`unit-tests` 在本仓库**从未成功过一次**。
查 `actions/runs?branch=...` 全历史共 19 次 CI run，success 数 = **0**；
单独筛 `unit-tests` job，历史上全是 `failure` / `cancelled`。

**用的是"差异对照法"定位根因**：

| job | 命令 | 结果 |
|---|---|---|
| `unit-tests` | `cargo test --workspace --lib` | ❌ exit **101** |
| `integration-tests` | `cargo test -p parity --lib` + `cargo test --test integration_runner` | ✅ 通过 |

两者都包含 parity 测试，为何一个挂一个过？因为 `--workspace --lib` **多**编译并
运行了 `oa4rust` facade 自己的 lib 测试，其中只有一个用例：

`oa4rust/src/lib.rs::cors_guard::create_app_builds_without_panic`

而 `create_app` 把 **80 个 crate 的路由链式 `.merge()`** 成一个巨型 axum Router。

**关键证据是仓库自己的注释**（`oa4rust/.cargo/config.toml`）：
> `create_app` 将 80 个 crate 路由链式 `.merge()` 为一个巨型 axum Router。
> 该构造在默认约 1–2MB 的线程栈上会栈溢出（已确认是栈大小需求，而非无限递归——
> 64MB 栈可确定性通过）。

而该文件里唯一的缓解手段是：
```toml
[target.x86_64-pc-windows-msvc]
rustflags = ["-C", "link-args=/STACK:67108864"]
```
**只对 Windows 主线程生效。** Linux/CI 上 `#[tokio::test]` 的 worker 线程仍是默认栈
（约 2MB）→ 栈溢出 → panic → **exit code 101**（与 annotation 完全吻合）。
`.github/workflows/` 里**没有** `RUST_MIN_STACK`；`integration-tests` 之所以过，
是因为它从不构造那个巨型合并 Router（`integration_runner` 的用例还全部 `#[ignore]`）。
另外注释里提到的"与集成测试的 64MB worker 栈一致"——**该 64MB 设置在仓库里根本不存在**，
是个失效的引用。

**本机验证（决定性）**：
```
# 修复前：RUST_MIN_STACK=262144 跑 cors_guard
thread 'cors_guard::create_app_builds_without_panic' has overflowed its stack   ← 复现！
# 修复后：同样的 262144
test cors_guard::create_app_builds_without_panic ... ok. 1 passed
```
（在 1MB/2MB/4MB 下修复前后都过——因为 Windows 二进制有 `/STACK:67108864`，
`RUST_MIN_STACK` 覆盖不了主线程。必须压到 256KB 才能把 Windows 上的这个缺陷暴露出来，
这也解释了为什么这个 bug 能潜伏这么久。）

**修复**：不再依赖平台链接参数，改为在显式 `stack_size(64MB)` 的线程上构造 Router：
```rust
const CREATE_APP_STACK_SIZE: usize = 64 * 1024 * 1024;
let handle = std::thread::Builder::new()
    .name("create_app_build".to_string())
    .stack_size(CREATE_APP_STACK_SIZE)
    .spawn(move || {
        tokio::runtime::Builder::new_current_thread()
            .enable_all().build().expect("...")
            .block_on(async move { create_app(pool, session_manager, rate_limiter).await
                .expect("unified create_app must build without panic") })
    }).expect("spawn create_app build thread");
let _app = handle.join().expect("create_app must build without panic");
```

**CI 对齐的干净库上全量验证**：
`cargo test --workspace --lib -j 1 --no-fail-fast` → 97 个目标，
**7621 passed / 0 failed / 136 ignored，EXIT=0**。

### 4. 环境/工具教训

- **`cargo build --bin` 最后一步可能失败**：`failed to remove target/debug/oa4rust.exe:
  拒绝访问 (os error 5)`——有**残留的 oa4rust.exe 进程**占着文件（本次 PID 5248）。
  `taskkill //F` 在 Git Bash 下参数会被转义坏（报"无效参数/选项 - '//F'"），
  要用 PowerShell `Stop-Process -Id <pid> -Force`。杀掉后重新 `cargo build` 25s 完成。
- **`cargo test` 的 debug test profile 编译非常久**（`parity` 有 94336 行生成测试，
  4385 条 warning），本次 `--workspace --lib` 全量编译+运行约 **36 分钟**。
- **git ref 被并发进程清空（本会话第 15、16 次）**：这次更狠——`.git/refs/heads/feat/`
  整个目录被删 + `packed-refs` 被回退，导致 `git rev-parse HEAD` 直接报
  "does not have any commits yet"。
  恢复方法（已验证有效）：
  ```bash
  git reflog -5                    # 找游离提交 SHA
  git cat-file -t <sha>            # 确认对象存在
  git merge-base --is-ancestor <旧sha> <新sha>   # 确认是超集
  mkdir -p .git/refs/heads/feat && git rev-parse <sha> > .git/refs/heads/feat/oa4rust-mobile
  # 同时用 python 改 .git/packed-refs 对应行（sed 里嵌 $(...) 会失效）
  git push origin feat/oa4rust-mobile
  ```

### 6. 方法论突破：不再靠猜，用 Docker 起真 Linux 复现

Windows 上无法复现 CI 的任何平台差异。改用本机已有的
**`rust:1.96.0-bookworm` 镜像**（16 核）在容器里跑真 Linux 构建：

- 源码打包进 volume 时要 **`tar --exclude=target --exclude=target-ci`**，
  否则会去拷 134GB 的 Windows `target/`（第一次就踩了，`cp -a` 卡住）。
  打包后仅 26MB。
- `CARGO_TARGET_DIR=/target` 指向**命名 volume**（避开 Windows 文件系统性能）。
- 编译：`cargo test --workspace --lib --no-run` → **EXIT=0，97 个测试目标全部编译通过**。
  → 顺带否定了"Linux 上 `#[cfg(test)]` 编译失败"的假设
  （注意 `quality` job 的 `cargo check --workspace` **不含 `--all-targets`**，
  本身不校验测试代码，这是个 CI 盲区，但本次不是失败原因）。
- 容器磁盘 939GB 空闲 → **彻底否定"runner 磁盘耗尽"假设**（那是我此前的头号猜想）。

### 7. 真正根因（已实锤）：`shared` 的测试硬依赖真实 Redis

在容器里跑 `cargo test --workspace --lib --no-fail-fast` → **EXIT=101 复现成功**。
逐目标比对，唯一差异在 `shared`：

| 环境 | `shared` 结果 |
|---|---|
| Windows 本机 | `133 passed; 0 failed` ✅ |
| Linux 容器（无 Redis） | `132 passed; 1 failed` ❌ |

失败用例：**`messaging::messaging_tests::test_redis_pubsub_bus_is_available`**
（`crates/shared/src/messaging.rs`）。

```rust
let pool = RedisPool::from_url("redis://127.0.0.1:6379").await;
let bus2 = RedisPubSubBus::<String>::new(pool.ok());
assert!(bus2.is_available());   // ← 要求真能连上 Redis
```

**为什么本机能过、CI 必挂** —— 本机恰好有一个 `oa4rust-redis` 容器
（`redis:latest`，Up 45 小时）监听 6379，`pool.ok()` 拿到 `Some` 断言成立；
CI 的 `unit-tests` job 的 `services:` **只有 postgres，没有 redis**，
连接失败 → `pool.ok()` = `None` → 断言失败 → panic → **exit code 101**。

对照实验（同一镜像、同一代码，只差 Redis）：
- 无 Redis：`132 passed; 1 failed`，**EXIT=101**
- 有 Redis（`apt-get install redis-server` 后 `redis-server --daemonize yes`）：
  `5 passed; 0 failed`，**EXIT_A=0**

这解释了为何 `unit-tests` 历史上 19 次 CI **从未成功过一次**，
而 `integration-tests`（只跑 `-p parity --lib` + `u2_probe`，不含 `shared` 的
单测）一直绿。也和"修了 `create_app` 栈问题后耗时从 11.5min 涨到 13.8min"
吻合——修完栈问题后跑得更远，终于撞上这个断言。
