### 2. 修 `CI / unit-tests`（提交 `aadddf5c`）——本日最大发现

**先说结论性事实**：`unit-tests` 在本仓库**从未成功过一次**。
查 `actions/runs?branch=...` 全历史共 19 次 CI run，success 数 = **0**；
单独筛 `unit-tests` job，历史上全是 `failure` / `cancelled`。

**用的是"差异对照法"定位根因**：

| job | 命令 | 结果 |
|---|---|---|
| `unit-tests` | `cargo test --workspace --lib` | ❌ exit **101** |
| `integration-tests` | `cargo test -p parity --lib` + `cargo test --test integration_runner` | ✅ 通过 |

两者都包含 parity 测试，为何一个挂一个过？因为 `--workspace --lib` **多**编译并
运行了 `oa4rust` facade 自己的 lib 测试，其中只有一个用例：

`oa4rust/src/lib.rs::cors_guard::create_app_builds_without_panic`

而 `create_app` 把 **80 个 crate 的路由链式 `.merge()`** 成一个巨型 axum Router。

**关键证据是仓库自己的注释**（`oa4rust/.cargo/config.toml`）：
> `create_app` 将 80 个 crate 路由链式 `.merge()` 为一个巨型 axum Router。
> 该构造在默认约 1–2MB 的线程栈上会栈溢出（已确认是栈大小需求，而非无限递归——
> 64MB 栈可确定性通过）。

而该文件里唯一的缓解手段是：
```toml
[target.x86_64-pc-windows-msvc]
rustflags = ["-C", "link-args=/STACK:67108864"]
```
**只对 Windows 主线程生效。** Linux/CI 上 `#[tokio::test]` 的 worker 线程仍是默认栈
（约 2MB）→ 栈溢出 → panic → **exit code 101**（与 annotation 完全吻合）。
`.github/workflows/` 里**没有** `RUST_MIN_STACK`；`integration-tests` 之所以过，
是因为它从不构造那个巨型合并 Router（`integration_runner` 的用例还全部 `#[ignore]`）。
另外注释里提到的"与集成测试的 64MB worker 栈一致"——**该 64MB 设置在仓库里根本不存在**，
是个失效的引用。

**本机验证（决定性）**：
```
# 修复前：RUST_MIN_STACK=262144 跑 cors_guard
thread 'cors_guard::create_app_builds_without_panic' has overflowed its stack   ← 复现！
# 修复后：同样的 262144
test cors_guard::create_app_builds_without_panic ... ok. 1 passed
```
（在 1MB/2MB/4MB 下修复前后都过——因为 Windows 二进制有 `/STACK:67108864`，
`RUST_MIN_STACK` 覆盖不了主线程。必须压到 256KB 才能把 Windows 上的这个缺陷暴露出来，
这也解释了为什么这个 bug 能潜伏这么久。）

**修复**：不再依赖平台链接参数，改为在显式 `stack_size(64MB)` 的线程上构造 Router：
```rust
const CREATE_APP_STACK_SIZE: usize = 64 * 1024 * 1024;
let handle = std::thread::Builder::new()
    .name("create_app_build".to_string())
    .stack_size(CREATE_APP_STACK_SIZE)
    .spawn(move || {
        tokio::runtime::Builder::new_current_thread()
            .enable_all().build().expect("...")
            .block_on(async move { create_app(pool, session_manager, rate_limiter).await
                .expect("unified create_app must build without panic") })
    }).expect("spawn create_app build thread");
let _app = handle.join().expect("create_app must build without panic");
```

**CI 对齐的干净库上全量验证**：
`cargo test --workspace --lib -j 1 --no-fail-fast` → 97 个目标，
**7621 passed / 0 failed / 136 ignored，EXIT=0**。

## 第三场：清除非 Option 读可空列的存量隐患（commit `bc29795d`）

用户原话：「把那些"非 Option 读可空列"的存量隐患也一起清掉」

### 1. 问题本质

`tokio_postgres::Row::get::<_, String>("col")` 在列为 **NULL 时 panic**
（`Error::UnexpectedNull`）。仓库里散落大量这种写法。危险在于：
**空表不触发** —— 只有真正取到含 NULL 的行才炸，所以测试常年绿的，
生产一跑就 500。

### 2. 方法论（本轮的核心价值：不拍脑袋，用 schema 精确判定）

粗筛会严重虚高。**必须"从 SQL 反解表名 + 用真实 schema 判可空"**：

1. 从数据库导出全量列定义：`5028 列 / 4402 可空`
   （`information_schema.columns`，落盘 `.tmp_null/cols_nullable.txt`，
   格式 `table|column|type|is_nullable`）。
2. 用正则把源码里**相邻拼接的字符串字面量合并成完整 SQL**，
   再从每条 SQL 的 `FROM/JOIN` 提取表名。
3. 对每个 `row.get("col")` 调用点，找"覆盖它或之前最近的 SQL 块"，
   用 `(table, column)` 精确判可空。

**效果**：初筛 6406 处 → 精确到表后 4877 处（**排除了 1500+ 误伤**）。
最典型误伤是 `id`：它在 371 个表里只有 108 个可空，
粗筛（"任一表可空即算可空"）会把它全判成危险。

### 3. 二次过滤（排除已安全写法）

即使命中可空列，也要看**读法本身是否安全**：
- `let x: Option<String> = row.get("col")` —— 安全（有类型注解）
- `...unwrap_or_default()` / `unwrap_or(...)` —— 安全
- 返回类型是 `Option<T>` —— 安全

过滤后：**确凿未修 4628 处**。

### 4. 修复语义（用户选定）

统一用仓库既有模式，与已修的 1486 处保持一致：
```rust
row.get::<_, Option<String>>("col").unwrap_or_default()   // NULL -> ""
row.get::<_, Option<bool>>("col").unwrap_or(false)        // NULL -> false
row.get::<_, Option<i64>>("col").unwrap_or(0)             // NULL -> 0
```

> 备选语义是"省略字段"（`shared/src/response.rs::row_to_json` 与
> `ActionResult` 注释里的 o2server/Gson 约定）。用户选了"沿用已有模式"，
> 理由是改动最小、风险最低、与 1486 处历史修复一致。

### 5. 实际改动

**77 文件 / 4262 处**。覆盖 7 种形态（见 commit message）。

### 6. ⚠️ 中途踩的大坑（务必记住）

我一开始误判为"timestamp 列不能用 `Option<String>` 读"，
回滚了 192 处 —— **结果失败数一个没少**。

**真因：容器连不上数据库。** `shared::testing::test_pool()` 硬连

### 2. 🎯 真凶找到了：`.git/packed-refs` 被写成 CRLF

**这解释了本会话 30+ 次"ref 凭空消失"的全部谜团。**

现象：
```
warning: ignoring ref with broken name refs/heads/main?
warning: ignoring ref with broken name refs/heads/feat/oa4rust-mobile?
... (所有分支都带一个 ?)
```

一开始以为是文件被删，其实 **`?` 是 Git 对 `\r` 的渲染**。
原始字节检查证实：
```python
raw = open('.git/packed-refs','rb').read()
# b'# pack-refs with: peeled fully-peeled sorted \r\n'
# b'7f041f24... refs/heads/docs/plans-status-audit\r\n'
```
**每行都是 CRLF** → Git 读到的 ref 名是 `refs/heads/main\r` →
名字非法 → 该 ref 被忽略 → 表现为"分支不存在 / 当前分支没有提交"。

**根因**：仓库 `core.autocrlf=true`，而 `.git/packed-refs` 本不该做
换行转换。某个 Windows 侧工具（IDE 的 git 集成？同步工具？）
把它按文本文件重写成了 CRLF。**这个进程仍在活跃**，
所以修好之后还可能再次被污染。

**修复（一条命令）**：
```bash
python -c "
p='.git/packed-refs'
raw=open(p,'rb').read()
open(p,'wb').write(raw.replace(b'\r\n',b'\n').replace(b'\r',b'\n'))
"
```
修完 `git branch -a` 立刻恢复，所有分支可见。

**诊断口诀**：Git 报 "broken name" + 名字尾部有 `?`
→ **先去看 packed-refs 的行尾**，别急着删 ref / 重建仓库。

### 3. 本会话"ref 消失"的完整因果链（复盘）

之前我一直在用"直接写 loose ref + 改 packed-refs"的方式恢复，
但当时**没意识到 packed-refs 本身是坏的** —— 我用 Python 改它时
用的是 `open(p,'w')` 文本模式，在 Windows 上默认把 `\n` 写成 `\r\n`，
**等于我自己也在持续制造这个问题**。

> 教训：**改 `.git/` 下的任何文件，一律用二进制模式（`'rb'`/`'wb'`）**，
> 绝不走文本模式，否则 Windows 的换行转换会把元数据写坏。
