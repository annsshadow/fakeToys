## ⚠️ 事故与修复记录（同日）— 重要教训

### 事故经过

删除污染文件 `ai/docs/FINAL_SUMMARY.md` 时发生连锁问题：

1. `git rm` 命令执行中被系统 SIGTERM 超时中断，导致误删 `ai/` 下 **288 个文件**（而非 1 个）。
   - 修复：`git checkout -- ai/` 全部恢复，无数据损失。
2. 期间**有外部进程（IDE git 集成）并发操作 git**，导致：
   - `.git/index.lock` 残留
   - 提交 `07def09f` 变为**游离提交**（不挂在任何分支）
   - 分支 `feat/oa4rust-mobile` 被回退到 **379 个提交之前**的 `5456bcc5`
   - 暂存区被塞入 32,751 个条目

### 关键根因：ref 存储位置

`refs/heads/` 目录**完全为空**——所有分支都打包在 `.git/packed-refs` 中。

因此修复时 `git update-ref` 写入的 loose ref 会被立即删除（或未生效），必须**同时改 packed-refs**：

- loose ref 路径：`.git/refs/heads/feat/oa4rust-mobile`（**需先 `mkdir -p` 父目录**，且必须写入**完整 40 位 SHA**，短 SHA 会导致 `rev-parse HEAD` 报 ambiguous）
- packed-refs 需同步 sed 替换

### 有效修复步骤（复用价值高）

```bash
git read-tree HEAD                              # 索引重置到 HEAD（不动工作区）
mkdir -p .git/refs/heads/feat
printf '%s\n' "$(git rev-parse <目标SHA>)" > .git/refs/heads/feat/oa4rust-mobile
sed -i 's|^<旧SHA> refs/heads/feat/oa4rust-mobile$|<新SHA> refs/heads/feat/oa4rust-mobile|' .git/packed-refs
```

CAS 安全写入（推荐，防并发）：`git update-ref <ref> <新值> <期望旧值>`

### 最终状态

- 分支恢复至 `07def09f`（领先 main **384 提交**，ahead origin 1）
- 污染文件已删除，全库 null 字节扫描**清零**
- 暂存区 0 条目

### 遗留说明

`git diff` 显示 198 个文件"已修改"，经 `git diff --ignore-cr-at-eol` 验证**内容差异为 0**，纯 CRLF/LF 行尾符差异（Windows `core.autocrlf=true` 正常行为）。**不要误当数据损坏处理**。

### 教训

1. **命令被 SIGTERM 中断后，必须复核实际影响范围**，不能凭命令意图判断结果。
2. **本仓库存在外部进程并发操作 git**，执行写操作前应确认，且优先用 CAS（`update-ref` 带旧值）。
3. **大仓库中避免 `git rm` / `git status` 全量操作**——易超时且输出巨大。
4. 删除文件用 `rm -f <单文件>` + `git status --short` 核对数量，比 `git rm` 更安全。

```
parity__hotpic__get_by_id                          → lib.rs:76:39

```

**关键推理**：此前（`9cb9b676`）我已给该 SQL 加了 `create_time::text`，为什么还失败？

答案：**`::text` 只解决"类型"问题，没解决"NULL"问题。**

- `migrations/029` 定义 `x_hotpic.create_time TIMESTAMP`（**无默认值**）
- `migrations/053` 的 seed 行：
  ```sql
  INSERT INTO x_hotpic (id, application, info_id, title, image_url, creator, deleted_at)
  VALUES ('test-id', 'test', 'test-id', 'Test Hotpic', '', 'system', NULL)
  ```
  **列清单里没有 `create_time`** → 该列为 **NULL**
- handler 写的是 `Value::String(row.get("create_time"))` → 推断为 `String`
- **`String` 不接受 NULL** → panic

即：`create_time::text` 后类型确实是 `text`（正确），但**值仍是 NULL**，
而 `row.get::<String>` 拿到 NULL 就报 `error deserializing`。

**本地 PostgreSQL 精确复现**（这是本次能快速定位的关键）：
```sql
CREATE TABLE _hotpic_probe (..., create_time TIMESTAMP);
INSERT INTO _hotpic_probe (id,title,image_url,creator) VALUES ('test-id','Test Hotpic','','system');
SELECT id, title, image_url, creator, create_time::text AS create_time FROM _hotpic_probe WHERE id='test-id';
SELECT pg_typeof(create_time::text), create_time IS NULL FROM _hotpic_probe;  -- text | t  ← 决定性证据
```

**修复**：按同文件 `image_url` 的既有惯例改为
```rust
Value::String(row.get::<_, Option<String>>("create_time").unwrap_or_default())
```
两处（`get_by_id` + `list_by_application_and_info_id`）一并修。

### 为什么之前 parity 测试能过、本地也过，只有 CI 挂

- parity 用的 `seed_fixtures.sql` **插入了 create_time** → 非 NULL → 不触发
- 本地库的 `x_hotpic.create_time` 是 **text** 类型（历史迁移不同），且有值
- 只有 CI 的**干净迁移历史** + `053` 的 NULL 行同时满足，才能触发

**教训（重要）**：`::text` 与 `Option<T>` 是**两个独立问题**。
- 非空但类型不匹配 → 加 `::text`
- 可空列 → 必须用 `Option<T>`
排查此类 `error deserializing column` 时，**先用 `pg_typeof()` + `IS NULL` 验证**，
不要只盯着类型。

### 2. processplatform_assemble_designer：parity get_flow

- 报错：`error retrieving column create_time: error deserializing column 6`（lib.rs:106）

### 教训（补充前一轮）

1. **seed 数据要做"全列审查"**：只要 handler 存在非 Option 读，seed 就必须为
   **每一列**提供非 NULL 值。补 seed 时必须对着 `SELECT` 的列清单逐列核对，
   而不是只修报错那一列。
2. **探针式测试对数据极度敏感**：`route_exists` 类测试不 seed、断言弱，
   却会被**其它迁移引入的数据**引爆。新增 seed 迁移时必须评估
   "这张表还有谁在读"。
3. **本地 schema 可能落后于迁移历史**：判断类型不匹配时，
   应查 `migrations/` 里的 `CREATE TABLE` 定义，而不是只看本地 `\d`。
   本地 `\d` 显示 text ≠ CI 是 text。
4. `ORDER BY create_time` 在 `SELECT ... AS create_time` 时**合法**
   （PG 允许 ORDER BY 引用输出列别名），已验证。

## 🚀 重大突破：本机现在可以完整编译并运行 Rust 测试了

**此前记忆里"本机无法编译 Rust"的结论已被推翻。** 根因有两层，都修好了：

### 层 1：`link` 命令被 GNU coreutils 抢占

Git Bash 的 `/usr/bin/link`（GNU coreutils 的硬链接工具）在 PATH 中**优先于**
MSVC 的 `link.exe`，于是 cargo 报：

```
error: linking with `link.exe` failed: exit code: 1
  = note: link: extra operand '....rcgu.o'
          Try 'link --help' for more information.
```

（注意错误信息里写的是 `link.exe`，但实际执行的是 `/usr/bin/link` —— 极具误导性）

### 层 2：即使找到 MSVC link.exe，仍缺 `LIB`

只把 MSVC 的 bin 目录前置，会换个错误：

```
LINK : fatal error LNK1181: cannot open input file 'kernel32.lib'
```

因为 MSVC 依赖 `LIB` 环境变量找 `.lib`。

### 解决方案（已固化为 `scripts/rust-env.sh`）

```bash
MSVC_DIR="/c/Program Files/Microsoft Visual Studio/2022/Community/VC/Tools/MSVC/14.44.35207"
SDK_LIB="/c/Program Files (x86)/Windows Kits/10/Lib/10.0.26100.0"

export PATH="$MSVC_DIR/bin/Hostx64/x64:$PATH"
export LIB="$(cygpath -w "$MSVC_DIR/lib/x64");$(cygpath -w "$SDK_LIB/ucrt/x64");$(cygpath -w "$SDK_LIB/um/x64")"
```

用法：`source scripts/rust-env.sh`（**必须 source**，否则 export 不生效）

**验证结果**：
- `cargo check -p organization_assemble_control` → Finished in 50s ✅
- `cargo test -p organization_assemble_control --lib identity_list` → 12 passed ✅

### 由此得到的关键能力：**本地真实复现 CI**

`shared/src/testing.rs::test_pool()` **硬编码 `dbname("oa4rust")`，无视 `DATABASE_URL`**！
（这是本轮踩的坑：我先用 `DATABASE_URL=...oa4rust_ciprobe` 跑测试，
结果它连的还是 `oa4rust` 库，而那个库早被我手工改过 → 测试"通过"是假象。）

**严谨的复现流程**（已脚本化在 `.tmp_ci/`）：
1. 新建库 `oa4rust_ciprobe`，按文件名顺序执行 `migrations/*.sql`（跳过 `_rollback`）
   - 注意：直接 psql 逐条执行会有 2 条失败很正常
     （`037_add_deleted_at.sql` 引用 Rust 运行器才建的 `schema_migrations`；
      `051` 依赖 `037` 加的列）—— CI 里由 `cargo run --bin oa4rust -- --migrate-only` 正确处理
2. `DROP DATABASE oa4rust; CREATE DATABASE oa4rust TEMPLATE oa4rust_ciprobe;`
   → 让硬编码的 `test_pool()` 连到干净库
3. `source scripts/rust-env.sh && DATABASE_DIALECT=postgres cargo test --workspace --lib`
4. 原库已备份到 `.tmp_ci/oa4rust_backup_*.sql`

**这才是判断"CI 是否会绿"的可靠方法** —— 比推一次跑一次快得多，且能看到全部失败
（不受 `cargo test` fail-fast 影响）。

### 本地复现环境的两个坑（都已踩过并解决）

1. **手工跑迁移会漏掉 2 条**：
   - `037_add_deleted_at.sql` 第 4 行就 `ALTER TABLE "schema_migrations"`，
     而该表由 Rust 运行器创建。手工 psql 执行 → 报"关系不存在" →
     **整条 254 行的迁移在事务中回滚** → `x_mind.deleted_at` 等一批列全部缺失！
   - `051_seed_component_test_data.sql` 依赖 `037` 加的列，连带失败。
   - 症状：`mind_assemble_control` 的 `real_mind_get_and_share_records` 报
     `left: 500, right: 200`；手动跑 SQL 得到
     `错误: 字段 "deleted_at" 不存在`。
   - **解法**（`.tmp_ci/fix_repro.sh`）：先手工建 `schema_migrations`
     表（与 Rust 运行器同构），再补跑 `037` 和 `051`。
   - ⚠️ 这类失败是**复现环境的假阳性**，不是真实 CI 问题——判断前先核对该列
     在 `migrations/` 里有没有对应 ALTER。

2. **`cargo test -j N`（并行）会因文件锁失败**：
   - `fatal error C1083: ... Permission denied`（cl.exe 写 .o 冲突）
   - `error: failed to remove ...rcgu.o: 拒绝访问。 (os error 5)`
   - **必须 `-j 1`**。首次全量编译约 **56 分钟**，增量重跑约 **1 分钟**。
   - 偶尔需要 `rm target/debug/deps/<pkg>-*.rcgu.o` 清掉被占用的中间文件。

3. **`cargo test` 默认 fail-fast**：想一次看全部失败，必须加 `--no-fail-fast`。
   否则一个包挂了，后面的包根本不会跑（会掩盖后续失败）。
